# 회원 파일 저장(S3)

EKS에서 회원이 올린 PDF 원본과 발행 사본을 어디에 두고, api·worker가 어떤 권한으로 쓰는지와 만들기·확인·지우기 순서다([#276](https://github.com/JminAILab/CatchU/issues/276), 구성은 [#389](https://github.com/JminAILab/CatchU/issues/389) 「PDF 저장(S3)」 결정). 단계·승인 지점·처음 준비는 [README.md](README.md)를 따른다.

파일을 api Pod의 빈 볼륨(`/tmp`)에 두면 Pod가 바뀔 때마다(재배포, 노드 교체, 볼륨 크기 상한 초과) 비어서 모든 회원의 파일이 없어진다. 그래서 EKS에서는 S3 버킷에 둔다. [11/18 2단계](https://github.com/JminAILab/CatchU/issues/276#issuecomment-6970235553)에서 실제 api·worker Pod의 허용·거부와 없는 파일 응답을 확인했다. 아래는 생성·재확인 절차다.

## 구성

| 무엇 | 정한 곳 | 내용 |
|---|---|---|
| 버킷 `catchu-prod-files` | [`scripts/create-s3.sh`](scripts/create-s3.sh) | 서울, 공개 차단 4개, 기본 암호화(AES256), ACL 끔. 지운 파일이 남지 않게 버전 관리는 켜지 않는다. 버킷 정책·CORS는 두지 않는다(미리 서명한 주소를 쓰지 않는다). 키는 `members/<회원 UUID>/…`뿐이다([api 파일 저장](../../api/docs/file-storage.md)) |
| S3 게이트웨이 엔드포인트 `catchu-s3` | 같은 스크립트 | 프라이빗 서브넷 경로표에 붙인다. 요금이 없고 노드·Pod의 S3 연결이 NAT 대신 이 경로로 간다. 정책은 기본값이다(노드의 이미지 받기·패키지 저장소도 S3를 쓴다) |
| api 역할 | [`cluster.yaml`](cluster.yaml)의 Pod Identity 연결(namespace `catchu`, 서비스 계정 `api`) | 버킷의 `members/` 아래 올리기·읽기·삭제와 `members/` 접두어 목록. 복사는 읽기+올리기다. 개발 서버 역할과 같은 권한이다 |
| worker 역할 | 같은 곳(서비스 계정 `worker`) | `members/` 아래 읽기만. 올리기·삭제·목록은 없다 |
| 서비스 계정 `api`·`worker` | [`k8s/namespace.yaml`](k8s/namespace.yaml) | 역할이 붙는 이름이다. 쿠버네티스 API 토큰은 탑재하지 않는다. web·migration·일회 Pod는 `default` 계정이라 AWS 권한이 없다 |
| 연결 허용 | [`k8s/network-policy.yaml`](k8s/network-policy.yaml) | api·worker → `169.254.170.23:80`(역할의 임시 자격을 주는 같은 노드의 EKS Pod Identity 에이전트), worker → 서울 S3 대역 443. api는 바깥 443이 이미 열려 있다. 노드 메타데이터 주소는 열지 않는다 |
| 앱 설정 | [`k8s/api.yaml`](k8s/api.yaml)·[`k8s/worker.yaml`](k8s/worker.yaml) | api `FILE_STORAGE_DRIVER=s3`·`FILE_STORAGE_S3_BUCKET`·`AWS_REGION`, worker `FILE_STORAGE_S3_BUCKET`·`AWS_DEFAULT_REGION`. 접근 키는 넣지 않는다 |

- 버킷 이름은 네 곳(`create-s3.sh`, `cluster.yaml`의 두 역할, `api.yaml`, `worker.yaml`)에 같은 값으로 적혀 있고 [`deploy.test.sh`](scripts/deploy.test.sh)가 서로 같은지 본다. S3 버킷 이름은 모든 AWS 계정이 함께 쓴다. 다른 계정이 이미 쓰는 이름이면 버킷 만들기가 `BucketAlreadyExists`로 멈추므로, 네 곳의 이름을 바꾸는 PR을 먼저 낸다.
- api는 없는 파일(S3의 '없음')과 저장소 장애('거부' 등)를 가려서 처리하고, S3는 목록 권한이 있어야 없는 파일에 '없음'을 돌려준다. 목록 권한을 `members/` 접두어로 좁힌 구성에서 EKS api의 없는 파일 읽기는 `NoSuchKey`였다([11/18 확인](https://github.com/JminAILab/CatchU/issues/276#issuecomment-6970235553)).
- worker는 목록 권한이 없어, 이미 지워진 원본을 읽으면 '없음'이 아니라 '거부'를 받고 그 추출 작업을 결과 없이 실패로 끝낸다. 자료는 api의 10분 시한으로 실패가 된다.
- **PDF 글 추출은 api의 큐 연결을 켠 뒤에 돈다**(README 5단계). 그 전에는 올리기·보기·발행 사본은 되고, 추출은 10분 뒤 실패로 보인다([api PDF 자료](../../api/docs/pdf-materials.md) 「설정」).
- 개발 서버의 PDF는 옮기지 않는다(개발 서버 자료는 옮기지 않는다는 10/6 결정). 개발 서버 버킷 `catchu-dev-server-files`는 4단계에서 지운다.

## 만들기(1단계)

1. **역할 연결.** `cluster.yaml`에 들어 있으므로 `eksctl create cluster`가 역할 둘과 연결을 함께 만든다. 이 파일이 `dev`에 반영되기 전에 클러스터를 만들었으면 두 연결만 따로 만든다. 이미 있는 연결(Load Balancer Controller·로그 수집기)을 다시 만들지 않도록, `cluster.yaml`에서 namespace `catchu`의 연결만 뽑은 설정 파일로 실행한다. 이 경로는 실제 클러스터에서 확인하지 못했다.
   ```bash
   ruby -ryaml -e 'c = YAML.load_file("deploy/aws/cluster.yaml"); puts YAML.dump("apiVersion" => c["apiVersion"], "kind" => c["kind"], "metadata" => {"name" => c["metadata"]["name"], "region" => c["metadata"]["region"]}, "iam" => {"podIdentityAssociations" => c["iam"]["podIdentityAssociations"].select { |a| a["namespace"] == "catchu" }})' > /tmp/catchu-app-roles.yaml
   bash deploy/aws/scripts/check-target.sh
   eksctl create podidentityassociation -f /tmp/catchu-app-roles.yaml --profile catchu
   ```
   어느 쪽이든 연결 둘을 확인한다. `api`와 `worker` 두 줄이 나와야 한다.
   ```bash
   aws eks list-pod-identity-associations --cluster-name catchu --namespace catchu --profile catchu --region ap-northeast-2 --query 'associations[].serviceAccount' --output text
   ```
2. **버킷과 엔드포인트.** README 「1단계 만드는 순서」 5번에서 다른 자원과 함께 만든다. 끝에 찍히는 확인 값(공개 차단 넷 모두 `true`, `AES256`, `BucketOwnerEnforced`, 버전 관리 `None`, 엔드포인트 `available`과 경로표)을 증거로 남긴다. 마지막 줄이 "worker 목록에 없는 S3 대역"이면 [k8s/README.md](k8s/README.md) 「worker 바깥 연결 대역 갱신」대로 고친다.
   ```bash
   bash deploy/aws/scripts/create-s3.sh            # 확인만
   bash deploy/aws/scripts/create-s3.sh --apply
   ```
3. **중간에 멈췄으면** 다시 실행해도 진행되지 않는다(만들 자원이 하나라도 있으면 멈춘다). 버킷만 만들어졌으면 `aws s3api delete-bucket --bucket catchu-prod-files --profile catchu --region ap-northeast-2`로 지우고 다시 실행한다. 엔드포인트까지 만들어졌으면 다시 실행하지 말고, 스크립트 안 `show_evidence`의 조회를 그대로 실행해 확인 값을 남긴다.

## 확인(2단계)

서비스 계정은 `k8s/namespace.yaml`, 연결 허용은 `k8s/network-policy.yaml`을 적용하면 생긴다([k8s/README.md](k8s/README.md) 「적용(2단계)」). 이 변경 전에 두 파일을 이미 적용했으면 `deploy.sh`보다 먼저 다시 적용한다. 서비스 계정이 없으면 api·worker Pod가 만들어지지 않아 `deploy.sh`가 6으로 멈춘다.

`deploy.sh`로 앱을 띄운 뒤 실제 Deployment Pod 안에서 본다. `k`는 [k8s/README.md](k8s/README.md)의 줄임이다.

```bash
k get pod -l app.kubernetes.io/name=api -o jsonpath='{.items[0].spec.containers[0].env[?(@.name=="AWS_CONTAINER_CREDENTIALS_FULL_URI")].value}'
k logs deploy/worker | grep -c 'pdf=enabled'
key=$(k exec -i deploy/api -- node - keep < deploy/aws/scripts/s3-check-api.js | tee /dev/stderr | sed -n 's/^남긴 파일: //p')
k exec -i deploy/worker -- /app/worker/.venv/bin/python - "$key" < deploy/aws/scripts/s3-check-worker.py
k exec -i deploy/api -- node - clean "$key" < deploy/aws/scripts/s3-check-api.js
```

| 줄 | 기대 | 다르면 |
|---|---|---|
| 1 | `http://169.254.170.23/v1/credentials` | 비어 있으면 역할 연결이 없을 때 뜬 Pod다. 연결은 그 뒤에 뜨는 Pod에만 들어간다. 연결을 확인한 뒤 `k delete pod -l app.kubernetes.io/name=api`(worker도 같게)로 다시 띄운다 |
| 2 | 1 이상 | worker에 버킷 값이 없거나 로컬 읽기 경로와 함께 들어 있다 |
| 3 api | 8줄 모두 `통과`, 끝에 `남긴 파일: members/<UUID>/s3-check` | `TimeoutError`·`ECONNREFUSED`는 연결 허용(NetworkPolicy)이나 엔드포인트, `CredentialsProviderError`는 역할 연결, `AccessDenied`·`NoSuchBucket`은 역할 정책이나 버킷 이름을 본다. '없는 파일 읽기'만 `AccessDenied`면 api 목록 권한의 접두어 조건을 본다 |
| 4 worker | 읽기 `허용`, 올리기·삭제·목록 `AccessDenied` | 읽기가 시간 초과면 worker의 S3 대역 목록을 본다. 올리기·삭제가 `허용`이면 worker 역할 정책이 넓다 |
| 5 api | 2줄 모두 `통과` | 남긴 파일이 지워지지 않았으면 관리자 권한으로 지운다 |

3~5의 출력(단계 이름과 결과뿐이다)을 #276 댓글에 남긴다. 완료 기준 「#389에서 정한 11월 새 기능 인프라가 EKS에 반영돼 api·worker가 쓴다」의 S3 부분과 「EKS에서 worker 역할의 S3 쓰기·삭제가 거부된다」의 증거다. 시험 파일은 새 UUID의 `members/<UUID>/` 아래에만 만들고 5에서 지운다. 화면 업로드·추출은 [11/19 합성 PDF 두 벌 확인](../../api/docs/pdf-materials.md#확인-범위)에서 실제 S3·큐·worker로 봤다. 위 권한 확인과 별개이며, 새 환경에서는 전환 뒤 다시 확인한다.

위 Pod 설정과 NetworkPolicy로 [11/18에 실제 S3 접근을 확인했다](https://github.com/JminAILab/CatchU/issues/276#issuecomment-6970235553). api는 허용된 읽기·쓰기 8줄을 통과했고 `members/` 밖 쓰기는 거부됐으며, worker는 읽기만 허용되고 쓰기·삭제·목록은 거부됐다. 별도 클러스터에 적용할 때도 위 확인을 생략하지 않는다.

## 지우기

README 「삭제 순서」 B에서 한다. 엔드포인트가 VPC에 남아 있으면 eksctl의 VPC 삭제가 실패하므로 클러스터를 지우기(B의 10번) 전에 지운다.

```bash
vpc=$(aws eks describe-cluster --name catchu --profile catchu --region ap-northeast-2 --query cluster.resourcesVpcConfig.vpcId --output text)
aws ec2 describe-vpc-endpoints --profile catchu --region ap-northeast-2 --filters "Name=vpc-id,Values=${vpc}" --query 'VpcEndpoints[].[VpcEndpointId,ServiceName,State]' --output text
aws ec2 delete-vpc-endpoints --vpc-endpoint-ids <엔드포인트 ID> --profile catchu --region ap-northeast-2
aws s3 rb s3://catchu-prod-files --force --profile catchu --region ap-northeast-2
```

`--force`는 버킷의 회원 파일을 모두 지운 뒤 버킷을 지운다. 되돌릴 수 없으므로 제출 확인 뒤 승인을 받고 한다. api·worker 역할과 연결은 `eksctl delete cluster`가 함께 지운다.
