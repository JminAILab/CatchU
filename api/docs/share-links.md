# 공유 링크 발급(#147)·목록·중단(#148)·수신자 비밀번호 확인(#150)

발급 UI의 병합 후 검증은 [#149 통합 검증](share-links-integration-149.md)을 따른다(실행 명령·응답 유실 재현·관측 결과와 미실행 범위).

`POST /v1/share-links`(회원 API `createShareLink`), `GET /v1/share-links`(`listShareLinks`), `PUT /v1/share-links/{linkId}/stop`(`stopShareLink`), `POST /v1/public/links/{token}/unlock`(수신자 API `unlockLink`)과 ShareLink 테이블이다. 코드는 `src/share-links/`에 있다.

## 발급 처리 순서

1. 회원 인증(Guard) 다음, 같은 회원의 발급 요청이 최근 1분에 10번을 넘으면 입력 검사·비밀번호 해시·저장 없이 `429 RATE_LIMITED`와 `Retry-After`(창 안 가장 오래된 요청이 빠질 때까지 남은 초)로 거부한다(#219, 컨트롤러). 아래 2의 입력 오류(400)·같은 키 재요청·한도 거절(409)도 센다. 거부한 요청은 세지 않고 링크·멱등 기록도 남기지 않아 같은 키로 다시 보낼 수 있다. 429는 요청을 처리하지 않은 것이라 앞선 같은 키 요청의 결과를 알려 주지 않는다. 응답을 모르던 요청이면 클라이언트는 키를 유지하고 `Retry-After` 뒤 같은 키·같은 본문으로 다시 보낸다(계약 #235). 같은 키 재요청도 비밀번호를 해시로 비교하므로 빈도에서 빼지 않는다. 이 판정이 서비스의 회원 ID 형식 검사(아래 2)보다 먼저라, UUID가 아닌 개발 토큰도 상한을 넘으면 429다.
2. 토큰의 회원 ID가 UUID가 아니면(#104 이전 개발 토큰) `401 AUTH_INVALID`. `Idempotency-Key` 헤더가 없으면 `400 INVALID_REQUEST`(키 길이는 아래 4에서 검사), 본문이 계약과 다르면 `400 VALIDATION_FAILED`(`details.violations`의 reason은 `isObject`·`whitelistValidation`·`isString`·`isNotEmpty`·`minLength`·`maxLength`). 길이는 아래 「비밀번호 길이」의 기준이며, trim 뒤 51자 이상 제목은 `title`의 `maxLength`, 8자 미만·64자 초과 비밀번호는 `password`의 `minLength`·`maxLength`다(#221). 빈 비밀번호는 지금처럼 `isNotEmpty`다. 알 수 없는 필드 이름은 응답에 반사하지 않고 `body` 한 건으로 알린다.
3. 비밀번호 해시와 토큰은 잠금 시간을 줄이려고 트랜잭션 밖에서 미리 만든다.
4. 한 READ COMMITTED 트랜잭션에서 회원 행을 `FOR KEY SHARE`로 확인하고(없으면 `401 AUTH_INVALID`, 다른 DB 오류는 500 그대로) #104의 `runIdempotentCreation`을 부른다. 이 공통 처리가 키 길이(1~128자, 코드 포인트로 셈)를 검사해 벗어나면 `400 INVALID_REQUEST`다. 그래서 빈 키·129자 이상 키는 3의 해시를 계산한 뒤에 거절된다(그 반복은 1의 빈도 상한이 묶는다). 잠금 순서는 **멱등 키 잠금 → 회원 단위 발급 잠금**이다.
   - 새 키: `issueShareLink`가 회원 단위 advisory lock을 잡고, 잠금을 얻은 **뒤의** 시각으로 유효 링크(중단 안 됨, 만료 전)를 모아 제목 중복(`LINK_TITLE_CONFLICT`)을 한도(`LINK_LIMIT_REACHED`, 5개)보다 먼저 판정한 뒤 저장한다(#23 9/28 결정).
   - 같은 키: 지문이 다르면 409. 지문이 같아도 기록이 가리키는 링크를 읽어 `isSameShareCreate`로 비밀번호까지 비교한다. 비밀번호만 달라도 `409 IDEMPOTENCY_CONFLICT`이고, 같으면 그 링크를 현재 상태로 200 응답한다(중단됐으면 `STOPPED`). 기록과 링크가 어긋나면 409가 아니라 500이다.
5. 응답 구성까지 같은 트랜잭션이다. 거절·실패하면 링크와 멱등 기록이 함께 롤백되어 같은 키를 다시 쓸 수 있다.

## 목록·중단 — #148

- **목록** `GET /v1/share-links`: 본인 링크만 발행 시각 최신순, 같은 시각이면 `linkId` 역순이다. `limit`은 1~100(기본 20), `page.nextCursor`는 마지막 페이지에서 null. 0개는 `items: []`인 정상 응답이다. 상태는 응답 시각으로 구한다.
  - 쿼리는 `cursor`·`limit`만 받는다. 다른 이름, 같은 이름 반복, 범위 밖 `limit`, 고치거나 다른 회원의 `cursor`는 `400 VALIDATION_FAILED`(reason `whitelistValidation`·`isInt`·`min`·`max`·`isCursor`)이며 입력값을 담지 않는다.
  - cursor는 소유자와 위치만 담은 불투명 문자열이다. 권한을 담지 않으므로 매 요청 인증된 회원의 링크만 다시 조회한다.
- **중단** `PUT /v1/share-links/{linkId}/stop`: #148 9/29 팀장 결정 표를 따른다. 업무 판정은 200과 404를 쓴다(입력 오류 400·인증 오류 401·서버 오류 500은 별도).

| 경우 | 응답 |
|---|---|
| 본인 유효 링크 | 200, `STOPPED`(중단 시각 기록) |
| 본인 링크 반복 중단 | 200, 처음 `stoppedAt` 유지(만료 시각이 지나도 `STOPPED`) |
| 본인 만료 링크 | 200, 중단 처리 없이 `EXPIRED` |
| 타인 링크·없는 링크·UUID 형식이 아닌 ID | 404 `RESOURCE_UNAVAILABLE`(소유 확인을 상태 확인보다 먼저) |
| 본문(객체·배열·문자열 등 종류 무관)이나 쿼리가 붙은 요청 | 400 `VALIDATION_FAILED`(reason `isEmpty`·`whitelistValidation`). JSON 원시값은 해석 단계에서 400 `INVALID_REQUEST` |

- 중단은 링크 행을 `FOR UPDATE`로 잠가 동시 중단도 같은 `stoppedAt` 하나로 모은다. `share_link` 행만 바꾸며 Catch 내용·공개 상태는 건드리지 않는다.
- 세 API 모두 회원 UUID가 아니거나 회원 행이 없는 토큰은 `401 AUTH_INVALID`다. 이 확인은 공통 Guard가 아니라 서비스에서 하고, 트랜잭션 안에서 회원 행을 `FOR KEY SHARE`로 잡는다([#162 검토 합의](https://github.com/JminAILab/CatchU/pull/162#issuecomment-5943491118)).

## 테이블

마이그레이션 `1790745895865-CreateShareLink`가 `share_link`와 두 외래 키를 만든다. #104(`1790500000000`) 뒤, B(`1790600000000`)와는 서로 참조하지 않는다.

- `share_link`: 제목 1자 이상(50자 상한은 API 입력 검사에만 적용한다. DB 상한 제약·마이그레이션은 추가하지 않으므로 DB 직접 쓰기는 이 상한을 보장하지 않는다), `expires_at = issued_at + 720시간`, 중단 시각 ≥ 발급 시각, 토큰 유일, `owner_id` 인덱스.
- `owner_id → member_account.member_id`.
- `unique(link_id, owner_id)`와 `idempotency_record (link_id, member_id) → share_link (link_id, owner_id)`: 멱등 기록이 있는 링크를, 그리고 기록한 회원이 소유한 링크만 가리킨다. 분석 요청 기록은 `link_id`가 null이라 검사 대상이 아니다.
- 기록이 가리키는 링크는 지울 수 없다. 되돌릴 때는 이 마이그레이션을 #104보다 먼저 되돌린다.

유효 링크의 제목 유일·5개 한도는 시간에 따라 달라지므로 정적 unique로 두지 않고 위 회원 단위 직렬화로 판정한다.

**토큰 저장:** `link_token_reference`에 토큰 자체를 저장한다(ERD `secret-lookup-key`, [#162 검토 합의](https://github.com/JminAILab/CatchU/pull/162#issuecomment-5943491118)). 발급·같은 키 재요청·목록(#148) 응답이 모두 `url`을 다시 만들어야 해서 되돌릴 수 없는 해시로는 저장할 수 없고, 암호화 보관은 키 관리 방식이 정해지지 않아 쓰지 않는다. 토큰은 `url` 밖(별도 응답 필드·로그·오류)에 내보내지 않는다. 비밀번호와 달리 DB가 유출되면 토큰도 함께 노출되는 한계가 남는다.

비밀번호 원문은 저장·응답·로그에 남기지 않고, 지문에도 넣지 않는다(짧은 비밀번호의 해시는 추측으로 원문을 알아낼 수 있다).

## 수신자 비밀번호 확인·접근 판정 — #150

grant 형식·수명·보관·시도 제한은 [#150 9/29 결정](https://github.com/JminAILab/CatchU/issues/150#issuecomment-5883572995), 차단 응답은 #173 계약을 따른다. 회원 JWT를 쓰지 않는다. 인증 예외 `@Public()`은 클래스가 아니라 `unlock` 메서드에만 붙이며, 이 컨트롤러에 경로를 더할 때(#151)도 경로마다 붙인다([보안 점검](../../docs/CatchU_security_checks.md)). `test/public-links-auth-boundary.test.cjs`가 실제 Guard로 `unlock`의 비로그인 허용과 같은 컨트롤러의 미지정 경로 인증 요구를 검사한다.

| 파일 | 내용 |
|---|---|
| `public-links.controller.ts` | `POST /v1/public/links/{token}/unlock` |
| `link-access.service.ts` | 링크 판정·unlock·수신 조회용 `assertReadable(token, grant)`(#151이 쓴다) |
| `link-grant.ts` | grant 서명·검증(HMAC-SHA256, `LINK_GRANT_SECRET`). 링크 ID·만료만 담고 서버에 저장하지 않는다 |
| `unlock-limiter.ts` | 링크·주소 단위 시도 제한과 직렬화(프로세스 메모리) |
| `link-limiter.ts` | 링크 전체 시도 제한과 링크별 검사 중 상한 |
| `hash-gate.ts` | unlock 경로 전체의 실행 중 해시·대기 상한 |
| `unlock-policy.ts` | 위 세 제한과 요청 빈도(`request-rate-limiter.ts`, #219)의 정책값(`PRODUCT_UNLOCK_POLICY`)과 생성. 정책값은 `UNLOCK_POLICY`로 주입한다 |

**unlock 판정 순서**

| 순서 | 조건 | 응답 |
|---|---|---|
| 1 | 토큰 형식이 틀림·없음·중단·만료 | 404 `LINK_UNAVAILABLE`, 고정 문구, `details` 없음(비밀번호 검사 전) |
| 2 | 비밀번호 없는 링크 | 400 `INVALID_REQUEST` |
| 3 | 본문이 `{ password: 비어 있지 않은 문자열 }`이 아님 | 400 `VALIDATION_FAILED`(세지 않음). 차단 중이어도 400. 비밀번호 길이는 검사하지 않는다(발급 길이 기준을 unlock에 적용하지 않음, 아래 「비밀번호 길이」) |
| 4 | 이 링크·주소 또는 이 링크 전체가 이미 차단 중 | 429 `LINK_UNLOCK_LIMITED`, `Retry-After`=차단 종료까지 남은 초(올림). 둘 다 차단 중이면 늦게 끝나는 쪽. 대기열보다 먼저 판정하고, 맞는 비밀번호도 거부하며 해시를 계산하지 않는다 |
| 5 | 같은 링크·주소의 요청이 최근 1분에 20번을 넘음(#219) | 429 `LINK_UNLOCK_LIMITED`, `Retry-After`=창 안 가장 오래된 요청이 빠질 때까지 남은 초. 맞는 비밀번호도 거부하며 해시를 계산하지 않고 실패로 세지 않는다. 거부한 요청은 빈도로도 세지 않는다 |
| 6 | 진행 중 unlock이 전체 상한(실행 중 해시 + 대기)에 닿았거나, 같은 링크·주소에 실행 중 포함 3개가 걸려 있음 | 429, `Retry-After: 1`(포화). 검사하지 않는다. 비밀번호 실패 횟수에는 포함하지 않는다. 요청 빈도에는 앞선 5단계에서 이미 포함했다 |
| 7 | (같은 링크·주소의 차례가 오면) 주소 자리와 링크 자리를 예약한다. 차단이면 4와 같고, 링크의 검사 중이 3개이거나 (집계 기간 안 링크 실패 + 검사 중)이 링크 전체 상한에 닿으면 포화, 새 키·새 링크가 기록 자리를 얻지 못하면 거절 | 429. 포화는 `Retry-After: 1`, 자리 없음은 아래 「기록 상한」. 비밀번호 실패 횟수에는 포함하지 않는다. 요청 빈도에는 앞선 5단계에서 이미 포함했다 |
| 8 | (해시 차례가 오면) 해시 직전에 링크 중단·만료와 주소·링크 차단을 다시 확인 | 중단·만료는 404, 차단은 429. 해시를 계산하지 않는다. 비밀번호 실패 횟수에는 포함하지 않는다. 요청 빈도에는 앞선 5단계에서 이미 포함했다 |
| 9 | 비밀번호 틀림 | 401 `LINK_PASSWORD_INVALID`. 주소와 링크 전체에 실패 1회 |
| 10 | 맞음 | 200 `{ grant }`. 그 링크·주소의 실패 기록은 지우고 링크 전체 실패 기록은 남긴다(방어적 재확인에서 차단이 보이면 429, grant 없음) |

- 어떤 단계에서 끝나도(오류·예외·요청 취소 포함) 예약한 주소·링크 자리와 해시·대기 자리를 모두 돌려준다. 클라이언트가 연결을 끊어도 서버 처리는 끝까지 간다.
  - 대기 중 취소: 차례가 오면 그대로 검사하고 기록한다(틀린 비밀번호는 실패로 센다). 끝난 뒤 자리를 돌려준다.
  - 해시 실행 중 취소: 해시가 실제로 끝날 때까지 실행 자리를 쥐고 있어, 취소 뒤 새 요청이 와도 동시 해시는 상한(2개)을 넘지 않는다.
- **grant:** 수명은 발급 후 최대 2시간이며 링크 만료를 넘지 않는다. 링크 ID가 다르거나 서명·형식이 틀리거나 만료되면 무효다. web은 `X-Link-Grant` 헤더로 보내고 링크별 `sessionStorage`에 둔다(#152).
- **수신 조회 판정(`assertReadable`):** 매 요청 1번 판정을 다시 한 뒤, 비밀번호 링크는 이 링크의 유효한 grant가 없으면 401 `LINK_PASSWORD_REQUIRED`다. grant가 있어도 중단·만료는 404다. 시도 제한(링크 전체 제한 포함)은 적용하지 않으므로, 링크가 차단돼도 이미 받은 grant로는 계속 열람한다.
- **주소별 시도 제한:** 같은 링크·같은 주소에서 15분 안에 10번 틀리면 그 시각부터 15분 차단한다(#150 9/29 결정). 차단 중 요청은 실패로 세지 않아 기간이 늘어나지 않고, 풀리면 처음부터 센다. 같은 링크·주소의 요청은 한 번에 하나씩 7~10단계를 해, 동시에 몰아 보내도 차단 전 검사는 10번을 넘지 않는다.
- **같은 링크·주소의 요청 빈도(#219):** 실패 기록은 성공하면 지워지므로, 비밀번호를 아는 사람이 맞는 비밀번호를 되풀이하면 실패 제한으로는 막히지 않고 요청마다 해시를 계산한다. 그래서 같은 링크·주소의 unlock을 1분에 20번까지만 받는다(`unlock-policy.ts`의 `rate`). 비밀번호를 몇 번 다시 넣는 정상 수신자에게는 넉넉하다. 링크마다 따로 세므로 링크를 여럿 가진 사람은 링크 수만큼 보낼 수 있고, 그 합은 아래 전체 해시 자원 상한이 묶는다.
- **주소:** Express가 `TRUST_PROXY_CIDRS`([api README 「설치와 환경변수」](../README.md#설치와-환경변수))에 적은 프록시만 믿고 정한 `request.ip`를 주소 단위로 바꾼 값이다. 설정하지 않으면 직접 연결 주소이고 `X-Forwarded-For`는 무시한다. 부하분산기 뒤에서 설정하지 않으면 모든 수신자가 같은 주소로 보여 한 사람의 실패가 그 링크의 주소 단위 전체를 막는다. IPv6 /64는 한 사람을 뜻하지 않는다. 가입자에게 /56·/48을 주는 망에서는 한 사람이 여러 /64를 가질 수 있고, IPv4 공유 NAT(회사망 등)에서는 여러 정상 수신자가 한 칸으로 묶여 함께 막힐 수 있다.
- **링크 전체 시도 제한(#150 10/4 보안 의견 2):** 주소를 바꿔 가며 시도해도 한 링크의 검사 수를 묶는다. 한 링크에서 최근 15분 안에 주소와 상관없이 N번 틀리면 그 시각부터 15분 동안 그 링크의 새 unlock을 막는다. **N은 30**이다(2026-10-05 담당자 결정, `unlock-policy.ts`의 `PRODUCT_UNLOCK_POLICY`). 이 값은 실측으로 검증한 최적값이 아닌 초기 선택이며, 정상 수신자 차단 영향과 운영 결과에 따라 바꿀 수 있다. 시험은 운영값 30과 후보 20·50으로 같은 규칙을 검사한다.
  - 집계 기간 안의 검사가 모두 실패하면 차단 전 검사는 정확히 N번이다. 중간에 성공이 섞이면 성공은 실패로 세지 않으므로 그보다 많을 수 있다.
  - 성공은 링크 전체 실패 기록을 지우지 않는다. 한 수신자의 성공이 다른 주소에서 쌓인 실패를 지우지 않게 하기 위해서다.
  - 영향: URL을 가진 한 사람이 여러 주소로 N번 틀리면, 정상 수신자도 15분 동안 그 링크의 새 비밀번호 확인(unlock)이 차단될 수 있다. 이미 발급된 유효한 grant의 열람은 유지된다. 9/28 제안에서 링크 전체 차단을 피했던 이유이며, 10/4 보안 의견에 따라 이 위험을 받아들인다. 정상 수신자끼리의 실패로도 걸릴 수 있다(예: 구직자가 비밀번호를 잘못 전달해 여러 수신자가 반복해 틀린 경우, 올바른 비밀번호를 다시 받아도 차단이 끝날 때까지 비밀번호 확인을 할 수 없다). 정상 수신자 수와 실패 횟수에 대한 실측 자료는 없다. 발행자는 링크를 중단하고 새 URL을 발행할 수 있다.
  - 추측 횟수(전제에 따른 추정치, 보장 상한 아님): api 프로세스 1개·재시작 없음·링크 실패 기록 유지 조건에서, 실패 N번과 15분 차단을 쉬지 않고 반복하면 한 링크에 하루 약 96×N번, N=30이면 약 2,880번 시도할 수 있다. 재시작으로 기록이 초기화되거나 프로세스가 늘면 더 늘어난다. 짧은 비밀번호는 이 범위 안에서 맞혀질 수 있어, 추측 저항은 시도 제한보다 아래 「비밀번호 길이」의 발급 최소 길이에 기댄다.
- **비밀번호 길이:** 계약([#223](https://github.com/JminAILab/CatchU/pull/223), 2026-10-06 병합)은 발급 본문의 선택 비밀번호를 trim·정규화 없이 입력 그대로 8~64자, 제목을 trim 후 1~50자로 정한다. 글자 수는 유니코드 코드 포인트(DB `char_length`와 같음)로 센다. 결합 이모지·국기처럼 화면에서 한 글자로 보여도 코드 포인트 수만큼 센다. 발급 API는 이 기준으로 검사한다(#221, 위 「발급 처리 순서」 2). unlock은 길이를 검사하지 않고(빈 값만 400) 저장된 검증값과 비교하므로, #221 이전에 8자 미만으로 발급된 링크도 맞는 비밀번호로 열린다. 다만 본문 검사가 멱등 처리보다 먼저라, #221 이전에 허용됐던 제목 51자 이상 또는 비밀번호 8자 미만·65자 이상 요청을 같은 `Idempotency-Key`로 다시 보내면 기존 응답 대신 `400 VALIDATION_FAILED`다. 위반 이유는 각각 `title.maxLength`, `password.minLength`, `password.maxLength`다. 기존 링크와 멱등 기록은 바뀌지 않으며, 기존 비밀번호로 unlock할 수 있다.
- **링크별 독립과 전체 자원:** 링크별 차단은 서로 독립이다. 다만 아래 전체 해시 자원 상한은 링크 구분 없이 걸려, 한 링크에 몰린 요청이 다른 링크의 unlock도 잠시 포화(429, `Retry-After: 1`)로 만들 수 있다.
- **전체 해시 자원(`hash-gate.ts`):** unlock 경로에서 동시에 계산하는 scrypt는 2개(scrypt는 libuv 스레드 풀 기본 4개에서 돌고 1회 약 32 MiB를 쓴다. 같은 풀을 쓰는 파일·DNS 작업을 막지 않도록 일부만 쓴다), 처리 중이지만 해시를 계산하지 않는 요청은 20개까지다. 발급 API의 해시는 세지 않는다. 처리 시간은 해시 시간에 따른 추정이다. #219에서 해시를 p=3으로 올린 뒤 로컬 측정(2026-10-05)에서 해시 1회는 약 190ms(강화 전 약 60~90ms)라, 실행 자리 2개로 초당 약 10번 검사한다.
- **기록 상한:** 주소 기록과 링크 기록은 각 1만 개다. 프로세스 메모리라 재시작하면 초기화되고, 서버·프로세스가 늘면 제한이 헐거워진다(api는 프로세스 1개로 띄운다, #24 배포 설정 목록).
  - 주소 기록: 새 키는 검사 전에 자리를 예약한다. 자리가 없으면 만료된 기록을 정리하고, 그래도 없으면 차단 중도 검사 중도 아닌 기록 가운데 가장 오래 쓰지 않은 것 하나를 밀어낸다(#150 10/4 보안 의견 3). 밀려난 주소의 실패 누적은 초기화되지만 그 링크의 링크 전체 누적은 남는다.
  - 링크 기록: 실패 누적·차단·검사 중이 남은 기록은 밀어내지 않는다(밀어내면 링크 전체 누적이 초기화된다). 빈 기록은 쓰자마자 지운다.
  - 밀어낼 기록이 없으면(모두 차단·검사 중이거나 누적이 남음) 새 키·새 링크의 unlock은 검사 없이 429로 거절한다. 밀어내기로 바꿔도 용량 부족에 따른 거절이 완전히 없어지지는 않는다. 이미 기록이 있는 키·링크는 이 용량 거절을 받지 않지만, 주소·링크 차단과 전체 해시 자원 상한은 그대로 적용된다. `Retry-After`는 검사 중 자리가 있으면 1초, 없으면 가장 빨리 풀리는 기록까지다. 9/30에는 이때 새 키를 거절하는 방식을 유지하기로 했으나(PR #195 「확인받을 것」 2), 10/4 보안 의견에 따라 주소 기록은 밀어내기로 바꿨다.
- **응답 시간:** 없음·중단·만료는 같은 조회 경로를 타고, 차단되지 않은 검증만 해시를 한 번 계산한다. 응답 시간이 같다고 보장하지 않는다. 2026-09-30 로컬 측정(직렬화 적용 판본, 각 25회 중앙값): 404 2.0ms, 400 2.1ms, 429 1.9ms, 401 94.0ms, 200 91.6ms. 해시를 계산하는 401·200만 느리고, 링크 존재 여부(404)는 비밀번호 없는 링크(400)·차단(429)과 비슷하다.
