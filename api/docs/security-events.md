# 보안 사건 최소 기록 — #222

[10/4 팀장 결정](https://github.com/JminAILab/CatchU/issues/88#issuecomment-5975854431)에 따라 공통 오류 필터가 다음 세 코드만 `SecurityEvent` 경고 한 줄로 기록한다.

- `AUTH_INVALID`: 회원 인증 실패(401). 회원 토큰의 형식·서명·만료 오류와, 토큰의 회원 ID가 형식에 맞지 않거나 회원이 없는 경우 등이 포함된다. Google 로그인 완료 API의 실패 응답도 같은 코드를 쓴다(아래 참고).
- `LINK_PASSWORD_INVALID`: 링크 비밀번호 불일치(401)
- `LINK_UNLOCK_LIMITED`: 링크 비밀번호 확인 거절(429). 비밀번호 실패 차단 외에 요청 빈도·처리 용량 제한에도 같은 코드를 쓴다(아래 참고).

`AUTH_REQUIRED`·`LINK_PASSWORD_REQUIRED`는 정상 진입에서도 발생하므로 제외한다. 발급 빈도 제한 `RATE_LIMITED`를 포함한 나머지 업무 4xx도 보안 사건으로 기록하지 않는다.

기록 여부는 경로가 아니라 오류 코드로 정한다. 따라서 [Google 로그인](google-login.md) 완료 API가 `401 AUTH_INVALID`를 반환하는 경우도 현재 같은 형식으로 한 줄 기록된다. 여기에는 로그인 시도가 없거나(이미 사용된 시도 포함) 만료됐거나 시작자가 다른 경우, 인증 코드 교환에서 Google이 `invalid_grant`·`access_denied`로 응답한 경우, Google ID 토큰 검증 실패, 비활성 계정이 포함된다. 사용자가 Google 승인을 취소해 완료 API가 `{cancelled: true}`로 응답하는 경우는 오류가 아니므로 기록되지 않는다. 다만 취소 요청이라도 로그인 시도가 없거나 만료됐으면 `AUTH_INVALID`로 기록된다.

로그인 시도 만료와 이미 사용된 시도의 재요청도 기록하며, 원인은 구분하지 않는다. 10/4 결정의 인증 실패(401)에 해당하기 때문이다([2026-10-12 팀장 결정](https://github.com/JminAILab/CatchU/pull/259#issuecomment-6118177454)). web 콜백 연결 뒤 정상 로그인에서도 이 기록이 자주 남는 것이 확인되면 제외를 다시 검토한다.

`LINK_UNLOCK_LIMITED`도 오류 코드 기준이라, 비밀번호 확인 API가 이 코드로 거절하면 원인과 관계없이 같은 형식으로 한 줄 기록된다. 현재 이 코드로 거절하는 경우는 다음과 같다. 판정 순서와 `Retry-After`는 [공유 링크](share-links.md)의 「수신자 비밀번호 확인·접근 판정」을 따른다.

- 실패 차단: 같은 링크·주소 또는 링크 전체가 비밀번호 실패 한도로 차단 중이거나, 검사 차례에서 차단이 확인된 경우.
- 요청 빈도: 같은 링크·주소의 요청이 빈도 상한(#219)을 넘은 경우. 맞는 비밀번호도 해당한다.
- 처리 용량: 서버 전체의 진행 중 비밀번호 확인 상한(실행 중 해시와 대기의 합), 같은 링크·주소의 대기 상한(실행 중 포함), 링크별 검사 중 상한, 링크 실패 누적과 검사 중 요청의 합이 링크 전체 한도에 닿은 경우, 주소·링크 기록 상한에서 자리를 얻지 못한 경우.

기록 줄에는 분류 코드·경로 틀·요청 식별자·시각만 있어 로그만으로는 이 원인들을 구분할 수 없다. 요청 빈도·처리 용량 거절도 기록하며, 원인은 구분하지 않는다. 계약에서 수신자 경로의 429는 이 코드 하나로 비밀번호 시도 제한을 뜻하고, 10/4 결정이 이 코드를 기록 대상으로 정했기 때문이다([2026-10-12 팀장 결정](https://github.com/JminAILab/CatchU/pull/259#issuecomment-6118177454)). 원인을 구분하지 못해 실제로 곤란한 일이 생기면 다시 검토한다.

형식은 `<분류 코드> <메서드> <등록된 경로 틀> requestId=<UUID> at=<ISO 시각>`이다. 실제 URL·토큰·비밀번호·요청 본문·헤더·쿼리·예외 원문은 기록하지 않는다. 등록 경로가 없으면 `[unmatched]`를 사용한다. 요청 식별자는 서버 내부에서 요청마다 생성하며 응답·web으로 전달하지 않는다.

구현은 `src/common/errors/api-exception.filter.ts`와 `src/common/http/request-id.ts`다. 기존 오류 응답·차단 정책·해시 순서는 바꾸지 않는다.

검사 위치:
- `test/security-events.test.cjs`: 기록·제외 및 합성 민감정보의 로그 비노출 단위 검사.
- `test/auth.test.cjs`: 실제 회원 인증 실패·정상 진입의 로그 검사.
- `test/db/public-links-unlock.test.cjs`: 실제 HTTP·PostgreSQL에서 비밀번호 실패·시도 제한과 로그 검사.

실행은 api 폴더의 `npm test`를 사용하며 테스트 DB 준비는 [README](../README.md#db-테스트)를 따른다. 합성 자료만 사용하고 운영 로그 저장·보관 환경은 별도 검증한다.
