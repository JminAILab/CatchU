# 잠금 대기 상한 — #220

api가 DB 잠금을 기다리는 최대 시간이다. 상한은 코드가 아니라 **앱 DB 계정**에 건다. 이 문서는 결정·적용 위치, 경로별로 상한을 넘었을 때 남는 것, 측정값과 그 한계, 판단이 필요한 결과, 시험 방법을 적는다.

## 결정과 적용 위치

[2026-10-16 #220 합의](https://github.com/JminAILab/CatchU/issues/220#issuecomment-6206164416)의 내용이다.

- 앱 계정(`catchu_app`)에만 `lock_timeout = '3s'`를 건다. 마이그레이션 계정과 공통 DB 연결 설정(`src/database/database.config.ts`의 `buildDataSourceOptions`, 앱과 마이그레이션 명령이 함께 쓴다)에는 넣지 않는다. 같은 앱 계정의 모든 잠금 대기에 걸린다.
- 계정 설정은 새 연결부터 적용되므로 설정한 뒤 api를 다시 띄운다.
- 3초는 부하 측정으로 정한 값이 아닌 초기값이다. 결과 반영은 잠금을 쥔 채 후보 등록까지 하므로 경쟁 검사에서 함께 보고, 측정 결과가 나오면 값을 다시 정한다(아래 「측정」·「판단이 필요한 결과」).
- `idle_in_transaction_session_timeout`은 이번에 정하지 않았다.

개발 서버에는 [#310](https://github.com/JminAILab/CatchU/pull/310)이 적용했다. 설정 명령·새 연결의 적용값(앱 `3s`, 마이그레이션 계정 `0`) 확인·DB 초기화 뒤 다시 거는 방법은 [개발 서버 안내 「순서」](../../deploy/dev-server/README.md#순서) 3단계에 있고, 자동 배포의 서버 안 확인도 앱 계정 상한이 `3s`인지 본다([cd 안내](../../deploy/dev-server/cd/README.md)). 합의는 EKS 운영 DB(#276)에도 같은 값을 옮기기로 했다.

로컬 개발 DB, `npm test`의 기본 연결, 배포 로컬 구성의 앱 계정([`deploy/local-db/init-roles.sh`](../../deploy/local-db/init-roles.sh))에는 상한이 없다. 그 환경의 api는 잠금을 끝까지 기다린다.

## 상한을 넘으면

PostgreSQL이 그 문장을 `55P03`(lock_not_available)으로 끝내고 트랜잭션은 롤백된다. HTTP 요청은 공통 오류 처리로 `500 INTERNAL_ERROR`(`Cache-Control: no-store`, DB 원문 없음)가 된다.

`lock_timeout`은 **잠금 획득 시도마다 따로** 걸린다([PostgreSQL 16 설정 설명](https://www.postgresql.org/docs/16/runtime-config-client.html#GUC-LOCK-TIMEOUT)). 그래서 요청 하나가 3초보다 오래 기다릴 수 있다.

- 잠금 여러 개를 차례로 기다리는 요청은 잠금마다 3초까지 기다린다. 관찰: 후보 500건 반영과 겹친 같은 키 접수 재응답 하나가 앞 요청 뒤에서 키 잠금을 기다린 뒤 요청 행을 다시 기다려 4.0초 뒤 200을 받았다.
- 같은 행을 다른 요청 뒤에서 기다리면 앞 요청이 쥔 튜플 잠금과 행을 쥔 트랜잭션을 차례로 기다린다. 앞 요청이 포기한 직후 튜플 잠금을 얻으면 다시 3초를 기다린다. 관찰: 같은 요청 행을 결과 수신과 진행 알림이 함께 기다릴 때 앞쪽은 3.0초, 뒤쪽은 6.0초 뒤 실패했다(실행마다 어느 쪽이 길어질지는 다르다).

경로별 결과는 아래와 같다. 후속 동작은 모두 각 기능의 기존 계약이며, 상한 때문에 자동 재시도·재반영을 더하지 않았다.

| 경로 | 기다리는 잠금 | 상한을 넘으면 | 남는 것과 후속 |
|---|---|---|---|
| 링크 발급(최초) | 같은 키 → 회원 발급 | 500 | 링크·멱등 기록 없음(전체 롤백). 같은 키로 다시 보내면 201 |
| 링크 발급(같은 키 재요청) | 같은 키 | 500 | 기존 링크·멱등 기록 그대로. 이후 같은 키 200 |
| 개발 로그인 | 회원 신원 | 500, 쿠키 없음 | 회원·프로필·세션 없음. 다시 로그인하면 200 |
| Google 로그인 | 회원 신원 | 500, 쿠키 없음 | 회원·세션 없음. 로그인 시도는 DB 작업 전에 소비돼 같은 시도는 `401 AUTH_INVALID`이고 새 인증으로 로그인한다([Google 로그인](google-login.md)) |
| 세션 갱신·로그아웃 | 세션 행 | 500, `Set-Cookie` 없음 | 이전 Refresh·세션 그대로(폐기 안 함). 같은 쿠키로 다시 하면 200·204([세션 안내](auth-sessions.md)) |
| 분석 접수(신규) | 같은 키 → 회원 접수 | 500 | 요청·동의·시도·멱등 기록 없음. 같은 키로 다시 보내면 202 |
| 분석 접수(같은 키 재응답, 진행 중 요청이 있는 다른 키) | 요청 행(멱등 소유 확인 `FOR KEY SHARE`, 상태 읽기) | 500 | 기존 요청·동의·시도·멱등 기록 그대로, 다른 키 기록 없음. 이후 둘 다 200 |
| worker 맥락 조회 | 요청 → 시도 행(`FOR SHARE`) | 500 | 상태 변화·자격정보 반환 없음. 다시 조회하면 200 |
| 결과·진행 알림 수신 | 요청 → 시도 행 | `ReceiverStorageError`(큐 작업은 `RECEIVER_STORAGE_UNAVAILABLE`) | 수신 기록·Receipt 없음. worker는 결과를 다시 보내지 않으므로([worker 「보장하지 않는 범위」](../../worker/README.md#보장하지-않는-범위)) 요청은 접수 60분 판정에서 처리 시한 실패로 닫힌다 |
| 결과 반영 ① 초기 잠금 | 요청 → 시도 → 수신 기록 행 | 반영 실패(`STORAGE_UNAVAILABLE` 로그) | 수신 기록만 남고 시도는 `PENDING`(실패 항목 없음). 같은 결과 재전달은 `DUPLICATE`로 재반영하지 않고, 접수 60분 판정에서 `APPLY_FAILED`/`CLOSED`([시한 닫기](analysis-deadline.md)) |
| 결과 반영 ② 반영 중 | 저장소 관측 잠금, 회원·작업별 등록 잠금 등 | 반영 실패(`STORAGE_UNAVAILABLE` 로그) | 보호 기록·Catch·근거·후보 연결 전체 롤백. 별도 트랜잭션이 `APPLY_FAILED`와 실패 항목(`APPLICATION`/`STORAGE_UNAVAILABLE`)을 기록하고 다음 판정(1분 주기)에서 닫힌다 |
| 결과 반영 ③ 실패 기록 중 | 요청 행(실패 기록 트랜잭션) | `FAILURE_RECORDING_FAILED` 로그 | 시도는 `PENDING`, 실패 항목 없음. ①과 같이 접수 60분 판정에서 닫힌다 |
| 시한 닫기 | 요청은 `SKIP LOCKED`라 기다리지 않음. 요청을 잡은 뒤 시도 행 | 그 요청만 실패로 셈(`QueryFailedError:55P03` 로그), 나머지는 계속 | 그 요청은 그대로이고 다음 판정에서 닫힌다. 제품 경로는 시도보다 요청을 먼저 잠가 이 대기는 시험에서만 만들었다 |

운영의 받기 소비자는 동시 1이다([큐 연결 「받기」](analysis-queue.md#받기)). 한 api 안에서는 결과·진행 알림 수신이 다른 결과의 반영과 겹치지 않는다. 반영 중 수신 경쟁은 api가 여럿일 때의 경우다. HTTP 요청(접수 재응답·같은 회원의 새 접수·worker 맥락 조회)과 시한 닫기는 한 api에서도 반영과 겹친다.

## 측정

2026-10-18 로컬에서 시험 파일마다 2~4회 실행한 범위다. Windows 11의 Docker Desktop에서 PostgreSQL 16 컨테이너를 쓰고, api와 DB가 같은 컴퓨터에 있으며 다른 부하는 없다. 잠금을 쥐는 쪽은 테스트 DB 계정 연결(계정 상한 없음, 시험이 멈추지 않게 그 트랜잭션에만 20초)이고, 기다리는 쪽은 시험 전용 앱 계정(3초)으로 띄운 api다.

**정상 경쟁**: 약 1초 쥔 잠금은 모두 기다린 뒤 성공했다(개발 로그인·세션 갱신·분석 접수·worker 맥락 조회·시한 닫기 1.03~1.07초). 동시 요청은 아래와 같다.

| 동시 요청 | 결과 | 응답 시간 |
|---|---|---|
| 같은 신원 개발 로그인 5건 | 모두 200, 회원 1명·세션 5개 | 42~89ms |
| 같은 신원 Google 로그인 3건 | 모두 200, 회원 1명 | 15~48ms |
| 같은 Refresh 토큰 갱신 3건 | 200 1건·401 2건, 세션 폐기(기존 재사용 감지 계약) | 21~30ms |
| 첫 분석 접수 10건(같은 키 5·다른 키 5) | 202 1건·200 9건, 요청 1개 | 109~228ms |
| 같은 시도 worker 맥락 조회 5건 | 모두 200(서로 막지 않음) | 65~117ms, 약 0.55초 쥔 잠금 뒤 564~587ms |

**강제 상한 초과**: 잠금을 3초 넘게 쥐면 위 표의 결과가 3.0~3.1초 뒤에 났다. 링크 발급은 잠금 전 비밀번호 해시 시간이 더해져 3.2~3.6초다. 반영 ③은 반영과 실패 기록이 각각 기다려 6.4초다.

**후보가 많은 합성 결과의 반영**: 접수 API로 만든 요청에 #103 합성 결과의 후보를 늘려(작업 정체가 모두 달라 후보마다 Catch 1개, 근거 1개) 반영했다. 반영이 요청·시도 행을 쥔 동안 같은 키 접수 재응답 3건, 같은 결과 재전달 1건, 진행 알림 1건, 시한 닫기 1건(동시 6건)을 보냈다.

| 후보 | 반영 보유 | 경쟁 요청 |
|---|---|---|
| 40 | 358~375ms | 모두 기다린 뒤 성공(0.4~0.5초) |
| 100 | 814~857ms | 모두 성공(0.9~1.0초) |
| 300 | 2322~2480ms | 모두 성공(2.4~2.6초) |
| 500 | 3841~3922ms | 맨 앞에서 기다린 요청은 3.0~3.1초 뒤 실패(접수 재응답 500, 수신 저장 실패). 뒤에 줄 선 요청은 실행에 따라 실패하거나 3.9~4.0초 뒤 성공 |

시한 닫기는 매번 반영을 기다리지 않고 1~15ms에 그 요청을 건너뛰었고, 반영 결과(Catch·등록 수, `APPLIED`/`CLOSED`)는 경쟁과 관계없이 같았다. 반영 보유 시간은 후보 수에 거의 비례해 이 환경에서 후보 1건에 약 8ms였다. 이 비율이면 약 370건부터 3초를 넘는다(추정).

**한계**: 한 환경의 몇 번 실행이다. 후보마다 근거 1개인 MOCK 합성 자료이고, api와 DB 사이 네트워크 지연·다른 회원의 동시 부하·운영 DB 사양을 반영하지 않았다. 이 측정만으로 모든 부하에서 3초가 적정하다고 볼 수 없다.

## 판단이 필요한 결과

아래는 기존 계약대로 동작하지만 값·범위를 정할 때 함께 볼 결과다. 재현은 「시험」의 파일로 한다.

1. **후보가 많은 반영과 3초**: worker 결과의 후보 수에는 코드상 상한이 없다([worker 생성 문서](../../worker/docs/generation.md)). 반영은 잠금을 쥔 쪽이라 상한으로 실패하지 않지만, 보유가 3초를 넘으면 그동안 같은 요청의 접수 재응답, 같은 회원의 새 접수(진행 중 요청을 돌려주는 경로), worker 맥락 조회, (api가 여럿이면) 수신이 실패한다. 재현: `lock-wait-limit-application.test.cjs`의 후보 500건 시험.
2. **요청 전체 대기는 3초보다 길 수 있음**: 상한은 잠금 획득 한 번의 값이다. 관찰된 최대는 6.0초(줄 선 수신)·4.0초(줄 선 접수 재응답 성공)다. 요청 전체의 상한이 필요한지는 정하지 않았다.
3. **수신이 상한에 걸리면 결과가 사라짐**: 큐 결과 작업은 재시도하지 않고(`attempts: 1`) worker도 다시 보내지 않으므로, 그 분석 결과는 버려지고 요청은 60분 뒤 실패로 닫혀 회원이 다시 요청해야 한다. 지금 수신이 3초 넘게 기다릴 수 있는 경우는 api가 여럿일 때 같은 요청의 긴 반영과 겹치는 경우뿐이다(그 밖의 경쟁 잠금은 짧다).
4. **반영 실패의 종료 시점 차이**: ②는 1분 안의 다음 판정에서 닫히지만, ①·③은 실패를 기록하지 못해 접수 60분 판정까지 `PENDING`으로 남는다. 그동안 회원은 재요청할 수 없다(기존 재요청 판정).

## 시험

`npm test`가 자동 탐색한다. 상한을 넘기는 시험마다 3초 이상 기다리므로 네 파일을 합쳐 약 1분 30초 걸린다.

| 파일 | 확인하는 것 |
|---|---|
| `test/support/lock-wait-limit.cjs` | 시험 전용 앱·마이그레이션 계정 생성(앱 계정에만 `ALTER ROLE … IN DATABASE <시험 DB> SET lock_timeout = '3s'`)·삭제, 권한 확인, 잠금 쥐기·대기 확인·시간 측정 |
| `test/db/lock-wait-limit-role.test.cjs` | 계정별 설정(앱 계정의 시험 DB 1건뿐), `buildDataSourceOptions`로 연 새 연결의 적용값(앱 `3s`·마이그레이션 계정 `0`·다른 DB `0`), 그 계정으로 띄운 앱의 연결 `3s`, 공통 설정에 상한 없음, 삭제 뒤 계정·설정 없음. 3초 조건의 링크 발급 두 잠금 시험, 개발·Google 로그인, 세션 갱신·로그아웃 |

| `test/db/lock-wait-limit-worker-context.test.cjs` | 요청·시도 행을 쥔 동안의 worker 맥락 조회, 정상 대기와 동시 조회 |

| `test/db/share-links-key-lock.test.cjs` + `test/support/share-link-lock-cases.cjs` | 링크 발급 두 잠금 시험을 이 파일의 앱 연결에만 주입한 500ms에서 돌린다(적용값을 시험이 확인). 같은 시험을 위 계정 파일이 3초 조건에서 돌린다 |

- 연결 시작 옵션(`-c lock_timeout=500ms`)은 계정 설정보다 우선한다. 시험 파일은 각자 다른 프로세스에서 하나씩 돌므로(`--test-concurrency=1`) 500ms 주입이 계정 파일에 닿지 않고, 각 파일이 자기 적용값을 확인한다.
- 계정은 DB 서버 전체에 생기므로 시험이 끝나면 지운다. 이름은 `catchu_t220_app_<난수>`·`catchu_t220_mig_<난수>`이고 비밀번호는 실행마다 만든 난수이며 로그에 남기지 않는다. 실행을 강제로 끊어 계정이 남았으면 테스트 DB 서버에서 `SELECT rolname FROM pg_roles WHERE rolname LIKE 'catchu\_t220\_%'`로 찾아 `DROP OWNED BY <이름>; DROP ROLE <이름>;`으로 지운다.
- 테스트 DB 계정에 역할 생성 권한(superuser 또는 CREATEROLE)이 필요하다. [README 「DB 테스트」](../README.md#db-테스트)의 `docker run` 계정과 CI의 PostgreSQL 서비스 계정은 superuser다. 권한이 없으면 로컬에서는 3초 시험을 이유와 함께 건너뛰고, `CI=true`(GitHub Actions)에서는 건너뛰지 않고 실패한다. 2026-10-18 CREATEROLE 없는 계정으로 두 동작을 확인했다.
- 시험 앱 계정은 자료 읽기·쓰기만 받고(운영 앱 계정과 같은 범위), 시험 마이그레이션 계정은 접속만 받아 적용값 확인에만 쓴다. 비밀번호는 16진수 난수라 SQL 따옴표를 깨지 않는다.
