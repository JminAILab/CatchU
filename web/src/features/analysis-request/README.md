# 저장소 선택·동의·분석 요청과 재분석 (D, #154)

현행 U7은 [직접 주소 등록](../repository-management/README.md#현행-u7-직접-등록--424) 후 본인 등록을 고른다. 하단 제목은 「저장소 등록과 분석 요청」이다. 등록 완료와 접수는 별개이며 현재 고지·새 동의가 필요하다. `DAILY_LIMIT_REACHED`의 429는 확정된 하루 제한이므로 키를 놓고 한국 시간 다음 날 안내를 한다. 아래 빈도 제한의 `RATE_LIMITED` 429는 같은 키·본문을 유지한다. 관측 세 필드는 상태 응답에서 검사하며 NONE/UNKNOWN/FOUND와 수집 한계를 구분한다. 고지는 2026-10-30 [#424 팀장 확정](https://github.com/JminAILab/CatchU/issues/424)의 `catchu-real-analysis-notice-v2`를 API에서 읽는다. 같은 결정으로 최신 분석이 끝나면 결과와 관계없이 새 동의·하루 제한 아래 재분석하며 기존 Catch와 설명을 유지하고 새 작업만 더한다.

[저장소 연결 관리 모달](../repository-management/README.md)(#153) 아래쪽 **연결할 수 있는 저장소** 영역이다. 서버가 허용한 저장소를 고르고, 현재 분석 안내(고지)를 버튼 앞에 보인 뒤 **[동의하고 분석 요청]** 하나로 동의와 첫 요청을 보낸다. 정본은 [web 기능 설계 W2·「내 자산 화면 구조」](../../../../aidlc/spaces/default/intents/260914-catchu-october-mvp/construction/u1-web/functional-design/functional-spec.md)와 [회원 API](../../../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/contract-design/member-api.yaml)의 `GET /analysis-notice`·`POST /analysis-requests`, 서버 동작은 [api 분석 고지·접수](../../../../api/docs/analysis-intake.md)다.

「연결된 저장소」의 재분석이 허용된 최신 요청에는 아코디언 안에 **[동의하고 다시 요청]**을 둔다(아래 「재분석」). 첫 요청과 재요청은 같은 상태 객체가 맡아 한 번에 하나만 보내고, 접수·거부 결과에 따라 「연결된 저장소」를 실제 이력(#140)으로 다시 읽는다.

## 파일

| 파일 | 역할 |
|---|---|
| `analysis-request-api.ts` | 고지 조회와 접수 POST, 응답 검증. 202는 새 접수, 200은 기존 작업. 그 밖의 2xx·계약과 다른 본문·다른 저장소의 상태는 접수 여부를 모르는 결과로 돌려준다 |
| `analysis-request-store.ts` | 선택·고지·요청·재요청 상태, 멱등 키·본문 붙잡기, 오류 코드별 안내. 화면과 분리한 상태 객체 |
| `analysis-request-section.tsx` | 영역 화면(`AnalysisRequestSection`)과 아코디언 안 재요청(`RetryRequest`). 고지 본문은 React 텍스트로만 그리고 줄바꿈은 CSS(`white-space: pre-line`)로 살린다 |

## 조립

`RepositoryManagement`가 상태 객체를 만들어 모달을 닫아도 유지하고, 컴포넌트가 내려가면(회원 변경·화면 이동) 버린다. `requestApi`를 생략하면 `api.member`로 만든 제품 호출을 쓴다. 미리보기·시험은 합성 호출을 넘긴다. `connectSection`을 넘기면 이 영역 대신 그것을 그린다.

`connectionNotice`(`DISCONNECTED`·`REAUTH_REQUIRED`·`CHECKING`)는 #153 조립이 연결 상태로 정한다. 값이 있으면 입력 단계에서 저장소 선택·분석 안내·[동의하고 분석 요청] 대신 재연동 안내(또는 확인 중)를 보인다. 요청 중·응답 불명·빈도 제한의 표시와 [같은 요청 다시 보내기], 결과 안내는 바꾸지 않으며 상태 객체의 판정·키 처리도 그대로다. 규칙은 [저장소 연결 관리 표시 규칙](../repository-management/README.md#표시-규칙)을 따른다.

선정 목록은 `RepositoryApi.analyzableRepositories`로 읽는다. 같은 `GET /me/repositories`를 계약 `Repository`의 필수 필드인 `allowedScopeRevision`까지 검증한다(빈 값·문자열 아님·누락이면 목록 전체를 조회 실패로 본다). #153의 이름 결합용 `repositories`는 바꾸지 않았다.

## 동작

- **본문:** `repositoryId`, `consent.accepted=true`, 현재 고지의 `noticeRevision`, 고른 저장소의 `allowedScopeRevision`. 고지·목록이 준비되고 고른 저장소가 목록에 있을 때만 버튼이 켜진다.
- **중복 제출:** 누르는 즉시 요청 중으로 바꿔 입력과 버튼을 막는다.
- **결과 안내:** 202는 접수(분석 완료 아님), 200은 이 저장소에 이미 접수된 요청이 있어 새 요청을 만들지 않았다는 안내다. 응답 불명 뒤 재전송에서 200을 받아도 그 요청이 앞선 시도로 만들어졌다고 특정하지 않는다(서버의 200은 같은 키 재전송과 같은 저장소의 진행 중 작업 반환을 모두 포함한다). 둘 다 선택을 풀고 열려 있는 「연결된 저장소」를 다시 불러온다. 그 조회는 따로 표시되며, 실패해도 접수 안내는 그대로이고 POST를 다시 보내지 않는다. 접수 안내는 「연결된 저장소」에서 상태를 확인할 수 있다고 단정하지 않는다.
- **접수 응답 검증:** 200·202 모두 `AnalysisStatus`의 필수 필드·타입·enum·0 이상의 정수 개수·시각과 시간대, `retry`·실패 항목(`candidateId`가 있으면 비어 있지 않은 문자열)까지 확인한 뒤 화면용 요약으로 바꾼다. 추가 응답 필드는 공통 클라이언트 규약대로 무시한다. 200의 종료된 현재 상태도 허용하며 서버의 업무 판정을 다시 하지 않는다. 기존 이력 목록 해석은 바꾸지 않는다.
- **응답 불명:** 조회 실패·5xx·계약과 다른 성공 응답이면 키와 본문을 붙잡고 **[같은 요청 다시 보내기]**만 보인다. 자동으로 다시 보내지 않고, 새 키를 만들지 않는다. 모달을 닫았다 열거나 다른 저장소를 누르려 해도 붙잡은 요청은 바뀌지 않는다(그동안 목록·고지를 다시 읽지 않는다). 보관 범위와 한계는 아래 절을 따른다.
- **빈도 제한(429):** 이번 시도는 처리되지 않은 것으로 안내하고 키·본문을 유지한다. 앞선 시도가 응답 불명이었다면 그 접수 여부는 여전히 모르는 것으로 남긴다. 유효한 `Retry-After`(1 이상의 정수 초)가 있으면 남은 초를 보여 주고 **[같은 요청 다시 보내기]**를 막는다. 상태 객체도 기한 전 `resend()` 직접 호출을 거부한다. 기한이 지나면 버튼만 켜지며, 사용자가 눌러야 같은 키·본문으로 보낸다. 다시 429를 받으면 새 응답의 기한으로 기다린다. 헤더가 없거나 잘못된 형식이면 시간을 추정하지 않고 같은 키·본문의 재전송을 바로 허용한다.
- **확정 거부(4xx, 401·429 제외):** 키를 놓고 다음 요청은 새 키로 보낸다. 403은 코드로 나눈다.
- **보내지 않음(공통 인증 통합 시험 전환을 켰을 때):** 재인증 필요·로그아웃 처리 중 등으로 공통 인증이 요청을 보내지 않으면(`memberMutationOutcome()`의 `not-sent`) 결과 불명으로 만들지 않는다([#286 기준 2](https://github.com/JminAILab/CatchU/issues/286#issuecomment-6207895584)). 앞선 시도가 없으면 선택·동의를 둔 채 입력 단계로 돌리고 「지금은 요청을 보내지 않았습니다. 입력은 그대로 두었습니다.」로 안내한다. 다시 누르면 그때의 인증 상태로 보낼지 정한다. 앞선 시도가 응답 불명이거나 빈도 제한 뒤라면 붙잡은 키·본문을 그대로 두고 이번에 보내지 않았다는 문장을 알린다. 자동으로 다시 보내지 않는다. 보낸 뒤 로그인이 바뀌어 반영하지 않은 응답(`discarded`)은 응답 불명이다. 전환을 끈 기본 호출에는 이 구분이 없다. 재요청도 같다.

| 코드 | 안내·동작 |
|---|---|
| 403 `CONSENT_REQUIRED` | 고지·범위 판본이 바뀌었다. 고지와 목록을 다시 읽고, 사용자가 버튼을 다시 눌러야(새 동의) 새 키로 보낸다 |
| 403 `GITHUB_CONNECTION_REQUIRED` | GitHub 연동 확인 링크 |
| 403 `REPOSITORY_NOT_ALLOWED` | 선택을 풀고 목록을 다시 읽는다 |
| 403 `REPOSITORY_PRIVATE` | 비공개이거나 없는 저장소라 확인할 수 없다는 안내와 공개 주소 확인 요청 |
| 422 `REPOSITORY_UNVERIFIED` | GitHub에서 확인하지 못했다는 안내와 잠시 후 재시도 요청. 비공개로 단정하지 않음 |
| 그 밖의 403 | 지금은 요청할 수 없음(재동의를 유도하지 않음) |
| 409 `ANALYSIS_IN_PROGRESS` | 다른 저장소가 진행 중. 「연결된 저장소」를 다시 불러온다 |
| 409 `REANALYSIS_DEFERRED`·`RETRY_NOT_ALLOWED` | 이 저장소의 이전 요청 때문에 새 요청으로 받지 않음. 재분석 사유로 바꾸지 않는다 |
| 400 | 고지와 목록을 다시 읽는다 |
| 401 | 로그인 안내. 앞선 시도가 응답 불명이었으면 상태 객체가 유지되는 동안 그 요청을 계속 붙잡고, 앞선 불명 안내를 지우지 않은 채 이번 시도가 처리되지 않은 이유(로그인은 연장됐지만 인증 오류로 거부됨 / 로그인 필요)를 알린다. 이번 401로 앞선 시도를 미접수로 확정하지 않는다. 앞선 결과 불명이 없으면 서버의 인증 단계에서 거부돼 접수 기록이 남지 않은 요청이라 키·본문을 놓고(다시 누르면 새 키) 선택은 둔다. 이때 로그인이 연장됐으면 「로그인이 연장되었습니다. 다시 눌러 주세요.」, 아니면 로그인 안내다. 인증 통합을 끈 화면에서는 공통 401 처리로 로그인 화면으로 이동하므로 상태 객체와 붙잡은 요청이 사라지며, 로그인 뒤 복원하지 않는다(아래 「붙잡은 요청의 보관 범위와 한계」) |

- **고지 조회:** 403이면 조회 실패와 나눠 ‘지금은 분석을 요청할 수 없음’으로 보이고 재동의를 유도하지 않는다. 선정 목록 403 `GITHUB_CONNECTION_REQUIRED`는 연동 확인 링크를 보인다.
- **「연결된 저장소」 갱신:** 접수(202·200)와 상태를 바꿨을 수 있는 거부(409 `ANALYSIS_IN_PROGRESS`·`REANALYSIS_DEFERRED`·`RETRY_NOT_ALLOWED`·`IDEMPOTENCY_CONFLICT`, 재요청의 404)는 모달이 열려 있으면 이력(`GET /analysis-requests`, #140)을 다시 읽는다. 그 조회가 실패하면 목록 자리에 조회 실패(‘분석이 실패한 것은 아닙니다’)가 보이고 접수 안내는 그대로이며 POST를 다시 보내지 않는다. 응답 불명은 접수 결과가 아니라서 다시 읽지 않는다([상태 새로고침]으로 확인).

## 재분석

- **제공 조건:** 「연결된 저장소」의 저장소별 최신 요청이 서버 이력에서 `retry.allowed=true`일 때만 아코디언 안에 보인다. 화면은 처리·반영 상태나 `retry.reason`으로 허용 여부를 다시 계산하지 않는다. 완료한 정상 결과·0건·부분 결과·실패도 서버가 허용하면 보이며, 진행·반영·복구 중에는 서버 판정대로 막는다. 완료된 분석의 새 사유 `ANALYSIS_FINISHED`도 응답으로 읽는다.
- **새 동의:** 현재 고지(`GET /analysis-notice`)를 버튼 앞에 다시 보이고, 본문에 현재 `noticeRevision`과 그 저장소의 현재 `allowedScopeRevision`, `retryOfRequestId`(그 최신 요청 ID)를 싣는다. 이전 요청의 동의를 다시 쓰지 않는다. 고지·선정 목록이 준비되지 않았거나 그 저장소가 선정 목록에 없으면 버튼을 끈다.
- **키:** 입력 단계에서만 받으므로 새 키로 보낸다. 요청 중·응답 불명·빈도 제한·늦은 응답·중복 클릭은 첫 요청과 같은 규칙이며, 응답 불명이면 같은 키·같은 본문(재요청 참조 포함)의 [같은 요청 다시 보내기]만 쓴다. 다른 요청(첫 요청이나 다른 저장소의 재요청)이 붙잡혀 있으면 재요청 버튼 대신 아래 영역에서 결과를 확인하라는 안내를 보인다.
- **결과 안내:** 요청 중·응답 불명·결과 안내와 [같은 요청 다시 보내기]는 모달 아래쪽 요청 영역 한 곳에서 보인다(「연결된 저장소」 조회가 실패해도 남아 있어야 하므로). 202는 ‘다시 요청을 접수했습니다’, 그 밖은 첫 요청과 같다.

| 재요청 거부 | 안내·동작 |
|---|---|
| 409 `RETRY_NOT_ALLOWED` | 지금 다시 요청할 수 없음. 「연결된 저장소」를 다시 읽어 서버의 현재 판정을 보인다(그사이 다른 요청이 생겨 최신 요청이 바뀐 경우 등) |
| 404 `RESOURCE_UNAVAILABLE` | 다시 요청할 이전 요청을 찾지 못함. 기존 작업 ID를 추정하지 않고 다시 읽는다 |
| 409 `REANALYSIS_DEFERRED`·`ANALYSIS_IN_PROGRESS`, 403 | 첫 요청과 같은 안내. 403 `CONSENT_REQUIRED`는 고지·목록을 다시 읽고 사용자가 다시 눌러야 새 판본·새 키로 보낸다 |

첫 요청이 409 `RETRY_NOT_ALLOWED`를 받으면(같은 저장소에 이전 요청이 있음) 재요청으로 바꿔 보내지 않고 「연결된 저장소」에서 최신 상태를 확인하도록 안내한다.

## 붙잡은 요청의 보관 범위와 한계

붙잡은 키·본문과 429 대기 기한은 `RepositoryManagement`가 만든 상태 객체의 메모리에만 있다. 같은 회원이 내 자산 화면에 머무는 동안(모달 닫기·다시 열기 포함)만 유지되고, 새로고침·화면 이동·회원 변경·탭 종료로 사라진다. 모달을 다시 열어도 대기 기한은 새로 시작하지 않으며, 상태 객체의 `dispose()`는 키·본문과 대기 기한을 함께 초기화한다. 영속 저장(localStorage 등)과 붙잡은 요청을 버리는 기능은 두지 않았다. 서버가 계속 응답하지 못하면 화면에서 할 수 있는 일은 같은 요청 다시 보내기뿐이다.

**사용자 주도 재로그인·로그아웃(통합 시험 전환을 켰을 때):**

- 미확정 요청은 공통 등록 수단(`unsaved-changes.ts`)에 `unconfirmed-analysis-request` 사유로 등록한다(O-3). 판정은 상태 객체의 `holdsUnconfirmedRequest()`이며 대상은 요청 중·응답 불명·앞선 결과 불명이 남은 429 대기(그 뒤 보내지 않음 포함)다. 입력 단계(아직 안 보냄·최초 보내지 않음·연장 뒤 401·확정 뒤)와 앞선 결과 불명이 없는 429 대기는 대상이 아니다. 등록은 `RepositoryManagement`가 상태 객체가 살아 있는 동안(모달 닫기와 무관) 두고 화면이 내려가면 푼다. 판정은 확인하는 순간 상태 객체를 읽는다. 이 사유는 저장하지 않은 입력(`hasUnsaved()`)으로 세지 않는다.
- 이동 전 확인 창·문구·취소와 계속은 확인 흐름(#287)이 사유를 읽어 정한다([#287 A 답변](https://github.com/JminAILab/CatchU/issues/287#issuecomment-6310239160)). 취소하면 이동·로그아웃 요청 없이 머물고 키·본문·안내가 남는다. `login-changed`는 가드가 화면을 이미 정리했으므로 묻지 않는다.
- 같은 세션의 Access 갱신, 재인증 필요, 로그아웃 진행 중·확정 실패·결과 불명 동안에는 붙잡은 키·본문·안내를 그대로 둔다.
- 로그아웃 확정 성공·새 로그인·회원 변경으로 기존 로그인 범위가 폐기되거나, [다시 로그인]으로 내 자산 화면을 떠나면 화면이 해제되어 붙잡은 요청 상태가 정리된다. 다른 탭 로그인·회원 변경 감지 때의 즉시 정리는 [팀장 결정 2](https://github.com/JminAILab/CatchU/issues/251#issuecomment-6206414443)대로다.
- 정리되는 것은 이 화면의 키·본문·결과 확인 정보이며 서버 요청은 취소되지 않는다(취소 API 없음). 앞선 요청의 상태는 다시 로그인한 뒤 「연결된 저장소」(#140)에서 확인한다.

**같은 키·같은 본문 재전송(키를 붙잡고 있을 때):** 서버에 그 키의 접수 기록이 저장돼 있어야 저장된 응답 대상의 **현재 상태**를 200으로 돌려준다(이때는 연결·선정·판본을 다시 검사하지 않는다). 앞선 시도가 저장되지 않았다면 기록이 없으므로 재전송은 새 접수와 같은 판정을 받아 202이거나 거부 응답(예: 그사이 판본이 바뀌었으면 403 `CONSENT_REQUIRED`)일 수 있다. 화면은 받은 응답대로 안내한다.

**키를 잃은 뒤:** **앞선 요청이 접수됐는지 화면이 확인할 방법이 없다.** 이후 사용자가 다시 누르는 요청은 새 키·새 본문의 새 요청이며, 그 결과는 서버의 신규 접수 판정([`analysis-intake.service.ts`](../../../../api/src/analysis-intake/analysis-intake.service.ts) `create`)을 따른다. 아래 응답은 신규 접수 제한의 결과일 뿐 앞선 요청의 결과를 알려 주는 복구가 아니다. 표는 GitHub 연결·선정 대상·동의(고지·범위 판본) 등 선행 검사를 통과했다는 전제의 결과다. 선행 검사에 걸리면 표의 응답 대신 그 403이 먼저 나온다.

| 앞선 요청의 실제 상태 | 새 키 요청의 서버 응답 |
|---|---|
| 저장되지 않음 | 다른 조건이 맞으면 202 새 접수 |
| 저장됐고 ACTIVE, 같은 저장소 | 200, 그 ACTIVE 요청을 그대로 돌려줌(새 동의·요청 없음) |
| 저장됐고 ACTIVE, 다른 저장소로 요청 | 409 `ANALYSIS_IN_PROGRESS` |
| 저장됐고 닫힘, 정상 완료·0건·부분 결과·실패 등 | `retryOfRequestId`가 없으면 409 `RETRY_NOT_ALLOWED`. 「연결된 저장소」에서 최신 요청을 확인하고 [동의하고 다시 요청]으로 새 동의·최신 요청 참조를 보낸다 |

- 연결·선정·고지/범위 판정이 ACTIVE 확인보다 먼저라, 그사이 판본이 바뀌었으면 위 경우에도 먼저 403 `CONSENT_REQUIRED`가 나온다.
- 저장된 접수 기록이 있는 같은 키·같은 본문 재전송만 앞선 요청을 그대로 확인하는 경로다. 키를 잃으면 이 경로를 쓸 수 없다.
- 서버의 200은 같은 키 재전송인지 같은 저장소 ACTIVE 반환인지 응답으로 구분되지 않는다.
- 앞선 요청의 실제 상태 확인은 「연결된 저장소」(분석 이력 조회)에서 한다.

## 검사

`npm test`의 `test/analysis-request-auth-outcome.test.mjs`: 보내지 않음·반영하지 않은 응답·연장 뒤 401과 앞선 결과 불명의 조합별 안내·키·본문 처리. `test/analysis-request-unconfirmed.test.mjs`: 미확정 요청 판정의 상태별 대상 여부(재요청 포함)와 공통 등록 연결. 둘 다 합성 응답이다.

`npm test`의 `test/analysis-request.test.mjs`·`test/analysis-request-rate-limit.test.mjs`·`test/analysis-request-response.test.mjs`·`test/analysis-request-retry.test.mjs`: 판본 필드 검증, 고지 응답, 접수 응답 필수 필드·중첩 형식 오류와 429 뒤 잘못된 200의 키 보존, 202·200·409·403 코드별 처리, 중복 클릭, 응답 불명 뒤 같은 키·본문 재전송, 429 대기 기한·직접 재전송 차단·무효 헤더·기한 갱신, 늦은 응답, 모달 재열기 유지·초기화, 접수 성공과 상태 조회 실패의 분리, 실패 재요청의 제공 조건·본문(새 판본 동의·`retryOfRequestId`)·새 키·응답 불명 뒤 같은 키·본문·거부 코드별 안내와 상태 갱신, 재요청의 429 대기 중 재전송 차단·대기 뒤 같은 요청 재전송, 응답 불명 뒤 401의 키·본문 유지(같은 상태 객체 안. 실제 로그인 이동·복원은 검사하지 않음). 모두 합성 응답이다. 미리보기는 `/preview/repository-management?intake=…`(값은 화면 위쪽 안내). `intake=limited`는 최초 전송에서 3초 제한을 받고, 기한 뒤 사용자가 같은 요청을 다시 보내면 202로 접수되는 합성 시나리오다. 재요청은 `failed-repo`·`closed-*` 저장소를 펼쳐 보며, `intake=retry-not-allowed`·`retry-missing`이 재요청 거부를 흉내 낸다.
