# 내 자산 목록·상세와 회원 페이지

B 담당의 제품 `/assets`와 개발용 미리보기를 관리한다. 제품 페이지는 공통 회원 가드·API 클라이언트를 사용하며 합성 자료로 조회 실패를 대체하지 않는다. `/preview/assets`·`/preview/assets-connected`의 자료만 합성이다.

## 제품 페이지 연결 (#168·#169)

`src/app/(member)/assets/page.tsx`가 `AssetsMemberPage`를 연다. `(member)`의 `MemberShell`이 로그인·헤더를 담당하고 `AssetsMemberBoundary`가 회원 변경 시 저장소 이름·Catch 목록/상세·D 모달을 함께 초기화한다. 별도 로그인·토큰 저장소를 만들지 않는다.

- `web/.env.example`에 따라 `NEXT_PUBLIC_API_BASE_URL`을 API 주소(`/v1` 제외)로 설정한다. 개발용 로그인은 web과 api 양쪽에서 허용할 때만 사용한다. 실행 안내는 [공통 web README](../../../README.md)를 따른다.
- `/assets`에 들어가면 미인증 상태는 `/login?next=…`로 이동한다. 로그인 후 저장소 필터와 Catch 상세 주소로 돌아간다. 현재 메모리 토큰은 새로고침 시 다시 로그인이 필요하며 실제 Google OAuth 연결을 의미하지 않는다.
- B 조회·저장은 `createCatchApi(api.member)`, D 모달은 `createRepositoryApi(api.member)`를 사용한다. 두 인스턴스와 `accessTokenStore`는 모듈 수준의 안정적인 객체다.
- 저장소 이름은 별도로 조회한다. 로딩·실패는 필터 아래에 표시하며 Catch 목록·상세를 숨기지 않는다. 정상 0건과 실패를 구분하고, 이름을 몰라도 URL 필터와 조회된 Catch를 유지한다. 이름 다시 불러오기는 Catch의 필터·페이지·저장 결과를 초기화하지 않는다.
- D 일반 닫기는 B 목록을 갱신하고 저장소 이름도 다시 조회한다. [이 저장소 Catch 보기]는 선택한 저장소의 목록과 이름을 갱신하며 일반 닫기 콜백을 추가 호출하지 않는다.
- 새 저장소 선택·동의·분석 요청은 [#154](https://github.com/JminAILab/CatchU/issues/154)의 `connectSection`, GitHub 연동·복귀는 회원 담당 화면에서 연결한다. 제품 조립만으로 이 기능들이 구현된 것은 아니다.

연결 기반은 [#185 공통 인증](https://github.com/JminAILab/CatchU/pull/185)·[#187 저장소 관리](https://github.com/JminAILab/CatchU/pull/187)다. 실제 API에는 `/me`, `/me/repositories`, `/analysis-requests`와 B Catch 조회·저장 경로가 필요하다. 없는 API를 모의 성공 응답으로 바꾸지 않는다. 검증 시 실제 서버·DB와 합성 HTTP 대역을 구분한다.

## 실행

`web/README.md`의 Node.js 24.21.0 환경에서 `npm ci`, `npm run dev`를 실행하고 `/preview/assets`를 연다. 개발 모드에서만 제공하며 `npm run build` 뒤 `npm run start`에서는 404다. 기본 `/`와 공통 레이아웃을 바꾸지 않는다.

## 확인할 동작

- Catch 탭의 저장소 필터로 예시를 고르고 카드 제목 또는 카드를 눌러 상세 팝업을 연다.
- 제목은 계약대로 문자열 또는 `null`이다. `null`이면 대체 제목 없이 목록·상세의 제목을 생략하고, 카드의 [상세 보기]로 열고 닫은 뒤 같은 버튼으로 초점을 돌려준다. `synthetic-catch-api-pagination`이 제목 없이 설명은 생성된 합성 예시다. 목록·상세·확인/불일치/공개 저장 응답에 같은 검사를 쓰며 누락·빈 문자열·잘못된 타입은 계속 거부한다.
- 닫기·목록으로 돌아가기·Escape로 닫아도 저장소 필터가 유지된다. 브라우저 뒤로 가기·앞으로 가기와 새로고침으로 필터와 상세를 복원한다.
- 다른 세 탭은 준비 중 안내를 보여 준다.
- 화면 위 **개발용 미리보기 도구**에서 목록의 정상·빈 자료·조회 중·조회 실패를 선택한다. 상세 상태는 팝업을 열기 전에 선택한다. 이 선택기는 제품 기능이 아니다.
- 조회 실패에서 다시 불러오기는 정상 합성 화면으로 돌아간다. 네트워크 요청이나 재분석을 실행하지 않는다.
- 초안·질문의 생성 실패와 미생성을 정상 생성으로 바꾸지 않는다. 확인 완료·불일치·공개 설정·원본 비공개 제한은 독립적으로 표시한다.
- 확인·불일치·공개/숨김을 저장하는 동작과 질문 답변 저장은 없다. 근거 주소도 합성이므로 외부 링크로 열지 않는다.

## 연결 경계와 제안

현재 `/preview/assets`는 개발용 주소다. 실제 내 자산 주소·회원 가드·헤더·공통 스타일은 [#106](https://github.com/JminAILab/CatchU/issues/106)에서 조율한다. 이번 CSS 모듈은 이 미리보기에만 적용하며 새 스타일 도구를 도입하지 않는다.

미리보기 래퍼의 바깥 여백은 `0`이며 `body` 여백을 음수 값으로 상쇄하지 않는다. 독립 미리보기에서는 브라우저 기본 `body` 여백 8px을 허용하고, [공통 레이아웃 PR #171](https://github.com/JminAILab/CatchU/pull/171)의 `body { margin: 0; }`과 합치면 바깥 여백도 0이 된다. 연결할 때 좌우 잘림과 가로 스크롤이 없는지 확인한다.

| 연결 | 이번 구현·제안 |
|---|---|
| 실제 페이지 주소 | 제품 `/assets`를 위 「제품 페이지 연결」 구성으로 조립한다. |

## 목록 API 연결 구성 (#168)

`AssetsConnected`는 #106의 인증 가드 안에 넣는 화면이다. 로그인·토큰 저장·제품 경로는 이 기능에서 만들지 않는다. 회원이 바뀌거나 로그아웃하면 `AssetsMemberBoundary`로 화면을 해제하고 새 회원은 새 세대로 마운트한다(아래 연결 방법). `api` 인스턴스는 렌더마다 새로 만들지 않는다.

- `createCatchApi(transport)`: transport는 `/catches` 상대 경로와 method/body/signal/cache를 받아 공통 `ApiResult`를 반환한다. #106이 API 기준 주소·`/v1`·Bearer·401 인증 만료를 처리하고, `readApiResponse`로 응답을 해석한다. PUT의 객체 body는 transport에서 JSON으로 직렬화한다.
- `AssetsConnected`: `repositoryId`·`catchId`를 주소와 맞추며 필터 변경과 뒤로 가기 때 다시 조회한다. 목록에 아직 없는 Catch도 별도 상세 GET으로 연다. 저장소 이름은 Catch 데이터에 없으므로 `repositories`로 공급한다. 이름이 준비되지 않았다고 서버가 반환한 Catch를 숨기지 않는다.
- `assets-store`: 필터별 cursor 초기화, 이전 응답 무시·요청 중단, 동시 재조회 합치기, 다음 페이지 실패 시 기존 목록 유지, 같은 Catch 중복 제거를 담당한다. 조회 실패를 합성 자료나 정상 0건으로 대체하지 않는다.
- D 슬롯의 `onShowRepository(repositoryId)`는 필터 적용·상세 닫기·목록 재조회, `onClosed()`는 현재 필터 재조회다. 저장소 보기로 닫으면 `onClosed`를 추가 호출하지 않는다. 같은 저장소를 다시 골라도 재조회하며, 기존 조회가 진행 중이면 끝난 뒤 새 조회를 한 번 실행한다. 같은 조회 중 반복된 D 갱신은 하나로 합치고, 필터 변경·화면 해제 시 이전 갱신 예약을 버린다. 후속 조회도 실패하면 사용자 재조회를 기다린다. D가 모달을 열기 직전에 `onOpen()`을 호출해 Catch 상세를 먼저 닫는 경계를 추가 제안한다. D의 실제 모달 구현은 #153에 남아 있다.

개발 모드의 `/preview/assets-connected`는 같은 연결 컴포넌트에 **모의 응답**을 주입한다. 더 보기, 저장소 관리 콜백, 상세 직접 진입을 확인할 수 있다. `failure=all` 또는 `failure=detail`을 주소에 넣으면 조회 오류를 재현한다. 이 주소도 프로덕션에서는 404이며 실제 인증·API·DB 검증 증거가 아니다.

검사: `npm test`에서 응답 계약과 요청 순서 역전·필터/페이지·조회 실패를 검사한다. 전체 검사는 `web/README.md`의 `npm run check`를 따른다. #106의 실제 회원 화면 및 #153의 실제 모달 조립은 별도 연결 검증이 필요하다.

실제 B HTTP 연결 검사는 `web/`에서 `node scripts/catches-api-smoke.mjs`로 실행한다. API를 먼저 빌드하고 `CATCH_API_ROOT`에 해당 `api/` 절대 경로를 지정한다(생략하면 `../api`). DB 설정은 API README의 테스트 DB 환경 변수를 사용하며 이름은 `_test`로 끝나야 한다. 검사기는 무작위 스키마에 실제 회원·동의·요청·시도 및 B 마이그레이션을 적용하고, 개발 로그인 HTTP로 받은 토큰을 사용한다. Catch 등록과 E 완료 상태를 같은 트랜잭션에서 준비해 회원별 활성 요청 제약을 지킨다. 종료 시 자기 스키마를 제거한다. 실데이터 DB에 실행하지 않는다. 이 검사는 개발 로그인 HTTP·B API·JWT·PostgreSQL 연결을 확인한다. 자료는 합성이며 E 수신 기록·완료 처리·보호 관찰은 시험 대역이다. #106 로그인 페이지·회원 클라이언트, D 모달, 실제 worker·C 수신자 HTTP는 이 스크립트의 범위가 아니다.

인증 오류 검사에는 [#176](https://github.com/JminAILab/CatchU/pull/176)의 인증 코드 구분이 반영된 API가 필요하다. 토큰 없음(`AUTH_REQUIRED`)과 만료·변조·잘못된 헤더(`AUTH_INVALID`)의 조회 오류를 확인하고, 인증이 끊긴 뒤 확인·불일치·공개·숨김 요청이 대상 Catch의 DB 행을 바꾸거나 성공으로 표시되지 않는지 검사한다. 실패한 재조회만으로 저장 잠금이 풀리지 않고, 유효한 인증으로 다시 조회한 뒤 사용자가 재시도할 때만 저장되는지도 확인한다. 토큰·서명 키는 검사 프로세스 메모리에서만 사용한다.

## 상세 저장 연결 (#169)

CatchActions는 작업 사실·기여를 각각 체크한 뒤 confirmation을 한 번 호출한다. 확인이 성공해도 미공개 상태를 유지하고, [지금 공개]를 별도로 눌러야 visibility를 호출한다. 불일치는 별도 mismatch 호출이며 본문·확인·공개를 자동 변경하지 않는다. 질문 답변이나 설명 편집은 제공하지 않는다.

- 저장 중에는 중복 PUT을 보내지 않는다. 닫기·다른 Catch 이동은 허용하지만 이미 보낸 PUT을 취소했다고 표시하지 않는다.
- 서버 성공 응답으로 상세와 현재 목록의 해당 Catch를 함께 갱신한다. 목록의 페이지·필터와 카드 포커스를 보존하며 저장 전에 시작된 GET 응답이 저장 결과를 덮어쓰지 않게 한다.
- 저장 실패나 접수 불명은 성공 표시 없이 마지막 조회 값을 유지한다. 수동 [현재 상태 다시 불러오기]로 조회에 성공한 뒤 다음 저장을 허용한다. 자동 재저장하지 않는다.
- 원본 보호 상태에서는 공개를 비활성으로 안내하고 서버도 최종 조건을 검사한다. 보호 상태나 초안 없음으로 본인 상세를 차단하지 않는다.
- 개발용 모의 화면에서 저장은 메모리의 합성 자료에만 적용된다. failure=save로 저장 실패를 확인한다. 실제 API 연결 스크립트는 확인 후 미공개, 별도 공개, 불일치 후 공개 유지, 숨김 후 C용 공개 자료에서 제외, 뒤늦은 원본 보호 거절도 검사한다. C의 실제 수신자 HTTP·링크와 전체 로그인 화면은 이 검사에 포함되지 않는다.


배포용 미리보기 차단은 빌드 후 `node scripts/catches-preview-smoke.mjs`로 재현한다(PORT 기본 3119). 전용 서버를 띄워 두 미리보기 경로의 404를 확인하고 검사 프로세스만 종료한다.

제품 조립은 위 구성을 사용하고, 준비 중 탭의 `tab` 주소와 기존 조회 표시를 유지한다. 공통 인증·D 연결은 #106·#153 담당과 검토한다.

## 회원 전환 경계 (#169)

`AssetsMemberBoundary`는 #106 회원 가드 안에서 B 화면을 감싸는 연결 부품이다. 공통 토큰 저장소의 `get()`·`subscribe()`를 받아 토큰이 없으면 자식을 표시하지 않고, 토큰이 바뀌면 하위 화면을 새로 마운트한다. 토큰은 React key·DOM·URL·영구 저장소에 넣지 않고 메모리에서 변경 여부만 비교한다. 같은 토큰의 중복 설정은 화면을 초기화하지 않는다. 토큰 갱신도 안전하게 새 세션으로 취급한다.

아래는 공통 인증 PR #185의 `accessTokenStore`·`api.member`를 사용하는 **클라이언트 컴포넌트의 조립 구조**다. 실제 제품 경로는 `assets-member-page.tsx`를 사용한다. `tokens`에 매 렌더 새 래퍼 객체를 넘기면 세대 추적이 끊기므로 `accessTokenStore` 자체를 넘긴다.

```tsx
const catches = createCatchApi(api.member); // 모듈 수준의 안정적인 인스턴스

<MemberGuard>
  <AssetsMemberBoundary tokens={accessTokenStore}>
    <MemberAssets />
  </AssetsMemberBoundary>
</MemberGuard>
```

`MemberAssets` 안에서 회원별 저장소 자료를 조회하고 `AssetsConnected`와 D 슬롯을 함께 조립한다. 회원별 자료를 경계 밖 부모에 저장해 이전 회원의 props를 다시 전달하면 안 된다. 외부 캐시를 쓰는 경우에도 회원 단위 분리·해제는 별도로 필요하다. 로그인 이동·401 토큰 제거는 공통 가드·API 클라이언트 책임이며 이 경계는 인증 권한을 판정하지 않는다.

화면 해제는 이미 보낸 PUT의 서버 처리를 취소한다는 뜻이 아니다. 기존 `assets-store.dispose()`가 늦은 GET/PUT 응답을 버리며 새 화면은 새 store로 조회한다. 로그인 복귀만으로 확인·불일치·공개·숨김 요청을 다시 보내지 않는다.
검사 범위: `npm test`의 회원 경계 8개 사례는 세대 변경·구독 해제와 store 생명주기를 검사한다. React 재마운트·공통 인증 연결은 별도로 PR #185 `6302c2f`의 토큰 저장소·API 클라이언트를 임시 페이지에 넣고 모의 HTTP로 확인했다. 이전 회원의 지연 GET/PUT 전달, 이전 회원의 늦은 401, 현재 회원 401의 화면 제거, 재로그인 후 PUT 횟수 유지가 통과했다. 검사 중 토큰·회원·Catch는 모두 합성이고 실제 Google 로그인·API·DB·D 모달 연결 증거는 아니다. 임시 페이지와 공통 인증 복사본은 커밋하지 않았다. 제품 조립 후 같은 시나리오를 실제 개발 로그인·B API와 다시 확인해야 한다.

## 저장소 관리 창에서 탭을 떠날 때 (#168·#169)

관리 창이 열린 상태에서 브라우저 뒤로·앞으로 가기로 Catch 탭을 떠나면 D 슬롯이 해제된다. B는 URL의 `tab`과 동기화하면서 `managementOpen`만 해제한다. 이 경로에서 `onClosed`나 목록 재조회를 실행하지 않는다. 일반 닫기의 현재 목록 재조회, [이 저장소 Catch 보기]의 필터 적용·재조회는 기존대로 유지한다. 근거는 [PR #187의 B/D 연결 합의](https://github.com/JminAILab/CatchU/pull/187#issuecomment-5906174447)다.

브라우저 회귀 확인은 PR #187 `f9c143e`의 D 컴포넌트와 이 B 변경을 임시 개발 미리보기에서 조립해 수행했다. 자료·응답은 합성이며 최종 제품 경로·인증·API·DB의 통합 검증은 아니다.

- 포트폴리오 → Catch → 연결 관리 → 브라우저 뒤로 → Catch → 카드: 수정 전 상세가 열리지 않았고, 수정 후 정상으로 열린다.
- 앞으로 가기로 탭을 떠난 뒤 다시 돌아와도 관리 창이 자동으로 열리지 않으며 Catch 상세를 열 수 있다.
- 같은 저장소에서 위 왕복 중 목록 GET·`onClosed` 추가 호출은 각각 0회다. 일반 닫기는 `onClosed`와 목록 GET이 각각 1회 증가한다.
- [이 저장소 Catch 보기]는 `onShowRepository`와 해당 목록 GET만 각각 1회 실행하고 `onClosed`를 추가 호출하지 않는다.

검사용 횟수 표시와 임시 D 미리보기는 제품 코드·이 PR에 포함하지 않는다. 실제 `/assets` 조립 뒤 같은 경로를 다시 확인한다.

## 실제 개발 로그인 연결 검사와 화면 보완 (#168·#169)

- 목록에서 `RESOURCE_UNAVAILABLE`을 받으면 목록 재조회 안내를 표시한다. 상세의 접근 불가 문구와 401의 로그인 안내는 유지한다.
- `100vh`는 독립 미리보기의 바깥 래퍼에만 둔다. `AssetsConnected`는 높이를 강제하지 않으므로 공통 헤더와 함께 배치해도 헤더 높이만큼 페이지가 늘어나지 않는다.
- 검사 스크립트는 실제 회원·분석 기반을 포함한 API 판본이 필요하다. 2026-09-30 확인 판본은 PR #167 `26021c5`다. `CATCH_DB_TEST_REQUIRED=1`과 `TEST_DB_*`를 설정하고 `CATCH_API_ROOT`를 해당 API 폴더로 지정한다.

브라우저에서는 PR #185 `6302c2f`의 개발 로그인 화면·공통 API 클라이언트·회원 가드·CORS와 B 작업본을 임시 폴더에서 조립했다. 실제 Nest HTTP와 일회용 PostgreSQL 스키마를 사용했고, 합성 회원 A의 확인 → 별도 공개 → 불일치 표시 → 숨김이 DB에 저장되는 것을 확인했다. 로그아웃 후 회원 B로 로그인하면 B의 Catch만 보였고, 로그인 복귀 후 A의 Catch 주소 직접 조회는 같은 접근 불가 안내로 거절됐다. 재로그인·조회만으로 추가 PUT이 발생하지 않았다.

공통 헤더 아래 준비 중 탭은 높이 720px 환경에서 문서 높이도 720px, 긴 목록은 1011px로 스크롤을 유지했다. 목록 404는 별도 합성 오류로 안내를 확인했고 상세 404는 실제 API 거부로 확인했다. 임시 `/assets`와 시험용 상태 조회 서버는 PR에 포함하지 않는다. 저장소 표시 이름·분석 결과는 합성이며 E·D·worker·C 전체 연결과 실제 Google OAuth, 이름 미저장 회원 가드는 이번 검증에 포함하지 않는다.
