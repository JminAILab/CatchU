# 후보 묶음과 작업 동일성 — #118

[#118](https://github.com/JminAILab/CatchU/issues/118)의 범위다. 관계 조회까지 마친 수집 결과로 후보를 작업 단위(PR, PR 없이 합친 병합, 커밋 묶음)로 묶는다. 그다음 본인 기여를 확인하고 작업 동일성 값(`workIdentity`)을 만든다. 판정 기준은 작업 동일성 판별 기준 문서들이다.

- [작업 단위와 판정 입력](../../docs/CatchU_work_identity_unit.md)
- [판정 규칙과 값 만드는 법](../../docs/CatchU_work_identity_rules.md)
- [합성 사례·시험·한계](../../docs/CatchU_work_identity_cases.md)
- [기록과 결정](../../docs/CatchU_work_identity_records.md)

2026-10-08·09 팀장 결정([결정 문서](../../docs/ai-dlc-input-mvp/2026-10-08_catch-decisions.md))이 본인 기여의 뜻, 후보 문장의 숫자, 제목, 250건 넘는 PR을 정했다. Catch 개편 CR1(FR2.1)은 PR·병합 단위를 이슈 번호로 나누지 않고 나누기 글도 남기지 않는다(그 결정의 나누기를 대체). 이 문서와 기준 문서·결정 문서가 다르면 기준 문서·결정 문서를 따른다. 아래는 기준 문서가 #118에 맡긴 선택과, 코드가 기준을 옮긴 방법이다. 크기 상한 때문에 다음 둘은 따로 뒀다.

- 후보 문장·근거·제목과 생성 단계(#120)가 이어 붙일 곳: [후보 문장과 근거](candidate-text.md)
- 알려진 한계, 시험, 실제 자료로 확인할 것: [후보 판정의 한계와 검사](candidate-checks.md)

이 문서에서 쓰는 말:

- **연동 계정**: 회원이 연결한 GitHub 계정. 같은 계정인지는 GitHub 계정 번호로만 본다.
- **본인 커밋**: 연동 계정이 커밋 작성자로 기록된 커밋. 기록상 명의이며 직접 썼다는 뜻은 아니다.
- **wi1**: 작업 동일성 값을 만드는 규칙의 판본 이름. 값은 `wi1:`로 시작한다.
- **방법 B**: PR·병합에 속하지 않은 커밋을 정해 둔 규칙으로 묶는 방법(작업 단위 문서).
- **창**: 기본 브랜치 커밋 목록으로 받은 커밋. **머리**는 창에서 어느 커밋의 부모도 아닌 커밋이고, **본선**은 머리에서 첫 부모만 따라간 사슬이다([수집 문서](relation-collection.md)).
- **연결 PR 조회**: 커밋 하나를 담은 PR을 GitHub에 묻는 조회. 후보 문장에는 이 말 대신 「GitHub가 알려 준 커밋의 PR」처럼 쓴다.
- **보류**: 그 변경을 어느 후보에도 넣지 않는 것. 셀지는 이유에 따라 다르다(아래 「후보로 내지 않은 건수」).
- **확인 중단**: 수집이 상한·오류로 멈춰 필요한 확인을 끝내지 못한 것.
- C1~C30·L1~L15는 [합성 사례·시험·한계](../../docs/CatchU_work_identity_cases.md)의 사례·한계 번호다.

## 한눈에 보기

- 후보 하나는 작업 단위 하나다. PR이 기본이고, 그다음 PR 없이 합친 병합, 그 밖의 본인 커밋 묶음이다. 같은 변경은 한 단위에만 둔다. 배정받은 변경에 본인 기여 커밋이 없거나, 그 가운데 변경이 있음을 확인한 커밋이 없는 단위는 후보가 아니다.
- 본인 기여는 본인 커밋뿐이다. PR을 연 것은 기여가 아니다.
- SHA가 다른 커밋은 다시 낸 PR이나 cherry-pick 표시가 있고, 공백을 무시한 변경(파일 모드 포함)이 같을 때만 합친다.
- 수집이 멈춰 확인하지 못한 변경은 후보로도, 후보로 내지 않은 건수로도 내지 않는다. 멈춘 확인과 무관한 단위는 다 받았을 때처럼 판정한다.
- 팀장 결정을 따른 것: 본인 기여와 squash 커밋, 연동 계정이 연 PR을 세지 않음(「본인 기여」), 250건 넘는 PR의 비교 API 확인([수집 문서](relation-collection.md#250건에-닿은-pr))과 커밋 목록을 다 받지 못한 PR 때문의 보류(「목록을 다 받지 못한 PR」)·근거 한계(「배정」), 후보 문장의 숫자·근거 순서와 제목([후보 문장과 근거](candidate-text.md)).
- 기준 문서에 없어 이 구현이 정한 것(리뷰 대상): 후보로 내지 않은 건수를 세는 단위, 빈 커밋만 기준 미달, 변경이 있음을 확인한 본인 기여 커밋이 없는 단위는 후보가 아님, 근거 커밋 20건 상한. PR 소속 판정은 #117이 고정한 API 판본 2022-11-28에 기댄다([수집 문서](relation-collection.md#api-판본-고정). 연결 PR 조회로만 안 PR의 병합 커밋은 GraphQL `mergeCommit`).
- 재분석(Catch 개편 CR2): 단위를 정한 뒤 이미 다른 Catch에 속한 커밋의 변경을 빼고, 남은 새 변경으로만 후보를 만든다. 열쇠·묶음 설명·로그 두 숫자는 [소속 커밋 빼기](commit-assignment.md)에 있다.
- 하지 않는 것: 제목·초안·질문, 이슈만으로 기여한 후보, 추가 기준 브랜치 값을 요청에서 받기(받을 칸이 없다), 총 처리 시간 측정.

## 부르는 법과 아직 하지 않는 것

`app.candidates.build_candidates(request, outcome, assigned)`가 입구다(`assigned`는 맥락 조회의 소속 커밋 집합, 기본은 빈 집합). `outcome`은 `collect(..., relations=RelationOptions())`의 결과다([관계 조회](relation-collection.md)). 돌려주는 값은 결과 조합(`compose_result`)에 넘기는 `GenerationOutput`(적합 후보·`notProvided`·실패)이다. GitHub를 부르지 않고 토큰도 받지 않는다. 판정은 모두 수집한 관측에서 나온다. "같은 작업이다" 같은 결론을 밖에서 받지 않는다.

처리 순서에 연결할 때([#121](https://github.com/JminAILab/CatchU/issues/121))는 다음 순서로 부른다. `tests/candidate_scenarios.py`의 `run_case`가 이 순서의 예다.

1. `collect(request, …, relations=RelationOptions())`
2. `build_candidates(request, outcome, assigned)`
3. `compose_result(request, output, …)`, 그다음 메시지 스키마 검사

돌려준 `failures`에는 수집 실패(`outcome.stage_failures()`)가 이미 들어 있다. 다시 더하지 않는다.

- 처리 순서에는 #121의 LIVE 조립(`app/processing/live.py`)으로 연결했다. 합성 자료로만 검사했고, 실제 요청을 받아 끝까지 돈 확인은 #121의 실제 연결 확인에서 한다.
- 초안·최소 질문은 만들지 않는다(`NOT_GENERATED`). 제목도 만들지 않는다([후보 문장과 근거](candidate-text.md#제목)).
- 첫 호출 전 검사에서 멈춘 수집(저장소 없음)은 수집 실패만 돌려준다.
- 다음은 부른 쪽이나 수집의 결함이라 `ValueError`를 낸다. 근거 부족이나 0건으로 숨기지 않는다.
  - 저장소가 없는데 수집 실패도 없는 결과
  - 첫 호출 전 검사를 통과했는데 관계 조회 없이(`relations` 없음) 수집한 결과
  - 수집을 마쳤다는데 멈춘 단계나 닿지 못한(`NOT_REACHED`) 조회·상세·목록이 있는 결과
  - 수집을 마쳤는데 PR 밖 본인 커밋이나 그 커밋을 들인 병합의 연결 PR 조회 기록이 없는 결과
  - 연결 PR 조회(병합 커밋 포함)가 PR을 찾았다면서 PR이 없거나 알려지지 않은 PR을 돌려줬거나, 알려지지 않은 PR의 커밋 목록이 있는 결과
  - PR 커밋 목록으로만 본 커밋이 받은 PR 커밋 목록에 없는 결과

## 본인 기여

본인 커밋은 **커밋 작성자의 GitHub 계정 번호가 연동 계정과 같은 커밋**뿐이다. 사람이 직접 썼는지, 도구가 썼는지는 뜻하지 않는다. 그래서 후보 문장은 '작성한'이 아니라 '작성자로 기록된'으로 쓴다([결정 문서 「본인 기여의 뜻」](../../docs/ai-dlc-input-mvp/2026-10-08_catch-decisions.md#본인-기여의-뜻)). 커미터, PR을 연 계정, 이름·메일, 메시지·본문의 주장은 기여 근거로 쓰지 않는다. GitHub가 작성자를 계정과 연결하지 못한 커밋(작성자 없음)은 본인 커밋이 아니고 세지도 않는다. 그래서 연동 계정에 연결되지 않은 메일로 커밋한 회원은 결과가 EMPTY일 수 있다.

PR을 연 것만으로는 기여로 보지 않는다. [수집 통제 문서의 인계 표](../../docs/CatchU_collection_control_scope.md#32-인계-내용--a가-주는-것)(2026-10-08 고침)와 같다. 그래서 연동 계정이 연 PR에 본인 기여 커밋이 없으면 다른 계정 커밋만 있는 단위처럼 후보도 아니고 건수에도 세지 않는다(2026-10-09 팀장 결정).

**PR 커밋 목록과 squash 커밋.** GitHub가 squash 병합으로 새로 만든 커밋의 작성자는 그 안 변경의 명의로 보지 않는다(결정 문서 「본인 기여의 뜻」).

- PR 커밋 목록을 끝까지 받았으면 목록의 원래 커밋만 기여 근거다. squash·rebase로 새로 생긴 커밋은 PR에 배정만 된다.
- 목록을 다 받지 못했으면(크기 상한, 판본 불일치, 250건에서 다 읽지 못함, 목록 밖에서 연결 PR 조회로만 앎) 연결 PR 조회·`merge_commit_sha`로 배정한 커밋도 근거로 쓴다. 다만 그 PR의 `merge_commit_sha`이면서 부모가 하나인 커밋은 squash 커밋일 수 있어 근거에서 뺀다. 그 커밋 말고 본인 기여 커밋이 없으면 PR을 연 계정과 무관하게 그 PR 하나에 근거 부족 1로 센다. 이 PR의 기여를 바꿀 수 있는 확인이 수집 중단으로 끝나지 않았을 때만 센다(아래 「수집이 멈췄을 때」).
- 목록을 조회 오류나 수집 상한으로 받지 못했으면 그 PR의 변경은 확인 중단으로 보류하고 세지 않는다. 수집 실패는 수집이 남긴 것을 그대로 옮긴다.
- 같은 변경을 따라 다른 단위로 간 본인 커밋도 같다. 그 커밋이 든 PR 목록에서 확인한 원래 커밋이면 그 PR의 `merge_commit_sha`여도(fast-forward로 합친 PR의 마지막 커밋) 기여 근거다. 그 커밋이 든 PR 가운데 하나라도 목록에서 확인하지 못한 squash 후보 커밋이면 근거가 아니다.

## 소속 판정

병합 아닌 커밋마다 소속을 다섯 상태 가운데 하나로 정한다(`Membership`).

| 상태 | 뜻 | 처리 |
|---|---|---|
| `ASSIGNED` | PR 단위를 정했다 | 배정 |
| `OUTSIDE` | PR 밖이 확정됐다(연결 PR 조회가 빈 목록이고 수집한 PR 커밋 목록에 없으며, 아래 「목록을 다 받지 못한 PR」의 보류에 걸리지 않는다). PR 조회가 허용되지 않은 요청의 커밋도 여기다 | PR 없는 병합이나 커밋 묶음으로 |
| `RANGE_LIMITED` | 자료 범위 한계로 확인하지 못했다(연결 PR 조회 응답이 크기 상한을 넘음·한 쪽보다 많음·기준 저장소를 알 수 없는 PR이 있음, 병합이 들인 커밋이 창 밖에 닿음, 병합의 첫 부모 쪽 경계를 확인하지 못함, 추가 기준 브랜치를 끝까지 받지 못함, 창의 머리가 하나가 아님) | 보류, 단위 미확정으로 셈 |
| `CONFLICT` | 필요한 조회를 마쳤는데 근거끼리 답이 어긋나거나, 다 받지 못한 PR 목록과 겹칠 수 있다(아래 목록) | 보류, 단위 미확정으로 셈 |
| `STOPPED` | 수집이 상한·오류로 멈춰 확인하지 못했다 | 보류, 세지 않음 |

근거는 PR 커밋 목록, 병합된 PR의 `merge_commit_sha`, 연결 PR 조회 순으로 본다. 다른 계정 커밋은 연결 PR을 조회하지 않는다. PR 목록·`merge_commit_sha`에 없으면 병합 단위의 구성으로만 쓰고 후보·집계에는 쓰지 않는다. 커밋마다 어느 PR에 어떤 근거로 속하는지는 `Grouping.observations`에, PR 커밋 목록을 본 판본(PR 머리 커밋)과 끝까지 읽었는지는 `Grouping.pull_request_commits`에 남는다.

단위 미확정(`CONFLICT`)이 되는 경우는 다음 다섯이다.

- 연결 PR 조회가 돌려준 병합되지 않은 PR의, 끝까지 받은 커밋 목록에 그 커밋이 없다(C16). 목록 밖 PR의 `merge_commit_sha`처럼 조회 대상을 정한 뒤 알게 된 근거로 소속이 나온 본인 커밋도 그 조회 결과와 어긋나면 같다.
- 연결 PR 조회는 빈 목록인데, 병합 커밋으로 합친 PR이 그 커밋을 들였다.
- PR 없는 병합 후보의 연결 PR 조회가 PR을 돌려줬다.
- 필요한 조회를 마쳤는데 서로 안쪽이 아닌 두 PR 없는 병합이 같은 커밋을 들였다(아래 「배정」). 창의 머리가 하나가 아니면 그 보류가 먼저다.
- 커밋 목록을 다 받지 못한 PR과 겹칠 수 있어 PR 밖을 확정하지 않았다(아래).

연결 PR 조회가 PR을 돌려줬는데 그 PR의 커밋 목록이 조회 범위·크기 한계로 없거나 덜 받은 경우는 어긋남으로 보지 않고 그 PR에 배정한다. 그 PR이나 먼저 병합된 PR의 목록을 수집이 멈춰 받지 못했으면 확인 중단으로 보류한다(「배정」 1).

C17(짧은 SHA만 있어 판본을 확정하지 못한 근거)은 이 구현에서 생기지 않는다. 수집은 전체 SHA만 받고, 짧은 SHA로는 작업 동일성 값을 만들 수 없다(`test_c17_short_sha_cannot_become_an_identity`). 자료 범위 한계(연결 PR 묶음 응답의 크기 초과, 연결 PR이 100건보다 많음 등)로 소속을 확인하지 못한 본인 변경은 C17이 아니다. 전체 SHA라 근거 요건은 채웠고 정한 범위대로 조회도 마쳤으므로 단위 미확정으로 센다([기록](../../docs/CatchU_work_identity_records.md#결정)의 2026-09-30 집계 결정: 'UNDETERMINED는 필요한 조회를 마쳤지만 소속을 판단할 수 없는 경우에만 쓴다'). 운영 로그에는 `rangeLimited`로 따로 센다. 연결 PR 조회의 거절(null 커밋, HTTP 200의 한도 밖 `errors`, 오류 상태)은 다른 조회 오류처럼 수집 실패다([실패 코드](associated-pr-lookup.md#결과와-실패)).

### 목록을 다 받지 못한 PR

[결정 문서 「커밋이 250개 넘는 PR」](../../docs/ai-dlc-input-mvp/2026-10-08_catch-decisions.md#커밋이-250개-넘는-pr)대로 한다. 대상은 PR 목록으로 받은 PR 가운데 커밋 목록을 정한 범위대로 조회했지만 다 받지 못한 PR이다. 응답 크기 초과, 판본 불일치, 250건에서 다 읽지 못함(수·판본 어긋남, 비교 쪽수·응답 크기 상한, 포크에서 연 PR, 기준 커밋 모름, 커밋 조회 불허)이 해당한다.

- 그런 PR 가운데 병합되지 않고 닫혔거나 기본 브랜치가 아닌 곳을 대상으로 한 PR이 하나라도 있으면, 그 저장소에서 PR 밖으로 판정될 본인 커밋(연결 PR 조회가 빈 목록이고 받은 PR 커밋 목록 어디에도 없는 커밋)을 모두 보류한다. 그 PR의 받지 못한 커밋은 연결 PR 조회가 돌려주지 않아, 따로 내면 한 작업이 Catch 둘로 갈릴 수 있기 때문이다. 기본 브랜치 이름을 모르면 기본 브랜치가 아닌 것으로 본다. 정한 범위대로 조회를 마쳤으므로 단위 미확정(`UNDETERMINED`)으로 세고 실패는 남기지 않는다. 운영 로그에는 따로 센다(`heldByIncompleteLists`).
- 모두 기본 브랜치를 대상으로 한 열린·병합 PR이면 보류하지 않는다. 그 PR의 커밋이 기본 브랜치에 들어와 있으면 연결 PR 조회가 그 PR을 돌려주기 때문이다. 대신 PR 없는 병합·커밋 묶음 후보의 근거에 「커밋 목록을 다 받지 못한 기본 브랜치 대상 PR이 있어, 그 PR에도 담긴 커밋일 수 있다」를 붙인다. 남는 경우는 한계 L13이다([알려진 한계](candidate-checks.md#알려진-한계)).
- 비교 조회 거절(404·422)이나 수집 상한으로 멈췄으면 위 보류가 아니라 확인 중단이다. 세지 않고 수집 실패가 남는다(2026-09-30 집계 결정, [기록](../../docs/CatchU_work_identity_records.md#결정)).

## 배정

같은 변경은 한 단위에만 둔다. 앞선 것부터 다음 순서다.

1. **PR**: 먼저 병합된 PR. 병합 시각이 같으면 번호가 작은 PR이 앞선다. 병합된 PR이 없으면 번호가 가장 작은 PR이다. 배정할 PR이나 그보다 앞선 PR의 커밋 목록을 수집이 멈춰 보지 못했으면 그 변경은 보류한다(더 앞선 PR에 들어 있었을 수 있다). 먼저 병합된 PR의 목록을 정한 범위대로 조회했지만 다 받지 못했으면(크기 상한, 판본 불일치, 250건에서 다 읽지 못함) 보류하지 않고 배정한다. 대신 그 후보의 PR 근거에 「먼저 병합된 PR 가운데 커밋 목록을 다 받지 못한 PR이 있어, 그 PR에도 담긴 변경일 수 있다」를 붙이고 건수는 바꾸지 않는다(2026-10-09 팀장 결정).
2. **PR 없는 병합**: 먼저 들인 병합. 한 병합이 다른 병합의 창 안 조상이면 조상이 먼저 들였다. 조상 관계가 없으면 커밋 시각과 SHA로 정한다. 창 안 조상을 늘 앞에 두는 순서에서 커밋 시각이 이른 병합, 같으면 SHA가 작은 병합이 앞선다. GitHub 목록 순서는 쓰지 않으므로 같은 커밋을 어떤 순서로 받아도 결과가 같다.
3. **커밋 묶음**.

한 커밋을 여러 PR 없는 병합이 들였으면 그 커밋을 처음 들인 가장 안쪽 병합에 둔다. 서로 안쪽이 아닌 두 병합이 들였으면 단위 미확정이다. 다만 그 커밋을 들인 병합의 연결 PR 조회를 수집이 멈춰 하지 못했거나 기본 브랜치 목록 단계에서 멈췄으면, 필요한 조회를 마치지 못했으므로 확인 중단으로 보류하고 세지 않는다. 가장 안쪽 병합을 PR 없는 병합으로 확인하지 못했으면(아래 「병합이 들인 커밋」) 그 병합을 거쳐 바깥 병합에 들어온 커밋도 같은 상태로 보류한다. 바깥 병합 후보의 설명에 적는 「안쪽 병합이 먼저 들인 커밋 N건」은 배정을 마친 뒤 실제로 안쪽 병합에 배정된 커밋만 센다.

### 병합이 들인 커밋

PR 없는 병합이 들인 커밋은 창의 부모 관계로 센다([수집 문서](relation-collection.md#단계-순서와-github-api)). 들인 커밋 가운데 흡수 병합(기준 브랜치를 작업 브랜치로 받아온 병합)이 있으면, 그 흡수 병합이 기준 브랜치에서 들인 커밋은 빼고 원래 단위에 둔다. 다음이면 그 병합을 확정하지 않는다. 이 보류는 연결 PR 조회가 준 확정·단위 미확정보다 앞선다.

- 첫 부모 쪽 조상이 창 밖으로 이어진다(창이 저장소 처음까지 닿지 않은 흔한 경우). 창만으로는 첫 부모가 이미 담은 커밋을 다 빼지 못한다. 그래서 수집이 첫 부모와 병합을 비교해 받은 범위로 들인 커밋을 정한다. 비교를 끝까지 받았고 그 범위가 모두 창 안이면 확정한다. 다 받지 못했거나(쪽수·응답 크기 상한, 수가 맞지 않음) 비교가 없으면 자료 범위 한계, 수집이 멈춰 부르지 못했으면 확인 중단이다.
- 들인 커밋을 걷다 창 밖에 닿았다(자료 범위 한계).
- 추가 기준 브랜치를 끝까지 받지 못했다. 본선에 없는 병합은 그 브랜치를 받아온 흡수 병합일 수 있다(자료 범위 한계).

목록 단계에서 멈춰 창이 잘렸을 수 있으면 위 자료 범위 한계는 모두 확인 중단이다.

## 같은 변경

SHA가 다른 두 커밋은 관계 근거와 공백을 무시한 같은 diff가 함께 있을 때만 같은 변경으로 합친다. 관계 근거는 재제출과 cherry-pick 표시뿐이다.

- **공백을 무시한 diff 값**: GitHub 커밋 상세의 파일별 `patch`와 파일 모드 줄로 `git patch-id --stable` 값을 다시 계산한다. git처럼 공백(스페이스·탭·LF·CR 네 바이트)만 지우고, 파일 머리글 줄(모드 줄 포함)도 넣고, `\ No newline at end of file` 줄은 넣지 않는다. 커밋 상세에는 파일 모드가 없다. 그래서 관계 근거가 있고 모드를 빼고 계산한 값이 같은 두 커밋만, 수집이 같은 커밋을 diff 형식으로 한 번 더 받아 모드 줄을 읽는다. 다음 경우는 값을 만들지 않으며 같은 변경으로 확정하지 않는다: 파일 목록이 잘림, 변경 파일이 없음(빈 커밋), `patch`가 없는 파일(이진·큰 변경)이 있음, 이름 바꿈 같은 추가·삭제·수정 밖의 상태, 줄 수가 hunk 머리글과 맞지 않음, 파일의 추가·삭제 줄 수가 `patch`의 줄 수와 다름(잘린 `patch`), 모드 줄을 받지 못했거나 상태와 맞지 않음(diff 응답이 크기 상한을 넘었거나 파일을 맞출 수 없음). 모드 확인을 수집이 멈춰 하지 못했으면 변경 내용을 받지 못했을 때처럼 다룬다(「수집이 멈췄을 때」).
- **번호 읽기**: 재제출의 뒤 PR 제목과 본문은 따로 읽는다. 번호 뒤에 영문자·숫자·`_`가 오지 않으면 센다(`#11`, `(#11)`, `#11을`). 다음은 세지 않는다: 앞에 글자·숫자·`_`·`/`·`&`가 붙은 번호(`abc#11`, `&#11;`), `#011`처럼 0으로 시작하는 번호, `#11a`, `owner/repo#11`, 코드 블록·인라인 코드·HTML 주석·HTML `<pre>`·`<code>` 안의 글자, `http://`·`https://`·`www.`로 시작하는 주소 안의 글자(`?ref=#11`). 주소는 이 저장소의 `https://github.com/{owner}/{name}/pull/N`만 번호로 센다. 줄 앞에서 연 HTML 주석 안에서는 펜스를 열지 않는다. 마크다운을 줄여 읽으므로 실제 화면과 다르게 지우는 글이 있고, 그런 글에서는 재제출 관계나 서로 다른 번호를 놓칠 수 있다. 자세한 규칙은 `same_change.py`에 있다.
- **확정하지 못한 관계**: 관계 근거는 있는데 필요한 조회를 마치고도 diff가 다르거나 비교할 수 없으면(`patch` 없음, 응답 크기 초과, 모드를 확인하지 못함) 합치지 않는다. 「같은 작업을 다시 낸 것일 수 있다」나 「cherry-pick으로 옮긴 같은 변경일 수 있다」 한계를 붙인다. 붙이는 곳은 두 변경을 실제로 가진 후보 둘이다. 한쪽 변경이 다른 확인된 같은 변경을 따라 다른 단위로 배정됐으면 그 단위의 후보에 붙인다. 수집이 멈춰 비교하지 못했으면 「수집이 멈췄을 때」의 규칙을 따른다.
- **squash 커밋과 원래 커밋**: 둘을 같은 변경으로 잇지 않는다. squash 커밋은 `merge_commit_sha`로 PR에 배정되지만 기여 근거인지는 「본인 기여」대로 정한다. 그래서 기준 문서 「한계와 실제 구현에서 검증할 것」의 squash 항목처럼 원래 커밋 목록을 받은 PR에서는 squash 커밋이 두 번째 후보를 만들지 않는다.
  - C8의 통합 PR #12를 squash로 합치면: 원래 커밋은 먼저 병합된 #10·#11에 가고, #12에는 squash 커밋만 남는다. #12는 후보가 아니고, 연동 계정이 연 PR이어도 건수에 세지 않는다.
  - C20·C25에서 옮긴 PR을 squash로 합치면: squash 커밋이 release 같은 다른 브랜치에 있으면 관측하지 않으므로 Catch는 하나다. 기본 브랜치에 있으면 그 PR에 배정되지만 기여 근거가 아니라 Catch는 하나이고 건수도 없다.
  - 시험: `test_squash_merged_integration_pull_request_is_not_a_second_candidate`, `test_squash_commit_of_cherry_picked_pull_request_is_not_contribution`, `test_own_squash_commit_without_the_whole_list_is_insufficient_evidence`, `test_listed_own_commit_that_is_merge_commit_sha_counts_where_its_change_goes`, `test_own_squash_commit_is_not_contribution_where_its_change_goes`, `test_squash_commit_listed_in_another_pull_request_is_not_contribution`.

## 커밋 묶음(방법 B)

PR·병합에 속하지 않은 본인 커밋을 다음 규칙으로 묶는다.

- 부모가 하나뿐이고 그 부모도 PR·병합에 속하지 않은 본인 커밋이며, 두 커밋의 변경 파일(바꾼 경로와 이전 경로)이 겹치면 잇는다.
- 같은 변경으로 확정한 PR 밖 본인 커밋들은 부모 관계와 관계없이 한 묶음에 든다. 사이에 다른 계정 커밋이 있어도 그렇다.
- 작성 시각 차이와 메시지 비슷함은 보지 않는다. 같은 변경으로 확정한 커밋이 아니면 다른 계정 커밋이 사이에 끼었을 때 잇지 않는다. 그래서 커밋 하나짜리 후보가 많을 수 있다.
- 변경 내용을 받지 못해 판단하지 않은 쌍은 따로 두고 한계를 적는다. 변경 파일이 잘려 겹침을 끝까지 보지 못한 쌍도 그렇다.
- 같은 결과 안에서는 입력 순서와 관계없이 같은 묶음이 나온다.

## 수집이 멈췄을 때

수집이 멈췄으면 확인하지 못한 변경을 보류한다. 내보낸 후보는 멈춘 확인과 무관해야 한다. 결과의 `eligibility.independentOfFailures`는 늘 참이기 때문이다. 멈춘 확인과 무관한 단위는 다 받았을 때처럼 판정한다.

- 멈춰서 보지 못한 연결 PR 조회, 더 앞선 PR의 커밋 목록, 병합의 경계 비교, 창 밖 경계(목록 단계에서 멈춤)에 걸린 변경은 보류한다. 목록 단계에서 멈췄으면 창의 머리가 하나가 아닌 것도 다 받았을 때 달라질 수 있으므로 확인 중단이다.
- 이웃 커밋이 확인 중단으로 보류됐거나, 이웃과 잇는지 볼 변경 내용을 수집이 멈춰 받지 못했으면 그 커밋 묶음 전체를 보류한다. 이웃이 자료 범위 한계·단위 미확정으로 보류되면 그 커밋 없이 묶는다(묶음 경계가 달라질 수 있다).
- **비교하지 못한 같은 변경**: 관계 근거가 있는데 수집이 멈춰 변경 내용이나 파일 모드를 받지 못해 비교하지 못한 쌍이 있으면, 비교 결과에 따라 배정이나 건수가 달라질 변경만 확인 중단으로 보류하고 세지 않는다. 그 쌍으로 이어진 변경들을 다음 순서로 본다. 자세한 규칙은 `grouping.py`의 `_roots_to_hold`에 있다.
  - 이미 보류된 변경(자료 범위 한계·단위 미확정)이 하나 이어져 있으면 그 보류는 그대로 두고 나머지를 보류한다. 둘 이상이면 같은 변경인지에 따라 세는 수가 달라지므로 그 변경까지 모두 확인 중단으로 바꿔 세지 않는다.
  - 이어진 변경이 모두 서로 다른 PR·PR 없는 병합에 소속을 확인했으면 아무것도 보류하지 않고 양쪽 후보에 「…일 수 있다」 한계를 붙인다. 같은 변경이었어도 각 단위의 소속은 그대로이기 때문이다.
  - 그 밖에는 가장 앞선 단위의 변경만 두고 나머지를 보류한다. 가장 앞선 단위가 커밋 묶음이고 그런 변경이 둘 이상이면 합쳤을 때 묶음의 구성이 달라지므로 모두 보류한다.
- **단위별 판정**: 기여 확인은 요청 전체의 완료 여부가 아니라 그 단위에 걸린 확인으로 판단한다. 다음 가운데 하나면 그 단위의 확인이 끝나지 않은 것이다: 그 단위에 걸린 변경을 확인 중단으로 보류했다, 그 단위의 커밋이 든 관계 쌍을 비교하지 못했다, 병합된 PR인데 본인 커밋의 연결 PR 조회를 마치지 못했다(squash·rebase 커밋이 그 조회로 배정된다), 이 PR이나 먼저 병합된 PR의 커밋 목록을 받지 못했다. PR의 기여 확인은 그에 더해 어느 PR이든 커밋 목록을 받지 못했으면 끝나지 않은 것으로 본다. 그 목록의 커밋이 같은 변경으로 이 PR의 기여가 될 수 있기 때문이다.
- 보류한 변경은 어느 후보에도 넣지 않고, 판단한 것이 아니므로 `notProvided`에도 세지 않는다. 수집 실패는 수집이 남긴 것만 그대로 옮긴다.

## 후보로 내지 않은 건수(`notProvided`)

순서는 근거 부족, 기준 미달, 단위 미확정이고 0건은 넣지 않는다. 확인 중단을 세지 않는 것과 단위 미확정의 범위는 2026-09-30 집계 결정이다([기록](../../docs/CatchU_work_identity_records.md#결정)). 기준 문서가 세는 단위를 정하지 않아 나머지는 다음처럼 정했다(리뷰 대상).

| 이유 | 세는 단위 |
|---|---|
| `INSUFFICIENT_EVIDENCE` | ① 커밋 목록을 다 받지 못해 본인 squash 후보 커밋을 기여로 확인하지 못한 PR 하나마다 1(PR을 연 계정과 무관. 그 PR의 기여를 바꿀 수 있는 확인이 수집 중단으로 끝나지 않았을 때만). ② 본인 기여 커밋 가운데 변경이 있음을 확인한 커밋이 없고, 받지 못한 커밋이 조회 범위 밖(상세 조회 개수나 남은 여유)이라 받지 못한 단위 하나마다 1. 연동 계정이 연 PR인데 본인 기여 커밋이 없는 것은 세지 않는다(PR을 연 것은 기여가 아니다, 2026-10-09 팀장 결정) |
| `BELOW_CRITERIA` | 본인 기여 커밋의 변경 내용을 모두 받았고 모두 빈 커밋(변경 파일 0개)인 단위 하나마다 1 |
| `UNDETERMINED` | 근거끼리 어긋난 본인 변경, 다 받지 못한 PR 목록과 겹칠 수 있어 PR 밖을 확정하지 않은 본인 변경, 자료 범위 한계로 소속을 확인하지 못한 본인 변경 하나마다 1. 셋 모두 정한 범위대로 조회를 마친 보류다. 같은 변경으로 합친 커밋은 하나로 센다 |

**후보 자격.** 본인 기여 커밋 가운데 변경 파일을 확인한(비지 않은) 커밋이나 응답이 커서 받지 못한(변경이 있는) 커밋이 하나라도 있어야 후보다. 모두 받았고 모두 비었으면 기준 미달이다. 변경 내용을 받지 못한 커밋은 빈 커밋으로 보지 않지만, 그런 커밋만으로는 확인할 작업 사실이 없어 후보로 내지 않는다. 수집이 멈춰 받지 못한 커밋이 있으면 확인 중단(세지 않음), 나머지(상세 조회 개수나 남은 여유 밖)는 근거 부족 ②다. 커밋 조회가 허용되지 않은 요청은 변경 내용을 보지 않으므로 이 검사를 하지 않는다.

기준 문서들은 기준 미달을 정의하지 않는다. 작은 변경·커밋 하나·이유 부재로는 빼지 않으므로, 확인할 작업 사실이 전혀 없는 경우(본인 커밋이 모두 변경 파일 0개)만 기준 미달로 정했다.

로그는 건수만 남긴다(`후보 판정 종료: … insufficient=… belowCriteria=… undetermined=… heldAfterStop=… rangeLimited=… heldByIncompleteLists=… sameIdentityMerged=…`). `heldAfterStop`은 확인 중단으로 보류한 본인 변경, 멈춘 확인 때문에 세지 않은 PR(①), 변경 내용을 수집이 멈춰 받지 못한 단위를 함께 센다. `rangeLimited`는 자료 범위 한계로 보류한 본인 변경(단위 미확정에 든다)과 근거 부족 ②를, `heldByIncompleteLists`는 단위 미확정 가운데 다 받지 못한 PR 목록 때문에 보류한 변경을 센다. 세는 곳은 `build_candidates` 한 곳이다.

## 작업 시각과 다시 볼 곳 사실 (새 Catch NC3)

결과 v4의 후보마다 첫·마지막 작업 시각과 다시 볼 곳 사실이 붙는다(기능 설계 `aidlc/spaces/default/intents/261109-new-catch/construction/nc3-revisit-facts/functional-design/rules.md`).

- **작업 시각(BR4.1):** `build_candidates`가 같은 작업 식별값 후보를 합친 뒤 후보마다 본인 커밋(`own_commit_shas`)의 작성 시각(`authored_at`) 최소·최대를 싣는다. 커밋 시각은 쓰지 않는다. 기록이 없으면 후보 판정 결함(`ValueError`)이다. 결과에는 UTC 초 단위 `Z` 글로 싣는다.
- **다시 볼 곳(`app/candidates/revisit.py`):** 처리(`app/processing/live.py`)가 후보 판정 뒤·생성 앞에서 후보마다 부른다. 재료는 후보 판정과 같은 기록 묶음(기본 브랜치 창 커밋과 관계 조회 커밋)의 그 후보 본인 커밋뿐이고 GitHub·AI를 부르지 않는다. 병합 커밋을 빼고 (작성 시각, 식별값) 순서로 한 번 훑는다.
  - 규칙 다섯: 다시 고친 곳(앞 커밋이 넣은 줄과 글자가 같은 줄을 뒤 커밋이 같은 파일에서 지움, (경로, 줄 글자) 사전, 이름 바꿈은 기억을 잇고 지운 파일·되돌린 쌍은 빼고 글자·숫자 없는 줄은 보지 않음), 옮긴 곳(한 커밋 안 renamed, 또는 지움·만듦의 내용 식별값 `blob_sha`가 하나씩만 맞음, 빈 파일 식별값은 맞추지 않음), 확장자 바꿈(같은 폴더·같은 이름, 확장자만 다름, 대소문자만 다르면 옮긴 곳), 되돌림(「This reverts commit <40자>」이 같은 후보 커밋), 시험 파일 있음(폴더 `test`·`tests`·`__tests__`·`spec`·`e2e`·`androidtest`, 이름 `test_*.py`·`*_test.*`·`*.test.*`·`*.spec.*`, **지운 시험 파일은 치지 않음**).
  - 변경 내용을 받지 못했거나 파일 목록이 잘린 커밋은 경로 규칙에서, patch 없는 파일은 줄 규칙에서만 뺀다.
  - **좁은 산출물 목록:** 잠금 파일 18개 이름, 빌드 폴더 `build`·`dist`·`out`, `.min.js`, AI 하네스 폴더(`.claude`·`.codex`·`.agents`·`.cursor`·`.kiro`·`.aidlc`·`.windsurf`·`.gemini`, 첫 폴더 `aidlc`), 지시 파일(`AGENTS.md`·`CLAUDE.md`·`GEMINI.md`·`.cursorrules`·`.github/copilot-instructions.md`), 비밀 경로(`app.redact.is_secret_path`). 이 판정에서만 쓰고 재료 분류(`title.classify`)는 바꾸지 않는다.
  - **규칙 끄기:** `ENABLED_KINDS` 상수에서 종류를 빼는 코드 변경으로 끈다. 환경 변수는 없다.
  - **상한·순서:** 종류 순서 → 사실의 마지막 커밋 순서 → 첫 경로 글자로 늘어놓고 30개까지, 사실마다 경로·커밋 20개, 1,024자 넘는 경로의 사실은 만들지 않는다. 결과에는 종류·경로·커밋만 담고 줄 글자는 담지 않는다.
  - **판정 예외 갈래(NFR8.3):** 기록이 없는 본인 커밋이나 자기 결과가 api 등록 검사 규칙(종류별 개수·소속·겹침·상한)을 어기면 `RevisitFactsDefect`를 낸다. 처리는 `Exception`이면 그 후보 사실만 빈 배열로 두고 `다시 볼 곳 계산 실패: requestId=… attemptId=… error=<예외 종류 이름>` 한 줄을 남긴다. 팀 규칙 「예외를 삼키지 않는다」의 예외 한 곳이다. 그 후보의 작업 시각·다른 후보·결과 전송은 그대로다.
- 합성(MOCK) 경로는 템플릿의 새 칸을 그대로 쓰고 다시 볼 곳 판정을 부르지 않는다.
