# 관계 조회 — #118

> [허용 GitHub 자료 수집과 근거 정규화](github-collection.md)의 「관계 조회(#118)」 절을 문서 크기 상한(36 KB) 때문에 따로 옮겼다. 이 문서에서 「수집 문서」는 그 문서를 가리킨다.

[#118](https://github.com/JminAILab/CatchU/issues/118)은 후보를 작업 단위(PR, PR 없이 합친 병합, 커밋 묶음)로 묶고 작업 동일성 값(`workIdentity`)을 만든다. 관계 조회는 이 판정에 필요한 GitHub 관계를 목록 뒤에 더 모은다. 관계는 커밋이 어느 PR에 담겼는지, 커밋과 연결된 PR, 병합 커밋이 들인 커밋, 커밋의 변경 내용과 파일 모드다. 판정 기준은 [작업 단위와 판정 입력](../../docs/CatchU_work_identity_unit.md)의 「[PR 소속과 같은 변경을 확인하는 근거](../../docs/CatchU_work_identity_unit.md#pr-소속과-같은-변경을-확인하는-근거)」다. 관계 조회는 관측만 모은다. 소속 확정·같은 변경 확인·후보 판정은 `app/candidates/`가 이 관측으로 한다([후보 묶음과 작업 동일성](candidate-decision.md)).

이 절에서 쓰는 말:

- **연동 계정**: 회원이 연결한 GitHub 계정. 같은 계정인지는 GitHub 계정 번호로만 본다. 본인 커밋은 연동 계정이 작성자로 기록된 커밋이다.
- **기본 브랜치**: 저장소 확인 응답의 `default_branch`.
- **병합 커밋**: 부모가 둘 이상인 커밋. 변경으로 세지 않고 단위 경계에만 쓰므로 변경 내용을 조회하지 않는다.
- **`merge_commit_sha`**: 병합된 PR이 기준 브랜치에 남긴 커밋의 SHA. 병합 방식에 따라 병합 커밋, squash 커밋, rebase로 옮겨진 마지막 커밋이다.
- **확인 중단**: 호출 수·수집 시간·수집 총량 상한에 걸렸거나 조회가 오류로 끝나 수집이 멈춘 것. 결과의 `failures`에 수집 실패 1건이 들어간다.
- **한계**: 조회 개수 범위 밖이거나 쓸 수 없는 응답이라 보지 못한 부분. 근거의 `coverageLimits`에 남기며 실패가 아니다.

## 부르는 법과 기본 경로에서 그대로인 것

`collect(..., relations=RelationOptions())`로 부르면 결과의 `relations`에 `RelationObservations`가 담긴다. 목록을 부른 연결·호출 통제·상한 계산·자격정보를 그대로 쓴다. 새 연결을 열지 않고, 토큰은 `Authorization` 머리글에만 쓴다. [수집 문서](github-collection.md) 통제 표의 호스트·주소·우회 이동·다른 저장소·자료 안의 글·재시도·비밀값·임시 자료 통제는 관계 조회의 호출에도 그대로 적용된다. 관계 조회가 글을 읽는 곳은 변경 내용의 필수 조회 계획과 파일 모드 확인뿐이다(아래 「변경 내용」). 커밋 메시지의 cherry-pick 표시·이슈 번호와 PR 제목·본문의 PR 번호를 글자 규칙으로 찾고, diff 형식 응답에서는 파일 머리글의 경로·모드 줄만 읽는다. 글 속 주소를 부르거나 글을 지시로 따르지 않고 관측 사실에 글자를 넣지 않는다.

`relations`를 주지 않은 기본 경로는 부르는 경로·순서·호출 수가 #117과 같고, 관계 조회용 경로는 부르지 않는다(`tests/test_collection_relations.py`의 `test_default_path_*`). 한계 문구는 '작성한'을 '작성자로 기록된'으로 바꾼 두 곳만 다르다(2026-10-08 결정 「본인 기여의 뜻」). 기본 브랜치 이름도 읽지 않으므로 그 값이 이상해도 기본 경로는 멈추지 않는다. PR 응답의 `base.sha`는 두 경로 모두 새 필드 `PullRequestRecord.base_sha`로 읽지만, 없거나 형식이 다르면 `None`으로 두고 실패로 보지 않는다. [수집 문서](github-collection.md) 수집 순서의 2번과 최악 298회 계산은 이 기본 경로에 대한 것이다.

관계 조회 경로에서 달라지는 것:

- 저장소 확인은 기존 검사를 모두 통과한 뒤 기본 브랜치 이름을 읽는다. 없거나 비었으면 `COLLECTION_FETCH_FAILED`로 멈춘다.
- 목록(최근 커밋 500·PR 100·이슈 목록 항목 100)은 같다. 다만 목록 단계는 상세를 정하지 않는다. #117의 상세(연동 계정이 작성자로 기록된 최근 커밋 200건의 변경 내용, 연동 계정이 연 최근 PR 30건의 커밋 목록)와 그 「상세 조회 개수 범위 밖」 한계 대신, 아래 단계가 무엇을 조회할지 정한다.

## 단계 순서와 GitHub API

REST 경로는 [수집 문서](github-collection.md)처럼 F가 검사한 저장소 좌표·SHA·번호와 경로 틀로 만든다(`app/collection/api_paths.py`). 쪽 크기는 100이다. 같은 경로를 두 번 부르지 않고, 이미 받은 변경 내용도 다시 받지 않는다. 연결 PR 조회만 GraphQL 묶음 조회이며, 주소·쿼리 틀·응답 대응·실패·상한은 [연결 PR 묶음 조회](associated-pr-lookup.md)에 있다. 같은 단계에서 같은 SHA를 두 번 묻지 않는다.

| 순서(`stopped_during` 값) | 허용 종류 | 경로 | 하는 일 |
|---|---|---|---|
| 0. 목록(`LISTS`) | 수집 문서와 같음 | 수집 문서와 같음 | 저장소 확인(기본 브랜치 이름 포함)과 허용된 종류의 목록 |
| 1. 추가 기준 브랜치(`BASE_BRANCHES`) | COMMIT | `GET /repos/{owner}/{repo}/commits?sha={브랜치}` | 호출하는 쪽이 명시한 브랜치마다 최근 커밋을 `max_base_branch_commits`(100)까지 받는다. 「추가 기준 브랜치」 참고 |
| 2. PR 커밋 목록(`PULL_REQUEST_COMMITS`) | PULL_REQUEST | `GET /repos/{owner}/{repo}/pulls/{번호}/commits`(최대 3쪽) | 목록의 **모든** PR(다른 계정이 연 PR 포함, 2026-10-09 팀장 결정으로 유지)의 커밋 목록. 먼저 병합된 PR부터(병합 시각, 같으면 번호순) 읽고, 그 뒤 병합되지 않은 PR을 번호순으로 읽는다. 판본을 확인하고, 250건에 닿은 PR은 「250건에 닿은 PR」의 두 경로를 더 부른다 |
| 3. 로컬 계산 | — | 호출 없음 | 연결 PR을 조회할 커밋을 고른다 |
| 4. 연결 PR 조회(`LOOKUPS`) | COMMIT과 PULL_REQUEST | `POST /graphql`(커밋 100개씩 묶어 커밋마다 연결 PR 첫 100개), 경계 비교 `GET /repos/{owner}/{repo}/compare/{첫 부모}...{병합}`(최대 10쪽) | 고른 커밋을 묶음으로 차례로 조회한다. 그 결과로 PR 없는 병합 후보를 고르고 다음 묶음으로 조회한다. 그다음 첫 부모 쪽이 창 밖으로 열린 후보 병합의 경계를 비교한다(「PR 없는 병합 후보」) |
| 5. 변경 내용(`DETAILS`) | COMMIT | `GET /repos/{owner}/{repo}/commits/{sha}`, 모드 확인은 같은 경로를 diff 형식(`Accept: application/vnd.github.diff`)으로 | 「변경 내용」 참고 |

PR 커밋 목록을 먼저 병합된 PR부터 읽는 것은 여러 PR에 든 변경을 먼저 병합된 PR에 배정하기 때문이다. 중간에 멈춰도 배정에서 앞서는 PR의 목록이 먼저 남는다.

PR 커밋 목록은 PR 하나를 끝까지 읽은 뒤에만 남긴다. 읽는 중 멈춘 PR은 `NOT_REACHED`이고, 그 PR에서 본 커밋도 남기지 않는다. 250건 미만 목록은 PR 목록에서 본 머리 커밋이 목록의 끝(목록에 있고, 그 커밋을 부모로 둔 커밋이 없음)일 때만 쓴다. 빈 목록은 머리 커밋이 PR 응답의 기준 커밋과 같거나, 기본 브랜치를 대상으로 한 PR의 머리 커밋이 기본 브랜치 목록에 있을 때만(관측한 판본의 PR 커밋이 0건) 끝까지 받은 목록으로 쓴다. 아니면 읽는 동안 PR이 바뀌었거나 쪽마다 다른 판본을 받은 것이라 판본 불일치(`REVISION_MISMATCH`)로 버리고 다시 부르지 않는다. 그 PR 근거에는 「조회하는 동안 PR이 바뀌어 커밋 목록을 관측한 판본과 맞출 수 없었다」가 붙는다. 기본 브랜치 목록에 없고 PR 커밋 목록이나 250건 경로의 비교 API로만 본 커밋은 `relations.commits`에 작성자·부모·메시지·시각과 함께 담는다. 이 커밋들은 기본 브랜치 커밋과 SHA가 겹치지 않는다. 읽은 결과는 PR 기록의 `commits`·`commits_status`·`commits_truncated`에도 쓴다. 그래서 `evidence_for(PR 기록)`이 실제 커밋 수와 한계를 보인다.

**연결 PR을 조회할 커밋.** 먼저 기본 브랜치의 병합 아닌 본인 커밋 가운데 읽은 PR 커밋 목록에도 없고, 알려진 PR의 `merge_commit_sha`와도 다른 것을 조회한다. 기본 브랜치 목록 순서(최근 것부터)로 모두 조회하며, 개수 상한은 없다(묶음 요청 하나에 100개). 그다음 PR 없는 병합 후보(아래) 가운데, 들인 커밋에 PR 밖으로 확인됐거나 수집이 멈춰 확인하지 못한 본인 커밋이 있는 병합 커밋을 조회한다. 이 병합 커밋에는 작성자 제한이 없다. PR 커밋 목록과 `merge_commit_sha`로 먼저 소속을 정하고 남은 커밋만 조회하는 것은 판별 기준이 정한 순서이며, 호출 수를 아끼기 위해서다([「#118이 지킬 것과 시험할 것」](../../docs/CatchU_work_identity_cases.md#118이-지킬-것과-시험할-것)).

**PR 없는 병합 후보.** 기본 브랜치 목록으로 받은 커밋(아래에서 "창")의 부모 관계로 정한다(`app/collection/graph.py`).

- 머리는 창의 어떤 커밋의 부모도 아닌 창 커밋이다. 머리가 하나가 아니면 병합 단위를 확정할 수 없으므로 병합 후보를 조회하지 않는다.
- 본선은 머리에서 첫 부모(병합할 때 받는 쪽 브랜치의 커밋)만 따라간 사슬이다.
- 흡수 병합은 본선에 없으면서, 첫 부모가 아닌 부모가 본선이나 추가 기준 브랜치에 있는 병합이다. 기준 브랜치를 작업 브랜치로 받아온 병합이므로 작업 단위로 쓰지 않는다.
- 병합이 들인 커밋은 첫 부모가 아닌 부모들의 창 안 조상에서 첫 부모의 창 안 조상과 병합 자신을 뺀 것이다. 그 가운데 흡수 병합이 있으면 그 흡수 병합이 기준 브랜치에서 들인 커밋도 뺀다. 그 커밋은 원래 들어온 단위에 속한다. 첫 부모가 아닌 쪽을 걷다가 창 밖 부모에 닿으면 다 보지 못한 것으로 표시한다.
- 첫 부모 쪽을 걷다가 창 밖 부모에 닿으면(첫 부모 쪽 경계가 열림) 첫 부모가 이미 담은 커밋을 창만으로는 다 빼지 못한다. 경계를 추정하지 않고, 연결 PR 조회 대상 병합이면 비교 API(`첫 부모...병합`)를 `max_compare_pages`(10)쪽까지 부른다. 전체 수만큼 다 받았고, 병합 커밋이 들어 있고, 응답이 준 시작 커밋이 첫 부모일 때만 다 읽은 것이고, 그때 병합 커밋을 뺀 비교 범위가 들인 커밋이다. 시작 커밋이 없거나 형식이 틀린 응답, 쪽수·응답 크기 상한, 쪽마다 다른 전체 수, 전체 수와 맞지 않는 개수(빈 쪽 포함)는 다 읽지 못한 것이다. 결과는 `merge_boundaries`(`MergeBoundary`)에 남고, 비교 범위의 커밋은 `relations.commits`에 넣지 않는다. 창이 저장소의 모든 이력을 담았으면 열린 경계가 없어 부르지 않는다. PR 조회가 허용되지 않은 요청은 연결 PR 조회 단계가 없어 경계 비교도 하지 않는다.
- PR 커밋 목록·`merge_commit_sha`로 설명되지 않고 흡수 병합도 아닌 병합이 후보다. 병합 후보는 커밋 조회를 마친 뒤에야 정해진다. 커밋 조회 중 멈췄으면 그때까지의 결과로 고르고, 조회하지 못한 커밋도 PR 밖일 수 있다고 본다.
- 이 후보와 들인 커밋의 정의(`relations.pull_request_less_merges`) 하나를 연결 PR 조회 대상, 변경 내용 계획, 후보 처리의 병합 단위 판정이 함께 쓴다.

| 연결 PR 조회 결과(`Lookup`) | 뜻 |
|---|---|
| `FOUND` | 다음 쪽 없이 이 저장소를 기준으로 연 PR을 돌려줬다 |
| `EMPTY` | 다음 쪽 없이 이 저장소의 PR이 0건이었다(정상 부재). 다른 저장소를 기준으로 연 PR만 돌려준 경우도 여기에 든다 |
| `LIMITED` | 묶음 응답이 단일 응답 크기를 넘었거나(그 묶음의 커밋 모두), 다음 쪽이 있거나(PR이 100건보다 많다. 첫 100건이 다른 저장소 PR로만 찼어도 같다), 기준 저장소를 알 수 없는 PR(`baseRepository`가 null)이 있었다. 다음 쪽은 부르지 않는다. 자료 범위의 한계다 |
| `NOT_REACHED` | 계획했으나 수집이 멈춰 조회하지 못했다. 실패한 묶음과 그 뒤에 계획한 커밋이 여기에 든다 |

조회 거절·오류 응답·null 커밋은 결과 상태가 아니라 수집 실패다(아래 「멈추는 응답」). 다른 저장소를 기준으로 연 PR은 버리고 수만 센다(`foreign_ignored`, 로그의 `foreignBaseIgnored`). 기준 저장소를 알 수 없어 버린 PR은 `unknown_base`로 센다. PR 목록에 없던 이 저장소의 PR은 `pull_requests_from_lookups`에 남긴다. 다만 그 PR의 커밋 목록은 조회하지 않는다. 그 PR 기록의 근거(`evidence_for`)에는 커밋 목록에 관한 한계로 「최근 PR 목록 밖의 PR이라 이 PR에 담긴 커밋 전체는 확인하지 않았다」만 붙는다.

## 변경 내용

변경 내용은 필수 조회, 파일 모드 확인, 선택 조회 셋으로 나눠 계획한다(`RelationObservations.detail_tiers`의 `needed`·`unit_first`·`outside_pull_requests`·`evidence`, 모드 확인은 `mode_checks`). 한 커밋은 한 단계에만 든다. 다른 계정의 커밋은 필수 조회에서만 조회하고, 병합 커밋은 어디서도 조회하지 않는다. 아래 순서로 부른다.

| 단계 | 대상 | 상한에 걸리면 |
|---|---|---|
| 필수 조회 | ① 재제출 관계인 두 PR의 커밋 목록에 든 병합 아닌 커밋 전부. 재제출로 보는 경우는 병합 없이 닫힌 PR과 그보다 나중에 만들어져 병합된 PR이 있고, 뒤 PR의 제목이나 본문이 앞 PR을 번호나 같은 저장소의 PR 주소로 가리킬 때뿐이다 ② cherry-pick 표시(커밋 메시지의 `(cherry picked from commit <전체 SHA>)`)로 이어진 두 커밋. 두 커밋을 모두 관측했을 때만이다 ③ 나눌 수 있어 보이는 단위(PR 커밋 목록, 또는 PR 없는 병합이 들인 커밋)의 모든 커밋. 이슈 조회가 허용됐고, 그 단위의 본인 커밋 메시지가 이슈 목록에서 본 이슈를 2개 이상 가리킬 때다. 흡수 여부나 첫 부모 쪽 경계를 확인하지 못한 병합은 뺀다 | 개수 상한 없이 부른다. 호출 수·시간·총량 상한에 걸리면 확인 중단이다 |
| 파일 모드 확인 | 관계 근거(재제출·cherry-pick 표시)가 있고, 모드를 빼고 계산한 diff 값이 같은(값이 있는) 쌍의 양쪽 커밋. 커밋마다 한 번 같은 경로를 diff 형식으로 받는다 | 필수 조회와 같다. 상세 조회 개수에는 세지 않는다 |
| 선택 0. 단위의 첫 기여 커밋 | 받은 PR 커밋 목록마다 가장 최근 본인 병합 아닌 커밋, 그다음 연결 PR 조회가 돌려준 PR마다 가장 최근 본인 커밋(목록에서 이미 골랐거나 목록을 끝까지 받은 PR은 뺀다). 최근 것부터. PR 단위마다 변경을 확인한 기여 커밋이 하나는 남게 먼저 부른다 | 조회하지 않고 `BEYOND_RANGE`(한계)로 둔다 |
| 선택 1. PR 밖 본인 커밋 | 연결 PR 조회가 빈 목록인 본인 커밋. PR 조회가 허용되지 않았으면 기본 브랜치의 본인 커밋 전부. 최근 것부터 | 선택 0과 같다 |
| 선택 2. 그 밖의 본인 커밋 | 기본 브랜치 목록과 `relations.commits`에 남은 본인 커밋. 최근 것부터 | 선택 0과 같다 |

필수 조회의 관계 판별은 후보 판정과 같은 정의를 쓴다. 글자 규칙(cherry-pick 표시·이슈 번호·PR 번호 읽기)과 diff 값 계산은 `app/candidates/same_change.py`에 있다. 재제출의 상태·순서 조건(앞 PR은 병합 없이 닫혔고 뒤 PR은 더 나중에 만들어져 병합됐다)은 `app/collection/relations.py`의 `resubmission_shape`·`default_resubmission`에 있다. 수집의 조회 계획과 후보 처리가 이 둘을 함께 부른다.

**파일 모드 확인.** 커밋 상세(JSON)에는 파일 모드가 없다. 그래서 같은 변경으로 비교할 쌍만 diff 형식으로 한 번 더 받아, 파일 머리글의 경로·모드 줄(`new file mode 100755` 등)만 Python으로 읽는다. diff의 파일을 변경 파일 목록과 모두 맞추면 그 커밋 기록의 `ChangedFile.mode_lines`에 넣는다. 응답이 크기 상한을 넘었거나(`OVERSIZED`) 파일을 맞추지 못하면(경로가 다름, 이름 바꿈·이진 파일 같은 다른 머리글 줄) 모드를 넣지 않고, 후보 처리는 그 쌍을 비교할 수 없다고 본다. 결과는 `mode_checks`(`ModeCheck`)에 남는다. 필수 조회 도중에 멈췄으면, 받은 변경 내용으로 모드 확인이 필요했을 커밋을 `NOT_REACHED`로 둔다.

선택 0은 PR 단위가 후보가 될 수 있는지, 선택 1은 커밋 묶음을 볼 때 쓰인다. 선택 2는 근거의 관측 사실(커밋별 변경 파일·줄 수)에 쓰이고, 후보 처리가 본인 기여 커밋이 모두 빈 커밋(변경 파일 0개)인 단위를 기준 미달(`BELOW_CRITERIA`)로 셀 때도 쓰인다. 선택 조회를 건너뛰어 변경 내용이 없는 커밋은 빈 커밋으로 보지 않는다. 다만 단위에 변경이 있음을 확인한 본인 기여 커밋이 하나도 없으면 그 단위는 후보가 되지 않고 근거 부족으로 센다([후보 문서](candidate-decision.md#후보로-내지-않은-건수notprovided)).

선택 조회는 아래를 모두 채울 때만 하나씩 부른다. 그래서 선택 조회 때문에 호출 수·수집 총량 상한에 걸리지는 않는다. 수집 시간은 여유를 남길 뿐이라(HTTPS 호출 하나는 주소 확인·여러 주소로의 연결 시도·TLS 연결 때문에 대기 합보다 오래 걸릴 수 있다) 네트워크가 느리면 시간 상한에 걸릴 수 있다. 선택 조회도 응답이 오류이거나 시간 초과·연결 오류면 수집이 멈추고 수집 실패가 된다.

- 필수 조회를 포함해 지금까지 부른 변경 내용 조회가 `max_commit_details`(200)보다 적다. 이미 이 수에 닿았으면 나머지는 시간을 보지 않고 `BEYOND_RANGE`다.
- 수집 시간 마감이 아직 지나지 않았다. 이미 지났으면 건너뛰지 않고 시간 상한 실패(`TIME_LIMIT_EXCEEDED`)로 멈춘다(호출로 세지 않는다).
- 남은 호출이 1회 이상이다.
- 남은 수집 시간이 연결·응답 대기 합의 두 배(2×(5+15)=40초)보다 길다.
- 남은 수집 총량이 단일 응답 크기 상한(10MB)보다 크다.

마감 전의 여유 부족은 조회 범위의 한계다. 부르지 못한 커밋은 처음 건너뛸 때 한계 하나를 남긴다(「연동 계정이 작성자로 기록된 커밋 일부는 상세 조회 개수(200건)나 남은 호출·시간·총량 여유 밖이라 변경 내용을 조회하지 않았다」). 건너뛴 수는 CatchU가 센 수라 적지 않는다(2026-10-08 팀장 결정). 이 조건은 앞 단계가 쓰고 남은 양에 달려 있다. 남은 호출·총량은 받은 응답으로 정해지지만 남은 시간은 실제 시계로 잰다. 그래서 응답이 같아도 앞 호출이 느렸으면 선택 조회를 덜 받는다. 그러면 커밋 묶음(유일한 부모와 변경 파일이 겹치는지)과 그 workIdentity가 달라지거나, 변경을 확인하지 못한 단위가 근거 부족으로 빠질 수 있다. 저장소가 클수록 선택 조회를 덜 받는다. 응답 크기를 넘은 변경 내용은 `OVERSIZED` 한계다.

관계 조회 경로에서는 본인 커밋·PR의 근거에 「연동 계정이 작성자로 기록된 커밋이 아니라 …」·「연동 계정이 연 PR이 아니라 …」 문구가 붙지 않는다. 변경 내용을 받지 못한 본인 커밋에는 `BEYOND_RANGE`·`NOT_REACHED`·`OVERSIZED`의 한계 문구가 붙는다. 본인 병합 커밋에는 「병합 커밋이라 변경 내용을 조회하지 않았다」가, 커밋 조회가 허용되지 않은 요청에서 PR 커밋 목록으로만 본 본인 커밋에는 「커밋 조회가 허용되지 않은 요청이라 변경 내용을 조회하지 않았다」가 붙는다.

## 허용 자료 종류

허용 목록 밖의 종류는 관계 조회에서도 부르지 않는다. 비교 API는 GitHub 문서에서 커밋 API([Commits](https://docs.github.com/en/rest/commits/commits)) 항목에 속하는 커밋 자료 조회로, 두 커밋 사이의 커밋을 돌려준다. 연결 PR 조회는 커밋(GraphQL `Commit`)마다 그 커밋을 담은 PR을 묻는다. 그래서 둘 다 커밋 조회(COMMIT)가 허용돼야 부르고, PR을 돌려주는 연결 PR 조회는 PR 조회(PULL_REQUEST)도 허용돼야 부른다. 비교 API는 PR 커밋 목록을 보완하거나 연결 PR 조회 대상 병합의 경계를 볼 때만 쓰므로 PR 조회도 허용돼야 한다.

| 허용 종류 | 관계 조회에서 부르는 것 | 부르지 않는 것 |
|---|---|---|
| PULL_REQUEST 없음 | 추가 기준 브랜치, 변경 내용과 파일 모드 확인 | PR 목록·PR 커밋 목록·PR API·비교 API·연결 PR 조회. 기본 브랜치의 본인 커밋을 모두 PR 밖(선택 1)으로 다룬다 |
| COMMIT 없음 | PR 커밋 목록(PR 계열 API의 자료) | 커밋 목록·추가 기준 브랜치·PR API·비교 API·연결 PR 조회·변경 내용. 250건에 닿은 PR도 250건만 쓴다. PR 커밋 목록으로만 본 커밋에는 변경 내용이 없다 |
| ISSUE 있음 | 이슈 목록(수집 문서와 같음) | 관계 조회용 호출은 없다. 이슈 번호는 본인 커밋의 이슈 근거에만 쓴다 |

## 멈추는 응답

관계 조회의 모든 호출은 같은 게이트웨이와 요청 상한 안에서 하고, 200이 아닌 응답·오류·상한이면 수집을 멈춘다. 비교 API·추가 기준 브랜치의 404·409·422와 diff 형식 조회의 오류 응답도 같다. 연결 PR 조회는 HTTP 200이라도 `errors`·null 커밋·모양 오류가 있으면 그 묶음을 쓰지 않고 멈춘다(실패 코드는 [연결 PR 묶음 조회](associated-pr-lookup.md#결과와-실패)). GitHub 문서상 큰 diff는 시간 초과로 5xx를 줄 수 있어, diff 형식 조회도 수집 실패로 끝날 수 있다([한계](candidate-checks.md#알려진-한계)). 404는 `REPOSITORY_UNREACHABLE`, 409·422는 `COLLECTION_FETCH_FAILED`, 호출 한도 응답은 `RATE_LIMITED`다. 다시 부르지 않는다. 멈추지 않는 응답은 하나뿐이다. 추가 기준 브랜치 커밋 목록의 첫 쪽이 빈 Git 저장소 응답(409, #117과 같은 문구)이면 커밋 0건으로 받는다.

단일 응답 크기(10MB)를 넘은 경우는 실패가 아니라 한계다. PR 커밋 목록이면 그 PR을 `OVERSIZED`로 두고, 받은 쪽도 소속 근거로 쓰지 않는다. PR API·비교 API면 그 목록의 한계(「250건에 닿은 PR」), 경계 비교면 그 병합의 경계를 확인하지 못한 것, 연결 PR 조회면 그 묶음의 커밋 모두 `LIMITED`, 변경 내용이면 `OVERSIZED`, 모드 확인이면 비교할 수 없음이다. 응답 모양이 어긋나면 `COLLECTION_FETCH_FAILED`로 멈춘다.

멈추면 실패 하나를 남기고(코드는 [수집 문서](github-collection.md)와 같다) 연결을 닫는다. 멈춘 단계는 `relations.stopped_during`에 남는다. 이미 받은 것은 그대로 둔다. 계획했으나 닿지 못한 것은 `NOT_REACHED`로 둔다. 읽지 못한 PR 커밋 목록(PR 기록도 같다), 계획한 연결 PR 조회·경계 비교·모드 확인 가운데 하지 못한 것, 받지 못한 변경 내용(계획한 것과 본인의 병합 아닌 커밋)이 여기에 든다. 연결 PR 조회 중 멈췄으면 앞서 끝낸 묶음은 두고 실패한 묶음부터 `NOT_REACHED`로 둔다. 조회하지 못한 커밋도 PR 밖일 수 있다고 보고 그 커밋을 들인 PR 없는 병합 후보와 그 경계 비교까지 `NOT_REACHED`로 넣는다. 이 구분으로 후보 처리는 확인이 중단된 변경을 보류하고 세지 않는다.

## 250건에 닿은 PR

[PR 커밋 목록 API](https://docs.github.com/en/rest/pulls/pulls#list-commits-on-a-pull-request)는 PR 하나에 커밋을 최대 250건만 준다. 목록이 250건에 닿으면 다음 쪽 표시가 없어도 다 읽었다고 보지 않고, 아래 순서로 PR 전체를 확인한다. 확인 경로와 조건은 작업 동일성 기준의 [결정 기록](../../docs/CatchU_work_identity_records.md#결정)(2026-10-08 「커밋이 250개 넘는 PR은 PR 전체 커밋 수와 비교 API로 확인한다」)이 정했다.

1. 포크(다른 저장소)에서 연 PR이 아니고, PR 응답에 기준 커밋(`base.sha`)이 있고, 커밋 조회도 허용돼야 한다. 하나라도 아니면 250건만 쓰고 이유를 한계로 남긴다.
2. [PR API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)(`GET /repos/{owner}/{repo}/pulls/{번호}`)로 PR의 전체 커밋 수(`commits`)와 그때의 머리 커밋(`head.sha`)을 받는다(1회). PR 목록 항목에는 전체 커밋 수가 없다. 머리 커밋이 PR 목록에서 본 것과 다르면 PR이 조회 중에 바뀐 것이라 비교 API를 부르지 않고 250건만 쓴다. 전체 커밋 수가 중복을 뺀 목록 수보다 작아도 비교 API를 부르지 않고 250건만 쓴다. PR API 응답이 크기 상한을 넘었으면 전체 수를 몰라 250건만 쓴다.
3. [비교 API](https://docs.github.com/en/rest/commits/commits#compare-two-commits)(`GET /repos/{owner}/{repo}/compare/{base.sha}...{PR 머리 커밋 SHA}`)를 `max_compare_pages`(10)쪽까지 읽는다. 이 응답은 비교 범위의 전체 커밋 수(`total_commits`)를 준다.
4. 비교 범위의 전체 수가 PR 전체 커밋 수와 같고, 받은 커밋이 그 수에 닿고, PR 커밋 목록의 250건과 관측한 머리 커밋이 모두 들어 있을 때만 다 읽은 것(`complete`)으로 본다. 판본은 PR API의 머리 커밋과 비교 결과로 확인하므로 GitHub가 어느 250건을 주든 결과가 같다. 빈 쪽이나 다음 쪽 표시가 없는 것은 끝의 증거로 쓰지 않는다.

어긋나면(어느 쪽이든 전체 수가 다름, 받은 개수가 전체 수보다 많거나 그 전에 끝남, 250건이나 머리 커밋이 빠짐) 비교 범위에 기준 브랜치 커밋이 섞였거나 판본이 다를 수 있어 비교 결과를 하나도 쓰지 않고 250건만 남긴다. 비교 쪽수 상한이나 비교 응답 크기 상한에 걸렸으면 250건을 모두 담았을 때만 받은 데까지 PR 커밋으로 더하고 `complete`는 거짓으로 둔다. 비교 조회 거절(404·422)은 한계가 아니라 수집 실패다. 비교 호출도 같은 요청 호출 상한(제안 300회, 실제 HTTP 요청 수) 안에서 하고 예산을 따로 떼지 않는다(2026-10-09 팀장 확인). 상한에 걸리면 수집 실패다.

이런 PR 하나에 최대 14회(목록 3·PR API 1·비교 10)를 부르며, 기본값으로 1,000건까지 확인한다. 결과는 `PullRequestCommits`의 `complete`·`full_list_via_compare`·`limits`에, 확인 근거는 `compared_from`(비교 시작으로 쓴 `base.sha`)·`merge_base`(응답이 준 비교 시작 커밋)·`total_commits`(PR 커밋 수)에 있다. 다 읽지 못한 PR의 근거에는 남긴 커밋 수에 따라 한계가 붙는다.

- 250건만 남겼으면 「PR 커밋 목록 API가 돌려주는 250건까지만 확인했다」와 위의 이유.
- 비교 API로 250건 밖을 일부 더 읽었으면 「PR 커밋이 많아 N건까지만 확인했고 나머지는 확인하지 못했다」. N은 남긴 PR 커밋 수(원본 숫자)다.

다 읽지 못한 PR이 있으면 후보 처리는 그 PR과 겹칠 수 있는 커밋을 PR 밖으로 확정하지 않을 수 있다([후보 문서](candidate-decision.md#목록을-다-받지-못한-pr)). 남은 위험도 있다. `base.sha`는 PR 응답에 기록된 기준 브랜치 커밋이며, 병합 시점의 기준 브랜치 끝과 다를 수 있다. 수와 250건 포함을 대조해 어긋나면 쓰지 않지만, 수가 같다고 두 커밋 집합이 같다는 증명이 되지는 않는다.

## 추가 기준 브랜치

`RelationOptions(extra_base_branches=("release/1.0",))`처럼 호출하는 쪽이 기본 브랜치 밖의 기준 브랜치(통합 브랜치 등)를 명시할 수 있다. 그러면 그 브랜치의 첫 부모 사슬도 흡수 병합을 가리는 데 쓴다. 브랜치 이름으로 기준 브랜치를 추정하지는 않는다. 이름 규칙은 다음과 같고, 어기면 `ValueError`다.

- 영문자·숫자·`.`·`_`·`/`·`-`만 쓰고 255자 이하다.
- `..`·`//`가 없다.
- `/`·`-`로 시작하거나 `/`·`.lock`으로 끝나지 않는다.

중복된 이름과 기본 브랜치와 같은 이름은 무시한다. 경로에는 이름 전체를 URL 인코딩해 넣는다.

개수 상한(다음 쪽 있음)이나 응답 크기 상한으로 끝까지 받지 못한 브랜치가 처음 나오면 커밋 공유 한계 하나(「따로 지정한 기준 브랜치 가운데 커밋을 끝까지 받지 못한 브랜치가 있어, 그 브랜치를 받아온 병합을 작업과 구별하지 못했을 수 있다」)를 남긴다. 브랜치 이름·개수는 넣지 않는다. 그 사슬이 뿌리 커밋에 닿지 않았으면 후보 처리는 본선에 없는 PR 없는 병합을 흡수 병합인지 모르는 것으로 보고 확정하지 않는다. 브랜치가 없다는 응답은 다른 조회 오류처럼 수집을 멈춘다(「멈추는 응답」).

**지금은 비어 있다.** 기본값은 빈 목록이고, 요청 계약의 `Request`·`Scope`는 정의 밖 필드를 받지 않아(`additionalProperties: false`, [메시지 스키마 v1](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/contract-design/worker-messages.yaml)) 요청에서 이 값을 받을 칸이 없다. LIVE 조립([#121](https://github.com/JminAILab/CatchU/issues/121))은 넘길 공급원이 없어 이 값을 넘기지 않으므로 기본 브랜치만 기준 브랜치가 된다. 그때는 통합 브랜치를 작업 브랜치로 받아온 병합이 흡수 병합으로 가려지지 않는다. 그 병합이 PR 없는 병합 후보가 되거나, 들인 커밋이 실제보다 넓게 잡힐 수 있다.

## API 판본 고정

PR 소속 판정은 PR 응답의 `merge_commit_sha`에 기댄다. 호출 통제(`gateway.py`)는 모든 REST 호출에 `X-GitHub-Api-Version: 2022-11-28`을 고정해 보낸다. GitHub REST API 판본 2026-03-10은 PR을 돌려주는 모든 응답(PR 목록·PR API 포함)에서 이 필드를 뺐다([Breaking changes](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes)). 판본 머리글을 올리면 오류 없이 이 값이 모두 비게 된다. 그러면 소속 근거 하나가 사라지고 연결 PR 조회가 늘어나므로, 판본을 바꿀 때는 관계 조회도 함께 고친다. 연결 PR 조회는 GraphQL이라 이 머리글을 보내지 않고, 같은 값을 `mergeCommit`으로 받는다. `test_relation_phase_reuses_the_connection_in_planned_order`가 관계 조회의 모든 REST 호출에 이 판본이 실리는지 확인한다. GitHub는 새 판본이 나온 뒤에도 이전 판본을 24개월 지원한다고 안내한다([API Versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions)).

## 상한(제안값)

관계 조회는 목록과 같은 요청당 상한(호출 2,500회·총량 50MB·수집 시간 1,800초·단일 호출 대기·단일 응답 10MB)을 함께 쓴다. 현행 값은 [#424 후속 결정](repository-analysis-u7.md)을 따른다. 호출 수는 실제 HTTP 요청 수(REST 1회, GraphQL 묶음 요청 1회)다. 연결 PR 묶음 크기(`max_lookup_batch`, 100)와 이전 비교 근거는 [연결 PR 묶음 조회](associated-pr-lookup.md#제안-상한과-근거)에 있다. 비교 쪽 수와 추가 기준 브랜치 범위는 기존 제안값을 유지한다. 요청 전체 처리 3,600초는 [큐 소비자](queue-consumer.md)가 잰다.

| 상한(`CollectionLimits`) | 제안값 | 넘으면 |
|---|---|---|
| `max_compare_pages` | 250건에 닿은 PR 하나당, 또는 첫 부모 쪽이 열린 PR 없는 병합 하나당 비교 API 10쪽(1,000건) | 그 PR 목록의 한계, 또는 그 병합의 경계를 확인하지 못함 |
| `max_base_branch_commits` | 추가 기준 브랜치 하나당 최근 커밋 100건(1쪽) | `BaseBranchLine.complete`를 거짓으로 두고 공유 한계를 남긴다. 사슬이 잘렸으면 본선에 없는 병합을 확정하지 않는다 |
| `max_commit_details` | 선택 조회는 필수 조회와 합쳐 1,500건까지. 필수 조회와 모드 확인은 이 수로 줄이지 않는다 | 한계(`BEYOND_RANGE`) |
| `max_pull_request_commit_lists`(기존) | 관계 조회에서는 쓰지 않는다 | — |

판정에 꼭 필요한 호출은 조회 개수로 줄이지 않는다. 모든 PR의 커밋 목록, 연결 PR 조회, 250건에 닿은 PR의 PR API·비교 API, 열린 경계의 비교, 필수 조회의 변경 내용, 파일 모드 확인이 그렇다. 이 호출이 상한에 걸리면 확인 중단이다. 그래서 관계 조회 없는 경로의 호출 계산은 LIVE 경로에 맞지 않는다. PR 커밋 목록만으로도 1,800회(PR 600건 × 3쪽)일 수 있다. 연결 PR 조회는 #267부터 단계마다 대상 커밋 100개당 요청 1회다(본인 커밋 3,000건이면 30회, PR 없는 병합 후보는 다음 단계에서 따로). 첫 부모 쪽이 열린 병합마다 경계 비교가 1~10회 더 든다. 파일 모드 확인은 관계 근거가 있고 모드를 뺀 값이 같은 쌍의 커밋마다 1회다. PR과 경계가 열린 병합이 많은 저장소는 여전히 `BUDGET_EXCEEDED`로 멈춰 결과가 PARTIAL_FAILED나 FAILED가 될 수 있다.

## 검사와 실제 연결 전 확인할 것

`tests/test_collection_relations.py`가 합성 GitHub 응답으로 위 단계·조건(기본 경로 불변, 판본 머리글, 판본 확인, 조회 거절, 경계 비교, 변경 내용 단계와 마감, 파일 모드 확인, 250건 비교, 멈춤과 `NOT_REACHED`, 허용 종류별 호출, 창 계산, 근거 문구)을 확인한다. 연결 PR 묶음 조회의 시험은 [그 문서](associated-pr-lookup.md#검사와-실제-연결-전-확인할-것)에 있다.

**실제 GitHub에서는 확인하지 않았다.** 실제 연결에서 확인할 것:

- 250건을 넘는 실제 PR에서 비교 API의 `total_commits`와 PR API의 `commits`가 같은지, `base.sha`가 오래된 PR에서는 어떻게 되는지
- 연결 PR 묶음 조회의 필드 대응과 A의 토큰으로 실행되는지([그 문서](associated-pr-lookup.md#검사와-실제-연결-전-확인할-것)), 포크에서 연 열린 PR의 커밋에 빈 목록을 주는지(문서에 적혀 있지 않다)
- 비교 API가 병합의 첫 부모와 병합 사이에서 들인 커밋만 주는지, diff 형식 응답의 파일 머리글(`a/`·`b/` 접두어, 경로 따옴표, 모드 줄)이 합성 응답·로컬 git 출력과 같은지. 다르면 모드 확인이 모두 '맞출 수 없음'이 되어 관계 쌍을 합치지 않는다. 큰 diff가 시간 초과(5xx)로 끝나는지도 본다
- 저장소 크기별 관계 조회의 호출 수와 시간(합성 비교는 [연결 PR 묶음 조회](associated-pr-lookup.md#제안-상한과-근거))
- 후보 판정 쪽 항목은 [후보 판정의 한계와 검사](candidate-checks.md#합성-검사로-확인한-것과-실제-자료로-확인할-것)에 있다
