# 후보 판정의 한계와 검사 — #118

> [후보 묶음과 작업 동일성](candidate-decision.md)의 「알려진 한계」·「시험」·「합성 검사로 확인한 것과 실제 자료로 확인할 것」 절을 문서 크기 상한(36 KB) 때문에 따로 옮겼다. 말뜻과 사례·한계 번호는 그 문서를 따른다.

## 알려진 한계

- **추가 기준 브랜치**: 기본값은 빈 목록이고 요청 계약에는 받을 칸이 없다. LIVE 조립([#121](https://github.com/JminAILab/CatchU/issues/121))에서 저장소별 내부 설정으로 넘기지 않으면 기본 브랜치만 기준 브랜치다. 그때 통합 브랜치를 받아온 병합이 PR 없는 병합 후보가 되거나 들인 커밋이 넓게 잡힐 수 있다([추가 기준 브랜치](relation-collection.md#추가-기준-브랜치)). 넘겼는데 그 브랜치를 끝까지 받지 못하면 본선에 없는 병합을 확정하지 않는다([병합이 들인 커밋](candidate-decision.md#병합이-들인-커밋)).
- **본선**: 기본 브랜치에서 `git pull`로 만든 병합이 있으면 첫 부모 사슬이 실제 본선과 다를 수 있다. 창의 머리가 하나가 아니면(시각이 어긋난 목록 등) 병합 단위를 확정하지 않고 단위 미확정으로 센다. 목록 단계에서 멈췄으면 확인 중단이라 세지 않는다.
- **PR 조회가 없는 요청의 병합**: 첫 부모 쪽 경계 비교는 연결 PR 조회 단계에서만 한다. 그래서 커밋 조회만 허용한 요청에서는 첫 부모 쪽이 창 밖으로 이어진 PR 없는 병합을 확정하지 않는다(자료 범위 한계).
- **squash와 rebase 마지막 커밋**: 커밋 목록을 다 받지 못한 PR에서는 `merge_commit_sha`이면서 부모가 하나인 커밋을 기여 근거에서 뺀다. rebase로 합친 PR의 마지막 커밋도 목록 없이는 squash 커밋과 구분하지 못해 함께 빠진다. 연결 PR 조회로 배정된 나머지 rebase 커밋은 근거로 남는다.
- **L13**: 커밋 목록을 다 받지 못한 기본 브랜치 대상의 열린·병합 PR은 보류 대상이 아니다. 그 PR에서 받지 못한 커밋 가운데 하나가 PR 없이 기본 브랜치에도 직접 들어왔으면 그 커밋은 PR 밖 후보가 되어, 한 작업이 Catch 둘로 갈릴 수 있다. 그 후보의 근거에 「커밋 목록을 다 받지 못한 기본 브랜치 대상 PR이 있어, 그 PR에도 담긴 커밋일 수 있다」가 남는다(2026-10-09 팀장 결정).
- **먼저 병합된 PR의 목록**: 먼저 병합된 PR의 커밋 목록을 다 받지 못했으면(크기 상한, 판본 불일치, 250건에서 다 읽지 못함) 그 PR에도 든 변경이 뒤 PR에 배정될 수 있다. 보류하지 않고 뒤 PR 후보의 PR 근거에 「먼저 병합된 PR 가운데 커밋 목록을 다 받지 못한 PR이 있어, 그 PR에도 담긴 변경일 수 있다」를 붙이며, 건수는 바꾸지 않는다(2026-10-09 팀장 결정, [배정](candidate-decision.md#배정)). 수집이 멈춰 받지 못한 목록은 지금처럼 확인 중단이다. 앞선 PR이 병합되지 않은 PR(병합된 PR이 없을 때 번호가 작은 PR)이면 이 문장을 붙이지 않는다. 결정이 먼저 병합된 PR만 정했고, 병합 안 된 PR의 커밋이 250건을 넘으면서 다른 PR과 커밋을 나누는 경우는 드물어 남는 누락으로 둔다(2026-10-10 팀장 확인).
- **수집 범위(L14)**: 관계 조회는 최근 PR 100건 목록의 모든 PR(다른 계정이 연 PR 포함)의 커밋 목록을 받고, 거기서 찾은 본인 커밋(squash로 합친 PR의 원래 커밋 포함)의 변경 내용도 상세 조회 범위 안에서 받는다(2026-10-09 팀장 결정으로 유지). 그래서 L14의 누락은 다음만 남는다: 최근 PR 100건 밖의 PR, 커밋 목록 크기 상한이나 250건 한계로 다 받지 못한 목록, 상세 조회 개수(200건)나 남은 여유 밖의 커밋.
- **호출 예산**: 판정에 꼭 필요한 호출은 조회 개수로 줄이지 않는다. 그래서 PR 커밋 목록만으로 최악 300회(PR 100건 × 3쪽)가 될 수 있고, 연결 PR 조회는 PR 커밋 목록으로 설명되지 않은 본인 커밋마다 1회다. PR과 직접 커밋이 많은 저장소는 요청당 호출 상한(제안 300회)에 걸려 `BUDGET_EXCEEDED`로 멈추고, 결과가 PARTIAL_FAILED나 FAILED가 될 수 있다([상한](relation-collection.md#상한제안값)). 호출 수를 줄이는 방법(여러 커밋의 연결 PR을 한 번에 묻는 GraphQL 묶음 조회)과 상한 재검토는 #267에서 #121 실제 연결 전에 한다(2026-10-10 팀장 결정).
- **큰 diff**: 파일 모드 확인(diff 형식 조회)의 오류는 다른 조회 오류처럼 수집 실패다. [GitHub 문서](https://docs.github.com/en/rest/commits/commits#get-a-commit)는 큰 diff가 시간 초과로 5xx 응답을 줄 수 있다고 적는다. 그래서 큰 diff가 시간 초과되면 요청이 수집 실패로 끝날 수 있다. 다만 이 조회는 관계 근거가 있는 두 커밋 모두 보통 조회(커밋 상세)에서 `patch`를 받은 경우에만 하므로 드물다. #121 실측에서 확인한다.
- **남은 시간**: 변경 내용 선택 조회는 남은 수집 시간(실제 시계)에 따라 덜 받을 수 있다. 그러면 같은 응답이어도 커밋 묶음이 달라지거나, 변경 내용을 확인하지 못한 단위가 근거 부족으로 빠질 수 있다.
- **총 처리 시간**: 기준 문서의 수집 상한에는 요청당 총 처리 시간([#116 제안](../../docs/CatchU_collection_control_scope.md#23-자원시간-상한) 20분, 수집·후보·생성 합)도 들어 있다. 수집 모듈은 수집 시간(10분)만 재고, worker의 다른 곳도 아직 총 처리 시간을 재지 않는다.
- **이슈 단위**: 이슈로만 기여한 후보는 만들지 않는다. 작업 단위 문서가 이슈 단위의 형식만 정했고 10월 동의 문구(커밋·PR·diff)에 이슈가 없기 때문이다. 이슈 기록은 이슈 조회가 허용된 요청에서 나누기 신호와, 본인 기여 커밋이 가리킨 이슈의 근거([후보 문장과 근거](candidate-text.md#후보-내용))로만 쓴다. `identity.py`는 형식만 지원한다.
- **병합 커밋에만 생긴 변경**: 충돌 해결처럼 병합 커밋에만 생긴 변경은 어느 단위의 변경도 아니다. 병합 커밋은 경계로만 쓰기 때문이다(기준 문서 「한계와 실제 구현에서 검증할 것」의 열린 항목에 대한 이 구현의 답).
- **결과 사이 변화**: 다른 결과에서 단위·묶음·나누기가 바뀌면 값이 달라진다(기준 문서의 한계 L1~L6. 묶음 경계 변화는 L3, 나누기 변화는 L5). 10월에는 이 경로가 없다.

## 합성 검사로 확인한 것과 실제 자료로 확인할 것

합성 검사로 확인했다(네트워크 없음, 로컬 검증):

- wi1 값의 불변·민감성, 공백을 무시한 diff 값과 실제 `git patch-id --stable`의 대조, 번호 읽기 규칙
- 입력 순서를 바꿔도 같은 묶음·병합 배정·나누기
- 기준 문서 사례(C1·C3·C6–C8·C10–C17·C20–C30)와 쌓아 올린 PR, PR 조회를 허용하지 않은 요청(PR 호출 0회)
- 보류 건수를 조회 완료(단위 미확정)와 확인 중단으로 나눈 로그

합성 검사 통과는 실제 확인이 아니다. 앞의 두 항목은 #118에서 확인하지 못한 항목으로, [#117](https://github.com/JminAILab/CatchU/issues/117) 실제 수집 결과에 후보 판정을 직접 돌려 확인한다. 나머지는 다른 이슈로 넘긴 항목이다.

- 연결 PR API와 `merge_commit_sha`가 병합 커밋·squash·rebase마다 실제로 PR을 가리키는지(rebase로 합친 PR의 마지막이 아닌 커밋 포함), PR 번호가 저장소 안에서 다시 쓰이지 않는지, 보류 건수의 실제 빈도
- GitHub의 `patch`와 diff 형식 응답(파일 모드 줄)으로 계산한 값이 실제 git의 `git patch-id --stable`과 같은지(합성 검사는 합성 git 저장소로만 대조했다), 64자 SHA 저장소
- repositoryId가 이름 변경·이전 뒤에도 같은지: #133
- 실제 요청을 회원 영역(A)이 주는 자격정보로 끝까지 수집해 후보까지 만들 때 관계 조회의 호출 수·시간이 상한 안에 드는지, 큰 diff의 diff 형식 조회가 시간 초과(5xx)로 끝나는지: 처리 순서 연결([#121](https://github.com/JminAILab/CatchU/issues/121))에서 잰다
- 실제 자료에서 잘못 합침·잘못 나눔 검수: [#122](https://github.com/JminAILab/CatchU/issues/122)([#37](https://github.com/JminAILab/CatchU/issues/37)의 실제 자료 사용 조건 안에서)
- B가 저장소·방식이 다른 값을 거부하는 것과 E 실패 기록을 잇는 통합 검증, 동시에 등록해도 한 Catch로 모이는지(PR #143의 시험 재사용): [#105](https://github.com/JminAILab/CatchU/issues/105)

원본 비공개 관측 책임(기준 문서의 OQ-B3)은 #118의 범위가 아니다.
