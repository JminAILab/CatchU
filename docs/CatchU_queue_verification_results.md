# CatchU 큐 기술 검증 — 결과 기록

> **지위: 기록** — [큐 기술 검증](CatchU_큐_기술검증.md)의 확인 방법과 실험 결과다. 2026-10-02 세 엔진 재실행 기록이며 소급 수정하지 않는다. 판정과 개발 조건·배포 전 조건은 원 문서 「결론」에, 쟁점은 [구현 요구와 쟁점](CatchU_queue_requirements.md)에 있다. 영역 이름(E·F·B·H)과 용어 「분석」(생성기 호출 하나 전체, LLM 호출은 그 일부)·「정체 복구」(잠금이 끊긴 작업을 큐가 다시 주는 것)는 원 문서 첫머리와 「결론」을 따른다. 본문의 개발 조건·배포 전 조건·쟁점 번호와 절 링크는 이 기록을 올린 2026-10-02 판 원 문서·구현 요구 문서 기준이다. AI가 한 번에 읽을 수 있게 36 KB 미만으로 유지한다.

## 결과

47개 시나리오의 판정과 분석 호출 수는 세 엔진에서 모두 같았다. 엔진마다 충족 38, 미충족 9, 무효·오류 0이며, 미충족 9개는 모두 비교용 "큐만" 변형과 정체 복구를 끈 변형이다. 판정에 쓰지 않은 관찰값 가운데 실행 시각·순서·무작위 값에 따라 달라지는 것은 엔진마다 달랐다. 아래 2의 E 거부 이유(B2·B4), 두 번째 작업을 넣은 직후의 상태(B2~B4, 대기·처리 중), 중복 방지 이벤트 수(B6), 작업 완료 직후 F가 남긴 잠금 갱신 오류 로그(valkey-7.2.11의 일반 F·정체 복구 켬 생성기 호출 전 중단과 L3), L2에서 정체 전에 남은 두 오류 로그의 순서, 재전송 메시지 ID(D1, 무작위 접미사), 접수 시각(G1)이다. 엔진별 요약은 [results/](queue-verification/results/)에 있고, 프로세스별 원본 로그는 키트를 돌리면 `runs/`에 생기며 커밋하지 않는다.

### 1. Node·Python 연결

| 확인 | 기대 | 실제 |
|---|---|---|
| 양쪽 패키지가 Redis에서 실행하는 스크립트 | 같아야 같은 큐 구조를 공유한다 | 49개 모두 SHA-1까지 같다(`compare_lua.cjs`). 공식 Python README도 같은 스크립트를 써서 상호 운용된다고 적는다 |
| Node가 넣은 합성 요청(`Request`) → Python | 값 그대로, worker 계약 검사 통과 | 그대로, 통과. 한글·이모지·따옴표·역슬래시·줄바꿈·U+2028·빈 목록(`allowedResourceTypes: []`)을 넣은 요청도 같다 |
| Python이 받은 값을 반환값·새 작업으로 돌려줌 → Node | 값 그대로 | 그대로. 정수·음수·2⁵³−1·소수·참거짓·null·빈 목록·빈 객체가 Python에서 각각 정수·소수·불리언·`None`·목록·사전으로 읽히고 Node로 돌아와도 같다 |
| 요청 → dev worker 처리 → 결과 → E 수신(합성 시나리오 7개) | 분석 1회, E `ACCEPTED`, 시나리오마다 미리 정한 종결값·실패 단계와 일치, 큐를 거친 결과가 F 보존본과 같음 | 성공·정상 0건·부분 실패·실패·초안 실패(본문 `null`)·질문 실패 모두 충족. 본인용 최소 질문(한글)도 그대로 전달됐다 |
| 생성기가 실행 여부를 확인하지 못하는 시나리오 | 결과 없음, E가 `RECEIVED`·`RUNNING`·`UNCERTAIN`을 받음 | 충족. 단 E 처리 상태는 `RUNNING`에 머문다(「[E와 확인할 쟁점](CatchU_queue_requirements.md#e와-확인할-쟁점)」 1) |
| E가 돌려준 수신 확인(Node 작업의 반환값) → Python | Python이 읽을 수 있음 | 작업 ID로 다시 읽어 `ACCEPTED/OK`를 얻었다 |

판본 관련 사실(공식 자료):

- Python 패키지는 PyPI에서 Alpha로, 공식 문서 원본(6.3.11 태그)의 설명문에서 "실험적"으로 표시된다. 공식 CI에는 Node와 Python이 같은 큐를 쓰는 교차 언어 시험이 없다. 그래서 개발 조건 6을 둔다.
- BullMQ 공식 블로그(2026-09-27)는 당시 판본(Node 6.3.9, Python 3.2.7)을 나열하고, 모든 언어가 같은 Lua 스크립트를 공유해 한 언어에서 넣은 작업을 다른 언어 worker가 처리할 수 있다고 설명한다. 그 뒤 판본끼리의 대응표는 없다. 이번 두 판본(6.3.11, 3.3.0)은 그보다 새 판본이라 스크립트 비교로 확인했다.
- Node 6부터 `ioredis`는 자동 설치되지 않는다. api에서 쓰려면 직접 설치해야 한다. `@nestjs/bullmq` 12.0.0은 bullmq 6.x와 api의 NestJS 12를 허용한다(판본 범위만 확인했고 Nest 모듈로 실행하지는 않았다).
- Python에는 Node의 일부 기능(작업 시작 횟수 상한, 중복 방지 키 직접 해제)이 없고, 작업 ID 형식 검사(`:` 금지 등)도 하지 않는다. 작업 ID 규칙은 애플리케이션이 지킨다.

### 2. 중복 전달

요청 작업의 작업 ID는 `attemptId`로 두었다. 두 번째 작업이 실제로 처리됐는지(큐가 버리는 경우는 처리되지 않았는지)를 먼저 확인하고 판정했다.

| 사례 | 큐만(일반 F) | 보호 F |
|---|---|---|
| 같은 작업 ID로 다시 넣음, 완료 작업이 Redis에 남아 있음 | 큐가 무시. 분석 1회 | — |
| 같은 작업 ID로 다시 넣음, 완료 작업을 지운 뒤 | **새 작업이 생겨 분석 2회** | 분석 1회. 결과가 이미 E에 닿은 것을 확인하고 다시 보내지 않음 |
| 다른 작업 ID로 같은 요청을 다시 넣음 | **분석 2회** | 분석 1회. 위와 같음 |
| BullMQ 중복 방지 옵션(`deduplication`, `id: attemptId`) | (큐 동작 관찰, 일반 F로는 돌리지 않음) 대기 중 두 번째 추가는 무시. **작업이 끝나면 풀려** 같은 중복 방지 ID로 새 작업(작업 ID가 다름)이 생김 | 분석 1회. 새 작업은 보존 결과 분기로 감 |
| 같은 `attemptId`인데 내용(`requestedAt`)이 다른 요청 | — | 분석·재전송 없이 멈춤(사람 확인). 분석 1회 |
| 시도 기록이 없는데 접수 시각이 기록 수명(시험값 60초)보다 오래된 요청 | — | 분석 0회. `UNCERTAIN`만 보냄(쟁점 3) |

- **큐가 막는 것**: 같은 작업 ID의 작업 기록이 Redis에 남아 있는 동안의 추가. 중복 방지 옵션은 작업이 끝날 때까지만 막는다. 공식 문서도 작업 ID 중복 방지는 작업이 지워지면 끝나고, BullMQ는 최악의 경우 "최소 한 번" 전달이라고 적는다.
- **애플리케이션이 막아야 하는 것**: 작업 기록이 지워진 뒤의 재전달, 다른 작업 ID로 들어온 같은 시도, 큐 자료가 사라진 뒤 다시 넣은 요청, F 기록이 지워진 뒤 다시 온 요청. 보호 F의 시도별 기록이 앞의 둘을 막았고, 셋째는 아래 5에서, 넷째는 위 표의 마지막 행에서 확인했다.
- 일반 F가 두 번 돈 경우 두 번째 결과는 #116 규칙대로 새 `messageId`로 보내졌고, 같은 `resultId`라 E가 중복으로 걸렀다. 두 결과의 완료 시각(`finishedAt`, 초 단위)이 같으면 `DUPLICATE`, 다르면 내용 충돌(`PAYLOAD_CONFLICT`)로 거부했다. E의 중복 검사는 잘못된 반영은 막지만, 이미 일어난 두 번째 분석(수집·LLM 비용)은 막지 못한다.

### 3. worker 중단과 재기동

F를 다섯 지점에서 강제 종료(SIGKILL)하고 다시 띄웠다. 숫자는 분석 호출 횟수, 괄호는 E가 받은 것이다. 각 실행은 죽은 직후의 기록(중단 로그, 분석 호출 수, 시작 표식·결과·전송 기록)이 그 지점과 맞는지 먼저 확인했고, 맞지 않은 실행은 없었다.

| 중단 지점 | 일반 F, 정체 복구 켬(`maxStalledCount=1`, 기본값) | 일반 F, 정체 복구 끔(`0`) | **보호 F, 정체 복구 켬** | 보호 F, 정체 복구 끔 |
|---|---|---|---|---|
| 생성기 호출 전(`RUNNING`을 보낸 뒤) | 1 (`SUCCEEDED`) | 0, **E가 `RUNNING`에 멈춤** | **1 (`SUCCEEDED`)** | 0, **E가 `RUNNING`에 멈춤** |
| 시작 표식 뒤·분석 호출 전 | (표식 없음) | (표식 없음) | **0 (`UNCERTAIN`)** | 0 (`UNCERTAIN`) |
| 분석 중(호출은 했고 끝났는지 모름) | **2** (`SUCCEEDED`) | 1, **E가 `RUNNING`에 멈춤** | **1 (`UNCERTAIN`)** | 1 (`UNCERTAIN`) |
| 분석 끝·결과 보존 전 | (시험 안 함, 분석 중과 같은 경로) | (시험 안 함) | **1 (`UNCERTAIN`)** | 1 (`UNCERTAIN`) |
| 결과 보존 뒤·전송 전 | **2** (`SUCCEEDED`) | 1, **E가 `RUNNING`에 멈춤** | **1 (`SUCCEEDED`)** | 1 (`SUCCEEDED`) |

`UNCERTAIN`을 받은 경우에도 E의 처리 상태는 `RUNNING`으로 남는다(쟁점 1).

- **기본 설정의 정체 복구가 분석을 다시 부른다.** 죽은 worker의 잠금이 만료되면 큐가 작업을 대기열로 돌려 재기동한 worker에게 다시 준다. 공식 문서도 같은 동작을 적는다. 큐는 "분석 호출을 시작했는지"를 모른다.
- **정체 복구를 끄면 다시 부르지는 않지만 작업이 조용히 실패한다**("job stalled more than allowable limit"). 처리 함수가 다시 불리지 않으니 일반 F에서는 모든 지점에서 E가 `RUNNING`에 머문다. 보호 F는 재기동 때의 기동 점검이 시작 표식만 남은 시도에는 `UNCERTAIN`을, 보존 결과에는 그 결과를 보내 E가 알게 됐다. 그러나 생성기를 부르기 전에 죽은 요청은 기록에 시작 표식이 없어 E가 `RUNNING`에 머물렀다. 한 번도 분석하지 않았는데도 그렇다. 자동 재실행을 막는 큐 설정은 이것뿐이지만, 요청을 멈춰 세우는 대가가 크다. 그래서 개발 조건 3에서 정체 복구를 켜 두고 재실행 방지는 애플리케이션이 맡는다.
- **보호 F + 정체 복구 켬**에서는 다섯 지점 모두 기대한 결과가 나왔다. 다시 받은 작업은 기록을 보고 하나만 한다. 결과가 있으면 E에 닿았는지 보고 닿지 않았으면 그 결과를 다시 보낸다. 시작 표식만 있으면 분석하지 않고 `UNCERTAIN`을 보낸다. 둘 다 없으면 분석을 부른 적이 없으므로 처음 실행한다.
- 시작 표식을 남긴 직후, 분석을 부르기 전에 죽은 경우도 `UNCERTAIN`이 된다(분석 0회). 기록만으로는 "표식 뒤 호출 전"과 "호출 중"을 구별할 수 없어 안전한 쪽을 택한 것이다. 표식과 호출 사이에 다른 일을 두지 않는다.
- 결과를 만들었지만 보존하기 전에 죽은 경우도 시작 표식만 남으므로 `UNCERTAIN`이 됐다. [#116](CatchU_collection_control_temp_data.md#43-정리-실패프로세스-중단)이 "막을 방법이 없다"고 한 범위와 같다.
- 결과 보존 뒤 중단에서 보존 결과를 보낸 것은 재기동 때의 기동 점검이었다([#116 「정리 실패·프로세스 중단」](CatchU_collection_control_temp_data.md#43-정리-실패프로세스-중단)의 "기동할 때 전달 표식이 없는 결과를 찾아 다시 보낸다"). 그 뒤 정체 복구로 다시 받은 작업은 E의 수신 확인을 보고 건너뛰었다.
- 이 판단은 worker 프로세스 하나·동시 처리 1을 전제로 한다. 그래야 다시 받은 작업을 꺼낼 때나 기동할 때 앞 실행이 끝났거나 죽어 있다. 배포 중 앞 worker와 새 worker가 잠시 함께 돌거나 worker를 여러 대로 늘리면 살아 있는 실행을 실행 불명으로 잘못 볼 수 있다(배포 전 조건 6). 여러 대가 필요하면 공유 저장소와 실행 중인 소유자 확인을 다시 정한다.

#### 살아 있는 worker의 잠금 상실

생성이 잠금 시간보다 오래 걸리는 경우다. 실험은 분석 6초·잠금 2초로 했고, worker는 죽지 않았다.

| 구성 | 분석 호출 | 관찰 |
|---|---|---|
| 일반 F, 분석이 이벤트 루프를 막음 | **2** | 잠금 갱신이 멈춰 처리 중인 작업이 정체로 판정되고 다시 실행됐다. 두 번째에도 정체돼 결국 실패 처리. E는 두 번째 결과를 내용 충돌로 거부 |
| 보호 F, 같은 구성 | 1 | 정체 1회 뒤 다시 받은 작업에서 결과가 E에 닿은 것을 보고 분석을 건너뛰었고, 요청 작업은 완료로 끝남 |
| 일반 F, 분석을 별도 스레드에서 실행 | 1 | 잠금이 계속 갱신돼 정체 판정 자체가 없음(정체 0회), 요청 작업 완료. valkey-7.2.11에서는 작업 완료 직후 잠금 갱신 오류 로그가 1건 남았다 |

Python BullMQ는 잠금 갱신을 같은 asyncio 루프에서 돌린다. dev worker의 생성기 인터페이스는 동기 함수이므로, worker의 처리 함수에서 그대로 부르면 생성이 잠금 시간(기본 30초)보다 길 때 위 첫 줄과 같아진다. 실제 수집·생성은 30초를 넘기 쉽다([#116 「자원·시간 상한」](CatchU_collection_control_scope.md#23-자원시간-상한)의 제안은 요청당 최대 20분). 그래서 개발 조건 4를 둔다. worker가 하나뿐이어도 생기는 일이다.

### 4. 결과 전달과 수신 확인

| 사례 | 기대 | 실제 |
|---|---|---|
| 보존 결과를 `messageId`만 새로 붙여 다시 보냄([#116 「재전달」](CatchU_collection_control_temp_data.md#52-재전달)) | 분석 없이 같은 결과, E `DUPLICATE` | 분석 1회 유지, `ACCEPTED` 뒤 `DUPLICATE/ALREADY_RECEIVED`. Python이 두 번째 수신 확인도 읽음 |
| E가 수신 기록을 저장한 뒤 큐 작업 완료(수신 확인 반환) 전에 죽음 | 큐가 결과를 E에 다시 줌, E는 중복 수신으로 처리 | 재기동한 E가 같은 결과를 다시 받아 `DUPLICATE`로 끝났다. 분석 1회. 등록을 하지 않는 실험이라 등록 중복 여부는 확인하지 못했다. **이때 결과 본문은 등록 경로로 다시 넘어가지 않는다**(E 수신 구현이 중복이면 본문을 넘기지 않음, 쟁점 4·배포 전 조건 1) |
| E가 꺼진 동안 F가 결과를 보냄 | 결과는 큐에서 기다림, 수신 확인 없음은 실패가 아님 | 결과 작업이 대기 상태, 반환값 없음. E를 켜자 `ACCEPTED`. 분석 1회 |
| 종결 결과 뒤에 늦은 `RUNNING` | 종결 상태 유지 | E가 무시(`TERMINAL_UNCHANGED`) |

- 큐 작업이 "완료"됐다는 것은 받는 쪽 처리 함수가 예외 없이 끝났다는 뜻일 뿐이다. 요청 작업 완료는 "F가 이 시도를 다뤘다"(처리 전 거부 포함)이다. 결과 작업 완료는 "E 수신 처리가 끝났다"이며 수락뿐 아니라 거부(`REJECTED`)·식별 불가로 끝난 경우도 포함한다. 저장소 오류일 때만 작업이 실패로 끝난다(식별 불가·저장소 오류는 E 수신 코드로 확인했고, 실험에서 관찰한 것은 수락·`DUPLICATE`·내용 충돌 거부·접수 맥락 불일치 거부다). 어느 쪽도 서비스 DB 반영(`APPLIED`)이나 본인 조회 가능이 아니다. 실험에서도 E 반영 상태는 계속 `PENDING`이었다(B 등록을 하지 않았으므로).
- 수신 확인을 Node 작업의 반환값으로 돌려주고 Python이 작업 ID로 읽는 방식이 동작했다. BullMQ의 이벤트 스트림(`QueueEvents`)은 기본으로 새로 시작한 뒤의 이벤트만 읽는다. 마지막으로 읽은 위치를 넘기면 이어 읽을 수 있지만, 스트림은 약 1만 건에서 잘리고 큐 자료와 함께 사라질 수 있으므로 수신 확인의 유일한 통로로 쓰지 않는다.

### 5. 큐 저장소 조건

자료가 사라지는 사례는 "보낸 것이 실제로 큐에서 사라졌는지"를 먼저 확인하고 판정했다. E가 큐에서 사라진 요청을 다시 넣는 구현은 아직 없으므로, 그 자리는 실행기가 같은 요청을 같은 작업 ID로 다시 넣어 대신했다.

| 사례 | 실제 |
|---|---|
| 상시 영속성이 없는 서버 재시작(NCP와 비슷한 조건), F가 처리하기 전 | **대기 중 요청이 사라졌다.** E는 아무것도 받지 못해 `QUEUED`에 머물렀다. 실행기가 같은 요청을 다시 넣자 F가 처리했다(분석 1회, F가 처음 받은 요청이라 보호 기록은 쓰이지 않음) |
| 같은 조건, F가 결과를 보낸 뒤 E가 받기 전 | **보낸 결과와 진행 알림이 사라졌다.** E는 `QUEUED`에 머물렀다. 실행기가 같은 요청을 다시 넣자 보호 F가 "결과는 있는데 큐에도 수신 확인에도 없음"을 보고 분석 없이 보존 결과를 새 `messageId`로 다시 보냈고 E가 `ACCEPTED`로 받았다(분석 1회) |
| 같은 조건, F가 `UNCERTAIN`을 보낸 뒤 E가 받기 전 | **보낸 알림이 사라졌다.** 실행기가 같은 요청을 다시 넣자 보호 F가 시작 표식만 있는 것을 보고 분석 없이 `UNCERTAIN`을 다시 보냈고, E 처리 상태가 `QUEUED`에서 `UNCERTAIN`이 됐다(분석 1회) |
| 같은 조건, 결과가 사라졌고 아무도 요청을 다시 넣지 않음 | F의 주기 점검(시험값 2초)이 결과 작업이 없어진 것을 보고 보존 결과를 다시 보냈고, E가 `ACCEPTED`로 받은 뒤 다음 점검에서 전달 표식을 남겼다(분석 1회) |
| 같은 조건, E가 결과를 거부(`REJECTED`, 접수 맥락 불일치)한 뒤 큐 자료가 사라짐 | 거부를 확인한 주기 점검이 거부 표식을 큐 밖에 남겼고, 큐 자료가 사라진 뒤의 점검 3번 모두 다시 보내지 않았다(전송 1회) |
| AOF(1초 단위 기록)를 켠 서버를 정상 종료로 재시작(로컬 비교용, NCP에서 쓸 수 있는지 미확인) | 요청이 남아 처리됐다 |
| 분석 중 큐 서버가 12초 멈췄다가 빈 상태로 복귀 | 두 프로세스 모두 죽지 않고 다시 연결했다. 분석이 끝난 뒤 결과 전송은 서버가 돌아올 때까지 재시도돼, **프로세스를 다시 띄우기 전에** E가 `ACCEPTED`로 받았다. 요청 작업 기록은 사라져 F의 완료 기록이 오류("Missing key")로 끝났다. 분석 1회 |
| 축출 정책이 `allkeys-lru` | 연결과 작업 추가는 그대로 됐다. Node는 연결마다 `IMPORTANT! Eviction policy is allkeys-lru. It should be "noeviction"` 경고를 냈고, Python은 작업 추가만으로는 경고하지 않고 작업 상태를 조회할 때 처음 같은 경고를 냈다 |

- 축출 정책이 잘못돼도 BullMQ는 경고만 하고 돈다. 메모리가 차면 큐 자료가 조용히 지워질 수 있으므로 배포 전 조건 3에서 직접 확인한다. `noeviction`이어도 메모리가 차면 쓰기가 실패하므로 메모리 사용량과 큐 추가 실패를 지켜본다.
- Python 클라이언트는 기본 연결에서 연결 오류·시간 초과가 나면 명령마다 최대 20회 다시 시도한다(간격을 늘려 최대 20초, 기다리는 시간만 합쳐 약 350초이고 접속·명령 시간은 별도). 작업 가져오기는 이 재시도를 다 쓴 뒤에도 15초를 쉬고 다시 시작한다(공식 소스). NCP 장애 조치 최대 3분보다 길게 버티지만, DNS 전환 뒤 재연결은 확인하지 못했다.
