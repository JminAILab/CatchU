# CatchU 코딩 절차 — 코드 수정·검사·자료·PR

> 지위: [작업관리](CatchU_작업관리.md) §4·§7의 코딩·검사·자료·PR 절을 2026-10-01에 그대로 옮긴 문서다([#197](https://github.com/JminAILab/CatchU/issues/197)). 지위와 적용 범위는 작업관리와 같다. AI가 한 번에 읽을 수 있게 19 KB 미만으로 유지한다.

코드를 고치거나 PR을 쓸 때 읽는다. 착수 안내·이슈 본문·진행·종료 같은 공통 절차는 [작업관리](CatchU_작업관리.md)에 있다.

## 코딩 전 범위와 기존 변경 확인

“이 이슈 구현해 줘”의 기본 흐름은 **관련 이슈·명세·기존 코드 확인 → 구현·필요한 테스트 → PR → 사람 리뷰·수정**이다. 범위와 기대 결과가 정해져 있으면 AI가 착수 조건·관련 계약·서비스 README와 실제 설정·필요한 검사를 직접 확인하고 바로 구현한다. 확인 내용과 예정 검사는 짧게 알릴 수 있지만 별도 설계안·검증 계획·작성 전 승인을 만들지 않는다(11월 Unit 구현은 AI-DLC 단계의 기능 설계·코드 생성 계획과 그 승인을 따른다). ERD·목업·API에 없는 권한·공개·실패·자료 사용 조건은 그 작업에 필요한 요구사항·기능 설계 원문을 찾아 적용한다. 내부 함수·컴포넌트 구성과 검사 도구는 담당자·AI가 정하고, 제품 범위·계약·실제 외부 자료 사용과 비용·담당과 일정을 바꿔야 할 때만 사람의 판단을 받는다. 이미 합의된 사항은 다시 묻지 않는다. 내부 구성은 다음을 지향하되(머지 조건 아님), 계약·서비스 README 규약과 트랜잭션 순서가 먼저다. 밖에서 온 값(요청·큐 메시지·외부 응답)은 들어온 곳에서 검사해 타입으로 바꾸고, 계약·ERD가 요구할 때만 안쪽에서 다시 검사한다. 바뀌는 이유가 다른 일(입력 해석·업무 판단·저장)이 한 함수에 얽히면 나누되, 한 업무의 호출 순서는 한 함수에 남기고 줄 수만 보고 쪼개지 않는다. 어긋나면 버그가 되는 계약 값·상태 목록은 같은 서비스(web·api·worker) 안에서 한 곳에 두고, 모양만 비슷한 코드는 세 번째에 합치되 이슈 범위 밖 코드는 이슈로 남긴다. 수정 전에 현재 작업 폴더의 브랜치·HEAD·미커밋 변경을 확인한다. 읽기 실패는 파일·계약·규칙이 없다는 뜻이 아니다.

| 상황 | 다음 행동 |
|---|---|
| 현재 작업 폴더에 기존 변경이 있음 | 기존 변경을 덮어쓰거나 되돌리거나 자기 작업에 섞어 커밋하지 않는다. 겹치는 변경의 의도가 불명확할 때 확인하고, 필요하면 별도 작업 폴더를 사용한다. 다른 사람의 로컬 상태는 알 수 없으므로 병렬 작업은 관련 이슈·PR과 합의한 수정 범위로 조율한다. |
| 계약이 없거나 변경이 필요함 | 11월 Unit 작업은 [코딩 운영](#코딩-운영)의 계약 수정 규칙을 따른다. 그 밖에는 제안하는 담당자가 필요한 정보·변경 이유·영향과 막히는 범위를 정리하고 연결 상대가 검토한 뒤 선택안과 함께 팀장에게 올린다. 당사자 사이에 풀리지 않은 충돌도 같다. 합의가 필요한 실제 연결은 보류하되 허용된 독립 작업은 진행한다. 예를 들어 분석 상태의 의미·화면 초안은 준비할 수 있고, 모의 응답은 미합의임을 표시한다. |
| 루트 설정·공통 컴포넌트·계약·의존성·잠금 파일을 바꿔야 함 | 관련 작업에서 합의된 범위와 검토 상대를 확인한다. 기능 공통 부분은 영향을 받는 담당자, 공통 환경·CI·배포 설정은 해당 준비 작업 담당자와 조율한다. 필요한 변경과 관련 잠금 파일만 포함하고 설정 안내·환경 변수 예시도 함께 맞춘다. 특정 초기화 담당자나 팀원 1에게 모든 검토를 몰지 않는다. |
| 필요한 서비스 기반이 아직 준비되지 않음 | 해당 초기화 이슈·PR의 준비 상태와 README를 확인하고 미완료 항목을 초기화 담당자에게 연결한다. 기능 담당자가 각자 같은 서비스를 다시 초기화하지 않는다. |

초기화는 이슈의 범위와 선행 조건에 따라 진행한다. AI는 기존 파일과 필요한 설정을 확인하고, 실행에 영향을 주는 미결이나 충돌만 관련 담당자에게 확인한다.

PR 대상은 `dev`다. 11월 팀 방식의 Unit은 통합 브랜치 `intent/260925-intent-12`로 합친다([코딩 운영](#코딩-운영)). 서비스 폴더나 초기화 담당을 기준으로 상시 통합 브랜치를 나누지 않는다.

## 검사 선택과 결과 보고

AI는 바뀌는 사용자 행동과 영향을 확인해 필요한 검사를 골라 실행하고, 결과를 보고할 때 함께 설명한다. **테스트의 기대 결과는 이슈 완료 기준과 그 근거에서 가져오며, AI가 작성한 테스트도 그 기준과 대조한다.**

| 변경 | 검사 선택의 예 |
|---|---|
| 화면 문구·배치 | 해당 화면과 영향을 받는 사용자 조작 확인 |
| 공개·숨김·소유권·분석 상태 | 관련 정상·거부·실패 사례, 본인·수신자 조회 및 상태 전환 확인 |
| API·큐 계약 | 보내는 쪽과 받는 쪽의 해석, 오류·중복 처리 확인 |

- 적용 가능한 정적·타입 검사, 관련 단위·통합 테스트, 빌드 또는 런타임 실행 확인을 서비스 README와 실제 설정에서 고른다. 새 테스트는 그 서비스의 검사 명령이 찾는 위치·이름에 둔다(벗어나면 CI가 실패 표시 없이 건너뛴다). 새 명령은 실제로 확인한 뒤 서비스 README에 반영하고, PR마다 돌릴 검사면 [CI](../.github/workflows/ci.yml)에도 넣는다. 예시 명령·AI-DLC 도구 테스트를 제품 검사 결과로 보고하지 않는다.
- 기능별 동작·연결 안내는 서비스 README에 덧붙이지 않고, 그 README 맨 위에 적힌 기능 문서 위치에 쓴다. 같은 기능의 문서가 있으면 그 파일에 더하고, README에 이미 있는 기능 절은 그 기능을 고칠 때 기능 문서로 옮기고 README에는 제목과 링크만 남긴다. 코드를 고치기 전에 맡은 기능의 그 문서도 읽는다. 서비스 README·규약·기능 문서가 36 KB를 넘으면 절을 나눠 옮긴다(Codex는 도구 출력 한 번이 약 40 KB를 넘으면 가운데를 버린다).
- 변경 줄 수만으로 검사를 생략하지 않는다. 사소한 변경마다 테스트 파일을 추가하거나 매번 전체 테스트를 반복하지 않으며, 공통 변경·실패·남은 위험이 있으면 검사 범위를 넓힌다.
- 결과는 **통과 / 실패 / 실행하지 못함 / 해당 없음**을 구분한다. 실제 명령·작업 위치·검사한 판본(미커밋 변경 포함 여부)과 결과를 남기고, 관련 검사를 못 했으면 이유·남은 위험·다음 조치를 적는다. 실제 연결과 모의 대상을 구분한다. 예: “실제 API·DB 확인, worker 결과는 모의 처리”. 결과는 PR에 한 번 기록하되, 변경 없이 검증만 수행한 경우에는 관련 PR 댓글 또는 해당 이슈 댓글 한 곳에 기록한다. 이슈·검증표 등 다른 곳에서는 그 기록을 링크하며, PR 본문에 명령·세부 증거를 적을 때는 `추적 정보`를 사용한다.
- 실패하면 기대 결과와 실제 결과를 확인한다. 자기 변경의 결함은 수정 후 관련 검사를 다시 실행하고, 공통 환경·계정·계약 문제는 `막힌 이유 / 필요한 조치 / 요청 상대 / 다음 행동`으로 연결한다. 30분 이상 해결하지 못한 버그는 기존 도움 요청 규칙을 따른다. 실패 원인을 임의의 계약·기준 변경으로 없애지 않는다.

## 자료와 실행 로그

- 비밀값은 Git·환경 변수 예시·화면·로그에 남기지 않는다. 일반 개발·검사에는 합성·비식별 자료와 모의 외부 응답을 우선 사용한다. 실제 자료·외부 호출이 필요한 검사는 허용된 대상·범위·비용·자료 취급 조건 안에서 수행하고 일반 검사와 구분한다. 작업 요청이나 오류 해결 필요만으로 실험 원문·사용자 자료·모델 응답·대화 기록의 열람·복구·외부 전송까지 허용됐다고 추정하지 않는다.
- 실행 로그는 요청·분석 작업의 시작, 실제 완료·실패, 중요한 처리 단계를 구분할 수 있게 남긴다. 시각·수준·서비스·처리 단계와 합의된 요청/작업 식별자, 성공·실패 및 필요한 소요 시간·안전한 오류 정보를 사용한다. 식별자 형식·전달 방식은 연결 계약에서 정한다.
- 모든 함수의 인자·반환값을 통째로 기록하거나 예외를 삼키지 않고, 실패를 다른 오류나 코드로 바꿀 때 원인이 다른 실패를 한 코드로 묶지 않는다(계약이 정한 응답 코드는 그대로 따른다). 비동기 작업은 요청 접수만으로 완료 로그를 남기지 않는다. 오류 객체·URL에도 인증정보나 요청/응답 원문이 섞일 수 있으므로 필요한 항목만 기록한다. **AI·이슈·PR에 공유하는 로그에도 같은 자료 보호 기준을 적용한다.**
- worker의 데코레이터, NestJS의 로거 등 구현 방식은 서비스에서 선택한다. Next.js의 서버 로그와 브라우저 개발 로그를 구분하고 브라우저에는 민감정보를 출력하지 않는다. 새 로그 플랫폼 도입을 개발 준비의 조건으로 삼지 않는다.

## PR 작성·리뷰 요청·잘못 올린 PR 처리

- 작성자는 AI가 작성한 내용을 포함해 무엇이 달라졌고, 어떤 기준·증거로 확인했으며, 무엇이 남았는지 이해하고 설명한 뒤 PR을 올린다. PR을 올린 사람은 리뷰를 요청한 상대에게 직접 설명한다.
- 검토자는 변경된 행동과 핵심 예외를 결과물·검증 증거로 확인하고 코드의 관련 문제도 검토한다. 판단하기 어려운 계약·권한 쟁점은 관련 담당자에게 확인한다. 무엇을 확인하고 승인했는지 설명할 수 있어야 하며, AI의 자기 검토를 팀원의 PR 승인으로 세지 않는다. 모든 코드를 암기하거나 모든 PR에서 전체 테스트를 다시 실행할 필요는 없다.
- PR 본문에 논의·검토 상대를 적었다면 GitHub의 **Reviewers에도 실제 계정을 지정**한다. AI가 등록할 때는 지정 결과까지 확인하고, 계정이 불명확하거나 권한 때문에 실패하면 미지정 사실과 필요한 조치를 알린다.
- 잘못 올린 PR이 아직 열려 있으면 사유와 대체 PR(있다면)을 남기고 **닫아서 기록을 보존**한다. 이미 머지됐다면 사유를 댓글로 남기고 수정할 내용을 후속 PR로 이어 간다.

근거: 9/15 오후·9/16 오전 회의 결정, [#60](https://github.com/JminAILab/CatchU/issues/60). 결론을 PR 최상단에 쓰는 기존 원칙은 아래 양식을 따른다. PR 번호 확인을 별도 의무 규칙으로 추가하지 않는다.

## PR 본문

항목과 짧은 작성 안내는 PR 양식에 두고, 여기에는 판단·갱신 기준만 둔다. 목표는 상단만 읽어도 무엇이 바뀌었고 무엇을 검토해야 하는지 알 수 있는 본문이다.

- 선택 항목: `하지 않는 것`은 범위나 승인 여부를 오해할 수 있을 때만 한 문장으로 쓴다. `시도했다 접은 것`·`리뷰 반영`·`추적 정보`는 해당 내용이 있을 때만 쓴다. 승인·완료 구분 문장(머지가 승인·완료가 아니라는 문장)은 여기에만 쓴다. 해당 없는 선택 항목과 절은 지운다.
- 범위와 한계: 같은 설명은 한 절에만 쓴다. 검증 결과를 해석하는 데 필요한 한계는 그 결과 옆에 쓴다(예: 저장분 재현에 성공했지만 로직 타당성을 입증한 것은 아니다). 머지 판단에 영향을 주는 미검증 사항은 예외로 `리뷰 요청`에도 한 줄로 쓴다.
- 근거와 식별자: 필요한 근거는 본문에 뜻으로 쓴다. `추적 정보` 밖의 ID는 첫 등장에 풀어 쓰고 정의 위치가 있으면 링크한다(이슈·PR 번호 제외). 절 번호에는 절 제목을 함께 쓴다. 대응표·보조 ID·기준 커밋·검사 명령·파일 해시는 `추적 정보`로 내린다.
- 도구 내부 정보: AI 도구·AI-DLC의 명령·훅·오류 문구는 `추적 정보`에 두고, 본문에는 결과물에 준 영향과 사람이 할 조치만 쓴다. 단계명은 뜻으로 풀어 쓴다. 본문의 요청자·작성자는 GitHub 계정으로 쓴다.
- 결과물 링크: 커밋 고정 링크를 쓴다. 브랜치 링크는 브랜치를 지우면 깨지고, 커밋이 쌓이면 리뷰 당시 판본이 아닌 최신본을 가리킨다. merge commit 규칙이라 원래 커밋은 머지 후에도 남는다.
- 검증: `docs/`만 바꾼 PR은 대조한 결정·판본을 쓰고 제품 검사는 `해당 없음: 문서 변경` 한 줄로 묶는다. 적용되지만 수행하지 못한 검증은 이유와 함께 `수행하지 못한 검증`에 쓴다. 적용되지 않는 체크 항목은 "해당 없음: 사유"로 쓰거나, 선택 항목이면 지운다.
- 이슈 연결: 이 PR의 머지로 이슈의 완료 기준을 모두 충족할 때만 `Closes #번호`를 쓴다. 일부 결과물 제출이거나 완료 기준에 머지 후 별도 검증·작업이 남아 있으면 `Refs #번호`로 참조하고, 남은 기준을 확인한 뒤 종료한다. `Refs`는 참조 표현이며, 그것만으로 Project 연결이나 상태 변경이 일어나지 않는다. 자동 종료는 종료 키워드 등으로 연결된 PR이 기본 브랜치에 머지되고 저장소의 자동 종료 설정이 켜져 있을 때만 일어난다. 두 조건을 확인하고, 설정을 확인하지 못했다면 자동 종료를 가정하지 않고 그 사실을 보고에 적는다. 머지 후 실제 이슈·Project 상태를 검증한다.
- 리뷰 반영: 본문은 항상 최종 변경 상태를 설명하도록 고치고, 결과물 링크도 새 커밋으로 갱신한다. `리뷰 반영`에는 결론·범위·검증에 영향을 준 주요 리뷰만 "지적 → 반영 또는 미반영 이유"로 짧게 요약하고 원래 댓글·커밋을 연결한다. 사소한 수정은 기존 리뷰 기록으로 갈음한다. 주요 반영이 없으면 절을 생략한다.
- 올리기 전 점검: 결론이 한 문장인지, 리뷰 요청에 실제 검토 쟁점이 있으면 리뷰어별로 적었는지(쟁점이 없으면 확인할 결과만), 풀지 않은 ID·절 번호와 빈 절, `하지 않는 것` 밖의 승인·완료 구분 문장이 없는지 확인한다.
- 적용 시점: 새 PR부터 이 기준을 적용한다. 기존 열린 PR은 다음 수정 때 요약을 보완하며, 본문을 일괄 수정하지 않는다.
