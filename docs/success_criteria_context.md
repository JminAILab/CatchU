## 프로젝트 최소 컨텍스트

- CatchU(팀명 재민아이/JAEMIN_AI): GitHub 활동을 분석해 증거카드를 만들고 채용에 활용하는 양면 플랫폼
- 취준생 측: 채용공고 요구사항 × 내 카드 대조(커버리지 맵) / 기업 측: 자소서(주장)와 GitHub 기록(근거) 대조
- 제품 철학: "주장에 실제 근거가 붙는가". AI가 사람을 판정하는 기능에는 부정적 입장
- PoC 진행 중: 1일차에 실레포 사건 1건(A042)으로 카드 필드 8개의 채움 상태를 실측 (완전 1 / 수동 4 / 절반 1 / 구조적 빈칸 1 / 역설적 풍부 1)

## 전제 (문제 프레이밍)

1. 기존 시스템 개선 프로젝트가 아니므로 "기존 30초 → 10초" 식 비포/애프터가 존재하지 않는다. 비교 대상은 "이 서비스 없이 사람이 하던 일"이며, 비포는 실험으로 만들어야 한다.
2. 핵심 사용자 질문 "이 지원자가 우리 회사에서 어떤 일을 할 수 있을까"는 예측 판단이라 정답지가 원리적으로 불가능하다. 측정은 한 층 아래에서 한다: **"판단의 재료(지원자가 실제로 한 일 + 근거)를 얼마나 빠르고 정확하게 확보하게 해주는가"**.
3. LLM 채점(논리성 점수 등)은 배제한다. LLM 편향을 상속하고, "AI 판정에 부정적"이라는 팀 입장과 자기모순이기 때문. 대신 셀 수 있는 단위(근거 붙은 주장 개수 등)로 변환한다.
4. 목표 수치를 지금 정하지 않는다. 측정 항목·방법·입력을 먼저 고정하고, 목표치는 PoC 실측 축적 후 설정한다.
5. 운영 지표(클릭수·체류시간)는 비포가 없어 개선율 지표로 쓸 수 없다. 배포 후 참고치로만 취급한다.

## 후보 지표 4종 (측정 절차 포함)

### 지표 1 — 비교 실험: 판단 재료 확보 속도·양
- 설계: 정답지가 있는 레포(PoC 대상 레포 — 사건·근거가 이미 파악됨)로 팀이 정답지 작성("실제로 한 기술적 판단 N개 + 근거 커밋")
- 평가자를 A(레포 원본만)/B(카드 제공)로 분리. 같은 사람이 양쪽을 하면 안 됨(정답 학습). n=3씩 소규모 허용
- 과제: 핵심 질문에 서술로 답하되 **주장마다 근거(커밋/카드)를 붙이도록 강제**
- 측정: ① 근거 붙은 주장 개수 ② 근거가 실제로 주장을 지지하는지(팀 사후 대조) ③ 소요 시간 ④ 오독(틀린 주장) 개수
- 유일하게 외부 평가자가 필요한 지표. 1회성 실험
- 상태: "질문을 비교한다"는 초기안은 채점 기준 부재로 폐기, "정답지 기반 과제"로 대체됨

### 지표 2 — 카드 필드 자동 채움률
- 정의: 카드 필드 8개 중 기계가 채운 필드 수. PoC 1일차 실측(기계 채움: 시계열 골격 + author 귀속뿐)이 baseline
- 측정: 파이프라인 버전 갱신 시 **같은 레포·같은 사건**에 재실행하여 기계 채움 필드 수 비교. 외부 인력 불필요
- 파생 지표(후순위): 소유자가 만족 수준까지 수정한 양(수정 필드/문장 수) — 서비스 형태 이후
- 지인 레포 섭외의 목적은 비포/애프터가 아니라 **유형 다양성**(정상 / 부실 커밋 / GitLab 미러) 확보
- ⚠️ 미검증: baseline인 "수동 4"가 본인 작업 기록인지 정리 AI의 재구성인지 이재민 본인이 확인 예정. 검증 전까지 baseline으로 확정하지 말 것

### 지표 3 — 근거 링크 일치율
- 정의: 카드의 검증 가능한 주장 문장(카드당 4~6개 예상) 각각에 대해, 링크된 커밋/diff가 실제로 지지하는지 3등급 판정(일치/부분 일치/불일치)
- 집계: 카드별 평균이 아니라 **전체 주장 문장 합산 비율**(짧은 카드에 의한 왜곡 방지)
- 채점자: 해당 레포 소유자가 아닌 팀원 + 애매한 건 소유자 확인 (PoC 1일차 "당사자 진술 층위" 판정 방식의 확장)
- 버전 간 비교 조건: 측정용 레포 세트(입력) 고정, 표본 규칙(레포당 무작위 N장) 고정
- 좋아요/싫어요 방식은 만족도이지 정확도가 아니므로 배제

### 지표 4 — 커버리지 맵 정확도
- 정의: 실제 채용공고 1건의 요구사항 항목(10개 내외) × 카드 매핑에서 [맞은 연결 / 과잉 연결 / 누락] 집계
- 정답지: 사람이 먼저 수동 매핑. 단 **고정본이 아니라 갱신본** — 시스템이 제안한 연결이 검토 후 타당하면 "시스템 선발견" 출처 표기와 함께 정답지에 추가. 정답지에 버전을 매겨 측정 기준을 남김
- 파생 지표: "사람이 놓친 타당한 연결을 시스템이 발견한 횟수" — 이 기능의 존재 이유에 해당
- 주의: 커버리지 % 자체는 성공 지표가 아님(빈칸이 많은 사용자에게 빈칸을 정확히 보여주는 것이 성공). 위험 우선순위는 과잉 연결(근거 아닌 것을 근거라 붙이면 제품 철학 붕괴)
- 열린 논점: 맞은 연결/과잉/누락 중 무엇을 우선 지표로 삼을지는 팀 논의 필요

## 공통 설계 원칙

- 정답지를 사람이 만들 수 있는 범위(자기 레포, 공고 1건)로 좁혀 그 안에서 시스템을 채점한다
- 판단 자체가 아니라 판단의 재료를 잰다
- 정답지·입력·집계 방식을 고정해야 버전 간 비교가 성립한다
- 모든 지표는 팀 인력으로 측정 가능하게 설계 (예외: 지표 1의 외부 평가자 1회)
