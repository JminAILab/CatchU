# AI-DLC 2.9.0 업데이트 사전 검토

2026-09-16. [#37](https://github.com/JminAILab/CatchU/issues/37) / [PR #58](https://github.com/JminAILab/CatchU/pull/58). **읽기 전용 검토 결과이며 설치 허용·설치 완료 기록이 아니다.**

## 결론

**현재 intent는 2.8.1을 유지하고, 2.9.0 전환은 보류하는 것을 권고한다.** 공식 배포는 확인했지만 다음 두 제약 때문에 지금 프로젝트까지 일관되게 갱신할 수 있다고 판단하지 않는다.

1. 전체 workflow가 완료되기 전 프로젝트 refresh는 공식적으로 차단된다. feasibility 한 단계의 승인이나 단계 사이 대기는 전체 workflow 완료가 아니다. 현재 설치의 `config --dry-run --json`도 활성 `default/260914-catchu-october-mvp`를 이유로 거부했다.
2. v2.9.0 태그의 `core/tools/aidlc.ts`에는 review-brief 명령 등록은 있지만 네이티브 `loadDelegate`의 해당 분기는 없다. 2.8.1에서 겪은 것과 같은 구조적 누락이다. **정적 소스 검토 결과**이며 2.9.0 배포 바이너리에서 실행 재현한 것은 아니다. 현재 2.8.1 전용 보완을 그대로 적용할 수 없다.

버전 갱신을 위해 intent를 완료·보관 처리하거나 승인·상태·무결성 기준을 직접 수정하지 않는다. 기계 버전만 바꾼 혼합 상태도 현재 프로젝트의 성공적인 업그레이드로 보고하지 않는다. 설치 여부는 사용자가 이 결과를 검토한 뒤 결정한다.

## 사용자 결정 — 2.8.1 유지, Scope Definition 진행

2026-09-16 후속 답변으로 사용자는 **2.9.0 설치 보류와 현재 검증된 2.8.1의 Scope Definition 진행**을 선택했다. 위 사전 검토 당시의 권고·미실행 기록은 보존한다. 버전 업데이트는 진행 중 workflow에 적용할 공식 지원 경로가 확인되거나 이번 workflow 종료 시 다시 검토한다. 다음 단계마다 업데이트를 자동 시도하는 상시 규칙이 아니다.

승인된 feasibility 조건·구현 착수 제한과 C01·C02의 기존 완료 기한을 유지한다. Scope Definition 범위 확정 전에 재검증 일정·담당·수용 기준 및 C10 실제 가용량·공통 책임을 구체화한다. 이 선택은 Scope Definition의 작성 전 확인·공식 승인이나 추가 API 호출 허용이 아니다. 설치·refresh·하네스 변경은 실행하지 않았다. [현재 질문 기록](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/scope-definition/scope-definition-questions.md), #37 / PR #58에 연결한다.

## 로컬 보완의 취급

### review-brief

- 현재 `/Users/ljm/.local/bin/aidlc`에는 활성 버전이 **2.8.1**이고 첫 두 인수가 `engine review-brief`인 경우에만 Bun 보조 진입점을 쓰는 네 줄 분기가 있다.
- `scripts/aidlc-review-brief-entry.ts`와 설치 사본은 2.8.1 실행 경로·무결성을 검사한 뒤 해당 버전 원본 CLI를 호출한다. 2.9.0을 지원하지 않는다. 버전 문자열만 바꾸는 이식은 하지 않는다.
- 2.9.0 소스의 `TOOLS.reviewBrief` 정의(L137)와 명령 등록(L1005)은 있지만 `loadDelegate`(L2005~2072)에 분기가 없고, null이면 L2082~2084에서 기존과 같은 오류 경로로 간다. 이를 **해소됐다고 확인하지 못한 네이티브 실행 위험**으로 남긴다.
- 기계 update/use 과정에서 launcher가 다시 생성될 수 있으므로 보완 분기 보존을 가정하지 않는다. 2.9.0 native/copy 분리도 있으므로 2.8.1 소스 호출 보완이 새 배포 구조에서 그대로 성립한다고 보장하지 않는다.
- 전환을 다시 검토할 때는 공식 수정 여부 및 검증된 배포본을 우선 확인한다. 별도 로컬 변경이 필요하면 원인·최소 변경안·무결성/승인 경계·원복을 제시하고 사용자의 별도 허용을 받는다. 지금 추가 패치는 없다.

### runtime graph

2.9.0 태그 문서에도 `aidlc engine runtime compile`이 명시돼 있다. 이는 이번 **새 버전 문서를 조회해서 확인한 사실**이며, 2.8.1 회고를 상시 규칙으로 승격한 것이 아니다. 실제 2.9.0 설치에서 현재 worktree/intent/세션 경로에 생성되는지는 실행 검증하지 않았다. `graph compile`과 runtime 재생성을 혼동하지 않는다.

## 백업·복구 계획 — 미실행

현재 설치 상태를 바꾸지 않았으므로 이번 검토 자체의 원복 작업은 없다. 향후 설치를 허용받더라도 다음 준비·검증을 먼저 수행한다.

1. **변경 전 보존:** 승인 후 Git 리비전과 깨끗한 작업 상태, `aidlc/` 기록·활성 커서/세션 연결, `.codex/`·`.agents/`·프로젝트 스탬프/소유권 기준·설정을 식별한다. 기계 2.8.1 원본 바이너리/런타임·manifest/무결성 자료, 현재 보완 launcher·보조 파일·Bun 경로를 별도 보존한다. 비밀값은 Git/문서에 넣지 않는다. 이 계획은 전체 백업을 이미 만들었다는 뜻이 아니다.
2. **공식 설치 경로:** 허용 시 exact `--version 2.9.0`을 사용하고 공급자 checksum·크기·가능한 provenance 검증을 유지한다. latest에 맡기거나 해시 기준을 수정하지 않는다. current workflow의 refresh 제한을 우회하지 않는다.
3. **기계 원복:** 공식 안내는 이전 활성 버전 보존과 실패 시 설치 원복을 설명한다. 공개 명령은 `aidlc use 2.8.1`이며 별도 public rollback 명령은 없다. 2.8.1이 실제 온전하게 보존됐는지 먼저 확인한다. 없는 버전은 use가 설치를 시도할 수 있으므로 offline 원복을 가정하지 않는다.
4. **보완 원복:** 기계 버전 복귀와 launcher 보완 복귀는 별개다. 현재 정상 작동하는 보완 launcher를 보존해야 한다. 기존 `aidlc.before-review-brief-entry-20260916`은 **보완 전 원본**이므로 그것만 복원하면 2.8.1 등록 누락이 다시 드러난다. 허용된 원복 후 13개 읽기 전용 검사와 doctor를 다시 수행한다.
5. **프로젝트 원복:** update/use는 프로젝트 파일을 원복하지 않는다. 향후 공식적으로 허용되는 refresh를 실제 수행했다면 그 변경 범위와 별도 백업으로 복구해야 한다. 새 승인·감사 이벤트를 과거 snapshot으로 덮지 않는다. 혼합 상태·원복 불완전 격리 경로는 doctor 결과와 정확한 대상부터 확인하며 임의 삭제하지 않는다.
6. **수용 검사:** version/stamp·manifest 무결성, 활성 intent/세션/기록·계획 불변, summary/context/review 및 잘못된 입력 거부, runtime 생성 위치·회고 조회, 재실행/원복 검사를 통과해야 한다. 테스트를 위해 실제 workflow 승인·완료를 위조하지 않는다.

## 수행하지 않은 것과 다음 선택

- 2.9.0 바이너리·archive를 다운로드/설치/실행하지 않았다. 소스·공식 문서·릴리스 메타데이터만 읽었다. 정적 검토를 새 배포본 회귀 시험 통과로 표현하지 않는다.
- update/use/pin/refresh, 새 하네스 수정·Bun 설치·Scope Definition 질문/산출물 작성은 하지 않았다. 2.8.1 유지가 현재 검토 권고이지 사용자의 최종 설치 선택을 대신한 것은 아니다.
- **권고 선택:** 2.9.0 설치를 보류하고 2.8.1로 현재 intent를 계속한다. 공식 프로젝트 전환이 가능한 시점과 review-brief 위험 해소 근거가 생기면 다시 검토한다.
- **대안:** Scope Definition 착수를 더 보류하고, 현재 프로젝트와 분리된 2.9.0 배포본 검증의 범위·다운로드/실행 허용을 별도로 논의한다. 이 대안도 현재 intent refresh 보호를 자동 해제하지 않는다.

## feasibility 승인 경계와 Scope Definition 인계

사용자의 이번 `Approve`는 공식 `orchestrate report --stage feasibility --result approved --user-input Approve`로 기록됐다. 같은 명령이 다음 단계 포인터를 자동 이동했으나 **Scope Definition의 질문·산출물 작성은 아직 시작하지 않았다.** 이 문서는 승인 이벤트를 대신 만드는 기록이 아니라 사용자 지시를 후속 작업에 연결하는 운영 메모다.

- 승인은 관찰된 가능성과 잔여 위험을 바탕으로 후속 범위·요구사항 검토를 계속하는 판단이다. 생성 사실성·운영 안전성 확보 또는 10월 달성 승인이 아니다.
- **Scope Definition 범위 확정 전**, [제약 등록부](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/feasibility/constraint-register.md)의 C01·C02 재검증 일정과 C10 실제 가용량·공통 작업 책임을 구체화해 사용자에게 제시한다. 기존 ljm0850 검증 담당·단계 기한은 유지하며 새 날짜·시간 배정·미배정 실행 책임을 임의 확정하지 않는다.
- 기존 검증 통과 조건과 관련 구현 착수 제한을 유지한다. 기준 미달 또는 일정 수용 불가가 드러나면 실행 가능성을 재검토한다. 현재 2~4시간 추정은 추가 호출·시간 배정 승인이 아니다.
- 설치 여부는 이 사전 검토 결과를 보고 사용자가 정한다. 그 전 다음 단계 본문에 착수하지 않는다. #37 및 PR #58에서 승인·잔여 조건·업데이트 판단을 연결하고 PR 병합을 자동 실행하지 않는다.
