# P4 설계 노트 — 운영자 페르소나에서 도출한 것들

**버전:** v2.0 · 2026년 9월 1일
**원본 문서:** `대표 페르소나 P4 — 서비스 운영자(관리자) v2.0`
**용도:** 관리자 페이지 기능명세·화면 설계의 입력값

---

## 1. 형식에 대한 메모

관리자는 우리 팀 자신이라 "설득해야 하는 사용자"가 아니다. 원래는 **권한 정의 + 운영 시나리오** 형식이 더 맞지만, P1~P3와 형식을 통일하기로 결정해 페르소나로 작성했다.

**형식을 맞추면서 잃지 않도록**, 운영 정의서에 들어갔어야 할 내용(권한 모델·처리 흐름·화면 요구사항)은 이 노트에 담았다. 페르소나 본문과 이 노트를 합치면 운영 정의서 한 벌이 된다.

**페르소나 형식의 한계 두 가지**

- P4에는 **이탈이 없다.** 운영자는 서비스를 그만 쓸 수 없다
- P4의 **성공 지표가 반대다.** P1~P3은 많이 쓰게 하는 것이 목표지만, P4는 등장 횟수를 줄이는 것이 목표다

## 2. v1.0 → v2.0 개정 — 개발자와 운영자를 분리한다

팀 논의의 핵심 지적은 **"현재 개발자와 운영자의 입장이 섞여 있다"**였다. 이 기준으로 전면 개편했다.

### 무엇이 섞여 있었나

v1.0의 고통 5개를 두 축으로 나누면 이렇게 갈린다.

| v1.0 고통 | 실제 성격 | 처리 |
| --- | --- | --- |
| ③ 시간 | **운영자** | **핵심 고통으로 승격** |
| ② 맥락이 부족하다 | 운영자 — 다만 독립 고통이 아니라 **시간을 잡아먹는 원인** | 시간 고통의 ①로 종속 |
| ① 판단 기준이 없다 | 상동 | 시간 고통의 ②로 종속 |
| ④ 양방향 리스크 (과잉 제재 vs 방치) | 미검증 추론 | **페르소나에서 제거** → 5장 |
| ⑤ 법적·보안 불안 (개인정보·인젝션·로그) | **개발자** | **페르소나에서 제거** → 3장 |

### 핵심 고통을 하나로 단일화했다

팀 결정: **"핵심 고통은 무조건 시간 쪽으로 가야 한다."**

v2.0은 고통을 **"운영에 쓸 시간이 없다"** 하나로 세우고, 그 아래 시간을 잡아먹는 세 가지를 배치했다.

```
운영에 쓸 시간이 없다
  ├ ① 맥락을 찾으러 화면을 오간다
  ├ ② 지난번에 어떻게 했는지 찾을 수 없다
  └ ③ 애매하면 미루고, 미루면 다시 읽는다
```

> **"맥락 부족"과 "판단 기준 없음"을 버린 것이 아니다.** 독립된 고통으로 세울 근거가 약했을 뿐이고, 시간의 원인으로 놓으니 오히려 설계 요구가 선명해진다 — *한 화면에 모아라, 이력을 남겨라.*

### 그 밖의 변경

| 구분 | 내용 |
| --- | --- |
| **삭제** | 시스템 모니터링·인젝션 탐지 시나리오 (자동 처리 영역) / 목표에서 "억울한 제재를 만들지 않고 싶다"·"법적 문제를 만들고 싶지 않다" / 필요한 것에서 대시보드 수치·보안 로그 |
| **변경** | 한 줄 명제를 시간 중심으로 / POV·HMW 전면 재작성 / 시나리오 4개 → 3개 |
| **유지** | 서비스에서의 위치(예외 처리자), 자동 처리 원칙, 권한 모델, 제재 단계, 원칙 1과의 관계 |

## 3. 개발자 관심사로 이관한 것

아래는 **실재하는 요구이지만 운영 페르소나의 고통이 아니다.** 개발·보안 요구사항으로 별도 관리한다.

| 항목 | 왜 운영자 고통이 아닌가 | 어디서 다루나 |
| --- | --- | --- |
| **개인정보 처리의 법적 근거** | 운영 화면의 문제가 아니라 **서비스 설계 단계의 법적 요건** | 확정 정의서 미결 / 8/27 강사 지적 사항 |
| **프롬프트 인젝션 탐지** | **자동 처리 영역** *[팀 결정]*. 사람이 여는 화면을 만들지 않는다 | 개발·보안 요구사항 |
| **로그 보관 기준·범위** | 시스템 설계 결정 | 개발 요구사항 |
| **시스템 헬스체크·에러 알림** | 개발자가 받는 알림이지 운영 판단이 아니다 | 개발 요구사항 |

> **확정 정의서 7.6의 "시스템 모니터링" 항목은 기능으로는 유지한다.** 다만 **운영자 페르소나의 여정에서는 제외**한다. 기능이 존재하는 것과 이 사람이 그 기능을 쓰는 것은 다른 문제다.

### "이상탐지는 자동으로 간다"의 범위

| 대상 | 자동 | 사람 |
| --- | --- | --- |
| DM·포스팅 필터 | 자동 차단 | 필터를 통과했는데 신고된 건만 |
| 프롬프트 인젝션 | **전부 자동** | **없음** |
| 시스템 이상·에러 | **전부 자동** (개발자 알림) | 운영 판단 아님 |
| 기업 인증 | 자동 승인 | **AI 이상 감지 건만** |

## 4. 원칙 1과 관리자 AI 판정 — 정리 필요

### 표면적 모순

확정 정의서 원칙 1은 **"평가하지 않는다"**이다. 그런데 관리자 영역에서는 AI가 사람에 대해 판정을 내린다(기업 인증 이상, DM 필터, 문의 분류, 인젝션 탐지).

발표에서 **"평가 안 한다면서 왜 AI가 계정을 거르냐"**는 질문이 나올 수 있다.

### 구분선 제안

| 구분 | 내용 | 우리 입장 |
| --- | --- | --- |
| **채용 판단** | 이 사람이 이 자리에 적합한가 | **하지 않는다** — 원칙 1 |
| **안전 판단** | 이 행위가 서비스 규칙을 위반했는가 | **한다** — 다만 AI는 1차 선별까지, 제재 결정은 사람 |

핵심은 **"AI가 최종 결정을 내리지 않는다"**는 점에서 두 영역이 일치한다는 것이다. 채용에서는 기업이, 운영에서는 운영자가 결정한다.

→ 이 문장을 확정 정의서 원칙 1에 한 줄로 추가할 것을 제안한다.

## 5. 미검증 가설 — 페르소나에서 뺐지만 버리지 않은 것

v1.0의 **"양방향 리스크"**(과잉 제재 vs 방치)는 팀 논의에서 확신이 서지 않는다고 판단되어 페르소나에서 제거했다. 다만 **제재 단계 설계의 근거**로는 여전히 유효하므로 여기 남긴다.

> 잘못 정지시키면 그 사용자의 구직이 막히고, 방치하면 피해자가 계속 생긴다. 어느 쪽으로 틀려도 손해라서 **결정을 미루게 된다.**

**검증 방법:** 실제 운영을 시작한 뒤 미처리 대기 건의 체류 시간을 보면 안다. 미루는 패턴이 실재하면 이 가설이 맞는 것이다.

## 6. 제재 단계 설계

현재 확정 정의서에는 **정지 · 해제 · 이용 제한 · 강제 탈퇴**만 있다. 고통 ③(애매하면 미룬다)을 풀려면 앞에 가벼운 단계가 필요하다.

| 단계 | 조치 | 회복 |
| --- | --- | --- |
| 1 | **경고** — 알림만 발송, 기능 제한 없음 | 자동 |
| 2 | **이용 제한** — DM 발송·포스팅 차단, 열람은 가능 | 기간 만료 또는 해제 |
| 3 | **계정 정지** — 로그인 차단, 프로필 비노출 | 운영자 해제 |
| 4 | **강제 탈퇴** — 계정·데이터 삭제 | 불가 |

> **1단계가 있으면 "아무것도 안 함"을 피할 수 있다.** 결정을 미루게 만드는 구조를 없애는 것이 이 설계의 목적이며, 그것이 곧 처리 시간을 줄인다.

## 7. 권한 모델 (초안 — 미확정)

| 권한 | 내용 | 대상 |
| --- | --- | --- |
| **조회** | 회원 목록, 신고 내역, 인증 대기열, 처리 이력 | 운영자 전원 |
| **제재** | 경고 · 이용 제한 · 계정 정지 · 정지 해제 | 운영자 |
| **강제 탈퇴** | 계정 및 데이터 삭제 | **2인 승인 권장** — 되돌릴 수 없음 |
| **기업 인증** | 승인 · 반려 · 추가 서류 요청 | 운영자 |
| **고객센터** | 에스컬레이션 문의 응답 | 운영자 |
| **시스템** | 로그 조회, 알림 임계치 설정 | **개발 담당** (운영 권한과 분리) |

### 확인해야 할 것

- 운영자 계정을 일반 기업/개인 계정과 어떻게 분리할 것인가
- 관리자 행위 자체의 로그를 남길 것인가 (누가 누구를 정지시켰는지)
- 강제 탈퇴 시 데이터 삭제 범위 — 카드·DM·포스팅·신고 이력

## 8. 페르소나가 만드는 설계 제약

**v2.0에서 시간 중심으로 재정렬했다.**

| # | 제약 | 근거 |
| --- | --- | --- |
| 1 | **사람이 봐야 하는 건의 수를 최소화** | HMW-1. 자동화가 어필 포인트라는 결정과 직결 |
| 2 | **한 건의 처리가 한 화면에서 완결** | 고통 ①. **화면 이동이 곧 처리 시간이다** |
| 3 | **신고 처리 화면에 맥락이 함께 표시** | 전후 메시지, 양측 이력. 찾으러 가지 않게 |
| 4 | **유사 건의 과거 처리 이력을 같은 화면에 표시** | 고통 ②. 기록을 남기는 것만으로는 부족하고, **판단하는 자리에 보여야** 시간이 준다 |
| 5 | **모든 제재에 사유 기록 필수** | 제약 4의 입력값 |
| 6 | **가벼운 조치 단계를 제공** | 고통 ③. 미루지 않게 하는 것이 시간 절약 |
| 7 | **AI 판정에는 근거를 함께 표시** | 근거가 없으면 사람이 재판단할 수 없어 시간이 늘어난다 |
| 8 | **되돌릴 수 없는 조치는 확인 단계를 둔다** | 강제 탈퇴 등 |

### 제약 4가 v2.0에서 강화된 지점

v1.0은 *"처리 이력을 조회할 수 있어야 한다"*였다. v2.0은 **"판단하는 화면에 함께 표시되어야 한다"**로 올렸다. 조회 기능이 따로 있으면 결국 찾으러 가는 시간이 들고, 그러면 안 찾는다.

### 제약 7은 다른 페르소나와 같은 규칙이다

P3(HM)이 요구한 "모든 항목에 한 뎁스 내 근거 링크"와 같은 형태다. **AI가 무언가를 판정하면 그 근거를 함께 보여준다** — 서비스 전체를 관통하는 규칙이다.

## 10. 네 페르소나 종합

| 기능 | P1 취준생 | P2 HR | P3 HM | P4 운영자 |
| --- | --- | --- | --- | --- |
| **팀 프로젝트에서 누가 무엇을 했는지 구분** | ✔ | ◐ | ✔ | — |
| GitHub 증거 카드 | ✔ 만든다 | ◐ 요약을 본다 | ✔ 원본을 본다 | — |
| **AI 판정에 근거 표시** | ◐ | ◐ | ✔ | ✔ |
| **한 화면에서 완결** | ✔ | ◐ | ✔ | ✔ |
| 조건 검색 · 추천 | — | ✔ 핵심 | ◐ 심화 검색 | — |
| DM | ◐ 받는다 | ✔ 보낸다 | — | ✔ 신고를 처리 |
| 후보 요청 항목 | ✔ 설정한다 | ✔ 채운다 | — | — |
| 기업 인증 | ◐ 신뢰 판단 | ✔ 신청한다 | — | ✔ 심사한다 |
| 점수 · 순위 | ✗ 거부 | 원함 | ✗ 거부 | — |

### 세 가지 관찰

1. **가장 넓게 걸리는 기능은 GitHub 증거 카드**(P1·P2·P3)이며, 그 안의 **"누가 무엇을 했는지 구분"**이 최우선이다.
2. **"AI 판정에는 근거를 붙인다"와 "한 화면에서 완결"이 P3·P4에서 동일하게 나왔다.** 서비스 전체 규칙으로 승격할 만하다.
3. **P4는 다른 셋과 방향이 반대다.** 관리자 페이지의 성공 지표는 사용량이 아니라 **처리 대기 건수와 건당 처리 시간이 낮은 것**이다. (KPI v3.0 9장의 운영 KPI 2개와 일치)
