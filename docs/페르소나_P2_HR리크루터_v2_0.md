# 대표 페르소나 P2 — HR·리크루터

> **"개발자를 뽑아야 하는데, 어디서 무엇을 판단해야 할지 모르겠다."**

**버전:** v2.0 · 2026년 9월 1일 · 팀 논의 반영
**함께 보는 문서:** `P2 설계 노트` — 검증 상태·서비스 범위·설계 제약
**관련 페르소나:** `P1 취준생·신입 개발자` (찾는 대상) / `P3 기술 면접관(HM)` (판단을 넘길 상대) / `P4 서비스 운영자`

---

## 대상 정의

| | |
| --- | --- |
| **초기 사용자** | 30~150명 규모 IT 기업의 인사담당자 — HR이 1~2인이고 개발 직군 채용을 겸하는 조직 |
| **채용 대상** | 개발자 전반. **소싱·헤드헌팅은 주로 경력 개발자에게 일어난다** |
| **확장 대상** | 채용 대행사·서치펌의 주니어 리크루터, 스타트업 대표·운영 담당 |
| **분리** | 기술 면접관(HM) — 행동과 고통이 달라 **P3로 분리** |

**왜 이 규모인가:** 대기업 공채는 지원자가 몰려 소싱이 필요 없고, HR 조직이 크면 소싱 전담자가 따로 있다. **HR이 혼자 다 해야 하는 구간**이 이 페르소나가 사는 자리다.

> **"신입"이라는 한정을 뺐다.** 헤드헌팅은 신입 개발자에게는 거의 일어나지 않는다. P2가 찾는 대상은 경력 개발자가 주가 된다. **P1(취준생·신입)과 시점이 어긋나는 문제는 `P2 설계 노트` 2장에서 다룬다.**

## 프로필 — 박서연 (가명, 31세)

- IT 기업 인사팀. **HR 담당자는 본인 포함 2명** *[추론]*
- HR 경력 6년, 개발 직군 채용은 3년째 *[추론]*
- 채용·온보딩·평가·노무를 함께 담당한다. **채용은 특정 시즌에 일이 몰린다** *[추론]*
- **업무가 많아 채용 한 건에 많은 시간을 쓰기 어렵다.** 기술 스택을 따로 공부할 시간은 특히 부족하다 *[추론]*
- **개발자 출신이 아니다.** 기술 용어는 일하면서 익혔다 *[인터뷰]*
- 링크드인·채용 플랫폼을 열어 **수작업으로 후보를 검색하고 개별 연락한다** *[인터뷰]*
- 이력서를 **10분 안에** 판단한다 *[조사]*

## 서비스에서 이 사람의 위치

박서연은 **찾는 사람**이다. 서비스 안에서 가장 능동적으로 움직이는 사용자이며, 검색·추천·DM의 실제 주체다.

| 단계 | 하는 일 |
| --- | --- |
| **① JD 확보** | TO를 받아 채용 공고를 등록한다. 기술 요건은 HM이 작성한 것을 받는다 |
| **② 탐색** | 조건 필터와 추천으로 후보를 훑는다. 이 서비스에서 가장 오래 머무는 화면 |
| **③ 접촉** | DM을 보낸다. 응답을 기다린다 |
| **④ 전달** | 괜찮아 보이는 사람을 HM에게 넘긴다 → **P3 시나리오 ①로 이어진다** |

## 목표

**표면적인 목표**

- 정해진 기간 안에 개발자 TO를 채우는 것

**실질적인 목표**

1. **후보를 찾아내고 싶다** — 지원을 기다리는 것 말고 다른 경로가 필요하다
2. 개발자가 아니어도 **이 사람이 볼 만한지 대략은 가늠하고 싶다**
3. HM에게 넘길 때 **"왜 이 사람인지" 한 줄이라도 붙이고 싶다**
4. 보낸 연락에 **답이 왔으면 좋겠다**
5. HM의 시간을 **덜 쓰고 싶다** — 물어볼 때마다 미안하다

## 핵심 고통

### ① 후보를 찾는 것 자체가 가장 어렵다 *[인터뷰]*

- 링크드인 등에서 **수작업으로 검색하고 한 명씩 연락**한다
- 개발 직군에서 쓸 수 있는 소싱 채널이 마땅치 않다 *[추론]*
- 지원자가 오기를 기다리는 것 외에 다른 경로가 없다

### ② 기술을 몰라서 판단이 막힌다 *[인터뷰]*

- **HM이 작성한 JD를 받지만, 그 내용을 온전히 이해하지 못한다** *[추론]*
- 이력서에 적힌 기술 스택이 **실제 실력인지 나열인지** 알 수 없다
- GitHub 링크가 있어도 열어보면 무엇을 봐야 할지 모른다 *[추론]*
- 그 결과 **자바 개발자에게 파이썬 포지션을 보내는** 실수가 생긴다 *[조사]*

### ③ 보낸 연락에 답이 없다 *[조사]*

- 연봉·근무형태 같은 정보가 빠진 제안은 대체로 무시된다
- **그런데 무엇이 빠졌는지는 답이 오지 않는 이상 알 수 없다**
- 이 후보가 무엇을 알고 싶어 하는지 모르는 채로 보낸다

### ④ HM이라는 병목 *[추론]*

- 최종 기술 판단은 HM이 해야 하는데, HM은 개발이 본업이라 바쁘다
- 애매한 후보를 자주 넘기면 신뢰를 잃는다
- **거를 수는 있어야 하는데 거를 근거가 없다**

### ⑤ 시간 *[조사]*

- HR 담당자의 57.8%가 이력서를 10분 이내에 검토한다
- 채용 외 업무가 동시에 돌아가고, 채용은 시즌에 몰린다

## POV — 관점 진술

### 메인 POV

> **인사담당자 박서연은 개발자가 아니어도 후보의 실제 개발 경험을 알아보고, 지원을 기다리지 않고 먼저 찾아낼 수 있는 방법이 필요하다.**
> **왜냐하면 채용 외 업무를 병행하느라 기술 스택을 익힐 시간이 부족하고, 이력서에 적힌 기술 스택만으로는 그것이 실제 실력인지 판단할 수 없기 때문이다.**

### 보조 POV

| # | POV |
| --- | --- |
| **POV-A**<br>(판독) | 박서연은 **비개발자도 읽을 수 있는 형태의 개발 경험 요약**이 필요하다. 왜냐하면 기술 스택 나열만으로는 실제 실력을 가늠할 수 없고, 매번 HM에게 묻기에는 HM의 시간이 부족하기 때문이다. |
| **POV-B**<br>(전달) | 박서연은 **HM에게 근거를 붙여 후보를 넘길 방법**이 필요하다. 왜냐하면 애매한 후보를 반복해서 올리면 신뢰를 잃고, 결국 자신의 판단 범위가 좁아지기 때문이다. |
| **POV-C**<br>(접촉) | 박서연은 **이 후보가 제안에서 무엇을 알고 싶어 하는지 미리 알 방법**이 필요하다. 왜냐하면 정보가 빠진 제안은 대체로 무시되는데, 무엇이 빠졌는지는 답이 오지 않는 이상 알 수 없기 때문이다. |

## HMW — 우리가 어떻게 하면

### 메인 HMW

> **우리가 어떻게 하면, 개발자가 아닌 인사담당자가 개발자 후보를 스스로 찾아내고, 그 사람의 실제 개발 경험을 읽어내고, 근거와 함께 기술 면접관에게 넘길 수 있게 할 수 있을까?**

### 하위 HMW

| # | 대응 | 질문 |
| --- | --- | --- |
| HMW-1 | ① | 우리가 어떻게 하면, 조건을 정확히 모르는 사람도 **쓸 만한 후보 목록**에 도달하게 할 수 있을까? |
| HMW-2 | A | 우리가 어떻게 하면, **기술 용어를 모르는 사람에게** 개발 경험을 읽히게 할 수 있을까? |
| HMW-3 | A | 우리가 어떻게 하면, **판단을 대신하지 않으면서** 비개발자의 판단을 도울 수 있을까? |
| HMW-4 | B | 우리가 어떻게 하면, 후보를 넘길 때 **근거가 함께 따라가게** 할 수 있을까? |
| HMW-5 | C | 우리가 어떻게 하면, **후보가 원하는 정보를 담아** 연락을 보내게 할 수 있을까? |

> HMW-3은 P3의 HMW-3과 같은 질문이다. **다만 방향이 반대다** — HM은 판단을 대신할까 봐 경계하고, HR은 판단을 대신해주길 바란다. (`P2 설계 노트` 3장)

## 서비스 접점 시나리오

### ① JD 등록 국면 — 공고를 쓴다

개발팀에서 백엔드 1명 TO를 받음 → **HM이 작성한 기술 요건을 받아** JD 등록 → 회사 프로필(회사명·위치·소개·홈페이지) 정비 → 기업 인증 마크 신청

### ② 탐색 국면 — 후보를 찾는다 *(가장 오래 머무는 화면)*

조건 필터로 검색(기술스택·경력·지역·근무조건) → 결과가 적으면 **추천 목록**으로 넘어감 → 각 후보의 **경험 요약**을 훑음 → **"이 사람은 리액트로 뭔가를 꾸준히 만들었구나"**가 개발 용어 없이 읽힘 → 지금 뽑을 사람은 아니지만 괜찮은 사람은 **북마크 + 메모**

### ③ 접촉 국면 — 연락한다

후보를 고름 → **이 후보가 제안에 포함해달라고 설정해둔 항목**(연봉 범위·근무형태·기술스택 등)이 작성 화면에 표시됨 → 항목을 채워 DM 발송 → 응답을 기다림

### ④ 전달 국면 — HM에게 넘긴다

응답한 후보, 또는 유력한 후보의 프로필 링크를 HM에게 전달 → **"이래서 골랐다"를 근거와 함께 한 줄 붙임** → HM이 증거 카드를 열어 확인 *(→ P3 시나리오 ①)*

## 이 페르소나가 아닌 사용자

- **대기업 공채 HR** — 지원자가 몰려 소싱이 필요 없다. 선별 도구가 필요한 것이지 발견 도구가 아니다
- **전업 리크루터·서치펌** — 소싱이 본업이라 시간·업무 병행 문제가 없고, HM 병목(고통 ④)도 성립하지 않는다
- **소싱 전담자가 따로 있는 대형 HR 조직** — 분업되어 있어 이 페르소나의 고통이 나뉘어 있다
- **개발 직군을 채용하지 않는 기업**
- **기술 면접관(HM)** — P3로 분리
