## 2. 왜 개편하는가

2026-10-30 팀장 질문: AI-DLC로 만든 Unit은 커밋이 적은데 판단이 많다. PR 기반으로 Catch를 뽑는 대전제가 틀렸나, 결국 지침을 준 AI로 분류해야 하나.

검토하면서 대전제를 둘로 나눴다.

- **"작성자가 낸 PR = Catch 경계"는 유지한다.** 경계는 같은 작업을 다시 알아보는 열쇠라 분석할 때마다 같아야 한다. 재분석 때 설명을 유지하는 FR2.5와 2026-10-30의 지우지 않는 재분석 결정이 여기에 기댄다.
- **"PR 하나 = 판단 하나"는 맞지 않는다.** 판단의 이유는 Catch마다 작성자가 쓰는 설명(FR2.1)이 맡는다.

경계 자체에 AI를 쓰기 어려운 진짜 이유는 AI가 아니다. 분석할 때마다 경계를 처음부터 다시 계산하는 지금 방식이 문제다. 한 번 정한 소속을 저장하면(§3-4) 경계 안팎에 AI를 쓸 길이 열린다.

## 3. 정한 것 (팀장 결정)

### 3-1. 이 intent (2026-11-01)

- Catch 개편은 새 AI-DLC intent로 팀장이 직접 맡는다. 크기는 MVP 수준이다.
- 12월 intent는 납품 계획까지 승인됐고 Unit이 진행 중이므로, 거기에 Unit을 더하지 않는다.

### 3-2. Catch 경계는 PR 그대로 (2026-11-02 팀장 확인)

- 작성자가 낸 PR이 Catch 하나다. PR이 없으면 병합, 그것도 없으면 커밋 묶음이 하나다.
- 한 이슈가 여러 PR로 나뉘어도 Catch를 합치지 않는다. 이유는 네 가지다.
  - 공지·조율 이슈가 거대한 Catch가 된다.
  - 이슈 여럿을 가리키는 PR을 어느 쪽에 둘지 정할 수 없다.
  - 첫 분석 내용이 고정되므로, 이슈 단위 Catch는 늦게 온 PR을 담지 못한다.
  - 이슈를 가리키는 방식이 팀마다 다르다.
- PR로 나눈 것 자체를 작성자의 판단으로 본다. 2026-10-08의 "작성자가 한 PR로 묶은 경계를 존중한다"를 반대 방향에도 적용한 것이다.
- 작은 PR이 많으면 Catch도 많아진다(CatchU 팀장 PR 163개). 이것은 경계가 아니라 목록 정리로 다룬다(#454).
- 이슈를 읽는 12월 요청에서도 한 PR이나 PR 없이 합친 병합을 이슈 번호로 나누지 않는다(2026-11-02). #118의 나누기를 끈다.

### 3-3. Catch를 엮는 기능은 다시 만들지 않는다 (2026-11-01)

- 9월의 '주장'(여러 Catch를 묶어 제목·본문을 다는 구조)은 12월에 뺀 그대로 둔다.
- 여러 PR로 나눈 작업은 텍스트 자료를 발행 순서에 머리글처럼 두어 보인다. 발행 항목은 Catch·텍스트·PDF가 한 순서로 섞이고, 텍스트 본문은 검색 조각이자 "작성자 자료 원문"이 된다.
- 시연 발행본의 RAG 품질 평가 때 확인한다(#441 「범위」·「완료 기준」).
- 다시 볼 조건: 시연이나 팀원이 아닌 1명의 사용에서 "Catch가 흩어져 고르기·읽기 어렵다"는 반응이 실제로 나올 때.

### 3-4. 소속 저장 (2026-11-01, 이 intent에 넣는다)

- **목적:** 재분석 때 같은 작업이 중복 Catch로 생기지 않게 한다.
- **저장:** 한 회원·한 저장소 안에서 커밋 SHA마다 소속 Catch를 저장한다. 커밋 하나는 Catch 하나에만 속한다. 탈퇴할 때 함께 지운다.
- **재분석:** 요청에 "이미 소속된 커밋 목록"을 실어 worker에 넘긴다. worker는 그 커밋을 새로 묶는 재료에서 빼고, 남은 새 커밋만 묶는다. 새로 맡은 커밋이 없는 단위는 후보가 되지 않는다(지금 규칙).
- **결과:** 후보마다 소속 커밋 전체를 싣는다. 지금은 근거로 최근 20건만 싣는다.
- **바꾸지 않는 것:** 열쇠 값(`wi1`)을 만드는 법, Catch 내용, 본인 기여 판정.
- **열쇠가 같은 PR 단위:** 지금처럼 기존 Catch로 이어진다. 그 PR에 나중에 더해진 커밋은 기존 Catch 소속으로 기록만 하고, 내용은 처음 그대로 둔다(10/30).
- **막는 것:**
  - 범위가 밀려 생기는 중복
  - 새 커밋이 묶음에 붙어 생기는 중복
  - 재분석 때 통합 PR이 Unit 커밋을 다시 흡수해 생기는 중복
  - 규칙을 고쳐서 생기는 중복. 고친 규칙은 새 커밋에만 적용된다.
- **막지 못하는 것:**
  - 첫 분석의 경계. 이것은 PR 범위로 막는다(§3-5).
  - rebase로 SHA가 바뀐 커밋. 지금도 있는 한계다.
  - 이어지는 작업이 새 Catch가 되는 것. 10/30 한계와 같다.
- **시점:** 출시 직전 DB 초기화 전(§8-6). 그 뒤에는 기존 Catch의 소속 전체를 되살릴 길이 없다.

### 3-5. 수집 상한 (2026-11-01, U7 #424에서 처리. 이 intent의 전제)

- U7 후속에서 처리한다. 시작 값과 판정 기준은 #424 본문에 있다.

## 4. AI 초안 재료 고르기와 변경 묶음 (설계안, intent에서 확정)

**문제:** 큰 PR이나 큰 커밋 묶음에서 AI 초안이 앞쪽 파일로만 만들어지고, 그 안에서 무엇을 했는지 보이지 않는다.

### 4-1. 파일 세 갈래

기준은 누가 썼느냐가 아니라 **다른 것에서 다시 만들어지는 파일이냐**다. GitHub가 "생성된 파일"을 가리는 기준과 같은 생각이다.

| 갈래 | 뜻 | 예 | AI 초안 재료에서 |
|---|---|---|---|
| 작업 내용 | 이 작업에서 바꾼 원본 | 소스 코드(AI가 짰어도 포함), 시험, 사용자 문서 | 먼저 담는다 |
| 작업 기록 | 다시 만들어지지 않는, 작업 과정의 기록 | 설계 문서·ADR, AI 도구의 계획·명세 파일, 질문·답 기록 | 작업 내용 다음에 담는다 |
| 산출물 | 다른 것에서 다시 만들어지는 파일 | 잠금 파일, 빌드 결과·압축 파일, 생성 코드, 실행 기록·감사 로그, OS가 만드는 파일, 통째로 넣은 외부 라이브러리 | 담지 않는다 |

이 판정은 본인 기여 판정을 바꾸지 않는다. "AI가 썼다"고 표시하지 않고, 진위도 판정하지 않는다.

### 4-2. 1단계: 규칙만 쓰고, 판정 자리는 비워 둔다

1. **산출물 거르기:** 저장소의 `.gitattributes`에 작성자가 표시한 생성·외부 파일, 공개 목록(GitHub Linguist 기준: 잠금 파일·빌드 결과·압축 파일·`node_modules`·`vendor` 같은 폴더), OS 파일을 뺀다.
2. **종류로 순서 정하기:** 코드 → 시험 → 설정 → 문서(작업 기록 포함) 순이다. 지금 제목 규칙의 종류 표를 다시 쓰되, 아래 빈틈을 보완한다.
   - `*Test.java`·`*Tests.cs` 같은 이름 꼴과, 대소문자를 가리지 않는 `Tests/` 폴더
   - 실행 결과가 들어가 커지는 노트북(`.ipynb`)
   - 모바일 프로젝트 구조
3. **변경 묶음의 씨앗 만들기:** 다음 순서로 시도한다.
   - 바뀐 파일이 갈라지는 폴더 깊이를 저장소마다 찾아 그 폴더로 나눈다.
   - 계층별 구조(`controller`·`service`·`repository`)면 파일 이름 앞부분으로 나눈다.
   - 시험 파일은 대상 파일의 묶음에 붙인다.
   - 그래도 나뉘지 않으면 묶음 하나로 둔다. 지금과 같다.
4. **재료 담기:** 묶음마다 고르게 담고, 한 파일이 차지하는 양에 상한을 둔다. 묶음 안에서는 2의 종류 순서를 따른다.
5. **판정 자리:** worker에 "판정 공급자" 자리를 둔다. 1단계에서는 규칙 결과를 그대로 쓰고, 시험은 합성 판정으로 한다. 10월 생성 모듈이 합성 제공자로 시험하는 방식과 같다.

1단계는 보내는 자료의 종류(본인 커밋의 줄·경로·상태)와 보내는 회사를 바꾸지 않는다.

### 4-3. 2단계: 판정 자리에 AI (2026-11-02 팀장 결정, 이 intent에 넣는다)

- **부르는 때:** 재료 상한을 넘는 큰 후보에만, 후보 하나에 요청 한 번.
- **입력:** 바뀐 파일 목록(경로·상태·줄 수·앞 몇 줄).
- **질문 1(규칙이 모르는 파일만):** 작업 내용 / 작업 기록 / 다시 만들어지는 산출물 중 무엇인가.
- **질문 2(묶음이 애매한 파일만):** 씨앗 묶음 중 어디에 속하나, 아니면 공통인가.
- **질문 3(파일마다):** 이 작업을 얼마나 대표하나(1\~5 점수).
- **공급자:** OpenAI Decisions API(§5와 같은 회사). 같은 입력에 대한 질문 여러 개(최대 400개)를 한 요청에 넣는다. 따로 표본 비교는 하지 않는다.
- **확인:** §5-3의 Catch 20개에 재료 상한을 넘는 큰 PR을 넣어, 설명 초안이 그 작업을 대표하는지 함께 본다.
- **§5와의 관계:** 고지와 추가 호출 예외는 §5와 함께 고친다. 재료 고르기는 글쓰기 전에 해야 하므로, 큰 후보에는 §5의 판정과 다른 요청이 하나 더 나간다. 이 요청이 실패했을 때 규칙 결과로 갈지는 기능 설계에서 정한다.

## 5. Catch 제목·작업 사실·설명 초안 (2026-11-01 팀장 결정)

- 작업 사실이 「PR 없이 병합한 병합 커밋 f0b728b28882」처럼 나와, 그것으로 할 수 있는 일이 없다.
- 기계적으로 자르거나 단순한 사실만 적어서는 문제가 있다. AI로 이해되게 만들어야 하지 않나.
- 이어진 논의에서: 커밋 메시지가 부실하면 AI가 새로 써야 한다. 시연에서 면접관이 Catch가 무엇인지 궁금해할 텐데, 사람의 말로 쓴 글이 아닌 것이 큰 문제다.

**지금 모양이 된 이유**
2026-10-08 결정이 근거 없는 서술과 오귀속을 막으려고 다음을 정했다.
- 제목은 근거로 확인되는 조각(대상·종류·동작)으로만 만든다.
- 작업 사실은 구조 값(번호·SHA 앞 12자·상태)만 쓴다.
- 파일 경로·커밋 메시지·PR 글·센 숫자는 문장에 넣지 않는다.

#120의 2026-10-12 결정은 설명도 틀 문장으로 만들었다. "바뀐 줄에 글자가 있다는 것만으로 자유 문장 전체의 뜻이 사실이라고 볼 수 없다"는 이유였다. 분석 고지 v2(U7 #433) 3절은 외부 AI에 커밋 메시지와 PR·이슈의 글을 보내지 않는다고 적었다.

**12월 설계로 넘겼지만 다루지 않은 것** (`docs/ai-dlc-input-december/CatchU_12월_범위_보완.md` 「3-3」)
- 생성된 제목을 Catch마다 표시할지
- 문장형 제목을 쓸지. 쓴다면 그 낱말이 근거에 있는지 확인할 방법도 함께 정한다.

### 5-1. 새로 확인한 사실

- 12월 받은 사람 AI가 Catch에서 읽는 근거는 작업 사실 → 나의 기여 → 근거의 관측 사실 → 작성자 설명이다. 제목과 AI 초안은 검색 조각이 되지 않는다(U3 BR1.1).
  - 관측 사실은 「커밋 {SHA 앞 12자}, 작성 시각 …」「병합 커밋(부모 2개)」「변경 파일 N개, 추가 X줄·삭제 Y줄」「PR #n, 상태 …」「PR 커밋 N건」뿐이다.
  - 그래서 작성자 설명이 없는 Catch는, 12월 AI가 "무엇을 했나"를 쓸 재료가 없다.
- 수집 기록에는 커밋 메시지, PR 제목, PR을 연 계정이 이미 있다. 기록의 글을 쓰는 데 GitHub 조회가 늘지 않는다.
- 10월 계약의 제목·작업 사실에는 길이 상한이 없다. api 등록도 길이를 검사하지 않는다.
- 12월 기계 대조(FR6.4)는 api의 공통 모듈(TypeScript)이라 worker에 그대로 쓸 수 없다.
- 12월 첫 이용 AI 고지(`AI_NOTICE_VERSION` `2026-11-v1`, web과 api에 같은 상수)는 보내는 기능의 목록만 적고, 보내는 내용의 항목은 적지 않는다.
- 실측(팀장 공개 저장소, gh 조회): 본인 커밋(병합 제외) 첫 줄 가운데 글이 거의 없는 것은 TheMe 96개 중 2개, BEASTA-ZOO 61개 중 5개, algo-problem 99개 중 0개다. 모두 커밋 규칙(접두사·이슈 키)이 있던 저장소라, 일반 저장소에서는 더 많을 수 있다. CatchU 병합 PR 제목 200개는 중간값이 49자이고, 151개가 40자를 넘는다.
- 예: 「PR 없이 병합한 병합 커밋 f0b728b28882」(TheMe)의 근거인 본인 커밋 첫 줄은 「style: 테마 생성 모달 css #S07P31C203-127」이다. 같은 단위의 병합 커밋 메시지에는 브랜치 이름에 든 사람 이름이 들어 있다.
- 2026-10-24 인용 사전 시험은 PR 글을 넣어 만든 Catch로 했기 때문에, 이 빈틈이 보이지 않았다(§2).

### 5-2. 정한 것

**제목**은 다음 순서로 정한다.
1. **기록의 글:** 본인이 연 PR이고, 그 PR에 다른 계정의 커밋이 없다고 확인됐으면(커밋 목록을 끝까지 받은 때) PR 제목을 쓴다. 있는지 알 수 없으면 PR 제목을 쓰지 않는다. 그 밖에는 단위 안 본인 커밋(병합 커밋 제외) 가운데 가장 처음 것의 메시지 첫 줄을 쓴다(뒤 커밋은 리뷰 뒤 고친 것이 많다). 자르지 않고, 화면에서 보이는 줄 수를 제한한다. 비밀값·개인정보 가리기 규칙에 걸리는 글은 쓰지 않는다.
2. **부실하거나 전체를 나타내지 못하면 Claude가 쓴다:** 부실은 글이 거의 없는 것(문자·숫자 2자 이하이거나, 짧은 흔한 낱말 목록의 낱말 하나뿐)이거나, 판정 질문 "무엇을 했는지 알려 주나"의 확률이 0.5 미만인 것이다. 본인 커밋이 2개 이상인 단위의 커밋 메시지는 "이 Catch의 작업 전체를 나타내나"도 묻고, 0.5 미만이면 Claude 후보로 간다. Claude는 지금의 생성 호출에서 바뀐 줄만 보고 제목 후보를 쓴다. 후보마다 근거로 삼은 줄을 가리키게 하고, 목적·효과·평가(「성능 개선」 같은 말)는 쓰지 않게 지시한다. 코드 이름·파일 이름은 바뀐 줄에 적힌 표기 그대로 쓰게 지시한다(12월 FR6.4의 생성 지시와 같다).
3. **기계 대조:** 제목의 영어 이름·숫자는 그 제목이 가리킨 줄에, 파일 이름은 가리킨 줄의 경로에 있는지 본다. 재료 전체에서 찾으면 다른 줄의 이름으로도 통과하기 때문이다. 12월 기계 대조(FR6.4)의 규칙을 worker에 다시 짠다.
4. **판정:** 고르기 질문 "뒷받침되면서 무엇을 했는지 가장 잘 알려 주는 제목은?"(후보들과 "없음")에서 0.9 이상인 후보를 쓴다.
5. 모두 떨어지면, 전체를 나타내는지에서만 떨어진 기록의 글은 그대로 쓰고 그 밖에는 지금의 조각 제목(대상·종류·동작)을 쓴다.

**작업 사실**
- 첫 줄에는 종류만 둔다. 「PR #7, 상태 병합됨」(지금 그대로), 「PR 없이 합친 병합」, 「PR·병합 없이 들어간 본인 커밋」(묶음이면 묶음)이다.
- SHA와 날짜는 넣지 않는다. SHA는 근거 링크와 관측 사실에 남고, 날짜는 관측 사실의 작성 시각에 이미 있다. 기간을 적으면 일한 시간으로 잘못 읽힌다.
- 기록의 글이 쓸 만하면 한 줄을 더한다. 「PR 제목: "…"」 또는 「본인 커밋 메시지 첫 줄: "…"」이다. 쓸 만한지는 제목 2의 부실 기준으로만 본다(전체를 나타내는지는 보지 않는다). 이 줄은 GitHub 기록 원문이라 12월 AI가 인용할 수 있다.
- AI가 쓴 글은 작업 사실에 넣지 않는다.

**설명 초안**
- Claude가 바뀐 줄만 보고 사람의 말로 1\~3문장을 쓴다. 문장마다 근거로 삼은 줄을 가리키고, 목적·효과·평가는 쓰지 않는다.
- 문장마다 제목 3과 같은 기계 대조를 하고, 판정 질문(참일 확률)이 0.9 이상인 문장만 남긴다.
- 문장이 모두 떨어지면 설명 없이 둔다(NOT_GENERATED, 실패로 세지 않는다). 판정 호출이 오류로 끝나면 지금처럼 실패로 기록하고 다시 부르지 않는다.
- 틀 문장은 AI 쪽을 껐을 때만 쓴다. 생각해볼 질문은 지금의 틀 그대로다.
- 설명 초안은 사람이 읽는 화면(구직자 Catch 상세, 받은 사람 화면)에만 나온다. 12월 AI의 근거와 MCP에는 지금처럼 들어가지 않는다.

**판정 모델**
- OpenAI Decisions API 하나를 쓴다. Catch마다 요청 1번에 그 Catch의 질문을 모두 넣고, 미국에서 처리한다.
- 공식 안내(2026-11-01 확인)
  - 글을 쓰지 않고 참일 확률·고르기·점수로만 답한다. 모델은 `gpt-6-luna` 하나이고, 요청 하나에 질문을 400개까지 넣는다.
  - 입력 100만 토큰당 0.10달러이고, 출력은 무료다.
  - 받은 자료를 학습에 쓰지 않고, 오남용 감시 기록을 최대 30일 둔다. 무보관(ZDR)은 승인된 고객만 쓸 수 있다.
  - 한국어 성능은 안내에 없다.
- 확인(5-3)에서 한국어 판정이 기준에 못 미치면, 같은 질문을 Claude로 판정한다. 회사와 고지의 받는 곳은 그대로이고, Catch당 약 1.5초가 더 든다. 같은 모델이 쓰고 채점하는 한계가 있다.
- 판정은 분석에서 만드는 제목·작업 사실·설명 초안에만 쓴다. 12월 받은 사람 쪽 기본 요약·질의응답·JD 요약은 FR6.9대로 판정 없이 둔다.
- Microsoft-Decision-1은 Azure(Foundry)나 OpenRouter를 거쳐 써야 하고, 한국어 성능이 확인되지 않았다. 이번에는 쓰지 않는다.

**켜고 끄기와 진행**
- OpenAI 판정 키가 설정돼 있을 때만 AI 쪽(Claude가 쓰는 제목·설명과 판정)이 켜진다. 끄면 기록의 글은 규칙(제목 2의 "글이 거의 없는 것")만으로 고르고, 제목은 조각 제목, 설명은 틀 문장으로 돌아간다.
- 두 단계로 나누지 않고, 한 설계로 한 번에 넣는다. 나누면 고지 판본과 결정 기록을 두 번 고쳐야 한다.
- 합치기 전 확인(5-3)을 넘으면 AI 쪽을 켠 채 합친다. #441 NFR3 측정 전까지 넘지 못하면 끈 채 합친다.

**기본값** (팀장 이의 없음)
- 판정 문턱은 0.9에서 시작한다.
- Claude에는 지금처럼 바뀐 줄만 보낸다. 커밋 메시지와 PR 제목은 Claude에 보내지 않는다.
- 화면에는 Catch마다 출처 칸을 두지 않고, 공통 안내 한 줄만 둔다.
- 재료는 도구 폴더를 빼지 않고 순서만 바꾼다: 코드 → 시험 → 설정 → 문서 → 그 밖. 빼면 문서만 고친 작업의 재료가 없어진다. §4-2의 2와 같은 순서이고, §4-2의 1(산출물 거르기)은 넣지 않는다(§8-2).

**12월 범위 보완 「3-3」의 두 항목에 대한 답**
- 생성된 제목을 Catch마다 표시할지: 표시하지 않고, 공통 안내 한 줄로 알린다.
  - 한계: FR6.4는 제목을 AI 설명 초안(설명·제목·질문)에 넣고, NFR7은 받은 사람이 AI 초안과 근거 원문을 화면 표시로 구분할 수 있어야 한다고 한다. 공통 안내 한 줄로는 Catch마다 구분되지 않아 NFR7을 다 채우지 못한다. 채우려면 제목 출처 칸이 필요하고, 그러면 worker 메시지·api 저장·발행 사본·화면 계약이 바뀐다(§8-10).
  - 기록의 글을 쓴 Catch는 작업 사실에 「PR 제목: "…"」 같은 줄이 있어, 상세 화면에서는 출처가 간접적으로 보인다.
- 문장형 제목을 쓸지: 쓴다. 사람이 쓴 기록의 글을 먼저 쓰고, AI가 쓴 제목은 기계 대조와 판정을 넘은 것만 쓴다.

### 5-3. 합치기 전 확인 (한 번)

- Catch 20개(CatchU 6·TheMe 7·algo-problem 7, 재료 상한을 넘는 큰 PR 포함)를 만들고, 팀장이 제목·문장마다 맞음·틀림을 표시한다. 본인 커밋이 여럿인 Catch는 제목이 작업 전체를 나타내는지도 표시한다. 화면에 기록의 글이 나가는 Catch도 판정이 고른 AI 제목 후보를 시험용으로 남겨 함께 표시한다. 판정은 OpenAI 하나로 만들어 잰다.
- 기준 시작 값: 틀린 제목이 통과한 것 0건, 틀린 문장이 통과한 것 1건 이하. 맞는데 버린 것은 건수만 적는다. 그 가운데 표기 차이(k8s와 Kubernetes 같은)로 기계 대조에서 버린 것은 따로 센다. 많으면 12월 쪽 표기 처리 결정과 함께 정하고 worker와 api를 같이 바꾼다.
- 기준에 못 미치면 지시문 수정은 한 번까지만 한다(NFR3의 조정 방식과 같다). 한국어 판정이 기준에 못 미치면 같은 질문을 Claude로 판정해 다시 잰다. Claude 판정도 기준을 넘지 못하면 AI 쪽을 끈 채 합친다.
- 이 결과로 AI 쪽을 켤지와 문턱을 정한다.
- 확인 자료 20개를 OpenAI로 보내는 것은 팀장이 허락했다(2026-11-02). CatchU는 비공개라 서비스 수집으로 만들 수 없어, 그 6개는 수집 결과를 직접 넣는 개발용 실행으로 만든다.
- 한계: 표본이 모두 커밋 규칙이 있던 팀장 저장소다. 일반 저장소에서 기록의 글이 부실한 비율과 그때의 판정은 이 확인으로 알 수 없다.

## 8. intent 시작 전 결정 (2026-11-02 팀장)

1. Catch 경계: 정했다(§3-2).
2. 산출물 거르기(§4-2의 1): 넣지 않는다(2026-11-02). 판정 없이 규칙만 쓰는 경로(AI 쪽을 껐거나 판정이 실패한 큰 후보)에서는 코드처럼 보이는 산출물(`*.min.js`·외부 라이브러리 폴더·생성 코드)이 재료 앞자리를 차지할 수 있다. 이것은 한계로 둔다. 3\~5와 2단계는 넣는다.
3. 산출물을 커밋 묶기에서 무시할지: 무시하지 않는다(2026-11-02, 2026-10-19 D1 유지). 표본에서는 algo-problem의 `.DS_Store`로 이어질 수 있는 쌍이 많아야 하나다.
4. 한 PR 안의 서로 다른 이슈 번호: 정했다(§3-2).
5. 통합 브랜치: `intent/260925-intent-12`를 같이 쓴다(2026-11-02). 그 브랜치에서 만든 작업 브랜치(`영역/작업내용`)에서 intent를 진행하고, 단계 승인마다 커밋한 뒤 PR·merge commit으로 통합 브랜치에 넣는다. PR은 Unit마다 나눌 수 있다. 통합 브랜치가 dev로 합쳐진 뒤 남은 PR은 dev로 올린다. `team.md`와 컨벤션 §2.1은 고치지 않는다.
6. 시작 시점: 지금 시작한다(2026-11-02, #454 → 입력 문서 PR → intent 순). 통합 브랜치에는 12월 intent의 통합 확인 뒤에 넣는다. 출시 직전 DB를 초기화하고 다시 분석하므로 "첫 분석 전" 조건은 "초기화 전"이 된다(시연 발행본도 지워진다).
7. 외부 전송의 허락: 정했다(§5-3).
8. 카드생성논리(2026-08-12)의 "같은 입력이면 같은 결과": 이렇게 고쳐 적는다(2026-11-02, 옛 문서는 그대로). "Catch의 경계와 소속은 정해진 규칙으로 정한다. 같은 입력(저장소 기록과 이미 정한 소속)이면 같은 결과가 나오고, 한 번 정한 소속은 바뀌지 않는다. AI는 제목·설명 같은 글과 재료 고르기에만 쓴다."
9. AI 제목을 몇 개로 잴지: 20개 모두 잰다(2026-11-02, §5-3). 정한 그대로면 AI 제목은 TheMe의 4개쯤뿐이라, 10개 중 1개꼴로 틀려도 셋 중 둘은 통과한다.
10. 제목 출처 표시와 NFR7: 한계로 두고, 이 intent 요구사항에 NFR7·FR1.4의 예외로 적는다(2026-11-02). 출처 칸은 시연에서 문제가 보이면 출시 직전 초기화 전에 더할 수 있다.
