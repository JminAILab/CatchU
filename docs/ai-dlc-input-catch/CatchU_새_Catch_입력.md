### 2-3. 기술 팀장이 보는 것 (근거)

- **우리 근거는 얇다.** 2026-08-27 현직 면접관 인터뷰 한 번이다(`docs/페르소나_P3_기술면접관_v3_0.md`, `docs/P3_설계노트_v2_0.md` §6). 확인 목록 8개 가운데 셋(GitHub에서 먼저 보는 것, 면접 질문 준비 방법, 평가표)은 확인하지 못했다.
- **인터뷰에서 한 말.** GitHub를 봐야 한다고 생각하지만 시간이 없어 거의 못 본다. 요약이라도 원본으로 바로 갈 수 있어야 믿는다. 점수화·등급화·강점 정리·공고 매칭은 원하지 않는다("내 판단을 대신하지 마라"). 원하는 것은 질문 자체가 아니라 질문을 만들 재료다.
- **바깥 자료.** AI를 쓰게 한 면접은 결과물보다 이유와 맞바꿈, AI가 만든 코드의 문제를 찾아 고치는지를 본다(Canva, 2025-06-11·2025-10-20). 후속 질문으로 이해를 가른다("이 줄을 빼면 어떻게 되나", interviewing.io 면접관 67명 조사). 반대로 기초 실력은 AI 없이 직접 보는 회사도 많고(Cursor·Anthropic·Google), GitHub 기록은 사람 대부분에게서 드물게 남는다. 주소는 §10.
- **CatchU 자신.** 판단은 이슈·PR 리뷰·문서·AI-DLC 승인 기록에 남았지만, U2 질문 답 19개 가운데 사람의 이유가 든 글은 3\~4개였다(Catch 개편 입력 §2). GitHub에 남은 글도 사람이 판단했다는 확실한 증거가 아니다.

**정리.** Catch가 기술 팀장에게 줄 수 있는 것은 ① 이 사람이 무엇을 맡아 무엇을 했는지 빨리 보는 그림 ② 지원자가 같은 형식으로 적은 자기 판단 ③ 그 판단을 시험할 코드 자리와 원본이다. 판단의 증명과 평가는 줄 수 없다.

## 3. 정한 것 (팀장 결정)

### 3-1. 새 Catch로 바꾼다 (2026-11-09)

- §4의 방향으로 Catch를 바꾼다.
- 설계 검토가 제안한 0단계(공개 저장소 수 세기, 현직 개발자와 정적 화면 비교)는 하지 않는다. 그 결과로 정하려던 아래 넷은 가장 단순한 안으로 둔다(2026-11-09 팀장 확인).
  - 면접관 화면의 Catch 순서는 §3-4 그대로 두고 새 칸만 끼운다.
  - 면접관 화면 맨 위에 공통 안내 문장을 더하지 않는다. Catch마다 붙는 '확인하지 않음' 표지도 두지 않는다.
  - 규칙이 뽑은 '같은 작업 안에서 다시 고친 곳' 같은 사실은 지원자 화면에만 보인다.
  - 리뷰 상태는 모으지 않는다.

### 3-2. AI 설명 초안은 '무엇을 했나'만 (2026-11-07, #487)

'왜'는 작성자 설명이 맡는다. 지시문만 바꾸고, 바꾸면 FR10 확인을 다시 한다(BR9.3).

### 3-3. 생각해 볼 질문은 AI가 작업 전체를 묻는다 (2026-11-08, #487)

- 코드 한 줄이나 이름이 아니라 작업 전체를 묻고, 정해진 틀 대신 AI가 질문 글을 쓴다. 종류 셋(배경·다른 방법·확인 방법)과 1\~3개는 그대로다.
- 질문에는 판정·기계 대조를 붙이지 않는다. 본인만 보기 때문이다. AI 쪽을 끈 경로도 같은 지시와 응답 모양을 쓴다.
- #120 2026-10-12 결정(틀 문장 질문)과 Catch 개편 FR7.4 「생각해 볼 질문은 지금의 틀 그대로」를 대체한다.
- 분석 고지 v3 2절의 「질문은 정해진 문장으로 만듭니다」는 CR3 PR에서 뺀다(2026-11-09). 3절이 이미 질문에 Anthropic을 쓴다고 적었으므로 #487 전후 모두 맞고 판본을 올리지 않는다.

### 3-4. 발행본 Catch 순서와 근거 접기 (2026-11-08, #488)

받은 사람 화면의 Catch는 위에서부터 불일치 표지 → AI 설명 초안 → 작성자 설명 → 기록에서 확인한 내용이다. 작업 사실은 펼치고, 본인 기여와 근거 목록은 「근거 자세히 보기」 아래에 접는다. Catch 개편 CR3 PR 뒤에 합친다.

### 3-5. 제목 출처 표시는 나중에 (2026-11-03)

Catch 개편이 다 들어간 뒤 제품 전체를 점검할 때 정한다. 이 문서는 제안하지 않는다(§8-2에 판단 재료만).

### 3-6. 그대로 두는 Catch 개편 결정

작업 단위(PR → PR 없이 합친 병합 → 본인 커밋 묶음)와 소속 저장, 같은 입력이면 같은 결과(Catch 개편 NFR4), 제목 규칙(기록의 글, FR5.1), 판정(OpenAI Decisions, FR4). 본인 기여는 연동 GitHub 계정이 작성자로 기록된 커밋이다(2026-10-08 결정).

## 4. 새 Catch (설계안)

### 4-1. 정의

> Catch는 지원자가 분석된 작업 가운데 골라 면접관에게 보내는 한 장이다. 그 작업에서 내린 판단을 지원자가 자기 말로 적고, 면접관이 그 말을 시험해 볼 코드 자리와 GitHub 원본이 함께 붙는다. Catch는 판단을 증명하지 않는다. 판단은 면접에서 확인한다.

이 정의를 intent 요구사항 머리에 적는다(§8-1). 고르지 않은 작업도 지원자 화면에는 Catch로 남는다. 원칙 넷은 이미 있는 것이다(P3 설계 제약 2·3·5, 12월 FR1.4·NFR7).

- CatchU는 판단을 증명하거나 평가하지 않는다.
- 면접관에게 가는 글은 누가 썼는지 구분한다.
- 면접관은 원본으로 한 번에 갈 수 있어야 한다.
- 고르는 일은 지원자가 하고, CatchU는 순위나 추천을 내지 않는다.

지금과 달라지는 것은 셋이다.

| | 지금 | 새 Catch |
|---|---|---|
| 면접관이 받는 것 | 작업마다 만든 카드가 같은 무게로 늘어선다 | 지원자가 고른 3\~5장과 그 안의 코드 자리 |
| 믿음의 근거 | AI 문장을 기계 대조와 판정으로 거른다 | 원본 링크와 짚어 볼 곳, 면접에서 확인 |
| 판단의 주인 | 기록과 AI가 판단을 보여 주려 한다 | 지원자가 자기 이름으로 말하고 CatchU는 시험할 자리를 붙인다 |

### 4-2. 면접관이 보는 한 장 (TheMe `c6bdf0c`, 1\~3단계가 다 들어간 뒤)

작성자 글과 AI 초안 글은 모양을 보이려고 지어낸 예시다. 〔 〕는 화면에 나오지 않는 설명이다.

```
feat : 게시글 등록 이미지 리사이징 #S07P31C203-153   〔제목: 지금 규칙(기록의 글) 그대로〕
ljm0850/TheMe                                        〔제목 아래 줄: 저장소 이름, 규칙〕

「AI 설명 초안」                                      〔Claude, 판정을 거침, 무엇을 했나만〕
  선택한 이미지를 canvas로 360x360 크기로 줄여 썸네일 파일을 만든다. …

「작성자 설명」  2026년 11월에 마지막으로 고침         〔작성자〕
  이 작업에서 정한 것: 사진을 올리기 전에 브라우저에서 작게 줄여 올리기로 했다.
  맡은 부분: 게시글 작성 화면 두 곳과 프로필 설정 창의 사진 올리기
  무엇이 문제였나: 원본 사진이 그대로 올라가 피드가 늦게 떴다.
  고른 것과 버린 것: 서버에서 줄이는 안도 봤지만 서버 쪽 일정이 빠듯해 화면에서 했다.
  어떻게 확인했나·결과: 개발자 도구로 올리기 전후 파일 크기를 비교했다. 자동 시험은 없다.
  짚어 볼 곳:

  관련 커밋: ba6bba8 [이 작업의 본인 커밋]           〔사본 근거와 맞을 때만 붙는 표지, 2단계〕
  〔'AI가 낸 것 가운데 받아들이지 않았거나 고친 것' 칸은 비워 두어 보이지 않는다〕

「기록에서 확인한 내용」
  PR 없이 합친 병합
  본인 커밋 메시지 첫 줄: "feat : 게시글 등록 이미지 리사이징 #S07P31C203-153"
  ▸ 근거 자세히 보기 (접힘): 병합 커밋, 본인 커밋 ba6bba8·d42d9a3, 본인 기여 문장
```

면접관은 면접 전에 제목과 「이 작업에서 정한 것」을 훑고 원본을 연다. 면접 중에는 짚어 볼 곳을 띄우고 설명을 청한다. 면접 뒤 평가는 자기 도구로 한다. 질문은 CatchU가 주지 않고 면접관이 만든다. 예를 들어 위 커밋을 열면 캔버스가 사진 비율과 상관없이 360×360으로 그리고 업로드가 끝나기를 기다리지 않는 것이 보이므로, "가로로 긴 사진은 어떻게 보였나요?"를 물을 수 있다.

### 4-4. 지원자 쪽 흐름

1. 분석은 지금 그대로다(작업마다 Catch, 모두 비공개로 시작).
2. 고르기: 발행 화면에 "저장소마다 3\~5개를 권합니다" 안내. 본인 목록에 '설명 씀/안 씀' 걸러 보기(1단계), 작업 시각순 정렬(3단계). 추천·순위는 없다.
3. 고른 Catch 상세에서 쓰기: 기억 되살리기(AI 초안, 기록의 글, 근거 목록, 3단계의 사실)와 생각해 볼 질문을 보며 칸 제목이 붙은 칸에 쓴다. 편집 화면은 칸마다 입력 칸을 따로 보이고, 저장할 때 한 글로 합친다(§8-1). 질문 답은 따로 저장하지 않는다. 질문 옆 "질문에 대한 답변을 저장하는 기능은 제공하지 않습니다"는 "질문을 보고 아래 칸에 자기 말로 적어 보세요" 같은 말로 바꾼다.
4. 짚어 볼 곳: 지원자가 GitHub에서 커밋 판본의 줄 링크를 복사해 붙이고 메모 한 줄을 단다.
5. 안내 한 줄: "이 글은 링크를 가진 누구나 보고 외부 AI로도 보냅니다. 다른 사람의 이름·평가와 비밀값은 쓰지 마세요."

- 의존: Catch 개편 PR 3개(CR1→CR3→CR2).

9. 짚어 볼 곳: 지원자가 작성자 설명 안에 GitHub 줄 링크와 메모를 붙인다(1단계). 규칙이 후보를 내는 별도 칸은 만들지 않는다.
10. 병합 요청 제목: 쓰지 않는다. Catch 개편 FR5.1 그대로이고 고지 3절도 그대로다. 다른 곳에서 옮긴 저장소에서 제목이 작업 일부만 말하는 것은 한계로 둔다.
11. 팀 프로젝트에서 누가 무엇을 했나: 「맡은 부분」 칸, 저장소 이름, 기록의 본인 기여(접힘)만 쓴다. 맡은 폴더 이름과 다른 계정 섞임 한 줄은 더하지 않는다(CR1 기능 설계 Q1 그대로).
12. 정정 한 줄: 넣지 않는다. 틀린 점은 작성자 설명의 '더 쓰기'에 적는다. 10월 FR3.5와 C-07의 `mismatch` 참·거짓 값은 그대로다.
13. Catch 정의: §4-1 정의를 요구사항 머리에 적는다. '사람은 결과물이 아니라 판단의 흔적으로 설명된다' 명제는 기능을 고르는 판정 기준으로 채택하지 않는다.

### 8-2. 이 intent에서 정하지 않는 것 (판단 시점과 재료만)

| 결정 | 판단 시점 | 판단 재료 |
|---|---|---|
| 제목 출처 표시 | Catch 개편이 다 들어간 뒤 제품 점검(2026-11-03) | 넣으면 worker 결과, `catch_asset`, C-07, 받은 사람 응답이 바뀌고, 기존 Catch에도 값이 생기려면 DB 초기화 전이어야 한다. 기록의 글을 쓴 Catch는 작업 사실 둘째 줄로 출처가 간접적으로 보인다 |
| 기계 대조 빼기 | #485(#487 확인 뒤) | 새 설계에서 분석 쪽 AI 글이 면접관에게 가는 곳은 AI 초안 하나뿐이고, #488 순서대로면 Catch 맨 앞에 보인다 |
| CatchU 저장소 공개 | 12월 OQ2 | 판단 기록이 가장 많은 저장소다. 공개하지 않으면 예시와 시연은 다른 공개 저장소로 한다 |
| 출시 직전 DB 초기화 날짜 | 정하지 않음 | 3단계는 그 전에 들어가야 모든 Catch에 값이 생긴다. 작성자 글은 그 뒤에 써야 남는다 |

### 8-3. 남는 위험 (한계로 적을 것)

- 면접관이 새로 얻는 글은 '나중에 쓴 자기 진술'이다. 증거처럼 보이게 하지 않고 시험할 자리와 원본을 붙인다.
- 지원자 답도 AI로 쓸 수 있다. 막지 않고 작성자 글로 구분하며, 시험은 면접관이 짚어 볼 곳에서 한다.
- 'AI가 낸 것 가운데 받아들이지 않았거나 고친 것'을 정직하게 쓴 사람이 더 많이 물릴 수 있다. 이 칸을 다른 칸과 같은 고정 칸(건너뛸 수 있음)으로 두고 구체적으로 묻는다.
- 지원자가 짚어 볼 곳 링크를 직접 찾아 붙여야 한다. 붙이지 않은 Catch에는 짚어 볼 곳이 없다.
- 규칙이 만든 종류 줄과 본인 기여 문장이 받은 사람 AI 답에서 'GitHub 기록 원문'으로 보인다(§8-1의 8).
- 다른 곳(GitLab 등)에서 옮긴 저장소의 'PR 없이 합친 병합'은 제목이 첫 본인 커밋 첫 줄이라 작업 일부만 말할 수 있다(§8-1의 10).
- 에이전트가 자기 계정으로 커밋한 PR을 맡기고 검토·병합만 한 일, 남의 PR을 리뷰한 일은 Catch가 되지 않는다(본인 기여 정의, `worker/docs/candidate-decision.md`). 지원자 계정으로 커밋하는 도구를 썼다면 본인 커밋이다.
- 발행 뒤 저장소가 비공개로 바뀌거나 지워지거나 강제 푸시로 커밋이 사라지면 짚어 볼 곳 링크가 열리지 않는다. 사본에는 주소만 남는다(12월 FR4.3).
- 면접관 쪽 근거는 인터뷰 한 번이고, 0단계를 하지 않으므로(§3-1) 새 모양을 면접관에게 먼저 보이지 않고 만든다. 열람 기록도 없어(12월 보류 항목) 운영 중 반응은 링크를 보낸 사람에게 직접 묻는다.
- DB 초기화 때 작성자 글도 사라진다(Catch 개편 「한계」).
