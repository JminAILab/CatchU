# 증거카드 — 이상형 예시와 추출 방법 (초안 v0.1)

> **용도**: "카드가 완성되면 어떤 모습인가"의 기준점. PoC의 목표 정의이자, 실제 데이터가 이 이상형 대비 몇 %짜리 카드를 주는지 재는 자였다.
> **지위**: 카드 형태는 가설이다 — 인터뷰(면접관이 실제로 원하는 정보)와 PoC(실제로 추출되는 정보) 결과로 갱신한다.

## 1. 이상적인 카드 예시

> 배경 가정: 신입 팀 프로젝트(쇼핑몰), 지원자가 주문 모듈 담당. 기록이 충실한 경우의 **상한선**.

---

### 📌 주문 처리의 재고 차감 동시성 문제 해결
**유형**: 문제해결

**무엇을 했나** — 동시 주문 시 재고가 음수로 내려가는 버그를 발견하고, 낙관적 락을 시도했다가 비관적 락으로 전환해 해결.

**판단의 흐름**
| 날짜 | 사건 | 출처 |
|---|---|---|
| 7/12 | 재현 테스트와 함께 버그 보고 | 커밋 링크 |
| 7/13 | 낙관적 락 구현 | 커밋 링크 |
| 7/15 | 비관적 락으로 전환 — "동시 주문이 몰리는 시간대엔 충돌이 잦아 재시도 비용이 더 컸음" | PR #23 링크 |

**어디에 있나** — `order/service.py`의 `deduct_stock()`. 결제 모듈·알림 모듈이 이 함수를 호출 (코드 위치 링크)

**본인 기여** — 관련 커밋 7개 중 6개 작성 (git 기록 기준)

**사용 기술** — SQLAlchemy, MySQL `SELECT FOR UPDATE`

**연결** — 공고의 "트래픽 상황에서의 안정적 처리" 요구에 대응 / 자소서 2문단 "동시 주문 상황을 고려한 설계" 주장의 근거

**기록에 없는 것 (면접 확인 지점)** — 락 전환 판단이 실측 기반이었는지 추정이었는지 / 데드락 가능성 고려 여부 — 커밋·PR에 남아 있지 않음

---

**설계 의도 요약**
- 카드 단위 = 기능이 아니라 **판단이 일어난 사건**
- 가장 값진 필드 = 판단의 흐름 중 **시도했다가 버린 흔적** (완성 코드에는 안 보이는 층위)
- 판정 없음 — 형용사·점수 없이 사실(기록)과 연결(공고·자소서 대응)만. 판단은 읽는 사람이 한다
- "기록에 없는 것" 필드 = 진정성 검증을 면접으로 넘기되, 무엇을 물을지까지 제공

## 2. 필드별 추출 방법 (대표 예시)

| 카드 필드 | 원천 데이터 | 추출 방법 | 비고 |
|---|---|---|---|
| 무엇을 했나 / 유형 | 커밋 메시지 + diff + PR 제목·본문 | REST `GET /repos/{o}/{r}/commits`, `GET .../pulls` → 관련 커밋들을 사건 단위로 묶고 LLM으로 서술 생성 | 사건 경계 묶기(클러스터링)가 핵심 난제 — 파일 경로·시간 근접·PR 소속 기준 |
| 판단의 흐름 | 커밋 시계열, PR 본문·리뷰 코멘트, 이슈 | `GET .../commits?path=...`(파일별 이력), `GET .../pulls/{n}/commits`, `GET .../issues/{n}/comments` | 본인 발화만 사용(타인 코멘트는 익명화 원칙). "구현→교체" 패턴은 diff 비교로 메시지 없이도 탐지 가능 |
| 어디에 있나 (구조) | 레포 파일 트리, import 관계, 설정 파일 | `GET .../git/trees?recursive=1`(전체 트리 1회 호출), package.json·requirements.txt 파싱, 필요 시 클론 후 tree-sitter로 호출 관계 | 층위1~2(스택·모듈 구조)까지가 현실적. 콜그래프는 무거움 — PoC에서 깊이 결정 |
| 본인 기여 | 커밋 author | `GET .../commits?author={login}` 로 커밋 단위 귀속 | **REST에는 git blame이 없음** — 라인 단위 귀속은 GraphQL blame 또는 클론 후 `git blame` 필요. MVP는 커밋 단위 근사로 시작 권장 |
| 사용 기술 | diff 내 import·의존성 파일 | `GET .../commits/{sha}` 응답의 files(patch) 파싱 | 대형 커밋은 diff 잘림(아래 고려사항) |
| 공고 연결 | 카드 서술 × 공고 요구역량 | LLM 매칭 (임베딩 후보 추림 → LLM 판정) | 색B — 틀릴 수 있는 층. 기여(사실)와 신뢰도 구분 표시 필요 |
| 자소서 연결 | 카드 × 자소서 문단 | 자소서를 색인으로 사용 — 문단별 주장 추출 → 카드와 매칭 | 자소서는 분석 대상이 아니라 색인(D-19 방향) |
| 기록에 없는 것 | 흐름의 공백 | 규칙 기반: 교체·삭제가 있는데 이유 서술이 없음 / 큰 diff에 메시지 한 줄 등 | "없음"의 탐지라 LLM 환각 주의 — 보수적으로 |

**호출 전략 메모**: 레포당 트리 1회 + 커밋 목록 페이지네이션 + 상세는 카드 후보 커밋만 — 전 커밋 상세 조회는 rate limit(인증 시 5,000회/시)에 걸림. GraphQL은 한 번에 묶어 가져오기에 유리하나 blame 등 무거운 필드는 별도 예산으로.

## 3. 추출 시 고려사항 (한계와 대응)

### 데이터가 얇은 경우 — 가장 흔한 현실
1. **커밋 메시지 부실** ("fix", "update") — 흐름 필드가 빈약해짐. 대응: diff 기반 보강(메시지가 아니라 변경 내용에서 사건 추론) + "이유 기록 없음" 자체를 카드에 남김(면접 질문으로는 유효). 한지우의 기본 상태가 이것이므로 **PoC는 부실 메시지 레포를 반드시 포함**해야 함.
2. **스쿼시 머지** — 중간 판단 흔적(낙관적 락 시도)이 main 히스토리에서 소실. PR이 남아 있으면 `pulls/{n}/commits`로 복원 가능하나, 브랜치·포크 삭제 시 유실. 팀 관행에 따라 복원율이 갈림.
3. **main 직접 푸시 (PR 없음)** — 신입 팀플에서 흔함. 시간축이 커밋 메시지 하나로 줄어듦. 이 경우 공간축(구조)이 받쳐야 함 — 두 축이 서로 보완하는 설계의 이유.
4. **몰아치기 커밋** — 마감 전 한 커밋에 전부. 사건 분리 불가, 기여율도 왜곡(커밋 수 ≠ 기여량). 사실만 표시하고 해석하지 않음("커밋 1개, 변경 5,000줄" — 판정 없이).

### API·기술 제약
5. **git blame 부재 (REST)** — 라인 단위 기여 귀속 불가. GraphQL blame 또는 클론 필요 — MVP는 커밋 단위 귀속으로 시작하고 정밀도는 확장 과제로.
6. **대형 커밋 diff 잘림** — REST 커밋 상세는 파일 수·패치 크기 제한으로 잘림. 큰 커밋은 "잘렸음"을 인지하고 처리(잘린 데이터로 서술 생성하면 왜곡).
7. **Rate limit** — 인증 5,000회/시. 레포 규모에 따라 분석 시간 설계 필요. 카드=영속 자산(추출 1회, 조회 무제한) 구조가 이 제약의 해법이기도.

### 신뢰·안전 제약
8. **히스토리는 조작 가능** — 리베이스·날짜 수정·타인 커밋 흉내 모두 가능. 카드는 "기록이 이렇다"까지만 말하고 진위는 면접으로 (일관성 ≠ 진정성). 시스템이 조작 탐지를 약속하지 않음.
9. **공동 기여자의 개인정보** — 팀 레포 커밋에는 동의하지 않은 팀원의 이름·이메일이 포함됨. 지원자 본인 커밋만 사용하고 타인 식별자는 수집 단계에서 제거·익명화 — 사후 필터링이 아니라 **수집 시점에** 설계.
10. **커밋 메시지·README·코드 = 인젝션 벡터** — 추출 파이프라인은 문서 내용을 지시가 아니라 데이터로 취급(격리). 탐지 시 부분 분석. LLM 서술 생성 단계가 가장 취약한 지점.
11. **LLM 서술의 환각** — "무엇을 했나"를 LLM이 쓰므로, 모든 서술 문장에 원본 링크가 붙어야 함(근거 없는 문장 생성 금지). 근거 병기가 UX 기능이자 환각 통제 장치.

## PoC와의 연결

- 판정 질문 갱신: "카드가 나오는가" → **"이상형 대비 어느 필드까지 채워지는가"**
- 카드 품질의 임시 정의: 채워진 필드 수 × 각 필드의 근거 링크 유무
- 측정 대상 추가: 부실 메시지 레포에서의 필드 충족률 / diff 기반 보강의 효과 / 인젝션 탐지 오탐률
- 코드 분석 존폐 논쟁과의 연결: 3번(PR 없는 레포)에서 공간축이 실제로 시간축을 받치는지가 실측 포인트
