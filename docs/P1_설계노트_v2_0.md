# P1 설계 노트 — 취준생 페르소나에서 도출한 것들

**버전:** v2.0 · 2026년 9월 1일
**원본 문서:** `대표 페르소나 P1 — 취준생·신입 개발자 v3.0`
**용도:** 기능명세서 작성 시 입력값. 페르소나 본문에서 분리해 별도 관리한다.

> 페르소나는 **사람**에 대한 문서이고, 이 노트는 **그 사람 때문에 우리가 지켜야 할 것**에 대한 문서다.
> 갱신 주기가 다르다 — 페르소나는 사용자 이해가 바뀔 때, 이 노트는 기능이 추가·변경될 때 고친다.

### v2.1 → v3.0 (2026-09-01) — 팀 논의 반영

| 구분 | 내용 |
| --- | --- |
| **삭제** | 프로필의 "커밋 메시지는 fix/update 수준" — **실제로는 커밋이 꽤 구체적이다** / 고통의 '평가 기준 불투명'·'탈락 후 원인 불명'·'CS 기초' / "링크드인 해봐라" |
| **추가** | 목표 4번 **"말이 아니라 자료로 나를 어필하고 싶다"** / 듣는 것에 "포트폴리오가 중요하다는데 뭘 어떻게 꾸며야 하지" / 필요한 것에 "남들은 어떻게 정리했는지 볼 수 있는 것" |
| **구조 변경 ①** | **B면(평가 기준 불투명)을 제거하고 고통 ②(말로 설명하지 못한다)로 교체.** 빼기로 한 두 항목이 곧 B면의 내용 전부였고, 새로 추가된 '어필'이 그 자리를 대신한다. POV-B·HMW-3도 '기준'에서 '전달'로 이동 |
| **구조 변경 ②** | **'가벼울 것' 요구를 제거.** 취업이 절박해 시간이 걸려도 한다는 판단. 대신 **"들인 시간이 그 기업 하나로 끝난다"**를 고통으로 재정의 |
| **표현 수정** | "부실한 커밋 부끄러움" → "정리해서 보여주지 않으면 대충 한 것처럼 보일까 봐" / POV "지속적으로" → **"재사용 가능한 형태로"** / HMW-4 "아무것도 하지 않는 동안에도" → **"프로젝트에 집중하는 동안에도"** |

**두 표현 수정의 이유**

- **재사용 가능한 형태로** — 기업은 필요할 때 한 번씩 열어본다. 상시 노출이 아니라 한 번 만들어 여러 곳에 다시 쓰는 자산이 목표다
- **프로젝트에 집중하는 동안에도** — 사용자는 GitHub에서 역량을 키우는 중이고 우리는 바로 그 활동을 분석한다. **프로젝트에 쓰는 시간이 곧 발견될 재료가 쌓이는 시간**이라는 구조를 표현이 담아야 한다

### 결정 근거 3건 (9/1)

1. 초기 사용자는 **인공지능사관학교 수료생으로 유지**
2. **JD 기반 자소서 작성 지원 기능을 포함** (확정 정의서 미결 8번 → 포함으로 결정)
3. 시간 관련 서술의 근거는 **"채용공고 탐색·자소서 작성·포트폴리오 정리·면접 준비를 병행하고 있어 프로젝트 경험을 기업별로 다시 정리할 시간이 부족하다"** *(v3.0에서 '가벼움 요구'가 아니라 '재사용 필요'의 근거로 성격이 바뀜)*

## 2. POV 검증 상태

| 기준 | 확인 | 근거 |
| --- | --- | --- |
| **실제성 (Real)** | ⚠ 부분 확인 | 인출 실패·시간 부족은 팀 내 관찰과 수료생 경험에 기반. **취준생 대상 직접 인터뷰는 아직 없음** — 8/27 인터뷰는 기업 측(면접관·HR)이었다 |
| **가치성 (Valuable)** | ✔ | 해결되면 자소서·면접·발견 세 국면에 동시에 작용 |
| **영감 (Inspiring)** | ✔ | "정리해준다"가 아니라 **"꺼내준다 → 고르게 한다 → 남는다"**라는 방향을 열어준다 |

> ⚠ **실제성 검증이 가장 약한 고리다.** 기업 측은 두 건의 현직자 인터뷰로 뒷받침되지만 구직자 측은 없다. 수료생 3~5명 대상 확인만으로도 POV의 신뢰도가 크게 올라간다.

**확인해야 할 질문 예시** *(KPI v3.0의 P1 Baseline 측정과 같은 자리에서 진행)*

- 자소서를 쓸 때 프로젝트 내용이 기억나지 않아 막힌 적이 있는가
- 커밋·PR을 다시 훑어 경험을 정리해본 적이 있는가. 없다면 왜 안 했는가
- **면접에서 준비한 만큼 설명하지 못했다고 느낀 적이 있는가** *(v3.0 고통 ② 검증)*
- 기업마다 포트폴리오를 다시 만드는가, 같은 것을 내는가 — 그 이유는
- 자기 GitHub를 기업이 볼 것이라고 생각하는가
- **다른 사람의 프로필·포트폴리오를 참고한 적이 있는가** *(v3.0에서 추가된 니즈 검증)*
- 기업이 먼저 연락해오는 서비스가 있다면 프로필을 관리할 의향이 있는가

## 3. HMW를 필터로 쓴 기능 점검

메인 HMW 기준으로 확정 정의서 7장의 기능을 분류했다. **판정이 아니라 논의 재료다.**

> **메인 HMW:** 우리가 어떻게 하면, 프로젝트 경험이 있는 취준생·신입 개발자가 반복적인 정리 부담 없이 자신의 개발 경험을 근거와 함께 보여주고, 기업에게 발견될 수 있게 할 수 있을까?

**하위 HMW (v3.0 기준)**

| # | 질문 |
| --- | --- |
| HMW-1 | 흩어진 커밋·PR에서 **본인이 잊어버린 개발 판단**을 꺼내줄 수 있을까 |
| HMW-2 | **평가하지 않으면서** 무엇을 보여줄지 고를 수 있게 도울 수 있을까 |
| HMW-3 | **말로 설명하지 않아도** 그 사람이 한 일이 전달되게 할 수 있을까 |
| HMW-4 | 구직자가 **프로젝트에 집중하는 동안에도** 기업에게 발견될 수 있을까 |
| HMW-5 | **보여주고 싶지 않은 부분은 감추면서도** 보여줄 만한 것은 드러내게 할 수 있을까 |

### 기능 점검표

| 기능 | 대응 | 판정 |
| --- | --- | --- |

**사용법:** 새 기능 아이디어가 나올 때마다 이 표에 한 줄을 추가하고 "메인 HMW에 답하는가"를 묻는다.

## 4. 결제 모델과 HMW의 충돌

확정 정의서 7.7의 과금 기준은 **"정보 노출 범위 차등"**이다. 무료 기업에게는 구직자의 정보가 최소한(직무 경력·기술 수준)만 보이고, 구독해야 프로젝트 경험·세부 기술·근무 방식·구직 상태가 보인다.

그런데 메인 HMW는 **"기업에게 발견될 수 있게 한다"**이다.

구직자 입장에서 보면 **내가 발견될 확률이 기업의 결제 여부에 따라 내려가는 구조**다. 이 사실을 알면 등록 동기가 약해진다.

**논의 방향 후보**

| 안 | 내용 | 영향 |
| --- | --- | --- |
| A | 검색·발견은 전면 무료, 접촉(DM 발송 수)에 과금 | 발견 확률 유지. 수익은 접촉 단계에서 발생 |
| B | 현행 유지 | 구직자 유입 동기 약화 위험 |
| C | 포트폴리오 프로젝트이므로 과금 구현만 하고 실제 제한은 두지 않음 | 8/27에 나왔던 "전 기능 구현" 방침과 일치 |

→ 확정 정의서 미결 6번(가격 정책) 논의 시 함께 올릴 것.

## 5. 페르소나가 만드는 설계 제약

기능 설계 시 반드시 통과해야 하는 조건이다. **v3.0에서 1·2·3번의 근거가 바뀌고 5번이 신설되었다.**

| # | 제약 | 근거 |
| --- | --- | --- |
| 1 | **첫 분석 결과에 "내가 몰랐던 것"이 있어야 한다** | 고통 ①. 온보딩 길이보다 **첫 결과의 밀도**가 이탈을 가른다 |
| 2 | **준비 모드의 결과가 발견 모드의 프로필에 자동 반영** | 들인 시간이 그 기업 하나로 끝나면 안 된다 |
| 3 | **보여주고 싶지 않은 부분을 감출 수 있어야 함** | "정리되지 않은 채 보이면 대충 한 것처럼 보일까 봐"라는 걱정 |
| 4 | **점수·등급을 보여주지 않음** | 원칙 1이자, 이 페르소나에게는 또 하나의 평가로 읽힘 |
| 5 | **카드는 설명 없이도 읽혀야 한다** | **신설.** 고통 ② — 본인이 옆에서 말로 보충할 수 없는 상태에서 전달되는 것이 카드의 조건 |

### v3.0에서 제약 1이 바뀐 이유

v2.1의 제약 1은 *"첫 카드 추출까지 최소 단계 — 온보딩이 길면 이탈"*이었고, 근거는 **'가벼움' 요구**였다. 팀 논의에서 그 요구가 걷혔다 — 취업이 절박한 사람은 시간이 걸려도 한다.

대신 남은 것은 **첫 결과가 기대에 못 미치면 돌아오지 않는다**는 것이다. 온보딩이 3분이든 10분이든, 카드에 *"어? 내가 이런 걸 했었네"*가 없으면 이후 국면이 없다. **제약의 대상이 '길이'에서 '밀도'로 옮겨갔다.**

> 이 제약은 KPI v3.0의 **경험 재발견** 지표와 같은 것을 가리킨다. 설계 제약과 성공 지표가 한 지점에서 만나는 드문 경우다.

### 제약 2가 리텐션의 전부다

발견되는 모드는 프로필이 상시 살아 있어야 성립한다. **준비하는 모드에서 한 작업이 자동으로 발견되는 모드의 자산이 되어야** 서비스가 지속된다. 별도의 "프로필 업데이트" 작업을 요구하는 순간 이 사람은 하지 않는다 — 시간이 없어서가 아니라, **그 작업에는 눈앞의 보상이 없기 때문**이다.

### 제약 5가 P3와 이어진다

카드가 설명 없이 읽혀야 한다는 요구는 P1 쪽 근거이지만, 도착점은 P3다. 기술 면접관은 지원자 옆에 두고 보지 않는다. **P1의 "말로 못 한다"와 P3의 "5분 안에 파악해야 한다"가 같은 카드 하나를 요구한다.**

## 6. 서비스가 해결하지 않는 것

기대치를 미리 정렬한다.

| 항목 | 사유 |
| --- | --- |
| GitHub 외 도구(노션·이슈 트래커 등)의 협업 기록 | 분석 대상은 Git · GitHub · GitLab 한정 |
| 구두 논의·회의에서의 판단 | 기록 자체가 없음 |
| 자소서 문장의 첨삭·평가 | 원칙 1 — 재료 제공까지만 |
| **탈락 원인의 진단** | 우리가 지원을 받지 않으므로 결과를 알 수 없다. **팀 논의에서 "탈락 후 원인은 우리가 어떻게 할 수 없다"로 명확히 정리됨** |
| 면접 대응 훈련·스피치 코칭 | 고통 ②는 **자료로 우회**해서 푼다. 말하기 자체를 개선하지 않는다 |

### JD 기반 자소서 지원의 경계선

포함하기로 결정했으나, v1.2에서 'AI 자소서 피드백'을 책임 문제로 제외한 결정과 경계가 아직 명확하지 않다. 기능명세 단계에서 다음 선을 명문화해야 한다.

| 포함 | 제외 |
| --- | --- |
| 공고 항목에 대응하는 **카드를 추천**한다 | 작성한 문장을 **평가**한다 |
| 카드의 근거를 **재료로 제시**한다 | 문장을 **대신 쓰거나 수정**한다 |
| 어떤 카드가 이 공고와 겹치는지 **보여준다** | 적합도를 **점수로 표시**한다 |

## 7. 미결 사항

| # | 항목 | 상태 |
| --- | --- | --- |
| 1 | POV 실제성 검증 | 구직자 측 인터뷰 미실시 — 수료생 3~5명 필요. **KPI v3.0의 P1 Baseline 측정과 겸해 진행** |
| 2 | 유입 경로 | 상정한 경로가 수료 기수 네트워크뿐. 확정 정의서의 콜드스타트 전략("팔로워 많은 사용자 노출")과 연결 안 됨 |
| 3 | 팔로우의 동기 | **v3.0에서 부분 해소** — "남들은 어떻게 정리했는지 본다"가 한 가지 답이 되었다. 다만 등급별 공개 범위(확정 정의서 미결 3번)는 여전히 미정 |
| 4 | 결제 모델과 HMW 충돌 | 4장 참조. 확정 정의서 미결 6번과 함께 논의 |
| 5 | JD 기반 자소서 지원 경계 | 6장 표를 기능명세에 반영할지 확정 |
| 6 | **고통 ②의 측정 방법** | **신설.** "말이 아니라 자료로 전달된다"를 어떻게 재는가. 현재는 KPI v3.0의 P1 정성 평가("카드가 내가 한 일을 설명하는 데 도움이 되었는가")가 가장 가깝다 |
