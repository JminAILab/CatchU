## 1. 이 문서의 범위

취준생이 CatchU에서 하는 일의 화면과 흐름을 정의한다.

**다루지 않는 것**

- 기업이 우리 플랫폼 안에서 쓰는 화면 (별도 명세)
- 관리자 화면 (별도 명세)
- 카드 추출 알고리즘 내부 — `카드생성논리_상세설명.md`가 정본이다. 이 문서는
  그 결과가 화면에서 어떻게 보이고 사용자가 무엇을 제어하는지만 다룬다.

**경계면 하나를 여기서 다룬다**: 지원자가 발행한 링크를 받아 카드를 보는 사람의 화면
(VIEW-01·02). 그 사람은 우리 회원이 아니고 우리 플랫폼 밖 회사에 있다. 지원자가
통제하는 범위 안이므로 취준생 측 명세에 둔다.

## 2. 사용자

**주 사용자**: 개발 직군 취업을 준비하는 사람. 대표 페르소나는 `페르소나_취준생_완성본.md`.

**열람자**: 지원자가 발행한 링크로 카드를 보는 사람(면접관·채용담당자).
회원가입하지 않고, 우리 플랫폼 밖의 공고로 채용을 진행한다.

**주의**: 서비스 전체로 보면 1차 핵심 고객은 면접관이다. 취준생 측 화면은 그 면접관이
읽을 재료를 지원자가 직접 만들고 통제하는 자리다. 취준생을 위한 별개 제품이 아니다.

## 3. 서비스가 하는 일

> 내 GitHub 기록에서 **판단의 흔적**을 뽑아내고, 그중 무엇을 누구에게 보일지 내가 정한다.
> 만든 링크는 **어느 회사에나** 보낼 수 있다.

지원자가 얻는 것은 네 가지다.

1. **인출 가능한 형태의 기억** — 6개월 전에 무슨 판단을 했는지 면접장에서 떠올리지 못하는
   문제를, 커밋·PR로 복원된 사건 목록으로 해소한다.
2. **주장과 흔적의 대조** — 내가 하려는 주장에 실제 기록이 붙는지, 붙는 기록이 있는데
   내가 주장하지 않고 있는지를 본인이 먼저 발견한다(§7.5.3 4분면).
3. **밖에서 쓸 수 있는 링크** — 원티드·사람인·이메일 어디로 지원하든, 링크 하나를 붙이면
   상대가 근거를 직접 열어볼 수 있다. **상대가 우리 서비스를 쓸 필요가 없다.**
4. **통제권** — 무엇이 공개되고 어느 링크에 무엇이 담기는지, 언제 열렸는지를 본인이 안다.

**하지 않는 것**: 점수·등급·합격 확률·적합도. 자소서 대필. AI 생성 판별. 사유는 §4.

## 4. 설계 원칙

이 원칙들은 화면을 판정하는 자다. 기능 제안이 올라오면 여기에 먼저 대본다.

### 4.1 시스템은 사람을 판정하지 않는다

점수·등급·순위·적합도·합격 예측을 만들지 않는다. 시스템이 내놓는 것은 **판단의 재료**이고
판단은 읽는 사람이 한다.

판별 기준은 **문장의 주어**다.
- "이 사람은 백엔드 적합도 82%다" → 시스템이 주어. **금지.**
- "당신이 요구한 '동시성 처리'에 대응하는 기록이 이것이다" → 기준을 제시한 사람이 주어. **허용.**

정렬 가능한 수치는 곧 순위이므로, 적합도로 목록을 정렬하는 기능은 이 원칙 위반이다.

**검색에도 그대로 적용된다.** 자연어로 물을 수 있게 하는 것과 자연어로 답하는 것은 다르다.
질문은 자유롭게 받되 **답변은 카드 목록과 근거 링크로만** 낸다(§7.6.4).

이 원칙이 중요한 이유: 우리가 점수를 만드는 순간 우리는 GitRoll과 같은 제품이 되고,
"근거를 직접 열어 보여준다"는 우리의 유일한 차별점이 사라진다.

### 4.2 기록이 얇은 것을 역량이 부족한 것으로 렌더링하지 않는다

실측상 사건의 62~87%가 커밋 1개짜리다. 기록이 얇은 것이 다수이지 예외가 아니다.

빈칸은 사실로만 표시한다. `근거 없음`은 되고 `부족함`은 안 된다. 진행률 바, 완성도 %,
경고색, 느낌표 아이콘처럼 **결핍을 시각적으로 강조하는 장치는 카드·역량 영역에 쓰지 않는다.**
빨간색 0/5 게이지는 문장으로 판정하지 않았을 뿐 판정이다.

검색 결과 0건도 마찬가지다. `해당하는 카드가 없습니다`는 되고 `경험이 없습니다`는 안 된다.

이 미끄러짐은 이 프로젝트에서 반복해서 재발한 논점이다. 화면에서 발견하면 지적한다.

### 4.3 카드의 두 축을 섞지 않는다

**가시성**과 **큐레이션**은 다른 층위다. 섞으면 삭제·열람 투명성의 단위가 무너진다.

| | 단위 | 뜻 |
|---|---|---|
| **가시성** | 카드 단위 · **전역 1회** | 숨긴 카드는 이 서비스 어디에도 없는 것으로 취급 |
| **큐레이션** | **세트별로 다름** | 공개 카드 중 골라 이번 링크에 담는다 |

대표 카드는 포트폴리오 성격이라 보내는 곳마다 다른 게 정상이다. 반대로 가시성을
회사별로 두면 "내 카드가 지금 누구에게 보이는가"에 답할 수 없게 된다.

→ **회사별 공개 범위 설정은 만들지 않는다.**

### 4.4 큐레이션의 정성도를 열람자에게 노출하지 않는다

기본값을 그대로 썼는지, 몇 번 고쳤는지, 발행까지 며칠 걸렸는지 — 열람 화면에 내보내지
않는다. 노출하는 순간 "세트 관리를 성실히 했는가"라는 새 스펙이 생기고, 학점·어학점수
자리에 커밋 로그를 갈아끼운 것에 지나지 않게 된다.

### 4.5 카드는 주장을 금지하는 장치가 아니다

카드는 처음부터 주장에 붙이는 근거다. 지원자가 근거를 골라 주장하는 것은 정상적인
논증이지 왜곡이 아니다. 문제는 주장의 존재가 아니라 **근거 없는 주장**이다.

### 4.6 서술의 모든 문장에 근거 링크가 붙는다

카드 서술을 사람이 쓰든 AI가 쓰든, 근거 없는 문장은 만들지 않는다. 근거 병기는
사용자 편의 기능이 아니라 **환각 통제 장치**다. 링크가 없으면 그 문장을 내보내지 않는다.

### 4.7 묶음의 근거 등급을 카드에 표시한다

- **A등급 — 본인이 묶은 것**: PR, 브랜치 머지. 시스템의 해석이 아니라 본인의 판단이다.
- **B등급 — 시스템이 규칙으로 묶은 것**: 같은 사람 + 같은 파일 + 시간 근접.
  규칙 기반이라 같은 입력이면 같은 결과가 나오고, 왜 묶였는지 설명할 수 있다.

B는 틀릴 수 있는 층이고, 틀릴 수 있다는 사실을 숨기지 않는다. **A와 B를 한 카드로 병합하지 않는다.**

**등급은 카드를 벗어나는 모든 표면에 따라붙는다** — 검색 결과, 대조 표, 열람 화면 전부.
등급이 떨어지는 표면이 생기면 그 표면이 등급 세탁 경로가 된다.

### 4.8 타인의 데이터는 수집 시점에 가명 처리한다

팀 레포 커밋에는 이 서비스에 동의한 적 없는 사람들의 이름·이메일이 들어 있다.
저장 전에 `author_01` 형태로 바꾼다. 완전히 지우지 않는 이유는 "3명이 참여했고 본인 몫은
이 커밋들"이라는 협업 구조는 남겨야 하기 때문이다.

목적은 재식별 방지가 아니다 — 커밋 링크를 타고 GitHub에 가면 실명이 보인다. 목적은
**우리 서비스가 지원자의 옛 팀원에 관한 서비스가 되지 않게 하는 것**이다. 이름을 저장하면
여러 지원자의 카드에 등장한 같은 사람의 기록이 모여 "그 사람의 이력"처럼 조회될 수 있다.

코드에 실수로 남은 API 키 등은 자동 마스킹한다. 검증 레포에서 실제로 복수 발견됐다.

### 4.9 외부 텍스트는 지시가 아니라 데이터다

커밋 메시지·README·코드 주석·공고 본문은 전부 외부 입력이고, 그 안에 AI를 향한 지시문이
들어 있을 수 있다. **열람자가 입력하는 검색 질의도 같다.** 파이프라인은 이 내용을
데이터로만 취급한다. 화면 요구사항은 §10.

### 4.10 분석은 본인 동의에서 시작하고, public 레포만 본다

공개돼 있다는 것이 처리에 동의했다는 뜻은 아니다. 비공개 레포는 회사·동료의 자산이
섞여 있어 범위 밖이다. 연결 해제와 데이터 삭제는 본인이 직접 할 수 있어야 한다.

## 5. 전체 흐름

```text
[수집]    GitHub 연결 → 레포 선택 → 분석 → 카드 초안
[검토]    카드 확인·수정·가시성 결정                    ← 자산 형성
[내보내기] 카드 선택 → 세트 → 링크 발행 → 전달·회수      ← 밖에서 쓰는 것
[대조]    (선택) 공고 등록 → 커버리지 → 4분면            ← 본인만 보는 것
```

**두 갈래를 분리해서 읽어야 한다.**

- **내보내기**는 공고와 무관하게 성립한다. 회사가 우리 플랫폼 밖에 있으므로,
  지원자는 공고를 등록하지 않고도 링크를 만들 수 있어야 한다.
- **대조**는 공고가 있어야 성립하고, **본인만 보는 준비 도구**다. 그 결과를
  기업에 보내는 기능은 없다.

세트에 공고를 연결하면 대조 결과를 참고해 카드를 고를 수 있다. 연결하지 않아도 세트는
만들어진다. **공고는 세트의 필수 성분이 아니라 선택 성분이다.**

## 7. 화면 명세

### 7.1 메인 · 회원

#### MAIN-01 비회원 메인

**목적**: 이 서비스가 무엇을 하는지 설명 없이 전달한다.

**구성**

- 서비스 명제 한 줄
- **실물 카드 예시 1장** `★A5` — 설명 문단보다 카드 실물이 빠르다.
- 3단계 요약: GitHub 연결 → 카드 생성 → **링크 하나로 어디든 전달**
- CTA: `GitHub로 시작하기` / `로그인`

**넣지 않는 것**: 공고 둘러보기. 우리는 공고 포털이 아니다.

#### MAIN-02 로그인 홈

- 다음 할 일 1개 — 진행 단계에 따라 하나만. 목록이 아니다.
- 최근 생성된 카드 3장
- 발행 중인 링크 — 만료 임박, 최근 열람 여부

**금지**: 프로필 완성도 %, 체크리스트 진행률. §4.2에 걸린다.
"아직 안 한 것"을 세는 UI가 곧 결핍 게이지다.

#### MEMBER-01 회원가입
- **GitHub OAuth를 기본 경로로 둔다** `★A2` — 어차피 연결이 필수라 가입과 연결을 한 번에 끝낸다
- 이메일 가입은 보조 경로
- 예외: 중복 이메일 / 형식 오류 / 비밀번호 조건 / 인증 만료 / OAuth 거부·실패

#### MEMBER-02 로그인
이메일 · GitHub · 상태 유지 · 비밀번호 재설정.
예외: 미가입 / 불일치 / OAuth 실패 / 네트워크 / 제한 계정.

#### MEMBER-03 로그아웃
저장되지 않은 편집이 있으면 먼저 안내.

#### MEMBER-04 프로필

**최소 항목만**: 이름 또는 닉네임 / 연락처(선택) / 한 줄 소개 / GitHub 계정 / 외부 링크

**넣지 않는 것**: 학력, 자격증, 어학, 경력 연차, 기술 스택 자가 입력.
사유 — 우리가 대체하려는 스펙 나열 그 자체다. 기술 스택은 자가 신고가 아니라 카드에서
나와야 한다. 자가 신고 스택을 두면 근거 없는 주장을 우리가 화면으로 권하는 셈이다.

#### MEMBER-05 비밀번호 재설정
가입 이메일 → 인증 → 재설정.

#### MEMBER-06 회원 탈퇴

**탈퇴 전 고지 필수**

- 삭제되는 것: 카드 전체, 분석 데이터, 세트
- **발행된 링크 전부 즉시 무효화** — 링크를 받은 쪽에 미리 알릴 수 없다는 점 명시.
  진행 중인 전형이 있으면 상대가 갑자기 못 열게 된다
- GitHub 연결 해제 / 복구 불가

### 7.2 온보딩

#### ONB-01 온보딩

**3단계까지만.**

```text
안내 → GitHub 연결 → 레포 선택 → 분석 시작
```

희망 직무·지역·신입경력 구분은 받지 않는다. 우리는 공고를 추천하지 않으므로 희망 조건을
쓸 데가 없다. 쓰지도 않을 정보를 첫 화면에서 요구하면 이탈만 만든다.

`나중에 하기`는 두되, GitHub 연결 없이는 할 일이 없다는 점을 명시한다.

### 7.3 GitHub 연결과 분석

#### REPO-01 연결

```text
GitHub 연결 → 권한 안내 → 인증 → 레포 목록 → 선택 → 분석 시작
```

**권한 안내에 명시할 것**
- 읽는 것: public 레포의 커밋·PR·이슈·코드 변경 내용
- 안 읽는 것: private 레포
- 함께 작업한 사람의 이름·이메일은 저장 전 가명 처리
- 언제든 연결 해제·데이터 삭제 가능

#### REPO-02 레포 선택

**표시**: 레포명 / 최근 커밋일 / 본인 커밋 수 / 주 언어 / 이미 분석됨 여부

**표시하지 않는 것**: 스타 수, 추천 뱃지, "분석하기 좋은 레포" 라벨.
어느 레포가 좋은지 판정하지 않는다.

**제약**: 최초 분석은 레포 3개까지 `★A6`. GitHub API 시간당 5,000회 제한 아래에서
분석 시간을 예측 가능하게 유지하기 위함이며, 실측 후 조정한다.

#### REPO-03 분석 진행·결과

**상태**: 대기 / 수집 중 / 사건 묶는 중 / 카드 작성 중 / 완료 / 실패 / 권한 만료

분석 시간이 수 분 단위이므로 **이탈 가능해야 한다** — 완료 시 알림, 재방문 시 이어보기.

**완료 화면**
```text
레포 3개에서 사건 47건을 찾았습니다.
  본인이 묶은 단위(PR·머지)  12건
  시스템이 규칙으로 묶은 것    35건

카드 초안 47장이 만들어졌습니다. 확인하고 고쳐주세요.
```

**필수 고지**
> 자동 분석 결과이며 부정확할 수 있습니다. 공유하기 전에 내용을 확인해 주세요.

**실패 시**: 기존 카드는 절대 삭제·변경하지 않는다. 부분 실패면 어느 레포가 실패했는지 명시.

**재분석**: 카드는 생성 시점 기준으로 고정한다. 레포에 커밋이 쌓이면 묶음 경계가 달라질 수
있으므로, 재분석은 본인이 명시적으로 실행할 때만 하고 **기존 카드가 달라질 수 있음을
먼저 고지한다.** 수정한 카드가 덮어써지는지는 `★A7`.

### 7.4 카드

#### CARD-01 카드 목록

**표시**: 제목 / 레포 / 기간 / 근거 등급(A·B) / 서술 형태(서사·스냅샷) / 가시성 상태

**필터**: 레포 / 등급 / 형태 / 가시성 / 유형
**정렬**: 최신순 / 레포별. **품질순·중요도순은 없다** — 순위를 만드는 정렬이다.

**규모 문제**: 레포 3개에서 47장이 나왔다. 실제로는 더 나올 수 있다. 이 화면 설계는
카드 개수 실측에 의존하며 대량일 때의 목록 형태는 미해결이다 `★A8`.
본인 화면에는 키워드 검색을 둔다(열람자 검색은 §7.6.4와 다른 물건이다).

#### CARD-02 카드 상세

**필드 8종** (`카드생성논리_상세설명.md` 정본)

| 필드 | 내용 |
|---|---|
| 무엇을 했나 | 사건 요약 |
| 판단의 흐름 | 시간순 전개, 각 항목에 커밋 링크 |
| 어디에 있나 | 코드 위치 |
| 본인 기여 | 이 사건에서 본인 커밋 수 / 전체 |
| 사용 기술 | |
| 유형 | 의사결정 / 문제해결 / 협업 / 완성도 |
| 연결 | 등록한 공고와의 대응 (없으면 빈칸) |
| **기록에 없는 것** | 흔적은 있는데 이유가 안 남은 지점 |

**함께 표시**
- **근거 등급 배지**: `본인이 묶은 단위(PR #23)` 또는
  `시스템 추정 — 적용 규칙: 동일 저자 + order/ 경로 + 6시간 이내`
  B등급은 적용 규칙을 문장으로 보여준다. "왜 이렇게 묶였나"에 답할 수 있어야 한다.
- 모든 서술 문장에 근거 링크

**`기록에 없는 것` 필드의 문안 규칙** — §4.2에 걸리기 가장 쉬운 자리다.

| 쓴다 | 안 쓴다 |
|---|---|
| 락 전환의 판단 근거가 커밋·PR에 남아 있지 않습니다 | 판단 근거가 부족합니다 |
| 면접에서 물어볼 수 있는 지점입니다 | 이 부분을 보완하세요 |

빈 곳은 결함이 아니라 **면접 질문거리**로 제시한다. 기록에 답이 없는 질문이 좋은 면접
질문이라는 것이 이 필드의 존재 이유다.

#### CARD-03 카드 편집

**할 수 있는 것**
- 모든 필드 직접 수정 / 근거 링크 추가·교체·삭제
- 사건 묶음 조정 (커밋을 카드에서 빼거나 옮기기)
- **직접 진술 추가** `★A9` — 기록에 없는 배경을 본인이 쓸 수 있다.
  단 기록 기반 서술과 **시각적으로 분리**하고 `본인 진술` 표시를 붙인다.
  기억으로 보충한 말과 기록이 뒷받침하는 말을 섞지 않는다.

**할 수 없는 것**
- 근거 등급 변경 (B를 A로 올릴 수 없다. 등급은 사실이지 설정이 아니다)
- 커밋 링크가 가리키는 대상 위조

#### CARD-04 가시성 (전역 1회)

**상태 2가지뿐**: `공개` / `숨김`

숨긴 카드는 어떤 세트에도 담기지 않고, 어떤 링크에도 나타나지 않고, 열람자 검색에
걸리지 않고, 대조 계산에도 들어가지 않는다.

**회사별·세트별 가시성은 없다.** §4.3.

**숨김이 신호가 되는 문제** `★A10`

카드를 숨길 수 있다는 사실 자체가 열람자에게 "숨긴 게 있나?"라는 추론을 유발할 수 있고,
극단적으로는 "숨김이 많은 지원자"라는 판정이 가능해진다.

두 방향이 있다.
- **(가) 숨김의 존재·개수를 열람 화면에 일절 노출하지 않는다** — 추론의 근거를 제거
- (나) 전량 공개를 기본으로 하고 숨김을 예외로 둔다 — 숨김의 의미를 희석

**결정 경로**: 면접관 인터뷰에서 확인하거나 재민이 판단한다. 둘 중 어느 쪽이든
**화면 확정 전에 닫는다.** 그 전까지 화면은 (가)를 전제로 그린다 — (가)가 (나)보다
되돌리기 쉽다. (나)로 가면 기본값만 바꾸면 되지만, (나)로 그려놓고 (가)로 가면
열람 화면에서 노출 지점을 다시 찾아 제거해야 한다.

### 7.5 공고와 대조 (선택 경로 · 본인만 봄)

> 이 절 전체가 **선택**이다. 공고 없이도 세트 발행(§7.6)은 성립한다.

#### JOB-01 공고 확보 — 2층 구조

공고는 두 층으로 나뉘며 용도가 다르다.

| | 층1 · 표본 공고 | 층2 · 사용자 등록 |
|---|---|---|
| 누가 만드나 | 팀이 미리 준비, 고정 | 사용자가 직접 |
| 무엇에 쓰나 | 시연 / 체험 / 측정 기준 | 실사용 |
| 개수 | 소수(직무별 몇 건) | 사용자별 무제한 |
| 변하나 | **버전 고정** | 자유 |

**층1 — 표본 공고 세트**

실제 채용 공고를 수집해 **회사명·담당자·연락처 등 식별 정보만 치환**하고 요구사항
텍스트는 원문 그대로 유지한다. 처음부터 지어내지 않는다.

*왜 지어내면 안 되나*: 우리가 공고를 쓰면 우리 카드에 잘 대응하는 요구사항을 무의식적으로
쓰게 된다. 그러면 대조 기능 시연이 "우리가 낸 문제를 우리가 푸는" 모양이 되고, 발표
심사위원이 가장 먼저 찌를 지점이다. 커버리지 정확도 측정의 기준선도 같이 오염된다.

*절차 규칙*: **표본 세트는 시연용 카드보다 먼저 고정한다.** 카드를 보고 공고를 고르면
같은 오염이 우회로로 되돌아온다.

*사용자 노출 여부* `★A15`: 표본을 "예시 공고로 먼저 해보기"로 열어주면 공고 등록 마찰이
줄고 첫 경험이 빨라진다. 반대로 우리가 고른 공고가 사용자의 기준을 물들일 수 있다.
현재 안은 **열어주되 표본임을 명시**.

**층2 — 사용자 직접 등록**

```text
공고 등록 → 원문 링크 + 본문 붙여넣기 → 요구사항 항목 추출 → 사용자 확인·수정 → 저장
```

- 회사명·직무명·마감일은 사용자 입력
- 본문에서 요구사항 항목(필수·우대)을 항목 단위로 쪼개 제시하고, 사용자가 확인·수정
- 추출 결과를 그대로 쓰지 않는다 — 확인 단계가 필수다

*왜 크롤링이 아닌가*: 공고 수집 크롤링은 동의 기반 수집 원칙 및 공고 사이트 약관과
충돌한다. 제휴·API는 20주 안에 확보 가능성이 없다. **이 경로가 없으면 이 서비스는
데모 전용 제품이 된다** — 층2는 사용량이 적더라도 화면이 있어야 한다.

#### JOB-02 공고 목록
등록한 공고 + 표본 공고 / 마감일 / 대조 상태 / 연결된 세트.
검색·필터·추천 없음. 본인이 등록한 것만 있으므로 목록이 짧다.

#### JOB-03 대조 (커버리지)

**공고 요구사항 항목 × 내 카드**의 대응 관계.

```text
A사 · 프론트엔드 신입

요구사항                        대응하는 카드
─────────────────────────────────────────
React 기반 UI 개발              카드 3장  [보기]
상태 관리 경험                  카드 1장  [보기]
테스트 코드 작성                기록 없음
CI/CD 구성 경험                 기록 없음
```

**표기 규칙**
- `기록 없음`만 쓴다. `부족`·`미달`·`0%`·빨간색 게이지 없음. §4.2
- 커버리지 비율(7/10 = 70%)을 숫자로 내지 않는다. 비율은 점수이고 정렬 가능하다.
- 각 연결마다 `왜 이 카드인가`를 열 수 있어야 하고, 사용자가 연결을 끊거나 추가할 수 있다.
  **과잉 연결**(근거 아닌 것을 근거라고 붙이는 것)이 이 기능에서 가장 위험한 실패다.
- 결과에 근거 등급이 함께 표시된다(§4.7)

#### JOB-04 4분면 — 주장과 흔적의 대조

자소서·포트폴리오 텍스트를 붙여넣으면 **주장**과 **흔적**을 교차시켜 보여준다.

| | 흔적 있음 | 흔적 없음 |
|---|---|---|
| **주장함** | 근거가 붙어 있다 — 면접에서 바로 꺼낼 수 있는 것 | 기록에 없는 주장 — 면접에서 파고들 자리 |
| **주장 안 함** | ★ **말 안 하고 있는 것** | (표시할 것 없음) |

**★ 칸이 이 기능의 존재 이유다.** 카드가 47장인데 자소서에 3개만 썼다면, 나머지 중
이 공고에 대응하는 것이 있는데 본인이 떠올리지 못해 안 쓴 것이다. 우리 취준생 페르소나의
핵심 고통이 정확히 **인출 실패**다.

**제약**
- **본인만 본다.** 열람자 화면에 4분면은 없고, 결과를 기업에 보내는 기능도 없다.
- 붙여넣은 자소서는 **분석 대상이 아니라 색인**으로만 쓴다. 자소서를 평가하지 않는다.
- 우상단 칸(기록에 없는 주장)에 `과장`·`허위` 같은 라벨을 붙이지 않는다.
  기록에 안 남는 일은 흔하다. **면접 질문거리로 제시한다.**
- 자소서 텍스트 보관 여부·기간은 `★A11`.

**여기서 자소서를 고쳐주지 않는다.** 사유는 §13.

### 7.6 세트와 링크 — 밖에서 쓰는 것

> 지원자가 실제로 하는 일은 "이번에 보낼 카드를 골라 링크를 만들어 전달하는 것"이다.
> 우리 안에서 지원을 접수하지 않으므로 이것이 유일한 내보내기 경로다.

#### SET-01 세트 구성

```text
카드 선택 → (선택) 공고 연결 → 소개 문구 → 미리보기 → 링크 발행
```

**공고 연결이 두 번째이고 선택이라는 점이 중요하다.** 회사는 우리 플랫폼 밖에 있고,
지원자는 대개 원티드·사람인·이메일로 지원하면서 링크만 붙인다. 공고를 우리 DB에 넣어야만
링크를 만들 수 있다면 그 마찰 때문에 아무도 안 쓴다.

- 공개 카드 중에서만 고른다 (숨긴 카드는 목록에 없다)
- 공고를 연결하면 대조 결과가 있는 카드를 **먼저 보여주되 자동 선택하지 않는다.**
  제안의 주어는 시스템이고 확정의 주어는 지원자다.
- 세트마다 카드 구성이 다른 것이 정상이다

#### SET-02 링크 발행

| 항목 | 기본값 |
|---|---|
| 만료일 | 30일 `★A12` |
| 열람 비밀번호 | **필수** `★A3` |
| 다운로드 허용 | 끔 |
| **자연어 검색 허용** | 켬 `★A13` |
| 메모(누구에게 보냈는지) | — |

**비밀번호가 필수인 이유**: 링크만으로 열리면 URL 유출 하나로 연락처 포함 개인 자료
전체가 노출된다. 최소 수집·통제 원칙과 정면으로 어긋난다.

#### SET-03 발행 링크 관리

- 발행한 링크 목록 / 만료 상태 / **열람 기록(언제 열렸는가)**
- 즉시 중단 / 만료일 변경 / 재발행

**열람 기록은 지원자에게 보인다.** 내 자료가 언제 열렸는지 아는 것은 통제권의 일부다.

**열람자의 검색 질의를 지원자에게 보여줄 것인가** `★A14` — 미결.
보이면 투명성이 올라가지만 열람자가 위축되어 검색을 안 쓰게 될 수 있다. 안 보이면
"무엇이 조회됐는지"에 지원자가 답할 수 없다. 중간안으로 "검색 사용 횟수만" 표시가 있다.

#### VIEW-01 열람 화면 (링크 수신자)

로그인 없이 열린다. 우리 회원이 아니어도 된다.

**보이는 것**: 지원자 소개 / 담긴 카드 / 각 카드의 근거 링크 / 근거 등급 /
(연결됐다면) 어느 공고를 기준으로 구성된 세트인지

**보이지 않는 것**
- 숨긴 카드의 존재·개수 (`★A10` 확정 전까지 (가)안 전제)
- 세트에 담지 않은 공개 카드
- 4분면 결과, 자소서 텍스트
- 카드를 몇 번 고쳤는지, 기본값을 썼는지, 발행까지 며칠 걸렸는지 (§4.4)
- 점수·등급·요약 판정

**할 수 있는 것**: 카드 열람 / 근거 링크 열기 / 자연어 검색(VIEW-02) / (허용 시) 다운로드

#### VIEW-02 세트 내 자연어 검색

**왜 필요한가**: 세트에 카드가 여러 장이면 열람자가 전부 읽지 않는다. 면접관의 첫 제약이
"시간이 없다"이므로, 원하는 것을 바로 꺼내는 경로가 없으면 링크는 열리고 닫힌다.
CARD-01의 규모 문제(`★A8`)에 대한 열람자 측 답이기도 하다.

**동작**
```text
질의: "동시성이나 락 관련 작업 있어요?"

→ 해당하는 카드 2장

  ① 주문 재고 차감 동시성 처리          [본인이 묶은 단위 · PR #23]
     낙관적 락 → 비관적 락 전환         커밋 3건 보기
  ② 결제 중복 요청 방지                  [시스템 추정 · 규칙: 동일 저자 + payment/ + 4시간]
                                        커밋 1건 보기
```

**답변 형식 제약 — 이게 핵심 통제다**

| 낸다 | 안 낸다 |
|---|---|
| 해당 카드 목록 + 근거 링크 | 산문 요약, 총평 |
| 카드의 원문 필드 | 새로 생성한 서술 |
| 근거 등급 배지 | 관련도 점수, 순위 |
| `해당하는 카드가 없습니다` | `해당 경험이 없습니다` |

질문은 무엇이든 받되 **답변은 카드와 링크로만 낸다.** "이 사람 우리 팀에 맞나요?"라고
물어도 시스템은 판정 문장을 만들지 않고, 관련 있는 카드를 내놓거나 없다고 말한다.
질의를 검열하지 않는 이유는 그것이 의도 판정이 되기 때문이다 — 우리는 의도를 판정하지 않는다.
통제는 입력이 아니라 **출력 형식**에서 한다.

**범위 제약**
- 검색 대상 = **이 세트에 담긴 카드만.** 다른 세트, 미포함 공개 카드, 숨긴 카드는 대상 밖
- 다른 지원자의 카드에 접근 불가
- 세트 밖 카드가 검색에 걸리면 큐레이션 층위가 무너진다(§4.3)

**보안**: 열람자 질의는 외부 입력이다. 지시가 아니라 데이터로 취급한다(§4.9, §10).

**비용**: 세트 카드 수 × 질의 수가 입력 토큰 규모를 결정한다. 세트당 카드 상한이
필요할 수 있다 `★A16`.

**지원자 통제**: SET-02에서 검색 허용을 끌 수 있다. 끄면 카드 목록만 보인다.

## 8. AI를 쓰는 곳과 쓰지 않는 곳

**쓴다**

| 자리 | 하는 일 | 제약 |
|---|---|---|
| 카드 서술 생성 | 사건 요약 문장 작성 | 모든 문장에 근거 링크 강제. 링크 없는 문장은 폐기 |
| 공고 요구사항 항목화 | 본문을 항목 단위로 분해 | 사용자 확인 필수 |
| 카드-요구사항 대응 제안 | 후보 연결 제시 | 각 연결에 근거 표시, 사용자가 끊고 붙임 |
| 4분면 주장 추출 | 자소서 문단에서 주장 단위 분리 | 색인 용도. 평가하지 않음 |
| **세트 내 검색** | 질의 → 해당 카드 선별 | **출력은 카드 목록 + 링크만.** 서술 생성 없음 |

**쓰지 않는다**
- 점수·등급·적합도·합격 확률 (§4.1)
- 자소서·이력서 작성·첨삭·요약 (§13)
- AI 생성 여부 판별 — 커밋도 코드도 AI로 만들 수 있으므로 진정성은 증명 불가다.
  일관성과 구체성의 기록까지만 제공하고 진정성 검증은 면접으로 넘긴다.
- 사건 묶기 — 규칙 기반이다. 현재 파이프라인 전 구간에 AI 호출·비결정 요소 0건이며,
  같은 입력이면 같은 결과가 나오는 성질을 유지한다.

**공통**: AI 결과는 전부 수정 가능 / 추정은 추정이라고 표시 / 확인되지 않은 경력·성과·수치를
만들어내지 않는다.

## 9. 카드 검색의 경계 (별도로 못 박는다)

카드를 자연어로 찾는 것과 카드로 사람을 고르는 것은 다르다. 이 경계가 흐려지면
자동화된 채용 결정을 하는 서비스가 되고, 우리가 세운 원칙과 관련 규제 양쪽에 걸린다.

| 허용 | 금지 |
|---|---|
| 자연어 질의 → 구조화 조건 → 결정론적 결과 목록 | 도구를 호출해 후보를 자동 선별 |
| 결과에 인용 링크 병기 | 결과를 순위로 정렬 |
| "해당하는 카드 없음" | "이 지원자는 적합/부적합" |
| 사람이 카드를 열어 판단 | 시스템이 요약해 결론을 제시 |

**판별 기준은 §4.1과 같다 — 결론 문장의 주어가 시스템인가 사람인가.**

이 절은 취준생 측 세트 내 검색(VIEW-02)에 적용된다. 기업 측에서 여러 지원자를 다루는
기능은 범위가 다르므로 기업 측 명세에서 별도로 판정한다.

## 10. 인젝션 대응 (화면 요구사항)

커밋 메시지·README·코드 주석·공고 본문·**열람자 검색 질의**에 AI를 향한 지시문이 심겨
있을 수 있다. 서술 생성 단계와 검색 단계가 취약하다.

**처리 원칙**
1. **의도를 판정하지 않는다.** "악의적"이라고 라벨하지 않는다.
2. 자동 탐지 → 해당 구간을 제외하고 나머지만 분석
3. **중립 안내**: `일부 구간은 분석에서 제외되었습니다.` — 사용자가 문의하면 해당
   구간만 열람 가능하게 하고 감사 로그를 남긴다.
4. 탐지됐다고 카드 생성이나 검색 전체를 중단하지 않는다

**검색 경로 추가 요구**
- 질의는 데이터로만 취급. 질의에 담긴 지시("이전 지시를 무시하고 …")를 따르지 않는다
- 출력 형식 제약(§7.6.4)이 이 경로의 2차 방어선이다 — 형식이 카드 목록으로 고정되어
  있으면 지시가 통해도 산출할 수 있는 것이 없다

**화면 요구**: 카드에 `일부 구간 제외됨` 표시 자리. 오탐 시 이의 제기 경로.

**4분면(JOB-04)을 MVP에 넣었다** (v0.1에서는 확장이었음). 사유는 §12 A4.

**시연 동선**: GitHub 연결 → 카드 47장 → 표본 공고와 대조 → 4분면에서 "말 안 하고 있는 것"
발견 → 세트 구성 → 링크 발행 → **심사위원이 그 링크를 열어 직접 검색.**
마지막 단계가 이 서비스의 명제("근거를 직접 열어 보여준다")를 관객이 몸으로 확인하는 자리다.

공고 비교 / 검색 프리셋 / 통합 캘린더 / 다중인증 / 데이터 다운로드 /

## 13. 선행 초안에서 삭제·이동한 것과 사유

> 08-2x 선행 초안(AI 급조본) 대비 변경 내역. 재개 방지용 기록이다.

### 삭제 — 원칙 충돌

| 삭제한 것 | 어디에 있었나 | 사유 |
|---|---|---|
| AI 적합도 요약 / 적합도순 정렬 / 적합도 비교 | 공고 카드, 정렬, 후속 | 적합도는 점수이고, 정렬 가능하다는 건 순위화 가능하다는 뜻이다. **선행 초안 §17도 "합격 확률 85%" 표현을 금지하고 있어 문서 안에서 모순이었다** |
| 자기소개서 AI 작성 (STAR 정리 / 글자 수 요약 / 문항 의도 분석) | ASSET-03 | **가장 큰 문제였다.** 우리가 기업에 파는 명제는 "주장에 근거가 붙는가"다. 그 주장을 우리가 대신 쓰면 대조 기능은 우리가 만든 텍스트를 우리가 검증하는 꼴이 된다. 문제와 해결책을 동시에 파는 구조. 별건으로 이 항목은 이전에 기각된 이력이 있다 |
| 이력서 AI 첨삭 | ASSET-02 | 위와 같은 이유 + 스코프 |
| 예상 면접 질문 생성 | ASSET-04 | `기록에 없는 것` 필드가 이미 질문거리를 준다. 그건 기록에서 나온 것이고, 생성된 질문은 근거가 없다 |
| 회사별 포트폴리오 공개 범위 | 16.6 | 가시성을 회사별로 두면 "내 카드가 지금 누구에게 보이는가"에 답할 수 없다 (§4.3) |
| 프로필 완성도 % / 신규 사용자 체크리스트 | MAIN-02, ONB-06 | 안 한 것을 세는 UI는 결핍 게이지다 (§4.2) |

| 채용공고 수집·제공 | JOB-01·02 | 선행 초안에 **공고 출처가 한 줄도 없었다.** 크롤링은 원칙 위반, 제휴는 20주 내 불가 → 2층 구조로 대체 |

### 이동

| 옮긴 것 | 어디로 | 사유 |
|---|---|---|
| 기업 메시지함 / 면접 일정 조율 | 기업 측 명세 + 후속 | 선행 초안 스스로 "기업 회원·채용관리 시스템이 필요하다"고 적어놓고 MVP 필수에 넣었다. 기업 측이 없으면 영원히 비어 있는 화면 |

## 14. v0.1 → v0.2 변경 (2026-08-24)

재민 확인 결과 반영. **구조 변경 2건이 핵심이다.**

### ① 세트가 공고에서 독립했다 (SET-01)

v0.1은 `공고 선택 → 카드 선택`이었다. 그러면 우리 DB에 공고가 있어야만 링크를 만들 수 있고,
**우리 플랫폼 밖 공고에 지원하는 경우가 막힌다.** 이것이 원래 구상의 중심이었으므로
순서를 뒤집었다: `카드 선택 → (선택) 공고 연결 → 링크`.

*배경*: 과거 설계에 "토큰은 공고 스냅샷"이라는 결정이 있었고, 이후 외부 공고를 빼는 방향으로
한 번 갔다가 지금 되돌아온 논점이다. **공고를 토큰의 필수 성분에서 제외하는 것으로
이 왕복을 닫는다.**

### ② 세트 내 자연어 검색 신설 (VIEW-02)

v0.1은 이 기능을 기업 측 소관으로 밀어놨다. 그런데 **토큰 한 장 안에서 도는 검색**은
지원자가 통제하는 범위이므로 취준생 측 경계면이 맞다. 카드 대량 문제(A8)의 열람자 측
답이기도 하다.

핵심 설계는 **출력 형식 제약**이다 — 질의는 자유롭게 받고 답은 카드 목록과 링크로만 낸다.
경계 규정은 §9에 별도 절로 못 박았다.

### ③ 공고 2층 구조 (JOB-01)

표본 공고(실제 공고 익명화, 버전 고정) + 사용자 직접 등록. 지어낸 더미를 배제한 이유와
"표본을 카드보다 먼저 고정한다"는 절차 규칙을 함께 기재.

### ④ 4분면을 MVP로 승격 (JOB-04)

v0.1의 A4 선택을 뒤집었다. 사유는 §12.
4분면이 무엇인지 화면 명세로 독립시키고 각 칸의 의미와 문안 규칙을 기재.

### ⑤ A10 결정 경로 명시 (CARD-04)

"미결"에서 "인터뷰 또는 재민 판단, 화면 확정 전 마감"으로. 그 전까지 (가)안을 전제로
화면을 그린다 — (가)→(나) 전환이 반대 방향보다 싸다.

### 그 밖
- §3에 "밖에서 쓸 수 있는 링크"를 서비스 가치 3번으로 추가
- §5 흐름도를 `내보내기`/`대조` 두 갈래로 분리
- §6 내비게이션에서 `세트·링크`를 `공고`보다 앞으로
- §4.1·4.2·4.7·4.9에 검색 경로 적용 문장 추가
- 예외 화면 3종 추가 (검색 결과 없음 / 검색 실패 / 표본 체험 경로)
- 임의 선택 지점 A13~A16 신설
