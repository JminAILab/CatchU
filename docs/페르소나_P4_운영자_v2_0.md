> **"운영에 쓸 수 있는 시간은 알림을 확인하는 그 몇 분뿐이다."**

**버전:** v2.0 · 2026년 9월 1일 · 팀 논의 반영

**관련 페르소나:** `P1 취준생` · `P2 HR·리크루터` · `P3 기술 면접관(HM)`

## 프로필 — 이현우 (가명, 28세)

- CatchU 개발팀 멤버. **백엔드 개발이 본업, 운영은 겸임** *[추론]*
- 관리자 페이지를 매일 열지 않는다. **알림이 올 때, 하던 일을 멈추고 연다** *[추론]*
- 서비스 운영 경험 없음 *[추론]*
- 자동화를 최대한 걸어두고, 사람 손이 가는 일을 줄이는 쪽을 선호 *[결정]*

> **이 문서는 이현우가 '운영자로서' 겪는 것만 다룬다.** 그가 개발자로서 갖는 관심사(개인정보 처리의 법적 근거, 로그 설계, 인젝션 대응 방식 등)는 운영 페르소나가 아니라 **개발·보안 요구사항**이므로 `P4 설계 노트`로 옮겼다.

---

## 서비스에서 이 사람의 위치

이현우는 **예외 처리자**다. 서비스는 자동 처리를 기본으로 하고, 사람은 자동으로 끝나지 않은 건만 본다. *[결정]*

| 영역 | 자동 처리 | 사람이 보는 경우 |
| --- | --- | --- |
| DM·포스팅 | **필터가 자동 차단** | **필터를 통과했는데 신고된 건** |
| 기업 인증 | 서류 제출 → **자동 승인** | AI가 이상을 감지한 건 |
| 고객센터 | **AI 1차 응답** | AI가 해결하지 못한 문의 |
| 회원 관리 | — | 신고 누적·제재 판단은 사람 |
| 시스템 이상 · 인젝션 탐지 | **전부 자동** | **사람이 보지 않는다** |

> **자동화 자체가 프로젝트의 어필 포인트다.** *[결정]* 이현우가 하는 일이 적을수록 서비스 설계가 잘된 것이다. **이 페르소나의 성공은 "덜 등장하는 것"이다.**

## 목표

1. **운영 때문에 개발이 끊기지 않는 것**
2. 사용자 피해를 **빨리 막는 것**
3. 같은 상황에서 **같은 판단을 하는 것**

---

## 핵심 고통 — 운영에 쓸 시간이 없다

개발이 본업이다. 운영은 알림이 왔을 때 하던 일을 멈추고 처리한다. **한 건에 쓸 수 있는 시간은 몇 분이다.**

그 몇 분을 잡아먹는 것들이 있다.

### ① 맥락을 찾으러 돌아다닌다

신고 내용 한 줄만 보고는 판단이 서지 않는다. 앞뒤 메시지, 신고당한 사람의 이력, 신고한 사람의 이력을 **각각 다른 화면에서 찾아야 한다.** 한 건에 화면을 네다섯 번 오간다.

### ② 지난번에 어떻게 했는지 찾을 수 없다

비슷한 건을 전에도 처리했는데 **어떻게 판단했는지 기록이 없다.** 매번 처음부터 다시 판단하게 되고, 그래서 같은 상황에 다른 결정이 나온다.

### ③ 애매하면 미룬다

결정을 못 하고 넘기면, 다음에 다시 열 때 **처음부터 다시 읽어야 한다.** 미루는 것 자체가 시간을 두 배로 쓰는 일이다.

> **운영 한 건이 길어지면 그날 개발이 무너진다.** 그래서 처리 시간이 길어질수록 미루게 되고, 미루면 다시 읽는 시간이 든다.

## POV — 관점 진술

### 메인 POV

> **서비스 운영자 이현우는 예외로 넘어온 건을 몇 분 안에 판단하고 끝낼 수 있는 화면이 필요하다.**
> **왜냐하면 개발이 본업이라 운영은 하던 일을 멈추고 처리해야 하고, 맥락을 찾으러 화면을 오가거나 판단을 미루는 순간 그날의 개발 작업이 무너지기 때문이다.**

### 보조 POV

| # | POV |
| --- | --- |
| **POV-A**<br>(맥락) | 이현우는 **판단에 필요한 것이 한 화면에 모여 있는 상태**가 필요하다. 왜냐하면 신고 내용 한 줄만으로는 결정할 수 없고, 흩어진 정보를 찾으러 다니는 시간이 처리 시간의 대부분이기 때문이다. |
| **POV-B**<br>(일관성) | 이현우는 **과거에 같은 상황을 어떻게 처리했는지 볼 수단**이 필요하다. 왜냐하면 운영 경험이 없어 기준을 만들어가는 중이고, 기록이 없으면 매번 처음부터 판단하게 되기 때문이다. |

## HMW — 우리가 어떻게 하면

### 메인 HMW

> **우리가 어떻게 하면, 운영을 겸임하는 사람이 예외 건을 몇 분 안에 끝내고 하던 일로 돌아갈 수 있게 할 수 있을까?**

### 하위 HMW

| # | 대응 | 질문 |
| --- | --- | --- |
| HMW-1 | 전부 | 우리가 어떻게 하면, **사람이 봐야 하는 건의 수 자체를** 줄일 수 있을까? |
| HMW-2 | A | 우리가 어떻게 하면, 신고 한 건을 볼 때 **필요한 맥락이 이미 붙어 있게** 할 수 있을까? |
| HMW-3 | B | 우리가 어떻게 하면, **처리한 판단이 자동으로 다음 판단의 참고 자료**가 되게 할 수 있을까? |
| HMW-4 | ③ | 우리가 어떻게 하면, **미루지 않고 지금 끝낼 수 있는** 선택지를 줄 수 있을까? |

> **HMW-1이 이 페르소나의 최우선 질문이다.** 다른 페르소나는 서비스를 더 많이 쓰게 하는 것이 목표지만, P4는 **덜 쓰게 하는 것**이 목표다.

## 서비스 접점 시나리오

### ① 신고 처리 국면 *(주 시나리오)*

필터를 통과한 DM·포스팅이 신고됨 → 알림 → 관리자 페이지 진입 → **신고 내용 + 전후 메시지 + 양측의 이전 이력 + 유사 건의 과거 처리 결과가 한 화면에** → 경고 / 이용 제한 / 정지 중 선택 → **사유를 기록**하고 종료 → 하던 개발로 복귀

### ② 기업 인증 이상 국면

대부분의 인증은 자동 승인되어 이현우에게 오지 않음 → AI가 이상을 감지한 건만 대기열에 쌓임 → **AI가 무엇을 이상하다고 봤는지**와 제출 서류를 함께 확인 → 승인 / 반려 / 추가 서류 요청

### ③ 고객센터 에스컬레이션 국면

AI가 1차 응답으로 해결하지 못한 문의가 넘어옴 → 이전 대화 내역과 함께 확인 → 답변 → 반복되는 유형이면 AI 응답 범위에 추가

> **시스템 이상·인젝션 탐지 시나리오는 없다.** 자동 처리 영역이며, 사람이 대응 화면을 여는 흐름을 만들지 않는다. *[팀 결정]*

## 이 페르소나가 아닌 사용자

- **전담 CS 조직** — 하루 종일 관리자 화면에 있는 사람. 시간 압박의 성격이 다르다
- **외부 위탁 운영사** — 서비스 맥락을 모르는 상태로 매뉴얼에 따라 처리
- **대규모 운영** — 자동화 비중과 도구 구성이 완전히 달라진다
- **보안·인프라 담당자** — 시스템 모니터링과 인젝션 대응은 자동 처리 영역이며, 사람이 붙는다면 그것은 운영자가 아니라 개발자의 일이다
