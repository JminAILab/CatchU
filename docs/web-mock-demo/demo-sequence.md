# 9/30 CatchU web 핵심 흐름 시연

2026-09-21 · 작성/연결 조율: 팀원 1 `ljm0850` · 화면 담당 검토용

**발표 본편은 네 흐름만 보여준다.** GitHub 저장소를 선택해 분석을 요청하고, Catch와 근거를 확인한 뒤 공개·공유하는 연결로 설계를 설명한다. 모든 기능·오류·경계 검사를 발표에서 재현하지 않는다. 발표 구성만 줄이며 승인된 구현 범위·담당·검사 기준은 유지한다.

## 발표 본편

모의 로그인·프로필 작성·GitHub 연동은 발표 전에 기존 화면에서 완료한다. 홈에서 공통 네비게이션의 자산을 거쳐 GitHub 영역에 진입한 상태로 시작한다. 이 준비가 실제 인증·GitHub 연결의 완료를 뜻하지는 않는다.

| 순서 | 화면에서 할 일 | 설명할 설계 | 담당·요구사항 |
|---|---|---|---|
| 1. 저장소 선택·분석 요청 | GitHub 영역에서 합성 저장소 선택 → 해당 저장소 분석 동의 → 요청 → 모의 처리 완료 후 결과 목록 | 무엇을 입력받고 어떤 결과로 연결하는가. 분석 과정은 모의 동작임을 표시 | D → B · FR2/3/4 |
| 2. Catch·근거 확인 | 목록에서 Catch A 선택 → 설명·합성 근거·확인 질문 확인 → 목록 복귀 | 분석 결과의 형태와 근거의 연결, 사용자가 판단할 수 있는 정보 | B · FR4 |
| 3. 확인·공개 | Catch A 확인 완료 → 별도 공개 | 열람·확인·공개는 서로 다른 행동. 생성된 설명을 사용자 판단 없이 자동 공개하지 않음 | B · FR5/6 |
| 4. 링크 발행·수신자 열람 | 공통 네비게이션의 링크 관리 → 새 링크 발행 → 성공 URL을 독립 새 탭에서 열기 → 같은 Catch와 근거 확인 | 정리한 결과를 다른 사람에게 전달하는 활용 흐름. 소유자와 수신자 화면의 연결 | C · FR7/8 |

같은 저장소·분석·Catch·링크 상태를 끝까지 이어 간다. 중간 자료 교체나 주소 직접 입력으로 소유자 화면의 연결을 대신하지 않는다. 본편의 링크는 비밀번호 없이 발행하고, 성공 응답 이후 URL을 보여준다. 특정 Catch 하나만 담은 링크를 자동 생성한다는 뜻은 아니다.

본편에서 Catch A 하나를 자세히 다루면 충분하며, B를 같은 순서로 반복 확인·공개할 필요는 없다. A·B는 서로 다른 Catch를 구분하는 이름일 뿐 정상·오류 유형이 아니다.

## 평가항목과 화면 시연의 역할

| 평가항목 | 발표에서 설명할 근거 |
|---|---|
| 문제 정의 기획 | 대상 사용자·문제·기대 효과를 설명하고, 네 흐름이 어떤 문제를 해결하는지 연결 |
| 전체 구성 및 구조 설계 | 서비스 구성도와 역할·연결 관계. 화면만으로 구조 검증을 대신하지 않음 |
| 기능 구체화 설계 | 저장소 선택부터 공유까지의 실제 화면 이동과 행동 |
| 데이터 분석 설계 | 입력 기록 → 분석 과정 → Catch·근거의 대응을 설계 자료와 함께 설명 |
| 설계 간 정합성 | 요구사항·화면·API·데이터 설계가 같은 대상과 상태를 설명하는지 연결 |
| 핵심 기술 검토 초기 PoC | 실제 수행한 실험의 결과와 한계를 별도 증거로 제시. 합성 화면을 분석 기술 검증으로 주장하지 않음 |
| 마일스톤 진행상황 | 문서 승인·코드 구현·실행 검증을 구분해 완료·진행·미착수와 다음 작업을 설명 |

이 표는 평가 대응 방향이며, 구성도·실험 결과·전체 발표 자료가 이미 완성됐다는 뜻이 아니다. 발표 시간은 미정이므로 임의의 분량을 약속하지 않는다.

## 발표 준비와 보조 장면

- 기존 모의 초기화·화면 조작으로 사전 준비한다. 합성 프로필·저장소·Catch·근거를 사용하며 실제 계정·비밀값·GitHub 근거 URL을 꾸며 넣지 않는다. 새 자료 불러오기 도구를 요구하지 않는다.
- 소유자와 수신자는 같은 브라우저·같은 origin을 쓴다. 수신자는 소유자 탭을 복제하지 않고 opener 없는 독립 새 탭에서 URL을 연다. 다른 PC·시크릿 창에서 상태가 공유되는 시연으로 설명하지 않는다.
- **오류·경계 장면은 본편에 넣지 않는다.** 질문이나 설계 설명에 필요하고 구현·실행 확인된 경우에만 아래 보조 장면을 사용한다. 모두 준비하거나 발표할 것을 추가 완료 조건으로 삼지 않는다.

| 보조 장면 | 필요한 경우에만 보여줄 내용 |
|---|---|
| 사용자 판단·공개 제어 | 기존 Catch A에 불일치 표시 또는 직접 숨김 → 수신자의 다음 조회에서 비노출. 불일치 예시용 Catch는 따로 만들지 않음 |
| 분석 실패 복구 | 분석 요청 자체의 실패 → 사용자 명시적 재요청 → 성공 결과·Catch 목록. 완료 분석 재분석이나 개별 Catch 재생성이 아님 |
| 링크 접근 제어 | 발행 시 비밀번호 설정 또는 기존 링크 중단. 변경·해제가 필요하면 중단 후 새 URL 발행이라는 기존 기준 유지 |

## 발표와 별개로 유지할 검사

승인된 테스트 지침의 정상·오류·경계 검사, 정적·타입 검사·빌드·CI·타인 승인·새 작업 폴더 재현과 작은 변경 PR 기준은 유지한다. 로그인·프로필·연동을 본편에서 생략해도 FR1 구현과 검사는 제외하지 않는다. 아래는 특히 발표 준비와 혼동하지 않을 항목이다.

- 요청 차단·중복 방지, 조회 실패와 분석 실패·빈 결과의 구분, 저장 실패·손상·복구, 링크 제목·발행 응답 불명, 비밀번호·중단·만료 경계, 키보드 접근성은 기존 지침으로 검사한다.
- 유효 링크 최대 5개는 검사로 확인한다. 발표용 링크 4개 사전 준비는 필요 없다.
- 숨김·불일치는 다음 조회에서 반영한다. 열린 수신자 화면은 저장소 이벤트·탭 복귀만으로 자동 갱신하지 않는다. 불일치 취소·확인만으로 자동 재공개되지 않는다.
- 기존 Catch·공개 상태·링크 보존과 동일 근거 Catch 중복 방지 검사도 유지한다. 실패 재요청 화면을 보여줬다는 이유만으로 해당 검사가 통과했다고 기록하지 않는다.

| 팀원 1 | 연결 조율·평가 설명과 증거 구분, 흐름 정리 후 기존 계획대로 CI 작성 |

남은 접점은 관련 구현 전에 구체화하며 작성 책임을 이 문서에서 새로 배정하지 않는다.

- A/D/B: 자산 진입 요소·파일·작성/검토 책임, 기본 선택과 GitHub 내부 저장소·Catch 배치, 목록·상세의 이동. 소유자 레이아웃 담당만으로 공통 네비게이션 전체 책임을 정하지 않는다.
- A/C: 링크 관리 메뉴·연결 파일·작성/검토 책임. 수신자 헤더 목적지는 C와 팀원 1이 조율하되 본편의 필수 이동으로 사용하지 않는다.
- D/B와 팀원 1: 분석 결과의 Catch 반영 함수·호출·저장 실패/부분 저장 경계. 기존 Catch·링크와 실패한 분석이 함께 있는 검사 조건의 도달 경로·자료·준비 방법·작성 책임도 확인한다.

원본 계획의 담당·경로·검사 계약을 변경해야 한다면 원본 세션에서 처리한다. 전체 디자인·모든 접점 해결을 골격이나 CI 착수의 추가 조건으로 삼지 않는다.
