# 9/30 CatchU web 모의 시연 순서표

2026-09-21 · 작성/연결 조율: 팀원 1 `ljm0850` · 화면 담당 검토용

이 문서는 승인된 합성 web 시연 범위 안에서 **어떤 화면에서 무엇을 조작하고, 어떤 결과를 보여줄지** 정리한다. 화면 디자인·코드·실행 결과가 아니며 새 기능·담당·검사 기준을 결정하지 않는다. 발표 분량은 아직 정하지 않았으므로 근거 없는 소요 시간을 배정하지 않는다.

시연의 핵심은 **선택한 저장소에서 나온 Catch를 본인이 확인하고 별도로 공개한 뒤, 수신자가 같은 링크로 열람하는 연결**이다. 모의 로그인·GitHub 연동·분석 동의·Catch 확인·공개를 서로 다른 행동으로 보여준다. 실제 인증·분석·보안·배포가 완료됐다고 설명하지 않는다.

## 시작 상태와 자료

- 하나의 브라우저와 같은 주소(origin)를 사용한다. 예를 들어 `http://127.0.0.1:3000`에서 시작하면 수신자도 같은 주소를 쓴다. `localhost`와 섞거나 다른 PC/시크릿 창으로 링크를 전달하는 시연은 하지 않는다.
- 소유자 탭과 수신자 탭을 구분한다. 수신자는 같은 브라우저의 opener 없는 독립 새 탭에 URL을 붙여 넣는다. 소유자 로그인 탭의 복제로 수신자 인증 상태를 만들지 않는다.
- 시작 시 승인 계획의 모의 초기화로 해당 시연 namespace와 모의 세션만 비운다. 정상 흐름에서는 프로필 미작성·GitHub 미연동·미발행 상태부터 진행한다. 이후 분기 전환에서 초기화가 필요한 경우 기존 결과를 보존하는 장면을 먼저 마친다.
- 합성 프로필 예시: 표시 이름 `시연 사용자`, 한 줄 소개 `합성 저장소로 개발 경험을 정리합니다`, 직무 `웹 개발`, 기술 태그 `TypeScript`. 실제 인물·계정·비밀값을 사용하지 않는다. 문구는 시연 자료 제안이며 새 필수 입력 조건이 아니다.
- 합성 저장소 한 개와 Catch 두 개를 준비하면 공개/숨김의 독립성을 보여줄 수 있다. 설명용 이름은 `시연 저장소`, `Catch A`, `Catch B`로 두되 실제 식별자는 기존 계획의 안정 ID를 사용한다. A·B는 서로 다른 Catch를 구분하는 이름이며 정상·오류 유형이 아니다. 불일치 시연도 기존 A에 대한 사용자 판단으로 진행하고 별도 오류 Catch를 요구하지 않는다. 실제 GitHub PR/커밋 URL을 꾸며 붙이지 않는다.
- 링크 제목 예시는 `9월 화면 시연`이다. 제목은 소유자 관리용으로만 보여준다. 비밀번호가 필요한 분기에는 실제 비밀번호가 아닌 합성 값만 사용한다.
- 실패·응답 불명·만료 등은 승인 계획의 모의 상태 선택과 주입 가능한 시계로 재현한다. 실제 요청이나 시스템 시각 변경을 추가하지 않는다. 이 순서표는 새 시나리오 선택 기능을 요구하지 않는다.

## 정상 화면 흐름

아래 경로는 승인 계획의 경로다. 버튼 명칭·배치의 최종 디자인을 고정하지 않는다. 정상 흐름은 화면 안의 이동으로 연결하고, 주소 직접 입력은 명시적인 직접 접근 검사에만 사용한다. 수신자 헤더 클릭과 자산 공통 탭의 상세 배치는 아래 미결 표에서 따로 관리한다.

일반적인 자산 접근은 **홈 → 공통 네비게이션의 자산 → GitHub 영역 → 연결된 저장소·Catch 확인**으로 이어진다. 분석 이력이 없는 홈의 ‘분석 시작’ 버튼을 일반 이동의 전제로 삼지 않는다. 완성 제품의 자산 종류별 탭(자기소개서·포트폴리오·이력서·GitHub 등)은 장기 구상이며 이번 모의 시연의 구현 범위를 늘리지 않는다. 자산 진입 시 기본 선택, GitHub 내부의 저장소·Catch 배치와 세부 이동은 관련 화면 담당이 구체화한다. 이 순서표에서 특정 버튼·탭 구성이나 새 URL을 확정하지 않으며, 아래 경로는 기존 계획을 참조한다.

| 순서 | 화면/경로 | 조작과 다음 이동 | 보여줄 핵심 내용 | 담당·요구사항 |
|---|---|---|---|---|
| N1 | 모의 로그인 `/login` | 모의 로그인 → 최초 프로필 `/profile?mode=onboarding` | 합성 시연 표시. 실제 Google/GitHub 인증이 아님 | 팀원 2 A · FR1, NFR1 |
| N2 | 프로필 `/profile?mode=onboarding` | 합성 이름·선택 필드 입력 → 저장 → `/home` | 저장한 프로필이 다음 화면에 이어짐. 필수값 누락은 성공 처리하지 않음 | 팀원 2 A → 팀원 3 D · FR1 |
| N3 | 홈 `/home` | 미연동 홈 확인 → `/profile`의 GitHub 연동으로 이동 → 모의 연결 후 홈에서 같은 상태 확인 → 공통 네비게이션의 자산으로 이동 | 로그인과 GitHub 연동은 별개. 미연동 홈 진입은 가능하고 분석 시작은 제한 | 팀원 3 D / 팀원 2 A · FR1 |
| N4 | 자산 GitHub `/assets/github` | 자산의 GitHub 영역으로 이동 → 합성 저장소 선택 → 해당 저장소 분석 동의 → 분석 요청 | 저장소·동의·분석이 같은 대상을 가리킴. 선택/동의 없이 요청하지 않음. 자산 내부의 기본 선택·배치·이동 요소는 담당자가 구체화 | 팀원 3 D · FR2 |
| N5 | 분석 `/analysis/[analysisId]` | 진행 표시 → 모의 완료 → 해당 결과 목록 `/assets` | 결과로 넘어가도 같은 분석·저장소 유지. 완료 분석은 재조회만 가능 | 팀원 3 D → 팀원 4 B · FR3/4 |
| N6 | Catch 목록 `/assets` → 상세 `/assets/[catchId]` | Catch A 선택 → 설명·합성 근거·최소 질문 확인 → 같은 결과 목록으로 복귀 | 목록·상세·근거의 연결. 열람만으로 확인/공개되지 않음 | 팀원 4 B · FR4 |
| N7 | Catch 확인·공개 | Catch A 확인 완료 → 아직 미공개임을 확인 → 별도 공개. Catch B도 같은 순서로 공개 | 확인과 공개의 분리. 상세 편집·재생성 없이 본인 판단으로 공개 | 팀원 4 B · FR5/6 |
| N8 | 링크 목록 `/links` → 발행 `/links/new` | Catch 공개 후 공통 네비게이션으로 링크 관리 이동 → 링크 목록에서 새 링크 발행 선택 → 제목 입력, 우선 비밀번호 없이 발행 → 성공 `/links/[linkId]` → URL 확인 | Catch 공개와 링크 발행은 별개 행동. 대표 구성 없이 발행. 성공 응답 전 URL을 보여주지 않음. 30일 고정 만료 | 팀원 3 C · FR7/8 |
| N9 | 수신자 목록 `/s/[token]` | URL을 독립 새 탭에서 열기 → Catch A 선택 | 로그인 없이 공개 프로필·공개 Catch 열람. 발행자 관리 메뉴·링크 제목·비공개 항목 없음 | 팀원 3 C · FR8 |
| N10 | 수신자 상세 `/s/[token]/catches/[catchId]` | 해당 Catch 설명·근거 확인 → 같은 링크 목록 복귀 | 소유자가 공개한 같은 Catch를 보여줌. 실제 분석 결과나 검증된 기여라고 표현하지 않음 | 팀원 3 C · FR4/8, NFR1 |

전체 흐름에서 이름·저장소·분석·Catch·링크를 연결된 상태로 유지한다. 서로 다른 정적 예시를 수동 교체해 연결된 것처럼 보이게 하지 않는다. 화면의 로딩·빈 상태·실패는 성공 화면과 구분한다.

N7→N8은 사용자가 **공통 네비게이션의 링크 관리로 이동**하는 흐름이다. Catch 공개만으로 발행 화면에 자동 이동하거나 특정 Catch 하나를 담은 링크가 자동 생성되는 것으로 표현하지 않는다. 메뉴 명칭·배치와 세부 이동 요소는 담당자가 구체화하며, 공통 네비게이션과 C 영역의 연결 파일·작성 책임은 아래 미결 표에서 확인한다.

## 정상 흐름 뒤에 보여줄 오류·경계 장면

아래 장면은 승인 범위에서 발표 중 보여줄 오류·경계 흐름을 묶은 것이다. 모든 검사 항목을 발표에서 재현해야 한다는 뜻은 아니며, 시연에서 생략한 항목도 기존 구현·검사 기준은 유지한다. 정상 흐름을 먼저 한 번 끝내고, 분기마다 시작 상태·기대 결과를 분명히 보여준다.

| 장면 | 시작·조작·복귀 | 관객에게 보여줄 결과 | 담당·검사 연결 |
|---|---|---|---|
| E1 공개/숨김과 다음 조회 | N9/N10의 수신자 화면을 열어 둠 → 소유자가 Catch A 숨김 → 수신자 탭으로 복귀만 함 → 그 뒤 목록 새로고침과 Catch A 직접 상세 조회 | 탭 복귀만으로 기존 화면이 지워지지 않음. 다음 조회에서 A는 목록 제외·상세 본문 비노출. B와 링크 자체는 유지. 소유자는 저장 성공을 즉시 확인 | B·C · FR6/8, M3 |
| E2 확인·불일치·저장 실패 | A·B가 공개된 상태에서 기존 Catch A를 다시 검토 → 불일치 표시 → 수신자 다음 조회 → 불일치 취소 → 확인 완료 → 별도 공개. E1 뒤라면 시작 전에 A를 다시 공개한다. 별도 저장 실패 시나리오에서 공개/숨김 재현 → 정상 상태로 복귀 | 공개 중 불일치 표시로 A는 숨김. 수신자 다음 조회에서 A는 비노출·B는 유지. 취소나 확인만으로 자동 재공개되지 않음. 저장 실패는 성공으로 표시하지 않고 마지막 성공 상태 보존 | B·C · FR5/6/8, M3 |
| E3 요청 차단과 조회 실패 | 미연동·미선택·미동의 조건을 각각 재현 → 조건 충족 후 요청. 진행 중 중복 요청과 `query-failed`를 재현 → 조회 재시도 | 부적격 요청 거부. 진행 중 중복으로 새 작업/결과 생성 없음. 조회 실패는 분석 실패·0건이 아니며 조회 재시도는 같은 분석 유지 | A·D · FR1/2/3, M2 |
| E4 분석 실패와 명시적 재요청 | 저장소 선택·동의 → 분석 요청 → `analysis-failed` 오류 안내 → 사용자가 다시 요청 → 처리 중 → 성공 → 생성된 Catch 목록 확인 | 클릭 전 자동 재요청 없음. 명시적 재요청만 새 분석 ID. 성공 결과와 Catch 목록으로 연결. 완료한 분석에는 재요청 제공 안 함 | D·B · FR3/4, M2 |
| E5 빈 결과와 오류 구분 | `empty-result` 완료 목록 확인 → 별도 조회 실패 비교. 유효 링크에서 공개 자산 0개인 수신자 목록도 확인 | 정상 0건은 빈 상태, 조회 실패는 오류. 공개 자산이 0개여도 링크를 자동 중단하지 않음 | D·B·C · FR3/4/8, M2/M4 |
| E6 발행 조건과 응답 불명 | 공백 제목·유효 제목 중복 확인. `issue-unknown-committed`와 `issue-unknown-not-committed`에서 결과 확인/재시도 | 거부와 발행 중·불명·성공 구분. 불명 단계에는 성공 URL 없음. 접수됐으면 같은 URL 확인, 미접수면 같은 작업으로 재시도해 중복 링크 방지 | C · FR7, M4 |
| E7 비밀번호·중단·만료 | 새 링크 발행 시 합성 비밀번호 설정 → 오입력/정상 입력 → 같은 탭 새로고침/독립 새 탭 비교. 기존 링크 중단 후 다른 조건으로 새 URL 발행. 별도 모의 시계로 만료 직전/정각/이후 조회 | 발행 후 비밀번호 수정·해제 없음. 구URL 거부·새URL 새 조건/30일. 비밀번호 통과 기록으로 중단·만료 우회 불가. 열린 화면 자동 회수 여부와 다음 조회 거부를 구분 | C · FR8, M3/M4/M5 |

각 분기는 승인 계획의 모의 상태로 재현한다. E4는 **분석 작업 자체의 실패를 다시 요청하는 장면**이며, 완료된 Catch의 내용 불일치나 개별 Catch 재생성을 다루지 않는다. 기존 Catch·링크가 있는 상태를 E4의 시작 조건으로 요구하지 않고, 완료한 분석을 재분석하는 UI도 추가하지 않는다. 연결 자체를 증명하는 N1~N10은 중간 자료 교체 없이 수행한다.

승인 계획의 **기존 Catch·공개 상태·링크 보존과 동일 근거 Catch 중복 방지 검사**는 유지한다. 다만 E4를 수행했다는 이유만으로 이 검사까지 통과했다고 기록하지 않는다. 기존 자료와 실패한 분석이 함께 있는 조건의 도달 경로, 검사 자료와 준비 방법, E4와 함께 확인할지 별도 검사로 확인할지는 아래 연결 상세에서 확인한다.

유효 링크 최대 5개 제한은 발표에서 보여주지 않으며, 이를 위한 링크 4개 사전 준비도 요구하지 않는다. 4→5 발행 성공·5→6 발행 거부와 기존 링크 보존은 테스트 지침 M4의 검사로 확인한다. 존재하지 않는 링크/Catch, 키보드 조작, 저장 손상·명시적 복구, 다른 브라우저에서 상태를 공유하지 않는 한계도 테스트 지침 M4/M5와 최종 재현에서 확인한다. 발표 중 보여줄 장면을 정리했다는 이유로 검사에서 제외하지 않는다.
