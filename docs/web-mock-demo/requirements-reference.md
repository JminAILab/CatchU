# 이번 web 모의 시연 요구사항 참조

2026-09-21 · intent `260920-catchu-web-mock`

승인된 요구사항의 FR/NFR 본문을 팀이 저장소 안에서 읽도록 발췌했다. 출처 약호만 제거했고 행동·오류·경계 조건은 유지했다. 원본 승인 기록이나 새 요구사항 문서가 아니다. 원본 파일 식별·해시는 [출처와 사본 관리](provenance.md)에 있다. 요구사항에 남은 OQ 구현 상세는 [승인 계획](code-generation-plan.md)에서 확인한다.

9/30까지 합성 자료로 로그인·프로필 → 홈/연동 → 저장소 선택·동의 → 분석 → 결과 확인·공개 → 링크 발행 → 비로그인 열람을 연결한다. 실제 OAuth/GitHub/LLM/API/DB/큐·api/worker 초기화·NCP 배포를 선행 조건으로 두지 않는다. 대표 구성·설명 편집/재생성·PDF/서류·JD·피드/DM 등 제외 범위를 확대하지 않는다.

이 문서의 FR/NFR 번호는 이번 모의 시연 안에서만 사용한다. 기존 실제 MVP의 동일 번호·기능 책임·[잔여 검증 조건](provenance.md#기존-실제-mvp-조건의-뜻)과 별개다. 모의 성공으로 실제 보안·분석 품질·영속성·배포가 검증됐다고 하지 않는다.

## 기능 요구사항

모든 FR은 이번 시연의 필수 행동이다. ‘모의’는 합성 자료와 시연용 상태 전환을 뜻한다. 실제 서비스 인증/보안/경합 제어를 구현·검증했다고 해석하지 않는다. 상세 경로·필드·저장 수단은 OQ에서 정하되 아래 행동 기준은 유지한다.

### FR1 — 모의 로그인·프로필·홈과 연동 상태

모의 로그인·프로필과 홈을 연결하고 GitHub 연동 상태를 구분한다. GitHub 미연동도 로그인 홈 진입을 허용하되 분석 요청 전에는 연동 조건을 확인한다. 홈은 재사용 입력의 프로필 GitHub 연결 → 내 자산 GitHub 탭 → 저장소 선택/동의 흐름을 따른다.

- 정상: 모의 로그인 후 합의할 프로필 정보를 입력/저장하면 홈과 이후 해당 표시 화면에 같은 사용자 상태가 이어진다.
- 경계: 미연동 상태로 홈을 볼 수 있지만 분석 요청은 실행되지 않고 연동으로 이어지는 안내를 확인할 수 있다.
- 모의 로그인·GitHub 연동·분석 동의·Catch 공개는 각각 구분하며, 앞 상태의 성공을 뒤 상태의 성공으로 자동 전환하지 않는다.
- 프로필 필수/선택·수신자 공개 필드, 저장/취소·인증 후 복귀 위치는 OQ1에서 정한다. 이름만 필수 또는 모든 프로필 필드 공개를 현재 정책으로 확정하지 않는다.

### FR2 — 저장소 선택·동의와 분석 요청의 연결

합성 지원 저장소를 선택하고 해당 저장소의 분석에 동의한 경우에만 모의 분석 요청을 시작한다. 선택·동의·요청 결과가 같은 저장소/분석을 가리키도록 전달한다.

- 정상: 선택한 저장소에 동의하고 요청하면 그 저장소의 모의 진행 상태와 결과로 이어진다.
- 거부: 미선택·미연동·미동의 상태에서는 요청이 시작되지 않는다. GitHub 저장소가 공개라는 사실을 분석 동의나 자산 공개로 대체하지 않는다.
- 경계: 접수되지 않은 요청을 접수 완료로 표시하지 않는다. 이후 상태/결과를 보기 위해 별개의 정적 예시를 수동으로 바꾸는 방식은 선택 전달의 통과로 세지 않는다.
- 동의 UI의 실제 배치와 경로는 OQ1, 시연용 식별자와 상태 전달 수단은 OQ2에서 정한다. 최종 API 계약으로 고정하지 않는다.

### FR3 — 진행·실패·재조회·명시적 재요청

동일 분석의 진행·완료·분석 실패와 상태 조회 실패를 구분하고, 실패 이후 사용자의 명시적 재요청을 지원한다.

- 정상: 접수한 분석의 상태가 바뀌면 해당 분석의 화면에 반영되며 완료 시 FR4의 결과 확인으로 연결된다.
- 오류: 조회 실패는 분석 실패나 빈 결과로 바뀌지 않는다. 다시 조회/재방문은 같은 분석의 조회이며 새 분석 요청을 만들지 않는다.
- 복구: 분석 실패 후 기존 결과·공개 상태·링크는 보존된다. 사용자가 명시적으로 재요청하기 전 새 분석을 시작하지 않는다.
- 중복: 진행 중 동일 요청을 반복하거나 재요청 결과를 다시 반영해도 동일 Catch가 중복 생성되지 않는 모의 행동을 확인한다. 실제 서버의 원자성 검증을 대신하지 않는다.

### FR4 — 결과 목록·상세·합성 근거 확인

완료된 분석의 결과 목록에서 Catch 상세·설명 초안·근거·최소 생각해볼 질문을 확인하고 같은 결과 목록으로 돌아갈 수 있다. 근거와 설명은 연결된 합성 예시로 제공한다.

- 정상: 분석에서 전달된 결과를 목록에서 선택하면 해당 Catch의 상세·연결 근거를 보며, 복귀 시 같은 분석 결과를 유지한다.
- 빈 상태: 정상 조회 결과가 0장이면 빈 상태로 안내한다. 로딩·조회 실패는 0장으로 표시하지 않고 각각 구별한다.
- 경계: 상세를 열거나 스크롤한 사실만으로 확인 완료·공개 완료를 기록하지 않는다.
- 합성 근거를 실제 저장소 분석 결과나 검증된 기여로 표시하지 않는다. 원문을 대신할 합성 근거를 확인할 수 있어야 하며 실제 PR/커밋 주소를 꾸며 만들지 않는다.

### FR5 — 확인·불일치 표시와 미공개 유지

본인이 Catch 설명/근거를 확인하고 불일치를 표시하거나 미공개로 유지할 수 있게 한다. 확인 완료와 별도 공개 선택을 분리한다.

- 정상: 확인 완료 후에도 공개를 선택하기 전에는 수신자에게 나타나지 않는다. 별도 공개 동작은 FR6으로 이어진다.
- 오류 대응: 합성 오류 Catch를 불일치로 표시하고 미공개로 유지하는 행동을 재현할 수 있다. 공개 중인 Catch를 숨기는 행동은 FR6으로 확인한다.
- 경계: Catch 설명 직접 편집·재생성·대표 주장 작성·내부 검토자 선택 공유를 이번 대응 수단으로 추가하지 않는다.
- 불일치 취소·재공개 상세는 OQ3에 남긴다. 일반 확인 완료 동작이 불일치/숨김을 자동 해제하는 것으로 구현하지 않는다.

### FR6 — 별도 공개·숨김과 기존 링크 반영

사용자가 서비스 안에서 개별 Catch의 공개/숨김을 선택하게 한다. 기본 링크는 사용자가 공개로 선택한 전역 GitHub 자산을 보여주고 현재 숨김을 기존 링크에도 반영한다.

- 정상: 별도 공개 선택이 성공한 Catch만 수신자 열람에 포함된다. 생성·확인·GitHub 저장소 공개만으로 포함되지 않는다.
- 숨김: 공개 Catch를 숨긴 뒤 이미 발행한 같은 링크를 다시 열거나 새로고침하고 상세로 접근하면 해당 Catch가 노출되지 않는다. 다른 공개 자산과 링크 자체는 유지한다.
- 실패: 모의 공개/숨김 변경이 실패하면 성공으로 표시하지 않으며 마지막 성공 상태를 유지한다.
- 링크마다 전체 GitHub 자산을 새로 선택하도록 요구하지 않는다. 수신자 상태와 소유자 상태의 공유·갱신 및 실제 시연 환경은 OQ2에서 명시한다.

### FR7 — 대표 없는 링크 발급과 발행 상태

대표 구성 없이 기본 프로필·공개 자산을 열람할 링크를 발급한다. 제목과 유효 링크 한도를 확인하고 발행 중·실패·접수/응답 불명·성공을 구분한다.

- 정상: 유효한 제목과 한도 조건에서 발행 성공 결과를 받은 뒤에만 완료 화면에 링크를 표시한다. 대표 구성 완성을 선행 조건으로 요구하지 않는다.
- 제목: 제목은 필수이며 수신자에게 표시하지 않는다. 앞뒤 공백을 제거한 유효 링크 제목의 중복을 허용하지 않는다. 새 제목 길이 상한·별도 정규화 규칙을 임의 추가하지 않는다.
- 개수: 사용자당 유효 링크 최대 5개를 적용한다. 4개에서 1개 발행은 가능하고 5개에서 추가 발행은 거절된다. 중단/만료 링크는 유효 개수·유효 제목 비교에서 제외한다.
- 오류: 발행 중·실패·응답 불명을 완료로 보여주거나 성공한 링크를 가진 것처럼 처리하지 않는다. 실제 요청 중복/경합 제어를 통과했다고 주장하지 않는다.

### FR8 — 수신자 비로그인 열람과 링크 접근 조건

수신자는 기업 로그인 없이 유효한 링크로 기본 프로필·현재 공개 자산과 근거를 열람한다. 수신자 헤더는 로그인 여부와 관계없이 발행자 관리 화면과 분리하며 발행자 관리 메뉴를 노출하지 않는다. 중단·발행 후 30일 고정 만료·선택 비밀번호 조건을 모의 동작으로 확인한다.

- 정상: 유효하고 비밀번호가 없는 링크는 비로그인 열람이 가능하며 비밀번호를 요구하지 않는다. 비밀번호가 설정된 링크는 올바른 입력 후 허용된 자료만 보여준다.
- 거부: 비밀번호 오입력, 중단·만료·존재하지 않는 링크, 숨김·존재하지 않는 Catch를 통해 제한된 내용을 볼 수 없다. 제한된 링크를 다시 전달하거나 같은 URL에 재접근해도 거부된다.
- 수명: 모든 발행 링크의 만료는 발행 시점부터 30일 고정이다. 만료 직전/경계/이후를 시간을 제어한 시연·검사로 확인하며, 기간 선택·연장을 추가하지 않는다. 정확한 모의 시계/시간 기준은 OQ2에서 정한다.
- 비밀번호 설정: 선택 비밀번호는 **발행 시에만 설정**하며, 발행 후 비밀번호 변경·해제 기능은 제공하지 않는다. 비밀번호 조건을 바꿔야 하면 기존 링크를 중단하고 원하는 조건으로 **새 URL을 발행**해 전달한다.
- 대체 발행: 기존 링크를 중단한 뒤에도 기존 URL은 계속 열람 거부되고, 새 URL은 새로 설정한 비밀번호 조건과 새 발행 시점부터 30일 만료를 적용한다. 만료/중단된 URL을 재활성화하지 않는다.
- 독립성: 링크 중단은 자산 삭제·전역 숨김이 아니며 자산을 모두 숨겨도 링크를 자동 중단하지 않는다. 공개 결과 0건과 조회 실패를 구분한다.
- 비밀번호 관련 구현 계획에는 위 확정 행동의 모의 시연 방식과 아직 미정인 인증 유지 상세만 남긴다(OQ3). 프로필/Catch 본문 버전 정책의 경계는 OQ1/OQ3를 유지하며 대표 보존 규칙으로 본문/프로필 동결을 추정하지 않는다.

## 비기능 요구사항

| ID | 요구사항·통과 기준 |
|---|---|
| NFR1 | **합성 자료와 실제 처리의 구분.** 시연 화면·README·검증 기록에서 모의 상태/합성 자료임을 알 수 있다. 시연 실행에 실제 OAuth/GitHub/LLM/API/DB/큐 연결이나 사용자 비밀값이 필요하지 않으며, 합성 전환을 실제 인증·분석·권한 통과로 기록하지 않는다. 필요한 환경 예시는 비밀값을 포함하지 않는다. |
| NFR2 | **필수 상태 안내와 기본 접근성.** 제공하는 화면의 빈/로딩/실패/접근 거부 상태가 구별되고 가능한 다음 행동을 안내한다. 핵심 입력·버튼에 의미를 알 수 있는 이름이 있으며 키보드로 정상 흐름의 주요 행동을 수행할 수 있다. 색상만으로 공개/실패를 구분하지 않는다. 상세 검사 방식은 테스트 지침에서 확정하며 임의 성능 수치·WCAG 인증을 약속하지 않는다. |
| NFR3 | **express·Minimal 검사.** 요구사항별 단위 테스트(요구사항당 하나)와 컴포넌트별 정상 경로 최소 검사를 매핑한다. 테스트 파일은 정상 경로와 최소 두 오류/경계 사례를 다루고 문서화된 준비만으로 실행 가능해야 하며 항상 성공하는 빈 검사는 불가하다. 기존 테스트를 유지하고 의미 있는 시연 행동 검사·정적 검사·타입 검사·빌드를 통과한다. 실제 명령/배치/증거는 구현 계획·테스트 지침에 명시한다. 기본 순서는 test-after이며 선택적 80% 라인 조건은 추가하지 않는다. |
| NFR4 | **설치·실행·검사 재현.** web에 필요한 런타임/의존성·설치 재현 방식, 실행/종료·정상 화면 확인, 실제 검사/빌드 명령, 필요한 환경 예시, 최소 틀/경로·합성 상태 예시 하나·README를 제공한다. 작성자 외 팀원이 새 작업 폴더에서 문서대로 설치·실행·검사하고 작은 변경 PR까지 제출한 증거를 남긴다. 담당·시점 미확정을 재현 완료로 대신하지 않는다. |

80% 라인 커버리지의 새 org 적용 대상은 `mvp/enterprise/feature/infra/classic`이며 이번 `express`에는 해당하지 않는다. team/project에는 추가 확정 수치가 없다. 이후 테스트 지침에서 다른 상위 의무가 확인되면 출처·범위를 제시하고 임의 면제하지 않는다. 기존 MVP에 적용되는 기준은 그대로다.


## 승인 계획에서 구체화한 사항

- 홈은 D·팀원 3, A·팀원 2는 로그인·프로필·GitHub 연동. B는 팀원 4, C/D는 팀원 3.
- 실패 후 명시적 재요청만 구현한다. 완료한 분석은 재조회만 제공하고 재분석을 추가하지 않는다.
- 팀원 1은 시연 화면·이동 순서·핵심 내용 정리 후 CI 작성(날짜 미정). 팀원 3 골격은 독립 진행. 첫 S+CI PR의 실제 CI 통과·타인 승인 전 병합 금지는 유지한다.
- 프로필/경로·상태 저장·재진입·실패/응답 불명 처리·파일 분담·도구·브랜치·재현 제안은 [구현 계획 「OQ별 구현 제안」](code-generation-plan.md#oq별-구현-제안)에 있다. 수신자 갱신 보정 반영과 별도 기능 접점은 [착수 안내 「관련 기능 구현 전에 조율할 접점」](README.md#관련-기능-구현-전에-조율할-접점)에서 구분하며, 별도 접점이 이 참조본으로 해결됐다고 보지 않는다.
