### 2-2. 팀의 다음 진행 방식

11월 개발(12월 intent `260925-intent-12`)은 AI-DLC 팀 방식으로 했다. 담당마다 Unit을 맡아 기능 설계부터 시험까지 진행하고, 통합 브랜치 `intent/260925-intent-12`에 PR로 모은 뒤 `dev`로 올렸다(2026-11-14 조회 기준).

- 통합 브랜치는 2026-11-13 #533으로 `dev`에 들어갔다. 통합 브랜치에만 있는 커밋은 0개이고 `dev`가 26개 앞서 있다. 통합 브랜치로 가는 열린 PR도 없다.
- 남은 것은 둘이다. #420(U8 PDF 자료)이 실제 S3 확인을 남겨 열려 있다. #496은 외부 로그인 확인 뒤 두 기록 표의 행을 통합 브랜치 대상 PR로 남기기로 했다(2026-11-11 팀장 결정). 그렇게 정한 이유였던 11/9 행(#498)은 #533으로 `dev`에 들어갔다.
- 그 뒤 Unit 밖 작업은 `dev`로 올렸다(예: #485의 PR #544).

다음부터는 각자 자유롭게 개발하되 AI-DLC의 스킬과 에이전트를 적극 활용한다(팀장). 그런데 AI가 읽는 팀 지침과 AI-DLC 규칙 메모(`team.md` 전체, `org.md`의 한 구절)에는 11월 방식이 그대로 남아 있다(§4-2). 그래서 팀원이 AI에게 일을 맡기면 AI가 통합 브랜치나 Unit 맡기를 안내할 수 있다. Claude Code는 이 메모를 세션마다 읽고, Codex는 AI-DLC 단계를 돌릴 때 읽는다(Codex 쪽은 2026-09-23에 확인한 동작). 12월 intent도 AI-DLC 기록상 아직 '진행 중'이다(19단계 중 12단계 완료, `intents.json`의 `in-flight`).

저장소에는 Claude Code와 Codex 양쪽에 같은 AI-DLC 스킬 42개와 에이전트 14개가 있다. 스킬에는 scope를 정해 처음부터 도는 것과 한 단계만 도는 것이 있다. scope마다 도는 단계는 `.claude/scopes/`가 정본이다. 예를 들어 `express`와 `bugfix`에도 배포 단계가 있고, `feature`는 33단계를 모두 돈다.

## 3. 정한 것 (2026-11-14 팀장)

1. 독자는 둘이다. 저장소를 보러 온 바깥 사람, 그리고 팀원과 각자의 AI.
2. 11월 방식(통합 브랜치, Unit 맡기)을 끝낸다. 일반 작업은 레포 컨벤션 §2의 기본 규칙대로 이슈 → `영역/작업내용` 브랜치 → `dev` PR(작성자 외 승인 1건, merge commit)로 한다. AI-DLC가 Construction 작업 폴더를 만들면 레포 컨벤션 §2.1의 AI-DLC 예외를 따른다(작업 폴더의 결과를 그 intent의 작업 브랜치로 합친 뒤 `dev` PR).
3. 각자 자유롭게 개발하되 AI-DLC의 스킬과 에이전트를 적극 활용한다. 활용 방식은 권하기다. AI가 코드 작업을 시작할 때 작업 크기에 맞는 AI-DLC 스킬을 한 줄로 권하고, 고르는 것은 담당이 한다. AI-DLC 하네스(`.claude/`, `.codex/`, `.agents/`)는 고치지 않고 그대로 쓴다.
4. 12월 intent는 기록에서도 닫는다. '진행 중'으로 두지 않고 보관한다(§5).
5. "12월 intent가 아닌 작업에는 team.md의 11월 규칙을 쓰지 않는다" 같은, 범위를 가르는 예외 문장은 넣지 않는다. 예외 문장은 쌓이기만 하고, 12월 intent가 끝나 가를 대상도 없다.
6. `team.md`의 11월 문장과 `org.md`의 11월 구절(2026-10-26 #398이 넣은 「Way of Working」의 dev 가져오기 구절)도 새 방식으로 바꾼다. "AI-DLC 문서는 건드리지 않는다"는 처음 방침의 예외 둘이다. #398처럼 팀 문서와 같은 PR로 바꾸고, 지금도 맞는 줄은 남긴다(§4-2).
7. 그 밖의 AI-DLC 쪽은 건드리지 않는다: 하네스, `AGENTS.md`의 AI-DLC 관리 블록, `org.md`의 다른 문장, 승인 기록과 감사 기록, `docs/ai-dlc-input/` 스냅샷. `project.md`는 §6에 둔다.
8. #496의 기록 PR 대상은 `dev`로 바꾼다. 통합 브랜치로 정한 이유(11/9 행 #498이 그 브랜치에만 있음)가 #533으로 없어졌다. #496 본문은 게시 전에 팀장이 확인한다.
9. 서비스 README의 착수 안내 네 문장(§4-2)은 이번에 바꾼다. 서비스 문서를 코드와 맞추는 일은 하지 않는다.
10. 순서: 입력 문서 PR → 12월 intent 닫기(§5) → AI 지침 PR(§4-2) → 문서 개편 intent(의도 정리부터 요구사항까지, §4-1) → 첫 화면 PR.

## 5. 시작 전에 할 일: 12월 intent 기록 닫기

12월 intent는 AI-DLC 2.11.2의 `intent archive`(보관)로 닫는다. 끝냈지만 AI-DLC 단계를 다 밟지 않은 일을 닫는 기능이다.

AI-DLC의 '완료'는 마지막 단계를 마치거나 건너뛸 때 찍힌다. 그런데 12월 intent는 Unit 진행이 통합 쪽 상태에 찍히지 않고, AI-DLC의 마지막 통합 시험 단계(빌드와 시험)는 쓰지 않기로 했다(레포 컨벤션 결정 이력 2026-10-28, 2026-11-12 팀장 재확인: 마무리 검증은 2차 통합 확인). Unit별 코드 생성 단계의 시험은 했다. 남은 단계를 건너뛰어 '완료'로 찍으면 실제로 한 일이 기록상 건너뜀으로 남는다. 그래서 보관으로 닫는다.

- 보관하면 `intents.json`의 상태가 `archived`, 상태 파일의 Status가 `Archived`로 바뀐다. 이전 상태는 그 옆에 남는다. 닫는 이유는 `--reason`으로 감사 기록에 함께 남긴다.
- 지우는 것은 없다. 산출물, 승인 기록, 감사 기록이 그대로 남는다. `intent unarchive`로 되돌린다.
- 보관한 intent는 AI-DLC가 더 이어 가지 않고, 기본 intent 목록에서 숨긴다. 새 intent를 만들 때 12월 intent를 이어 갈지 묻지 않는다.
- 보관은 사람이 요청할 때만 한다.

지금 막는 것은 맡은 Unit 9개다. origin의 `claim/aa0d9c26/…` 브랜치 9개(u2\~u10)가 모두 '맡음'(`claimed`)이고, 보관은 맡은 Unit이 남아 있으면 거부된다. 보관이 보는 것은 실행하는 clone 안의 맡기 기록(로컬 참조와 캐시)이다. 순서는 다음과 같다.

1. Unit을 맡지 않은 저장소 본체 clone 하나를 쓴다. 다른 폴더에서 `git worktree`로 갈라 만든 폴더는 안 된다(레포 컨벤션 §2.1 「Unit 합치기」). 그 clone에서 12월 intent를 고른다.
2. 같은 clone에서 Unit 9개를 놓는다(`release`). 놓기는 `team.md`의 통합 브랜치 줄에서 이름을 읽어 그 브랜치를 가져온다. 그래서 `team.md`를 바꾸기 전, 브랜치를 지우기 전에 한다. 통합 브랜치(`3edcf6e5`) 상태 파일의 「Unit Progress」에서 u2\~u10은 모두 미완료라, 이미 끝난 Unit이라는 이유로 거부되지 않는다(2026-11-14 확인). 놓으면 claim 브랜치에 '놓음' 기록이 한 커밋 더 올라가고 브랜치는 남는다.
3. 같은 clone에서 12월 intent를 보관한다. 이유 예: "11월 개발 끝(Unit은 2026-11-13 #533으로 dev에 합침). AI-DLC의 마지막 통합 시험 단계는 쓰지 않음(2026-10-28). 마무리 검증은 2차 통합 확인".
4. 보관으로 바뀐 intent 목록·상태 파일·감사 기록을 PR로 `dev`에 올린다.
5. #496의 기록 PR 대상을 `dev`로 바꾼 뒤(§3의 8), 레포 컨벤션 §2.1 「삭제」("마지막 `dev` PR 병합 뒤 남은 Unit 제출·후속 작업이 없으면")에 맞는지 대조하고 통합 브랜치와 Unit 브랜치(`claim/…`)를 지운다.

2와 5는 원격 저장소를 바꾼다. 먼저 격리 사본에서 같은 순서로 돌려 본다. 격리 사본은 내 컴퓨터에 만든 빈 원격 저장소를 origin으로 둔 clone이고, 기준 `dev`, 통합 브랜치, 실제 claim 참조 9개를 함께 넣는다. 실제 실행은 팀장 확인 뒤에 한다.

2차 통합 확인(EKS, `docs/CatchU_통합확인.md`)은 AI-DLC 밖의 절차라 보관과 상관없이 남는다.

## 7. 남는 위험

- 두 사람이 같은 때 새 intent를 만들면 `intents.json`(작업마다 항목 하나인 목록)을 둘 다 고쳐 `dev`에 합칠 때 충돌한다. 이 파일은 intent를 열고 닫을 때마다 바뀐다(지금까지 이 파일을 고친 커밋 10개). 두 작업의 항목을 각각 남겨 합치면 풀린다.
- 한 단계만 다시 도는 스킬(`/aidlc-<단계>`)은 선택한 intent의 그 단계 파일에 결과를 쓰는 것으로 보인다. 본 작업의 진행 위치는 그대로다(2.11.2 스킬 설명, 실행 확인 안 함). 2026-09-24 확인(2.10.0) 때는 Unit 밖 단계에서 승인·완료 기록이 늘 거부됐고, 2.11.2에서는 다시 확인하지 않았다.
- `team.md`와 `org.md`를 바꾸면 앞으로 모든 AI-DLC 단계가 읽는 팀 규칙이 바뀐다.
- `team.md`의 통합 브랜치 줄을 지우면, AI-DLC의 팀 방식 Unit 명령은 `org.md`의 "the merge target is that same branch — never `main` …" 문장에서 `main`을 통합 브랜치로 읽는다(`.claude/tools/aidlc-unit.ts`의 이름 찾기 규칙). 이 이름은 Unit 명령에서만 쓴다. 팀 방식 Unit을 다시 쓰려면 `team.md`에 통합 브랜치 줄을 먼저 둔다.
- 팀원 컴퓨터의 Unit 폴더는 12월 intent의 `aidlc-state.md`를 Git이 보지 않게 숨겨 둔 상태다(`skip-worktree`). §5의 보관 PR이 이 파일을 바꾸므로, 그 폴더에서 `dev`를 가져오면 멈출 수 있다(레포 컨벤션 §2.1 「상태 파일」·「최신화」). 새 작업은 `dev`에서 새 폴더로 하고 Unit 폴더는 더 쓰지 않는다.
- 통합 브랜치를 지우면 그 브랜치를 가리키는 이슈 본문의 링크가 열리지 않는다. 2026-11-14 조회로 #129·#416·#420·#441 본문에 16개가 있다. PR 본문과 저장소 파일에는 없고, 댓글은 세지 않았다.
- 코딩 절차는 한도까지 18 B가 남았다. 한 줄을 더하려면 다른 곳을 줄여야 한다.
