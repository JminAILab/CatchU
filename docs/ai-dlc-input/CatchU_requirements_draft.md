# CatchU — 실제 사용자 검증을 위한 요구사항 초안

작성일: 2026-09-08 · 수정일: 2026-09-09 · 상태: 만족도 조사 중심의 검증 방안 반영, 개발 범위·일정 확정 전

목표는 소수의 실제 구직자와 HR/HM이 자신의 자료로 사용할 수 있는 서비스를 만드는 것이다. 이번 사용자 검증은 참여 가능한 응답자의 만족도·체감 유용성·개선 의견 조사에 집중한다. 사용자의 Q1·Q3·자원 답변, 2026-09-09 검증 방식 조정과 [이용 흐름·결정 기록](./CatchU_scope_and_journeys.md)을 바탕으로 작성했다. 아래 상세 동작과 확인 기준은 설계 제안이며, 구현·검증이 완료됐다는 뜻은 아니다. AI-DLC 실행 도구가 연결되기 전 대화와 문서로 준비한 산출물이다.

## 1. 기준과 범위

- GitHub 자산을 만드는 기존 기반을 유지한다. 구직자는 경험 후보·근거·질문을 보고 자기 PR에 활용할 내용을 고른다. 기업은 자신의 JD로 지원자 자료를 확인한다. (현행 목적, Q1)
- 링크 발행부터 기업의 근거 확인까지 주 경로를 먼저 완성한다. HR 검색·소싱도 이번 산출물 범위에 유지하되 완성도를 낮출 수 있다. (기존 팀 합의)
- 신입·취업준비생부터 시작하고, 초기 사용자는 인공지능사관학교 수료생이다. HM 검증이 어렵다는 팀 상황을 반영해 이번 외부 검증은 만족도 조사 중심으로 진행한다. 응답자 구성과 인원, 실제 HR/HM의 설문 참여 가능성은 미정이다. (기존 팀 합의, 2026-09-09 사용자 승인)
- 지원 접수·전형 관리·면접 진행·평가 기록은 기존 채용 시스템이 맡는다. CatchU에서 JD와 자료를 확인하는 경험을 설계한다. (v10의 역할 분담)
- 개발팀 4인, 12월 중순 목표다. 기본 투입 시간은 평일 09:00~18:00이며 추가 투입은 별도 설득·합의가 필요하다. 회의·휴식·검증을 고려한 실제 개발량과 역할·기술 환경은 작업 계획에서 구체화한다. (기존 제약, 사용자 자원 답변)
- 서버·LLM/API 월 예산은 개인당 약 40만 원, 4인 합산 약 160만 원을 계획 기준으로 둔다. 공용·개인 계정 간 배분과 예상 사용량은 미정이므로 특정 규모를 수용할 수 있다고 단정하지 않는다. (사용자 자원 답변, 합산 계산)

## 2. 기능별 요구사항과 확인 기준

아래 동작은 팀 내부의 기능·자료 품질 확인 기준으로 구체화한다. 실제 HM의 과제 수행 실험이나 시간 측정을 통과해야 한다는 뜻은 아니다. 외부 사용자 조사는 4절에 별도로 정리한다.

| 항목 | 요구사항 초안 | 확인할 동작 | 근거·의존 사항 |
|---|---|---|---|
| F1. GitHub 자산 생성 | 본인이 분석에 동의한 공개 저장소에서 작업 기록을 정리해 Catch와 근거를 제공한다. | 사용자가 분석 결과에서 원본 기록을 열어 설명과 실제 작업을 대조할 수 있다. | 유지할 GitHub 기반, 시작 문서 1·4절 |
| F2. 경험 선택 가이드 | 정리된 기록에서 경험 후보·근거·생각해볼 질문을 제공한다. | 사용자가 글을 먼저 쓰지 않아도 후보를 살펴보고 활용할 내용을 고를 수 있다. 기록에 없는 맥락은 사실로 채우지 않고 돌아볼 질문으로 제시한다. | Q1; 구체적인 질문·표현 방식은 제안 |
| F3. 자기 PR 자료 구성 | 사용자가 프로필·자기소개서·포트폴리오 등 본인의 자료와 GitHub 자산을 구성한다. | 준비한 자료를 다시 열어 확인하고 기업에 전달할 내용을 확인할 수 있다. 문장 자동 작성·첨삭은 이 요구사항에 포함하지 않는다. | 현행 목적; 서류 형식·입력 방식은 후속 설계 |
| F4. 링크 발행과 공개 통제 | 사용자가 정해진 열람 범위로 링크를 발행하고 공개를 중단할 수 있게 한다. | 링크의 접근 조건과 공개 중단이 적용된다. 기업의 원자료 열람·요약·질의응답이 허용 범위를 넘지 않는지 확인한다. | Q2 최종 결정에 의존; 전역 숨김과 링크별 선택의 관계 미결 |
| F5. JD 기반 한 장 요약 | HR/HM이 자신의 JD에 대응하는 지원자의 서류 대목과 GitHub 근거를 요약으로 확인한다. | 요약에서 해당 원자료로 이동할 수 있다. 자료에서 확인되지 않는 항목을 지원자의 역량 부족으로 판정하거나 매칭 %로 표시하지 않는다. | 기존 팀 합의; 재료 범위는 Q2, JD 없이 열었을 때의 동작은 후속 설계 |
| F6. 상세 근거와 질의응답 | HM이 Catch·원본 기록과 근거가 연결된 답변을 통해 더 확인할 지점을 찾는다. | 답변의 근거를 확인할 수 있다. 근거·서술 규칙을 충족하지 못하면 자료 목록으로 대체하며, 숨김·공개 중단된 자료를 답변에 계속 노출하지 않는다. | v10의 상세 열람·RAG 안; 열람 경계는 Q2에 의존 |
| F7. HR에서 HM으로 자료 전달 | HR이 후보 자료를 HM에게 전달해 채용 검토를 이어갈 수 있게 한다. | HM이 전달된 자료에 적용되는 열람 조건으로 접근할 수 있고, 전달로 허용 범위가 넓어지지 않는지 확인한다. | 현행 흐름; 전달 URL·계정 조건·JD 공유 방식 미결 |
| F8. HR 검색·소싱 | HR이 검색 대상에 포함된 구직자를 찾아 공개 자료를 확인하고 접촉·전달로 이어갈 수 있게 한다. | 검색 노출 설정에 맞는 자료를 찾을 수 있다. 공개 프로필 열람과 지원자가 발행한 링크의 열람 권한을 혼동하지 않는다. | 기존 팀 합의; 최소 필터·접촉 방식·완성 수준은 자원 확인 후 결정 |

Catch 4구획, 선택 상한과 맥락 가이드, 프로필·한 장 요약·서류·RAG 화면에 관한 기존 팀 합의는 유지한다. 이 표에서 생략한 v10 기능을 폐기한 것으로 해석하지 않는다. 공고·과금·MCP·소셜 등 나머지 항목의 역할과 우선순위는 별도 검토하며, 모두 첫 사용자 검증의 선행 조건으로 두지는 않는다.

## 3. 실제 사용자에게 제공하기 위한 준비

아래는 Q3에 따라 제안하는 최소 준비다. 상시 대응 조직이나 새로운 관리 제품을 전제로 하지 않는다.

| 항목 | 준비할 내용 | 확인 방법 제안 |
|---|---|---|
| 실패 대응 | 분석·요약의 진행 및 실패 상태를 알리고, 기존 자료를 보존하며 재시도할 수 있게 한다. | 분석 실패 뒤 기존 자료를 다시 열고 작업을 이어갈 수 있는지 확인한다. |
| 자료와 접근 관리 | 저장소 연결 동의, 링크 접근 조건, 공개 중단, 데이터 삭제 요청의 처리 방법을 정한다. 요약·답변 등 파생 결과에도 열람 통제가 적용돼야 한다. | 서로 다른 사용자·링크의 접근과 공개 중단 후 열람을 점검한다. Q2 결정과 데이터 처리 기준 수립 후 확인한다. |
| 문의와 운영 대응 | 문의 경로, 오류·오귀속 신고 처리 담당자, 서비스 오류 및 처리량·API 사용량 확인 방법을 정한다. | 담당자가 문제를 파악하고 처리 경과를 안내할 수 있는지 확인한다. 공개 중단과 재개 기준도 정한다. |
| 비용과 사용량 | 월 합산 약 160만 원의 계획 예산과 첫 검증의 예상 사용량에 맞춰 분석·질의 사용 한도 및 초과 시 동작을 정한다. | 기술 환경·참여 규모를 정하고 실제 자료의 처리 시간과 호출 비용을 측정한다. 현재는 한도 숫자나 응답 시간 목표를 임의로 정하지 않는다. |

구체적인 기술·배포 구성과 보관·파기 기간은 아직 정하지 않았다. 기존 보안·개인정보 요구를 이어받아 실제 운영 범위에 맞게 설계한다.

## 4. 이번 사용자 조사와 내부 확인

### 조사 시작 전 준비

직접 사용 후 조사할 수 있도록 경험 선택 → 자료 구성·링크 전달 → JD 기반 요약과 상세 근거 확인의 핵심 동작을 연결한다. 적용할 열람 범위를 정해 확인하고, 발견된 오귀속·접근 오류에 대응하며, 문의 담당자와 조사 대상·체험 방식·설문 문항을 준비한다. 일부 기능이 시연 단계라면 직접 사용한 부분과 구분해 조사한다. RAG와 검색·소싱 등 기존 산출물 범위는 유지하며, 이번에 체험할 수준과 이후 구현·조사할 수준을 구분한다.

### 만족도·체감 유용성·개선 의견

| 구분 | 확인할 내용 | 결과 해석 |
|---|---|---|
| 직접 사용 후 응답 | 이해하기 쉬운 정도, 경험 선택·자료 확인의 편의, 체감 유용성, 불편함 | 해당 응답자의 사용 만족도와 체감 유용성 |
| 설명·시연만 본 뒤 응답 | 기대되는 도움, 이해하기 어려운 부분, 첫인상 | 기대 유용성과 첫인상. 실제 사용 만족도와 구분 |
| 자유 의견 | 도움이 된 부분, 신뢰하기 어려웠던 설명, 추가로 필요한 자료, 개선 제안 | 기능과 표현을 개선하기 위한 구체적인 의견 |

응답자의 역할과 채용·기술 면접 경험, 직접 사용 여부, 체험한 기능 범위를 기록한다. HM이 참여하면 해당 사용 경험을 확인할 수 있고, 참여하지 못하면 HM의 업무 효과는 미검증으로 남긴다. 비HM의 응답을 HM의 업무 효과로 일반화하지 않는다. 응답자 수·응답 척도·결과 판단 기준은 조사 설계에서 정한다. 만족도 응답을 시간 단축·작업 이해의 정확성·채용 판단 품질의 증거로 쓰지 않는다.

### 내부 확인과 후속 가설

근거 링크가 열리는지, 설명이 원본 기록과 일치하는지, 접근 조건과 공개 중단이 지켜지는지, 실패 시 자료를 보존하고 이어갈 수 있는지는 팀 내부에서 별도로 확인한다. 이 결과를 사용자 만족도와 구분해 기록한다.

v10의 ‘면접관이 5분 안에 작업 내용과 물어볼 지점을 찾는다’는 미검증 상태의 후속 가설로 유지하며, 이번 조사와 프로젝트의 통과 조건에서는 제외한다. HM의 참여와 관찰이 가능한 후속 단계에서 과제 완료 기준·시간 측정 범위·비교 방법을 정해 검증한다.

## 5. 다음 결정과 그 영향

| 결정 | 현재 상태 | 정해야 하는 시점 |
|---|---|---|
| 기업의 열람 범위 | 카드 수가 줄어들면 링크별 선택도 고려한다는 조건부 의견. 전역 숨김과의 관계 미결 | F4~F7의 권한·자료 범위를 확정하기 전 |
| 역할·실제 개발량·기술 환경·예산 배분 | 기본 투입 시간과 월 예산 규모는 확인됨. 역할·기술 환경·공용/개인 예산 배분은 미정 | 개발 범위를 일정에 배정하고 운영 구성을 정하기 전 |
| 조사 응답자·체험 방식 | 초기 사용자 집단은 알려져 있고 구체적인 응답자·인원·HR/HM 설문 참여 가능성은 미정 | 설문 문항·체험 안내·조사 일정을 확정하기 전 |

현재는 요구사항 초안 작성까지 진행했다. 실제 구현, 배포, 외부 참여자 모집·연락, 사용자 검증은 수행하지 않았다.
