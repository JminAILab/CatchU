# CatchU — AI-DLC 시작 문서

상태: 방향 전환·후속 답변·만족도 조사 중심의 검증 방안을 반영한 시작 초안 · 2026-09-09

이번 대화에서 사용자가 설명한 방향 전환, 유지 사항, 후속 질문 답변을 기준으로 작성했다. 현행 구상은 1~2절에, v10에 기록된 추가 팀 결정은 3절에 구분했다. 기존 합의의 출처와 미결 상태를 보존하며, 이번 설명을 개별 화면·정책·구현 방식 전체에 대한 승인으로 확대하지 않는다. 후속 결정과 구체화안은 [이용 흐름과 개발 범위](./CatchU_scope_and_journeys.md)에 기록한다.

참고 원문: [v10 기획 기록](./CatchU_v10_reference.md). 원문에 있는 설계안과 미결 질문을 모두 이번 구현의 필수 조건으로 자동 적용하지 않는다. 이 초안에서 생략한 항목도 폐기 결정으로 해석하지 않는다.

## 1. 방향 전환과 현재 구상

이전에는 잡코리아·사람인 같은 채용플랫폼에 GitHub 분석 기능을 더하는 구상이었다. 개편 이후에는 링크드인에 가까운 포지션에서 구직자의 자기 PR을 돕고, 기존 채용 시스템을 거스르지 않으면서 HR과 HM의 자료 확인 업무를 지원하는 방향으로 바뀌었다. 이 비교는 제품 포지션에 관한 설명이며, 특정 서비스의 기능 전체를 구현 범위로 정한 것은 아니다.

팀이 확실히 유지하는 것은 GitHub 데이터의 활용과 기존의 데이터 처리 방식이다. GitHub 기록을 분석·정리해 구직자의 자산으로 만드는 기반을 이어받으며, 그 자산을 자기 PR과 채용 과정에 연결하는 방식을 설계한다. 기존 미결인 구현 세부 사항까지 확정된 것으로 해석하지 않는다.

작업용 정의: CatchU는 정리된 GitHub 자산을 바탕으로 구직자의 자기 PR을 돕고, HR/HM이 자신의 JD(채용 요건)에 따라 지원자의 자산을 확인할 수 있게 하는 서비스다. 기록을 사건 단위로 정리한 자료는 기존 명칭인 ‘Catch’를 사용한다. 최종 핵심 한 줄의 문안은 별도로 정한다.

## 2. 사용자와 먼저 검증할 경험

- 구직자: 정리된 GitHub 기록에서 활용할 경험 후보·근거·생각해볼 질문을 제공받고, 자기소개서·포트폴리오에 담을 내용을 고른다. 이 가이드의 첫 범위는 후속 질문에서 확인됐다. 문장 자동 작성·첨삭까지 제공할지는 이번 설명에서 확정되지 않았다.
- 기업: HR과 HM이 자신의 JD를 기준으로 지원자의 프로필·자기소개서·포트폴리오·GitHub 자산을 확인한다. 기존에 사용하는 채용 시스템과 업무 흐름에 연결될 수 있어야 한다.
- 운영자: 개발팀이 운영을 겸한다. 운영 부담을 줄이는 방향으로 설계한다.

제품이 제공하려는 가치는 구직자의 자기 PR 준비와 HR/HM의 자료 확인 지원이다. 이번 사용자 검증은 팀의 HM 검증 여건을 고려해 참여 가능한 사용자의 만족도·체감 유용성·개선 의견 조사에 집중한다. 직접 사용 후 응답과 시연·설명만 본 뒤의 기대 유용성·첫인상은 구분한다. 응답자의 역할과 채용 경험을 기록하며, HM이 참여하지 못하면 HM의 업무 효과는 미검증으로 남긴다.

v10의 ‘면접관이 5분 안에 작업 내용과 물어볼 지점을 찾는다’는 후속 검증 가설로 보존하며 이번 통과 조건으로 삼지 않는다. 근거와 설명의 일치, 링크 동작, 공개 범위 준수 등 기능·자료 품질은 팀 내부에서 별도로 확인한다. 설문 문항·응답자 수·결과 판단 기준은 요구사항 분석에서 구체화한다.

## 3. v10에 기록된 추가 팀 결정

아래는 기존 합의를 보존한 목록이다. 1~2절의 현행 목적에 연결해 구현 범위와 적용 방식을 검토한다. 변경이 필요하면 이유와 변경안을 제시한다.

| 묶음 | 기록된 결정 |
|---|---|
| 대상과 두 경로 | 초기 대상은 신입·취업준비생, 초기 사용자는 인공지능사관학교 수료생이다. 구직자의 링크 발행과 기업의 검색·소싱을 모두 만든다. 링크 발행을 주 경로로 먼저 완성하고 검색·소싱의 완성도는 낮출 수 있다. 향후 경력 구간으로 확장한다. |
| 채용 과정과의 관계 | 채용 동선은 외부 링크로 종료하며 기존 ATS와 역할을 나눈다. 매칭 %를 제공하지 않고 JD에 해당하는 내용 표기까지 한다. |
| 기업의 읽기 경험 | 신뢰성과 시간 절약을 우선한다. HR은 요약, HM은 상세 근거를 본다. JD 기반 개발자 한 장 요약을 제공한다. 검색 UX는 기존 서비스와 비슷하게 두고 GitHub 기록을 더한다. |
| Catch와 화면 | Catch 명칭과 4구획(무엇을 했나 / 판단의 흐름 / 궤적 및 기록 / 기록에 없는 것)을 사용한다. 선택 상한과 맥락 가이드를 둔다. 프로필·한 장 요약·서류·RAG로 열람 화면을 구성하고 Catch 클릭으로 상세를 연다. 상한 숫자와 최초 화면 등은 미결이다. |
| 운영과 확장 | 운영은 자동 처리를 기본으로 하고 인젝션 탐지는 자동으로 수행한다. 익명 게시판은 확장 범위로 둔다. |
| 보안·개인정보 | 관련 기준을 기획 단계에 포함한다. 개별 통제 방식과 보관·파기 정책은 필요한 검토를 거쳐 정한다. |

## 4. 프로젝트 제약

- 개발팀 4인, 최종 산출물 목표는 2026년 12월 중순이다.
- v10의 본인이 분석에 동의한 공개 저장소라는 데이터 범위를 기존 기준으로 이어받는다.
- 기본 투입 시간은 팀원 4명 모두 평일 09:00~18:00이다. 추가 투입은 별도 설득·합의가 필요하며 기본 일정에 포함하지 않는다. 팀원별 역할과 회의·휴식 등을 제외한 실제 개발량은 작업 계획에서 구체화한다.
- 서버·LLM/API 월 예산은 개인당 약 40만 원, 4인 합산 약 160만 원을 계획 기준으로 둔다. 공용·개인 계정 간 배분과 예상 사용자 규모는 미정이다.
- 사용 가능한 기술과 배포 환경은 팀장이 별도로 제공할 예정이다.
- 최종 산출물은 소수의 실제 구직자와 HR/HM이 사용할 수 있는 서비스라는 목표를 유지한다. 이번 외부 검증은 참여 가능한 응답자의 만족도 조사 중심으로 진행하며 HM의 실측 검증을 완료 조건으로 두지 않는다. 응답자 구성·참여 인원·운영 규모는 미정이다.

## 5. 시작할 때 확인할 핵심 질문

1. 가이드의 첫 범위는 경험 후보·근거·생각해볼 질문 제공으로 정했다. 구체적인 제시 방식과 사용자가 내용을 고르는 흐름을 설계한다.
2. HR/HM의 진입·자료 확인·전달 흐름과 공개 통제를 정한다. 카드 수가 줄어든다면 링크별로 선택한 자산까지 열람하도록 하는 것도 괜찮다는 사용자 의견은 조건부 검토안으로 두며, 전역 숨김의 폐기나 최종 공개 범위 확정으로 해석하지 않는다.
3. 이번 사용자 검증은 만족도·체감 유용성·개선 의견 조사로 구체화하고, 기능·자료 품질 확인은 별도로 계획한다. 확인된 투입 시간·예산을 바탕으로 역할·기술 환경·응답자 구성을 정한다. HM의 5분 내 확인 여부는 후속 검증으로 남긴다.

## 6. 이후 설계에서 활용할 참고 자료

GitHub 분석·Catch 생성·근거 확인에 관한 기존 자료는 유지할 기반으로 활용한다. 미결인 세부 사항은 미결로 남긴다. 프로필·프리셋 구조, JD 사이드 패널, 전역 숨김, MCP 등 자산의 활용·공개·전달 방식은 현행 사용자 흐름에 연결해 검토한다.

‘작성에 기여하지 않는다’ 같은 이전 문구는 현재 확인된 내용 선택 가이드까지 막는 제한으로 적용하지 않는다. 공고·탐색·접촉·과금 등 기존 채용플랫폼 구상의 기능도 현재 포지션에서의 역할을 검토한다. 링크드인이라는 비교만으로 소셜 기능을 추가하거나 기존 기능을 일괄 폐기하지 않는다.

적용 여부가 미판정인 이전 원칙 세 벌, 상세 접근·변경 표, Catch 실물 예시, 보안 기준 대응표, 기본값·검사기·버전 처리 등의 질문은 v10을 참고한다. 현행 범위와 관련된 질문을 해당 설계 단계에서 다루고, 과거 질문 목록 전체를 먼저 해결하는 절차로 삼지 않는다.

## 7. 이 입력으로 진행할 작업

GitHub 자산을 다루는 기존 기반에서 출발해, 구직자의 자기 PR과 HR/HM의 기존 업무에 연결하는 흐름을 구체화한다. 이번 범위와 성공 기준을 정하고 요구사항, 유저 스토리, 도메인 모델을 만든다. 방향과 범위를 좌우하는 미결을 AI가 임의로 확정하지 않으며, 세부 질문은 그 결정에 의존하는 설계를 진행하기 전에 해결한다.
