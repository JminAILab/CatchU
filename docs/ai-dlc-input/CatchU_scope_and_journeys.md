# CatchU — 이용 흐름과 개발 범위 초안

작성일: 2026-09-08 · 수정일: 2026-09-09 · 상태: 만족도 조사 중심의 검증 방안 반영, Q2 공개 범위는 조건부 검토·결정 미결

사용자가 승인한 [시작 문서](./CatchU_AI-DLC_start_draft.md)를 구체화한 작업 문서다. 확정된 목적, 이전 합의, 이번 제안을 구분한다. 이 문서의 작성 완료는 개발 범위 전체의 확정을 뜻하지 않는다.

진행 방식: 현재 작업 폴더와 연결된 도구에서 AI-DLC 실행 환경을 확인하지 못했다. [공식 AI-DLC 의도·범위 정리 절차](https://awslabs.github.io/aidlc-workflows/reference/04-stages/ideation/)를 참고해 대화와 문서로 준비하고 있으며, 자동 워크플로우의 실행·단계 완료를 기록한 산출물은 아니다.

초기 대상은 신입·취업준비생, 초기 사용자는 인공지능사관학교 수료생이라는 기존 결정을 이어받는다. HR/HM을 위한 설계를 우선하되, 구직자가 활용할 만한 자산을 만들고 전달할 수 있어야 기업의 확인 경험도 성립한다.

## 2. 먼저 연결할 이용 흐름

아래 순서는 검토용 제안이다. 개별 화면, 계정 권한, 자동 생성 방식은 확정하지 않는다.

### 구직자: 기록에서 자기 PR에 쓸 내용 찾기

| 단계 | 사용자의 행동과 서비스의 도움 | 다음 단계에 넘기는 결과 |
|---|---|---|
| 1. 자산 만들기 | 동의한 저장소를 연결하고 분석 결과와 원본 근거를 확인한다. | 확인 가능한 GitHub 자산과 Catch |
| 2. 활용할 내용 찾기 | 정리된 GitHub 기록에서 제시된 경험 후보·근거·생각해볼 질문을 확인하고 자기소개서·포트폴리오에 담을 내용을 고른다. | 사용자가 선택한 경험과 근거; 가이드의 첫 범위는 Q1 답변으로 확인됨 |
| 3. 자기 PR 구성하기 | 선택한 내용을 활용해 본인이 프로필·자기소개서·포트폴리오를 준비하고 서비스에 구성한다. | 본인이 작성한 자료와 이를 뒷받침하는 GitHub 자산 |
| 4. 전달하기 | 기업이 열람할 자료와 공개 설정을 확인하고 링크를 발행해 기존 지원 경로로 전달한다. | 열람 링크; 기업이 읽을 자산의 경계는 Q2에서 확인 |

가이드 예시(가상): 반복 요청을 제거한 변경 기록이 있다면 관련 근거를 보여주고, 사용자가 당시 문제·본인의 역할·선택 이유·확인 방법을 돌아볼 질문을 제공한다. 기록에 없는 의도나 성과 수치를 사실처럼 채워 넣지 않는다. 경험 후보·근거·질문을 제공하는 범위는 Q1에서 확인됐으며, 이 예시의 질문 문구와 표현 방식은 구체화 제안이다.

Q1을 바탕으로 한 구직자 가이드 요구사항 초안:

| 항목 | 요구사항 | 확인 기준 제안 |
|---|---|---|
| G1. 경험 후보 제시 | 정리된 GitHub 기록에서 자기소개서·포트폴리오에 활용할 경험 후보를 제시한다. | 사용자가 주장이나 글을 먼저 작성하지 않아도 경험 후보를 확인할 수 있다. |
| G2. 근거 확인 | 각 경험 후보를 뒷받침하는 Catch와 원본 기록을 확인할 수 있게 한다. | 사용자가 후보의 설명을 근거와 대조하고, 자신의 글에 활용할지 판단할 수 있다. |
| G3. 경험을 돌아볼 질문 | 경험을 구체적으로 설명하는 데 도움이 되는 질문을 제공한다. | 질문을 통해 사용자가 자신의 역할·선택 이유·확인 방법 등을 돌아볼 수 있다. 기록에 없는 맥락을 확인된 사실로 제시하지 않는다. |

세 항목의 상세 동작과 확인 기준은 설계 제안이다. 사용자는 후보·근거·질문을 보고 활용할 내용을 직접 고른다. 질문 응답의 저장·서류 반영 방식은 아직 정하지 않았다. 이번 답변은 문장 자동 작성·첨삭을 추가하거나 v10의 주장과 근거 연결 기능을 영구 제외하는 결정으로 확대하지 않는다.

### HR/HM: 기존 채용 과정에서 JD와 지원자 자료 확인하기

| 단계 | 사용자의 행동과 서비스의 도움 | 다음 단계에 넘기는 결과 |
|---|---|---|
| 1. 자료 열기 | HR이 기존 지원 자료에 포함된 CatchU 링크를 연다. | 지원자가 열람을 허용한 자료 |
| 2. JD에 따라 확인하기 | 기업이 자신의 JD를 입력하거나 선택하고, HR이 관련 서류 대목과 GitHub 근거를 요약으로 확인한다. | JD와 원자료에 연결된 요약 |
| 3. HM에게 전달하기 | HR이 후보 자료를 HM에게 전달한다. 같은 JD와 자료 범위를 이어받도록 하는 방안을 검토한다. | 전달 대상과 공유 범위는 미결; 전달만으로 열람 범위를 확대하지 않는 안을 제안 |
| 4. 근거 살펴보기 | HM이 서류·Catch·원본 기록을 살펴 실제 작업 내용과 더 확인할 지점을 파악한다. | HM이 직접 준비할 면접 질문의 근거 |
| 5. 기존 업무 이어가기 | 면접 진행과 평가 기록은 기업의 기존 채용 시스템에서 이어간다. | 기존 채용 절차의 계속 진행 |

JD가 아직 없는 경우의 첫 화면과 JD 입력 시점은 화면 설계 때 정한다. HR을 거치지 않고 기존 채용 자료에서 HM이 링크를 여는 경우도 고려한다. HR과 HM을 반드시 순서대로 통과해야 하는 승인 절차는 추가하지 않는다.

### 기업 검색·소싱: 함께 보존할 확장 경로

HR이 검색 대상에 포함된 구직자를 찾고 → 공개 자료를 확인하고 → 접촉·전달을 거쳐 채용 검토로 이어가는 흐름이다. 기존 합의대로 구현 범위에 유지한다. 첫 검증에서는 주 경로를 우선하고, 검색·소싱에 필요한 최소 기능과 접촉 수단은 자원 확인 후 구체화한다. 검색 결과의 공개 자료와 지원자가 발행한 링크의 열람 범위가 같다고 가정하지 않는다.

## 3. 개발 범위를 정리하는 안

| 구분 | 내용 | 현재 상태 |
|---|---|---|
| 먼저 연결할 주 경로 | GitHub 자산 생성 → 자기 PR에 쓸 내용 선택 → 프로필·서류와 자산 구성 → 링크 전달 → JD 기반 요약·근거 확인 | 목적과 주 경로 우선순위는 확인됨. 단계별 최소 기능은 제안 상태 |
| 함께 구현할 확장 경로 | HR의 후보 검색·소싱 | 기존 팀 합의 유지. 완성 수준은 자원과 함께 결정 |
| 기존 합의를 반영할 화면 | Catch 4구획, 선택 상한과 맥락 가이드, 프로필·한 장 요약·서류·RAG 열람 | 시작 문서 3절의 합의 유지. 상한 숫자·첫 화면·요약과 RAG의 재료 범위는 미결 |
| 기존 채용 시스템이 맡는 일 | 지원 접수, 전형 상태 관리, 면접 진행과 평가 기록 | v10 1-6절의 역할 분담 유지 |
| 추가 확정 없이 구현하지 않을 항목 | 구직자 문장 자동 작성·첨삭, 소셜 기능 전체, ATS 직접 연동 등 | 이번 설명만으로 새 범위를 승인한 것으로 해석하지 않음 |

이 표는 첫 흐름의 범위를 정리한 것으로, v10의 기능 목록을 모두 대체하지 않는다. 과금·공고·MCP 등 기존 항목은 필요한 흐름에 연결해 우선순위를 검토한다. 생략만으로 폐기하거나 기존 미결을 확정하지 않는다.

## 4. 성공 여부를 확인하는 방법 제안

이번 사용자 검증은 참여 가능한 응답자의 만족도·체감 유용성·개선 의견 조사로 진행한다. 팀이 HM 검증의 어려움을 공유했고, 2026-09-09 이 방식으로 조정하기로 했다. 실제 사용 가능한 서비스를 만든다는 목표와 기존 기능 범위는 유지한다.

### 이번에 조사할 내용

| 대상 경험 | 조사 항목 제안 | 남길 결과 |
|---|---|---|
| 구직자의 자기 PR 준비 | 경험 후보·근거·질문이 이해하기 쉬웠는지, 글에 담을 내용을 고르는 데 도움이 됐다고 느꼈는지 | 사용 만족도, 체감 유용성, 도움이 된 부분, 불편한 부분 |
| HR의 JD 기반 자료 확인 | 관련 자료를 살펴보기 편했는지, 요약과 근거 연결이 유용하다고 느꼈는지 | 응답자의 체감 유용성, 부족한 정보, 개선 의견 |
| HM의 상세 근거 확인 | 작업 기록을 이해하기 쉬웠는지, 더 확인할 지점을 생각하는 데 도움이 됐다고 느꼈는지 | HM이 응답하면 해당 사용 경험을 기록. 다른 역할의 응답은 그 응답자의 의견으로 구분 |

설문 구성과 결과 해석 기준:

- 가능하면 핵심 흐름을 짧게라도 직접 사용한 뒤 조사한다. 직접 사용한 응답은 사용 만족도·체감 유용성으로, 설명·시연만 본 응답은 기대 유용성·첫인상으로 구분해 기록한다.
- 응답자의 역할, 채용·기술 면접 경험, 직접 사용 여부를 기록한다. HM의 참여 가능 여부는 미정이며, 참여하지 못하면 HM의 업무 효과는 미검증으로 남긴다. 비HM 응답을 HM의 업무 효과로 일반화하지 않는다.
- 만족도 점수와 함께 도움이 된 부분, 불편한 부분, 신뢰하기 어려웠던 설명, 추가로 필요한 정보를 받는다. 응답자 수·응답 척도·결과 판단 기준은 조사 설계 때 정하며 목표 점수나 통과율을 임의로 확정하지 않는다.
- 결과는 실제 응답자와 체험한 기능의 범위에 맞춰 해석한다. 만족도 조사로 시간 단축, 작업 이해의 정확성, 채용 판단의 품질이 입증됐다고 주장하지 않는다.

### 후속 검증 가설

v10의 ‘면접관이 5분 안에 작업 내용과 물어볼 지점을 찾는다’는 아직 검증하지 못한 가설로 보존한다. 이번 조사의 통과 조건이나 프로젝트 완료 조건으로 삼지 않는다. HM의 참여와 과제 수행 관찰이 가능한 후속 단계에서 시간의 측정 범위와 완료 기준을 정해 검증한다.

### 팀 내부의 기능·자료 품질 확인

아래는 사용자 만족도와 별도로 진행할 내부 확인이다. 실제 HM의 실험 참여를 전제로 하지 않는다.

- 검증용 자료로 자산 생성 → 자기 PR 자료 구성·링크 전달 → JD 기반 요약·근거 확인의 동작이 이어지는지 확인한다. 검색·소싱도 기존 산출물 범위에 유지한다.
- Catch와 기업용 요약의 설명을 원본 근거와 대조하고, 발견된 오귀속·근거 없는 서술 문제를 수정한다.
- 근거 링크 동작과 Q2에서 정할 열람 범위를 확인한다. 요약·질의응답·전달 과정에서도 해당 접근 규칙과 공개 중단이 적용되는지 점검한다.
- 분석·요약 실패 시 상태를 알리고 기존 자료가 보존되는지 확인한다. 문제를 전달할 경로와 팀의 대응 담당자를 정하고 오류·처리량·API 사용량을 확인할 수 있게 한다.

조사 시작 전에는 응답 대상과 체험 방식, 설문 문항, 수집·정리 담당자를 준비한다. HM 시간 측정과 관찰 담당자 배정을 이번 조사의 필수 준비로 두지 않는다. 기능·자료 품질 확인 결과와 사용자 조사 결과는 구분해 남긴다. 기능별 요구사항과 확인 기준은 [요구사항 초안](./CatchU_requirements_draft.md)에 정리한다.

## 5. 질문과 답변 기록

### Q1. 구직자 가이드의 첫 범위 — 답변 받음

구상에 가까운 방식은 무엇인가?

- 정리된 GitHub 기록에서 활용할 경험 후보·근거·생각해볼 질문을 제시한다.
- 사용자가 작성한 주장이나 글에 연결할 GitHub 근거를 제안한다.
- 두 방식을 모두 제공한다.

[Answer]: 정리된 GitHub 기록에서 활용할 경험 후보·근거·생각해볼 질문을 제시한다. (사용자 답변, 2026-09-08)

반영: 기록에서 출발해 경험 후보와 근거를 확인하고, 질문을 통해 맥락을 돌아본 뒤 활용할 내용을 고르는 흐름으로 구체화했다. 기존에 작성한 글이나 주장의 입력을 이 가이드의 출발 조건으로 두지 않는 안을 제안한다. v10의 주장에 카드 후보를 연결하는 안은 참고안으로 보존한다.

### Q2. 기업이 JD 기반으로 확인할 자산의 범위 — 조건부 의견 받음

요약·질의응답이 참고할 GitHub 자산은 어디까지인가?

- 구직자가 해당 링크에서 열람하도록 선택한 자산까지.
- 구직자가 숨기지 않은 전체 자산까지.
- 아직 미정이며, 공개 범위 설계 때 비교한다.

[Answer]: 처음에는 숨긴 카드를 전역 처리하려고 생각했다. 카드 수가 줄어든다면 구직자가 해당 링크에서 열람하도록 선택한 자산까지 설정하는 것도 괜찮다고 본다. (사용자 의견, 2026-09-08)

반영: 링크별 선택 범위를 조건부 검토안으로 둔다. ‘카드 수가 줄어든다면’의 기준과 선택 부담은 아직 확인되지 않았으므로 공개 범위의 최종 결정으로 처리하지 않는다. 전역 숨김을 폐기한다는 결정으로도 해석하지 않는다.

설계 시 비교할 안: 링크별로 열람할 자산을 선택하면서, 전역 숨김은 이미 발행한 모든 링크에서도 특정 카드를 감추는 기능으로 함께 둘 수 있다. 이는 두 기능의 관계에 대한 제안이며 아직 채택되지 않았다. 어느 범위를 채택하든 요약·질의응답이 같은 열람 경계를 따르도록 하는 안을 함께 검토한다.

기존 기록: v10은 RAG에 숨김 제외 전체 Catch를 사용하는 안을 담고 있고, 한 장 요약의 재료 범위는 미결이다. 새 공개 범위를 정할 때 이 차이의 처리도 명시한다.

### Q3. 12월 중순 산출물의 성격 — 답변 받음

- 소수의 실제 구직자와 HR/HM이 사용하며 검증할 수 있는 서비스.
- 팀 발표에서 핵심 흐름을 보여주는 시연용 서비스.
- 아직 팀에서 결정하지 않음.

[Answer]: 소수의 실제 구직자와 HR/HM이 사용하며 검증할 수 있는 서비스 수준으로 생각 중이다. (사용자 답변, 2026-09-08)

반영: 실제 자료를 이용한 주 경로, 열람 통제, 오류 대응을 갖춘 서비스라는 산출물 목표는 유지한다. 이후 2026-09-09 결정에 따라 이번 사용자 검증은 만족도 조사 중심으로 조정했다. 참여 인원, 서비스 운영 시간, 운영 규모는 아직 정하지 않았다. 후속 자원 답변은 아래 Q4에 반영했으며, 역할·기술 환경과 작업량을 확인하기 전에는 일정 달성 가능성을 확정하지 않는다.

### Q4. 팀의 투입 시간과 월 예산 — 답변 받음

[Answer]: 기본적으로 평일 오전 9시부터 오후 6시까지 투입 가능하다. 추가적으로 필요하다면 설득이 필요하다. 서버·LLM/API 월 예산은 개인당 약 40만 원으로 생각하면 된다. (사용자 답변, 2026-09-08)

반영: 기본 일정은 4명이 평일 09:00~18:00에 참여하는 것을 기준으로 한다. 이 시간 전체를 순수 개발 시간으로 계산하지 않고 회의·휴식·검증 등을 고려해 작업량을 산정한다. 추가 근무를 일정 달성의 전제로 삼지 않는다. 월 예산은 4인 합산 약 160만 원 규모로 계획하되, 공용·개인 계정 간 배분은 아직 정하지 않았다.

### 추가 결정: 이번 검증 방식 조정 — 2026-09-09

팀은 HM 검증이 어려워 만족도 조사 정도로 진행할 수밖에 없다는 상황을 공유했다. 사용자는 만족도·체감 유용성·개선 의견 조사 중심으로 문서를 수정하고, 5분 목표는 후속 검증 가설로 남기며, 기능·자료 품질은 팀 내부에서 별도로 확인하는 방안을 승인했다. 실제 HM이 설문에 참여할 수 있는지는 아직 확인되지 않았다.

Q1에 의존하는 구직자 가이드 요구사항은 2절에, 이번 조사 방식·후속 가설·내부 확인은 4절에 구체화했다. Q2는 범위별 대안을 비교한 뒤 결정한다. 열람 범위가 미정인 동안 해당 결정에 의존하는 권한·요약·질의응답 설계는 확정하지 않는다. 확인된 시간·예산을 바탕으로 역할·기술 환경·작업량과 조사 대상·체험 방식을 구체화한다. HR→HM 전달 형식, 최초 화면 등은 그 다음에 필요한 질문으로 다룬다.
