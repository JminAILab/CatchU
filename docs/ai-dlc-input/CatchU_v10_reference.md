# CatchU 기획 문서 — AI-DLC 워크플로우 입력용

- 이 문서는 다른 문서를 참조하지 않는다. 필요한 내용은 본문에 풀어 썼다.
- 이 문서의 결정은 팀 검증 전이다.
- `[미결]` — 아직 정하지 않았거나 두 안이 공존하는 것. 6절에 질문으로 모았다.
- 이 문서에 없는 것은 "하지 않는다"가 아니라 "아직 안 적었다"이다. 특히 2-6의 제약 목록은 완전하지 않다.

## 입력 안내

- **이번 작업의 목표**: 이 문서를 출발점으로 요구사항 분석 → 유저 스토리 → 도메인 모델을 만든다. 6절의 미결은 시작 전에 다 답해야 하는 것이 아니라 요구사항 분석에서 물어야 할 목록이다. 단, 답이 나오기 전에 두 안 중 하나를 골라 진행하지 않는다.
- **"포함"의 뜻**: 4절의 포함은 제품 범위다. 1차 산출물의 우선순위(티어)는 이 워크플로우에서 배정한다. 배정 기준은 팀이 정한 것 둘뿐이다 — ① **주 경로가 먼저다.** 구직자가 자기 저장소에서 쓸 만한 기록을 발견한다 → 주장에 근거(카드)를 붙인다 → 링크로 전달한다 → 면접관이 실제로 한 일과 물어볼 지점을 확인한다. 이 흐름이 끝까지 이어지는 것이 1차 검증 대상이다 ② **검색·소싱은 확장 경로다.** 지금 만들되 완성도는 주 경로보다 낮게 둘 수 있다. 구직자 간 소셜(팔로우·DM·포스팅·피드)과 양측 MCP의 우선순위는 `[미정]`.
- **합의 상태** — 팀 결정과 사용자 검증은 별개다.
  - 팀이 회의에서 정한 것: 채용 동선은 외부 링크로 종료 / 대상은 신입·취준생에서 시작해 경력으로 확장, 양쪽 문을 모두 만든다 / 매칭 % 금지, "JD에 해당하는 내용 표기"까지 / 검색 UX는 기존 서비스와 비슷하게 두고 GitHub 데이터를 얹는다 / 커뮤니티는 확장 / 저연차 헤드헌팅은 출시 후 시간이 풀 문제 / 초기 사용자는 인공지능사관학교 수료생 / 인젝션 탐지는 전부 자동 / 운영은 자동 처리가 기본 / Catch 명칭 / HR은 요약·HM은 디테일 / 설계 우선순위 = 신뢰성 + 간편화(시간) / Catch 레이아웃 4구획 고정, 선택 상한과 맥락 가이드 / 보안·개인정보 기준을 기획 문서에 / JD 기반 개발자 한 장 요약 / 열람 화면 탭 = 프로필(대표 주장) · 한 장 요약(첫째 탭 자리) · 서류 · RAG, Catch 클릭 → Catch Detail / CatchU를 대표하고 모든 판단의 기준이 되는 핵심 한 줄을 만든다(문안은 미결)
  - 팀장이 정하고 팀이 아직 확인하지 않은 것: 서비스 정의 문장 / 프로필·프리셋·대표 주장 구조 / 카드 탐색 3층 / 기업 측 범위 / 렌즈 = JD 프리셋 하나 / RAG 자연어 서술 답변 / 자소서 원문·요약 병기 / MCP 양측 허용과 조건 / 팔로우·맞팔 DM·피드 / 카드 가시성 전역 1회 / 기술 스택 자가 입력 + 카드 표시 / 공개 범위 2단 / JD 기반 자소서 지원 제외 / 카드 간 관계 저장 안 함 / 시스템의 주장 생성 안 함 / JD 탭 대신 JD 사이드 패널(현재 화면의 JD 관련 대목 정리)
  - 가설(사용자 검증 전): P1의 고통 세 가지 — 구직자 인터뷰가 아직 없다 / P2의 고통 — 전용 인터뷰가 없다 / 3층 탐색이 회상을 돕는다 — 실측이 본인 1인 · 교육과정 레포 3개 / 얇은 카드(스냅샷형)가 부실해 보이지 않는가 / 면접관이 비어 있는 항목을 어떻게 읽는가
- **검증할 가설** — 기능 완성과 별개로 팀이 실제 사용자에게 확인할 것: ① 구직자가 카드에서 실제 면접에 쓸 경험을 발견하는가 ② 자기 주장에 붙일 근거를 스스로 고르고 설명할 수 있는가 ③ 면접관이 5분 안에 본인이 한 일과 물어볼 지점을 찾는가. 지원자를 점수화하는 것이 아니라 서비스가 의도한 도움을 주는지 확인하는 것이다.
- **품질 하한** (팀 확정 전): 근거 링크 유효율 100% — 깨진 링크는 품질 편차가 아니라 버그 / 타인 기여를 본인 것으로 표시하는 오귀속 0건 — 1건이라도 나오면 원인을 찾을 때까지 해당 기능 공개 보류
- **자원·제약**: 개발 4인 / 최종 산출물 2026년 12월 중순 / 팀원 역할·투입 가능 시간 `[미정]` / 사용 가능한 기술과 배포 환경 — 이 문서에서 제외했다, 팀장이 별도로 준다 / LLM·API 예산 `[미정]` / 산출물의 성격(시연용인지 실제 사용자 운영용인지) `[미정]`
- **원칙이 충돌하면**: 2절의 원칙 세 벌 중 임의로 하나를 고르지 말고 팀에 묻는다. 세 벌의 우선순위는 정해지지 않았다(6절 4번).

## 용어

| 용어 | 뜻 |
|---|---|
| **Catch (카드)** | GitHub 기록에서 사건 단위로 추출한, 문장마다 근거 링크가 붙은 객관적 서술 데이터. 점수·등급이 아니다. 이전 명칭 "증거카드". 본문의 "카드"는 Catch를 뜻한다 |
| **사건** | Catch 1장의 단위. 커밋 여러 개가 "하나의 작업 덩어리"로 묶인 것 |
| **경계 (근거 등급) A / B** | A = 본인이 묶은 단위(PR·브랜치 머지). B = 시스템이 규칙(같은 사람 + 같은 파일 + 시간 근접)으로 묶은 것. 카드와 그 카드가 나가는 모든 표면에 표시한다 |
| **서사형 / 스냅샷형** | 커밋이 여럿이라 판단의 흐름이 있는 카드 / 커밋 1개짜리 사실 스냅샷 카드. 스냅샷형이 다수다 |
| **주장** | 구직자가 쓴 "나는 어떤 개발자다" 문장에 근거로 카드 묶음을 붙인 것. 카드는 기록의 서술, 주장은 카드 기반의 자기 어필 |
| **대표 주장** | 주장의 프리셋. 여러 벌 중 디폴트 하나가 신원 페이지에 노출된다 |
| **프리셋** | 이력서·자소서·포트폴리오·대표 주장 각 항목이 여러 벌 가지는 버전. 링크를 발행할 때 항목별로 하나씩 고른다 |
| **링크** | 구직자가 발행하는 열람용 URL. 항목별 프리셋 한 벌씩 + 설정(만료일·비밀번호·다운로드·검색 허용). 기업은 이 링크로 열람 화면에 들어온다 |
| **열람 화면** | 링크로 열리는 기업용 화면. 탭: 프로필(신원 + 대표 주장) / 한 장 요약 / 이력서 / 자소서 / 포트폴리오 / RAG. JD 프리셋은 사이드 패널에 항상 떠 있다 |
| **한 장 요약** | JD 프리셋 기준으로 지원자를 한 장으로 정리한 렌즈 매핑. 근거로 Catch가 붙고, 클릭하면 Catch Detail이 열린다 |
| **Catch Detail** | Catch 한 장의 4구획 상세 화면(1-7). 요약·프로필·RAG 결과·검색 표시 어디서든 Catch를 클릭하면 열린다 |
| **JD 사이드 패널** | 열람 화면에 항상 떠 있는 JD 프리셋. 지금 보고 있는 화면(프로필·이력서·자소서·포트폴리오)에서 JD 항목에 대응하는 대목을 따로 정리해 보여준다 |
| **숨김** | 카드 단위·전역 1회의 가시성. 숨긴 카드는 프로필·링크·RAG·MCP 어느 경로에서도 없는 것으로 취급한다 |
| **공개 범위** | 구직자끼리 누가 보느냐 — 전체 공개 / 맞팔 공개 2단. 기업 열람 경로에는 적용되지 않는다 |
| **렌즈 / JD 프리셋** | 기업이 직접 입력한 조건(JD). 탐색과 열람 RAG에 걸어 "JD에 해당하는 내용"을 표기한다. 지원자에게 보이지 않는다 |
| **RAG 답변** | 숨김을 제외한 전체 카드를 재료로 렌즈를 걸어 자연어로 서술하는 답변. 문장마다 근거 링크, 평가 없음 |
| **검색 허용** | 링크 단위 스위치. 끄면 RAG 탭이 비활성 |
| **인재풀 노출** | 프로필 단위 스위치. 끄면 기업 검색에 잡히지 않는다 |
| **두 개의 문** | 링크 발행(지원자→기업, 지원 후, 주 경로) / 검색·소싱(기업→지원자, 지원 전, 확장 경로) |
| **MCP** | 구직자·기업이 자기 LLM·도구에서 우리 데이터를 읽는 경로 |
| **HR / HM** | 인사담당자·리크루터(P2) / 기술 면접관(P3) |
| **ATS** | 기업의 채용관리 시스템. 채용 프로세스는 거기서 돈다 |

## 1. 제품 정의

### 1-1. 한 문장 정의

**"구직자가 자기 자산을 쌓아두는 곳이고, 기업은 그 자산을 열람하러 들어온다."** 핵심은 구직자다 — 구직자가 많아야 이 포지션이 성립한다.

팀 결정: **이 프로젝트(CatchU)를 대표하는 핵심 한 줄**을 만들고, 그것을 모든 판단의 기준으로 삼는다. 그 한 줄이 위 정의 문장인지, 근본 명제("사람은 결과물이 아니라 판단의 흔적으로 설명된다")인지, 새로 쓰는지는 `[미결]`(6절 1번). 한 줄이 통과해야 할 시험 둘 — 밖으로: 설명 없이 서비스가 전달되는가 / 안으로: 어떤 기능의 포함·제외를 그 한 줄만으로 판정할 수 있는가.

부연 세 가지:
- 채용 프로세스와의 관계 — "CatchU는 채용 프로세스를 대체하지 않는다. 기업은 쓰던 ATS를 그대로 쓴다. 우리는 그 위에 판단 재료를 얹는다."
- 자산의 실체 — "개발자 구직자의 GitHub 활동에서 Catch를 추출해, 구직자에게는 면접 준비 자산으로, 기업에게는 서류·면접의 판단 근거로 제공한다."
- 기업이 읽는 방식 — 기업이 자기 기준(JD 프리셋)을 렌즈로 들고 와서 지원자의 주장과 증거를 한 화면에서 대조한다.

### 1-2. 해결하려는 문제

- **구직자(P1)**: "프로젝트와 GitHub에 개발 경험은 남아 있지만, 이를 기업이 이해할 수 있는 역량과 근거로 정리하고 전달하기 어렵다." 고통 ① 있는데 꺼내지 못한다 — "재료가 없어서가 아니라, 재료가 어디에 있는지 몰라서 못 쓴다" ② 말로는 다 설명하지 못한다 ③ 시간이 부족하다 — "들인 시간이 그 기업 하나로 끝난다"
- **기술 면접관(P3)**: "지원자의 개발 경험은 남아 있지만, 제한된 시간 안에 핵심 역량과 실제로 한 일을 판단하기 어렵다." 고통 ① 시간 부족 — "GitHub를 봐야 한다는 건 알지만 실제로는 확인하지 못한다" ② 판단 근거 부족 ③ 정보 분산 ④ 지원자마다 자료의 성격이 다르다
- **HR·리크루터(P2)**: "개발자를 뽑아야 하는데, 어디서 무엇을 판단해야 할지 모르겠다." 고통 ① 후보를 찾는 것 자체가 가장 어렵다 ② 기술을 몰라서 판단이 막힌다 ③ 보낸 연락에 답이 없다 ④ 시간 부족

### 1-3. 대상 사용자

- "산출물의 대상은 신입·취준생. 이들이 자리를 잡으면 경력 구간으로 확장한다." "양쪽 문(링크 발행·기업 검색)을 모두 만든다."
- 초기 사용자는 "인공지능사관학교 수료생으로 유지"
- 사용자 유형 4종 — P1 취준생·신입 개발자 / P2 HR·리크루터(30~150명 규모 IT 기업 인사담당자; 채용 대상은 개발자 전반, "소싱·헤드헌팅은 주로 경력 개발자에게 일어난다") / P3 기술 면접관(30~300명 규모 IT 기업 개발팀 팀장) / P4 서비스 운영자(운영을 겸임하는 개발팀 멤버 1명). 상세는 3절.
- P2가 소싱하는 대상은 주로 경력 개발자로, 지금 프로필을 올리는 사람(신입·취준생)과 다르다. 팀의 결정: 저연차는 인바운드 풀이 커서 기업이 헤드헌팅할 이유가 없다(HR 멘토링). public repo만 보는 동안 이 서비스는 신입을 위한 서비스이고, private repo 정리가 끝나야 경력직을 노릴 수 있다. 신입도 연차가 쌓이므로 헤드헌팅(검색·소싱)은 출시 후 시간이 쌓이면 풀리는 문제다 — 확장 경로로 지금 만들어 둔다.

### 1-4. 핵심 순간과 흐름

**장면**
- **구직자 두 모드**: 준비하는 모드(공고를 열고, 재료를 골라 자소서를 쓰고, 면접 답변을 준비) / 발견되는 모드(프로필을 올려두고, 공개 범위를 정해두고, 기업의 연락을 기다림)
- **두 개의 문**: 링크 발행(지원자→기업, 지원 후, "주 경로") / 검색·소싱(기업→지원자, 지원 전, "확장 경로를 미리 놓음"). "검색·소싱은 링크 발행의 부산물이고 역은 성립하지 않는다."
- **기술 면접관**: "ATS에서 지원자를 보다가, 링크를 통해 우리 화면으로 들어와 자기소개서·포트폴리오·프로필·증거 카드를 한 화면에서 확인한다. 카드를 검색하면 이 지원자에게 물어볼 지점이 드러난다." 진입 경로는 전달받는 경로(HR이 추린 후보의 링크) 하나다. HM은 직접 탐색하지 않는다 — 리크루팅·헤드헌팅은 HR의 업무다
- **HR**: ① JD 확보(HM이 작성한 기술 요건을 받아 공고 등록) ② 탐색(헤드헌팅, "가장 오래 머무는 화면") ③ 접촉(DM) ④ 전달(후보의 프로필 링크를 HM에게)
- **운영자**: "예외 처리자" — 자동 처리를 기본으로 하고, 사람은 자동으로 끝나지 않은 건만 본다
- "면접 준비 — 물어볼 지점 찾기"까지를 CatchU, "면접 진행·평가 기록"은 기업 ATS로 둔다
- **기업 화면의 구분(팀 결정)**: HR은 요약, HM은 디테일. HR은 후보를 고르고 넘기는 사람이라 한 장으로 보고, HM은 근거를 확인하는 사람이라 Catch·근거 링크까지 내려간다

**흐름** — 순서 자체가 결정인 지점은 ★. 나머지 순서는 AI-DLC가 다듬는다.

- **구직자**: 가입(GitHub OAuth) → 온보딩 안내 1장 → 저장소 연결(권한 고지) → 레포 선택 → 분석(이탈 가능, 완료 알림) → 카드 탐색(3층)·숨김 설정 → 대표 주장 작성(카드 후보 제안 → 확정) → 디폴트 지정 → ★서류 등록(이력서·자소서·포트폴리오) — 서류 유도는 저장소 연결 뒤에 둔다, 앞에 두면 서류가 이겨서 연결이 밀린다 → 링크 발행(항목별 프리셋 선택 + 설정) → 열람 기록 확인. 발견되는 모드에서는: 인재풀 노출·DM 수신 설정 → 기업 DM 수신 → 회사 프로필 확인 → 응답
- **HR**: 기업 가입·인증 신청(자동 승인, 이상 건만 심사) → 회사 프로필 → 공고 등록(외부 지원 링크) → JD 프리셋 입력·저장 → 구직자 검색(조건 필터 + JD 렌즈 표기) → 공개 프로필(디폴트 대표 주장 + 기본 정보) → 북마크·메모 → DM → 후보를 HM에게 전달. ★전달하는 것이 공개 프로필인지 지원자가 발행한 링크인지는 미결(6절 26번). ★검색·소싱은 링크 발행의 부산물이다 — 프로필이 쌓여야 검색할 대상이 생기고, 초기 공고는 운영자가 기입한다
- **HM**: ★링크로만 진입 → 비밀번호 → 한 장 요약(JD 기준. Catch를 클릭하면 Catch Detail) / 프로필(대표 주장) / 이력서·자소서·포트폴리오(사이드 JD 패널이 그 화면의 JD 관련 대목을 정리) → RAG 탭(서술 답변) → 물어볼 지점 확보 → 면접은 ATS·현장. 첫 화면(랜딩)이 무엇인지는 `[미결]`(6절 48번)
- **운영자**: 알림 → 예외 건을 한 화면에서 처리(전후 맥락·양측 이력·과거 처리 병기) → 사유 기록
- **MCP**: 구직자는 본인 데이터를, 기업은 ★링크 토큰 범위 안의 열람 데이터를 자기 도구에서 읽는다 — 열람 기록·숨김·등급·스위치가 그대로 적용된다

### 1-5. 우리가 하는 것

- 프로필·서류·Catch는 "구직자 소유이며 우리에 남는다"
- **Catch**: "'이 사람이 언제 무엇을 어떻게 작업했는지'를 기록으로 보여주는 단위. 점수도 등급도 아닙니다." "판단의 흔적을 보여주고, '왜'는 면접에서 본인이 말하게 하는 것." 카드 1장 = 사건 1개. 묶는 근거는 A(본인이 이미 묶어놓은 것: PR·브랜치 머지) / B(시스템이 규칙으로 묶은 것) 두 종류이며 카드에 표시한다
- **카드와 주장은 다르다**: 카드는 기록의 객관적 서술이 담긴 데이터이고, 주장은 그 카드를 근거로 한 자기 어필이다
- **대표 주장(어필 층)**: "지원자가 '나는 어떤 개발자다'라는 주장을 쓰면, 시스템이 그 주장에 대응하는 카드 후보를 제안하고 지원자가 확정한다." "대표 카드 선정 주체 = 지원자. 시스템은 고르지 않고 3층 재료만 제공한다." — 층 1 사실 속성 묶음(측정) / 층 2 커밋 메시지 원문(인용, 날짜 병기) / 층 3 diff(열람). 시스템이 주장을 생성·추천하지 않는다. 주장에 붙일 수 있는 Catch 수에는 상한을 둔다(숫자 미정) — 카드가 많아질수록 개성이 희석되고 고르는 일이 번거로워진다(팀 결정). 고를 때 맥락 가이드를 준다. 상한 대비 몇 장을 썼는지는 기업에 보이지 않는다
- **프로필(신원 페이지)**: 헤드라인·경력·스킬 + 대표 주장(디폴트 프리셋)
- **구직자 자산과 프리셋**: 이력서·자소서·포트폴리오·대표 주장이 각각 프리셋을 여러 벌 가진다. 카드 전체 목록이 재료다. "공통 데이터로 분리 보관. 재사용" — "경로가 늘어도 서류 묶음은 한 벌이다"
- **링크 발행**: 각 탭에서 프리셋을 하나씩 골라 발행한다. 공고는 붙이지 않는다 — 지원자 측 JD 입력이 없기 때문. 만료일 / 비밀번호(필수) / 다운로드 / 검색 허용. 만료 상태 / 열람 기록 / 즉시 중단 / 재발행
- **열람 화면(기업이 링크로 여는 화면)** (팀 결정): 탭은 프로필(신원 정보 + 이 링크에 담긴 대표 주장 — "주장 + 붙은 카드 + 근거 링크 + 경계 등급") / 한 장 요약 / 이력서 / 자소서 / 포트폴리오 / RAG. 대표 주장은 별도 탭이 아니라 프로필 한 장 안에 있다. 한 장 요약이 대표 주장이 있던 자리(첫째 탭 위치)에 들어간다. Catch는 어디서 보이든 클릭하면 Catch Detail(4구획)로 열린다
- **개발자 한 장 요약 (팀 결정)**: Catch만 나열하면 오히려 읽는 시간이 늘어난다. 그래서 이 개발자에 대한 한 장 요약을 JD 프리셋 기준으로 만든다 — 프론트엔드를 뽑는 JD면 백엔드 기록은 들어가지 않는다. 형태는 렌즈 매핑이다: JD 항목별로 대응하는 Catch·서류 대목을 링크와 함께 놓고, Catch를 클릭하면 Catch Detail이 열린다. 서술 규칙(문장마다 근거 링크, 판정어·점수·순위 없음, 미달 시 목록으로 강등)이 그대로 적용된다. JD에 대응하는 기록이 없는 항목은 "기록 없음"까지만 — 부족으로 렌더링하지 않는다. 열린 것: 재료의 풀 — 이 링크에 담긴 프리셋(지원자가 고른 것)까지인가, 숨김 제외 전체 Catch인가(RAG와 같은 풀) / 지원자가 자기 요약을 볼 수 있는가(렌즈는 지원자에게 안 보인다는 결정과 부딪힌다) / 생성·갱신 시점 — 링크 발행 시점에는 기업의 JD가 없으므로 그때 고정할 수 있는 것은 원본 프리셋뿐이다. 요약은 기업이 JD를 넣을 때 생성되는가, JD를 바꾸면 갱신되는가, JD 없이 연 열람자는 무엇을 보는가 / 자소서를 재료에 넣는가 / HR용 요약 화면과 같은 것인가 — 6절 47번
- **자소서 원문·요약 병기**: 기업에게 자기소개서를 원문과 요약본 둘 다 보여준다. JD 사이드 패널이 자소서 화면에서 JD 관련 대목을 따로 정리해 주면 그것이 매핑형 요약이다 — 별도 요약본이 그래도 남는지, 사이드 패널이 대체하는지 `[미결]`(6절 10번). 요약 문장에도 카드와 같은 규칙(문장마다 원문 링크, 평가 문장 없음)을 적용하는지 `[미결]`
- **RAG 답변**: 숨김을 제외한 전체 카드를 재료로, JD 프리셋을 렌즈로 걸어 자연어로 답한다. 답변은 서술에 한정한다 — ① 모든 문장에 근거 링크 ② 판정어·점수·순위 없음 ③ 조건을 못 채운 답변은 카드 목록으로 강등. "출력은 카드 목록과 링크뿐"이라는 형식 제약은 기본 출력에서 쓰지 않고 강등 단계에만 남긴다. 기업이 그 답변 위에서 판정하는 것은 기업의 판단이다
- **프롬프트 인젝션**: 입력 측 자동 탐지 + 출력 검사. 자연어 답변 허용으로 출력 형식 제약이라는 2차 방어선이 약해진다는 것을 인지하고 채택한다. 막는 것을 시도하되 실패하면 기술 부채로 기록한다
- **렌즈**: 기업이 직접 입력한 JD 프리셋 하나. 탐색과 열람이 같은 프리셋을 쓴다 — 같은 목적이기 때문. 회원은 저장·재사용, 비회원 또는 등록 전이면 JD 입력란. 지원자에게 안 보인다. 지원자 JD와 공고 JD는 렌즈로 쓰지 않는다 — 사유: 지원자가 넣는 렌즈는 유무 자체가 평가에 영향을 주고 그 정확도를 우리가 검증할 수 없다 / 공고는 이미지 형식·자사 ATS 유도가 많아 렌즈용 JD를 따로 입력하는 흐름이 생긴다. 탐색에서 렌즈는 "JD에 해당하는 내용이 이력서·포트폴리오·카드에 있으면 그것을 표기하고 자료를 제공하는 선"까지다. **열람 화면에서는 JD 사이드 패널로 항상 떠 있다(팀장 안)** — 별도 JD 탭 대신, 지금 보고 있는 화면(프로필·이력서·자소서·포트폴리오)에서 JD 항목에 대응하는 대목을 따로 정리해 보여준다. 조건: 항목별 대응 유무를 세어 보여주지 않는다(개수·%·색 없음 — 나란히 놓인 유/무는 읽는 사람이 세어 점수를 만든다) / 대응 없는 항목은 "해당 내용 없음"까지 / 항목 순서는 JD 순서 그대로, 대응 많은 순으로 정렬하지 않는다
- **기업 측**: 회사 프로필 / 채용공고 등록(JD) — "지원 버튼은 자사 ATS로 나가는 외부 링크" / 구직자 검색(기술 스택·연차 중심 + 희망 조건 필터, JD 렌즈 표기) — 탐색은 HR의 일이고 HM은 전달받은 링크로 열람한다 / DM(구직자 수신 ON/OFF, 신고, 욕설·성희롱 등 필터링) / 북마크·메모
- **구직자 사이**: 팔로우는 일방, 맞팔이 되면 관계 성립, 1단만. 팔로우의 목적 — 원치 않는 DM 최소화, 팔로우한 사람의 포스팅 피드, 프로필 정보 탐색 범위 제한. DM은 맞팔 사이에서 가능. 맞팔이면 프로필 데이터를 추가로 볼 수 있다. 포스팅 + 피드(팔로우한 사람의 글, 시간순). 설정: 팔로잉 목록 공개/비공개, 기업 인메일 알람 ON/OFF
- **MCP**: 구직자 — 평소 쓰는 자기 LLM으로 본인 데이터(카드·서류·주장)를 읽는다. 자소서·포트폴리오를 JD와 대조하는 점검은 우리 화면이 아니라 여기서 한다. 기업 — 링크 토큰 범위의 열람 데이터를 기업의 도구(ATS·LLM)에서 읽는 것을 허용한다. 허용하는 이유: 현재 채용 프로세스를 거스르지 않기 위해서다. 조건: MCP 접근도 열람 기록에 남는다 / 응답에 숨김이 반영되고 경계 등급이 포함된다(외부 도구가 등급을 화면에 표시하는지는 보장 못 한다) / 링크 비밀번호·검색 허용 스위치가 MCP에도 적용된다. 기업이 자기 LLM으로 판정하는 것은 관여하지 않는다
- **운영**: 자동 처리가 기본. 사람이 보는 것은 "필터를 통과했는데 신고된 건", "AI가 이상을 감지한" 기업 인증 건, "AI가 해결하지 못한 문의", "신고 누적·제재 판단"
- GitHub OAuth를 통한 저장소 연결
- **ATS와의 분담 중 CatchU 몫**: 지원자 서류 열람(구직자가 등록한 것 + GitHub Catch) / 주장의 근거 확인(카드 → 커밋·PR) / 면접 준비 — 물어볼 지점 찾기(카드 검색)

### 1-6. 우리가 하지 않는 것 (다른 주체가 맡는 것)

- **채용 프로세스 — 기업 ATS**: "채용 프로세스는 기업 ATS에서 돈다. 우리 안에서 채용이 완결되지 않는다. 우리 안의 채용 동선은 외부 링크를 거는 것으로 종료"
- **지원 접수 / 지원자 파이프라인 관리 / 전형 상태 추적**
- **면접 진행·평가 기록 — 기업 ATS**
- **판정 — 사람이 한다**: 점수·등급·순위·적합도·매칭 %를 만들지 않는다. 채용 판단은 기업이, 안전 판단(규칙 위반)은 운영자가 결정. MCP를 통해 자신의 LLM으로 사람을 판정해도 우리는 관여하지 않는다. 그것은 고객의 판단이다
- **주장 생성 — 지원자가 한다**: 취준생이 자기 LLM(MCP)으로 카드를 읽고 방향을 잡는 것은 고객의 판단. 우리는 관여하지 않는다
- **진정성 검증 — 면접이 한다**: AI 생성 여부를 판별하지 않는다
- **자소서·이력서 작성·첨삭 — 관여하지 않는다**: 작성에 쓸 GitHub 데이터를 가져다줄 뿐이다. 구직자가 직접 쓰든 LLM을 쓰든 관여하지 않는다. 기업 열람용 자소서 요약(1-5)은 별건이다
- "사이트 밖으로 나가지 않는다"는 원칙은 "문서 확인에서 사이트 밖으로 나가는 것을 최소화한다"로 읽는다. 이를 위해 MCP를 막는 것은 고객의 want에 반한다
- 그 밖의 항목은 5절.

### 1-7. Catch — 고정 레이아웃, 예시, 서술 규칙

**레이아웃은 4구획으로 고정한다 (팀 결정)** — 무엇을 했나 / 판단의 흐름 / 궤적 및 기록 / 기록에 없는 것. 카드마다 같은 자리에 같은 것이 있어야 5분 안에 훑을 수 있다.

| 구획 | 내용 | 어디서 나오나 |
|---|---|---|
| 무엇을 했나 | 사건 요약 | diff |
| 판단의 흐름 | 시간순 전개. 각 항목에 커밋·PR 링크와 작성자 표시(본인 / 타인은 가명 author_0n). 개수·비율로 요약하지 않는다 | 커밋 시각 + diff + 파일 변화 + 커밋 작성자 |
| 궤적 및 기록 | 코드 위치(파일·함수), 커밋·diff 링크, 사용 기술, 경계 등급 — A: "본인이 묶은 단위(PR #n)" / B: "시스템 추정 — 적용 규칙: 동일 저자 + 같은 경로 + n시간 이내"(규칙을 문장으로 보여준다) | 파일 경로 · 코드 · 묶음 규칙 |
| 기록에 없는 것 | 흔적은 있는데 이유가 안 남은 지점 — 면접에서 물어볼 지점 | 흐름의 공백 |

이전 필드 8종의 행방: 무엇을 했나·판단의 흐름·기록에 없는 것은 그대로 / 본인 기여는 흐름의 작성자 표시로 / 어디에 있나·사용 기술·경계 등급은 궤적 및 기록으로. **유형(의사결정·문제해결·협업·완성도·판단 유보)과 연결(렌즈 대응)의 자리는 `[미결]`**(6절 46번) — 아래 예시에는 임시로 제목 줄에 뒀다.

**예시 1 — 상한 (가상. 기록이 충실한 팀 프로젝트, 주문 모듈 담당)**

> **주문 처리의 재고 차감 동시성 문제 해결** · 유형: 문제해결 · 경계 A(PR #23)
> **무엇을 했나** — 동시 주문 시 재고가 음수로 내려가는 버그를 발견하고, 낙관적 락을 시도했다가 비관적 락으로 전환해 해결.
> **판단의 흐름** — 7/12 재현 테스트와 함께 버그 보고 [커밋·본인] → 7/13 낙관적 락 구현 [커밋·본인] → 7/15 비관적 락으로 전환 — "동시 주문이 몰리는 시간대엔 충돌이 잦아 재시도 비용이 더 컸음" [PR #23·본인]
> **궤적 및 기록** — `order/service.py`의 `deduct_stock()`, 결제·알림 모듈이 이 함수를 호출 · [커밋 7/12·본인] [커밋 7/13·본인] [PR #23·본인] · SQLAlchemy, MySQL `SELECT FOR UPDATE` · 경계 A(PR #23)
> **기록에 없는 것** — 락 전환 판단이 실측 기반이었는지 추정이었는지 / 데드락 가능성 고려 여부 — 커밋·PR에 남아 있지 않음

가장 값진 구획은 "시도했다가 버린 흔적"(낙관적 락)이다 — 완성 코드에는 안 보이는 층위다.

**예시 2 — 실물 서사형 요약 (기록이 좋은 레포, 5커밋)**

> **카카오맵 컴포넌트 재작성과 신구 병행 배치** — 지도 컴포넌트를 새 구조로 재작성 → 마커 모듈을 TS에서 JS로 전환 → 최종적으로 기존 구현을 복원하고 새 버전을 별도 파일로 남김. 모든 문장에 실제 커밋 링크.

"시도했다가 되돌렸다"는 흔적이 그대로 보인다. 이력서에는 절대 안 쓰는 내용이지만 면접관에게는 "왜 되돌렸어요?"라는 질문거리다. 카드는 자격 증명이 아니라 면접에서 대조할 좌표다.

**예시 3 — 하한 (실물. 커밋 메시지가 부실한 레포, 단일 커밋)**

> **목록 렌더링 key 바인딩 교체** · 경계 B(시스템 추정 — 작성자 분리 + 파일 겹침 + 240분) · 유형: **판단 유보** — 문제해결(렌더링 오류를 목격하고 수정)일 수도, 완성도(알려진 취약 패턴의 예방적 교정)일 수도 있으나 단일 시점 기록만으로는 구분 불가
> **무엇을 했나** — 팔로우·팔로잉 두 목록의 `v-for` `:key`를 배열 인덱스에서 항목 값으로 교체 (+4/−4, 1파일). 커밋 메시지("key_fix")는 대상만 지시할 뿐 내용 복원에 기여하지 못했고, 서술은 전적으로 diff에서 나옴
> **판단의 흐름** — 구조적 부재. 시계열이 점 1개다. 유일한 단서는 diff의 − 줄(수정 전 상태가 인덱스 key였다는 사실) — "무엇에서 무엇으로"는 있으나 "언제·왜 인지했나"는 없음 [커밋·본인]
> **궤적 및 기록** — 목록 컴포넌트 1파일, +4/−4 · [커밋·본인] · Vue · 경계 B(시스템 추정 — 작성자 분리 + 파일 겹침 + 240분)
> **기록에 없는 것** — ① 계기: 실제 렌더링 오류를 목격했나, 학습 자료·코드 리뷰에서 알게 됐나 ② 교체한 항목 값이 목록 안에서 고유했는가 ③ 수정 후 문제가 해소됐는지 확인했는가

하한에서도 카드는 만들어진다. "무엇을"은 메시지 품질과 무관하게 diff에서 복원되지만, "왜"와 "흐름"은 커밋 개수(기록의 시계열성)가 만들지 diff가 만들지 않는다. 실측에서 사건의 62~87%가 이런 커밋 1개짜리였다.

공동 작업 사례(타인 커밋이 섞인 사건)의 실물 예시는 아직 없다. 그 경우 흐름의 각 커밋에 본인 / author_0n 표시가 붙는다.

실물 예시(2·3)의 커밋 링크는 이 문서에서 뺐다. 카드 품질 검증에 쓸 때 원본 저장소의 커밋·diff를 연결한다.

**서술 규칙** — 예시의 서술문은 사람이 diff를 읽고 쓴 것이다. 생성 주체(사람/LLM)는 미결(6절 13번)이지만 규칙은 같다.

| 쓴다 | 안 쓴다 |
|---|---|
| 락 전환의 판단 근거가 커밋·PR에 남아 있지 않습니다 | 판단 근거가 부족합니다 |
| 면접에서 물어볼 수 있는 지점입니다 | 이 부분을 보완하세요 |
| 당신이 요구한 '동시성 처리'에 대응하는 기록이 이것이다 (기준을 낸 사람이 주어) | 이 사람은 백엔드 적합도 82%다 / 이 코드는 좋다·나쁘다·위험하다 (시스템이 주어, 형용사) |
| 이렇게 짰다 (과거 사실) | 이 코드를 보니 대규모도 할 수 있겠다 (전이 예측) |
| 근사 복원 — 실질 차이 2곳 | 복원(원본과 일치) — 기록이 말하는 것보다 강한 서술 |
| 유형: 판단 유보 — 단일 시점 기록으로는 구분 불가 | 근거 없이 문제해결/완성도로 분류 |

- 문장마다 근거 링크가 붙는다. **링크가 있다는 것과 링크가 문장을 뒷받침한다는 것은 다르다** — 생성문은 근거와 사실을 대조하는 검사를 거친다. 실측에서 "복원"이라 쓴 문장이 기계 대조로 "근사 복원"으로 정정된 적이 있다.
- 카드가 얇은 것(스냅샷형)은 기록 형태의 한계이지 평가 근거가 아니다. 밀도가 낮다는 표시가 "역량이 낮다"로 미끄러지지 않도록, 빈 구획은 결함이 아니라 면접 질문거리로 제시한다.

## 2. 설계 원칙과 제약

### 2-0. 설계 우선순위 (팀 결정)

**신뢰성 + 간편화, 특히 시간.** 신뢰성은 근거를 직접 열어 검증할 수 있는 것이고(근거 링크 유효율·사실 일치), 간편화는 읽는 사람의 시간을 아끼는 것이다(HR 요약·한 장 요약·5분 밀도). 두 축이 부딪히는 자리가 하나 있다: 간편화는 요약을 부르고, 요약은 시스템이 화자가 되는 순간 판정으로 미끄러진다. 그래서 간편화는 서술 규칙(1-7) 안에서만 구현한다 — 짧게 만들되 링크 없는 문장·평가 문장은 만들지 않는다.

원칙 체계가 세 벌 있다. 셋의 관계와 우선순위를 정한 문서는 없다(6절 4번).

### 2-1. 헌법 5원칙

헌법 5원칙과 근본 명제("사람은 결과물이 아니라 판단의 흔적으로 설명된다")가 현행 설계에 그대로 적용되는지는 미판정 `[미결]`.

| # | 원칙 | 요지 |
|---|---|---|
| 1 | 비판정 | 점수·등급·적합도 예측을 내리지 않고 판단 재료(증거 매핑)만 제공. 최종 판단은 사람. "별표의 주어가 시스템이면 판정, 사람(기업)의 입력 기준이면 매핑". RAG 자연어 답변(서술 한정) 결정으로 적용 범위가 "서술 허용·평가 금지"로 구체화됐다 |
| 2 | 일관성 ≠ 진정성 | 커밋·PR·코드도 AI 생성 가능하므로 진정성은 증명 못 한다. 일관성·구체성의 증거까지만 제공하고 진정성 검증은 면접으로 |
| 3 | 동의 기반 접근 | 모든 분석은 본인 동의에서 시작. 공개 ≠ 처리 동의. public repo만 |
| 4 | 데이터 거버넌스 | 최소 수집, 집계·익명 통계만, 벡터 완전 삭제 보장, 타인 발화 익명화 |
| 5 | 예측이 아니라 사실 | "무엇을 할 수 있는가"(예측)에 직접 답하지 않고 "무엇을 했는가"(사실) × 렌즈 × 검증으로 분해 |

### 2-2. 서비스 원칙 4개

| 원칙 | 내용 |
|---|---|
| 원칙 1 | 평가하지 않는다. 제안: "채용 판단(이 사람이 이 자리에 적합한가)은 하지 않는다 / 안전 판단(이 행위가 규칙을 위반했는가)은 한다 — AI는 1차 선별까지, 제재 결정은 사람" 구분을 추가 `[미결]` |
| 원칙 2 | 사이트 밖으로 나가지 않는다 — "문서 확인에서 사이트 밖으로 나가는 것을 최소화"로 해석. 정확한 문안은 `[미결]`(6절 6번) |
| 원칙 3 | 공개 범위는 본인이 정한다 |
| 원칙 4 | 주장과 근거를 연결한다 |

### 2-3. 설계 원칙 10개

| # | 원칙 |
|---|---|
| 1 | **시스템은 사람을 판정하지 않는다.** 점수·등급·순위·적합도·합격 예측을 만들지 않는다. 판별 기준은 문장의 주어 — "이 사람은 백엔드 적합도 82%다"(시스템이 주어)는 금지, "당신이 요구한 '동시성 처리'에 대응하는 기록이 이것이다"(기준을 제시한 사람이 주어)는 허용. 정렬 가능한 수치는 곧 순위이므로 적합도 정렬은 위반. 검색: 자연어로 묻고 자연어 서술로 답하되, 문장마다 근거 링크, 판정어·점수·순위 없음, 미달 시 카드 목록으로 강등 |
| 2 | **기록이 얇은 것을 역량이 부족한 것으로 렌더링하지 않는다.** 사건의 다수가 커밋 1개짜리다. `근거 없음`은 되고 `부족함`은 안 됨. 진행률 바·완성도 %·경고색·느낌표처럼 결핍을 강조하는 장치를 카드·역량 영역에 쓰지 않는다. 검색 결과 0건도 "해당하는 카드가 없습니다"까지 |
| 3 | **카드의 두 축을 섞지 않는다.** 가시성(카드 단위·전역 1회 — 숨긴 카드는 어디에도 없음)과 큐레이션(프리셋별로 다름). 회사별 공개 범위 설정은 만들지 않는다 |
| 4 | **큐레이션의 정성도를 열람자에게 노출하지 않는다.** 기본값 사용 여부·수정 횟수·발행까지 걸린 시간 — 노출하면 "프리셋 관리 성실도"라는 새 스펙이 생긴다 |
| 5 | **카드는 주장을 금지하는 장치가 아니다.** 지원자가 근거를 골라 주장하는 것은 정상적인 논증. 문제는 근거 없는 주장 |
| 6 | **서술의 모든 문장에 근거 링크가 붙는다.** 사람이 쓰든 AI가 쓰든 근거 없는 문장은 내보내지 않는다 — 환각 통제 장치. RAG 답변 문장에도 적용. 자소서 요약 문장 적용 여부는 `[미결]` |
| 7 | **묶음의 근거 등급을 카드에 표시한다.** A(본인이 묶은 것: PR·브랜치 머지) / B(시스템이 규칙으로 묶은 것: 같은 사람 + 같은 파일 + 시간 근접). B는 틀릴 수 있는 층이고 그 사실을 숨기지 않는다. A와 B를 한 카드로 병합하지 않는다. 등급은 카드를 벗어나는 모든 표면(검색 결과·열람 화면·MCP 응답)에 따라붙는다 |
| 8 | **타인의 데이터는 수집 시점에 가명 처리한다.** `author_01` 형태. 완전히 지우지 않는 이유는 협업 구조("3명이 참여했고 본인 몫은 이 커밋들")를 남기기 위해. 목적은 재식별 방지가 아니라 우리 서비스가 지원자의 옛 팀원에 관한 서비스가 되지 않게 하는 것. 코드에 남은 API 키 등은 자동 마스킹 |
| 9 | **외부 텍스트는 지시가 아니라 데이터다.** 커밋 메시지·README·코드 주석·공고 본문·열람자의 검색 질의 전부. 방어: 입력 측 자동 탐지 + 출력 검사 + 카드 목록 강등. 실패 시 기술 부채로 기록 |
| 10 | **분석은 본인 동의에서 시작하고, public 레포만 본다.** 공개돼 있다는 것이 처리 동의는 아니다. 비공개 레포는 회사·동료 자산이 섞여 범위 밖. 연결 해제와 데이터 삭제는 본인이 직접 |

### 2-4. 그 외 설계 결정

| 결정 | 내용 |
|---|---|
| 카드 선정 | 시스템은 모든 사건을 카드로 만들고 거르지 않는다 — 거르면 암묵 판정. 측정값(커밋 수·코드 비율)으로 정렬·추천하지 않는다 — 3층 탐색으로 대체. 소유자가 수백 건을 전수 선택하는 것은 비현실이므로 재료(그룹·메시지 원문·diff)로 돕는다 |
| 열람 RAG의 대상 | 숨김을 제외한 전체 카드. 제출된 대표 주장에 한정되지 않는다 — 기업은 제출된 주장을 보고 같은 화면에서 주장 밖을 직접 검색한다. 전제: 가입 시 "연결한 레포의 기록을 기업 열람에 개방한다"에 명시적으로 동의, 동의 범위 = 연결한 레포 |
| 렌즈 층위 분리 | 카드 추출(사실 계층)은 기업 렌즈에 중립. 렌즈는 정렬·검색·연결(관점 계층)에만. 기업별 재추출은 카드를 기록이 아닌 맞춤 서사로 만들므로 하지 않는다 |
| 수량 지표 배제 | 카드 수·커밋 수·지원자 간 집계·비교 뷰를 기업 표면에 제공하지 않는다 — 수량은 점수의 원재료이고, 커밋 쪼개기 조작이 보상받는 유일한 지점. 카드 안의 "본인 기여"도 개수·비율이 아니라 커밋별 작성자 구분으로 표시한다 |
| 카드 스냅샷 고정 | 카드는 생성 시점 기준으로 고정. 재분석은 소유자가 명시적으로 실행할 때만, 그때 카드가 달라질 수 있음을 고지 |
| 가명화의 경계 | 링크 너머(GitHub) 재식별은 막지 않는다 — 검증 가능성을 우선한 선택임을 명시 |

- 한 장 요약의 재료 풀은 미정이다(6절 47번) — "링크에 담긴 프리셋"이면 프로필 탭 열과 같은 규칙을, "숨김 제외 전체"면 RAG 열과 같은 규칙을 따른다. JD 사이드 패널은 지금 보고 있는 문서만 읽고 다른 자료를 끌어오지 않는다(팀장 안) — 그래서 그 열의 규칙을 따른다. 검색 허용 OFF일 때 둘이 각각 어떻게 동작하는지는 미정이다.
- 기업 MCP에 대한 요구는 "응답에 숨김 반영과 경계 등급을 포함한다"까지다. 외부 도구가 등급을 화면에 표시하는지는 우리가 보장할 수 없다 — 요구할 수 있는 것과 없는 것을 구분한다.

## 3. 사용자와 페르소나

### 3-1. 사용자 유형과 목표

| 유형 | 실질적 목표 |
|---|---|
| P1 취준생·신입 개발자 | 하나뿐인 프로젝트에서 무엇을 골라 보여줄지 / 근거 있는 면접 답변 / 경험을 데이터·근거로 증명 / "말이 아니라 자료로 나를 보여주고 싶다" / 한 번 정리해둔 것이 계속 쓰이는 것 / 내가 못 찾은 회사가 나를 찾아오는 경로 |
| P2 HR·리크루터 | 후보를 찾아내고 싶다 / 개발자가 아니어도 볼 만한지 가늠 / HM에게 넘길 때 "왜 이 사람인지" 한 줄 / 보낸 연락에 답 / HM의 시간을 덜 쓰고 싶다 |
| P3 기술 면접관(HM) | 우리 팀과 맞는지 / 실제 프로젝트에서 무엇을 했는지 / GitHub·프로젝트를 빠르게 이해 / 근거 있는 질문을 내 손으로 준비 / 판단을 남에게 맡기지 않고 내가 [인터뷰] |
| P4 서비스 운영자 | 운영 때문에 개발이 끊기지 않는 것 / 사용자 피해를 빨리 막는 것 / 같은 상황에서 같은 판단 |

- P2·P3 사이의 긴장: HM은 AI 판단을 거부("내 판단을 대신하지 마라"), HR은 환영(JD 적합도 %). 원칙 1에 따라 HM 쪽 요구를 채택했다. 그 결과 P2는 원하는 것을 온전히 받지 못하는 사용자다
- P4는 방향이 반대: 이 페르소나의 성공은 "덜 등장하는 것"이다

### 3-2. 대상에서 제외·축소한 것

- 1차 핵심 고객은 면접관이 아니라 구직자다. 기업은 있으나 "보는 쪽"이다 — 기업을 뺀다는 뜻이 아니라 주체가 구직자라는 뜻
- P2의 대상에서 "신입"을 뺐다 — 헤드헌팅은 신입 개발자에게는 거의 일어나지 않는다
- P3의 "직접 탐색 경로"를 뺐다 — 리크루팅·헤드헌팅은 HR의 업무다
- P4에서 개발자 관심사(개인정보 처리 법적 근거·인젝션 탐지·로그·헬스체크)를 뺐다 — 운영자 여정에서 제외, 기능은 유지
- 커뮤니티(익명 게시판)는 확장 — 1차 산출물 범위 밖. 실명 프로필에 붙는 포스팅·피드는 별개이며 포함이다
- P1의 고통에서 "평가 기준 불투명"·"탈락 후 원인 불명"·"CS 기초·코딩 테스트 부담"·"가벼울 것" 요구를 뺐다 — 탈락 원인은 우리가 알 수 없고, 취업이 절박한 사람은 시간이 걸려도 한다

## 6. 미결 질문 목록

문서상 답이 없거나 두 안이 공존하는 것만. 괄호는 관련 절. 취소선은 답한 것.

**제품 정의·원칙**
1. CatchU를 대표하는 핵심 한 줄 — 1-1의 정의 문장인가, 근본 명제인가, 새로 쓰는가. 시험 둘: 설명 없이 서비스가 전달되는가 / 그 한 줄만으로 기능의 포함·제외를 판정할 수 있는가 (1-1)

47. 개발자 한 장 요약과 JD 사이드 패널 — ① 한 장 요약은 어디까지 읽는가: 이 링크에 담긴 프리셋(지원자가 고른 것)까지인가, 숨김 제외 전체 Catch(RAG와 같은 풀)인가. 전체면 지원자가 담지 않은 Catch를 시스템이 첫째 탭에 밀어 올리는 것이 된다 ② JD 패널은 현재 보고 있는 문서만 읽는가, 다른 자료도 가져오는가 ③ 검색 허용 OFF일 때 요약과 패널은 각각 어떻게 동작하는가 ④ 지원자가 자기 요약을 볼 수 있는가(렌즈는 지원자에게 안 보인다는 결정과 부딪힌다) ⑤ 생성·갱신 시점 — 발행 시점에는 기업 JD가 없으므로 원본 프리셋 고정과 요약 결과 고정은 별개다. 기업이 JD를 입력·변경하면 요약은 언제 생성·갱신되는가 ⑥ HR이 HM에게 전달할 때 같은 JD와 요약을 공유하는가 ⑦ 자소서를 재료에 넣는가 ⑧ 서술 규칙 미달 시 강등 형태 ⑨ HR용 요약 화면과 같은 것인가, HM도 보는가 (1-5, 2-7, 4-2)
48. 열람 화면의 첫 화면(랜딩)은 한 장 요약인가 프로필(대표 주장)인가 — 5분 안에 읽는 사람은 첫 탭만 본다. 첫 탭이 요약이면 읽기의 틀이 지원자의 주장에서 JD로 바뀐다. JD를 입력하지 않은 열람자는 처음에 무엇을 보는가. RAG 탭은 그대로 남는가 (1-4, 4-2)
