**원본 문서:** `대표 페르소나 P3 — 기술 면접관(HM) v3.0`
**용도:** 기능명세서 작성 시 입력값. 페르소나 본문에서 분리해 별도 관리한다.

## 1. 개정 이력

### 기업 페르소나 v1.0 → P3 v2.0 (2026-09-01)

기존 "기업 페르소나"의 내용은 실제로 **기술 면접관(HM)**이었으므로 번호를 재배치하고, "확장 대상: HR 채용 담당자"를 **P2로 분리**했다.

| | P2 (HR·리크루터) | P3 (김도윤 / HM) |
| --- | --- | --- |
| 하는 일 | **찾는다** | **본다** |
| JD | 받아서 공고로 등록 | **기술 요건을 작성** |
| 고통 | 사람을 못 찾는다 | 볼 시간이 없다 |
| 주 기능 | 검색·추천·DM | 증거 카드 열람 |

주요 변경: [추론] 태그를 8/27 인터뷰 결과로 승격 / "면접 질문 추천" → "질문거리가 되는 근거" / 지원자 비교·평가 근거 저장 삭제 / 고통 ④(도메인 편차) 신설 / 시나리오 3개 신설.

### P3 v2.0 → v3.0 (2026-09-01) — 팀 논의 반영

| 구분 | 내용 |
| --- | --- |
| **변경 ①** | **"서비스가 관여하는 구간은 면접 직전까지"라는 서술 삭제.** ATS와의 관계를 표로 다시 정의 (2장) |
| **변경 ②** | **"기여도"라는 표현 전면 제거** → "이 사람이 실제로 한 일" / "누가 무엇을 했는지" (3장) |
| **변경 ③** | 시나리오에 **JD 작성 국면 신설** — HM이 JD 기술 요건을 작성하고 HR이 공고로 등록. P2 v2.0과 방향 일치 |
| **삭제** | **HMW-5**(GitHub 미사용 도메인의 공정성) — 4장 |
| **추가** | 공감지도 듣는 것에 **"이 사람 기술적으로 어떤 것 같아요?"**(동료 면접관) · **"이런 사람은 어때요?"**(HR) |

## 2. 서비스 위치 재정의 — 이번 개정의 핵심

### 무엇이 문제였나

v2.0은 이렇게 적혀 있었다.

> "서비스가 관여하는 구간은 면접 직전까지다. 면접 진행과 그 이후의 평가·기록은 우리 범위 밖이다."

이 문장은 **"채용 프로세스는 ATS가 하고 우리는 프로필 링크만 발행한다"**로 읽힌다. 우리 서비스가 링크 발행기로 축소돼 보이고, 실제로 제공하는 판단 재료가 지워진다.

### 새 정의

**CatchU는 채용 프로세스를 대체하지 않는다. 기업은 쓰던 ATS를 그대로 쓴다. 우리는 그 위에 판단 재료를 얹는다.**

| 구간 | 기업 ATS | CatchU |
| --- | --- | --- |
| 공고 게시 · 지원 접수 · 전형 관리 | ✔ | — |
| 지원자 서류 열람 | ✔ 기업이 받은 것 | ✔ 구직자가 등록한 것 + **GitHub 증거** |
| 주장의 근거 확인 | — | ✔ 카드 → 커밋 · PR |
| 면접 준비 — 물어볼 지점 찾기 | — | ✔ 카드 검색(RAG) |
| 면접 진행 · 평가 기록 | ✔ | — |

**"면접 직전까지"가 아니라 "서류와 면접 준비 과정에 재료를 제공한다"가 정확하다.**

### 8/28에 기각한 방향과 어떻게 다른가 — 반드시 구분해야 한다

8월 28일 회의에서 **"기업 ATS에 API로 데이터를 가공해 보내는 구상"**은 기각되었다. 이번 재정의가 그것과 혼동되면 안 된다.

| | 기각된 안 (8/28) | 이번 정의 (v3.0) |
| --- | --- | --- |
| 데이터가 어디에 있나 | 기업 ATS로 **보낸다** | **우리 쪽에 있다** |
| 기업이 보는 화면 | 기업 ATS 화면 | **우리 화면** (링크로 진입) |
| 연동 개발 | ATS별 API 연동 필요 | **불필요** — 링크 하나 |
| 데이터 관리 책임 | 기업 | **구직자 본인** (원칙 3) |

> **"ATS에 보여준다"는 표현을 문서에 쓰지 않는다.** ATS를 쓰는 담당자가 **링크를 눌러 우리 화면으로 들어와** 본다는 뜻이며, 이것이 원칙 2(사이트 밖으로 나가지 않는다)와도 맞는다.

### 확정 정의서와의 관계 — 확인 필요

확정 정의서 8장은 **"채용 프로세스 참여"를 하지 않는 것**으로 명시하고 있다. 이번 재정의는 그 결정을 뒤집지 않지만, **"면접 준비에 재료를 제공한다"는 층이 8장에 적혀 있지 않다.**

→ **확정 정의서 6.1 서비스 흐름도에 이 층을 추가할지 팀에서 결정해야 한다.** (미결 1번)

## 3. "기여도"를 쓰지 않는다 — 용어 정리

팀 논의에서 **"기여도"가 퍼센트로 읽힐 위험**이 지적되었다. 우리는 비율을 계산하지 않는다.

| 쓰지 않는 표현 | 대신 쓰는 표현 |
| --- | --- |
| ~~프로젝트별 기여도 분석~~ | **프로젝트에서 이 사람이 실제로 한 일** |
| ~~개인 기여도~~ | **누가 무엇을 했는지** / 맡은 부분 |
| ~~기여율 · 참여도~~ | (사용하지 않음) |

**왜 위험한가** — "기여도 70%" 같은 표기는 원칙 1(평가하지 않는다)과 정면으로 부딪히고, 8/27 인터뷰에서 거부된 "점수화·등급화"와 같은 것으로 읽힌다. **표현 하나가 서비스 성격을 바꿔버린다.**

### 함께 맞춰야 할 곳

| 문서 | 현재 표기 | 조치 |
| --- | --- | --- |
| `P3 페르소나 v3.0` | — | ✔ 반영 완료 |
| `P1 설계 노트 v2.0` | "팀 프로젝트 개인 기여 분리" | 표현 검토 필요 |
| `KPI v3.0` | **"개인 기여 귀속 정확도"** | **유지해도 무방** — 비율이 아니라 *"이 사람이 했는가"*의 정확도이며, 내부 평가 지표이지 사용자 화면 문구가 아니다 |
| `확정 정의서` | — | 해당 표현 없음 |

## 4. HMW-5 삭제와 고통 ④의 처리

**삭제된 HMW-5:** *"GitHub를 쓰지 않는 도메인의 지원자를 불리하게 만들지 않을 수 있을까"*

### 고통 ④는 남는다

도메인별 GitHub 활용 편차(게임 업계 등)는 8/27 인터뷰에서 실제로 지적된 문제이므로 **고통 ④로 유지한다.** 다만 **우리가 풀 문제로 세우지 않는다.**

| 처리 | 내용 |
| --- | --- |
| 고통으로 기록 | ✔ 유지 — 면접관이 실제로 느끼는 어려움 |
| HMW로 세움 | ✗ 삭제 — 우리가 답할 질문이 아니다 |
| 스코프 처리 | **안티 페르소나로 명시** — "사내 저장소·비공개 코드 중심 도메인"은 이 서비스의 대상이 아니다 |

### 설계 제약은 유지한다

설계 제약 5번(**GitHub 활동량 자체를 지표로 쓰지 않음**)은 HMW-5가 없어져도 유효하다. 근거가 "도메인 공정성"에서 **"원칙 1 — 활동량은 평가가 아니다"**로 옮겨간다.

> 커밋 수·기여 그래프 같은 **양적 지표를 전면에 세우지 않는다**는 뜻이다. 활동은 근거의 위치를 가리키는 데 쓰고, 많고 적음을 판정에 쓰지 않는다.

## 5. "물어볼 지점"의 경계선 — 결정 필요

팀 논의에서 **"카드 목록을 RAG로 검색하면 이 사람의 질문거리를 만들어준다"**는 표현이 나왔다. 이것이 v1.2의 Won't Have와 어디까지 양립하는지 확정해야 한다.

**v1.2 F-09:** *"예상 질문 생성은 하지 않는다"*
**8/27 인터뷰:** *"내 판단을 대신하지 마라"*

### 두 해석

| 해석 | 내용 | 원칙 1 |
| --- | --- | --- |
| **A. 재료까지** | 검색하면 관련 카드들이 나오고, 면접관이 그것을 보고 질문을 만든다 | ✔ 안전 |
| **B. 문장까지** | 검색 결과로 질문 문장을 생성해 보여준다 | ⚠ v1.2 Won't Have와 충돌 |

### 현재 문서는 A로 쓰여 있다

페르소나 v3.0은 *"물어볼 지점이 되는 근거 — 질문 자체가 아니라, 질문을 만들 재료"*로 적었고, 시나리오 ④는 *"질문은 내가 만든다. 서비스는 재료까지만 준다"*로 닫았다.

**P1의 자소서 지원과 같은 선이다.**

| | 포함 | 제외 |
| --- | --- | --- |
| **P1 (자소서)** | 카드를 추천한다 | 문장을 쓰거나 평가한다 |
| **P3 (면접)** | 물어볼 지점을 드러낸다 | 질문 문장을 생성한다 |

> **원칙 1이 양쪽에서 같은 형태로 적용된다.** 기능명세에서 하나의 규칙으로 쓸 수 있다.

**다만 팀이 B를 의도했다면 v1.2 Won't Have를 명시적으로 해제해야 한다.** 지금 상태로 개발에 들어가면 담당자마다 다르게 구현한다. (미결 2번)

## 7. 서비스가 해결하지 않는 것

| 항목 | 사유 |
| --- | --- |
| 면접 진행 · 면접 기록 | 기업 ATS의 몫 (2장 표) |
| 평가 근거 저장 · 평가표 | 상동. 북마크 + 메모까지가 범위 |
| 지원자 간 비교 · 순위 | 원칙 1 |
| 면접 질문 문장 생성 | v1.2 Won't Have. 5장 참조 |
| 사내 저장소·비공개 코드 분석 | 분석 대상은 공개 Git · GitHub · GitLab |
| 도메인별 공정성 보정 | 4장 — 안티 페르소나로 처리 |

> **고통 ⑤(면접 이후 기록 부족)는 실재하지만 우리가 풀지 않는다.** 페르소나에는 남기되, 기능으로 이어지지 않는다는 점을 명시해야 나중에 "이것도 해야 하지 않나"가 반복되지 않는다.

## 8. 페르소나가 만드는 설계 제약

| # | 제약 | 근거 |
| --- | --- | --- |
| 1 | **한 화면, 5분 안에 훑을 수 있는 밀도** | 채용이 부업이라 확보 가능한 시간이 그만큼뿐 |
| 2 | **모든 요약 항목에 한 뎁스 내 근거 링크** | [인터뷰] 명시 요구. 요약을 못 믿는 사람도 쓸 수 있어야 함 |
| 3 | **점수·등급·강점 정리·순위를 만들지 않음** | [인터뷰] 명시 거부 + 원칙 1 |
| 4 | **팀 프로젝트에서 누가 무엇을 했는지 구분해 표시** | 판단 근거 부족의 핵심. **비율이 아니라 구분이다** (3장) |
| 5 | **GitHub 활동량 자체를 지표로 쓰지 않음** | 원칙 1 — 많고 적음은 평가가 아니다 (4장) |
| 6 | **ATS를 쓰는 사람이 링크 하나로 들어올 수 있어야 함** | **신설.** 2장의 서비스 위치. 별도 연동 없이 진입 |

### 제약 4가 이 페르소나의 핵심

김도윤이 알고 싶은 건 "이 프로젝트가 좋은가"가 아니라 **"이 사람이 이 프로젝트에서 뭘 했는가"**다. P1의 한지우도 같은 것을 증명하고 싶어 한다. **양쪽 페르소나가 같은 기능을 요구하는 유일한 지점**이라 우선순위가 가장 높다.

### 제약 6이 P2·P3를 잇는다

P2 시나리오 ④(전달)와 P3 시나리오 ②(후보 확인)는 **같은 링크의 양쪽 끝**이다. 기능명세에서 이 링크의 형태(권한·유효기간·열람 범위)를 정의해야 한다.
