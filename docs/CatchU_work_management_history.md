# CatchU 작업관리 결정 이력

> 지위: [작업관리](CatchU_작업관리.md)와 [코딩 절차](CatchU_coding_procedures.md)의 결정 이력. 2026-10-01에 작업관리 §8에서 옮겼다([#197](https://github.com/JminAILab/CatchU/issues/197)). 새 항목은 이 파일 끝에 더한다. 옛 항목의 절 링크는 옮기기 전 작업관리를 기준으로 쓴 것이다.

- 2026-09-14 — Codex·Claude Code가 공통 작업관리 기준을 읽도록 적용 준비안과 이슈·PR 양식을 작성. 담당·일정 확정 및 원격 Project 생성·연결은 포함하지 않음.
- 2026-09-14 — 사용자가 Projects 사용법을 몰라도 작업을 시작하도록, 일상적인 작업 의도에서 AI가 먼저 기존 작업을 조회하고 필요한 질문 1~2개를 던지는 착수 안내를 추가했다. 이미 답한 내용·확정 제품 행동은 다시 묻지 않으며, 와이어프레임 초안도 실행 작업으로 구분했다.
- 2026-09-15 — 회의 가결에 따라 PR 본문을 결론 우선 구조로 바꿨다. 결론과 리뷰 요청을 찾으려면 본문을 끝까지 읽어야 하던 문제(PR #33·#36·#38·#39)를 줄이기 위해 양식 맨 위에 요약을 두고, 선택 항목은 해당 없으면 지워 작은 PR이 길어지지 않게 했다. 판단·갱신 기준은 §4 `PR 본문`에 두었다. 같은 변경에서 dev를 기본 브랜치가 아닌 것으로 전제한 안내(§4 종료, §5 양식)를 실제 기본 브랜치 확인과 `Closes`/`Refs` 기준으로 고쳤다.

- 2026-09-16 — 회의 결정(#60)에 따라 작성자의 내용 확인·직접 설명, 실제 리뷰어 지정, 잘못 올린 PR의 종료·기록 보존을 §4에 추가했다. AGENTS.md·CLAUDE.md의 기존 공통 문서 연결을 그대로 사용한다.
- 2026-09-16 — 이슈 본문을 결론 우선 구조로 바꿨다. 상단만 읽어서는 무엇을 만드는 작업인지 알 수 없던 문제를 줄이기 위해 `요약`을 첫 칸으로 두고 `결과물`을 흡수했으며, 선행 조건·담당 제안을 조건부로 내렸다. 분량 제한이 아니라 배치·중복·경과 누적이 원인이므로 판단 기준을 §4 `이슈 본문`에 두었다. `bug.yml`은 버그 등록 사례가 없어 이번 변경에서 제외하고 첫 실제 사례로 검증한다.
- 2026-09-16 — 라벨 체계는 현행을 유지하기로 했다. `mvp-october`는 Project 자동 편입 스위치이고, 기능 영역은 제목 접두사, 우선순위·상태는 Project 필드로 표현한다. 같은 의미의 라벨을 따로 두지 않는다.
- 2026-09-17 — PR #63 리뷰에 따라 설명 상대를 명확히 하고 PR 처리 절 제목을 이슈 종료 절과 구분했다. 잘못 올린 PR은 열린 경우 닫아 보존하고, 이미 머지된 경우 사유 댓글과 후속 PR로 처리하도록 보완했다.
- 2026-09-17 — 우선순위 필드가 빈 이슈(#56·#59·#60·#61)가 생겨, 새 이슈를 등록하기 전에 AI가 우선순위를 묻고 답으로 `우선순위` 필드를 설정하도록 §4 착수 안내와 착수 5번에 넣었다. 우선순위는 본문이 아니라 필드에 두는 기존 원칙을 유지한다. 정하지 못한 경우에는 등록을 막지 않고 미정으로 드러낸다.
- 2026-09-20 — 최소 코딩 하네스 논의와 교차검토에 따라, 완료 기준의 기대 결과·현재 작업 폴더 변경 보존·계약/공통 변경·검사 선택/보고·사람 리뷰·자료/로그 보호와 초기화 후 준비 확인을 보완했다. 초기화 조건은 합의된 범위·기존 착수 조건과 실행에 필요한 미결 확인으로 두었다. 임시 통합 브랜치 운영안을 컨벤션에 연결하고, 자동 배포 선택·기능 개발 우선·지연 시 로컬 시연 검토를 후속 입력으로 기록했다. 서비스별 실제 명령은 초기화 결과를 기다리며, 새 아키텍처 결정·담당 확정·구현 착수 승인·CI/배포 완료는 포함하지 않는다.
- 2026-09-23 — 팀장 결정에 따라 §7에 [코딩 운영](CatchU_작업관리.md#코딩-운영)을 두었다. AI-DLC 절차가 복잡해 진행이 늦어져, 코딩은 이슈·`dev` PR 흐름으로 하고 AI-DLC는 계약·마일스톤 기록에 쓴다. 9/24에 코딩 사용 여부를 담당자가 정하도록 바꿨다. 뼈대에 CI를 넣지 않으므로 80% 커버리지·머지 전 CI는 CI 도입 전까지 머지 조건이 아니다. PostgreSQL·TypeORM·Redis 확정, BullMQ·서비스 LLM 보류를 기록했다.
- 2026-09-23 — PR 요약이 문단이 되고 ID·절 번호와 승인 구분 문장이 반복돼 리뷰어가 요약만으로 판단을 시작하지 못했다(#91, PR #74 리뷰). 9/15 구조는 유지하고 `PR 본문`·PR 양식·AGENTS.md의 해당 문장을 교체했다. PR #93 리뷰에 따라 ID 뜻과 절 제목을 본문에 쓰고 정의 링크는 보조로 붙이도록 명시했다.

- 2026-09-28 — 사용자 요청에 따라 [PR #108](https://github.com/JminAILab/CatchU/pull/108)(관련 [#96](https://github.com/JminAILab/CatchU/issues/96))에서 도입한 선행 2~3개만 등록하는 제한을 없앴다. 파트 전체의 분할 목록을 먼저 제시하고, 모든 하위 이슈 분할에서 최소 범위·확인할 결과를 적을 수 있는 작업은 개수 제한 없이 연결·등록한다. 선행 작업 미완료·구현 세부사항의 미결은 등록을 미루는 이유로 삼지 않으며, 최소 범위나 결과를 정할 수 없는 항목만 요약에 남겼다가 질문으로 정해지면 등록한다. 파트 분할 안내의 질문 수는 공통 절차와 같이 한 번에 1~2개로 명시했다.
- 2026-09-28 — 팀장 결정으로 §3의 '주 작업은 사람당 진행 중 하나를 기본'이라는 문장을 삭제했다. 9/14 초안에 근거 기록 없이 들어간 문장이며, 한 사람이 여러 작업을 병렬로 진행하는 실제 운영과 맞지 않는다.
- 2026-09-28 — 팀장이 담당 사이의 연결을 매번 해석·전달하고, 전체 검증표 검토가 작은 API 연결의 대기 조건이 되던 부담을 줄이려고 §4 「진행·검토」·「코딩 전 범위와 기존 변경 확인」과 §7 「코딩 운영」의 기존 항목을 교체·보완했다(새 항목 없음). 계약 PR 병합 뒤 비어 있던 API 명세·ERD 링크도 채웠다. 같은 PR에서 명세가 있으면 별도 준비 산출물 없이 구현하는 기본 흐름, 필요할 때만 질문, 준비된 일부 선행의 관계 해제를 해당 문장에 넣고 이슈·PR 양식의 반복 칸을 줄였다.

- 2026-09-30 — [#189](https://github.com/JminAILab/CatchU/issues/189)에서 비AI-DLC 공통 지침을 점검했다. AGENTS.md의 서비스·승인 문서 안내를 갱신하고, 착수·검토·종료 시 공통 문서를 읽도록 하던 안내를 작업에 해당하는 절을 실제로 읽는 표로 구체화했다. CLAUDE.md는 표를 참조하고 이 절에서 정본·읽기 경로의 유지보수 위치를 명시했다. 9/16에 보류한 버그 양식은 공통 규칙과의 정합성을 위해 담당·분류를 조건부로 맞추고 합성 초안을 시험했다. 실제 버그 등록 사례의 검증은 남아 있다. PR의 검사 증거 기록 조건도 명확히 했으며 기존 우선순위 질문·승인·머지 정책은 유지한다.
- 2026-09-30 — 교차 검토 후 사용자가 기존 계약 분류를 유지하도록 결정했다. [시험안 635549e](https://github.com/JminAILab/CatchU/commit/635549edf5ca38d4acc2a36d2b7a0efed7a15a13)의 요청 필드·경로·메시지 등을 포함하는 확대 문구를 철회하고, §7에 [9/23 후속 결정](../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/domain-design/2026-09-23-followup.md)과 [계약 소유 규칙](../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/contract-design/contract-summary.md#contract-ownership-rules)의 기존 분류를 복원했다. 확대 필요성은 미채택 제안이며 별도 결정 없이 운영 기준으로 적용하지 않는다. 과거 승인 원본은 수정하지 않았다. 기존 이슈·PR 본문 변경과 계약 문서 수정의 읽기 경로, 절 제목·refresh 시 표 보존 안내를 보완했다.
- 2026-10-01 — 팀장 요청으로 §4 「코딩 전 범위와 기존 변경 확인」 첫 문단에 코드 작성 지향 기준 3개를, 「자료와 실행 로그」에 실패 분류 한 구절을 넣었다([#182](https://github.com/JminAILab/CatchU/issues/182)). 평소 코딩 경로에는 내부 구조 기준이 없었다. AGENTS.md 카드로 두는 안도 시험했으나, #189의 읽기 표가 코드 수정 때 이 절을 가리키게 되어 매 세션 읽히는 분량을 늘리지 않고 이 문서에 두었다. §4의 지향 기준은 머지 조건이 아니며, 줄 수·인자 수 상한은 넣지 않았다.
- 2026-10-01 — 작업관리 §4의 「코딩 전 범위와 기존 변경 확인」부터 「PR 본문」까지 다섯 절과 §7 「코딩 운영」을 [코딩 절차](CatchU_coding_procedures.md)로, §8의 결정 이력을 이 파일로 옮겼다([#197](https://github.com/JminAILab/CatchU/issues/197)). Codex는 도구 호출 한 번의 출력이 약 40 KB를 넘으면 앞뒤 약 20 KB만 남기고 가운데를 버리는데, 작업관리(약 52 KB)에서 버려지는 구간이 바로 이 절들이었다. Claude Code도 읽기 한도(약 25,000토큰)까지 여유가 약 5%였다. 내용은 바꾸지 않았고([#182](https://github.com/JminAILab/CatchU/issues/182)의 지향 기준 문장도 절과 함께 옮겼다), 바깥 링크가 가리키는 「코딩 운영」은 제목과 안내를 남겼다. 기각: Codex 출력 한도 설정 상향(호출 한 번의 한도가 프로그램에 고정돼 효과 없음), 작업관리 안에서 순서만 바꾸기(잘리는 절만 바뀜), 서비스 폴더에 CLAUDE.md 두기(상위 파일 가져오기 승인 문제가 남음), 원칙 문장을 AGENTS.md 본문에 두기(다른 코딩 절의 잘림이 남음).
- 2026-10-02 — [코딩 절차](CatchU_coding_procedures.md) 「검사 선택과 결과 보고」에 서비스 문서 배치·크기 규칙을 넣었다([#202](https://github.com/JminAILab/CatchU/issues/202)). 기능별 동작·연결 안내는 서비스 README에 덧붙이지 않고 그 README 맨 위에 적힌 기능 문서 위치에 쓰며, README에 이미 있는 기능 절은 그 기능을 고칠 때 옮긴다(팀장 결정). 서비스 README·규약·기능 문서가 36 KB를 넘으면 절을 나눠 옮긴다. 작업관리([#197](https://github.com/JminAILab/CatchU/issues/197))와 api README([#199](https://github.com/JminAILab/CatchU/issues/199))가 작업마다 절이 덧붙어 Codex가 가운데를 버리는 크기를 넘었고, api README 맨 위 안내만으로는 다른 서비스에 닿지 않았다. web·worker README 맨 위에 각 기능 문서 위치를 적었고, 크기 검사는 [#201](https://github.com/JminAILab/CatchU/issues/201)의 CI 범위에 넣기로 했다. 기각: 서비스마다 같은 폴더 이름 강제(web이 쓰는 기능 폴더 README 방식과 충돌), 작업관리 §8의 크기 규칙을 넓히기(코드를 고치는 AI의 읽기 경로에 없음), 서비스 폴더마다 AGENTS.md 두기(저장소 루트에서 연 Codex 세션은 하위 폴더 AGENTS.md를 읽지 않고, 코딩 절차는 이미 코드 수정 읽기 경로에 있음).
- 2026-10-03 — [#201](https://github.com/JminAILab/CatchU/issues/201)에서 dev 대상 PR의 CI를 도입해, [코딩 절차](CatchU_coding_procedures.md) 「코딩 운영」 검사 행과 작업관리 §7의 "CI 도입 시점과 필수 상태 검사는 별도 이슈에서 정한다"를 실제 기준으로 바꿨다. CI는 서비스 README의 검사 명령과 문서 크기 상한을 확인하고, 통과해야 dev에 머지되도록 필수 상태 검사를 걸기로 했다(팀장 결정, 적용은 PR #208 머지 직후). 80% 라인 커버리지는 계속 머지 조건이 아니다. 경로별 실행·우회 권한과의 관계는 [레포 컨벤션](CatchU_레포_컨벤션.md) 결정 이력에 있다. 같은 변경에서 「검사 선택과 결과 보고」에 새 테스트를 서비스 검사 명령이 찾는 위치·이름에 두라는 문장을 더했다(팀장 요청). CI는 각 서비스의 검사 명령만 실행해, 위치·이름이 다른 테스트는 실패 표시 없이 빠지기 때문이다.
