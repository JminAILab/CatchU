## 전체 흐름 그림

```
[취준생]                    [시스템]                         [기업/면접관]

레포 연결 + 개방 동의 ──→  ① 수집 (읽기 전용)
  (동의 범위 = 연결한          · 타인 정보는 저장 전에 가명 처리
   레포. 연결 안 한 레포는     · API 키 등 시크릿은 자동 마스킹
   시스템에 존재하지 않음)          │
                           ② 사건 묶기
                              · 커밋들을 "하나의 작업 덩어리"로
                              · 묶은 근거를 반드시 함께 기록
                                   │
                           ③ 카드 생성 (전부 다)
                              · 탈락 없음 — 모든 사건이 카드가 됨
                              · 카드는 생성 시점 기준으로 고정
                                   │
                           ④ 정렬·추천 (소유자 화면 전용)
                              · 점수 아님 — 측정값으로 줄 세우기만
                              · 이 순위는 기업에게 보이지 않음
                                   │
         ┌─────────────────────────┘
         ▼
⑤ 소유자가 카드 상태 결정
   · 대표 : 내세울 카드 (몇 장) ──────────────→  첫 화면에 보임
   · 대기 : 기본 상태 (나머지 전부) ──────────→  검색하면 보임
   · 숨김 : 감출 카드 ························→  아예 안 보임
                                                       │
                                              ⑥ 기업의 사용
                                                 · 첫 화면: 대표 카드
                                                 · 검색: 숨김 빼고 전체
                                                 · 면접장에서 "이분 ○○
                                                   경험 있나?" → 즉시 검색
```

## 각 단계, 한 문장씩

1. **수집** — 취준생이 보여주기로 선택한 public 레포만 연결합니다(개방 동의의
   범위 = 연결한 레포). 커밋·코드 변경 내역을 읽기 전용으로 가져오되, 함께 작업한
   타인의 이름·이메일·계정은 저장 전에 가명으로 바꾸고, 코드에 남은 API 키 등은
   자동으로 가립니다.
2. **사건 묶기** — 커밋 하나는 너무 잘고 레포 전체는 너무 크니, 중간 단위인
   "사건"으로 묶습니다. 어떻게 묶었는지는 항상 함께 기록합니다.
   (자세한 방법은 별도 문서 "카드는 어떻게 만들어지는가")
3. **카드 생성** — 모든 사건이 카드가 됩니다. 시스템이 걸러내지 않습니다 —
   걸러내는 순간 그게 곧 평가가 되기 때문입니다. 카드는 생성 시점의 기록으로
   고정됩니다(레포에 커밋이 추가되어도 기존 카드가 소리 없이 바뀌지 않음).
4. **정렬·추천** — 시스템이 측정값(커밋 수, 코드 비율 등)으로 "볼만한 순서"를
   만들어 **소유자에게만** 보여줍니다. 이 순위·수치는 기업 화면에 나가지 않습니다.
   [가설] 추천 상위 10~20장 — 적정 개수는 인터뷰로.

   > **[09-02 정정] ④는 폐기됐다.** 측정값(커밋 수·코드 비율)으로 카드를
   > 줄 세우는 정렬·추천은 하지 않는다 — 화면목록 v0_4 A04가 품질순·중요도순
   > 정렬과 점수·등급을 전역 금지로 두었다.
   > 대체된 것은 둘이다. ① 탐색은 **3층 회상 구조**(그룹 → 커밋 메시지 원문 →
   > diff, A04-01~03) ② 카드 고르기는 **주장 기반 후보 제안**(A05-03).
   > 근거: 08-30 실측에서 메타데이터 묶음만으로는 회상이 성립하지 않았고,
   > 커밋 메시지 원문 층에서 회상이 일어났다.
5. **소유자 결정** — 대표 카드 몇 장을 고르고, 감출 건 숨김으로. 나머지는 대기.
   [가설] 대표는 프로젝트당 3~5장 — 면접관이 몇 장을 보는지 인터뷰로.
6. **기업의 사용** — 첫 화면엔 대표 카드, 검색은 숨김 제외 전체. 면접 중 궁금한
   경험을 그 자리에서 검색해 바로 봅니다. 열람 요청·승인 왕복은 없습니다 —
   면접 시간(30분~1시간)에 성립하지 않기 때문입니다.

## 왜 이렇게 정했나 — 핵심 결정 4가지

**① 시스템은 줄만 세우고, 고르는 건 소유자** — 시스템이 카드를 걸러내면 암묵적
평가가 됩니다. 전부 만들고, 정렬만 하고, 선택권은 소유자에게. 정렬이 놓친 카드는
소유자가 검색해 대표로 올릴 수 있습니다.

**② 기업 검색은 대표만이 아니라 (숨김 빼고) 전체** — 대표 몇 장만 보인다면
포트폴리오와 다를 게 없습니다. 차별점은 "본인이 보여주기로 한 것 너머를 기업이
질문할 수 있는 기록"입니다. 이 검색은 본인도 모르던 강점을 발견해줄 수 있고 —
같은 원리로 약점도 발견될 수 있습니다. 그 대칭을 받아들이는 대신, 카드에는
판정이 없고 사실과 링크만 있어서 발견된 것에 대해 본인이 면접에서 반론할 수
있습니다. 전제: 가입 시 "연결한 레포의 기록을 기업 검색에 개방한다"를 명시적으로
동의받습니다.

> **[09-02 확인] ②는 유효하다.** 열람 화면의 RAG 검색이 그 자리다 —
> 대상은 숨김을 제외한 공개 카드 전체이며, 지원자가 제출한 세트에
> 한정되지 않는다.
> 세트(어필 프리셋)는 "나는 ○○한 개발자입니다" 형태의 주장 2~3개와
> 거기 붙인 카드 한 벌이고, 회사마다 다르게 낼 수 있다. 그 옆에서 RAG는
> 주장 층 없이 카드만 다룬다. 기업은 제출된 주장을 보고, 같은 화면에서
> 주장 밖을 직접 검색한다 — 둘 다 있어야 대조가 성립한다.

**③ 사실은 하나, 관점은 위에** — 카드 내용은 어느 기업이 보든 같습니다. 기업마다
다른 건 "무엇을 먼저 찾는가"(검색·정렬)뿐. 기업 렌즈로 추출 자체를 바꾸면 카드가
기록이 아니라 맞춤 서사가 됩니다.

**④ 세기 쉬운 숫자는 기업에게 안 보여준다** — 카드 수·커밋 수 같은 수량 지표와
지원자 간 비교·집계 화면은 기업 쪽에 제공하지 않습니다. 이유 둘: 수량은 점수의
원재료가 되기 쉽고(우리는 비판정), 커밋 쪼개기 같은 부풀리기가 이득을 보는
지점을 없애기 위해서입니다. 조작이 보상받는 지표를 아예 화면에서 빼는 것이
"진짜인지 판별"하는 것보다 우리 원칙에 맞는 대응입니다.

## 자주 나올 질문 (미리 답)

**Q. 타인 정보를 가명 처리하는데, 카드의 커밋 링크를 누르면 GitHub에서 실명이
보이지 않나?** — 맞습니다. 우리의 목표는 완전한 익명화가 아니라 "우리 서비스가
그 사람에 관한 서비스가 되지 않는 것"입니다. 실명을 저장하면, 여러 지원자의
카드에 조연으로 등장한 같은 사람의 기록이 검색 한 번으로 모입니다 — 동의한 적
없는 사람의 행동 이력이 우리 DB에서 조회되는 겁니다. 가명화는 그 집적을
차단합니다. 링크 너머는 GitHub의 공개 범위이고, 우리는 "우리 산출물이 추가
노출을 만들지 않는다"까지를 책임 경계로 명시합니다(재식별 자체를 막는다고
주장하지 않습니다 — 검증 가능성을 우선한 선택).

**Q. 커밋을 조작해서 카드를 부풀리면?** — 시스템은 진짜/가짜 판별을 하지
않습니다(판별을 시작하면 판정 기계가 되고, 오탐이 생깁니다). 대신 두 겹으로
대응합니다: 부풀리기가 이득을 보는 수량 지표를 기업 화면에서 뺐고(결정 ④),
카드는 자격증이 아니라 면접 대조 재료라 "왜 이렇게 했나"라는 질문 앞에서 내용
없는 카드는 무너집니다. 검증의 주체는 시스템이 아니라 면접입니다.

**Q. 얇은 카드(커밋 1개)가 검색에 걸리면 부실해 보이지 않나?** — 알려진 위험이고
[가설] 상태입니다. 카드의 빈 부분은 "기록 형태의 한계이지 평가 근거가 아님"을
표기하는 방안을 검토 중이며, 실제로 면접관이 어떻게 읽는지가 인터뷰 확인 1순위입니다.

## 아직 정하지 않은 것 (인터뷰·멘토링이 정해줌)

- 추천·대표 카드의 적정 개수 / 정렬 기준의 우선순위
- 커밋 1개짜리 얇은 카드의 쓸모 (스냅샷 카드 수요)
- **검색이 무엇을 매칭하는가** — 면접관의 질문은 "협업 갈등" 같은 역량 언어인데
  카드의 정보는 코드 변경 언어라, 이 간극을 잇는 검색 방식이 미설계. 의미 기반
  검색(AI)을 쓸지 포함해 검토 대상 (사실 계층의 무AI 원칙과는 층위가 다름)
- 면접관은 "비어 있는 항목"을 어떻게 읽는가 (숨김/없음 구분 문제 — HR 멘토링 안건)
- 카드가 탈락 사유 찾기에 쓰일 때의 안전장치 — 모든 채용 자료의 공통 조건이지만,
  우리 카드는 근거가 열려 있어 지원자가 반론 가능하다는 것이 차별점. 이 프레임이
  실제로 작동하는지 HR 멘토링에서 확인
- 카드 서술문의 AI 자동 생성 여부 (현재 카드 서술 예시는 사람이 작성한 것)

## → [08-24 추록] 카드 상태 모델 개정 — 3상태에서 2축으로

본문 ⑤·⑥단계의 **대표 / 대기 / 숨김 3상태**는 폐기한다.
카드의 상태는 하나의 축이 아니라 **성격이 다른 두 축**이었다.

### 두 축

**축 1 — 가시성 (공개 / 숨김)**
- 카드 단위로, **전역에서 한 번** 정한다.
- 숨긴 카드는 어느 기업에게도, 어떤 경로로도 존재하지 않는 것으로 취급한다.

**축 2 — 큐레이션 (제출 세트)**
- **공고마다 다르다.** 지원자가 공개 카드 중에서 골라 그 공고에 제출한다.
- 시스템은 공고를 렌즈로 삼아 후보 카드를 제안하고, **확정은 지원자가 한다.**

### 왜 나눴나

앞으로 내세울 카드는 포트폴리오와 같은 성격이다. 지원하는 회사가 다르면
보여줄 것도 달라지는 게 정상인데, 3상태 모델의 "대표"는 전역 1벌이라
어느 기업에게나 같은 카드를 내밀게 되어 있었다.

반대로 가시성을 공고별로 두면 안 된다. "누가 내 무엇을 봤는가"를 보여주는
열람 기록과, 본인이 직접 카드를 지우는 기능이 **무엇을 단위로 동작하는지**가
무너지기 때문이다. 감춘 것이 공고마다 다르면 지원자 본인도 자기가 무엇을
감췄는지 추적할 수 없다.

### 본문에서 어긋나는 대목

- ⑤단계의 3상태 그림 — 위 두 축으로 대체
- ⑥단계 "첫 화면 = 대표 카드" — 전역 대표가 없으므로, 기업이 처음 보는 것은
  **그 공고에 지원자가 제출한 세트**다
- 핵심 결정 ②("기업 검색은 숨김 빼고 전체")는 그대로 유효하다.
  검색 대상은 제출 세트가 아니라 공개 카드 전체이며, 숨김만 빠진다

### 함께 정한 것

큐레이션에 얼마나 공을 들였는지는 **기업 화면에 내보내지 않는다.**
기본값을 그대로 썼는지, 몇 번 고쳤는지, 제출까지 얼마나 걸렸는지 같은 것들이다.
이런 걸 보여주면 "제출 세트를 잘 다듬는 능력"이라는 새로운 스펙이 생긴다.
학점과 어학점수가 있던 자리에 커밋 로그를 새로 놓는 셈이라 하지 않는다.
