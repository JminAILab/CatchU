## 1. 질문 (개편이 만든 것)

링크드인 포지션 개편으로 프로필이 본체가 됐다. 구직자가 "나는 어떤 개발자다"라는
주장을 쓰면 시스템이 대응 카드 후보를 제안하는 구조를 검토 중인데, 막힌 지점:

> **구직자가 첫 주장을 어떻게 떠올리는가.**
> 본인 주도 사건 113건(실측)을 다 읽는 것은 부담이고, 시스템이 "당신은 이런
> 개발자입니다"를 제시하면 사람을 규정하는 것이 된다(비판정 위반).

검증한 가설: **서술 없이 사실 속성(메타데이터)만 묶어 보여줘도 본인이 회상할 수
있다** — 성립하면 규정 없이 회상을 돕는 최저비용 해법.

## 2. 실험 1 — 메타데이터 묶음 42그룹 (기각)

Code가 본류 3레포의 본인 주도 사건 113건을 사실 속성(레포×디렉터리×확장자 집합)
으로 묶어 42그룹 산출(해석·명명·순위 없음). 재민이 표본 3종으로 회상 테스트:

| 표본 | 내용 | (a) 무슨 작업인지 떠오르나 |
|---|---|---|
| G03 | bz README .md ×10건 | **O** — 단, 파일명이 내용을 말해주는 특수 사례 |
| G04 | bz smart-contracts .sol ×9건 | **X** — "Solidity 만졌다" 이상이 안 나옴 |
| G01 | TheMe Front/theme .ts+.vue ×27건 | **X** — 사건 특정 불가 |

**판정: 기각.** 회상의 열쇠는 속성(어디서·언제·몇 번)이 아니라 내용(무엇을)이고,
메타데이터에는 내용이 없다. 유일한 성공(G03)은 파일명이 우연히 내용을 담은 경우.
부수 확인: 기능명세 화면 문안의 "47건"은 어떤 기존 정의로도 재현 불가 —
근거 없는 수치로 판정(실측 113).

## 4. 결론 — 3층 회상 구조 (서술 생성 없이 성립)

| 층 | 재료 | 성격 | 회상력 (실측) |
|---|---|---|---|
| 1 | 사실 속성 묶음 (그룹) | 측정 | 단독 불충분 — 탐색의 뼈대로만 |
| 2 | **커밋 메시지 원문** | **기록 인용** (서술 생성 아님) | 대부분 충분 — 4건 중 3건, 최상급 1건 |
| 3 | diff | 기록 열람 | 잔여 지점의 최후층 |

**전 층이 기록의 인용·열람이라 시스템의 해석·서술이 0** — "규정하지 않으면서
회상을 돕는다"는 원래 딜레마가 서술 없이 풀린다. LLM 서술 생성의 지위 확정:
"없으면 안 되는 것"이 아니라 **층 2가 실패하는 잔여 지점(부실 메시지 레포)의
보강 후보.**

관찰 하나: 층 2+메타데이터의 협업(ERC721 사례 — 메시지가 트리거, 날짜가 판별,
기억이 내용)은 이상형 카드의 "기록에 없는 것 → 당사자 진술 보완" 흐름의 자연
발생이다. 화면이 이 협업을 유도하는 배치(메시지 옆에 날짜)면 진술 채록이 싸진다.
