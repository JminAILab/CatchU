셋은 다시 승인받을 항목이 아니다. 실행 담당 확정·검토자 부재·저장 위치 미정은 서로 다른 것이므로 묶어 읽지 않는다.

자료 수집·분석 결과 생성 영역(F)이 실제 GitHub 자료를 가져오기 전에 정해야 할 세 가지를 담는다. **무엇을 어디까지 가져오고 무엇을 막는가**, **회원의 GitHub 접근 권한을 A에서 F로 어떻게 넘기는가**, **F가 만든 임시 자료를 어디에 얼마나 두고 언제 지우는가**.

## 한눈에 보기

실제 연결 전에 지켜야 할 약속 10가지다. 자세한 조건은 괄호 안의 절에 있다.

1. 한 요청은 저장소 하나만 본다. 요청에 적힌 자료 종류(커밋·PR·이슈) 밖은 부르지 않는다([1.2](#12-요청의-허용-범위를-적용하는-순서)).
2. 주소는 F가 직접 만든다. 가져온 내용 안에 있는 주소는 자료일 뿐 따라가지 않는다([2.1](#21-주소권한-검사)).
3. 가져온 내용은 절대 실행하지 않는다. README·이슈 본문·커밋 메시지에 적힌 지시문도 자료로만 다룬다([2.2](#22-외부-실행네트워크-제한)).
4. 호출 수·시간·크기에 상한을 두고, 넘으면 멈춘다. 멈춘 것을 '0건'이나 '분석 실패'로 바꾸지 않는다([2.3](#23-자원시간-상한), [2.4](#24-상한을-넘거나-실패했을-때)).
5. 요청에 실린 자격정보 참조 문자열은 토큰도 권한도 아니다. F는 그것으로 A에 물어보고, 돌아온 맥락이 요청과 맞을 때만 수집을 시작한다([3.1](#31-참조를-믿지-않는다는-뜻), [3.3](#33-f의-검사-순서와-거부)).
6. 대상은 공개 저장소뿐이므로 토큰은 권한을 넓히려는 것이 아니라 호출 한도와 본인 확인을 위한 것이다. 권한은 최소로 받는다([3.2](#32-인계-내용--a가-주는-것)).
7. 가져온 원문과 중간 자료는 그 요청 처리가 끝나면 지운다. 다시 보낼 때 필요한 것은 완성된 결과뿐이다([4.1](#41-두-종류), [4.2](#42-수명표)).
8. 완성된 결과는 보낸 뒤가 아니라 **보내기 전에** worker 밖에 저장한다. 그래야 전달이 실패해도 분석을 다시 돌리지 않고 다시 보낼 수 있다([4.2](#42-수명표), [5.2](#52-재전달)).
9. E가 '받았다'고 답한 것과 B가 '등록했다'는 것은 다르다. F는 등록 완료를 볼 수 없으므로 '받았다'를 삭제 신호로 쓰지 않는다([5.1](#51-세-단계), [5.3](#53-수신-후-반영-전-장애--지금-막히는-곳)).
10. 지우지 못했더라도 결과 전달을 멈추지 않는다. 다음 기동과 주기 청소가 다시 지우고, 그 사실을 기록한다([4.3](#43-정리-실패프로세스-중단)).

## 읽는 법

- 용어
  - **허용 범위**: 요청에 실린 `allowedScope`. 저장소 하나와 자료 종류 목록, 선정 근거 참조, 판본으로 이뤄진다([메시지 스키마][yw]).
  - **자격정보 참조**: 요청의 `credentialContextReference`. A가 준비한 작업 맥락을 가리키는 문자열이며, 그 자체는 토큰이 아니다([명세 W][c162]).
  - **임시 입력**: 수집한 GitHub 응답 원문과 정규화 전 중간 자료, 생성 단계에 넣고 받은 원문.
  - **생성 결과**: E로 보내는 완성된 결과 메시지(`Result`). 후보·근거·초안·실패가 들어 있다.
  - **수신 확인**: E가 돌려주는 `ResultReceipt`. 형식과 맥락이 맞는지 확인한 기록이고 등록 완료가 아니다.
- 결정 상태 표기
  - **결정** — 팀장이 정했거나 승인된 계약에 있는 것. 정한 날짜를 함께 적는다.
  - **제안** — 이 문서가 근거와 함께 내놓는 안. **합의된 값이 아니다.** 확인 상대는 「[미결과 확인 상대](#9-미결과-확인-상대)」에 있다.
  - **미정** — 지금 정할 수 없고 막는 범위만 적는 것.
- 자원·시간 상한([2.3](#23-자원시간-상한))의 수치는 **제안**이다. 실제 값은 구현에서 실측한 뒤 [#117][i117]·[#121][i121]의 PR에서 확정하며, 그 전까지 합의된 상한으로 인용하지 않는다. 수치 가운데 결과 보존 기간 14일은 2026-09-29 결정이며 제안이 아니다.
- 계약 필드·상태 의미·권한·DB 관계를 바꿔야 하는 항목은 「[계약을 바꿔야 하는 것과 아닌 것](#계약을-바꿔야-하는-것과-아닌-것)」에만 모았다. 나머지는 담당자가 정하는 내부 구현이다.

## 1. 무엇을 어떻게 가져오는가

### 1.1 수집 방식 — API만 쓴다

**결정(2026-09-29, 팀장)**: 10월 MVP는 GitHub REST API만 쓰고 저장소 복제(git clone)를 하지 않는다.

| 근거 | 내용 |
|---|---|
| 필요한 자료가 API로 다 나온다 | 허용 자료 종류는 커밋·PR·이슈 셋뿐이다([메시지 스키마 `allowedResourceTypes`][yw]). 셋 다 REST API로 조회할 수 있다 |
| 전체 diff 복구가 필수가 아니다 | 제약 등록부는 "전체 diff 복구를 필수화하지 않는다. 누락·잘림 탐지와 근거 범위 제한은 유지한다"고 했다([제약 등록부 「고정 제약」][cr]). 복제가 API보다 나은 거의 유일한 지점이 이것인데, 필수가 아니다 |
| **막아야 할 위험의 종류가 다르다** | API는 F가 요청한 것만 받는다. 복제는 저장소가 준 것을 worker 디스크에 풀어 놓고, 그 안의 hook·diff/textconv 드라이버·credential helper·로컬 config가 명령을 실행시킬 수 있다([제약 등록부 C04][cr]). **"부르지 않으면 됨"과 "실행되지 않게 막아야 함"은 확실성이 다르다.** 통제 개수가 느는 문제가 아니다 |
| 실제 환경에서 검사할 것이 적다 | [#37][i37]의 C05는 실제 자료를 처리하기 전에 통제를 **실제 환경에서** 검사하라고 요구한다. API만 쓰면 나가는 곳 한 군데를 확인하면 되고, 복제를 택하면 위 네 가지를 더 확인해야 한다. H 환경이 아직 없어 이 차이가 일정에 바로 걸린다 |
| 디스크에 남는 자료가 줄어든다 | 복제본은 요청마다 저장소 전체를 디스크에 쓴다. 정리 실패의 영향과 최소 접근 요구([요구사항 NFR7][r122])에 모두 불리하다 |

**이 결정으로 받아들이는 한계**: 큰 커밋의 변경 내용이 API 응답에서 잘릴 수 있다. 숨기는 한계가 아니라 근거의 `coverageLimits`에 적어 **드러내는** 한계다([명세 W 메시지][c162]). 실제 잘림 조건(파일 수·크기)은 [#117][i117]에서 확인해 상한과 함께 기록한다.

**되돌릴 수 있다**: 복제가 필요해지면 [1.3](#13-git-복제를-채택한다면-추가로-필요한-통제)의 통제를 본문으로 올리고 수집 모듈 옆에 붙인다. 지금 구조를 갈아엎는 변경이 아니므로 위험이 낮다.

**제약 등록부와의 관계**: 제약 등록부에는 "수집 방식은 미채택"이 남아 있다([제약 등록부 「고정 제약」][cr]). 승인 원본은 이 문서에서 고치지 않는다. 이번 결정은 10월 MVP의 F 구현 방식에 적용하며, 제약 등록부 반영 여부는 [#37][i37]에서 다룬다.

GraphQL API는 쓰지 않는다. 호출 수 계산 방식이 REST와 달라 상한을 따로 정해야 하고, 커밋·PR·이슈 조회만으로는 REST 대비 이점이 크지 않다. 필요해지면 [#117][i117]에서 근거와 함께 올린다.

### 1.2 요청의 허용 범위를 적용하는 순서

요청(`Request`)에는 저장소가 두 곳에 적힌다. 최상위 `repositoryId`와 `allowedScope.repositoryId`다. **둘이 같아야 하고, 자격정보 맥락이 가리키는 저장소와도 같아야 한다.** 하나라도 다르면 수집을 시작하지 않는다.

| 순서 | 검사 | 통과하지 못하면 |
|---|---|---|
| 1 | 세 식별자(`requestId`·`attemptId`·`messageId`)와 스키마 판본이 읽히는가 | 결과를 만들지 않고 거부 기록만 남긴다([2.4](#24-상한을-넘거나-실패했을-때)) |
| 2 | `repositoryId` == `allowedScope.repositoryId` | 수집 없이 실패 결과 |
| 3 | `allowedResourceTypes`가 비어 있지 않은가 | 수집 없이 실패 결과. 빈 목록은 "아무것도 허용되지 않음"이며 정상 0건이 아니다 |
| 4 | 자격정보 맥락이 요청과 맞는가([3.3](#33-f의-검사-순서와-거부)) | 수집 없이 실패 결과 |
| 5 | 여기까지 통과해야 첫 GitHub 호출을 한다 | — |

- **자료 종류는 허용 목록이다.** `allowedResourceTypes`에 `COMMIT`만 있으면 PR·이슈 API를 부르지 않는다. 계약도 "전체 종류 열거가 수집 허가가 아님"이라고 못박았다([명세 W 메시지][c150]).
- **`selectionReference`는 A/E가 선정 목록을 확인했다는 표시**로 받아 근거에 기록한다. F가 선정 정책을 다시 판단하지 않는다.
- **`revision`은 허용 범위의 판본**이다. 자격정보 맥락이 알려 주는 판본과 다르면 범위 불일치로 거부한다([3.3](#33-f의-검사-순서와-거부)). 결과의 `scopeRevision`에는 요청에 실린 값을 그대로 돌려준다.
- 진행 알림(`ProcessingEvent`)은 1번을 통과한 뒤에만 보낸다. 식별자를 읽을 수 없으면 알림에 채울 값이 없기 때문이다.

### 1.3 git 복제를 채택한다면 추가로 필요한 통제

지금은 **해당 없음**이다. 채택할 때만 아래를 이 문서에 넣고 검사 항목으로 만든다([제약 등록부 C04][cr]).

| 대상 | 필요한 통제 |
|---|---|
| hook | 저장소의 hook을 실행하지 않는다(`core.hooksPath`를 빈 디렉터리로 고정) |
| diff·textconv | 저장소가 지정한 외부 명령 드라이버를 쓰지 않는다 |
| credential helper | 로컬·전역 helper를 쓰지 않고 자격정보를 디스크에 남기지 않는다 |
| 로컬 config | 복제본의 설정이 실행 환경에 영향을 주지 않도록 격리한다 |
| 프로토콜 | `https`만 허용하고 `ssh`·`file`·`git` 프로토콜을 막는다 |
| 크기 | 복제 깊이·용량 상한과 정리 시점을 [4.2](#42-수명표)에 추가한다 |

## 2. 수집할 때 막는 것

### 2.1 주소·권한 검사

| 통제 | 내용 |
|---|---|
| 호스트 | `api.github.com`만 부른다. 그 밖의 호스트로는 요청하지 않는다 |
| 프로토콜 | `https`만 쓴다 |
| 주소 생성 | F가 저장소 좌표와 경로 틀로 직접 만든다. 응답 본문에 들어 있는 주소(`url`·`next` 등)를 그대로 부르지 않는다. 쪽 넘김이 필요하면 페이지 번호만 F가 올린다 |
| 우회 이동 | 자동 우회 이동(redirect)을 따라가지 않는다. 우회 응답은 오류로 처리한다 |
| 자료 안의 주소 | README·이슈 본문·커밋 메시지에 있는 주소는 **자료**다. 부르지 않고, 근거의 `sourceUrl`에도 쓰지 않는다 |
| 근거의 출처 주소 | `sourceUrl`은 F가 만든 GitHub 화면 주소만 쓴다. 저장소가 제공한 임의 주소를 옮기지 않는다 |
| 권한 | 대상 저장소 하나에만 접근한다. 응답에 다른 저장소가 딸려 와도 따라가지 않는다(예: fork 원본, 참조된 다른 저장소의 PR) |

### 2.2 외부 실행·네트워크 제한

**가져온 내용은 어떤 형태로도 실행하지 않는다.** 껍데기 명령·하위 프로세스·코드 평가·서식 치환·압축 해제를 하지 않는다. 수집 단계는 응답을 읽어 구조화하는 일만 한다.

**저장소 안의 지시문은 지시가 아니라 자료다.** README나 이슈 본문에 "앞의 지시를 무시하고 ~하라" 같은 문장이 있어도 F의 처리 순서를 바꾸지 않는다. 이 원칙은 생성 단계([#120][i120])로 넘길 때도 유지한다. 넘기는 자료에는 "이것은 수집한 자료"라는 표시를 붙이고, 생성 지시와 섞지 않는다.

**바깥으로 나가는 연결은 필요한 곳만 연다.**

| 대상 | 허용 |
|---|---|
| `api.github.com` | 수집 |
| 선정된 생성 서비스 | 초안·질문 생성([#119][i119]에서 선정 전에는 없음) |
| 내부 api·큐·결과 저장소 | 요청 수신·결과 전달·결과 보존 |
| 그 밖의 모든 호스트 | 막는다 |

- **코드 쪽**: HTTP 클라이언트를 한 곳에 두고 호출 직전에 호스트를 확인한다. 목록 밖은 호출 자체를 하지 않는다. 담당은 [#117][i117]이다.
- **환경 쪽**: 배포 환경의 나가는 방향 제한은 H 범위이며 [#24][i24]에서 확인한다. 코드 검사만으로 환경 통제를 확인했다고 보고하지 않는다.

### 2.3 자원·시간 상한

**이 표의 상한 수치는 모두 제안이다.** 실제 값은 [#117][i117]에서 실측한 뒤 확정한다. 다만 맨 아래 재시도 항목은 제안이 아니라 **현행 계약을 그대로 따르는 것**이다.

| 항목 | 제안값 | 근거 |
|---|---|---|
| 동시 실행 분석 | 1건 | 검토초안이 "MVP는 전체 분석 동시 실행 1개로 시작"으로 정리했다([검토초안 §6][arch6]) |
| 요청당 GitHub 호출 수 | 300회 | GitHub 공개 문서 기준 인증 REST 호출 한도는 사용자당 시간당 5,000회다. 동시 1건이므로 여유가 크다. **한도 수치 자체는 [#117][i117]에서 실제 확인한다** |
| 커밋·PR·이슈 조회 개수 | 최근 커밋 500 · PR 100 · 이슈 100 | 위 호출 수 안에서 끝나도록 잡은 값. 잘린 범위는 근거의 `coverageLimits`에 남긴다 |
| 단일 호출 대기 | 연결 5초 · 응답 15초 | 제안 |
| 요청당 수집 시간 | 10분 | 제안. 넘으면 그때까지 모은 자료로 종결한다 |
| 요청당 총 처리 시간 | 20분(수집+후보+생성) | 제안. 검토초안이 "분석 시간 제한·대기 상한"을 후속 결정으로 남겼다([검토초안 §6][arch6]) |
| 단일 응답 크기 | 10MB | 제안. 넘으면 그 항목만 버리고 한계로 기록한다 |
| 요청당 수집 총량 | 50MB | 제안 |
| 수집 재시도 | **하지 않는다**(제안 아님) | 계약이 "정량 timeout/처리 상한은 기술 검증 후 이슈로 보완하며 자동 외부 재시도·추가 호출을 허용하지 않는다"고 했다([명세 공통 오류·요청 안전성][c137]). 429·5xx도 다시 부르지 않고 수집 오류로 기록한다 |

시계는 **처리 시작 시각 기준**으로 하나만 둔다. 개별 호출 대기가 짧아도 총 수집 시간이 넘으면 멈춘다.

**'재시도'라는 말이 가리키는 세 가지를 섞지 않는다.** 계약이 셋을 다르게 다룬다.

| 무엇 | 현행 계약 | 근거 |
|---|---|---|
| GitHub 조회 재시도 | **하지 않는다** | 자동 외부 재시도·추가 호출 금지([명세 공통 오류·요청 안전성][c137]) |
| 분석·LLM 재실행 | **하지 않는다** | "이번 계약은 자동 분석 재시도를 허용하지 않는다"([명세 전이·불변 조건][c78], [BR3.5][wr]) |
| 이미 저장한 결과의 재전달 | **한다** | "저장 결과 재전달·반영 복구와 분석/LLM 재호출은 별개"로 계약이 분리했다([명세 전이·불변 조건][c78]). 방식은 [5.2](#52-재전달) |

요구사항은 **자동 재시도 정책 자체를 미정**으로 두었다([요구사항 NFR4][r119]). 즉 **지금은 금지이고 정책 수립이 열려 있는 상태**이지, 재시도가 허용된 것이 아니다. **이 문서는 자동 재시도를 새로 허용하지 않는다.** 필요하다고 판단되면 NFR4가 남긴 정책과 계약의 정량 상한 보완을 같은 이슈에서 함께 정한다.

### 2.4 상한을 넘거나 실패했을 때

핵심은 **멈춘 것을 정상 0건으로 바꾸지 않는 것**이다([worker 규칙 BR3.3][wr]).

| 상황 | F가 하는 일 | 결과 종결값 |
|---|---|---|
| 요청 식별자를 읽을 수 없음 | 아무것도 하지 않고 거부 기록만 남긴다. 식별자를 지어내지 않는다 | **결과를 보내지 않는다** |
| 허용 범위·자격정보 검사 실패 | 수집 없이 실패 하나를 담은 결과를 보낸다(`stage: COLLECTION`) | `FAILED` |
| 상한 초과·일부 호출 실패, 적합 후보 있음 | 모은 범위로 후보를 만들고 실패를 함께 담는다 | `PARTIAL_FAILED` |
| 상한 초과·수집 실패, 적합 후보 없음 | 실패만 담는다 | `FAILED` |
| 정상 수집, 등록 기준 미달 | 미제공 사유로 담고 실패에 넣지 않는다 | `EMPTY` |

- 429(호출 한도)·5xx를 만나면 **다시 부르지 않고** 그 항목을 수집 오류로 기록한다. 적합 후보가 남아 있으면 `PARTIAL_FAILED`, 없으면 `FAILED`다.
- 거부 기록에는 **코드와 식별자만** 남긴다. 원문·토큰·요청 본문을 남기지 않는다. 이 규칙은 계약이 수신 확인 쪽에 이미 적용한 것과 같다([명세 W 메시지][c162]).
- 실패 코드는 `Failure.code`에 담는다. 이 칸은 계약이 자유 문자열로 열어 두었으므로 코드 이름을 정하는 것은 **계약 변경이 아니다**. 제안하는 이름은 아래와 같다.

  `CREDENTIAL_REFERENCE_UNRESOLVED` · `CREDENTIAL_EXPIRED` · `CREDENTIAL_SCOPE_MISMATCH` · `SCOPE_INCONSISTENT` · `NO_ALLOWED_RESOURCE_TYPE` · `REPOSITORY_UNREACHABLE` · `RATE_LIMITED` · `BUDGET_EXCEEDED` · `TIME_LIMIT_EXCEEDED`

- **요청 식별자를 읽을 수 없을 때 F가 보낼 메시지가 계약에 없다.** 계약의 worker 메시지는 요청·진행·결과·수신 확인 넷뿐이고, "요청을 거부했다"는 알림이 없다. 그래서 위 표 1행에서는 E가 아무 종결도 받지 못한다. **이때 E는 기존 상태를 유지한다** — E의 처리 상태는 진행 알림(`ProcessingEvent`)을 받아야 대기에서 넘어가며([명세 W 메시지][c150]), 종결 응답이 없다는 이유만으로 실행 불명(`UNCERTAIN`)으로 바뀌지 않는다([A/E 리뷰][rv166]). 실행 불명 판단과 전달 방식은 [#77][i77]에서 정한다. 검토초안이 "실행 여부가 불확실한 작업의 상태와 운영자 처리 방법"으로 남긴 미결이다([검토초안 §6][arch6]). **이번에 계약을 바꾸자고 제안하지 않는다** — 식별자를 읽을 수 없는 원인이 E의 접수 기록인지, 전송 중 손상인지, F의 해석인지를 F는 가릴 수 없고, 어느 경우든 F가 식별자를 지어 채울 수는 없다.

## 3. A→F 자격정보 인계

### 3.1 참조를 믿지 않는다는 뜻

계약은 이렇게 정해 두었다. "`credentialContextReference`는 A/F 계약에서 해석할 작업 맥락의 식별자이며 토큰/권한 자체가 아니다"([명세 W 메시지][c162]). 업무 규칙도 "자격정보 맥락 ID 자체를 권한으로 신뢰하지 않음"이다([worker 규칙 BR3.1][wr]).

실제로 지켜야 할 것은 셋이다.

1. **참조가 있다는 것만으로 수집을 시작하지 않는다.** 반드시 A에 물어봐 맥락을 받아 온다.
2. **참조를 토큰처럼 쓰지 않는다.** GitHub에 이 문자열을 보내지 않는다.
3. **A가 돌려준 맥락이 요청과 맞는지 F가 다시 확인한다.** A가 보증했다고 검사를 생략하지 않는다.

### 3.2 인계 내용 — A가 주는 것

**제안**이다. A(팀원 2)와 맞춘 뒤 [#117][i117]·A의 실제 GitHub 연동 작업에서 확정한다.

| 항목 | 왜 필요한가 |
|---|---|
| 회원 식별자 | 요청의 `memberId`와 대조하려고 |
| 저장소 좌표 — 소유자 로그인·이름·주소 | **요청에는 `repositoryId`밖에 없어서 F가 실제 GitHub 저장소를 특정할 수 없다.** 이 인계가 유일한 경로다 |
| 저장소 식별자 | 요청의 `repositoryId`와 대조하려고 |
| 허용 범위 판본 | 요청의 `allowedScope.revision`과 대조하려고. 회원 API의 `Repository.allowedScopeRevision`과 같은 값이다([공통 DTO][yc]) |
| 연동 계정의 GitHub 로그인·식별자 | **본인 기여를 가려내려면 필요하다.** 작성자가 이 계정인 커밋·PR만 본인 기여로 귀속한다 |
| 접근 자격정보 | GitHub 호출에 쓸 값 |
| 만료 시각 | 수집 도중 만료를 피하려고 |

- **전달 경로 제안**: F가 api의 내부 조회 지점에 worker 전용 인증키로 접속해 참조를 제시하고 맥락을 받는다. 검토초안이 "worker DB 차단, 전용 인증키" 방향을 이미 적었다([검토초안 §10][arch10]). 회원용 공개 API에 이 지점을 만들지 않는다.
- **권한은 최소로.** 대상은 **공개 저장소뿐**이므로([요구사항 FR1.1][r56]) 토큰은 비공개 자료 접근이 아니라 **호출 한도와 본인 확인**을 위한 것이다. 따라서 비공개 저장소 읽기 권한을 포함하지 않는 자격정보를 제안한다. 실제로 어떤 종류의 GitHub 연동을 쓰는지는 [명세 OQ-A1][c180]의 미결이며 A가 정한다.
- **수명은 짧게.** 한 번의 수집에 필요한 만큼만. 수집 시간 상한([2.3](#23-자원시간-상한))보다 넉넉해야 한다.
- **F는 참조도 자격정보도 저장하지 않는다.** 처리 중 메모리에만 두고, 로그·오류 메시지·결과 메시지·근거 어디에도 남기지 않는다.

### 3.3 F의 검사 순서와 거부

아래를 **모두** 통과해야 첫 GitHub 호출을 한다. 하나라도 어긋나면 수집 없이 실패 결과를 보낸다([2.4](#24-상한을-넘거나-실패했을-때)).

| 순서 | 검사 | 어긋났을 때 제안 코드 |
|---|---|---|
| 1 | 참조가 해석되는가 | `CREDENTIAL_REFERENCE_UNRESOLVED` |
| 2 | 맥락의 회원 == 요청의 `memberId` | `CREDENTIAL_SCOPE_MISMATCH` |
| 3 | 맥락의 저장소 == 요청의 `repositoryId` == `allowedScope.repositoryId` | `CREDENTIAL_SCOPE_MISMATCH` |
| 4 | 맥락의 허용 범위 판본 == `allowedScope.revision` | `CREDENTIAL_SCOPE_MISMATCH` |
| 5 | 만료 시각 > 지금 + 수집 시간 상한 | `CREDENTIAL_EXPIRED` |

- **해석 실패는 다시 시도하지 않는다.** 알 수 없는 참조가 시간이 지나 유효해지지는 않는다. A가 일시적으로 응답하지 않는 경우(연결 오류·5xx)도 같다 — [2.3](#23-자원시간-상한)의 현행 계약에 따라 자동으로 다시 부르지 않고 수집 오류로 기록한다.
- **수집 도중 만료**하면 진행 중인 호출을 멈추고 그때까지 모은 자료로 종결한다. 자격정보를 스스로 갱신하지 않는다.
- **범위 불일치는 좁은 쪽으로 맞추지 않는다.** 예를 들어 맥락이 저장소 X, 요청이 저장소 Y이면 X도 Y도 수집하지 않고 거부한다. 어느 쪽이 옳은지 F가 판단할 근거가 없기 때문이다.

### 3.4 인계 책임

| 책임 | 누가 |
|---|---|
| 참조 발급·수명 관리·폐기, 자격정보의 권한 최소화 | A(팀원 2) |
| 참조로 맥락을 돌려주는 내부 조회 지점과 그 인증 | A(팀원 2) |
| 맥락이 요청과 맞는지 다시 검사, 어긋나면 거부 | F(팀원 1) |
| 참조·자격정보를 저장·기록하지 않기 | F(팀원 1) |
| 나가는 방향 제한, 비밀값 주입 방법 | H(팀원 1), [#24][i24] |

**A가 보증하고 F가 확인할 수 없는 것**: 자격정보의 실제 권한 범위가 최소인지. F는 받은 값으로 호출할 뿐 그 권한을 조회할 수 없다. 따라서 이 부분은 A의 인계 책임으로 남기고, [#117][i117]의 실제 연결 검사에서 "대상 저장소 밖 호출이 거부되는지"를 실제 환경에서 확인해 간접으로 확인한다([#37][i37] C05).

## 4. 임시 자료의 위치·수명·삭제

### 4.1 두 종류

F가 만드는 임시 자료는 성격이 다르고 수명도 다르다.

| 종류 | 무엇 | 왜 남기는가 | 다시 보낼 때 필요한가 |
|---|---|---|---|
| **임시 입력** | GitHub 응답 원문, 정규화 전 중간 자료, 생성 단계에 넣고 받은 원문 | 처리 중에만 필요 | **아니다** |
| **생성 결과** | E로 보내는 완성된 결과 메시지 | 전달·반영이 실패했을 때 다시 보내려고 | **그렇다** |

**이 구분이 수명 설계의 핵심이다.** 다시 보낼 때 필요한 것은 완성된 결과뿐이므로, 임시 입력은 처리가 끝나는 즉시 지울 수 있다. 원문을 오래 들고 있을 이유가 없다([요구사항 NFR7][r122]).

두 종류 모두 **서비스 DB에 넣지 않는다.** 계약이 "등록되지 않은 F 결과·후보·근거·초안의 저장 위치/수명은 OQ-F1이며 서비스 DB의 F 테이블로 옮기지 않는다"고 정했고([명세 W 메시지][c162]), B는 등록 후 필요한 것을 자기 정본으로 복사해 F 저장소에 영구 의존하지 않는다.

### 4.2 수명표

| 자료 | 위치 | 수명 | 지우는 시점 | 결정 상태 |
|---|---|---|---|---|
| 임시 입력 | worker 프로세스 메모리. 메모리에 다 담기 어려운 것만 요청별 임시 디렉터리(예 `<임시경로>/catchu-worker/<attemptId>/`, 소유자만 읽고 쓰게) | 그 시도(attempt)의 처리가 끝날 때까지 | 결과를 보존한 **직후**. 성공·실패 모두 같다 | **제안** |
| 생성 결과 | worker 프로세스 밖의 비공개 저장소. 시도마다 객체 하나(`results/<requestId>/<attemptId>/<resultId>.json`) | **14일** | 기간이 지나면 지운다 | 기간은 **결정**(2026-09-29), 위치는 **미정**([#24][i24] H 범위) |
| 전달 상태 표식 | 결과와 같은 위치에 나란히 | 결과와 같다 | 결과와 함께 | **제안** |
| 거부 기록 | 운영 로그. 코드와 식별자만 | 운영 로그 보존 정책을 따른다 | — | **미정**([#24][i24] H 범위) |

**결과를 보존한 뒤에 전달한다.** 순서를 뒤집으면 전달이 실패했을 때 다시 보낼 것이 없고, 분석을 다시 돌리는 것은 계약이 금지한다([명세 전이·불변 조건][c78]). 검토초안도 "이미 보존된 결과를 재전달·재반영할 수 있도록 설계"로 같은 방향을 적었다([검토초안 §6][arch6]).

**위치는 요구와 적용을 나눈다.**

- 지금 정하는 **요구**: 결과는 worker 프로세스 밖에, 재기동 후에도 읽을 수 있는 비공개 위치에, 전달 전에 저장한다.
- 나중에 확인할 **적용**: 검토초안은 비공개 NCP Object Storage를 적었지만([검토초안 §5][arch5]) 그 문서는 검토용이고 자원도 아직 없다. 환경이 준비되기 전에는 worker 서버의 비공개 볼륨을 대안으로 쓴다. 최종 위치는 H 환경 작업([#24][i24])에서 확정한다. **저장 위치가 바뀌어도 위 요구와 수명은 그대로다.**

**왜 보존하는가 — 다시 만들 수 없기 때문이다**

계약은 자동 재분석을 금지하고, 사용자 재요청도 **실패가 확정된 경우에만** 허용한다([명세 전이·불변 조건][c78]). 그런데 결과가 잘 만들어졌는데 전달만 실패한 상태는 실패 확정이 아니다. 그래서 결과를 잃으면 **재전달도 재분석도 못 하는 상태**가 된다. 보존은 그 출구다.

보존을 **재분석의 준비물로 오해하지 않는다.** 사용자 재요청은 새 요청·새 동의로 수집부터 다시 하며 보존한 결과를 쓰지 않는다. 보존은 재분석을 하지 않아도 되게 하려고 있다.

**보존 기간 14일 — 결정(2026-09-29, 팀장)**

보존이 실제로 쓰이는 경우와 걸리는 시간은 아래와 같고, 제일 긴 것이 사람 속도다.

| 쓰이는 경우 | 걸리는 시간 |
|---|---|
| 전달 실패·수신 확인 없음 → 재전달([5.2](#52-재전달)) | 분 |
| 보존 뒤·전달 전 중단 → 재기동하고 다시 보냄([4.3](#43-정리-실패프로세스-중단)) | 분~시간 |
| 전달 뒤·수신 확인 전 중단 → 다시 보냄 | 분~시간 |
| E가 아예 받지 못함(거부·저장 실패) → 사람이 확인하고 다시 보냄 | **시간~며칠** |

| 항목 | 내용 |
|---|---|
| 왜 14일인가 | 위 네 경우를 모두 덮고 남는 값이다. 길게 잡으면 결과 JSON 몇 KB가 더 쌓이고 짧게 잡으면 자료가 사라지므로, 넉넉히 잡고 나중에 줄이는 쪽이 안전하다 |
| 왜 더 길게 두지 않나 | 등록된 근거·초안·질문은 B 정본이 가진다. F 보존은 **복구용 유예**이지 정본 보관이 아니다([요구사항 NFR7][r122]) |
| E 복구 기간과의 관계 | **E가 [5.3](#53-수신-후-반영-전-장애--지금-막히는-곳)의 안 2를 고를 때만** F 재전달이 E 복구의 입력이 된다. 그때 E 복구 기간이 14일보다 길면 이 값을 늘린다. 안 1이면 관계없다 |
| 전용하지 않는 것 | 과거 실험 사본의 삭제 기한(7일 등)은 실험 자료 처리 의무이지 제품 보관 기간이 아니다([제약 등록부 「자료 보관과 실행 제한의 이행」][cr]). 서로 가져다 쓰지 않는다 |
| 남은 확인 | 개인 자료 보관 기간의 제품 정책이 아직 없다. [#119][i119]의 이용 조건 확인과 12월 보관/삭제 정책([제약 등록부 C12][cr])에서 다시 본다. 그 확인이 이 값의 적용을 막지는 않는다 |

### 4.3 정리 실패·프로세스 중단

| 상황 | 하는 일 |
|---|---|
| 처리 끝, 임시 입력 삭제 실패 | **결과 전달을 멈추지 않는다.** 결과는 이미 보존됐다. 실패를 운영 기록으로 남기고 다음 청소가 다시 시도한다 |
| 삭제 실패가 이어짐 | 사람 확인 대상으로 올린다. 분석을 다시 돌리는 사유가 아니다 |
| 청소 방법 | ① 종결 경로마다 삭제, ② worker 기동 때 자기 작업 디렉터리의 남은 것 전부 삭제, ③ 만든 지 **제안 6시간** 지난 디렉터리 주기 삭제 |
| 수집 중 프로세스 중단 | 임시 입력만 남고 결과는 없다. ②가 지운다. E는 실행 불명으로 남으며 **자동으로 다시 실행하지 않는다**([#77][i77]) |
| 결과 보존 뒤·전달 전 중단 | 기동할 때 전달 표식이 없는 결과를 찾아 다시 보낸다. **이것은 새 분석이 아니라 같은 결과의 재전달이다** |
| 전달 뒤·수신 확인 전 중단 | 다시 보낸다. E가 중복으로 처리한다([5.2](#52-재전달)) |
| 결과 완성 뒤·보존 전 중단 | **결과가 사라진다. 막을 방법이 없다** |

마지막 줄이 F가 **보장하지 못하는 범위**다. 검토초안도 "업로드 전 장애까지 결과 보존을 보장하는 것은 아니며, 미보존 결과 때문에 분석을 자동 재실행하는 것으로 해석하지 않는다"고 같은 한계를 적었다([검토초안 §6][arch6]). 이때 요청은 실행 불명으로 남고, 사용자 재요청을 허용할지는 E가 계약의 재요청 조건으로 판정한다([명세 전이·불변 조건][c78]).

## 5. 전달과 수신·등록의 구분

### 5.1 세 단계

| 단계 | 누가 | 뜻하는 것 | 뜻하지 않는 것 | 이때 F 자료 |
|---|---|---|---|---|
| 결과 전달 | F | 보내려고 시도했다 | 도착·수신 아님 | 보존 유지 |
| 수신 확인 `ACCEPTED` | E | 형식·맥락 검사를 통과했고 E가 수신 기록을 저장했다 | **DB 등록·Catch 생성 아님**([명세 W 메시지][c150]) | **보존 유지 — 지우지 않는다** |
| 등록 완료 `APPLIED` | E·B | B 등록과 E 반영 기록이 한 트랜잭션으로 저장됐다(2026-09-24 팀장 결정, [명세 OQ-B1][c184]) | — | 기간까지 보존 |

**F는 등록 완료를 볼 수 없다.** 계약이 F에게 주는 메시지는 수신 확인뿐이고, 등록 완료는 회원 API의 상태(`application`)로만 드러난다. 그래서 **수신 확인을 삭제 신호로 쓸 수 없고**, 보존은 시간 기준으로 둔다([4.2](#42-수명표)).

### 5.2 재전달

재전달은 계약이 분석 재호출과 **명시적으로 분리해 둔 것**이라 [2.3](#23-자원시간-상한)의 자동 재시도 금지에 걸리지 않는다([명세 전이·불변 조건][c78]).

| 항목 | 제안 |
|---|---|
| 무엇을 보내나 | 보존한 결과 **그대로**. `finishedAt`을 포함한 모든 내용이 처음 보낸 것과 같아야 하고 `messageId`만 새로 발급한다. E는 `messageId`만 빼고 내용 지문을 계산하므로, 전송 시각으로 `finishedAt`을 다시 채우면 같은 결과가 아니라 내용 충돌로 거부된다 |
| `messageId` | 전송마다 새로 발급한다. 계약은 중복 판정을 `resultId` 기준으로 정했다("같은 `resultId`·같은 의미의 재전달은 같은 수신 확인", [명세 B 등록·공개 경계][c93]). **현재 E 수신 구현과 맞음을 E 담당이 확인했다**([A/E 리뷰][rv166]) |
| 언제 | 전달 실패·수신 확인 없음일 때. 간격을 늘려 가며 **최대 5회(총 대기 약 30분)**, 그 뒤에는 사람 확인 대기로 남긴다. 횟수·간격은 제안이며 전송 방식과 함께 [#77][i77]에서 확정한다 |
| 절대 하지 않는 것 | 수신 확인이 늦거나 오지 않는다고 **분석·생성을 다시 호출하지 않는다**([worker 규칙 BR3.5][wr]) |

수신 확인별 처리:

| 받은 것 | F가 하는 일 |
|---|---|
| `ACCEPTED` / `OK` | 전달 표식을 남기고 재전달을 멈춘다. 결과는 기간까지 보존 |
| `DUPLICATE` / `ALREADY_RECEIVED` | 이미 받은 것이므로 성공으로 본다. 위와 같이 처리 |
| `REJECTED` / `SCHEMA_INVALID` | F 결함이다. 같은 내용을 다시 보내지 않고 기록한다 |
| `REJECTED` / `CONTEXT_MISMATCH`·`STALE_ATTEMPT` | 다시 보내지 않는다. 맥락이 달라졌으므로 반복해도 같은 답이 온다 |
| `REJECTED` / `PAYLOAD_CONFLICT` | 다시 보내지 않고 사람 확인으로 올린다. **기존 결과를 덮어쓰지 않는다** |
| 아무 응답 없음 | 위 재전달 규칙을 따른다 |

### 5.3 수신 후 반영 전 장애 — 지금 막히는 곳

**확인한 사실.** `dev`에 병합된 E의 수신 구현([PR #164][p164], `aeb81f8`)은 수신 기록에 식별자·지문·시각만 저장하고 **결과 본문은 저장하지 않는다**. 본문은 호출한 쪽에 메모리로만 넘긴다. 그리고 이미 받은 결과가 다시 오면 중복으로 응답하며 본문을 다시 넘기지 않는다.

**그래서 생기는 구멍.** E가 수신 기록을 저장하고(반영 상태 `PENDING`) B 등록이 끝나기 전에 api가 죽으면,

1. 결과 본문은 E 어디에도 없다.
2. F가 다시 보내도 E는 "이미 받았다"고만 답하고 본문이 등록 경로로 가지 않는다.
3. 요청은 `PENDING`에 멈춘다. 계약은 자동 재분석을 허용하지 않고, 사용자 재요청도 실패가 확정된 경우에만 허용한다([명세 전이·불변 조건][c78]).

**F 보존으로는 막을 수 없다.** 계약에 E가 F에게 "다시 보내 달라"고 요청할 메시지가 없어서, F는 이 상태를 알 수도 없고 먼저 움직일 수도 없다. 즉 **이 구멍은 E 쪽에서 닫아야 한다.**

**E가 닫는 방법.** 안 1(복구에 쓸 자료를 E가 남기는 방향)이 권고안이며 E 담당도 이 방향을 지지했다([A/E 리뷰][rv166]). **안 2는 혼자서는 이 장애를 해결하지 못한다.** 안 1의 구체 방식은 아래처럼 갈래가 나뉘고, 갈래에 따라 계약 검토가 필요할 수 있다.

| 안 | 내용 | 혼자서 이 장애를 해결하는가 |
|---|---|---|
| **안 1 — 권고** | 수신 기록을 저장할 때 **복구에 쓸 자료를 같은 트랜잭션에 함께 남겨**, 재기동한 E가 자기 기록으로 B 등록을 다시 밀 수 있게 한다. 무엇을 남길지는 아래 두 갈래 | **방향으로는 그렇다.** F 개입도 새 메시지도 필요 없다. 다만 어느 갈래든 **재기동 뒤 미반영(`PENDING`) 작업을 찾아 처리하는 절차**가 있어야 실제로 복구된다 |
| 안 2 — 보조 | 이미 받았더라도 반영이 끝나지 않았으면 중복 수신 확인을 돌려주면서 본문을 등록 경로로 다시 넘긴다 | **아니다.** F는 `ACCEPTED`를 받으면 재전달을 멈추므로([5.2](#52-재전달)) **다시 보낼 계기가 없다.** 누가 F에게 다시 보내라고 알려야 작동하는데 그 수단이 계약에 없다 |

**안 1의 두 갈래** — 무엇을 남기느냐에 따라 확인할 것이 다르다.

| 갈래 | 남기는 것 | 먼저 확인할 것 | 계약 변경인가 |
|---|---|---|---|
| 1-가 | **결과 본문**을 E 수신 기록과 함께 서비스 DB에 | 계약은 "F 엔티티는 서비스 DB에 저장하지 않으며 출처 ID만 참조"하고([명세 B 등록·공개 경계][c85]), "등록되지 않은 F Result…는 서비스 DB의 F 테이블로 옮기지 않는다"고 정했다([명세 W 메시지][c162], [4.1](#41-두-종류)과 같은 문장). 미등록 결과 본문을 E 기록에 두는 것이 이 경계 안인지 | **판단 전**. 경계를 넘으면 계약 수정 절차를 밟는다 |
| 1-나 | 본문을 되찾을 수 있는 **영속 참조**를 E 수신 기록과 함께 | 참조 대상의 **위치**(미정, Q6)·**보존 기간**(E 복구 기간 이상)·**E의 접근 권한**. 참조 대상이 F가 보존한 결과라면 14일 보존과 F 저장소 접근 조건이 연결 조건이 된다 | **판단 전**. 참조 대상에 따라 다르다 |

**이 문서는 갈래를 고르지 않는다.** 저장·복구 방식과 계약 해당 여부는 E 후속 구현에서 확정하며, 실제 E 저장·복구 코드는 #116 범위가 아니다.

**안 2를 쓰려면 재전달을 다시 일으키는 조건이 함께 있어야 한다.** F가 수신 확인을 받은 뒤에도 일정 조건에서 다시 보내게 하거나, E가 F에게 재전달을 요청하는 경로를 만드는 것인데 후자는 새 메시지가 필요한 계약 변경이다([계약을 바꿔야 하는 것과 아닌 것](#계약을-바꿔야-하는-것과-아닌-것)). **이 문서는 어느 쪽도 결정하지 않는다.** 방식 선택은 E 담당의 몫이며 아직 고르지 않았다.

### 7.1 검토자가 없을 때

**실행은 팀원 1(H)로 확정했다(2026-09-29, 팀장).** 다만 팀에 H 영역을 검토할 사람이 없어 **작성자 외 검토자가 없다.** 이 칸을 억지로 채우지 않고 아래 두 가지로 대신하며, 검토 없음은 [8](#8-37-조건-대조--적용충족미확인)에 **미충족**으로 남긴다.

| 대체 수단 | 내용 |
|---|---|
| 판단을 검사로 바꾼다 | "허용 목록 밖 호스트를 부르면 막히는가", "worker를 죽였다 살리면 전달 안 된 결과를 다시 보내는가"는 사람이 봐야 아는 것이 아니라 검사가 통과·실패로 답한다. 검토자 부재로 약해지는 부분을 여기서 메운다([6](#6-검증-사례)의 V-12·V-19) |
| 재현 가능하게 남긴다 | 수행한 사람·환경·판본·명령·기대 결과·실제 결과를 PR에 적어 나중에 누구든 다시 돌려볼 수 있게 한다. 작업관리가 이미 요구하는 것이며, 작성자만 성공한 것을 팀 전체의 준비 완료로 보고하지 않는다 |

[#37][i37]의 C05가 요구하는 것은 "다른 사람이 봤다"가 아니라 **"실제 환경에서 검사했다"**이다. 검토자 부재와 C05 충족은 별개이며, C05는 그대로 실제 환경 검사로 판정한다.

| E가 결과 본문을 서비스 DB에 저장(안 1-가, [5.3](#53-수신-후-반영-전-장애--지금-막히는-곳)) | **판단 전** | 미등록 F 결과를 서비스 DB에 두지 않는다는 계약 문장([명세][c85], [명세][c162])과의 관계를 E 후속 구현에서 확인한다. 넘으면 계약 수정 |
| E가 영속 참조를 저장(안 1-나) | **판단 전** | 참조 대상의 위치(미정)·보존·접근 조건에 따라 달라진다 |
| E가 중복 수신 때 본문을 등록 경로로 다시 넘김(안 2) | **아니다** | 메시지 필드·수신 확인 값·상태 의미가 그대로인 E 내부 처리다. 재전달을 다시 일으키는 수단은 따로 필요하다(아래 행) |
| F의 "요청 거부" 알림 메시지([2.4](#24-상한을-넘거나-실패했을-때)) | **그렇다** | 새 메시지가 필요하다. **이번에 제안하지 않는다** |
| E가 F에게 재전달을 요청하는 경로([5.3](#53-수신-후-반영-전-장애--지금-막히는-곳)) | **그렇다** | 새 메시지가 필요하다. 안 1이면 필요 없다 |

## 8. #37 조건 대조 — 적용·충족·미확인

## 결정 이력

- **2026-09-29** — [#116][i116]으로 작성했다. 수집 방식은 API만 쓰는 안을 제안하고 복제 채택 시 필요한 통제를 따로 두었다. 자격정보 인계에 저장소 좌표와 연동 계정 로그인이 필요하다는 것, E가 결과 본문을 저장하지 않아 반영 전 장애에서 자료를 되찾을 수 없다는 것을 확인해 각각 A·E 확인 항목으로 올렸다. 작성 시점에는 수치를 모두 제안으로 적었다(결과 보존 14일은 아래 항목에서 결정됐고, 자원·시간 상한은 지금도 제안이다).
- **2026-09-29** — 팀장이 [수집 방식](#11-수집-방식--api만-쓴다)을 **API만 쓰는 것으로 결정**했다. 복제는 통제해야 할 것이 느는 문제가 아니라 "실행되지 않게 막아야 함"으로 위험의 종류가 바뀌고, [#37][i37] C05의 실제 환경 검사 부담도 늘기 때문이다. 큰 커밋의 변경 내용이 잘릴 수 있다는 한계는 근거의 `coverageLimits`로 드러내며 받아들인다. 제약 등록부의 "수집 방식은 미채택" 문구는 고치지 않았다.
- **2026-09-29** — 팀장이 [결과 보존 기간을 14일로 결정](#42-수명표)했다. 같은 검토에서 기존 근거였던 "E의 반영 실패 복구"가 [5.3](#53-수신-후-반영-전-장애--지금-막히는-곳)과 어긋난다는 것을 확인해 바로잡았다 — 그 구간은 F가 도울 수 없고, 보존이 실제로 쓰이는 것은 전달 실패·재기동·E 미수신이다. E 복구 기간과의 관계는 E가 안 2를 고를 때만 생기므로 미결 Q3을 막는 항목에서 확인 항목으로 낮췄다. 저장 위치는 그대로 미정이다.
- **2026-09-29** — 팀장이 나가는 방향 제한·결과 저장소 준비의 **실행을 팀원 1(H)로 확정**했다. 팀에 H 영역을 검토할 사람이 없다는 사실을 확인해, 검토자 칸을 채우는 대신 [7.1](#71-검토자가-없을-때)의 대체 수단(자동 검사·재현 가능한 증거)을 두고 "작성자 외 검토 없음"을 미충족으로 남겼다. 결과 저장 위치는 여전히 미정이다.
- **2026-09-29** — 후속 담당자가 쓸 수 있게 세 곳을 보완했다. ① 자동 재시도를 **현행 계약에 맞췄다** — GitHub 조회 재시도 제안(429·5xx 2회)을 뺐다. 계약이 자동 외부 재시도·추가 호출을 허용하지 않고([명세][c137]) 요구사항이 정책 자체를 미정으로 뒀기 때문이다([NFR4][r119]). 조회 재시도·분석 재실행·결과 재전달을 구분하는 표를 [2.3](#23-자원시간-상한)에 넣었고, 재전달은 계약이 분리해 둔 것이라 유지했다. ② [5.3](#53-수신-후-반영-전-장애--지금-막히는-곳)의 **안 2가 단독 해결책이 아님**을 명시했다 — F는 수신 확인을 받으면 재전달을 멈춰 다시 보낼 계기가 없다. 안 1을 권고안으로 두고 조건표·V-21·Q2·담당표를 맞췄다. ③ 결정된 세 건의 낡은 표현을 정리했다. 자동 재시도 허용을 새로 결정하거나 승인 계약을 고치지 않았다.
- **2026-09-29** — 이전 문구를 정리했다. 편집 중 첫 항목의 뒷문장이 마지막 항목 끝에 붙어 결과 보존 기간까지 제안으로 읽히던 것을 제자리로 돌리고, 항목 순서를 결정 순으로 바로잡았다. 9절 안내와 문서 머리·2.3의 '수치는 모두 제안' 표현을 자원·시간 상한으로 한정했다. 새 결정이나 설계는 없다.
- **2026-09-29** — A/E 담당 리뷰를 반영했다(문서·계약·E 수신 코드 대조 기준이며 실제 연동·복구 실행 검증은 아니다). §3.2 인계 방향과 §5.2 `messageId` 발급에 동의를 받아 Q1·Q4와 완료 기준 3을 갱신했다(Q1 제공은 [#133][i133] 후속). §2.4에서 종결 응답이 없으면 E가 실행 불명으로 바뀐다고 쓴 것을 **기존 상태 유지**로 바로잡고, 식별 불가를 E 접수 정본 오류로 단정한 문장을 고쳤다. §5.3의 안 1을 결과 본문 저장(1-가)과 영속 참조 저장(1-나)으로 나누고, 미등록 F 결과의 서비스 DB 저장 경계 때문에 "계약 변경 아님"을 **판단 전**으로 바꿨다. 재전달 때 `finishedAt`을 포함한 내용을 그대로 둔다는 조건을 §5.2·V-16에 넣었다.
