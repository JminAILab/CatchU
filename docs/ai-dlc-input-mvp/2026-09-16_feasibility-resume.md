# 10월 MVP feasibility 재개 안내

> 지위: 재개 준비·변경 영향 검토 메모(2026-09-16). 공식 feasibility 평가나 단계 승인 기록이 아니다. 조회 기준은 dev `d70d33a`와 아래 PR 판본이다. 이후 변경은 재개 시 다시 확인한다.

## 최신 인계 — feasibility 승인 후, Scope Definition 질문 진행

아래 §1~§5는 최초 재개 준비 시점의 기록이다. 이후 기존 답변·실험·사실 정정을 반영한 feasibility 산출물에 대해 사용자가 공식 승인했고, 기존 명령으로 승인·포인터 전환을 기록했다. 생성 사실성·운영 안전성 확보 또는 10월 달성을 승인한 것이 아니다. 승인 산출물과 감사 기록은 현재 intent에 보존한다.

**Scope Definition 범위 확정 전** C01·C02 재검증 일정, C10 실제 가용량·공통 작업 책임을 구체화해 제시한다. 기존 수용 기준·구현 착수 제한은 유지하고 미달·일정 수용 불가 시 실행 가능성을 재검토한다. 시간 배정·추가 API 호출은 자동 승인된 것이 아니다.

다음 단계 본문에 착수하기 전에 요청한 [2.9.0 사전 검토](../ai-dlc/2026-09-16_2.9.0_업데이트_검토.md)를 완료했고, 사용자는 설치를 보류하고 검증된 2.8.1로 Scope Definition 진행을 선택했다. [질문·최신 입력 검토](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/scope-definition/scope-definition-questions.md)를 시작했다. 범위·백로그 본문은 이번 단계의 작성 전 확인 후 작성하며 아직 승인하지 않았다. 버전 업데이트는 진행 중 workflow에 적용할 공식 지원 경로가 확인되거나 이번 workflow 종료 시 다시 검토한다. 설치·refresh·추가 하네스 수정은 하지 않는다. 2.8.1 장애 회고는 [기존 운영 기록](../ai-dlc/2026-09-16_feasibility_회고_재개점검.md)에만 보존하며 후속 버전 상시 규칙으로 등록하지 않았다.

- 첫 intent의 완료 상태·승인 산출물은 변경하지 않았다. 과거 답변을 최신화하거나 단계 완료로 처리하지 않았다.

## 3. 재개 직후 검토 순서

1. 기존 feasibility 질문·답변을 읽고 이미 확인한 NCP 계정·Admin, 담당·가용량을 재질문하지 않는다. Admin 확인을 서버 생성·외부 접속 검증 완료로 확대하지 않는다.
2. PoC 제출본을 읽어 기록·재현 검증·미검증을 구분한다. 규칙 기반 결과를 LLM 생성 검증으로 보지 않는다. 코드 채택은 분석 및 domain-design 전 수용 검토의 근거를 갖춰 결정한다.
3. #53·#55·#56으로 바뀐 입력을 반영하되 과거 승인 기록은 보존한다. 현행 입력 문서의 이력서 제외와 후속 재포함 결정의 관계는 별도 문서 보완 대상으로 남긴다.
4. 10월 일정 판단 전에 이력서 적용 시점·방식에 따른 작업량을 확인한다. 채용공고·알림은 메뉴 그림에 있다는 이유로 10월 기능으로 확정하지 않는다. LLM 실험·선정과 실제 환경 검증의 필요 시점도 구분한다.
5. 공식 평가·제약·위험 산출물 작성과 확인·승인은 AI-DLC 절차에서 진행한다. 화면 세부 계약을 모두 확정할 때까지 독립 검토를 멈추지 않되, 결론을 바꾸는 미정은 가정·조건·확인 책임과 함께 드러낸다.

추가로 이미 병합된 A-01 저장소 선택·분석 동의 초안에는 옛 홈 직행·GitHub 연동 미정 설명이 남아 있다. 팀원 4의 후속 보완을 팀원 2의 자산 탭 구성과 맞춘다. 같은 문서를 두 담당자가 동시에 독립 재작성하지 않는다.

rough-mockups에서는 위 초안의 제출 판본을 고정하고 홈 → 프로필 연동 → 자산 repo 연결 → 진행/실패/결과 → Catch 확인·공개 → 대표 구성(선택) → 링크 발행 → 비로그인 열람을 연결 검토한다. 화면 ID는 별도 URL이나 물리적 페이지를 강제하지 않는다. 현재 메모는 담당 제안·연결 확인을 팀 승인으로 바꾸지 않는다.

## 5. 브랜치 운영

- 새 재개 브랜치에는 최신 dev와 기존 feasibility 기록을 함께 둔다. 열린 화면 PR 전체를 미리 합치지 않는다.
- 이미 병합된 브랜치는 미반영 커밋·미커밋 변경·사용 중인 작업 폴더를 확인한 뒤 별도로 정리한다.
- `docs/share-link-manage-draft`는 PR #57에서 재사용 중이므로 이전 PR #38 병합만 보고 삭제하지 않는다.
- `revert-18-docs/스택확정-mvp입력`은 MVP 입력·작업관리 등을 제거하는 미병합 되돌리기 커밋이다. 재개에 반영하지 않으며 생성 경위 확인 후 별도 처리한다.
