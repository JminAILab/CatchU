```text
[아이콘 하나]                                  [로그인]
```

## 4. PC 웹 와이어프레임

### 4.1 L01 — 링크 발행 준비

[화면 제안] 대표 없이 발행 가능하다는 H §7의 안내 위치 제안을 수용해 L01에 둔다. 공개 자료를 요약해서 확인하되 여기서 프로필·주장·Catch를 편집하거나 자동 공개하지 않는다.

```text
┌─ L01 링크 발행 준비 ─────────────────────────────────────┐
│ [CatchU 로고] [내 자산] [공유 링크]                       │
│ [채용 공고] [알림] [프로필]                              │
├─────────────────────────────────────────────────────────┤
│ [임시 예시] 기본 프로필: <공개 허용 항목 요약>            │
│ 대표 구성: 있음 — <저장된 주장> + Catch A·B              │
│ 현재 공개 GitHub 자산: A·B·C·D                           │
│ 대표 밖의 공개 GitHub 자산도 수신자가 볼 수 있습니다.    │
│ 대표 구성을 완료하지 않아도 링크를 발행할 수 있습니다.   │
│ [공개 자료 확인으로]                                     │
├─────────────────────────────────────────────────────────┤
│ 링크 제목(필수): [예: A사 지원                       ] │
│ 나에게만 보이며 발행 후 제목을 수정할 수 없습니다.      │
│ 현재 유효 링크: <N>/5개 — 중단·만료 링크 제외            │
│ 5개라면 사용하지 않는 링크를 중단한 뒤 발행해 주세요.    │
│ [공유 링크 관리로]                                      │
│ 비밀번호 사용 □     [선택 시 비밀번호 입력            ] │
│ [비밀번호 보기] ← 사용 선택 시 표시                     │
│ 비밀번호는 발행 후 변경·해제할 수 없습니다.              │
│ 유효기간: 발행 시점부터 30일 — 고정                      │
│ [돌아가기]                                  [링크 발행] │
└─────────────────────────────────────────────────────────┘
```

- [임시 예시] A·B는 대표 Catch, C·D는 대표 밖 공개 Catch다. 팀원 2 W03의 미공개·숨김 예시 상태를 공개로 바꾼 결과가 아니라 독립적인 화면 예시다.
- [연결 제안] [공개 자료 확인으로] → W03. [돌아가기] → 진입한 W03·W06·L03, 직접 진입 시 L03을 복귀 기본값으로 제안한다. 다른 화면의 편집·저장 상세는 해당 담당에게 남긴다.
- [결정] [링크 발행]을 누르면 **요청 전 즉시 발행 중 표시와 버튼 차단**을 적용한다(F 2026-09-15). [화면 제안] 서버의 생성 성공 응답(URL·발행/만료 시각) 후에만 L02로 이동한다. 대기·실패·응답 유실은 완료가 아니며 복구는 §4.8을 따른다. 대표 없음만으로 발행을 막지 않는다(FR3.1).
- [결정] 제목은 필수이고 앞뒤 공백을 뺀 값으로 비교한다. 같은 사용자의 유효 링크에는 같은 제목을 쓸 수 없다. 중단·만료된 제목은 다시 쓸 수 있으며, 같은 수신처의 조건 변경은 기존 링크 중단 후 같은 제목으로 새로 발행한다. 제목은 수신자에게 전달하지 않으며 10월에는 발행 후 편집하지 않는다(F 2026-09-15).
- [화면 제안] 공백만 입력하면 ‘링크 제목을 입력해 주세요’를 표시한다. [공유 링크 관리로] → L03. 유효 링크 5개를 확인하면 한도 안내와 관리 경로를 제공한다. 제목 길이 제한은 화면 검토 항목으로 남긴다.
- [결정] 서버는 사용자 단위로 **같은 제목의 유효 링크 확인·유효 링크 5개 미만 확인·생성을 한 번에 처리**한다. 버튼 차단이나 사전 조회만으로 다른 탭·동시 요청의 중복/한도 초과를 막았다고 하지 않는다. 5개는 10월 시작값이며 중단·만료는 세지 않는다. 제목·한도는 FR4 원문에 없던 후속 발행 조건이다(F 2026-09-15). [미정] 잠금·API·저장 구조는 #23 계약 설계에서 정한다.
- [결정] 공개 자산 조회에 성공해 0개로 확인돼도 발행을 허용한다(F, §4.7). [화면 제안] ‘현재 공개된 GitHub 자산이 없습니다’ 안내와 [링크 발행]을 제공한다. 조회 실패를 0개로 취급하지 않으며, 공개 프로필 항목은 OQ3의 합의 대상이다.

- [화면 제안] 발행자 비밀번호 오타 확인을 위해 기본은 가림 상태로 두고 [비밀번호 보기]를 누르면 현재 입력값을 표시하며 버튼을 [비밀번호 숨기기]로 바꾼다. 다시 누르면 가린다. 발행 전 입력값 확인용이며 발행 후 저장된 비밀번호 원문 조회·변경 기능이 아니다.

- [요구] 실제 발행·만료 시각을 기준으로 안내하며 기간 선택·연장 기능을 두지 않는다(FR4.5). [화면 제안] 비밀번호 원문 재조회 기능은 추가하지 않는다.

### 4.3 L03 — 공유 링크 관리

[화면 제안] 본인 권한을 확인한 발행자만 상단 [공유 링크] 또는 L02에서 진입하고 현재 목록을 조회한다. **발행 시각 최신순 한 목록**에 제목과 상태를 표시한다. [결정] 상태는 아이콘만 쓰지 않고 **유효·중단됨·만료됨 글자**로 함께 전달한다. 발행 후 제목 편집은 10월에 제공하지 않는다(F 2026-09-15). [화면 제안] 상태별 탭·검색·일괄 중단은 추가하지 않는다. 동일 시각 정렬·목록 분할은 연결 계약에서 합의한다.

```text
┌─ L03 공유 링크 ─────────────────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크]
│ [채용 공고] [알림] [프로필]
│ 공유 링크                         [새 링크 발행]
│ 발행 시각 최신순                  [목록 새로고침]
│ [임시 예시 — 실제 발행 결과 아님]
├────────────────────────────────────────────────────
│ 제목: A사 지원
│ URL: https://example.invalid/share/demo-a
│ 상태: 유효                  비밀번호: 설정됨
│ 발행: <발행 시각>           만료: <만료 시각>
│ 남은 기간: <약 N일 — 보조 표시>
│ [URL 복사] [링크 중단]
├────────────────────────────────────────────────────
│ 제목: B사 이전 지원
│ URL: https://example.invalid/share/demo-b
│ 상태: 중단됨                비밀번호: 없음
│ 발행: <발행 시각>           만료: <만료 시각>
│ 이 URL은 다시 활성화할 수 없습니다.
├────────────────────────────────────────────────────
│ 제목: C사 지원
│ URL: https://example.invalid/share/demo-c
│ 상태: 만료됨                비밀번호: 설정됨
│ 발행: <발행 시각>           만료: <만료 시각>
│ 새 링크가 필요하면 위의 [새 링크 발행]을 누르세요.
└────────────────────────────────────────────────────
```

- [연결 제안] [새 링크 발행] → L01에서 현재 저장된 구성·공개 자산을 조회하고 비밀번호 조건을 새로 확인한다. 기존 링크의 조건을 자동 복제하지 않으며 버튼 클릭만으로 발행하지 않는다. 기존 URL 복구가 아니고 새 URL을 수신자에게 전달해야 한다. W03·W06 연결 조건은 §6을 유지한다.
- [요구] 중단 후 같은 URL의 재접근도 열람되지 않으며 자산은 삭제·숨김 처리되지 않는다(FR4.3). [결정] 중단·만료 URL 복구 및 발행 후 비밀번호 변경·해제 기능은 두지 않는다(M OQ4).

#### 4.3.1 상태·시각과 행동

| 확인된 링크 상태 | 표시·가능한 행동 [화면 제안] | 적용 조건 |
|---|---|---|
| 유효 | 발행·만료 시각, 남은 기간, 비밀번호 설정됨/없음, [URL 복사]·[링크 중단] | 유효는 비밀번호·Catch 공개 조건까지 충족했다는 뜻이 아님 |
| 중단됨 | 발행·만료 시각, 비밀번호 설정 여부, 재활성화 불가 안내 | 복사·중단 버튼 없음. 새 발행은 목록 상단 → L01 |
| 만료됨 | 발행·만료 시각, 비밀번호 설정 여부, 새 링크 안내 | 기간 연장·URL 복구·중단 버튼 없음 |
| 중단과 만료가 함께 확인됨 | 주 상태 ‘중단됨’, 보조 ‘만료 시각도 지났습니다’ | 두 사실을 보존하는 표시 제안. 서버 상태 enum·우선순위를 확정하지 않음 |

- [화면 제안] 정확한 만료 시각을 주 정보로 표시한다. 표시 형식은 `YYYY-MM-DD HH:mm:ss (KST, UTC+09:00)`를 제안하며 L02와 맞춘다. 만료 값은 발행 시점부터 30일인 서버 기준 시각을 사용한다. 남은 기간은 유효한 링크에만, 24시간 이상은 일 단위 내림으로 ‘약 N일’, 그 미만은 ‘24시간 미만’으로 표시하는 안이다. 날짜·남은 기간 표시는 접근 허용 판정을 대신하지 않는다.
- [연결 제안] 본인 링크 식별·제목·URL, 서버 기준 발행/만료 시각·현재 상태·확인 시각, 유효 링크 수, 비밀번호 설정 여부, 중단 확인 결과가 필요하다. 중단·만료 동시 성립 정보도 합의한다. 정보의 의미만 정리하며 비밀번호 원문·API 경로·스키마는 확정하지 않는다.
- [화면 제안] 목록을 읽은 뒤 상태가 바뀔 수 있으므로 복사·중단 전에 현재 조건을 확인한다. 복사 확인은 클립보드 쓰기 성공만 뜻하며 이후 열람을 보장하지 않는다. 상태 확인 실패 시 성공이나 유효로 단정하지 않고 재조회 안내를 표시한다.

#### 4.3.2 중단 확인과 결과 4분기

[화면 제안] [링크 중단]은 선택한 URL을 명시하는 확인 상자를 연다. [취소]는 상자를 닫고 요청하지 않는다. 실행 전 취소와 전송 후 요청 취소를 구분한다.

```text
┌─ 이 링크를 중단할까요? ─────────────────────────────
│ [임시 예시] 대상: A사 지원 — …/demo-a
│ 중단하면 이 URL로 자료를 열람할 수 없습니다.
│ 이미 열린 화면에는 다음 이동·새로고침부터 반영됩니다.
│ 중단한 URL은 다시 활성화할 수 없습니다.
│ 자료 자체를 삭제하거나 숨기지는 않습니다.
│ [취소]                               [링크 중단]
└────────────────────────────────────────────────────
```

| 결과 분기 | 표시 [화면 제안] | 버튼·이동·확인 조건 [화면 제안] |
|---|---|---|
| 요청 중 | ‘중단을 요청하고 있습니다.’ | 해당 링크 반복 제출 차단. 전송 후 [취소]는 제공하지 않음. 화면 이탈이 요청 취소라는 안내도 하지 않음 |
| 성공 확인 | ‘링크가 중단되었습니다.’ | 확인 상자를 닫고 L03 해당 행을 중단됨으로 갱신. 서버의 중단 확인 전에는 이 문구를 쓰지 않음 |
| 실패 확정 | ‘링크를 중단하지 못했습니다.’ | 실패가 확정된 경우만 사용. [상태 다시 확인] → 현재 상태 조회 → 유효하면 중단 확인 상자를 다시 열 수 있음. 중단·만료면 해당 상태 표시 |
| 응답 불명 | ‘중단 여부를 확인하지 못했습니다.’ | [상태 다시 확인]으로 조회만 수행. 중단 완료·실패·계속 열람 가능 어느 것도 단정하지 않음. 확인 전 중단 재전송 차단 |

[연결 제안] 결과 조회가 중단됨을 확인하면 그 상태로 갱신하되 이번 클릭으로 중단됐다고 추정하지 않는다. 유효 상태 조회만으로 아직 처리 중인 요청이 끝났다고 판단하지 않으며, 미처리·실패가 확정돼 재요청 가능한지 함께 확인한다. 요청 식별·중복 처리·결과 조회의 계약, 불명 상태로 전환할 대기 시간은 OQ14와 연결 합의 대상으로 남긴다. 프런트엔드 버튼 차단만으로 중복 처리가 해결됐다고 하지 않는다.

#### 4.3.3 목록 조회·빈 상태·재진입

| 상황 | 표시와 다음 행동 [화면 제안] |
|---|---|
| 최초 조회 중 | ‘공유 링크 목록을 불러오는 중입니다.’. 빈 목록이나 유효 상태를 먼저 표시하지 않음 |
| 조회 성공·0개 | ‘발행한 링크가 없습니다.’ + [새 링크 발행] → L01 |
| 조회 실패 | ‘공유 링크 목록을 불러오지 못했습니다.’ + [목록 다시 불러오기]. 0개로 대체하지 않음 |
| 기존 목록 갱신 중·실패 | 이전 목록에는 ‘마지막 확인 기준·최신 상태 확인 필요’를 표시하고 상태 의존 행동을 잠시 막음. 실패 시 재조회 제공 |
| 중단 응답 불명 후 재진입 | 목록과 해당 요청 결과를 다시 확인. 이전 화면의 ‘요청 중’을 성공으로 치환하지 않음. 조회 실패 시 불명 상태 유지 |
| 발행자 세션 만료·권한 확인 실패 | 본인 목록 표시 중지. 인증 만료가 확인되면 회원 영역의 로그인 경로, 단순 통신 실패면 재조회 안내. 비로그인 수신자 경로와 구분 |

[화면 제안] 목록 조회 실패 중에도 상단 탐색과 [새 링크 발행] 진입은 유지할 수 있다. 발행 응답이 불명이면 §4.8의 같은 제목 [다시 발행]을 제공한다. 제목을 바꿔 발행해도 이전 요청의 성공 여부를 확인한 것은 아니다. [연결 제안] 로그인 후 복귀·입력 유지 범위는 회원·공통 담당과 합의하며 브라우저 저장소에 비밀번호를 보관하는 기능을 추가하지 않는다.

```text
┌─ V01 비밀번호 입력 ─────────────────────────────────────┐
```

- [요구] 유효하고 비밀번호가 설정된 링크는 올바른 조건을 충족해야 V02를 열람한다. 미설정 링크는 V01을 건너뛴다(FR4.2·FR4.4).
- [화면 제안] 빈 입력·오입력은 V01에서 안내하고 본문은 표시하지 않는다. [열람하기]는 현재 링크 조건과 비밀번호를 확인해 V02로 연결한다.
- [미정] 세션 유지 기간·재인증·오입력 제한 상세는 OQ4·OQ14 연결 설계에서 정한다. 인증 성공을 만료·중단 이후 열람 권한으로 사용하지 않는다(NFR1).

### 4.5 V02 — 공개 자료 열람·접근 불가 상태

[결정] F의 「팀장 확인 (2026-09-14): 링크 용어·수신자 접근 불가 안내」(`da69eb4`)에 따라 수신자에게 중단·만료·없는 URL 사유를 구분하지 않는다. 비밀번호 없이 중단 사실이나 URL 존재 여부를 추론할 단서를 주지 않도록 동일하게 안내하며, 비밀번호 입력보다 먼저 표시하는 순서는 유지한다. 중단·만료 상태 구분은 발행자 L03에만 둔다. [화면 제안] 공통 문구는 “이 링크는 열람할 수 없습니다.”이며 프로필·Catch 본문과 사유별 안내를 표시하지 않는다. 이 문구 통일은 열람 허용 조건을 완화하지 않는다.

```text
┌─ V02 공개 자료 ─────────────────────────────────────────┐
│ 수신자 전용 헤더 — §3.1                                 │
├─────────────────────────────────────────────────────────┤
│ 기본 프로필: <공개 허용 항목>                            │
│ 직무·기술 스택을 표시하면 ‘직접 입력한 정보’ 구분        │
├─────────────────────────────────────────────────────────┤
│ 대표 — 있는 경우                                        │
│ <발행 당시 대표 주장 문구>                               │
│ [Catch A 상세 보기]             [Catch B 상세 보기]      │
├─────────────────────────────────────────────────────────┤
│ 그 밖의 공개 GitHub 자산                                 │
│ [Catch C 상세 보기]             [Catch D 상세 보기]      │
└─────────────────────────────────────────────────────────┘

┌─ V02 접근 불가 상태 — 자료 대신 표시 ────────────────────┐
│ 수신자 전용 헤더 — §3.1                                 │
├─────────────────────────────────────────────────────────┤
│ 이 링크는 열람할 수 없습니다.                           │
└─────────────────────────────────────────────────────────┘
```

- [화면 제안] [상세 보기] → 해당 Catch의 V03. 대표가 없으면 대표 영역을 생략하고 공개 GitHub 자산 목록을 표시한다.
- [요구] 대표 밖 공개 자산도 열람하며 현재 숨긴 Catch는 제외한다. 기존 대표에 숨긴 카드가 생겨도 다른 카드로 자동 보충하지 않는다(FR3.2·FR3.4).
- [결정] 공개 자산 0개 발행을 허용하며 수신자에게는 공개 허용 프로필과 자료 없음 안내를 제공한다(F, §4.7). [화면 제안] ‘현재 열람할 수 있는 공개 GitHub 자산이 없습니다’를 표시한다. 숨긴 카드의 제목·개수·내용은 공개하지 않는다. 발행 후 전체 숨김으로 0개가 된 경우에도 현재 링크 조건을 적용한다.
- [미정] 프로필·Catch 본문 버전은 OQ3이므로 화면 전체가 발행 당시 그대로라는 문구를 사용하지 않는다.

### 5.2 열람 중 상태가 바뀌는 경우

[결정] F의 2026-09-15 확인에 따라 서버는 **공개 자료 목록 진입·Catch 상세 열기·새로고침·비밀번호 확인을 포함한 수신자의 요청마다** 현재 링크 상태와 Catch 공개 상태를 판단한다.

- 이미 열린 화면은 실시간으로 회수하지 않는다. 요청 없이 보고 있는 화면은 유지한다.
- 10월에는 주기적 확인·서버 알림·다른 탭에서 돌아왔을 때의 확인을 넣지 않는다.
- 수신자 응답은 **브라우저·중간 서버에 캐시하지 않는다.** 뒤로 가기 등으로 중단 전 응답을 재사용하지 않도록 계약 설계에 포함한다.
- 중단 확인 상자에는 이미 열린 화면에 다음 이동·새로고침부터 반영됨을 알린다(§4.3.2).

| 다시 확인한 변화 | 화면 전환 [화면 제안] | 지켜야 할 경계 |
|---|---|---|
| 링크 중단·만료 확인 | 프로필·Catch 표시를 공통 접근 불가 안내로 교체. 재인증으로 우회시키지 않음 | [요구] FR4.3~FR4.5·NFR1. 사유 노출은 §4.5 기준 |
| 링크 유효, 해당 Catch 숨김·원본 비공개 확인 | 요청한 V02 목록에서 해당 Catch 제외. 해당 V03을 새로 요청하면 내용 대신 열람 불가·[공개 자료 목록으로] 표시 | [요구] FR1.5·FR3.4. 다른 공개 Catch 유지. 요청 없이 이미 보고 있는 화면은 회수하지 않음 |
| 링크 유효, 공개 자산 모두 제외 | 허용된 프로필과 자료 없음 안내 | [요구] 링크 상태와 자산 상태 분리. [결정] §4.7의 공개 자산 0개 발행 허용과 일치 |

[미정] 요청마다 확인하는 시점과 캐시 금지 자체는 결정됐다. 캐시 금지의 구체 방식·인증 세션과의 관계·응답 경합 처리는 #23의 계약 설계에, 원본 비공개 확인 방법은 OQ2에, 프로필·Catch 본문 버전은 OQ3에 남긴다. 실제 접근 제어 검증은 구현 후 수행한다.

- [미정] 필드명·버전 형식·전송 수단·저장 방식·API 계약, 동시 변경 판정·발행 직전 재확인·복귀 조작의 세부는 후속 협의 대상이다. 기본 프로필·Catch 본문 버전(OQ3), W03~W06의 나머지 상세 검토도 이번 두 조건 확인으로 완료하지 않는다.

### 6.4 운영 기록 연결 — FR10.3·NFR8

[요구] 해당 기능의 오류·접근 권한 위반 징후를 운영자가 기록에서 확인할 수 있어야 한다(FR10.3·NFR8). [연결 제안] M OQ13의 애플리케이션 로그와 운영자 요약 화면 제안을 연결하되, 여기서는 발생 지점·전달할 정보의 의미만 정리한다. L03에 운영자 로그 화면을 추가하거나 운영 담당을 팀원 1로 자동 배정하지 않는다.

| 발생 지점 | 기록 연결안 [연결 제안] | 사용자 화면과의 구분 |
|---|---|---|
| L01 발행 처리·결과 조회 | 서버의 발행 처리·권한 확인 지점에서 오류·거부 결과를 공통 운영 기록에 연결. 클라이언트 응답 유실은 서버 처리 결과와 구별할 요청 참조로 연결 | 클라이언트 타임아웃을 발행 실패 확정으로 기록하지 않음 |
| V01 비밀번호 검증 | 서버 검증 지점의 불일치·처리 오류·권한 위반 징후를 구분해 전달 | 비밀번호 입력값·저장된 원문은 기록하지 않는 안. 단일 오입력을 곧바로 공격으로 단정하지 않음 |
| L03 중단 처리·결과 조회 | 서버의 본인 권한 판정·중단 처리 오류·결과 조회 오류를 연결 | 화면의 요청 중·불명 상태와 서버의 최종 결과를 구분 |
| V02·V03 접근 확인 | 링크 중단·만료·비공개 Catch 접근 거부와 권한 우회 징후를 서버 판정 지점에서 연결 | 상세 원인은 권한 있는 운영 기록에서만 확인. 수신자에게는 §4.5 공통 안내 유지 |

[연결 제안] 사건 시각·처리 종류·요청/대상 참조·결과 구분·오류 분류를 연결에 필요한 정보 후보로 둔다. 공유 URL의 비밀 식별 부분, 인증 토큰·비밀번호·프로필·Catch·근거 원문 전체가 로그에 유입되지 않도록 제외·마스킹을 함께 합의한다. 이는 고정 로그 스키마가 아니다. 정상 접근 거부와 권한 위반 징후를 구분하고, 화면 오류가 서버에 도달하지 않은 경우의 수집 방식도 공통 담당과 확인한다.

[미정] 실제 기록 항목·도구·보관 기간·조회 권한·담당·대응 시간은 OQ13에 남긴다. 자동 탐지·경고 임계값·자동 중단을 새로 확정하지 않는다. 이 영역에서 AI를 호출하지 않는다는 이유로 전체 제품의 AI 호출량·비용 기록 요구를 삭제하지 않으며, 해당 기록은 호출을 수행하는 영역과 공통 운영의 연결 대상으로 둔다. 신규 분석·AI 호출 중단이 현재 허용된 기존 링크 열람을 없애지 않는 FR10.4도 유지한다.
