## 1. 목적·적용 범위·지위

팀원들이 구현 전에 사용자 요청 흐름, 서비스 책임, 연결 규칙, 공통 개발 기반을 같은 기준으로 이해하기 위한 문서다. 공식 AI-DLC 설계를 대체하지 않으며, 후속 domain-design·contract-design·인프라 설계의 입력으로 사용한다.

이 문서의 표현은 다음과 같이 구분한다.

| 구분 | 의미 |
|---|---|
| 기존 확정 사실 | 기존 기술 방향·승인 범위·확인된 팀 결정 |
| 이번 대화에서 채택 | 팀장이 이번 논의에서 선택한 아키텍처·개발 준비 방향. 공식 설계 승인은 아님 |
| 조건부 우선안 | 먼저 검토할 안이며 비용·일정·호환성 등의 확인이 필요 |
| LLM 제안 | 검토를 위해 제시했으나 확정하지 않은 내용 |
| 미결 | 담당자 후속 설계나 별도 판단이 필요한 내용 |

범위 판단은 승인 산출물과 확인된 후속 결정을 따른다. 과거 입력 문서나 다른 worktree의 초안을 dev 반영 사항으로 취급하지 않는다. 이 문서의 담당 표는 논의에서 확인한 책임 구분과 제안이며, 실행 현황판을 대신하지 않는다.

## 2. 첫 MVP의 제품 흐름과 이후 기능

첫 MVP는 다음 흐름을 실제로 연결한다.

> Google 로그인·GitHub 연동 → 선정 공개 저장소 선택·분석 동의 → 실제 분석 → 경험 후보·근거·짧은 설명 초안 확인 → 사용자의 별도 공개 선택 → 링크 발급 → 수신자의 비로그인 열람

기본 목록·상세·공개/숨김·불일치 표시를 포함한다. 분석 결과는 자동 공개하지 않으며, 숨긴 자산은 기존 링크에서도 제외한다. 링크 중단·30일 만료·선택 비밀번호 등 기존 승인 기준을 유지한다. 이 문서의 요약에 생략된 세부 승인 조건을 삭제한 것으로 해석하지 않는다.

대표 주장 편집·Catch 대표 구성·발행 당시 대표 구성 보존은 첫 MVP 이후 개발하며 날짜는 미정이다. 탐색·일괄 관리·부가 UI는 후속 검토 후보이고, 별도 내부 품질·운영 기능 G는 10월에서 제외한다. 서비스 권한·자료 보호·실패 처리·호출 상한은 계속 필요하다.

RAG와 MCP는 **첫 MVP에서 연결하기 좋은 구조만 준비하고 실제 제공은 이후**로 둔다. Catch와 근거의 연결, 소유권·공개 권한, 재사용 가능한 서비스 업무 규칙을 기반으로 삼는다.

| 후속 구상 | 방향과 한계 |
|---|---|
| RAG | 링크 수신자의 질문에 관련 Catch·근거를 찾아 활용하는 방향 |
| JD 활용 | 승인된 JD 기반 요약·질문 응답과의 연결 검토. 본인 경험 추천·구성 안내는 별도 후속 후보 |
| Catch를 청크로 사용 | 팀장 구상. 청크 분할·검색 방식·임베딩·벡터 저장소는 미결 |
| MCP | 본인 권한 안에서 데이터 조회와 서비스 조작을 제공하는 방향. 실제 도구 목록은 후속 설계 |
| 테스트 활용 | MCP를 통한 서비스 흐름 검증을 검토하되, 브라우저 화면 검증과 구분 |

CatchU가 자기소개서 문장이나 포트폴리오 초안을 생성하는 기능은 추가하지 않는다. 사용자가 MCP로 제공받은 본인 데이터를 외부에서 활용하는 것은 별개다. 승인된 JD 기능의 자료 범위·권한·호출 상한을 이 구상만으로 변경하지 않는다.

## 3. 전체 구성과 핵심 요청 흐름

기존 스택은 **Next.js / NestJS / FastAPI / NCP**다. 이번 대화에서는 첫 MVP부터 컴퓨트 서버를 두 대로 나누기로 했다. 브라우저는 NestJS API를 직접 호출한다.

```text
브라우저
 ├─ 화면 요청 ──────────→ Next.js
 └─ 인증·분석·조회·공유 → NestJS
                           │
           서비스 서버      ├─ PostgreSQL
          [Next.js/NestJS]   ├─ 요청 큐 ─────────→ FastAPI worker
                           │                    [분석 서버]
                           │                         │
                           │                  GitHub 수집·LLM 분석
                           │                         │
                           │                  비공개 Object Storage
                           │                  구조화된 완료 결과 저장
                           │                         │
                           └─ 결과 큐 ←──────────────┘
                                │             작업 ID·저장 위치 전달
                           결과 읽기·검사
                                │
                           PostgreSQL 반영
                                │
브라우저 ←──── NestJS를 통한 상태·결과 조회 ─────┘
```

그림은 논리적 요청 흐름이다. 요청 큐와 결과 큐는 역할이 다른 논리적 큐 두 개이며, 이를 위해 Redis 계열 서버를 반드시 두 개 운영해야 하는 것은 아니다. 큐·DB의 실제 관리형 구성과 VPC 배치는 후속 설계한다.

분석 요청은 다음 순서로 처리한다.

1. 브라우저가 NestJS에 저장소와 분석 동의를 전달한다.
2. NestJS가 사용자 권한·요청 조건·진행 중인 동일 작업을 확인하고 분석 작업을 등록한다.
3. 요청 큐를 통해 worker에 작업을 전달한다. 메시지에 GitHub 토큰 같은 비밀값을 넣지 않는다.
4. worker는 필요한 경우 NestJS 내부 API에서 해당 작업에 필요한 GitHub 접근 토큰을 받는다.
5. worker가 수집·분석하고, 구조화된 완료 결과를 비공개 Object Storage에 저장한다.
6. 결과 큐로 작업 식별자와 저장 위치를 전달한다.
7. NestJS가 결과를 읽고 형식·작업 연결·반영 조건을 검사하여 DB에 반영한다.
8. 브라우저가 NestJS를 통해 상태와 결과를 조회한다.

**사용자에게 분석 완료를 표시하는 기준은 서비스 DB 반영까지 끝난 상태**다. Object Storage 업로드만으로 완료 처리하지 않는다.

클라이언트는 DB에 직접 접근하지 않는다. 상태 조회는 첫 MVP에서 **주기적 조회 방식**으로 시작하며, 완료·실패 시 중단한다. 일시적인 조회 오류를 분석 실패로 표시하지 않는다. 조회 간격과 화면 이탈·재접속 동작은 후속 설계한다.

## 4. 서비스 책임·데이터 소유권·접근 경계

A~I는 회의용 영역 구분이며 공식 AI-DLC 유닛 ID가 아니다.

| 구성 요소 | 책임 | 경계 |
|---|---|---|
| Next.js | 화면·사용자 입력·API 호출·상태 표시 | DB·큐·worker 직접 접근 없음 |
| NestJS A | Google 로그인, CatchU 인증, GitHub 연동·토큰 관리 | GitHub 토큰을 브라우저에 제공하지 않음 |
| NestJS E | 분석 요청 접수, 작업 상태, 중복 요청·실패·재요청 관리 | 분석 완료와 자산 공개를 같은 상태로 취급하지 않음 |
| NestJS B | 자산·Catch·근거의 서비스 저장, 본인 조회, 공개/숨김 | 분석 성공만으로 공개하지 않음 |
| NestJS C | 링크 발급·중단·만료·비밀번호·수신자 권한 확인 | 링크 발행 당시 공개 여부만 믿지 않고 현재 권한 확인 |
| FastAPI worker F | GitHub 자료 수집·근거·경험 후보·짧은 설명 초안 생성 | 서비스 PostgreSQL에 직접 접근하지 않음 |
| 큐 | 작업과 결과 알림 전달 | 사용자에게 보여 줄 최종 상태의 정본으로 사용하지 않음 |
| Object Storage | 완료 결과의 임시 보존·재전달 지원 | 공개 자산 저장소나 클라이언트 직접 조회 경로로 사용하지 않음 |

E와 B는 처음부터 별도 서버나 별도 DB로 나누는 것이 아니라, **NestJS 안에서 변경 책임을 구분**한다.

예를 들어 E는 “분석 작업이 완료됐다”를 관리하고, B는 “생성된 자산을 사용자가 공개했다”를 관리한다. 분석 상태가 변경돼도 공개 상태가 자동으로 바뀌어서는 안 된다.

결과 검사 역시 LLM 내용 전체의 사실성을 보증하는 절차는 아니다. 형식 검사·작업 소유권·근거 연결 검사와, C01에서 다룬 사실·기여 귀속 품질 문제를 구분한다.

## 5. 주요 기술 선택과 판단 근거

| 항목 | 이번 논의의 방향 | 이유·대안·남은 조건 |
|---|---|---|
| 관계형 DB | PostgreSQL 채택 | 자산·사용자·링크 관계 관리와 향후 Catch 검색 구상 |
| DB 운영 | NCP 관리형 우선, MVP 단일 구성 | 초기 운영 부담을 줄이는 선택. 12월은 단일 구성을 전제로 하지 않으며 구체적 HA 방식은 미결 |
| ORM | TypeORM 채택 | 팀장의 사용 경험과 취업 관점 선호. 국내 점유율 우위가 입증된 것으로 기록하지 않음 |
| 향후 검색 | 키워드·유사어 목록과 `pg_trgm` 활용 구상 | 문자 유사도 기반 접근과 의미 검색은 구분. 첫 MVP 검색 기능 추가나 최종 검색 구조 확정은 아님 |
| 큐 운영 | NCP 관리형 서비스 우선 | 정확한 엔진·버전·영속성·장애 동작·비용 확인 필요 |
| 큐 라이브러리 | **BullMQ 우선 검증 후보** | NestJS·Python 간 사용 가능성을 검증. Redis Streams 직접 구현은 대안 |
| 완료 결과 보존 | 비공개 NCP Object Storage | DB 반영 실패 시 저장된 결과를 다시 전달하기 위한 기반 |
| 배포 | 이미지 기반, 두 서버에서 Docker Compose로 수동 배포 | 초기 운영 규모와 팀원의 학습 부담을 고려 |
| 이미지 생성 | MVP는 팀장 PC | 검증한 커밋에서 반복 가능한 방식으로 생성. 서버 CPU 대상 확인 필요 |
| 이미지 저장소 | NCP Container Registry 우선 | 계정 권한·크레딧 적용·비용 확인 필요 |
| 외부 요청 진입점 | ALB 조건부 우선 | 일정상 어렵다면 서비스 서버의 리버스 프록시 대안 검토 |
| 운영자 접속 | NCP SSL VPN 조건부 우선 | 비용·크레딧·팀장 Mac 환경 확인 후 판단. 별도 bastion은 대안 |

BullMQ 최종 선정은 팀원 1이 판단한다. 다음을 확인하기 전에는 채택 완료로 기록하지 않는다.

- NestJS 요청 → Python 처리 → NestJS 결과 수신의 호환성.
- worker 중단·메시지 재전달이 **자동 LLM 재실행으로 이어지지 않는지**.
- 결과 재전달 시 DB에 중복 반영하지 않는지.
- NCP 관리형 큐의 명령 제한·메모리 정책·영속성·장애 복구 동작과 맞는지.

실험에 사용한 모델과 서비스 최종 LLM 선정은 별개이며, API-only 수집과 Git 복제 병행 여부도 미결이다.

## 6. 비동기 작업·실패·재요청 기준

| 상황 | MVP 방향 |
|---|---|
| 같은 사용자가 같은 저장소의 진행 중 분석을 다시 요청 | 기존 작업을 반환 |
| 같은 사용자가 결과 생성 후 서비스 DB 반영을 기다리거나 반영 실패를 복구하는 중인 같은 저장소를 다시 요청 | §3의 완료 기준(서비스 DB 반영 완료)에 따라 아직 진행 중이므로 기존 작업을 반환. 새 분석을 시작하지 않음 |
| 완료·실패 후 사용자가 명시적으로 다시 요청 | 새 작업으로 처리 |
| 분석 실패 | 자동 분석 재시도 없이 사용자 재요청 기준 유지 |
| 완료 결과 전달·DB 반영 실패 | 이미 보존된 결과를 재전달·재반영할 수 있도록 설계 |
| 결과 메시지 중복 수신 | 같은 결과를 중복 저장하지 않도록 검사 |
| 브라우저 종료·새로고침 | 분석 작업과 분리하고, 다시 접속하면 저장된 상태 조회 |
| 처리량 | MVP는 전체 분석 동시 실행 1개로 시작 |

**분석 재실행과 결과 재전달은 구분한다.** 큐가 메시지를 다시 전달했다고 LLM 호출을 자동 반복해서는 안 된다.

다음은 후속 계약 설계에서 반드시 정해야 한다.

- 작업 등록 후 큐 전달에 실패한 경우의 복구.
- worker가 작업을 받았거나 실행 중이거나 실패했음을 E에 알리는 방법.
- 실행 여부가 불확실한 작업의 상태와 운영자 처리 방법.
- 완료 결과 저장 후 결과 알림이 유실된 경우의 발견·재전달.
- DB 반영 후 결과 메시지 처리 완료 확인 순서와 중복 방지.
- 반영 실패를 실패로 확정하는 조건·시점과 그 뒤 사용자 재요청을 허용하는 시점.
- 분석 시간 제한·대기 상한·사용자별 호출 상한.
- 재분석 결과와 기존 자산의 중복·버전 관계.
- 완료 결과 보관 기간과 반영 거부·장기 미처리 자료의 정리 기준.

Object Storage에는 구조화된 완료 결과를 보존한다. 모든 중간 산출물·원문·모델 응답을 운영용으로 계속 보관하기로 결정한 것은 아니다. 업로드 전 장애까지 결과 보존을 보장하는 것은 아니며, 미보존 결과 때문에 분석을 자동 재실행하는 것으로 해석하지 않는다.

## 7. 로그인·권한·비밀값

| 영역 | 채택 방향 |
|---|---|
| 서비스 로그인 | Google OAuth 이후 CatchU Access JWT·Refresh Token 사용 |
| 브라우저 저장 | Access Token은 메모리, Refresh Token은 HttpOnly·Secure 쿠키 |
| GitHub 연결 | Google 로그인과 별도 연결. 재방문마다 다시 연동하지 않는 방향 |
| GitHub 설치 경험 | MVP에서 저장소에 GitHub App 설치를 필수로 요구하지 않음 |
| GitHub 앱 종류 | OAuth App·GitHub App 중 최종 방식은 필요한 API 권한·갱신 동작 확인 후 결정 |
| 사용자 GitHub 토큰 | NestJS가 관리하고 PostgreSQL에 암호화 저장. 암호화 키는 별도 보관 |
| worker의 토큰 사용 | 내부 API에서 해당 작업에 필요한 접근 토큰을 받아 메모리에서 사용 |
| 서비스 간 인증 | MVP는 전용 인증키와 HTTPS·내부 접근 제한·작업별 권한 확인 |

| 배포 비밀값 | 보호된 서버 파일과 Compose secrets를 이용하는 MVP 방식 |

쿠키의 SameSite·도메인, CORS·CSRF, 토큰 수명·갱신·폐기 규칙은 미결이다.

본인 조회는 NestJS에서 소유권을 확인한다. 비로그인 링크 조회도 매 요청마다 링크 유효성과 현재 공개 권한을 확인한다. 수신자 화면 응답은 **브라우저나 중간 서버에 저장되지 않게** 한다. 저장되면 중단 후에도 뒤로 가기 등으로 다시 열려 FR4.3을 어긴다. 이미 열린 화면을 실시간으로 회수하지 않는 점, 다음 요청부터 반영하는 점, 요청 시점 확인이 통신 문제로 실패했을 때의 처리는 [2026-09-15 팀장 확인 「링크 발행 중복 방지·열람 중 상태 변경」](2026-09-14_followup.md#팀장-확인-2026-09-15-링크-발행-중복-방지열람-중-상태-변경)을 따른다. 캐시 금지의 구체 방식은 계약 설계에서 정한다.

DB 비밀번호·GitHub 인증정보·LLM 키·암호화 키를 Git, 이미지, 로그, 브라우저 코드에 넣지 않는다. Compose secrets 사용만으로 원본 비밀 파일의 저장 암호화가 해결되는 것은 아니므로 파일 권한·백업·이전 방식은 별도로 마련한다.

사용자 GitHub 토큰은 배포용 공통 환경변수 파일에 모으지 않는다. worker에는 필요한 접근 토큰만 전달하며 Refresh Token이나 DB 토큰 암호화 키를 제공하지 않는다. 작업별 토큰 전달 허용과 GitHub가 부여한 토큰 자체의 권한 범위는 구분한다.

## 8. NCP 배치·수동 배포·복구

인터넷에서 worker·DB·큐로 직접 접근할 일이 없는 구성을 기본으로 한다. 서비스 간 통신은 필요한 경로만 허용한다.

worker에는 GitHub·LLM으로 나가는 통신이 필요하다. **VPC의 구체적인 서브넷·라우팅·NAT·접근 제어·TLS 종료 위치는 아직 설계하지 않았다.** ALB 사용만으로 이 항목들이 결정되지는 않는다.

팀원 1만 NCP에 직접 접속해 배포·운영한다. 팀원 2·3은 배포 과정에서 발견된 자기 서비스의 결함을 수정한다.

MVP 운영 허용 수준은 다음과 같다.

- 장애 시 **대략 하루의 변경 유실을 허용**한다. 이를 충족할 백업 설정과 실제 복구 검증이 필요하다.
- 장시간 중단과 팀장 수동 복구를 허용한다. 구체적인 복구 시간 목표는 미정이다.
- 이 허용 수준을 12월 운영 기준에 자동 적용하지 않는다.
- **LLM 제안:** 과거 백업 복원으로 숨김·링크 중단이 되돌아갈 수 있으므로, 복구 중 수신자 접근을 제한하고 공개 권한을 확인한 뒤 재개한다. 구체적인 확인 절차는 미결이다.

NCP 계정은 팀장 개인 계정이 아니며, 200만 원 크레딧과 계정 사용 가능 기간이 **12월 10일까지라는 전제**다. 실제 종료 조건·시각은 확인이 필요하다. 최종 완성 목표도 12월 10일 전이다.

계정 종료 후에는 개인 계정에서 규모를 줄여 운영하는 방안을 고려하고 있다. NCP 유지 여부와 예산은 미정이다. 따라서 DB 자료·필요한 객체·이미지·설정·비밀값을 이전하고 복구를 검증할 시간을 종료 전에 확보해야 한다. 같은 계정 안의 백업만으로 계정 종료에 대비했다고 보지 않는다.

12월 Kubernetes 도입은 팀장 구상으로 남기되, 운영 예산과 계정 이전 계획을 함께 검토한다.

## 9. 최소 폴더 구조와 초기화·코딩 하네스

다음은 **폴더 역할 제안**이다. 이 문서 작성으로 실제 폴더나 애플리케이션을 초기화하지 않는다.

```text
CatchU/
├─ web/                    Next.js 화면
├─ api/                    NestJS 기능별 모듈
├─ worker/                 FastAPI 수집·분석 처리
├─ contracts/              요청·결과 큐 메시지 계약과 예시
├─ deploy/                 Dockerfile·Compose·수동 배포·복구 관련 자료
├─ docs/                   팀 문서·개발 안내
├─ .github/workflows/      공통 CI 연결
├─ AGENTS.md               기존 공통 지침 진입점
└─ CLAUDE.md               기존 공통 지침 진입점
```

`contracts/`는 첫 MVP에서 요청·결과 큐 계약부터 시작한다. 모든 DB 모델과 업무 코드를 공통 폴더로 모으지 않는다. 기계적으로 검사 가능한 형식이 바람직하지만, JSON Schema 등 정확한 형식과 검증 도구는 미결이다. 폴더를 만드는 것만으로 계약 검증이 실행되는 것은 아니다.

서비스 내부 폴더는 각 담당자가 기능·책임에 맞춰 제안한다. 사람별 폴더를 만들거나 세 스택에 같은 내부 구조를 강제하지 않는다.

### 부담을 줄인 CI 기준

각 서비스 담당자가 로컬에서 실행 가능한 설치·실행·정적 검사·빌드 또는 실행 준비·테스트 명령을 제공하고, 팀원 1이 GitHub Actions에 연결한다.

초기화 작업 자체는 로컬 준비와 CI 연결을 나눠 진행할 수 있다. 테스트는 기능 구현과 함께 필요한 것을 작성하며, 통과 표시만을 위한 빈 테스트를 완료 근거로 삼지 않는다. 초기 CI에는 이미지 생성·업로드·자동 배포를 포함하지 않는다.

정확한 명령은 도구 선정 후 각 README에 기록한다. 현재는 실행 가능한 명령이 마련됐다고 표시하지 않는다. CI에서 발견된 서비스 코드·테스트 결함은 해당 서비스 담당자가 수정한다. 실제 NCP·OAuth·LLM 연결 검증은 일반 CI 검사와 구분한다.

### 최소 코딩 지침에 포함하기로 한 규칙

- 서비스 내부 변경은 담당자가 진행하고 기존 PR 검토 절차를 따른다.
- 연결 계약 변경은 변경자가 초안을 작성하고 상대 담당자와 먼저 검토한다.
- 공통 설정·CI·배포에 영향을 주는 변경은 팀원 1과 먼저 조율한다.
- 각 담당자가 자기 영역의 구현·테스트·결함 수정을 책임진다.
- 환경변수 예시에는 실제 비밀값을 넣지 않으며, 설정 변경 시 실행 안내도 갱신한다.

**PR 제출 전 확인 기준 제안:** 해당 변경에 필요한 검사·빌드·테스트 결과, 연결 상대 검토 여부, 설정·계약 문서 변경, 수행하지 못한 검증과 이유를 남긴다.

기존 AGENTS.md·CLAUDE.md·작업관리 문서를 재사용한다. AI-DLC 관리 블록을 개편하거나 별도 AI 프레임워크를 만들지 않는다. 코드 리뷰 도구 선정은 모든 개발 준비의 선행 조건으로 두지 않는다.

| 보안·NFR 설계 | 토큰 저장 방향, worker DB 차단, 전용 인증키 | 쿠키·갱신·폐기, 최소 권한, 키 교체, 호출 상한 |

| 개발 준비·검증 | 서비스별 초기화 담당, 공통 CI·배포 담당 | 실제 명령, BullMQ 호환성, 통합·복구 검증 증거 |

연결 검증에서는 정상 분석뿐 아니라 **중복 요청·worker 중단·결과 중복 전달·DB 반영 실패·숨김 후 기존 링크 조회·백업 복구**를 확인해야 한다. 상세 사례와 담당은 후속 설계에서 정한다.

이 문서는 결정 이유와 미결을 전달하는 입력으로 유지한다. 공식 설계에서 채택·변경된 항목은 해당 산출물을 연결하고, 메시지 계약 등 구현에 필요한 표현을 `contracts/`에 반영한다. 동일한 계약을 초안과 공식 설계에서 서로 다르게 유지하지 않는다.

후속 설계에서는 이 문서의 링크만 나열하지 않고, 필요한 결정·지위·이유·미결과 기준 커밋을 해당 입력에 명시한다. 기존 공식 설계 산출물을 이 문서에 복제해 별도로 승인·관리하지 않는다.
