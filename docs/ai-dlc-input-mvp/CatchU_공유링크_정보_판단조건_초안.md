## 1. 목적과 범위

이 문서는 **링크를 발행·관리하고, 수신자가 자료를 열람하는 데 필요한 정보와 처리 기준**을 정리합니다.

- **발행자:** 자신의 자료를 공유할 링크를 만들고 관리하는 사용자
- **수신자:** 전달받은 링크로 프로필·Catch를 열람하는 방문자
- **대표 구성:** 대표 문구와 그 문구에 연결한 Catch의 구성. 첫 MVP 완료 후 개발 범위이며 개발일은 미정입니다.

기존 결정과 담당자 제안을 구분하고, 다른 담당자에게 확인할 질문을 모았습니다. **API 경로·필드명·DB 구조와 상세 접근 케이스표는 후속 작업**입니다.

| 표기 | 의미 |
|---|---|
| `[요구]` | 승인 요구사항 |
| `[결정]` | 팀장 확인·팀 합의 |
| `[화면 제안]` | 화면 표시·사용자 행동에 대한 검토안 |
| `[연결 제안]` | 기능 간 정보 전달·처리 기준에 대한 검토안 |
| `[미정]` | 추가 확인이 필요한 사항 |

`[요구]`는 원래 승인 요구사항의 출처를 뜻하며, 모두 첫 MVP에 제공한다는 뜻은 아닙니다. 현재 적용 시점은 다음 표와 각 절의 구분을 따릅니다.

## 2. 기능별 필요한 정보

아래는 **첫 MVP의 각 기능에 필요한 정보의 의미**입니다. 공개 프로필 항목·버전 등 §4의 미결은 계약 확정 전 질문으로 유지합니다.

| 기능 | 하는 일 | 필요한 정보 |
|---|---|---|
| 발행 준비 | 공유할 내용을 불러와 확인 | 공개 허용 프로필, 사용자가 서비스에서 공개로 선택한 전역 GitHub 자산·근거, 조회 성공 여부 |
| 링크 발행 | 제목과 비밀번호 조건으로 새 링크 생성 | 발행자, 제목, 유효 링크 수, 비밀번호 설정 여부. 대표 구성·버전은 필수 입력이 아님 |
| 목록 조회 | 본인이 발행한 링크 확인 | 로그인 사용자·링크 소유자, 링크별 제목·상태·만료 시각·비밀번호 여부 |
| 링크 중단 | 선택한 링크의 이후 열람 차단 | 링크 소유자, 대상 링크, 현재 상태, 중단 처리 결과 |
| 비밀번호 확인 | 비밀번호가 설정된 링크의 열람 인증 | 설정 여부, 입력 검증 결과, 기존 인증의 유효 여부 |
| 수신자 열람 | 현재 허용된 기본 프로필·공개 Catch·근거 제공 | 링크 상태, 비밀번호 인증, 공개 허용 프로필, 현재 Catch 공개·열람 상태 |

**첫 MVP 완료 후 개발:** 저장된 대표 구성·버전 조회, 발행할 대표 구성 전달과 발행 당시 대표 구성 열람은 후속 입력입니다. 대표 조회나 저장본 전달을 기본 링크의 진입·발행·열람 선행 조건으로 두지 않습니다.

**결과는 다음처럼 구분합니다.**

- **조회:** 조회 중 / 성공·자료 있음 / 성공·자료 없음 / 조회 실패
- **발행:** 성공 / 같은 제목 있음 / 한도 도달 / 실패 확정 / 결과 불명
- **중단:** 요청 중 / 성공 확인 / 실패 확정 / 응답 불명
- **비밀번호:** 미인증 / 오입력 / 인증 성공 / 확인 실패
- **열람:** 열람 가능 / 링크 접근 불가 / 개별 Catch 열람 불가 / 자료 없음 / 확인 실패

‘자료가 없다’는 것은 **조회에 성공해 0개임을 확인한 상태**입니다. 자료를 가져오지 못한 상태와 구분합니다.

## 3. 기존 판단 원칙

### 3-1. 발행·관리

| 원칙 | 근거 |
|---|---|
| 첫 MVP는 대표 없이 발행하며, 공개 Catch가 0개여도 발행할 수 있습니다. | `[요구]` FR3.1의 대표 없는 경로 · `[결정]` 9/14 확인·첫 MVP M04 |
| 생성·확인만으로 자산이 공개되지 않습니다. 사용자가 서비스에서 공개로 선택한 전역 GitHub 자산·근거만 공유하며 링크별 자산 선택 제한을 새로 도입하지 않습니다. | `[결정]` 첫 MVP M03·M04의 기본 링크 열람 기준 |
| 공개 자산 조회 실패를 자산 0개로 처리하지 않습니다. | `[결정]` 9/14 확인 |
| 제목은 필수이며 앞뒤 공백을 제외해 비교합니다. 같은 사용자의 유효 링크끼리는 제목이 중복될 수 없습니다. | `[결정]` #49 |
| 유효 링크는 사용자당 최대 5개입니다. 중단·만료 링크는 제목 중복 비교와 개수 계산에서 제외합니다. | `[결정]` #49 |
| 동시 발행에서도 중복·한도를 지킵니다. 발행 응답을 받지 못하면 같은 제목으로 재시도하고 목록에서 결과를 확인합니다. | `[결정]` #49 |
| 비밀번호는 발행할 때만 설정하고 변경·해제하지 않습니다. 링크는 발행 후 30일에 만료되며 중단·만료 URL은 재활성화하지 않습니다. | `[요구]` FR4.5 · `[결정]` MVP 입력 OQ4 |
| 링크 중단은 자산 숨김·삭제와 별개입니다. | `[요구]` FR4.3 |
| Catch를 모두 숨겨도 기존 링크를 자동 중단하지 않습니다. | 링크 초안 §4.7(`[요구]` 표기) |

**발행 거절의 우선순위:** 응답 유실 후 재시도가 제목 중복과 한도 도달에 동시에 해당하면 **‘같은 제목 있음’을 먼저 반환**합니다. 이미 만들어진 링크를 한도 초과로 오해하지 않게 하기 위한 기준입니다. [#38 팀장 리뷰](https://github.com/JminAILab/CatchU/pull/38#pullrequestreview-5205743020)에 따라 #23 계약에 명문화합니다.

### 3-2. 수신자 열람

수신자는 서비스 로그인 없이 링크로 열람합니다(FR4.2). 판정 순서는 다음과 같습니다.

1. **링크 확인:** 중단·만료·없는 URL이면 같은 접근 불가 안내를 표시합니다.
2. **비밀번호 확인:** 유효한 링크에 비밀번호가 설정됐다면 인증을 확인합니다.
3. **자료 확인:** 현재 열람이 허용된 Catch만 제공합니다.
4. **자료 0개 처리:** 허용된 Catch가 없으면 공개 허용 프로필과 자료 없음 안내를 제공합니다(9/14 확인).

| 원칙 | 근거 |
|---|---|
| 링크 접근 불가 안내는 비밀번호 입력보다 먼저 표시합니다. 인증한 적이 있어도 중단·만료 링크는 열람할 수 없습니다. | `[요구]` FR4.3·FR4.5 · `[결정]` 9/14 확인 |
| 현재 공개 권한을 적용하며 숨긴 Catch는 기존 링크에서도 제외합니다. GitHub 저장소가 공개돼 있다는 이유만으로 서비스 자산을 자동 공개하지 않습니다. | `[요구]` FR3.2 · `[결정]` 첫 MVP M03·M04 |
| 원본 비공개가 확인된 Catch는 숨김과 같은 규칙으로 제한합니다. 일시적 확인 실패만으로 비공개라고 단정하지 않습니다. | `[요구]` FR1.5 |
| 숨긴 Catch와 없는 Catch는 같은 안내를 표시합니다. | `[결정]` 9/14 확인 |
| 링크 제목은 발행자 관리용이며 수신자에게 제공하지 않습니다. | `[결정]` #49 |

**첫 MVP 완료 후 개발:** 대표 문구·연결 구성의 발행 당시 보존, 숨긴 대표 카드 제외와 자동 보충 금지(FR3.4)는 대표 기능의 후속 기준으로 남깁니다. 현재 공개 권한 확인·숨김 적용은 첫 MVP에서도 유지합니다. 대표 보존으로 Catch 본문·프로필 버전 정책까지 확정하지 않습니다.

### 3-3. 상태 변경·통신 실패

다음은 모두 `[결정]` [#49](https://github.com/JminAILab/CatchU/pull/49) 기준입니다.

- **요청마다 확인:** 목록 진입·Catch 상세 열기·새로고침·비밀번호 확인 때 현재 링크·Catch 상태를 확인합니다.
- **열린 화면:** 실시간으로 회수하지 않습니다. 중단 확인창에 다음 이동·새로고침부터 반영된다고 안내합니다.
- **10월 제외:** 주기적 확인·서버 알림·탭 복귀 확인은 넣지 않습니다.
- **캐시 금지:** 수신자 응답을 브라우저·중간 서버에 저장해 재사용하지 않도록 합니다.
- **통신 실패:** 새로 요청한 자료는 보류하고 기존 화면은 유지합니다. 실패를 중단·만료·비공개로 단정하지 않습니다.

## 4. 담당자 제안과 남은 질문

기존 결정·담당자 답변·검토할 제안과 남은 질문을 구분합니다.

### 4-1. 공개 프로필과 수정 내용의 반영

**의미:** 수신자에게 어떤 프로필을 보여 주고, 발행 후 수정한 내용을 기존 링크에도 반영할지 정하는 항목입니다.

**확정된 범위·원칙**

- `[결정]` 수신자 기본 프로필은 첫 MVP에 포함합니다(승인 범위 M01·M04). 9/15 오전 회의의 ‘프로필 제외’를 수신자 기본 프로필까지 제외하는 것으로 해석하지 않습니다.
- `[결정]` 공개 권한은 열람 요청 시점의 상태를 적용하며, 발행 후 숨긴 Catch는 기존 링크에서도 열람할 수 없습니다(M03·M04, §3-2·§3-3).

**담당자 의견 — 팀원 2 답변**

출처: [PR #67 팀원 2 리뷰](https://github.com/JminAILab/CatchU/pull/67#pullrequestreview-5244954868). §2에는 수정 의견이 없으며, 아래는 §4-1에 대한 답변입니다.

- `[화면 제안]` 공개 항목 후보는 **표시 이름·한 줄 소개·직무·기술 스택·GitHub 계정**입니다. 기존 제안과 같으며 실제 공개 항목은 추가 확인 후 확정합니다.
- `[담당자 답변·정책 합의 대기]` **프로필과 Catch 본문은 발행 당시 내용을 유지**하고, 발행 후 원본 수정은 기존 링크에 반영하지 않으며 새 링크부터 반영한다는 답변입니다. 내용의 기준 시점과 위의 현재 공개 권한 적용을 구분합니다. 저장·조회 방식은 후속 설계 대상입니다.

**대표 구성 보존과의 범위 대조**

첫 MVP 이후로 분리한 것은 **대표 문구와 연결 구성의 발행 당시 보존**(FR3.4, §4-2·§4-3)입니다. 이번 답변은 **기본 프로필·Catch 본문의 기준 시점**에 관한 것으로, 대표 기능을 첫 MVP에 다시 포함시키는 뜻이 아닙니다. 다만 승인 범위의 기본 링크 기준은 본문·프로필 버전 정책을 관련 계약에서 해결하도록 남겼으므로, 담당자 답변만으로 최종 확정하지 않습니다. 발행 후 새로 공개한 자산까지 기존 링크에서 제외하는 정책으로도 확대하지 않습니다.

**남은 미결**

- 실제 공개할 프로필 항목과 공개 허용 조건 — 팀원 2·팀장 확인.
- 담당자 답변의 발행 당시 내용 유지안을 첫 MVP의 본문·프로필 버전 정책으로 채택할지 — 팀장과 연결 당사자 확인. 대표 보존 후속화와 구분해 판단합니다.
- 채택 시 저장·조회·버전 식별 방식, 재분석 결과 및 발행 후 새로 공개한 자산의 연결 처리 — 후속 설계에서 정하며 B 관련 최종 계약은 담당 확정 뒤 합의합니다.

### 4-2. 발행 준비 중 대표 변경·재분석

**적용 시점: 첫 MVP 완료 후 개발.** 아래 대표 저장본·연결 보존 제안은 현재 기본 링크의 선행 조건이 아닙니다. 첫 MVP Catch 본문의 버전·재분석 결과 반영은 §4-1과 B 연결 계약의 미결로 구분합니다.

**의미:** 발행 전에 대표를 수정하거나, 발행 후 재분석으로 Catch가 바뀌었을 때 기존 연결을 어떻게 유지할지 정하는 항목입니다.

| 상황 | 제안 | 확인할 질문 |
|---|---|---|
| 준비 화면에서 대표 A를 확인한 뒤 다른 탭에서 B로 수정 | `[연결 제안]` 확인한 저장본 A로 발행 | A를 발행 시점까지 보존·전달할 수 있나요? 사용할 수 없다면 어떻게 안내하나요? |
| 발행 후 재분석으로 Catch가 변경됨 | `[연결 제안]` 대표는 기존 Catch A를 계속 가리키고, 대표의 연결 대상을 바꾸려면 새 링크 발행 | 기존 Catch를 유지할 수 있나요? 유지할 수 없다면 어떻게 처리하나요? |

위 제안은 **대표의 연결 구성**에 관한 것입니다. 대표 밖의 새 공개 자산까지 기존 링크에서 숨긴다는 뜻은 아닙니다.

## 5. 기본 보호와 10월 제외 운영 기능

### 5-1. 첫 MVP에서 유지할 기본 보호

첫 MVP M06에 따라 본인 소유·현재 공개 권한, 동의·최소 전송·비밀값/비공개 자료 보호·삭제, 서비스별 호출/시간/출력 상한을 유지합니다. 상세 수치·기록 항목·보관 기준은 후속 설계/계약에서 확인하며 이 문서에서 임의 확정하지 않습니다.

- 미공개 자료는 본인만 확인하며, G 제외를 내부 선택 공유의 허용으로 해석하지 않습니다.
- 요청마다 링크·비밀번호·Catch 권한을 확인하고 수신자 응답을 캐시하지 않습니다. 확인 실패를 자료 없음·비공개로 단정하지 않습니다.
- 비밀번호·URL 비밀 부분·자료 원문이 보호되지 않은 기록에 노출되지 않도록 자료 최소화·비밀값 보호를 적용합니다. 기록을 검토하더라도 별도 G 운영 조회 기능의 구현을 전제하지 않습니다.
- 호출/시간/출력 상한과 사용자 자신의 링크 중단은 유지합니다. 서비스별 보호 상한을 FR10.3/10.4 또는 NFR5/7/8 전체 충족의 대체 증거로 쓰지 않습니다.

### 5-2. 10월 제외 — G 운영 조회·전체 중단

**FR10.3의 별도 운영 기록 조회와 FR10.4의 신규 분석/AI 전체 중단·재개는 G 10월 제외**입니다. 재도입 날짜·담당은 미정이며 H/I나 링크 담당에게 대신 배정하지 않습니다. 아래 정보표는 재도입 시 검토할 후속 입력입니다.

| 전달할 내용 | 구분할 점 |
|---|---|
| 발행·중단 실패와 결과 불명 | 실패 확정인지, 결과 확인이 필요한지 |
| 비밀번호 실패·접근 거부 | 일반적인 거부인지, 권한 위반 징후인지 |
| 자료 조회·상태 확인 실패 | 자료 없음·비공개와 구분되는 확인 실패인지 |

`[연결 제안·10월 제외 후속]` 비밀번호·URL의 비밀 부분·자료 원문은 운영 기록에 포함하지 않는 방향입니다. G 재도입 검토 시 기록 항목·보관 책임을 확인합니다. 기존 @ljm0850 확인·@csyg0616 링크 입력 제안은 운영 구현/보관 담당 확정으로 세지 않습니다.

`[요구·10월 제외 후속]` 신규 분석·AI 호출을 운영상 중단해도 **현재 허용된 기존 자료 열람은 유지**한다는 FR10.4의 원래 기준은 후속 입력으로 보존합니다. 첫 MVP에 전체 중단 기능이 있다는 전제나 그 기능의 시험 완료를 뜻하지 않습니다.

## 6. 후속 작업 — 접근 판정 케이스표

첫 MVP에 적용되는 원칙과 질문을 바탕으로 **예상 화면·자료 제공 여부·다음 행동**을 작성합니다. 대표 보존·G 운영 조회/전체 중단은 이 케이스표의 선행 조건에서 제외합니다.

|---|---|
| 기본 조합 | 링크 3종 × 비밀번호 유무 2종 × Catch 분류안 3종 = 18개 |
| 링크 상태 | 유효 / 중단 / 만료 |
| 비밀번호 | 미설정 / 설정. 설정 시 미인증·오입력·인증 성공으로 추가 분기 |

| 통신 실패 | 최초 진입 / 비밀번호 검증 / 열람 중 후속 요청 |

Catch 3종은 검토용 분류안입니다. 숨김과 원본 제한이 겹치는 경우도 확인하며, 안내 문구가 같더라도 판정 조건은 구분합니다.
