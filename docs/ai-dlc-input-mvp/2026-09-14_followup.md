첫 화면 결과물은 MVP 입력 §2.5에 따라 목적·진입·정보·버튼·이동과 관련 빈 상태·로딩·실패·미정 질문을 설명한다. 완성 디자인이나 실제 API 연결은 첫 제출의 필수 조건이 아니다. 담당자는 자신의 영역을 설계·코딩·테스트하며, 사람의 책임 배분과 AI 에이전트 역할은 별도로 기록한다.

## 팀장 확인 (2026-09-15): GitHub 연동·자산 탭 분석 경로

지위: **팀장 결정 입력.** 팀원 1이 제시한 사용자 흐름과 PR #53 수정 요청을 근거로 기록한다. 팀 전체의 화면 배치 합의나 공식 API·설계 승인을 뜻하지 않는다. 기존 승인 기록을 소급 수정하지 않는다.

- 기본 로그인은 Google OAuth이고, GitHub 미연동 상태의 홈 진입은 허용한다. **10월 저장소 분석 요청 전에는 GitHub 연동이 필요하다.** 이는 OQ1의 연동 필요 여부에 대한 후속 결정이며, 연동만으로 저장소 소유·커밋 관계가 검증되거나 분석 동의가 완료되는 것은 아니다.
- 처음 분석하는 미연동 사용자는 **홈 → 프로필의 GitHub 연동 화면 → 연동 성공 → 네비게이션의 자산 · GitHub 탭 → 저장소 선택·동의 → 분석 요청**으로 진행한다. 이미 연동한 사용자는 자산의 GitHub 탭에서 저장소 선택·동의로 진행한다. 기존 문서의 ‘내 자산’은 여기서 말하는 네비게이션의 ‘자산’ 영역이다.
- 분석 도중 떠났다가 돌아온 사용자는 **자산 → GitHub 탭 → 기존 분석 선택 → 현재 진행 상태·완료 결과·실패 안내**로 이동한다. 탭 복귀나 상태 새로고침은 상태 조회이며 새 분석을 요청하지 않는다.
- 실패한 분석은 **자산 → GitHub 탭 → 실패한 저장소의 실패 내용 확인·명시적 재요청 → 요청 접수 후 진행 상태 확인**으로 연결한다. 완료한 분석의 재분석 정책과 사용자당 동시 분석 수는 별도 미정으로 유지한다.
- GitHub 연결은 계정 연결, 저장소별 동의는 분석 허용, Catch 확인·공개 선택은 결과 관리로 구분한다. 분석 완료를 Catch 확인·공개 완료로 표시하지 않는다. 결과 단위 검토 집계 제외와 Catch별 상태 유지 결정은 아래 홈·알림 절을 따른다.
- **repo 연결**은 자산 GitHub 탭에서 저장소 선택·분석 동의·분석 요청을 버튼 하나로 처리하는 행동이다. 버튼 앞에 동의 내용을 보여 주고 버튼 이름에 동의를 담아, 누르는 행동이 동의와 요청임을 분명히 한다(FR1.1). repo 연결은 모두 자산 GitHub 탭에서 하며, 홈에서 저장소 선택으로 바로 가지 않는다.
- **로그인 홈 CTA**는 상태에 따라 나눈다. GitHub 미연결이면 프로필의 GitHub 연결로, 연결했지만 연결된 repo가 없으면 자산 GitHub 탭으로 보낸다. 연결된 repo가 있다는 것은 분석 요청이 접수된 저장소가 1개 이상이라는 뜻이며 진행 중·실패 여부와 무관하다. 홈은 이 두 사실만 확인하고 분석 상태·결과를 조회하지 않는다.
- 둘 다 연결된 사용자의 10월 로그인 홈은 아래 「홈 분석 결과 안내를 알림으로 이동」 절에 따라 홈 담당이 제안한다. 12월에는 팔로우한 사람의 포스팅 피드를 보여 주고, 팔로우한 사람이 없으면 팔로우가 많은 사람의 공개 포스팅을 보여 준다(12월 범위 보완 §2).
- 화면 초안에서 연결할 항목: 자산으로 직접 들어온 미연동 사용자도 같은 연동 화면으로 안내하고, 연동 성공 후 자산 GitHub 탭으로 돌아오게 하는 안을 검토한다. 연동 취소·실패·만료 시 안내와 복귀, A-01 선택·동의 및 A-02·A-03 진행·실패의 탭 내 표현 또는 상세 이동은 담당자 간 검토로 정한다. 기존 화면 ID는 초안 내부 식별자이며 별도 페이지·URL을 강제하지 않는다.
- 담당 경계 제안: 팀원 2는 프로필 연동과 자산 탭의 목록·Catch 결과, 팀원 4는 홈 진입 및 자산 탭에서 이어지는 저장소 선택·동의·진행·실패 화면, 팀원 1은 연동·기여 관계 확인과 분석 상태·결과 계약을 조율한다. 자산 탭 안의 구성 요소 경계는 #20·#22·#23·#50의 후속 검토에서 맞추며 메뉴 위치만으로 기존 담당 영역 전체를 바꾸지 않는다.

## 팀장 확인 (2026-09-14): 링크 용어·수신자 접근 불가 안내

지위: 팀 합의. 별도 회의 기록은 없으며 PR #33(공유 링크 흐름·와이어프레임 초안)과 PR #38(관리·예외 동작 v0.7) 검토 과정에서 팀장이 확인했다. 승인 요구사항을 소급 수정하지 않고 링크 초안과 새 intent가 이 확인을 함께 참조한다.

- 링크 관련 용어는 승인 요구사항과 같이 **‘발행’**으로 통일한다. 이슈 #21 제목·본문, 이 문서의 표와 MVP 입력 §2.5 담당표는 ‘발행’으로 갱신했다. 홈 초안에 남은 ‘발급’은 홈 담당의 다음 판에서 맞춘다. 이전 판·이슈의 ‘발급’은 같은 뜻이다.
- 수신자 화면은 **중단·만료·없는 URL의 사유를 구분하지 않고 같은 접근 불가 문구 하나**를 표시한다. 비밀번호가 설정된 링크라도 비밀번호 입력보다 이 안내를 먼저 표시하며, 문구가 하나이므로 링크 상태는 노출되지 않는다. 중단·만료 구분은 발행자의 링크 관리 화면에만 둔다. 이유: FR4.3·FR4.5는 열람 불가만 요구하고 NFR6의 안내 일치는 발행자 측 상태 전환 화면 기준이며, 사유를 구분하면 수신자가 비밀번호 없이 구직자의 중단 사실과 URL 존재 여부를 알게 된다. 구체 문구는 링크 담당의 화면 제안이다(현재 “이 링크는 열람할 수 없습니다.”).
- 유효한 링크 안에서 **숨긴 Catch와 없는 Catch를 직접 열었을 때도 같은 문구 하나**를 표시한다(PR #38 검토에서 확인). 링크 단위와 같은 원칙으로, Catch의 존재·숨김 여부를 추론할 단서를 주지 않는다. 비밀번호 조건을 아직 충족하지 않았으면 Catch 구분 없이 비밀번호 입력부터 적용하고, 링크 자체가 접근 불가면 링크 공통 문구를 우선한다. 구체 문구는 링크 담당의 화면 제안이다(현재 “현재 열람할 수 없는 자료입니다.”). 응답 코드·응답 시간 등 화면 밖 단서의 통제는 권한 계약·검증에서 확인한다.
- **공개 GitHub 자산이 0개로 확인돼도 링크 발행을 허용**한다(PR #38 검토에서 확인, 링크 초안 §4.7의 A안). 이유: 승인 요구사항(FR3.1·FR4.2)에 최소 자산 조건이 없고, 발행 후 자산을 모두 숨기면 프로필만 보이는 링크가 어차피 생기므로 발행 시점 조건을 추가해도 보장되는 것이 없다. 발행 준비 화면은 공개 자산이 없음을 안내하고, 수신자는 공개 허용 프로필과 자료 없음 안내를 본다. 조회 실패는 0개로 취급하지 않는다. 프로필 공개 항목은 OQ3에 남는다.

## 팀장 확인 (2026-09-15): 링크 발행 중복 방지·열람 중 상태 변경

지위: 팀 합의. 별도 회의 기록은 없으며 #23에 올라온 공유 링크 결정 요청 2건(발행 응답 유실 시 동일 요청 판단, 열람 중 공개·링크 상태 변경의 재검증 시점)에 팀장이 답했다. 승인 요구사항을 소급 수정하지 않는다. 링크 제목·최대 개수는 FR4에 없던 발행 조건을 더하는 것이며 FR4.2~FR4.5의 행동을 바꾸지 않는다.

**발행 응답 유실과 중복 방지**

- 링크 발행 시 **제목을 필수로** 입력한다. 제목은 발행자가 링크를 구분하기 위한 것이며 **수신자에게 보이지 않는다**. 앞뒤 공백을 뺀 값으로 비교한다. 발행 후 제목 수정은 10월에 제공하지 않는다.
- 같은 사용자의 **유효한 링크끼리 제목이 같으면 새 링크를 만들지 않는다**. 중단·만료된 링크는 비교 대상에서 뺀다. 같은 수신처에 조건을 바꿔 다시 보내려면 기존 링크를 중단하고 같은 제목으로 새로 발행한다(OQ4 결정과 같다).
- 한 사용자의 **유효한 링크는 최대 5개**다. 중단·만료 링크는 세지 않는다. 한도에 닿으면 발행 화면에서 사용하지 않는 링크를 중단한 뒤 발행하도록 안내한다. 5개는 10월 시작값이며 사용 기록을 보고 조정한다.
- 발행 성공 여부는 [공유 링크] 목록에서 제목과 상태 표시로 확인하고, URL은 목록에서 다시 복사한다. 상태는 아이콘만으로 전하지 않고 유효·중단됨·만료됨 글자를 함께 표시한다.
- 화면은 [링크 발행]을 누르는 즉시 버튼을 발행 중 상태로 바꿔 재클릭을 막은 뒤 요청을 보낸다. 이는 같은 탭의 연속 클릭만 줄이며 중복 방지의 보장이 아니다.
- 서버는 **같은 제목의 유효 링크 확인, 유효 링크 5개 미만 확인, 생성을 사용자 단위로 묶어 한 번에 처리**한다. 확인과 생성을 따로 요청하면 거의 동시에 들어온 두 요청(응답 유실 직후 재시도, 다른 탭)이 모두 통과해 중복 링크나 6번째 링크가 생기기 때문이다. 입력 중 제목 중복을 미리 알려주는 조회는 편의 기능으로 둘 수 있으나 중복 방지 장치로 쓰지 않는다.
- 이 규칙으로 같은 제목의 재요청은 항상 안전하다. 응답을 받지 못하면 화면은 “발행 여부를 확인하지 못했습니다”와 다시 발행을 제공하고, 서버는 새로 만들거나 이미 있음을 돌려준다. 이미 있음에는 “같은 제목의 유효한 링크가 이미 있습니다”와 [공유 링크]로 가는 경로를 보여준다. 첫 요청이 실제로 성공한 경우일 수 있으므로 “발행 실패”로 안내하지 않는다(NFR6).
- 잠금 방식·API 형식·저장 구조는 계약 설계에서 정한다. 제목 길이 제한과 목록의 상태 표시 모양은 링크 담당의 화면 제안이다.

**열람 중 공개·링크 상태 변경**

- 서버는 **수신자의 요청마다** 현재 링크 상태와 Catch 공개 상태를 판단한다. 대상은 공개 자료 목록 진입, Catch 상세 열기, 새로고침, 비밀번호 확인이다. FR4.3·NFR1이 요구하는 통제는 이 수준이다.
- **이미 열려 있는 화면을 실시간으로 회수하지 않는다.** 주기적 확인, 서버 알림, 다른 탭에서 돌아왔을 때의 확인은 10월에 넣지 않는다. 이유: 이미 표시된 내용은 캡처로도 남으므로 화면에서 지워도 보호 효과가 없고, 탭 복귀 확인이 실제로 쓰일 상황이 매우 적다.
- 수신자 화면 응답은 **브라우저나 중간 서버에 저장되지 않게** 한다. 저장되면 중단 후에도 뒤로 가기 등으로 다시 열려 FR4.3을 어긴다. 계약 설계에 반드시 넣는다.
- 발행자의 링크 중단 확인 안내에 **이미 열려 있는 수신자 화면에는 다음 이동이나 새로고침부터 반영된다**는 점을 알린다(NFR6).
- 요청 시점의 확인이 통신 문제로 실패하면 새로 요청한 자료만 보여주지 않고 다시 시도를 안내한다. 이미 표시된 화면은 그대로 둔다. 확인 실패를 중단·만료·비공개로 단정하지 않는다.
- 캐시 금지의 구체 방식, 인증 세션과의 관계, 원본 비공개 확인 방법(OQ2)·프로필과 Catch 본문 버전(OQ3)은 이 확인으로 정하지 않는다.

## 공식 계획 제안에 반영할 요청

- 첫 intent의 승인된 제품 행동·FR/NFR ID를 재사용하고, 10월 적용과 후속 결정만 구체화한다. 첫 intent를 다시 열거나 승인 이력을 소급 수정하지 않는다. 재사용은 새 단계 완료나 승인과 다르다.
- PoC 분석은 코드·의존성·입출력·흐름, 확인 가능한 실행 결과·한계, 유지·수정·제외 근거, 서비스 요구사항과의 차이, 재사용·재설계·추가 검증을 다룬다. 분석 전 코드 복사나 재사용을 근거로 한 일정 단축 확약은 하지 않는다. 규칙 기반 결과는 LLM 초안 생성 검증과 구분한다.
- 공통 데이터·권한·상태 모델을 확인하고 구현·검토 가능한 유닛으로 분할한 뒤 API 계약과 의존성을 정한다. 사람별 큰 담당 영역을 유닛 하나로 고정하지 않는다.
- 각 담당자가 연결 구현을 시작할 때 필요한 설계·계약·검증 기준, 첫 통합 흐름과 전체 기능 검증, NCP 수동 배포·외부 URL·자료 유지·복구 확인의 검토 지점을 제안한다. 자동 배포 파이프라인은 제외한다.
- 10월 필수 범위는 MVP 입력 §1·§3을 유지한다. 대표 구성은 링크 발행 필수 조건이 아니다. 미완료 기능을 임의 제외하거나 12월로 넘기지 않는다.
- NCP 계정 수령·권한, 서비스 LLM API 제공자·모델·등급, GitHub OAuth 준비는 실제 확인한다. GitHub OAuth의 용도는 12월 FR1.2와 분석 연결이며, 10월 분석 전 GitHub 연결 필요는 위 팀장 확인을 따르며, 소유·커밋 관계 확인과 동의 상세는 OQ1·OQ11에서 정한다. 예정일이 지났다는 사실은 준비 완료가 아니다. 팀원 1의 조율·자문과 팀원 4의 학습 부담을 가용량에 반영한다.
- 12월 범위 보완 결정([`CatchU_12월_범위_보완.md`](../ai-dlc-input-december/CatchU_12월_범위_보완.md))은 12월 intent의 입력이다. 이번 intent는 그 문서 §4의 설계 제약만 참조해, 권한 판정 위치·공개 상태 모델·분석 이벤트 기록·계정 유형·링크 발행·홈과 헤더 구조를 설계할 때 12월 확장을 막지 않는다. 해당 기능을 10월에 구현하지 않으며 10월 필수 범위는 위 항목을 유지한다.

## 입력의 효력과 실행 기록

원래 §2.5 전체가 제안이라고 적힌 부분 중 **팀원 2·3·4의 담당 작업 진행 여부**에 이번 회의 결과를, **인증·홈 진입**, **링크 용어·수신자 접근 불가 안내**, **분석 이력 확인 경로·홈 최근 분석**, **링크 발행 중복 방지·열람 중 상태 변경**, **홈 분석 결과 안내**, **GitHub 연동·자산 탭 분석 경로**에 위 팀장 확인을 후속 입력으로 적용한다. GitHub 연결 없이 홈에 들어가는 것과 분석을 요청할 수 있는 것은 별개이며, Google OAuth는 기본 로그인 방식이지 유일한 방식으로 확정한 것이 아니다. 연결 계약과 공식 단계 승인은 그대로 미결이다. 기존 입력·승인본을 소급 변경하지 않고 새 intent가 이 후속 입력을 함께 참조하도록 한다.
