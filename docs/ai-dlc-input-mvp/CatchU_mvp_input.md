## 1. 이번 intent의 목적과 경계

- **목적:** 2026년 10월 1~2일 중간 발표에서 구직자가 저장소 분석 → 경험 후보·근거 확인 → Catch 설명 초안 확인·공개 → 대표 구성 → 링크 발행 → 수신자의 비로그인 열람까지 **실제 서비스 안에서 완주**하는 MVP를 설계하고 구현한다.
- **범위:** 승인된 요구사항의 시점 열이 **10월**인 기능 요구사항 16개와 **공통** 2개, 그리고 10월에 적용되는 비기능 요구사항 7개(§3). 시점이 12월인 항목(자기소개서·포트폴리오, JD 요약·패널·질의응답, 기업 검색·제안·DM, 복수 프리셋, 목록 밖 저장소, 서술 오류 재생성, 조건별 운영 경고)은 이번 intent에 포함하지 않는다. 제외는 12월 범위의 폐기가 아니다.
- **이전 intent와의 관계:** 첫 intent는 방향·범위·요구사항 검토까지 완료했다. 승인된 제품 행동과 FR/NFR ID를 재사용하고, 이번에는 10월 구현 범위와 변경된 실행 조건을 구체화한다. 기존 산출물의 재사용을 새 intent의 단계 완료·자동 생략으로 간주하지 않는다. AI-DLC 진행 요청은 §7.1에 둔다.
- **이번 intent 밖:** 12월 기능의 상세 설계·구현, 사용자 조사 실행, 12월 품질 검증(NFR3), 자동 배포 파이프라인 구축. 10월 수동 배포와 배포 결과 확인은 이번 작업에 포함한다.

### 1.1 완료 조건과 발표 대안

아래는 승인된 요구사항과 §2.2의 시연 방식을 이번 작업의 완료 확인으로 연결한 **제안**이다. 세부 검사 조건은 설계·검증 계획에서 확정한다.

- 동의한 사전 선정 저장소를 서비스 안에서 실제 분석하고, 생성한 Catch 초안·근거 확인, 별도 공개 선택, 대표 구성, 링크 발행, 외부 수신자의 비로그인 열람을 NCP 배포 환경에서 확인한다. 과거 수동 결과나 모의 응답만으로 완료 처리하지 않는다.
- 대표 구성 없이도 발행·열람할 수 있는 경로를 함께 확인한다. 대표 구성은 정상 시연의 한 예이며 발행의 필수 조건이 아니다(FR3.1).
- §3의 10월 적용 FR/NFR별 통과 결과를 남긴다. 비공개·숨김, 링크 중단·만료·비밀번호, 분석 실패·재요청·중복, 원본 비공개 확인, 내부 선택 공유의 권한 분리, 운영 중단 중 기존 열람을 포함한다. 만료 등 시간 조건은 검증 환경에서 재현할 방법을 정한다.
- 배포한 버전, 사용한 저장소·결과 버전, 실행 환경, 확인 결과와 남은 결함을 기록한다. 외부 URL 접속, 설정·비밀값 주입, 재시작 후 필요한 자료 유지, 재배포·실패 시 복구 절차와 담당을 확인한다. 구체 복구 목표는 OQ14에서 정한다.
- 발표 노트북 로컬 실행은 **발표를 진행하기 위한 대안**이다. 외부 URL 열람 등 충족하지 못한 조건은 미완료로 기록하며, 로컬 시연 성공을 NCP 배포 완료로 계산하지 않는다. 목표 범위를 바꿔야 하면 별도로 검토·승인한다.

## 2. 팀장 결정 (2026-09-13)

승인된 요구사항의 제약 C1·C6과 후속 결정 OQ16이 후속 확인으로 남긴 항목이다. 요구사항 팀 검토는 끝났고, 아래의 **확정** 표시는 기존 입력에 기록된 팀장 결정을 유지한다. **제안·미기입**은 별도이며 이번 문서 보완으로 확정하지 않는다. 결정의 근거 문서는 이 파일이며, 레포 컨벤션 §1 「결정 이력」이 여기를 가리킨다.

### 2.2 배포 대상과 시연 방식 — 확정

- **배포 대상은 네이버 클라우드 플랫폼(NCP)이다.** 소속 기관의 NCP 지원이 확보돼 2026-09-09 검토안의 AWS(ECS·ECR·S3)를 대체한다. 인프라 설계는 처음부터 NCP 지원 범위와 서버 1대의 제약을 기준으로 한다. AWS 서비스 이름을 NCP 상품명으로 치환하는 방식으로 설계를 확정하지 않는다.
- **10월 시연은 NCP 서버 1대에 수동 배포**(컨테이너 실행)해 수신자가 실제 URL로 링크를 여는 방식으로 한다. 배포 준비가 늦어지면 발표 노트북 로컬 실행으로 후퇴한다.
- NCP 지원 범위는 팀단위로 계정이 하나 제공되며 200만 크레딧으로 12월 10일 즉 프로젝트 종료일까지 사용이 가능하며 서버 GPU 스토리지 등 리소스에 제한은 없다. 관리형 상품 사용이나 단일 서버 내 실행을 미리 가정하지 않는다. 월 예산 약 160만 원과는 별개로 지원된다.
- **계정 준비 상태 (2026-09-13, 팀장 답변):** NCP 팀 계정은 2026-09-14(월)에 전달받을 예정이다. 현재는 수령 전이며 로그인·자원 생성 권한은 계정 수령 후 확인한다.
- **배포 준비 제안:** 수동 배포 담당·준비물·접속 및 데이터 유지 검사·복구 절차를 delivery-planning의 작업과 검증 기준에 포함한다. 실행할 AI-DLC 단계와 산출물의 담당 위치는 §7.1의 진행 계획에서 확인한다.

### 2.3 10월 구현 우선순위 — 확정, Bolt 상세는 제안

링크 주 경로를 앞에서부터 잇는 우선순위를 유지한다. **제안:** 첫 Bolt는 ①~⑤를 얇게 한 번 연결하는 세로 슬라이스(walking skeleton)로 두고, 이후 Bolt에서 각 단계를 보강한다. 구체 분할·의존성·담당·일정은 가용량과 PoC 확인 후 delivery-planning에서 검토한다. 아래 순서를 기술적 선행 조건까지 뒤로 미루라는 뜻으로 사용하지 않는다.

| 순서 | 내용 | 요구사항 ID |
|---|---|---|
| ① | 사전 선정 저장소 분석 실행, 진행·실패 상태, 중복 요청 방지 | FR1.1, FR1.4 |
| ② | 경험 후보·근거·생각해볼 질문, Catch 설명 초안 자동 생성 | FR2.1, FR2.2 |

분석 동의·사용자 식별·개인별 자료 권한·외부 AI 사용 조건은 ①~②의 선행 조건이다. FR10.3·FR10.4의 기록·중단 통제는 실제 분석·AI 호출 검증에 필요한 부분을 먼저 연결하고, ⑦에서 운영자 확인과 전체 검증을 마무리하는 방안을 제안한다. 첫 통합 흐름의 성공은 전체 10월 범위의 완료와 구분한다.

### 2.4 역할과 가용량(OQ16) — 확정 부분과 미기입

- **분담 구현 — 결정 (2026-09-14, 팀장 답변):** 공통 기준을 정한 뒤 MVP를 작업 단위로 나눠 팀원 1·2·3·4가 각자 담당 파트의 설계·코딩·테스트를 진행한다. 팀원 1·2·3의 포트폴리오·취업 준비 목적과 팀원 4의 웹 개발 과정 학습 목적을 유지한다. 구체 파트와 담당자는 팀이 배분하며, 대화 중 예시로 제시한 배분은 확정안으로 취급하지 않는다.
- **팀원 4**도 경험에 맞는 작은 구현 작업을 맡을 수 있다. 팀원 1의 지원 아래 기술적으로 간단한 작업과 web의 시각적인 부분을 우선 고려한다. 기존의 “유닛 담당 배정에서 제외” 방침은 이번 결정으로 대체하며, 독립 유닛 또는 유닛 안의 세부 작업 중 적절한 크기는 작업 분할 때 정한다.
- **AI-DLC 운영:** 팀장 세션은 공통 범위·설계·진행 계획과 통합을 조율한다. 각 팀원은 담당 범위에서 자신의 Codex 세션을 활용해 작업할 수 있다. 유닛별 작업·검토·승인 방식은 AI-DLC 진행 계획에서 정하며, 모든 구현을 팀장 세션에서 수행하는 방식으로 가정하지 않는다. 공통 단계 산출물은 팀 회의 또는 Slack에서 검토한다.
- **미정 담당 배분 (2026-09-13, 팀장 답변):** 아직 정하지 않은 항목은 §4의 목록에 남겨두고 팀원들이 함께 담당을 배분한다. 오류·AI 호출량·비용 확인과 신규 분석·AI 호출 중단·재개를 맡을 운영 담당도 미정이다. 이미 정한 역할은 유지하며, 내부 품질 검토자가 팀원 1이라는 이유로 운영 업무까지 자동 배정하지 않는다.
- **작성 책임과 시작 조건:** 담당자는 직접 코드 작성·수정 또는 AI와의 공동 구현, 코드 이해·리뷰·실행 확인·테스트를 맡는다. 사용자 흐름·와이어프레임 초안과 임시 데이터 기반 화면 프로토타입은 기존 요구사항을 기준으로 먼저 시작할 수 있다. 미정 정책은 질문으로 남기고 확정된 동작과 구분한다. 실제 API·저장·권한 처리를 연결하는 구현은 해당 작업의 공통 설계와 유닛 경계·API·데이터 계약을 확인한 뒤 진행한다. 기존의 “AI가 코드를 쓰고 팀원은 검토” 중심 설명은 이 방식으로 대체하며, 실제 팀원 배분표를 AI 에이전트 역할 배정과 구분해 개발 계획에 남긴다.
- **프로젝트 가용 시간 (2026-09-13, 팀장 답변):** 평일 09:00~18:00는 점심·휴식을 제외하면 사실상 이 프로젝트에 사용할 수 있다. 별도 정기 수업·필수 일정으로 추가 시간을 차감할 필요는 없는 것으로 계획한다. 이 시간에는 개발·학습·코드 리뷰·실행 확인·회의·팀원 간 자문이 포함된다. 점심·휴식 길이와 활동별 배분을 정하지 않았으므로 주당 순수 개발 시간을 수치로 확정하지 않는다(C2).
- **회의·자문:** 회의는 보통 1회 30분 이내다. 팀원 2·3이 팀원 1에게 요청하는 자문 시간은 이슈 크기에 따라 달라 현재 추정하기 어렵다. 계획에서는 팀원 1의 지원 여유를 고려하고, 회의·자문 시간을 제외하지 않은 채 각자의 독립 작업 시간을 모두 합산하지 않는다. 구체 작업량은 첫 통합 흐름의 실제 진행 결과로 조정한다.
- 🔲 **PoC 재사용성**: §6 참조. 확인 전이다.
- **서비스 자원·계정:** NCP 팀 계정은 2026-09-14(월) 수령 예정이며 지원 내용과 준비 상태는 §2.2에 기록했다. 서비스용 LLM API는 Claude·OpenAI·업스테이지 Solar를 후보로 검토 중이며 미선정이다(§4 OQ11). GitHub OAuth App은 아직 등록하지 않았다(2026-09-13, 팀장 답변). 등록·설정은 GitHub 연결 구현과 검증에 필요한 준비 작업으로 남긴다. 🔲 NCP 계정 수령 후 이용 권한 확인과 서비스용 API 계정·등급 선정이 남아 있다.

### 2.5 담당 영역·목표·첫 결과물 — 제안 (2026-09-14)

팀장과 논의한 분담을 다음 AI-DLC 진행 계획의 입력으로 남긴다. 팀 전체의 최종 배분·공식 단계 승인을 뜻하지 않으며, 실제 작업량과 의존성을 검토해 조정한다. 진행 상태를 관리하는 작업표가 아니라 담당 경계와 첫 결과물에 대한 제안이다.

| 담당 | 담당 영역 | 목표 | 첫 결과물 |
|---|---|---|---|
| 팀원 1 | AI-DLC 공통 조율, PoC 분석, GitHub 분석 서버 처리 | 저장소 기록을 Catch 초안·근거로 만드는 처리 구조를 정하고 팀원들의 기능을 연결한다. | PoC 분석 요약, 분석 입력·상태·결과 데이터 초안, 전체 기능 담당표 |
| 팀원 2 | 회원·기본 프로필, 내 자산·대표 프리셋 | 구직자가 자신의 자료를 확인하고 공개할 자산과 대표 구성을 준비할 수 있게 한다. | 로그인·프로필 흐름, Catch 확인·공개·숨김·불일치 표시, 대표 주장 작성·Catch 선택의 와이어프레임 |
| 팀원 3 | 공유 링크 발행·관리, 수신자 열람 | 구직자가 준비한 자료를 링크로 전달하고 수신자가 허용된 자료를 열람할 수 있게 한다. | 발행자·수신자 흐름, 링크 발행·비밀번호·중단·만료·자료 열람의 와이어프레임 |
| 팀원 4 | 서비스 홈, 분석 화면 프론트엔드 | 사용자가 분석 시작 위치, 현재 상태, 다음 행동을 이해할 수 있게 한다. | 먼저 홈 와이어프레임을 작성하고, 이후 저장소 선택·분석 진행·실패·재시도 화면으로 확장 |

- **용어 (2026-09-14 팀장 확인):** 링크는 승인 요구사항과 같이 ‘발행’으로 표기한다. 이 표의 이전 판과 이슈 #21의 원래 제목에 있던 ‘발급’은 같은 뜻이며, 확인 내용은 [회의 후속 입력](2026-09-14_followup.md)의 「팀장 확인: 링크 용어·수신자 접근 불가 안내」에 기록했다.
- **담당 경계:** 팀원 2는 본인의 Catch·근거 확인과 자산·대표 구성을, 팀원 3은 링크 전달과 수신자 열람을 맡는다. 팀원 4의 분석 상태 화면에서 결과의 Catch 상세 확인·관리로 이동하면 팀원 2 영역에 연결된다. 분석 처리·상태·결과를 제공하는 서버 측 계약은 팀원 1이 관련 담당자와 조율한다. Catch 설명의 직접 문구 수정은 제공하지 않는다(FR3.5).
- **첫 화면 결과물의 완료 기준:** 화면별 목적·진입 경로·주요 정보·버튼 동작·이동 대상을 표시하고, 해당하는 빈 상태·로딩·실패 상황과 미정 질문을 함께 남긴다. 주요 사용자 행동을 따라가며 다른 담당 화면과의 연결을 설명할 수 있으면 첫 초안 검토가 가능하다. 완성된 시각 디자인·실제 API 연결·작동하는 프로토타입은 첫 제출의 필수 조건이 아니다. 우선 PC 웹을 기준으로 작성하는 것을 제안하며, 공통 배치·용어·스타일은 첫 초안 공동 검토에서 맞춘다.
- **팀원 1의 첫 결과물 기준:** PoC에서 확인한 경로·리비전, 입력부터 결과까지의 처리, 재사용 후보와 한계, 재설계·추가 검증 사항을 구분한다(§6). 분석 데이터 초안은 상태·결과·오류의 예시를 포함하되 승인된 API 계약으로 취급하지 않는다. 전체 기능 담당표는 §3의 10월 적용 요구사항과 연결해 누락·중복·미배정을 드러내며, 공통 단계의 공식 산출물로 정리할 때 팀원 초안을 재사용한다.
- **구현으로 연결:** 팀원 2·3은 해당 영역의 화면·API·테스트를 맡는 것을 제안한다. 팀원 4는 홈 → 저장소 선택 → 분석 상태 화면 순서로 작은 작업을 완성하고 팀원 1이 기술적으로 지원한다. 공통 시각 디자인을 팀원 4 혼자 책임지는 것으로 배정하지 않는다. 사람별 담당 영역과 AI-DLC 유닛은 일대일로 고정하지 않으며, 큰 책임 범위 안에서 구현·검토 단위를 나눈다.
- **공통·미배정 작업:** 내부 선택 공유·품질 신호·검토 권한, 운영 기록·신규 처리 중단·재개, 환경 준비·수동 배포·복구, 통합 검증의 구현·검토·운영 담당을 개발 계획에서 배분한다. 사용자 화면이 필요하면 해당 기능 담당과 연결하고, 팀원 1에게 일괄 배정하지 않는다. 내부 공유 자료의 검토자 지정과 기능 구현·운영 담당 배정은 별개다. 인증·분석 동의·공개 권한·기존 링크 보존·원본 상태 변화처럼 영역을 가로지르는 규칙도 구현 및 통합 검증 책임을 명시한다.

**의미 확인 (2026-09-13, 팀장 답변):** 실패 후 다시 요청해도 같은 작업의 카드가 중복으로 쌓이지 않게 한다. 예를 들어 A·B 저장 후 실패한 분석을 재요청하면 A·B·A·B·C가 아니라 A·B·C로 남아야 한다. 이는 FR1.4의 의미 확인이며, 같은 카드의 식별 기준·부분 성공 결과 처리와 새 커밋 추가 후 재분석의 버전 정책은 설계에서 정한다.

**저장소 후보 (2026-09-13, 팀장 답변):** 아직 팀에서 논의하지 않았으며, 팀장 본인의 과거 프로젝트 공개 저장소를 우선 생각하고 있다. 프로젝트 경험이 있는 팀원 2의 저장소도 추가 후보로 검토 중이다. 최종 목록·개수는 미정이며 기존 초안의 “최소 3개”를 선정 조건으로 고정하지 않는다. 🔲 저장소 URL·소유자·분석 대상자의 기여 관계와 분석 동의는 선정 시 확인한다. 후보로 언급한 것을 분석 동의 완료로 간주하지 않는다.

**PoC와의 관계 (같은 날 확인):** 팀장이 우선 생각한 본인 저장소는 기존 PoC에서 이미 분석했던 저장소다. 과거 분석 결과를 비교 자료로 활용할 수 있다. 당시 분석 버전·범위와 이번 분석 대상을 대조하고, 새 서비스 안에서 실제 분석·초안 생성·링크 열람을 확인한다. 팀원 2의 추가 후보까지 PoC 검증이 끝났다고 해석하지 않는다.

**10월 실패 처리 — 결정 (2026-09-13, 팀장 답변):** 분석 실패 시 사용자에게 실패 사실과 재요청 버튼을 제공하며, 사용자가 다시 요청할 때 재시도한다. 자동 재시도는 하지 않는다. 실패로 기존 카드·링크가 손실되지 않게 하고, 재요청으로 같은 작업의 카드가 중복 저장되지 않게 한다(FR1.4·NFR4). 실패 유형별 안내·부분 성공 결과 처리·중복 식별 기준은 후속 설계에서 정한다. 이 결정으로 12월 정책까지 고정하지 않는다.

**제안:**

- 10월에는 선정 목록만 제공한다. 목록에 넣기 전에 커밋·PR·diff 규모와 분석할 기간·버전·대상을 확인하고, 예상 사건 수·LLM 호출량을 점검한다. 공개 목록이라는 이유로 처리 범위·호출량을 무제한으로 두지 않는다. 🔲 분석·전송·호출 상한과 초과 시 안내·중단 방식을 OQ3·OQ14와 함께 정한다.
- 진행 중 요청의 중복 방지와 실패 후 재요청의 카드 중복 방지를 별도로 설계한다. 🔲 구직자·저장소·분석 대상 버전·사건의 식별 기준, 부분 성공 결과 재사용과 카드 저장 단위를 정한다. 저장소 URL만으로 두 조건이 모두 충족된다고 가정하지 않는다.
- 🔲 같은 공동 저장소를 여러 구직자가 요청할 때 저장소 수집과 개인별 기여 판정·카드 생성의 경계를 정한다. 공유 가능한 수집 결과가 있더라도 분석 동의와 개인별 자료 권한을 합치지 않는다. 소유·커밋 관계 확인 방법도 분석 설계 전에 정한다.
- 목록 밖 저장소 입력·미지원 분류 UI는 12월(FR1.3)로 유지한다. 10월에도 선정 당시의 처리 조건, 선정 후 삭제·권한 변경·크기 증가·접근 실패에 대한 처리는 필요하다. 원본 상태 변화는 OQ2와 연결한다.

**제안:**

- Catch 본문은 생성 시점 기준으로 고정한다. 재분석은 소유자가 명시적으로 실행할 때만 하며 카드가 달라질 수 있음을 표시한다(카드생성논리 §3).

- **팀장 의견 (2026-09-13):** PoC 작성 당시 코드 품질은 신경 쓰지 않았다. 기존 코드 자체의 재사용보다 로직을 참고하고 서비스 구현은 재설계하는 방향을 선호한다. 다만 이는 분석 전 의견이며, 로직 채택·코드 재사용·재설계 범위의 최종 판단은 PoC 분석 이후에 한다.
- **방침:** PoC 분석을 먼저 수행한다. 필요한 코드·의존성·입출력·현재 실행 결과를 확인하고, 유지할 로직의 근거와 한계, 서비스 요구사항과의 차이, 재구현·통합 비용을 검토한다. 코드 품질을 고려하지 않았다는 작성자의 설명만으로 로직이 검증됐거나 코드 전부를 버려야 한다고 단정하지 않는다. 분석 전에는 코드를 이 저장소에 복사하거나 재사용을 일정 단축의 근거로 삼지 않는다. 기존 코드 검토의 필요성과 범위는 확인된 상태를 AI-DLC 진행 계획에 반영해 정한다.
- 🔲 분석 결과(검토한 경로·리비전, 실행 조건·결과, 유지·수정·제외할 로직과 이유, 코드 재사용 여부, 재설계 범위, 필요한 검증)는 확인 후 여기에 적는다. 로직만 채택하는 경우에도 입출력·규칙·예외·검증 사례를 유닛·계약 설계 전에 공유하고 해당 유닛의 구현 입력으로 연결한다. 보고서로 남길 경우 `aidlc/spaces/default/knowledge/documents/`에 두고 `aidlc knowledge onboard`로 등록할 수 있다. 보고서는 코드 실행·로직 타당성·통합 가능성 확인을 대신하지 않는다.
- 카드 생성 규칙의 현행 설명은 `docs/카드생성논리_상세설명.md`(v2, 2026-08-12)다. 핵심은 다음과 같다. 사건 묶기는 본인이 묶은 PR·머지(A등급)와 시스템 추정 묶음(B등급)을 구분해 표시한다. 시스템 추정 규칙은 같은 사람, 같은 파일, 시간 간격 세 가지뿐이고 AI 호출은 없다. 공동 기여자는 수집 시점에 `author_01` 같은 가명으로 바꾸고, 코드의 시크릿은 마스킹한다. 모든 문장에 근거 링크를 붙이고 점수·평가는 만들지 않는다. 사건의 62~87%가 커밋 1개짜리 스냅샷 카드였다.

## 7. AI-DLC 진행 요청과 참고 자료

### 7.1 진행 계획 제안 시 적용할 원칙

- 첫 intent의 승인된 의도·범위·요구사항을 재사용한다. 이미 합의한 제품 행동을 모두 다시 묻기보다 이번 10월 범위, NCP 배포, 역할·가용량, PoC·계정 준비의 차이를 확인한다. 단계별 재사용·축소·생략과 후속 단계에 필요한 입력 연결은 AI-DLC의 진행 계획 제안에서 검토하고 승인한다.
- **검토할 작업:** 개발 관행, 요구사항의 10월 적용과 미결 해결, 사용자 흐름·화면, 도메인·유닛·계약·개발 계획, 기능·비기능·인프라 설계, 구현·테스트·CI, 수동 배포와 결과 확인. 이는 확정된 단계 목록이 아니며 구체 단계·깊이·검토 지점은 제안을 보고 정한다.
- **분담 구현 계획:** §2.4의 결정과 §2.5의 담당 제안에 따라 공통 범위·설계와 작업 단위·의존성·연결 계약을 정리하고 팀원별 구현으로 연결한다. 큰 담당 영역을 유지하되 구현·검토할 유닛은 필요에 따라 나누고, 첫 세로 슬라이스로 통합을 확인하는 방식을 선호한다. 독립 작업을 함께 진행할 수 있는 조건, 팀별 검토·승인 방식, 브랜치와 파일 담당 범위, 통합 시점, 공통·미배정 작업의 책임을 제안에 포함한다. 구체 실행 방식은 설치된 AI-DLC의 팀별 유닛 작업 절차에 맞춰 정한다.
- **화면 작업 연결:** §2.5의 흐름·와이어프레임 초안은 공통 설계 완료 전에도 작성하고, 공동 검토로 화면 연결·UI 기준을 맞춘다. 그 결과를 해당 AI-DLC 단계의 입력으로 검토·보완하고 상세 화면·필요한 프로토타입·구현에 연결한다. 작성 주체와 정본을 지정해 팀장 세션과 담당자 세션이 같은 화면·코드를 따로 중복 작성하지 않도록 한다. 초안 작성이나 임시 데이터 시연만으로 공식 단계 승인·실제 분석 검증이 완료됐다고 처리하지 않는다.
- 자동 배포 파이프라인은 이번 범위 밖이지만 수동 배포 작업은 남는다. 운영 단계의 포함·축소 여부와 무관하게 환경 준비·배포 실행·기록 확인·복구 검증의 담당 작업과 산출물 위치를 진행 계획에 명시한다.
- 입력 문서가 상세하다는 이유로 단계 완료·승인으로 처리하지 않는다. 문서의 제안·미기입을 구체화하고 해당 절차에 따라 검토한다. 새 intent 생성과 실제 단계 실행은 별도 시작 요청에서 진행한다.
