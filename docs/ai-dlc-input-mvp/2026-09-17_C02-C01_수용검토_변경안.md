### 제출 원문에 대한 정정·주의사항

원문을 고치지 않고 이 기록을 함께 읽는다.

- §1 ‘인젝션은 수행하지 않았다’는 **시험 미실행이 아니라, R1에 합성 인젝션을 넣었고 제출 결과상 모델이 그 지시를 따르지 않았다**는 의미다(§3·§5). 사실성 미달과 별개이며 전반적 인젝션 방어 통과가 아니다.
- §1·§7의 Scope 회의 대기/진행 표현은 오래된 인계 상태다. 현행은 Scope 승인·Rough Mockups 진행이다.
- §8 ‘사용자 결정 필요 없음’은 현행 검토 결론이 아니다. 제한적 예외의 공식 반영과 별도 미결이 남아 있다.
- 입력·응답·실행기 등 일부 해시는 축약돼 있다. 설정의 전체 해시는 있으나 전체 설정 내용 및 `not_set` 목록은 남아 있지 않고, 프롬프트도 전체 본문이 아니라 요지다. 없는 내용을 추정해서 보충하지 않는다.
- N2 feed.ts 확장분을 경로 수준으로 축소한 것은 호출 전 보고된 입력 변경이다. 축소된 범위에만 판정이 적용된다. R1은 이전 정정 규칙을 반영한 **알려진 실패 회귀**이며 N1·N2의 새 사례 관찰과 구분한다.

## 설치된 2.8.1 절차와 이번 처리 경계

- [변경 처리 §7](../../.codex/aidlc-common/protocols/stage-protocol-recovery.md): 새 자료는 현재 단계 입력이다. 이전 승인 단계에 영향을 주는 변경은 **영향 분석 → 사용자 확인 → 공식 단계/단계군 이동 및 영향 단계 재검토** 경로를 요구한다.
- [단계 절차 §1·§3 및 Artifact Re-use](../../.codex/aidlc-common/protocols/stage-protocol.md): 기존 산출물은 Keep/Modify로 재사용할 수 있다. 수정 산출물의 작성 전 확인·해당 검토·회고·승인을 생략하지 않는다. 과거 승인 이력은 삭제하지 않는다.
- C01의 기존 차단 효과를 바꾸므로 **일반 메모, 문서 등록, PR 병합, `relaxed` 설정만으로 효력이 생긴다고 처리하지 않는다**. 센서 실패도 아니므로 센서 override를 대신 사용하지 않는다. C01/C02는 단계가 아니므로 이 이름의 단계 승인 명령도 만들지 않는다.
- 이번에는 제출 근거 접수, 정정·수용 검토와 변경안 준비까지만 한다. 현행 Scope 승인·Rough Mockups 상태와 모든 미해소 착수 제한을 유지한다. 변경 적용을 위해 과거 승인을 임의 무효화하거나 Rough Mockups를 완료 처리하지 않는다.
- **다음 공식 반영안:** 영향 범위는 feasibility C01의 실패 대응과 Scope 잔여 조건의 해당 적용 문구다. 현재 단계의 정상 절차를 건너뛰지 않는 시점에, 사용자가 영향 재검토 경로를 확인하면 공식 지원 경로로 이를 다룬다. 기존 산출물은 재사용하고 해당 조건만 수정 대상으로 제시한다. Scope의 기능 범위·담당을 새로 결정하지 않는다. 변경 전 판본을 보존하고 새 승인·결정으로 연결한다. 실제 이동 시점·범위는 별도 확인 전 실행하지 않는다.

Max와 해당 계정의 Claude Code는 개인용 정책 대상이다. 학습 허용 시 학습 파이프라인에서 최대 5년, 대화 삭제 시 기록에서 즉시 제거·백엔드에서 30일 이내 삭제라는 안내가 있다. 정책 위반으로 분류된 입력/출력은 최대 2년·분류 점수는 최대 7년, 피드백 자료는 5년, 법적 의무 등 예외도 있다. 이는 이번 자료가 위반으로 분류되거나 피드백 전송됐다는 뜻이 아니다. [공식 보관 안내](https://privacy.claude.com/en/articles/10023548-how-long-do-you-store-my-data)

Claude Code 안내는 Max의 학습 미허용 시 30일 보관이라고 설명한다. 학습 꺼짐은 무보관/ZDR이 아니다. `/feedback`·`/bug`·`/share` 전송 자료와 별도 세션 공유 설문은 다른 보관 조건을 가질 수 있으므로 전송 여부를 구분한다. [공식 데이터 사용 안내](https://code.claude.com/docs/en/data-usage)

사용자 확인·정리 대상(현재 **삭제 미완료**, 실제 앱/CLI 버전과 파일 위치는 이번에 열람하지 않음):

1. **설정:** 재검증에 쓴 같은 Max 계정의 [Privacy 설정](https://claude.ai/settings/data-privacy-controls)에서 모델 개선/학습 허용이 꺼져 있는지 확인한다. 현재 상태·확인 시각만 회신한다. 당시 껐다는 진술은 유지하되 현재 설정으로 과거를 입증하지 않는다. 피드백·버그 신고·세션 공유/내보내기 여부도 확인하며, 확인 때문에 세션 내용을 다시 AI에게 보내지 않는다.
2. **주 삭제 대상:** 9/17 15:16부터 진행한 Desktop Code 재검증 세션의 발췌/응답 포함 기록. 앱의 ‘닫기/보관’만으로 삭제했다고 하지 않는다. Desktop 보관 기능은 worktree 제거도 수반할 수 있으므로 제출 worktree를 삭제하는 조작으로 대체하지 않는다. [Desktop 안내](https://code.claude.com/docs/en/desktop)
3. **로컬 잔존 확인:** 해당 세션의 `~/.claude/projects/<프로젝트>/<세션>.jsonl`, 관련 subagent/tool-result 기록, 붙여넣기 캐시·프롬프트 이력·debug·file-history·memory·수동 내보내기 중 발췌/응답 사본이 있는 것만 대상이다. `CLAUDE_CONFIG_DIR` 등으로 경로가 달라질 수 있다. 문서상 Desktop 보관 규칙은 버전별 차이가 있으므로 자동 30일 삭제에 의존하지 않는다. 전역 폴더·전체 프로젝트 purge는 다른 세션/설정까지 지울 수 있어 이번 안내에 포함하지 않는다. [로컬 자료 위치·정리 공식 안내](https://code.claude.com/docs/en/claude-directory)
4. **조건부 원격 사본:** 실제 클라우드/공유 세션을 만들었다면 그 세션도 대상이다. 클라우드 Code의 공식 삭제는 세션 제목 메뉴의 Delete 또는 보관 목록의 삭제 아이콘을 이용한다. 로컬 Desktop에 같은 메뉴가 있다고 가정하지 않으며, 해당 세션이 없으면 삭제하려고 업로드하지 않는다. [클라우드 세션 삭제](https://code.claude.com/docs/en/claude-code-on-the-web#delete-sessions)
5. **보존/금지:** 이미 삭제한 임시 루트는 복원하지 않는다. PoC·기존 TheMe·제출 보고서/저장소와 무관한 대화·인증/설정은 삭제하지 않는다. 삭제용 백업/원문 내보내기를 새로 만들지 않는다. 대상 식별이 어렵거나 메뉴가 없으면 파일 내용 대신 세션 식별 정보·앱 버전·메뉴명만으로 지원을 요청한다.

완료 회신은 ‘대상 종류/세션 식별자, 삭제 시각(KST), 확인 방법, 미확인 사본 여부’만 남긴다. 삭제된 원문·응답의 스크린샷/재출력은 필요 없다. 로컬 기한(9/23 또는 더 이른 설계/구현 경계)은 공급자 보관 기간을 이유로 연장하지 않는다. 백엔드 정리는 정책상 처리로 구분하며 로컬 삭제 확인과 함께 완료됐다고 하지 않는다.

## 영향 산출물·단계·승인 지점 — 준비 범위 확정

사용자 ‘이 경로로 준비’ 확인은 아래 **준비 경로**의 선택이다. 현재 단계 이동이나 예외 적용 완료의 승인으로 확대하지 않는다.

| 영향 단계 | 재사용할 산출물과 변경할 부분 | 남길 승인 지점 |
|---|---|---|
| feasibility | `constraint-register.md` C01 실패 대응에 이번 1건의 예외 적용문, C02에 후보 확보의 제한적 수용/미확인 조건. `feasibility-assessment.md` 후속 검증·일정 판단만 갱신. `raid-log.md` R01·R02·I01/I02 관련 관찰과 R1 잔여 결함 연결(기존 결함을 일괄 종결하지 않음) | 기존 질문 답변 재사용 → 변경 부분 작성 전 확인 → 필요한 검토·회고 → 변경된 판단의 공식 승인. 기존 승인 판본은 보존 |
| scope-definition | `scope-document.md` 잔여 C01/C02 적용표, `intent-backlog.md` IB02 및 C02→C01 선행 조건/제출 상태만 후속 반영 | 기능 범위·우선순위·담당은 유지하고 차이만 검토. 수정 작성 전 확인과 해당 단계 공식 승인. 과거 Scope 승인을 소급 취소하지 않음 |
| rough-mockups | 팀별 화면·흐름 초안 재사용. 근거 확인·불일치·별도 공개 동작의 일관성만 확인 | 현재 정상 진행 유지. 팀별 제출·작성 전 요약·해당 검토·회고·단계 승인 그대로. 예외를 이유로 화면을 새로 만들거나 자동 완료하지 않음 |
| 이후 requirements / domain / contract / delivery | 새 산출물에서 ‘C01 미달+이번 1건 예외’, C02 제한적 수용과 별도 미결을 입력으로 추적 | 정상 설계·계약 승인 및 domain-design 승인/관련 구현 착수 전 남은 조건 확인 유지. 아직 시작하지 않은 단계를 재실행한다고 표현하지 않음 |

현재 승인 문서들은 수정하지 않았다. 공식 재검토 시에는 기존 산출물 Keep/Modify 재사용 선택으로 위 차이만 다루며 전량 재질문·새 실험·전체 재설계를 하지 않는다. C03~C12·NFR3 전체 품질·B 조건부 담당·제품 범위는 이번 변경 대상이 아니다. 검토 과정에서 실제 추가 영향이 발견된 경우에만 구체적인 관계를 먼저 제시한다.

현재 Rough Mockups의 정상 절차를 마치기 전에 이전 단계로 이동하지 않는다. 적법한 전환 시점에 위 영향 분석과 이동 범위를 먼저 제시하고 공식 경로를 사용한다. 해당 재검토가 후속 단계까지 다시 통과하도록 요구하면 영향을 받지 않은 산출물은 Keep을 제안하되 필요한 승인 자체를 자동 처리하지 않는다. 공식 반영을 위한 문서 검토/승인 대기 시간은 발생할 수 있으며, ‘추가 튜닝 없음’을 일정 확보로 계산하지 않는다.

## 후속 개선과 지금 가능한 작업

- 결함 후속: 문맥 줄/변경 줄의 입력 구분을 우선 설계 후보로 남긴다. 프롬프트에 같은 원칙이 이미 있었으므로 규칙 한 줄 추가로 해결됐다고 하지 않는다. 입력 표현·지시 준수·모델 한계의 원인은 분리 검증되지 않았다.
- 규칙 기반 귀속 검사는 보조 수단 후보다. 추가/삭제 줄 문자열 일치가 기여 귀속의 의미적 정확성을 보장하지 않는다. 새 필수 구현·담당·기한·호출을 배정하지 않는다. 기존 검사기의 머리줄 파싱 오류도 실제 채택 시 수정/검증 대상으로 남긴다.
- 사람 확인 동작은 유지하되 모델 원응답 성공과 분리한다. 인용 개수/문체 튜닝은 이번 추가 작업에 넣지 않는다. 개선안 모두 미실행이며 별도 우선순위·작업 허용 전까지 보류한다.
- 팀원 2 A/E: 연결·동의·분석 요청/실패/중복 상태와 화면 인계 초안. 팀원 3 C/D: 진행/결과 이동·공개 선택·현재 권한·링크 열람/거부 초안. 각자 담당 간 먼저 대조하고 계약 질문·입출력 예시는 후속 설계 입력으로 제출할 수 있다.
- 팀원 1 F/H/I: 근거/초안의 범위·불일치·미검증 표시 입력, 배포·복구 전제 정리, 연결 충돌 취합. 타 담당의 설계·시험·결함 수정 대행이 아니다. B 조건부 담당은 그대로다.
- 위 작업은 화면 흐름·상태·인계 및 계약 **준비**다. 공식 계약 확정, 관련 서비스 구현, 인프라 생성·배포, 실자료 전송, Rough Mockups 완료/승인을 대신하지 않는다.
