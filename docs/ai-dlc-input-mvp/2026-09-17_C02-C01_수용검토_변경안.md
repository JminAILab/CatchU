### 제출 원문에 대한 정정·주의사항

원문을 고치지 않고 이 기록을 함께 읽는다.

- §1 ‘인젝션은 수행하지 않았다’는 **시험 미실행이 아니라, R1에 합성 인젝션을 넣었고 제출 결과상 모델이 그 지시를 따르지 않았다**는 의미다(§3·§5). 사실성 미달과 별개이며 전반적 인젝션 방어 통과가 아니다.
- §1·§7의 Scope 회의 대기/진행 표현은 오래된 인계 상태다. 현행은 Scope 승인·Rough Mockups 진행이다.
- §8 ‘사용자 결정 필요 없음’은 현행 검토 결론이 아니다. 제한적 예외의 공식 반영과 별도 미결이 남아 있다.
- 입력·응답·실행기 등 일부 해시는 축약돼 있다. 설정의 전체 해시는 있으나 전체 설정 내용 및 `not_set` 목록은 남아 있지 않고, 프롬프트도 전체 본문이 아니라 요지다. 없는 내용을 추정해서 보충하지 않는다.
- N2 feed.ts 확장분을 경로 수준으로 축소한 것은 호출 전 보고된 입력 변경이다. 축소된 범위에만 판정이 적용된다. R1은 이전 정정 규칙을 반영한 **알려진 실패 회귀**이며 N1·N2의 새 사례 관찰과 구분한다.
- 모델 조회 16:21:24, R1 호출 16:21:30~16:21:45, 허용 문구 수신 약 16:22다. 사용자가 실행 확인표를 받고 직접 실행했다는 사실과, **인계서의 명시적 허용 후 호출 순서를 기록으로 입증하지 못했다**는 사실을 함께 남긴다. 사전 허용을 소급 작성하거나 자동 실행의 무단 호출로 단정하지 않는다. R1 미달 후 N1·N2 진행은 별도 사용자 허용 기록이 있다.
- 사용자 진술: OpenAI 데이터 공유 꺼짐·잔액 $0.0438 이상, Claude 학습 사용 꺼짐. 도구가 확인한 계정 설정으로 바꾸어 쓰지 않는다.
- 보고는 16:39 이후, 임시 루트 삭제는 16:42~16:48 사이(정확 시각 없음), 부재 확인은 16:48:59, 제출 커밋은 16:49:42다. 이 시각들로 보고·삭제·제출의 실제 작업시간을 역산하지 않는다. 사용자 작업시간 확인 불가는 재질문으로 메우지 않는다.

## 설치된 2.8.1 절차와 이번 처리 경계

- [변경 처리 §7](../../.codex/aidlc-common/protocols/stage-protocol-recovery.md): 새 자료는 현재 단계 입력이다. 이전 승인 단계에 영향을 주는 변경은 **영향 분석 → 사용자 확인 → 공식 단계/단계군 이동 및 영향 단계 재검토** 경로를 요구한다.
- [단계 절차 §1·§3 및 Artifact Re-use](../../.codex/aidlc-common/protocols/stage-protocol.md): 기존 산출물은 Keep/Modify로 재사용할 수 있다. 수정 산출물의 작성 전 확인·해당 검토·회고·승인을 생략하지 않는다. 과거 승인 이력은 삭제하지 않는다.
- C01의 기존 차단 효과를 바꾸므로 **일반 메모, 문서 등록, PR 병합, `relaxed` 설정만으로 효력이 생긴다고 처리하지 않는다**. 센서 실패도 아니므로 센서 override를 대신 사용하지 않는다. C01/C02는 단계가 아니므로 이 이름의 단계 승인 명령도 만들지 않는다.
- 이번에는 제출 근거 접수, 정정·수용 검토와 변경안 준비까지만 한다. 현행 Scope 승인·Rough Mockups 상태와 모든 미해소 착수 제한을 유지한다. 변경 적용을 위해 과거 승인을 임의 무효화하거나 Rough Mockups를 완료 처리하지 않는다.
- **다음 공식 반영안:** 영향 범위는 feasibility C01의 실패 대응과 Scope 잔여 조건의 해당 적용 문구다. 현재 단계의 정상 절차를 건너뛰지 않는 시점에, 사용자가 영향 재검토 경로를 확인하면 공식 지원 경로로 이를 다룬다. 기존 산출물은 재사용하고 해당 조건만 수정 대상으로 제시한다. Scope의 기능 범위·담당을 새로 결정하지 않는다. 변경 전 판본을 보존하고 새 승인·결정으로 연결한다. 실제 이동 시점·범위는 별도 확인 전 실행하지 않는다.
- 원문 등록은 DocumentKB 공식 `onboard`와 명시적 intent 연결만 사용한다. 이 검토안은 제품 입력 문서이며 정식 단계 산출물이나 승인 영수증이 아니다. 승인된 문서·감사·상태·도구 소유 카탈로그를 직접 고치지 않는다.
- 접수 결과: 공식 등록 `fresh` 1건, 문서 ID `01a0ae71-98c0-76f5-b986-0f79ed587540`, 추출 상태 `extracted`·잘림 없음. intent ID `01a09dc4-cc12-774d-8813-47bcf51644de` 연결을 조회로 확인했다. 제출 파일과 추출본 SHA-256 일치. 등록 시 도구가 생성한 `intents/audit/`의 문서 감사 기록은 그대로 보존한다. 이후 새 작업 폴더의 활성 intent를 공식 명령으로 같은 intent에 맞췄으며 단계 상태는 바꾸지 않았다.

### C01/C02 공식 변경 경로 조회와 구체 영향

AI-DLC 스킬의 [변경 처리 §7](../../.codex/aidlc-common/protocols/stage-protocol-recovery.md)과 [Artifact Re-use](../../.codex/aidlc-common/protocols/stage-protocol.md)를 대조하고, `aidlc engine status` 및 읽기 전용 `aidlc engine jump resolve --stage feasibility`를 조회했다. 현재는 Domain Design 최종 승인 대기다. 이동 조회는 `valid: true`, `direction: backward`, `current_slug: domain-design`, `target_slug: feasibility`를 반환했다. 실제 이동은 실행하지 않았으며 현재 승인 대기에서의 이동 실행 성공까지 검증한 것은 아니다.

**내용 수정 대상은 앞 절의 5개 산출물로 제한하되, 공식 이동의 영향 목록은 더 넓다.** 조회 결과는 feasibility → scope-definition → rough-mockups → approval-handoff → practices-discovery → requirements-analysis → domain-design 및 이후 units-generation부터 performance-validation까지의 예정 단계를 포함한다. 미시작 후속 단계가 목록에 있다는 사실은 구현 착수나 이미 완료한 단계의 재수행을 뜻하지 않는다.

- feasibility 3개 산출물: C01 미달·R1 한 건 예외, C02 제한 수용과 미확인 조건만 Modify 제안. 기존 판본을 변경 전에 보존한다.
- scope-definition 2개 산출물: 잔여 조건/IB02의 해당 참조만 Modify 제안. 기능·담당·기존 결정은 재사용한다.
- 중간의 완료 단계와 현재 Domain Design: 기존 제출물·Q1~Q8·회고·R-01 해결을 재사용하고 내용 영향이 없는 부분은 Keep 제안. 다만 규칙상 Keep은 생성 단계를 생략하고 승인 지점으로 가는 선택이므로, 과거 승인이 새 재검토 시도의 승인을 자동 대신한다고 약속하지 않는다. 구체적인 검토·확인은 실제 공식 지시가 요구하는 범위에서 수행한다.
- approval-handoff 변경 감지 안내는 복구된 입력 존재 여부 차이에 따른 비차단 안내로 그대로 둔다. 해당 표시만 없애기 위한 재승인·초기화 재수행은 하지 않는다. 위 변경 절차가 중간 단계의 승인을 요구하는 경우에는 C01/C02 변경의 영향과 재사용 범위를 별도로 제시한다.
