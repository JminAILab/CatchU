## 1. 이번 작업 범위와 기준

**우선 최소 골격과 로컬 검증을 진행한다.** 골격은 시연 흐름 정리와 CI 완료를 기다리지 않고 준비하며, 첫 코드 병합은 자동 검사와 리뷰 조건을 충족한 뒤 진행한다.

| 구분 | 적용 범위 |
|---|---|
| 전체 목표 | 합성 데이터로 로그인·프로필·홈·분석·Catch 확인/공개·링크 발행·수신자 열람 시연 |
| 지금 작업 | 실행 틀·모의 배너·초기 합성 데이터 1개·저장 어댑터·시계·테스트 설정·README |
| csyg0616의 후속 작업 | 홈·분석 정상 경로 → 링크·수신자 정상 경로 → 시나리오 선택 도구·통합 검사 조립. 다른 담당 기능과 정해진 데이터로 연결 |

## 3. 완료 기준과 진행 관계

| 단계 | 완료를 확인할 내용 | 구분할 후속 작업 |

| 첫 코드 병합 가능 | 같은 PR에 골격+CI 포함, 최종 커밋의 실제 CI 통과·타인 승인 1건 이상·리뷰 대화 해결·보호 조건 확인 | 전체 시연 완료와 별도 |

검사는 package.json·설정·잠금 파일을 만든 뒤 **web 폴더에서** 실행한다. 현재는 앱 패키지가 없어 실행 통과를 주장하지 않는다.

공통 검사: `npm ci` → `npm run lint` → `npm run typecheck` → `npm run test -- src/test/web-mock/` → `npm run build`.

#74의 **G0**는 위 로컬·CI 공통 검사 묶음의 식별자다. 골격 단계에서는 작성된 공통 테스트를 실제로 실행하고 기능이 추가되면 해당 검사도 포함한다. 개발·빌드 결과 실행과 종료는 별도로 확인한다.

골격 테스트는 `shared/model.test.ts`(초기 데이터·스키마·초기화), `shared/storage.test.ts`(저장/복원·손상·저장 실패), `shared/shell.test.tsx`(배너·로딩·복원 오류)다. 각 파일의 정상 사례와 오류·경계 사례 최소 2개 등 상세는 테스트 지침을 따른다.

1. csyg0616은 CI와 독립적으로 골격을 작성하고 로컬 검사를 수행한다.
2. 골격이 준비되면 CI 전에도 PR 검토와 다른 팀원의 로컬 재현을 진행한다.
3. ljm0850은 시연 화면·이동·핵심 내용 정리 후 CI를 작성한다. 골격 작업과 병행할 수 있다.
4. CI를 첫 PR에 결합하고 실제 병합 조건을 확인한다.
5. csyg0616은 골격 → 홈·분석 정상 경로 → 링크·수신자 정상 경로로 진행한다. 다른 기능 담당은 골격 인터페이스와 합성 자료를 이용해 병행한다.
6. csyg0616이 시나리오 선택 도구·통합 검사를 조립하고, 각 작성자가 자기 기능의 결함을 수정한다. 전체 연결 뒤 전체 브라우저 시나리오와 독립 재현 증거를 확인한다.

타인 재현을 모두 마지막까지 미루거나 전체 화면 검사를 골격 완료 조건으로 옮기지 않는다. 정확한 명령·전체 시나리오는 테스트 지침의 **‘명령 계약’·‘수동 브라우저 확인’·‘새 작업 폴더 재현’** 절을 따른다.

담당 대조 출처: [#70 아키텍처 초안의 ‘담당과 검토’](https://github.com/JminAILab/CatchU/blob/5c54235da97d6552e420eba0f5ba8da5a78f62fc/docs/ai-dlc-input-mvp/CatchU_공통_아키텍처_검토초안.md)와 이 문서의 출처 표에 연결한 「web 모의 시연 구현 계획」(code-generation-plan.md) ‘작업 패키지와 파일 소유’. 두 문서의 적용 범위가 달라 담당 불일치로 단정하지 않으며, 아래 연결 검토안은 이번 시연의 담당 확인을 전제로 한다.

출처: 원격 브랜치는 `git ls-remote`, 작업 폴더는 `git worktree list`와 상태 조회, 도구는 버전 명령·Node 공식 배포·npm 저장소 조회로 확인했다. 보호 조건은 [규칙 목록](https://github.com/JminAILab/CatchU/rules)과 [dev 보호 규칙](https://github.com/JminAILab/CatchU/rules/21272403)을 읽었다.

작업 전용 도구 선택 스크립트의 실행도 확인했다. 해당 터미널에서만 도구 경로·작업 위치를 바꾸며 시스템 설치는 교체하지 않았다. 앱 의존성 설치·초기화·제품 코드 작성·CI 실행은 아직 수행하지 않았다. 개인 설치 경로를 팀 공통 실행 조건으로 만들지 않는다.

### 실행 이슈 재조회 결과와 등록 전 확인

2026-09-21 열린 이슈 15개·종료 이슈 8개의 목록, 관련 이슈의 범위·완료 기준과 `골격·시연·CI·web-mock·skeleton` 검색 결과를 대조했다. 아래 세 실행 작업과 같은 목적·완료 기준의 이슈는 확인되지 않았다. 이 결과는 신규 등록 후보를 정리한 것이며 등록·배정 완료가 아니다.

종료된 [#26 「10월 MVP 두 번째 AI-DLC 진행 계획 수립」](https://github.com/JminAILab/CatchU/issues/26)은 계획 수립 완료이므로 구현을 위해 다시 열지 않는다. 검색에 나온 [#19 「PoC 처리 구조와 서비스 적용 차이 정리」](https://github.com/JminAILab/CatchU/issues/19)와 [#37 「10월 MVP 실행 가능성·제약 검토」](https://github.com/JminAILab/CatchU/issues/37)도 모의 시연 실행과 목적·완료 기준이 다르다. 기존 이슈의 상태는 각 원본에서 확인한다.

다음에는 세 후보의 담당·완료 기준·우선순위·선행 조건을 정리한다. 「web 모의 시연 착수 안내」(이 문서의 출처 표, PR #74)에 기재된 담당은 골격 `csyg0616`, 시연 흐름 정리와 CI `ljm0850`이다. 등록안에는 배정 근거와 남은 확인을 구분하고 실제 착수 여부를 따로 표시한다.

등록 직전에 동일 이슈가 새로 생겼는지 다시 조회하고, 같은 작업이 있으면 재사용한다. 우선순위는 사용자 답변 후 반영하고 Projects 편입·필드 적용을 확인한다. 근거는 [「CatchU 작업관리」 문서](../CatchU_작업관리.md)의 「AI가 작업마다 수행할 절차」 안 ‘우선순위 확인’·‘착수’다. P1은 먼저 연결·막힘 해소, P2는 이후 보강이며 P2도 필수 작업일 수 있다.

골격 작성·로컬 검사는 CI 완료와 독립적으로 진행한다. 시연 흐름 정리 후 CI를 작성하며 첫 코드 병합은 골격과 CI를 결합하고 검사·리뷰 조건을 충족한 뒤 진행한다. 상세 완료 기준은 이 준비안의 「3. 완료 기준과 진행 관계」를 따른다.

**자산 공통 탭 검토안:** `web/src/app/(owner)/assets/layout.tsx`를 후보로 두고 csyg0616 작성·yeongyeon1802 검토·leechaeah 연결 확인을 제안한다. 기존 공통 책임에 포함되는지 확인하며 확정 배정으로 쓰지 않는다.

**분석→Catch 연결 검토안:** 이번 시연의 Catch 담당 확인을 전제로 csyg0616이 분석 결과를 전달·호출하고 leechaeah가 Catch 반영 함수를 구현하는 안이다. 같은 식별자가 있으면 갱신하고 없으면 추가하되 기존 확인·공개 상태·링크를 보존한다. 양쪽에서 저장 로직을 중복 구현하지 않는다. 담당·함수와 오류 전달·일부 저장 실패의 처리는 합의가 필요하다.

**수신자 동작의 차이:**

- [공유 링크 초안 v0.20의 헤더 설명](https://github.com/JminAILab/CatchU/blob/a735120031f9b9b6b008125d8574cc0490a1ee64/docs/ai-dlc-input-mvp/CatchU_공유링크_흐름_와이어프레임_초안.md#31-공유-링크-방문자-전용-헤더)은 10월의 이동 없는 브랜드 표시를 미확정 제안으로 둔다. #74는 발행자 공개 프로필·해당 링크 첫 화면으로의 이동을 안내한다. 기존 초안의 수신자 본인 계정 메뉴와 발행자 공개 프로필은 다른 대상이다.

## 6. 실제 서비스 연결을 위한 기존 제안

v0.1의 실제 서비스용 검토 방향을 보존한 절이다. 이번 모의 시연의 필수 준비가 아니며 실제 연결 작업에서 다시 검토한다.

| 항목 | 보존할 제안·경계 |
|---|---|
| 화면 구조 | App Router·TypeScript strict, CSS Modules와 공통 CSS. 실제 재사용되는 요소만 공통화하고 빈 기능 폴더를 미리 모두 만들지 않음 |

| 공개 설정 | `NEXT_PUBLIC_API_BASE_URL=http://localhost:3001`은 실제 연결 때 확인할 후보. 빌드 시 공개 설정 반영·재빌드 여부 확인 |
| 로컬 설정 | .env.example 공유, .env.local Git 제외 확인. 기존 파일을 덮어쓰지 않고 공개 설정에 비밀값을 넣지 않음 |
| 인증 | 허용 출처·쿠키·CSRF·자격 증명 전달 계약 확인. 로그인 UI와 서버 권한 검사를 구분 |
| 오류·모의 자료 | 실제 API 오류를 모의 성공으로 자동 전환하지 않고 모의 자료를 제품 완료 증거로 사용하지 않음 |
| 브라우저 자동 검사 | Playwright는 향후 필요 시 도구·실행 서버·연결 조건을 검토할 후보 |
| README | 초기화 후 web/README.md 한 곳에 실제 재현 명령·설정·폴더 역할·오류 확인·검증 한계 기록 |

- [ ] #74와 다른 폴더·명령을 각자 적용하지 않도록 기준이 명확한가?
- [ ] 준비 완료·미검증·답변 대기를 구분하고 제안을 확정 배정으로 읽지 않도록 했는가?
- [ ] 골격 로컬 준비·첫 병합·전체 시연의 완료 기준이 구분되는가?

준비안은 검토 초안으로 유지하고 `docs/web-dev-preparation` 브랜치에서 공유한다. #74 리뷰에 해당 판본을 연결하며, dev 반영은 별도 문서 PR·리뷰 절차를 따른다. 이슈 등록·의존성 설치·앱 초기화는 후속 작업이다.

- v0.1 (2026-09-21): #70 후속 실제 서비스용 web 구조·명령·설정·README 제안 작성.
- v0.2 (2026-09-21): #74 적용 범위·차이·단계별 완료 기준·실제 환경 준비와 미결을 구분. 실제 서비스 제안은 이 문서의 「6. 실제 서비스 연결을 위한 기존 제안」에 보존. 공식 계획·담당·정책 변경은 수행하지 않음.
- v0.3 (2026-09-21): 담당 표기를 GitHub 계정명으로 통일. Catch 담당 확인, csyg0616의 작업량·일정 검토와 통합 조립 책임, CI 실패 자동 차단 미설정의 의미를 보완.
- v0.4 (2026-09-21): 출처에 문서명·파일 경로·판본과 적용 의미를 표시하고 절 번호 단독 참조를 풀어 썼다. 실행 이슈 재조회와 중복 판단, 신규 등록 전 확인 항목을 추가했다. 이슈 등록·Projects 변경·새 담당 또는 우선순위 확정은 수행하지 않았다.
