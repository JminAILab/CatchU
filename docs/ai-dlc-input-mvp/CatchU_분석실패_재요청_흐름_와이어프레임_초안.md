## 0. 10월 공통 헤더 적용

**[팀원 2·3 합의 — 2026-09-22 기록]** [10월 헤더 합의 #55](https://github.com/JminAILab/CatchU/issues/55)·[사용자 메뉴 동작 합의 #51](https://github.com/JminAILab/CatchU/issues/51)를 적용한다. 팀원 3이 두 사람의 안건 A~H 답변이 동일함을 확인해 기록한 범위다. API·시각 디자인·구현 승인과 구분한다.

| 화면·상태 | 10월 헤더 구성·동작 |
|---|---|
| 로그인 일반 서비스·발행자 | 왼쪽 로고 → 내 자산 → 공유 링크 → 채용공고(비활성 표시·클릭 시 안내창), 오른쪽 알림(비활성 표시·클릭 시 안내창) → 프로필. 로고는 로그인 홈, 내 자산은 자산 영역, 공유 링크는 L03으로 이동 |
| 비로그인 일반 홈 | 왼쪽 로고, 오른쪽 Google로 시작하기. 로고는 비로그인 홈, 헤더·본문 시작 버튼은 같은 로그인 흐름으로 연결 |
| 수신자 V01~V03, 로그인·비로그인 공통 | 이동 없는 브랜드만 표시. 로그인·프로필·관리 메뉴 없음. V03 본문의 같은 링크 V02 목록 복귀 버튼 유지 |

10월에는 채용공고·알림을 **비활성 표시(클릭 시 안내창)**로 두고 대표 구성 진입점(내 자산 내부 포함)은 숨긴다. **[결정]** 두 메뉴를 클릭하면 현재 화면 위 작은 안내창에 ‘개발 중인 기능입니다’와 [확인]을 표시하고, [확인]은 안내창만 닫고 기존 화면을 유지한다. 별도 페이지로 이동하지 않으며 10월에는 알림 목록·배지·설정 기능을 제공하지 않는다. 비활성은 기능 미제공을 뜻하며 클릭 불가가 아니다. **[미정]** 안내창의 추가 닫기 조작(X·Esc·바깥 클릭). 근거: [#55 9/23 제안](https://github.com/JminAILab/CatchU/issues/55#issuecomment-5788084856)·[합의](https://github.com/JminAILab/CatchU/issues/55#issuecomment-5788108788). 최초 프로필 입력의 저장 조건을 우회하는 메뉴 진입을 새로 허용하지 않는다. 12월 수신자 회원 연결·알림 설정은 후속 논의다.

로그인 일반 서비스의 프로필 버튼 근처에 **모달**을 열고 **프로필 보기 / 로그아웃**을 둔다. 프로필 보기 → 상세 프로필 → 수정 → 저장 성공·취소 후 상세 프로필로 돌아온다. 변경이 있는 취소·이동·로그아웃은 이탈 확인을 거치며, 머무르기를 선택하면 화면과 입력을 유지한다. 로그아웃은 최초 입력 W02를 포함해 성공 시 **비로그인 홈(H-01)**으로 이동하고, 실패 시 현재 화면·입력을 유지하며 완료로 표시하지 않는다. 모달 닫기 조작의 조합과 로그아웃 실패 안내의 구체 문구는 후속 검토다.

이 반영은 공통 헤더·프로필 연결만 다룬다. 분석 요청·동의·접수 불명·재요청 및 #64의 화면 단위 경계는 기존 기준을 유지한다. 화면 이동·로그아웃을 분석 취소·완료로 해석하지 않는다.

표시 구분:

- **[요구]** 승인 요구사항이 정한 행동. 화면이 어떤 방식으로 구현하든 지켜야 한다.
- **[결정]** MVP 입력에 명시된 팀장 결정.
- **[팀 합의]** 후속 입력에 팀장 확인으로 기록된 팀 합의.
- **[팀장 리뷰]** PR 리뷰에서 팀장이 진행 방향을 정한 사항. 후속 입력에 기록되기 전이며 공식 승인이 아니다.
- **[팀장 결정]** PR 댓글의 결정과 병합된 후속 입력을 뜻한다. AI-DLC 공식 승인은 별도로 구분한다.
- **[제안]** 요구·결정을 화면에서 표현하는 방식이나 문서에 없는 동작. 배치·이동·문구·버튼이 여기에 속한다.
- **[미정]** 합의가 필요한 정책·연결 조건.

화면 ID(H-01, A-01~A-03)는 초안 안의 식별자이며 공식 ID가 아니다. URL 경로·API 계약·상태 값 이름은 정하지 않는다.

## 2. 관련 요구사항과 화면 표현

| 근거 | 지켜야 할 행동 | 이 화면의 표현 |
|---|---|---|
| FR1.4, NFR4 | **[요구]** 분석 실패 시 기존 자료·링크를 보존하고 사용자의 재요청을 지원한다. 같은 저장소의 진행 중 중복 요청과 재요청에 따른 카드 중복 생성을 막는다 | **[제안]** 실패 안내에 ‘기존 자료와 링크는 유지됩니다’를 두고, 재요청은 [다시 분석 요청] 버튼으로만 실행한다. 요청 중 반복 제출을 화면에서도 막되, 진행 중 중복과 카드 중복 방지의 기준은 서버 판정이다. 화면에 ‘카드가 중복되지 않습니다’ 같은 보장 문구는 두지 않는다 |

| FR1.1, C4 | **[요구]** 구직자의 해당 저장소 분석 동의가 선행 조건이며 동의가 없으면 분석하지 않는다 | **[결정]** 재요청은 새 동의로 새 요청을 만든다(PR #89 Q1 A). **[미정]** 동의를 받는 화면 배치(A-03 안·A-01 재진입)와 받을 정보. 이번 와이어프레임에는 동의 단계를 그리지 않고 연결 질문으로 남긴다(OQ11, #24, §6) |

## 3. 진입 경로와 사용자 흐름 [제안]

```text
진입
  ├─ [A-02] 실패 상태의 [실패 내용 보기] → A-03
  └─ [내 자산] GitHub 관련 탭의 실패 항목 → A-03   [팀 합의]
  (홈에는 분석 상태를 두지 않아 A-03 진입 없음 — PR #44 [팀장 결정])
  (A-01에서 실패 이력 저장소를 다시 고르는 경로는 미정, #23)

[A-03 분석 실패·재요청]  (실패한 분석의 식별자로 상태 조회)
  ├─ 상태 조회 중 → ‘분석 상태를 불러오는 중입니다’
  ├─ 상태 조회 실패 → 조회 실패 안내 + [상태 다시 불러오기]
  ├─ 분석을 찾을 수 없음·본인 분석 아님 → 안내 + [내 자산 GitHub 탭으로]
  ├─ 이미 실패 상태가 아님(다른 곳에서 재요청됨 등)
  │    → 현재 상태 안내 + [진행 상태 보기] 또는 [결과 확인]
  │
  └─ 실패 확인 → 실패 안내 + 기존 자료·링크 유지 안내
       ├─ 재요청 불가(서버 판정: 유효 결과·등록 Catch 있음, 처리·반영·복구 진행 중 등)
       │    → [다시 분석 요청] 없음, 사유 안내(문구 미정)
       └─ 재요청 허용(서버 판정) → 사용자가 [다시 분석 요청] 선택
            ├─ 새 동의 필요 [결정] — 동의 화면 배치는 미정, 이번 흐름에 그리지 않음
            ├─ 요청 중 → 반복 제출 차단
            ├─ 접수 확인 → A-03에 ‘분석을 다시 요청했습니다’ 접수 확인 창
            │    ├─ [진행 상태 보기] → A-02 (누를 때만 이동)
            │    └─ [닫기] → 창만 닫고 A-03 유지 (요청 취소·재요청 없음)
            │         → 실패 안내·[다시 분석 요청] 대신
            │           ‘분석 재요청이 접수되었습니다’ + [진행 상태 보기]
            │           (현재 상태를 조회했으면 그 상태에 맞춰 안내)
            │    (접수 확인만으로 자동 이동하지 않음)
            ├─ 같은 분석의 재요청이 이미 진행 중
            │    → 접수 확인 창 없이 현재 상태 안내 + [진행 상태 보기]
            ├─ 거절(허용 조건 미충족·선정 조건 변경)
            │    → 접수 확인 창 없음. 사유 안내 + [다시 분석 요청] 비활성
            │      (A-03 유지, 기존 자료 경로 유지, 다시 활성화 조건 미정)
            └─ 접수 여부 불명 → 접수 확인 창 없음. [요청 상태 확인]
                 ├─ 접수 확인 → 접수 확인 창(위와 같음)
                 ├─ 거절 확인 → 거절 안내
                 └─ 여전히 불명 → 접수 불명 안내 유지
                 (자동 재제출 없음)

어느 상태에서든 [홈으로] 또는 상단 메뉴로 이동 가능
```

- **[결정]** 자동 재시도는 하지 않는다. **[제안]** 재요청은 사용자가 [다시 분석 요청]을 누를 때만 보낸다. 화면 진입, [상태 다시 불러오기], [요청 상태 확인]은 새 분석이나 재요청을 만들지 않는다.
- **[제안]** 접수가 확인되면 A-03에 ‘분석을 다시 요청했습니다’ 접수 확인 창을 띄운다. 접수 확인 창의 [진행 상태 보기]를 누르면 재요청한 분석의 현재 상태를 보여 주는 A-02로 이동하며, 접수 확인만으로 자동 이동하지 않는다. A-02는 병합된 분석 진행 초안의 화면을 따르며 이 초안에서 다시 설계하지 않는다.
- **[제안]** 이 접수 확인 창은 사용자가 A-03에서 방금 누른 [다시 분석 요청]의 접수 결과를 그 자리에서 알리는 안내다. 12월 범위인 헤더 알림(분석 완료·실패 안내, 알림 자리 #51)과 별개이며, 헤더 알림을 대신하거나 10월에 알림 목록·배지·발송 기능을 만드는 안이 아니다(헤더의 알림 아이콘은 §0의 비활성 표시만 해당). 재요청한 분석이 나중에 완료·실패한 사실은 이 접수 확인 창으로 알리지 않으며, 10월에는 A-02와 [내 자산] GitHub 관련 탭에서 확인한다(**[팀장 결정]**).
- **[제안]** 재요청이 거절되거나 접수 여부가 불명확하면 접수 확인 창을 띄우지 않고 해당 안내(§4.4·§4.5)를 유지한다.
- **[제안]** 요청 전송 후에는 [다시 분석 요청]을 ‘다시 분석을 요청하는 중입니다’로 바꾸고 반복 제출을 막는다. 화면을 떠나도 요청이 취소되거나 기록이 삭제된다고 안내하지 않는다.
- **[미정]** 재요청 뒤 A-02가 보여 줄 분석이 원래 분석과 같은 식별자인지 새 식별자인지(§6).

## 4. PC 와이어프레임 [제안]

헤더는 [9/16 회의 결정](2026-09-16_meeting-decisions.md)·#55에 맞춰 로고→홈으로 연결하고 별도 [홈]·[대표 구성]을 제거했다. 채용공고·헤더 알림 기능은 12월이며 10월에는 헤더에 비활성으로만 표시한다(§0). 프로필 동작은 §0의 #51·#55 합의를 적용한다. §4.3–4.5의 표시·버튼 분기는 접수 응답·분석 식별 계약에 따른 제안이다.

표기는 홈·A-02 초안과 같다. 굵은 선 상자(┏ ┃ ┗)는 강조 영역, `[[버튼]]`은 주 버튼, `[버튼]`은 보조 버튼이다. `[예시]`는 임시 표시값이며 실제 선정 저장소·처리 결과가 아니다. 화면의 배치·문구·버튼은 모두 제안이다.

**설계 주석 — 그리지 않은 정책:** 재요청 허용 조건은 **[결정]** 실패 확정·유효 결과/등록 Catch 없음·처리/반영/복구 진행 없음일 때만이며, 화면은 서버의 허용 여부(계약의 retry.allowed·reason)를 따른다(PR #89 Q1 A). 재요청에는 새 동의가 필요하다 **[결정]**. 실패 유형별 사유 문구, 재요청 불가 사유 문구, 동의를 받을 영역([다시 분석 요청] 전 A-03 안에 A-01의 저장소별 동의 안내와 같은 영역을 둘지, A-01로 보낼지)은 **[미정]**이라 화면에 그리지 않았다(§6).

### 4.1 실패 안내 — 재요청 전

```text
┌─ A-03 분석 실패·재요청 · 실패 안내 ────────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석에 실패했습니다.
│ ┃ 기존 자료와 링크는 유지됩니다.
│ ┃ 원하면 이 저장소의 분석을 다시 요청할 수 있습니다.
│ ┃
│ ┃ [[다시 분석 요청]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[요구]** 실패가 기존 자료·링크 손실로 이어지지 않는다(FR1.4·NFR4). **[제안]** 그 사실을 실패 안내에 한 줄로 보여 준다.
- **[제안]** [다시 분석 요청]만 주 버튼으로 두며, 서버가 재요청을 허용한 실패에서만 보여 준다([결정] PR #89 Q1 A). 불가로 판정되면 버튼 없이 사유를 안내한다(문구 미정). 자동 재시도나 ‘몇 초 뒤 다시 시도’ 같은 표시는 두지 않는다(OQ1 **[결정]**).
- **[미정]** 실패 사유를 사용자에게 어떤 구분으로 보여 줄지(OQ1). 사유 줄은 구분이 정해진 뒤 안내 아래에 추가한다.
- **[제안] 일부 실패·열람 가능한 결과 있음:** 서비스 등록·본인 열람 준비가 확인된 Catch가 있으면 실패 안내 아래에 ‘확인할 수 있는 결과가 있습니다’ 한 줄과 보조 버튼 [결과 확인]을 더한다. 이 상태에서는 [다시 분석 요청]을 두지 않는다 — 유효 결과·등록 Catch가 있는 부분 실패의 추가 생성·보완은 보류이며 재요청 대상이 아니다([결정] PR #89 Q1 A). 결과 확인과 재요청은 별개다. 후보 존재·F 처리 종료·결과 전달만으로 [결과 확인]을 활성화하지 않고, 열람 준비 미확인이면 결과 버튼 없이 ‘결과를 확인하는 중’ 안내만 둔다([결정] PR #68 Q3). A-03 진입은 A-02의 [실패 내용 보기] 선택으로만 이뤄지며 자동 이동은 없다. 표시명은 화면용이며 서버 상태값이 아니다. **[미정]** 열람 준비 판단 정보·버튼 활성 계약(#23 Q6), B 결과 화면 연결. 별도 와이어프레임은 그리지 않는다.

┌─ A-03 분석 실패·재요청 · 요청 중 ──────────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석에 실패했습니다.
│ ┃ 기존 자료와 링크는 유지됩니다.
│ ┃
│ ┃ 다시 분석을 요청하는 중입니다.
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- **[제안]** 요청 전송 후에는 버튼 자리를 ‘다시 분석을 요청하는 중입니다’로 바꿔 반복 제출을 막는다. 중복 방지의 기준은 서버 판정이다(FR1.4 **[요구]**).
- **[제안]** [홈으로]는 이동일 뿐이며, 떠나도 요청이 취소되거나 기록이 삭제된다고 안내하지 않는다. 접수가 확인되면 §4.3의 접수 확인 창을, 거절되면 §4.4를, 응답을 확인할 수 없으면 §4.5를 보여 준다.

### 4.3 재요청 접수 확인 — 접수 확인 창

```text
┌─ A-03 분석 실패·재요청 · 재요청 접수 ──────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│   ╔ 접수 확인 ════════════════════════════════════════════
│   ║ 분석을 다시 요청했습니다.
│   ║
│   ║ [[진행 상태 보기]]   [닫기]
│   ╚══════════════════════════════════════════════════
│
│ (접수 확인 창 뒤는 A-03 화면. 버튼을 누르기 전까지 이동하지 않음)
└────────────────────────────────────────────────────────────────
```

- **[제안]** 재요청 접수가 확인되면 A-03 위에 ‘분석을 다시 요청했습니다’ 접수 확인 창을 띄운다. [진행 상태 보기]를 누르면 **재요청한 분석의 현재 상태를 보여 주는 A-02**(병합된 분석 진행 초안 v0.5)로 이동한다. 접수됐다는 사실만으로 진행 중이라고 단정하지 않으므로, A-02는 조회한 현재 상태(진행 중·완료·실패·상태 조회 실패 등)에 맞는 화면을 보여 준다. **접수 확인만으로 자동 이동하지 않는다.**
- **[제안]** [닫기]는 창만 닫고 A-03에 머문다. 요청을 취소하거나 다시 요청하지 않는다. 닫은 뒤 화면은 §4.3.1을 따른다.
- **[제안]** 재요청 거절(§4.4)·접수 여부 불명(§4.5)에서는 이 접수 확인 창을 띄우지 않는다.
- **[제안]** 이 접수 확인 창은 재요청 접수 안내이며 12월 헤더 알림과 별개다(§3). 10월 헤더의 알림 아이콘은 비활성 표시(클릭 시 안내창, §0)로만 두고 알림 목록·배지·발송 기능은 추가하지 않으며, 접수 확인 창을 닫은 뒤의 안내는 §4.3.1의 A-03 화면 표시로 유지한다. 12월 헤더 알림에 재요청 접수를 포함할지는 12월 요구사항 분석에서 정한다(12월 범위 보완 §2).
- **[미정]** 접수 확인 창의 시각 형태(가운데 대화 상자·A-03 본문 위 안내 등)와 접근성 기준(OQ14), 헤더 알림 자리(#51)와 혼동되지 않게 하는 방식. 재요청 뒤 A-02가 보여 줄 분석이 원래 분석과 같은 식별자인지는 §6. A-02 화면은 분석 진행 초안을 따르며 이 초안에서 다시 설계하지 않는다.

#### 4.3.1 접수 확인 창을 닫은 뒤

```text
┌─ A-03 분석 실패·재요청 · 재요청 접수 후 ───────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석 재요청이 접수되었습니다.
│ ┃
│ ┃ [[진행 상태 보기]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 접수 확인 창을 닫은 뒤에는 §4.1의 실패 안내와 [다시 분석 요청]을 보여 주지 않고, ‘분석 재요청이 접수되었습니다’와 [진행 상태 보기]를 보여 준다. 이미 접수된 재요청을 다시 보낼 수 있는 것처럼 보이지 않게 하려는 표현이다.
- **[제안]** 접수됐다는 사실만으로 ‘진행 중’이라고 단정하지 않는다. 현재 상태를 실제로 조회했다면 그 상태에 맞춰 안내한다. 진행 중·완료로 확인되면 §5.2의 ‘이미 실패 상태가 아님’ 안내(진행 중이면 [진행 상태 보기], 완료면 [결과 확인])를, 다시 실패로 확인되면 §4.1의 실패 확인을 따른다. 조회 중이거나 조회에 실패하면 이 화면의 접수 안내를 유지한다.
- **[미정]** 접수 확인 창을 닫은 뒤 현재 상태를 언제 조회할지(자동 조회 여부·시점)와 조회할 분석 식별자(§6).

### 4.4 재요청 거절

```text
┌─ A-03 분석 실패·재요청 · 재요청 거절 ──────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 지금은 다시 분석을 요청할 수 없습니다.
│ ┃ [예시] 새 분석이 일시 중단되어 있습니다.
│ ┃ 기존 자료와 링크는 유지됩니다.
│ ┃
│ ┃ [[다시 분석 요청]]   (비활성)
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 거절되면 A-03에 머물며 사유를 한 줄로 안내하고, [다시 분석 요청]은 **§4.1과 같은 자리에 비활성으로 남긴다**. 접수 확인 창은 띄우지 않는다. 사유 줄의 문구는 임시 예시다.
- **[제안]** 비활성 버튼은 다시 요청하는 위치를 알려 주기 위한 표시이며, 화면이 스스로 버튼을 다시 활성화하거나 자동으로 재요청하지 않는다.
- **[미정]** 거절 사유의 구분(허용 조건 미충족·신규 분석 중단·선정 조건 변경·접근 불가)과 문구, 비활성 버튼이 **다시 활성화되는 조건·시점**과 그 안내, 활성화 여부를 화면에 반영하는 방식(OQ1·OQ13).

### 4.5 접수 여부 불명

```text
┌─ A-03 분석 실패·재요청 · 접수 여부 불명 ───────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 요청 접수 여부를 확인하지 못했습니다.
│ ┃
│ ┃ [[요청 상태 확인]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 요청 중 응답을 확인할 수 없으면 실패로 단정하거나 다시 제출하지 않고 이 상태로 연결한다. 이 상태에서는 접수 확인 창을 띄우지 않는다. 이 상태에서는 [다시 분석 요청]을 보여 주지 않는다(OQ1 **[결정]**의 자동 재시도 없음과 반복 요청 방지).
- **[제안]** [요청 상태 확인]은 A-03에 머문 채 해당 재요청의 접수·처리 상태를 다시 조회한다. 접수가 확인되면 §4.3의 접수 확인 창을 띄우고(자동 이동 없음), 거절이 확인되면 §4.4, 여전히 불명이면 ‘요청 접수 여부를 확인하지 못했습니다’ 안내를 유지한다. [요청 상태 확인]으로 **실제로 조회하는 동안에만** ‘요청 접수 여부를 확인하고 있습니다’를 보여 준다. 조회 동작은 저장소 선택 초안 §5.1과 같고, 접수 확인 뒤 A-02로 바로 가지 않고 접수 확인 창을 거치는 점만 다르다.
- **[미정]** 응답 확인 불가로 볼 대기 시간·판정 방식(OQ14), 실제 조회 방법(데이터 초안).

## 5. 버튼 동작과 상태

### 5.1 버튼 [제안]

표의 동작·조건은 모두 제안이다. 괄호 안의 [요구]·[결정]은 그 동작이 지키는 근거다.

| 버튼 | 동작·이동 | 조건·주의 |
|---|---|---|
| 다시 분석 요청 | 실패한 분석의 재요청 전송 → 접수 확인 시 A-03에 접수 확인 창 | 서버가 재요청을 허용한 실패 확인 상태에서만 표시([결정] PR #89 Q1 A). 재요청 거절 시 같은 자리에 비활성으로 남기고 사유를 함께 표시하며, 다시 활성화되는 조건·시점은 미정. 사용자가 누를 때만 전송([결정] OQ1). 전송 후 반복 제출 막음([요구] FR1.4). 새 동의 필요([결정] PR #89 Q1 A), 동의 화면 배치는 미정 |
| 요청 상태 확인 | A-03에서 해당 재요청의 접수·처리 상태 재조회 | 접수 여부 불명일 때만. 접수가 확인되면 접수 확인 창, 거절이면 거절 안내. 새 요청을 만들지 않음. 실제 조회 방법 미정 |
| 상태 다시 불러오기 | 이 분석의 상태만 다시 조회 | 상태 조회 실패일 때. 새 분석·재요청을 발생시키지 않음 |
| 진행 상태 보기 | 해당 분석(재요청한 분석 포함)의 A-02 | 재요청 접수 확인 창과 접수 확인 창을 닫은 뒤의 A-03(§4.3.1)에서, 또는 이미 실패 상태가 아니고 진행 중일 때. 누를 때만 이동하며 접수 확인만으로 자동 이동하지 않음 |
| 닫기 (접수 확인 창) | 창만 닫고 A-03 유지 | 요청을 취소하거나 다시 요청하지 않음. 닫은 뒤 실패 안내·[다시 분석 요청] 대신 ‘분석 재요청이 접수되었습니다’ + [진행 상태 보기](§4.3.1). 현재 상태를 조회했으면 그 상태에 맞춘 안내이며, 접수만으로 ‘진행 중’이라고 단정하지 않음 |
| 결과 확인 | 해당 분석의 결과(자산 영역) | 이미 실패 상태가 아니고 완료됐을 때. 이동만으로 확인·공개 처리하지 않음([요구] FR4.1) |
| 홈으로 | H-01 | 모든 상태에서 유지. 요청 취소·기록 삭제를 안내하지 않음 |
| 로그인으로 이동 | 인증 영역(기본 로그인은 Google OAuth — [팀 합의]) | 세션 만료 시. 복귀 위치는 회원 담당과 확인 |

### 5.2 상태별 표시

## 7. 검토 기준

아래 접수 확인 창·닫은 뒤 표시·거절·접수 불명 기준은 현재 제안의 일관성 점검용이다. 계약 확정 전 구현 승인 조건으로 사용하지 않는다.

- A-02·[내 자산] GitHub 관련 탭에서 A-03으로 들어오는 경로와, 실패 안내 → 사용자 재요청 → 접수 확인 창 → [진행 상태 보기]로 A-02 이동 흐름이 드러난다. 홈에서 A-03으로 바로 가는 경로가 남아 있지 않다(PR #44 팀장 결정).
- 재요청 접수가 확인되면 A-03에 접수 확인 창을 띄우고, [진행 상태 보기]를 누를 때만 A-02로 이동하며 접수 확인만으로 자동 이동하지 않는다.
- 재요청 접수 확인 창이 12월 헤더 알림(분석 완료·실패 안내, 알림 자리 #51)과 구분되고, 10월에 알림 목록·배지·발송 기능을 추가하는 안으로 읽히지 않는다(헤더 알림 아이콘은 §0의 비활성 표시만).
- 접수 확인 창의 [닫기]는 요청을 취소하거나 다시 요청하지 않는다. 닫은 뒤에는 실패 안내·[다시 분석 요청] 대신 ‘분석 재요청이 접수되었습니다’와 [진행 상태 보기]를 보이고, 접수 사실만으로 ‘진행 중’이라고 단정하지 않는다.
- 재요청 거절·접수 여부 불명에서는 접수 확인 창을 띄우지 않는다. 거절 시 [다시 분석 요청]이 같은 자리에 비활성으로 남아 사유와 함께 보이고, 다시 활성화되는 조건·시점은 확정처럼 표현되지 않는다.
- 재요청은 사용자가 [다시 분석 요청]을 누를 때만 보내며, 화면 진입·상태 재조회·요청 상태 확인이 재요청을 만들지 않고 자동 재시도가 없다.
- 실패가 기존 자료·링크 손실로 이어지지 않는다는 안내가 있고, 카드 중복 방지는 화면 문구가 아닌 서버 판정 요구로 남는다.
- 요청 중·재요청 거절·접수 여부 불명·상태 조회 실패가 구분되고, 접수 불명에서 다시 제출할 수 없다.
- 실패 유형별 문구·재요청 불가 사유 문구·재요청 진입 경로·동의 화면 배치가 확정처럼 표현되지 않는다. 재요청 허용 조건과 새 동의 필요는 PR #89 Q1 A 결정을 따르고, 화면은 서버의 허용 판정을 따른다. 일부 실패의 결과 제공은 PR #68 Q3 결정을 따르되 판단 정보 계약은 미정으로 표시되고, 부분 결과 열람 가능과 재요청 허용이 섞이지 않는다. 유효한 동의가 분석 실행의 필수 조건이라는 요구·새 동의 필요 결정과, 동의 확인 방법·화면에서 받을 정보가 미정이라는 점이 구분된다.
- 접수 확인 창의 [진행 상태 보기]가 A-02의 진행 중 화면으로 고정되지 않고 재요청한 분석의 현재 상태를 보여 주는 A-02로 연결된다.
- 접수 여부 불명은 ‘요청 접수 여부를 확인하지 못했습니다’로 표시하고, ‘확인하고 있습니다’는 실제로 조회하는 동안에만 쓴다.
- [다시 분석 요청]이 12월의 Catch 설명 재생성(FR3.6)이나 미지원 분류 안내(FR1.3)로 읽히지 않는다.
- 모든 배치·문구·예시가 제안 또는 가상 예시로 구분된다.

이 기준은 팀 검토용 체크 항목이며 제품 동작의 테스트 통과나 팀 승인 완료를 뜻하지 않는다. 원본 요구사항·AI-DLC 공식 기록은 이 초안에 맞춰 변경하지 않는다.
