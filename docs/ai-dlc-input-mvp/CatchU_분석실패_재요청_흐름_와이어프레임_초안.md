> 지위: 팀 검토용 초안 v0.4 (2026-09-15). 이슈 #50의 산출물이며 팀원 1이 조율하는 AI-DLC에 전달할 참고 입력이다. 공식 요구사항·설계·승인 기록이 아니다.

표시 구분:

- **[결정]** MVP 입력에 명시된 팀장 결정.
- **[팀 합의]** 후속 입력에 팀장 확인으로 기록된 팀 합의.
- **[팀장 리뷰]** PR 리뷰에서 팀장이 진행 방향을 정한 사항. 후속 입력에 기록되기 전이며 공식 승인이 아니다.
- **[제안]** 요구·결정을 화면에서 표현하는 방식이나 문서에 없는 동작. 배치·이동·문구·버튼이 여기에 속한다.
- **[미정]** 합의가 필요한 정책·연결 조건.

화면 ID(H-01, A-01~A-03)는 초안 안의 식별자이며 공식 ID가 아니다. URL 경로·API 계약·상태 값 이름은 정하지 않는다.

## 2. 관련 요구사항과 화면 표현

| 근거 | 지켜야 할 행동 | 이 화면의 표현 |
|---|---|---|
| FR1.4, NFR4 | **[요구]** 분석 실패 시 기존 자료·링크를 보존하고 사용자의 재요청을 지원한다. 같은 저장소의 진행 중 중복 요청과 재요청에 따른 카드 중복 생성을 막는다 | **[제안]** 실패 안내에 ‘기존 자료와 링크는 유지됩니다’를 두고, 재요청은 [다시 분석 요청] 버튼으로만 실행한다. 요청 중 반복 제출을 화면에서도 막되, 진행 중 중복과 카드 중복 방지의 기준은 서버 판정이다. 화면에 ‘카드가 중복되지 않습니다’ 같은 보장 문구는 두지 않는다 |
| MVP 입력 OQ1 | **[결정]** 분석 실패 시 실패 사실과 재요청 버튼을 제공하고, 사용자가 다시 요청할 때 재시도한다. 자동 재시도는 하지 않는다. 재요청으로 같은 작업의 카드가 중복 저장되지 않게 한다 | **[제안]** A-03에 [다시 분석 요청]을 주 버튼으로 둔다. 화면을 열거나 상태를 다시 불러와도 분석을 다시 요청하지 않고, 접수 여부가 불명확해도 자동으로 다시 제출하지 않는다 |
| MVP 입력 OQ1 | **[제안]** 진행 중 요청의 중복 방지와 실패 후 재요청의 카드 중복 방지를 별도로 설계한다. 식별 기준·부분 성공 결과 처리·재분석 버전 정책은 설계에서 정한다 | **[미정]** 재요청을 같은 분석으로 볼지 새 분석으로 볼지, 부분 성공 결과를 재사용할지는 화면에서 정하지 않는다(§6) |
| FR1.1, C4 | **[요구]** 구직자의 해당 저장소 분석 동의가 선행 조건이며 동의가 없으면 분석하지 않는다 | **[미정]** 재요청 때 동의를 다시 받는지. 이번 와이어프레임에는 동의 단계를 그리지 않고 연결 질문으로 남긴다(OQ11, #24, §6) |
| FR10.4 | **[요구]** 운영자가 신규 분석을 중단하면 새 분석이 시작되지 않고 기존 자료 열람은 유지된다 | **[제안]** 중단 중 재요청이 거절되면 사유를 안내하고 기존 자료 경로는 유지한다. **[미정]** 재요청이 신규 분석 중단의 대상인지와 그 안내(OQ13) |
| 후속 입력 팀장 확인 (2026-09-15) | **[팀 합의]** 실패한 분석을 다시 찾는 곳은 [내 자산] 안의 GitHub 관련 탭이며, 각 항목에서 실패 안내(A-03)로 이동한다. 탭 이름·배치·내부 화면은 자산 담당의 화면 제안이다 | [내 자산] GitHub 관련 탭의 실패 항목을 A-03 진입 경로로 둔다. 탭 쪽 표현은 자산 담당 영역이다 |

## 3. 진입 경로와 사용자 흐름 [제안]

```text
진입
  ├─ [H-01] 최근 분석 상자(실패)의 [실패 내용 보기] → A-03
  ├─ [A-02] 실패 상태의 [실패 내용 보기] → A-03
  └─ [내 자산] GitHub 관련 탭의 실패 항목 → A-03   [팀 합의]
  (A-01에서 실패 이력 저장소를 다시 고르는 경로는 미정, #23)

[A-03 분석 실패·재요청]  (실패한 분석의 식별자로 상태 조회)
  ├─ 상태 조회 중 → ‘분석 상태를 불러오는 중입니다’
  ├─ 상태 조회 실패 → 조회 실패 안내 + [상태 다시 불러오기]
  ├─ 분석을 찾을 수 없음·본인 분석 아님 → 안내 + [홈으로]
  ├─ 이미 실패 상태가 아님(다른 곳에서 재요청됨 등)
  │    → 현재 상태 안내 + [진행 상태 보기] 또는 [결과 확인]
  │
  └─ 실패 확인 → 실패 안내 + 기존 자료·링크 유지 안내
       └─ 사용자가 [다시 분석 요청] 선택
            ├─ (동의 재확인 여부는 미정 — 이번 흐름에 그리지 않음)
            ├─ 요청 중 → 반복 제출 차단
            ├─ 접수 확인 → A-03에 ‘분석을 다시 요청했습니다’ 알림창
            │    ├─ [진행 상태 보기] → A-02 (누를 때만 이동)
            │    └─ [닫기] → 알림만 닫고 A-03 유지 (요청 취소·재요청 없음)
            │         → 실패 안내·[다시 분석 요청] 대신
            │           ‘분석 재요청이 접수되었습니다’ + [진행 상태 보기]
            │           (현재 상태를 조회했으면 그 상태에 맞춰 안내)
            │    (접수 확인만으로 자동 이동하지 않음)
            ├─ 같은 분석의 재요청이 이미 진행 중
            │    → 알림창 없이 현재 상태 안내 + [진행 상태 보기]
            ├─ 거절(허용 조건 미충족·신규 분석 중단·선정 조건 변경)
            │    → 알림창 없음. 사유 안내 + [다시 분석 요청] 비활성
            │      (A-03 유지, 기존 자료 경로 유지, 다시 활성화 조건 미정)
            └─ 접수 여부 불명 → 알림창 없음. [요청 상태 확인]
                 ├─ 접수 확인 → 알림창(위와 같음)
                 ├─ 거절 확인 → 거절 안내
                 └─ 여전히 불명 → 접수 불명 안내 유지
                 (자동 재제출 없음)

어느 상태에서든 [홈으로] 또는 상단 메뉴로 이동 가능
```

- **[결정]** 자동 재시도는 하지 않는다. **[제안]** 재요청은 사용자가 [다시 분석 요청]을 누를 때만 보낸다. 화면 진입, [상태 다시 불러오기], [요청 상태 확인]은 새 분석이나 재요청을 만들지 않는다.
- **[제안]** 접수가 확인되면 A-03에 ‘분석을 다시 요청했습니다’ 알림창을 띄운다. 알림창의 [진행 상태 보기]를 누르면 재요청한 분석의 현재 상태를 보여 주는 A-02로 이동하며, 접수 확인만으로 자동 이동하지 않는다. A-02는 PR #42 초안의 화면을 따르며 이 초안에서 다시 설계하지 않는다.
- **[제안]** 재요청이 거절되거나 접수 여부가 불명확하면 알림창을 띄우지 않고 해당 안내(§4.4·§4.5)를 유지한다.
- **[제안]** 요청 전송 후에는 [다시 분석 요청]을 ‘다시 분석을 요청하는 중입니다’로 바꾸고 반복 제출을 막는다. 화면을 떠나도 요청이 취소되거나 기록이 삭제된다고 안내하지 않는다.
- **[미정]** 재요청 뒤 A-02가 보여 줄 분석이 원래 분석과 같은 식별자인지 새 식별자인지(§6).

## 4. PC 와이어프레임 [제안]

표기는 홈·A-02 초안과 같다. 굵은 선 상자(┏ ┃ ┗)는 강조 영역, `[[버튼]]`은 주 버튼, `[버튼]`은 보조 버튼이다. `[예시]`는 임시 표시값이며 실제 선정 저장소·처리 결과가 아니다. 화면의 배치·문구·버튼은 모두 제안이다.

**설계 주석 — 그리지 않은 정책 [미정]:** 실패 유형별 사유 문구, 재요청 허용 조건(횟수·대기·실패 유형), 재요청 전 동의 재확인은 정해지지 않아 화면에 그리지 않았다. 동의 재확인이 필요하다고 정해지면 [다시 분석 요청] 전에 A-01의 저장소별 동의 안내와 같은 영역을 둘지 검토하고, 허용 조건이 정해지면 실패 안내 아래에 조건 안내를 추가한다(§6).

### 4.1 실패 안내 — 재요청 전

```text
┌─ A-03 분석 실패·재요청 · 실패 안내 ────────────────────────────
│ CatchU      [홈]   [내 자산]   [대표 구성]   [공유 링크]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석에 실패했습니다.
│ ┃ 기존 자료와 링크는 유지됩니다.
│ ┃ 원하면 이 저장소의 분석을 다시 요청할 수 있습니다.
│ ┃
│ ┃ [[다시 분석 요청]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[요구]** 실패가 기존 자료·링크 손실로 이어지지 않는다(FR1.4·NFR4). **[제안]** 그 사실을 실패 안내에 한 줄로 보여 준다.
- **[제안]** [다시 분석 요청]만 주 버튼으로 둔다. 자동 재시도나 ‘몇 초 뒤 다시 시도’ 같은 표시는 두지 않는다(OQ1 **[결정]**).
- **[미정]** 실패 사유를 사용자에게 어떤 구분으로 보여 줄지(OQ1). 사유 줄은 구분이 정해진 뒤 안내 아래에 추가한다.

### 4.2 요청 중 — 응답을 기다리는 중

```text
┌─ A-03 분석 실패·재요청 · 요청 중 ──────────────────────────────
│ CatchU      [홈]   [내 자산]   [대표 구성]   [공유 링크]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석에 실패했습니다.
│ ┃ 기존 자료와 링크는 유지됩니다.
│ ┃
│ ┃ 다시 분석을 요청하는 중입니다.
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 요청 전송 후에는 버튼 자리를 ‘다시 분석을 요청하는 중입니다’로 바꿔 반복 제출을 막는다. 중복 방지의 기준은 서버 판정이다(FR1.4 **[요구]**).
- **[제안]** [홈으로]는 이동일 뿐이며, 떠나도 요청이 취소되거나 기록이 삭제된다고 안내하지 않는다. 접수가 확인되면 §4.3의 알림창을, 거절되면 §4.4를, 응답을 확인할 수 없으면 §4.5를 보여 준다.

### 4.3 재요청 접수 확인 — 알림창

```text
┌─ A-03 분석 실패·재요청 · 재요청 접수 ──────────────────────────
│ CatchU      [홈]   [내 자산]   [대표 구성]   [공유 링크]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│   ╔ 알림 ════════════════════════════════════════════
│   ║ 분석을 다시 요청했습니다.
│   ║
│   ║ [[진행 상태 보기]]   [닫기]
│   ╚══════════════════════════════════════════════════
│
│ (알림창 뒤는 A-03 화면. 버튼을 누르기 전까지 이동하지 않음)
└────────────────────────────────────────────────────────────────
```

- **[제안]** 재요청 접수가 확인되면 A-03 위에 ‘분석을 다시 요청했습니다’ 알림창을 띄운다. [진행 상태 보기]를 누르면 **재요청한 분석의 현재 상태를 보여 주는 A-02**(분석 진행 초안 PR #42 `b827fe0`)로 이동한다. 접수됐다는 사실만으로 진행 중이라고 단정하지 않으므로, A-02는 조회한 현재 상태(진행 중·완료·실패·상태 조회 실패 등)에 맞는 화면을 보여 준다. **접수 확인만으로 자동 이동하지 않는다.**
- **[제안]** [닫기]는 알림만 닫고 A-03에 머문다. 요청을 취소하거나 다시 요청하지 않는다. 닫은 뒤 화면은 §4.3.1을 따른다.
- **[제안]** 재요청 거절(§4.4)·접수 여부 불명(§4.5)에서는 이 알림창을 띄우지 않는다.
- **[미정]** 알림창의 시각 형태(가운데 대화 상자·화면 상단 알림 등)와 접근성 기준(OQ14). 재요청 뒤 A-02가 보여 줄 분석이 원래 분석과 같은 식별자인지는 §6. A-02 화면은 PR #42를 따르며 이 초안에서 다시 설계하지 않는다.

#### 4.3.1 알림을 닫은 뒤

```text
┌─ A-03 분석 실패·재요청 · 재요청 접수 후 ───────────────────────
│ CatchU      [홈]   [내 자산]   [대표 구성]   [공유 링크]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석 재요청이 접수되었습니다.
│ ┃
│ ┃ [[진행 상태 보기]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 알림을 닫은 뒤에는 §4.1의 실패 안내와 [다시 분석 요청]을 보여 주지 않고, ‘분석 재요청이 접수되었습니다’와 [진행 상태 보기]를 보여 준다. 이미 접수된 재요청을 다시 보낼 수 있는 것처럼 보이지 않게 하려는 표현이다.
- **[제안]** 접수됐다는 사실만으로 ‘진행 중’이라고 단정하지 않는다. 현재 상태를 실제로 조회했다면 그 상태에 맞춰 안내한다. 진행 중·완료로 확인되면 §5.2의 ‘이미 실패 상태가 아님’ 안내(진행 중이면 [진행 상태 보기], 완료면 [결과 확인])를, 다시 실패로 확인되면 §4.1의 실패 확인을 따른다. 조회 중이거나 조회에 실패하면 이 화면의 접수 안내를 유지한다.
- **[미정]** 알림을 닫은 뒤 현재 상태를 언제 조회할지(자동 조회 여부·시점)와 조회할 분석 식별자(§6).

### 4.4 재요청 거절

```text
┌─ A-03 분석 실패·재요청 · 재요청 거절 ──────────────────────────
│ CatchU      [홈]   [내 자산]   [대표 구성]   [공유 링크]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 지금은 다시 분석을 요청할 수 없습니다.
│ ┃ [예시] 새 분석이 일시 중단되어 있습니다.
│ ┃ 기존 자료와 링크는 유지됩니다.
│ ┃
│ ┃ [[다시 분석 요청]]   (비활성)
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 거절되면 A-03에 머물며 사유를 한 줄로 안내하고, [다시 분석 요청]은 **§4.1과 같은 자리에 비활성으로 남긴다**. 알림창은 띄우지 않는다. 사유 줄의 문구는 임시 예시다.
- **[제안]** 비활성 버튼은 다시 요청하는 위치를 알려 주기 위한 표시이며, 화면이 스스로 버튼을 다시 활성화하거나 자동으로 재요청하지 않는다.
- **[미정]** 거절 사유의 구분(허용 조건 미충족·신규 분석 중단·선정 조건 변경·접근 불가)과 문구, 비활성 버튼이 **다시 활성화되는 조건·시점**과 그 안내, 활성화 여부를 화면에 반영하는 방식(OQ1·OQ13).

### 4.5 접수 여부 불명

```text
┌─ A-03 분석 실패·재요청 · 접수 여부 불명 ───────────────────────
│ CatchU      [홈]   [내 자산]   [대표 구성]   [공유 링크]
├────────────────────────────────────────────────────────────────
│ 분석 실패·재요청
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 요청 접수 여부를 확인하지 못했습니다.
│ ┃
│ ┃ [[요청 상태 확인]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 요청 중 응답을 확인할 수 없으면 실패로 단정하거나 다시 제출하지 않고 이 상태로 연결한다. 이 상태에서는 알림창을 띄우지 않는다. 이 상태에서는 [다시 분석 요청]을 보여 주지 않는다(OQ1 **[결정]**의 자동 재시도 없음과 반복 요청 방지).
- **[제안]** [요청 상태 확인]은 A-03에 머문 채 해당 재요청의 접수·처리 상태를 다시 조회한다. 접수가 확인되면 §4.3의 알림창을 띄우고(자동 이동 없음), 거절이 확인되면 §4.4, 여전히 불명이면 ‘요청 접수 여부를 확인하지 못했습니다’ 안내를 유지한다. [요청 상태 확인]으로 **실제로 조회하는 동안에만** ‘요청 접수 여부를 확인하고 있습니다’를 보여 준다. 조회 동작은 저장소 선택 초안 §5.1과 같고, 접수 확인 뒤 A-02로 바로 가지 않고 알림창을 거치는 점만 다르다.
- **[미정]** 응답 확인 불가로 볼 대기 시간·판정 방식(OQ14), 실제 조회 방법(데이터 초안).

## 5. 버튼 동작과 상태

### 5.1 버튼 [제안]

표의 동작·조건은 모두 제안이다. 괄호 안의 [요구]·[결정]은 그 동작이 지키는 근거다.

| 버튼 | 동작·이동 | 조건·주의 |
|---|---|---|
| 다시 분석 요청 | 실패한 분석의 재요청 전송 → 접수 확인 시 A-03에 알림창 | 실패 확인 상태에서 활성. 재요청 거절 시 같은 자리에 비활성으로 남기고 사유를 함께 표시하며, 다시 활성화되는 조건·시점은 미정. 사용자가 누를 때만 전송([결정] OQ1). 전송 후 반복 제출 막음([요구] FR1.4). 동의 재확인·허용 조건은 미정 |
| 요청 상태 확인 | A-03에서 해당 재요청의 접수·처리 상태 재조회 | 접수 여부 불명일 때만. 접수가 확인되면 알림창, 거절이면 거절 안내. 새 요청을 만들지 않음. 실제 조회 방법 미정 |
| 상태 다시 불러오기 | 이 분석의 상태만 다시 조회 | 상태 조회 실패일 때. 새 분석·재요청을 발생시키지 않음 |
| 진행 상태 보기 | 해당 분석(재요청한 분석 포함)의 A-02 | 재요청 접수 알림창과 알림을 닫은 뒤의 A-03(§4.3.1)에서, 또는 이미 실패 상태가 아니고 진행 중일 때. 누를 때만 이동하며 접수 확인만으로 자동 이동하지 않음 |
| 닫기 (알림창) | 알림만 닫고 A-03 유지 | 요청을 취소하거나 다시 요청하지 않음. 닫은 뒤 실패 안내·[다시 분석 요청] 대신 ‘분석 재요청이 접수되었습니다’ + [진행 상태 보기](§4.3.1). 현재 상태를 조회했으면 그 상태에 맞춘 안내이며, 접수만으로 ‘진행 중’이라고 단정하지 않음 |
| 결과 확인 | 해당 분석의 결과(자산 영역) | 이미 실패 상태가 아니고 완료됐을 때. 이동만으로 확인·공개 처리하지 않음([요구] FR4.1) |
| 홈으로 | H-01 | 모든 상태에서 유지. 요청 취소·기록 삭제를 안내하지 않음 |
| 로그인으로 이동 | 인증 영역(기본 로그인은 Google OAuth — [팀 합의]) | 세션 만료 시. 복귀 위치는 회원 담당과 확인 |

### 5.2 상태별 표시

| 상황 | 표시·행동 [제안] | 근거·미정 |
|---|---|---|
| 상태 조회 중 | 분석 상태 상자에 ‘분석 상태를 불러오는 중입니다’ | [다시 분석 요청]을 보여 주지 않음 |
| 상태 조회 실패 | ‘분석 상태를 불러오지 못했습니다’ + [상태 다시 불러오기] | 분석 실패와 구분하고 재요청 버튼을 보여 주지 않음. 자동 재조회 미정(OQ14) |
| 분석을 찾을 수 없음·본인 분석 아님 | ‘이 분석을 찾을 수 없습니다’ + [홈으로] | 다른 사용자의 분석 존재 여부를 드러내지 않는 안. 권한·식별 계약 미정 |
| 실패 확인 | §4.1. 실패 안내 + 기존 자료·링크 유지 안내 + [다시 분석 요청] | 기존 자료·링크 보존·사용자 재요청 지원([요구] FR1.4·NFR4), 자동 재시도 없음([결정] OQ1). 실패 유형별 문구 미정 |
| 일부 결과 후 실패 | 실패 확인과 같이 표시하고 부분 결과로 가는 버튼을 붙이지 않음 | 부분 결과 노출·재사용 미정(OQ1) |
| 요청 중 | §4.2. ‘다시 분석을 요청하는 중입니다’, 반복 제출 막음 | 화면 차단은 보조, 서버 판정이 기준([요구] FR1.4). 응답 확인 불가 대기 시간 미정(OQ14) |
| 재요청 접수 확인 | §4.3. A-03에 ‘분석을 다시 요청했습니다’ 알림창 + [진행 상태 보기]·[닫기]. 자동 이동 없음 | [진행 상태 보기]를 누르면 재요청한 분석의 현재 상태를 보여 주는 A-02(PR #42 초안). 접수만으로 진행 중이라고 단정하지 않음. 새 식별자 여부 미정 |
| 재요청 접수 후 알림을 닫음 | §4.3.1. 실패 안내·[다시 분석 요청] 대신 ‘분석 재요청이 접수되었습니다’ + [진행 상태 보기] | [닫기]는 요청 취소·재요청을 하지 않음. 접수 사실만으로 ‘진행 중’이라고 단정하지 않음. 현재 상태를 조회했다면 그 상태의 행(진행 중·완료는 ‘이미 실패 상태가 아님’, 다시 실패는 ‘실패 확인’)을 따르고, 조회 중·조회 실패면 접수 안내 유지. 조회 시점·자동 조회 여부 미정 |
| 같은 분석의 재요청이 이미 진행 중 | 알림창 없이 현재 상태 안내 + [진행 상태 보기]. 자동 이동 없음 | 진행 중 중복 방지([요구] FR1.4). 판정 단위 미정(OQ1) |

| 신규 분석 중단 중 | 재요청이 거절되면 §4.4의 사유 안내와 비활성 버튼 | 새 분석 미시작·기존 열람 유지([요구] FR10.4). 재요청이 중단 대상인지와 미리 알릴지 미정(OQ13) |

## 6. 미정 사항과 연결 확인

아래는 이 초안이 확정하지 않은 항목이다. 한꺼번에 답을 요구하는 질문지가 아니며, 관련 담당과 순서대로 확인한다.

**정하는 곳:** 동의 방식·기록은 #24 공통 준비에서, 재요청 허용 조건·실패 유형·요청 식별과 접수 확인 방법은 팀원 1의 분석 입력·상태·결과 데이터 초안에서, 재요청 진입 경로와 재분석 진입은 #23 결정 항목에서, 신규 분석 중단의 영향은 OQ13 운영 계획(담당 미정)에서 정하는 것으로 본다. 이 초안은 그 결과를 받기 전까지 해당 항목을 제안·미정으로 유지한다.

| 구분 | 미정·확인 사항 | 확인 상대 |
|---|---|---|

**이 화면에 필요한 정보의 의미(API 계약 아님):** 로그인 상태, 실패한 분석의 식별자, 저장소 표시명, 현재 처리 상태(실패·진행 중·완료 등, 구분 미정), 재요청 결과(접수·거절 사유·새 분석으로 이동할 참조), 요청 접수 불명 여부. 실패 사유 구분과 재요청 허용 조건은 미정이라 필수 표시 정보로 두지 않는다. **유효한 분석 동의는 분석 실행의 필수 조건**이다(FR1.1·C4). 다만 재요청 때 동의를 다시 받아야 하는지, 기존 동의의 유효 여부를 무엇으로 확인하는지, 이 화면에서 사용자에게 받을 정보가 무엇인지는 미정이다(OQ11, #24). 원본 diff·Catch 본문·외부 AI 제공자 정보는 표시 데이터에 포함하지 않는다.

## 7. 검토 기준

- 홈·A-02·[내 자산] GitHub 관련 탭에서 A-03으로 들어오는 경로와, 실패 안내 → 사용자 재요청 → 접수 확인 알림창 → [진행 상태 보기]로 A-02 이동 흐름이 드러난다.
- 재요청 접수가 확인되면 A-03에 알림창을 띄우고, [진행 상태 보기]를 누를 때만 A-02로 이동하며 접수 확인만으로 자동 이동하지 않는다.
- 알림창의 [닫기]는 요청을 취소하거나 다시 요청하지 않는다. 닫은 뒤에는 실패 안내·[다시 분석 요청] 대신 ‘분석 재요청이 접수되었습니다’와 [진행 상태 보기]를 보이고, 접수 사실만으로 ‘진행 중’이라고 단정하지 않는다.
- 재요청 거절·접수 여부 불명에서는 알림창을 띄우지 않는다. 거절 시 [다시 분석 요청]이 같은 자리에 비활성으로 남아 사유와 함께 보이고, 다시 활성화되는 조건·시점은 확정처럼 표현되지 않는다.
- 재요청은 사용자가 [다시 분석 요청]을 누를 때만 보내며, 화면 진입·상태 재조회·요청 상태 확인이 재요청을 만들지 않고 자동 재시도가 없다.
- 실패가 기존 자료·링크 손실로 이어지지 않는다는 안내가 있고, 카드 중복 방지는 화면 문구가 아닌 서버 판정 요구로 남는다.
- 요청 중·재요청 거절·접수 여부 불명·상태 조회 실패·신규 분석 중단이 구분되고, 접수 불명에서 다시 제출할 수 없다.
- 동의 재확인·재요청 허용 조건·실패 유형별 문구·부분 성공·재요청 진입 경로가 확정처럼 표현되지 않는다. 유효한 동의가 분석 실행의 필수 조건이라는 요구와, 재동의 필요 여부·확인 방법·화면에서 받을 정보가 미정이라는 점이 구분된다.
- 알림창의 [진행 상태 보기]가 A-02의 진행 중 화면으로 고정되지 않고 재요청한 분석의 현재 상태를 보여 주는 A-02로 연결된다.
- 접수 여부 불명은 ‘요청 접수 여부를 확인하지 못했습니다’로 표시하고, ‘확인하고 있습니다’는 실제로 조회하는 동안에만 쓴다.
- [다시 분석 요청]이 12월의 Catch 설명 재생성(FR3.6)이나 미지원 분류 안내(FR1.3)로 읽히지 않는다.
- 모든 배치·문구·예시가 제안 또는 가상 예시로 구분된다.

이 기준은 팀 검토용 체크 항목이며 제품 동작의 테스트 통과나 팀 승인 완료를 뜻하지 않는다. 원본 요구사항·AI-DLC 공식 기록은 이 초안에 맞춰 변경하지 않는다.
