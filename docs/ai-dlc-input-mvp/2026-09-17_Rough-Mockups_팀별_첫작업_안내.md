## 현재 결정과 이 안내의 경계

사용자가 첫 MVP 범위·후속 범위·우선순위를 `Approve`로 승인했고 공식 절차로 Scope Definition 완료를 기록했다. B 조건부 담당과 C01/C02 등 잔여 제약은 유지한다. 승인 당시 두 문서의 본문에 남은 ‘승인 전’ 표기는 작성 당시 지위이며, 이번 후속 승인 기록과 구분한다. 승인 원문을 소급 수정하지 않는다.

- 기준: [범위 문서](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/scope-definition/scope-document.md), [우선순위 백로그](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/scope-definition/intent-backlog.md), 두 산출물 기준 커밋 `e3d32132818f3756a300574e7d9509a49bab6c66`.
- 현재 단계는 **Rough Mockups의 입력 준비·공동 검토**다. 이 문서는 팀에 전달할 작업 안내이며 `wireframes.md`·`user-flow.md`를 대신하는 공식 화면 산출물이 아니다. 아직 그 산출물을 생성하거나 Rough Mockups를 승인하지 않았다.
- 각 담당자가 자기 초안·시나리오 점검·결함 수정을 맡고 연결 상대와 먼저 검토한다. 공통 세션/팀원 1은 범위·공통 정책·충돌을 조율하며 모든 화면·서버 초안을 대신 작성하지 않는다.
- A~I는 회의 영역, W01·A-01·L01 등은 기존 초안의 식별자다. 공식 AI-DLC 유닛·API·라우트·상태값으로 확정하지 않는다.
- 실제 API 호출·모델 변경·인프라 생성·제품 구현·PR 머지는 허용되지 않았다. C01/C02는 9/18 현재 제출 접수 후 [수용 검토·예외 변경안](2026-09-17_C02-C01_수용검토_변경안.md)을 준비 중이다. C01 기준 미달·C02 제한적 수용 방향과 별도 미결을 구분하며, 이 안내로 착수 제한을 해제하지 않는다. 최대 3호출은 이미 사용한 호출을 포함하고 새 한도를 부여하지 않는다.

## 2. 공통 제출 규격 — 한 번만 적용

각자 **기존 담당 문서의 다음 판과 차이 메모**를 우선한다. 같은 화면의 사본·새 보고서를 중복 생성하지 않는다. 서버 입력을 담을 기존 문서가 없으면 담당 문서의 `후속 설계 입력` 절 또는 #23의 짧은 댓글 표로 충분하다.

1. 읽은 원문 경로·커밋/PR, 재사용할 절, 이번에 바꿀 절을 적는다. `[확정] / [화면 제안] / [후속 설계 입력] / [미결]`을 구분한다.
2. 화면마다 사용자·진입 → 상태 → 행동 → 다음 화면/복귀를 표시한다. 정상·빈 결과·조회 중·조회 실패·권한/연결 실패를 해당하는 만큼 대조하고 비해당은 이유를 적는다.
3. 화면별 접근성 메모 한 줄: 제목 계층, header/main/nav 등 영역, 키보드 첫 진입·오류/모달 후 초점. 기존 PC 저해상도 수준을 우선 재사용하고 작은 화면의 주요 차이/미결을 표시한다. 새 디자인 시스템·고화질 전면 재작업은 요구하지 않는다.
4. 필요한 정보는 의미·출처·확인 불가 시 표시로 기술한다. 가상 입출력 예시는 ‘실제 실행 결과 아님’으로 표시하고 필드명/API/DB 확정과 구분한다.
5. 각 담당은 자기 정상/예외 흐름을 문서상 따라가 점검하고, 연결 상대의 의견·수정·남은 이견을 남긴다. 문서 시나리오 점검을 제품 테스트 통과로 세지 않는다.
6. 관련 이슈에 **결과물 고정 커밋 링크 + PR + 변경 요지 + 점검 결과 + 상대 의견 + 미결/착수 제한**을 제출한다. 지원자·기한은 합의 전 미정이다.

### 지금: 팀별 입력은 병행, 공식 단계는 공통 세션에서 관리

- 파일 정본은 기존 `docs/ai-dlc-input-mvp/` 담당 초안이다. 서버 질문은 같은 문서의 별도 절 또는 #23 댓글에 연결한다. 미병합 자료도 커밋 고정 링크·지위가 있으면 검토 입력으로 읽을 수 있다. 읽었다고 병합/수용/공식 완료로 세지 않는다.
- 다른 팀원이 쓰는 브랜치/워크트리를 함께 수정하지 않는다. 기존 담당 브랜치는 본인 작업을 유지하고, 새 담당은 최신 dev에서 `docs/<담당영역>-rough-input` 같은 별도 브랜치/워크트리를 사용한다. #58의 승인 범위와 안내는 dev에 병합됐으며, 추가 자료는 해당 PR의 고정 링크로 읽는다. 다른 작업 브랜치 전체를 임의 병합하거나 공통 상태를 복사·편집하지 않는다.
- 제출 순서: **담당 초안 → 연결 상대의 문서 검토/의견 → 해당 이슈+PR 고정 링크 → 공통 세션 검토**. 각자 끝난 영역부터 제출할 수 있고 모든 팀의 전체 설계 완료를 기다리지 않는다. 이견·상대 답변 미수신은 그대로 제출할 수 있다.
- 공통 세션은 최신 Scope와 FR/NFR/C 조건, 진입/복귀의 양쪽 일치, 빈/조회 실패/권한·공개 경계, 후속/G 기능 혼입, 가상 예시와 실제 결과 구분을 검토한다. 수정은 해당 담당에게 반환하며 팀원 1이 대신 전부 수정하지 않는다.
- 팀원 세션은 AI-DLC 상태·승인·감사·도구 소유 DocumentKB를 직접 수정하지 않는다. 지금의 팀 입력을 `--single` 실행이나 공식 유닛 완료로 대신 기록하지 않는다. 공통 현재 intent의 단계 포인터는 이 세션에서 관리한다.

### 공식 Rough Mockups 산출물 작성 전

설치된 2.8.1의 `rough-mockups`는 기존 의도·범위·백로그 읽기 → 화면/흐름/기기·접근성 등 질문·답변 대조 → **작성 전 통합 요약 Looks correct 확인** → `wireframes.md`/`user-flow.md` 작성 → 지정된 독립 검토 → 회고 → 별도 단계 승인 순서다. 각 팀 초안은 이 과정의 입력이지 자동으로 단계 완료가 아니다.

공통 정본 위치: `aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/rough-mockups/`. 기존 파일 경로·채택/수정/보류 절을 연결해 재사용하고, 새 완성 디자인을 한 벌 더 만들지 않는다. 브랜드/기기/세부 접근성 중 기존 답변으로 해결되지 않는 내용만 필요 시 1~2개씩 확인한다. 이번 안내로 작성 전 확인이나 공식 승인을 건너뛰지 않는다.
