## 0. 10월 공통 헤더 적용

**[팀원 2·3 합의 — 2026-09-22 기록]** [10월 헤더 합의 #55](https://github.com/JminAILab/CatchU/issues/55)·[사용자 메뉴 동작 합의 #51](https://github.com/JminAILab/CatchU/issues/51)를 적용한다. 팀원 3이 두 사람의 안건 A~H 답변이 동일함을 확인해 기록한 범위다. API·시각 디자인·구현 승인과 구분한다.

| 화면·상태 | 10월 헤더 구성·동작 |
|---|---|
| 로그인 일반 서비스·발행자 | 왼쪽 로고 → 내 자산 → 공유 링크 → 채용공고(비활성 표시·클릭 시 안내창), 오른쪽 알림(비활성 표시·클릭 시 안내창) → 프로필. 로고는 로그인 홈, 내 자산은 자산 영역, 공유 링크는 L03으로 이동 |
| 비로그인 일반 홈 | 왼쪽 로고, 오른쪽 Google로 시작하기. 로고는 비로그인 홈, 헤더·본문 시작 버튼은 같은 로그인 흐름으로 연결 |
| 수신자 V01~V03, 로그인·비로그인 공통 | 이동 없는 브랜드만 표시. 로그인·프로필·관리 메뉴 없음. V03 본문의 같은 링크 V02 목록 복귀 버튼 유지 |

10월에는 채용공고·알림을 **비활성 표시(클릭 시 안내창)**로 두고 대표 구성 진입점(내 자산 내부 포함)은 숨긴다. **[결정]** 두 메뉴를 클릭하면 현재 화면 위 작은 안내창에 ‘개발 중인 기능입니다’와 [확인]을 표시하고, [확인]은 안내창만 닫고 기존 화면을 유지한다. 별도 페이지로 이동하지 않으며 10월에는 알림 목록·배지·설정 기능을 제공하지 않는다. 비활성은 기능 미제공을 뜻하며 클릭 불가가 아니다. **[미정]** 안내창의 추가 닫기 조작(X·Esc·바깥 클릭). 근거: [#55 9/23 제안](https://github.com/JminAILab/CatchU/issues/55#issuecomment-5788084856)·[합의](https://github.com/JminAILab/CatchU/issues/55#issuecomment-5788108788). 최초 프로필 입력의 저장 조건을 우회하는 메뉴 진입을 새로 허용하지 않는다. 12월 수신자 회원 연결·알림 설정은 후속 논의다.

로그인 일반 서비스의 프로필 버튼 근처에 **모달**을 열고 **프로필 보기 / 로그아웃**을 둔다. 프로필 보기 → 상세 프로필 → 수정 → 저장 성공·취소 후 상세 프로필로 돌아온다. 변경이 있는 취소·이동·로그아웃은 이탈 확인을 거치며, 머무르기를 선택하면 화면과 입력을 유지한다. 로그아웃은 최초 입력 W02를 포함해 성공 시 **비로그인 홈(H-01)**으로 이동하고, 실패 시 현재 화면·입력을 유지하며 완료로 표시하지 않는다. 모달 닫기 조작의 조합과 로그아웃 실패 안내의 구체 문구는 후속 검토다.

이 반영은 공통 헤더·프로필 연결만 다룬다. 분석 요청·동의·접수 불명·재요청 및 #64의 화면 단위 경계는 기존 기준을 유지한다. 화면 이동·로그아웃을 분석 취소·완료로 해석하지 않는다.

표시 구분:

- **[요구]** 승인 요구사항이 정한 행동. 화면이 어떤 방식으로 구현하든 지켜야 한다.
- **[결정]** MVP 입력에 명시된 팀장 결정.
- **[팀 합의]** 후속 입력에 팀장 확인으로 기록된 팀 합의.
- **[팀장 리뷰]** PR 리뷰에서 팀장이 진행 방향을 정한 사항. 후속 입력에 기록되기 전이며 공식 승인이 아니다.
- **[제안]** 요구·결정을 화면에서 표현하는 방식이나 문서에 없는 동작. 배치·이동·문구·버튼이 여기에 속한다.
- **[미정]** 합의가 필요한 정책·연결 조건.

화면 ID(H-01, A-01~A-03)는 초안 안의 식별자이며 공식 ID가 아니다. URL 경로·API 계약·상태 값 이름은 정하지 않는다.

## 2. 관련 요구사항과 화면 표현

| 근거 | 지켜야 할 행동 | 이 화면의 표현 |
|---|---|---|
| FR1.4, NFR4 | **[요구]** 진행·실패 상태를 표시한다. 실패 시 기존 자료·링크를 보존하고 사용자의 재요청을 지원한다. 같은 저장소의 진행 중 중복 요청과 재요청에 따른 카드 중복 생성을 막는다 | **[제안]** 한 분석의 현재 상태를 보여 주는 화면으로 두고, 이 화면에는 새 분석 요청 버튼을 두지 않는다. 실패 시 기존 자료·링크 유지 안내와 [실패 내용 보기] → A-03을 보여 준다 |
| MVP 입력 OQ1 | **[결정]** 실패 시 사용자가 다시 요청할 때만 재시도하고 자동 재시도는 하지 않는다 | **[제안]** A-02에는 재요청 실행 버튼을 두지 않고 A-03의 명시적 버튼에서 실행한다. 상태 조회를 다시 해도 분석을 다시 요청하지 않는다 |
| FR2.2, FR4.1 | **[요구]** 경험 후보·근거·질문과 Catch 설명 초안을 제공하되 확인과 공개 선택을 분리한다 | **[제안]** 완료 시 [결과 확인]으로 해당 결과에 연결하고, 완료를 ‘확인 완료’나 ‘공개 완료’로 표시하지 않는다 |
| FR10.4 (10월 제외) | G 신규 분석·AI 호출 전체 중단과 전용 상태 표시는 첫 MVP 제외 | 현재 상태 조회·자료 보호는 유지. 운영 중단 영향(OQ13)은 후속 검토로 보존 |
| OQ14 | **[미정]** 허용 대기 시간·실패 판정 시간 | 진행률·남은 시간·단계별 소요 시간을 표시하지 않는다. 오래 걸릴 때의 안내 기준도 정하지 않는다(§6) |
| PR #68 사용자 답변 Q2·Q3 | **[결정]** 오류 없이 분석했지만 등록 기준에 맞는 후보가 없으면 정상 완료·새 Catch 없음. 부분 실패는 실패 영향과 분리해 등록 기준 충족을 확인한 후보만 제공하고 일부 실패도 안내한다. 오류·조회 실패를 0건으로, 일부 실패를 전체 성공으로 표시하지 않는다 | **[제안]** 0건은 완료 안내만 두고 [결과 확인]을 붙이지 않는다. 서비스 등록·본인 열람 준비가 확인된 Catch가 있을 때 ‘일부 실패·열람 가능한 결과 있음’(화면 표시명, 서버 상태값 아님)으로 주 버튼 [결과 확인]과 보조 행동 [실패 내용 보기]를 둔다(§4.2·§5.2). 열람 준비가 확인되지 않으면 결과 버튼을 두지 않는다. **[미정]** 열람 준비를 확인할 조회 정보·버튼 활성 계약(#23 Q6), B 결과 화면 연결, 재요청 허용 조건(#23 Q5). 부분 결과 열람 가능 여부만으로 재요청을 허용하지 않는다 |
| 후속 입력 팀장 확인 | **[팀 합의]** 기본 로그인은 Google OAuth, GitHub 연결 없이 홈 진입 허용 | 이 화면은 로그인한 사용자가 자신의 분석을 보는 화면이다. 로그인 후 복귀는 회원 담당과 연결 확인 |
| 후속 입력 팀장 확인 (2026-09-15, PR #46 병합) | **[팀 합의]** 진행 중·완료·실패한 분석을 다시 찾는 곳은 [내 자산] 안의 GitHub 관련 탭이다. A-02는 ‘이 화면을 떠나도 내 자산의 GitHub 탭에서 다시 열 수 있다’고 안내할 수 있으며, 떠날 때 분석이 취소되거나 계속된다고 단정하지 않는다 | 진행 중 화면에 재확인 안내 두 줄을 둔다(§4.1). 탭 이름·배치·표시 정보·내부 화면은 자산 담당 영역. 탭 목록 데이터는 분석 데이터 초안, 사용자당 동시 분석 수·재분석 진입 경로는 #23 결정 항목으로 미정 |

## 3. 진입 경로와 사용자 흐름 [제안]

```text
진입
  ├─ [A-01] 분석 요청 접수 확인 → A-02
  ├─ [A-01] 진행 중 저장소의 [진행 상태 보기] → A-02
  ├─ [내 자산] GitHub 관련 탭의 분석 항목 → A-02
  └─ [A-03] 재요청 접수 확인 창 또는 닫은 뒤의
       [진행 상태 보기] 클릭 → 재요청한 분석의 A-02 (PR #52 제안)

[A-02 분석 진행]  (한 분석의 식별자로 상태 조회)
  ├─ 상태 조회 중 → ‘분석 상태를 불러오는 중입니다’
  ├─ 상태 조회 실패 → 조회 실패 안내 + [상태 다시 불러오기]
  │    (분석 실패로 표시하지 않음)
  ├─ 분석을 찾을 수 없음·본인 분석 아님 → 안내 + [내 자산 GitHub 탭으로]
  │
  ├─ 진행 중 → 진행 중 안내 + [상태 다시 불러오기]
  │    └─ 주기적 상태 조회 적용 [팀 합의]. 조회 간격·실패 후 재개 조건은 미정(§4.1)
  │
  ├─ 완료·결과 있음 → 완료 안내 + [결과 확인] → 해당 결과(자산 영역)
  │    (이동만으로 확인·공개 처리하지 않음)
  ├─ 완료·검토할 Catch 없음(오류 없는 완료로 확인되고 등록 대상 0건)
  │    → ‘이번 분석에서 검토할 Catch가 없습니다’ (정상 완료·새 Catch 없음, [결정] PR #68 Q2)
  │
  ├─ 일부 실패·열람 가능한 결과 있음 → 일부 실패 안내 + 주 [결과 확인] + 보조 [실패 내용 보기]
  │    (서비스 등록·본인 열람 준비가 확인된 Catch가 있을 때만 — [결정] PR #68 Q3, 표시명·배치 [제안], 판단 정보 [미정] #23 Q6)
  │    열람 준비 미확인이면 결과 버튼 없이 ‘결과를 확인하는 중’ 안내
  │
  └─ 실패 → 실패 안내 + [실패 내용 보기] → A-03
       (자동 재시도 없음, 기존 자료·링크 유지)

어느 상태에서든 [홈으로] 또는 상단 메뉴로 이동 가능
```

- **[제안]** 완료·실패로 바뀌어도 다른 화면으로 자동 이동하지 않고 A-02에 머물며, 완료면 [결과 확인], 실패면 [실패 내용 보기]를 보여 준다. 사용자가 상태를 확인한 뒤 직접 이동한다. **[팀 합의]** 상태가 바뀐 사실은 주기적 상태 조회로 반영한다(§4.1). **[미정]** 조회 간격·조회 실패 뒤 재개 조건(§6).
- **[제안]** [홈으로]와 상단 메뉴는 모든 상태에서 유지한다. 화면을 떠날 때 분석이 취소되거나 계속된다고 단정하는 안내를 하지 않는다.
- **[팀 합의] 떠난 뒤 다시 찾기 (후속 입력, PR #46 병합):** 화면을 떠난 뒤 같은 분석은 상단 메뉴 [내 자산]의 GitHub 관련 탭에서 다시 연다. 진행 중 화면에 ‘이 화면을 떠나도 내 자산의 GitHub 탭에서 다시 열 수 있습니다’ 안내를 둔다(§4.1). ‘홈에서 다시 확인할 수 있다’는 안내는 두지 않는다. **[미정]** 탭 이름·배치·표시 정보·내부 화면(자산 담당 영역), 탭 목록에 쓰는 분석 상태 데이터(분석 데이터 초안), 사용자당 동시 분석 수와 재분석 진입 경로(#23).
- **[제안]** 이 화면에는 분석 요청 취소 기능을 두지 않는다. 요청 후 취소 가능 여부는 저장소 선택 초안과 같이 미정이다.

## 4. PC 와이어프레임 [제안]

헤더는 [9/16 회의 결정](2026-09-16_meeting-decisions.md)·#55에 맞춰 별도 [홈]·[대표 구성]을 제거했다. 로고는 홈으로 이동한다. 메뉴 배치·프로필 연결·10월 미제공 메뉴 숨김은 §0의 #51·#55 합의를 적용한다.

버튼 표기는 홈 초안과 같다. 이 문서의 굵은 선 상자(┏ ┃ ┗)는 강조 영역, `[[버튼]]`은 주 버튼, `[버튼]`은 보조 버튼이다. `[예시]`는 임시 표시값이며 실제 선정 저장소·처리 결과가 아니다. 화면의 배치·문구·버튼은 모두 제안이다.

**설계 주석 — 진행 단계·진행률·대기 시간 [미정]:** 와이어프레임에는 진행 단계, 진행률, 남은 시간, 요청 시각을 그리지 않았다. 어떤 단계를 사용자에게 보여 줄지, 진행률과 남은 시간을 표시할 근거가 있는지, 허용 대기 시간과 실패 판정 시간은 정해지지 않았다. 정해지면 상태 문구 아래에 추가한다(OQ14, §6).

### 4.1 진행 중

```text
┌─ A-02 분석 진행 · 진행 중 ─────────────────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 진행 상태
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석이 진행 중입니다.
│ ┃ 이 화면을 떠나도 내 자산의 GitHub 탭에서
│ ┃ 다시 열 수 있습니다.
│ ┃
│ ┃ [상태 다시 불러오기]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 진행 중에는 주 버튼을 두지 않고 [상태 다시 불러오기]를 보조 버튼으로 둔다. 이 버튼은 **이 분석의 상태만 다시 조회**하며, 새 분석 요청이나 재요청을 발생시키지 않는다.
- **[팀 합의 기반 안내]** ‘이 화면을 떠나도 내 자산의 GitHub 탭에서 다시 열 수 있습니다’를 진행 중 화면에 둔다(후속 입력의 팀장 확인, PR #46 병합). 떠날 때 분석이 취소되거나 계속된다고 단정하지 않는다. **[제안]** 문구 속 ‘GitHub 탭’은 자산 담당이 정할 탭 이름에 맞춰 바꾼다. ‘홈에서 다시 확인할 수 있다’는 안내는 두지 않는다(§3).
- **[팀 합의]** 진행 중 상태 조회는 첫 MVP에서 **주기적 조회 방식**으로 시작하고, 완료·실패가 확인되면 조회를 멈춘다. 일시적인 조회 오류를 분석 실패로 표시하지 않는다. 근거: [공통 아키텍처 검토초안](CatchU_공통_아키텍처_검토초안.md) §3(PR #70 병합본), 회원·자산 v0.10 §5.5. **[미정]** 조회 간격, 조회 실패 뒤 주기 조회를 다시 시작하는 조건, 화면 이탈·재접속 시 동작. [상태 다시 불러오기]는 조회 실패 시 수동 재조회용으로 유지하는 안이다.

### 4.2 완료

```text
┌─ A-02 분석 진행 · 완료 ────────────────────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 진행 상태
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ [예시] example-org/demo-repo-a
│ ┃ 분석이 완료되었습니다. 결과와 근거를 확인해 주세요.
│ ┃ 결과 확인과 공개 선택은 별도입니다.
│ ┃
│ ┃ [[결과 확인]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** [결과 확인]은 이 분석의 결과로 연결한다. 이동만으로 확인·공개 상태를 바꾸지 않는다(FR4.1 **[요구]**). 결과 화면의 내부 설계는 자산 담당 영역이다. 여는 화면은 §6의 기존 이슈 링크으로 남긴다.
- **[제안]** A-02의 ‘분석 완료’는 분석 처리가 끝났다는 상태이며 사용자의 확인 완료·공개 완료와 구분한다. A-02에는 검토 현황을 표시하지 않는다. **[팀장 결정, PR #44]** 홈도 결과 단위 집계를 쓰지 않으며 Catch별 검토 상태는 내 자산에서 확인한다.
- **[미정]** 생성된 경험 후보·Catch 수를 보여 줄지(근거 데이터 합의 전 표시하지 않음). **[결정]** 오류 없이 분석했지만 등록 기준에 맞는 후보가 없음이 확인된 0건은 정상 완료·새 Catch 없음이며(PR #68 Q2) 안내는 §5.2를 따른다. 수집·생성·반영·조회 오류를 0건으로 표시하지 않는다.
- **[결정 — 결과 진입 조건] 일부 실패·열람 가능한 결과 있음:** 완료 상자와 같은 틀을 쓰되 제목·안내를 ‘일부 분석이 실패했습니다. 확인할 수 있는 결과가 있습니다’로 구분하고 ‘분석이 완료되었습니다’ 문구는 쓰지 않는다. 주 버튼 [결과 확인], 보조 행동 [실패 내용 보기] → A-03(사용자 선택으로만, 자동 이동 없음). 서비스 등록·본인 열람 준비가 확인된 Catch가 있을 때만 [결과 확인]을 두며 후보 존재·F 처리 종료·결과 전달만으로 활성화하지 않는다([결정] PR #68 Q3). 열람 준비가 확인되지 않으면 결과 버튼 없이 ‘결과를 확인하는 중’ 안내를 둔다. 표시명·버튼 배치는 D 담당의 화면 제안이며 서버 상태값이 아니다. 부분 결과 열람 가능 여부는 재요청 허용 조건과 별개다(#23 Q5). **[미정]** 열람 준비를 확인할 조회 정보·버튼 활성 계약(#23 Q6), B 결과 화면 연결. 별도 와이어프레임은 그리지 않는다.

```text
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** A-02에는 재요청 실행 버튼을 두지 않고 [실패 내용 보기] → A-03에서 명시적으로 재요청한다. 자동 재시도는 하지 않는다(OQ1 **[결정]**).
- **[제안·미결]** A-03을 따로 그린 비교안은 유지하되 탭 안/별도 화면은 #64에서 정한다. 상세는 A-03 초안을 재사용하고 접수 확인 창 또는 닫은 뒤의 [진행 상태 보기]로 연결한다.
- **[미정]** 실패 유형별 문구, 재요청 전 확인 절차, 실패 확정·반영 복구 판정, 재요청 시 이미 제공된 결과의 처리(#23 Q5·Q6). 일부 실패의 결과 제공 자체는 §4.2 ‘일부 실패·열람 가능한 결과 있음’을 따른다([결정] PR #68 Q3).

### 4.4 상태 조회 실패

```text
┌─ A-02 분석 진행 · 상태 조회 실패 ──────────────────────────────
│ [CatchU 로고] [내 자산] [공유 링크] (채용공고) (알림) [프로필]
├────────────────────────────────────────────────────────────────
│ 분석 진행 상태
│
│ ┏ 분석 상태 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ ┃ 분석 상태를 불러오지 못했습니다.
│ ┃ 분석이 실패했다는 뜻은 아닙니다.
│ ┃ 잠시 후 다시 불러와 주세요.
│ ┃
│ ┃ [[상태 다시 불러오기]]
│ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│
│ [홈으로]
└────────────────────────────────────────────────────────────────
```

- **[제안]** 조회 실패는 분석 실패와 구분해 [실패 내용 보기]·재요청 안내를 보여 주지 않는다. 저장소 이름을 확인할 수 없으면 표시하지 않는다. [상태 다시 불러오기]는 4.1과 같이 이 분석의 상태만 다시 조회하며 새 분석·재요청을 발생시키지 않는다.
- **[팀 합의]** 주기적 상태 조회(§4.1, PR #70). **[미정]** 조회 간격과 조회 실패 뒤 재개 조건(OQ14).

## 5. 버튼 동작과 상태

### 5.1 버튼 [제안]

표의 동작·조건은 모두 제안이다. 괄호 안의 [요구]·[결정]은 그 동작이 지키는 근거다.

| 버튼 | 동작·이동 | 조건·주의 |
|---|---|---|
| 상태 다시 불러오기 | 이 분석의 상태만 다시 조회 | 진행 중·상태 조회 실패일 때 표시. 새 분석 요청·재요청을 발생시키지 않음([결정] OQ1, [요구] FR1.4). 주기적 조회(§4.1)와 별개로 조회 실패 시 수동 재조회용으로 유지하는 안 |
| 결과 확인 | 이 분석의 결과로 연결(자산 영역) | 완료·결과 있음, 또는 일부 실패·열람 가능한 결과 있음(서비스 등록·본인 열람 준비 확인)일 때만. 이동만으로 확인·공개 처리하지 않음([요구] FR4.1). 목적지 세부는 자산 담당과 확인 |
| 실패 내용 보기 | 이 분석의 A-03 | 실패·일부 실패일 때. 재요청은 A-03에서 실행. 자동 재시도 없음([결정] OQ1) |
| 홈으로 | H-01 | 모든 상태에서 유지. 분석을 취소하거나 기록을 삭제한다고 안내하지 않음. 떠난 뒤 같은 분석은 [내 자산]의 GitHub 관련 탭에서 다시 연다([팀 합의], 후속 입력·PR #46 병합). 탭 내부는 자산 담당 영역 |
| 로그인으로 이동 | 인증 영역(기본 로그인은 Google OAuth — [팀 합의]) | 세션 만료 시. 복귀 위치는 회원 담당과 확인 |

### 5.2 상태별 표시

| 상황 | 표시·행동 [제안] | 근거·미정 |
|---|---|---|
| 상태 조회 중 | 분석 상태 상자에 ‘분석 상태를 불러오는 중입니다’ | ‘진행 중’과 구분 |
| 상태 조회 실패 | §4.4. ‘분석 상태를 불러오지 못했습니다’ + [상태 다시 불러오기] | 분석 실패로 표시하지 않음. 주기적 조회는 팀 합의(§4.1, PR #70), 실패 뒤 재개 조건은 미정(OQ14) |
| 분석을 찾을 수 없음·본인 분석 아님 | ‘이 분석을 찾을 수 없습니다’ + [내 자산 GitHub 탭으로] | 다른 사용자의 분석 존재 여부를 드러내지 않는 안. 복귀 목적지는 회원·자산 v0.10 §5.1과 일치([#23 Q1·Q2](https://github.com/JminAILab/CatchU/issues/23)). 권한·식별 계약 미정 |
| 진행 중 | §4.1. 진행 중 안내 + 내 자산 GitHub 탭 재확인 안내 + [상태 다시 불러오기] | 진행 표시([요구] FR1.4). 단계·진행률·남은 시간 표시 미정(OQ14) |
| 진행이 오래 지속됨 | **이번 초안에서 별도 안내를 그리지 않음** | ‘오래 걸린다’고 볼 기준과 안내·실패 판정 미정(OQ14) |
| 신규 분석 중단 중 진행 중인 분석 (10월 제외·후속) | 첫 MVP 전용 상태로 그리지 않음. 일반 현재 상태 조회는 유지 | G 운영 중단 영향·재개 안내(OQ13)는 후속 검토 |
| 완료·결과 있음 | §4.2. A-02에 머물며 완료 안내 + [결과 확인] | 자동 공개 없음([요구] FR2.2·FR4.1). 자동 이동하지 않는 안. 분석 완료는 사용자의 검토 현황(일부·전체 검토)이 아니며 A-02에 검토 현황을 표시하지 않음 |
| 완료·검토할 Catch 없음 | 정상 조회로 검토할 Catch가 0장이면 분석 상태 상자에 ‘이번 분석에서 검토할 Catch가 없습니다’ + [홈으로]. 별도 와이어프레임은 그리지 않음 | PR #42 팀장 리뷰 때 홈 v0.5와 맞춘 안내 제안 유지. 현행 홈에는 0건 안내·집계가 없음. 결과의 대상 Catch 수를 정상 조회한 경우만이며, 조회 실패·집계 대기는 0장으로 보지 않음. 전체 검토로 표시하지 않고 [결과 확인]을 붙이지 않음. **[결정]** 오류 없이 분석했지만 등록 기준에 맞는 후보가 없음이 확인되면 정상 완료·새 Catch 없음(PR #68 Q2). 수집·생성·반영·조회 오류를 0건으로 바꾸지 않음. 사용자 역량 부족으로 표현하지 않음 |
| 실패 | §4.3. A-02에 머물며 실패 안내 + [실패 내용 보기]. 자동 이동하지 않는 안 | 기존 자료·링크 보존·사용자 재요청 지원([요구] FR1.4·NFR4), 자동 재시도 없음([결정] OQ1) |
| 일부 실패·열람 가능한 결과 있음 | §4.2. 일부 실패 안내 + 주 [결과 확인] + 보조 [실패 내용 보기]. 서비스 등록·본인 열람 준비가 확인된 Catch가 있을 때만. 전체 성공 안내와 구분 | **[결정]** 실패 영향과 분리한 적합 후보만 제공, 일부 실패 안내, 전체 성공 표시 없음(PR #68 Q3). 등록·본인 열람 준비 확인 후 결과 진입은 **[결정]**(팀장 승인 리뷰). 표시명·배치는 **[제안]**. 판단 정보·버튼 활성 계약 **[미정]** #23 Q6. 재요청 허용 조건은 별개(#23 Q5) |
| 일부 실패·열람 준비 미확인 | 실패 안내 + ‘결과를 확인하는 중’ 안내 + [실패 내용 보기]. 결과 버튼 없음 | 후보 존재·F 처리 종료만으로 열람 가능으로 보지 않음([결정] PR #68 Q3). 반영 대기·복구 판정은 **[미정]** #23 Q6. 조회 실패와 구분. 확인 가능한 후보가 없으면 ‘실패’ 행 |
| 로그인 세션 만료 | 본인 정보 표시 중지 + [로그인으로 이동] | 복귀 위치는 회원 담당과 확인 |

## 7. 검토 기준

- A-01 요청 접수·[진행 상태 보기], 내 자산 GitHub 관련 탭, A-03 접수 확인 창 뒤의 [진행 상태 보기]에서 이 화면으로 오는 경로가 드러난다. 홈의 특정 분석 진입은 제거되며 이동이 새 분석·재요청을 만들지 않는다.
- 진행 중·완료·실패·상태 조회 실패가 구분되고, 조회 실패가 분석 실패로 표현되지 않는다.
- 완료가 확인 완료·공개 완료로 표현되지 않고, [결과 확인] 이동만으로 확인·공개가 처리되지 않는다.
- ‘분석 완료’가 사용자의 검토 현황(일부·전체 검토)으로 표현되지 않고, 결과 0건이 전체 검토로 표현되지 않는다. 오류 없이 정상 조회로 검토할 Catch가 0장인 경우에만 A-02의 0건 안내를 쓰고, 일부 실패는 서비스 등록·본인 열람 준비된 결과가 있을 때만 [결과 확인]을 붙이며 전체 성공으로 표현되지 않는다(PR #68 Q2·Q3). 0건 / 일부 실패·열람 가능 / 열람 준비 미확인 / 조회 실패가 섞이지 않고, 부분 결과 열람과 재요청 허용이 섞이지 않는다. 판단 정보 계약은 확정처럼 표현되지 않는다.
- 실패가 기존 자료·링크 손실이나 자동 재시도로 이어지지 않고, 재요청은 A-03의 명시적 행동으로 남는다.
- A-03의 독립 화면 그림을 확정 배치로 읽지 않으며 #64의 탭 안/별도 화면·진입·복귀 미결이 표시된다.
- 진행 단계·진행률·남은 시간·대기 시간·조회 간격·재개 조건이 확정처럼 표현되지 않는다.
- 화면을 떠날 때 분석 취소나 계속을 단정하지 않고, 떠난 뒤에는 [내 자산]의 GitHub 관련 탭에서 다시 열 수 있다는 팀 합의 안내만 두며 탭 이름·내부 화면·동시 분석 수·재분석 진입을 확정처럼 표현하지 않는다.
- 완료·실패 후 A-02에 머물며 다음 행동 버튼을 제공하고, [상태 다시 불러오기]가 새 분석·재요청을 발생시키지 않는다.
- 모든 배치·문구·예시가 제안 또는 가상 예시로 구분된다.

이 기준은 팀 검토용 체크 항목이며 제품 동작의 테스트 통과나 팀 승인 완료를 뜻하지 않는다. 원본 요구사항·AI-DLC 공식 기록은 이 초안에 맞춰 변경하지 않는다.
