# 팀장 확인 (2026-10-08): Catch의 기여 표시·숫자·제목·나누기

기록일: 2026-10-08 (2026-10-09 보완: 「한 분석 안의 LLM 재호출」 추가, 「Catch 제목」의 '제목만 null일 때', 「커밋이 250개 넘는 PR」의 보류. 아래 「변경 기록」)
출처: 2026-10-08·09 팀장과의 대화(별도 회의 기록 없음). #118(후보 판정) 구현을 다른 AI 도구(Codex)로 따로 검토한 결과와 Catch의 뜻을 다시 검토한 내용을 바탕으로 했다. 그 검토 결과는 저장소에 남기지 않았고, 이 문서에 필요한 내용을 풀어 적었다.
지위: **팀장 결정 입력.** [#118](https://github.com/JminAILab/CatchU/issues/118) 커밋 전에 팀장이 정했다. 승인 요구사항과 이전 단계의 승인 기록은 소급 수정하지 않는다. 계약(API 명세·ERD)과 worker 설계(규칙·기능 설계)의 변경은 AI-DLC로 별도 PR에 반영한다(아래 「AI-DLC로 반영할 것」). 화면 배치·문구의 세부는 각 담당의 개발 이슈에서 정한다.

## 한눈에 보기

- Catch의 본인 기여는 **연동 계정이 커밋 작성자로 기록된 변경**이다. 직접 썼다는 증명이 아니다.
- 수신자에게도 나가는 제목·작업 사실·나의 기여에 **CatchU가 센 숫자를 쓰지 않는다.**
- Catch 제목은 **#120이 근거로 확인할 수 있는 조각(대상·종류·동작)으로만** 만들고, 없으면 null이다. 9/24 「팀장 확인」의 제목 항목 가운데 사실 범위와 실패 때의 값을 대체한다.
- 이슈 조회가 없는 10월 요청에서는 한 PR이나 병합 안의 커밋이 서로 다른 `#번호`를 가리킨다는 **것만으로는 나누지 않는다.** 작성자가 묶은 경계를 따른다.
- 커밋이 250개 넘는 PR의 확인 경로는 작업 동일성 기준을 구현에 맞게 고친다.
- 한 분석 안의 LLM 재호출을 '추가 호출 금지'에서 **뺀다**(2026-10-09). 허용은 건별로 정하며, 이번에 허용하는 것은 제목 형식 고쳐 쓰기뿐이다. GitHub 조회 재시도, 분석 전체 재실행, 결과 재전달은 계속 막는다.

## 본인 기여의 뜻

- Catch의 본인 기여는 연동 계정이 커밋 작성자로 기록된 변경(기록상 명의)이다. 사람이 직접 썼는지, 도구가 썼는지, 누가 판단했는지는 뜻하지 않는다. worker가 만드는 문장에서는 '작성한'이 아니라 '작성자로 기록된'으로 쓴다.
- PR을 연 것만으로는 기여로 보지 않는다. [수집 통제 문서](../CatchU_collection_control_scope.md)의 인계 표는 본인 기여를 '작성자가 이 계정인 커밋·PR'로 적었다. 이보다 좁힌 #118의 선택을 팀장 결정으로 받아들이고, 그 표도 커밋만으로 고쳤다.
- 회원의 기여 확인 체크는 '근거에 나온 내 계정의 커밋이 내 작업 기록이 맞다'를 확인하는 것이다. 아니면 확인하지 않고 불일치 표시를 하거나 미공개로 둔다.
- GitHub가 squash 병합으로 새로 만든 커밋의 작성자는 그 안 변경의 명의로 보지 않는다. PR의 원래 커밋 목록을 확인했으면 원래 커밋의 작성자로 판단하고, 확인하지 못했으면 근거 부족으로 센다. 다만 조회 오류나 수집 상한 때문에 목록을 받지 못했으면 근거 부족이 아니라 수집 실패로 기록한다(작업 동일성 기준의 C17과 「#118이 지킬 것」 5번). 지금 #118 구현과 다르며 #118 PR에서 고친다.
- 지금 수집기는 회원이 연 PR만 커밋 목록을 받는다([worker README](../../worker/README.md)). 그래서 회원이 다른 사람이 연 PR에 커밋했고 그 PR이 squash·rebase로 병합됐으면 회원의 원래 커밋을 찾지 못해 Catch에서 빠질 수 있다([합성 사례 문서](../CatchU_work_identity_cases.md)의 한계 L14). 다른 사람이 연 PR도 커밋 목록을 받을지는 #118을 고칠 때 호출 예산과 함께 정한다(2026-10-09).

## 수신자에게 나가는 숫자와 근거 순서

- 제목·작업 사실·나의 기여에 CatchU가 센 숫자(몇 건 중 몇 건, 줄 수 합계, 본인 커밋 수)를 쓰지 않는다. 근거 한계 문장에 든 본인 커밋 수도 '20건을 넘어'·'일부'처럼 숫자 없이 쓴다. 근거: [P3 설계노트](../P3_설계노트_v2_0.md) 설계 제약 4·5(「비율이 아니라 구분이다」, 「GitHub 활동량 자체를 지표로 쓰지 않음」).
- 다른 계정 커밋이 섞였는지는 숫자 없는 문장(있다·없다·알 수 없다)으로 알린다. 문장의 주어는 '연동 계정이 작성자로 기록되지 않은 커밋'이다. 범위는 PR 단위면 그 PR 커밋 목록 전체, PR 없이 합친 병합이면 그 병합이 들인 커밋 전체다. '없다'는 목록을 끝까지 받았을 때만 쓴다.
- 근거 칸의 원본 숫자(그 커밋의 파일·줄 수, PR 커밋 수)는 상세에 남긴다. 링크를 열기 전에 작은 수정과 대량 생성을 가를 단서이기 때문이다. 수신자 목록 화면에는 개수를 두지 않는 배치를 [#152](https://github.com/JminAILab/CatchU/issues/152)에 제안한다.
- 근거는 worker가 보낸 순서대로 보인다. PR·병합 단위는 그 PR·병합 근거가 먼저 오고, 그다음 본인 커밋이 최근 것부터 온다. 커밋 묶음은 본인 커밋이 최근 것부터 온다. 저장한 순서를 지키는 수정은 B가 한다([#165 요청](https://github.com/JminAILab/CatchU/issues/165#issuecomment-6055244028)).

## Catch 제목

9/24 「팀장 확인」의 Catch 제목 항목 가운데 'workFacts(작업 사실)에 없는 사실을 넣지 않는다'는 아래 조각 규칙과 확인 기준으로, '생성에 실패하면 workFacts 첫 항목으로 채워 항상 값이 있게 한다'는 null로 대체한다. Catch마다 제목을 두는 것, 짧은 명사구로 쓰고 CatchU가 평가하는 말을 덧붙이지 않는 것(대상 이름 안의 낱말은 거르지 않는 한계는 아래 「형식」), 구직자가 고칠 수 없는 것, 본인 화면과 수신자 화면이 같은 제목을 쓰는 것은 유지한다.

- **값:** 제목은 [#120](https://github.com/JminAILab/CatchU/issues/120)이 설명 초안과 같은 생성에서 만든다. 아래 조각을 모두 확인한 것만 쓰고, 없으면 null이다. 10월과 12월을 나누지 않는다. #118은 제목을 만들지 않는다.
- **확인할 수 있는 조각으로만 만든다:** 제목은 대상·종류·동작 세 조각으로만 이루어지고 그 밖의 낱말을 넣지 않는다. 모델은 대상과 그 대상이 기대는 줄을 지목한다. 종류와 동작은 코드가 정하고, 제목 글자도 코드가 조각을 이어 만든다.
  - 대상: 지목한 줄에 있는 코드 이름이나 변경 파일 이름을 원문 그대로 쓴다.
  - 종류: 대상 파일의 위치로 코드가 정한다(시험·문서·설정·코드). 위치를 가르는 규칙은 #120에서 정한다.
  - 동작: 바뀐 모양으로 코드가 정한다(추가·삭제·수정·이름 변경). 대상이 파일 이름이면 GitHub가 표시한 파일 상태(추가·삭제·수정·이름 변경)를 따른다. 대상이 코드 이름이면 추가 줄에만 있을 때 추가, 삭제 줄에만 있을 때 삭제, 둘 다에 있을 때 수정이다.
  - 예: 「`loginRateLimit` 코드 추가」, 「`install.md` 문서 수정」(백틱은 이 문서의 표기이고 제목 글자가 아니다). 정확한 글자 모양은 #120에서 정한다.
  - 이유: '로그인 세션 자동 복구' 같은 일반 낱말은 근거에 있는지 기계로 확인할 수 없다. [보안 점검](../CatchU_security_checks.md)은 생성 문장의 사실이 근거에 있는지 대조하고 근거에 없는 사실은 확정하지 말라고 정한다. 그래서 모든 조각을 확인할 수 있는 모양만 쓴다. 문장형 제목은 12월 설계로 넘긴다.
- **확인 기준:** 근거가 가리키는 연동 계정 커밋의 추가·삭제 줄과 변경 파일(경로·상태)이다. 바뀌지 않은 문맥 줄, 다른 계정 커밋, PR 본문·커밋 메시지는 쓰지 않는다. 코드는 지목한 줄이 회원 커밋의 추가·삭제 줄인지와 대상이 그 줄이나 변경 파일 경로에 있는지를 확인한다. 어긋나거나, 종류나 동작을 정할 수 없거나(위치 규칙에 없는 경로, GitHub 파일 상태가 위 넷이 아닌 경우), 바뀐 줄(patch)을 받지 못했거나 잘렸으면 null이다.
  - 설명 초안도 같은 확인 기준(근거가 가리키는 연동 계정 커밋의 추가·삭제 줄과 변경 파일(경로·상태))을 쓴다. 2026-10-04 [#120 댓글](https://github.com/JminAILab/CatchU/issues/120#issuecomment-5975855051)은 생성된 초안·제목의 사실·숫자·파일 경로가 근거로 수집한 값에 있는지 대조하라고 했다. 지금 그 값에는 번호·개수 같은 구조 값만 있어, 대조 대상을 위의 추가·삭제 줄과 변경 파일 경로로 바꾼다.
- **형식:** 공백 포함 40자 이내(제안값, 화면에 붙여 본 뒤 조정)다. 조각 밖의 낱말을 넣지 않으므로 활동량 숫자, 사람을 주어로 세우는 말, 저장소 글을 옮긴 문장은 들어가지 않는다. 다만 대상은 코드 이름·파일 이름을 원문 그대로 쓰므로 그 이름 안의 낱말·기호는 거르지 않는다(한계). 화면은 제목을 일반 글자로만 그린다([보안 점검](../CatchU_security_checks.md)의 화면 출력).
- **고쳐 쓰기:** 40자를 넘는 것처럼 형식을 어기면 모델이 대상을 다시 고르게 해 최대 3회 고친다. 어긴 규칙과 지목할 수 있는 줄만 보내는 작은 호출이고, 고친 조각은 확인을 다시 통과해야 한다. 3회는 형식을 어긴 응답을 고치는 횟수이며, 실패한 호출을 다시 하는 횟수가 아니다. 고쳐 쓰기는 요청당 총 처리 시간 상한([수집 통제 2.3](../CatchU_collection_control_scope.md#23-자원시간-상한), 수치는 #117·#121 실측 뒤 확정) 안에서만 하고, 남은 시간이 모자라면 멈추고 제목을 null로 둔다. 총 처리 시간을 넘기면 결과 전체를 보내지 않기 때문이다. 생성 호출 상한에는 넣지 않는다. 요청 하나의 고쳐 쓰기 호출 수에도 상한을 둔다. 한 커밋을 파일 경로로 나눌 수 있어 후보 수가 조회 개수로 묶이지 않기 때문이다. 상한에 이르면 그 뒤 후보의 제목은 고쳐 쓰지 않고 null로 둔다. 숫자는 #120에서 생성 호출 상한과 함께 정하고, 호출마다 보내는 입력·출력 크기 상한도 생성 호출과 같이 #120에서 정한다([요구사항 NFR5](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/requirements-analysis/requirements.md), [보안 점검](../CatchU_security_checks.md)의 LLM 행). 확인 실패(조각이 근거와 맞지 않음)와 호출 실패(시간 초과·서버 오류 포함)는 다시 하지 않고 null로 둔다. 고쳐 쓰기는 한 분석 안에서 LLM을 다시 부르는 일이므로, 아래 「한 분석 안의 LLM 재호출」의 계약 정정이 병합된 뒤에 구현한다.
- **제목만 null일 때:** 생성 호출(초안·제목을 만드는 LLM 호출 한 번. worker README의 '생성기', 곧 분석 전체 실행과 다르다)은 성공해 초안이 나왔는데 제목만 null이 되면(위 「확인 기준」의 null, 3회 고쳐 써도 형식 위반, 요청당 고쳐 쓰기 상한에 이름, 시간이 모자라 고쳐 쓰기를 멈춤, 고쳐 쓰기 호출 실패) 실패 목록(failures)에 넣지 않고 요청 결과(outcome)도 바꾸지 않는다. 제목 없음은 정해 둔 값이기 때문이다. 건수만 운영 로그에 남겨 [#122](https://github.com/JminAILab/CatchU/issues/122) 검수에서 본다. 생성 호출 자체가 실패하면 지금 계약대로 초안 실패로 처리하고 failures에 넣는다(2026-10-09).
- **품질 제약과의 관계:** 생성 품질 제약 C01(9/17 재검증에서 바뀌지 않은 문맥 줄을 이번 변경으로 잘못 귀속한 결함 때문에 기준 미달로 둔 제약, [제약 목록](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/feasibility/constraint-register.md))을 이 변경 때문에 다시 검토하지 않는다. 확인 기준이 문맥 줄을 빼는 것도 그 결함을 막기 위해서다.
- **모델:** 개발용 모델은 제목 품질을 확인하는 단계에서 팀장이 정한다. 그 전에는 [코딩 절차](../CatchU_coding_procedures.md)대로 가짜 생성기로 개발한다. 실제 회원 자료를 보내기 전에는 서비스 모델과 이용 조건 확인(제약 C06)을 갖춘다.
- **자동 생성 안내:** 회원·수신자 화면에 공통 안내 「제목과 설명은 CatchU가 GitHub 기록에서 자동으로 만들었습니다」를 둔다. 회원 화면에는 사실과 다르면 불일치 표시를 하거나 공개하지 말라는 안내를 덧붙인다. 제목이 있으면 모두 생성된 값이므로 계약에 따로 칸을 두지 않는다.
- 팀장은 실제 서비스를 열 때 DB를 초기화한다고 확인했다([MVP 입력](CatchU_mvp_input.md)의 「자료 초기화 구상」과 같은 방향이며 시점은 미결). 그래서 #120 전에 제목 없이 등록된 Catch는 실제 서비스에 남지 않는 것으로 본다.

## 한 PR·병합 안의 서로 다른 번호

- 이슈 조회가 허용되지 않은 요청(10월 동의 범위 '커밋·PR·diff')에서는, 한 PR이나 PR 없이 합친 병합 안의 본인 커밋 메시지가 PR 번호가 아닌 서로 다른 `#번호`를 둘 이상 가리킨다는 것만으로는 나누지 않는다. 다른 근거로 나누기 세 조건([단위 나누기](../CatchU_work_identity_unit.md))이 확인되면 나눈다. 지금 #118은 10월에 번호 말고 다른 나누기 근거를 쓰지 않아, 이런 단위는 한 후보가 된다.
- 이유: 서로 다른 번호의 변경을 한 PR로 묶은 것도 작성자의 판단이므로 그 경계를 따른다. 커밋 메시지의 번호는 누가 썼는지, 작업 구분인지 이유·출처인지 알 수 없다는 점도 고려했다.
- 그런 단위에는 후보의 묶음 한계 기록(계약 이름 groupingLimitations)에 「본인 커밋이 서로 다른 번호 N개를 가리키지만, 작성자가 한 PR(또는 병합)로 묶은 경계를 따라 한 작업으로 두었다」(N은 가리킨 번호 수)를 남긴다. 이 기록은 화면에 나가지 않는다. #122 검수에서 건수만 보고, 건수에 따라 자동으로 나누기로 바꾸는 기준은 두지 않는다.
- #118 구현 검토는 작업 동일성 기준의 사례 C7(한 PR 안의 두 작업은 Catch 2개)을 근거로, 이슈 조회가 없어도 나눠야 한다고 판정했다. 위 이유로 따르지 않는다. 기준 문서 C7에 10월 범위를 적는다([결정 기록](../CatchU_work_identity_records.md#결정)).

## 커밋이 250개 넘는 PR

[작업 동일성 기준](../CatchU_작업동일성_판별기준.md)의 확인 경로를 구현에 맞게 고친다. 확인 경로·조건과 이유는 [결정 기록](../CatchU_work_identity_records.md#결정)에 둔다. 기준과 구현이 같은 말을 하려면 #118에 판본 확인과 어긋난 비교 결과 버리기가 들어가야 하므로, 이 문서는 #118과 함께 또는 먼저 병합한다.

커밋 목록을 다 받지 못한 PR이 있으면, 그 PR과 겹칠 수 있는 커밋은 'PR 밖'(직접 push·PR 없는 병합)으로 확정하지 않고 보류한다. 그 PR의 일부일 수 있는 커밋을 따로 내면 한 작업이 Catch 둘로 갈리기 때문이다. 판본이 어긋난 경우뿐 아니라 목록을 다 받지 못한 모든 경우(수 어긋남, 비교 결과를 끝까지 못 받음, 포크에서 연 PR, 기준 커밋 모름)에 적용한다(2026-10-09). 보류한 커밋을 세는 방법은 기존 2026-09-30 집계 결정을 따른다([결정 기록](../CatchU_work_identity_records.md#결정)). 겹칠 수 있는 커밋은 PR 상태로 정한다. 목록을 다 받지 못한 PR이 병합되지 않고 닫혔거나 기본 브랜치가 아닌 브랜치를 대상으로 하면, 그 저장소에서 'PR 밖'으로 판정될 본인 커밋(연결 PR 조회가 빈 목록이고 받은 PR 커밋 목록 어디에도 없는 커밋)을 모두 보류한다. 기본 브랜치를 대상으로 한 열린 PR과 병합된 PR이면 보류하지 않는다. 그 PR의 커밋이 기본 브랜치에 들어와 있으면 연결 PR 조회가 그 PR을 돌려주고, 들어와 있지 않으면 기본 브랜치 커밋을 대상으로 하는 'PR 밖' 판정에 들지 않기 때문이다. 남는 드문 경우는 [합성 사례 문서](../CatchU_work_identity_cases.md)의 한계 L13으로 적었다(2026-10-09).

## 한 분석 안의 LLM 재호출

2026-10-09 팀장이 '추가 호출 금지'를 좁혔다. PR #260 자동 리뷰가, 위 제목 고쳐 쓰기가 승인 계약의 '자동 외부 재시도·추가 호출을 허용하지 않는다'([계약 요약](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/contract-design/contract-summary.md)의 공통 오류·요청 안전성)와 부딪힌다고 지적한 뒤의 결정이다.

- **바꾼 것:** 한 분석 안의 LLM 재호출을 '추가 호출 금지'에서 뺀다. 허용은 건별로 정하며, 실제로 허용하는 것은 아래 「이번에 허용하는 것」뿐이다.
- **이 금지가 온 곳:** 요구사항은 자동 재시도 정책을 미정으로 두었다([요구사항 NFR4](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/requirements-analysis/requirements.md)). 요구사항 본문의 '추가 호출 금지를 유지한다'와 실행 허가 표의 '추가 호출 허가 없음'은 실현 가능성 검증(C01·C02)의 실험 호출과 단계 실행 허가에 관한 것으로 읽는다. 금지는 도메인 설계 Q4·Q5에서 팀장이 '자동 재호출이나 추가 호출 허가로 확대하지 마세요', '추가 호출 금지는 유지합니다'라고 답한 것([도메인 설계 질문](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/domain-design/domain-design-questions.md))이 계약과 worker 설계로 이어진 것이다. 이 결정은 NFR4가 열어 둔 정책 가운데 이 한 가지만 정한다.
- **그대로 막는 것:** GitHub 조회 재시도(수집 통제), 분석 전체를 다시 돌리는 것(대기열이 같은 작업을 다시 주는 것. 중복 방지 NFR4, 시도 1회 [#233](https://github.com/JminAILab/CatchU/issues/233), 정체 복구 0회 [#121](https://github.com/JminAILab/CatchU/issues/121)), 결과 재전달.
- **이번에 허용하는 것:** Catch 제목 형식 고쳐 쓰기뿐이다(제목당 최대 3회, 요청당 고쳐 쓰기 호출 상한과 요청당 총 처리 시간 상한 안, 위 「고쳐 쓰기」). 생성 호출이나 고쳐 쓰기 호출이 실패하면(시간 초과·서버 오류 포함) 다시 부르지 않는다. 다른 재호출을 열려면 팀장 결정과 계약 정정이 다시 필요하다.
- **반영:** 아래 「AI-DLC로 반영할 것」의 계약·설계 항목과 [수집 통제 문서](../CatchU_collection_control_scope.md)의 재시도 표. [#120](https://github.com/JminAILab/CatchU/issues/120) 범위의 '실패 후 자동 보완·재생성·모델 대체 정책을 추가하지 않는다'와 완료 기준의 '추가 자동 생성·모델 교체를 발생시키지 않는다'도 이 예외에 맞춰 고치고, 요청당 고쳐 쓰기 호출 상한 숫자를 정하는 일을 더한다.

## AI-DLC로 반영할 것

- 계약: 후보·회원 Catch·수신자 Catch의 `title`을 '필수 칸이되 값 없음 허용'으로 바꾼다. 계약 요약에 '제목이 없으면 null이며 생성된 제목처럼 꾸미지 않는다'와 '근거 목록 순서가 표시 순서'를 적는다. 계약 요약 W 표의 'failures의 수집/생성 오류'에 '초안이 나왔는데 제목만 null인 경우는 failures가 아니다'를 덧붙인다.
- 계약 요약의 재호출 문장: '자동 외부 재시도·추가 호출을 허용하지 않는다'에 예외 한 줄을 둔다. 'worker는 한 분석 안에서 Catch 제목이 형식을 어겼을 때만 제목을 고쳐 쓰려고 LLM을 다시 부를 수 있다. 제목당 최대 3회이고, 요청당 고쳐 쓰기 호출 상한(이슈에서 정함)과 요청당 총 처리 시간 상한 안이며 생성 호출 상한에는 세지 않는다. 요청당 상한에 이르면 그 뒤 제목은 null로 둔다. 생성 호출이나 고쳐 쓰기 호출이 실패하면(시간 초과·서버 오류 포함) 다시 부르지 않는다.' '자동 분석 재시도를 허용하지 않는다'(전이·불변 조건)에는 '한 분석 안의 제목 고쳐 쓰기는 분석 재시도가 아니다'를 덧붙인다.
- ERD: Catch 제목 칸의 빈칸 금지를 푼다.
- [worker 설계 규칙](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/construction/u3-worker/functional-design/rules.md):
  - BR3.2(후보 적합성과 제목 규칙)의 제목 문구와 같은 파일 요약표의 BR3.2 줄을 바꾼다. 제목은 근거가 가리키는 회원 커밋의 추가·삭제 줄과 변경 파일(경로·상태)로 확인되는 조각(대상·종류·동작)으로만 만든다. 모델은 대상과 근거 줄을 지목하고, 종류·동작과 제목 글자는 코드가 정한다. 위반 처리 문장(violation)의 '수집/생성 오류는 failures로 구분'에 '초안이 나왔는데 제목만 null인 경우(확인 실패, 3회 고쳐 써도 형식 위반, 요청당 고쳐 쓰기 상한에 이름, 시간 부족으로 멈춤, 고쳐 쓰기 호출 실패)는 failures에 넣지 않는다'를 덧붙인다. '평가하는 말을 넣지 않음'에는 대상 이름 안의 낱말은 거르지 않는 한계를 덧붙인다. 'workFacts에 없는 사실' 조항과 'workFacts 첫 항목' 대체를 지우고, 생성이나 확인에 실패하면 null로 둔다.
  - BR3.4(초안 실패와 후보 분리)의 '자동 재호출을 추가하지 않음'에 제목 형식 고쳐 쓰기(제목당 최대 3회, 요청당 상한 안, 호출이 실패하면 다시 부르지 않음) 예외를 둔다.
  - BR3.5의 '새 분석 재시도를 수행하지 않음'에 '한 분석 안의 제목 고쳐 쓰기는 분석 재시도가 아니다'를 덧붙인다.
  - [기능 설계](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/construction/u3-worker/functional-design/functional-spec.md)의 R-01·R-02 적용 기록('추가 호출 금지를 유지한다')은 고치지 않고, 같은 파일에 이번 예외를 새 줄로 덧붙인다.
- 요구사항 본문·실행 허가 표의 '추가 호출 금지', 도메인 설계의 '자동 분석·LLM 재호출을 허용하지 않는다'([구성 요소](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/domain-design/components.md)의 실패와 중복, [결정 기록](../../aidlc/spaces/default/intents/260914-catchu-october-mvp/inception/domain-design/decisions.md) ADR-007)와 Q4·Q5 답은 소급 수정하지 않는다. 계약 정정 기록에 이 경우만 좁힌다고 적는다.
