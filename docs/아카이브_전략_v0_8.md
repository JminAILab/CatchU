## 0. 헌법 — 흔들리지 않는 5원칙

> 무게중심이 "취준생 중심"에서 "기업 중심"으로 바뀌어도 이 5개는 그대로다. 코드 중심 전환이 이 중 어느 조항의 근거도 무효화하지 않으며, 오히려 다섯 조항 전부 코드라는 새 영역에서 더 강하게 시험받는다. 새 아이디어는 이 5원칙과 충돌부터 점검하고, 충돌하면 아이디어가 아니라 원칙이 우선한다.

1. **비판정 (D-02)**: 시스템은 판정하지 않는다. 제공하지 않은 정보(증거 없음·동의 없음)가 판정 신호로 변질되는 것을 막는다. 점수·등급·적합도 예측을 내리지 않고 판단 재료(증거 매핑)만 제공한다. 최종 판단은 사람.
   - **코드 적용 (신규)**: "이 코드가 좋다/나쁘다/위험하다"(형용사·시스템이 주어) = 판정 ✗. "당신이 요구한 X에 이 코드가 대응한다"(사실·기업 기준이 주어) = 매핑 ✓. **별표의 주어가 시스템이면 판정, 사람(기업)의 입력 기준이면 매핑.**

2. **일관성 ≠ 진정성 (D-06)**: 커밋·PR·코드도 AI 생성 가능하므로 진정성은 증명 못 한다. 일관성·구체성의 증거까지만 제공하고, 진정성 검증은 면접으로 넘기되 그 면접을 증거 기반으로 날카롭게 만든다.
   - **코드 적용 (신규)**: 코드를 보여줄수록 "본인이 짠 게 맞나"라는 질문이 커지지만, 시스템은 AI 생성 여부를 판별하지 않는다. 코드는 검증 대상이 아니라 면접 질문의 재료다.

3. **동의 기반 접근 (D-13)**: 모든 분석은 취준생 본인 동의에서 시작. 공개 repo라도 임의 분석 불가(공개 ≠ 처리 동의). 분석 대상은 public repo만 — 비공개는 제3자(회사·동료) 자산이 섞여 범위 밖.

4. **데이터 거버넌스**: 최소 수집, 집계·익명 통계만(개인 추적 불가), 벡터 완전 삭제 보장. 타인 발화는 익명화.
   - **코드 적용 (신규)**: 코드 본문을 임베딩·보관하면 수집·보관의 무게가 커진다. "최소 수집"과 "코드 전체를 본다"의 긴장을 인식하고 설계한다.

5. **예측이 아니라 사실 (D-15)**: "무엇을 할 수 있는가"(예측)에 직접 답하지 않고, "무엇을 했는가"(사실) × 렌즈 × 검증으로 분해한다.
   - **코드 적용 (신규)**: "이 코드를 보니 대규모도 할 수 있겠다"는 전형적 전이 예측이라 금지. 코드는 "이렇게 짰다"는 과거 사실까지만.

# 본문 — 상담 이후의 새 시스템

## C1. 정체성 — 기업(면접관) 중심의 단일 평면 ✅ 확정

### 무게중심 이동

이전(v0.7까지): 취준생이 자기 증거(증거카드)를 차려놓고, 기업이 그것을 열람한다.

이후(v0.8): **기업(면접관)이 자기 기준(공고의 요구역량)을 렌즈로 들고 와서, 그 렌즈로 지원자의 주장(자소서·포트폴리오·README)과 증거(코드·구조·기여)를 한 평면에서 꿰뚫어 본다.**

취준생이 프레임을 짜고 기업이 따라가는 게 아니라, 기업이 자기 프레임으로 지원자를 본다. 강사님의 "기업 입장에서 다시 보라"는 피드백의 정체가 이 무게중심 이동이다.

### 핵심 고객 = 기업(면접관)

- 핵심 고객은 기업. 핵심 페르소나는 면접관(→ C2).
- 취준생용 기능(내 자소서가 내 코드로 뒷받침되나 미리 보기 등)은 **같은 엔진의 확장**이지 지금 설계 대상이 아니다. 취준생은 동의·데이터 제공의 주체로는 여전히 1급이지만, 화면 설계의 1순위는 기업이다.

### 단일 평면 (single surface) — 핵심 가치

면접관 지우의 현실: 자소서는 ATS에, 포트폴리오는 PDF·노션에, 코드는 GitHub에 — **세 군데 흩어져** 있다. 5분 전에 이걸 다 열어 머릿속에서 연결하는 비용이 곧 "1분 만에 탭 닫는" 피로다. 이것은 v0.7 2장 Pain Point에 이미 있던 문제다 — "자소서·GitHub·포트폴리오가 분리된 도구로 존재 → 교차 대조에 큰 비용".

**우리의 핵심 가치 = 그 세 평면을 하나로 포개는 것.** 자소서의 "대용량 처리했다"(주장)와 그 코드(증거)가 같은 화면에서 손가락 하나로 연결되면, 면접관은 머릿속 연결 노동을 안 해도 된다. "증거를 꺼내 연결하고 유통시킨다"의 **"연결"이 곧 이 단일 평면**이다.

목표: **이 페이지 안에서 모든 걸 본다. GitHub·자소서·포트폴리오 어디로도 나갈 필요가 없다.**

### 단일 평면의 처리 규칙 — 시스템은 새로 쓰지 않는다

README·자소서·포트폴리오는 셋 다 "주장"이다(D-24 그대로). 셋 다 같은 규칙으로 다룬다:

- **원문 그대로 펼침** — 시스템이 요약·재서술하지 않는다.
- **공고 렌즈로 비춤** — 관련 부분에 하이라이트(색). 원문 위에 얹을 뿐 원문을 안 건든다.
- **증거(코드)로 연결** — 주장 → 대응 코드. (D-24의 '주장을 렌즈로 쓴 질의')
- **하지 않는 것** — 요약·재서술·적합도 판정. (자르고/비추고/연결만)

**요약 기능 제외 (확정).** 자소서의 글의 흐름·말투·강조 순서·밀도 자체가 그 사람의 신호다. 시스템이 요약해 "요지 3개"로 만들면 그 신호를 죽인다 — 억지로 늘린 글과 잘 정리된 글의 차이가 사라진다. 요약 안 함은 게으름이 아니라 **신호 보존**이다. 단, 우리는 "잘 쓴 글" 규범을 강제하지 않는다(그것도 판정이다). 원문을 안 건드려 면접관이 스스로 차이를 읽게 할 뿐이다.

### 헌법 영향

안 흔들림. 3장의 배제절("GitHub에서 중요한 건 코드 자체가 아니라 코드 뒤의 의사결정")의 *"아니라"*만 폐기. 코드 뒤의 판단도, 코드 자체도 둘 다 증거다. 철학을 바꾸는 게 아니라 더 정직하게 적는 것.

## C2. 핵심 페르소나와 진짜 고통 ✅ 확정

### "채용담당자"는 단일 인물이 아니다 — 단계별 분해

| 단계 | 누가 | 코드 읽나 | 도메인 맥락 | 시간 |
|---|---|---|---|---|
| 서류 | 비기술 HR | ✗ | ✗ | 1분 |
| 코딩테스트 | (별도 플랫폼) | — | — | 우리 영역 밖 |
| **기술 면접** | **팀장급 이상 (배치 관점)** | ✓✓ | △ 도메인 일반지식은 있으나 *이 레포*는 백지 | 5분 전~짧음 |
| 최종 | 임원/CEO (기술 판단은 위임) | ✗ | ✗ | 적음 |

**회사 규모별 실제 구성 (관찰):**
- **작은 회사**: 한 면접 자리에 권한 그룹(CEO/CTO) + 미래 팀(팀장/팀원)이 **섞임.** 코드 읽는 깊이가 다른 여러 명이 같은 화면을 동시에 본다.
- **큰 회사**: 단계 분리. 기술 면접 = **같은 직군 팀장급 이상**(가끔 CTO). 임원 면접은 따로.
- **공통분모**: 코드를 보는 사람은 거의 항상 **팀장급 이상**이다. 순수 "또래 동료(나랑 같이 코드 짤 사람)"가 면접관인 경우는 드물다.

### 핵심 페르소나 = 기술 면접관 (지우) — 팀장급, 배치 관점

- **지우**: 팀장급 개발자. 신입~주니어 면접에 기술 면접관으로 투입. 본인 일도 바쁨. 지원자 GitHub를 **면접 5분 전이나 자리에서 처음** 본다.
- **보는 관점 = "배치 관점"**: "이 코드 깨끗한가"(또래 동료 시선)가 아니라 **"이 사람을 우리 팀 어디에 쓸 수 있을까"**(관리자 시선). 역량 배치·성장 가능성 중심. 이 관점이 우리 색B(공고 렌즈)와 정확히 맞물린다 — 팀장은 공고를 쓴 사람이거나 최소한 자기 팀 니즈를 알고 면접에 들어오므로, 렌즈의 주인이 명확하다.
- 지우를 핵심으로 두는 이유: ① 코드를 가장 깊이 보는 사람 ② 배치 관점이라 "이 사람을 어디 쓸까"라는 가장 구체적 관심 ③ **가장 까다로운 사용자를 기준으로 설계하면 얕게 보는 사람(임원·크로스팀)은 같은 재료의 얕은 버전으로 자동 커버**된다. 작은 회사의 "섞인 그룹"도 줌인 동선(깊이를 사용자가 정함)이 흡수 — CEO는 층위1에서 멈추고, 팀원은 코드까지 내려간다.
- 중요: 지우도 도메인 일반지식은 있지만 *지원자의 이 레포*는 처음 본다. "팀장이라 맥락이 있다"는 가정은 틀렸다 — 레포 맥락은 누구에게나 백지다.

### 지우는 챔피언이다 (사용자이자 도입 추천자)

기술 판단을 위임받은 CEO에게 "이 도구 도입하시죠"라고 어필하는 건 지우(팀장급)다. 즉 지우는 **사용자이면서 동시에 구매를 밀어올리는 챔피언**(B2B SaaS). 한 회사에서 지우가 써보고 → CEO에게 어필 → 회사 도입. 단일 면접관에게 강렬한 경험을 주는 것이 회사 단위 도입의 씨앗.

함의: 지우가 "어필할 만한" 구체적 경험을 줘야 한다 — "5분 전에 열었는데 바로 질문거리가 손에 잡혔다." 북극성 사례가 곧 이 어필 포인트.

*(단, 우리 프로젝트 1차 목표는 "외부 인사가 보고 매력을 느끼는 것"이므로 실제 GTM·판매 전략은 MVP 이후. 지금은 "지우가 어필하고 싶을 만큼 좋은 단일 면접 경험"에 집중.)*

### 진짜 고통 = 방향 상실 (놓친 것에 대한 불안이 아니다)

면접관이 5분 전 GitHub를 열고 느끼는 건 "내가 뭘 놓칠까 봐 불안하다"가 아니라 **"어디부터 봐야 할지 모르겠다"**다. 고통은 누락 불안이 아니라 **방향 상실**이다.

따라서 우리는 **위험 탐지기가 아니라 방향 안내자**다. 면접관은 "놓친 걸 잡아주는 도구"를 원하지 않는다 — 자기 전문성을 의심당하기 싫고, 시스템이 "여기 중요/위험"이라 판정하면 결국 자기 눈으로 다시 본다(검색에서 확인: 채용담당자는 자동 분석 숫자에 의존하지 않고 자기 판단을 쓴다). 우리가 줄 것은 **읽기 시작할 발판**이다.

### 코드 질문은 "수요 없음"이 아니라 "비용 때문에 후퇴" — 막힌 수요 해방

관찰: 면접에서 README 기반 질문은 흔하지만, **코드 기반 질문은 드물고 면접 시간이 긴 경우에만** 나온다. 이걸 "코드 질문 수요가 없다"로 읽으면 안 된다.

근거: 코드 리뷰를 직접 하는 면접관들은 그것이 면접에서 **가장 가치 있는 부분**이라고 증언한다 — 함께 일하면 많은 시간을 쓸 일을 미리 해보는 것. 그런데도 "자주 간과된다(overlooked)"고 인정한다. 즉 **좋은 줄 알면서도 비용·번거로움 때문에 빠뜨린다.** "시간이 길 때만 본다"는 것이 곧 비용 문제의 증거 — 수요가 없으면 시간이 길어도 안 본다.

→ 우리의 가치 = 코드 보기의 **진입 비용을 5분→30초로 낮춰**, 지금은 시간 길 때만 일어나는 코드 질문이 평범한 면접에서도 일어나게 하는 것. "기존 수요 충족"이 아니라 **"막힌 수요 해방"**이라 더 가치 있다.

### 북극성 사례

❌ **아님 — abi 보안 취약점 사례**: 좋은 교보재였으나 시스템 목표로는 부적합. ① 너무 어려움(데이터/제어흐름 정적분석 필요) ② 코드 분석이 아니라 도메인 지식 문제(콜그래프를 줘도 비전문가는 위험을 못 봄 — 면접관 전문성에 달림) ③ 본질이 위험 탐지 = 판정이라 우리가 안 되기로 한 것.

✅ **북극성 = "위치·기여·연결만으로 면접관이 질문을 만들 수 있는 사례"** (채팅앱 WebSocket 예시):
> "공고의 '실시간 데이터 처리' 요구에 대응하는 코드: 지원자가 작성한 WebSocket 핸들러(본인 커밋 80%). 이 핸들러는 메시지 큐와 연결되고 재연결 로직을 포함한다. 자소서의 '대용량 동시접속' 주장이 이 부분에 대응."

여기엔 "잘했다/위험하다"가 한 글자도 없다. 위치+기여+연결+주장 매핑뿐. 그런데 면접관은 이걸 받고 질문이 바로 나온다("재연결은 어떤 케이스를 고려했나요?"). **시스템이 위치만 짚어줘도 가치가 난다 = 매핑으로 충분 = 헌법 통과.**

### "무엇을 할 수 있나"의 분해

면접관의 진짜 궁금증("이 친구가 우리 회사에서 뭘 할 수 있나")에 시스템이 직접 답하면 판정이지만, 재료로 분해하면 우리가 제일 잘하는 일:
- 우리가 찾는 것 (공고 요구역량)
- → 이 친구가 비슷한 걸 해봤나 (기여 + 코드)
- → 어떻게 했고 본인이 맞나 (구조 맥락 + 면접 질문)

면접관이 "할 수 있는가"를 스스로 추론하고, 시스템은 그 재료를 5분 만에 쥐여준다. (D-15 그대로)

## C2.5 시장 포지셔닝 — 라이브 세션 흐름과의 관계

> 페르소나(지우의 고통)와 구분되는, 시장에서 우리의 자리.

### 시장 흐름: 기술 면접이 "라이브 세션"으로 이동 중

2026년 기술 면접의 무게중심이 "지원자가 과거에 올린 코드를 본다"에서 **"면접 중에 AI 에이전트와 함께 짜고 그 과정을 리뷰한다"**(Plan/Build/Review)로 옮겨가는 중. 대부분의 코드가 AI 생성이라, 리뷰가 "사람이 결과물이 맞는지 판단하는 마지막 방어선"으로 격상됨.

**이 흐름과 우리 헌법이 같은 방향인 부분**: 시장도 "정적 산출물은 게임 가능하지만 대화로 검증하면 못 속인다"로 가고 있음 — 우리 헌법 2조(진정성은 면접에서)와 동일. 라이브 도구도 "코드 기반으로 면접 질문 자동 생성"·"점수가 아니라 추천, 최종 판단은 사람"·"모든 점수에 출처(citation)" — 우리 D-02/D-19와 일치.

### 위협이자 기회

- **위협(정직하게)**: 라이브로 가면 "과거 GitHub 레포"의 비중이 줄 수 있음. 강사님 협의 때 "왜 라이브가 아니라 과거 레포인가"에 답이 있어야 함.
- **우리 자리 = 라이브의 앞단(보완, 경쟁 아님)**: 라이브 세션은 면접 시간 안에서만 일어나고 사전 준비를 못 도움. 라이브는 "지금 이 자리에서 어떻게 하나"를 보지만 **"이 사람이 그동안 뭘 쌓아왔나"는 못 봄.** 우리는 면접 *전에* 과거 레포로 방향을 잡아주는 자리 — 비어 있는 앞단. (재민 본인의 후회 "기록·증거를 안 남긴 것"이 정확히 라이브가 못 보는 그 영역)

### 확장 방향 (MVP 밖) — 과거 분석 → 라이브 세션 맞춤 설계

과거 GitHub 분석으로 **그 지원자에게 맞춘 라이브 세션 흐름을 설계**하는 방향. 라이브 도구의 약점(모든 지원자가 같은 과제)을 우리 분석 자산으로 보완 — "이 사람 과거에 X를 많이 했으니 라이브에선 그 깊이를 확인하는 과제를." 시장 흐름에 경쟁이 아니라 **재료를 공급**하는 위치.

⚠ 단 헌법 주의: "이 사람 약점은 여기"(약점 판정 = 형용사 = 비판정 위반)가 아니라, "공고 요구역량 중 과거 코드에 증거가 적은 영역은 여기"처럼 렌즈로 풀어야 함. 그리고 이건 코어(면접 전 단일 평면)가 선 다음의 확장 — 지금 깊이 파면 정체성이 "면접 운영 도구"로 번짐(D-21에서 라이브 방송을 자른 정신).

## C3. 증거 구조 — 직교하는 두 축 ✅ 확정 (D-01 재정의)

> **결론: 증거는 두 직교 축이고, 둘 다 MVP의 기둥이다.** 원래 질문("코드는 증거카드의 5번째 유형인가, 별도 클래스인가")은 둘 다 틀린 질문이었다 — 코드는 카드 안에 들어가는 유형도, 카드 옆에 서는 클래스도 아니고, **카드와 다른 축**이다.

### 두 축

- **시간 축 = 증거카드 (D-01 유지, 폐기 아님)** — 커밋·PR·이슈·리뷰의 흐름. **"어떻게 만들어왔나"**(의사결정 흔적). 사건 단위. LLM 텍스트 추출(기존 설계 그대로).
- **공간 축 = 구조 (신규)** — 시스템 구성도·모듈·디렉터리·코드 본문. **"지금 무엇을 어떻게 만들었나"**(관계·배치). 정적분석. abi 같은 구조적 통찰이 사는 곳.

둘은 별개 클래스도 상하관계도 아닌, **한 파일/함수에 걸린 두 면(面)**. 코드 뷰(파일/함수)에서 교차한다.

### 검증 경로 (가설 ㄷ)

처음 가설은 "구조와 사건은 같은 줌 축의 위아래"였으나, 줌인 동선을 구체 예시(블록체인 토큰 전송)로 끝까지 그려 공격한 결과 **반증·수정됨**: 층위1→층위2→코드 본문은 한 줌 축(공간)으로 연속이지만, 커밋내역(카드)은 그 축에 안 실리고 **시간 축에서 직교로 들어온다.** abi 위험이 Token.sol 한 카드 안이 아니라 Token.sol+Access.sol의 **관계(공간 축)**에서 보였던 것이 이를 확증 — 재민의 실제 경험("공간/구조를 보고 알았다")과 일치.

### 둘 다 기둥인 이유 (안전판이 아니다)

하나만 빠져도 다른 프로젝트가 된다:
- **공간축이 빠지면** → "코드 중심" 피드백에 부응 못 함, v0.7로 회귀.
- **시간축이 빠지면** → 신입의 엉망 코드는 구조만 보면 "엉망"으로만 보임. 그 사람이 그 안에서 무슨 고민을 했는지(시간축)가 사라짐. 우리 플랫폼은 신입 중심이라 치명적.

근본 이유: 헌법 5조의 **"무엇을 했나"가 사실 두 얼굴**이었다 — 무엇을 만들었나(공간) × 어떻게 만들어왔나(시간). 둘을 겹쳐야 "이 사람이 이걸 이렇게 만들어냈다"는 온전한 사실이 된다. 하나 빠지면 헌법 5조의 "사실"이 반쪽.

### 한 축이 침묵하면 다른 축이 받친다

- **잘 짠 코드**: 의도가 코드에 녹아 커밋·PR에 안 적힘 → 시간축(카드) 침묵 → **공간축(깔끔한 구조)이 말함.** "좋은 코드는 주석이 필요 없다" 역설의 해소 — 디렉터리 구조 자체가 역량 증거.
- **신입의 엉망 코드**: 구조가 미숙해 공간축 빈약 → **시간축(커밋·PR)이 고민의 흔적을 보여줌.**
- 지우의 행동이 이를 실증: README에 아키텍처 있으면 봄(공간축), 없으면 커밋으로 감(시간축) — 본능적으로 두 축을 오가며 보완.

### 미결 — 각 축의 깊이는 실측으로 닫는다

두 축이 **대등한 기둥**이라는 게 "둘 다 똑같이 깊게 판다"는 뜻은 아니다. 시간축(카드)은 기존 설계라 추가 비용 적음. 공간축(구조)은 정적분석이라 무거우며, **특히 층위3~4(콜그래프·데이터흐름)를 어디까지 파느냐는 지금 책상에서 정할 게 아니라 구현·실측으로 닫을 영역**(인젝션 경계를 측정으로 닫기로 한 것과 같은 종류). C5·토이프로젝트 단계에서 결정.

## C4. 분석 범위 — 프로젝트 repo만 ✅ 확정 (시장 검증 완료)

> **분석 대상 = 프로젝트 repo만.** TIL·알고리즘은 분석하지 않는다.

### 근거 (재민 경험 + 시장 검증 일치)

- **신입도 프로젝트 repo는 무조건 있다**: 공채 축소·중고신입 요구 + 부트캠프/국비/사관학교 모두 팀프로젝트 필수. "프로젝트 없는 신입"이라는 우려 케이스가 현실엔 거의 없음.
- **면접관은 프로젝트만 본다**: 재민의 블로그 방문기록 추적 — 프로젝트 후기엔 방문 많고 TIL은 클릭도 안 함. 시장 확증: 면접관이 GitHub에서 답하려는 질문은 "이 사람이 실제로 뭘 만들 수 있나" 하나로 수렴. 2026 신입 채용 기준은 "튜토리얼 클론이 아니라 실제 배포되어 쓰이는 프로젝트."
- **알고리즘은 코테로 별도 검증** → GitHub에서 안 봄.

### TIL의 가치는 죽은 게 아니라 "곁가지 프로젝트(코드)"로 흡수됨

"AI 시대에 TIL의 의미가 흐려진다"는 직감이 시장과 일치 — 면접관이 보는 "성장·호기심" 신호가 **TIL 문서(글)가 아니라 커리큘럼 너머를 탐색한 곁가지 프로젝트(코드)**로 표현된다. 즉 "배웠다는 기록"보다 "만들어봤다는 증거"가 신호. D-16에서 TIL을 "기록 단위 증거"로 살렸던 가치(학습→적용)가 이제 코드 형태로 더 잘 드러남 → "프로젝트만" 좁혀도 그 신호를 안 잃음.

### TIL·알고리즘을 빼는 이유 — C3 두 축과 정합

TIL은 마크다운 문서, 알고리즘은 단일 파일 풀이라 **공간축(모듈·구조)이 통째로 빔.** C3의 두 축 중 하나가 빈 증거는 우리 구조에 안 맞음. "가치 없어서"가 아니라 ① 코드 중심 정체성 밖 ② 공간축 구조 없음 ③ 면접관이 안 봄.

### 동질화 문제 — "신입 프로젝트는 다 비슷하다"는 반론

이 반론은 우리 존재 이유를 위협하는 듯하나, 뜯어보면 오히려 수요를 증명한다.

- **"비슷하다"는 겉(주제)에만 맞다**: 다 쇼핑몰·배달앱이라도 속(결제를 직접 짰나 라이브러리로 떼웠나, 동시성 고민했나, 커밋을 꾸준히 쌓았나 막판에 몰아쳤나)은 사람마다 다름. **면접관이 "다 비슷하다"고 흥미를 잃는 건 겉만 보고 속을 들여다볼 비용이 없어서** — 우리가 푸는 바로 그 지점(C2 방향상실의 신입 버전).
- **동질화는 "강의 직후 첫 프로젝트"에 집중**: SSAFY 관찰 — 학습 마무리 첫 프로젝트는 95% 동일, 자기주도 팀플로 갈수록 빠르게 흩어짐(이후 70~80%→확실히 다름). 그리고 지원자는 자기를 가장 잘 보여줄 레포를 고르므로(C2 레포 단위 가시성), 동질 프로젝트는 상당 부분 자연 필터링됨.
- **비슷해 보이는 건 지원자 역량/README의 문제지 시스템 문제가 아니다**: 우리는 정직한 거울 — 있는 걸 비추지 없는 차이를 창작하지 않음(D-02). 변별 안 되는 지원자를 변별되게 만드는 건 우리 일이 아님. (단, 그 관찰을 지원자 본인에게 "코칭"으로 돌리는 길은 있음 → D-04, 취준생 페르소나 단계에서)

### 미결 / 이관

- **C5로 이관**: 겉(README 주제)에서 면접관이 흥미 잃기 전에 속(두 축)을 어떻게 들이미느냐. README를 그대로 첫 화면에 띄우는 게 "또 쇼핑몰" 반응을 부를 위험 — 화면 설계 과제.
- **취준생 페르소나 단계로**: 동질화 코칭(D-04 부활) — "흔하다"(판정·기업향) 아닌 "이렇게 하면 더 드러난다"(개선·지원자향).
- **D-23/D-16 보류** (폐기 아님): TIL "기록 단위 증거" 설계는 취준생/확장 단계에서 부활 가능. 클론코딩/강의-따라하기(남의 의사결정을 자기 것처럼)는 두 축이 사실로 비추되(커밋 몰림·구조 동일) 판정 안 함, 진위는 면접에서 — D-23 "기타 fail-safe" 정신.

## C5. 코드 뷰 동선 ⏳ 큰 그림 합의 (표면 디테일 남음)

> **줌인 동선 + 색 두 개 겹침.** C3(증거 단위) 확정 후 종착지가 명확해짐.

### 레이아웃 — 데스크톱/태블릿 가로 우선

면접관은 면접 자리에서 노트북·태블릿으로 본다(코드를 폰으로 보지 않음). 따라서 모바일 퍼스트가 아니라 **가로 넓은 화면 우선**으로 설계해도 정당하다. 이 전제가 "나란히(레이아웃 A)"를 가능하게 한다.

### 첫 화면 = 레이아웃 A (나란히)

README(주장)와 층위1 구조 지도(증거)를 **한 화면에 동시에**. 주장과 증거가 눈을 안 옮기고 대조된다. 탭 구조(README 탭 | 구조 탭)나 위아래(B)는 주장과 증거가 동시에 안 보여 제외 — 면접관이 README만 보고 덮을 위험.

### 줌인 동선

```
[1단계]  README 요약 │ 층위1 시스템 구성도     ← 나란히(A), 주장↔증거 즉시 대조
                          ↓ (구조에서 클릭)
[2단계]  층위2 디렉터리/모듈 구조 (화면 가득)   ← 구조에 집중
                          ↓ (색칠된 데서 클릭)
[3단계]  코드 + 커밋내역 (화면 가득)           ← 증거카드의 자리 (C3 종착지)
```

각 단계에서 다음으로 내려갈지 **면접관이 클릭으로 결정**(깊이를 사용자가 정함). 얕게 보는 면접2는 1단계에서 멈추고, 깊게 보는 지우는 코드까지 내려간다. 같은 화면, 다른 깊이.

### 두 색 겹침

- **색A (기여)** = git blame, 지원자가 짠 곳. **사실** (주어 = git 기록, 시스템 아님). 안 틀림.
- **색B (공고 관련)** = 공고 요구역량 렌즈가 비춘 곳. **사람 기준이 주어** (LLM 매칭이라 틀릴 수 있음 — 색A와 신뢰도 달라 UI 구분 필요할 수 있음).
- **황금 지점 = A∩B** — 이 사람이 직접 짰고(A) + 우리가 찾는 역량과 관련된(B) 곳. 면접 질문이 쏟아지는 자리.

### 구조를 그리는 규칙 — 시스템은 의미로 묶지 않는다

- 구조는 **지원자가 만든 그대로** 비춘다. 디렉터리 구조 자체가 지원자의 의사결정 산물(역량 증거)이므로, 시스템이 `/auth` 폴더를 보고 "auth"라 읽는 건 안전하지만, 흩어진 파일을 "이건 인증 관련이니 묶자"고 의미로 묶으면 시스템의 해석(판정)이다.
- 다이어그램 수준 = 코드에서 **기계 추출한 그대로**(디렉터리·import). LLM이 "이건 MVC 패턴" 식으로 의미 부여하면 틀릴 때 신뢰 붕괴 — 지우는 깊이 보는 사람이라 금방 알아챔. **정확한 날것 > 예쁜 가짜.**

### 아키텍처 층위 정의

- 층위1 (시스템 구성도): 스택·큰 덩어리. 설정 파일(package.json·docker-compose)에서 추출. 가벼움·안전.
- 층위2 (모듈/레이어 구조): 디렉터리·파일명 패턴. 부분적으로 코드 봄.
- 층위3 (호출/의존 관계 — 콜그래프): 정적분석. 무거움. abi 사례가 요구한 층위.
- 층위4 (데이터/제어 흐름): 최상 난이도. 결함 탐지로 미끄러짐 → 헌법 위험.
- → 지우가 5분 안에 원하는 건 **층위1~2**. 층위3~4는 직접 코드 보며/면접에서 확인. 무겁고 위험한 3~4를 안 해도 지우를 만족시킬 수 있음.

### 미결 (실측으로 닫을 디테일)
- README 첫 화면 압축 방식 — 잠정: "첫 단락 + 더보기"(시스템은 자르기만, 새로 안 씀). 면접관 실제 반응으로 확정.

## C6. 외부 공고 제거 ⏳ 방향 수립 (강사님 협의 대상)

> **D-21 크게 흔듦.** 플랫폼 내에서 채용 프로세스가 돌게.

- 기업이 직접 공고를 올리면, A가 외부 기업정보를 작성·관리하던 합병증(D-21의 상당 부분, D-24(마)의 출처별 두 입력)이 통째로 소멸. 구현은 늘지만 **설계는 단순**해짐(우리는 설계 단계라 이득).
- 콜드스타트는 설계가 아니라 **운영으로 분리** — 초기엔 운영자가 공고를 기입. (D-13에서 동의 초대로 콜드스타트 흡수한 것과 같은 논리)
- D-21의 "외부 공고 검증 불가" 문제는 외부 공고가 없으면 문제 자체가 사라짐 → 근거 무효화 확인됨.
- MVP 범위와 직결되므로 강사님 협의 후 정식 확정.

## 기술 무게중심 경고

- 코드를 1급으로 올리면 프로젝트 핵심이 **LLM 텍스트 추출 → 코드 정적분석**으로 이동.
