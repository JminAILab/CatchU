*※ 실제 면접관 인터뷰 전, 프로젝트 기획과 일반적인 채용 프로세스를 기반으로 작성한 1차 가설입니다. 인터뷰를 통해 검증 및 보완할 예정입니다.*

# 1. 대상 정의

| **구분** | **내용** |
|---|---|
| 초기 사용자 | 30~300명 규모 IT 기업의 팀장급 개발자 및 기술 면접관 |
| 확장 대상 | CTO, 채용 담당자, 시니어 개발자 |
| 핵심 질문 | “이 사람을 우리 팀 어디에 배치할 수 있을까?” |

# 2. 프로필

## 김민준 (가명, 36세)

| **직무** | 백엔드 개발팀장(기술 면접관) |
|---|---|
| **개발 경력** | 11년 |
| **팀장 경력** | 3년 |
| **조직 규모** | 직원 30~300명 규모 IT 기업 |
| **면접 경험** | 연간 15~20회 |
| **주요 업무** | 개발, 코드 리뷰, 장애 대응, 팀 운영 |
| **채용 역할** | 기술 면접 진행, 평가 의견 작성, 최종 채용 의사결정 참여 |

**상세 배경**

- 개발과 팀 운영이 본업이며 채용은 부가 업무다.
- 기술 면접 교육을 별도로 받은 경험은 많지 않다.
- 인사 담당자, CTO와 함께 면접에 참여하는 경우가 많다.
- 기술 역량 검증의 책임은 팀장에게 집중된다.
- 지원자 검토는 면접 직전 5~20분 안에 이뤄지는 경우가 많다.

# 3. 목표 (Goal)

**표면적인 목표**

- 좋은 개발자를 채용하는 것

**실질적인 목표**

- 지원자의 실제 역할과 기술 역량을 빠르게 파악한다.
- GitHub 프로젝트 경험을 객관적인 근거로 확인한다.
- 근거 기반의 기술 면접 질문을 준비한다.
- 지원자를 일관된 기준으로 비교한다.
- 우리 조직에 적합한 인재인지 판단한다.

# 5. 핵심 고통 (Pain Point)

## ① 시간 부족

- 개발 업무가 우선이라 면접 준비 시간이 부족하다.
- 지원자 정보를 충분히 검토하기 어렵다.
- 여러 탭을 동시에 열어 자료를 비교해야 한다.
- 면접 직전까지 검토를 마치지 못하는 경우가 많다.

## ② 판단 근거 부족

- GitHub를 열어도 무엇을 봐야 할지 모르겠다.
- 프로젝트에서 실제 수행한 역할을 파악하기 어렵다.
- 문제 해결 과정이 충분히 드러나지 않는다.
- 지원자의 주장과 실제 기록이 연결되지 않는다.

## ③ 역할 맥락 부족

- 프로젝트 규모와 맥락을 이해하기 어렵다.
- 담당 범위와 의사결정 과정을 알기 어렵다.
- 협업 방식과 팀 내 역할을 파악하기 어렵다.
- 조직 적합성을 판단할 근거가 부족하다.

# 7. 필요한 것 (Needs)

- 면접 전에 질문 목록을 빠르게 만들 수 있어야 한다.
- 지원자의 주장과 실제 기록이 연결되어야 한다.
- 평가표 작성에 활용할 근거가 남아야 한다.
- AI는 판단을 대신하는 것이 아니라 판단을 도와야 한다.

# 8. 욕구의 두 칸

## 미래 (To-Be)

**이력서 확인**   →   **AI 분석 결과 확인**   →   **핵심 프로젝트 파악**   →   **맞춤형 질문 생성**   →   **면접 진행**   →   **평가 기록**

- 질문 준비 시간을 줄인다.
- 평가의 일관성을 확보한다.
- 채용 성공 가능성을 높인다.

# 10. 이 페르소나가 아닌 경우
