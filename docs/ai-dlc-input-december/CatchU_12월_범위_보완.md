### 누락 경위

첫 intent의 참고 원문인 [v10 기획 문서](../ai-dlc-input/CatchU_v10_reference.md) 4절 기능 목록에서 "포함"이던 기능 중 일부가 [승인 요구사항](../../aidlc/spaces/default/intents/260909-catchu-definition-review/inception/requirements-analysis/requirements.md)의 12월 항목에 오르지 않았다. 팀장은 이 기능들이 12월 목표였다고 확인했다.

- **팔로우·포스팅·피드·구직자 간 DM:** AI-DLC 시작 설명에 "링크드인이라는 비유만으로 소셜 기능 전체를 추가하지 않는다"는 기준이 들어갔다. 이 문장이 의도 정리와 범위 정의를 거쳐 요구사항의 "제품 범위 밖·자동 확대 금지"로 이어졌고, 네 기능을 12월 항목으로 따로 묻는 질문이 없어 제외처럼 굳었다.
- **알림·MCP·채용공고 등:** 입력 문서 [범위와 이용 흐름](../ai-dlc-input/CatchU_scope_and_journeys.md) 3절은 "과금·공고·MCP 등 기존 항목은 필요한 흐름에 연결해 우선순위를 검토한다. 생략만으로 폐기하지 않는다"고 넘겼다. 첫 intent의 범위·요구사항 기록에서는 이 항목들이 다뤄지지 않았다.

9/15에 판단한 대상은 v10 4절에서 "포함"이면서 첫 intent 기록에 없던 항목이다. 키워드 대조로 찾았으므로 다른 표현으로 들어간 항목은 빠졌을 수 있다. 10월 MVP intent가 첫 MVP 밖으로 둔 기능은 §6에 파트별로 대조했다.

**MCP를 검증에도 쓴다([9/24]):** 화면 흐름은 코딩 에이전트가 브라우저 자동화 MCP(예: Playwright MCP)로 조작해 E2E로 검사하고, 기능은 CatchU MCP 서버를 검사 통로로도 써서 끝까지 검사한다. 제품 기능이 아니라 개발·검증 방식이며, 요구사항 분석에서 검증 방식으로 다룬다.

**우선순위:** 팀장이 밝힌 순서는 대표 구성(1순위)과 운영 기능(후순위, 가능하면 포함) 두 가지다. 나머지 항목의 순서는 요구사항 분석에서 정한다. 순서를 밝히지 않은 항목을 후순위로 해석하지 않는다.

**마일리지 조건**

- 현금으로 사거나 현금·재화로 바꾸는 기능을 두지 않는다.
- 직접 링크 열람은 차감 대상이 아니다. 요구사항은 직접 GitHub 근거 열람을 기업 구독으로 제한하지 않는다(FR4.2).
- 탐색 중 정보 열람에서 무엇을 무료로 둘지는, 비구독 기업도 기본 프로필·대표 주장·근거를 확인하고 그 밖의 정보에서 차등을 두는 첫 intent 범위 정의의 비교 방향(C02)과 함께 정한다.
- 확인 전 조사 메모: 온라인 결제 대행(PG) 가맹에는 사업자등록증이 기본 서류다. 운영진이 무상 지급하고 이 서비스 안에서만 쓰며 현금 구매·환전이 없는 마일리지는 결제가 없고, 단일 서비스에서만 쓰는 선불전자지급수단의 등록 예외 유형에 해당할 가능성이 있다. 법 해석이므로 12월 적용 전에 소속 기관이나 전문가에게 확인한다.

### 3-2. 9/24 확인에서 남은 미결

9/24 인터뷰의 결정을 기존 기록과 대조하며 드러난 미결이다. 결정이 아니며, 요구사항 분석에서 질문으로 다룬다.

- **프로필 상세:** 보여 줄 항목 전체 목록, 보는 사람(구직자끼리·기업·링크 수신자)별로 보일 항목. 구직자끼리는 공개 범위(전체·맞팔)를 적용한다.
- **기업 등록:** 누가 기업을 등록하고 소속을 승인하는지, 직책 종류와 직책별 권한(v10은 DM 권한을 예로 들었다). 기업 인증이 범위 밖이므로 사칭을 어떻게 줄일지도 함께 정한다.
- **기업 안 공유:** 후보자 메모와 질의 기록을 같은 기업 회원에게 공유할지. 지원자 자료이므로 첫 intent는 "회사 안 공유로 지원자 자료의 열람 권한이 자동으로 넓어지지 않는다"를 따로 두었다.
- **채용공고와 JD 프리셋:** 공고에 JD 프리셋을 연결할지. v10은 공고가 이미지 형식이거나 자사 채용 시스템으로 넘기는 경우가 많아, 대조용 JD를 따로 입력하게 했다.
- **기업 소속 회원의 소셜 이용:** 팔로우·포스팅·피드를 기업 소속 회원도 쓰는지. 공개 범위와 피드는 지금 구직자 기준으로 적혀 있다.
- **MCP 인증·권한:** 토큰을 누가 어떻게 발급하는지, 링크 비밀번호·만료·중단과 검색 노출 해제가 MCP 접근에 어떻게 반영되는지. 8/26 기록은 "MCP 서버는 쉽고 실제 비용은 인증·권한 모델"로 봤다. v10은 MCP 접근도 열람 기록에 남기고 호출 한도를 두었다.
- **MCP 쓰기 범위:** v10은 MCP를 읽기 전용으로 두었다. 헤드헌팅 제안 발송이나 구직자 주장 저장 같은 쓰기를 MCP로 허용할지.
- **검사용 MCP:** 기능 검사 통로로 쓸 MCP가 사용자용 MCP와 같은 서버·권한인지, 개발 환경 전용 도구를 따로 두는지.
- **관리자 처리 세부:** 제재 단계(경고·제한·정지)와 해제, 처리 이력 조회, 관리자 권한. [P4 설계 노트](../P4_설계노트_v2_0.md) 「6. 제재 단계 설계」「7. 권한 모델 (초안 — 미확정)」을 출발 입력으로 한다.
- **지표 정의:** 지표별 집계 주기·보관 기간, 품질 지표를 실시간으로 보일지. [KPI 문서](../CatchU_KPI_성공기준_v4_1.md)의 사실 일치율·귀속 정확도는 표본을 판정하는 방식이라 지표 화면의 숫자와 구분한다.
- **운영 기능의 나머지:** 내부 선택 공유(FR10.2)와 조건별 경고(FR10.5)의 포함 여부.
- **§6에서 "요구사항 분석"으로 표시한 항목**의 포함 여부와 순서.

### 3-3. 10월 후속 결정(2026-10-08)에서 12월 설계로 넘긴 것

10월 MVP의 [팀장 확인 (2026-10-08)](../ai-dlc-input-mvp/2026-10-08_catch-decisions.md)에서 12월 설계에서 다시 정하기로 한 것이다. 결정이 아니며, 12월 도메인 설계를 다시 시작할 때 다룬다.

- **한 PR·병합 안의 서로 다른 번호:** 10월(이슈 조회 없음)에는 한 PR이나 병합 안의 본인 커밋이 서로 다른 `#번호`를 가리킨다는 것만으로는 나누지 않고 작성자가 묶은 경계를 따른다. 이슈 조회가 허용되는 요청에서도 그 경계를 따를지 정한다. 지금 #118은 이슈 조회가 허용되면, 서로 다른 이슈 번호가 둘 이상이고 나누기 조건을 모두 채울 때 나눈다.
- **나누지 않는 규칙을 다시 볼지:** 10월에 나누지 않은 단위의 기록 건수(#122 검수에서 봄)를 보고 정한다.
- **생성된 제목의 표시:** 10월에는 제목과 설명이 자동 생성임을 화면 공통 안내 한 줄로 알린다. 12월 요구사항 FR1.4(기록에서 확인한 내용·작성자 설명·AI 해석 구분)에 맞춰 Catch마다 따로 표시할지 정한다.
- **문장형 제목:** 10월 제목은 근거로 확인할 수 있는 조각(대상·종류·동작)으로만 만든다. 일반 낱말이 든 문장형 제목을 쓸지, 쓴다면 그 낱말이 근거에 있는지 확인할 방법을 함께 정한다.

## 4. 10월 설계에 주는 제약

10월 MVP intent는 위 기능을 10월에 구현하지 않는다. 아래는 기존 제품 행동을 지키면서 후속 확장을 검토하기 위한 원칙이다. 물리적 배치·저장 구조·프레임워크는 해당 설계 단계에서 결정한다.

- **권한 판정 재사용:** 화면·링크·향후 MCP에서 일관된 권한 규칙을 재사용한다. API 한 곳이라는 물리적 위치를 미리 강제하지 않는다. MCP의 구체 허용 범위는 12월 요구사항 분석에서 정한다.
- **공개 상태 모델:** 10월 공개·숨김과 기업·링크 열람 규칙을 유지한다. 12월 구직자 간 전체·맞팔 공개를 추가할 때 기존 규칙과의 적용 대상·우선순위를 구분할 수 있도록 설계한다. 저장값의 개수나 같은 필드 사용 여부를 지금 지정하지 않는다.
- **분석 상태·기록:** 10월에 필요한 분석 식별자·상태와 완료·실패·운영 기록을 확보한다. 12월 알림에서 필요한 기록을 활용할 수 있도록 검토하되, 이를 이유로 10월에 알림 발송·이벤트 전달 시스템을 구축하지 않는다. 상세 기록·보관 기준은 OQ13에서 정한다.
- **계정 유형:** 구직자·기업 계정의 역할을 구분할 여지를 둔다. §2의 회사 프로필 구성 재사용과 동일 데이터 구조 강제는 구분한다. 회사와 로그인 계정의 관계, 프로필 소유·편집 권한은 12월 설계에서 정한다.
- **링크 발행:** 10월 발행은 무료다. 향후 마일리지 등 발행 조건을 추가할 경계를 검토하되, 10월에 잔액·차감 기능을 구현하지 않는다.
- **홈·헤더:** 10월 로그인 홈에는 분석 결과 상자를 두지 않는다. 12월에는 피드가 로그인 홈의 중심이 되고, 분석 완료·실패 안내는 헤더 알림으로 간다(#51). 10월 분석 진입·재방문 경로는 후속 입력의 「팀장 확인 (2026-09-24): B 계약 확인·내 자산 화면 구조」를 따른다(내 자산 Catch 탭의 저장소 연결 관리).

## 변경 기록

- 2026-10-08 — 「3-3. 10월 후속 결정(2026-10-08)에서 12월 설계로 넘긴 것」을 추가했다. 이유: 10월 MVP의 팀장 확인(2026-10-08)이 네 가지를 12월 설계로 넘겼다. 영향: 12월 도메인 설계를 다시 시작할 때 이 절을 질문으로 다룬다. 12월 승인 요구사항은 바꾸지 않는다.
- 2026-09-25 — 팀장 인터뷰를 이어 MCP와 관리자 기능을 보완했다. MCP의 목적(구직자에게 데이터를 제공, HR 헤드헌팅, ATS의 MCP 전환)과 기업 MCP의 검색 포함, MCP를 E2E 검증에도 쓰는 방식(9/24)을 §2에 넣었다. 관리자 처리 기능(신고 처리·제재, 기업 등록 관리, 채용공고 관리)과 지표 화면의 원칙·묶음(9/25)을 §2에 넣고, 남은 미결을 §3-2에 더했다.
- 2026-09-24 — 팀장 인터뷰로 MVP 이후 기능을 보완했다. 8월 마지막 주 회의의 합의(프로필 상세, 기업 등록·소속·권한, 기업 JD 프리셋, 서류 프리셋, 수신자 JD 입력, 포스팅의 글 읽기 권한)와 9/24 결정(이력서 여러 벌, 기업 안 JD 공유, 대표 구성 1순위, 운영 기능 후순위 포함)을 §2에 넣고 항목마다 출처를 달았다. 대조 중 드러난 미결을 §3-2에, 10월 MVP가 뒤로 민 기능의 파트별 대조를 §6에 두었다. 다른 문서가 참조하는 §2·§4의 번호는 유지했다. 같은 날 #97(내 자산 화면 구조)이 머지되어 서류 등록 위치를 내 자산의 서류별 탭으로 구체화하고, §4 마지막 문장의 10월 분석 경로 참조를 그 결정으로 고쳤다.
- 2026-09-17 — [결정 댓글](https://github.com/JminAILab/CatchU/issues/56#issuecomment-5715760038)로 확인한 9/16 PDF 파일 업로드 결정을 §2에 반영했다. 제공 방식·파일 형식을 미결에서 빼고, 남은 네 항목은 회의 후속 기준 §4와 맞췄다.
- 2026-09-16 — [팀장 결정](https://github.com/JminAILab/CatchU/issues/56#issuecomment-5692700641)에 따라 이력서를 제외에서 **12월 포함**으로 변경했다. 수신자가 필요한 자료를 한 화면에서 함께 확인하도록 하며, FR5.2~FR5.4는 서류 종류와 무관하게 같게 적용한다. 제공·보관 방식, 파일 규격, 업로드 위치, 열람·다운로드는 미결로 남기고 링크 다운로드 옵션은 재검토 중으로 표시했다. 알림·DM·홈·수신자 헤더의 [회의 후속 기준](../ai-dlc-input-mvp/2026-09-16_meeting-decisions.md)도 연결했다.
