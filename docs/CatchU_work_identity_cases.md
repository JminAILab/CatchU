> [작업 동일성 판별 기준](CatchU_작업동일성_판별기준.md)의 절을 2026-10-02 [#203](https://github.com/JminAILab/CatchU/issues/203)에서 그대로 옮긴 파일이다. 지위와 적용 범위는 그 문서와 같고, 다른 절은 그 문서에서 찾는다. AI가 한 번에 읽을 수 있게 36 KB 미만으로 유지한다.

## 합성 사례와 기대 판정

사례의 값은 모두 설명용 합성 값이다. 실제 저장소 자료나 과거 실험 자료가 아니다.
- **기본 후보**: 회원 M1, 저장소 `synthetic-repo-0001`(R1), 방식 LIVE, 나누지 않은 PR #3 전체를 한 후보로 본 결과, 제목 "알림 목록 페이지 나누기".
- LIVE는 실제 결과였다면 어떻게 판정되는지 보이려는 가정이다.
- SHA는 `aaaa…`처럼 같은 글자 40개로 적는다.
- **기대 판정**은 계약과 작업의 뜻에서 정했다.
  - **판정 범위 밖**은 작업 의미로는 같을 수 있지만 회원이나 저장소가 달라 서로 비교하지 않는 경우다. C10은 값이 같고, C11은 저장소가 달라 값이 다르다.
  - 범위도 다르고 작업도 다르면 '다른'으로 적는다(C12·C13).
  - **비교 대상 아님**은 재전달과 중복 등록을 구분하려고 넣은 대조 사례다.
- **Catch 영향**은 B가 받은 값으로 등록했을 때의 결과다.

C1~C5의 "기존 Catch 참조"는 다른 결과에서 같은 작업이 다시 왔다고 가정한 것이다. 10월에는 이 경로가 없다(「판정 규칙」 10월의 결과 사이 경로). 한 결과 안에서는 F가 같은 변경을 한 후보로 두므로 B까지 가지 않는다(C8·C14·C20·C23·C25).

**같은 변경 확인 사례.** 한 결과 안에서 SHA가 다른 두 변경을 같은 변경으로 볼지 정하는 사례다(「PR 소속과 같은 변경을 확인하는 근거」). C20·C23은 실제 중복을 합치는 사례다. C21·C22·C24·C30은 관계 근거가 없어 합치지 않는 사례다. C30은 시간 순서와 diff가 재제출과 같지만 두 PR을 잇는 근거가 없다. C25는 관계 근거가 있어 실행 결과가 다른 공백 차이까지 합치는, 감수한 한계다. C26은 관계 근거는 있지만 diff가 달라 확정하지 못하는 사례다. C14·C20~C26·C30의 diff 모양과 cherry-pick 표시는 합성 저장소에서 git 2.54.0으로 확인했다. 재제출 관계는 PR API의 병합 여부·만든 시각·본문에서 오므로 git으로 만들지 않고, 설명용 스크립트에 합성 PR 자료로 넣어 확인했다(C14·C23·C26·C30).

## #118이 지킬 것과 시험할 것

1. 값은 이 문서의 함수로만 만든다. 제목·문장·전달 번호를 넣지 않는다.
2. 한 결과 안에서 같은 변경(같은 SHA, 또는 7번 기준으로 확정한 변경. 경로로 나눈 커밋은 같은 커밋·같은 경로)은 한 후보에만 속한다. 병합 커밋은 변경으로 세지 않는다. 여러 단위에 들어 있는 변경은 「무엇을 하나의 작업으로 보는가」의 배정 규칙을 따른다. 배정받은 변경이 없는 단위는 후보를 만들지 않는다. 그래서 후보끼리 값이 모두 다르다.
3. 단위는 나누기 세 조건(따로 확인, 겹치지 않음, 배정된 모든 변경이 한 부분에 속함)을 채울 때만 나눈다. 못 채우면 한 후보로 둔다. 이슈 조회가 허용되지 않은 요청에서는 PR 번호가 아닌 서로 다른 번호만으로 나누지 않고 groupingLimitations에 남긴다(C7).
4. 이슈 API가 준 PR은 PR 단위로 적는다. PR 조회가 허용되지 않은 요청에서는 PR 단위를 쓰지 않는다.
5. 근거의 판본을 확정할 수 없으면 기존 규칙대로 INSUFFICIENT_EVIDENCE다. 근거 요건은 채웠지만 단위만 정할 수 없는 변경은 「결정」대로 보류한다.
   - 보류하기 전에 허용된 수집 범위와 수집 상한 안에서 확인을 시도한다. PR 목록의 `merge_commit_sha`와 PR 커밋 목록(250개가 넘으면 PR 전체 커밋 수와 비교 API로 확인)으로 먼저 소속을 정하고, 남은 커밋에만 "연결된 PR" API를 쓴다. 호출 수를 아끼기 위해서다(「PR 소속과 같은 변경을 확인하는 근거」).
   - 커밋 목록을 다 받지 못한 PR이 있으면 그 PR과 겹칠 수 있는 커밋은 PR 밖으로 확정하지 않고 보류한다(「결정」, 2026-10-09). 시험: 커밋 300개인 PR을 병합 없이 닫고 그 브랜치를 PR 없이 기본 브랜치에 합쳤고, 비교 결과의 커밋 수가 PR 전체 커밋 수와 맞지 않아 250개만 쓰는 경우, 받은 250개 밖의 본인 커밋은 따로 후보가 되지 않는다. 기대값: PR 후보 1개(한계 기록), 보류한 커밋은 UNDETERMINED, failures 없음, outcome SUCCEEDED. 같은 커밋들이 기본 브랜치를 대상으로 한 열린 PR의 것이면 보류하지 않는다(L13).
   - 보류한 커밋을 세는 법은 「결정」의 2026-09-30 집계를 따른다. 정한 범위대로 조회를 마쳤으면(수·판본 어긋남, 비교 쪽수 상한, 포크에서 연 PR, 기준 커밋 모름) 근거끼리 어긋나지 않아도 UNDETERMINED로 센다. 요청의 수집 상한이나 조회 오류(비교 조회 거절 404·422 포함)로 멈췄으면 아래 수집 실패로 센다.
   - 조회를 마쳤는데도 근거끼리 어긋나 정할 수 없으면 후보로 내보내지 않고 UNDETERMINED로 센다. 실패는 기록하지 않는다.
   - 수집 상한이나 조회 오류로 확인을 마치지 못했으면 후보로 내보내지 않고 notProvided에도 세지 않는다. 수집 실패를 failures에 기록하고 다시 부르지 않는다([#116 문서 2.4][d116-24]).
   - 보류 건수를 두 경우로 나눠 운영 로그에 남긴다. 요청 식별자와 건수만 남기고 커밋 내용·원문은 남기지 않는다.
6. outcome은 내보낸 후보 수와 failures 수로 계산한다. 조회를 마친 뒤 보류만 있으면 SUCCEEDED·EMPTY, 확인이 중단됐으면 PARTIAL_FAILED·FAILED다.
7. 같은 변경은 같은 SHA이거나, 관계 근거(재제출·cherry-pick 표시)가 있고 공백을 무시한 diff(`git patch-id --stable`과 같은 기준, 앞뒤 문맥 줄 포함)가 같을 때만 확정한다. 재제출은 병합 없이 닫힌 PR과 그보다 나중에 만들어져 병합된 PR 사이에서, 뒤 PR의 제목·본문이 앞 PR을 번호나 같은 저장소의 PR 주소로 가리킬 때만 인정한다. PR 상태와 만든 순서만으로는 인정하지 않는다. 같은 이슈 참조·파일 겹침·제목 유사는 관계 근거로 쓰지 않는다. 관계 근거가 없으면 공백을 무시한 diff가 같아도 합치지 않는다. 변경 내용이 없거나(`patch` 누락) 잘려 비교할 수 없으면 확정하지 않는다.
8. 값은 결과와 함께 보관하고, 재전달·반영 복구 때 다시 계산하지 않는다.
9. 단위의 식별(PR 번호·병합 커밋·SHA)을 그 후보의 근거에서 찾을 수 있게 한다. 커밋이 많을 때 대표 근거만 둘지는 #118에서 정한다.
10. 합성(MOCK) 경로는 알려진 합성 값을 계속 써도 된다. #103·#113 시험의 기대값을 이 함수로 바꾸지 않는다.
11. 시험: C1~C17, C20~C30과 쌓아 올린 PR 사례(공유 커밋은 먼저 병합된 앞 PR로, 뒤 PR은 자기 커밋만으로 후보가 됨)를 함수·묶음 단위 시험으로 옮긴다(C18·C19는 E 수신 시험의 몫이다). C14·C20~C26·C30의 diff는 실제 git 커밋으로 만들고, 재제출 여부를 가리는 사례(C14·C23·C26·C30)에는 PR 자료(병합 여부·만든 순서·본문)를 합성해 붙인다. 관계 근거가 없으면 공백을 무시한 해시가 같아도 두 후보가 남는지(C21·C22·C24·C30), 관계 근거가 있으면 한 후보로 합쳐지는지(C14·C20, 공백만 다른 변경은 C23·C25) 본다. 다음을 함께 확인한다.
    - 불변성: 쓰지 않는 입력이 바뀌어도 값이 같다. C10은 두 회원의 값이 같아야 한다.
    - 민감도: 저장소·방식·단위·부분이 바뀌면 값이 다르다.
    - 형식: `wi1:` 뒤에 16진수 64자가 붙는다.
    - 부분: 정렬 순서와, 한 커밋을 한 가지로만 적는 규칙.

- 위 한계 사례 L1~L13.
- **repositoryId의 실제 형식이 정해지지 않았다.** 다음을 확인한다.
  - 이름 변경·이전 뒤에도 같은 값인가.
  - 저장소를 지우고 같은 이름으로 새로 만들었을 때 옛 값을 다시 받지 않는가.
  - 한 회원이 같은 GitHub 저장소를 두 값으로 갖지 않는가.
  - 값이 바뀌면 같은 작업이 나뉘고(중복), 재사용되면 다른 작업이 합쳐질 수 있다. A 담당(`yeongyeon1802`)이 실제 GitHub 연결 구현([#133][i133])에서 검증하기로 했다(E 의견). 저장소 식별 정보 전달은 [#116][i116]에서 다룬다. 불변 값이 아니면 그때 계약 보완 대상이다(계약4).
- **GitHub 사실.** 다음은 확인했다.
  - 이슈·PR은 번호를 함께 쓴다(「식별자 충돌」).
  - [PR 커밋 목록 API][gh-prc]는 최대 250개까지만 돌려준다. 더 많으면 [커밋 목록 API][gh-lc]로 전체를 받으라고 공식 문서가 안내한다. 그러나 커밋 목록 API는 지정한 커밋에서 닿는 이력 전체를 주므로 PR이 어디서 시작하는지 알 수 없다. 이 기준은 그 안내 대신 PR 전체 커밋 수와 비교 API를 쓴다(2026-10-08 팀장 결정, [결정 기록](CatchU_work_identity_records.md#결정)).
  - [커밋과 연결된 PR API][gh-cpr]는 기본 브랜치에 있는 커밋이면 그 커밋을 들여온 병합 PR을 돌려준다. 기본 브랜치에 없으면 연결된 병합·열린 PR을 돌려준다.
- 다음은 실제 구현에서 확인해야 한다.
  - PR 번호가 저장소 안에서 다시 쓰이지 않는가.
  - 위 연결 API와 `merge_commit_sha`가 병합 커밋·squash·rebase 방식별로 실제로 PR을 가리키는가. rebase로 합친 PR은 `merge_commit_sha`가 마지막 커밋만 가리키므로 나머지 커밋을 어떻게 잇는지 본다.
  - 수집 상한 안에서 확인을 마칠 수 있는가. 보류 건수 로그를 조회 완료(C16)와 확인 중단(C27~C29)으로 나눠 실제 빈도를 본다(「결정」).
  - PR 조회가 허용 범위에 없을 때 단위가 어떻게 달라지는가(L2).
  - 커밋이 250개를 넘는 PR에서 PR 커밋 목록 API가 앞쪽과 뒤쪽 가운데 어느 250개를 주는지, 수가 같을 때 비교 범위와 PR 커밋이 실제로 같은지([#121][i121]).
- **공백을 무시한 diff를 비교하는 방법을 확인한다.** API가 주는 변경 내용(`patch`, 앞뒤 문맥 줄 포함)으로 `git patch-id --stable`과 같은 기준(공백과 줄 번호 무시)을 계산할 수 있는지 본다. `patch`가 빠진 파일(바이너리·큰 변경, [#116 문서][d116])은 비교를 포기하는지도 확인한다(C14·C20·C23·C26).
- **PR 제목·본문의 참조를 읽는 방법을 확인한다.** `#번호`(조사가 붙은 모양 포함)와 같은 저장소의 PR 주소를 세고, 코드 블록·인라인 코드·HTML 주석 안의 글자, 앞에 글자가 붙은 번호, 다른 저장소의 PR은 세지 않는지 본다. 제목·본문은 PR 목록·PR API 응답에 들어 있어 호출이 늘지 않는지도 본다(C14·C30).
- **충돌 해결로 병합 커밋에만 생긴 변경**을 어느 단위의 변경으로 볼지 확인한다. 이 제안은 병합 커밋을 변경으로 세지 않는다.
- **squash로 합친 PR의 squash 커밋**을 그 PR의 원래 커밋과 같은 변경으로 볼지 확인한다. 지금 규칙은 둘을 잇지 않는다. 그래서 cherry-pick한 PR을 squash로 합치고 squash 메시지에 cherry-pick 표시가 남지 않으면, squash 커밋이 관계 근거 없는 변경으로 그 PR에 남아 후보가 된다(C20·C25가 Catch 2개가 됨). 통합 PR을 squash로 합치면 C8의 #12도 후보가 된다. C8·C20·C25는 병합 커밋으로 합친 경우를 가정했다. 2026-10-08 팀장 결정([본인 기여의 뜻](ai-dlc-input-mvp/2026-10-08_catch-decisions.md#본인-기여의-뜻))으로, GitHub가 squash 병합으로 새로 만든 커밋의 작성자는 그 안 변경의 명의로 보지 않는다. PR의 원래 커밋 목록을 받았으면 원래 커밋으로 판단하므로 위 경우는 생기지 않을 것으로 본다. 목록을 받지 못했으면 근거 부족이다. 조회 오류나 수집 상한이 원인이면 수집 실패다(C17·「#118이 지킬 것」 5번). 실제 구현에서 확인한다.
- **결정성을 확인한다.** 방법 B의 묶음과 나누기 결정이 같은 입력에서 항상 같아야 한다(L3·L5).
- 64자 SHA 저장소와, 파일 이름이 바뀐 커밋에서 부분 경로를 무엇으로 쓸지 확인한다.
- 동시에 등록해도 한 Catch로 모이는지는 [PR #143][p143]의 시험을 재사용한다.
- 실제 자료에서 잘못 합침·잘못 나눔을 세는 검수는 [#122][i122]에서 한다. 실제 자료 사용 조건([#37][i37]) 안에서만 한다.
- 원본 비공개 관측 책임([OQ-B3][c186])은 이 문서의 범위가 아니다. F에 배정하지 않는다.
- [#116 문서][d116]는 2026-09-30 병합됐다(PR #166, `6acd4a5`). 이 문서는 병합 직전 판본 `98c9f99`와 대조했다. 병합 때 2.4 표의 요청 불일치·자격정보 실패 행이 바뀌었지만, 이 문서가 인용하는 상한 초과·조회 오류 때의 결과는 그대로다. 상한 수치와 실패 코드 이름은 #116의 제안값이다. #116이 바뀌면 이 문서의 「판정 규칙」과 C27~C29를 함께 맞춘다.
