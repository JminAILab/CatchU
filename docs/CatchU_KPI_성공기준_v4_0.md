## 0. v3.0에서 바뀐 것

네 페르소나가 팀 논의를 거쳐 개정되면서, KPI의 **중심축**을 다시 잡았다.

| | v3.0 | **v4.0** |
| --- | --- | --- |
| 중심축 | 증거의 정확성 (Primary) + 시간 (조건부) | **증거의 정확성 → 회수 → 이해 → 검증** 사슬 |
| P1 대표 지표 | 경험 재발견 + 정리 시간 단축률 | **개발 경험 회수 성공률** (정리 시간은 참고로 강등) |
| P2 지표 | 조건 충족 후보 발견률 (전제 미검증으로 보류) | **후보 발견 + 개발 경험 이해** 두 갈래 (전제 정리됨) |
| P3 지표 | 후보 파악 시간 단축률 (조건부) | **실제 수행 내용 파악 + 근거 확인** (시간은 폐기) |
| P4 지표 | 자동 처리율 + 평균 처리시간 | 동일 — **다만 시간 지표의 위상이 올라감** (3장) |

### 왜 바꾸는가

페르소나 개정 후 세 사람을 다시 읽으면, 이들을 관통하는 것은 **시간이 아니다.**

| | 원하는 것 |
| --- | --- |
| **P1** | 내가 실제로 했던 일을 **꺼내준다** |
| **P2** | 비개발자도 실제 개발 경험을 **읽는다** |
| **P3** | 실제로 한 일을 보고 **원본 근거까지 확인한다** |

셋을 연결하는 자산은 **증거 카드와 그 근거**다. 그래서 KPI도 그 사슬을 따라간다.

**특히 P1의 변화가 결정적이다.** v3.0 페르소나는 *"시간이 걸려서 못 한다"*가 아니라 **"시간이 걸려도 나를 어필할 수 있다면 한다"**로 정의되었다. 그러면 *경험 정리 시간 단축률*은 P1의 대표 성공 기준이 될 수 없다.

## 1. 핵심 성공 기준

> **CatchU의 핵심 성공 기준은 GitHub에 흩어진 개발자의 실제 활동을 정확한 근거로 구조화하여, 개발자는 자신의 경험을 다시 꺼내 활용할 수 있고 기업은 그 경험을 이해하고 원본까지 검증할 수 있게 만드는 것이다.**

### KPI 체계도

```
                    GitHub의 실제 활동
                          ↓
          ┌───────────────────────────────┐
          │  AI가 제대로 추출했는가?        │  ⭐ 사실 일치율
          │                               │  ⭐ 개인 수행 내용 귀속 정확도
          └───────────────────────────────┘
                          ↓
          ┌───────────────────────────────┐
          │  개발자에게 가치가 있는가?      │  ⭐ 개발 경험 회수 성공률
          └───────────────────────────────┘
                          ↓
          ┌───────────────────────────────┐
          │  기업에게 전달되는가?           │  개발 경험 이해 · 수행 내용 파악
          └───────────────────────────────┘
                          ↓
          ┌───────────────────────────────┐
          │  믿을 수 있는가?                │  ⭐ 근거 확인 성공률
          └───────────────────────────────┘

    검색 · 추천 · DM  →  증거를 사람과 기업 사이에서 연결하는 Service KPI
    P4 운영          →  그 서비스를 유지하는 운영 KPI
```

### 최상위 KPI로 쓰지 않는 것

| 제외 지표 | 사유 |
| --- | --- |
| 취업 성공률 · 채용 성공률 · 최종 합격률 | **CatchU는 지원 → 면접 → 합격 구간에 관여하지 않는다** |
| **기업 실무자의 실제 업무 시간** | 지속 측정 주체가 우리가 아니다 (3장) |
| **P1의 경험 정리 시간 단축률** | P1 v3.0에서 "시간이 걸려도 한다"로 정의됨. 대표 지표 자격 없음 → 참고 지표 |

## 2. KPI 설계 원칙

1. **측정 가능성이 지표 선정의 1차 조건이다.** 데이터 출처·계산식·수집 주기를 지금 적을 수 없으면 KPI로 쓰지 않는다. *(특강에서 든 KPI 선정 기준 — 측정 방법을 적을 수 없는 지표는 지표가 아니다)*
2. **정확도 지표에도 비교 대상이 필요하다.** 단순 규칙 기반과 비교한다. (10장)
3. **"사용자에게 점수를 매기지 않는다"(원칙 1) ≠ "프로젝트 지표가 없다".** 원칙 1은 *사용자 화면*에 대한 것이고, KPI는 *우리가 프로젝트를 평가하는 잣대*다.
4. **성과 목표값과 최소 품질 기준은 다르다.** 근거 없는 숫자는 지금 적지 않는다.
5. **한 방향으로만 좋은 결과는 성공이 아니다.** 서로 반대로 당기는 지표는 함께 본다. (6.1)
6. **"기여도"라는 표현을 쓰지 않는다.** 퍼센트로 읽혀 원칙 1과 부딪힌다. → **"수행 내용" / "누가 무엇을 했는지"** *(P3 v3.0 결정)*

## 3. 측정 가능성 — 무엇을 우리가 잴 수 있나

**같은 "시간" 지표라도 측정 주체가 다르면 성립 여부가 갈린다.**

| 지표 | 측정 방법 | 가능 |
| --- | --- | --- |
| 증거 카드 사실 일치율 · 귀속 · 커버리지 · 링크 유효율 | Ground Truth 대조 — **피험자 0명** | ✅ |
| 개발 경험 회수 성공률 | P1 테스터(수료생 동기) | ✅ |
| 개발 경험 이해 · 수행 내용 파악 · 근거 확인 | 대역 피험자로 수행 가능 | ◐ 조건부 |
| **P3 후보 파악 시간 단축률** | 기업 실무자의 실제 업무 시간 | ❌ **통제 불가** |
| **P4 예외 건 평균 처리시간** | **시스템 로그** — 신고 접수 시각 → 처리 완료 시각 | ✅ **직접 측정 가능** |

> **P3의 시간은 못 재고 P4의 시간은 잰다.** 외부 실무자의 업무 시간이 아니라 **우리 서비스 내부의 이벤트 간격**이기 때문이다. 이 구분이 v4.0에서 P3 시간 지표를 폐기하고 P4 시간 지표를 유지하는 이유다.

## 5. KPI 상세

### 5.1 ⭐ 증거 카드 사실 일치율 (Primary)

**정의** — 카드가 제시한 주장과 근거가 실제 GitHub 기록과 일치하는 비율

```
실제 근거와 일치하는 카드 수 ÷ 평가 대상 카드 수 × 100
```

| 항목 | 내용 |
| --- | --- |
| 카드 주장 | "JWT 기반 인증 로직을 구현했다" |
| 제시 근거 | Commit A · PR #24 · 관련 코드 변경 |
| 판정 | 해당 커밋·PR이 실재하고 그 내용이 주장을 뒷받침하는가 → ○ / × |

**이것이 Primary인 이유** — 세 페르소나를 관통하는 것이 증거 카드이고, **서비스의 원칙 4(주장과 근거를 연결한다)가 곧 이 지표**다. 그리고 **피험자 없이 우리가 100% 통제할 수 있다.**

---

### 5.2 ⭐ 개인 수행 내용 귀속 정확도 (AI Quality)

**정의** — 카드가 서술한 행동을 **실제로 이 사용자가** 수행했는가

```
귀속이 맞는 카드 ÷ 팀 프로젝트 카드 × 100
```

**분모에 주의** — **팀 프로젝트 카드만** 센다. 1인 프로젝트는 귀속 오류가 발생할 수 없어, 분모에 넣으면 1인 레포를 늘리는 것만으로 수치를 100%에 가깝게 만들 수 있다.

**세 페르소나가 모두 요구하는 지점**

| | 요구 |
| --- | --- |
| P1 | "팀플에서 내 몫이 뭐였는지 흐릿하다" |
| P2 | 기술 스택이 나열이 아니라 실제 활동임을 확인해야 한다 |
| P3 | "이 사람이 실제로 무엇을 했는지" — **필요한 것 목록의 핵심** |

> **명칭 주의:** "기여도"가 아니라 **"수행 내용"**이다. 퍼센트로 읽히는 표현은 원칙 1과 부딪힌다. *(P3 v3.0 결정)*

---

### 5.3 ⭐ 개발 경험 회수 성공률 (P1 Value)

**정의** — 사용자가 스스로 떠올리지 못한 실제 개발 경험 중, CatchU 카드를 통해 되찾은 비율

```
회수 성공률 =
  카드로 회수한 경험 수
  ────────────────────────────────────── × 100
  Ground Truth 주요 경험 중
  사용자가 스스로 작성하지 못한 경험 수
```

**측정 절차**

1. Ground Truth로 그 레포의 **주요 개발 경험 목록**을 확보한다 *(11장)*
2. 사용자에게 **CatchU 없이** 자신의 경험·기여 3건 이상을 작성하게 한다 → **스스로 떠올린 것**
3. CatchU 카드를 보여준다
4. 카드 중 **"맞다, 내가 했다"고 확인하고 근거가 실재하는 것** 중, 2단계에서 나오지 않은 항목을 센다

```
예시
  Ground Truth 주요 경험      10건
  스스로 작성                  6건
  스스로 못 떠올린 것           4건   ← 분모
  카드로 회수                  3건   ← 분자
  → 회수 성공률 75%
```

**커버리지와 혼동하지 않는다**

| 지표 | 분모 | 무엇을 재나 |
| --- | --- | --- |
| 핵심 경험 커버리지 | **전체** 주요 경험 | **AI 성능** — 빠뜨리지 않았는가 |
| **회수 성공률** | 사용자가 **놓친** 경험 | **사용자 가치** — 놓친 것을 되찾아줬는가 |

> **이 지표가 P1의 핵심 고통 ①(있는데 꺼내지 못한다)을 직접 잰다.** 시간 단축은 결과이고 회수가 원인이다. **CatchU가 시간 절약 도구가 아니라 경험 복원 도구임을 보여주는 지표다.**

**함께 받는 정성 평가 (5점 척도)**

- "생성된 자료가 내가 실제로 한 일을 설명하는 데 도움이 되었는가?"

### 5.4 근거 확인 성공률 (Evidence UX)

**정의** — 사용자가 카드의 주장으로부터 실제 원본(Commit·PR)까지 스스로 도달한 비율

```
"이 카드의 주장을 검증할 원본 근거를 찾아보세요."
  → 성공률 (+ 소요 시간은 참고)
```

**시스템 지표인 근거 링크 유효율과 분리한다** *(6.2)* — 링크가 100% 유효해도 UI 때문에 못 찾으면 UX 실패이고, UI가 좋아도 링크가 깨지면 기술 결함이다.

P3가 명시적으로 요구한 **"모든 항목에 한 뎁스 내 근거 링크"**가 실제로 작동하는지 검증하며, **P2(비개발자)와 P3(개발자) 양쪽에 적용한다.**

## 6. 보조 AI Metric

### 6.1 핵심 경험 커버리지

```
카드가 포착한 주요 경험 ÷ Ground Truth 주요 경험 × 100
```

**일치율과 서로 반대로 당긴다.**

```
AI가 매우 보수적으로 동작하면
  주요 경험 10개 → 카드 2개만 생성 → 둘 다 정확 → 사실 일치율 100%
  숫자는 완벽하지만 서비스는 쓸모없다.
```

**두 지표는 반드시 함께 보고하며, 한쪽만 좋은 결과는 성공으로 보지 않는다.**

### 6.2 근거 링크 유효율

```
유효한 링크 ÷ 전체 근거 링크 × 100
```

**기준은 100%다.** 깨진 링크는 품질 편차가 아니라 **버그**이므로 목표값을 논할 항목이 아니다.

### 6.3 Critical Error — 타인 기여 오귀속

**정의** — 타인의 Commit·PR을 사용자 본인의 활동으로 잘못 귀속하는 경우

| 처리 | 내용 |
| --- | --- |
| 발생 시 | **1건이라도 발견되면 원인 분석 착수** |
| 조치 | 원인 해결 전까지 해당 분석 기능 공개 보류 |

비율 지표가 아니라 **안전 조건**이다. 남의 커밋을 이 사람 것으로 붙이는 순간 서비스의 존재 이유가 무너진다.

### 6.4 오답 유형 기록

*모델이 틀린 비율만 세지 말고 **어떤 방식으로** 틀렸는지를 유형별로 남기는 오차 분석이다. 특강에서 모델 평가의 필수 절차로 든 항목이며, 개선할 지점을 찾는 근거가 된다.*

| 유형 | 내용 | 귀속 축 |
| --- | --- | --- |
| 환각 | 존재하지 않는 커밋·PR을 근거로 제시 | 정확성 |
| 근거 부족 | 근거는 실재하나 주장을 뒷받침하지 못함 | 정확성 |
| 과장 | 사실이지만 수행 범위를 부풀림 | 정확성 |
| **오귀속** | 타인의 기여를 본인 것으로 표시 | **Critical Error** |
| 누락 | 중요한 경험을 카드로 만들지 못함 | 완전성 |

## 7. 사용자 검증 Metric — 테스터 확보 시

핵심 KPI가 아니다. 피험자가 확보되면 수행하는 검증 지표이며, 확보하지 못하면 **"미측정"으로 명시한다.**

### 7.1 공통 프로토콜 — 하나의 실험, 세 관점

**P1의 "전달 가능성" · P2의 "개발 경험 이해" · P3의 "수행 내용 파악"은 사실상 같은 측정이다.** 같은 자료·같은 질문을 주고 **피험자 유형만 바꾼다.**

**질문 (공통)**

1. 이 사람이 프로젝트에서 **실제로 무엇을 했나요?**
2. **어떤 기술을 실제로 사용**했나요?
3. 그렇게 판단할 수 있는 **근거는 무엇인가요?**

| 피험자 | 지표명 | 확인하는 것 |
| --- | --- | --- |
| **비개발자** (P2 대역) | **개발 경험 이해 성공률** | 기술 용어를 몰라도 읽히는가 |
| **개발자** (P3 대역) | **실제 수행 내용 파악 성공률** | 기술자가 판단 가능한 수준인가 |
| **본인** (P1) | **경험 전달 가능성** | 내가 한 일이 왜곡 없이 표현됐는가 |

> **시간을 재지 않는다.** 재는 것은 **답할 수 있었는가**다. 이렇게 하면 기업 실무자의 업무 시간을 측정할 필요가 없어진다.

### 7.2 P1 — 재사용 가능성

**정의** — 한 번 생성한 경험 자산을 다른 공고·프로필·면접 준비에 다시 사용할 수 있는가

P1 v3.0의 **"들인 시간이 그 기업 하나로 끝난다"**는 고통에 직접 대응한다. 측정 방식은 1차 실험 후 확정한다. *(미결)*

### 7.3 P2 — 후보 발견 성공률

**정의** — 주어진 조건에 맞는, 검토 가능한 후보를 제한 시간 안에 찾아낸 과제의 비율

```
조건: "React 경험 / 3년차 / 광주·전남 / 근무 가능"
탐색 과제 10건 중 성공 건수
```

> **P2 v2.0에서 "신입" 한정이 빠지고 소싱 대상이 경력 개발자로 정리되면서, 이 지표의 전제가 명확해졌다.** v3.0에서 "확정 보류"였던 것을 검증 지표로 올린다.

**"추천 정확도"라는 표현은 쓰지 않는다.** 우리는 누가 좋은 후보인지 평가하지 않으므로(원칙 1) 정확도의 기준이 성립하지 않는다. **"설정한 조건과 실제 후보 정보가 일치하는 비율"**로 측정한다.

### 7.4 P3 — 면접 질문 근거 확보율

**정의** — CatchU가 제공한 증거 중, HM이 **"면접에서 확인해볼 만하다"**고 판단한 근거가 있었는가

**표현에 주의한다.**

| 쓰지 않는 이름 | 쓰는 이름 |
| --- | --- |
| ~~AI 면접 질문 정확도~~ | **면접 질문 근거 확보율** |
| ~~면접 질문 생성 품질~~ | 상동 |

P3 v3.0은 **"질문 자체가 아니라 질문을 만들 재료"**를 원한다. 시나리오도 *"질문은 내가 만든다. 서비스는 재료까지만 준다"*로 닫혀 있다. **지표 이름이 서비스 성격을 바꾸므로 조심한다.**

## 8. 운영 KPI (P4)

P4 v2.0은 핵심 고통이 **"운영에 쓸 시간이 없다"** 하나로 단일화되었고, 성공 기준도 *"이현우가 하는 일이 적을수록 잘 설계된 것"*으로 명확하다.

### 8.1 핵심 KPI 2개

| KPI | 계산식 | 방향 |
| --- | --- | --- |
| **운영 자동 처리율** | 사람 개입 없이 끝난 운영 건 ÷ 전체 운영 건 × 100 | ↑ |
| **예외 건 평균 처리시간** | **신고 접수 시각 → 처리 완료 시각**의 평균 | ↓ |

> **P4의 시간 지표는 시스템 로그로 직접 측정된다.** 외부 실무자의 업무 시간이 아니라 우리 서비스 내부의 이벤트 간격이므로, P3의 시간 지표와 성격이 완전히 다르다. (3장)

### 8.2 운영 모니터링 Metric (KPI 아님)

AI 오탐률 · 운영자 개입 건수 · 시스템 오류율

## 9. 서비스 운영 이후 KPI

실사용자가 확보된 뒤 측정하는 층이다. **포트폴리오 프로젝트라 실측이 어려울 수 있으므로 정의만 두고 실측 여부를 명시한다.**

| KPI | 정의 | 실측 |
| --- | --- | --- |
| 프로필 공개 완료율 | 가입자 중 GitHub 연결 → 카드 생성 → 공개까지 도달한 비율 | 테스터 대상 가능 |
| 후보 프로필 열람률 | 검색 결과 노출 대비 실제 열람 비율 | 실사용자 필요 |
| DM 전환율 | 열람 대비 접촉 발생 비율 | 실사용자 필요 |
| **기업 → 개발자 접촉 발생 건수** | 실제로 연결이 일어난 횟수 | 실사용자 필요 |

**클릭 수·체류 시간·재방문율은 쓰지 않는다.** 허영 지표이거나 실측 계획이 없다.

> 미측정 항목은 **"측정 설계는 했으나 실사용자 부재로 미측정"**이라고 발표에 명시한다. 재지 못한 것을 숨기지 않고 한계로 밝히는 것은 특강에서 발표 구성의 필수 요소로 든 항목이다.

## 10. Baseline 계획

### 10.1 즉시 착수 — 규칙 기반 baseline (피험자 0명)

특강에서는 **"단순 규칙·기존 모델과 비교해야 성능의 의미가 생긴다"**고 했다. "일치율 92%"만으로는 그게 좋은 건지 알 수 없다.

| 항목 | 내용 |
| --- | --- |
| 방식 | 커밋 메시지 키워드 + 변경 파일 확장자·경로만으로 카드 생성 (LLM 미사용) |
| 예시 | `*.jsx` 변경 + "component" 키워드 → "React 컴포넌트 작업" 카드, 근거는 해당 커밋 |
| 비교 항목 | **사실 일치율 · 귀속 정확도 · 커버리지 모두 비교 가능** |

```
                        규칙 기반    CatchU
사실 일치율                71%        92%   (+21%p)
핵심 경험 커버리지          38%        85%   (+47%p)
개인 수행 내용 귀속 정확도   —          97%
```

**피험자가 0명이고, 스크립트 자체가 개발 산출물로 남는다.**

### 10.2 즉시 착수 — P1 baseline (수료생 동기 5명)

| 항목 | 내용 |
| --- | --- |
| 과제 | **CatchU 없이** GitHub를 직접 뒤져 자신의 경험·기여 3건 이상 작성 |
| 기록 | **작성한 경험 목록** — 회수 성공률의 분모를 만드는 자료 |
| 시점 | **즉시** — P1 실제성 검증 인터뷰와 겸해서 진행 |

> **이 목록이 없으면 "카드 보고 기억났다"를 검증할 수 없다.** 회수 성공률의 성패가 여기에 달려 있다.

### 10.3 조건부 — 사용자 검증 baseline

7장의 공통 프로토콜을 수행할 수 있게 되면, **기존 자료(이력서·포트폴리오·GitHub 원본)만 주고** 같은 3문항에 답하게 해 대조군을 만든다.

## 11. Ground Truth 작성 규칙

**Primary KPI가 사실 일치율이므로, 이 문서의 주 실험은 Ground Truth 평가다.**

| # | 규칙 |
| --- | --- |
| 1 | **GitHub 원본 기록을 기준으로** 정답을 작성한다 |
| 2 | **카드 생성 결과를 보기 전에** Ground Truth를 작성한다 |
| 3 | 가능하면 **2명이 독립적으로** 판정한다 |
| 4 | 의견이 갈린 항목은 **합의 후 최종 라벨**을 확정한다 |
| 5 | 끝내 애매한 항목은 **평가 대상에서 제외하고 별도 표시**한다 |

> 2번이 가장 중요하다. 카드를 먼저 보면 "그럴듯하다"에 이끌려 정답이 카드 쪽으로 끌려간다.

**담을 항목**

| 항목 | 쓰이는 곳 |
| --- | --- |
| 후보가 실제로 수행한 **주요 개발 경험 목록** | 커버리지의 분모 · **회수 성공률의 기준** |
| 각 경험을 뒷받침하는 커밋·PR | 사실 일치율의 판정 기준 |
| 팀 프로젝트에서 각 커밋의 **실제 작성자** | 귀속 정확도의 판정 기준 |

**평가 대상 레포에 팀 프로젝트를 반드시 포함한다** — 귀속 정확도는 팀 프로젝트에서만 측정된다. 수료생 동기의 파이널 프로젝트 레포가 가장 현실적인 확보처이며, **동의를 받고 사용한다.**

## 12. 실험 설계 — 사용자 검증을 하게 될 경우

7장을 수행하게 되면 아래 통제가 필요하다.

### 12.1 학습 효과 통제

같은 피험자에게 같은 후보 자료를 기존 방식 → CatchU로 연달아 주면, **두 번째가 잘 되는 것은 이미 그 사람을 알기 때문**이다.

| | 후보 A | 후보 B |
| --- | --- | --- |
| **1군** | 기존 자료 | CatchU |
| **2군** | CatchU | 기존 자료 |

- **후보 세트는 최소 2개, 가능하면 3~4개.** 세트 간 난이도를 사전에 맞춘다(레포 규모·기술 스택·팀 인원·커밋 수)

### 12.2 피험자 대역과 한계

| 대역 | 대체 피험자 | 발표에 명시할 한계 |
| --- | --- | --- |
| P3 (HM) | 개발 경험이 있는 동료·수료생 | 실제 채용 판단 경험 없음 |
| P2 (HR) | 비개발자 지인 | 채용 실무 맥락 없음 |
| P1 | 인공지능사관학교 수료생 동기 | 표본이 한 기관에 편중 |

> **n이 작아도 괜찮다.** "n=5, 대역 피험자, 통제 실험"이라고 밝히고 결과를 제시하는 편이 출처 불명의 큰 숫자보다 신뢰를 얻는다.

### 12.3 기록 양식

```
피험자ID | 유형(비개발자/개발자/본인) | 군(1/2) | 후보세트 | 자료(기존/CatchU) |
Q1정답 | Q2정답 | Q3정답 | 근거제시여부 | 자유메모
```

## 14. 실패 조건 (Kill Criteria)

| 조건 | 판정 |
| --- | --- |
| **사실 일치율이 규칙 기반 baseline과 비슷하거나 낮음** | 실패 — LLM을 쓸 이유가 없다 |
| **커버리지와 일치율 중 한쪽만 높음** | 실패 — 6.1의 트레이드오프 |
| **타인 기여 오귀속 1건 이상** | 원인 규명 전까지 해당 기능 공개 보류 |
| **근거 링크 유효율 100% 미만** | 원칙 4 미구현. 버그로 처리 |
| **경험 회수 성공률이 0에 수렴** | 실패 — 사용자가 이미 아는 것만 보여준 것 |
| **자료만 보고 "무엇을 했는지" 답하지 못함** | 실패 — 전달이 되지 않는 카드는 카드가 아니다 |

> 마지막 두 줄이 v4.0에서 새로 생겼다. **정확하기만 하고 아무것도 되찾아주지 못하거나 전달되지 않으면, 지표가 좋아도 실패다.**

### 문제 제기에 쓰는 근거 — 주의

**"면접관의 절반이 GitHub를 확인하지만 57.8%는 이력서를 10분 안에 검토한다"는 문장은 쓰지 않는다.** 두 수치의 모집단이 다르다(전자는 채용 과정 일반 조사, 후자는 **HR 담당자** 대상 조사).

**문제 제기에는 직접 확보한 인터뷰 발언을 쓰고, 숫자는 직접 측정한 결과를 쓴다.** 시장 조사 수치는 확정 정의서(레포 밖)의 시장 배경 절에만 두고, 인과를 주장하는 문장으로 엮지 않는다.

> 위 결과 숫자는 **형식 예시이며 실측값이 아니다.** 측정 후 실제 값으로 교체한다.
