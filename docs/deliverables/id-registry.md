## 1. 사용 규칙

### 1.1 ID 규칙

| 대상 | 형식 | 10월 MVP판 | 12월 계획판(가칭) | 원본 ID 병기 |
|---|---|---|---|---|
| 유스케이스 | `UC-NN` | UC-01부터 | UC-101부터 | 원본에 UC가 없으므로 병기 없음. 관련 FR로 추적 |
| 기능 요구사항 | `FR-영역-NN` | 01부터 | 같은 영역코드에서 101부터 | 승인 FR ID(예: FR1.1)를 반드시 병기 |
| 비기능 요구사항 | `NFR-분류-NN` | 01부터 | 101부터 | 승인 NFR ID(예: NFR1) 병기 |
| 업무규칙 | `BR-NN` | 01부터 | 101부터 | 기능 설계 규칙 ID(예: BR2.1) 병기 |
| 화면 | `SCR_영역_NN` | 01부터 | 51부터 | 초안 ID(W01·H-01 등), v2.2 PNG 접두사, 기능 설계 W1~W8 병기 |
| 엔티티·테이블 | ERD v1 엔티티명 그대로 | ERD v1 13개 | 이름 뒤에 "(가칭)" | 한글명·테이블명 제안(snake_case 복수형) 병기 |
| 분석 기능 | `BDA-NN` | BDA-01부터 | BDA-101부터 | 관련 FR·화면·엔티티 병기 |
| 데이터 요구사항 | `DR-NN` | DR-01부터(목록은 05 DB 요구사항 분석서 2.1절) | DR-101부터(목록은 06 DB 요구사항 분석서 2절) | 관련 FR·엔티티 병기. 목록은 각 DB 문서가 정본이고 이 파일에는 규칙만 둔다 |
| 보류·미정 기능 | `DEF-NN` | 해당 없음 | DEF-01부터 | 출처 절 병기 |
| 제외·범위 밖 | `EXC-NN` | 해당 없음 | EXC-01부터 | 출처 절 병기 |

- 번호는 순서일 뿐 우선순위가 아니다. 우선순위는 12절 규칙으로 따로 적는다.
- 10월 ID(01~49, 화면 01~50)와 12월 가칭 ID(101~, 화면 51~)는 겹치지 않는다.
- 10월 문서는 10월에 하지 않는 항목을 가리킬 때 12월 계획판 ID(FR-*-101~, DEF-NN, EXC-NN)를 참조용으로 쓸 수 있다. 이때 그 항목은 미승인 계획이다.
- 문서 안에서만 쓰는 보조 번호(예: 05 문서의 관계 번호 R-01~R-19)는 다른 문서가 인용하지 않는 한 이 파일에 올리지 않는다.
- 팀원은 실명으로 적는다. GitHub 이슈·팀 문서의 번호 표기와는 이재민(팀장) = 팀원 1, 이영연 = 팀원 2, 최수영 = 팀원 3, 이채아 = 팀원 4로 대응한다.
- 과거 실험(C01/C02) 원문·발췌·생성 응답은 어떤 문서에도 옮기지 않는다. 데이터 예시가 필요하면 "합성 예시"로 새로 만든다.

## 2. 승인 요구사항 전수 분류

## 11. 용어집

| 용어 | 정의 |
|---|---|
| Catch | 구직자의 GitHub 기록에서 확인한 작업 하나를 작업 사실·본인 기여·근거·설명 초안으로 정리한 자산. 옛 용어 '증거카드'는 쓰지 않는다 |
| Catch 제목(title) | F가 '무엇을 했나'를 짧은 명사구로 생성한 Catch 이름. 구직자는 고칠 수 없다(9/24) |
| 작업 사실(workFacts) | 근거에서 관측한 작업 내용 목록. 관측하지 않은 동기·성과를 넣지 않는다 |
| 본인 기여(subjectContribution) | 해당 작업에서 구직자 본인에게 귀속되는 기여. 타인 기여를 본인에게 귀속하지 않는다 |
| 근거 | Catch의 사실을 뒷받침하는 GitHub 출처(URL·리비전)와 표현 사실·기여 범위·누락/잘림 한계. 등록 후 정본은 CatchEvidence |
| 후보(작업 후보) | worker가 근거와 본인 기여를 확인해 등록 기준을 충족한다고 제공한 작업 단위(WorkCandidate). 등록되면 Catch가 된다 |
| 미제공 사유(notProvided) | 근거 부족·기준 미달로 후보를 제공하지 않은 이유. 수집·생성 오류(failures)와 구분한다 |
| 설명 초안(draft) | 근거에 연결된 짧은 Catch 설명. 생성됨·실패·미생성 상태를 가지며 생성만으로 공개되지 않는다 |
| 최소 생각해볼 질문(reflection) | 구직자가 경험을 고르도록 돕는 질문. 본인만 보고 답변은 저장하지 않는다 |
| 확인(confirmation) | 구직자가 근거·본인 기여를 확인했다는 표시. 공개와 별개다 |
| 불일치 표시(mismatch) | 구직자가 Catch 내용이 기록과 맞지 않는다고 표시한 것. 공개를 막지 않는다(9/24) |
| 공개·미공개 | Catch의 공개 상태 두 가지(PUBLIC·PRIVATE). 최초는 미공개. 숨김을 따로 구분하지 않는다(9/24) |
| 숨기기 | 공개 Catch를 미공개로 바꾸는 행동. 기존 링크에도 다음 요청부터 반영된다 |
| 원본 보호(SOURCE_PRIVATE) | 원본 저장소의 비공개 전환이 확인되어 관련 Catch를 수신자에게 보이지 않게 한 상태. 일시 조회 실패와 구분한다 |
| 공유 링크 | 구직자가 발행해 전달하는 URL. 소유자의 현재 공개 Catch 전체와 기본 프로필을 연다. 특정 Catch와 연결하지 않는다 |
| 링크 제목 | 발행자가 링크를 구분하는 필수 이름. 수신자에게 보이지 않는다 |
| 발행·중단·만료 | 링크를 만드는 행동 / 소유자가 링크를 끄는 행동 / 발행 30일 뒤 자동으로 열람 불가가 되는 것. 중단·만료 링크는 되살리지 않는다 |
| 링크 수신자 | 링크를 받아 로그인 없이 열람하는 사람. 10월의 두 번째 사용자 |

| 선정 저장소 | 팀이 사전 선정한 지원 공개 저장소 목록. 10월 분석 대상은 이 안에서만 고른다 |

## 12. 우선순위 규칙

**10월 MVP판**은 M01~M07 전체가 첫 MVP 완료 조건이므로(scope-document 「완료 판정」, 10월 요구사항 「추적성과 첫 MVP 완료 판정」) M01~M07에 연결된 승인 FR·NFR과 그 적용에 필요한 9/24 팀장 결정 FR을 모두 **상**으로 둔다. 구현 순서는 우선순위와 별개이며 bolt-plan의 첫 연결 순서와 개발 이슈를 따른다(예: FR-LNK-05~07은 기본 발행 뒤에 구현해도 완료 전 필수이므로 상). scope-document가 "후속 검토 후보 — 개발 약속 아님"으로 둔 기능(DEF-07)은 10월 우선순위를 매기지 않는다. **12월 계획판**은 팀장이 밝힌 순서만 따른다. 대표 구성(FR-REP-101~103)은 1순위이므로 **상**, 운영 기능(FR-OPS-101~104)은 "후순위, 가능하면 포함"이므로 **하**, 순서를 밝히지 않은 나머지 포함 기능은 **중(미정)**으로 적는다. 12월 범위 보완은 "순서를 밝히지 않은 항목을 후순위로 해석하지 않는다"고 적었으므로 중(미정)을 하로 낮추지 않는다. 복수 대표 프리셋(FR-REP-104)은 "이 우선순위에 넣지 않았다"는 문장에 따라 중(미정)이다. 보류·제외 항목은 우선순위를 매기지 않는다. 유스케이스의 우선순위는 관련 FR 가운데 가장 높은 우선순위를 따른다(10월 유스케이스는 모두 상).
