## 0. 왜 지금 정했나

이번 주는 학습 주간이라 코드가 거의 없다. **규칙을 바꾸는 비용이 가장 싼 시점**이고, 다음 주부터 코드가 쌓이면 되돌리기 어려워진다.

그리고 우리에게는 다른 팀에 없는 이유가 하나 더 있다.

**우리 레포는 우리가 만드는 서비스가 읽을 데이터다.**

CatchU는 GitHub 기록에서 증거카드를 뽑는다. 그 대상이 될 수 있는 레포를 우리가 지금 만들고 있다. PoC에서 실제로 측정한 결과가 두 가지 있다.

**실측 1 — PR 없이 main 직행한 레포는 카드 등급이 떨어진다.**
우리 파이프라인은 "저자가 명시적으로 묶은 작업 단위"(A등급)와 "시스템이 추정한 묶음"(B등급)을 구분한다. PR과 머지 커밋이 A등급을 만든다. 그게 없으면 커밋들을 파일 경로와 시간 근접으로 **추정**해야 하고, 전부 B로 떨어진다. 샘플로 돌린 레포 중 하나가 정확히 이 경우였다.

**실측 2 — "무엇을"은 코드에서 복원되지만 "왜"는 커밋 메시지에만 있다.**
커밋 메시지가 "fix" 한 줄인 레포를 돌려봤다. 무엇을 바꿨는지는 diff로 복원됐다. 왜 그렇게 바꿨는지는 **어디에서도 복원되지 않았다.** 코드에 남지 않는 정보다.

즉 아래 규칙들은 "좋은 개발 습관"이라서가 아니라, **우리 서비스가 읽었을 때 무엇이 남는지를 실제로 재본 결과**다.

부수적으로 이 기록은 각자의 자산이기도 하다. 20주 뒤 이 레포는 4인 각자의 포트폴리오 근거가 된다.

## 1. 레포 구조

**모노레포 1개**, 최상위 디렉터리는 배포 단위와 1:1로 대응.

```
CatchU/
├─ web/      Next.js — 사용자 화면
├─ api/      NestJS — API 서버
├─ worker/   FastAPI — 수집·카드 추출
└─ docs/     문서 정본
```

**왜 모노레포인가**: 나중에 쪼개는 것이 나중에 합치는 것보다 쉽다. 지금 결정을 유예하는 비용이 가장 낮은 선택이다.

**왜 `FE/BE`가 아닌가**: 백엔드가 2벌(API 서버 + 분석 워커)이라 `BE/` 안에 다시 둘이 들어간다. 그러면 최상위 디렉터리가 아무 배포 단위에도 대응하지 않는 껍데기가 되고, 9월 배포 때 경로 필터·빌드 설정이 한 단계씩 복잡해진다.

## 2. 브랜치

```
main   배포 브랜치
 └─ dev   통합 브랜치
     ├─ web/login
     ├─ api/auth
     ├─ worker/extract-cards
     └─ docs/컨벤션
```

- 작업 브랜치 이름은 `영역/작업내용`. 짧게 쓰고 머지되면 지운다.
- **문서도 같은 규칙**을 따른다. `docs/`도 PR로 올린다. 규칙이 하나여야 "이건 어느 쪽이지"를 매번 판정하지 않는다.
- `web`·`api`처럼 중간 통합 브랜치는 **두지 않는다.** 검증할 것이 없는데 머지 단계만 늘고, 오히려 프론트-백엔드 통합이 늦어진다.
- **dev는 지금부터 둔다.**

**dev에 대한 정직한 고지**: 9월 초 CI가 붙기 전까지 dev는 자동 검증을 하지 않는다. 그때까지는 "머지가 한 번 더 필요한 main"에 가깝다. 그럼에도 지금 만드는 이유는, 나중에 브랜치 정책을 바꾸는 비용이 더 크기 때문이다.

## 3. 머지

레포 설정에서 **merge commit만 허용**하고 squash·rebase 머지는 껐다.

| | 브랜치의 중간 커밋 | 작업 단위 경계 |
|---|---|---|
| Squash | 사라짐 | 사라짐 |
| Rebase | 남음 | 사라짐 |
| **Merge commit** | **남음** | **남음** |

우리가 카드에서 가장 값지다고 본 것이 **"시도했다가 버린 흔적"**이다. 낙관적 락을 넣었다가 비관적 락으로 바꾼 과정 같은 것. 완성된 코드에는 안 보이고 중간 커밋에만 있다. squash는 그걸 지운다.

머지 커밋은 "이 커밋들이 한 작업이었다"를 기록에 남긴다(§0 실측 1의 A등급).

**주의**: 끈 것은 *머지 버튼*이지 rebase 명령 자체가 아니다.
→ **브랜치 최신화는 `git rebase dev`, dev에 올릴 때는 merge commit.**

**대가**: main 히스토리가 일직선이 아니게 된다. 일반적으로는 단점이지만, 우리는 그 구조 자체가 데이터다.

## 4. 커밋 메시지

**규칙은 둘. ① 접두사를 붙인다. ② 바꾼 이유를 한 줄이라도 남긴다.**

Conventional Commits 전체를 가져오지는 않는다. 지키기 어렵고, 우리가 실제로 손해 본 지점은 형식이 아니라 **이유의 부재**였다(§0 실측 2). 다만 접두사는 **필수**로 둔다 — 커밋 종류가 한눈에 갈리면 히스토리를 나중에 읽는 쪽(사람이든 우리 파이프라인이든)이 훨씬 싸게 읽는다.

### 접두사 5종 (필수)

| 접두사 | 쓰는 경우 |
|---|---|
| `feat:` | 기능 추가·변경 |
| `fix:` | 버그 수정 |
| `refactor:` | 동작은 그대로, 코드 구조 개선 (리뷰 지적 반영 포함) |
| `docs:` | 문서 |
| `chore:` | 설정·빌드·의존성 등 나머지 |

- **5종 외에는 쓰지 않는다.** 애매하면 `chore:`.
- **영역 표기(`feat(api):` 등)는 쓰지 않는다.** 영역은 브랜치 이름(§2)과 변경 파일 경로에 이미 있다.

### 예시

```
feat: 증거카드 목록 화면 — 카드 희박 시 개수 대신 빈 상태 문구로
fix: 커밋 묶음 등급 판정에서 머지 커밋이 B로 떨어지던 문제
refactor: 카드 추출기에서 GitHub 수집부 분리 — 리뷰 지적 반영
docs: 레포 구조·컨벤션 확정 반영 (커밋 접두사 필수화)
chore: worker 의존성에 httpx 추가
```

```
❌ fix                        접두사만 있고 이유가 없다
❌ 수정                       접두사도 이유도 없다
❌ feat(api): 로그인 추가      영역 표기는 쓰지 않는다
❌ update: 문서 정리          5종 밖의 접두사
```

**언어**: 접두사는 영문 5종 고정, 설명은 한국어.

## 5. 기록에 관한 두 가지

- **기각 사유는 PR 본문에.** "이 방향으로 가려다 접었다"는 브랜치를 지워도 PR 본문에는 영구히 남는다. 팀 관행(결정은 기각 사유까지 기록)을 GitHub에서 잇는 방법이다.
- **Issue는 그라운드 룰대로.** 버그를 30분 이상 못 잡으면 Issue 작성 + Slack.

## 6. 다음 주부터 달라지는 것 (예고)

현재 레포는 private이고 조직 플랜을 아직 구독하지 않았다. 이 상태에서는 **브랜치 보호가 걸리지 않는다** — 지금은 main에 직접 push해도 막히지 않는다.

다음 주 구독 후 main·dev에 다음을 건다.

- PR 없이 직접 push 금지 (승인자 수는 0 — 혼자 작업하는 밤에 막히지 않게)
- force push 금지, 브랜치 삭제 금지

**즉 이번 주는 합의로만, 다음 주부터는 기술적으로 막힌다.** 갑자기 안 되는 게 아니라 예고된 것으로 알아두면 좋겠다.
