## 0. 왜 지금 정했나

이 문서를 쓴 2026-08-18 주는 학습 주간이라 코드가 거의 없다. **규칙을 바꾸는 비용이 가장 싼 시점**이고, 코드가 쌓이기 시작하면 되돌리기 어려워진다.

그리고 우리에게는 다른 팀에 없는 이유가 하나 더 있다.

**우리 레포는 우리가 만드는 서비스가 읽을 데이터다.**

CatchU는 GitHub 기록에서 증거카드를 뽑는다. 그 대상이 될 수 있는 레포를 우리가 지금 만들고 있다. PoC에서 실제로 측정한 결과가 두 가지 있다.

**실측 1 — PR 없이 main 직행한 레포는 카드 등급이 떨어진다.**
우리 파이프라인은 "저자가 명시적으로 묶은 작업 단위"(A등급)와 "시스템이 추정한 묶음"(B등급)을 구분한다. PR과 머지 커밋이 A등급을 만든다. 그게 없으면 커밋들을 파일 경로와 시간 근접으로 **추정**해야 하고, 전부 B로 떨어진다. 샘플로 돌린 레포 중 하나가 정확히 이 경우였다.

**실측 2 — "무엇을"은 코드에서 복원되지만 "왜"는 커밋 메시지에만 있다.**
커밋 메시지가 "fix" 한 줄인 레포를 돌려봤다. 무엇을 바꿨는지는 diff로 복원됐다. 왜 그렇게 바꿨는지는 **어디에서도 복원되지 않았다.** 코드에 남지 않는 정보다.

즉 아래 규칙들은 "좋은 개발 습관"이라서가 아니라, **우리 서비스가 읽었을 때 무엇이 남는지를 실제로 재본 결과**다.

부수적으로 이 기록은 각자의 자산이기도 하다. 20주 뒤 이 레포는 4인 각자의 포트폴리오 근거가 된다.

## 1. 레포 구조

**모노레포 1개**, 최상위 디렉터리는 배포 단위와 1:1로 대응.

```
CatchU/
├─ web/      Next.js — 사용자 화면
├─ api/      NestJS — API 서버
├─ worker/   FastAPI — 수집·카드 추출
└─ docs/     문서 정본
```

> **스택 표기의 지위 (2026-09-13 확정)**: 위 트리의 Next.js·NestJS·FastAPI는 2026-09-09 AI-DLC 실현 가능성 검토(Q4)의 검토안이었고, 요구사항 팀 검토를 마친 뒤 2026-09-13 팀장이 그대로 확정했다. 배포 대상은 소속 기관의 지원이 확보된 네이버 클라우드 플랫폼(NCP)이며, 검토안의 AWS(ECS·ECR·S3)를 대체한다. 결정 기록은 `docs/ai-dlc-input-mvp/CatchU_mvp_input.md` §2.1~§2.2이고, 작업 큐 등 세부 구성은 AI-DLC 설계 단계에서 정한다. 디렉터리 구조(배포 단위 1:1)는 변경 없다.

**왜 모노레포인가**: 나중에 쪼개는 것이 나중에 합치는 것보다 쉽다. 지금 결정을 유예하는 비용이 가장 낮은 선택이다.

**왜 `FE/BE`가 아닌가**: 백엔드가 2벌(API 서버 + 분석 워커)이라 `BE/` 안에 다시 둘이 들어간다. 그러면 최상위 디렉터리가 아무 배포 단위에도 대응하지 않는 껍데기가 되고, 9월 배포 때 경로 필터·빌드 설정이 한 단계씩 복잡해진다.

## 2. 브랜치

```
main   배포 브랜치
 └─ dev   통합 브랜치
     ├─ web/login
     ├─ api/auth
     ├─ worker/extract-cards
     └─ docs/컨벤션
```

- 작업 브랜치 이름은 `영역/작업내용`. 짧게 쓰고 머지되면 지운다.
- **문서도 같은 규칙**을 따른다. `docs/`도 PR로 올린다. 규칙이 하나여야 "이건 어느 쪽이지"를 매번 판정하지 않는다.
- `web`·`api`처럼 상시 영역별 중간 통합 브랜치는 **두지 않는다.** 검증할 것이 없는데 머지 단계만 늘고, 오히려 프론트-백엔드 통합이 늦어진다. 10월 MVP 코딩에는 AI-DLC Construction의 intent 통합 브랜치(§2.1)·Bolt 경계 rebase도 적용하지 않는다([코딩 운영](CatchU_작업관리.md#코딩-운영)). 연결 검증이 필요한 작업의 임시 예외는 아래 운영안을 검토한다.
- **dev는 코드가 쌓이기 전에 미리 두었다.**

**dev의 검증**: dev 대상 PR마다 [CI](../.github/workflows/ci.yml)가 web·api·worker README의 검사 명령과 AI가 읽는 문서의 크기 검사를 실행하고, 이를 통과해야 머지할 수 있다(필수 상태 검사, §7). 관련 경로가 바뀌지 않은 서비스의 검사는 건너뛰며, 건너뛴 검사는 통과로 친다. 어떤 경로가 어느 검사를 돌리는지는 CI 파일에 있다. CI 통과가 사람 리뷰를 대신하지 않는다. PR과 승인 1건이 필요하며(§7), 검토자는 무엇을 확인했는지 설명할 수 있어야 한다([작업관리](CatchU_작업관리.md)). dev를 코드가 쌓이기 전에 둔 이유는 나중에 브랜치 정책을 바꾸는 비용이 더 크기 때문이다.

### 임시 통합 브랜치 운영안

> 지위: 2026-09-20 논의 방향을 반영한 검토안. 저장소 설정이나 AI-DLC 규칙의 적용 완료를 뜻하지 않는다.

**기본은 작업별 PR을 `dev`로 보낸다. 여러 작업을 먼저 합쳐 연결 검증할 필요가 있을 때만 임시 통합 브랜치를 사용한다.** 작업을 여러 개로 나누거나 여러 사람이 참여한다는 이유만으로 만들지 않는다. 예를 들어 “worker의 실패 결과가 api에 반영되고 web에서 실패 안내로 보인다”를 하나의 확인 대상으로 묶을 수 있다.

- 관련 이슈에 함께 확인할 완료 결과, 포함할 작업, 통합을 정리할 사람과 검토 상대를 짧게 남긴다. 각 담당자는 자기 변경·검사·결함 수정을 맡으며, 통합 담당을 팀원 1로 고정하지 않는다.
- 임시 통합 브랜치는 `dev`에서 만들고, 포함된 작업 브랜치는 이를 기준으로 나눈다. 작업 PR의 대상은 해당 통합 브랜치이며, 최종 PR의 대상은 `dev`다. 관련 없는 변경은 묶음에 넣지 않는다.
- 작업 PR에서는 해당 변경을 검토하고, 최종 `dev` PR에서는 합쳐진 동작·계약과 `dev` 대비 변경을 확인한다. 기존 리뷰·검사 증거를 재사용하며 통합으로 생긴 영향에 필요한 검사를 추가한다. `dev` 반영은 기존 PR·사람 승인·merge commit 기준을 따른다.
- 공유 통합 브랜치는 `dev`의 변경을 merge로 받아 갱신하며 rebase·강제 push로 이력을 재작성하지 않는다. `dev` 반영과 관련 작업 종료를 확인하면 사용이 끝난 통합·작업 브랜치를 정리한다.

| 병합 조건 | 코드 PR은 최종 SHA의 CI 통과·작성자 외 승인·대화 해소 후 merge commit. 첫 CI 작성 전 골격 작성·리뷰는 가능하나 병합 대기. 이 문서의 조건이 GitHub에 이미 설정됐다는 뜻은 아님 |

| 공동 브랜치 최신화 | 여러 팀원이 사용하는 공동 브랜치를 rebase·강제 push하지 않음. dev 변경 반영이 필요하면 팀원 1이 작업 PR 경계에서 조율하고, 공동 브랜치에서 나눈 동기화 작업 브랜치에 dev를 merge해 검사·리뷰 후 공동 브랜치로 PR. 진행 중 작업은 알려진 새 기준으로 최신화. 원본 Construction 규칙의 Bolt 경계 최신화 설명을 별도 Bolt가 없는 이번 작업에 그대로 실행하지 않음 |
| 종료·삭제 | 개인 작업 브랜치는 해당 PR 병합과 다른 작업의 참조 해소 후 삭제. 공동 브랜치는 dev 최종 PR 병합·열린 하위 PR/후속 작업 없음·검증 증거 보존 확인 후 삭제. 이 안내를 승인했다고 실제 삭제를 실행한 것은 아님 |

원본 계획의 공유 이력 보존과 merge commit 원칙을 따른다. branch/ruleset 조작은 별도 실행 작업으로 수행하며, `web/*` 전체를 보호 대상으로 묶어 개인 작업 브랜치까지 제한하지 않는다.

## 3. 머지

레포 설정에서 **merge commit만 허용**하고 squash·rebase 머지는 껐다.

| | 브랜치의 중간 커밋 | 작업 단위 경계 |
|---|---|---|
| Squash | 사라짐 | 사라짐 |
| Rebase | 남음 | 사라짐 |
| **Merge commit** | **남음** | **남음** |

우리가 카드에서 가장 값지다고 본 것이 **"시도했다가 버린 흔적"**이다. 낙관적 락을 넣었다가 비관적 락으로 바꾼 과정 같은 것. 완성된 코드에는 안 보이고 중간 커밋에만 있다. squash는 그걸 지운다.

머지 커밋은 "이 커밋들이 한 작업이었다"를 기록에 남긴다(§0 실측 1의 A등급).

**주의**: 끈 것은 *머지 버튼*이지 rebase 명령 자체가 아니다.
→ **개인 작업 브랜치 최신화는 합칠 대상 브랜치를 기준으로 rebase한다(기본은 `git rebase dev`). dev에 올릴 때는 merge commit.** §2 운영안의 공유 통합 브랜치는 그 절의 갱신 방법을 따른다.

**강제 푸시**: rebase는 커밋을 재작성하므로 해시가 바뀐다. 이미 원격에 올린 브랜치를 rebase하면 일반 push가 거부되고 강제 푸시가 필요하다. 이때 `--force`는 원격 상태와 무관하게 덮어쓰므로, PR 리뷰 중 다른 사람이 남긴 커밋을 지울 수 있다. `--force-with-lease`는 그 경우 거부된다.
→ **강제 푸시는 `--force-with-lease`로, 개인 작업 브랜치에 한해서만.** §2 운영안의 공유 통합 브랜치는 제외한다. `main`·`dev`는 강제 푸시 자체가 차단되어 있다(§7).

**대가**: main 히스토리가 일직선이 아니게 된다. 일반적으로는 단점이지만, 우리는 그 구조 자체가 데이터다.

## 4. 커밋 메시지

**규칙은 둘. ① 접두사를 붙인다. ② 바꾼 이유를 한 줄이라도 남긴다.**

Conventional Commits 전체를 가져오지는 않는다. 지키기 어렵고, 우리가 실제로 손해 본 지점은 형식이 아니라 **이유의 부재**였다(§0 실측 2). 다만 접두사는 **필수**로 둔다 — 커밋 종류가 한눈에 갈리면 히스토리를 나중에 읽는 쪽(사람이든 우리 파이프라인이든)이 훨씬 싸게 읽는다.

### 접두사 5종 (필수)

| 접두사 | 쓰는 경우 |
|---|---|
| `feat:` | 기능 추가·변경 |
| `fix:` | 버그 수정 |
| `refactor:` | 동작은 그대로, 코드 구조 개선 (리뷰 지적 반영 포함) |
| `docs:` | 문서 |
| `chore:` | 설정·빌드·의존성 등 나머지 |

- **5종 외에는 쓰지 않는다.** 애매하면 `chore:`.
- **영역 표기(`feat(api):` 등)는 쓰지 않는다.** 영역은 브랜치 이름(§2)과 변경 파일 경로에 이미 있다.

### 예시

```
feat: 증거카드 목록 화면 — 카드 희박 시 개수 대신 빈 상태 문구로
```

## 7. 브랜치 보호 설정 내역

> **지위: 확정 (2026-08-24)**

### 머지 방식 (레포 전체 설정)

| 설정 | 값 |
|---|---|
| Allow merge commits | ✅ |
| Allow squash merging | ⬜ 끔 |
| Allow rebase merging | ⬜ 끔 |

사유는 §3 — 브랜치의 중간 커밋과 작업 단위 경계를 둘 다 남기는 방식이 merge commit뿐이다.

### 브랜치 보호 (브랜치별 ruleset)

`main`과 `dev`에 각각 ruleset 1벌씩 두고, dev에는 필수 상태 검사만 담은 `dev-ci`를 하나 더 둔다. 대상 브랜치는 이름으로 정확히 지정한다(넓은 패턴을 쓰지 않는 이유는 §6 #8).

| 규칙 | `main` | `dev` |
|---|---|---|
| PR 없이 머지 금지 (Require a pull request before merging) | ✅ | ✅ |
| 승인 (Required approvals) | 1 | 1 |
| 리뷰 대화 해소 후 머지 (Require conversation resolution before merging) | ✅ | ✅ |
| 강제 푸시 차단 (Block force pushes) | ✅ | ✅ |
| 삭제 차단 (Restrict deletions) | ✅ | ✅ |
| 필수 상태 검사 (Require status checks to pass) | ⬜ 배포 PR을 시작할 때 정함 | ✅ `changes`·`docs-size`·`web`·`api`·`worker` (`dev-ci`, PR #208 머지 직후 적용) |

켜지 않기로 한 항목은 이 표에 없다 — 그 목록과 사유는 §6에 있다.

`main`·`dev` ruleset은 내용이 같아도 **분리해서 유지한다.** 브랜치마다 필수 상태 검사를 따로 정할 수 있게 하기 위해서다. 필수 상태 검사의 이름은 [CI](../.github/workflows/ci.yml)의 job 이름이므로, job 이름을 바꾸면 `dev-ci`도 함께 고친다.

**우회 권한(bypass)**: 조직 역할이 Organization admin인 사람(현재 이재민 1인)에 한해 **"pull request에 한해서만"**. PR을 여는 것 자체는 면제되지 않고 승인 대기만 면제된다. 전면 우회를 주지 않은 이유는 §3에 있다 — PR 없이 머지하면 머지 커밋이 생기지 않아 "이 커밋들이 한 작업이었다"는 기록이 남지 않는다. 우회 권한은 그 ruleset의 규칙에만 적용되며, `dev-ci`에는 우회 권한을 두지 않는다. 그래서 승인 대기를 건너뛰는 우회 병합도 CI는 통과해야 한다. CI 고장으로 아무도 머지하지 못하면 Organization admin이 `dev-ci`를 잠시 끄고, 끈 사실과 이유를 관련 이슈에 남긴다.

### 팀원의 레포 접근 권한 등급

**Write.** GitHub Organization 팀 `CatchU-dev`에 부여했다(통합 브랜치 `dev`와는 다른 것이다).

- **Read로는 안 된다** — 승인 버튼은 눌리지만 효력이 없다. 화면에는 승인 1건으로 표시되면서 머지는 계속 차단되므로, 승인한 본인만 처리했다고 생각하게 되어 조용히 어긋난다.
- **`Maintain`·`Admin`도 쓰지 않는다** — 레포 설정 접근 권한이 딸려 오기 때문이다. (바로 위 우회 권한의 Organization admin은 조직 전체의 역할이고, 이 등급들은 레포 하나에 대한 접근 권한이다. 층위가 다르다.)

### 설정 후 검증 (실측)

규칙이 우리 워크플로와 충돌하지 않는지 실제로 확인했다.

| 확인 항목 | 결과 |
|---|---|
| `dev`에 직접 push | 거부됨 ✅ |
| 작업 브랜치에서 `--force-with-lease` push | 통과 ✅ |
| PR 승인 없이 머지 시도 | 차단됨 ✅ |

두 번째 항목이 이 검증의 핵심이다. 여기가 막히면 §3의 브랜치 최신화 방식을 쓸 수 없다.
