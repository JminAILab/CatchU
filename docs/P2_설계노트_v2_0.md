# P2 설계 노트 — HR·리크루터 페르소나에서 도출한 것들

**버전:** v2.0 · 2026년 9월 1일
**원본 문서:** `대표 페르소나 P2 — HR·리크루터 v2.0`
**용도:** 기능명세서 작성 시 입력값. 페르소나 본문에서 분리해 별도 관리한다.

---

## 1. 개정 이력

### v1.0 (2026-09-01)

P1·P3를 쓴 뒤, 확정 방향에서 **검색·추천·DM의 실제 주체**를 정의하기 위해 신설. 원래 기업 페르소나 하나(김도윤)에 HR이 "확장 대상"으로 묶여 있었으나 두 사람은 **하는 일이 반대**여서 분리했다.

### v1.0 → v2.0 (2026-09-01) — 팀 논의 반영

| 구분 | 내용 |
| --- | --- |
| **삭제** | "채용이 절반"이라는 비중 수치 / **"몇 명을 HM에게 가져다줬는가로 성과가 측정된다"** — 우리가 확인한 바 없는 내용 / "채용 규모가 줄어서"라는 전제 / "개발자는 주당 수십 건의 비슷한 메시지를 받는다" / **POV-A(탐색)** |
| **변경** | 한 줄 명제 단순화 / **대상에서 "신입" 제거** (2장) / 고통 ②를 **"HM이 작성한 JD를 이해하지 못한다 → 자바 개발자에게 파이썬 포지션"** 흐름으로 재정리 / "요약 카드" → **"경험 요약"** (5장) / 듣는 것에 "**괜찮은** 지원자 없어요?" |
| **추가** | **POV-C(접촉)** — 후보가 제안에서 무엇을 알고 싶어 하는지 / HMW-5를 "무시당하지 않게" → **"후보가 원하는 정보를 담아 보내게"** / 시나리오 ③에 후보 요청 항목 표시 |

**삭제 사유 세 가지**

- **성과 측정 문장** — "HM에게 몇 명을 넘겼는가"는 실제 HR의 평가 기준일 수도 있으나 **우리가 확인한 적이 없다.** 추론을 사실처럼 적으면 이후 설계가 그 위에 쌓인다
- **"채용 규모가 줄어서"** — 소싱을 하는 이유로 제시했으나 인과가 명확하지 않다. 규모 축소 없이도 개발자는 원래 찾기 어렵다
- **"주당 수십 건"** — 경력 개발자 대상 링크드인 조사 수치이며, 박서연 본인의 고통이 아니라 상대방 사정이다

## 2. "신입" 제거가 만든 변화 — 이번 개정의 핵심

### 무엇이 바뀌었나

v1.0의 최대 리스크는 **"신입 채용에서 HR이 실제로 소싱을 하는가"**였다. 팀의 답은 **"하지 않는다"**였고, 그래서 대상에서 신입을 뺐다.

| | v1.0 | v2.0 |
| --- | --- | --- |
| P2가 찾는 대상 | 신입 개발자 | **개발자 전반. 소싱은 주로 경력자** |
| 전제 검증 상태 | 미검증 리스크 | **부분 해소** — 신입 소싱은 드물다는 것을 인정하고 범위를 조정 |

### 새로 생긴 긴장 — P1과 P2가 다른 사람을 가리킨다

| | 대상 | 근거 |
| --- | --- | --- |
| **확정 정의서 메인 타깃** | 취준생·신입 개발자 | 8/31 결정 |
| **P1 페르소나** | 취준생·신입 | — |
| **P2가 찾는 사람** | **경력 개발자** | 이번 개정 |

**즉 P1이 프로필을 올려도, P2가 찾는 사람은 P1이 아니다.**

### 팀의 해소 논리 — 시간축

> 당장은 신입 개발자 중심으로 하지만, 그들의 경력이 쌓이면 **3~4년 뒤 우리 사이트가 헤드헌팅 사이트가 된다.**

지금 가입한 신입이 경력자가 되면서 소싱 대상이 된다는 구조다. 서비스 논리로는 성립한다.

### 다만 발표에서 정직하게 다뤄야 한다

이 논리는 **"지금은 매칭이 활발하게 일어나지 않는다"**를 함께 인정하는 것이다. 숨기면 질문받고, 먼저 말하면 설계 의도가 된다.

**정리 방향 후보**

| 안 | 내용 | 영향 |
| --- | --- | --- |
| A | **1단계는 "증명 도구", 2단계가 "매칭 플랫폼"**이라고 명시 | 신입에게는 지금 당장 가치가 있고(증거 카드·링크 발행), 매칭은 사용자가 쌓인 뒤 작동. **가장 정직하고 방어 가능** |
| B | 신입 소싱을 하는 소수(스타트업·중소기업)를 P2로 유지 | v1.0 A안. 이번 논의로 사실상 기각됨 |
| C | 확정 정의서의 메인 타깃을 경력자까지 넓힘 | 8/31 결정을 뒤집는 것. 권하지 않음 |

> **A안을 권한다.** P1의 가치(경험 재발견·증거 카드·링크 발행)는 매칭이 없어도 성립한다. KPI v3.0이 Primary를 카드 사실 일치율로 잡은 것과도 맞물린다 — **우리가 지금 증명할 수 있는 것은 매칭이 아니라 증거의 품질이다.**

### 남은 검증 질문

- 개발자를 뽑을 때 지원자를 기다리는가, 찾아 나서는가 — **경력 채용에서**
- 찾아 나선다면 어디서 찾는가 — 링크드인·플랫폼·지인 추천
- 개발 직군 이력서에서 무엇을 보고 1차로 거르는가
- HM이 준 JD를 이해하지 못해 곤란했던 경험이 있는가
- HM에게 후보를 넘길 때 무엇을 함께 전달하는가

## 3. HR과 HM이 정반대를 요구한다 — 핵심 긴장

| | HM (P3) | HR (P2) |
| --- | --- | --- |
| AI 판단에 대한 태도 | **거부** — "내 판단을 대신하지 마라" *[인터뷰]* | **환영** — JD 적합도 % 표시가 유용하다 *[인터뷰]* |
| 원하는 출력 형태 | 근거 링크가 달린 원본 | 읽기 쉬운 요약, 가능하면 순위 |
| 이유 | 판단 책임이 자신에게 있음 | 기술을 몰라 판단할 수단이 없음 |

**우리는 원칙 1(평가하지 않는다)에 따라 HM 쪽 요구를 채택했다.** 그 결과 P2는 **원하는 것을 온전히 받지 못하는 사용자**가 된다.

### 이 긴장을 다루는 방법

| 방향 | 내용 | 원칙 1과의 관계 |
| --- | --- | --- |
| **활동의 사실을 말한다** | "React 저장소에 6개월간 주 3회 커밋" — 해석 없이 사실만 | ✔ 안전 |
| **조건 충족 여부를 표시** | "이 JD의 기술스택 3개 중 2개에 활동 이력 있음" | ✔ 확정 정의서의 "이 조건에 해당하는 사람이 있다"와 일치 |
| **용어를 풀어준다** | 기술 용어에 설명을 붙여 비개발자가 읽게 함 | ✔ 안전 |
| ~~적합도 % 표시~~ | 그리팅 방식 | ✗ 8/31 기각 |
| ~~후보 순위·랭킹~~ | | ✗ 원칙 1 |

> **HMW-3("판단을 대신하지 않으면서 비개발자의 판단을 돕는다")이 P2 설계의 핵심 질문이다.** 여기서 답을 못 찾으면 HR은 우리 서비스를 쓸 이유가 약해진다.

**세 번째 방향(용어 풀이)이 이번 개정으로 더 중요해졌다.** 고통 ②가 "HM이 쓴 JD를 이해하지 못한다"로 바뀌면서, 용어 풀이가 후보 화면뿐 아니라 **JD 화면에도 필요**해졌기 때문이다.

## 4. 신규 기능 제안 — 후보 요청 항목

### 배경

고통 ③과 POV-C에서 나온 요구다. **정보가 빠진 제안은 무시되는데, 무엇이 빠졌는지는 답이 오지 않는 이상 알 수 없다.** 이 고리를 끊으려면 후보 쪽에서 미리 알려주는 수밖에 없다.

### 제안 구조

| 측 | 화면 | 내용 |
| --- | --- | --- |
| **구직자 (P1)** | 프로필 설정 | **"제안에 이 항목들을 포함해주세요"** 체크 — 연봉 범위 · 근무형태 · 기술스택 · 위치 · 팀 규모 등 |
| **기업 (P2)** | DM 작성 화면 | 후보가 요청한 항목이 **입력란으로 표시**됨. 비어 있으면 인지시킴 |

### 8/28 결정과 이어진다

8월 28일 회의에서 **"제안 메시지에 핵심 정보 강제 포함 — 근무형태·연봉 등"**이 이미 논의되었다. 이번 제안은 그 결정을 **"기업이 일괄로 채우는 것"에서 "후보별로 요청 항목이 다른 것"**으로 구체화한 것이다.

### 원칙과의 관계

| 원칙 | 관계 |
| --- | --- |
| 원칙 1 (평가하지 않는다) | ✔ 충돌 없음 — 요구사항 전달이지 평가가 아니다 |
| 원칙 3 (공개 범위는 본인이 정한다) | ✔ 같은 계열 — 무엇을 받을지도 본인이 정한다 |

### 확정 정의서에 없다

7.1(구직자 측)·7.3(기업 측) 어디에도 이 기능이 없다. **기능 추가 여부를 팀에서 결정해야 한다.** 화면이 두 개(구직자 설정 + HR DM 작성) 늘어난다.

## 5. 용어 정리 — "카드"를 아무 데나 쓰지 않는다

팀 논의에서 **"요약 카드"가 "증거 카드"와 혼동된다**는 지적이 나왔다. 현재 확정 정의서 7.2는 두 가지를 모두 "카드"로 부른다.

| 확정 정의서 표기 | 대상 | 제안 |
| --- | --- | --- |
| 면접 **증거 카드** | 기술자(HM) | **유지** — 근거 링크가 달린 단위. "카드"가 맞다 |
| 기술 분석 **카드** | HR | **"경험 요약"으로 변경 제안** — 러프한 요약이라 성격이 다르다 |

**왜 구분해야 하나**

- 증거 카드는 **단위**다. 개별로 공개/숨김이 가능하고, 근거 링크가 달리고, 사실 일치율의 측정 대상이다
- HR이 보는 것은 **뷰**다. 여러 카드를 비개발자용으로 묶어 보여주는 층이다
- 같은 이름을 쓰면 기능명세에서 "카드를 숨기면 요약도 사라지는가" 같은 질문이 계속 나온다

→ **확정 정의서 7.2의 명칭 변경 여부를 팀에서 결정해야 한다.**

## 7. 페르소나가 만드는 설계 제약

| # | 제약 | 근거 |
| --- | --- | --- |
| 1 | **경험 요약은 비개발자가 읽을 수 있어야 한다** | 고통 ②. HR용 뷰의 존재 이유 그 자체 |
| 2 | **검색 결과가 비어 있으면 안 된다** | 조건을 정확히 모르는 사람이 쓴다. 0건은 곧 이탈 |
| 3 | **북마크에 메모가 붙어야 한다** | 시즌에 몰리는 업무 특성상, 지금 아닌 사람을 저장해두는 것이 실제 업무 방식 |
| 4 | **DM 작성 시 후보가 요청한 항목이 표시된다** | 고통 ③·4장 |
| 5 | **후보를 링크 하나로 HM에게 넘길 수 있어야 한다** | P2 → P3 연결 지점. 이게 없으면 두 페르소나가 끊긴다 |
| 6 | **JD 화면에도 용어 풀이가 필요하다** | **신설.** 고통 ②가 "HM이 쓴 JD를 이해 못 한다"로 바뀌면서, 용어 풀이의 적용 범위가 후보 화면에서 JD 화면까지 넓어졌다 |

### 제약 5가 두 페르소나를 잇는다

P2 시나리오 ④(전달)와 P3 시나리오 ①(후보 확인)은 **같은 링크의 양쪽 끝**이다. 기능명세에서 이 링크의 형태(권한·유효기간·열람 범위)를 정의해야 한다.
