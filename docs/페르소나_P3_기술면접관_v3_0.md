## 서비스에서 이 사람의 위치

**CatchU는 채용 프로세스를 대체하지 않는다.** 기업은 쓰던 ATS를 그대로 쓴다. 우리가 하는 일은 그 위에 **판단 재료를 얹는 것**이다.

김도윤은 ATS에서 지원자를 보다가, 링크를 통해 우리 화면으로 들어와 **자기소개서 · 포트폴리오 · 프로필 · 증거 카드**를 한 화면에서 확인한다. 카드를 검색하면 이 지원자에게 **물어볼 지점**이 드러난다.

| 구간 | 기업 ATS | CatchU |
| --- | --- | --- |
| 공고 게시 · 지원 접수 · 전형 관리 | ✔ | — |
| 지원자 서류 열람 | ✔ 기업이 받은 것 | ✔ 구직자가 등록한 것 + **GitHub 증거** |
| 주장의 근거 확인 | — | ✔ 카드 → 커밋 · PR |
| 면접 준비 — 물어볼 지점 찾기 | — | ✔ 카드 검색(RAG) |
| 면접 진행 · 평가 기록 | ✔ | — |

**두 가지 경로로 들어온다**

| 경로 | 내용 |
| --- | --- |
| **① 전달받는 경로** | HR(P2)이 추린 후보의 프로필 링크를 받아 확인한다 |
| **② 직접 탐색 경로** | 본인이 작성한 JD를 기준으로 심화 검색해 후보를 직접 본다 |

## 목표

**표면적인 목표**

- 좋은 개발자를 채용하는 것

**실질적인 목표**

1. 우리 팀과 잘 맞는 사람인지 확인하고 싶다
2. 지원자가 실제 프로젝트에서 **무엇을 했는지** 알고 싶다
3. GitHub와 프로젝트를 **빠르게** 이해하고 싶다
4. 근거 있는 기술 면접 질문을 **내 손으로** 준비하고 싶다
5. 판단을 **남에게 맡기지 않고** 내가 내리고 싶다 *[인터뷰]*

## 핵심 고통

### ① 시간 부족 *[인터뷰]*

- 개발 업무가 우선이라 면접 준비 시간이 부족하다
- **GitHub를 봐야 한다는 건 알지만 실제로는 확인하지 못한다**
- HR 담당자의 57.8%가 이력서를 10분 이내에 검토한다 *[조사]*

### ② 판단 근거 부족 *[추론]*

- README만으로는 **이 사람이 실제로 무엇을 했는지** 파악하기 어렵다
- 커밋만으로 역할을 판단하기 어렵다
- 프로젝트 설명이 대부분 비슷하다
- 무엇을 질문해야 할지 빠르게 떠오르지 않는다

### ③ 정보 분산 *[추론]*

- 이력서 · 포트폴리오 · GitHub · 블로그를 각각 열어 확인해야 한다

### ④ 지원자마다 자료의 성격이 다르다 *[인터뷰]*

- 도메인에 따라 GitHub를 아예 쓰지 않는 분야가 있다(예: 게임 업계 — 사내 저장소·비공개 코드)
- **GitHub 활동량을 기준으로 삼으면 공정성 문제가 생긴다**

### ⑤ 면접 이후 기록 부족 *[조사]*

- 평가 근거를 기억에 의존하게 되고, 협의 시 인상에 기대는 경우가 생긴다
- *(→ 서비스 범위 밖. `P3 설계 노트` 참조)*

## 필요한 것

| 항목 | 근거 |
| --- | --- |
| GitHub 핵심 활동 요약 | ① |
| **프로젝트에서 이 사람이 실제로 한 일** — 팀 프로젝트에서 누가 무엇을 했는지 구분 | ② |
| 기술 스택 자동 정리 | ①② |
| 프로젝트 핵심 요약 | ①② |
| **자료 정규화 뷰** — 지원자마다 제각각인 자료를 같은 형식으로 | ③④ *[인터뷰]* |
| **모든 항목에 한 뎁스 내 근거 링크** — 요약을 믿지 못해도 원본으로 바로 갈 수 있게 | ② *[인터뷰]* |
| **물어볼 지점이 되는 근거** — 질문 자체가 아니라, 질문을 만들 재료 | ② |

> **"기여도"라는 말을 쓰지 않는다.** 퍼센트로 읽히기 쉬운 표현이고, 우리는 비율을 계산하지 않는다. **"이 사람이 실제로 한 일"** 또는 **"누가 무엇을 했는지"**로 적는다.

> **[인터뷰]에서 명시적으로 거부된 것:** 점수화 · 등급화 · 강점 정리 · 공고 매칭. "내 판단을 대신하지 마라."

## 사용자의 언어

- 면접 전에 **5분 안에 질문거리가 손에 잡혔으면 좋겠다**
- GitHub와 이력서를 따로 열지 않고 **한 화면에서 보고 싶다**
- AI가 대신 판단하는 것이 아니라 **판단할 근거를 제공해 주었으면 좋겠다**
- 요약을 보여주더라도 **원본으로 바로 갈 수 있어야 믿는다** *[인터뷰]*

## POV — 관점 진술

### 메인 POV

> **기술 면접관 김도윤은 제한된 시간 안에 지원자의 핵심 역량과 실제로 한 일을 빠르게 파악할 수 있는 정보가 필요하다.**
> **왜냐하면 개발 업무와 면접을 병행하는 상황에서 이력서·포트폴리오·GitHub를 모두 직접 분석하기에는 시간이 부족하고, 충분한 근거 없이 지원자를 평가하는 것에 부담을 느끼기 때문이다.**

### 보조 POV

| # | POV |
| --- | --- |
| **POV-A**<br>(시간) | 김도윤은 **지원자 자료를 짧은 시간에 훑을 수 있는 형태**가 필요하다. 왜냐하면 채용이 본업이 아니어서 GitHub까지 확인할 시간을 확보할 수 없기 때문이다. |
| **POV-B**<br>(역할) | 김도윤은 **팀 프로젝트에서 이 사람이 실제로 한 일**을 알 방법이 필요하다. 왜냐하면 README와 프로젝트 설명은 대부분 비슷하게 쓰여 있어 개인이 맡은 부분을 분간할 수 없기 때문이다. |
| **POV-C**<br>(신뢰) | 김도윤은 **요약을 검증할 수 있는 원본 링크**가 필요하다. 왜냐하면 AI가 정리한 결론을 그대로 받아들이면 자신의 판단을 대신 맡기는 것이 되고, 그 책임은 결국 자신에게 돌아오기 때문이다. |

## 서비스 접점 시나리오

### ① JD 작성 국면 — 기술 요건을 쓴다

TO가 승인됨 → **JD의 기술 요건을 직접 작성** → HR에게 전달하면 HR이 공고로 등록 *(→ P2 시나리오 ①)*

### ② 후보 확인 국면 — HR이 넘긴 사람을 본다

HR로부터 후보 프로필 링크를 받음 → 한 화면에서 이력서·포트폴리오·GitHub 증거 카드를 확인 → **"이 프로젝트에서 이 사람이 뭘 했지"**가 카드로 정리되어 있음 → 의심스러운 항목은 근거 링크를 눌러 실제 커밋·PR 확인 → 면접에서 물어볼 지점 두세 개를 메모

### ③ 직접 탐색 국면 — 내가 찾는다

본인이 쓴 JD를 기준으로 심화 검색 → 증거 카드 중심으로 훑음 → 관심 있는 사람은 북마크 + 메모 → HR에게 전달하거나 직접 연락 요청

### ④ 면접 직전 국면 — 5분

회의 사이 빈 시간에 후보 프로필을 다시 엶 → **카드를 검색해 물어볼 지점을 빠르게 재확인** → **질문은 내가 만든다.** 서비스는 재료까지만 준다

## 이 페르소나가 아닌 사용자

- **대기업 공채 중심 채용** — 지원자가 몰려 개별 검토 구조가 다름
- **개발 직군을 채용하지 않는 기업**
- **GitHub를 평가 요소로 전혀 사용하지 않는 기업**
- **사내 저장소·비공개 코드 중심 도메인** — 게임 업계 등. 지원자의 공개 코드가 없어 증거 카드가 성립하지 않음 *[인터뷰]*
- **HR 채용 담당자** — P2로 분리
