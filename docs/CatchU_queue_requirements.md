# CatchU 큐 기술 검증 — #121 구현 요구와 E·H 쟁점

> **지위: 제안** — [큐 기술 검증](CatchU_큐_기술검증.md)의 #121 구현 요구, 진행 알림·실행 불명 판단(#23 Q4·Q5), E와 확인할 쟁점, 배포 서버 적용 조건이다. 앱 안에서 장애를 복구하지 않는 범위와 Q4·Q5의 답은 [10/6 팀장 결정][d23]이며, [#121][i121]·[#233][i233] 본문과 같은 범위다. 판정과 개발 조건·배포 전 조건은 원 문서 「결론」에, 실험 결과는 [결과 기록](CatchU_queue_verification_results.md)에 있다. 영역 이름(E·F·B·H)과 용어 「분석」(생성기 호출 하나 전체, LLM 호출은 그 일부)·「정체 복구」(잠금이 끊긴 작업을 큐가 다시 주는 것)는 원 문서 첫머리와 「결론」을 따른다. 승인된 [API 명세 v1][contract]과 [worker 메시지 계약][wm]이 정본이며, 어긋나면 계약이 이긴다. AI가 한 번에 읽을 수 있게 36 KB 미만으로 유지한다.

## 큐가 해 주는 것과 #121이 구현할 것

[10/6 팀장 결정][d23]에 따라 서버·worker·큐가 끊기는 장애는 앱에서 복구하지 않는다. 정한 시간 안에 끝나지 않은 요청은 E가 실패로 닫고, 사용자가 다시 요청한다. 이 처리 시한(접수 후 60분)과 닫힌 뒤 재요청은 계약 PR이 병합된 뒤 적용하며, 구현은 [#237][i237]이다. 그래서 아래 표의 앱 몫은 큐가 같은 작업을 다시 주지 않게 하는 설정과 기존 계약 검사다.

| 필요 | BullMQ가 해 주는 것 | 애플리케이션이 할 것(담당) |
|---|---|---|
| 요청을 F에 전달 | 작업 보관·전달, 같은 작업 ID의 기록이 남아 있는 동안 중복 추가 무시 | 작업 ID = `attemptId`(`:` 없음 확인). `attempts: 1`(재시도 없음)·backoff 없음. 완료·실패 작업 보관 기간은 처리 시한보다 길게 둔다([#233][i233], 쟁점 6) |
| worker가 죽었을 때 | 정체 복구로 작업을 다시 줌(최소 한 번) | 정체 복구를 0회(`maxStalledCount: 0`)로 둬 다시 받지 않는다. 그 작업은 큐에서 실패로 끝나고, 요청은 처리 시한에 닫힌다(F, 아래 2) |
| 분석이 두 번 돌지 않음 | **해 주지 않음** | 위 두 설정으로 큐가 같은 작업을 다시 주지 않게 한다. 시도별 기록은 두지 않는다. 큐 자료가 사라져 한 번 더 도는 드문 경우는 받아들인다(F·E) |
| 실행 불명 판단 | **해 주지 않음**(큐에는 "호출을 시작했는지" 상태가 없음) | 생성기가 실행 여부를 확인하지 못하거나 시간이 초과될 때만 `UNCERTAIN`을 알린다(기존 [#113][i113] 동작). 다시 보내지 않는다(F) |
| 분석 중 잠금 유지 | 잠금 자동 갱신(같은 이벤트 루프가 살아 있을 때만) | 동기 생성기를 스레드에서 실행하고, 진행 알림은 스레드에서 루프로 넘겨 보낸다(F, 개발 조건 4) |
| 결과를 E에 전달 | 결과 작업 보관, E가 처리를 끝내기 전에 죽으면 다시 줌 | 결과 작업 ID = `messageId`. F는 한 번 보내면 끝이고 결과 보존·재전달은 두지 않는다(아래 7). E는 같은 결과가 두 번 와도 수신 기록을 하나만 남긴다(#233 완료 기준) |
| 수신 확인 전달 | 작업 반환값 보관 | E가 수신 확인(`ResultReceipt`)을 돌려주고 F가 읽어 기록한다. 통로는 #233에서 정한다(E·F, 쟁점 5) |
| 큐 자료 유실 대비 | **해 주지 않음** | 앱에서 따로 대비하지 않는다. api는 대기 시도를 주기마다 같은 작업 ID로 넣기만 한다(#233). 끝나지 않은 요청은 처리 시한에 닫힌다 |
| 메시지 형식 | 문자열·숫자·참거짓·null·목록·객체를 그대로 옮김 | 보내기 전과 받은 직후에 기존 계약 v1 검사를 그대로 쓴다 |

#121에 넘길 F 몫의 구현 요구다. [#121][i121] 본문과 같은 범위이고, api 쪽 큐 연결은 [#233][i233]이다. 키트의 보호 worker(`py/f_worker.py`)는 시도별 기록·재전송으로 재실행을 막는 실험이다. 10/6 결정으로 이 방식은 채택하지 않았고, 실험 결과는 근거로 남는다.

1. **판본 고정**: worker에 `bullmq==3.3.0`(redis-py 7.4.1이 함께 고정됨). api의 Node 쪽과 함께 올리고 재현 키트를 다시 돈다.
2. **worker 설정**: 동시 처리 1, 정체 복구 0회(`maxStalledCount: 0`). 분석 중 worker를 강제 종료하면 그 작업은 실패로 끝나고 다시 실행되지 않아야 한다. 키트에서 기본값(1회)은 분석 중 강제 종료 뒤 분석을 한 번 더 불렀고, 0회는 다시 부르지 않았지만 작업이 조용히 실패해 E가 "실행 중"에 머물렀다([결과 3](CatchU_queue_verification_results.md#3-worker-중단과-재기동)). 이런 요청은 처리 시한이 닫는다.
3. **시도별 기록**: 두지 않는다 — 10/6 결정([#23][d23]). 요청 지문·시작 표식·결과 보존·전송 기록을 큐 밖에 남기지 않는다.
4. **다시 받은 작업의 판정**: 두지 않는다 — 10/6 결정. 2의 설정과 `attempts: 1`로 큐가 같은 작업을 다시 주지 않는다.
5. **기동 점검과 주기 점검**: 두지 않는다 — 10/6 결정. 임시 파일을 쓰게 되면 worker 기동 때만 지운다.
6. **생성기는 스레드에서 실행**한다(개발 조건 4). 요청당 총 처리 상한(제안 20분, [#116 「자원·시간 상한」](CatchU_collection_control_scope.md#23-자원시간-상한))을 넘으면 결과 없이 그 작업을 끝내고 다음 작업을 받는다. 멈춘 생성기 하나가 worker를 붙잡지 않게 하기 위해서다. Python 스레드는 밖에서 멈출 수 없으므로, 끝나지 않은 스레드를 어떻게 다룰지(별도 프로세스로 나눌지)는 #121에서 정해 PR에 적는다.
7. **재전달 규칙**: 두지 않는다 — 10/6 결정. 결과는 E에 한 번 보내면 끝이다. E가 거부한 결과(`REJECTED`)는 다시 보내지 않고 기록만 남긴다. [#116 「재전달」](CatchU_collection_control_temp_data.md#52-재전달)이 #77에 넘긴 항목의 답이다.
8. **로그**: 작업 ID·`attemptId`·처리 결과(종결 결과 전송, `UNCERTAIN`, 처리 전 거부, 상한 초과, 수신 확인 종류)만 남기고 메시지 본문은 남기지 않는다([코딩 절차 「자료와 실행 로그」](CatchU_coding_procedures.md#자료와-실행-로그)).

**받아들인 위험(10/6 결정).** 큐 자료가 사라지면 같은 시도가 한 번 더 실행될 수 있다. worker가 상한을 넘겨 멈춘 사이 재요청이 들어오면 분석이 두 번 돌 수 있다. 둘 다 드물고 분석 비용만 더 든다. 닫힌 뒤 큐에서 꺼낸 오래된 작업은 요청 정보 조회([#232](https://github.com/JminAILab/CatchU/issues/232))가 "모름"으로 답해 분석하지 않는다(시간 초과로 닫힌 시도도 들도록 #232에서 맞춘다). 닫힌 뒤 늦게 온 결과는 E 수신 코드가 거부해 Catch가 생기지 않는다. 이 범위는 worker README에 적는다(#121 완료 기준).

## 진행 알림과 실행 불명 판단 — #23 Q4·Q5 결정

[#23][q23]에서 F가 #77 결과로 답하기로 한 두 가지다. Q4·Q5는 [10/6 팀장 결정][d23]으로 정했고, 아래는 그에 맞춘 것이다.

**알림 방식.** worker→api 큐 하나에 진행 알림과 종결 결과를 작업 이름(`ProcessingEvent`·`Result`)으로 나눠 넣고, E 소비자 하나가 차례로 받는다. 작업 ID는 메시지의 `messageId`다. 순서가 뒤바뀌어도 E 수신 처리가 종결 상태를 지키는 것을 확인했다([결과 4](CatchU_queue_verification_results.md#4-결과-전달과-수신-확인)). api→worker 요청은 다른 큐 하나를 쓰고 작업 ID는 `attemptId`다. 큐 이름·접두사는 [#233][i233]에서 정해 PR에 적는다. 진행 알림과 결과는 한 번 보내고 다시 보내지 않는다.

**실행 불명 판단 기준(F).** F는 생성기가 실행 여부를 확인하지 못하거나 시간이 초과될 때만 `UNCERTAIN`을 보낸다(기존 [#113][i113] 동작). 시도별 기록을 두지 않으므로, 기록(시작 표식 등)을 근거로 보내는 `UNCERTAIN`은 생기지 않는다. E는 지금 수신 코드대로 처리하고(쟁점 1), 끝나지 않은 요청은 처리 시한에 닫힌다(계약 PR 병합 뒤 적용, 구현 [#237][i237]).

| F가 아는 것 | F가 보내는 것 | 분석 | 실험 |
|---|---|---|---|
| 생성기가 실행 여부를 확인하지 못함·시간 초과 | `UNCERTAIN`(기존 [#113][i113] 동작). 다시 보내지 않음 | 다시 부르지 않음 | 실행 확인 실패만 관찰함(시간 초과는 같은 처리 경로로 코드 확인) |
| 처리 중 worker가 죽음(생성기 호출 전·분석 중) | 없음. 정체 복구 0회라 그 작업은 큐에서 실패로 끝난다. E는 대기나 실행 중으로 남다가 처리 시한에 닫힌다 | 다시 부르지 않음 | 관찰함([결과 3](CatchU_queue_verification_results.md#3-worker-중단과-재기동)의 일반 F·정체 복구 끔) |
| E가 아직 대기로 아는 시도의 요청 작업이 큐 자료와 함께 사라짐 | api가 같은 작업 ID로 다시 넣으면 처음 받은 요청처럼 처리 | F가 이미 분석했다면 한 번 더 부를 수 있음(받아들인 위험) | 관찰함([결과 2](CatchU_queue_verification_results.md#2-중복-전달)의 완료 작업을 지운 뒤 같은 ID로 다시 넣음, 일반 F 2회) |
| 시작 표식·보존 결과·실행 차단 기록에 근거한 판단 | 생기지 않음. 시도별 기록을 두지 않는다 | — | 키트 보호 F에서 관찰함(채택하지 않은 방식) |

## E와 확인할 쟁점

담당 E는 팀원 2 `yeongyeon1802`다. 쟁점 1·2는 [10/6 팀장 결정][d23]으로 답했고, 3·4는 그 결정으로 두지 않는다. 5·6의 남은 부분은 api 쪽 큐 연결 [#233][i233]에서 정해 PR에 적고 E가 리뷰한다.

1. **`RUNNING` 뒤의 `UNCERTAIN`을 E가 반영하지 않는다.** 10/6 결정으로 실행 중 → 실행 불명 전이(`RUNNING → UNCERTAIN`)를 더하지 않는다. [E 상태 전이 정본][espec]과 수신 코드는 `QUEUED → RUNNING 또는 UNCERTAIN`만 두므로, `RUNNING` 뒤에 온 `UNCERTAIN`은 관측으로만 저장된다. 화면에는 처리 시한까지 "실행 중"으로 보이고, 그 뒤 실패로 닫힌다(계약 PR 병합 뒤 적용, 구현 [#237][i237]).
2. **`UNCERTAIN`인 요청을 누가 어떻게 끝내는가.** 10/6 결정: 접수 후 60분 안에 끝나지 않은 요청은 E가 실패로 닫는다. 실행이 멈췄다는 증거는 따로 요구하지 않는다. 실행 불명뿐 아니라 대기·실행 중인 요청과, 결과를 받았지만 Catch 반영이 끝나지 않은 요청도 같다. 반영 실패는 60분을 기다리지 않고 바로 닫는다. 시간 초과로 닫힌 요청과 반영 실패로 닫혀 등록된 Catch가 0건인 요청은 새 동의·새 요청으로 다시 요청할 수 있다. 지금 계약은 시간 경과로 실패를 확정하는 것과 그 뒤의 재요청을 막으므로, 이 동작은 계약 PR 병합 뒤 적용한다(구현 #237). 운영자가 증거를 보고 실패로 확정하는 절차는 두지 않는다.
3. **큐에서 사라진 요청의 재발행.** 두지 않는다 — 10/6 결정([#23][d23]). api는 대기 시도를 같은 작업 ID로 넣기만 하고, 사라졌는지 판단하거나 한도를 두지 않는다(#233). F의 실행 차단 기록도 없다. 끝나지 않은 요청은 처리 시한에 닫힌다.
4. **수신 뒤 반영 전 장애([#116 「수신 후 반영 전 장애」](CatchU_collection_control_temp_data.md#53-수신-후-반영-전-장애--지금-막히는-곳)).** 두지 않는다 — 10/6 결정([#23][d23]). 결과를 받은 뒤 Catch 반영 전에 멈춘 요청은 앱에서 복구하지 않고 처리 시한에 닫는다. 결과 복구 방식 1-나([#234](https://github.com/JminAILab/CatchU/issues/234))도 함께 거뒀다.
5. **수신 확인 통로와 결과 작업 보관 기간.** 이번 실험에서는 E 소비자의 작업 반환값으로 돌려줬다. 따로 수신 확인 큐를 둘지, 결과 작업을 얼마나 남길지, 결과 작업을 언제 완료로 표시할지는 #233 담당이 정해 PR에 적는다. 어느 쪽이든 BullMQ 이벤트 스트림(`QueueEvents`)은 약 1만 건에서 잘리고 큐 자료와 함께 사라질 수 있으므로 수신 확인의 유일한 통로로 쓰지 않는다([결과 4](CatchU_queue_verification_results.md#4-결과-전달과-수신-확인)). F는 수신 확인을 읽어 `ACCEPTED`·`DUPLICATE`·`REJECTED`를 구분해 기록할 뿐, 결과를 다시 보내지 않는다.
6. **요청 작업 옵션과 보관 기간.** 요청을 넣을 때 `attempts: 1`(재시도 없음)·backoff 없음으로 명시한다(개발 조건 2). 큐는 완료·실패한 요청 작업이 남아 있는 동안만 같은 `attemptId`의 추가를 무시한다. 그래서 보관 기간을 처리 시한보다 길게 둔다(#233). 그래야 처리 전 거부로 대기에 남은 시도를 주기마다 다시 넣어도 다시 처리되지 않는다. 자동 삭제는 다른 작업이 끝날 때 늦게 평가된다. 계약은 `attemptId`에 빈 문자열만 막지만, E의 시도 ID는 DB에 uuid로 저장된다([회원·분석 선행 테이블](../api/docs/member-analysis.md#테이블-참조와-저장), #104). 이 값은 큐 작업 ID 제약(정수만으로 된 문자열·`:` 금지)을 지키므로 요청 작업 ID로 그대로 쓸 수 있다. E는 시도 ID 하나를 DB·메시지·작업 ID에 같이 쓰자고 했다([E 의견 3번](https://github.com/JminAILab/CatchU/issues/23#issuecomment-6007219268)). 계약에 형식을 적을지는 #23에서 따로 답한다.

## 배포 서버 적용 조건

배포 대상은 AWS다([레포 컨벤션 §1](CatchU_레포_컨벤션.md#1-레포-구조)). AWS에서 큐 서버(Redis 계열)로 무엇을 쓸지는 아직 정하지 않았다. 그래서 여기에는 서비스와 관계없이 실제 서버에서 확인할 것만 적는다. BullMQ 채택 완료 조건은 아래 표의 확인(배포 전 조건 3) 하나이며, H가 [#24][i24]에서 확인한다. 큐 서버에 닿는 서버에서 [재현 키트 「실행」](queue-verification/README.md#실행)대로 돌린다.

| 확인 | 왜 | 방법 |
|---|---|---|
| 축출 정책이 `noeviction`(메모리가 차도 지우지 않음)이다 | 다른 정책이면 메모리가 찰 때 큐 자료가 조용히 지워질 수 있다. 잘못돼도 BullMQ는 경고만 하고 돈다([결과 5](CatchU_queue_verification_results.md#5-큐-저장소-조건)) | 실제 값을 `INFO memory`나 서비스 설정 화면으로 본다. 다르면 운영을 시작하지 않는다. `noeviction`이어도 메모리가 차면 쓰기가 실패하므로 메모리 사용량과 큐 추가 실패를 지켜본다 |
| 키트의 연결 시나리오가 돈다(허용 명령) | 관리형 서비스는 일부 명령을 막을 수 있다. 스크립트 실행(`EVALSHA`)·`MULTI`·대기형 꺼내기 명령·`CLIENT SETNAME`·`INFO`가 막히지 않았는지 본다 | 키트의 A 묶음 등을 실제 서버에 대고 돌린다 |
| 재시작·장애 조치 뒤 api·worker가 다시 연결된다 | 로컬에서는 큐 서버가 12초 멈춘 뒤 양쪽이 다시 연결됐다([결과 5](CatchU_queue_verification_results.md#5-큐-저장소-조건)). 실제 서버의 전환 방식에서는 확인하지 않았다 | 큐 서버를 재시작하거나 장애 조치를 일으킨 뒤 두 서비스의 연결과 작업 처리를 본다 |

참고로 남기는 것(채택 조건이 아님):

- **영속성 설정**: 실제 `INFO persistence` 값을 기록만 한다. 큐 자료가 사라지면 끝나지 않은 요청은 처리 시한에 닫히고 사용자가 다시 요청하므로(10/6 결정) 관문이 아니다.
- **서비스 재시작**: api·worker가 죽으면 컨테이너 재시작 같은 운영 설정으로 다시 띄운다(10/6 결정).
- **접근 제한**: 큐 메시지에는 계약상 비밀값이 없지만 회원 ID 등이 평문으로 저장된다. 큐 서버에는 api·worker 서버만 닿게 한다.
- **클러스터 모드**: 쓰지 않는 것을 권한다. 쓰면 큐 접두사를 `{...}`로 묶어야 한다(BullMQ 문서).
- **엔진·판본**: 키트는 Redis 7.2.11·Valkey 7.2.11·Valkey 8.1.6에서 같은 결과를 냈다. 실제 서버의 엔진·판본이 다르면 그 판본으로 키트를 다시 돌린다(개발 조건 6).

**지난 조사(2026-10-02, 당시 배포 대상 NCP).** 아래는 배포 대상이 NCP이던 때의 조사 기록이며 AWS 사실이 아니다. 키트가 NCP에서 고를 수 있던 세 엔진으로 시험하고 NCP가 막은 명령 10개를 끈 서버로 돈 것은 이 조사 때문이다. NCP의 관리형 Redis 상품은 2025-06-19부터 **Cloud DB for Cache**이며, 한 상품 안에서 Redis와 Valkey를 고른다. 공식 문서 확인일은 2026-10-01이고, 교차 검토로 고친 항목(장애 조치 범위·접속·백업)은 2026-10-02에 다시 확인했다.

| 항목 | 공식 문서로 확인한 것 | 로컬에서 재현한 것 | 당시 미확인 |
|---|---|---|---|
| 엔진·판본 | 새로 만들 수 있는 것은 Redis 7.2.11, Valkey 7.2.11, Valkey 8.1.6. NCP 표의 End of Life는 Redis 7.2가 2026-02-28(이미 지나 새 마이너 판본이 나오지 않음, 판매 종료·운영 지원 종료일은 미공지), Valkey 7.2가 2027-04-16, Valkey 8.1이 2028-03-31. Redis 5.0·7.0은 판매 종료. 메이저 판본 올리기는 공식 지원하지 않음 | 세 엔진 모두 같은 결과 | — |
| 막힌 명령 | `BGREWRITEAOF`·`BGSAVE`·`SAVE`·`SLAVEOF`·`FLUSHALL`·`FLUSHDB`·`CONFIG`·`KEYS`·`MIGRATE`·`SHUTDOWN` | BullMQ 스크립트는 이 명령을 쓰지 않음(소스 확인). 비교용 AOF 시나리오를 뺀 46개 시나리오가 10개를 끈 서버에서 돎 | 스크립트 실행(`EVALSHA`)·`MULTI`·대기형 꺼내기 명령·`CLIENT SETNAME`·`INFO` 허용 여부는 문서에 명시가 없었다 |
| 축출 정책 | Config Group에서 `maxmemory-policy`를 바꿀 수 있다. 기본값과 허용 값은 문서에 없다. `CONFIG` 명령이 막혀 있다 | 잘못돼도 경고만 나옴([결과 5](CatchU_queue_verification_results.md#5-큐-저장소-조건)) | 콘솔에서 `noeviction`을 고를 수 있는지 |
| 영속성·백업 | "캐시 DB라 데이터 무결성을 보장하지 않음, 중요한 데이터는 별도 저장 권장". 재시작 때 데이터 손실 가능, Stand Alone은 재시작 때 전부 삭제. Config 항목에 `appendonly`가 없다. 백업은 기본 꺼짐(고가용성을 켜면 켜짐으로 고정), 하루 1회, 최대 7일, 복원은 백업 시점으로 새 서버 생성 | 영속성 없이 재시작하면 대기 요청·보낸 결과·보낸 `UNCERTAIN`이 사라짐 | 실제 `INFO persistence` 값 |
| 장애 조치 | Simple 모드의 고가용성(Active/Standby Master)은 DNS 전환 자동 장애 조치 최대 3분이고, 재시작 때 두 서버가 함께 재시작된다. 이 3분은 Simple 고가용성 기준이며 클라이언트가 다시 연결을 마치는 시간을 보장하지 않는다. Cluster 모드의 장애 조치 시간은 확인하지 못했다 | 12초 멈춤 뒤 양쪽 클라이언트 재연결 | DNS 전환 뒤 재연결, 장애 조치 직전 쓰기 유실 범위, `timeout`·`tcp-keepalive` 기본값이 대기 연결을 끊는지 |
| 접속·보안 | 외부에서 직접 접속은 안 되고 NCP 안(Private Subnet)이나 SSL VPN을 거쳐 접속한다. 민간 클라우드는 비밀번호·계정 권한 기능 없음, 접근 제어는 ACG(접근 허용 규칙). TLS 내장 지원은 문서에 없다. IP 대신 Private 도메인으로 접속 권장 | — | Valkey 인증 방식(문서끼리 다름) |
| 클러스터 모드 | VPC에서만, 샤드 3~10 | — | — |
| 비용 | 시간 요금제만, 최소 사양 메모리 1.5GB, 고가용성은 추가 요금 | — | 실제 금액 |

당시 NCP 자원은 만들지 않았다. 배포 대상이 AWS로 바뀌어 이 표의 당시 미확인 항목은 더 확인하지 않는다.

## 결정 이력

이 문서를 나누기 전의 작성 이력과 2026-10-06 리뷰 반영(PR #207)은 [큐 기술 검증 「결정 이력」](CatchU_큐_기술검증.md#결정-이력)에 있다.

- **2026-10-06** — [팀장 결정(#23)][d23]에 맞춰 앱 안 장애 복구를 뺐다. 「#121이 구현할 것」 3·4·5·7(시도별 기록, 다시 받은 작업 판정, 기동·주기 점검, 재전달)은 "두지 않는다"로 바꿨다. 2는 정체 복구를 1회에서 0회로 바꾸고, 6에 요청당 총 처리 상한을, 7에 `REJECTED`는 기록만 남긴다는 것을 더했다. 같은 날 PR #207 리뷰 반영으로 더한 `UNCERTAIN` 재전송 요구도 거뒀다. 진행 알림 표는 생성기가 실행 여부를 확인하지 못한 경우만 `UNCERTAIN`으로 남겼다. 쟁점 1·2는 결정(전이 추가 없음, 접수 후 60분 처리 시한)으로 답했고, 3·4는 두지 않으며, 5·6은 [#233][i233] 범위로 줄였다. 처리 시한과 닫힌 뒤 재요청은 계약 PR 병합 뒤 적용한다(구현 [#237][i237]). 배포 대상이 AWS로 바뀌어([레포 컨벤션 §1](CatchU_레포_컨벤션.md#1-레포-구조)) 「NCP 적용 조건」을 「배포 서버 적용 조건」으로 바꾸고 서비스와 관계없는 확인만 적었다. NCP 조사는 지난 기록으로 남겼다. 키트 실험 결과는 근거로 그대로 유효하다.
