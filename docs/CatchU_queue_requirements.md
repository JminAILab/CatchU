# CatchU 큐 기술 검증 — #121 구현 요구와 E·H 쟁점

> **지위: 제안** — [큐 기술 검증](CatchU_큐_기술검증.md)의 #121 구현 요구, 진행 알림·실행 불명 판단(#23 Q4·Q5 제안), E와 확인할 쟁점, NCP 적용 조건이다. 판정과 개발 조건·배포 전 조건은 원 문서 「결론」에, 실험 결과는 [결과 기록](CatchU_queue_verification_results.md)에 있다. 영역 이름(E·F·B·H)과 용어 「분석」(생성기 호출 하나 전체, LLM 호출은 그 일부)·「정체 복구」(잠금이 끊긴 작업을 큐가 다시 주는 것)는 원 문서 첫머리와 「결론」을 따른다. 승인된 [API 명세 v1][contract]과 [worker 메시지 계약][wm]이 정본이며, 어긋나면 계약이 이긴다. AI가 한 번에 읽을 수 있게 36 KB 미만으로 유지한다.

## 큐가 해 주는 것과 #121이 구현할 것

| 필요 | BullMQ가 해 주는 것 | 애플리케이션이 할 것(담당) |
|---|---|---|
| 요청을 F에 전달 | 작업 보관·전달, 같은 작업 ID의 기록이 남아 있는 동안 중복 추가 무시 | 작업 ID = `attemptId`(`:` 없음 확인). 재시도 횟수를 1로 명시하고, 완료한 요청 작업은 일정 기간 남긴다(E, 쟁점 6) |
| worker가 죽어도 요청을 잃지 않음 | 정체 복구로 작업을 다시 줌(최소 한 번) | 다시 받은 작업을 시도별 기록으로 판정(F, 개발 조건 1·3) |
| 분석이 두 번 돌지 않음 | **해 주지 않음** | 생성기를 부르기 **전에** 시작 표식을 큐 밖에 남기고, 결과를 큐 밖에 보존한 **뒤에** 보낸다(F) |
| 실행 불명 판단 | **해 주지 않음**(큐에는 "호출을 시작했는지" 상태가 없음) | 시작 표식은 있고 결과가 없는 시도가 다시 오면 분석하지 않고 `UNCERTAIN`을 보내고, 그 알림이 E에 닿을 때까지 점검한다(F) |
| 분석 중 잠금 유지 | 잠금 자동 갱신(같은 이벤트 루프가 살아 있을 때만) | 동기 생성기를 스레드에서 실행하고, 진행 알림은 스레드에서 루프로 넘겨 보낸다(F, 개발 조건 4) |
| 결과를 E에 전달 | 결과 작업 보관, E가 처리를 끝내기 전에 죽으면 다시 줌 | 결과 작업 ID = `messageId`(재전달마다 새로 발급). 아래 재전달 규칙(F) |
| 수신 확인 전달 | 작업 반환값 보관 | E 소비자가 수신 확인(`ResultReceipt`)을 반환값으로 돌려주고 F가 작업 ID로 읽는다(E·F, 쟁점 5) |
| 큐 자료 유실 대비 | **해 주지 않음** | 요청: E가 접수 기록으로 다시 넣는다(개발 조건 5). 결과·`UNCERTAIN`: 큐에서 사라졌거나 E가 처리하다 실패로 남았으면 F가 큐 밖 기록으로 다시 보낸다(배포 전 조건 2) |
| 메시지 형식 | 문자열·숫자·참거짓·null·목록·객체를 그대로 옮김 | 보내기 전과 받은 직후에 기존 계약 v1 검사를 그대로 쓴다 |

#121에 넘길 F 몫의 구현 요구다. 시도별 기록의 위치와 수명은 [#116 「수명표」](CatchU_collection_control_temp_data.md#42-수명표)의 결과 보존 위치(H 환경에서 확정)를 따른다. 키트의 보호 worker(`py/f_worker.py`)가 아래를 모두 구현한 참고 예다. 사람이 검토하지 않은 실험 코드이므로 그대로 옮기지 말고 요구로 읽는다.

1. **판본 고정**: worker에 `bullmq==3.3.0`(redis-py 7.4.1이 함께 고정됨). Node 쪽과 함께 올리고 재현 키트를 다시 돈다.
2. **worker 설정**: 동시 처리 1, 정체 복구 허용 횟수는 기본 1 유지.
3. **시도별 기록**: 요청 내용의 지문(전송마다 바뀌는 `messageId` 제외), 분석 시작 표식(이미 있으면 생성기를 부르지 않음), 보존 결과, 전송 기록, 전달 표식(수신 확인 `ACCEPTED`·`DUPLICATE`를 받았다는 표시, #116 정의), 거부 표식(`REJECTED`), 보낸 `UNCERTAIN` 알림의 전송 기록과 처리 표식(알림 작업이 완료로 끝난 것을 본 표시. 진행 알림에는 수신 확인이 없다), 사람 확인 표식.
   - 시작 표식은 생성기 호출 전에 디스크에 확정(fsync)한다. LLM 호출 직전에 두면 수집 중 중단 뒤 수집이 자동으로 다시 돈다.
   - 시작 표식과 생성기 호출 사이에는 다른 일(진행 알림 전송 등)을 두지 않는다. 기록만으로는 표식 뒤 호출 전과 호출 중을 구별할 수 없어, 그 사이에 죽어도 분석하지 않은 채 `UNCERTAIN`이 된다([결과 3](CatchU_queue_verification_results.md#3-worker-중단과-재기동)).
   - 새로 만든 폴더는 상위 폴더까지 디스크에 확정한다. 그러지 않으면 전원 장애 뒤 그 안의 표식이 사라질 수 있다. 프로세스 강제 종료 시험으로는 드러나지 않는 결함이라 키트도 시험하지 못했다.
   - `attemptId`를 파일 이름으로 바로 쓰지 않는다. 계약은 빈 문자열만 막는다(쟁점 6). 키트는 SHA-256 앞 32자로 폴더 이름을 만든다.
   - 실험은 worker 한 대·로컬 디스크의 배타적 파일 생성으로 했다.
4. **다시 받은 작업의 판정** — 다음 중 하나만 한다. worker 하나·동시 처리 1이 전제다(배포 전 조건 6).
   - 같은 `attemptId`인데 요청 내용이 처음과 다름 → 아무것도 보내지 않고 사람 확인으로 둔다.
   - 결과 있음 → 아래 재전달 규칙.
   - 시작 표식만 있음 → 분석하지 않고 `UNCERTAIN`을 보내고, 이 알림이 E에 닿을 때까지 아래 7의 결과 재전달처럼 점검한다. 보낸 알림 작업이 기다리는 중이면 다시 넣지 않고, 완료(E가 받아 저장했거나 거부 판정을 돌려줌)면 처리 표식을 큐 밖에 남기고 멈추고, 큐에서 사라졌거나 실패로 남았으면 다시 보낸다. 처리 표식이 있으면 큐 자료가 사라진 뒤에도 다시 보내지 않는다(7의 전달 표식과 같다). 큐는 같은 ID의 작업이 남아 있으면 상태(대기·완료·실패)와 관계없이 새 추가를 무시한다. 그래서 ID를 시도마다 고정하고 다시 넣기만 하면, E가 처리하다 실패한 알림(E 저장소 일시 오류, E 소비자의 정체 복구 한도 초과)은 다시 가지 않고 E가 끝내 실행 불명을 모른다. 다시 보내는 방법(전송마다 새 `messageId`, 또는 실패한 작업을 지우거나 되돌린 뒤 같은 ID)은 #121에서 E와 정한다(쟁점 5). E는 같은 시도의 `UNCERTAIN`을 여러 번 받아도 처리 상태를 바꾸지 않는다(E 수신 코드로 확인). 생성기 실행 확인 실패나 오래된 요청으로 보낸 `UNCERTAIN`도 같다. 키트는 ID를 고정하고 다시 넣기만 해서 이 경우를 다루지 못한다(키트 README 한계).
   - 기록 없음 → 첫 실행. 단 접수 시각이 실행 차단 기록의 수명보다 오래됐으면 분석하지 않고 `UNCERTAIN`을 보낸다(쟁점 3, 배포 전 조건 5). 이 알림도 위처럼 E에 닿을 때까지 점검하므로, 보낸 기록을 시도별로 남긴다.
5. **기동 점검과 주기 점검**: 기동할 때 기록을 훑어 보존 결과는 재전달 규칙대로 점검하고, 시작 표식만 남고 처리 표식이 없는 시도에는 `UNCERTAIN`을 보낸다(worker 한 대라면 기동 때 남은 시도는 죽은 실행이다). 그 뒤에도 #116의 간격에 맞춰 보존 결과와 이미 보낸 `UNCERTAIN` 알림이 E에 닿았는지 주기적으로 점검한다(배포 전 조건 2, 처리 표식이 있는 시도는 점검하지 않는다). 주기 점검은 시작 표식만 보고 `UNCERTAIN`을 새로 보내지 않는다(그 시도는 아직 살아 있는 실행일 수 있다). 시도 하나의 기록이 손상되면 그 시도만 사람 확인으로 돌리고 나머지와 worker 기동은 막지 않는다. 큐 서버 연결 오류는 기록 문제가 아니므로 그 점검만 멈추고 다음에 다시 본다.
6. **생성기는 스레드에서 실행**한다(개발 조건 4).
7. **재전달 규칙** — [#116 「재전달」](CatchU_collection_control_temp_data.md#52-재전달)이 "전송 방식과 함께 #77에서 확정"하기로 한 항목의 제안이다.
   - 모든 전송 기록의 결과 작업과 수신 확인을 본다. 가장 최근 전송이 기다리는 중이어도 앞선 전송이 이미 수락됐을 수 있다.
   - 수신 확인은 계약 형식과 `resultId`·`requestId`·`attemptId`가 보존 결과와 맞을 때만 믿는다.
   - `ACCEPTED`·`DUPLICATE`면 전달 표식을 남기고 멈춘다. `REJECTED`면 거부 표식을 큐 밖에 남기고 다시 보내지 않는다(큐 자료가 사라진 뒤에도). #116 표대로 기록한다.
   - 보낸 결과 작업이 아직 큐에서 기다리는 중이면 다시 넣지 않는다(다시 넣어도 같은 줄 뒤에 선다).
   - 결과 작업이 큐에서 사라졌거나, 실패로 끝났거나, 수신 확인 없이 끝났으면 새 `messageId`로 다시 보낸다. 새 `messageId`는 전송 기록에 **먼저** 쓰고 큐에 넣는다. 반대 순서면 넣은 뒤 기록 전에 죽었을 때 다음 재전송이 같은 ID를 만들어 큐에서 무시될 수 있다.
   - 횟수·기한은 #116 제안(최대 5회, 간격을 늘려 총 약 30분)을 그대로 두고, 큐에서 기다린 시간도 이 기한에 넣는다. 기한 안에 수신 확인이 없으면 사람 확인 대기로 올린다(E가 오래 꺼진 경우도 여기에 걸린다).
   - 키트 실행에서 거친 분기는 `ACCEPTED`를 보고 멈춤, 사라진 결과를 다시 보냄(기동 점검·다시 받은 작업·주기 점검), `REJECTED`를 보고 멈춤이다. `DUPLICATE` 수신 확인으로 멈춤, 기다리는 중, 실패로 끝난 결과 작업, 형식이 틀린 수신 확인, 횟수·기한 초과 분기는 실행되지 않았다(#121에서 시험).
8. **로그**: 작업 ID·`attemptId`·판정(첫 실행/재전달/`UNCERTAIN`/건너뜀)만 남기고 메시지 본문은 남기지 않는다([코딩 절차 「자료와 실행 로그」](CatchU_coding_procedures.md#자료와-실행-로그)).

## 진행 알림과 실행 불명 판단 — #23 Q4·Q5 제안

[#23][q23]에서 F가 #77 결과로 답하기로 한 두 가지의 제안이다.

**알림 방식.** worker→api 큐 하나에 진행 알림과 종결 결과를 작업 이름(`ProcessingEvent`·`Result`)으로 나눠 넣고, E 소비자 하나가 차례로 받는다. 작업 ID는 메시지의 `messageId`다. 순서가 뒤바뀌어도 E 수신 처리가 종결 상태를 지키는 것을 확인했다([결과 4](CatchU_queue_verification_results.md#4-결과-전달과-수신-확인)). api→worker 요청은 다른 큐 하나를 쓰고 작업 ID는 `attemptId`다. 큐 이름·접두사는 E와 정한다.

**실행 불명 판단 기준(F).** 표에서 `UNCERTAIN`을 보내는 세 경우 모두, 보낸 알림은 「#121이 구현할 것」 4·5대로 E에 닿을 때까지 점검하고 큐에서 사라졌거나 실패로 남았으면 다시 보낸다. E가 처리하다 실패로 남은 알림은 키트에서 시험하지 않았다.

| F가 아는 것 | F가 보내는 것 | 분석 | 실험 |
|---|---|---|---|
| 생성기가 실행 여부를 확인하지 못함·시간 초과 | `UNCERTAIN`(기존 [#113][i113] 동작) | 다시 부르지 않음 | 실행 확인 실패만 관찰함(시간 초과는 같은 처리 경로로 코드 확인) |
| 시작 표식은 있는데 결과가 없는 시도가 다시 옴, 또는 기동 때 그런 시도가 남아 있음(worker 중단 뒤. 수집 중 중단도 여기에 든다 — [#116 「정리 실패·프로세스 중단」](CatchU_collection_control_temp_data.md#43-정리-실패프로세스-중단)이 #77로 넘긴 판단) | `UNCERTAIN` | 다시 부르지 않음 | 관찰함(표식 뒤 호출 전·분석 중·보존 전 중단, 알림 유실 뒤 재발행) |
| 시작 표식이 없음(생성기 호출 전에 중단) | 진행 알림부터 다시, 정상 처리 | **처음 부름** — 부른 적이 없으므로 재실행이 아니다 | 관찰함 |
| 기록이 없는데 접수 시각이 실행 차단 기록의 수명보다 오래됨 | `UNCERTAIN` | 부르지 않음 — 예전에 실행됐는지 알 수 없다 | 관찰함(쟁점 3에서 E와 확정) |
| 결과가 보존돼 있음 | 재전달 규칙에 따라 보존 결과 | 부르지 않음 | 관찰함 |
| 같은 `attemptId`인데 요청 내용이 다름 | 없음, 사람 확인 | 부르지 않음 | 관찰함 |

## E와 확인할 쟁점

담당 E는 팀원 2 `yeongyeon1802`다. 모두 #121의 실제 연결 전에 정해야 한다. 계약 쟁점(1·2)은 [#23][q23]에 올리고, E 쪽 구현 몫(개발 조건 2·5·6, 배포 전 조건 1, 쟁점 3·5·6의 방식·시점·보관 기간)은 [#134](https://github.com/JminAILab/CatchU/issues/134)의 후속 후보 「실제 worker 요청·진행·결과 전달 어댑터 연결」(미등록)에서 맞춘다.

1. **`RUNNING` 뒤의 `UNCERTAIN`을 E가 반영하지 않는다.** 계약 본문은 "F 진행은 RUNNING, 실행이 확인되지 않으면 UNCERTAIN을 유지한다"고 하고 진행 알림의 "실행 불명 해소는 #77"로 넘겼다([명세 「전이·불변 조건」·「W — worker 메시지 계약」][contract]). 그런데 [E 상태 전이 정본][espec]은 `QUEUED → RUNNING 또는 UNCERTAIN`만 두고, 수신 구현도 그렇다. F가 `UNCERTAIN`을 보내는 실제 경우는 대부분 `RUNNING` 뒤라서 지금은 사용자에게 계속 "실행 중"으로 보인다(기록 수명보다 오래된 요청은 `UNCERTAIN`만 보내고, 앞선 `RUNNING`이 큐에서 사라진 경우와 함께 E는 `QUEUED`에서 바로 `UNCERTAIN`이 된다. [결과 2](CatchU_queue_verification_results.md#2-중복-전달)·[결과 5](CatchU_queue_verification_results.md#5-큐-저장소-조건)). 선택지: (가) 기능 설계의 전이표를 계약 문장에 맞춰 `RUNNING → UNCERTAIN`을 더한다(계약 수정 절차에 해당하는지는 E·팀장 확인), (나) 지금처럼 실행 불명 관측은 저장하고 처리 상태는 `RUNNING`으로 두되, 저장된 관측을 사용자 표시·운영 확인에 쓴다. E는 [#113 처리 PR의 승인 리뷰](https://github.com/JminAILab/CatchU/pull/177#pullrequestreview-5349526861)에서 "실제 실행 불명 해소는 #77·#121의 연결 과제로 유지"한다고 했다.
2. **`UNCERTAIN`인 요청을 누가 어떻게 끝내는가.** 계약상 실행 불명은 닫힐 수 없고 재요청은 실패 확정 증거가 있어야 한다. 사용자당 진행 중 요청은 하나이므로, 실행 불명 요청은 그 사용자의 다른 저장소 분석까지 막는다. 운영자 확인 뒤 실패로 확정하는 길이 필요한지, 누가 맡는지는 [검토초안 §6][arch6]이 남긴 미결이다. E 확인 뒤 팀장이 정한다. 그런 길을 두더라도 실행이 실제로 멈췄고 결과가 없다는 증거가 있어야 하며, 시간이 지났다는 것만으로 실패로 확정하면 기존 규칙에 어긋난다. 이번 실험에서 이 상태는 생성기의 실행 확인 실패, 시작 표식을 남긴 뒤 결과를 보존하기 전까지의 강제 종료 뒤 재기동, 기록 수명보다 오래된 요청에서 생겼다.
3. **큐에서 사라진 요청의 재발행.** 접수(202) 뒤 큐 추가가 실패하거나 큐 자료가 사라지면 E는 `QUEUED`에 머문다. 그런데 F가 처리 전에 거부한 요청도 `QUEUED`에 머문다(계약에 거부 메시지가 없음, [#113][i113]·[#116 「상한을 넘거나 실패했을 때」](CatchU_collection_control_scope.md#24-상한을-넘거나-실패했을-때)). 그래서 E가 `QUEUED`만 보고 다시 넣으면 거부된 요청이 되풀이해 들어간다(분석은 없음). 제안: E는 자기 상태 대신 요청 작업의 큐 상태로 판단한다. 작업이 없으면 다시 넣고, 완료로 남아 있으면(F가 다뤘음, 반환값에 거부 여부) 다시 넣지 않는다. 그러려면 완료 작업을 남겨 두는 기간이 필요하다(쟁점 6). 요청 작업이 실패로 남아 있으면(처리 중 예외, 정체 복구 허용 횟수 초과) 같은 작업 ID로 다시 넣어도 큐가 무시하고, 실패만으로는 F가 어디까지 했는지 알 수 없다. 이때 작업을 지우고 다시 넣을지, 사람 확인으로 넘길지를 E·F가 정한다. 재발행에는 요청당 한도(횟수 또는 접수 뒤 기간)를 두고, 그 기간은 완료 요청 작업 보관 기간과 F 시도 기록 보존 기간(14일) 안이어야 한다. F 기록이 지워진 뒤 다시 넣으면 시작 표식이 없어 분석이 다시 돈다. 한도 안에 넣었어도 큐에서 오래 기다리다 기록이 지워진 뒤 처리되면 같은 일이 생긴다. 그래서 실행을 막는 기록(요청 내용·시작 표식)의 수명을 결과 보존 14일과 따로 정하고, F는 기록이 없는데 접수 시각이 그 수명보다 오래된 시도를 분석하지 않고 `UNCERTAIN`으로 두기를 제안한다(키트에서 확인, [2](CatchU_queue_verification_results.md#2-중복-전달)). 한도를 넘으면 다시 넣지 않고 사람 확인으로 둔다. 계약을 바꾸지 않는 방법이지만 큐 내부 반환값에 기대므로 E·F가 합의해야 한다. 다시 넣는 시점(기동 때·주기·상태 조회 때)도 E가 정한다.
4. **수신 뒤 반영 전 장애([#116 「수신 후 반영 전 장애」](CatchU_collection_control_temp_data.md#53-수신-후-반영-전-장애--지금-막히는-곳)).** 큐는 E가 결과 작업을 끝내기 전에 죽으면 결과를 다시 준다. #116이 "안 2"(이미 받았어도 반영 전이면 본문을 등록 경로로 다시 넘김)에 없다고 한 "다시 보낼 계기"를 큐가 줄 수 있다는 뜻이다. 다만 그러려면 반영 전 중복 수신에서 본문이 등록 경로로 넘어가야 하고(지금 수신 구현은 넘기지 않음, [결과 4](CatchU_queue_verification_results.md#4-결과-전달과-수신-확인)에서 확인), 정체 복구 허용 횟수를 넘으면 결과 작업도 조용히 실패한다. 큐 자료가 사라질 수도 있으므로 #116의 권고 "안 1"(E가 복구에 쓸 자료를 수신 기록과 같은 트랜잭션에 남김)이 여전히 필요하다. [E 수신 안내](../api/docs/analysis-receiver.md)는 반영 복구를 #105에서 "다시 전달된 같은 결과"로 잇는다고 적는다. 큐 재전달이 그 계기가 될 수 있지만, 지금 수신은 중복일 때 본문을 넘기지 않으므로 수신 구현이나 #105 연결 코드가 반영 상태를 확인한 뒤 다시 받은 본문을 넘겨야 한다. 결과 작업을 반영 기록까지 끝낸 뒤 완료할지는 이 둘과 함께 E가 정한다.
5. **수신 확인 통로와 결과 작업 보관 기간.** 이번에는 E 소비자의 작업 반환값으로 돌려줬다. 따로 수신 확인 큐를 둘지, 결과 작업을 얼마나 남길지(F가 읽기 전에 지워지면 F는 "큐에서 사라짐"으로 보고 다시 보내고, E는 `DUPLICATE`로 답한다)를 맞춘다. 어느 쪽이든 BullMQ 이벤트 스트림(`QueueEvents`)은 약 1만 건에서 잘리고 큐 자료와 함께 사라질 수 있으므로 수신 확인의 유일한 통로로 쓰지 않는다([결과 4](CatchU_queue_verification_results.md#4-결과-전달과-수신-확인)). 진행 알림(`ProcessingEvent`) 작업도 같이 정한다. 지금 수신 구현은 저장소 오류 때 예외를 던지고, 키트 E 소비자처럼 소비자가 이 예외를 그대로 넘기면 그 알림 작업은 큐에 실패로 남는다(제품 api에는 아직 큐 소비자가 없다). F가 실패로 남은 알림을 보고 다시 보내려면 실제 소비자도 처리 실패를 이렇게 작업 실패로 남겨야 한다. 예외를 삼켜 완료로 끝내면 F는 E가 처리한 것으로 보고 멈춘다. 이것을 전제로 둘지, F가 새 `messageId`로 보내 같은 시도의 관측이 E에 여러 번 가도 되는지 아니면 실패한 알림 작업을 지우거나 되돌린 뒤 같은 ID로 다시 보내는지(방법은 「#121이 구현할 것」 4대로 #121에서 정한다), 그리고 완료·실패 작업의 보관 기간을 E와 정한다. F가 진행 알림·결과 작업에 재시도 횟수·간격(`attempts`·`backoff`)을 주면 E의 일시 오류는 큐가 흡수하지만, 정체 복구 한도 초과는 막지 못하므로 보조 수단이다.
6. **요청 작업 옵션과 보관 기간.** 요청을 넣을 때 재시도 횟수를 1로 명시한다(개발 조건 2). 완료한 요청 작업을 남겨 두는 동안만 큐가 같은 `attemptId`의 추가를 막고 쟁점 3의 판단도 할 수 있다. 보관 기간을 정한다(자동 삭제는 다른 작업이 끝날 때 늦게 평가된다). 또 계약은 `attemptId`에 빈 문자열만 막는다. 다만 E의 시도 ID는 DB에 uuid로 저장된다([회원·분석 선행 테이블](../api/docs/member-analysis.md#테이블-참조와-저장), #104). 이 값은 큐 작업 ID 제약(정수만으로 된 문자열·`:` 금지)을 지키므로 요청 작업 ID로 그대로 쓸 수 있다. 남은 확인은 둘이다. 요청 메시지의 `attemptId`에 이 값을 그대로 넣는지는 실제 연결 어댑터에서 E와 확인하고, 계약에 형식을 적을지는 #23에서 정한다. 계약이 형식을 정하지 않는 동안 F 기록 파일 이름에는 해시값을 쓴다(키트와 같음).

## NCP 적용 조건

NCP의 관리형 Redis 상품은 2025-06-19부터 **Cloud DB for Cache**이며, 한 상품 안에서 Redis와 Valkey를 고른다. 공식 문서 확인일은 2026-10-01이고, 교차 검토로 고친 항목(장애 조치 범위·접속·백업)은 2026-10-02에 다시 확인했다.

|---|---|---|---|
| 엔진·판본 | 새로 만들 수 있는 것은 Redis 7.2.11, Valkey 7.2.11, Valkey 8.1.6. NCP 표의 End of Life는 Redis 7.2가 2026-02-28(이미 지나 새 마이너 판본이 나오지 않음, 판매 종료·운영 지원 종료일은 미공지), Valkey 7.2가 2027-04-16, Valkey 8.1이 2028-03-31. Redis 5.0·7.0은 판매 종료. 메이저 판본 올리기는 공식 지원하지 않음 | 세 엔진 모두 같은 결과 | 엔진 선택은 H가 [#24][i24]에서 정한다 |
