## 1. 핵심 성공 기준

> **GitHub에 흩어진 개발자의 실제 활동을 정확한 근거로 구조화하여, 개발자는 자신의 경험을 다시 꺼내 활용할 수 있고 기업은 그 경험을 이해하고 원본까지 검증할 수 있게 만드는 것.**

```
GitHub 실제 활동 → ① 제대로 추출했나 → ② 개발자에게 가치가 있나 → ③ 기업에 전달되나 → ④ 믿을 수 있나
                    사실 일치율            회수 성공률           (조건부 지표)      근거 확인 성공률
                    귀속 정확도
```

**KPI로 쓰지 않는 것**

| 제외 | 사유 |
|---|---|
| 취업·채용 성공률 | 지원→면접→합격 구간에 관여하지 않는다 |
| 기업 실무자의 실제 업무 시간 | 우리가 통제할 수 없는 환경에서 발생한다 (§3) |
| P1 경험 정리 시간 단축률 | P1 v3.0이 *"시간이 걸려도 한다"*로 정의됨 → 참고 지표로 강등 |

## 2. 설계 원칙

1. **측정 가능성이 1차 조건.** 데이터 출처·계산식·수집 주기를 지금 못 적으면 KPI로 쓰지 않는다.
2. **정확도에도 비교 대상이 필요하다.** 규칙 기반 baseline과 비교한다 (§6.1).
3. **원칙 1(평가하지 않는다)은 *사용자 화면*에 대한 것**이고, KPI는 *우리가 프로젝트를 평가하는 잣대*다.
4. **한 방향으로만 좋은 결과는 성공이 아니다.** 반대로 당기는 지표는 함께 본다 (§5.1).
5. **"기여도"를 쓰지 않는다.** 퍼센트로 읽혀 원칙 1과 부딪힌다 → **"수행 내용" / "누가 무엇을 했는지"**.

## 3. 무엇을 잴 수 있나 — 판정 기준은 *통제 가능 여부*

| 판정 | 조건 | 해당 |
|---|---|---|
| ✅ 성공 기준으로 쓴다 | 우리가 만든 데이터·로그로 직접 잰다 | GT 대조 · P1 테스터 과제 · P4 처리시간 |
| ◐ 참고로만 잰다 | 우리가 운영하는 실험 안이라 통제되지만 대역 피험자라 일반화 불가 | 대역 과제 · **실험 세션 내 소요 시간** |
| ❌ 재지 않는다 | 관측도 통제도 안 되는 환경 | **기업 실무자의 실제 업무 시간** |

> **P3의 업무 시간은 못 재고 P4의 처리시간은 잰다** — 후자는 우리 서비스 내부의 이벤트 간격이기 때문이다.
> **"시간을 아예 안 잰다"는 뜻이 아니다.** P3 v3.0의 요구는 *"면접 전 5분"*이다. 실험 세션 안의 소요 시간은 **참고로 기록**하되 합격선으로 쓰지 않는다.

## 4. 핵심 KPI 4개

| 우선 | KPI | 무엇을 증명하나 | 측정 |
|---|---|---|---|
| ⭐ **Primary** | 증거 카드 **사실 일치율** | AI가 만든 카드를 믿을 수 있는가 | ✅ GT 대조 (피험자 0명) |
| ⭐ AI Quality | 개인 수행 내용 **귀속 정확도** | 그 일을 **이 사람이** 했는가 | ✅ GT 대조 (피험자 0명) |
| ⭐ P1 Value | 개발 경험 **회수 성공률** | 잊고 있던 것을 되찾아줬는가 | ✅ 수료생 동기 5명 |
| Evidence UX | **근거 확인 성공률** | 요약에서 원본까지 도달하는가 | ✅ 위 5명 세션에 병합 |

**기업 측 테스터 없이 4개를 다 잰다. 남은 전제는 Ground Truth 하나다.**
**발표에서 앞에 세우는 둘** — 사실 일치율(*AI를 믿을 수 있다*) · 회수 성공률(*사용자에게 실제로 준 것이 있다*).

> 🔲 **안건 1의 결과에 따라 이 표에 행이 늘 수 있다** — 기술 스택 도출 정확도 · 프리셋 연결 타당성.

### 4.0 🔲 안건 1 — 정확도를 어느 표면까지 적용할 것인가

v1.4로 근거 링크를 단 표면이 셋이 되었다. **각 층은 주장을 만든 주체가 다르다.**

| 층 | 주장을 만든 주체 | 현재 |
|---|---|---|
| 증거 카드 | **AI** | ✅ 재는 중 |
| 기술 스택 배지 (v1.4 §5.2 — 자가 입력 금지, 전부 카드에서 도출) | **AI(집계 규칙)** | ❌ |
| 프리셋 문장 (v1.4 §6.2 — 전체 공개, 프로필 첫 화면) | **사용자** | ❌ |
| 경험 요약(HR용) | AI(파생) | ❌ |

**KPI 4.1은 *"AI가 만든 주장이 기록과 맞는가"*를 잰다. 프리셋은 *"사용자의 주장을 그 카드가 뒷받침하는가"*다 — 다른 종류의 정확성이고 책임 주체도 다르다.**

**결정 후 이 절에 확정 내용을 적고, 아래 4.1~4.4의 판정 대상 문구를 맞춘다.**

---

### 4.1 ⭐ 증거 카드 사실 일치율 (Primary)

카드의 주장과 근거가 실제 GitHub 기록과 일치하는 비율.

```
실제 근거와 일치하는 카드 수 ÷ 평가 대상 카드 수 × 100
```

| 예 | |
|---|---|
| 주장 | "JWT 기반 인증 로직을 구현했다" |
| 근거 | Commit A · PR #24 · 관련 코드 변경 |
| 판정 | 그 커밋·PR이 실재하고 내용이 주장을 뒷받침하는가 → ○/× |

**Primary인 이유** — 세 페르소나를 관통하는 것이 증거 카드이고, **원칙 4(주장과 근거를 연결한다)가 곧 이 지표**다. 그리고 피험자 없이 100% 통제된다.

### 4.2 ⭐ 개인 수행 내용 귀속 정확도

```
귀속이 맞는 카드 ÷ 팀 프로젝트 카드 × 100
```

- **분모는 팀 프로젝트 카드만.** 1인 프로젝트는 귀속 오류가 발생할 수 없어, 넣으면 1인 레포를 늘리는 것만으로 100%에 가까워진다.
- **판정 규칙** — "팀 프로젝트 카드" = **본인 외 작성자의 커밋이 1건 이상 있는 레포에서 생성된 카드.** 그 영역을 혼자 작업했더라도 레포에 타인이 있으면 분모에 넣는다.

> P1(*"팀플에서 내 몫이 흐릿하다"*) · P2(스택이 나열이 아니라 실제 활동인지) · P3(*"이 사람이 실제로 무엇을 했는지"* — 필요한 것 목록의 핵심) 셋이 모두 요구하는 지점.

### 4.3 ⭐ 개발 경험 회수 성공률

사용자가 **스스로 떠올리지 못한** 실제 경험 중 카드로 되찾은 비율.

```
              카드로 회수한 경험 수
─────────────────────────────────────────── × 100
GT 주요 경험 중 사용자가 스스로 작성하지 못한 수
```

```
예)  GT 주요 경험 10건 / 스스로 작성 6건 → 분모 4건 / 카드로 회수 3건 → 75%
```

**계산·통제 규칙** — 이게 없으면 분모가 피험자 성실도에 좌우된다. 대충 쓰면 분모가 커져 수치가 오르고, 성실히 쓰면 1~2건이라 0%/100%로 튄다.

| # | 규칙 |
|---|---|
| 1 | **개인별 비율을 평균 내지 않는다.** 전원의 분자 합 ÷ 분모 합 |
| 2 | 작성 과제에 **시간 상한 30분 + 하한 3건** |
| 3 🔲 | **GT 작성자와 피험자를 분리한다** → 안건 2-B에서 담당 배정과 함께 확정 |
| 4 | 분모 0건인 피험자(전부 스스로 떠올림)는 합에서 빼고 **건수를 별도 표기** |

**커버리지와 다르다** — 커버리지의 분모는 *전체* 주요 경험(AI 성능), 회수의 분모는 사용자가 *놓친* 경험(사용자 가치).

> **P1 핵심 고통 ①(있는데 꺼내지 못한다)을 직접 잰다. CatchU가 시간 절약 도구가 아니라 경험 복원 도구임을 보여주는 지표다.**

함께 받는 정성 평가(5점) — *"생성된 자료가 내가 실제로 한 일을 설명하는 데 도움이 되었는가?"*

### 4.4 근거 확인 성공률

주장에서 실제 원본(Commit·PR)까지 스스로 도달한 비율. **성공 판정은 도달 여부로 하고, 소요 시간은 참고로만 기록한다.**

시스템 지표인 **근거 링크 유효율(§5.2)과 분리한다** — 링크가 다 살아 있어도 UI 때문에 못 찾으면 UX 실패, UI가 좋아도 링크가 깨지면 기술 결함이다.

> ### 🔲 안건 3 — 확인 과제를 어느 층에서 시작할 것인가
> 현재 정의는 *"카드의 주장에서 원본까지"*다. 그런데 **실제 사용자는 카드에서 출발하지 않는다** — v1.4 §5.4에서 프로필 첫 화면에 있는 것은 디폴트 프리셋이고 그 옆이 스택 배지다.
>
> | | 과제 문구 | 통과 층 |
> |---|---|---|
> | A | *"이 **카드**의 근거 원본을 찾아보세요"* | 1층 (현재안) |
> | B | *"이 **프리셋 문장**의 근거 커밋까지 가보세요"* | **3층 전부** — P3가 요구한 *"모든 항목에 한 뎁스 내 근거 링크"*가 성립하는지 드러남 |
> | C | 층별 개별 과제 | 세션 시간 증가 |
>
> **§6.2 세션 과제지를 만들기 전에 정해야 한다. 세션은 한 번뿐이다.**

## 5. 보조 지표

### 5.1 핵심 경험 커버리지 — 사실 일치율과 짝

```
카드가 포착한 주요 경험 ÷ GT 주요 경험 × 100
```

**두 지표는 반대로 당긴다.** AI가 보수적으로 굴어 카드를 2개만 만들면 일치율은 100%가 되지만 서비스는 쓸모없다. **반드시 함께 보고하고, 한쪽만 좋은 결과는 성공으로 보지 않는다.**

### 5.2 근거 링크 유효율

```
유효한 링크 ÷ 전체 근거 링크 × 100      기준 100% — 깨진 링크는 품질 편차가 아니라 버그다
```

> 🔲 **안건 3 — 어느 층까지 100%를 요구할 것인가.** 이 기준은 링크가 한 종류일 때 세운 것이다.
> 카드→커밋 ✅ 유지 / 프리셋 문장→카드 🔲 / **배지→근거 카드(배지 × N, 수가 가장 많다)** 🔲
> v1.4 §5.2는 배지의 근거 링크를 *"우리 차별점이 한 화면에서 드러나는 지점"*이라 못박았다. **차별점이라면 유효율 기준도 따라와야 한다.**

### 5.3 Critical Error — 타인 기여 오귀속

타인의 Commit·PR을 본인 활동으로 귀속하는 경우. **1건이라도 발견되면 원인 분석에 착수하고, 해결 전까지 해당 분석 기능 공개를 보류한다.** 비율 지표가 아니라 **안전 조건**이다.

### 5.4 오답 유형 기록

| 유형 | 내용 | 축 |
|---|---|---|
| 환각 | 존재하지 않는 커밋·PR을 근거로 제시 | 정확성 |
| 근거 부족 | 근거는 실재하나 주장을 뒷받침하지 못함 | 정확성 |
| 과장 | 사실이지만 수행 범위를 부풀림 | 정확성 |
| **오귀속** | 타인의 기여를 본인 것으로 표시 | **Critical** |
| 누락 | 중요한 경험을 카드로 만들지 못함 | 완전성 |
| 과대 도출 🔲 | 근거가 빈약한데 스택 배지로 올라감 (설정 파일 한 줄 → `[Java]`) | 안건 1-C |
| 근거 불일치 🔲 | 프리셋 문장에 연결된 카드가 그 문장을 뒷받침 못 함 | 안건 1-B |

## 6. 측정 계획

### 6.1 규칙 기반 baseline — 즉시 착수, 피험자 0명

*"일치율이 몇 %"*만으로는 좋은 건지 알 수 없다. **비교 대상이 있어야 성능에 의미가 생긴다.**

| | |
|---|---|
| 방식 | 커밋 메시지 키워드 + 변경 파일 확장자·경로만으로 카드 생성 (**LLM 미사용**) |
| 예 | `*.jsx` 변경 + "component" → "React 컴포넌트 작업" 카드, 근거는 해당 커밋 |
| 비교 | 사실 일치율 · 귀속 정확도 · 커버리지 전부 |

```
[측정 후 채운다]        규칙 기반    CatchU     차이
사실 일치율                __%        __%      __%p
핵심 경험 커버리지          __%        __%      __%p
귀속 정확도                __%        __%      __%p
```

**스크립트 자체가 개발 산출물로 남는다.**

### 6.2 P1 세션 — 즉시 착수, 수료생 동기 5명

**한 번의 세션에서 셋을 얻는다.** 회수 성공률의 분모·분자, 그리고 근거 확인 성공률.

| 단계 | 내용 | 산출 |
|---|---|---|

## 7. 목표값 · 최소 품질 · 실패 조건

### 7.1 성과 목표값 — baseline 측정 후 결정

```
사실 일치율        규칙기반 __%  →  목표 __% 이상
핵심 경험 커버리지  규칙기반 __%  →  목표 __% 이상
경험 회수 성공률   기준 없음     →  1차 측정 후 설정
```

이렇게 해야 *"왜 그 숫자냐"*에 **"규칙 기반이 이 수치였기 때문"**이라 답할 수 있다.
**함께 정할 것** — 아래 Kill Criteria의 *"한쪽만 높음"* 임계값.

### 7.2 최소 품질 기준

| 항목 | 상태 |
|---|---|
| 일치율 · 귀속 · 커버리지 | GT 1차 평가 후 확정 — **지금은 숫자를 적지 않는다** |
| 근거 링크 유효율 | **100%.** 깨진 링크는 버그 |
| 타인 기여 오귀속 | **0건.** 비율이 아니라 안전 조건 |

### 7.3 실패 조건 (Kill Criteria)

| 조건 | 판정 |
|---|---|
| 사실 일치율이 규칙 기반과 비슷하거나 낮음 | 실패 — **LLM을 쓸 이유가 없다** |
| 커버리지와 일치율 중 한쪽만 높음 | 실패 — §5.1 트레이드오프 *(임계값은 7.1에서 확정)* |
| 타인 기여 오귀속 1건 이상 | 원인 규명 전까지 해당 기능 공개 보류 |
| 근거 링크 유효율 100% 미만 | 원칙 4 미구현. 버그 처리 |
| 경험 회수 성공률이 0에 수렴 | 실패 — 사용자가 이미 아는 것만 보여준 것 |
| 자료만 보고 "무엇을 했는지" 답하지 못함 | 실패 — **전달되지 않는 카드는 카드가 아니다** |

## 8. 운영 KPI (P4)

P4 v2.0의 성공 기준은 *"이현우가 하는 일이 적을수록 잘 설계된 것"*이다.

| KPI | 계산식 | 방향 |
|---|---|---|
| 운영 자동 처리율 | 사람 개입 없이 끝난 건 ÷ 전체 운영 건 × 100 | ↑ |
| 예외 건 평균 처리시간 | 신고 접수 시각 → 처리 완료 시각의 평균 | ↓ |

**모니터링(KPI 아님):** AI 오탐률 · 운영자 개입 건수 · 시스템 오류율
**전제:** 처리 로그에 접수·완료 시각이 남아야 한다. 실사용자 신고가 0건이면 분모도 0이므로 **합성 시나리오 리허설 여부는 미결**이다.

## 9. 조건부 지표 — 대역 피험자를 확보하면

핵심 KPI가 아니다. **확보하지 못하면 "미측정"으로 명시한다.**

**공통 프로토콜** — 같은 자료·같은 3문항을 주고 피험자 유형만 바꾼다.
*① 실제로 무엇을 했나 ② 어떤 기술을 실제로 썼나 ③ 그 판단의 근거는 무엇인가*

| 피험자 | 지표 | 보는 자료 |
|---|---|---|
| 비개발자(P2 대역) | 개발 경험 이해 성공률 | 경험 요약 |
| 개발자(P3 대역) | 실제 수행 내용 파악 성공률 | 증거 카드 |
| 본인(P1) | 경험 전달 가능성 | 증거 카드 |

**판정하는 것은 "답할 수 있었는가"다.** 소요 시간은 참고로만 기록한다.

| 그 외 | 상태 |
|---|---|
| P1 재사용 가능성 | 정의만 있고 계산식 미정 |
| P2 후보 발견 성공률 | 우리 프로필은 신입인데 P2 소싱 대상은 경력자다. 조건을 신입 기준으로 다시 쓸지 미측정 선언할지 **미결**. 모집단은 v1.4 §6.3 **인재풀 노출 ON**인 프로필로 한정된다 |
| P3 면접 질문 **근거 확보율** | ~~AI 면접 질문 정확도~~ 아님. P3는 *"질문이 아니라 질문을 만들 재료"*를 원한다 |

**실험 통제** — 같은 피험자에게 기존 자료 → CatchU를 연달아 주면 두 번째가 잘 되는 것은 이미 그 사람을 알기 때문이다. 후보 세트 2개 이상으로 순서를 교차한다.
**n이 작아도 괜찮다.** *"n=5, 대역 피험자, 통제 실험"*이라 밝히는 편이 출처 불명의 큰 숫자보다 신뢰를 얻는다.

**서비스 운영 이후(실사용자 필요, 정의만 둠):** 프로필 공개 완료율 · 후보 프로필 열람률 · DM 전환율 · 기업→개발자 접촉 건수. **클릭 수·체류 시간·재방문율은 쓰지 않는다.**

## 11. 발표 연결

```
[문제]  기술 면접관은 지원자의 실제 개발 경험을 확인하고 싶지만, 개발 업무와 채용을 병행해
        GitHub까지 직접 확인하기 어렵다. 개발자 본인도 자신이 무엇을 했는지 다시 꺼내기 어렵다.

        "GitHub를 봐야 한다고 생각하지만 실제로는 거의 보지 못한다."  — 2026.08.27 현직 기술 면접관

[해결]  GitHub 커밋·PR을 근거 링크가 달린 증거 카드로 구조화한다.

[결과]  규칙 기반 baseline 대비 사실 일치율 · 커버리지 · 귀속 정확도  ← 측정 후 기입
        P1 5명 회수 성공률 · 근거 확인 성공률 · 정성 평가        ← 측정 후 기입

[한계]  기업 실무자 검증은 대역 피험자로 대체. 실사용자 Service KPI는 미측정.
        GT는 팀이 작성했으며 2인 독립 판정 + 판정자 간 일치율을 함께 제시.
```

> **숫자는 측정 후에 넣는다.** 예시 값을 슬라이드에 남기지 않는다.

### 🔲 안건 4 — 문제 제기의 근거

**"면접관의 절반이 GitHub를 확인하지만 57.8%는 이력서를 10분 안에 검토한다"는 문장은 쓰지 않는다.** 57.8%는 **HR 담당자** 조사, 50%는 **채용 과정 일반** 조사로 모집단이 다르다. 이어 붙여 인과를 주장하면 지적당했을 때 문제 제기 전체가 흔들린다.

**그런데 확정정의서(레포 밖)의 시장 배경 절은 반대로 서술되어 있다** — *"10분 이내 검토 57.8%와 GitHub 확인 50%의 조합이 우리 서비스의 존재 이유다."* 그 문서가 상위 문서이므로 **정의서를 고치거나 이 판단을 철회해야 한다.** P2 v2.0 · P3 v3.0도 같은 수치를 인용 중이다.
