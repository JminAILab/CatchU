# CatchU 작업 동일성 판별 기준

> **지위: 채택** (2026-09-30, 팀장 `ljm0850`) · F(팀원 1)가 [#111][i111]에서 2026-09-29 제안으로 작성했고, 2026-09-30 B·E 검토와 팀장 결정을 반영한 뒤 팀장이 [#118][i118]의 구현 기준으로 채택했다(「결정」). B(`leechaeah`)·E(`yeongyeon1802`)는 `5c004e4`에 일반 검토 의견을 남겼고(승인 아님), 이 수정본에 그 의견을 반영했다. E는 `8155e6d`의 처리 기준을 승인했다([E 수정본 승인][e180r]). B는 `eab0989`를 다시 확인해 B1~B5와 반영 거부 구분을 수용했고(승인 아닌 의견), 요청한 구현 설명 정정 3곳은 이 판에 반영했다([B 수정본 확인][b180r]). 팀장이 정한 것은 네 가지다(「결정」). 단위 미확정 변경의 보류(2026-09-29), SHA가 다른 두 변경을 같은 변경으로 보는 기준(2026-09-30), 확인 중단으로 보류한 변경의 집계 방식(2026-09-30), 저장소별 판정(2026-09-30)이다. 확인 중단 때 실패를 기록하고 적합 후보 유무로 PARTIAL_FAILED·FAILED를 나누는 것은 기존 규칙(worker 규칙 BR3.2·BR3.3, #116 문서 2.4)에 맞춘 보완이다. 실제 판별 코드는 이 기준으로 [#118][i118]에서 만든다. [API 명세 v1][c92]·[ERD][e119]와 어긋나면 계약이 이긴다. 이 기준은 필드·권한·상태 의미·DB 관계와 유일성을 바꾸지 않는다. B 등록의 기본 동작 인용은 [PR #143][p143]의 `e2acdfe` 기준이며, 저장소·방식 불일치 거부는 같은 PR의 `a5ac5dd` 구현을 별도로 구분한다([구현 커밋][b180impl]).

같은 작업이 Catch로 두 번 만들어지거나, 서로 다른 작업이 한 Catch로 합쳐지지 않도록 **workIdentity**(후보가 어떤 실제 작업인지 나타내는 값)를 만드는 방법과 판정 규칙을 정한다.

## 한눈에 보기

1. **작업**은 한 저장소에서 회원이 기여한 변경의 묶음이다. 기본 단위는 저자가 묶은 것(PR 하나, 또는 PR 없이 병합한 브랜치 하나)이고, 어디에도 속하지 않은 커밋은 F가 묶는다.
2. **같은 작업인지는 그 작업을 이루는 GitHub 기록(PR 번호, 병합 커밋, 커밋과 그 diff)으로만 본다.** F가 만든 제목·설명·초안·근거 문장은 보지 않는다. PR 제목·본문은 재제출을 확인할 때 원 PR의 번호·주소를 찾는 데만 읽는다. 그래서 표현만 바뀌면 같은 값이 나오고, 근거가 일부 겹쳐도 작업 단위가 다르면 다른 값이 나온다. SHA가 다른 두 변경은 같은 작업에서 비롯됐다는 관계(원 PR을 가리키는 재제출 설명, cherry-pick 표시)가 확인되고, 공백을 무시한 diff가 같을 때만 같은 변경으로 본다(2026-09-30 팀장 결정). 관계 근거가 없으면 공백을 무시한 diff가 같아도 합치지 않는다. 같은 이슈를 참고했거나 같은 파일을 고친 것은 관계 근거가 아니고, PR 상태와 만든 순서만으로도 재제출로 보지 않는다. 관계가 확인된 두 변경 사이에서는 문자열 안 공백이나 들여쓰기만 다른 차이를 구분하지 못하며, 이 한계는 감수한다.
3. **한 결과(한 번의 분석이 낸 후보 목록) 안에서 같은 변경은 한 후보에만 속한다.** 여러 PR에 같은 변경이 들어 있으면(통합·반영용 PR, 다시 연 PR) 한 곳에만 배정한다.
4. **한 단위 안에 서로 다른 작업이 있다는 근거가 있을 때만 단위를 나눈다.** 근거가 없으면 나누지 않고 한 후보로 둔다(도메인 설계 [Q7][q7] 결정).
5. **판정 범위는 한 회원·한 저장소·한 방식(합성 MOCK 또는 실제 LIVE) 안이다.** 회원은 B가 이미 (회원, workIdentity) 조합을 하나만 허용해 구분한다. 저장소와 방식은 workIdentity 값 안에 넣는다. 초기 B 등록 코드(`e2acdfe`)는 기존 Catch를 참조할 때 저장소와 방식을 대조하지 않았고, 최신 PR #143은 다르면 그 결과의 반영 전체를 거부한다. 어느 쪽이든 저장소나 방식이 다른 작업이 같은 값을 가지면 안 되기 때문이다. 원본과 포크처럼 저장소가 다르면 같은 변경도 각각 Catch가 된다. 저장소 간 중복 판별은 10월 MVP 범위가 아니다(2026-09-30 팀장 결정).
6. **값은 `wi1:` 뒤에 SHA-256 해시를 붙인 68자 문자열이다.** 해시 입력은 규칙 판본(판별 규칙을 바꿀 때 올리는 번호, 지금 wi1)·방식·저장소·작업 단위·나눈 부분(한 단위를 둘 이상으로 나눴을 때 이 후보에 속한 커밋·파일)이다. B는 문자열이 같은지만 비교한다.
7. **어느 PR에 속하는지 확인하지 못한 변경은 후보로 내보내지 않고 보류한다(2026-09-29 팀장 결정).** 틀린 내용을 Catch에 넣지 않는 쪽을 택했고, 대신 보류한 작업은 회원에게 보이지 않는다. 보류의 기록은 두 경우로 나뉜다(「결정」).
   - 허용된 수집 범위와 수집 상한(호출 수·시간·총량) 안에서 필요한 조회를 마쳤는데도 정해지지 않으면 notProvided(내보내지 않은 후보를 사유별로 세는 칸)의 기존 사유 값 UNDETERMINED로 센다. 실패는 기록하지 않는다.
   - 수집 상한이나 조회 오류로 확인을 마치지 못했으면, 보류와 별개로 수집 실패를 기록한다. 그래서 결과는 적합 후보가 있으면 PARTIAL_FAILED, 없으면 FAILED가 된다(BR3.3·#116 문서 2.4의 기존 규칙). 이 보류는 notProvided에 세지 않는다(2026-09-30 팀장 결정). 두 경우의 보류 건수는 운영 로그에서 나눠 본다.
8. **같은 결과의 재전달과 같은 작업의 중복 등록은 다른 문제다.** 재전달은 E가 resultId와 결과 내용이 같은지(messageId만 뺀 결과 전체의 해시)로 알아본다. 중복 등록은 B가 (회원, workIdentity)로 막는다.
9. **10월에 이 값이 하는 일은 두 가지다.** ① 한 결과 안에서 후보마다 다른 값을 내, 서로 다른 작업이 한 Catch로 합쳐지지 않게 한다. ② 같은 회원의 다른 저장소 작업이 번호가 같다는 이유로 기존 Catch에 붙지 않게 한다. 같은 작업이라도 다음 분석에서 커밋 SHA가 바뀌거나(rebase) F가 커밋을 묶는 범위가 달라지면 v1은 다른 값을 내 새 Catch를 만든다. 10월 계약은 Catch를 만든 저장소를 다시 분석하지 않으므로 이 일이 생기지 않는다(「판정 규칙」). 재분석을 도입하기 전에 처리를 정하고, 그때까지 v1을 재분석에 쓰지 않는다.

## 식별자가 가리키는 것

| 식별자 | 가리키는 것 | 같은 값이 다시 오면 | 막는 곳 |
|---|---|---|---|
| requestId | 회원의 분석 요청 하나. 실패 뒤 재요청은 새 요청이다 | — | E |
| attemptId | 그 요청을 처리한 시도 하나. 10월은 요청당 하나다 | 끝난 시도의 늦은 결과는 반영하지 않는다. 시도당 결과는 하나라서, 이미 결과를 받은 시도에 다른 resultId가 오면 거부한다 | E |
| resultId | 한 시도에서 F가 만든 결과 하나(후보 목록 전체) | 내용이 같으면 재전달로 보고, 다르면 거부한다 | E |
| candidateId | 결과 안의 후보 하나 | 같은 결과의 반영을 다시 실행하면 저장된 등록을 그대로 돌려준다 | B의 후보 등록 기록 |
| workIdentity | 후보가 가리키는 실제 작업 하나. 요청·시도·결과가 달라도 같은 작업이면 같다 | 같은 회원에게 이미 있으면 기존 Catch를 참조한다 | B의 (ownerId, workIdentity) 유일성 |

**같은 결과의 재전달**은 전달이 반복된 것이다. 결과 자체는 같다. E는 resultId와 내용 지문(messageId만 뺀 결과 전체의 SHA-256)으로 이를 알아보고 중복 수신으로 답한다([E 지문][x-efp], [중복 판정][x-edup]). 응답 유실이나 반영 복구로 반영을 다시 실행하면 B는 후보 등록 기록으로 같은 catchId를 돌려준다([기능 설계 L76][f76]). 이때 B는 동일성을 새로 판정하지 않는다. 다만 받은 후보의 workIdentity가 저장된 Catch의 값과 같은지 확인하고, 다르면 거부한다([B 재반영 대조][x-breapply]).

**같은 작업의 중복 등록**은 서로 다른 후보가 같은 작업을 가리키는 것이다. resultId·candidateId가 달라도 생긴다. B는 (회원, workIdentity)로 이를 알아본다.

E의 지문과 B의 재반영 대조가 모두 같은 값을 요구한다. 그래서 F는 값을 결과를 만들 때 한 번만 계산해 결과와 함께 보관하고, 재전달·반영 복구 때 다시 계산하지 않는다.

## 무엇을 하나의 작업으로 보는가

**작업은 한 저장소에서 회원이 기여한 변경의 묶음이다.** 근거로 작업 사실과 본인 기여를 확인할 수 있어야 한다. 묶는 출발점은 저자가 이미 묶어 둔 단위다. [레포 컨벤션 §0][conv]과 [카드생성논리 방법 A][cardA]가 이 단위를 가장 믿을 만한 작업 경계로 보았다. 그 밖의 커밋은 F가 규칙으로 묶는다([방법 B][cardB]).

| 작업 단위 | 뜻 | 값에 쓰는 식별 |
|---|---|---|
| PR | 회원이 참여한 PR 하나. 병합 여부와 병합 방식은 따지지 않는다 | PR 번호 |
| 병합 | PR 없이 브랜치를 병합 커밋으로 합친 묶음 | 병합 커밋 SHA |
| 커밋 묶음 | PR·병합에 속하지 않은 커밋을 F가 규칙으로 묶은 것(방법 B) | 커밋 SHA 집합 |
| 이슈 | 코드 변경 없이 이슈로만 기여한 것. 계약의 허용 자료 종류에 있어 형식만 정한다. 10월 동의 문구(커밋·PR·diff)에는 없다 | 이슈 번호 |

- **한 후보는 작업 단위 하나에서 나온다.** 저자가 따로 연 PR 두 개를 F가 한 후보로 합치지 않는다.
- **한 결과 안에서 같은 변경은 한 후보에만 속한다.** 같은 변경인지는 「PR 소속과 같은 변경을 확인하는 근거」로만 확정한다. 한 커밋을 파일 경로로 나눈 경우에는 같은 커밋의 같은 경로를 같은 변경으로 본다.
- **병합 커밋은 변경으로 세지 않는다.** 부모가 둘 이상인 병합 커밋은 단위의 경계를 정하는 데만 쓴다([PoC 경계 A][poc-a]도 병합 커밋을 내용에서 뺐다). PR을 합친 병합 커밋과 기준 브랜치를 받아온 병합 커밋이 모두 그렇다. 단위를 나눌 때도 병합 커밋은 어느 부분에도 넣지 않는다.
- **여러 단위에 들어 있는 변경의 배정.** 변경이 여러 단위에 들어 있으면 한 단위에만 배정한다.
  - PR에 속한 커밋과, PR을 squash·rebase로 합친 커밋은 PR에 배정한다.
  - 여러 PR에 들어 있으면 가장 먼저 병합된 PR에 배정한다. 병합된 PR이 없으면 번호가 가장 작은 PR에 배정한다. 쌓아 올린 PR(뒤 PR이 앞 PR의 커밋을 담음)에서는 공유 커밋이 먼저 병합된 앞 PR로 가고, 뒤 PR은 자기 커밋만 갖는다.
  - PR 없는 병합끼리 겹치면 그 변경을 처음 들인 가장 안쪽 병합에 배정한다([PoC 경계 A][poc-a]).
  - 기준 브랜치(기본 브랜치나 통합 브랜치)를 작업 브랜치로 받아온 병합은 작업 단위로 쓰지 않는다. 그 병합이 들여온 커밋은 원래 들어온 단위에 속하고, 어디에도 속하지 않은 직접 커밋은 커밋 묶음으로 본다. 어느 브랜치를 기준 브랜치로 볼지는 #118에서 정한다(PoC는 저장소별 목록을 썼다).
- **배정 뒤 배정받은 변경이 하나도 없는 단위는 후보를 만들지 않는다.** 이미 들여온 변경만 옮긴 통합·반영용 PR, 같은 변경으로 다시 연 PR 중 배정받지 못한 쪽이 그 예다. 배정받은 변경만으로 작업 사실과 본인 기여가 확인되는 단위만 후보가 된다. 값은 그 단위로 만들고, 다른 단위에 배정된 변경을 부분으로 적지 않는다.
- **PR 조회가 허용되지 않은 요청.** 요청의 허용 자료 종류에 PULL_REQUEST가 없으면([명세 L155][c155]) 그 결과에서는 PR 단위를 쓰지 않는다. 병합·커밋 묶음 단위로만 묶으며, 이는 단위 미확정이 아니다. 다른 결과에서 PR을 볼 수 있게 되면 값이 달라진다(한계 L2).
- **단위 나누기(Q7).** 한 단위 안에 서로 다른 작업이 있으면 나눌 수 있다. 세 조건을 모두 채워야 한다.
  - 작업 사실과 본인 기여가 따로 확인된다.
  - 부분끼리 변경이 겹치지 않는다.
  - 단위에 배정된 모든 변경(다른 단위에 배정된 변경은 빼고)이 어느 한 부분에 속한다.
  - 하나라도 못 채우면 나누지 않는다. 속할 곳을 보일 수 없는 변경을 임의로 한 부분에 붙이거나 따로 후보로 내지 않는다.
- **부분은 PR·병합 단위를 커밋으로 나누거나, 한 커밋 안을 파일 경로로 나눌 때만 쓴다.** F가 묶은 커밋 묶음은 커밋 경계로 나누지 않고 별도 커밋 묶음 단위로 만든다.
- 어떤 커밋을 어느 커밋 묶음으로 묶는지(방법 B의 기준)와 본인 기여를 어떻게 가리는지는 #118의 범위다. 이 문서는 묶은 결과에서 값을 만드는 방법과, 묶을 때 지킬 조건만 정한다.

## PR 소속과 같은 변경을 확인하는 근거

**커밋이 어느 PR에 속하는가.** GitHub가 준 관계로만 정한다. 커밋 메시지·PR 제목·브랜치 이름의 글자로 정하지 않는다.

| 근거 | 쓰는 방법 |
|---|---|
| PR 커밋 목록 | PR에 담긴 커밋 SHA 목록. [PR 커밋 목록 API][gh-prc]는 최대 250개까지만 돌려주므로, 넘으면 [커밋 목록 API][gh-lc]로 전체를 받는다. 병합되지 않고 닫힌 PR의 커밋은 이 목록으로만 알 수 있다 |
| 병합된 PR의 `merge_commit_sha` | [PR API][gh-pr]가 주는 값이다. squash로 합쳤으면 대상 브랜치(PR을 병합한 브랜치)의 squash 커밋, rebase로 합쳤으면 대상 브랜치가 옮겨 간 커밋, 병합 커밋으로 합쳤으면 그 병합 커밋이다. 병합 전에는 시험용 병합 커밋이라 쓰지 않는다 |
| 커밋과 연결된 PR | [연결 PR API][gh-cpr]. 기본 브랜치에 있는 커밋이면 그 커밋을 들여온 병합 PR을 돌려준다. 기본 브랜치에 없으면 병합됐거나 열린 PR을 돌려주고, 병합되지 않고 닫힌 PR은 돌려주지 않는다 |
| 병합 커밋의 부모 | PR 없는 병합이 어느 커밋을 들였는지 정한다 |

- **한 근거로 소속이 나오고, 확인한 다른 근거와 어긋나지 않으면 소속을 확정한다.**
- **API가 원래 돌려주지 않는 관계는 어긋남이 아니다.**
  - squash·rebase로 합친 PR은 대상 브랜치에 새 SHA의 커밋을 만든다. PR 커밋 목록에는 원래 커밋만 남는다. 그래서 연결 PR API나 `merge_commit_sha`가 병합된 PR을 가리키는 커밋이 그 PR의 커밋 목록에 없는 것은 정상이다. 그 PR에 배정한다.
  - 병합되지 않고 닫힌 PR의 커밋은 연결 PR API가 돌려주지 않는다. PR 커밋 목록에 있으면 그 PR에 속한다.
- **PR 밖 확정**: 조회가 정상으로 끝났고, 연결 PR API가 빈 목록을 돌려줬고, 수집한 PR의 커밋 목록 어디에도 없으면 PR 밖이 확정된 것이다. 직접 push처럼 커밋 묶음으로 본다. 연결 PR API의 빈 목록만으로는 정하지 않는다.
- **단위 미확정**: 필요한 조회를 마쳤는데 근거끼리 서로 다른 답을 내는 경우다. 예를 들어 열린 PR #3에 대해 연결 PR API는 이 커밋에 PR #3을 돌려주는데, 같은 요청에서 받은 PR #3의 전체 커밋 목록에는 이 커밋이 없는 경우다. 두 조회 사이에 브랜치가 강제 푸시로 바뀐 경우 등이다.
- **확인 중단**: 조회를 마치지 못한 경우다(수집 상한, 조회 오류). 단위 미확정과 처리가 다르다(「판정 규칙」).

**SHA가 다른 두 커밋이 같은 변경인가.** 목적은 코드가 완전히 같은지 증명하는 것이 아니라, 같은 작업이 Catch로 두 번 등록되지 않게 하는 것이다(2026-09-30 팀장 결정, 「결정」).

1. **같은 SHA면 같은 변경이다.**
2. **SHA가 다르면 두 조건을 모두 채울 때만 같은 변경으로 확정한다.**
   - **관계 근거가 있다.** 두 변경이 같은 작업에서 비롯됐다는 근거다. 둘 중 하나여야 한다.
     - 재제출: 다음 두 가지를 모두 채워야 한다.
       - 한쪽 PR은 병합되지 않은 채 닫혔고, 다른 쪽 PR은 그보다 나중에 만들어져 그 변경을 담아 병합됐다. 한쪽 PR이 아직 열려 있거나, 둘 다 병합되지 않았거나, 병합되지 않은 PR이 병합된 PR보다 나중에 만들어졌으면 재제출로 보지 않는다. 되돌린 변경을 다시 넣으려고 연 PR일 수 있기 때문이다.
       - 뒤 PR(병합된 PR)의 제목이나 본문이 앞 PR을 번호(`#11`)나 같은 저장소의 PR 주소로 직접 가리킨다. 예를 들어 본문에 "#11을 기준 브랜치에 맞춰 다시 올립니다"라고 적은 경우다. 본문의 주소는 부르지 않고, 이미 수집한 앞 PR의 번호와 맞는지만 본다([#116 문서 2.1][d116-21]). 코드 블록·인라인 코드·HTML 주석 안의 글자, `abc#11`처럼 앞에 글자가 붙은 번호, 다른 저장소의 PR은 세지 않는다. `#11을`처럼 번호 뒤에 조사가 붙어도 센다. GitHub 화면은 이 모양에 링크를 만들지 않지만(2026-09-30 확인) 원 PR을 적은 것은 같기 때문이다. 그 문장이 '재제출'이라는 말을 쓰는지는 따지지 않는다. 앞 PR이 병합 없이 닫혔고 공백을 무시한 diff도 같아야 하기 때문이다. 그래서 뒤 PR이 앞 PR을 재제출이 아닌 뜻으로 적어도 합쳐질 수 있다(한계 L12).
     - cherry-pick 표시: 커밋 메시지의 `(cherry picked from commit <SHA>)`가 다른 쪽 커밋을 가리킨다.
     - 같은 이슈를 참고했거나, 같은 파일을 고쳤거나, 제목·설명이 비슷한 것은 관계 근거가 아니다(C24). PR 상태와 만든 순서만으로도 재제출로 보지 않는다. 앞 PR이 병합 없이 닫혔고 뒤 PR이 나중에 병합됐어도, 뒤 PR이 앞 PR을 가리키지 않으면 서로 무관한 PR일 수 있다(C30).
   - **공백을 무시한 diff가 같다.** 파일 경로와 diff에 나오는 줄에서 공백을 모두 빼고 비교하며, 줄 번호는 무시한다. diff에 나오는 줄은 더하고 뺀 줄과 그 앞뒤의 바뀌지 않은 문맥 줄이다. `git patch-id --stable`과 같은 기준이다([git 문서][git-pid]).
     - 더하고 뺀 줄만 비교하지 않고 문맥 줄도 함께 본다(`git patch-id`와 같다). 그래서 더하고 뺀 줄이 같아도 rebase로 앞뒤 문맥 줄이 바뀌었으면 값이 달라지고, 확정하지 않는다(C26, 한계 L10).
     - 변경 내용이 없거나 잘려 있으면 비교할 수 없으므로 확정하지 않는다. GitHub 커밋 API는 바이너리 파일과 변경이 큰 파일에서 `patch`를 빼고 준다. `patch`가 없는 파일을 빈 변경으로 보지 않는다.
3. **관계 근거 없이 공백을 무시한 diff만 같으면 합치지 않는다.** 이 비교는 공백을 모두 빼므로 실행 결과가 다른 두 변경을 같게 볼 수 있다. 합성 저장소에서 확인한 예는 다음과 같다(2026-09-30, git 2.54.0).
   - 같은 원본 `message = "old"`를 한 커밋은 `message = "a b"`로, 다른 커밋은 `message = "ab"`로 바꿨다. 실행 결과는 `a b`와 `ab`로 다른데 `--stable` 값은 같다(C21).
   - Python에서 `y = 2`를 조건이 거짓인 if 블록 안으로 들여 쓴 변경과, 같은 줄에 공백만 더한 변경도 `--stable` 값이 같다. 앞쪽만 프로그램 동작을 바꾼다(C22).
   - 관계 근거가 있으면 이런 차이도 같은 변경으로 본다(C25, 한계 L11). 목적이 같은 작업의 중복 등록을 막는 것이라 이 한계는 감수한다(2026-09-30 팀장 결정). 반대로 포매터로 공백만 정리해 다시 낸 변경은 이 기준으로 같은 변경이 된다(C23).
4. **확정하지 못하면 합치지 않는다.** 두 변경을 각자의 단위에 그대로 두고 두 후보를 모두 낸다. 후보를 빼지 않는다.
   - **다른 변경**: 관계 근거가 없다. 공백을 무시한 diff나 내용, 시간 순서가 재제출과 같아도 그렇다(C21·C22·C24·C30). groupingLimitations에 따로 적지 않는다.
   - **같은 변경 미확정**: 관계 근거는 있는데 공백을 무시한 diff가 다르거나, 변경 내용이 없어 비교할 수 없다(C26). 같은 작업일 수 있다는 점을 두 후보의 groupingLimitations에 적는다.
   - 어느 쪽이든 실제로는 같은 작업이 Catch 2개가 될 수 있다(한계 L10). 뒤 후보를 잘못 빼면 그 작업은 어디에도 남지 않지만, 중복은 회원이 비공개 상태에서 알아볼 수 있기 때문이다.
   - 두 후보는 저자가 따로 연 두 단위에서 나온다. 한 단위를 입증 없이 나누는 것이 아니므로, [Q7 기술 설계][q7d]의 "구별 가능성을 입증하지 못한 후보를 임의로 서로 다른 작업이라고 처리하지 않는다"와 부딪치지 않는다고 본다. 관계 근거가 없는 두 변경을 합치지 않는 것은 2026-09-30 팀장 결정이다.

| 범위 | 처리 | 이유 |
|---|---|---|
| 회원 | B의 (ownerId, workIdentity) 유일성이 구분한다. F는 회원 ID를 값에 넣지 않는다 | 같은 PR을 함께 작업한 두 회원은 같은 값을 갖지만 각자 Catch를 가진다. 다른 회원의 기여를 한 Catch에 붙이면 소유·공개 판단이 섞인다([ERD L121][e121]) |
| 저장소 | 요청의 repositoryId를 값에 넣는다. 저장소가 다르면 비교하지 않는다 | ① PR·이슈 번호는 저장소마다 새로 매겨진다. ② 초기 B 등록 코드(`e2acdfe`)는 기존 Catch를 참조할 때 새 요청의 저장소를 대조하지 않고 원 요청 저장소의 보호 판단만 봤다([조회][x-blookup], [시험][x-btest]). 그 판본에서는 값이 같으면 다른 저장소의 작업이 원 저장소 Catch에 붙어, 새 요청 저장소의 목록 필터와 보호 판단에서 빠졌다. 최신 PR #143은 저장소가 다르면 그 결과의 반영 전체를 거부한다([구현 커밋][b180impl]). 그래도 값이 같으면 다른 저장소의 정상 결과가 거부되므로 저장소를 값에 넣는다. ③ Catch의 저장소는 원 요청에서 정해지고 회원 Catch 응답과 저장소 필터에 쓰인다([ERD L125][e125]). 원본 보호(원본 저장소 상태에 따른 공개 제한)도 회원·저장소별이다([ERD L151][e151]). 그래서 포크나 옮긴 코드처럼 같은 변경이어도 저장소마다 따로 판정한다. 10월 MVP는 저장소마다 Catch가 생기는 것을 허용하고 저장소 간 중복 판별은 하지 않는다(2026-09-30 팀장 결정, 「검토 쟁점과 답」 계약2) |
| 방식 | sourceMode(MOCK/LIVE)를 값에 넣는다 | 합성 결과는 실제 작업 기록이 아니다. B는 새 입력의 방식을 그 시도와 대조한다([입력 대조][x-bmode]). 초기 판본(`e2acdfe`)은 기존 Catch를 찾을 때 (ownerId, workIdentity)만 쓰고 기존 Catch의 방식은 대조하지 않았다([조회][x-blookup]). 최신 PR #143은 방식이 다르면 그 결과의 반영 전체를 거부한다([구현 커밋][b180impl]). 지금 합성 경로는 이 함수의 값을 쓰지 않아 10월에는 이 충돌 경로가 없다. 합성 경로가 이 함수를 쓰게 될 때를 대비한 방어용이다 |

값에 넣지 않는 범위도 있다. 동의 범위 판본(scopeRevision)과 분석 시점의 저장소 커밋이다. 넣으면 동의 범위가 바뀌거나 새 커밋이 생길 때마다 같은 작업이 새 Catch가 된다. 이는 2026-09-13 팀장 답변 "실패 후 다시 요청해도 같은 작업의 카드가 중복으로 쌓이지 않게 한다"([MVP 입력 L189][m189])와 맞지 않는다. 어느 시점의 저장소를 분석했는지 기록하는 방법과, 새 커밋이 생긴 뒤 다시 분석할 때의 처리([MVP 입력 L200][m200])는 재분석 정책을 정할 때 함께 정한다.

## 판정 입력

| 입력 | 뜻 | 출처 |
|---|---|---|
| 규칙 판본 | 판별 규칙의 판본. 지금은 `wi1` | 상수 |
| 방식 | MOCK 또는 LIVE | 요청의 sourceMode |
| 저장소 | 분석 대상 저장소 | E가 접수한 요청의 repositoryId. 결과의 repositoryId와 같다 |
| 작업 단위 | PR 번호, 병합 커밋 SHA, 커밋 SHA 집합, 이슈 번호 중 하나 | F가 수집한 GitHub 기록이 준 번호·SHA. 제목·본문 글자에서 뽑지 않는다 |
| 나눈 부분 | 단위를 나눴을 때만: 이 작업에 속한 커밋, 한 커밋 안을 나눴으면 커밋과 파일 경로 | F의 묶음 결과. 나누지 않았으면 비운다 |

다음은 바뀌어도 값이 같아야 하므로 입력으로 쓰지 않는다.

| 쓰지 않는 입력 | 이유 |
|---|---|
| 제목, 작업 사실, 기여 설명, 초안, 최소 질문, 묶음 설명 | F가 만드는 문장이라 실행마다 달라질 수 있다. 표현만 바뀐 같은 작업이 같은 값이어야 한다([명세 L92][c92], [ERD L119][e119]) |
| 근거 문장, 근거 목록의 구성, evidenceId | 같은 작업이라도 근거를 더 보거나 덜 볼 수 있다. 근거가 겹친다고 같은 작업도 아니다([worker 모델 L35][w35]) |
| candidateId, resultId, attemptId, requestId, consentId, messageId, finishedAt | 전달·처리 번호일 뿐 작업을 가리키지 않는다 |
| PR 제목·본문 수정, PR에 추가된 커밋, 근거의 판본 값(sourceRevision) | 나누지 않은 PR은 PR 전체가 하나의 작업이라 커밋이 늘어도 같은 작업이다. 판본 값은 다른 작업끼리 같을 수도 있다(합성 자료의 `synthetic-revision-11`이 세 작업에 쓰였다) |
| 목록 순서, SHA 대소문자 | 정규화로 없앤다 |
| 회원 ID | B가 범위로 적용한다 |
| 동의 범위 판본, 분석 시점의 저장소 커밋 | 「판정 범위」의 이유 |

## 판정 규칙

F는 먼저 「무엇을 하나의 작업으로 보는가」의 조건대로 한 결과의 후보를 묶는다(같은 변경은 한 후보에만, 근거가 있을 때만 나누기). 그다음 후보마다 값을 만든다.

- **동일 작업**: 방식·저장소·작업 단위·나눈 부분이 모두 같다. 회원이 같은지는 B가 본다.
- **다른 작업**: 넷 중 하나가 다르고, 그 차이가 근거로 보인다. 저자가 따로 연 단위이거나, 근거로 구별돼 나눈 부분인 경우다. 근거(이슈·파일·리뷰·판본 값)가 겹쳐도 작업 단위나 나눈 부분이 다르면 다른 작업이다.
- **판정 불가**: 같은지 다른지 보일 수 없거나 확인을 마치지 못한 경우다. 아래 다섯 가지로 나눠 처리한다.

| 판정 불가 상황 | 처리 |
|---|---|
| **구별 불가**: 한 결과 안에서 한 단위의 두 변경이 서로 다른 작업인지 근거로 보일 수 없다 | 나누지 않고 한 후보로 내보낸다. 묶음의 한계는 groupingLimitations에 적는다([Q7 기술 설계][q7d]). notProvided에 세지 않는다 |
| **단위 미확정**: 근거·작업 사실·본인 기여는 확인됐다. 허용된 범위와 상한 안에서 필요한 조회도 마쳤다. 그런데 근거끼리 답이 어긋나 변경이 어느 단위에 속하는지 정할 수 없다(「PR 소속과 같은 변경을 확인하는 근거」). PR 조회가 허용되지 않은 요청은 여기에 들지 않는다(「무엇을 하나의 작업으로 보는가」) | 보류한다: 후보로 내보내지 않고 notProvided에 UNDETERMINED로 센다(「결정」). 수집은 정상으로 끝났으므로 실패는 기록하지 않는다 |
| **확인 중단**: 수집 상한(호출 수·수집 시간·총 처리 시간·수집 총량)에 걸렸거나 조회가 오류(429·5xx 등)로 끝나 소속 확인을 마치지 못했다 | 보류한다: 확인하지 못한 변경은 후보로 내보내지 않는다(「결정」). 이와 별개로 수집 실패를 failures에 기록한다(`stage: COLLECTION`, 코드는 [#116 문서 2.4][d116-24]의 제안 이름: `BUDGET_EXCEEDED`·`TIME_LIMIT_EXCEEDED`·`RATE_LIMITED` 등). 다시 부르지 않는다. 판단한 것이 아니므로 notProvided에는 세지 않는다. 결과는 적합 후보가 있으면 PARTIAL_FAILED, 없으면 FAILED다 |
| **같은 변경 미확정**: SHA가 다른 두 변경에 관계 근거(재제출·cherry-pick 표시)는 있는데, 공백을 무시한 diff가 다르거나 변경 내용이 없어 비교할 수 없다(C26). 관계 근거가 없으면 diff가 같아도 여기에 들지 않고 다른 변경이다(C21·C22·C24·C30) | 합치지 않고 두 후보를 모두 낸다. 같은 작업일 수 있다는 점은 두 후보의 groupingLimitations에 적는다. 후보를 빼지 않는다 |
| **결과 사이 변화**: 다른 결과에서 같은 작업의 단위나 부분이 바뀌었다. rebase, 묶음 경계 변화, 나누기 결정 변화가 예다 | v1은 다른 값을 낸다. 이는 [Q7 기술 설계][q7d]와 [MVP 입력 L189][m189]에 맞지 않는다. 그래서 재분석을 도입하기 전에 처리를 정하고, v1을 그대로 쓰지 않는다. 10월에는 이 경로가 없다(아래) |

근거의 판본을 확정할 수 없는 후보(짧은 SHA만 있고 원본에서 확정하지 못함 등)는 판정 이전의 문제다. 근거 요건([명세 L165][c165])을 채우지 못했으므로 기존 규칙대로 INSUFFICIENT_EVIDENCE(근거 부족)로 센다. UNDETERMINED는 근거 요건을 채우고 필요한 조회도 마친 뒤 단위만 정할 수 없을 때 쓴다.

**"끝까지 확인"의 뜻.** 요청의 허용 자료 종류와 [#116 문서 2.3][d116-23]의 수집 범위, 그리고 수집 상한 안에서 필요한 조회를 시도한다는 뜻이다. 상한을 넘는 추가 호출이나 자동 재시도는 하지 않는다. 이 문서에서 **수집 상한**은 #116의 호출 수·수집 시간·총 처리 시간·수집 총량 상한을 함께 가리킨다. 수집 상한에 걸려 멈추거나 조회가 오류로 끝났으면 수집 실패다. 반면 #116의 조회 개수 범위(최근 커밋·PR 개수) 밖이라 보지 못한 자료와, 단일 응답 크기 상한을 넘어 그 항목만 버린 자료는 수집 실패가 아니다. 근거의 한계(coverageLimits)로 남긴다. 이 구분은 [#116 문서 2.3·2.4][d116-24]를 따른다.

**10월의 결과 사이 경로.** 10월 계약에서는 같은 회원·저장소에서 Catch를 만든 결과 뒤에 또 결과가 오지 않는다. 실패 뒤 재요청은 앞 요청이 Catch를 하나도 만들지 않았을 때만 허용된다([명세 L74][c74]). 정상 완료(EMPTY 포함)나 유효 결과가 있는 부분 실패 뒤의 재분석은 거부된다([명세 L75][c75]). 그래서 다른 결과의 후보가 같은 저장소의 기존 Catch를 참조하는 경로가 없다.

제목·설명의 글자 유사도로 판정을 대신하지 않는다. 표현이 비슷한 다른 작업은 합쳐지고, 표현이 다른 같은 작업은 나뉘기 때문이다.

## workIdentity 만드는 법

```text
work_identity(방식, 저장소, 작업 단위, 나눈 부분):
  단위 =
    PR        → {"type": "PULL_REQUEST", "number": PR 번호}
    병합       → {"type": "MERGE", "commit": 병합 커밋 SHA}
    커밋 묶음   → {"type": "COMMITS", "commits": 정렬한 SHA 목록}
    이슈       → {"type": "ISSUE", "number": 이슈 번호}
    정할 수 없음 → 값을 만들지 않는다(단위 미확정: 후보를 내보내지 않음)
  부분 = 나눴으면 정렬한 [{"commit": SHA} 또는 {"commit": SHA, "path": 경로}], 아니면 []
  글 = 정규 JSON({"version": "wi1", "sourceMode": 방식, "repositoryId": 저장소,
                  "unit": 단위, "part": 부분})
  반환 "wi1:" + SHA-256(글의 UTF-8 바이트)의 소문자 16진수   # 68자
```

- **정규 JSON**: 키를 이름순으로 정렬하고 공백 없이 쓴다(`,` `:`). UTF-8로 쓰고 한글 등을 이스케이프하지 않으며, 숫자는 정수로 쓴다. Python으로는 `json.dumps(값, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`다.
- **정규화**
  - 저장소 값은 요청 값을 그대로 쓴다. 불투명한 문자열이라 대소문자나 공백을 바꾸지 않는다.
  - PR·이슈 번호는 GitHub가 준 1 이상의 정수를 쓴다.
  - SHA는 전체 길이 16진수를 소문자로 쓴다. 보통 40자이고, SHA-256 저장소면 64자다.
  - 파일 경로는 그 커밋에서 GitHub가 준 저장소 기준 경로를 그대로 쓴다. 대소문자를 구분하고 유니코드 정규화를 하지 않는다.
  - 커밋 목록은 중복을 없애고 정렬한다. 커밋이 하나도 없는 커밋 묶음은 만들지 않는다. 그런 입력은 F의 결함이므로 값을 만들지 않고, 단위 미확정(UNDETERMINED)으로도 세지 않는다.
- **부분의 정규화**
  - 단위 전체가 한 후보면 부분을 비운다. 모든 커밋을 부분으로 나열하지 않는다.
  - 한 커밋은 한 가지로만 적는다. 커밋 전체가 이 후보에 속하면 `{"commit"}`만 쓰고, 그 커밋의 모든 경로가 이 후보에 속해도 `{"commit"}`으로 줄인다. 경로로 나눈 커밋만 `{"commit", "path"}`로 적는다.
  - 항목은 (커밋 SHA, 경로) 순으로 정렬하고, 경로가 없는 항목을 앞에 둔다. 문자열은 유니코드 코드 포인트 순으로 비교한다(Python 기본 비교).
- **해시를 쓰는 이유**
  - 커밋 묶음과 부분은 길이 제한이 없다. B의 유일성 색인에 넣을 값은 짧고 길이가 일정해야 한다.
  - 저장소 값은 불투명 문자열이라 `:` 같은 구분자가 들어갈 수 있다. 문자열을 이어 붙이면 서로 다른 입력이 같은 문자열이 될 수 있다. 그래서 정규 JSON으로 경계를 분명히 한 뒤 해시한다.
  - B는 값을 해석하지 않고 같은지만 본다. PR #143 코드 그대로다([B 묶기][x-bbatch]).
- **SHA-256을 고른 이유**
  - Python과 Node 표준 라이브러리에 있다.
  - E가 결과 지문에 이미 같은 함수를 쓴다.
  - 서로 다른 입력이 같은 값이 될 가능성은 실무에서 무시할 수 있다.
  - 비밀을 숨기려는 용도가 아니다. 입력(저장소 값·PR 번호)은 비밀이 아니고, 값은 회원·수신자 응답에 나가지 않는다.

## 식별자 충돌

| 충돌 | 처리 |
|---|---|
| 저장소가 다른데 PR 번호가 같다 | 저장소를 값에 넣어 구분한다 |
| 합성 결과와 실제 결과의 저장소 값·번호가 같다 | 방식을 값에 넣어 구분한다 |
| 이슈와 PR 번호가 같다 | 이슈와 PR은 한 저장소에서 번호를 함께 쓴다. 이 저장소의 이슈 API로 #143을 조회하면 PR이 나온다. 그래서 번호가 같으면 같은 대상이다. 이슈 API가 준 항목이 PR이면(`pull_request`가 있으면) PR 단위로 적고 이슈 단위로 적지 않는다 |
| 같은 SHA를 병합 단위와 커밋 묶음으로 봤다 | 한 결과 안에서는 같은 변경이 한 후보에만 속하므로 생기지 않아야 한다. 단위 종류가 값에 들어가 구분된다 |
| 서로 다른 작업의 근거 판본 값(sourceRevision)이 같다 | 판본 값을 입력으로 쓰지 않는다 |
| SHA가 다른 두 변경의 공백을 무시한 해시가 같다(문자열 안의 공백·들여쓰기만 다름) | 관계 근거가 없으면 합치지 않는다. 다른 변경이다(C21·C22·C30). 관계 근거가 있으면 같은 변경으로 본다. 이때 실행 결과가 달라지는 공백 차이도 구분하지 못한다(C25, 한계 L11). 2026-09-30 팀장 결정으로 감수한다 |
| 짧은 SHA가 여러 커밋에 들어맞는다 | 짧은 SHA를 쓰지 않는다. 원본에서 확정할 수 없으면 근거 부족이다 |
| 규칙 판본이 다르다 | 접두사와 해시 입력의 판본이 달라 값이 같을 수 없다 |
| 한 결과 안에서 두 후보의 값이 같다 | 이 제안에서는 F가 지킬 조건의 위반이다. 계약과 B는 이 경우를 받아들여 한 Catch로 모은다([기능 설계 L74][f74], [B 시험][x-bsame]). 두 번째 후보의 내용은 저장되지 않으므로 F가 내보내기 전에 한 후보로 합친다. B 동작은 바꾸지 않는다 |
| SHA-256 해시 충돌 | 무시할 수 있는 확률이다. 같은 값인데 기존 Catch의 원 요청 저장소·방식이 새 요청과 다르면 반영을 거부하는 후속 보완에 B·E가 동의했다(B4·E4). B의 검사·거부는 [PR #143 구현][b180impl]에 있고, E 실패 기록·복구와 실제 연결 검증은 [#105][i105]에 남아 있다 |
| 합성 값(`synthetic-work-…`)과 실제 값(`wi1:…`) | 접두사가 달라 겹치지 않는다 |

## 규칙 판본 취급

- 규칙 판본은 값 앞의 `wi1:`로 보이고, 해시 입력에도 들어간다.
- **판본을 올리는 변경**: 작업 단위·부분·배정의 정의, 입력 목록, 정규화, 직렬화, 해시 함수가 바뀔 때다. 제목·초안 생성, 근거 선택, 코드 정리는 판본을 올리지 않는다.
- B는 문자열 전체를 비교한다. 그래서 판본이 다른 값끼리는 같은 작업으로 판정되지 않고, 잘못 합쳐지지 않는다. 대신 판본을 바꾸면 같은 작업도 새 Catch가 될 수 있다. 10월에는 wi1만 쓰므로 판본이 섞이지 않는다. 판본을 바꾸거나 재분석을 도입할 때 기존 값과 잇는 방법(옮기기·대응표)을 함께 정한다.
- [ERD L105][e105]의 "의미/범위 버전을 포함해 중복 검사"는 **이 규칙 판본**으로 해석했다. 작업의 뜻과 판정 범위를 정하는 규칙의 판본이라는 뜻이다. 동의 범위 판본(scopeRevision)을 뜻한다면 「판정 범위」의 이유로 문제가 생긴다(「검토 쟁점과 답」 계약1).
- 한 번 만든 값은 결과와 함께 보관하고, 재전달·반영 복구 때 다시 계산하지 않는다. 판본이 바뀐 뒤 옛 결과를 재전달해도 옛 값을 그대로 보낸다.

## 기존 Catch 참조와 새 후보 등록

- **이 문서는 B·E 코드와 계약 필드를 바꾸지 않는다.** B는 (ownerId, workIdentity) 유일성과 문자열 같음 비교를 그대로 쓴다([조회][x-blookup]). workIdentity의 형식을 검사하지 않는다. 합성 값과 실제 값이 함께 쓰이기 때문이다(B3).
- **저장소·방식이 다른 기존 Catch에 같은 값이 오면 반영을 거부한다(B4·E4).** 초기 인용 판본 `e2acdfe`는 새 입력과 현재 시도의 방식만 대조했다([입력 대조][x-bmode]). 이후 [PR #143의 `a5ac5dd`][b180impl]에 기존 Catch와 새 요청의 저장소·방식 검사·거부 및 회귀 검사가 추가됐다. 2026-09-30 확인 시 B 구현은 PR에 반영됐고 아직 병합 전이며, E의 실패 기록·복구와 실제 연결 검증은 [#105][i105]에 남아 있다. B·E가 합의한 처리 경계는 다음과 같다.
  - 같은 트랜잭션에서 기존 Catch의 원 요청 저장소·sourceMode를 새 요청과 대조한다. 다르면 정상 기존 참조나 후보 0건으로 처리하지 않고 그 결과의 반영을 거부한다.
  - 거부하면 이번 반영의 신규 Catch·근거·후보 연결과 E 반영 완료 기록을 함께 되돌리고, 기존 Catch와 수신 결과는 보존한다. E의 반영 실패 기록은 되돌린 뒤 따로 처리한다.
  - B가 추가한 불일치 거부·전체 되돌림 회귀 검사와, 아직 남은 E 실패 기록·복구·실제 연결 검증을 구분한다. 내부 오류 형식의 연결과 실제 재반영 경로는 [#105][i105]에서 B `leechaeah`·E `yeongyeon1802`가 맞춘다.
- **기존 Catch를 참조할 때는 본문·근거·출처·확인·불일치·공개 상태를 바꾸지 않고, 새 후보의 내용도 더하지 않는다.** 기존 규칙을 유지한다([ERD L205][e205], [B 시험][x-bkeep], B2). 그래서 잘못 합치면 뒤 작업의 내용이 어디에도 저장되지 않는다. F가 한 결과 안의 값을 후보마다 다르게 내고, 저장소를 값에 넣어야 하는 이유다.
- **처리 결과(outcome).** outcome은 F가 적는다. E는 그 값이 후보 수·실패 수와 맞는지 검사하고, 맞지 않으면 결과 전체를 거부한다([E 대조][x-eoutcome]). 보류한 변경은 어느 경우든 후보 수에 들어가지 않는다. 실패가 기록되는지는 아래 표처럼 경우마다 다르다.

| 상황 | 보류한 변경 | failures | 결과(적합 후보 있음 / 없음) |
|---|---|---|---|
| 단위 미확정(조회 완료) | 내보내지 않고 UNDETERMINED로 셈 | 없음 | SUCCEEDED / EMPTY |
| 확인 중단(수집 상한, 조회 오류) | 내보내지 않음. notProvided에 세지 않음 | 수집 실패 1건 이상 | PARTIAL_FAILED / FAILED |

- 이 구분은 [#116 문서 2.4][d116-24]의 표와 같다. 멈춘 것을 정상 0건(EMPTY)으로 바꾸지 않는다([BR3.3][br33]).
- EMPTY는 정상 완료다. 10월에는 그 저장소를 다시 요청할 수 없다([명세 L74][c74], [L75][c75]). PARTIAL_FAILED도 유효 결과가 있어 재분석할 수 없다. FAILED는 계약의 재요청 조건(등록 Catch 0건 등)을 따진다.
- 상한에 걸리면 보류한 변경이 없어도 수집 실패를 기록한다. 보류 여부와 실패 기록은 따로 정해진다.
- 실패 기록과 PARTIAL_FAILED·FAILED 구분은 이 문서가 새로 정하는 재분석 정책이 아니다. 기존 규칙([BR3.2][br32]·[BR3.3][br33], [#116 문서 2.4][d116-24], [명세 L74][c74]·[L75][c75])을 확인 중단에 적용한 것이다.
- **#103·#113 합성 자료에는 이 함수를 쓰지 않는다.** [#103 합성 결과 세트][x103]와 [#113][i113] 가짜 생성기는 주어진 합성 값을 그대로 쓴다. 이 함수로 다시 계산하면 여러 사례가 같은 합성 PR(`pull/1`)을 가리켜 하나로 합쳐진다.
  - 합성 값에는 저장소가 들어 있지 않다. 개발 환경에서 같은 회원이 같은 합성 사례를 두 저장소 요청에 주입하면, 초기 판본(`e2acdfe`)에서는 두 번째 저장소의 후보가 첫 저장소의 합성 Catch를 참조했다. 최신 PR #143에서는 저장소가 달라 `CONTEXT_MISMATCH`로 그 결과의 반영 전체가 거부된다. 합성 자료는 바꾸지 않으므로 개발 시험에서 이 조합을 피한다.
  - [`two-candidates-same-work`][x2c]는 B가 같은 값의 두 후보를 한 Catch로 모으는지 시험하는 사례로 계속 쓴다.
  - 이 문서 기준으로 보면, 그 두 번째 후보는 PR과의 연결을 확인하지 않은 커밋이다. PR에 속하면 F가 처음부터 한 후보로 묶고, 속하지 않음이 확인되면 다른 작업이다. 확인할 수 없으면 단위 미확정이라 따로 후보로 내지 않는다.
  - 이 차이 때문에 세트를 고치지 않는다. 세트의 값은 판별 알고리즘의 정답이 아니다.

## 합성 사례와 기대 판정

사례의 값은 모두 설명용 합성 값이다. 실제 저장소 자료나 과거 실험 자료가 아니다.
- **기본 후보**: 회원 M1, 저장소 `synthetic-repo-0001`(R1), 방식 LIVE, 나누지 않은 PR #3 전체를 한 후보로 본 결과, 제목 "알림 목록 페이지 나누기".
- LIVE는 실제 결과였다면 어떻게 판정되는지 보이려는 가정이다.
- SHA는 `aaaa…`처럼 같은 글자 40개로 적는다.
- **기대 판정**은 계약과 작업의 뜻에서 정했다.
  - **판정 범위 밖**은 작업 의미로는 같을 수 있지만 회원이나 저장소가 달라 서로 비교하지 않는 경우다. C10은 값이 같고, C11은 저장소가 달라 값이 다르다.
  - 범위도 다르고 작업도 다르면 '다른'으로 적는다(C12·C13).
  - **비교 대상 아님**은 재전달과 중복 등록을 구분하려고 넣은 대조 사례다.
- **Catch 영향**은 B가 받은 값으로 등록했을 때의 결과다.

C1~C5의 "기존 Catch 참조"는 다른 결과에서 같은 작업이 다시 왔다고 가정한 것이다. 10월에는 이 경로가 없다(「판정 규칙」 10월의 결과 사이 경로). 한 결과 안에서는 F가 같은 변경을 한 후보로 두므로 B까지 가지 않는다(C8·C14·C20·C23·C25).

**같은 변경 확인 사례.** 한 결과 안에서 SHA가 다른 두 변경을 같은 변경으로 볼지 정하는 사례다(「PR 소속과 같은 변경을 확인하는 근거」). C20·C23은 실제 중복을 합치는 사례다. C21·C22·C24·C30은 관계 근거가 없어 합치지 않는 사례다. C30은 시간 순서와 diff가 재제출과 같지만 두 PR을 잇는 근거가 없다. C25는 관계 근거가 있어 실행 결과가 다른 공백 차이까지 합치는, 감수한 한계다. C26은 관계 근거는 있지만 diff가 달라 확정하지 못하는 사례다. C14·C20~C26·C30의 diff 모양과 cherry-pick 표시는 합성 저장소에서 git 2.54.0으로 확인했다. 재제출 관계는 PR API의 병합 여부·만든 시각·본문에서 오므로 git으로 만들지 않고, 설명용 스크립트에 합성 PR 자료로 넣어 확인했다(C14·C23·C26·C30).

## #118이 지킬 것과 시험할 것

1. 값은 이 문서의 함수로만 만든다. 제목·문장·전달 번호를 넣지 않는다.
2. 한 결과 안에서 같은 변경(같은 SHA, 또는 7번 기준으로 확정한 변경. 경로로 나눈 커밋은 같은 커밋·같은 경로)은 한 후보에만 속한다. 병합 커밋은 변경으로 세지 않는다. 여러 단위에 들어 있는 변경은 「무엇을 하나의 작업으로 보는가」의 배정 규칙을 따른다. 배정받은 변경이 없는 단위는 후보를 만들지 않는다. 그래서 후보끼리 값이 모두 다르다.
3. 단위는 나누기 세 조건(따로 확인, 겹치지 않음, 배정된 모든 변경이 한 부분에 속함)을 채울 때만 나눈다. 못 채우면 한 후보로 둔다.
4. 이슈 API가 준 PR은 PR 단위로 적는다. PR 조회가 허용되지 않은 요청에서는 PR 단위를 쓰지 않는다.
5. 근거의 판본을 확정할 수 없으면 기존 규칙대로 INSUFFICIENT_EVIDENCE다. 근거 요건은 채웠지만 단위만 정할 수 없는 변경은 「결정」대로 보류한다.
   - 보류하기 전에 허용된 수집 범위와 수집 상한 안에서 확인을 시도한다. PR 목록의 `merge_commit_sha`와 PR 커밋 목록(250개가 넘으면 커밋 목록 API로 전체)으로 먼저 소속을 정하고, 남은 커밋에만 "연결된 PR" API를 쓴다. 호출 수를 아끼기 위해서다(「PR 소속과 같은 변경을 확인하는 근거」).
   - 조회를 마쳤는데도 근거끼리 어긋나 정할 수 없으면 후보로 내보내지 않고 UNDETERMINED로 센다. 실패는 기록하지 않는다.
   - 수집 상한이나 조회 오류로 확인을 마치지 못했으면 후보로 내보내지 않고 notProvided에도 세지 않는다. 수집 실패를 failures에 기록하고 다시 부르지 않는다([#116 문서 2.4][d116-24]).
   - 보류 건수를 두 경우로 나눠 운영 로그에 남긴다. 요청 식별자와 건수만 남기고 커밋 내용·원문은 남기지 않는다.
6. outcome은 내보낸 후보 수와 failures 수로 계산한다. 조회를 마친 뒤 보류만 있으면 SUCCEEDED·EMPTY, 확인이 중단됐으면 PARTIAL_FAILED·FAILED다.
7. 같은 변경은 같은 SHA이거나, 관계 근거(재제출·cherry-pick 표시)가 있고 공백을 무시한 diff(`git patch-id --stable`과 같은 기준, 앞뒤 문맥 줄 포함)가 같을 때만 확정한다. 재제출은 병합 없이 닫힌 PR과 그보다 나중에 만들어져 병합된 PR 사이에서, 뒤 PR의 제목·본문이 앞 PR을 번호나 같은 저장소의 PR 주소로 가리킬 때만 인정한다. PR 상태와 만든 순서만으로는 인정하지 않는다. 같은 이슈 참조·파일 겹침·제목 유사는 관계 근거로 쓰지 않는다. 관계 근거가 없으면 공백을 무시한 diff가 같아도 합치지 않는다. 변경 내용이 없거나(`patch` 누락) 잘려 비교할 수 없으면 확정하지 않는다.
8. 값은 결과와 함께 보관하고, 재전달·반영 복구 때 다시 계산하지 않는다.
9. 단위의 식별(PR 번호·병합 커밋·SHA)을 그 후보의 근거에서 찾을 수 있게 한다. 커밋이 많을 때 대표 근거만 둘지는 #118에서 정한다.
10. 합성(MOCK) 경로는 알려진 합성 값을 계속 써도 된다. #103·#113 시험의 기대값을 이 함수로 바꾸지 않는다.
11. 시험: C1~C17, C20~C30과 쌓아 올린 PR 사례(공유 커밋은 먼저 병합된 앞 PR로, 뒤 PR은 자기 커밋만으로 후보가 됨)를 함수·묶음 단위 시험으로 옮긴다(C18·C19는 E 수신 시험의 몫이다). C14·C20~C26·C30의 diff는 실제 git 커밋으로 만들고, 재제출 여부를 가리는 사례(C14·C23·C26·C30)에는 PR 자료(병합 여부·만든 순서·본문)를 합성해 붙인다. 관계 근거가 없으면 공백을 무시한 해시가 같아도 두 후보가 남는지(C21·C22·C24·C30), 관계 근거가 있으면 한 후보로 합쳐지는지(C14·C20, 공백만 다른 변경은 C23·C25) 본다. 다음을 함께 확인한다.
    - 불변성: 쓰지 않는 입력이 바뀌어도 값이 같다. C10은 두 회원의 값이 같아야 한다.
    - 민감도: 저장소·방식·단위·부분이 바뀌면 값이 다르다.
    - 형식: `wi1:` 뒤에 16진수 64자가 붙는다.

**SHA가 다른 두 변경은 관계 근거와 공백을 무시한 diff로 같은 변경을 정한다** (2026-09-30, 팀장 `ljm0850`, PR #180 추가 검토)

#111의 목적은 코드가 완전히 같은지 증명하는 것보다 같은 작업이 Catch로 두 번 등록되는 것을 막는 데 있다고 보고 팀장이 정했다.

- **같은 변경**: 재제출·cherry-pick 표시처럼 같은 작업에서 비롯됐다는 관계가 확인되고, 공백을 무시한 diff가 같으면 같은 변경으로 본다(C14·C20·C23).
- **관계 근거**: 같은 이슈를 참고했거나 파일이 겹치는 것은 충분한 근거가 아니다(C24).
- **재제출의 관계 근거**: PR 상태와 생성 순서만으로 재제출을 확정하지 않는다. 원 PR을 명시한 재제출 설명 등 두 PR을 실제로 연결하는 근거를 요구하고, 관계를 확인할 수 없으면 자동으로 합치지 않는다(C14·C30).
- **관계 근거가 없는 독립 PR**: 공백을 무시한 diff가 같아도 자동으로 합치지 않는다(C21·C22·C24).
- **받아들인 비용**: 관계가 확인된 두 변경 사이에서는 문자열 안 공백이나 들여쓰기 차이를 구분하지 못할 수 있다(C25, 한계 L11).
- **이전 판과 달라지는 점**: 이전 판(`5c004e4`)은 공백을 뺀 diff의 해시만 같으면 같은 변경으로 봤다. 여기에 관계 근거를 조건으로 더했다. 검토 중에 공백까지 같아야 한다는 조건도 살폈지만 두지 않았다.
- **범위**: 같은 변경의 기준에만 해당한다. 위 09-30 정리(확인 중단 때의 기록)의 확인 대기 항목을 승인한 것이 아니다.

**E 검토 (`yeongyeon1802`): 결과 재전달·시도 구분 경계**

  - E 의견([1번][e180]): 동의한다. E는 값을 해석하거나 다시 계산하지 않고 결과 지문에 포함한다.
- **E2.** 같은 결과의 재전달(resultId·지문, 시도당 결과 하나)과 같은 작업의 중복 등록((회원, workIdentity))을 「식별자가 가리키는 것」처럼 나눈 것이 E의 수신 판정과 맞는가.
  - E 의견(2번): 동의한다. 같은 결과 ID로 제목 등 내용을 바꿔 보내면 E가 충돌로 거부한다는 설명도 맞다.
- **E3.** 보류한 변경을 빼고 outcome을 계산한다. 조회를 마친 뒤 모두 단위 미확정이고 실패가 없으면 EMPTY(재요청 불가)다. 수집 상한이나 조회 오류로 확인이 중단되면 수집 실패가 기록돼, 내보낸 후보가 있으면 PARTIAL_FAILED(재분석 불가), 없으면 FAILED(재요청 조건을 따짐)다. 이 구분([#116 문서 2.4][d116-24]와 같음)이 E의 종결·재요청 판정과 맞는가.
  - E 의견(2026-09-30, [3번][e180]): EMPTY·FAILED·PARTIAL_FAILED의 구분 자체에는 이견이 없다. `5c004e4` 본문이 호출·시간 제한으로 멈춘 경우도 UNDETERMINED로만 읽혀, 조회 완료와 확인 중단을 나누고 확인 중단은 실패로 기록하라고 요청했다. 이 질문과 본문은 이 수정본에서 그 요청대로 고쳤다. E는 [수정본 승인][e180r]에서 `8155e6d`의 이 구분이 요청대로 반영됐음을 확인했다.
- **E4.** (E 의견 4번에서 따로 답함) B4의 반영 거부 제안에 동의했다. 정상 기존 참조나 후보 0건으로 처리하지 않고, 이번 반영의 신규 저장과 E 반영 완료 기록을 같은 트랜잭션에서 되돌리며, 기존 Catch와 수신 결과는 보존한다. E의 반영 실패 기록은 되돌린 뒤 따로 처리하고 내부 오류 형식과 복구 절차는 후속 구현에서 구체화한다. 이미 구현된 동작과 이 보완 제안을 문서에서 구분해 달라고 했다. → E의 [수정본 승인][e180r]에 따라 「기존 Catch 참조와 새 후보 등록」에서 B의 PR 구현과 E의 남은 실패 기록·복구·실제 연결 검증을 구분했다([#105][i105]).
