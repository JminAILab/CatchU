# 큐 기술 검증 재현 키트 (#77)

[큐 기술 검증 문서](../CatchU_큐_기술검증.md)의 실험을 다시 돌리는 스크립트다. **제품 코드가 아니다.** 보호 worker(`py/f_worker.py`)는 사람이 검토하지 않은 실험 코드이므로 #121에 그대로 옮기지 말고, [「큐가 해 주는 것과 #121이 구현할 것」](../CatchU_queue_requirements.md#큐가-해-주는-것과-121이-구현할-것)을 요구로 읽는다. api·worker의 실행 경로와 의존성 파일을 바꾸지 않고, 이 폴더에 따로 고정한 판본으로 돈다. 자료는 모두 합성이며 GitHub·LLM을 부르지 않는다.

## 무엇을 쓰나

| 쪽 | 쓰는 것 |
|---|---|
| E 역할(Node) | `bullmq` 6.3.11 + `ioredis` 6.0.0, 그리고 dev의 실제 E 수신 처리(`api/dist`의 `AnalysisReceiver`). 저장소는 파일 대역(`lib/e-store.cjs`)이라 B 등록·DB 반영은 하지 않는다 |
| F 역할(Python) | `bullmq` 3.3.0(redis-py 7.4.1 고정 의존), dev worker의 요청 검사·처리(`app.processing.process_request`)와 가짜 생성기 |
| 큐 서버 | Docker로 띄우는 Redis 7.2.11, Valkey 7.2.11, Valkey 8.1.6 중 하나. NCP Cloud DB for Cache가 막은 명령 10개를 끄고, 상시 영속성을 끈 채로 띄운다(비교용 P2만 AOF를 켜고 명령을 막지 않으며, P4는 축출 정책만 `allkeys-lru`로 바꾼다) |

모의 분석 함수는 불릴 때마다 디스크에 한 줄을 먼저 쓴다. 그 줄 수가 분석 호출 횟수다.

## 준비

Docker, Node `24.21.0`/npm `11.19.0`, uv(Python `3.12.10`은 uv가 준비)가 필요하다. 저장소 루트에서:

```sh
cd api && npm ci && npm run build && cd ..
cd docs/queue-verification
npm ci
uv sync --locked
```

api 빌드는 E 수신 처리를 그대로 불러 쓰기 위해서다. `npm ci`가 `msgpackr-extract` 설치 스크립트를 건너뛴다고 경고해도 BullMQ는 순수 JS 대체 구현으로 돈다.

## 실행

```sh
node compare_lua.cjs
node run.cjs --engine valkey-8.1.6
node summarize.cjs
```

- `compare_lua.cjs`: Node·Python 패키지의 Lua 스크립트가 글자 단위로 같은지 본다. 어느 쪽이든 판본을 올리면 먼저 다시 돌린다.
- `run.cjs --engine <redis-7.2.11|valkey-7.2.11|valkey-8.1.6>`: 실험 전용 컨테이너 `catchu-q77-main`(127.0.0.1:6390)을 띄우고 모든 시나리오를 돈 뒤 지운다. 저장소 시나리오(P)는 `catchu-q77-aux`(127.0.0.1:6391)를 따로 띄웠다 지운다. 키트가 띄운 컨테이너에는 표식(`catchu-q77-kit=1` label)을 붙이고 그 표식이 있는 컨테이너만 지운다. 같은 이름의 다른 컨테이너가 있으면 이름 충돌로 멈추며 그 컨테이너는 건드리지 않는다. 6379 포트도 쓰지 않는다. 한 번에 하나만 실행한다.
- 일부만 돌리려면 시나리오 접두사를 뒤에 붙인다(예: `node run.cjs --engine valkey-8.1.6 C D`). 이때 결과는 `summary-<접두사>.json`에 따로 쌓인다.
- 한 엔진에 약 5~6분 걸린다. 결과는 `runs/<엔진>-ncp-like/summary.json`(커밋하지 않음)에 쌓인다.
- 행마다 판정(`status`)이 붙는다. `MEETS` 충족, `MISSES` 미충족, `INVALID` 무효(시험 전제가 성립하지 않음, 예: 지정한 지점에서 죽지 않음), `ERROR` 실행 오류, `SKIP` 건너뜀. "큐만" 묶음의 미충족은 큐 설정만으로는 요구를 채우지 못한다는 관찰이며 실험 실패가 아니다.
- `summarize.cjs`: 세 엔진의 전체 실행 결과가 모두 있어야 돈다. 요약을 [results/](results/)에 쓰고, 엔진 사이 비교표와 엔진별 충족·미충족·무효·오류 수를 출력한다. 엔진 일치는 판정이 난 행만 센다.
- 저장소의 `results/`는 2026-10-02 실행 기록이며 [결과 기록](../CatchU_queue_verification_results.md)의 근거다. 판본을 올려 다시 돌린 결과는 `results/`를 덮어 커밋하지 않고, 그 PR에 기록한다(코딩 절차 「검사 선택과 결과 보고」).
- 중단 복구를 빨리 보려고 잠금 2초·정체 검사 1초로 줄였다. 제품 설정값이 아니다.

NCP 실제 인스턴스에서 확인할 때는 NCP 안의 서버에서 `--engine` 없이 `Q77_REDIS_URL=redis://<Private 도메인>:<포트> node run.cjs A B C D G L`로 돌린다. 이때 P 시나리오는 건너뛴다(Docker가 필요하다).

## 시나리오

| 묶음 | 확인하는 것 |
|---|---|
| A | Node→Python→Node 왕복, Python이 넣은 작업을 Node가 읽기, 합성 시나리오 7개의 요청→F 처리→E 수신, Python이 E의 수신 확인 읽기 |
| B | 같은 요청이 두 번 들어올 때: 같은 jobId(완료 작업 보존/삭제), 다른 jobId, BullMQ `deduplication` 옵션, 같은 `attemptId`인데 내용이 다른 요청. 두 번째 작업이 실제로 처리됐는지(큐가 버리는 경우는 처리되지 않았는지)를 먼저 확인하고, 보호 F는 보존 결과 분기로 갔는지까지 본다 |
| C | F를 다섯 지점에서 강제 종료하고 다시 띄우기: 생성기 호출 전, 시작 표식 뒤·분석 호출 전(보호 F만), 분석 중, 분석 끝·결과 보존 전(보호 F만), 결과 보존 뒤·전송 전. 일반 F와 보호 F, `maxStalledCount` 1과 0. 지점마다 기대가 다르다: 호출 전 → 다시 실행해 정상 종결, 표식 뒤·분석 중·보존 전 → 분석 재실행 없이 `UNCERTAIN`, 보존 뒤 → 보존 결과 수락. 죽은 직후의 기록(중단 로그, 분석 호출 수, 시작 표식·결과 파일·전송 기록)이 지점과 맞지 않으면 무효로 표시한다 |
| D | 보존 결과 재전달, E가 수신 확인을 돌려주기 전에 죽기(등록 중복은 시험하지 않음), E가 꺼진 동안의 결과, 종결 뒤 늦은 진행 알림 |
| G | 시도 기록이 없고 접수 시각이 기록 수명(시험값 60초)보다 오래된 요청 |
| L | 분석이 잠금 시간보다 길 때: 이벤트 루프를 막는 경우(실제로 잠금을 잃었어야 유효)와 별도 스레드에서 도는 경우(잠금을 잃지 않아야 충족). 분석 횟수와 함께 요청 작업 완료·E 수락 횟수를 본다 |
| P | 영속성 없는 서버 재시작: F가 처리하기 전 요청 유실, F가 보낸 뒤 결과 유실, `UNCERTAIN` 알림 유실(이 셋은 실행기가 E 대신 같은 요청을 다시 넣는다), 재발행 없이 F 주기 점검이 결과를 다시 보냄, E가 거부한 결과는 큐 유실 뒤에도 다시 보내지 않음. AOF를 켠 재시작(비교용), 분석 중 12초 장애(프로세스를 다시 띄우기 전에 수락됐는지로 판정), 축출 정책이 noeviction이 아닐 때 Node·Python의 경고. 유실 시나리오는 "보낸 것이 실제로 사라졌는지"를 먼저 확인한다 |

"일반 F"는 큐가 다시 준 작업을 그대로 처리한다. "보호 F"는 시도(`attemptId`)마다 요청 지문·분석 시작 표식·결과·전송 기록을 큐 밖 파일에 남긴다. 폴더 이름은 `attemptId`의 SHA-256 앞 32자다(계약이 `attemptId` 형식을 빈 문자열 금지만 정하므로 파일 이름으로 그대로 쓰지 않는다). 새로 만든 파일·디렉터리는 상위 디렉터리까지 fsync한다. 다시 받은 작업은 기록을 보고 하나만 한다.

1. 같은 `attemptId`인데 요청 내용(`messageId` 제외)이 처음과 다르면 아무것도 보내지 않고 멈춘다.
2. 결과가 있으면 모든 전송 기록의 결과 작업과 수신 확인을 본다. 형식·식별자가 맞는 `ACCEPTED`·`DUPLICATE`면 전달 표식, `REJECTED`면 거부 표식을 큐 밖에 남기고 다시 보내지 않는다. 결과 작업이 기다리는 중이면 보내지 않는다. 사라졌거나 수신 확인 없이 끝났으면 새 `messageId`를 전송 기록에 먼저 쓰고 다시 보낸다. 처음 전송 뒤 재전송 5회(`F_MAX_RESENDS`)나 30분(`F_DELIVERY_DEADLINE_SECONDS`)을 넘으면 사람 확인 표식을 남기고 멈춘다.
3. 시작 표식만 있으면 분석하지 않고 `UNCERTAIN`을 보낸다. 메시지 ID는 시도마다 하나로 고정하고, 다시 받을 때마다 보낸다(앞서 보낸 알림이 큐에서 사라졌을 수 있으므로). **한계**: E가 이 알림을 처리하다 실패해 큐에 실패로 남으면, 큐가 같은 ID의 추가를 무시해 다시 가지 않는다. 제품 요구는 [「#121이 구현할 것」](../CatchU_queue_requirements.md#큐가-해-주는-것과-121이-구현할-것) 4·5(E에 닿을 때까지 점검)를 따른다.
4. 기록이 없는데 접수 시각이 `F_MAX_REQUEST_AGE_SECONDS`보다 오래됐으면 분석하지 않고 `UNCERTAIN`을 보낸다(기본은 꺼짐, G 시나리오만 켠다).
5. 그 밖에는 처음 실행한다.

기동할 때 기록을 한 번 훑어 결과는 2번대로, 시작 표식만 있는 시도는 `UNCERTAIN`을 보낸다(worker 한 대 전제). `F_RECHECK_SECONDS`를 주면 그 간격으로 결과 전달 점검을 되풀이한다(P7·P8만 2초로 켠다). 주기 점검은 보존 결과만 보고 `UNCERTAIN` 알림은 보지 않는다. 그래서 기동 뒤 큐에서 사라진 알림은 다음 기동 때나 요청 작업을 다시 받을 때까지 다시 가지 않는다(한계. 제품 요구는 [「#121이 구현할 것」](../CatchU_queue_requirements.md#큐가-해-주는-것과-121이-구현할-것) 5). 시도 하나의 기록이 손상되면 그 시도만 사람 확인으로 돌리고, 큐 서버 연결 오류면 그 점검을 멈췄다가 다음에 다시 본다.

## 파일

| 파일 | 역할 |
|---|---|
| `run.cjs` | 시나리오 실행기. 컨테이너·프로세스를 띄우고 죽이며 결과를 모은다 |
| `e_consumer.cjs` | E 역할 소비자. F→E 큐의 진행 알림·결과를 E 수신 처리에 넘기고 수신 확인을 작업 반환값으로 돌려준다 |
| `lib/common.cjs`, `lib/e-store.cjs` | 공통 설정, E 수신 저장소 파일 대역 |
| `py/f_worker.py` | F 역할 worker(일반·보호, 강제 종료 지점) |
| `py/echo_worker.py`, `py/tools.py` | 왕복 확인, 합성 요청 출력·수신 확인 읽기·보존 결과 재전달 |
| `compare_lua.cjs` | 양쪽 Lua 스크립트 비교 |
| `summarize.cjs` | `runs/`의 엔진별 요약을 `results/`로 옮기고 엔진 사이 비교표 출력 |
| `results/` | [결과 기록](../CatchU_queue_verification_results.md)이 인용한 2026-10-02 실행 요약 |
