# CatchU 작업관리 — 사람과 AI의 공통 운영안

> 지위: 적용 준비안 (2026-09-14 작성, 2026-09-20 최소 코딩 지침 보완, 2026-09-23 코딩 운영 결정 반영). 팀 전체의 담당·일정 승인이나 개발 환경·GitHub Project 설정 완료를 뜻하지 않는다. 구현 착수 기준은 [코딩 절차의 「코딩 운영」](CatchU_coding_procedures.md#코딩-운영)을 따른다. 원격 운영을 시작할 때 대상 Project와 접근 권한을 확인한다.

## 1. 목적과 정본

팀원은 할 일과 결과를 설명하고, Codex 또는 Claude Code는 관련 이슈와 Projects를 함께 정리한다. 이 문서는 두 도구가 읽는 공통 절차이며, 지침 파일 자체가 백그라운드 작업이나 GitHub 권한을 제공하지는 않는다.

이 문서는 이슈·설계 초안·문서·코딩 작업을 포함한 팀의 공통 작업 절차다. **코드 수정·검사·자료·PR 절차와 코딩 착수·브랜치 기준은 [코딩 절차](CatchU_coding_procedures.md)를 따른다.** 요구사항·설계·계약의 승인 원본은 `aidlc/`에 있으며, 이슈 완료·PR 병합이 AI-DLC 공식 승인을 대신하지 않는다.

- 팀 규칙·문서 지위는 [문서 안내](README.md), 브랜치·승인·머지는 [레포 컨벤션](CatchU_레포_컨벤션.md), 회의·소통은 [그라운드룰](CatchU_그라운드룰_2026-08-04.md)을 따른다.
- 제품 범위·이슈 필요성·완료 기준을 판단하기 전에 [문서 안내의 「개발 목표와 마일스톤」](README.md#개발-목표와-마일스톤)을 읽는다. 승인 원본은 [문서 안내의 승인 원본](README.md#ai-dlc-산출물과의-관계)에서 해당 작업의 요구사항·범위와 후속 결정을 찾는다. [10월 MVP 입력](ai-dlc-input-mvp/CatchU_mvp_input.md)은 결정·제안·미결을 구분해 읽으며, 후속 범위·승인 기록과 함께 확인한다. 입력 문서를 공식 승인 기록으로 취급하지 않는다.
- 요구사항·설계·승인 원본은 `aidlc/`, 실행 상태·담당·막힘은 GitHub Issue·Projects, 변경·검증 증거는 PR에 남긴다. 이 문서에 주차별 상태나 담당표를 복제하지 않는다.
- 사람별 영역과 AI-DLC 작업 단위는 일대일로 고정하지 않는다. 각 이슈의 실행 책임과 관련 작업 단위·계약을 연결한다.
- 공통 작업 절차는 이 문서, 코드 수정·검사·PR 절차는 [코딩 절차](CatchU_coding_procedures.md), 서비스별 설치·실행·검사 방법은 [web](../web/README.md)·[api](../api/README.md)·[worker](../worker/README.md)의 README에서 관리한다. 초기화 담당은 실행 기반을 준비하는 역할이며, 그 폴더의 모든 기능 개발·결함 수정·리뷰를 전담하지 않는다. 기능 담당자는 작업에 필요한 여러 서비스를 수정할 수 있다.

## 2. 최초 연결과 적용 범위

Project 생성·구조 변경은 사용자의 해당 요청으로 진행한다. 일반 작업 요청에서 새 Project를 자동 생성하지 않는다. 최초 연결 시 아래를 확인하고 대상 Project의 README에 운영 연결 정보를 남긴다. 인증 비밀값은 기록하지 않는다.

| 연결 정보 | 확인할 내용 |
|---|---|
| 대상 | 저장소 URL, Project URL·소유자·번호 |
| 접근 | 실제 GitHub 로그인 사용자, 저장소와 Project 각각의 쓰기 권한 |
| 구조 | 상태·영역·우선순위의 실제 필드와 선택지, 마일스톤 |
| 등록 | 범위 라벨(`mvp-october`·`release-december`) 존재와 자동 추가 설정, 기존 이슈 편입 방법 |
| 기준 | 이 문서와 요구사항·설계 원본 링크 |

AI는 원격을 읽어 대상과 필드 ID를 확인한다. 확인된 URL·번호는 다음 작업에서 재사용하되 필드 ID·담당 계정을 추정하지 않는다. 저장소 Write가 조직 Project 쓰기 권한까지 보장한다고 가정하지 않는다. 대상이 여러 개면 필요한 대상만 질문한다.

사용자가 맡긴 실행 작업은 연결된 Project 안에서 이슈 검색·작성·갱신·연결까지 함께 처리한다. 이미 허용된 갱신을 매번 다시 묻지 않는다. 단순 논의이거나 원격 등록 없이 초안·로컬 작업만 하라는 요청이면 그 범위를 우선한다. 와이어프레임·설계 초안 작성은 실제 결과물을 만드는 실행 작업이므로 ‘초안’이라는 단어만으로 작업관리 대상에서 제외하지 않는다. 머지·배포·범위 변경·공식 승인 권한으로 확대하지 않는다.

도구·인증·권한이 부족하면 가능한 로컬 작업을 계속하고, 미반영 내용과 필요한 조치를 보고한다. 실패한 원격 반영을 완료로 표시하지 않는다. Slack 도움 요청은 그라운드룰을 따르되, AI가 대신 발송하려면 사용자의 명시적 발송 요청이 필요하다.

## 3. 최소 Project 구성

공용 Project 하나에 상태별 실행 보드와 기능 영역별 전체 목록을 둔다. 사람별 Project는 만들지 않는다. 기본 구성은 다음 운영안으로 시작하며, 실제 설정이 다르면 임의 변경하지 않고 차이를 확인한다.

| 필드 | 값·원칙 |
|---|---|
| 상태 | 백로그 / 준비됨 / 진행 중 / 검토 요청 / 완료 |
| 담당자 | 합의된 실제 계정. 담당 제안은 본문에 쓰고 미확정이면 비워 둔다 |
| 기능 영역 | 분석 / 회원·자산·대표 / 링크·수신자 / 홈 / 공통·운영·배포 |
| 우선순위 | P1: 먼저 연결·막힘 해소 / P2: 이후 보강. P2도 MVP 필수일 수 있다 |

`mvp-october`(10월 MVP)와 `release-december`(11월 개발 이후 12월 공개판)는 자동 추가용 범위 라벨이다. 영역·우선순위는 Project 필드에 두고 같은 의미의 라벨을 별도로 유지하지 않는다. 매일 09:30 스크럼에서는 검토 대기·막힘·미배정부터 확인한다.

| 상태 | 전환 조건 |
|---|---|
| 백로그 | 필요하지만 범위·담당·선행 조건 정리가 남음 |
| 준비됨 | 담당·완료 기준이 명확하고 해당 작업의 착수 조건 충족 |
| 진행 중 | 실제 착수함 |
| 검토 요청 | 산출물·검증 결과·검토할 쟁점·요청 상대를 명시함 |
| 완료 | 이슈별 완료 기준을 확인하고 증거를 남김 |

초기 흐름·와이어프레임은 주요 행동·예외·다른 담당 화면으로의 이동을 설명하고 검토받으면 완료할 수 있다. 완성 디자인·API 연결은 필수가 아니다. 연결 구현은 해당 API·데이터·권한 기준 합의가 필요하다. 구현 완료에는 필요한 테스트와 PR 반영, 배포 완료에는 실제 환경 검증이 필요하다. PR 작성이나 AI의 자기 검토를 다른 팀원의 승인으로 세지 않는다.

## 4. AI가 작업마다 수행할 절차

### AI가 먼저 시작하는 착수 안내

팀원이 Projects 사용법·이슈 번호·등록 명령을 알아야 작업을 시작할 수 있는 흐름으로 만들지 않는다. “홈 만들려고”, “분석 실패 화면 할게”, “다 끝났어” 같은 일상적인 표현도 작업 착수·종료 안내의 계기로 삼는다.

새 작업의 기본 순서는 **AI의 기존 작업 조회 → 필요할 때만 질문 1~2개 → 작업 연결·등록과 착수**다. 질문은 범위·완료 결과·실제 계약 충돌처럼 답 없이는 잘못 만들 수 있을 때만 하고, 사용자에게 떠넘기지 않고 AI가 먼저 던진다.

1. 먼저 현재 요청·대화와 범위 문서, 기존 Project·이슈를 읽는다. 아직 작업 대상이 제시되지 않았다면 “지금 어떤 화면이나 기능을 하려는지 알려주세요”처럼 작업 내용부터 묻는다. 단순 인사·사용법 질문에는 등록 절차를 시작하지 않는다.
2. 관련 이슈를 찾으면 실제 제목·링크와 이번 요청의 차이를 짧게 설명한다. “이슈가 있나요?”, “Projects 확인했나요?”처럼 AI가 조회할 수 있는 사실을 팀원에게 묻지 않는다. 조회 실패를 이슈 없음으로 해석하지 않는다.
3. 연결할 작업·범위·완료 기준이 불명확하면 구현이나 원격 등록 전에 질문한다. 질문은 한 번에 1~2개로, 팀원이 이해하는 행동·결과물 중심으로 작성한다. FR ID·Project 필드명·API 명령을 알아야 답할 수 있는 질문은 하지 않는다.
4. 기존 이슈가 없다면 AI가 제목·목적·최소 범위·완료 기준의 짧은 등록안을 먼저 제시하고 빠진 정보만 묻는다. 팀원이 밝히지 않은 우선순위는 빠진 정보로 보고 등록 전에 묻는다(아래 `우선순위 확인`). 팀원이 이슈 본문을 직접 작성하거나 “등록해줘”라고 다시 말하도록 요구하지 않는다.
5. 답변으로 작업이 정해지면 이슈를 연결·등록하고 상태를 관리하며 실행한다. 담당 확정이 필요하면 “이번 작업은 본인이 맡는 것으로 정해졌나요?”처럼 확인한다. 로그인 사용자만으로 팀원 번호·담당을 추정하지 않는다.
6. 사용자가 이미 이슈·범위·착수 의도를 명확히 밝혔거나 이전 대화에서 답했다면 같은 질문을 반복하지 않는다. 연결할 이슈와 관리할 내용을 짧게 알리고 진행한다. 필요한 답변을 기다리는 동안 문서 읽기·기존 코드 확인 등 독립적인 준비는 계속할 수 있지만, 답변이 필요한 범위를 임의 확정하지 않는다.

| 팀원의 말·조회 결과 | AI가 먼저 할 안내·질문 |
|---|---|
| “홈 만들려고.” / 관련 흐름 초안 이슈가 있음 | 실제 이슈 링크를 보여주고 “기존 작업은 홈 와이어프레임 초안입니다. 이번에는 초안을 만드는 건가요, 실제 화면 구현을 시작하는 건가요?” |
| “분석 실패 화면 할게.” / 같은 작업이 없음 | “새 작업으로 ‘분석 실패 안내 화면’을 정리할 수 있습니다. 이번에는 화면 초안까지인가요, 실패 상태 표시와 재요청 동작 구현까지인가요?”라고 묻고 해당 범위의 완료 기준을 제시한다. API·권한 연결 기준은 별도 확인한다. |
| “이거 끝났어.” / 산출물만 있고 검토 여부가 미확인 | 증거를 먼저 읽고 “초안 작성은 확인했습니다. 팀원 검토도 끝났나요, 검토 요청으로 정리할까요?” |
| “B 파트 이슈로 나눠줘.” | 범위 문서·담당 표와 계약·설계·화면 문서의 그 파트 담당(Owner·owner) 부분, 기존 이슈를 읽고 해당 파트 전체의 하위 이슈 목록(번호·제목·확인할 결과·선행 번호·등록 여부)을 먼저 보인다. 이슈가 없는 선행 작업·계약과 맞지 않는 점은 목록 밖에 따로 알린다. 우선순위와 남은 경계는 필요한 것만 한 번에 1~2개씩 묻는다. |

이미 결정된 제품 행동은 질문 선택지로 되돌리지 않는다. 예를 들어 10월 실패 처리는 사용자 재요청이며 자동 재시도 채택 여부를 다시 묻지 않는다. 새로운 제품 범위나 연결 계약의 결정이 필요하면 그 쟁점을 분리하고, 단순 이슈 등록으로 승인된 것으로 처리하지 않는다.

### 우선순위 확인

AI가 새 이슈를 만들 때는 우선순위를 물어 답을 받은 뒤 등록한다. AI가 스스로 발견한 후속 작업도 같다. 질문은 필드 이름이 아니라 §3의 기준으로 한다. 예: “이 작업이 다른 작업을 막고 있거나 먼저 연결해야 하나요(P1), 그 뒤에 보강해도 되나요(P2)?”

- 선행 관계나 막힘을 근거로 한쪽을 제안할 수 있다. 다만 답을 받지 않고 채우지 않는다.
- 범위 질문이 남아 있으면 그 답을 받은 뒤 등록안과 함께 묻는다. 질문 수는 1~2개 한도를 지킨다.
- 팀원이 이미 밝혔으면 다시 묻지 않는다.
- P2를 범위 제외나 선택 기능으로 설명하지 않는다.
- 팀원이 정하지 못하면 필드를 비운 채 등록하고 미정으로 보고한다.

### 착수

1. 현재 요청·범위 문서·기존 이슈·PR을 확인한다. 이슈의 필요성과 범위를 검토할 때도 공통 개발 전제와 해당 이슈의 명시적인 후속 결정을 함께 읽고, 현재 결함·계획된 후속 구현·미결 연결 조건을 구분한다. 검색은 열린 이슈뿐 아니라 관련 종료 이슈도 포함한다. 번호를 지정받았으면 그 이슈를 먼저 읽는다.
2. 같은 목적·완료 기준의 이슈가 있으면 갱신한다. 종료 작업의 재발은 원인을 확인해 재개하거나 관련 버그로 연결한다. 검색 실패를 중복 없음으로 해석하지 않는다.
3. 실행 작업에 이슈가 없다면 `task.yml` 또는 `bug.yml`의 항목으로 작성한다. 단순 질문·설명에는 이슈를 만들지 않는다. 작은 수정은 기존 작업의 체크리스트로 충분한지 먼저 판단한다.
4. 필요한 명세·결정을 직접 링크하고, 판본이 중요하면 커밋 고정 링크를 쓴다. FR/NFR ID는 판단에 쓰이는 것만 적는다. 확정된 ID만 쓰며 설계 미작성·적용 ID 미확정은 그대로 표시한다. 승인 원문 전체를 복사하지 않는다. 선행 조건과 담당·분류는 확인한 뒤 필요한 경우에만 적는다(기준은 `이슈 본문`).
5. 범위 라벨을 적용하고(11월 개발 이후 작업은 `release-december`, 10월 MVP의 남은 작업은 `mvp-october`) Project 편입과 필드를 확인한다. CLI/API에서도 라벨을 명시하며 자동 추가가 지연되면 실제 편입 여부를 확인한 뒤 같은 이슈를 추가한다. `우선순위` 필드는 팀원의 답(`우선순위 확인`)으로 설정하고, 등록 후 원격에서 값을 다시 읽어 확인한다. `gh project item-list`의 JSON은 한글 필드 이름이 깨져 설정된 값도 비어 보이므로, GraphQL `fieldValueByName`처럼 필드 이름으로 조회한다. 실행 책임자·날짜·작업량을 추정하지 않는다. 실제 착수한 작업만 진행 중으로 옮긴다.

### 이슈 본문

항목과 짧은 작성 안내는 이슈 양식에 두고, 여기에는 판단·갱신 기준만 둔다. 목표는 상단만 읽어도 무엇을 만드는 작업이고 무엇이 확인되면 끝인지 알 수 있는 본문이다.

- 배치: 규칙·기준은 `선행 조건과 미결`이 아니라 `범위`나 `완료 기준`에 쓴다. 상태·기능 영역·우선순위는 본문이 아니라 Project 필드에 둔다. 같은 내용을 여러 칸에 나누어 쓰지 않는다.
- 근거: 작업 판단에 필요한 결정 요지와 직접 출처는 뜻과 함께 본문에 둔다. 전체 대응표·보조 링크·상세 이력은 `<details>`로 접고, 짧으면 접기를 만들지 않는다. 링크로 끝난다는 이유로 판단에 필요한 결정을 접지 않는다.
- 완료 기준: 한 항목에 한 조건만 쓴다. 합의된 작업 범위에서 사람이 확인할 수 있는 기대 결과를 적고, 제품 동작을 바꾸면 승인된 제품 행동·합의된 계약과 대조한다. AI는 관련 정상·거부·실패 사례(서버·worker·큐·DB 장애의 앱 복구는 제외)와 근거를 제안하고 미정인 부분만 확인한다. 설계 서술은 결과물 문서에 두며, 이미 결정된 행동을 다시 선택하게 하거나 구현에 맞춰 기대 결과를 정하지 않는다. 작업 중에 기준을 임의로 낮추지 않으며, 합의로 바꿨다면 이유를 남긴다.
- 조건부 항목: 확인은 항상 수행한다. 선행 조건이 없음을 확인했으면 절을 지우고, 실제 선행 이슈가 있으면 적은 뒤 `blocked by` 관계도 설정한다. 외부 결정·권한·계정 때문에 막혔으면 필요한 조치와 다음 행동을 기록한다. 확인하지 못했으면 없음으로 간주하지 않고 미확인으로 표시한다.
- 담당 칸의 생애주기: 담당·분류 결정이 필요할 때만 쓴다. 확정되면 Project 필드에 반영하고 본문의 제안 문구는 지운다. 합의 주체나 조율 역할처럼 필드로 표현할 수 없는 정보는 남긴다.
- 경과와 기록 보존: 진행 기록은 댓글에 남기고 본문은 최신 상태만 설명하도록 고친다. 본문에 쌓인 날짜별 기록을 옮길 때는 지우지 않는다. 이미 댓글·문서에 있는 기록은 링크하고 중복만 덜어내며, 본문에만 있는 결정·확인은 출처와 날짜를 보존해 옮긴다. 이전 결정을 대체했다면 무엇을 대체했는지 연결한다. 경과에 섞인 선행 조건·담당 변경은 댓글로 내리지 말고 해당 칸으로 올린다.
- 상태 표기: 다른 PR·이슈의 상태(미병합·진행 중·대기)를 본문에 쓰지 않고 링크만 둔다. 상태는 원본에서 확인하며, 본문에 적으면 그 PR이 머지되는 순간 틀린 설명이 된다.
- 근거 선별: 이슈마다 같은 링크 목록이나 상위 이슈·이 문서의 규칙을 옮겨 적지 않는다. 그 작업의 판단에 실제로 쓰이는 출처만 남긴다.
- 분량: 짧은 문장이나 목록으로 쓰고 한 항목에는 한 가지만 쓴다. 권장 분량에 맞추려고 예외·권한·데이터 조건을 지우지 않는다.
- 등록 후 확인: 양식의 `required`는 웹 폼 입력 검사이며 CLI/API 생성 경로를 강제하지 않는다. 등록한 뒤 실제 본문에서 필수 항목 누락, 조건부 항목의 확인 누락, 같은 내용 반복을 확인한다.
- 적용 시점: 새 이슈부터 이 기준을 적용한다. 기존 이슈는 일괄 수정하지 않고, 다음 갱신 때 손대는 부분의 오래된 설명과 중복까지 정리한다.

### 진행·검토

- 의미 있는 변경·막힘·검토 요청 시 갱신한다. 파일 저장마다 댓글을 남기지 않는다.
- 실제 선행 이슈는 `blocked by / blocking`으로 연결한다. 단순 참고와 구분한다. 다른 이슈의 일부(함수·테이블·커밋)만 필요하면 그 부분이 준비될 때까지 `blocked by`를 두고 본문에 필요한 부분을 적는다. 필요한 부분이 대상 작업 환경에서 사용 가능함을 확인하고 남은 실행 의존이 없으면 원본 이슈가 열려 있어도 관계를 풀고 제공된 커밋·PR을 본문에 연결한다. 같은 판본·조건의 기존 검증 근거는 재사용한다. 외부 결정·계정 문제는 `막힌 이유 / 필요한 조치 / 요청 상대 / 다음 행동`으로 기록한다.
- 갱신 직전에 최신 본문·필드를 다시 읽고 필요한 부분만 바꾼다. 다른 팀원의 변경·검토 기록을 덮어쓰지 않는다.
- 검토 요청은 변경이 실제로 영향을 주는 담당자에게 산출물 링크와 확인할 쟁점을 남기고, 같은 계약·판본의 기존 확인·시험 결과는 링크로 갈음한다. PR 병합에 필요한 작성자 외 승인 1건은 따로 받는다. 코드·문서는 기존 PR 양식을 사용하고 이슈와 PR을 연결한다. 보드에는 원칙적으로 이슈만 올린다.
- 큰 작업은 독립 담당·선행 조건·완료 결과가 달라질 때 상위 이슈의 하위 이슈(sub-issue) 한 단계로 나눈다. 하위 이슈 하나는 PR 하나로 다른 사람이 확인할 결과 하나이며(예: 계약 경로 묶음 하나, 와이어프레임 화면 하나의 API 연결) 화면 상태·날짜·구현 준비·개별 테스트 사례로 더 나누지 않는다. 같은 담당의 api·web은 각각 결과가 있을 때만 나누고 api를 선행으로 둔다. 나눈 하위 이슈는 최소 범위와 확인할 결과를 본문에 적어 개수 제한 없이 모두 상위 이슈에 연결·등록하고, 같은 목적·완료 기준의 기존 이슈는 재사용한다. 선행 작업 미완료나 구현 세부사항의 미결만으로 등록을 미루지 않는다. 실제 선행 이슈는 `blocked by`로 연결하고, 미결은 `선행 조건과 미결`에 적으며 상태는 기존 전환 기준을 따른다. 최소 범위나 확인할 결과를 아직 정할 수 없는 항목만 상위 이슈 `요약`에 미결과 함께 남기고, 필요한 질문으로 정해지면 등록한다. 상위 이슈 완료 기준은 ‘요약에 남은 작업 없이 하위 이슈가 모두 완료됐다’ 한 줄이다. 기능 완료에 필요한 테스트는 다른 영역과의 연결 검사도 같은 이슈에 포함한다. 별도 완료 결과가 필요한 여러 영역의 통합·권한·배포 검증은 별도 작업으로 두고, 필요한 구현과 기대 결과가 준비된 부분부터 실행한다. 다른 부분의 검토·구현 완료를 선행으로 걸지 않는다.
- 해당 작업의 품질 확인·환경 준비·통합 검증에 미배정된 책임이 있으면 명시한다. 검토자·초기화·통합 검증 담당이라는 이유로 기능 구현·운영 책임이나 다른 담당 사이의 연결 중계를 자동 배정하지 않고 실제 작업의 범위와 담당을 확인한다. 담당·지원·일정 조정이 필요하면 영향과 선택안을 모아 팀장에게 올린다.

### 코딩·검사·자료·PR 절차

「코딩 전 범위와 기존 변경 확인」·「검사 선택과 결과 보고」·「자료와 실행 로그」·「PR 작성·리뷰 요청·잘못 올린 PR 처리」·「PR 본문」은 [코딩 절차](CatchU_coding_procedures.md)로 옮겼다. 코드를 고치거나 PR을 쓸 때는 그 문서를 읽는다.

### 종료와 실패 복구

1. 이슈의 완료 기준별로 산출물·검증·PR 반영을 대조한다. 미충족 항목이 있으면 완료하지 않고 남은 작업을 적는다. 이슈 포기는 완료가 아닌 중단 사유로 기록하고 완료 통계에서 구분한다.
2. 충족한 작업은 완료 증거를 남기고 이슈 종료와 Project 완료 상태를 맞춘다. 종료 키워드의 자동 종료를 가정하지 않고, 머지 후 실제 이슈·Project 상태를 확인한다(이슈 연결 기준은 [코딩 절차](CatchU_coding_procedures.md#pr-본문)의 `PR 본문`).
3. 원격에서 이슈·Project를 다시 읽어 반영을 검증한다. 이슈 생성만 성공하고 필드 설정이 실패했다면 같은 이슈를 보완한다. 응답이 불확실하면 먼저 검색하고 새 이슈를 중복 생성하지 않는다.
4. 사용자에게 이슈·PR 링크, 변경된 상태, 검증 결과, 미반영 항목만 간결하게 보고한다. 원격 작업 실패와 제품 작업 실패를 구분한다.

Projects 완료, AI-DLC 공식 승인, AWS 전체 MVP 검증은 별도다. Projects 요청만으로 AI-DLC 실행·승인·상태 파일 수정을 하지 않는다.

## 5. 양식과 자동화의 역할

- `.github/ISSUE_TEMPLATE/task.yml`, `bug.yml`은 웹 작성 양식이자 AI 작성 항목의 기준이다. CLI/API에서 작성할 때도 필수 항목 누락을 확인한다. 웹 폼의 필수 입력 검사가 모든 생성 경로를 강제하지는 않는다.
- 두 양식은 `release-december`를 기본 지정한다. 10월 MVP의 남은 작업에 쓰면 `mvp-october`로 바꾼다. 범위 밖 아이디어를 MVP 작업으로 자동 편입하지 않는다.
- 폼의 답변은 이슈 본문이다. 영역·우선순위·선행 이슈를 본문에 썼다고 Project 필드나 의존성이 설정됐다고 보고하지 않는다.
- 초기 설정자는 범위 라벨을 만들고 대상 저장소의 `is:issue label:mvp-october,release-december` 자동 추가를 설정한다. 활성화 전 존재하던 이슈는 별도 편입한다. 라벨은 사전 생성해야 하므로 템플릿 파일 추가만으로 자동화 완료라고 보고하지 않는다.
- 최초 Project 설정 전에는 폼에 추정 Project 번호나 고정 담당자를 넣지 않는다. 일상 갱신에는 인증된 GitHub CLI 또는 연결 도구를 사용한다. 토큰은 파일·이슈·로그에 남기지 않는다.
- 이슈·PR 양식은 저장소의 실제 기본 브랜치에 반영돼야 적용된다. 적용을 보고하기 전에 원격 기본 브랜치 설정을 확인하고, 기본 브랜치가 아닌 곳에 반영된 것만으로 활성화됐다고 보고하지 않는다. 기존 PR·승인·merge commit 절차를 유지한다.
- 이슈·Projects 등록 자동화는 내장 자동 추가와 AI 갱신으로 시작한다. 이를 위한 GitHub Actions·별도 등록 스크립트는 실제 반복 문제가 확인된 뒤 도입한다. 제품 PR의 빌드·테스트 CI 준비와는 별개다. 이 지침은 상시 실행되는 봇이 아니다.

## 6. 팀원 사용 예시

팀원은 다음처럼 작업 내용과 상황만 말하면 된다. Projects 확인·등록·상태 갱신까지 문장에 넣도록 요구하지 않는다.

- “B 파트 이슈로 나눠줘.”
- “분석 실패 화면 할게.”
- “API 기준이 없어서 막혔어.”
- “초안 올렸어.”
- “이거 끝났어.”

AI가 §4의 착수 안내에 따라 기존 작업을 확인하고 필요한 질문·이슈 관리·검토 연결을 먼저 수행한다. 팀원에게 이 예시의 정확한 문구를 외우도록 요구하지 않는다.

최초 도입 때 각 도구에서 이 문서를 읽었는지와 GitHub 읽기·쓰기 가능 여부를 확인한다. 실제 등록 테스트는 원격 작업 요청을 받은 뒤 수행한다. 이후 같은 세션의 합의된 작업은 매번 별도 등록 요청을 반복하지 않아도 된다.

## 7. 개발 준비 완료 확인

핵심 기준은 **팀원이 새 작업 폴더에서 안내대로 환경을 준비하고, 작업에 필요한 서비스를 실행하고, 작은 변경을 검사한 뒤 PR로 제출할 수 있는가**다. 아래는 실제 프로젝트와 명령이 준비된 뒤 초기화 작업에서 확인할 목록이며, 지금 통과했다는 기록이 아니다. 매 작업에 목록 전체를 붙이지 않는다.

- [ ] 서비스 README에 필요한 버전·도구·설치·환경 설정·실행·정상 확인·종료 방법과 검사 명령이 있고, 새 작업 폴더에서 따라 했다. Python은 선택한 가상환경 준비 방법도 확인했다.
- [ ] 필요한 DB·큐 등 공통 환경의 준비 안내와 연결 조건을 확인했다. 각 서비스는 연결 요구를 제공하고 공통 환경 담당자는 준비 안내를 마련하며, 실제 사용자는 자기 환경에서 실행한다. 운영·배포 책임이나 스키마·메시지 처리 책임은 별도 작업 범위를 따른다.
- [ ] 작은 변경의 기대 결과를 이슈에서 확인하고 관련 검사·빌드 또는 런타임 확인을 수행했다. 실제 연결·모의 대상을 구분했다.
- [ ] 기존 양식으로 PR을 제출하고 검토 상대가 변경과 검증 증거를 확인할 수 있다.
- [ ] 누가 어떤 환경·판본에서 수행했는지, 작성자 외 재현 여부와 실패·미검증 사항을 초기화 이슈·PR에 남겼다. 작성자만 성공했으면 다른 팀원까지 준비 완료로 보고하지 않는다.

서비스 초기화 담당자는 README와 실행·검사 기반을 준비하고, 이를 사용할 기능 담당자는 재현·사용성 확인에 참여한다. 공통 환경·CI·배포 준비는 해당 작업의 담당자와 검토자를 정한다. 기능 구현의 기대 결과·테스트·결함 수정은 각 기능 담당자의 책임이다. 실제 배분은 [#24](https://github.com/JminAILab/CatchU/issues/24)와 연결 작업에서 확인하며 여기 복제하지 않는다.

사람이 판단할 범위·계약·검사 선택은 이슈·PR에서 검토한다. dev 대상 PR의 CI와 필수 상태 검사는 [레포 컨벤션 「dev의 검증」](CatchU_레포_컨벤션.md#2-브랜치)을 따른다. 문서 작성만으로 CI나 브랜치 보호가 적용됐다고 보고하지 않는다.

**로컬 개발 준비와 AWS 배포·복구 준비는 각각 증거로 확인한다.** PR 검사와 자동 배포는 별도 작업이다.

10월 MVP에 한정해, 배포에 관한 2026-09-20 사용자 후속 방향은 **핵심 기능 개발을 우선하고, 진행 상황에 따라 자동 배포도 선택하며, 일정이 늦어지면 로컬 시연을 대안으로 검토한다**는 것이다. 자동 배포를 새 필수 조건으로 만들지 않는다. 이는 [기존 M07·자동 CD 제외 범위](../aidlc/spaces/default/intents/260914-catchu-october-mvp/ideation/scope-definition/scope-document.md)에 연결할 후속 입력이며, 기존 승인 원본은 소급 수정하지 않는다. 실제 시연 범위와 배포 미완료 항목을 구분해 보고하고, 로컬 시연 성공을 AWS 배포·복구 검증 통과로 기록하지 않는다. 로컬 시연을 선택할 때의 MVP 완료 판정은 범위의 후속 결정에 연결한다.
