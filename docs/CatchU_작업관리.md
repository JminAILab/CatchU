# CatchU 작업관리 — 사람과 AI의 공통 운영안

> 지위: 적용 준비안 (2026-09-14). 사용자의 저장소 지침·양식 준비 요청에 따라 작성했다. 팀 전체의 담당·일정 승인이나 GitHub Project 설정 완료를 뜻하지 않는다. 원격 운영을 시작할 때 대상 Project와 접근 권한을 확인한다.

## 1. 목적과 정본

팀원은 할 일과 결과를 설명하고, Codex 또는 Claude Code는 관련 이슈와 Projects를 함께 정리한다. 이 문서는 두 도구가 읽는 공통 절차이며, 지침 파일 자체가 백그라운드 작업이나 GitHub 권한을 제공하지는 않는다.

- 팀 규칙·문서 지위는 [문서 안내](README.md), 브랜치·승인·머지는 [레포 컨벤션](CatchU_레포_컨벤션.md), 회의·소통은 [그라운드룰](CatchU_그라운드룰_2026-08-04.md)을 따른다.
- 제품 범위는 [10월 MVP 입력](ai-dlc-input-mvp/CatchU_mvp_input.md)의 결정·제안·미결 구분과 그 문서가 연결한 승인 요구사항을 따른다. 입력과 이슈를 공식 승인으로 취급하지 않는다.
- 요구사항·설계·승인 원본은 `aidlc/`, 실행 상태·담당·막힘은 GitHub Issue·Projects, 변경·검증 증거는 PR에 남긴다. 이 문서에 주차별 상태나 담당표를 복제하지 않는다.
- 사람별 영역과 AI-DLC 작업 단위는 일대일로 고정하지 않는다. 각 이슈의 실행 책임과 관련 작업 단위·계약을 연결한다.

## 2. 최초 연결과 적용 범위

Project 생성·구조 변경은 사용자의 해당 요청으로 진행한다. 일반 작업 요청에서 새 Project를 자동 생성하지 않는다. 최초 연결 시 아래를 확인하고 대상 Project의 README에 운영 연결 정보를 남긴다. 인증 비밀값은 기록하지 않는다.

| 연결 정보 | 확인할 내용 |
|---|---|
| 대상 | 저장소 URL, Project URL·소유자·번호 |
| 접근 | 실제 GitHub 로그인 사용자, 저장소와 Project 각각의 쓰기 권한 |
| 구조 | 상태·영역·우선순위의 실제 필드와 선택지, 마일스톤 |
| 등록 | `mvp-october` 라벨 존재와 자동 추가 설정, 기존 이슈 편입 방법 |
| 기준 | 이 문서와 요구사항·설계 원본 링크 |

AI는 원격을 읽어 대상과 필드 ID를 확인한다. 확인된 URL·번호는 다음 작업에서 재사용하되 필드 ID·담당 계정을 추정하지 않는다. 저장소 Write가 조직 Project 쓰기 권한까지 보장한다고 가정하지 않는다. 대상이 여러 개면 필요한 대상만 질문한다.

사용자가 맡긴 실행 작업은 연결된 Project 안에서 이슈 검색·작성·갱신·연결까지 함께 처리한다. 이미 허용된 갱신을 매번 다시 묻지 않는다. 단순 논의이거나 원격 등록 없이 초안·로컬 작업만 하라는 요청이면 그 범위를 우선한다. 와이어프레임·설계 초안 작성은 실제 결과물을 만드는 실행 작업이므로 ‘초안’이라는 단어만으로 작업관리 대상에서 제외하지 않는다. 머지·배포·범위 변경·공식 승인 권한으로 확대하지 않는다.

도구·인증·권한이 부족하면 가능한 로컬 작업을 계속하고, 미반영 내용과 필요한 조치를 보고한다. 실패한 원격 반영을 완료로 표시하지 않는다. Slack 도움 요청은 그라운드룰을 따르되, AI가 대신 발송하려면 사용자의 명시적 발송 요청이 필요하다.

## 3. 최소 Project 구성

공용 Project 하나에 상태별 실행 보드와 기능 영역별 전체 목록을 둔다. 사람별 Project는 만들지 않는다. 기본 구성은 다음 운영안으로 시작하며, 실제 설정이 다르면 임의 변경하지 않고 차이를 확인한다.

| 필드 | 값·원칙 |
|---|---|
| 상태 | 백로그 / 준비됨 / 진행 중 / 검토 요청 / 완료 |
| 담당자 | 합의된 실제 계정. 담당 제안은 본문에 쓰고 미확정이면 비워 둔다 |
| 기능 영역 | 분석 / 회원·자산·대표 / 링크·수신자 / 홈 / 공통·운영·배포 |
| 우선순위 | P1: 먼저 연결·막힘 해소 / P2: 이후 보강. P2도 MVP 필수일 수 있다 |
| 마일스톤 | 10월 중간 발표 MVP. 정확한 마감일은 합의 전 비워 둔다 |

`mvp-october`는 자동 추가용 범위 라벨이다. 영역·우선순위는 Project 필드에 두고 같은 의미의 라벨을 별도로 유지하지 않는다. 주 작업은 사람당 진행 중 하나를 기본으로 하되 지원·검토 여유를 고려한다. 매일 09:30 스크럼에서는 검토 대기·막힘·미배정부터 확인한다.

| 상태 | 전환 조건 |
|---|---|
| 백로그 | 필요하지만 범위·담당·선행 조건 정리가 남음 |
| 준비됨 | 담당·완료 기준이 명확하고 해당 작업의 착수 조건 충족 |
| 진행 중 | 실제 착수함 |
| 검토 요청 | 산출물·검증 결과·검토할 쟁점·요청 상대를 명시함 |
| 완료 | 이슈별 완료 기준을 확인하고 증거를 남김 |

초기 흐름·와이어프레임은 주요 행동·예외·다른 담당 화면으로의 이동을 설명하고 검토받으면 완료할 수 있다. 완성 디자인·API 연결은 필수가 아니다. 연결 구현은 해당 API·데이터·권한 기준 합의가 필요하다. 구현 완료에는 필요한 테스트와 PR 반영, 배포 완료에는 실제 환경 검증이 필요하다. PR 작성이나 AI의 자기 검토를 다른 팀원의 승인으로 세지 않는다.

## 4. AI가 작업마다 수행할 절차

### AI가 먼저 시작하는 착수 안내

팀원이 Projects 사용법·이슈 번호·등록 명령을 알아야 작업을 시작할 수 있는 흐름으로 만들지 않는다. “홈 만들려고”, “분석 실패 화면 할게”, “다 끝났어” 같은 일상적인 표현도 작업 착수·종료 안내의 계기로 삼는다.

새 작업의 기본 순서는 **AI의 기존 작업 조회 → 필요한 질문 1~2개 → 작업 연결·등록과 착수**다. 질문을 사용자에게 떠넘기지 않고 AI가 먼저 던진다.

1. 먼저 현재 요청·대화와 범위 문서, 기존 Project·이슈를 읽는다. 아직 작업 대상이 제시되지 않았다면 “지금 어떤 화면이나 기능을 하려는지 알려주세요”처럼 작업 내용부터 묻는다. 단순 인사·사용법 질문에는 등록 절차를 시작하지 않는다.
2. 관련 이슈를 찾으면 실제 제목·링크와 이번 요청의 차이를 짧게 설명한다. “이슈가 있나요?”, “Projects 확인했나요?”처럼 AI가 조회할 수 있는 사실을 팀원에게 묻지 않는다. 조회 실패를 이슈 없음으로 해석하지 않는다.
3. 연결할 작업·범위·완료 기준이 불명확하면 구현이나 원격 등록 전에 질문한다. 질문은 한 번에 1~2개로, 팀원이 이해하는 행동·결과물 중심으로 작성한다. FR ID·Project 필드명·API 명령을 알아야 답할 수 있는 질문은 하지 않는다.
4. 기존 이슈가 없다면 AI가 제목·목적·최소 범위·완료 기준의 짧은 등록안을 먼저 제시하고 빠진 정보만 묻는다. 팀원이 이슈 본문을 직접 작성하거나 “등록해줘”라고 다시 말하도록 요구하지 않는다.
5. 답변으로 작업이 정해지면 이슈를 연결·등록하고 상태를 관리하며 실행한다. 담당 확정이 필요하면 “이번 작업은 본인이 맡는 것으로 정해졌나요?”처럼 확인한다. 로그인 사용자만으로 팀원 번호·담당을 추정하지 않는다.
6. 사용자가 이미 이슈·범위·착수 의도를 명확히 밝혔거나 이전 대화에서 답했다면 같은 질문을 반복하지 않는다. 연결할 이슈와 관리할 내용을 짧게 알리고 진행한다. 필요한 답변을 기다리는 동안 문서 읽기·기존 코드 확인 등 독립적인 준비는 계속할 수 있지만, 답변이 필요한 범위를 임의 확정하지 않는다.

| 팀원의 말·조회 결과 | AI가 먼저 할 안내·질문 |
|---|---|
| “홈 만들려고.” / 관련 흐름 초안 이슈가 있음 | 실제 이슈 링크를 보여주고 “기존 작업은 홈 와이어프레임 초안입니다. 이번에는 초안을 만드는 건가요, 실제 화면 구현을 시작하는 건가요?” |
| “분석 실패 화면 할게.” / 같은 작업이 없음 | “새 작업으로 ‘분석 실패 안내 화면’을 정리할 수 있습니다. 이번에는 화면 초안까지인가요, 실패 상태 표시와 재요청 동작 구현까지인가요?”라고 묻고 해당 범위의 완료 기준을 제시한다. API·권한 연결 기준은 별도 확인한다. |
| “이거 끝났어.” / 산출물만 있고 검토 여부가 미확인 | 증거를 먼저 읽고 “초안 작성은 확인했습니다. 팀원 검토도 끝났나요, 검토 요청으로 정리할까요?” |
| “이슈 번호의 와이어프레임 작업을 내가 맡았고, 기존 완료 기준대로 시작해줘.” | 이슈와 기준을 읽고 연결 사실을 알린 뒤 진행한다. 같은 담당·범위를 다시 묻지 않는다. |

이미 결정된 제품 행동은 질문 선택지로 되돌리지 않는다. 예를 들어 10월 실패 처리는 사용자 재요청이며 자동 재시도 채택 여부를 다시 묻지 않는다. 새로운 제품 범위나 연결 계약의 결정이 필요하면 그 쟁점을 분리하고, 단순 이슈 등록으로 승인된 것으로 처리하지 않는다.

### 착수

1. 현재 요청·범위 문서·기존 이슈·PR을 확인한다. 검색은 열린 이슈뿐 아니라 관련 종료 이슈도 포함한다. 번호를 지정받았으면 그 이슈를 먼저 읽는다.
2. 같은 목적·완료 기준의 이슈가 있으면 갱신한다. 종료 작업의 재발은 원인을 확인해 재개하거나 관련 버그로 연결한다. 검색 실패를 중복 없음으로 해석하지 않는다.
3. 실행 작업에 이슈가 없다면 `task.yml` 또는 `bug.yml`의 항목으로 작성한다. 단순 질문·설명에는 이슈를 만들지 않는다. 작은 수정은 기존 작업의 체크리스트로 충분한지 먼저 판단한다.
4. 관련 FR/NFR ID, 근거 문서·절·기준 커밋, 선행 작업, 담당 제안을 적는다. 확정된 ID만 쓰며 설계 미작성·적용 ID 미확정은 그대로 표시한다. 승인 원문 전체를 복사하지 않는다.
5. 10월 MVP 작업에 `mvp-october` 라벨을 적용하고 Project 편입과 필드를 확인한다. CLI/API에서도 라벨을 명시하며 자동 추가가 지연되면 실제 편입 여부를 확인한 뒤 같은 이슈를 추가한다. 실행 책임자·날짜·작업량을 추정하지 않는다. 실제 착수한 작업만 진행 중으로 옮긴다.

### 진행·검토

- 의미 있는 변경·막힘·검토 요청 시 갱신한다. 파일 저장마다 댓글을 남기지 않는다.
- 실제 선행 이슈는 `blocked by / blocking`으로 연결한다. 단순 참고와 구분한다. 외부 결정·계정 문제는 `막힌 이유 / 필요한 조치 / 요청 상대 / 다음 행동`으로 기록한다.
- 갱신 직전에 최신 본문·필드를 다시 읽고 필요한 부분만 바꾼다. 다른 팀원의 변경·검토 기록을 덮어쓰지 않는다.
- 검토 요청은 산출물 링크와 확인할 쟁점을 남긴다. 코드·문서는 기존 PR 양식을 사용하고 이슈와 PR을 연결한다. 보드에는 원칙적으로 이슈만 올린다.
- 큰 작업은 독립 담당·선행 조건·완료 결과가 달라질 때 하위 이슈로 나눈다. 구현에 필요한 테스트는 같은 이슈에 포함하고, 여러 영역의 통합·권한·배포 검증은 별도 작업으로 둔다.
- 내부 품질·운영, NCP 수동 배포·복구, 통합 검증의 미배정은 명시한다. 선택 공유 검토자 지정만으로 구현·운영 담당을 팀원 1로 정하지 않는다.

### PR 본문

항목과 짧은 작성 안내는 PR 양식에 두고, 여기에는 판단·갱신 기준만 둔다. 목표는 상단만 읽어도 무엇이 바뀌었고 무엇을 검토해야 하는지 알 수 있는 본문이다.

- 선택 항목: `하지 않는 것`은 범위나 승인 여부를 오해할 가능성이 있을 때만 쓴다. 예를 들어 초안이 결정처럼 읽힐 수 있거나, 미결로 남긴 부분을 이번 PR이 다룬 것으로 볼 수 있을 때다. "공식 승인 아님", "이슈 완료 아님" 같은 문장을 모든 PR에 관성적으로 쓰지 않는다. 해당 없는 선택 항목과 절은 지운다.
- 범위와 한계: 하지 않는 작업과 승인 범위에 관한 설명은 `하지 않는 것`에 모은다. 검증 결과를 해석하는 데 필요한 한계는 그 결과 옆에 쓴다(예: 저장분 재현에 성공했지만 로직 타당성을 입증한 것은 아니다). 같은 설명을 불필요하게 반복하지 않는다. 머지 판단에 영향을 주는 미검증 사항은 `리뷰 요청`에도 드러낸다.
- 근거: 리뷰 판단에 필요한 요구사항과 근거는 개수와 무관하게 뜻과 함께 본문에 둔다. 전체 대응표·보조 ID·기준 커밋·검사 명령·파일 해시는 `추적 정보`로 내린다.
- 도구 내부 정보: 도구 내부 이름과 오류(워크플로 파일명, 하네스 오류 메시지 등)는 사람이 확인하거나 조치할 일이 없으면 쓰지 않는다. 필요하면 무슨 일이 있었고 결과물에 어떤 영향이 있는지로 풀어 쓴다.
- 결과물 링크: 커밋 고정 링크를 쓴다. 브랜치 링크는 브랜치를 지우면 깨지고, 커밋이 쌓이면 리뷰 당시 판본이 아닌 최신본을 가리킨다. merge commit 규칙이라 원래 커밋은 머지 후에도 남는다.
- 검증: 적용되지만 수행하지 못한 검증은 이유와 함께 `수행하지 못한 검증`에 쓴다. 애초에 적용되지 않는 검증과 체크 항목은 체크하거나 빈 상자로 두지 않고 "해당 없음: 사유"로 쓰거나, 선택 항목이면 지운다.
- 이슈 연결: 이 PR의 머지로 이슈의 완료 기준을 모두 충족할 때만 `Closes #번호`를 쓴다. 일부 결과물 제출이거나 완료 기준에 머지 후 별도 검증·작업이 남아 있으면 `Refs #번호`로 참조하고, 남은 기준을 확인한 뒤 종료한다. `Refs`는 참조 표현이며, 그것만으로 Project 연결이나 상태 변경이 일어나지 않는다. 자동 종료는 종료 키워드 등으로 연결된 PR이 기본 브랜치에 머지되고 저장소의 자동 종료 설정이 켜져 있을 때만 일어난다. 두 조건을 확인하고, 설정을 확인하지 못했다면 자동 종료를 가정하지 않고 그 사실을 보고에 적는다. 머지 후 실제 이슈·Project 상태를 검증한다.
- 리뷰 반영: 본문은 항상 최종 변경 상태를 설명하도록 고치고, 결과물 링크도 새 커밋으로 갱신한다. `리뷰 반영`에는 결론·범위·검증에 영향을 준 주요 리뷰만 "지적 → 반영 또는 미반영 이유"로 짧게 요약하고 원래 댓글·커밋을 연결한다. 사소한 수정은 기존 리뷰 기록으로 갈음한다. 주요 반영이 없으면 절을 생략한다.
- 올리기 전 점검: 상단만 읽어도 무엇이 바뀌었고 무엇을 검토해야 하는지 알 수 있는지, 빈 절이나 상투적인 문구가 남지 않았는지 확인한다.
- 적용 시점: 새 PR부터 이 기준을 적용한다. 기존 열린 PR은 다음 수정 때 요약을 보완하며, 본문을 일괄 수정하지 않는다.

### 종료와 실패 복구

1. 이슈의 완료 기준별로 산출물·검증·PR 반영을 대조한다. 미충족 항목이 있으면 완료하지 않고 남은 작업을 적는다. 이슈 포기는 완료가 아닌 중단 사유로 기록하고 완료 통계에서 구분한다.
2. 충족한 작업은 완료 증거를 남기고 이슈 종료와 Project 완료 상태를 맞춘다. 종료 키워드의 자동 종료를 가정하지 않고, 머지 후 실제 이슈·Project 상태를 확인한다(이슈 연결 기준은 `PR 본문`).
3. 원격에서 이슈·Project를 다시 읽어 반영을 검증한다. 이슈 생성만 성공하고 필드 설정이 실패했다면 같은 이슈를 보완한다. 응답이 불확실하면 먼저 검색하고 새 이슈를 중복 생성하지 않는다.
4. 사용자에게 이슈·PR 링크, 변경된 상태, 검증 결과, 미반영 항목만 간결하게 보고한다. 원격 작업 실패와 제품 작업 실패를 구분한다.

Projects 완료, AI-DLC 공식 승인, NCP 전체 MVP 검증은 별도다. Projects 요청만으로 AI-DLC 실행·승인·상태 파일 수정을 하지 않는다.

## 5. 양식과 자동화의 역할

- `.github/ISSUE_TEMPLATE/task.yml`, `bug.yml`은 웹 작성 양식이자 AI 작성 항목의 기준이다. CLI/API에서 작성할 때도 필수 항목 누락을 확인한다. 웹 폼의 필수 입력 검사가 모든 생성 경로를 강제하지는 않는다.
- 두 양식은 10월 MVP용으로 범위 라벨을 기본 지정한다. 후속 범위 작업에 사용하면 해당 라벨을 제거하고 올바른 대상에 연결한다. 범위 밖 아이디어를 MVP 작업으로 자동 편입하지 않는다.
- 폼의 답변은 이슈 본문이다. 영역·우선순위·선행 이슈를 본문에 썼다고 Project 필드나 의존성이 설정됐다고 보고하지 않는다.
- 초기 설정자는 `mvp-october` 라벨을 만들고 대상 저장소의 `is:issue label:mvp-october` 자동 추가를 설정한다. 활성화 전 존재하던 이슈는 별도 편입한다. 라벨은 사전 생성해야 하므로 템플릿 파일 추가만으로 자동화 완료라고 보고하지 않는다.
- 최초 Project 설정 전에는 폼에 추정 Project 번호나 고정 담당자를 넣지 않는다. 일상 갱신에는 인증된 GitHub CLI 또는 연결 도구를 사용한다. 토큰은 파일·이슈·로그에 남기지 않는다.
- 이슈·PR 양식은 저장소의 실제 기본 브랜치에 반영돼야 적용된다. 적용을 보고하기 전에 원격 기본 브랜치 설정을 확인하고, 기본 브랜치가 아닌 곳에 반영된 것만으로 활성화됐다고 보고하지 않는다. 기존 PR·승인·merge commit 절차를 유지한다.
- 처음에는 내장 자동 추가와 AI 갱신으로 시작한다. GitHub Actions·별도 등록 스크립트는 실제 반복 문제가 확인된 뒤 도입한다. 이 지침은 상시 실행되는 봇이 아니다.

## 6. 팀원 사용 예시

팀원은 다음처럼 작업 내용과 상황만 말하면 된다. Projects 확인·등록·상태 갱신까지 문장에 넣도록 요구하지 않는다.

- “홈 화면 만들려고.”
- “분석 실패 화면 할게.”
- “API 기준이 없어서 막혔어.”
- “초안 올렸어.”
- “이거 끝났어.”

AI가 §4의 착수 안내에 따라 기존 작업을 확인하고 필요한 질문·이슈 관리·검토 연결을 먼저 수행한다. 팀원에게 이 예시의 정확한 문구를 외우도록 요구하지 않는다.

최초 도입 때 각 도구에서 이 문서를 읽었는지와 GitHub 읽기·쓰기 가능 여부를 확인한다. 실제 등록 테스트는 원격 작업 요청을 받은 뒤 수행한다. 이후 같은 세션의 합의된 작업은 매번 별도 등록 요청을 반복하지 않아도 된다.
