# CatchU 11월 개발 범위 결정

지위: **확정** (2026-10-21 팀장 결정, 2026-10-22·10-23·10-24 변경) · 2026-09-28 승인된 12월 요구사항·사용자 스토리를 재승인할 때 반영할 범위 결정이다 · 11월 기능의 구현 기준은 재승인된 요구사항이다 · 팀 합의나 AI-DLC 단계 승인이 아니라 팀장 결정이다 · 공수·담당·일정 진행 상태는 이 문서에서 관리하지 않는다(Issue·Projects).

10월 MVP 이후 11월에 개발할 기능의 범위와, 그 범위에 없는 12월 승인 기능의 처리를 정한다. 12월 승인 원본([요구사항](../aidlc/spaces/default/intents/260925-intent-12/inception/requirements-analysis/requirements.md)·[사용자 스토리](../aidlc/spaces/default/intents/260925-intent-12/inception/user-stories/stories.md))은 고치지 않고 보존한다.

2026-10-22에 방향을 바꿨다. CatchU는 팀원의 취업 포트폴리오이고, 12월 이용자는 소수의 외부 사용자가 자기 자료로 써 보는 수준이다. 그래서 실제 운영 서비스용 장치는 남의 자료를 다루는 데 꼭 필요한 것만 남기고, 그 시간을 설명할 수 있는 기능(특히 RAG)에 쓴다.

## 적용 방법

- **이 문서의 역할:** 11월 개발 범위에 대한 팀장 결정이자 12월 요구사항 재승인의 입력이다. **11월 기능 구현은 재승인 뒤에 시작한다.** 재승인 전에는 이 문서도 9월 승인 원본도 11월 기능의 세부 구현 기준으로 쓰지 않으므로, 두 기준이 함께 적용되는 기간은 없다.
- **재승인:** 11월 전에 저장소의 AI-DLC를 2.11.1로 올린 뒤, 12월 intent를 요구사항 단계부터 다시 진행해 이 문서를 반영한 요구사항·사용자 스토리를 재승인한다. 판본은 재승인을 시작하기 전에 올리고 진행 중에는 바꾸지 않는다. 재개할 때는 이 문서의 내용·지위·기준 커밋을 입력에 옮겨 적는다. 링크만으로는 AI-DLC가 원문을 읽지 않는다. 9월 승인 판본과 그 추적성 검증 결과는 당시 판본에 대한 기록으로 남고, 새 범위의 추적 관계는 재승인 때 다시 검증한다.
- **재승인 때 함께 정리할 것:** 아래 「대체하는 12월 기준」과 「프로젝트 목표에서 제외」를 반영하면서, 다른 조항 안에 남은 관련 기준도 맞춘다. 예를 들어 FR16.3·US16.2의 시작 안내는 주장 대신 Catch 설명·자료 직접 선택과 새 기능(질의응답·JD 요약·Claude 연결) 흐름으로, FR16.3의 기업 회원 안내와 FR19.1·NFR6의 해당 흐름 검증은 제외 기능에 맞춰 정리한다. 「개발 담당자가 정할 것」의 값은 승인 원본의 확정 절차(예: OQ4의 팀장 확정) 대신 개발 담당자가 정하는 것으로 반영한다.
  - 이어받는 조항 안에 제외 기능·옛 구조가 남아 있으니 함께 정리한다: FR1.1(기업 기능과 소속 역할), FR1.4(서비스 안 3층 탐색), FR1.5(프로필·기업 검색에서의 숨김), FR4.1·FR4.4(주장의 제목·본문, 외부 URL 주소, 대표와 추가 자료), FR13.5(MCP 검색, 주장 저장), FR14.1(기업 소속 권한·연락처 공유, 일반 링크 보관), NFR1(역할·연락 차단), NFR4(다중 조건 검색 성능), NFR5(OQ11의 보관 항목·기간), NFR7(주장 초안 기준의 부족 조건), FR19.1(NCP, 주장·서류·공유본, 기업 기능, MCP 세 흐름).
  - 용어를 맞춘다: 공유본 → 발행본, 서류 → 자료.
  - NFR3·OQ6의 근거 품질 통과 기준을 적는다: RAG 평가 표본에서 남의 기여를 본인 것으로 쓴 항목 0건(NFR3 그대로). 근거가 문장을 뒷받침하지 않는 항목과 맞는데 버려진 항목은 건수로 기록하고, 미달이면 통과로 치지 않고 조정안을 따로 정한다(OQ6). 허용 건수는 재승인 때 팀장이 정한다.
- **실행 계획:** 재승인 때 12월 intent의 실행 계획을 다시 짠다. 지금 설정에서 실행 대상인 운영 단계 7개(배포 파이프라인, 환경 준비, 배포 실행, 관측, 장애 대응, 성능 검증, 개선)와 인프라 설계·CI를 뺄지 이때 정한다. EKS 배포는 따로 진행한다.
- **재승인 뒤:** 현행 기준은 새 승인 요구사항·사용자 스토리로 넘어가고, 이 문서는 결정 이유를 남긴 기록이 된다.
- **10월 작업:** 10월 MVP 작업은 이 문서와 관계없이 10월 승인 기준과 계약을 따른다.
- **계약:** API 명세·ERD는 재승인 뒤 AI-DLC의 도메인 설계·계약 설계 단계에서 정하고 PR로 반영한다. 이 문서만으로 10월 계약을 바꾸지 않는다.

## 사용자 흐름

구직자
1. 공개 저장소를 등록하고 분석을 요청한다. 본인 기여는 분석하면서 확인한다.
2. 만들어진 Catch를 확인하고, Catch마다 자기 설명(맡은 역할·판단 이유·결과 등)을 쓴다.
3. 자기소개서·이력서·포트폴리오 같은 자료를 텍스트로 쓰거나 PDF로 올린다.
4. Catch와 자료를 골라 순서를 정하고 링크를 발행한다. 발행 직후 고정된 발행본을 확인한다.
5. 발행이 끝나면 AI 기본 요약이 자동으로 만들어진다. 실패하거나 마음에 들지 않으면 다시 만든다.
6. 저장해 둔 JD로 자기 링크의 JD 요구사항별 요약을 받아 면접을 준비한다.
7. Claude 웹·Desktop을 연결해 자기 Catch·설명·텍스트 자료를 읽으며 자기소개·면접 준비를 한다.

링크를 받은 사람(면접관·채용담당자)
1. 받은 링크를 로그인 없이 열어 자료(PDF 원본 포함)와 AI 기본 요약을 본다.
2. 로그인 없이 발행본에 대화형으로 질문한다. 답변의 근거를 누르면 원문의 해당 줄이 강조되고, PDF는 해당 쪽을 연다.
3. 자기 JD로 비교하려면 로그인해 JD를 저장하고, 그 링크에 JD 요구사항별 요약을 실행한다.
4. CatchU 계정으로 Claude를 연결하면, 비밀번호 없는 받은 링크를 Claude에서 읽게 할 수 있다.

기업 계정이나 기업 탭은 두지 않는다. 채용담당자도 일반 개인 계정을 쓴다.

## 결정

### 운영 최소선

남기는 것: 회원 자료 격리·권한 확인·비밀값 보호, 탈퇴 즉시 실제 삭제, 외부 AI 전송 고지, 하루 실행 제한, 삭제된 자료를 늦게 도착한 AI 결과가 되살리지 않게 하는 최소 확인.

빼는 것: 탈퇴의 2단계 삭제·실패 기록·재처리, 정밀한 사용량 기록과 남은 횟수 표시, 기능마다 넣었던 동시 요청·재전송·늦은 결과의 세부 처리와 시험, 기능 사이 실패 13종 시험(핵심 3개만 남김), 운영 절차서·비용 측정 보고서·외부 사용자 정형 관찰, 10월 링크 전환(12월 전에 10월 데이터를 모두 초기화한다).

### 저장소 등록과 분석

- 공개 저장소 등록은 간단히 한다. 등록할 때 소유·기여 관계를 미리 검사하지 않고, 분석에서 본인 커밋을 확인한다. 분석할 본인 기록이 없으면 그렇게 안내한다.
- GitHub 연결 본인 신원, 공개 여부 확인, 회원별 자료 분리는 유지한다.
- 수집 상한(커밋 목록·상세 조회·호출 수·수집 시간·생성 횟수·요청 처리 시한)을 올린다. 시연용 기준은 팀장 계정의 CatchU 저장소 커밋 약 500개가 반영되는 것이고, 값은 실측으로 정한다.

### 자료와 발행 링크

- 독립된 '주장'(제목·본문·여러 Catch 연결·순서·공개/대표)을 만들지 않는다. 대신 Catch마다 작성자 설명 하나를 둔다. 설명은 AI가 만든 설명 초안·확인된 사실과 구분해 보여 주고 덮어쓰지 않는다.
- 여러 경험을 묶는 강점 문장은 텍스트 자료에 자유롭게 쓴다. Catch와 구조적으로 연결하지 않는다.
- 자료는 텍스트와 PDF 두 종류다. URL 자료 종류는 따로 두지 않는다. 텍스트 자료 안에 주소를 적는 것은 된다.
- PDF는 원본을 보관하고, 받은 사람은 원본을 브라우저로 본다. worker가 쪽마다 글을 뽑아(`pypdf`) AI·검색 재료로 쓴다. 이미지 글자 인식은 없고, 글이 안 나오는 쪽은 "읽을 수 없음"으로 안내하며 AI가 읽은 것처럼 답하지 않는다. 크기·쪽 수 상한을 두고, 뽑은 글도 신뢰할 수 없는 입력으로 다룬다.
- 발행할 때 Catch(설명 포함)·텍스트·PDF를 직접 고르고 순서를 정한다. Catch의 공개/비공개는 발행 선택을 막지 않는다. 고르는 것 자체를 내보내겠다는 뜻으로 본다. 발행 때 권한·선택·크기를 다시 확인하고, 링크와 발행본을 함께 저장한다. PDF는 발행할 때 파일을 복사해 발행본마다 자기 파일을 갖는다.
- 발행 미리보기는 "발행 후 확인"으로 한다. 발행 전에는 고른 자료·순서와 접근 조건을 안내하고, 발행 직후 실제 고정 사본을 작성자에게 보여 준다.
- Catch 설명과 텍스트 자료를 여러 탭에서 고치면 마지막 저장이 남는다(충돌 감지는 하지 않는다). 저장하지 않고 떠나면 경고하고, 저장이 실패하면(서버 오류·연결 끊김·로그인 만료) 저장되지 않았다고 알리며 쓰던 내용은 화면에 남겨 다시 저장할 수 있게 한다.
- 발행본은 발행 당시 내용으로 고정한다. 링크가 중지·만료돼도 작성자는 발행 내용을 다시 볼 수 있고, 삭제는 따로 한다.
- 같은 작업이 다시 분석되면 기존 Catch를 그대로 참조하므로 설명이 유지된다. 다른 작업으로 판별돼 새 Catch가 생기면 기존 설명을 옮기지 않는다.

### AI 기본 요약

- 발행본마다 하나 만든다. JD 없이 발행 당시 내용으로 발행 뒤 백그라운드에서 생성한다.
- 생성되면 로그인 여부와 관계없이 그 링크를 여는 모든 사람에게 바로 보인다. 'AI 요약'임을 표시한다. 작성자 확인 단계와 요약 전용 미리보기는 없다.
- 실패하면 수신자에게는 요약이 없다고만 보이고, 작성자에게는 다시 만들기 버튼이 보인다. 성공한 뒤에도 다시 만들 수 있다.
- 발행본에 딸린 자료다. 링크가 중지·만료되면 수신자에게는 막히고 작성자는 계속 본다. 발행본을 삭제하거나 작성자가 탈퇴하면 함께 지운다. 그 뒤 늦게 도착한 결과는 저장하지 않는다.

### RAG 대화형 질의응답

- 링크를 연 사람이 그 발행본에 자유롭게 묻고, 앞 대화를 이어서 묻는다. 질문을 앞 대화에 맞게 다시 쓰고, 발행본에서 관련 조각을 찾아 답한다.
- 로그인하지 않아도 쓴다. 제한은 링크당 하루 질문 횟수 하나다(접속 주소별 제한 없음).
- 대화는 브라우저에만 두고 서버에 저장하지 않는다. 질문마다 최근 대화를 함께 보내되 신뢰할 수 없는 입력으로 다루고, 턴과 길이에 상한을 둔다.
- 찾는 범위는 그 링크의 발행 사본(Catch, 작성자 설명, 텍스트, PDF 글)뿐이다. 질문마다 링크 조건(비밀번호·만료·중지·삭제)을 다시 확인한다.
- 사람이 기다리는 기능이므로 큐가 아닌 바로 답하는 경로로 처리한다. 답은 항목 단위로 받아 아래 검사를 통과한 항목만 화면에 차례로 내보낸다(SSE 스트리밍).
- 발행할 때 사본을 조각으로 나누고 위치(항목·필드·글자, PDF 쪽)를 기록한다. 조각은 Voyage AI API로 임베딩해 벡터 저장소에 저장하고, 발행본을 지울 때 함께 지운다. 질문에 넘길 자료는 의미 검색으로만 고른다(링크 크기에 따라 통째로 넘기기와 나눠 쓰지 않는다).

### JD 요구사항별 요약

- 결과는 하나의 요약이다. JD 요구사항마다 JD 원문 줄, 관련 Catch·작성자 설명·자료 근거(근거 원문에 GitHub 기록과 작성자 자료를 구분해 표시), 자료로 확인되지 않는 점, 그 요구사항에 연결된 면접 질문을 보여 준다.
- JD를 요구사항으로 나누고, 요구사항마다 발행본에서 관련 조각을 찾아 근거로 넣는다. 생성은 요구사항마다 차례로 부른다. 요구사항과 결과의 대응, 일부 실패, 전체 실행 시한 처리는 둔다.
- 로그인한 회원만 실행한다. 링크를 받은 다른 회원(면접관)도 자기 JD로 실행할 수 있고, 결과는 실행한 회원만 본다. 링크 작성자는 다른 회원의 JD·결과를 볼 수 없다.
- 같은 JD로 다시 실행하면 새 실행이다. 본인 결과는 그 링크가 유효한 동안(만료·중지 전) 다시 열 수 있다. 발행본 삭제, 작성자 또는 실행한 회원의 탈퇴, 그 JD 삭제 때 함께 지운다.
- JD는 별도 JD 관리 페이지에서 저장·수정·삭제한다.
- 실행은 백그라운드로 처리한다. 브라우저를 닫아도 접수된 처리는 취소되지 않고, 나중에 상태·결과·실패 안내를 본다. 멈춘 실행은 처리 시한이 지나면 실패로 바뀐다. 자동 복구·중간 재개·자동 재시도는 없다.
- 입력이 상한을 넘으면 실행 전에 거부하고 안내한다. 일부만 골라 자동으로 검토하지 않는다.

### 근거와 AI 출력 검사 (기본 요약·질의응답·JD 요약 공통)

- 근거는 Claude API의 인용 기능으로 붙인다. 모델은 근거가 되는 줄만 가리키고, 근거 글은 API가 넘긴 자료에서 그대로 복사해 붙인다. 인용 단위(줄)는 서비스가 정해 넘긴다. 이 호출에서는 구조화된 출력을 함께 쓸 수 없다.
- 문장에 나온 숫자·PR 번호·파일 이름과 영어 표기(기술·저장소 이름 등)가 그 문장이 가리킨 근거 글 안에 있는지 기계적으로 확인하고, 맞지 않는 항목은 그 항목만 버리고 나머지는 보여 준다. 근거 없는 해석 문장은 'AI 해석'으로 표시하고, 숫자·PR 번호가 있거나 발행본 어디에도 없는 영어 표기가 있으면 버린다. 영어 표기는 대소문자를 가리지 않고, 흔한 낱말은 짧은 예외 목록으로 뺀다. PR 번호는 그 근거 글이 속한 Catch의 PR 번호도 맞는 것으로 본다. 생성 지시에는 원문 표기를 그대로 쓰고, PR·이슈 번호 대신 무엇을 했는지로 쓰게 한다(번호는 근거 원문에서 보인다). 검사에 걸린 항목은 경고를 붙여 보여 주지 않고 버린다.
- JD 요약의 면접 질문은 사실 주장이 아니므로, 영어 표기를 근거 원문과 그 JD 요구사항 줄에서 함께 찾고, 숫자·PR 번호는 같은 요구사항의 근거 칸이 인용한 근거 원문에서 찾는다. 질문은 확인되지 않은 일을 이미 한 것처럼 전제하지 않게 지시한다.
- 질문이나 JD 요구사항에 나온 영어 표기가 이번에 찾은 자료 어디에도 없으면, 서버가 "이번에 찾은 자료에서 'Kafka' 표기를 찾지 못함"처럼 알린다(JD는 「자료로 확인되지 않는 점」). 경험이나 역량이 없다고 쓰지 않는다.
- 출처 표시는 AI 문장이 아니라 근거 원문에 붙인다: "GitHub 기록 원문"(Catch의 GitHub 기록), "작성자 자료 원문"(설명·텍스트·PDF). AI가 쓴 문장은 근거가 붙어 있어도 확인된 사실로 표시하지 않는다.
- 근거를 누르면 원문의 해당 구절이 강조되고 그 위치로 이동한다. PDF는 쪽 번호와 뽑은 글의 강조 구절, "원본 n쪽 열기"를 보여 준다.
- 유지하는 것: 근거 없는 사실이나 역량을 단정하지 않는 지시, 점수·비율 같은 역량 평가 표현을 쓰지 않는 지시, 작성자의 설명·자료(PDF 포함)에 숨긴 지시로 결과를 조작하지 못하게 하는 방어. [보안 점검](CatchU_security_checks.md)의 LLM 기준은 그대로 적용한다. 그중 "생성 문장의 사실을 근거와 대조하고 근거에 없는 사실은 확정하지 않는다"는 위 기계 대조, 아래 사전 시험으로 정한 모델, RAG 평가의 사람 확인으로 지킨다. 기계 대조만으로 충족했다고 보지 않는다.
- 한계: 진짜 근거를 가리키면서 남의 일을 본인 것으로 쓰거나, 뜻을 뒤집거나(검토만 한 것을 도입했다고 씀), 역할·성과를 부풀린 문장은 기계 대조로 거르지 못한다. 근거 원문을 항목 아래 바로 보여 주지만, 이것을 검사로 치지 않는다.
- 사전 시험(2026-10-24, 팀장): 팀장 저장소의 PR로 만든 발행본에 함정 4종(자료에 없는 기술, 비교·계획만 한 것, 남이 한 일, 표기 차이)을 넣고, 질문 10개·JD 1개·기본 요약 1번을 Haiku와 Sonnet으로 한 번씩 돌렸다. 버림 규칙을 통과한 항목에서 남의 일을 본인 것으로 쓴 것·뜻 뒤집기·역할 부풀림은 두 모델 모두 0건이었다. 그래서 세 기능 모두 Haiku 5.5를 쓰고 판정 AI는 두지 않는다. 맞는데 버려진 항목이 많았고(Haiku 34·Sonnet 57) 주원인이 Catch 제목에만 있는 PR 번호여서, 위 PR 번호 허용·번호 대신 한 일로 쓰기·면접 질문 대조를 정했다. 원문은 한글인데 문장을 영어로 쓴 표기 차이는 약 2%여서 표기 쌍은 두지 않고, RAG 평가에서 많이 나오면 다시 본다. 한 번 돌린 결과이므로 오류가 나오지 않았다고 안전하다는 근거로 쓰지 않는다.
- RAG 품질 평가: 시연 발행본 1개에 질문 10개와 정답 근거를 만들어 검색 적중률과 근거 통과율을 스크립트로 한 번 재고 기록한다. 사람이 그 10개에서 근거가 문장을 뒷받침하는지 함께 보고, 남의 일을 본인 것으로 쓴 것·뜻이 뒤집힌 것·역할을 부풀린 것과 맞는데 버려진 항목을 따로 센다. JD는 같은 JD 하나로 두 방식(전체 넣기·검색 기반) 결과를 나란히 기록한다. 튜닝 반복·CI·AI 채점은 없다.

### Claude MCP

- Claude 웹·Desktop은 같은 원격 연결을 쓴다. 최소 OAuth로 연결하며, 자동 갱신 없이 만료되면 다시 승인하고, 연결별 관리 대신 전체 연결 해제를 제공한다.
- 구직자 본인: 연결할 때 본인의 공개·비공개 Catch와 현재·이후 저장할 텍스트 자료를 읽게 된다는 것을 한 번 안내하고 동의를 받는다. 도구는 Catch 조회(설명 포함)와 텍스트 자료 조회다. PDF 글은 넣지 않는다.
- 링크를 받은 사람: CatchU에 Google로 가입해 같은 방식으로 연결한다. Claude에 링크 주소를 주면 비밀번호 없는 링크는 웹과 같은 권한으로 읽는다. 비밀번호 있는 링크는 MCP로 읽지 않고 웹에서 보라고 안내한다. 비밀번호는 Claude를 거치지 않는다. 도구는 발행본 읽기(PDF 글 포함, 길면 나눠 읽기) 하나다. 호출마다 링크 만료·중지·삭제를 다시 확인한다.
- 링크 화면에 "Claude에서 분석하기" 버튼(요청 문장 복사와 연결 안내)을 둔다. 작성자에게는 발행 때 비밀번호 없는 링크는 받은 사람이 외부 AI 도구로 읽을 수 있다고 안내한다. 링크별 허용 설정은 없다.
- MCP로 쓰기·JD 요약·의미 검색은 하지 않는다. 기간별 사용 횟수는 기록하지 않고, 회원 기준으로 짧은 시간의 요청 빈도와 응답 크기만 제한한다. 원격 연결 요청은 Claude 쪽 서버에서 오므로 IP가 아니라 회원 기준으로 센다.

### 하루 실행 제한과 고지

- AI 호출이 드는 실행(분석, 기본 요약 생성·다시 만들기, JD 요약)은 계정당 하루 횟수 제한 하나만 둔다. 남은 횟수는 보여 주지 않고 "오늘 한도에 도달했습니다"를 안내한다. 질의응답은 링크당 하루 제한을 따른다. 전체 지출 상한은 Claude API 콘솔에서 설정한다.
- 외부 AI 전송은 첫 이용 때 한 번 동의받고(분석·요약·질의응답·PDF 처리), 그 뒤에는 화면마다 한 줄로 안내한다. 비로그인 질의응답 사용자에게는 입력란 옆 한 줄 안내가 고지 역할을 한다. 임베딩은 Voyage AI(운영사 MongoDB)가 자료를 받으므로 고지에 더한다. 문의 경로는 한 줄로 둔다.
- 구직자가 올린 자기 자료(텍스트·PDF)는 이름·이메일·전화번호를 포함해 첫 이용 동의 아래 그대로 AI에 보내고, 서비스가 개인정보를 찾아 가리지 않는다. 대신 자료를 올리는 화면에 "주민등록번호 같은 민감한 정보는 지우고 올려 주세요"를 안내한다. 저장소 분석의 비밀값·개인정보 가리기(10월 규칙)는 그대로 둔다.

### 회원 탈퇴

- 로그인한 사용자가 확인창으로 탈퇴를 요청하면 즉시 로그인·링크·MCP 접근을 막고 계정과 자료를 실제로 지운다. 10월 데이터를 초기화하면서 표 관계를 "회원을 지우면 관련 행도 함께 삭제"로 다시 정의하고, DB 밖의 GitHub 자격정보 파일도 지운다. 실패하면 오류를 보여 주고 팀이 확인한다.
- 작성자가 탈퇴하면 그 발행본의 AI 기본 요약과 다른 회원의 JD 요약 결과·실행 입력 사본도 지운다. 다른 회원이 저장한 JD 원본은 남긴다.
- 탈퇴 처리 중이거나 끝난 뒤 늦게 도착한 결과는 저장하지 않는다.

### 검증과 시연

- 통합 확인은 시연 시나리오로 겸해 두 번 한다. 1차는 "최소 연결 첫 결과"로, 기능별로 실제 연결이 되는지 본다. 새 저장소 등록 경로를 실제로 돌렸는지는 따로 기록하고, 10월 분석 경로로 대신 돌린 성공을 새 흐름 완료로 치지 않는다. 2차 뒤 남은 기간은 결함 수정에 쓴다.
- 보호 흐름 3개를 확인한다: 회원 자료 격리, 링크 중지 뒤 웹·질의응답·MCP 차단, 탈퇴 뒤 차단.
- 실제 Claude 연결은 웹에서 전체(연결·만료 재승인·해제)를 확인하고 Desktop은 연결만 확인한다. 기본 호환은 개발 초기에 먼저 확인한다.
- 실제 분석은 팀장 계정 하나로 CatchU 저장소를 분석하고 거부 사례 1~2종을 더해 확인한다. 팀원이 아닌 사람 1명이 자기 자료로 처음부터 써 보는 확인도 한다.
- 처음 쓰는 사람을 위한 최소 시작 안내(다음 행동 안내, 메뉴 연결, 기본 오류·404 화면)와 외부 사용자의 Google 로그인 대상 설정을 둔다.
- 시연 리허설과 제출 자료 정리는 12월 1~9일에 한다. 12월에 기능 개발은 하지 않는다.

## 11월 진행 방식

아래 다섯 덩어리는 AI-DLC Unit 나누기에 넣는 출발안이다. 최종 작업 단위(Unit)와 의존 관계는 Unit 나누기에서 정하고, 그 승인 기록이 이 표를 대신한다. 공용 기반은 팀장이 맡고, 나머지 Unit 담당은 납품 계획 단계에서 확정한다.

| 덩어리 | 내용 | 기다리는 것 |
|---|---|---|
| 공용 기반 | 공용 계약, AI 생성 공통(인용 기능 연결·근거 검사), 백그라운드 AI 실행 공통, 탈퇴, 하루 실행 제한·고지, 시작 안내, 통합 확인 진행 | 없음 |
| 발행·링크 | Catch 설명, 발행, 링크 열람·관리, 발행본 삭제 | 공용 계약, PDF, 텍스트 자료 |
| RAG | PDF, 발행본 색인·검색, 질의응답, 근거 원문 강조, RAG 평가, AI 기본 요약 | 공용 계약, AI 생성 공통, 발행 |
| Claude MCP | 연결(OAuth)·동의·해제, 본인용 도구, 받은 링크 읽기, 실제 연결 확인, 텍스트 자료 | 공용 계약, 링크 열람 |
| 저장소·JD | 저장소 등록·분석 대상 전환·수집 상한, 실제 분석 확인, JD 관리, JD 요구사항별 요약 | 검색(RAG), AI 생성 공통 |

- **AI-DLC:** 팀장이 재승인부터 도메인 설계 → Unit 나누기 → 계약 설계 → 납품 계획까지 한 번에 진행한다. 위 덩어리를 출발안으로 넣되, 더 나은 경계가 나오면 Unit 나누기 결과를 따른다. 다른 덩어리의 세부는 팀장 혼자 정하지 않고 "담당 확인 필요"로 남긴다. 각 담당은 개발을 시작하기 전에 계약 설계·Unit 나누기 결과에서 자기 Unit 부분을 확인하고, 이의가 없으면 그대로 시작한다.
- **구현:** AI-DLC 공식 팀 방식으로 한다. 납품 계획에서 팀마다 Unit을 맡는 방식을 고르고, 승인은 단계마다 받는다. 각 담당은 자기 Unit을 맡아(claim) 기능 설계부터 시험까지 진행하고 제출한다. 팀장이 고정·합치기 승인을 거쳐 intent 작업 브랜치에 merge commit으로 합치고, 그 브랜치를 PR·작성자 외 승인 1건·merge commit으로 `dev`에 올린다. 팀원 모두 같은 AI-DLC 판본(2.11.1)을 쓴다.
- **시험과 대안:** 이 방식은 우리 저장소에서 아직 끝까지 돌려 본 적이 없다. 개발 시작 전에 Unit 하나로 맡기 → 진행 → 제출 → 합치기 → `dev` PR까지 시험한다. 실패하면 구현만 이슈 → 브랜치 → PR로 바꾼다. 계약 설계가 늦어지면 계약을 기다리지 않는 일(Claude 연결, 저장소 등록, PDF 글 추출 확인)부터 시작한다.
- **원칙:** 계약에 없는 모양이 필요하면 혼자 정하지 않고 멈춘 뒤 계약 수정 PR로 처리한다. 공용 기반 PR은 그것을 가져다 쓰는 사람이 리뷰한다. 탈퇴를 위한 표 관계 전환은 개발 시작 전에 병합한다.
- **AI 생성 공통 관문:** 인용 기능 연결은 응답을 항목으로 묶기, 인용 보존, 원문 위치 연결, 거부 사례 처리가 되면 통과로 본다. 통과하지 못하면 원문 열람부터 확보하고 다른 생성 방식은 다시 산정해 범위를 정한다. 2026-10-24 사전 시험에서 네 가지를 확인했고, 실제 연결 때 다시 본다.
- **팀 규칙:** 구현 방식이 바뀌므로 [작업관리](CatchU_작업관리.md)의 코딩 운영은 PR로 고치고, AI-DLC `team.md`는 재승인 진행 중 AI-DLC 승인 관문에서 고친다.

## 개발 담당자가 정할 것

- 발행본·JD·AI 입력·PDF의 상한 값. 정상 링크와 JD가 AI 입력 상한 안에 들도록 맞춘다.
- 하루 실행 제한과 링크당 질문 제한의 값(넉넉하게).
- 결과가 끝났는지 자동으로 확인할지(폴링), 새로고침 버튼으로 확인할지.
- 근거가 틀린 문장을 버린 뒤 남은 내용이 너무 적을 때 빈 결과처럼 처리할지와 그 기준.
- 영어 표기 대조의 흔한 낱말 예외 목록(짧게 둔다).
- 기본 요약 다시 만들기의 반복 제한.
- 질의응답 대화를 새로고침 뒤에도 남길지.
- Voyage AI의 임베딩 모델 선택과 자료 보존·학습 사용 조건 확인.
- MCP 요청 빈도 제한 값(실제 Claude 호출량을 보고 넉넉하게), 거부를 돌려주는 형태.

## 아직 정하지 않은 것

- PDF 저장 위치: DB 또는 S3. S3면 DB 연쇄 삭제가 파일까지 지우지 못하므로 파일 삭제를 따로 만든다.
- 시연용 저장소 공개: 시연에서 CatchU 저장소를 분석하려면 공개해야 한다. 공개하면 공개 전에 이력·문서·AI-DLC 기록을 점검하고, 공개하지 않으면 대체 공개 저장소를 준비하고 분석·평가 대상을 다시 정한다.
- 남는 일을 내려놓을 순서: 계획한 일이 11월 가용보다 많다. 1차 통합 확인 때 먼저 내려놓을 순서를 미리 합의한다.

## 검토했지만 채택하지 않은 안

- 고정 발행본 대신 선택한 항목의 현재 내용을 보여 주기: 면접관과 구직자가 같은 내용으로 이야기하기 어렵고, AI 답변이 화면 내용과 어긋나게 된다.
- JD 요약을 자기 발행본에만 허용하기: 면접관이 자기 JD로 대조하는 것이 이 기능의 핵심이다.
- 링크 중지 때 발행본과 결과를 바로 지우기: 작성자가 보낸 내용을 다시 확인할 수 없고, 만료와의 처리가 갈라진다.
- 자료 옆 JD 패널, 독립 주장, MCP 의미 검색 도구, 구직자 본인용 MCP의 PDF 글: 같은 가치를 다른 기능이 이미 보여 주거나 공수에 비해 설명 가치가 작다.
- 비로그인 JD 요약: 계정 없이 결과를 본인에게만 보여 주는 방법과 남용 제한이 따로 필요하다.
- 링크 단위 한도 합산: 늦게 온 면접관이 다른 사람의 사용 때문에 막힐 수 있다.
- 근거가 틀린 문장의 링크만 빼고 문장은 남기기: 근거 없는 경력 문장이 비로그인 수신자에게도 보이고, [보안 점검](CatchU_security_checks.md)의 사실 대조 기준과 어긋난다.
- 모델이 근거 문구를 직접 옮겨 쓰게 하고 서버가 글자 일치를 확인하기: 조금만 다르게 옮겨도 맞는 내용이 버려진다. 인용 기능은 근거 글을 API가 원문에서 복사하므로 이 문제가 없다.
- 질문마다 판단 모델이 RAG와 통째로 넘기기 중 고르기: 질문마다 호출이 하나 늘고 판단이 틀릴 수 있다.
- 단어 검색(글자 겹침)만 쓰거나 검색 없이 통째로만 넘기기: RAG의 핵심 기술(임베딩·벡터 검색)을 보여 주지 못한다.
- 면접관 MCP에서 비밀번호 링크를 웹에서 푼 뒤 계정별 기록으로 읽기, 열린 링크 목록 도구: 계정별 열람 기록을 새로 만들어야 하고, 비밀번호 없는 링크만으로 핵심 흐름을 보여 줄 수 있다.
- 별도 JD 흐름 전체, PDF, 면접관 MCP 전체, AI 기본 요약, 대화형 스트리밍, 원문 강조를 빼기(MVP 과잉 점검의 큰 축소 후보): 승인된 요구사항에 있거나 이번 포트폴리오의 핵심 설명거리라, 빼면 잃는 것이 줄어드는 공수보다 크다고 보고 반증 검토에서 기각했다. 남는 일을 내려놓을 순서를 정할 때 후보로는 참고한다.
- 구현을 이슈·PR로만 하고 AI-DLC 팀 방식을 쓰지 않기: 2026-10-23 팀 회의에서 공식 팀 방식으로 정했다. 시험이 실패할 때의 대안으로 남긴다.
- 승인 원본(`aidlc/`)을 직접 고치기: 과거 승인 기록은 소급 수정하지 않는다. 공식 기준은 AI-DLC 재승인으로 바꾼다.
- 표기 차이·판정에 고르기 전용 모델(Microsoft-Decision-1) 쓰기: 사전 시험에서 판정 AI가 잡을 오류가 없었고 표기 차이는 약 2%였다. 자료를 받는 회사가 늘고 한국어 성능이 확인되지 않았다. 판정 AI가 필요해지면 비교 후보로 본다.
