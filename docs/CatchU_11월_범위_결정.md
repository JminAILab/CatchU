# CatchU 11월 개발 범위 결정

지위: **확정** (2026-10-21 팀장 결정) · 2026-09-28 승인된 12월 요구사항·사용자 스토리의 일부를 대체한다 · 팀 합의나 AI-DLC 단계 승인이 아니라 팀장 결정이다 · 공수·담당·일정은 이 문서에서 관리하지 않는다(Issue·Projects).

10월 MVP 이후 11월에 개발할 기능의 범위와, 그 범위에 없는 12월 승인 기능의 처리를 정한다. 12월 승인 원본([요구사항](../aidlc/spaces/default/intents/260925-intent-12/inception/requirements-analysis/requirements.md)·[사용자 스토리](../aidlc/spaces/default/intents/260925-intent-12/inception/user-stories/stories.md))은 고치지 않고 보존한다.

## 적용 방법

- **지금부터 요구사항 재승인 전까지:** 아래 「대체하는 12월 기준」과 「프로젝트 목표에서 제외」에 적은 부분은 이 문서가 승인 원본보다 우선한다. 적지 않은 부분은 승인 원본을 따르되, 다음 두 가지는 승인 원본의 어느 조항에 있어도 이 문서를 따른다.
  - 제외한 기능에 관한 기준은 다른 요구사항 안에 들어 있어도 적용하지 않는다. 예: FR16.3의 기업 회원·MCP 세 흐름 안내, FR19.1·NFR6의 기업 기능·MCP 세 흐름 외부 검증. 남은 흐름의 안내·검증은 그대로 적용한다.
  - 이 문서가 개발 담당자에게 맡긴 값과 방식(「개발 담당자가 정할 것」)은 승인 원본의 확정 절차(예: OQ4의 팀장 확정) 대신 개발 담당자가 정한다.
- **재승인:** 11월 전에 12월 intent를 요구사항 단계부터 AI-DLC로 다시 진행해, 이 문서를 반영한 요구사항·사용자 스토리를 재승인한다. 재개할 때는 이 문서의 내용·지위·기준 커밋을 입력에 옮겨 적는다. 링크만으로는 AI-DLC가 원문을 읽지 않는다. 9월 승인 판본과 그 추적성 검증 결과는 당시 판본에 대한 기록으로 남고, 새 범위의 추적 관계는 재승인 때 다시 검증한다.
- **재승인 뒤:** 현행 기준은 새 승인 요구사항·사용자 스토리로 넘어가고, 이 문서는 결정 이유를 남긴 기록이 된다.
- **계약:** API 명세·ERD는 기존 [코딩 운영](CatchU_coding_procedures.md#코딩-운영) 규칙대로 AI-DLC로 고쳐 PR로 반영한다. 재승인 뒤 도메인 설계·API 계약·ERD 단계에서 정한다. 이 문서만으로 10월 계약을 바꾸지 않는다.

## 사용자 흐름

구직자
1. 공개 저장소를 등록하고 분석을 요청한다. 본인 기여는 분석하면서 확인한다.
2. 만들어진 Catch를 확인하고, Catch마다 자기 설명(맡은 역할·판단 이유·결과 등)을 쓴다.
3. Catch와 텍스트·URL 자료를 골라 순서를 정하고 링크를 발행한다. 발행본은 발행 당시 내용으로 고정된다.
4. 발행이 끝나면 AI 기본 요약이 자동으로 만들어진다. 실패하거나 마음에 들지 않으면 다시 만든다.
5. 저장해 둔 JD로 자기 링크의 JD 요구사항별 요약을 받아 면접을 준비한다.
6. Claude 웹·Desktop을 연결해 자기 Catch·설명·자료를 읽으며 자기소개·면접 준비를 한다.

면접관·채용담당자
1. 받은 링크를 로그인 없이 열어 자료와 AI 기본 요약을 읽는다.
2. 자기 JD로 비교하려면 로그인해 JD를 저장하고, 그 링크에 JD 요구사항별 요약을 실행한다.
3. 요약의 근거를 눌러 해당 자료로 이동하고, 요구사항별 면접 질문을 확인한다.

기업 계정이나 기업 탭은 두지 않는다. 채용담당자도 일반 개인 계정을 쓴다.

## 결정

### 저장소 등록

- 공개 저장소 등록은 간단히 한다. 등록할 때 소유·기여 관계를 미리 검사하지 않고, 분석에서 본인 커밋을 확인한다. 분석할 본인 기록이 없으면 그렇게 안내한다.
- GitHub 연결 본인 신원, 공개 여부 확인, 회원별 자료 분리는 유지한다.

### 자료와 발행 링크

- 독립된 '주장'(제목·본문·여러 Catch 연결·순서·공개/대표)을 만들지 않는다. 대신 Catch마다 작성자 설명 하나를 둔다. 설명은 AI가 만든 설명 초안·확인된 사실과 구분해 보여 주고 덮어쓰지 않는다.
- 여러 경험을 묶는 강점 문장은 텍스트 자료에 자유롭게 쓴다. Catch와 구조적으로 연결하지 않는다.
- 발행할 때 Catch(설명 포함)와 텍스트·URL 자료를 직접 고르고 순서를 정한다. 발행 때 권한·선택·크기를 다시 확인하고, 링크와 발행본을 함께 저장한다.
- 발행 미리보기 방식(발행 후 확인, 간단한 발행 전 미리보기, 미리본 내용과 발행 내용의 일치 검사)은 개발 담당자가 정한다.
- Catch 설명과 텍스트 자료를 여러 탭에서 고치면 마지막 저장이 남는다. 저장하지 않고 떠날 때의 경고와 서버 오류 안내는 둔다.
- 발행본은 발행 당시 내용으로 고정한다. 링크가 중지·만료돼도 작성자는 발행 내용을 다시 볼 수 있고, 삭제는 따로 한다.
- 같은 작업이 다시 분석되면 기존 Catch를 그대로 참조하므로 설명이 유지된다. 다른 작업으로 판별돼 새 Catch가 생기면 기존 설명을 옮기지 않는다.

### AI 기본 요약 (신규)

- 발행본마다 하나 만든다. JD 없이 발행 당시 내용으로 발행 뒤 백그라운드에서 생성한다.
- 생성되면 로그인 여부와 관계없이 그 링크를 여는 모든 사람에게 바로 보인다. 'AI 요약'임을 표시한다. 작성자 확인 단계는 없다.
- 실패하면 수신자에게는 요약이 없다고만 보이고, 작성자에게는 다시 만들기 버튼이 보인다. 성공한 뒤에도 다시 만들 수 있다.
- 요약 전용 미리보기는 없다. 작성자는 발행 후 자기 발행본 화면에서 확인한다.
- 발행본에 딸린 자료다. 링크가 중지·만료되면 수신자에게는 막히고 작성자는 계속 본다. 발행본을 삭제하거나 작성자가 탈퇴하면 함께 지운다.
- 발행할 때 작성자 자료가 요약을 위해 외부 AI로 전송된다는 안내를 보여 준다.

확인 기준
- 발행 직후 생성이 접수되고, 같은 발행을 다시 보내도 생성이 두 번 접수되지 않는다. 생성 접수가 실패해도 발행본과 링크는 유지된다.
- 비로그인 수신자가 링크 조건(비밀번호·만료·중지)을 통과하면 요약을 보고, 조건을 통과하지 못하면 요약도 보지 못한다.
- 작성자만 다시 만들 수 있고, 동시에 여러 번 눌러도 마지막 결과 하나만 남는다. 늦게 끝난 이전 생성이 새 결과를 덮지 않는다.
- 발행본 삭제·작성자 탈퇴 뒤 늦게 도착한 결과는 저장하지 않는다.
- 요약의 근거 링크는 실제 발행본 항목만 가리키고, 없는 항목을 인용한 문장은 화면에 나오지 않는다.

### JD 요구사항별 요약

- 결과는 하나의 요약이다. JD 요구사항마다 JD 원문 줄, 관련 Catch·작성자 설명·자료 근거(작성자가 연결한 것과 AI가 찾은 후보를 구분), 자료로 확인되지 않는 점, 그 요구사항에 연결된 면접 질문을 보여 준다.
- 로그인한 회원만 실행한다. 링크를 받은 다른 회원(면접관)도 자기 JD로 실행할 수 있고, 결과는 실행한 회원만 본다. 링크 작성자는 다른 회원의 JD·결과를 볼 수 없다.
- 실행 한도는 계정 단위로만 센다. 실제 처리를 시작할 때 한 번 세며, 분석과 JD 요약의 남은 횟수를 보여 준다.
- 같은 JD로 다시 실행하면 새 실행이다. 본인 결과는 보관기간 동안, 링크가 유효할 때 다시 열 수 있다.
- JD는 별도 JD 관리 페이지에서 저장·수정·삭제한다.
- 실행은 백그라운드로 처리한다. 브라우저를 닫아도 접수된 처리는 취소되지 않고, 나중에 상태·결과·실패 안내를 본다. 자동 복구·중간 재개·자동 재시도는 없다.
- 입력이 상한을 넘으면 실행 전에 거부하고 안내한다. 일부만 골라 자동으로 검토하지 않는다.

### AI 출력 검사 (기본 요약·JD 요약 공통)

- 형식: 기본 요약과 JD 요약은 항목마다 근거가 붙는 독립된 짧은 항목 목록으로 만든다. 한 항목을 빼도 나머지가 읽히게 한다.
- 사실 대조: 각 항목이 인용한 근거가 실제 발행본 항목인지, 그리고 문장에 나온 구체적 사실(기술 이름, 파일·저장소 이름, PR 번호, 수치 등)이 인용한 항목의 글에 실제로 있는지 기계적으로 확인한다. 둘 중 하나라도 맞지 않는 문장은 그 문장만 버리고 나머지는 보여 준다. 구체적 사실이 없는 해석 문장은 'AI 해석'으로 표시하고 확인된 사실처럼 쓰지 않는다. 문장의 의미를 따로 판정하는 두 번째 AI 검사는 두지 않는다.
- 바뀌는 것: 자동 실패 판정과 검사량. 읽을 수 없거나 빈 결과만 전체 실패로 본다. 한 요구사항의 근거가 모두 빠지면 근거를 찾지 못한 정상 결과로 보여 준다. 문장마다 근거를 강제하거나 하나만 틀려도 전체를 실패시키지 않는다. 품질 확인은 개발 중 실제 자료로 2~3회 하고, 숨긴 지시 사례 1개를 확인한다.
- 유지하는 것: 기록에서 확인한 사실·작성자 설명·AI 해석의 구분, 근거 없는 사실이나 역량을 단정하지 않는 지시, 점수·비율 같은 역량 평가 표현을 쓰지 않는 지시, 작성자의 설명·자료에 숨긴 지시로 결과를 조작하지 못하게 하는 방어. [보안 점검](CatchU_security_checks.md)의 LLM 기준은 그대로 적용하며, 그중 "생성 문장의 사실을 근거와 대조하고 근거에 없는 사실은 확정하지 않는다"는 위 사실 대조와 'AI 해석' 표시로 충족한다.

### Claude MCP

- Claude 웹·Desktop은 같은 원격 연결을 쓴다. 최소 OAuth로 연결하며, 자동 갱신 없이 만료되면 다시 승인하고, 연결별 관리 대신 전체 연결 해제를 제공한다.
- 연결할 때 본인의 공개·비공개 Catch와 현재·이후 저장할 텍스트·URL 자료를 읽게 된다는 것을 한 번 안내하고 동의를 받는다. 자료마다 따로 설정하지 않는다. 발행 링크의 공개 설정과는 별개다.
- 도구는 Catch 조회(설명 포함)와 텍스트·URL 자료 조회다. MCP로 쓰기·JD 요약·다른 사람 자료 조회는 하지 않는다.
- 기간별 사용 횟수는 기록하지 않는다. 회원 기준으로 짧은 시간의 요청 빈도와 응답 크기만 제한한다. 원격 연결 요청은 사용자 컴퓨터가 아니라 Claude 쪽 서버에서 오므로 IP가 아니라 회원 기준으로 센다.

### 회원 탈퇴

- 로그인한 사용자가 확인창으로 탈퇴를 요청하면 즉시 로그인·링크·MCP 접근을 막고 삭제를 실행한다. 삭제가 실패하면 차단을 유지하고 팀이 같은 삭제를 다시 실행해 남은 자료를 확인한다.
- 작성자가 탈퇴하면 그 발행본의 AI 기본 요약과 다른 회원의 JD 요약 결과·실행 입력 사본도 지운다. 다른 회원이 저장한 JD 원본은 남긴다.

## 개발 담당자가 정할 것

- 발행 미리보기 방식.
- 발행본·JD·AI 입력의 상한 값. 정상 링크와 JD가 AI 입력 상한 안에 들도록 맞춘다.
- 결과가 끝났는지 자동으로 확인할지(폴링), 새로고침 버튼으로 확인할지.
- 근거가 틀린 문장을 버린 뒤 남은 내용이 너무 적을 때 빈 결과처럼 처리할지와 그 기준.
- 기본 요약 다시 만들기의 반복 제한과 사용량 집계 방식. 기존 사용량 규칙 안에서 정한다.
- MCP 요청 빈도 제한 값(실제 Claude 호출량을 보고 넉넉하게), 기록 방식, 거부를 돌려주는 형태.

| FR6.1·US6.1(한 장 요약·사이드 패널·질의응답에 JD 반영) | JD 요구사항별 요약 하나. 사이드 패널 없음. 근거에서 자료로 이동 |
| FR6.2·US6.2(질의응답) | 질의응답 없음. 근거 구분·확인 안 된 점 표시는 요약에서 유지 |
| FR6.3(수신자가 특정 서류를 참고에서 제외) | 제외 선택 없음 |

## 검토했지만 채택하지 않은 안

- 고정 발행본 대신 선택한 항목의 현재 내용을 보여 주기: 면접관과 구직자가 같은 내용으로 이야기하기 어렵고, AI 요약이 화면 내용과 어긋나게 된다.
- JD 요약을 자기 발행본에만 허용하기: 면접관이 자기 JD로 대조하는 것이 이 기능의 핵심이고, 구직자 혼자 쓰는 기능은 Claude 연결과 겹친다.
- JD 요약을 화면에서 기다리는 한 번의 요청으로 처리하기: LLM 호출 경로를 새로 만들어야 해 시간 절감이 불확실하고, 기본 요약에는 어차피 백그라운드 경로가 필요하다.
- 링크 중지 때 발행본과 결과를 바로 지우기: 작성자가 보낸 내용을 다시 확인할 수 없고, 만료와의 처리가 갈라진다.
- AI 질의응답·자료 옆 JD 패널: 요약이 핵심 가치를 대부분 보여 주며, 질의응답은 질문마다 실행·검증·한도 처리를 새로 요구한다.
- 비로그인 JD 요약: 계정 없이 결과를 본인에게만 보여 주는 방법과 남용 제한이 따로 필요하다. 비로그인 열람자는 기본 요약을 본다.
- 링크 단위 한도 합산: 늦게 온 면접관이 다른 사람의 사용 때문에 막힐 수 있다. 로그인 필수로 사람별 상한이 이미 있다.
- 근거가 틀린 문장의 링크만 빼고 문장은 남기기: 근거 없는 경력 문장이 비로그인 수신자에게도 보이고, [보안 점검](CatchU_security_checks.md)의 사실 대조 기준과 어긋난다.
- 기능 축소 목록을 미리 정해 두기: 후보가 모두 핵심 경험을 해친다고 보고 두지 않았다. 범위를 유지한다.
- 승인 원본(`aidlc/`)을 직접 고치기: 과거 승인 기록은 소급 수정하지 않는다. 공식 기준은 AI-DLC 재승인으로 바꾼다.

## 결정 이력

- **2026-10-21** — 팀장 결정. 10월 MVP 이후 11월 개발 범위와 프로젝트 목표에서 제외할 12월 기능을 위와 같이 정했다. 2026-10-20에 정한 사전 선택(저장소 등록 단순화, Claude 연결 범위 동의, 웹·Desktop 하나의 원격 연결과 최소 OAuth, 탈퇴 방식과 작성자 탈퇴 시 파생 결과 삭제, 미리보기 방식 위임)을 함께 확정했다. 12월 승인 원본은 보존하고, 11월 전에 AI-DLC로 요구사항부터 다시 진행해 재승인하기로 했다.
