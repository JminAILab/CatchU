# 12월 운영 최소화 기준

결정일: 2026-10-19. 지위: 팀장이 선택한 12월 제품·운영 방향의 후속 기록. [범위 변경표](scope-changes.md)의 관련 동작과 함께 적용하며 승인 원본과 10월 실행 계약은 보존한다.

사용자가 요청한 분석과 자료 제공에 집중하고, 이후 자료 관리는 작성자가 맡는다. 실패 안내·기존 자료 보존·현재 접근 조건·최소 처리 기록을 유지하면서 지속 추적, 자동 실패 재호출, 별도 운영 화면을 줄인다.

## GitHub는 분석 요청 시 확인

분석·재분석 요청을 처리할 때 지원 범위·공개 상태·접근 가능 여부와 기존 연결 계정 조건을 확인한다. 조회 실패를 비공개 확정으로 바꾸지 않는다. 이후 GitHub 공개 상태·접근 가능 여부·새 커밋을 지속 추적하지 않는다. 작성자는 필요할 때 직접 재분석·숨김·공유 중단을 사용하며 이 책임 경계를 안내한다.

FR4.5와 OQ8의 원본 관측은 12월에 이 요청 시 확인으로 한정한다. 이후 서비스 조회마다 외부 GitHub 상태를 재확인하는 조건은 두지 않는다. 서비스가 관리하는 현재 숨김·공개·구직 의사·탈퇴·소속·링크 조건은 각 요청에서 계속 적용한다. 기존 고정 공유본은 자기 링크의 수명·접근 조건을 따른다.

## 자료는 등록할 때 확인

서류·텍스트·외부 URL의 입력·지원 형식·크기 등 등록 조건은 등록 시 확인한다. 이후 내용의 정확성·최신성, 외부 URL의 변경·만료는 작성자가 관리한다. 외부 URL은 주소 보존과 외부 이동용으로 제공하고 본문 수집·변경 추적·도달 가능성의 상시 보장을 추가하지 않는다.

자료 소유권·현재 접근 조건과 안전한 화면 출력은 유지한다. 서비스에서 열람 가능한 PDF는 AI 읽기에 실패해도 등록·공유할 수 있고, 읽지 못한 자료는 AI 참고에서 제외해 그 범위를 알린다. 지원 규격·용량·수량과 URL 등록 검사 범위는 후속 설계에서 정한다.

## 실패는 안내하고 사용자가 다시 요청

분석·재분석·JD·AI 실행이 실패하면 실패를 안내하고 기존 확정 자료를 보존한다. 실패한 실행을 자동 재시작하거나 외부 AI 요청을 자동 반복하지 않고 사용자가 직접 다시 요청한다. 재분석은 성공한 경우에만 해당 저장소 결과를 교체한다. JD·AI 실패로 별도로 허용된 원문 열람을 막지 않는다.

상태·결과 조회 실패와 실행 실패를 구분하고, 실행 실패 뒤 요청이 계속 진행 중에 머물지 않게 한다. 같은 실행의 중복 전달은 새 실행으로 취급하지 않는다. 결과 보존도 숨김·중단·만료·탈퇴 등 기존 접근 조건을 따른다.

정상 실행 안에서 이미 승인된 생성 단계·제목 형식 보정 규칙과 실패 실행의 자동 재호출을 구분한다. 이 결정으로 10월 생성 계약을 소급 수정하지 않는다. DB·큐 재연결, 인프라 자동 장애 조치·노드 복구·자동 배포는 [확정 EKS 전제](delivery-plan.md#확정된-eks-전제와-12월-검증)에 따라 유지한다. worker 임시 결과 보존·재전달·이어 처리 기능은 추가하지 않는다.

## 사용량은 실제 실행 경계에서 집계

분석·JD·AI 실행량과 MCP 요청량의 기간별 상한을 설정으로 관리하고 사용 기록을 영속 보관한다. 실제 실행을 시작할 때 한도를 확인하고 같은 실행의 중복 차감을 막는다.

- 실행을 시작한 뒤 실패한 요청은 사용량에 포함한다. 실행 전 입력·인증·권한 검사에서 거부한 요청은 실행량에 포함하지 않는다.
- 같은 실행의 중복 전달은 한 번만 센다. 사용자가 새로 요청한 실행은 새로 센다.
- 같은 회원의 여러 MCP 연결은 회원 기준으로 합산한다. 같은 링크의 CatchU AI 호출은 웹·MCP 경로와 무관하게 합산한다.
- 기존 결과 조회는 분석·AI 실행량을 사용하지 않는다. MCP 조회는 MCP 요청량에 포함하고 외부 도구 자체 LLM 이용은 CatchU AI와 구분한다.
- AI·MCP 한도 소진이 별도로 허용된 웹·원문 열람까지 막지 않게 한다.

이 실행량·비용 통제와 FR10.3의 채용 안내 계정 쌍 반복 제한은 구분한다. 안내 반복 제한은 기존대로 실제 전달만 집계하고 실패·미전달은 제외한다. 검색 등 그 밖의 요청 제한은 해당 기능의 기준을 따른다. 상한값·기간·적용 단위와 회복 시점은 후속 설계에서 정하며 별도 과금·사용량 관리자 대시보드는 추가하지 않는다.

## 삭제 실패는 운영자가 수동 재처리

삭제 실패 대상과 처리 상태를 다시 찾을 수 있게 기록하고 필요한 접근 중단을 유지한다. 운영자가 수동으로 재처리한 뒤 실제 자료 정리 결과를 확인해야 완료로 안내한다. 실패 기록이나 접근 차단만으로 파기 완료를 표시하지 않는다.

자동 삭제 재시도 체계와 별도 관리자 화면은 추가하지 않는다. 권한 있는 운영자가 실행할 스크립트·명령 등 수단과 기록 항목·보관 기간·조회 권한은 설계에서 정한다. 기존 자료별 파기 시점·법적 예외 확인과 일반 링크 종료 후 자동 파기 범위는 유지한다.

## 문의는 외부 채널 하나로 수동 처리

이용자에게 외부 연락 채널 하나를 안내하고 담당자가 수동 확인·회신한다. 실제 경로로 시험 문의를 받아 확인·회신할 수 있어야 한다. 채널 주소와 담당자는 공개 전에 정하며 서비스 내부 고객센터·문의 티켓·신고함을 추가하지 않는다.

## 채용 안내는 차단과 수동 발송 제한

구직자는 특정 발송자의 새 안내를 차단·해제한다. 제보를 받은 권한 있는 운영자는 확인된 계정의 새 발송을 수동 중단·해제하고 대상·사유·결과를 기록한다. 운영자 제한은 해당 계정이 모든 후보에게 보내는 새 안내에 적용하고 같은 기업의 다른 계정으로 확대하지 않는다.

소속·역할 변경으로 제한을 해제하지 않는다. 운영자가 해제한 뒤에도 현재 발송 자격·구직 의사·수신자 차단·한도를 확인하며 막혔던 안내를 자동 전송하지 않는다. 자동 남용 판정·제재와 기업 전체 일시 중단은 추가하지 않는다. 자료 조회·검색·MCP는 각자의 기존 접근 조건을 유지한다.

## 복원은 스크립트 실행과 수동 확인

운영자가 스크립트로 복원 작업을 실행하고 최종 확인과 실제 서비스 반영은 수동으로 수행한다. 12월 시험은 다른 이름의 DB로 복원해 원본과 대조한 뒤 시험 자원을 정리하는 범위이며 운영 DB 전환 시험은 추가하지 않는다.

[#276의 확정 EKS 구성](https://github.com/JminAILab/CatchU/issues/276)과 [두 API 운영 검증 #280](https://github.com/JminAILab/CatchU/issues/280)에 연결해 12월 8일까지 확인한다. 대조 항목·성공 기준·실행 권한·정리 절차는 시험 전에 정한다. 자원·예산·동결 조건은 [실행 계획](delivery-plan.md#확정된-eks-전제와-12월-검증)을 따른다.

## 결정 이력

- 2026-10-19: 팀장이 위 운영 최소화 방향을 선택했다. 삭제 실패를 수동·자동 중 설계에서 고르던 10월 12일 미결을 수동 재처리로 구체화하고, GitHub 확인 시점·등록 이후 책임·실패 재요청·사용량 집계·문의·발송 제한·반자동 복원 범위를 후속 결정으로 연결했다. 상세 경과는 [계획 결정 이력](decision-history.md)에 남긴다.
