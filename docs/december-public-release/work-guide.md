# CatchU 12월 작업 설명과 포트폴리오 관점

작성일: 2026-10-12. 대상: CatchU 개발팀 4명. 지위: 팀 검토용 초안.

팀원이 12월 공개판에서 맡고 싶은 기능과 경험하고 싶은 설계를 고를 수 있도록 여덟 작업 묶음과 공통 작업을 설명한다. 담당자는 추후 팀 회의에서 정한다. 주담당은 기능의 설계·구현·검증을 이끌고 필요한 부분은 다른 팀원과 협업한다. 묶음의 크기와 실제 intent 개수도 배정·산정 과정에서 조정할 수 있다.

기준은 [12월 실행 계획의 작업 묶음](delivery-plan.md)과 [완료 기준](acceptance.md)이다. 제품 행동은 그 계획에 맞추고, 아래 설계 질문의 답은 담당자가 기존 코드와 연결 상대를 확인하면서 정한다. 승인 원본과 후속 범위의 대응은 [범위 변경표](scope-changes.md)에서 확인한다. 이 설명서의 지위와 읽는 순서는 [공개판 계획 안내](README.md)를 따른다. 기존의 11월 30일 기능 완료·12월 10일 제출은 참고 목표이며, 실제 일정과 개인별 예상량은 팀 회의·담당 배정·산정·진행 상황에 따라 조정한다.

포트폴리오의 중심은 **맡은 문제 → 고려한 선택지 → 선택 이유 → 구현한 부분 → 확인한 결과와 한계**다. 아래 내용은 앞으로 만들 수 있는 경험과 증거이며 이미 달성한 성과가 아니다. 각자 기존 구현·팀 공동 결정·본인 설계와 구현·AI 지원을 구분해 설명한다. 특히 10월부터 이어지는 기능은 기존 기반과 12월에 직접 바꾼 부분을 함께 남긴다.

## 작업을 고를 때 볼 점

| 작업 묶음 | 사용자가 얻는 결과 | 경험할 수 있는 설계 |
|---|---|---|
| 1. 저장소 분석과 Catch 관리 | GitHub 근거를 확인하고 최신 결과로 갱신 | 비동기 처리 상태, 결과 교체와 자료 보존, 분석과 화면의 연결 |
| 2. 주장과 서류 관리 | 경험을 글과 서류로 구성하고 공개 범위를 선택 | 작성 화면의 상태, 자료 관계, 임시 저장과 서버 저장, 공개 표현 |
| 3. 고정 공유본과 링크 | 보낸 당시의 자료를 정해진 조건으로 전달 | 현재 자료와 발행본 분리, 링크 접근 조건, 보관과 파기 |
| 4. 기업 등록과 소속 관리 | 동료와 기업 기능을 이용하고 소속을 관리 | 계정과 조직 관계, 역할별 권한, 자격 변경과 회수 |
| 5. 구직 의사와 기업 검색 | 관련 경험이 있는 후보와 실제 근거를 발견 | 의미 검색, 검색 자료 갱신, 자료 접근 조건, 후보별 결과 구성 |
| 6. 채용 안내와 차단 | 후보에게 채용 경로를 전달하고 연락을 통제 | 여러 조건의 발송 판정, 상태 변화, 운영 조치와 사용자 차단 구분 |
| 7. JD와 AI 자료 검토 | JD와 자료를 비교하고 근거를 확인 | AI 입력 범위, 출처 연결, 참고 자료 선택, 답변의 한계 표현 |
| 8. 제품 MCP | 외부 도구에서 허용 자료를 활용 | 외부 연결 수명, 공통 기능 재사용, 경로별 자격, 실제 도구 연동 |

관심 있는 기능과 함께 자신이 설계해 보고 싶은 쟁점을 고른다. 기존 경험을 살릴 부분과 새로 배울 부분, 필요한 협업을 회의에서 같이 이야기한다. 기능의 이름이나 기술 수로 포트폴리오의 우열을 정하지 않는다. 같은 기능에서도 화면 흐름·자료 구조·권한·검증 중 본인이 맡은 부분에 따라 설명할 경험이 달라진다.

## 1 저장소 분석과 Catch 관리

취준생이 공개 저장소의 개발 경험을 근거와 함께 확인하고, 새 커밋 이후 직접 재분석을 요청하는 기능이다. 10월 분석 기반을 확인한 뒤 12월의 재분석·교체 동작을 확장한다.

- **만들 범위:** 분석 진행·완료·실패와 결과 재접근, Catch 숨김, 저장소별 수동 재분석. 진행 중·실패 시 기존 결과와 주장 연결을 유지하고, 성공한 저장소의 Catch만 전체 교체한다. 새 Catch의 초기 상태는 기존처럼 숨김으로 한다.
- **직접 설계할 부분:** 새 결과를 언제 유효한 결과로 전환할지, 교체 중인 결과와 현재 사용 중인 결과를 어떻게 구분할지, 상태 조회 실패를 분석 실패와 어떻게 구분해 보여줄지 정한다. 횟수·비용 한도도 관련 기준과 맞춘다.
- **연결할 작업:** 2와 주장 문구 보존·Catch 재선택을 맞추고 5·8의 현재 자료 조회에 교체 결과를 반영한다. 3의 발행 공유본은 독립적으로 유지한다. 각 영역 전체를 혼자 구현하는 범위는 아니다.
- **포트폴리오 주제:** 비동기 분석 결과를 갱신하면서 기존 사용자의 자료를 보존하는 설계. 본인이 개선한 분석 처리·자료 전환·화면 상태 중 실제 기여를 중심으로 설명한다.
- **남길 증거:** 실제 분석 성공·실패의 상태 흐름, 재분석 전후 Catch와 주장 연결, 실패 시 보존 결과, 다른 저장소와 발행본이 유지되는 확인 사례. 기존 Catch 근거 링크·기여 귀속 기준의 표본 확인을 공통 검증에 연결한다. 분석 결과를 미리 넣은 시험과 실제 분석 실행을 구분한다.
- **이번에 이연하거나 제외한 것:** 비공개 저장소, 커밋 감지 자동 재분석, 기존 Catch와 새 Catch의 자동 대응, 별도 상단 알림·읽음 관리.

## 2 주장과 서류 관리

취준생이 Catch를 선택해 자기 경험을 글로 설명하고, 지원에 사용할 서류를 등록하는 기능이다. 작성한 자료가 공유·검색·AI·MCP에 쓰이므로 편집 화면과 자료 상태를 함께 다룬다.

- **만들 범위:** 복수 주장 작성·수정, 제목·본문·Catch 연결, 새 글의 클라이언트 임시 저장, 자기소개서 텍스트·이력서 PDF·포트폴리오 PDF 또는 URL 등록. 공개·비공개 설정과 공개 주장 중 대표 하나의 선택·공개 열람을 포함한다.
- **직접 설계할 부분:** 임시 작성과 서버 등록의 경계, 재분석 후 글은 남고 Catch를 다시 골라야 하는 상태, 서류와 주장의 관계, 대표 지정으로 보이는 자료가 달라짐을 설명하는 화면을 설계한다. 임시 저장 수단·수명과 로그아웃·계정 전환·탈퇴 시 브라우저 임시 글의 표시·정리, 파일 규격은 후속 결정 대상이다.
- **연결할 작업:** 1의 Catch 조회, 3의 발행 자료 선택, 5의 공개 자료·대표 여부, 7·8의 선택 서류 조회. 서류 등록은 재분석 기능 전체의 완료를 기다리지 않고 설계·개발할 수 있다.
- **포트폴리오 주제:** 편집 중 상태와 등록 자료를 구분하고, 자료 변경 이후에도 사용자가 작업을 이어가도록 설계한 경험. 화면 상태와 서버의 자료 조건을 일치시키는 판단을 설명할 수 있다.
- **남길 증거:** 작성·저장·수정·실패 흐름, 새 글 임시 저장과 등록 글 보존의 차이, Catch 재선택 화면, 대표 변경 전후 노출 범위, 선택한 서류만 이용 경로로 전달되는 확인 사례.
- **이번에 이연하거나 제외한 것:** 새 글의 서버 초안·기기 간 동기화, 외부 URL 본문 수집, 주장 복제 등의 비필수 편의. 서류를 종류별 한 벌로 제한하는 안은 채택하지 않았다.

## 3 고정 공유본과 링크

취준생이 선택한 자료를 발행 당시의 내용으로 전달하는 기능이다. 이후 현재 주장을 수정하거나 저장소를 재분석해도 받은 사람에게 전달한 내용은 유지한다.

- **만들 범위:** 공유본별 대표 주장 하나와 선택적 추가 주장·서류 선택, 미리보기·고정본 발행, 수신자의 요약에서 주장·Catch 근거 읽기, 비밀번호 등 링크 조건, 유효 링크 연장·종료·삭제와 작성자 보관 후 파기. 연장은 주소·고정 내용을 유지한다. 만료·중단된 링크는 다시 활성화하지 않고 새로 발행한다.
- **직접 설계할 부분:** 현재 자료와 고정본을 어떤 관계로 저장할지, 발행 시 선택한 내용의 일관성을 어떻게 보장할지, 수신자 접근 종료와 작성자 보관·파기를 어떻게 구분할지 정한다. 저장 방식과 유효·보관 기간, 연장 횟수·최대 기간·조작 방식은 미리 확정하지 않는다.
- **연결할 작업:** 2의 선택 자료를 받아 7의 웹 검토와 8의 공유본 MCP에 제공한다. 일반 링크 수명과 회원 탈퇴로 인한 전체 접근 중단·파기를 공통 탈퇴 작업과 맞춘다.
- **포트폴리오 주제:** 계속 바뀌는 원본과 이미 전달한 자료의 수명을 분리한 설계. 자료 보존·접근 권한·저장 비용 사이에서 실제 선택한 구조와 이유를 설명한다.
- **남길 증거:** 요약에서 주장·Catch 근거로 읽는 흐름, 발행 전후 자료 비교, 원본 수정·재분석·GitHub 비공개 전환 후 발행본 유지, 미선택 자료 제외, 유효 링크 연장 시 주소·내용 유지와 만료 시점 변경, 만료·중단 링크의 연장 거부와 작성자 보관·최종 파기 사례.
- **이번에 이연하거나 제외한 것:** 자동 외부 페이지 복제. 발행 시 만료일 직접 선택이나 발행 후 비밀번호 변경을 새 필수로 추가하지 않는다. 종료 링크 재활성화 금지는 위에서 유지하는 규칙이다.

## 4 기업 등록과 소속 관리

기업의 HR·기술 면접관이 소속을 등록하고 동료와 함께 기업 기능을 이용하는 기반이다. 개인 계정과 기업 소속을 구분해 한 사람의 변경이 다른 사람의 개인 자료에 영향을 주지 않게 한다.

- **만들 범위:** 기업 직접 등록, 소속 신청·승인·해제, 관리자·회원 두 역할, 관리자 인계와 기업 이용 종료. 두 역할 모두 검토·검색·안내를 이용하고 관리자는 소속·역할 관리를 추가로 맡는다.
- **직접 설계할 부분:** 개인 계정과 소속의 관계, 역할별 허용 작업, 소속 해제 이후 자격 회수, 마지막 관리자의 인계·기업 종료 흐름을 정한다. 이미 열린 화면에서 권한이 바뀐 경우의 새 요청 처리도 맞춘다.
- **연결할 작업:** 기존 로그인·회원 식별을 사용하고 5·6·8에 현재 기업 자격을 제공한다. 기업 이용 종료는 이 묶음에서 구현하고, 회원 탈퇴 전체 흐름과 연결한다.
- **포트폴리오 주제:** 조직 소속과 역할을 모델링하고 여러 기능에 일관된 권한 기준을 제공한 경험. 역할 수를 두 개로 정한 제품 제약 안에서 상태와 책임을 설명한다.
- **남길 증거:** 역할별 허용 작업 표, 신청·승인·해제 흐름, 자격 상실 후 검색·발송·MCP 새 접근 거부, 관리자 인계와 기업 종료가 다른 회원의 개인 자료에 미치는 영향 확인.
- **이번에 이연하거나 제외한 것:** 세분화된 직무 역할, 사용자 정의 권한, 기업 전체에 대한 운영상 일시 중단. 직접 등록과 소속 승인만으로 실제 재직 확인을 보장하지 않는다.

## 5 구직 의사와 기업 검색

기업 회원이 찾는 경험을 자연어로 입력하고, 관련 주장을 가진 후보와 실제 Catch 근거를 확인하는 기능이다. 구직자는 하나의 설정으로 검색 참여와 새 채용 안내 수신을 선택한다.

- **만들 범위:** 기본 OFF인 구직 의사 설정, 공개 주장·허용 Catch의 벡터 검색, 후보별 결과·근거 표시, 기업의 추가 주장 열람 조건. 구직 의사 OFF·비공개·숨김·재분석·탈퇴에 따른 자료 변경도 반영한다.
- **직접 설계할 부분:** 무엇을 검색 자료로 만들지, 임베딩을 언제 생성·갱신할지, 검색 결과와 원문 조회에 현재 접근 조건을 어떻게 적용할지, 후보별 중복을 어떻게 정리할지 결정한다. 저장소·모델·정렬 방식은 선택 이유와 일정·비용 제약을 비교해 정한다.
- **연결할 작업:** 2의 현재 공개 자료와 4의 기업 자격을 사용한다. 6은 현재 구직 의사를 확인하고, 8은 같은 검색·근거 조회를 사용한다. 모든 서류나 고정 공유본의 완성을 기다리지 않는다.
- **포트폴리오 주제:** 의미 검색을 실제 서비스의 자료 공개·변경 조건과 결합한 경험. 검색 결과가 생성되는 과정과 현재 허용 자료만 제공하는 방법을 설명한다.
- **남길 증거:** 소수 검색어의 후보·원문 근거 연결, 후보별 묶음, 자료 변경·구직 의사 OFF 전후 검색과 추가 주장 조회, 웹과 MCP의 같은 조건 적용. 시험한 자료와 검색어의 범위를 밝힌다.
- **이번에 이연하거나 제외한 것:** 구조화 필터, 필터용 기술 분류, 후보 평가문·역량 점수·매칭 퍼센트, 별도 품질 평가셋·모델 비교·반복 순위 최적화. 포트폴리오를 위해 검색 정확도 수치를 새 완료 기준으로 추가하지 않는다.

## 6 채용 안내와 차단

기업이 후보에게 포지션과 외부 지원·연락 경로를 전달하고, 구직자가 안내를 읽고 이동하거나 특정 발송자를 차단하는 기능이다.

- **만들 범위:** 제목(포지션)·본문(업무·요구사항·안내 사유)·외부 지원/연락 경로를 기본안으로 한 안내 발송, 받은 안내와 본인의 발송 목록·상세, 특정 발송자 차단·해제, 운영자의 계정별 발송 중단·해제와 최소 조치 기록.
- **직접 설계할 부분:** 단순 폼의 입력항목·표현·배치·조작 흐름은 고정하지 않고 담당자의 개선 의견을 적극 반영해 수정한다. 실제 발송 시 기업 자격·구직 의사·차단·운영 제한·반복 한도를 확인하는 위치와 조건을 정한다. 구직 의사 OFF와 탈퇴가 기존 안내 열람에 미치는 차이, 실패 결과, 운영 조치의 실행 수단도 설계한다. 별도 공고/JD 관리 기능은 선행으로 요구하지 않는다.
- **연결할 작업:** 4의 기업 자격과 5의 구직 의사·후보 식별을 사용한다. 시험 후보로 먼저 개발하고 실제 검색부터 외부 이동까지 연결한다. 공통 문의·운영 담당은 운영 자격과 담당을 정하고, 이 묶음은 발송 중단 동작을 구현한다.
- **포트폴리오 주제:** 사용자의 수신 선택과 서비스 운영 제한을 함께 반영하는 업무 규칙 설계. 서로 다른 조건의 적용 범위와 해제 이후 동작을 설명할 수 있다.
- **남길 증거:** 정상 발송·열람·외부 이동, 오래된 검색 화면에서 현재 조건으로 발송을 거부하는 사례, 차단·운영 제한·해제 조합, 구직자 탈퇴 후 기업의 기존 안내 원문 새 조회 거부.
- **이번에 이연하거나 제외한 것:** 서비스 안의 수락·거절·DM·별도 구직자 연락처 전달, 발송 후 수정·철회, 읽음 추적·지원 현황 관리, 기업 전체 차단·운영 중단. 외부 이동은 실제 지원 완료나 연락 성공으로 기록하지 않는다.

## 7 JD와 AI 자료 검토

수신자가 JD를 입력하고 현재 자료와 관련된 내용을 패널로 확인하며, 질문에 대한 근거와 출처를 살펴보는 기능이다. AI가 허용 자료에서 관련 Catch를 근거 후보로 제시한다.

- **만들 범위:** JD 입력·요약·현재 자료 패널, 질의응답, Catch 근거 후보·출처, 서류별 AI 참고 선택. 기록 사실·작성자 설명·AI 해석과 확인되지 않은 부분을 구분한다.
- **직접 설계할 부분:** 공유 범위와 참고 선택으로 AI 입력을 구성하는 방법, 읽기 불가·외부 URL·제외 서류 처리, 원문과 답변 근거의 연결, 필요한 임시 처리·재사용·수명을 정한다. 생성 결과가 없거나 실패해도 허용 원문을 읽는 경로를 유지한다.
- **연결할 작업:** 3의 공유 자료부터 연결하고 기업의 추가 자료 검토는 4·5의 자격·자료 조건도 적용한다. 유효한 웹 링크의 비로그인 검토와 기업 소속이 필요한 공유본 MCP를 구분한다.
- **포트폴리오 주제:** 허용 자료를 바탕으로 답변을 만들고 사용자가 출처와 한계를 확인할 수 있도록 구성한 경험. 프롬프트·자료 처리·화면 중 본인이 내린 판단을 구체적으로 설명한다.
- **남길 증거:** 근거가 있는 질문·없는 질문·참고 제외 서류가 있는 경우의 소수 사례, 사용한 자료 범위·출처·확인 공백 표시. 실제 검증 범위에 맞춰 답변의 한계를 설명한다.
- **이번에 이연하거나 제외한 것:** 저장된 검토 이력·재방문 이어보기, 근거 연결 자동 수정, 역량 점수, 별도 평가셋·점수 평가·반복 문장 개선. 검토 이력 이연을 모든 임시 저장과 외부 제공자의 보관이 없다는 뜻으로 해석하지 않는다.

## 8 제품 MCP

사용자가 외부 AI 도구에서 CatchU의 본인 자료를 활용하거나, 기업 회원 자격으로 받은 공유본과 후보 검색을 이용하는 기능이다. 12월에는 외부 도구 한 종류를 선정해 세 흐름 모두 연결한다.

- **만들 범위:** 연결 범위 안내·명시 승인·해제, 본인 자료 조회, 받은 공유본 검토, 후보 검색. 본인 자료는 일반 구직 회원도 이용하고, 나머지 두 흐름은 승인된 기업 회원만 이용한다.
- **직접 설계할 부분:** 연결 인증·승인 범위·해제, 웹과 공통 자료·권한 처리의 경계, 외부 요청·응답 형식, 사용자별 요청 합산과 서비스 AI 호출 한도의 구분을 정한다. 지원 도구·판본·환경을 실제로 확인한다.
- **연결할 작업:** 2의 최소 본인 자료부터 일찍 연결하고, 3·4의 공유본과 기업 자격, 4·5의 후보 검색으로 넓힌다. 6의 안내 발송이나 7의 JD 패널 완성을 기다릴 필요는 없다.
- **포트폴리오 주제:** 기존 서비스 기능을 외부 도구에 제공하면서 승인·권한·연결 수명을 일관되게 처리한 경험. 실제 연결 과정의 제약과 해결한 문제를 설명한다.
- **남길 증거:** 선정 도구의 판본·환경, 세 흐름 각각의 실제 자료·출처 반환, 연결 해제·기업 자격 상실 후 접근 거부, 여러 연결의 한도 합산 결과. 한 번의 도구 호출 성공과 전체 흐름 검증을 구분한다.
- **이번에 이연하거나 제외한 것:** 다른 도구 호환성 확대, 주장 쓰기·수정·채용 안내 발송, 외부 LLM 대화 수집. 개발에 사용하는 브라우저 MCP와 제품 MCP의 구현 기여를 구분한다.

## 함께 맡을 공통 작업

공통 작업에도 별도 구현·검증 시간과 책임이 필요하다. 기능 담당과 나눠 진행하며, 어느 사람에게 배정할지는 팀 회의에서 정한다.

### 회원 탈퇴와 자료 수명

회원 탈퇴 요청부터 로그인·MCP·링크 등 새 접근 중단, 자료별 파기, 실패한 삭제 작업의 확인·마무리까지 연결한다. 각 기능은 자기 자료의 처리를 구현하고 공통 담당은 전체 흐름의 완료를 확인한다. 실제 파기·보관 예외 기준은 실행 계획의 후속 확인 사항을 따른다.

- **설계 경험:** 여러 기능에 걸친 자료 수명과 부분 실패 처리. 별도 관리자 화면은 필수로 요구하지 않으며 수동·자동 처리와 필요한 실행 수단은 담당자가 설계한다.
- **남길 증거:** 자료·저장 위치별 처리 목록, 탈퇴 전후 접근 확인, 일부 삭제 실패 후 마무리 결과, 재가입 시 이전 권한·자료가 자동 복원되지 않는 사례.
- **설명할 한계:** 접근 차단과 실제 파기를 구분하고, 확인하지 않은 법적 준수나 외부 도구의 데이터 회수를 성과로 주장하지 않는다.

### 요청 한도와 비용 통제

분석·검색·안내·AI·MCP가 어떤 단위로 요청을 세고 제한할지 맞춘다. 회원의 여러 MCP 연결과 같은 링크의 CatchU AI 호출처럼 경로를 넘어 합산해야 하는 기준을 구현한다. 한도값과 실제 집계 방식은 관련 설계에서 정한다.

- **설계 경험:** 사용자·링크·처리 종류별 제한을 구분하고 여러 진입 경로에 적용하는 공통 기능 설계.
- **남길 증거:** 허용·한도 초과·회복 사례, 같은 사용자의 여러 연결 합산, 한 경로의 한도 소진이 다른 허용 조회를 불필요하게 막지 않는 결과.
- **설명할 한계:** 실제 확인한 실행 환경과 범위를 밝힌다. 측정하지 않은 비용 절감률·처리량·다중 서버 지원을 성과로 쓰지 않는다.

### 문의 경로와 운영 준비

이용자가 문제를 알릴 경로와 확인·회신 담당, 계정별 발송 중단을 실행할 담당·자격을 정한다. 발송 중단 기능은 6과 연결한다. 별도 고객센터는 이연하며, 관리자 화면은 필수로 요구하지 않고 필요한 실행 수단은 담당자가 설계한다.

- **설계 경험:** 공개 서비스의 문제 접수부터 실제 조치까지 책임과 절차를 연결하는 경험.
- **남길 증거:** 시험 문의의 접수·회신, 권한 있는 담당자의 조치와 실패 결과, 이용자 안내가 실제 처리와 일치하는 확인 사례.
- **설명할 한계:** 문의 채널 안내만으로 운영 체계 전체를 구축했다고 표현하지 않는다. 실제 처리한 부분과 맡은 책임을 밝힌다.

### 배포와 통합 검증

10월 AWS 기반을 재사용하고 신규 기능의 설정·자료 구조·외부 연결 변경을 반영한다. MCP 첫 실제 연결 전에 필요한 시험 환경·최소 변경분을 준비한다. 실제 사용자 흐름과 MCP 세 흐름, 12월로 이월한 백업 복원 시험을 확인하고, 기존 Catch 품질 표본·사용자 직접 사용 확인·제출과 시연 준비의 책임·결과를 연결한다. 외부 처리 조건은 분석·JD 등 AI 호출 기능 담당과 MCP 담당이 각각 근거를 준비한다.

- **설계 경험:** 기존 환경에 기능을 추가하면서 변경 영향을 확인하고 복원 가능성을 실제 시험하는 경험. 복원 대상·환경·방법·성공 기준은 후속 설계에서 정한다.
- **남길 증거:** 10월 기반과 본인의 변경분, 판본·환경별 실제 연결 결과, 백업 복원 시험의 기대·실제 결과와 남은 문제. 유효한 기능별 검증 기록은 재사용한다.
- **설명할 한계:** 새 인프라 전체 구축·무중단 운영·자동 장애 복구를 추가 목표로 삼지 않는다. 실제 측정한 경우에만 복원 시간 등의 수치를 설명한다.

여유가 있을 때의 선택 작업으로 **개발 전용 MCP**를 추가한다. 반복 시험의 준비·실행·결과 확인을 묶는 도구이며, 실제 착수할 때 담당자가 필요와 구현·유지 비용을 비교하고 설계한다. 포트폴리오에는 실제로 자동화한 범위와 검증 결과를 남기며, 구축 여부를 공개판 완료 조건으로 삼지 않는다.

기존 설계 문서·이슈·PR·검증 기록에서 다음 내용을 찾을 수 있게 연결한다. 포트폴리오용으로 별도의 긴 보고서를 매번 쓰는 절차는 추가하지 않는다.

| 기록 | 남길 내용 |
|---|---|
| 맡은 문제와 범위 | 사용자에게 필요한 행동, 10월의 기존 기반, 12월에 본인이 맡은 변경, 협업자와의 경계 |
| 실제 설계 판단 | 선택이 필요했던 쟁점, 검토한 대안, 선택 이유와 남은 제약. 이미 정해진 제품 결정을 본인의 새 설계 결정으로 쓰지 않음 |
| 구현 근거 | 본인의 코드·화면·계약 변경과 관련 PR, 연결 상대와 합의한 부분. AI가 작성한 내용 중 본인이 검토·수정·확인한 부분 |
| 검증 결과 | 환경·판본·시험 자료 범위, 기대·실제 결과, 실제 연결과 모의 처리, 미실행·남은 문제. 필요한 화면이나 실행 결과만 연결 |
| 결과 해석 | 구현·검증한 사실과 아직 측정하지 않은 효과 구분. 성능·비용·품질 수치는 측정 조건과 비교 기준이 있을 때만 사용 |

예를 들어 기업 소속 작업을 맡았다면, “역할 관리 구현”에서 한 걸음 더 나아가 **소속 승인·해제와 두 역할을 어떻게 모델링했는지, 열린 화면에서 자격이 바뀌었을 때 새 검색·발송·MCP 요청에 어떻게 반영했는지, 어떤 사례로 확인했는지**를 설명할 수 있다. 이런 설명을 뒷받침하는 실제 기록이 쌓인 뒤 포트폴리오의 성과 문장으로 옮긴다.

자료와 로그는 [저장소의 자료 취급 기준](../CatchU_coding_procedures.md#자료와-실행-로그)을 따른다. 포트폴리오에 공개할 화면·응답은 합성·비식별 자료를 사용하고 인증정보·공유 비밀번호·사용자 원문은 싣지 않는다. 서비스 검증에 사용한 자료를 외부 공개할 수 있는지 별도로 확인한다.

검색·JD 품질 확인은 합의한 소수 사례 수준을 유지한다. 포트폴리오를 이유로 새 평가셋·장기 부하시험·추가 플랫폼을 필수로 만들지 않는다. 이미 필요한 개발과 검증에서 얻는 증거를 정리한다.

## 팀 회의에서 이어갈 순서

1. 각자 관심 있는 기능과 경험해 보고 싶은 설계, 현재 익숙한 부분과 필요한 도움을 이야기한다.
2. 기능 주담당·구현 협업자·연결 검토자와 공통 작업 책임을 배정한다. 공통 검증의 사용자 확인·제출/시연 준비와 각 AI·MCP 기능의 외부 처리 조건 확인도 연결한다. 모든 계층을 한 사람이 혼자 구현하도록 강제하지 않는다.
3. 필요한 계약과 실제 구현 선행을 확인하고, 설계·학습·검토·수정·검증 시간을 포함해 작업량을 산정한다.
4. 설계를 희망하는 팀원은 AI-DLC 2.11.0 환경 확인 후 담당 기능의 별도 intent로 진행한다. 세부 기술 선택은 그 과정에서 결정한다.

현재는 담당 배정 전 설명 자료를 준비하는 단계다. 이 문서의 검토와 실제 배정·intent 생성·기능 개발은 각각 구분한다. 포트폴리오 주제 선택으로 공개판의 범위나 완료 기준을 바꾸지 않는다.
