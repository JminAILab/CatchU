# 12월 공개판 완료 기준과 검증 증거

지위: **팀 검토용 실행 초안**. 기준일: 2026-10-19. 아래는 팀장과 합의한 기능 범위를 완료 결과로 정리한 것이며, 아직 구현·검사·배포가 끝났다는 보고가 아니다. 적용 관계는 [범위와 변경 결정](scope-changes.md), 작업·미결·관리 일정은 [실행 계획](delivery-plan.md), 과거 승인 원본은 [12월 승인 문서 안내](../CatchU_12월_승인문서_안내.md)를 따른다.

목표는 불특정 사용자가 직접 이용하는 공개 서비스다. 취준생의 작성·공유, HR의 발견·채용 안내, HR·기술 면접관의 JD·근거 검토와 **제품 MCP 세 흐름 모두**를 확인한다. 일정은 [실행 계획](delivery-plan.md)의 단계별 시작 조건과 최신 고정점을 따른다. 11월 30일 핵심 흐름 외부 확인, 12월 8일까지 두 API·복원 검증, 12월 9일 00:00 변경 동결, 12월 10일 제출을 기준으로 기능별 중간 배치를 조정한다. 완료 여부는 날짜가 아니라 아래 결과와 증거로 판단한다.

이 문서는 승인 수용 기준을 모두 다시 적지 않는다. 공개판 구현 대상 기능은 [범위 변경표](scope-changes.md)가 변경·축소·이연·제외로 적은 부분을 뺀 승인 요구사항·사용자 스토리의 수용 기준이 그대로 완료 조건이다. 여기서는 후속 결정으로 달라진 부분, 기능 사이의 연결, 검증 수준과 증거를 적는다. 이 문서에 없다는 이유로 승인 원본의 조건을 빼지 않으며, 팀 논의 보류로 둔 항목은 결정 결과를 따른다.

2026-10-19의 [운영 최소화](operations.md)는 자료의 지속 추적 대신 요청·등록 시 확인과 사용자 관리를 적용하고, 실패한 실행의 자동 재호출 없이 기존 자료 보존·수동 조치를 검증한다. 서비스의 현재 권한 검사와 합의한 전체 기능·자료 형식·참조 범위는 유지한다.

## 확인 수준과 기록 방식

| 확인 종류 | 입증하는 것 | 입증하지 않는 것 |
|---|---|---|
| 모의 응답·준비한 시험 자료·로컬 검사 | 해당 구현의 준비·제한된 처리 결과 | 실제 분석·외부 도구 호환·배포 환경의 통합 완료 |
| 실제 API·DB·필요 외부 서비스의 흐름 | 실제 생성·저장·조회·권한·실패 처리가 연결된 범위 | 실행하지 않은 자료 형식·도구·환경까지의 동작 |
| 배포 시험 환경·실제 외부 도구 | 지정 판본·환경에서 확인한 공개 경로와 MCP 흐름 | 모든 도구 호환·일반적인 품질·운영 안정성 전체 |
| 소수 사례 직접 품질 확인 | 해당 검색어·질문에서 관련 근거·출처·확인 한계를 확인 | 정량 정확도·최적 순위·전체 질문의 답변 품질 |

각 기능은 정상·거부·실패 사례를 기대 결과와 대조한다. 환경·판본·시점·사례·기대/실제 결과·실패/미실행·남은 문제·확인 담당을 관련 PR 또는 이슈 한 곳에 남기고 다른 문서는 연결한다. 비밀값·개인정보 원문을 불필요하게 복사하지 않는다. 유효한 기존 검증 결과를 재사용하고 변경·영향·미검증 부분을 추가 확인한다. 문서 승인·이슈 종료·헬스체크만으로 실제 완료를 대체하지 않는다.

## 1. 저장소 분석·재분석과 작성 자료

| 확인 대상 | 완료 결과 |
|---|---|
| 시작 흐름 | 신규 회원이 Google로 로그인하고 GitHub 계정 연결과 분석 동의를 거쳐 저장소 선택에 도달. 로그인·연결 거부·취소·실패나 동의 전 상태에서는 분석을 시작하지 않고 성공으로 표시하지 않음. 미지원 저장소는 실행 전에 이유를 안내 |
| 최초 분석 | 회원이 연결한 GitHub 계정이 소유하거나 커밋한 지원 범위의 공개 저장소를 직접 선택해 실제 분석을 요청하고 Catch 설명·GitHub 근거를 확인. 계정 관계를 충족하지 않는 저장소는 실행 전에 이유를 안내하고 분석하지 않음. 기록 사실·작성자 설명·AI 해석을 구분 |
| GitHub 확인과 이후 관리 | 분석·재분석 요청 시 GitHub 연결·저장소 지원 범위·공개 여부·계정 관계를 확인. 이후 공개 여부·접근 가능 여부·새 커밋을 지속 추적하지 않고 사용자가 재분석·숨김·공유 중단으로 관리. 서비스의 현재 공개·숨김·소유권·접근 조건은 각 요청에 적용 |
| 분석 상태 | 분석 목록에서 진행·완료·실패를 확인하고 결과 또는 실패 안내로 다시 접근. 조회 실패를 분석 실패로 표시하지 않고 결과 열람으로 재분석하지 않음 |
| 수동 재분석 | 진행 중·실패 시 기존 Catch와 주장 연결 유지. 성공했을 때만 해당 저장소의 Catch 전체를 교체. 다른 저장소 결과와 발행 공유본 내용은 유지 |
| 새 Catch 초기 상태 | 새 Catch는 기존처럼 숨김 상태로 시작하며 재분석 결과도 동일하게 적용. 주장에 연결한 뒤에도 Catch 숨김 등 현재 이용 조건을 적용 |
| 주장 보존·재선택 | 성공 후에도 등록 주장의 제목·본문은 서버에 남고 수정 화면에서 새 Catch 선택 가능. 자동 연결 대응은 요구하지 않음 |
| 사용 가능한 Catch가 없는 주장 | 서버에 제목·본문을 보존하고 새 Catch 연결 전까지 현재 공개·검색·AI 참고·새 발행에서 제외. 연결 후에도 현재 이용 조건을 적용하며 다른 저장소의 유효한 Catch가 남은 경우는 구분 |
| 작성·임시 저장 | 제목·본문·Catch를 연결한 복수 주장 등록·수정. 새 미등록 글만 클라이언트 임시 저장하고 기존 등록 자료와 구분. 서버 초안·기기 간 동기화는 요구하지 않음 |
| 서류 등록 | 자기소개서 텍스트, 이력서 PDF, 포트폴리오 PDF 또는 외부 URL을 지원하고 공유본별로 선택. 종류별 한 벌 제한은 채택하지 않음 |
| URL·읽기 조건 | 외부 URL은 목적지로 이동해 읽고 본문 수집·고정·AI 참고를 하지 않음. 정상 열람 가능 PDF는 AI가 읽지 못해도 등록·열람·공유하고 AI 참고 불가를 구분. OCR·별도 다운로드 기능은 추가하지 않음 |
| 등록 이후 자료 관리 | 등록 시 필수 입력·허용 형식 등 조건을 확인하고 이후 내용의 정확성·최신성과 외부 URL 변경·만료는 작성자가 관리. 주기적 유효성 점검·외부 자료 변경 감지를 추가하지 않음 |
| 실패 표시 | 분석·저장 실패를 성공으로 표시하지 않음. 분석·재분석 실패는 안내하고 기존 자료를 보존하며 사용자가 직접 재요청. 실패한 실행을 자동 재시작하거나 외부 API를 자동 재호출하지 않음. 미리 준비한 Catch로 후속 기능만 확인한 결과와 실제 분석 결과를 구분 |

비공개 저장소 분석, 새 커밋에 따른 자동 분석, Catch 개별 원본 삭제, 별도 상단 알림·읽음·중복 알림 관리는 이번 완료 조건에 넣지 않는다. Catch 숨김과 현재 자료의 접근 조건은 유지한다. 재분석 결과의 저장·전환 방식, 지원 범위·규모·횟수·비용은 설계에서 정한다. 실패한 실행의 자동 재호출 금지는 한 실행 안에서 이미 승인된 생성 단계·제목 보정 규칙을 소급 삭제하지 않는다. 인프라 장애 조치 후 DB·큐 재연결과도 구분한다.

## 2. 공개 주장·고정 공유본·링크

| 확인 대상 | 완료 결과 |
|---|---|
| 공개와 대표 | 주장 공개·비공개를 선택하고 공개 주장 하나를 프로필 대표로 지정. 대표의 제목·본문·허용 Catch는 전체 공개하며 그 차이를 작성자에게 안내 |
| 자료 선택·발행 | 공유본별 대표 주장 하나와 선택적인 추가 주장·서류를 고르고 미리 본 뒤 고정 공유본을 발행. 유효한 링크 수신자는 선택 자료만 읽고 미포함 자료는 새로 노출되지 않음 |
| 요약에서 근거 읽기 | 유효 링크 수신자가 짧은 요약에서 설명·주장·Catch 근거로 들어갈 수 있음. 노출 수·길이·배치·생성 방식은 OQ1의 확정값으로 확인하며 새 수치 기준을 만들지 않음 |
| 내용 고정 | 이후 현재 자료 수정·재분석·숨김·원본 삭제·GitHub 저장소 비공개 전환과 독립적으로 발행 당시 주장·Catch·텍스트/PDF·URL 주소를 유지. 링크의 독립 접근 조건은 계속 적용. 새 발행에는 숨긴 Catch를 포함하지 않음 |
| 링크 접근 | 비밀번호·만료·중단·직접 삭제 등 적용 조건에 맞는 허용·거부. 만료·중단 링크는 재활성화하지 않고 새로 발행 |
| 유효 링크 연장 | 작성자가 아직 유효하고 중단·삭제되지 않은 링크를 만료 전에 연장 가능. 주소·고정 내용은 유지하고 변경된 만료 시점을 표시. 만료·중단·삭제된 링크는 연장으로 되살릴 수 없음 |
| 작성자 보관·파기 | 만료·중단 뒤 정한 기간 작성자가 확인·직접 삭제할 수 있고 보관 종료를 안내한 뒤 자동 파기. 탈퇴에는 일반 보관 기간을 자동 적용하지 않음 |
| 실제 전체 연결 | 실제 저장소 분석→자료 저장·선택→공유본 발행→수신자 열람을 확인. 발행 실패는 성공으로 표시하지 않음 |

10월 링크의 현재 권한 반영과 12월 고정 공유본을 혼동하지 않는다. 10월 링크 자동 이관을 추가하지 않고, 배포 준비에서 개발·시험 데이터 초기화 대상을 확인한다. 링크 기간·보관 기간·연장 횟수·최대 기간·조작 방식·파일 지원값은 후속 결정으로 검증값을 정한다. 발행 시 만료일 직접 선택·발행 후 비밀번호 변경은 이 연장 기능의 필수 선행으로 추가하지 않는다.

## 3. 기업 자격·구직 의사·검색

| 확인 대상 | 완료 결과 |
|---|---|
| 기업 등록·소속 | 회원의 직접 기업 등록과 소속 신청, 관리자의 승인·해제·역할 관리. 기업 관리자와 승인된 기업 일반 회원 모두 검토·검색·채용 안내 이용 |
| 마지막 관리자 유지 | 기업 이용을 계속하는 동안 다른 관리자 확보 전 마지막 관리자의 강등·일반 소속 해제를 막음. 기업 종료 후 탈퇴 경로와 구분 |
| 권한 구분 | 기업 미소속·미승인 회원에게 기업 검색 권한을 주지 않음. 소속 해제·탈퇴·기업 종료 후 해당 자격의 새 접근 거부 |
| 구직 의사 | 기본 OFF인 스위치 하나로 검색 참여·새 안내 수신을 함께 제어하고 ON의 의미 안내. 별도 수신 설정·기업 열람 허용 스위치는 두지 않음 |
| 추가 주장 열람 | ON인 회원의 공개 주장·허용 Catch를 기업 경로에서 무료 제공. 열람 전 제목과 ‘무료로 열람’ 안내, 열람 후 본문·연결된 허용 Catch 제공을 확인하며 구체 화면·조작 방식은 후속 설계에서 정함. OFF이면 과거 열람 기업도 기존 주소·검색 결과에서 추가 주장을 새 조회할 수 없음 |
| 대표·공유본 분리 | OFF가 주장 공개 상태를 바꾸지 않으며 대표 주장과 기존 공유본은 각자의 접근 조건을 유지 |
| 자연어 검색 | 별도 기술·직무 필터 없이 관련 경험을 입력하고 후보별로 묶인 결과와 실제 주장·Catch 근거를 확인. 관련성을 기술 조건 확정 충족·역량 점수로 표시하지 않음 |
| 변경·거부 | 숨김·주장 비공개·자료 변경·구직 의사 OFF를 결과와 근거 조회에 반영. 후보 중복, 결과 없음·검색 실패·자료 준비 중을 구분. 웹·MCP에 같은 자격 적용 |

검색 품질은 시험 자료와 **소수 검색어**로 관련 후보·원문 근거 연결을 직접 확인하고 검색어·결과·확인 내용을 기록한다. 별도 평가셋·정량 합격점·모델 비교·반복 순위 최적화는 이연한다. 이 축소가 자료 권한·변경 반영 검사나 기존 Catch 근거·기여 귀속 기준을 없애지는 않는다. 서류 전체·고정 공유본 검색, 조건 자동 추출, 후보 평가문·매칭 퍼센트·대화형 추천은 추가하지 않는다.

## 4. 채용 안내·발송자 차단

| 확인 대상 | 완료 결과 |
|---|---|
| 발송·수신 | 기업 검색에서 후보 발견·근거 확인 후 포지션·업무/요구사항·안내 사유·기업 측 외부 지원/연락 경로 전달. 수신자는 받은 목록·상세에서 기업·발송자·내용 확인 |
| 발송 이력 | 발송자가 본인의 간단한 발송 목록·상세를 확인. 기업 공동 관리함·읽음·외부 지원 결과는 요구하지 않음 |
| 외부 이동 | 수신자가 직접 이동을 선택하고 목적지를 확인. 후보 자료·연락처를 이동 경로에 자동 첨부하지 않으며 이동을 지원 완료·연락 성공으로 표시하지 않음 |
| 현재 발송 조건 | 실제 발송 시 기업 자격·기업 종료 여부·구직 의사·발송자 계정 차단·운영 발송 중단·반복 한도를 확인. 이전 검색 결과를 열어 둔 경우에도 현재 OFF이면 거부 |
| 차단·해제 | 특정 발송자 계정의 새 안내를 차단·해제. 같은 기업의 다른 계정으로 확대하지 않고 소속·역할 변경만으로 해제하지 않음. 검색·일반 자료 열람·MCP 권한은 각 조건 유지 |
| OFF와 복귀 | 계정을 유지한 채 OFF로 바꿔도 기존 받은 안내 열람 유지. ON·차단 해제로 거부했던 안내를 자동 전달하지 않고 ON을 계정 차단 해제로 처리하지 않음 |
| 탈퇴 이후 | 구직자 탈퇴 후 기업 발송자의 해당 안내 원문·구직자 자료 새 조회 거부. 기존 상세 주소도 동일 적용. 상태 표시만 바꾸고 원문을 계속 제공하지 않음 |
| 실패·반복 | 전달 실패를 성공으로 표시하지 않고 거부한 발송을 대기·자동 전달하지 않음. 계정 쌍 반복 제한은 실제 전달만 집계하고 실패·거부는 차감하지 않음. 확정한 집계값·단위에 맞게 검증 |

작성 폼은 제목·본문·외부 지원/연락 경로를 기본안으로 단순하게 구성한다. 담당자의 개선 의견에 따라 입력항목·표현·배치·조작 흐름을 수정할 수 있으며, 완료 판단은 정해진 칸 수 대신 위 전달·열람 결과로 한다. 별도 공고/JD 관리 기능은 선행으로 요구하지 않는다.

발송 전 내용 확인과 전달 후 수정·회수 불가 안내를 제공한다. 서비스 내 수락·거절·수락 취소, 발송 후 수정·철회, 별도 구직자 연락처 전달, DM·ATS·이메일/SMS·도착 알림·읽음 추적은 이연한다. 계정 차단으로 외부 연락이나 이미 복사된 정보까지 회수한다고 표현하지 않는다. 발신자 탈퇴 시 수신 화면과 안내 보관의 세부는 자료 수명 설계에서 정한다.

## 5. JD 패널·AI 근거 검토

완료 흐름은 JD 직접 입력·요약 → 현재 자료 관련 JD 패널 → 허용 자료 질문 → 실제 출처와 Catch 근거 후보 확인이다.

- 읽기 가능한 포함 서류를 기본 참고하되 수신자의 서류별 제외를 반영한다. 미공유·읽기 불가 서류·외부 URL 본문은 참고하지 않는다.
- 작성자가 연결한 근거와 AI가 제시한 후보를 구분하고 관련 이유·출처·확인 한계를 보여 준다. 근거 없이 JD 충족·역량 점수로 단정하지 않는다.
- 웹의 유효한 비로그인 공유 링크 검토와 기업 소속이 필요한 MCP 받은 공유본 검토 자격을 구분한다.
- 기업 경로로 허용된 추가 주장 검토에는 현재 기업 자격·구직 의사·주장 공개·Catch 이용 조건을 함께 적용한다. 공유본 검토 자격이나 과거 열람 이력으로 현재 접근 제한을 우회하지 않는다.
- 자료 접근·참고 선택·한도와 실패를 처리한다. JD·AI 실행 실패를 안내하고 기존 자료를 보존하며 사용자가 직접 재요청한다. 실패한 실행을 자동 재시작하거나 외부 API를 자동 재호출하지 않는다. 실패·한도 소진으로 유효한 원문·기존 요약 열람을 막지 않으며 재사용은 확정된 권한·선택·자료 조건을 적용한다.
- JD·질문·답변의 계정별 검토 이력·재방문 이어보기는 제공하지 않는다. 현재 검토·필요 재사용의 최소 저장·수명은 설계와 외부 처리 조건에 맞춰 확인한다. 무저장·외부 제공자 무보관을 가정하지 않는다.

품질은 **근거 있는 질문·근거 없는 질문·참고 제외 서류가 있는 경우**를 소수 사례로 확인한다. 질문·참고 자료·실제 출처·확인 한계를 기존 검증 기록에 남긴다. 별도 평가셋·점수 평가·반복 문장 개선은 이연한다. Catch 생성의 근거 링크·기여 귀속 기준은 유지하며 이 최소 검증으로 전체 AI 품질을 통과 처리하지 않는다.

## 6. 제품 MCP와 개발 검증

지원·검증 대상으로 선정한 **실제 외부 도구 한 종류와 배포 시험 환경**에서 다음 세 흐름을 각각 실행한다. 구체 도구·판본·환경과 호환성은 구현 전에 정하고 결과에 기록한다. 다른 도구 지원·호환성 검증은 이연한다. 한 종류 지원은 회원·연결 수를 하나로 제한한다는 뜻이 아니다.

| 흐름 | 자격·자료 | 완료 확인 |
|---|---|---|
| 본인 자료 활용 | 기업 미소속 일반 구직 회원도 사용 가능한 본인 Catch·주장과 별도 선택한 AI 읽기 가능 서류 활용 | 연결 승인 후 선택 자료·출처 조회. 숨김·주장 사용 조건을 적용하고 타인·미선택·읽기 불가 자료 제외 |
| 받은 공유본 검토 | 기업 관리자·승인된 기업 일반 회원, 유효한 링크 접근 조건 동시 충족 | 공유본 자료·출처 조회. 기업 자격만으로 비공유 자료를 제공하지 않음 |
| 후보 검색 | 기업 관리자·승인된 기업 일반 회원, 현재 구직 의사·공개 주장·허용 Catch 조건 | 웹과 같은 검색 대상·후보별 근거·추가 주장 접근 적용 |

연결 승인 범위를 안내하고 해제 후 새 접근을 막는다. 재연결은 새 명시 승인과 현재 자격을 적용한다. 소속 해제·탈퇴·기업 종료, 링크 접근 실패·만료·중단·삭제, 검색 참여 철회에 따른 거부를 자료 정책별로 확인한다. 현재 자료의 숨김을 발행 고정본에 일괄 적용하지 않는다. 재가입으로 이전 자료·기업 소속·권한·연결을 자동 복원하지 않는다.

제품 MCP는 조회·검색·검토 활용만 제공한다. 주장 저장·편집·공유 발행·채용 안내 발송, 개인 DM·연락처·운영 기록의 포괄 제공, 외부 LLM 대화 수집을 추가하지 않는다. 연결 승인은 외부 도구의 무보관·학습 미사용 보장이 아니다. 서비스 AI와 이용자 외부 도구의 실제 처리 조건을 별도로 확인한다.

개발 검증은 다음 두 경로를 기능이 준비되는 대로 병행한다.

| 경로 | 확인할 결과 |
|---|---|
| 브라우저 MCP | 실제 화면의 작성·공유·검색·안내 행동과 저장·반환·거부 결과 |
| 제품 MCP 직접 호출 | 세 흐름의 연결·자료 포함/제외·자격·해제·요청 한도 |

도구 호출 성공만으로 기능 전체를 통과 처리하지 않는다. DB에 넣은 시험 자료·미리 준비한 Catch를 썼다면 그 범위를 기록하고 등록·분석 자체의 증거로 세지 않는다. 반복할 핵심 시나리오는 재실행 절차와 판정 기준을 남긴다. 실제 외부 도구 연결 검증은 직접 호출 검사와 별도로 필요하다.

개발 전용 MCP는 여유가 있을 때 추가할 선택 작업이다. 반복 시험의 준비·실행·결과 확인을 돕는 범위로 두고 상세 설계·자체 완료 기준은 실제 착수 시 정한다. 구축하지 않아도 위 필수 검증을 충족하면 공개판 완료로 판단할 수 있다.

## 7. 탈퇴·기업 종료·삭제 실패

| 확인 대상 | 완료 결과 |
|---|---|
| 회원 탈퇴 | 로그인·MCP·현재 자료 제공·모든 발행 링크 접근 중단. 불필요한 자료·공유본 실제 파기는 확정한 기준에 따라 확인 |
| 마지막 관리자 인계 | 다른 기업 회원을 관리자로 지정한 뒤 본인 탈퇴. 기업과 다른 회원 권한 유지 |
| 기업 종료 후 탈퇴 | 영향을 안내하고 기업 활동·소속 권한 종료 후 본인 탈퇴. 다른 회원의 개인 계정·자료 유지 |
| 부분 실패 | 기업 종료와 본인 탈퇴 결과 구분. 탈퇴 실패를 완료로 표시하거나 종료 기업을 자동 재개하지 않음 |
| 삭제 실패 | 실패 대상을 기록하고 필요한 접근 중단을 유지. 권한 있는 운영자가 수동 재처리한 뒤 실제 파기 결과를 확인. 실패 기록·접근 차단만으로 삭제 완료를 안내하지 않음 |
| 보존 예외 | 적용 근거·항목·기간·조회 권한·분리 보관을 확인한 예외만 검증. 숨김·접근 중단을 실제 파기 완료로 대신하지 않음 |
| 재가입 | 같은 Google 계정의 재가입도 새 계정으로 시작하고 이전 자료·소속·권한·링크·MCP 연결을 자동 복원하지 않음 |

재분석 시 문구·고정본 유지, 구직 의사 OFF 시 기존 안내 열람, 일반 링크 종료 후 보관을 탈퇴 후 보존 근거로 쓰지 않는다. 실제 저장 위치·캐시·백업·외부 처리와 처리 책임·기간은 OQ11·12에서 확인한다. 이 문서는 법적 적용 확인이나 삭제 실행 완료의 증거가 아니다.

삭제 실패는 기록과 운영자 수동 재처리로 마무리한다. 자동 재시도 체계·전용 관리자 화면은 추가하지 않는다. 실행 수단·권한·기록 항목과 기간은 담당자가 설계하고, 접근 중단·자료별 파기 기준·실패 식별·수동 처리 완료를 확인한다.

## 8. 문의·계정별 운영 발송 중단

- 이용자가 찾을 수 있는 외부 연락 채널 하나와 확인·회신 담당을 정하고, 사람이 시험 문의를 접수·확인·회신할 수 있음을 확인한다.
- 사용자는 특정 발송자를 차단하고, 권한 있는 CatchU 운영자는 제보를 확인한 뒤 해당 계정의 새 채용 안내 발송을 수동 중단·해제할 수 있다. 기업 관리자의 소속 관리 권한과 구분한다.
- 중단 계정은 모든 후보에게 새 안내를 보내지 못하고 같은 기업 다른 계정에는 해당 조치가 적용되지 않는다. 소속·역할 변경으로 제한이 사라지지 않는다.
- 해제 후 현재 자격·기업 상태·구직 의사·수신자 차단·반복 한도를 다시 확인한다. 거부 안내 자동 전송·탈퇴 계정·종료 기업 복원을 하지 않는다.
- 무권한 조치를 거부하고 조치 대상·사유·결과의 최소 기록을 확인한다. 처리 실패는 성공으로 안내하지 않는다.
- 발송 중단을 전면 계정 정지로 확대하지 않는다. 자료·독립 공유 링크·검색·검토·MCP와 기존 안내 읽기·소속 정리·탈퇴는 각자의 기존 조건을 적용한다.

외부 채널 주소·담당·수동 실행 수단·기록 항목과 기간은 후속 설계·운영 준비에서 정한다. 서비스 내부 문의 티켓·신고함·고객센터·전용 관리자 화면·자동 남용 판정·자동 제재·기업 전체 일시 중단은 추가하지 않는다. 남는 검색·자료·AI 남용 대응 공백은 OQ13에서 공개 전에 확인하며, 추가 기능은 별도 범위 결정으로 다룬다.

## 9. 요청 한도·근거·남은 확인값

| 공통 조건 | 완료 확인 |
|---|---|
| 공통 원장 | 기간별 횟수·처리량 상한을 설정하고 실행 전에 한도를 확인. 사용 기록을 영속 공통 원장에 남기며 재기동·여러 API에서도 같은 집계를 사용 |
| 실행·실패 집계 | 분석·JD·AI 실행량과 MCP 요청량은 시작 후 실패도 집계. 시작 전 입력·인증·권한 거부는 제외. 같은 실행의 중복 전달은 한 번만 세고 사용자의 새 재요청은 새 사용량으로 집계 |
| 기존 결과 조회 | 원문·기존 결과 읽기는 분석·AI 실행량을 쓰지 않으며 MCP 조회는 MCP 요청량 기준 적용. 채용 안내 계정 쌍 반복 제한은 §4의 실제 전달 집계 기준 유지 |
| MCP 합산 | 같은 회원의 여러 연결·도구 요청을 합산. 연결을 바꿔 새 한도를 얻지 않음 |
| CatchU AI 합산 | 같은 링크의 JD·AI 호출을 제공 경로와 무관하게 합산. 경로·연결 변경으로 초기화하지 않음 |
| 한도 분리 | 외부 LLM 사용 자체를 CatchU AI 호출로 세지 않음. MCP 소진이 허용 웹 열람을, CatchU AI 소진이 허용 MCP 자료 조회를 막지 않음 |
| 근거 품질 | 기록·자기 설명·AI 해석, 실제 출처와 미참고 자료를 구분. 기존 Catch 생성의 근거 링크 유효성·기여 오귀속 기준을 유지 |
| 실제 사용자 확인 | 취준생·HR·기술 면접관의 직접 사용과 시연 참관, 체험·미체험을 구분. 내부 기능 검사를 대체하지 않음 |

이미 정한 실행·실패·중복·재사용 집계를 적용하며, 한도값·집계 기간·기능별 적용 단위·회복 조건은 OQ4, Catch 품질 표본·동의·버전·판정과 성능·규모·복구의 측정 가능한 목표는 OQ6, 사용자 확인 방식은 OQ7에서 정한다. 임의 처리 시간·가동률·복구 수치나 새 평가 체계를 추가하지 않는다. 합의한 검색·JD 최소 품질 확인과 기존 Catch 품질 기준은 구분한다.

첫 이용 안내의 구체 범위·제공 방식·검증은 팀 논의까지 보류한다. 안내 전체 제외로 확정하지 않으며, 이미 합의한 공개·접근·연결 승인·문의 안내는 유지한다.

## 10. 배포 반영·백업 복원·공개 판단

배포는 10월 이미지·검사·실행 절차와 확정한 [EKS 구성 #276](https://github.com/JminAILab/CatchU/issues/276)·[EKS 대상 main 자동 배포 #342](https://github.com/JminAILab/CatchU/issues/342)를 재사용해 12월 설정·자료 구조·외부 연결 변경분을 반영한다. 기존 기반이나 배포 스크립트를 중복 구축·산정하지 않고, 영향받는 기존 흐름과 신규 기능을 실제 환경에서 확인한다. EKS는 빈 DB로 시작하며 개발 서버 자료를 옮기지 않는다. 실제 배포 완료 여부는 해당 증거로 확인한다.

[10월 통합검증표](../CatchU_통합검증표.md)의 2026-10-06 결정은 재시작·재배포 후 DB 자료·공개·숨김·링크 상태 유지와 자동 백업 설정을 10월에 확인하고, **백업에서 실제 복원하는 시험을 12월로 이월**했다. 12월 시험은 운영자가 스크립트를 실행해 **다른 이름으로 DB를 복원하고 원본과 대조한 뒤 시험 자원을 정리**하는 범위다. 최종 대조·정리 결과를 사람이 확인하고 실제 결과를 남긴다. 운영 DB 전환 시험은 추가하지 않는다. 세부 대조 항목·시험 환경·담당·성공 판단은 후속 설계에서 정하고 미실행은 구분한다. [두 API 검증 #280](https://github.com/JminAILab/CatchU/issues/280)과 복원 시험을 12월 8일까지 확인하며 최초 단일 API 배포는 두 API 검증을 기다리지 않는다. 앱의 자동 장애 복구·분석 자동 재실행·새 관제 화면은 추가하지 않되, 확정한 EKS의 자동 장애 조치·노드 복구·관측·자동 배포와 장애 조치 후 재연결은 유지한다.

공개 전에는 문의·문제 조치 책임, 접근 중단·탈퇴·자료 수명, 비용 통제·장애 확인 수단이 실제로 작동하는지 각 기능 결과와 연결해 확인한다. 시험 계정·자료로 먼저 확인하고, 실제 사용자 확인은 지원 범위와 안내를 갖춘 뒤 진행한다.

**필수 흐름 실패, 비허용 자료 노출, 핵심 데이터 손실, 접근 중단 불능, 통제되지 않는 호출 비용이 있으면 해당 기능의 완료·공개 판단을 멈추고 수정한다.** 날짜가 됐다는 이유로 준비 완료로 처리하지 않는다. 공통 권한·수명 조건을 바꾸는 축소는 별도 제품 결정이다.

기능 담당은 실제 결과와 미완료·영향을 제시하고 팀장은 범위·일정 충돌과 공개 여부를 판단한다. 실제 제출 시에는 제출 판본·접속 경로·실제 결과·시연과 남은 제약을 함께 제시한다. 계획 문서 검토, AI-DLC 단계 승인, 코드 반영, 배포, 실제 검증, 제출을 서로 다른 상태로 기록한다.
