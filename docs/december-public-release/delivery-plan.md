# 12월 공개판 작업 구성과 실행 계획

지위: **팀 검토용 실행 초안**. 기준일: 2026-10-12. 팀장이 확인한 제품·운영 방향과 아직 검토할 작업 분할·일정 제안을 구분한다. 담당 배정·구현 견적은 미정이며, 이 문서의 검토를 막는 조건이 아니다.

12월 공개판은 취준생의 작성·공유, HR의 발견·채용 안내, HR·기술 면접관의 JD·근거 검토와 제품 MCP 세 흐름을 불특정 사용자가 직접 이용할 수 있게 하는 것이 목표다. 범위 변경은 [범위와 변경 결정](scope-changes.md), 결과 판정은 [완료 기준](acceptance.md), 팀원의 기능 선택·설계 경험은 [작업 설명서](work-guide.md)를 함께 읽는다. 승인 원본과 재개 경계는 [12월 승인 문서 안내](../CatchU_12월_승인문서_안내.md)를 따른다.

제품 범위가 정해졌다는 것과 구현·배포가 끝났다는 것은 다르다. 실행 상태·담당·막힘·실제 일정은 [작업관리](../CatchU_작업관리.md)에 따라 Issue·Projects에서 관리하고, 이 문서는 배정 전 기준과 참고 일정안을 설명한다. 승인 원본의 날짜 기록은 보존하며, 이번 일정 정정이 외부 제출 마감의 변경을 확인하거나 확정한 기록은 아니다.

이연한 기능의 상세 설계는 이번 계획의 선행 작업으로 잡지 않는다. 범위 경계만 유지하고, 개발 여력이 생겨 해당 기능을 실제로 추가하기로 하면 기능 개발 단계에서 담당자가 설계한다. 구현 대상과 이연 대상이 섞인 항목은 구현할 부분만 구체화하며, 팀 논의 보류 사항을 자동으로 이연 확정하지 않는다.

## 여덟 기능 묶음

번호는 설명용이며 개발 순서가 아니다. 각 묶음은 필요한 화면·API·분석 처리를 포함한다. 한 묶음을 PR 하나나 intent 하나로 강제하지 않는다.

| 묶음 | 함께 완성할 범위 | 다른 기능에 제공할 결과 |
|---|---|---|
| 1. 저장소 분석·Catch | 공개 저장소 분석·수동 재분석, 성공 시 해당 저장소 Catch 전체 교체·실패 시 보존, 숨김, 분석 상태·결과 조회 | 사용 가능한 Catch·근거 조회와 교체 결과 |
| 2. 주장·서류 | 복수 주장 작성·수정·Catch 재선택, 새 글 임시 저장, 서류 등록·선택, 공개·비공개와 대표 주장 | 본인 자료·대표 주장 조회, 공개 설정, 공유·검토에 선택할 자료 |
| 3. 공유본·링크 | 공유본별 대표 하나·선택적 추가 주장·서류의 고정본 발행, 요약에서 주장·Catch 근거 읽기, 유효 링크 연장, 접근·종료·삭제와 보관 후 파기 | 링크 조건을 적용한 고정 자료·요약·근거 조회 |
| 4. 기업·소속 | 기업 직접 등록, 소속 신청·승인·해제, 관리자·회원 두 역할, 관리자 인계·기업 종료 | 현재 기업 자격과 자격 상실 반영 |
| 5. 구직 의사·기업 검색 | 기본 OFF인 통합 설정, 기업의 추가 주장 열람, 자연어 벡터 검색·후보별 근거, 자료 변경 반영 | 현재 조건을 적용한 검색·근거 조회와 새 안내 수신 가능 여부 |
| 6. 채용 안내·차단 | 발송·수신·본인 발송 이력·외부 이동, 발송자 계정 차단·해제, 운영자의 계정별 발송 중단·해제 | 후보에게 안내를 전달하는 흐름과 현재 조건에 따른 거부 |
| 7. JD·AI 검토 | JD 입력·요약·패널, 허용 자료 질의응답, Catch 근거 후보·출처, 서류별 참고 선택 | 현재 허용 자료의 근거와 확인 공백을 보여 주는 검토 |
| 8. 제품 MCP | 외부 도구 한 종류의 연결 승인·해제, 본인 자료·받은 공유본·후보 검색 | 실제 외부 도구에서 세 흐름과 권한·해제·한도 확인 |

1은 Catch를, 2는 주장 문구와 Catch 연결을 맡는다. 재분석 성공 시 교체와 문구 보존·재선택을 함께 확인한다. 2는 자료 공개 설정을, 5는 구직 의사와 기업 경로의 접근 조건을 맡고, 6·8은 같은 현재 조건을 사용한다. 3의 발행 고정본은 독립된 링크 수명 규칙을 적용한다. 자료의 주담당과 이용 기능을 나누어 같은 권한·설정·조회를 중복 구현하지 않는다.

## 계약 합의와 실제 구현의 선행 관계

기능 담당자는 설계하면서 필요한 자료 형식·접근 조건·상태 의미를 연결 상대와 합의한다. 합의한 계약으로 병행 개발할 수 있지만 **실제 연결 완료에는 계약을 지키는 상대 구현이 필요하다**. 설계 전에 모든 API·데이터 구조를 확정하거나 선행 묶음 전체가 끝날 때까지 기다리는 방식은 피한다. 모의 응답은 준비 증거이며 통합 완료 증거가 아니다.

| 연결 | 먼저 합의할 부분 | 실제 연결 확인에 필요한 부분 |
|---|---|---|
| 1 → 2 | Catch 식별·사용 가능 조건, 재분석 성공·실패가 연결에 미치는 영향 | 실제 Catch 조회·교체. 서류 등록은 별도 진행 가능 |
| 2 → 3 | 선택 자료·고정 내용, 발행 시점·접근·보관 조건 | 선택 주장·Catch·서류 저장·조회. 최소 자료부터 연결하고 최종에는 모든 지원 형식 확인 |
| 2·4 → 5 | 공개 자료·대표 구분, 구직 의사, 기업 자격, 근거·변경 반영 | 공개 주장·Catch와 기업 자격 조회. 서류·공유본 전체 완료는 불필요 |
| 4·5 → 6 | 발송자·후보 식별, 현재 발송·수신 조건, 검색에서 안내로 이동 | 실제 기업 자격·구직 의사와 검색 후보 연결. 시험 후보로 먼저 개발한 뒤 검색부터 외부 이동까지 확인 |
| 3 → 7 | 허용 자료·서류 참고 선택·근거·한도·검토 중 자료 처리 | 공유본 조회·AI 호출. 비로그인 웹 링크 검토는 기업 기능을 기다리지 않음. 기업 추가 자료 경로는 4·5도 연결 |
| 2 → 8 본인 자료 | 회원 식별·연결 승인·해제, 본인 자료·선택 서류 범위 | 로그인·최소 본인 자료 조회와 실제 외부 도구 연결. 기업·검색·JD 완료는 불필요 |
| 3·4 → 8 받은 공유본 | 기업 자격과 링크 조건의 동시 적용 | 기업 자격·고정 공유본 조회. 7의 패널·답변 생성 완료는 불필요 |
| 4·5 → 8 후보 검색 | 웹과 같은 기업 자격·검색 대상·근거 조건 | 실제 검색·현재 접근 판정. 6의 채용 안내 완료는 불필요 |
| 배포·통합 검증 → 8 | 선정 외부 도구 연결에 필요한 시험 환경·접속·인증 조건 | 첫 실제 외부 도구 연결 전에 10월 기반의 시험 환경과 최소 MCP 변경분 준비. 새 인프라 전체 구축은 요구하지 않음 |

초기 병행 후보는 1·2의 필요한 자료 부분, 4의 기업 기능, 8의 첫 연결이다. 이후 준비된 입력부터 공유본·검색·JD·채용 안내와 나머지 MCP를 연결한다. 네 명을 이 항목에 고정 배치하거나 모두 동시에 시작한다는 뜻은 아니다.

MCP는 본인 자료 → 받은 공유본 → 후보 검색 순으로 연결 범위를 넓힌다. 최초의 작은 본인 자료 조회는 연결 위험을 확인하는 중간 결과다. 선택 서류를 포함한 전체 범위와 다른 두 흐름까지 확인해야 완료다. CatchU AI와 외부 도구 AI 처리를 구분하며, 제품 MCP에 쓰기·채용 안내 발송·새 AI 실행 기능을 추가하지 않는다.

## 기능과 함께 진행할 공통 작업

공통 작업의 주담당도 팀 회의에서 정한다. 마지막 주에 한꺼번에 붙일 작업으로 미루지 않는다.

| 공통 작업 | 공통 책임 | 각 기능 담당의 책임 |
|---|---|---|
| 탈퇴·자료 수명 | 회원 탈퇴 화면·요청·처리 결과, 로그인·외부 접근 중단, 재가입 경계, 자료별 처리와 실패 삭제의 마무리 연결 | 현재 자료·공유본·소속·검색 자료·안내 접근·AI 임시 자료·MCP 연결을 각 정책에 맞게 처리하고 검증 |
| 요청 한도·비용 | 사용자·링크·요청 구분과 공통 집계 경계 합의, 공통 처리 반영 책임 | 분석·검색·안내·AI·MCP 각 경로의 한도·실패 응답 적용 |
| 문의·운영 | 실제 문의 경로와 확인·회신, 운영 조치의 자격·실행 책임 | 6의 계정별 발송 중단·해제·기록, 각 기능의 합의된 공개·접근·연결 안내 |
| 배포·통합 검증 | 10월 기반 재사용, MCP 첫 실제 연결용 시험 환경, 변경분 취합·연결 확인·백업 복원 시험. 기존 Catch 품질 표본·사용자 직접 사용 확인·제출/시연 준비의 책임과 결과 연결 | 설정·자료 구조·외부 연결 변경과 기능별 검증 결과 제공. 분석 담당은 Catch 품질 근거를 준비하고, 기능의 배포·검증 책임을 공통 담당에게 전부 넘기지 않음 |

탈퇴는 자료 목록만 작성하는 일이 아니다. 마지막 관리자 인계·기업 종료는 4에서 구현하고 전체 탈퇴 흐름에 연결한다. 일반 링크 종료 후 보관·파기와 탈퇴 후 처리는 구분한다. 삭제 실패의 수동·자동 처리 방식은 담당자가 설계하고, 실패를 식별해 마무리할 수 있는 결과를 검증한다. 별도 관리자 화면은 필수로 요구하지 않으며 필요한 실행 수단은 담당자가 설계한다.

**여유가 있을 때 진행할 선택 작업:** 개발 전용 MCP로 반복 시험의 준비·실행·결과 확인을 묶는다. 2026-10-12 팀장 요청을 반영한 검증 지원 작업이며, 공개판 필수 범위·검증을 밀어내거나 완료 선행 조건이 되지 않는다. 실제 착수 시 반복 부담과 구현·유지 비용을 확인하고 담당자가 설계한다. 제품 MCP의 조회·검색·검토 활용 범위는 유지하며 기존 두 검증 경로의 완료를 기다려야 하는 세 번째 단계로 강제하지 않는다.

## 담당 배정과 설계 참여

**담당자 실명과 배정은 추후 팀 회의에서 정한다.** 회의에서는 희망 기능·설계 참여 정도·기존 경험을 확인한다. 기능마다 설계·구현·검증을 끝까지 챙길 주담당을 두고 필요한 협업자·연결 검토자를 붙이는 방식을 제안한다. 한 사람이 모든 계층을 혼자 구현하거나 여덟 묶음을 네 명에게 같은 개수로 나누지 않는다.

설계 참여 순서는 완료 기준 확인 → 희망 기능 확인 → 설계 책임·연결 상대 설정 → 담당자 설계·계약 검토 → 예상량 보완·구현 배치다. 한 사람의 주요 진행 작업은 하나를 원칙으로 하고, 검토 대기·공통 선행을 먼저 해소한다. 같은 코드를 여러 에이전트가 동시에 수정하지 않는다.

| 판단 대상 | 판단과 반영 책임 |
|---|---|
| 기존 범위·계약 안의 내부 구조 | 기능 담당자가 대안을 비교해 결정. 작은 구현 선택마다 추가 사전 승인 절차를 만들지 않음 |
| 새로 정하거나 변경해야 하는 API 응답·상태 의미·권한·DB 관계 등 연결 계약 | 제안 담당자가 이유·영향·선택안을 정리하고 연결 상대가 검토. 팀장 판단과 계약 반영으로 연결하며 반영 책임자를 지정 |

## AI-DLC 2.11.0 운영 준비

팀장은 2.11.0 채택과 희망자의 기능별 별도 intent 설계 참여를 선택했다. **이 문서는 실제 설치 상태를 확인하거나 업데이트하지 않았다.** 적용 전 CLI·프로젝트 하네스·팀원 환경의 버전 정합성과 기존 기록 보존·재개를 확인한다. 백업·복귀 절차를 준비하고 작은 기능에서 입력·질문·기록·검토·작업 간 분리를 먼저 확인한다. 조사 예산 한 작업일은 출발 제안이며 성공 보장이 아니다.

각 intent에는 적용 FR·스토리, 이번 범위 변경의 요지·출처·판본, 구현·제외 범위, 기존 코드·API·모델 기준 판본, 담당자의 판단 범위, 연결 상대·완료 기준을 입력한다. 링크만으로 맥락이 전달된다고 가정하지 않는다. 별도 작업 공간·브랜치·세션과 기록을 사용하고, 전체 12월 요구사항·변경 결정·설계 산출물과 연결한다.

기존 12월 intent는 사용자 스토리 승인 후 도메인 설계 직전에 정지했다. 기능별 intent 시작과 기존 intent 재개를 구분한다. 기존 방침보다 설계를 앞당기는 일정 변경은 위 판단 책임에 따라 팀장이 판단하고 해당 기능의 착수 시점·범위를 기록한다. 완료 단계 전체를 다시 수행하지 않고 변경된 범위와 영향 계약을 대상으로 절차·검토 지점을 정한다. 개별 intent 승인으로 다른 기능의 계약 변경이나 전체 공개판 완료를 대신하지 않는다.

새 작업의 **설정 제안**은 Guard Policy `off`, collaborators `off`, 독립 리뷰 유지다. AI-DLC 코드 생성 단계를 사용하면 초기 Plan Approval `on`과 sensors 유지를 제안한다. 실제 설정 선택·환경 확인 전에 기존 설정을 일괄 변경하지 않는다. 이 제안은 제품 권한·검사·사람의 PR 승인 기준을 낮추지 않는다. 코딩의 AI-DLC 사용은 담당자 요청에 따라 선택한다.

AI는 구조 설명·질문·대안 비교·근거 확인·검사를 돕고, 담당자는 설계 선택과 결과를 설명한다. 별도 검토자는 핵심 흐름·자료 노출·근거 귀속·비용·계약을 우선 확인한다. 실제 구현·테스트 증거는 담당자가 확인한다. 일반 개발의 이슈→브랜치→dev PR→작성자 외 승인 1건→merge commit은 [코딩 절차](../CatchU_coding_procedures.md)를 따른다.

## 주간 운영과 지연 대응

기존 월요일 회의에서 끝낼 사용자 행동과 제외 범위를 정하고, 매일 스크럼에서는 검토 대기·막힘·선행 작업을 다룬다. 금요일에는 실제 연결 결과와 차이를 확인한다. 상태 문서를 별도로 늘리지 않고 Issue·Projects를 사용한다.

- 10월 잔여 작업은 개발에 쓸 가용량에서 먼저 차감하고 예상량을 다시 비교한다.
- MCP 첫 연결에서 막히면 인증·도구 호환·공통 API 원인을 나누어 해소한다. 통합 검증 막바지로 미루지 않는다.
- 공유본·검색·MCP 연결 점검에서 지연이 확인되면 새 화면 편의 작업을 멈추고 공통 선행에 집중한다. 추가 축소는 팀장이 결정한다.
- 핵심 연결 점검 때 미완료면 예정한 검증 기간을 추가 기능 기간으로 자동 전환하지 않는다. 남은 양과 공개 조건을 비교해 범위·일정 충돌을 보고한다.
- MCP 세 흐름·필수 권한·자료 수명은 조용히 제외하지 않는다. 새 기능은 같은 기간에서 줄일 일과 선행 영향을 함께 제시한다.
- 필수 흐름 실패·비허용 자료 노출·핵심 자료 손실·접근 중단 불능·통제되지 않는 비용은 [공개 판단](acceptance.md)에 따라 수정 후 판단한다. 날짜만으로 완료를 선언하지 않는다.
