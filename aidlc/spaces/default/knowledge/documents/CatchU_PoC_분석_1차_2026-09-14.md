### 2-2. 데이터 스키마 요약

- `commit_details.json` 레코드: `sha, parents, is_merge, author_key, author_name, author_email, author_date, commit_date, message_subject, message_body, has_body, body_is_trailer_only, trailer_keys, files[{status, filename}], changed_file_count`. 【코드】 본인 커밋은 `author_key = "subject"`, 타인은 `author_NN`이며 `author_email`도 `author_NN@anonymized.invalid`로 치환돼 저장된다.
- `events.json` 사건 레코드: `event_id, boundary(A|B), rule, commit_shas[], commit_count, period{start,end,span_minutes}, authors[], primary_author, involves_subject, representative_files[], distinct_file_count, top_dirs[], shape_flags[], meets_shape_criteria`. A 전용 `merge_sha, source_branch, target_branch, merged_at`, B 전용 `gap_threshold_minutes, threshold_basis, threshold_imported, approximate`, 재분할 산출은 `parent_unit`. 【코드】
- 사건 ID는 시작 시각 순서로 매기는 **위치 번호**다(`A001…`, `B001…`, `RS001…`). 커밋이 추가되거나 임계값이 바뀌면 같은 사건의 ID가 달라질 수 있다【코드: `build_events.py` make_event 호출부】. 서비스의 카드 식별에 그대로 쓸 수 없다(§6 FR1.4).

### 3-3. 후보 선정과 근거 정리 【코드】

- 후보 선정: 하드 필터 3개(본인 주도 `primary_author == subject` / 형태 충족 / 코드 파일 비율 ≥ 0.5) 통과 사건을 커밋 수 desc → 코드 파일 수 → churn으로 정렬. 통과 3개 미만이면 코드 조건만 완화한 목록을 따로 낸다. `select_card_candidate.py`.
- 근거 정리(dossier): 사건 메타, 커밋 시계열(메시지 원문·+/-·GitHub URL), 커밋별 diff(커밋당 200줄 예산, 초과 시 `생략됨(N줄)`과 "잘린 데이터" 경고), 파일 생애(A/M/D/R/C), 낮은 임계 rename/copy 재검사, 파일별 상태 추적(예산 40파일, 초과 시 생략 명시), blob 해시 대조(생성 파일 vs 직전 트리, 경로 간 동일 blob). 서술·판단 문장은 만들지 않는다. `build_dossier.py`.
- 관례로 정한 경계값 6건(코드 비율 0.5, 확장자 목록, 3일, diff 200줄, 추적 40파일, leaf 정의 등)은 실측 근거가 없다고 스스로 기록했다【기록: REMEDIATION 3차 ④】.

### 7-4. 코드 재사용에 대한 권고

**로직을 참조해 재작성하되, 순수 함수 부분은 이식한다.** 근거:

- 【코드】 표준 라이브러리만 쓰고 언어가 worker 스택(FastAPI/Python)과 같다. `gap_sample.py`(46줄), `pick_threshold.select`(88줄), `build_events.split_by_rule`·`make_event`(약 100줄), `anonymize.Anonymizer`(244줄), `gate_anonymize`의 B계열 검사(약 150줄), `build_dossier`의 `redact`·파일 생애·blob 대조는 입출력이 분명한 순수 논리라 함수 단위로 옮길 수 있다.
- 【코드】 반면 CLI 위치 인자, import 시점 실행, `ROOT` 상대 경로, 하드코딩된 클론 경로(`build_import_graph.py`), 사건마다 `git show`를 부르는 churn 계산은 서비스 구조에 맞지 않는다. 테스트 코드는 0건이다.
- 【기록】 작성자도 "코드 품질보다 로직 참고 후 재설계"를 선호했다(MVP 입력 §6). 이 분석은 그 의견을 뒤집을 근거를 찾지 못했고, 위 순수 함수 범위만큼은 재작성 비용을 줄일 수 있다고 본다.

### 7-5. 데이터 재사용

- 8/23 스냅샷(TheMe 483커밋, 사건 210)과 저장분 `events.json`·`metrics.json`·`threshold.json`은 재작성한 모듈의 **회귀 테스트 기준**으로 쓸 수 있다. 【검증 V2·V3】이 그 대조 방법을 이미 보여준다.
- 단 데이터에는 본인 이메일 원문이 들어 있다. 팀 저장소에 넣으려면 본인 식별자도 치환한 사본을 만들고, 원본은 PoC 폴더에 둔다.
- 10월 시연에서 팀장 저장소를 분석하면 과거 결과와 비교할 수 있다. 비교 시점의 원격 tip이 저장분보다 1커밋 앞서 있으므로(§1-2) 기준 리비전을 고정해야 같은 수치가 나온다.

## 8. 재설계 범위 (제안)

PoC가 다루지 않은 것이 서비스 분석 경로의 절반 이상이다. worker 관점의 경계를 제안한다.

1. **입력 계약**: 사전 선정 저장소 slug, 기본 브랜치, 분석 대상자의 확인된 이메일 집합, 분석 동의 기록 ID, 기준 리비전(원격 tip SHA 고정). 통합 브랜치 목록은 자동 식별 결과를 입력이 아니라 산출로 기록.
2. **수집**: 인증 토큰 사용, 클론 또는 얕은 fetch로 이력 확보, 수집 시점 익명화(§3-1 유지), 원본 REST 응답 미보관. 대형 diff 잘림 표시 유지.
3. **묶기·근거**: 경계 A/B, 임계값 절차, 형태 플래그, 무결성 게이트 유지. 사건 안정 키 신설. 출력은 구조화 JSON.
4. **초안 생성(신규)**: 사건 JSON → 4구획 중 "무엇을 했나"와 "기록에 없는 것"을 LLM이 작성하되 모든 문장에 커밋 링크 인용을 강제하고, 인용 SHA가 사건 밖이면 기각하는 검증 게이트. "판단의 흐름"과 "궤적 및 기록"은 결정적 자료로 채운다. 호출 상한과 재시도는 OQ1·OQ3.
5. **상태·중복·실패(신규)**: 큐 작업 단위, 진행 중 중복 요청 차단, 부분 성공 결과 처리, 실패 시 기존 카드·링크 보존(NFR4).
6. **원본 상태·보관(신규)**: 공개 상태 확인과 비공개 전환 처리(FR1.5·OQ2), 발췌만 보관하고 원본 diff 미보관(OQ11).
7. **인젝션 통제(신규)**: `clean()`에 해당하는 단일 통과 지점을 유지하고, LLM 입력 직전에 지시문 탐지 또는 격리 프롬프트를 둔다. 탐지 성능은 보장하지 않는다(OQ14).

## 9. 추가 검증 — 시점별

### 9-1. feasibility 판단 전에 필요한 것

| 항목 | 이유 | 수행 조건 |
|---|---|---|
| 로그인 계정 ↔ 커밋 이메일 연결 방식의 실현 가능성 | FR1.1의 귀속이 여기에 달려 있다. Google OAuth만으로는 GitHub 이메일을 얻을 수 없다 | OQ1·OQ11 결정 입력. GitHub OAuth `user:email` 사용 여부 또는 사용자 확인 절차 중 택일 |
| LLM 초안 생성 소규모 실험 | FR2.2는 PoC에 근거가 없다 | 제공자 후보 1곳의 학습 미사용 등급(NFR2)으로 사건 1~2건(예: A042 dossier)에 초안 생성 → 근거 인용 준수 여부 확인. 실제 사용자 자료가 아니라 본인 저장소만 사용 |

### 9-2. domain-design 전에 필요한 것

| 항목 | 이유 |
|---|---|
| 통합 브랜치 자동 식별 규칙을 3저장소(+샌드박스 2)로 검증 | 사람이 넣던 인자를 대체해야 한다. bz/ADMISSION의 표를 재현하는 규칙이 첫 후보 |

### 9-3. 구현·통합 단계에서 확인할 것

- 익명화 게이트 B계열을 worker 테스트로 상시 실행, A계열은 클론 확보 시 실행.
- 무결성 게이트를 분석 완료 조건으로 코드화(N=N, 중복 0, 머지 혼입 0).
- 시크릿 마스킹 패턴 확장과 마스킹 후 잔존 검사(【검증 V4-b】 방식).
- 대형 diff·API 잘림 감지 표시가 초안 생성 입력까지 전달되는지.
- 회귀 테스트: 8/23 스냅샷으로 사건 210·임계값 426 재현(본인 식별자 치환 사본 사용).
- 인젝션 통과 지점의 위치와 LLM 입력 격리가 유지되는지 코드 리뷰.

## 10. 요약

- PoC는 수집·익명화·경계 A/B 묶기·근거 정리까지를 규칙 기반으로 구현했고, 현재 코드가 8/23 저장분을 그대로 재현한다【검증】. 익명화·게이트·경계·임계값 절차는 그대로 서비스 규칙으로 가져갈 근거가 충분하다.
- 10월 요구사항의 나머지 절반, 즉 동의·상태·중복·실패·공개 상태·초안 생성·운영은 PoC에 없다. 특히 본인 식별 방식, 통합 브랜치 자동 식별, 사건 안정 키 세 가지는 domain-design 전에 정해야 한다.
- 채택 권고는 "로직 참조 + 순수 함수 이식 + 나머지 재작성"이며, 이 문서는 그 결정을 기록하지 않는다. 결정과 담당은 feasibility·domain-design·delivery-planning에서 남긴다.
