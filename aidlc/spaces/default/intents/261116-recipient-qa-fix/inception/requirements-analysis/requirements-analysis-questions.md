# 요구사항 분석 질문 — #559 받은 사람 질의응답 고치기

> 범위·지킬 경계·완료 기준은 이슈 #559 본문이 정본이다. 아래는 이슈가 「구현 때 정한다」로 남겼거나, 계약·다른 담당과 맞춰야 해서 지금 정해 두어야 요구사항을 쓸 수 있는 것만 묻는다. 질문·답 원문은 옮기지 않고 질문 번호로 가리킨다.

## Q1. [개발자] 같은 근거의 기록 줄을 모델에 함께 보내는 방식

지금은 근거(커밋·PR 기록) 하나의 기록 줄마다 따로 조각이 되고 따로 검색된다(`api/src/published-index/chunker.ts`). 그래서 3번 질문에서는 커밋 규모 줄이 검색되지 않았고, 7번 질문에서는 규모 줄만 오고 같은 커밋의 식별값·시각 줄이 함께 오지 않았다. 함께 보내는 방법에 따라 계약(C-01·C-07·C-08·C-09)을 고쳐야 하는지와, FR6.2의 「질문에 넘길 자료는 의미 검색으로만 고른다」를 어떻게 읽을지가 달라진다.

A. 검색은 지금처럼 줄 하나가 조각 하나이고, 상위 8개를 고른다. 검색이 끝난 뒤 맞은 줄이 속한 근거(같은 Catch의 같은 커밋·PR 기록)의 다른 줄을 함께 붙여 모델에 보낸다. 줄마다 지금처럼 따로 인용할 수 있어서 다음은 그대로다: 인용 위치(사본 칸 하나 안, C-01), 출처 강조, 평가 정답 위치, JD 요약. 검색으로 고르는 수는 8 그대로지만 모델에 가는 줄 수는 8보다 늘 수 있다. 의미 검색은 근거를 고르는 데만 쓰고, 고른 근거의 나머지 줄은 구조로 붙이는 것으로 FR6.2를 읽는다. 계약 모양은 바뀌지 않는다.
B. 조각을 근거 하나(그 근거의 줄 전부) 단위로 묶어서 검색한다. 검색으로 고른 것만 보낸다는 FR6.2 문장에는 가장 곧다. 대신 조각 하나가 사본 칸 여러 개에 걸친다. 그래서 다음을 함께 바꿔야 하고, 팀원 4(JD 요약)와 계약을 맞춰야 한다: 조각 위치 모양(C-07·C-08·C-09), 조각 1,000자 제한, JD 요약의 조각 검사, 평가 정답 위치.
C. 조각과 보내는 줄은 그대로 두고, 같은 근거의 다른 줄을 인용할 수 없는 머리글로만 붙인다. 계약은 그대로다. 하지만 대조는 그 항목이 인용한 줄만 본다. 그래서 머리글에 있는 커밋 식별값이나 숫자를 답에 쓰면 그 항목이 버려지고, 7번 기준(어느 커밋의 기록인지 함께 말하기)을 맞추기 어렵다.
X. Other (please specify)

[Answer]: X. A로 하되 붙이는 범위를 같은 근거가 아니라 같은 Catch의 GitHub 기록 줄 전체로 넓힌 안을 검토해 줘. 3번은 정답 근거의 줄이 상위 8개에 하나도 없어서 같은 근거 붙이기로는 안 고쳐진다. 줄 수 상한도 함께 제안해 줘. (Q4에서 이어 정함)

## Q2. [개발자] 5번 질문의 답 실패 원인을 확인할 자료

5번은 「답을 만들지 못했습니다」였다. 이 문구가 나오는 길은 모델이 `- ` 항목을 하나도 쓰지 않은 경우(`NO_ITEMS`) 하나다. 그런데 지금 그 실패 로그(`ai_gate_failed`)에는 실패 이름만 있다. 모델이 항목이 아닌 줄을 몇 줄 썼는지, 왜 끝났는지 같은 칸이 없다. 11/12 api 로그가 남아 있는지는 Docker가 꺼져 있어 확인하지 못했다.

A. 실패 로그에 글 없이 수만 남는 칸(항목이 아닌 줄 수, 모델이 끝난 이유)을 더한다. 다시 잴 때 5번을 같은 질문으로 물어 그 로그로 원인을 평가 기록에 적는다. 다시 잰 5번에 답이 나오면 「재현되지 않음」과 늘린 칸의 값을 적는다. 11/12 로그는 찾지 않는다.
B. 먼저 11/12 api 컨테이너 로그를 찾아본다. Docker를 켜야 하므로 그때 확인을 받는다. 남아 있지 않으면 A로 간다.
C. 로그 칸은 그대로 두고, 다시 잴 때 결과만 적는다.
X. Other (please specify)

[Answer]: X. A로 하되 두 가지를 더해 줘. 첫째, 로그 칸에 위치를 못 찾아 버린 항목 수도 넣는다. 둘째, 로그 칸을 더한 뒤 지시를 고치기 전 상태로 5번을 먼저 한 번 물어 원인을 평가 기록에 적는다. 11/12 측정은 컨테이너가 아니라 호스트에서 돌린 평가 스크립트라 컨테이너 로그에는 없다.

## Q3. [화면·계약] 출처 딱지 옆 항목 제목을 패널에 넘기는 방식

답·요약 항목을 그리는 `GatedItemView`(`web/src/features/rag-answer/gated-item-view.tsx`)는 사본을 받지 않는다. 항목 제목은 패널을 다는 두 화면(받은 사람 화면, 작성자 발행본 화면)만 갖고 있다. 받은 사람 쪽 패널의 props는 계약 C-11 `RecipientSlotProps`이고, 4번 자리 JD 패널도 같은 props를 받는다.

A. 기본 요약·질의응답 두 패널에만 선택 prop 하나(근거 위치의 `publishedItemId`로 항목 제목을 찾는 함수)를 더한다. 두 화면은 자기가 가진 사본으로 이 함수를 넘긴다. `RecipientSlotProps` 공통 모양은 그대로이고 JD 패널도 바뀌지 않는다. C-11의 2·3번 자리 설명에 한 줄을 더하고, 받은 사람 화면 담당(팀원 3)과 PR 리뷰에서 맞춘다.
B. `RecipientSlotProps` 공통 칸으로 더한다. 모든 자리가 받으므로 JD 패널(팀원 4)도 타입이 바뀐다.
C. 패널이 사본 API를 따로 불러 제목을 찾는다. C-11은 그대로다. 대신 요청이 한 번 더 늘고, 비밀번호 통과·접근 불가 처리를 패널이 또 해야 한다.
X. Other (please specify)

[Answer]: A

## Q4. [개발자] 같은 Catch의 GitHub 기록 줄을 붙이는 범위와 상한 (Q1 이어서)

Q1 답에 따라 붙이는 범위를 같은 Catch의 GitHub 기록 줄로 넓혀 11/12 측정의 조각 위치로 따져 봤다.
- 3번 정답(Catch `0191e320`의 규모 줄 `evidence[2].representedFacts[1]`)은 같은 근거 붙이기로는 들어오지 않고, 같은 Catch로 넓히면 들어온다.
- 9번 정답은 세 Catch의 `evidence[0].representedFacts[1]`이다. 세 Catch 모두 상위 8개에 걸려 있어 Catch 단위로 넓히면 셋 다 들어온다.
- 시연 발행본의 GitHub 기록 줄은 약 49개다. Catch별로 약 9·9·31개이고, 근거 하나는 보통 두 줄이다.
- worker가 Catch 하나에 담는 본인 커밋은 최대 20건이다(`worker/app/candidates/build.py` `EVIDENCE_COMMIT_CAP`). 그래서 Catch 하나가 50줄 가까이 될 수 있다.

A. 검색 상위 8개는 늘 보낸다. 맞은 Catch마다 GitHub 기록 줄을 최대 12줄 더 붙이고, 보내는 줄은 전체 최대 40줄(검색 8개 포함)로 둔다.
  - Catch 순서: 그 Catch에서 가장 높은 검색 순위 순
  - Catch 안의 순서(한 근거의 줄은 함께): ① 맞은 줄과 같은 근거의 줄 ② 작업 사실·나의 기여 줄 ③ 남은 근거를 사본 순서대로
  - 작성자 설명은 검색으로 맞은 것만 보낸다.
  - 11/12 위치로 따지면 3번·9번 정답이 모두 들어가고, 보내는 줄은 30~40줄이다.
B. 상한을 낮게 둔다: Catch당 8줄, 전체 24줄. 3번 정답은 들어가지만, 큰 Catch(약 31줄)는 일부만 가고 9번처럼 세 Catch를 함께 묻는 질문에서 빠질 수 있다.
C. 상한 없이 맞은 Catch의 GitHub 기록 줄을 전부 보낸다(모델 입력 상한 80,000자만 둔다). 시연 발행본에서는 사실상 전체가 가고, Catch가 많은 발행본에서는 수백 줄이 된다.
X. Other (please specify)

[Answer]: X. A로 하되 두 가지를 더해 줘. 첫째, 12와 40은 11/12 위치에 맞춘 시작 값이라고 기록에 적고 다시 잰 뒤 조정하지 않는다. 둘째, 상한 때문에 붙이지 못한 줄 수를 로그 칸에 수로 남기고, 큰 Catch는 기록 일부만 가서 개수·전체 규모를 묻는 질문에 틀릴 수 있다는 점을 서비스 문서의 알려진 한계에 적는다.

## Q5. [개발자] 5번을 먼저 물어 볼 때의 코드 상태 (Q2 이어서)

Q2 답에서 「로그 칸을 더한 뒤 지시를 고치기 전 상태로 5번을 먼저 한 번 물어」 원인을 적기로 했다. 그런데 이번에는 지시 말고도 모델에 가는 것이 바뀐다. 보내는 줄이 늘고(Q4), 어느 Catch인지 머리글이 붙는다. 그래서 「고치기 전」을 어디까지로 볼지 정해야 한다. 참고로 `NO_ITEMS`는 모델이 `- ` 항목을 아예 안 쓴 경우뿐 아니라, 쓴 항목이 모두 위치를 못 찾았거나 잘려서 버려진 경우에도 난다(`checked-gate.ts` `modelItems`). 지금 실패 로그 `ai_gate_failed`는 이 수를 계산해 두고도 찍지 않는다.

A. 로그 칸만 더한 상태로 묻는다. 보내는 줄 늘리기·Catch 머리글·지시 수정은 모두 하기 전이라 11/12와 같은 조건이다. 실패 당시 조건에서 원인을 본다.
B. 보내는 줄 늘리기·Catch 머리글은 넣고, 지시만 고치기 전에 묻는다.
X. Other (please specify)

[Answer]: A
