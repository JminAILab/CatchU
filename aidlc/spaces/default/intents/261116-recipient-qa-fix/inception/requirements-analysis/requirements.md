# 요구사항 — #559 받은 사람 질의응답이 틀리게 답한 자리 고치기

> 범위·지킬 경계·완료 기준의 정본은 GitHub 이슈 #559 본문이다. 「12월 FR6.4」처럼 「12월」을 붙인 ID는 12월 intent 요구사항의 ID이고, 붙이지 않은 ID는 이 문서의 ID다. 이 문서는 그 위에 요구사항 분석 질문의 답(`requirements-analysis-questions.md` Q1~Q5)을 더해, 코드 생성이 따를 요구를 정한다. 질문·답 원문은 옮기지 않고 질문 번호로 가리킨다. 지금 코드의 자리는 코드 기록 `aidlc/spaces/default/codekb/CatchU/`(`business-overview.md`, `architecture.md` 「받은 사람 질의응답」·「답 항목 0개의 세 길」, `code-structure.md` 「받은 사람 AI 쪽 배치」)와 스캔 기록 `inception/reverse-engineering/developer-scan.md`를 따른다.

## 의도 분석

면접관이 발행본에 물었을 때 틀린 답이 두 가지로 나왔다. 하나는 카드에 보이는 기록을 두고 「자료에 없다」고 답한 것이다. 다른 하나는 다른 Catch의 작성자 설명을 끌어다 답한 것이다. 이런 답이 하나만 나와도 면접관은 나머지 답도 믿지 않는다. 2026-11-12 실측(Catch 3개 발행본, 질문 10개)에서 확인한 원인은 셋이다.

- 근거(커밋·PR 기록) 하나의 기록 줄이 줄마다 따로 조각이 되고 따로 검색된다. 그래서 규모 줄이 검색되지 않거나(3번), 규모 줄만 오고 같은 커밋의 식별값 줄이 오지 않는다(7번).
- 조각과 모델 입력에 어느 Catch의 것인지 표시가 없다(9·10번).
- 질의응답 지시가 「자료에 없는 일은 없다고 말한다」여서, 찾은 조각에 답이 없을 때 발행본 전체에 없다고 단정한다.

이번 일의 목표는 이슈 #559의 완료 기준 12개를 채우는 것이다. 11/12에 쓴 발행본에 같은 질문 10개를 한 번 다시 재서 확인한다. 고치는 범위는 다섯이다.

1. 같은 Catch의 기록 줄을 함께 보낸다.
2. 어느 Catch의 것인지 모델이 알게 한다. 검색 쪽은 1의 Catch 단위 붙이기가 대신한다(FR2.3 제외, 「범위 밖」).
3. 지시를 한 번 고친다.
4. 화면의 출처 딱지 옆에 항목 제목을 보인다.
5. 답 실패의 원인을 확인한다.

이렇게 고친 것이 다시 재기에서 재지도록, 평가 스크립트가 앱과 같은 함수로 질의응답 요청을 만들게 한다(FR7).

### FR2. 모델 입력이 어느 Catch의 것인지 알게 한다

출처: 이슈 #559 요약 2·범위 「지킬 경계」, 요구사항 승인 관문의 변경 요청(2·3번)

| ID | 요구 |
|---|---|
| FR2.1 | 질의응답이 모델에 넘기는 인용 문서마다, 그 줄이 속한 발행 항목을 알리는 머리글을 붙인다. 머리글은 인용할 수 없는 설명(인용 문서의 `context`)이고, 지금의 자료 종류 표시(「자료 종류: GitHub 기록 원문」·「자료 종류: 작성자 자료 원문」)에 더한다. |
| FR2.2 | Catch 항목의 머리글은 다음 둘로 그 Catch를 나타낸다. <br>- 발행 항목 순번 <br>- 그 Catch의 작업 사실 둘째 줄(`workFacts[1]`). worker가 쓸 만한 PR 제목이나 본인 커밋 첫 줄이 있을 때만 쓰는 줄이라 Catch마다 많아야 하나다(`worker/app/candidates/build.py` `_record_fact`). <br>둘째 줄이 없으면 순번만 쓴다. 둘째 줄은 글자 그대로 쓰고, 200자(UTF-16)를 넘으면 앞 200자까지만 쓴다. 200은 시작 값이다. 둘째 줄은 칸 위치로만 고르고 worker 문장을 글자로 대조하지 않는다. 구현이 worker 문장의 꼴을 글자로 대조해 글을 뽑게 되면, 프로젝트 규칙대로 두 쪽 문장을 맞춰 보는 시험을 함께 넣는다. <br>Catch 제목, AI 설명 초안(`aiDraft`), 저장소 이름, 작업 한계, 본인 커밋 표지는 머리글에 넣지 않는다(12월 FR6.4, 새 Catch 입력 4-3). 같은 Catch의 작성자 설명 줄에도 같은 머리글을 붙인다. |
| FR2.4 | 텍스트 자료 항목에는 Catch 표시 대신 발행 항목 순번과 자료 종류만 붙인다. 텍스트 자료 제목은 넣지 않는다. |

### FR5. 5번 질문의 답 실패 원인을 확인한다

출처: 이슈 #559 요약 5·범위 「답 실패」, [Q2]·[Q5]

| ID | 요구 |
|---|---|
| FR5.1 | 게이트 실패 로그(`ai_gate_failed`)에 글 없이 수와 이름만 남는 칸 셋을 더한다. <br>- 항목이 아닌 줄 수 <br>- 모델이 끝난 이유 <br>- 위치를 못 찾아 버린 항목 수 <br>`NO_ITEMS`는 두 경우에 난다. 모델이 `- ` 항목을 아예 쓰지 않은 경우와, 쓴 항목이 모두 위치를 못 찾았거나 잘려서 버려진 경우다(`checked-gate.ts` `modelItems`). 이 셋 중 어느 쪽인지 가를 수 있어야 한다. <br>이 칸은 게이트의 두 길 모두에서 실패 로그에 들어간다. 한 번 호출 `generate`는 평가 스크립트와 기본 요약이 쓰고, 스트리밍 `generateStream`은 앱의 질의응답이 쓴다. 두 길은 항목 판정 코드가 따로다(스트리밍은 `StreamItems.end()`에서 `NO_ITEMS`). |
| FR5.2 | 로그 칸만 더한 상태로, 11/12와 같은 경로인 평가 스크립트(`npm run rag-eval`의 measure 모드)로 5번을 묻는다. <br>- 순서: 이 실행은 다른 변경보다 먼저 한다. 보내는 줄 늘리기(FR1), Catch 표시(FR2), 지시 수정(FR3), 평가 스크립트를 공용 함수로 바꾸기(FR7)는 모두 그 뒤다. <br>- 질문 수: measure 모드는 질문이 10개가 아니면 거부하므로, 10개를 그대로 한 번 돌린다. <br>- 이 실행의 지위: 고치기 전의 기준선이다. 지시나 상한을 고친 뒤 다시 재는 일(12월 NFR3의 한 번)이 아니다. <br>그 로그로 5번의 원인을 평가 기록(`api/docs/rag-evaluation/`)에 적는다. 5번에 답이 나오면 「재현되지 않음」과 더한 칸의 값을 적는다. 원인은 어느 길(한 번 호출)에서 확인했는지 함께 적는다. 앱의 스트리밍 길에서는 5번이 다른 모양으로 실패할 수 있다는 점도 한계로 적는다. |
| FR5.4 | 로그 칸이 이 경로에서도 찍히는지 확인해 평가 기록에 적는다. 평가 스크립트는 앱과 같은 게이트(`createCheckedAiGenerationGate`)의 한 번 호출 `generate`를 부른다. `generate`는 `NO_ITEMS`를 던지기 전에 세 값을 로그 객체에 채운다(`recordCollected` 뒤 `ensureItems`, `checked-gate.ts`). 실제로 콘솔에 칸이 찍히는지는 기준선 실행 때 확인한다. |
| FR5.5 | 평가 스크립트는 기록을 날짜 이름으로 쓴다: `api/docs/rag-evaluation/<날짜>.md`, `api/.rag-eval/<날짜>-measure.json`(`rag-eval-report.cjs` `writeEvaluation`). 그래서 같은 날 다시 재면 기준선이 덮어쓰인다. 기준선 실행 뒤 두 파일의 이름을 바꿔 둔다(예: `<날짜>-baseline`). |
| FR5.3 | 원인이 항목 꼴 문제면 고친다. 고치는 범위는 원인이 정해진 뒤 코드 생성 계획에서 정하고, FR3의 지시 한 번 수정 안에 넣는다. 원인이 FR1~FR3으로 풀리는 문제면 따로 고치지 않는다. |

### FR6. 바뀐 규칙을 서비스 문서에 함께 고친다

## 전제

- [assumption] 11/12 측정에 쓴 발행본은 로컬 DB(Docker)에 남아 있다. FR5.2의 「11/12와 같은 조건」과 NFR1의 다시 재기는 모두 그 발행본을 그대로 쓴다. 평가 입력의 정답 위치도 그대로 쓴다. 남아 있지 않으면 이슈 #559대로 처리한다(요구사항 승인 때 팀장 결정). <br>- 발행본만 없고 같은 Catch 3개는 있으면: 같은 Catch 3개로 다시 발행해 기준선과 다시 재기를 한다. 「11/12와 같은 조건이 아니다」라는 한계를 평가 기록에 한 줄 적는다. <br>- Catch까지 없으면: 멈추고 팀장에게 돌아온다.
- 11/12 발행본의 세 Catch에는 모두 작업 사실 둘째 줄(`workFacts[1]`)이 있다. 11/12 측정의 검색 결과 위치에 세 Catch의 `workFacts[1]` 조각이 모두 나왔다. 다시 재는 발행본에 둘째 줄이 없는 Catch가 있으면, 그 Catch는 머리글에 순번만 남는다. 이것은 NFR1(b)·(c)의 한계로 평가 기록에 적는다.
- [assumption] 7번(어느 커밋인지 함께 말하기)과 9·10번(Catch를 섞지 않기)은 FR1의 함께 보내기와 FR2의 머리글로 모델이 알 수 있게 하는 것을 주된 수단으로 본다. 지시(FR3)에는 이슈가 정한 두 가지만 넣는다.
