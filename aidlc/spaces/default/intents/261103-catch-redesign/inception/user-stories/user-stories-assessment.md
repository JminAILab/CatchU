# Catch 개편 — 사용자 스토리 필요성 평가

입력: 요구사항 `aidlc/spaces/default/intents/261103-catch-redesign/inception/requirements-analysis/requirements.md`, 코드 지식 `aidlc/spaces/default/codekb/CatchU/business-overview.md`·`component-inventory.md`.

## 결정

Execute. 스토리를 쓴다.

## 이유

- 사람이 보는 결과가 바뀐다. 구직자·받은 사람 화면의 제목, 작업 사실, 설명 초안, 안내 문장이 바뀐다(요구사항 FR5~FR8).
- 사람이 둘이다. 구직자와 받은 사람이 같은 Catch를 서로 다른 화면에서 읽는다.
- 규칙이 복잡하다. 소속 저장의 단위별 동작(FR1.3·FR1.5·FR1.8), 제목을 정하는 순서와 판정(FR5)이 그렇다. 사람이 얻는 결과로 묶어 두면 기능 설계와 시험이 같은 장면을 본다.

## 고려한 것

| 요소 | 판단 |
|---|---|
| 일의 종류 | 기존 기능을 고치는 개편이다. 새 화면은 없지만 화면에 나오는 결과가 바뀐다 |
| 사람이 보는 범위 | 구직자 Catch 목록·상세, 받은 사람 목록·상세, 분석 고지 |
| 복잡도 | 재분석 소속 규칙, 제목 고르기 순서, 판정 문턱, 규칙 쪽과 AI 쪽의 넣는 순서 |

## 스토리가 가장 도움이 되는 곳

- 재분석 때 같은 작업이 한 Catch로 남고, 작성자 설명이 지켜지는 장면
- 제목과 작업 사실만 보고 무슨 작업인지 아는 장면
- 받은 사람이 AI가 쓴 글과 기록의 글을 구분하는 장면

## 스토리로 두지 않은 것

- Catch 20개 확인과 AI 쪽을 켤지의 결정(FR10)은 팀장의 확인 절차라 스토리로 두지 않는다(질문 Q1). 추적 표에는 N/A와 이유를 적는다.
- 스토리 수용 기준에 담기지 않는 비기능 요구사항(NFR3·NFR5·NFR6·NFR7)은 비기능 요구사항 단계와 기능 설계로 넘긴다.
