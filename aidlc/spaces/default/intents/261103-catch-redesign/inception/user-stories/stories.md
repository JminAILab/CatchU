# Catch 개편 — 사용자 스토리

입력: 요구사항 `aidlc/spaces/default/intents/261103-catch-redesign/inception/requirements-analysis/requirements.md`(FR1~FR10·NFR1~NFR7), 페르소나 `personas.md`(P1 구직자, P2 받은 사람), 코드 지식 `aidlc/spaces/default/codekb/CatchU/business-overview.md`·`component-inventory.md`.

모든 스토리는 Must다(범위 정의: 담는 것은 모두 완성). 「넣는 묶음」은 11/30까지 AI 쪽이 준비되지 않을 때 규칙 쪽을 먼저 넣는 기준이다(요구사항 「의도 분석」).

**정본:** 스토리의 수용 기준과 `requirements.md`의 수용 기준이 다르면 `requirements.md`가 정본이다.

## 묶음 1. 재분석해도 같은 작업은 한 Catch

### US1.1 이미 Catch에 속한 커밋은 다시 쓰이지 않는다

- **이야기:** 구직자(P1)로서, 같은 저장소를 다시 분석해도 이미 Catch에 들어간 커밋이 새 Catch에 다시 들어가지 않기를 원한다. 그래서 목록에 같은 작업이 두 번 나오지 않는다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽(시한: 출시 전 마지막 DB 초기화 전)
- **요구사항:** FR1.1, FR1.2, FR1.3, FR1.4, FR1.6, FR1.7, NFR4
- **수용 기준:**
  - AC1.1.1 Given 분석 결과의 후보가 커밋 c1·c2를 담는다. When 등록된다. Then (회원, 저장소, c1)·(회원, 저장소, c2)가 그 Catch를 가리키고, 같은 SHA를 다른 후보가 담아도 소속은 바뀌지 않는다.
  - AC1.1.2 Given 소속 커밋이 있는 저장소를 재분석한다. When worker가 맥락 조회를 부른다. Then 응답에 소속 커밋 SHA 목록이 있고 큐 요청 메시지의 모양은 그대로다.
  - AC1.1.3 Given 모든 커밋이 이미 다른 Catch 소속인 단위가 있다. When 재분석한다. Then 그 단위는 후보가 아니다.
  - AC1.1.7 Given 소속 커밋 일부를 뺀 단위가 있다. When 재분석한다. Then 후보 판정과 생성 재료의 작업 동일성 열쇠가 같다.
  - AC1.1.4 Given 본인 커밋 30개인 후보가 있다. When 등록된다. Then 30개 모두 그 Catch 소속으로 저장된다.
  - AC1.1.5 Given 같은 수집 결과와 같은 소속 목록이 있다. When 두 번 분석한다. Then 후보의 열쇠와 소속 커밋이 같다.
  - AC1.1.6 Given 소속 기록이 있는 회원이 탈퇴한다. When 탈퇴가 끝난다. Then 그 회원의 소속 기록이 0건이고 기존 탈퇴 연쇄 삭제 시험이 통과한다.
  - AC1.1.8 Given 이슈 번호 나누기(FR2)와 관계없는 단위가 있다. When 기존 작업 동일성 시험을 돌린다. Then 그대로 통과한다(열쇠 만드는 법은 바뀌지 않는다).
- **의존:** 없음
- **INVEST:** 소속 저장 하나로 독립적이고, 수용 기준이 시험 장면 그대로다.

### US1.2 기존 Catch에 커밋이 더해져도 내 설명은 그대로

- **이야기:** 구직자(P1)로서, 이미 만든 Catch의 PR에 나중에 커밋이 더해져도 그 Catch와 내가 쓴 작성자 설명이 그대로 남기를 원한다. 그래서 다시 쓰지 않아도 된다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽
- **요구사항:** FR1.5
- **수용 기준:**
  - AC1.2.1 Given 작성자 설명이 있는 기존 Catch의 PR에 커밋 1개가 더해졌다. When 재분석 결과가 등록된다. Then 새 커밋은 그 Catch 소속이 되고, Catch의 제목·작업 사실·근거·초안·작성자 설명·저장 시각은 바뀌지 않는다.
  - AC1.2.2 Given 통합 PR이 Unit Catch 소속 커밋 5개와 새 커밋 1개를 담는다. When 재분석한다. Then 통합 PR의 새 Catch에는 새 커밋 1개만 속하고, 5개는 Unit Catch 소속 그대로다.
- **의존:** US1.1(소속 저장)
- **INVEST:** PR 단위의 동작만 다룬다.

### US1.3 PR 없이 올린 새 커밋은 새 Catch로

- **이야기:** 구직자(P1)로서, PR 없이 직접 올린 새 커밋이 이미 Catch에 속한 커밋과 섞이지 않기를 원한다. 그래서 앞 Catch가 바뀌지 않는다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽
- **요구사항:** FR1.8
- **수용 기준:**
  - AC1.3.1 Given 이미 소속된 직접 커밋 3개 뒤에 같은 작업의 직접 커밋 2개가 더해졌다. When 재분석한다. Then 새 커밋 2개로 새 Catch가 생기고, 앞의 Catch와 그 소속은 바뀌지 않는다.
- **의존:** US1.1
- **INVEST:** 이어지는 작업이 새 Catch가 되는 것은 한계로 받아들인 동작이다(요구사항 「한계」).

### US1.4 여러 이슈를 가리키는 PR도 Catch 하나

- **이야기:** 구직자(P1)로서, 내 PR의 커밋이 서로 다른 이슈를 가리켜도 그 PR이 Catch 하나로 나오기를 원한다. 그래서 PR로 나눈 내 판단이 그대로 보인다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽
- **요구사항:** FR2.1
- **수용 기준:**
  - AC1.4.1 Given 본인 커밋이 서로 다른 이슈 2개를 가리키는 PR이 있고 이슈 조회가 허용된다. When 분석한다. Then Catch 하나가 나온다.
  - AC1.4.2 Given PR 없이 합친 병합의 커밋이 서로 다른 이슈를 가리킨다. When 분석한다. Then Catch 하나가 나온다.
- **예외:** 지금 나뉘던 단위는 나누기를 끄면 작업 동일성 열쇠가 달라진다(요구사항 FR1.7의 예외).
- **의존:** 없음
- **INVEST:** 나누기를 끄는 하나의 동작이다.

## 묶음 2. 제목과 작업 사실만 보고 무슨 작업인지 안다

### US2.1 내가 쓴 PR 제목·커밋 첫 줄이 제목으로

- **이야기:** 구직자(P1)로서, 내가 쓴 PR 제목이나 커밋 첫 줄이 쓸 만하면 그 글이 Catch 제목으로 나오기를 원한다. 그래서 내 말로 된 제목을 본다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽(AI 쪽을 껐을 때의 동작 포함)
- **요구사항:** FR5.1, FR5.2, FR5.7
- **수용 기준:**
  - AC2.1.1 Given 본인 PR이고 커밋 목록이 잘리지 않았고 다른 계정 커밋이 없다. Then 기록의 글은 PR 제목이다.
  - AC2.1.2 Given 커밋 목록이 잘렸다. Then 기록의 글은 단위 안 첫 본인 커밋(병합 제외)의 첫 줄이다.
  - AC2.1.3 Given 첫 줄에 토큰 모양 문자열이 있다. Then 그 글은 기록의 글로 쓰지 않는다.
  - AC2.1.4 Given AI 쪽이 꺼져 있고 첫 줄이 「fix」다. Then 부실이므로 제목은 조각 제목이다.
  - AC2.1.5 Given AI 쪽이 꺼져 있고 첫 줄이 「로그인 오류 메시지 수정」이다. Then 제목은 그 글이다.
- **의존:** 없음
- **INVEST:** 규칙만으로 시험할 수 있다.

### US2.2 작업 사실에 종류와 기록의 글이 보인다

- **이야기:** 받은 사람(P2)으로서, 작업 사실 첫 줄에서 작업 종류를 보고, 둘째 줄에서 작성자가 쓴 기록의 글을 보기를 원한다. 그래서 SHA나 날짜 대신 무엇을 했는지 읽는다. 12월 AI도 이 줄을 근거로 인용할 수 있다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽
- **요구사항:** FR6.1, FR6.2, FR6.3
- **수용 기준:**
  - AC2.2.1 Given 새로 만든 Catch가 있다. Then 작업 사실 첫 줄은 「PR #n, 상태 …」·「PR 없이 합친 병합」·「PR·병합 없이 들어간 본인 커밋」 가운데 하나이고, SHA 모양 16진수와 날짜가 없다.
  - AC2.2.2 Given 기록의 글이 부실하지 않다. Then 둘째 줄은 「PR 제목: "…"」 또는 「본인 커밋 메시지 첫 줄: "…"」이고 글은 원문 그대로다.
  - AC2.2.3 Given 기록의 글이 부실하다. Then 둘째 줄이 없다.
  - AC2.2.5 Given AI 쪽이 켜져 있고 기록의 글이 "전체를 나타내나"에서만 떨어졌다. Then 작업 사실 둘째 줄은 그대로 있다.
  - AC2.2.4 작업 사실의 어떤 줄도 Claude 출력에서 오지 않는다.
- **의존:** US2.1(기록의 글 고르기)
- **INVEST:** 작업 사실 모양 하나를 다룬다.

### US2.3 기록의 글이 부족하면 근거로 확인된 AI 제목

- **이야기:** 구직자(P1)로서, 기록의 글이 부실하거나 작업 전체를 나타내지 못하면, 바뀐 줄로 확인된 AI 제목이 나오기를 원한다. 그래서 커밋 메시지를 대충 썼어도 무슨 작업인지 알 수 있다.
- **우선순위:** Must · **넣는 묶음:** AI 쪽
- **전제:** FR10 확인 기준(NFR3)을 넘을 때만 켠다.
- **요구사항:** FR4.1, FR4.3, FR4.4, FR4.5, FR5.3, FR5.4, FR5.5, FR5.6, FR5.7, NFR1, NFR2
- **수용 기준:**
  - AC2.3.1 Given 판정 공급자가 OpenAI이고 판정 키가 없다. When 분석한다. Then 판정 호출이 0번이고 제목은 규칙대로(US2.1)다.
  - AC2.3.2 Given 판정 공급자가 Claude다. Then 기존 Claude 키만으로 AI 쪽이 켜지고, 판정 질문 집합은 OpenAI일 때와 같다.
  - AC2.3.3 Given AI 쪽이 켜져 있다. Then 생성 응답에 제목 후보가 항상 있고, 각 후보에 근거 줄 지목이 있으며, Claude 생성 요청 본문에 커밋 메시지·PR 제목이 없다.
  - AC2.3.4 Given 후보가 가리킨 줄에 없는 영어 이름이 제목에 있다. Then 그 후보는 버려진다(재료의 다른 줄에만 있어도 버려진다).
  - AC2.3.5 Given 판정이 "무엇을 했는지"에 0.4, 후보 A 고르기에 0.93을 돌려준다. Then 제목은 A다.
  - AC2.3.6 Given 기록의 글이 "전체를 나타내나"에서만 떨어지고 AI 후보도 모두 떨어졌다. Then 제목은 그 기록의 글이다.
  - AC2.3.7 Given Catch 3개(큰 후보 1개)가 있다. Then 제목·작업 사실·설명 판정 요청은 3번이고 각 요청에 네 종류 질문이 모두 있으며, 전체 판정 호출은 4번 이하다. 판정 호출이 실패해도 다시 부르지 않는다.
  - AC2.3.8 판정 요청에는 바뀐 줄·경로, 본인 PR 제목·커밋 메시지 첫 줄, AI가 쓴 후보 밖의 자료가 없다. 판정 공급자가 Claude여도 같다.
- **의존:** US2.1, US3.2(재료 순서), US3.3(큰 후보의 재료 판정)
- **INVEST:** 판정 공급자를 합성으로 바꿔 끼워 외부 호출 없이 시험한다.

## 묶음 3. 설명 초안

### US3.1 판정을 넘은 설명 문장만 보인다

- **이야기:** 받은 사람(P2)으로서, 설명 초안에서 근거로 확인된 문장만 보기를 원한다. 확인된 문장이 없으면 빈 칸 대신 설명이 아예 없기를 원한다. 그래서 틀린 설명에 속지 않는다.
- **우선순위:** Must · **넣는 묶음:** AI 쪽
- **전제:** FR10 확인 기준(NFR3)을 넘을 때만 켠다.
- **요구사항:** FR7.1, FR7.2, FR7.3, FR7.4, FR7.5, FR8.2
- **수용 기준:**
  - AC3.1.1 Given AI 쪽이 켜져 있다. Then 설명 응답의 문장마다 근거 줄 지목이 있다.
  - AC3.1.2 Given 문장 3개 가운데 하나의 판정이 0.85다. Then 설명은 2문장이다.
  - AC3.1.3 Given 모든 문장이 떨어진다. Then 설명 상태는 NOT_GENERATED이고 실패로 세지 않으며, 구직자·받은 사람 상세에 설명 칸이 화면에도 화면 낭독기에도 없다.
  - AC3.1.4 Given 판정 호출이 오류다. Then 설명은 실패로 기록되고, 상세에는 지금의 안내가 보인다.
  - AC3.1.5 Given 판정 키가 없다. Then 설명은 지금의 틀 문장이다.
  - AC3.1.6 Given 발행 사본에서 검색 조각을 만든다. Then 설명 초안은 조각에 없다.
- **의존:** US3.2(재료 순서), US3.3(큰 후보의 재료 판정)
- **INVEST:** 설명 하나의 생성·판정·표시를 다룬다.

### US3.2 재료가 코드부터, 변경 묶음마다 고르게 담긴다

- **이야기:** 구직자(P1)로서, 설명 초안의 재료가 앞쪽 몇 파일이 아니라 코드부터, 큰 PR이면 변경 묶음마다 고르게 담기기를 원한다. 그래서 설명이 내 작업을 제대로 가리킨다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽
- **요구사항:** FR3.1, FR3.2, FR3.3
- **수용 기준:**
  - AC3.2.1 Given 문서 파일이 앞, 코드 파일이 뒤에 오는 PR이 있다. When 재료를 고른다. Then 코드 줄이 먼저 담긴다.
  - AC3.2.2 Given `FooTest.java`가 있다. Then 시험으로 분류된다.
  - AC3.2.3 Given 서로 다른 폴더 두 곳을 고친 큰 PR이 있다. Then 변경 묶음이 2개 생기고 두 묶음의 줄이 모두 재료에 있으며, 한 파일이 파일 상한을 넘지 않는다.
- **의존:** 없음
- **INVEST:** 규칙만으로 시험할 수 있다.

### US3.3 큰 후보는 판정으로 작업을 대표하는 파일을 고른다

- **이야기:** 구직자(P1)로서, 재료 상한을 넘는 큰 PR에서 작업을 대표하는 파일이 먼저 재료가 되고 다시 만들어지는 산출물은 빠지기를 원한다. 그래서 큰 작업의 설명도 핵심을 가리킨다.
- **우선순위:** Must · **넣는 묶음:** AI 쪽
- **전제:** FR10 확인 기준(NFR3)을 넘을 때만 켠다.
- **요구사항:** FR4.2
- **수용 기준:**
  - AC3.3.1 Given 큰 후보 1개와 작은 후보 1개가 있다. Then 재료 판정 요청은 1번이다.
  - AC3.3.2 Given 합성 판정이 파일 X를 산출물로 답한다. Then X의 줄은 재료에 없다.
  - AC3.3.3 Given 같은 묶음의 파일 A(점수 5)·B(점수 2)가 있다. Then A의 줄이 B보다 먼저 담긴다.
  - AC3.3.4 Given 재료 판정 호출이 실패한다. Then 재료는 규칙 순서(US3.2)로 담긴다.
- **의존:** US3.2
- **INVEST:** 합성 판정으로 외부 호출 없이 시험한다.

## 묶음 4. 화면과 고지

### US4.1 목록에서 긴 제목도 정리돼 보인다

- **이야기:** 구직자(P1)로서, 그리고 받은 사람(P2)으로서, 목록 카드에서 긴 제목이 2줄로 정리돼 보이고 상세에서 전체를 읽기를 원한다. 그래서 기록의 글처럼 긴 제목도 목록을 어지럽히지 않는다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽
- **요구사항:** FR8.1
- **수용 기준:**
  - AC4.1.1 Given 100자 제목이 있다. Then 구직자·받은 사람 목록 카드에서 2줄 뒤 말줄임이고, 상세에서 전체가 보인다.
  - AC4.1.2 Given 말줄임된 카드가 있다. Then 카드 링크의 접근 이름에는 전체 제목이 있다.
- **의존:** 없음
- **INVEST:** 화면 표시 하나를 다룬다.

### US4.2 받은 사람이 제목이 누구의 글인지 안다

- **이야기:** 받은 사람(P2)으로서, 제목이 작성자의 기록의 글이거나 CatchU가 만든 글일 수 있다는 것을 안내로 알기를 원한다. 그래서 AI가 쓴 글을 사람의 글로 착각하지 않는다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽(제목·작업 사실 변경과 함께)
- **요구사항:** FR8.3
- **수용 기준:**
  - AC4.2.1 Given 받은 사람 목록이 있다. Then 안내는 「제목은 GitHub 기록의 글이거나 CatchU가 만든 글이고, 설명은 CatchU가 GitHub 기록에서 자동으로 만들었습니다」다.
  - AC4.2.2 Given 설명 없는 Catch의 상세가 있다. Then 안내는 제목 절만이다.
  - AC4.2.3 Given 제목도 설명도 없는 상세가 있다. Then 안내가 없다.
- **의존:** US2.1(제목이 기록의 글일 수 있음)
- **INVEST:** 안내 문장 하나를 다룬다.

### US4.3 구직자가 AI 설명 초안과 내 설명을 구분한다

- **이야기:** 구직자(P1)로서, Catch 상세의 안내가 AI 설명 초안을 가리킨다는 것을 글로 알기를 원한다. 그래서 같은 화면의 내 작성자 설명과 헷갈리지 않는다.
- **우선순위:** Must · **넣는 묶음:** 규칙 쪽
- **요구사항:** FR8.4
- **수용 기준:**
  - AC4.3.1 Given 구직자 Catch 상세가 있다. Then 안내 문장에 「설명 초안」이 있고 나머지 글은 지금과 같다.
- **의존:** 없음
- **INVEST:** 낱말 하나를 바꾸는 작은 스토리다.

### US4.4 분석 전에 어떤 자료가 어느 AI로 가는지 안다

- **이야기:** 구직자(P1)로서, 분석에 동의하기 전에 내 PR 제목·커밋 첫 줄과 바뀐 줄이 어느 AI 회사로 가는지, Catch에 기록의 글이 들어간다는 것을 고지에서 보기를 원한다. 그래서 알고 동의한다.
- **우선순위:** Must · **넣는 묶음:** AI 쪽(AI 쪽을 켜는 배포와 함께)
- **전제:** FR10 확인 기준(NFR3)을 넘을 때만 켠다.
- **요구사항:** FR9.1, FR9.2, NFR1
- **수용 기준:**
  - AC4.4.1 Given AI 쪽을 켠 배포가 있다. Then 접수 고지 판본이 v3이다. 2절에 AI가 쓰고 판정으로 거른다는 것이, 3절에 실제로 쓰는 판정 공급자와 보내는 항목(바뀐 줄·경로, 본인 PR 제목·커밋 메시지 첫 줄, AI가 쓴 후보)이, 4절에 Catch에 기록의 글이 들어간다는 것이 있다. 판정 공급자가 Claude면 3절에 Anthropic으로 기록의 글이 간다는 것이 있다.
  - AC4.4.2 Given AI 쪽을 켠 배포가 있다. Then web과 api의 첫 이용 고지 판본이 같은 새 값이고 받는 곳 목록에 OpenAI가 있다.
  - AC4.4.3 고지 문구는 그 문구를 바꾸는 PR에서 팀장이 승인했다는 기록이 PR에 있다.
- **의존:** US2.3, US3.1, US3.3(AI 쪽이 실제로 하는 일)
- **INVEST:** 고지 판본 하나를 다룬다.
