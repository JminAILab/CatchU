# Catch 개편 — Bolt 계획

Bolt는 Unit 하나를 기능 설계부터 코드 생성과 시험까지 지나 실제로 돌아가는 결과로 끝내는 구현 묶음이다. 이 계획에서는 Unit 하나가 Bolt 하나다(질문 Q2 A).

입력:
- Unit `inception/units-generation/`
- 계약 `inception/contract-design/contract-summary.md`
- 요구사항 `inception/requirements-analysis/requirements.md`, 스토리 `inception/user-stories/stories.md`
- 구성 요소 `inception/domain-design/components.md`
- 입력 문서 `docs/ai-dlc-input-catch/CatchU_Catch_개편_입력.md` §6·§8
- 이 단계의 답 `delivery-planning-questions.md`(Q1 B, Q2 A, Q3 B)

## 순서

| 순서 | Bolt | Unit | 첫 Unit 골격 | 시한 |
|---|---|---|---|---|
| 1 | B1 | CR1 `cr1-readable-catch` | 예 | 11/30(#441 NFR3 측정 전) |
| 2 | B2 | CR3 `cr3-ai-drafts` | 아니오 | 11/30(#441 NFR3 측정 전) |
| 3 | B3 | CR2 `cr2-commit-assignment` | 아니오 | 출시 직전 DB 초기화 전 |

- 첫 Unit 골격은 다른 Unit보다 먼저 끝내는, 처음부터 끝까지 실제로 이어지는 가장 작은 조각이다. CR1이 그것이다. B1의 실제 연결 확인을 팀장이 승인하기 전에는 B2를 시작하지 않는다.
- 엔진은 CR1 다음에 같은 층의 Unit을 이름 순으로 골라 CR2를 먼저 낸다. 그래서 B1이 끝난 뒤 엔진에 CR3으로 건너가라는 지시를 한 번 내린다(Q1 B). CR2와 CR3은 서로 기대지 않으므로, 이 순서는 의존 그래프를 어기지 않는다.
- 진행 방식은 지금 기록(`unit-major`, `serial`) 그대로다. Unit 하나의 기능 설계 → 비기능 요구사항 → 비기능 설계 → 코드 생성을 마치고 확인을 승인받은 뒤 다음 Unit으로 간다.
- 통합 브랜치(`intent/260925-intent-12`)에는 Unit마다 PR 하나씩 넣는다(Q3 B). 넣는 때는 12월 intent의 통합 확인 뒤이고, merge commit으로 넣는다.

## B1 — CR1 규칙 쪽 Catch (첫 Unit 골격)

- **담는 Unit:** CR1 `cr1-readable-catch`. 스토리 US1.4, US2.1, US2.2(첫 줄·규칙 둘째 줄), US3.2, US4.1, US4.2, US4.3.
- **증명하는 연결:** 고친 후보 판정·재료 고르기·제목 결정(worker)이 실제 분석 흐름에서 이어진다. 흐름은 결과 메시지, api 결과 반영과 Catch 등록, 구직자·받은 사람 화면(web) 순이다. 계약·DB를 바꾸지 않으므로 지금 api와 그대로 맞물린다.
- **완료 조건:**
  - 검증 명령(이 단계에서 정함)이 통과한다.
  - 로컬 실제 연결로 공개 저장소 하나를 분석해 화면에서 아래를 확인한다.
    - 기록의 글이 제목으로 나온다.
    - 작업 사실 첫 줄에 SHA·날짜가 없다.
    - 여러 이슈를 가리키는 PR이 Catch 하나다.
    - 목록 제목이 2줄에서 말줄임으로 끝난다.
    - 받은 사람 안내 문장이 새 문장이다.
  - CR1 PR이 통합 브랜치에 들어간다.
- **확인할 가설:** AI 없이 규칙만으로도 실제 저장소의 Catch 제목·작업 사실만 보고 무슨 작업인지 알 수 있다. 확인 방법은 팀장이 화면에서 읽어 보는 것이다.
- **보여 줄 것:** 로컬에서 띄운 web의 구직자 Catch 목록·상세와 받은 사람 공유 화면이다. 같은 저장소의 지금 결과와 나란히 본다.
- **실제 연결 방법:** 개발 서버는 큐를 연결하지 않는다. 그래서 로컬에서 api·worker·web을 LIVE로 띄워 공개 저장소를 분석한다. #450에서 쓴 로컬 실제 분석 방법과 같다.

## B2 — CR3 AI 쪽

- **담는 Unit:** CR3 `cr3-ai-drafts`. 스토리 US2.2(둘째 줄 지우기), US2.3, US3.1, US3.3, US4.4. 요구사항 FR10.1·FR10.2, NFR3, NFR5.
- **완료 조건:**
  - 검증 명령이 통과한다. 판정은 합성 어댑터로 시험한다.
  - FR10 확인 기록이 있다.
    - Catch 20개에 팀장이 표시한 결과다(CatchU 6개는 수집 결과를 넣는 개발용 실행).
    - 기준 결과, 조정 횟수, AI 쪽을 켤지와 문턱의 결정이 들어 있다.
  - 기준을 넘으면 고지 v3·첫 이용 고지 판본을 함께 넣고 AI 쪽을 켠다.
    - 고지 문구는 PR에서 팀장이 승인한다.
    - OpenAI 판정 키는 SSM에 있어야 한다.
  - 기준을 못 넘으면 AI 쪽을 끈 채 합친다. 이때 고지는 바꾸지 않는다.
  - CR3 PR이 통합 브랜치에 들어간다.
- **확인할 가설:** 판정(0.9 문턱)으로 거른 AI 제목·설명 문장이 틀린 제목 통과 0건, 틀린 문장 통과 1건 이하를 지킨다(NFR3).
- **보여 줄 것:** FR10 확인 기록과 AI 쪽을 켠 로컬 실제 분석 화면이다. 기록의 글이 부실한 Catch는 AI 제목이 보이고, 설명 칸은 판정을 넘은 문장만 보이거나 숨겨진다.

## B3 — CR2 소속 저장

- **담는 Unit:** CR2 `cr2-commit-assignment`. 스토리 US1.1, US1.2, US1.3. 계약 C1·C2, NFR6.
- **완료 조건:**
  - 검증 명령이 통과한다. 소속 기록 마이그레이션과 탈퇴 연쇄 삭제 시험이 포함된다.
  - 로컬 실제 연결로 같은 저장소를 두 번 분석해 두 가지를 확인한다.
    - 두 번째 분석이 새 Catch를 만들지 않는다.
    - 기존 PR Catch에 커밋이 더해져도 작성자 설명이 그대로다.
  - CR3이 먼저 들어가 있으므로, 합칠 때 `worker.generation`·`worker.processing`의 부딪힘을 풀고 NFR4·NFR2 시험을 다시 돌린다(Unit 의존 문서).
  - 배포는 진행 중인 분석이 없을 때 api와 worker를 함께 한다.
  - CR2 PR이 통합 브랜치에 들어간다. 출시 직전 DB 초기화 전이어야 한다.
- **확인할 가설:** 재분석해도 같은 커밋이 Catch를 두 번 만들지 않는다. 한 번 정한 소속과 작성자 설명은 바뀌지 않는다.
- **보여 줄 것:** 같은 저장소를 두 번 분석한 뒤의 구직자 Catch 목록이다. Catch 수와 설명이 그대로다.
