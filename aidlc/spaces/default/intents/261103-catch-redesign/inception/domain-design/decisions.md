# Catch 개편 — 설계 결정 기록

입력: 요구사항 `aidlc/spaces/default/intents/261103-catch-redesign/inception/requirements-analysis/requirements.md`, 스토리 `inception/user-stories/stories.md`, 코드 지식 `aidlc/spaces/default/codekb/CatchU/architecture.md`·`component-inventory.md`, 구성 요소 `components.md`, 이 단계의 답 `domain-design-questions.md`(Q1~Q4).

## ADR-001: 소속 기록은 Catch 등록이 같은 트랜잭션에서 쓴다

- **Context:** 재분석 중복을 막으려면 커밋마다 소속 Catch를 저장해야 한다(FR1.1·FR1.4). 지금 Catch 등록(`registerCandidates`)은 결과 반영이 연 한 트랜잭션 안에서 (회원, 열쇠)로 Catch를 찾고 만든다. 소속 기록이 Catch와 따로 쓰이면, 한쪽만 성공했을 때 소속이 없는 Catch나 없는 Catch를 가리키는 소속이 생길 수 있다.
- **Decision:** 소속 기록은 CatchRegistry(`api.catches`)가 소유한다. Catch를 만들거나 잇는 같은 트랜잭션에서 후보의 소속 커밋을 쓴다. 이미 기록된 SHA가 다시 오면 같은 Catch든 다른 Catch든 조용히 건너뛰고 저장된 소속을 바꾸지 않으며, 결과 반영을 실패시키지 않는다(FR1.1 수용 기준). 기존 Catch에 잇는 경우 새 커밋은 소속으로만 기록하고, 작성자 설명 두 칸을 포함한 Catch 내용은 쓰지 않는다. WorkerContext는 읽기만 한다(Q1).
- **Consequences:**
  - 좋은 점: 등록과 소속이 함께 성공하거나 함께 실패한다. 쓰는 곳이 하나라 "한 번 정한 소속은 바뀌지 않는다"(NFR4)를 한 자리에서 지킨다.
  - 나쁜 점: 등록 트랜잭션이 소속 행 쓰기만큼 길어진다(후보당 최대 수집 상한 3,000 커밋).
  - 받아들인 낭비: worker는 후보가 기존 Catch로 이어질지 모른다. 그래서 기존 PR Catch에 커밋이 더해진 후보에도 생성·판정 호출이 나가고, 그 결과는 버려진다(FR1.5). 이 호출 낭비는 허용한다.
  - 보안: 소속 기록은 회원 자료다. 쓰는 곳이 결과 반영 경로 하나뿐이라, 외부 요청으로 직접 바꾸는 길이 없다.
- **Alternatives Rejected:** 소속 기록만 맡는 새 api 구성 요소를 두고 결과 반영이 등록 뒤에 따로 부르는 안. 트랜잭션 경계가 하나 늘어 어긋남을 다뤄야 하고, MVP에 비해 무겁다.

## ADR-002: 소속 기록의 모양 — (회원, 저장소 ID, SHA) 유일, Catch는 (Catch ID, 회원) 한 쌍으로

- **Context:**
  - `catch_asset`에는 저장소 칸이 없다(코드 지식).
  - 같은 GitHub 계정을 두 회원이 연결할 수 있다(`github_connection`은 회원마다 하나만 막는다). 그래서 같은 저장소에서 두 회원의 본인 커밋 SHA가 겹칠 수 있다.
  - 탈퇴는 회원 행을 지워 연쇄 삭제로 회원 자료를 지운다. 연쇄 삭제가 아닌 외래 키는 탈퇴 시험이 잡는다(FR1.6).
- **Decision:**
  - 소속 기록의 유일 조건은 (회원, GitHub 저장소 ID, 커밋 SHA)다. 저장소 ID는 분석 요청이 가진 GitHub 저장소 ID(`repository_registration.repositoryId`)를 쓴다.
  - Catch는 (Catch ID, 회원) 한 쌍을 가리키는 외래 키로 묶는다. 소속 기록의 회원이 그 Catch의 주인과 다르면 DB가 거부한다.
  - 소속 기록은 Catch를 따라서만 지워진다. Catch는 회원 삭제와 분석 요청 삭제(`fk_catch_asset_source_request_id`) 두 길로 연쇄 삭제된다. 탈퇴 때는 회원 삭제 길로 지워진다.
  - 이를 위해 `catch_asset`에 (catch_id, owner_id) 유일 조건 하나만 더하고, 칸은 바꾸지 않는다(Q2).
- **Consequences:**
  - 좋은 점: 회원끼리 서로의 소속에 영향을 주지 않는다. 다른 회원의 Catch를 가리키는 소속을 DB가 막는다. 소속 기록 쪽 외래 키는 Catch 하나뿐이라 탈퇴 시험이 단순하다.
  - 같은 방식의 선례가 있다. 분석 요청이 저장소 등록을 (회원, 등록, 저장소) 한 쌍으로 가리키는 방식과 같다.
  - 나쁜 점: `catch_asset`에 유일 조건을 더하는 마이그레이션이 하나 생긴다. 이미 (catch_id)가 기본 키라 데이터 충돌은 없다.
  - 보안: 회원 일치를 코드가 아니라 DB 제약으로 막는다(교차 회원 쓰기 차단).
- **Alternatives Rejected:**
  - 저장소 칸과 Catch 외래 키만 두기(회원 없음): 두 회원의 SHA가 겹치면 유일 조건이 충돌해 FR1.1을 지킬 수 없다.
  - 회원 외래 키를 따로 직접 걸기: 지우는 길이 둘이 되고, 회원과 Catch 주인의 일치는 여전히 막지 못한다.
  - `catch_asset`에 저장소 칸 더하기: 기존 Catch의 저장소 값을 채워야 하고 칸 변경이 커진다.

## ADR-003: 이미 소속된 커밋 목록은 맥락 조회 응답으로 넘긴다

- **Context:** 입력 문서는 「요청에 실어」라고 했다. 큐 요청 메시지에 실으면 계약 판본이 오르고 큐 작업이 커진다(최대 3,000 SHA). worker는 시도마다 api 맥락 조회를 이미 부른다.
- **Decision:** WorkerContext 응답에 그 회원·저장소의 소속 커밋 SHA 목록을 더한다. 큐 요청 메시지는 바꾸지 않는다(요구사항 Q4, FR1.2). worker 안에서는 후보 판정과, 생성 단계가 단위·열쇠를 다시 계산하는 곳에 같은 목록을 넘긴다. 같은 수집 결과와 같은 소속 목록이면 같은 열쇠가 나온다(NFR4). 결과 메시지만 판본을 올리고, 맥락 조회 응답 변경과 함께 api·worker를 같이 배포한다(NFR6).
- **Consequences:**
  - 좋은 점: 큐 작업이 커지지 않는다. 목록이 시도 시점의 DB를 그대로 반영한다.
  - 나쁜 점: 맥락 조회 응답이 커진다(최대 3,000 SHA).
  - 보안: 맥락 조회는 worker 전용 내부 경로이고, 응답은 그 시도의 회원·저장소로 좁힌다.
- **Alternatives Rejected:** 큐 요청 메시지에 싣기. 요청 판본도 올라가 배포 때 거부되는 작업이 늘고, 큐 작업이 커진다.

## ADR-004: 판정은 worker의 새 구성 요소로 둔다

- **Context:** 판정 공급자는 외부 회사(OpenAI 기본, Claude 대체)와 키, 켜고 끄기 규칙이 생성 공급자(Claude 생성)와 다르다. 시험은 합성 판정으로 외부 호출 없이 해야 한다(FR4.1). 재료 고르기는 지금 `worker.generation`의 `select`에 있다.
- **Decision:** 판정은 Judgement로 따로 둔다. 판정 공급자 자리와 OpenAI·Claude·합성 어댑터가 여기 들어간다. 재료 순서·변경 묶음과 판정 답 적용은 DraftGeneration 안에 둔다(Q3). 판정 공급자는 AnalysisProcessing의 LIVE 조립이 설정에 따라 만들어 생성기에 넘긴다.
- **Consequences:**
  - 좋은 점: 공급자를 바꾸거나 끌 때 생성 코드를 건드리지 않는다. 판정 입력 제한(NFR1)을 한 자리에서 검사한다.
  - 나쁜 점: worker 패키지가 하나 는다.
  - 보안: 외부로 나가는 판정 입력 항목을 Judgement가 한정한다. 입력 글은 신뢰할 수 없는 입력으로 다룬다.
- **Alternatives Rejected:**
  - 둘 다 생성 안에 두기: 공급자·키 규칙이 생성 코드와 섞인다.
  - 둘 다 새 구성 요소로 두기: 재료 고르기는 지금 자리(`select`)를 고치는 쪽이 작다.

## ADR-005: 작업 사실 둘째 줄은 후보 판정이 규칙으로 정하고, 생성은 지우기만 한다

- **Context:**
  - 지금은 후보 판정(#118)이 작업 사실을 만들고, 생성(#120)은 작업 사실을 바꾸지 않는다.
  - 둘째 줄(기록의 글)은 부실 판단에 달렸다. 부실은 규칙 부실(FR5.2)이거나 판정 부실(FR5.3)이고, 판정은 생성 뒤에 나온다.
  - 작업 사실에는 AI가 쓴 글이 들어가면 안 된다(FR6.3).
- **Decision:**
  - CandidateGrouping이 첫 줄(종류), 기록의 글 고르기, 규칙 부실 기준에 따른 둘째 줄까지 정한다.
  - AI 쪽이 켜져 있고 판정이 "무엇을 했는지 알려 주나" 0.5 미만이면, DraftGeneration이 그 둘째 줄을 지운다.
  - 생성이 작업 사실에 하는 일은 이 줄 지우기 하나뿐이다(Q4). #118·#120 경계는 "생성은 작업 사실을 바꾸지 않는다"에서 "생성은 둘째 줄을 지울 수만 있다"로 좁게 바뀐다.
- **Consequences:**
  - 좋은 점: AI 쪽이 꺼지거나 생성·판정이 실패해도 규칙 결과가 남는다. 생성이 작업 사실에 글을 더하는 길이 없어 FR6.3이 구조로 지켜진다.
  - 나쁜 점: 생성이 작업 사실 구조(둘째 줄 위치)를 알아야 한다.
  - 보안: 작업 사실은 12월 AI 근거로 쓰이므로, AI 글이 들어갈 길을 구조로 막는 것이 근거 오염을 막는다.
- **Alternatives Rejected:** 생성이 판정 뒤 둘째 줄을 더하는 안. 생성이 작업 사실에 글을 더하는 길이 생겨, FR6.3을 코드 규율에만 맡기게 된다.
