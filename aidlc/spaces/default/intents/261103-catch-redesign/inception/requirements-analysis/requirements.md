## 의도 분석

이 개편이 푸는 문제는 둘이다(의도 설명 「Problem Statement」).

- **중복 Catch:** 재분석이 경계를 매번 처음부터 다시 계산한다. 그래서 범위가 밀리거나 새 커밋이 붙으면 같은 작업이 새 Catch가 된다. 이때 구직자가 쓴 작성자 설명은 옛 Catch에만 남는다(코드 지식 「business-overview.md」).
- **읽히지 않는 Catch:** 조각 제목과 SHA가 든 작업 사실로는 구직자도 받은 사람도 무슨 작업인지 알 수 없다. 12월 받은 사람 AI가 읽는 근거에도 작성자 설명 말고는 "무엇을 했나"가 없다.

목표는 다음과 같다.

- 한 번 정한 커밋의 소속을 저장해 재분석에도 같은 작업이 한 Catch로 남게 한다.
- 사람이 쓴 기록의 글(PR 제목·커밋 첫 줄)을 먼저 써서 Catch가 읽히게 한다.
- 기록의 글이 부실하면, AI가 쓰되 기계 대조와 판정을 넘은 글만 쓴다.

담는 것은 모두 완성한다. 규칙 쪽은 먼저 넣을 수 있고, AI 쪽은 그 뒤에 완성해 넣을 수 있다(범위 문서 「시한과 넣는 방식」).

- **규칙 쪽:** FR1·FR2·FR3, FR5.1·FR5.2·FR5.7, FR6, FR8.1·FR8.3·FR8.4
- **AI 쪽:** FR4, FR5.3~FR5.6, FR7.1~FR7.3, FR8.2, FR9, FR10

## 기능 요구사항

### FR1 소속 저장 (우선순위 목록 IB-1)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR1.1 | 한 회원·한 저장소 안에서 커밋 SHA마다 소속 Catch를 저장한다. 커밋 하나는 Catch 하나에만 속한다. | Given 분석 결과의 후보 A가 커밋 c1·c2를 담는다. When 등록된다. Then (회원, 저장소, c1)·(회원, 저장소, c2)가 A의 Catch를 가리킨다. Given 같은 SHA를 다른 후보가 다시 담는다. Then 저장된 소속은 바뀌지 않는다. |
| FR1.2 | 재분석 때 api는 worker가 분석 시도마다 부르는 맥락 조회 응답에 그 회원·저장소의 이미 소속된 커밋 목록을 싣는다. 큐로 가는 분석 요청 메시지는 바꾸지 않는다(Q4). | Given 소속된 커밋이 있는 저장소를 재분석한다. When worker가 맥락 조회를 부른다. Then 응답에 소속 커밋 SHA 목록이 있다. 큐 요청 메시지의 모양은 그대로다. |
| FR1.3 | **공통 규칙.** worker는 다른 Catch에 이미 속한 커밋을 새로 묶는 재료에서 뺀다. 후보 판정과 생성 재료 찾기 양쪽에서 같은 규칙으로 뺀다. 빼고 남은 새 커밋이 없는 단위는 후보가 되지 않는다. | Given 모든 커밋이 이미 다른 Catch 소속인 단위가 있다. When 재분석한다. Then 그 단위는 후보가 아니다. Given 소속 커밋 일부를 뺀 단위가 있다. Then 후보 판정과 생성 재료의 작업 동일성 열쇠가 같다. |
| FR1.4 | 결과 메시지는 후보마다 소속 커밋 전체를 싣는다. 지금처럼 근거로 최근 20건만 싣는 것이 아니다. api는 등록할 때 이를 저장한다. | Given 본인 커밋 30개인 후보가 있다. When 결과가 등록된다. Then 30개 모두 그 Catch 소속으로 저장된다. |
| FR1.5 | **PR 단위(PR 없이 합친 병합 포함).** 열쇠는 지금처럼 PR(병합)로 정한다. 같은 열쇠의 Catch가 있으면 그 Catch로 이어지고, 남은 새 커밋은 그 Catch 소속으로 기록만 한다. 기존 Catch의 제목·작업 사실·근거·초안·작성자 설명은 처음 그대로 둔다. 특히 작성자 설명 두 칸(`author_description`·`author_description_updated_at`)은 이 쓰기에서 건드리지 않는다. 같은 열쇠의 Catch가 없으면 남은 새 커밋으로 새 Catch가 된다. 이렇게 해서 통합 PR이 이미 Unit PR의 Catch에 속한 커밋을 다시 흡수하는 경우를 막는다. | Given 작성자 설명이 있는 기존 Catch의 PR에 커밋 1개가 더해졌다. When 재분석 결과가 등록된다. Then 새 커밋은 그 Catch 소속이 되고, Catch의 내용과 설명·저장 시각은 바뀌지 않는다. Given 통합 PR이 Unit Catch 소속 커밋 5개와 새 커밋 1개를 담는다. When 재분석한다. Then 통합 PR의 새 Catch에는 새 커밋 1개만 속하고, 5개는 Unit Catch 소속 그대로다. |
| FR1.8 | **PR 없는 커밋 묶음 단위.** 남은 새 커밋만으로 묶고 열쇠를 새로 만든다. 그래서 앞 작업에 이어지는 새 커밋은 새 Catch가 된다. 이것은 한계다(입력 문서 §3-4). | Given 이미 소속된 직접 커밋 3개 뒤에 같은 작업의 직접 커밋 2개가 더해졌다. When 재분석한다. Then 새 커밋 2개로 새 Catch가 생기고, 앞의 Catch와 그 소속은 바뀌지 않는다. |
| FR1.6 | 탈퇴 때 소속 기록도 회원 자료와 함께 지운다. | Given 소속 기록이 있는 회원이 탈퇴한다. When 탈퇴 4단계가 끝난다. Then 그 회원의 소속 기록이 0건이다. 기존 탈퇴 연쇄 삭제 시험이 통과한다. |
| FR1.7 | 작업 동일성 열쇠(`wi1`)를 만드는 법, Catch 내용, 본인 기여 판정은 바꾸지 않는다. 다만 FR2로 나누기가 꺼진 단위의 열쇠가 달라지는 것은 예외다. | 기존 작업 동일성 시험이 FR2와 관계없는 단위에서 그대로 통과한다. |

### FR2 이슈 번호로 나누지 않기 (IB-2)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR2.1 | 이슈를 읽는 요청에서도 한 PR이나 PR 없이 합친 병합을 이슈 번호로 나누지 않는다. 10월 후보 판정의 「나누기」(#118)를 끈다. | Given 본인 커밋이 서로 다른 이슈 2개를 가리키는 PR이 있고, 이슈 조회가 허용된다. When 분석한다. Then Catch 하나가 나온다. |

### FR3 AI 초안 재료의 순서와 변경 묶음 (IB-3)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR3.1 | 재료는 파일 종류 순서로 담는다. 순서는 코드 → 시험 → 설정 → 문서 → 그 밖이다. 도구 폴더는 빼지 않는다. 종류 판정의 빈틈을 메운다. 메울 것은 `*Test.java`·`*Tests.cs` 같은 이름 꼴, 대소문자를 가리지 않는 `Tests/` 폴더, `.ipynb`, 모바일 프로젝트 구조다. | Given 문서 파일이 앞, 코드 파일이 뒤에 오는 PR이 있다. When 재료를 고른다. Then 코드 줄이 먼저 담긴다. Given `FooTest.java`가 있다. Then 시험으로 분류된다. |
| FR3.2 | 재료 상한을 넘는 큰 후보는 변경 묶음으로 나눈다. 순서대로 시도한다. 먼저 저장소마다 바뀐 파일이 갈라지는 폴더 깊이로 나누고, 계층별 구조면 파일 이름 앞부분으로 나눈다. 시험 파일은 대상 파일의 묶음에 붙인다. 그래도 나뉘지 않으면 묶음 하나로 둔다. | Given 서로 다른 폴더 두 곳을 고친 큰 PR이 있다. When 재료를 고른다. Then 묶음이 2개 생긴다. |
| FR3.3 | 묶음마다 고르게 담고, 한 파일이 차지하는 양에 상한을 둔다. 묶음 안에서는 FR3.1의 순서를 따른다. 전체 재료 상한(24,000 B)은 그대로다. | Given 묶음 2개인 큰 후보가 있다. Then 두 묶음의 줄이 모두 재료에 들어 있고, 한 파일이 상한을 넘지 않는다. |

### FR4 판정 공급자 (IB-5·IB-6)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR4.1 | worker에 판정 공급자 자리를 둔다. 기본 공급자는 OpenAI Decisions API(`gpt-6-luna`, 미국 처리)다. 참일 확률·고르기·점수로만 답한다. 판정 공급자가 OpenAI면 OpenAI 판정 키가 설정돼 있을 때만, Claude면(FR4.5) 기존 Claude 키로 AI 쪽(Claude가 쓰는 제목·설명과 판정)이 켜진다. 시험은 합성 판정으로 한다. | Given 공급자가 OpenAI이고 판정 키가 없다. When 분석한다. Then 판정 호출이 0번이고, 제목은 규칙(FR5.2·FR5.7), 설명은 틀 문장이다. Given 공급자가 Claude다. Then 기존 Claude 키만으로 AI 쪽이 켜진다. Given 합성 판정이 있다. Then 판정 경로를 외부 호출 없이 시험할 수 있다. |
| FR4.2 | 재료 상한을 넘는 큰 후보에만 재료 판정 요청을 후보 하나에 한 번 보낸다. 입력은 바뀐 파일 목록(경로·상태·줄 수·앞 몇 줄)이다. 묻는 것은 셋이다. 규칙이 모르는 파일은 작업 내용·작업 기록·다시 만들어지는 산출물 중 무엇인지, 묶음이 애매한 파일은 어느 씨앗 묶음에 속하는지(또는 공통인지), 파일마다 이 작업을 얼마나 대표하는지(1~5)다. 판정 답은 재료 담기에 이렇게 쓴다. 갈래는 입력 문서 §4-1 표대로 작업 내용을 먼저, 작업 기록을 그다음에 담고, 산출물은 담지 않는다. 묶음 안에서는 대표 점수가 높은 파일부터 담고, 같은 점수면 FR3.1의 종류 순서를 따른다. 판정이 없거나 실패한 큰 후보는 FR3의 규칙 순서를 그대로 쓴다(산출물 거르기 없음의 한계와 같음). | Given 큰 후보 1개와 작은 후보 1개가 있다. When 분석한다. Then 재료 판정 요청은 1번이다. Given 합성 판정이 파일 X를 산출물로 답한다. Then X의 줄은 재료에 없다. Given 같은 묶음의 파일 A(점수 5)·B(점수 2)가 있다. Then A의 줄이 B보다 먼저 담긴다. Given 재료 판정 호출이 실패한다. Then 재료는 FR3 규칙 순서로 담긴다. |
| FR4.3 | AI 쪽이 켜져 있으면 판정은 생성 뒤 Catch마다 요청 한 번이다. 그 요청에 부실("무엇을 했는지 알려 주나"), 전체("작업 전체를 나타내나"), 제목 고르기, 설명 문장 질문을 모두 담는다(최대 400개). | Given Catch 3개가 있다. Then 제목·작업 사실·설명 판정 요청은 3번이고, 각 요청에 네 종류 질문이 모두 있다. |
| FR4.4 | 판정 호출이 실패해도 다시 부르지 않는다. | Given 판정 호출이 실패한다. Then 같은 후보에 판정 호출이 다시 나가지 않는다. |
| FR4.5 | 한국어 판정이 FR10 기준에 못 미치면 같은 질문을 Claude로 판정할 수 있어야 한다. 이때 판정 입력의 기록의 글(PR 제목·커밋 첫 줄)이 Anthropic으로 간다. 고지(FR9.1)는 실제로 쓰는 판정 공급자에 맞춰 적는다. | 설정 하나로 판정 공급자를 Claude로 바꿀 수 있고, 같은 질문 집합으로 판정한다. |

### FR5 제목 (IB-4·IB-7·IB-12)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR5.1 | **기록의 글을 고른다.** 본인이 연 PR이고 그 PR에 다른 계정의 커밋이 없다고 확인됐으면 PR 제목을 쓴다. 확인됐다는 것은 커밋 목록을 끝까지 받은 경우다. 있는지 알 수 없으면 PR 제목을 쓰지 않는다. 그 밖에는 단위 안 본인 커밋(병합 커밋 제외) 가운데 가장 처음 것의 메시지 첫 줄을 쓴다. 기록의 글은 자르지 않는다. 비밀값·개인정보 가리기 규칙에 걸리는 글은 쓰지 않는다. | Given 본인 PR이고 커밋 목록이 잘리지 않았고 다른 계정 커밋이 없다. Then 기록의 글은 PR 제목이다. Given 커밋 목록이 잘렸다. Then 첫 본인 커밋의 첫 줄이다. Given 그 첫 줄에 토큰 모양 문자열이 있다. Then 기록의 글로 쓰지 않는다. |
| FR5.2 | **규칙으로 부실을 판단한다.** 글이 거의 없으면 부실이다. 문자·숫자가 2자 이하이거나, 짧은 흔한 낱말 목록의 낱말 하나뿐인 경우다. AI 쪽을 껐을 때는 이 규칙만으로 판단한다. | Given 첫 줄이 「fix」다. Then 부실이다. Given AI 쪽이 꺼져 있고 첫 줄이 「로그인 오류 메시지 수정」이다. Then 그 글이 제목이다. |
| FR5.3 | **판정으로 부실을 판단한다(AI 쪽).** 판정 질문 "무엇을 했는지 알려 주나"의 확률이 0.5 미만이면 부실이다. 본인 커밋이 2개 이상인 단위의 커밋 메시지는 "이 Catch의 작업 전체를 나타내나"도 묻는다. 그 확률이 0.5 미만이면 Claude 후보 쪽으로 간다. 이 질문들은 FR4.3의 한 요청에 고르기 질문과 함께 담는다. | Given 판정이 "무엇을 했는지"에 0.4를 돌려준다. Then 기록의 글을 제목으로 쓰지 않고 고르기에서 0.9 이상인 Claude 후보를 쓴다. |
| FR5.4 | **Claude가 제목 후보를 쓴다.** AI 쪽이 켜져 있으면 기록의 글이 쓸 만해도 생성 호출에서 제목 후보를 항상 쓴다(입력 문서 §5-3의 시험용 후보 표시와 같다). 바뀐 줄만 보고 쓴다. 후보마다 근거로 삼은 줄을 가리킨다. 목적·효과·평가(「성능 개선」 같은 말)는 쓰지 않는다. 코드 이름·파일 이름은 바뀐 줄의 표기 그대로 쓴다. 커밋 메시지와 PR 제목은 Claude에 보내지 않는다. | Given AI 쪽이 켜져 있고 기록의 글이 쓸 만하다. Then 생성 응답에 제목 후보가 있다. Claude 요청 본문에 커밋 메시지·PR 제목이 없다. 응답의 각 후보에 근거 줄 지목이 있다. |

## 한계

- **소속 저장이 막지 못하는 것:** 첫 분석의 경계(PR 범위로 막는다), rebase로 SHA가 바뀐 커밋, PR 없는 단위에서 이어지는 작업이 새 Catch가 되는 것(FR1.8). 열쇠가 바뀌어 새 Catch가 생기면 작성자 설명은 옛 Catch에 남고 옮기지 않는다(12월 FR2.5 그대로).
- **산출물 거르기를 넣지 않은 결과:** 판정 없이 규칙만 쓰는 경로(AI 쪽을 껐거나, 판정이 실패한 큰 후보)에서는 코드처럼 보이는 산출물(`*.min.js`·외부 라이브러리 폴더·생성 코드)이 재료 앞자리를 차지할 수 있다.
- **DB 초기화:** 출시 직전 초기화 때 작성자 설명과 텍스트 자료도 함께 사라진다(Q3).
- **확인 표본:** 모두 커밋 규칙이 있던 팀장 저장소다. 일반 저장소에서 기록의 글이 부실한 비율과 그때의 판정은 이 확인으로 알 수 없다.
- **12월 NFR7·FR1.4 예외:** 공통 안내 한 줄로는 Catch마다 제목 출처가 구분되지 않는다. 기록의 글을 쓴 Catch는 작업 사실의 「PR 제목: "…"」 줄로 출처가 간접적으로 보인다. 시연에서 문제가 보이면 출시 직전 초기화 전에 출처 칸을 더할 수 있다.
- **같은 모델의 한계:** Claude 판정으로 바꾸면 같은 회사 모델이 쓰고 채점한다.
