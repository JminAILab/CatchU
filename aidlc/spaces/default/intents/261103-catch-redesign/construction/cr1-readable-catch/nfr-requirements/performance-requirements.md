# CR1 규칙 쪽 Catch — 성능 요구사항

입력:
- 기능 설계 `construction/cr1-readable-catch/functional-design/`(functional-spec.md W2·W3, rules.md BR3.3·BR5)
- 요구사항 `inception/requirements-analysis/requirements.md`(NFR2)
- 생성 한도 `worker/docs/generation-limits.md`

CR1은 외부 호출을 늘리지 않는다. 계산이 늘어나는 곳은 worker 안의 기록의 글 고르기와 재료 묶음 나누기다. 둘 다 이미 받은 수집 결과로만 계산한다.

| ID | 요구사항 | 확인 방법 | 근거 |
|---|---|---|---|
| NFR2.1 | 생성 호출은 지금처럼 후보마다 한 번이다. 기록의 글이 제목이면 조각 제목 고쳐 쓰기 호출을 하지 않는다. 그래서 생성 쪽 호출 수는 지금 이하다. | 호출 수 시험: 기록의 글 제목 후보는 고쳐 쓰기 호출이 0번이다. 그 밖의 후보는 지금과 같다. | NFR2, BR3.3 |
| NFR2.2 | 판정 호출은 0번이다(CR1에는 판정이 없다). | 호출 수 시험: CR1 경로에서 판정 공급자를 부르지 않는다. | NFR2 |

## 확인 사항 (인셉션 NFR이 없는 설계 제약)

- **처리 시간:** 재료 묶음 나누기와 종류 판정은 이미 받은 파일 목록으로만 하는 계산이고, 외부 호출이 없다.
  - 판정 기준(설계 제안값): 수집 상한 크기(커밋 3,000, `worker/app/collection/limits.py`)의 합성 후보 하나에서 재료 고르기가 5초 안에 끝난다.
  - 이 값은 생성 호출 하나의 시간 제한(45초, `generation-limits.md`)보다 충분히 작게 잡았다. 그래야 재료 계산이 요청 마감(큐에서 꺼낸 뒤 3,600초 − 60초)을 쓰는 몫이 되지 않는다.
  - 확인: 위 합성 후보로 재료 고르기 시험을 돌려 걸린 시간을 단언한다.
- **요청 크기:** 생성 요청의 크기는 지금 상한(자료 24,000 B, 지시문 포함 32,000 B)을 넘지 않는다(FR3.3, BR5.6).
  - 확인: 시나리오 S12·S26.
- **화면:** 목록 카드 제목은 CSS로만 줄이므로 렌더링 성능에 새 요구사항이 없다.
