# CR1 규칙 쪽 Catch — 보안 요구사항

입력:
- 기능 설계 `construction/cr1-readable-catch/functional-design/`(functional-spec.md, rules.md)
- 요구사항 `inception/requirements-analysis/requirements.md`(NFR1)
- 계약 `inception/contract-design/contract-summary.md`(C5·C6·C7)
- 기술 스택 `aidlc/spaces/default/codekb/CatchU/technology-stack.md`
- 이 단계의 답 `nfr-requirements-questions.md`(Q1 A·Q2 A)

CR1은 새 외부 호출, 새 저장 칸, 새 API, 인증·권한 변경이 없다. 바뀌는 것은 작성자의 GitHub 원문(PR 제목·커밋 첫 줄)이 제목과 작업 사실에 들어가 화면과 12월 AI 근거로 나가는 길이다.

## 인셉션 NFR1(외부 AI 처리)에서 물려받는 요구사항

| ID | 요구사항 | 확인 방법 | 근거 |
|---|---|---|---|
| NFR1.1 | Claude 생성 요청에는 지금처럼 바뀐 줄만 보낸다. 기록의 글(PR 제목·커밋 첫 줄)을 생성 요청에 넣지 않는다. | 요청 본문 시험: 기록의 글이 있는 후보의 생성 요청에 그 글이 없다. | NFR1, BR2.7 |

## 확인 사항 (인셉션 NFR이 없는 보안 제약)

- **가리기:** 기록의 글은 가리기 검사(비밀값·개인정보 꼴)를 통과한 글만 제목·작업 사실에 쓴다. 걸리면 그 단위는 기록의 글이 없다(FR5.1, BR2.4).
  - 확인: 토큰·이메일·전화번호 꼴이 든 첫 줄이 제목·작업 사실에 나오지 않는다(S5).
  - 가리기 검사는 2,000자를 넘는 글을 통째로 가린다(`worker/app/generation/redact.py`의 `MAX_LINE_CHARS`). 그래서 2,000자를 넘는 첫 줄은 기록의 글이 되지 못한다.
- **검사 한 곳:** 가리기 검사는 하나의 검사를 후보 판정과 생성이 함께 쓴다. 두 곳의 판단이 갈리지 않는다(BR2.4, BR2.7).
  - 확인: 코드 검토에서 검사 함수가 한 곳에만 있는지 본다.
- **화면 그리기:** 화면은 기록의 글을 글자로만 그리고 HTML로 해석하지 않는다. 줄임 표시는 보이는 모양에만 쓴다(FR8.1, BR6.1).
  - 확인: `<script>`·태그 꼴 제목이 글자 그대로 보이는 화면 시험.
- **로그:** 운영 로그에 기록의 글 원문을 남기지 않는다(team.md 「Code Style」).
  - 확인: 기록의 글이 든 후보로 처리한 뒤, 작업 사실 둘째 줄(`workFacts[1]`)과 제목 원문이 후보·생성·소비자 로그에 없는지 시험한다. 지금 시험(`worker/tests/test_consumer_processor.py`)은 `workFacts[0]`과 나의 기여만 본다.

## 위협 고려

- **원문 노출:** 작성자가 커밋 첫 줄에 남긴 비밀값이 공개 Catch로 나갈 수 있다. 가리기로 막는다. 정규식이 모든 비밀값을 잡지는 못한다(가리기 문서의 알려진 한계). 이 한계는 지금 생성 재료와 같다.
- **화면 삽입:** 제목에 태그 꼴 글이 들어올 수 있다. React가 글자로 그린다.
- **AI 지시 주입:** 커밋 첫 줄의 지시문이 12월 받은 사람 AI 근거에 들어갈 수 있다. NFR1.2로 확인한다.
- **권한:** 기록의 글은 회원 본인 분석 결과에서만 만들고, 공개 범위는 지금 Catch 공개 규칙을 그대로 따른다. 새 권한 경로는 없다.

## 해당하지 않는 것

- **NFR2(호출 횟수):** 판정 호출이 없고, 생성 호출은 줄어든다. 성능 요구사항에서 다룬다.
- **NFR3(판정 품질), NFR5(비밀값 보관):** CR3이 맡는다.
- **NFR6(배포 호환):** CR1은 계약을 바꾸지 않는다. 신뢰성 요구사항의 확인 사항에서 다룬다.
