# CR2 소속 저장 — 보안 요구사항

입력: CR2 기능 설계(`rules.md` BR3.1·BR3.6·BR3.7, `entities.md`), 요구사항 NFR4, 결정 기록 ADR-001~003, 팀 규칙(비밀값·사용자 자료를 로그에 남기지 않음), 이 단계의 답 `nfr-requirements-questions.md`(Q2 B).

소속 기록(커밋 SHA와 소속 Catch)은 회원 자료다. 비밀값은 아니지만 회원의 작업 기록을 이어 볼 수 있으므로 회원 자료로 다룬다.

## 요구사항

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| NFR4.6 | 소속 기록을 쓰는 길은 결과 반영 트랜잭션의 Catch 등록 하나뿐이다. 외부 요청(회원·공개 API)으로 소속을 쓰거나 고치는 길을 두지 않는다. | 코드 검토: 소속 표에 쓰는 곳이 등록 함수 하나다. 새 컨트롤러·경로가 없다. |
| NFR4.7 | 소속 행의 회원은 그 Catch의 주인이어야 하고, DB가 이를 막는다((catch_id, member_id) → catch_asset(catch_id, owner_id) 외래 키). 코드 검사에만 맡기지 않는다. | 시험: 다른 회원의 Catch ID로 소속 행을 쓰면 DB가 거부한다. |
| NFR4.9 | 소속 기록을 읽는 길은 worker 전용 맥락 조회 하나뿐이다. 그 시도의 회원·저장소 것만 돌려준다. 지금의 worker 키 인증(`X-Worker-Key`)과 오류 응답을 그대로 쓴다. | 시험: 다른 회원·다른 저장소의 소속은 응답에 없다. 키 없는 요청은 지금처럼 401이다. |
| NFR4.10 | 로그에는 SHA를 남기지 않는다. 새로 더하는 로그는 건수(받은 소속 SHA 수, 소속으로 버린 단위 수)뿐이다. api 오류 로그에도 SHA·DB 예외 원문을 싣지 않는다(지금 규칙). | 시험: 후보 판정 로그 줄에 40자 16진수가 없다. |
| NFR4.11 | 탈퇴 때 회원의 소속 기록이 0건이 된다. 소속 기록은 Catch를 따라 연쇄 삭제된다. | 탈퇴 연쇄 삭제 시험이 소속 기록을 포함해 통과한다. 삭제 목록 문서에 소속 기록 행이 있다. |

## 위협과 대응

| 위협 | 대응 |
|---|---|
| 같은 GitHub 계정을 연결한 두 회원이 서로의 소속을 바꾼다 | 소속 열쇠에 회원이 있어 서로 겹치지 않는다(ADR-002). 한 회원의 쓰기는 다른 회원 행에 닿지 않는다 |
| 조작된 결과 메시지가 다른 회원의 Catch에 소속을 붙인다 | 결과 수신은 지금처럼 수신 기록·시도·회원을 대조한다. 그래도 남는 교차 쓰기는 NFR4.7의 외래 키가 막는다 |
| 맥락 조회 응답이 다른 회원의 커밋 목록을 흘린다 | 조회를 시도의 회원·저장소로 좁힌다(NFR4.9) |
| 소속 목록이 커져 worker가 응답을 거부한다(가용성) | 응답 상한을 1 MiB로 올린다(신뢰성 요구사항 NFR6.3) |

## 범위 밖

- 소속 기록의 암호화나 별도 보존 기간은 두지 않는다. Catch와 같은 보존·삭제를 따른다.
- 새 비밀값이 없다.
