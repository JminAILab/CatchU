# CR2 소속 저장 — 신뢰성 요구사항

입력: CR2 기능 설계(`functional-spec.md` W7, `rules.md` BR1.6·BR1.7·BR1.8·BR3.2·BR3.3·BR3.5·BR4.1), 요구사항 NFR4·NFR6, 결정 기록 ADR-001.

| ID | 요구사항 | 확인 기준 |
|---|---|---|
| NFR4.1 | 같은 수집 결과와 같은 소속 집합이면 후보의 열쇠·본인 커밋 목록이 같다. 후보 판정과 생성 재료 찾기는 같은 집합을 같은 함수로 뺀다. | 시험: 같은 입력으로 두 번 돌린 후보의 열쇠·`ownCommitShas`가 같다. 재료 찾기가 모든 후보의 단위를 찾는다. |
| NFR4.2 | 한 번 쓴 소속은 바뀌지 않는다. 같은 (회원, 저장소, SHA)가 다시 오면 같은 Catch든 다른 Catch든 쓰지 않고 넘어가며, 결과 반영을 실패시키지 않는다. | 시험: 다른 Catch를 가리키는 같은 SHA를 다시 등록해도 저장된 소속이 그대로이고 반영이 성공한다. |
| NFR4.3 | Catch 등록과 소속 쓰기는 한 트랜잭션이다. 소속 쓰기가 실패하면 Catch 등록과 결과 반영 전체가 롤백되고 지금처럼 반영 실패로 기록된다. | 시험: 소속 쓰기에서 DB 오류가 나면 Catch·소속·등록 연결이 모두 남지 않는다. |
| NFR4.12 | 빼기 뒤 연결이 비는 커밋 묶음도 분석을 멈추지 않는다(BR1.8). 소속 집합이 비면 결과가 지금과 같다(BR1.7). | 시험: 소속 커밋을 거쳐서만 이어진 새 커밋 둘이 Catch 하나가 되고 고정 문장이 묶음 설명에 있다. 빈 집합 시험이 지금 결과와 같다. |
| NFR6.1 | 결과 메시지 판본은 api 수신 타입·worker 결과 조합·계약 YAML에서 같은 "3"이고, 요청·진행 상태·수신 응답은 "2" 그대로다. | 시험: worker가 "3"으로 보내고 api가 "3"을 받으며 "2" 결과는 `SCHEMA_INVALID`로 거부한다. |
| NFR6.2 | CR2는 api와 worker를 같은 배포에 넣고, 진행 중인 분석이 없을 때 배포한다. 옛 판본을 함께 받는 처리는 두지 않으며, 배포 중 걸린 분석은 실패로 끝나도 된다. | 배포 안내(코드 요약 「운영에 넣을 때」)에 이 조건이 적혀 있다. |

## 실패 동작

| 상황 | 동작 |
|---|---|
| 소속 기록 조회 실패(api) | 맥락 조회 500, worker는 지금 처리대로 그 시도를 끝낸다 |
| 맥락 조회 응답의 새 칸이 없거나 모양이 틀림(worker) | `CONTEXT_RESPONSE_INVALID`로 끝난다(지금 해석 실패와 같음) |
| 같은 결과 재전송 | 저장된 등록 묶음만 재응답하고 소속을 다시 쓰지 않는다(BR3.5) |
| CR2 배포 전에 만든 Catch | 소속 없음. 다음 재분석에서 같은 열쇠로 이어질 때 써진다 |

## 범위 밖

- 소속 기록의 백업·복구 장치를 따로 두지 않는다. DB 전체의 지금 운영을 따른다.
- 자동 재시도를 더하지 않는다.
