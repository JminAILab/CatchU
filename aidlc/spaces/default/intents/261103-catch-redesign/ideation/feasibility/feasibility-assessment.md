# Catch 개편 — 실현 가능성 평가

입력: 승인된 의도 설명 `aidlc/spaces/default/intents/261103-catch-redesign/ideation/intent-capture/intent-statement.md`, 이 단계의 답 `feasibility-questions.md`(Q1~Q7). 근거 문서는 `docs/ai-dlc-input-catch/CatchU_Catch_개편_입력.md`와 #445다. 시장 조사 단계는 건너뛰었다(내부 기능 개편).

## 결론

**실현 가능하다. 다만 조건이 셋 붙는다.**

1. AI 쪽(Claude가 쓰는 제목·설명과 OpenAI 판정)은 Catch 20개 확인을 넘을 때만 켠다. 못 넘으면 끈 채로 합쳐도 의도 설명의 성공 기준 가운데 AI와 무관한 것(중복 없음, 기록의 글 제목, 작업 사실 첫 줄, 이슈로 나누지 않음)은 채울 수 있다. (Q3, 의도 설명 「Success Metrics」)
2. 소속 저장은 출시 직전 DB 초기화 전에 들어가야 한다. 그 뒤에는 기존 Catch의 소속을 되살릴 길이 없으므로, 이 시한을 넘기면 소속 저장의 효과는 다음 초기화까지 미뤄진다. (Q2, Q6)
3. OpenAI 계정·키와 비밀값이 아직 없다. 팀장이 만들기 전까지 Catch 20개 확인을 할 수 없다. (Q5)

## 기술적 실현 가능성

| 영역 | 고칠 곳 | 판단 | 근거 |
|---|---|---|---|
| 소속 저장 | api의 소속 저장 표, 분석 요청·결과 메시지(소속 커밋 목록 두 칸, 판본 올림), 탈퇴 삭제 목록. worker는 이미 소속된 커밋을 새로 묶는 재료에서 뺀다. | 가능. 열쇠 값·Catch 내용·본인 기여 판정은 바꾸지 않으므로 기존 재분석(U7) 위에 더하는 변경이다. | Q1, Q2 |
| 제목·작업 사실·설명 초안 | worker의 만들기(제목 순서, 작업 사실 첫 줄, 설명 초안, 기계 대조) | 가능. 수집 기록에 커밋 메시지·PR 제목·PR을 연 계정이 이미 있어 GitHub 조회가 늘지 않는다. 기계 대조는 12월 api 모듈을 그대로 못 써서 worker에 다시 짠다. | Q1 |
| 재료 고르기와 판정 자리 | worker의 재료 찾기, 새 판정 공급자 자리 | 가능. 판정이 없거나 실패하면 규칙 결과로 돌아갈 수 있다(실패 때 동작은 기능 설계에서 정함). | Q1, Q3 |
| 이슈 번호 나누기 끄기 | worker의 후보 판정 「나누기」 | 가능. 기존 동작을 끄는 변경이다. | Q1 |
| 고지 | 분석 고지 v3(api), 첫 이용 고지 판본(web·api 두 상수) | 가능. 문구는 그 PR에서 팀장이 승인한다. | Q1, Q4 |
| 제목 출처 안내 | web 화면의 공통 안내 한 줄 | 가능. 어느 화면에 둘지는 요구사항 분석에서 정한다. | Q1 |
| 받은 사람 쪽 | 검색 조각·질의응답·요약·MCP | 바꾸지 않는다. | Q1 |

| 수집 상한(#424)이 늦어진다 | 진행 중인 별도 이슈 | 큰 PR이 Catch로 나오는 전제가 흔들린다 | 전제로 두고 RAID 기록에 둔다 | Q2 |

## Assumptions & Open Questions

- 공수는 이 단계에서 추정하지 않았다. 두 시한을 지킬 수 있는지는 납품 계획에서 판단한다. (Q6)
- 판정 요청이 실패했을 때 규칙 결과로 갈지는 기능 설계에서 정한다. (Q1, 입력 문서 §4-3)
