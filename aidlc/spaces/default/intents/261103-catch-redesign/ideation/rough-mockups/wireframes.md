# Catch 개편 — 화면 초안

입력: 승인된 의도 설명 `aidlc/spaces/default/intents/261103-catch-redesign/ideation/intent-capture/intent-statement.md`, 범위 문서 `ideation/scope-definition/scope-document.md`, 우선순위 목록 `ideation/scope-definition/intent-backlog.md`, 이 단계의 답 `rough-mockups-questions.md`(Q1~Q4).

새 화면은 없다. 기존 화면 네 곳에서 제목·작업 사실·설명 초안의 모양이 바뀌고, 받은 사람 화면의 기존 자동 생성 안내 문장이 고쳐진다. 반응형·접근성은 기존 화면 기준을 그대로 따른다(Q4). 아래 글과 예시는 모양을 보이려는 것이며 실제 문구는 요구사항 분석·기능 설계에서 정한다.

**변경 요청(화면 초안 검토 뒤) 반영:** 받은 사람 화면에는 이미 자동 생성 안내가 있다(`web/src/features/recipient/recipient-format.ts`의 `generatedNotice`, 10/8 결정 문장 「제목과 설명은 CatchU가 GitHub 기록에서 자동으로 만들었습니다」, 목록과 상세에 나옴). 그래서 Q1 답의 "받은 사람 상세에 한 줄을 더한다"를 "이 문장을 고친다"로 바꾼다. 받은 사람 상세의 설명 초안 칸도 이미 있다(설명이 없으면 「생성된 설명 초안이 없습니다.」).

## 바뀌는 곳 한눈에

| 화면 | 바뀌는 것 | 근거 |
|---|---|---|
| 구직자 Catch 목록 카드 | 제목이 기록의 글이나 AI 글로 길어질 수 있어 2줄까지 보이고 넘치면 말줄임 | Q2 |
| 구직자 Catch 상세 | 제목 전체, 작업 사실 첫 줄(종류만)과 기록의 글 한 줄, 설명이 없으면 설명 칸 숨김. 기존 "제목·설명은 자동 생성될 수 있다" 안내는 그대로 | Q1, Q2, Q3 |
| 받은 사람 Catch 목록 | 제목 2줄까지, 넘치면 말줄임. 목록 위의 기존 자동 생성 안내 문장을 고친다 | Q2, 변경 요청 |
| 받은 사람 Catch 상세 | 제목 전체, 작업 사실 첫 줄과 기록의 글 한 줄, **기존 자동 생성 안내 문장을 고침**(새 줄 없음), 판정을 넘은 설명 문장이 없으면 설명 칸 숨김 | Q2, 변경 요청 |

## 1. 구직자 Catch 목록 카드

```
+-- Catch card ------------------------------
| [title: 2 lines max, ellipsis on overflow]
|   예) 테마 생성 모달의 css를 고치고 입력 순서
|       를 바꾼 작업으로, 저장 버튼의 비활성...
| [status: 확인 전 / 미공개]
+--------------------------------------------
```
<!-- Text fallback: 목록 카드는 제목을 2줄까지 보이고 넘치면 말줄임으로 끝낸다. 그 아래 확인·공개 상태가 있다. -->

- 제목은 자르지 않고 저장하며 화면에서만 2줄로 줄여 보인다. 전체는 상세에서 본다. (Q2)
- 접근성: 카드 제목은 기존 목록의 제목 수준을 따른다. 말줄임된 제목도 카드 링크의 접근 이름에는 전체 제목을 쓴다(기존 카드가 제목을 접근 이름으로 쓰는 방식 유지). (Q4)

## 2. 구직자 Catch 상세

```
+-- Catch detail ----------------------------
| h1 [title: full text, wraps]
| [기존 안내] 제목·설명은 자동 생성될 수 있으므로
|            아래 근거와 대조한다   (변경 없음)
|
| h2 작업 사실
|   PR #7, 상태 병합됨                 <- 종류만, SHA·날짜 없음
|   PR 제목: "..."                     <- 쓸 만한 기록의 글일 때만
| h2 나의 기여
|   ...                                (변경 없음)
| h2 근거                              (변경 없음)
| h2 Catch 설명 초안                   <- 판정을 넘은 문장이 없으면 칸째 숨김
|   [1~3 sentences]
| h2 생각해 볼 질문                    (변경 없음)
+--------------------------------------------
```
<!-- Text fallback: 상세는 제목 전체, 변경 없는 기존 자동 생성 안내, 작업 사실(첫 줄은 종류만, 쓸 만한 기록의 글이면 한 줄 더), 나의 기여, 근거, 설명 초안(없으면 칸째 숨김), 생각해 볼 질문 순서다. -->

- 작업 사실 첫 줄의 종류는 「PR #7, 상태 병합됨」, 「PR 없이 합친 병합」, 「PR·병합 없이 들어간 본인 커밋」이다. 둘째 줄은 「PR 제목: "…"」 또는 「본인 커밋 메시지 첫 줄: "…"」이다. (범위 문서 「범위 안」, 입력 문서 §5-2)
- 설명 초안이 없으면 칸을 숨기고 안내하지 않는다. 판정·생성 오류로 실패한 경우만 지금처럼 안내한다. (Q3)
- 접근성: h1 제목, `main` 안에서 h2 구역 순서는 기존과 같다. 키보드 진입점은 기존 상세와 같다. 숨긴 설명 칸은 화면 낭독기에도 나오지 않는다. (Q4)

<!-- Text fallback: 받은 사람 목록은 위에 기존 자동 생성 안내 문장(고침)이 있고, 카드마다 제목을 2줄까지 보이고 넘치면 말줄임으로 끝내며, 상세 보기로 들어간다. -->

- 접근성: 카드 제목은 기존처럼 h3이고, 상세 보기의 접근 이름(「{제목} 상세 보기」)에는 전체 제목을 쓴다. (Q2, Q4)

## 4. 받은 사람 Catch 상세

```
+-- Catch 상세 ------------------------------
| h1 Catch 상세
| h2 [title: full text, wraps]
| [기존 안내 문장, 고침] 제목과 설명은 CatchU가 ...
|   (기록의 글이거나 AI 글일 수 있다는 뜻으로. 문구는 요구사항 분석에서)
| [작업 사실]
|   PR #7, 상태 병합됨
|   PR 제목: "..."
| [설명 초안]                          <- 판정을 넘은 문장이 없으면 칸째 숨김
| [그 밖의 기존 내용]                  (변경 없음)
+--------------------------------------------
```
<!-- Text fallback: 받은 사람 상세는 h1 Catch 상세, h2 제목 전체, 기존 자동 생성 안내 문장(고침), 작업 사실(종류와 기록의 글 한 줄), 설명 초안(없으면 칸째 숨김), 그 밖의 기존 내용 순서다. -->

- 안내는 새 줄을 더하지 않고 기존 문장(10/8 결정 「제목과 설명은 CatchU가 GitHub 기록에서 자동으로 만들었습니다」)을 제목이 기록의 글이거나 AI 글일 수 있다는 뜻에 맞게 고친다. 받은 사람이 AI 글과 기록의 글을 구분해야 한다는 12월 NFR7의 빈틈을 이 문장이 메운다. Catch마다 출처 칸은 두지 않는다. (변경 요청, 의도 설명 「Initial Scope Signal」)
- 안내 문장 고치기는 AI 쪽 켜기와 묶지 않고 제목·작업 사실 변경과 함께 넣는다. 기록의 글 제목은 규칙 쪽에서도 나오기 때문이다. 이 문장은 목록과 상세에 항상 보이므로, AI 쪽을 켜기 전·후 Catch가 섞여도 안내가 있는 상세와 없는 상세가 갈리지 않는다. 우선순위 목록의 IB-9(AI 쪽과 함께)는 이 결정으로 바뀐다. (변경 요청)
- 설명 초안은 구직자 상세(Q3)와 같게, 판정을 넘은 문장이 없으면 칸을 숨기고 판정·생성 오류일 때만 기존 안내(「생성된 설명 초안이 없습니다.」 등)를 보인다. (변경 요청)
- 접근성: 안내 문장의 위치·모양과 제목 구조(h1·h2), 초점 이동은 기존과 같다. 숨긴 설명 칸은 화면 낭독기에도 나오지 않는다. (Q4)

## Assumptions & Open Questions

- 고친 안내 문장의 문구는 요구사항 분석에서 정한다. (변경 요청)
- 범위 문서에 가정으로 남겼던 "IB-9는 AI 쪽과 함께 넣는다"는 변경 요청으로 바뀌었다. 안내 문장 고치기는 제목·작업 사실 변경(규칙 쪽)과 함께 넣는다. 요구사항 분석에서 이 결정을 따른다. (변경 요청)
- 좁은 화면과 공백 없는 긴 제목에서 2줄 제한이 어떻게 보이는지는 정하지 않았다(검토에서 위험으로 받음).
