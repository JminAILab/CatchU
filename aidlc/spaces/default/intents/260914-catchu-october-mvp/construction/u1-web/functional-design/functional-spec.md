# web — 최소 Functional Design

## 적용 범위

기존 회원·수신자 화면을 [API v1](../../../inception/contract-design/contract-summary.md)에 연결한다. 이 문서는 ui Unit의 화면 흐름/상태 정본이며 엔티티·DB·업무 규칙 저장소를 만들지 않는다. 세부 컴포넌트·props/state·시각 표현·시험 코드는 각 담당의 **개발 이슈로 보완**한다.

## 화면 흐름

| ID | 화면 책임·순서 | 계약/판정 주체 |
|---|---|---|
| W1 | 회원 진입 → 본인 프로필/연동 상태 확인 → 자가 입력 프로필 저장 → 지원 저장소 선택. 입력 출처와 검증 사실을 구분. 배치는 [내 자산 화면 구조](#내-자산-화면-구조) 참조 | A/팀원 2. /me·/me/profile·/me/repositories. Access JWT 소비; 실제 OAuth 경로/연동 상세는 OQ-A1 |
| W2 | 현재 고지·범위를 읽고 동의 → 사용자 분석 요청 → 접수/기존 작업 응답 표시 → 상태 조회. 배치는 [내 자산 화면 구조](#내-자산-화면-구조) 참조 | E/팀원 2. /analysis-notice·/analysis-requests. 새 요청 202, 같은 저장소 진행 작업 200, 다른 저장소 진행 작업 409 |
| W3 | processing/application을 구분해 진행·실행 불명·정상 0건·부분 실패·반영 실패 표시 → ownerResultsReady와 registeredCatchIds로 본인 결과 진입. 배치는 [내 자산 화면 구조](#내-자산-화면-구조) 참조 | E/팀원 2. 후보 존재/F 종료만으로 결과 버튼 활성화하지 않음; 조회 오류는 작업 실패/0건이 아님 |
| W4 | 본인 Catch 목록/상세 → 근거·본인 기여 확인 → 초안/생성 실패 상태와 최소 질문 확인 → 불일치 표시. 배치는 [내 자산 화면 구조](#내-자산-화면-구조) 참조 | B/팀원 4. /catches와 confirmation/mismatch. 없는 동기·성과·초안을 보충하지 않음. 최소 질문은 본인만, 답변 저장 없음 |
| W5 | 근거·기여 확인 완료 → ‘지금 공개’ 기본 제안 → 사용자의 자산별 별도 공개 선택 → 서버 확인 후 공개 상태 표시. 숨기기도 서버 결과로 반영 | B/팀원 4. visibility PUT. 초안 없어도 다른 공개 조건 충족 시 가능; 확인 완료만으로 자동 공개하지 않음 |
| W6 | 본인 링크 목록 → 제목·선택 비밀번호로 발급 → 링크 복사/상태 확인 → 선택 링크 중단 | C/팀원 3. /share-links·stop. 현재 공개 Catch 전체의 링크이며 자산 선택 없음. 대표/공개 Catch 없이도 발급 가능 |
| W7 | 수신 URL → 공통 접근 불가 또는 비밀번호 입력 → 허용된 현재 프로필/Catch 목록 → Catch 상세 | C/D·팀원 3. /public/links/{token}·unlock·catches/{catchId}. 로그인 없는 접근, 현재 권한 판정은 api |
| W8 | 명세 code로 오류 안내 → 조회 실패는 재조회 안내, 실패 확정·반영 실패로 닫힌 요청의 재요청은 서버 retry.allowed 확인 → 사용자 새 동의 후 W2. 배치는 [내 자산 화면 구조](#내-자산-화면-구조) 참조 | E/팀원 2·오류 공통 팀원 3. 새 키/분석 POST 자동 재호출 없음; 정상 0건/부분 결과 보완/재분석은 보류 |

## 내 자산 화면 구조

2026-09-24 팀장 결정([후속 입력 링크](../../../../../../../../docs/ai-dlc-input-mvp/2026-09-14_followup.md))으로 Ideation 거친 화면 설계(rough-mockups)의 자산 GitHub 탭, 분석별 결과 목록(W03-R), 분석 상태·실패 별도 화면(A-02·A-03) 배치를 대체한다.

자료 탭은 **Catch 탭 하나**이며 GitHub 탭은 두지 않는다. 포트폴리오·자기소개서·이력서는 준비 중 탭으로 두고 누르면 준비 중 안내만 보인다. 로그인 홈 CTA의 기존 ‘자산 GitHub 탭’ 목적지는 ‘Catch 탭의 저장소 연결 관리’로 바꾼다.

Catch 탭 위쪽에는 **GitHub 저장소 연결 관리** 영역과 [연결 관리] 버튼을 두며 버튼으로 모달을 연다. GitHub 미연동이면 프로필의 GitHub 연동 화면으로 안내하고, 연동 성공 뒤 Catch 탭의 저장소 연결 관리로 돌아온다. 복귀 시 모달을 자동으로 열지는 담당 개발 이슈에서 정한다.

모달 위쪽은 **연결된 저장소**(분석 요청이 접수된 저장소) 목록이다. 상태 아이콘을 누르면 아코디언으로 분석 상태를 간단히 보여 준다. 성공·부분 실패에서는 [이 저장소 Catch 보기]로 해당 저장소 필터를 적용하며, 본인 결과 진입 조건은 W3를 유지한다. 실패에서는 서버가 허용하는 재요청으로 이어진다. 모달 아래쪽은 **연결할 수 있는 저장소**의 선택·동의·요청이다. 동의 내용을 버튼 앞에 보이고 버튼 하나로 동의와 요청을 처리한다.

연결된 저장소의 이름은 분석 상태 응답에 추가하지 않는다. web이 `/me/repositories`의 선정 목록과 저장소 식별자로 합쳐 표시한다. 분석 요청이 선정 목록 안에서만 이뤄지는 현재 계약을 유지하며, 선정 목록에서 빠지는 저장소가 생기면 그때 계약 보완을 검토한다.

| 상태 아이콘 | 표시 기준과 아코디언 문구 |
|---|---|
| 분석 중 | 대기·실행 중과 실행 불명, 요청이 닫히기 전(lifecycle ACTIVE)의 반영 대기·반영 중·반영 실패를 묶는다. 실행 불명은 실행 확인이 아직 안 됐다는 문구로, 닫히기 전의 반영 실패는 반영 실패 문구로 구분한다. 요청이 닫혔는데(lifecycle CLOSED) 반영 완료가 아니면 분석 중에 두지 않고 실패로 표시한다. 아래 「화면 상태 전이」 표의 의미를 유지한다 |
| 성공 | 오류 없이 정상 완료. Catch가 없으면 ‘검토할 Catch가 없습니다’를 덧붙인다 |
| 부분 실패 | 제공된 결과와 실패 영향을 구분해 보여 준다. 10월 재요청 대상이 아니다 |
| 실패 | 서버가 확정한 처리 실패(FAILED, 처리 시한 초과 포함)와, 요청이 닫혔는데(lifecycle CLOSED) 반영 완료가 아닌 반영 실패(반영 대기 중 처리 시한 초과 포함)를 표시한다. 반영 실패로 닫힌 요청은 처리 결과를 분석 실패로 바꾸지 않고 반영 실패 문구로 구분한다. 재요청 버튼은 현재 `retry.allowed`가 true일 때만 보인다 |

실패 재요청은 고지 요약과 **[동의하고 다시 요청]** 버튼 하나로 새 동의·새 요청을 만든다. 기존 동의를 재사용하지 않는다. 10월에는 연결 해제 버튼을 두지 않으며, 해제 뒤 자료 처리는 후속 입력의 OQ2에서 정한다.

Catch 탭 아래쪽에는 **저장소 필터가 있는 Catch 목록**을 두고, Catch 상세는 **모달**로 연다. 목록·상세는 F가 생성하고 B가 저장한 `title`을 사용하며 구직자의 제목 편집은 제공하지 않는다. 필터와 상세 모달의 식별자는 주소 파라미터에 담아 새로고침·뒤로 가기·재로그인 뒤에도 같은 화면을 연다. W03-R과 A-02·A-03 별도 화면은 두지 않는다.

| 담당 | 화면·연결 책임 |
|---|---|
| 팀원 3(D) | 저장소 연결 관리 영역과 모달 |
| 팀원 4(B) | 내 자산 페이지 틀·탭 머리, 저장소 필터·Catch 목록·Catch 상세 모달 |
| 팀원 2(A/E) | 분석·저장소 API와 상태 의미, GitHub 연동 화면. 팀원 3의 모달 PR에서 상태 묶음을 검토 |

담당이 만나는 곳은 세 곳이다. Catch 탭 안 연결 관리 영역의 자리, [이 저장소 Catch 보기]가 거는 필터의 주소 파라미터(이름은 팀원 4가 결정), 모달을 닫을 때 Catch 목록 다시 불러오기다. 세부 배치·문구·표현은 각 개발 이슈에서 맞춘다.

## 화면 상태 전이

| 상황 | 표시·다음 행동 | 금지하는 치환 |
|---|---|---|
| 조회 시작 → 응답 | 로딩 → 성공 목록/상세 또는 정상 빈 자료 | 응답 전 빈 배열을 정상 0건으로 확정 |
| 조회 오류 | LOOKUP_FAILED 또는 API code에 맞는 안내; 재조회 가능 | processing=FAILED/EMPTY로 간주, 새 분석 자동 요청 |
| QUEUED/RUNNING | 접수/진행 표시; 같은 요청의 상태 확인 | F 결과가 없는데 생성 완료/등록 성공 표시 |
| UNCERTAIN | 실행 확인이 아직 안 됨을 표시. 처리 시한이 지나 서버가 닫으면(FAILED/APPLIED/CLOSED) 그 상태를 실패로 표시 | 화면이 시간 경과만으로 스스로 실패 확정·새 동의 없는 재요청 |
| EMPTY·APPLIED | 정상 등록 적합 후보 0건 안내 | 오류/근거 부족 설명을 수집 실패로 혼합 |
| PARTIAL_FAILED | 제공된 결과와 실패 영향을 분리 표시; 준비된 등록 ID만 열람 | 실패 후보를 존재하는 Catch처럼 표시, 추가 생성 자동 호출 |
| APPLY_FAILED | 처리 결과와 서비스 반영 실패를 구분. 요청이 닫히기 전에는 분석 중에 반영 실패 문구로, 닫히면(CLOSED) 실패로 표시. 재요청 안내는 서버 retry.allowed가 true일 때만(RECOVERING은 쓰지 않음) | 분석 성공으로 표시, 반영 복구 중으로 안내, retry.allowed 없이 재요청 |
| FAILED·APPLIED·CLOSED | 서버 retry.allowed가 true인 경우만 사용자 재요청 안내 | 과거 동의 재사용, 선행 이력 검사 우회 |
| 확인/공개 저장 중 → 응답 | 동일 상태 변경의 진행·성공·실패 표시; 실제 서버 값 기준 | 확인만으로 PUBLIC 표시, 거부된 공개를 성공 처리 |
| 수신 접근 | LINK_UNAVAILABLE는 없는/중단/만료 공통 안내. 유효 링크의 LINK_PASSWORD_REQUIRED/LINK_PASSWORD_INVALID는 비밀번호 분기. LINK_UNLOCK_LIMITED는 차단 안내이며 Retry-After의 남은 시간을 표시 | 존재/중단/만료 상세 사유 노출, grant만으로 현재 권한 우회, 차단을 비밀번호 오류로 표시 |

수신자 목록의 정상 0건은 200 응답의 빈 catches이며 조회 실패 500과 구분한다. 숨김·타인·없는 Catch 상세는 RESOURCE_UNAVAILABLE 공통 안내다. 다음 조회마다 현재 권한을 적용하며 이미 열린 화면을 실시간 회수하는 기능은 약속하지 않는다.

## API 소비 경계

| 항목 | web의 책임 |
|---|---|
| 목록 형식 | 회원은 items/page, 수신자는 profile/catches/page. opaque cursor를 해당 조회에만 사용; 다음 페이지도 새 권한 판정 결과를 표시 |
| 오류 | code/message/details를 소비하되 message 문자열 비교로 분기하지 않음. 알 수 없는 응답은 오류로 표시하고 성공/빈 자료로 추정하지 않음. #88 공통 해석 적용 |
| 재전송 | 생성 POST의 Idempotency-Key는 같은 사용자·operation·본문 요청에 유지. 응답 불명에 새 키로 자동 재요청하지 않음; 서버의 기존 자원 응답을 사용. 429 RATE_LIMITED는 처리하지 않은 요청이라 확정 결과로 보지 않고 키를 유지하며, Retry-After 뒤 같은 키로 다시 보낸다 |
| 공개 자료 | PublicCatch에 있는 title·근거·기여·draft만 표시. reflection·본인 확인/불일치·내부 ID·링크 제목을 수신자 화면에서 재구성하지 않음 |
| 초안/질문 | GENERATED와 실패/미생성을 구분. draft.content=null을 생성된 설명으로 표시하지 않음. 최소 질문의 상세 표시는 B 개발 이슈, 수신자 공개/답변 저장 없음 |
| 상태 정본 | 권한·등록·공개·링크 유효성·재요청 가능성은 api가 판정. worker와 직접 통신하거나 ProcessingEvent/ResultReceipt를 web에서 해석하지 않음 |
| 보호·캐시 | 본문/응답 영속 캐시 금지, no-store 준수. JWT/grant·비밀번호·민감 원문을 URL/로그로 추가 유출하지 않음. 실제 토큰/grant 저장·수명은 OQ-A1/C1 담당 설계 |
