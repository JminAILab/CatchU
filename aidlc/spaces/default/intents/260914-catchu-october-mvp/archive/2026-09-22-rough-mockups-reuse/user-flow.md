## 주 흐름 — 구직자에서 수신자까지

```text
구직자: Google 로그인
  -> 프로필/이름 확인 [A 원안: 미저장 시 입력·저장, 저장됨이면 홈]
  -> 홈 [GitHub 미연동도 진입 가능]
  -> GitHub 연동 필요 시 프로필에서 연결
  -> 내 자산 GitHub 탭
  -> 선정 저장소 선택 + 동의 내용 + 단일 동의·요청 행동
  -> 접수 확인 -> 현재 분석 상태 확인
  -> 실제 수집·분석 / 결과 보존·전달 / 서비스 반영
  -> 본인 결과 열람 가능 확인
  -> 해당 결과 목록 W03-R -> Catch 상세 W04 [기존 연결 원안]
  -> 근거·생성 초안·질문 확인
  -> 별도 공개 선택 W05 또는 미공개 유지
  -> 대표 없이 링크 발행 L01 -> 발행 결과 L02 / 관리 L03

수신자: URL 접근
  -> 링크 유효성 -> 설정됐으면 비밀번호 -> 현재 공개 권한 확인
  -> 현재 공개 프로필 + 허용 자료 목록 V02
  -> 허용 Catch 생성 본문·근거 V03 -> 목록 복귀
```

텍스트 설명: 분석은 사용자 요청으로 시작하고, 결과 확인과 자산 공개는 별도 행동이다. 링크는 대표 없이 발행하며 공개 자산 0개여도 발행할 수 있다. 기본 경로의 공개 선택은 사용자 가치 흐름의 예시이고 발행 필수 조건이 아니다. 수신자에게는 링크 조건과 현재 권한을 만족한 자료만 제공한다. 최초 이름 필수 여부·상세 배치는 A 원안, 담당 간 최종 이동은 연결 미결을 유지한다.

## 접수·진행·결과 흐름 — 기존 E §5.5 통합

| 현재 상황 | 사용자 행동/확인된 사실 → 다음 표현 | 지위·남은 연결 |
|---|---|---|
| 요청 전 | 로그인·연동·선정 대상·동의 확인 → 명시 요청 | 기존 기준. 미저장 선택을 자동 재전송하지 않음 |
| 요청 전송 중 | 응답 대기 → 접수 확인/거절/불명 | E 원안의 반복 제출 방지·이탈≠취소를 재사용 |
| 접수 확인 | 접수 작업 식별 → 해당 상태 조회 | 접수≠F 시작/완료. F 사실이 없는 진행률/남은 시간 생성 금지 |
| 접수 불명 | 접수 여부 확인 → 확인된 작업 조회 또는 거절 안내; 불명 지속은 그대로 안내 | 미접수/실패/0건으로 단정하거나 자동 재제출하지 않음. 참조·조회 방법은 E/D 계약 |
| 같은 사용자·저장소 진행 중 중복 | 기존 작업 반환 → 상태 확인 | AR 방향. **반영 대기·복구까지 확대는 E 제안**, F/D 수용 미결 |
| 접수 후 대기/진행 | 현재 확인된 상태 조회 → 갱신 | AR/AE 주기적 조회 방향. 종료/오류 후 재개·간격·이탈/재접속 세부는 미결 |
| 상태 조회 실패 | 조회 실패 안내 → 상태 다시 불러오기 | 분석 실패로 바꾸지 않음. 직전 상태는 최신 여부 확인 불가로 표시하는 E 원안 |
| F 종료·결과 보존/전달 | 서비스 반영/열람 준비 확인 → 아직 미확인이면 준비 중 표현 | DB 반영까지 끝나야 사용자 완료라는 AR/AE 방향. 반영 복구 실패 확정 시점은 미결 |
| 반영 완료·본인 열람 준비·결과 있음 | 결과 확인 → W03-R → W04 | 완료≠Catch 확인/공개·정확성 검증. E/F/B의 정보 대응은 후속 계약 |
| 정상 조회로 Catch 0장 확인 | 기존 ‘이번 분석에서 검토할 Catch가 없습니다’ 안내 원안, 결과 버튼 없음 | 결과 0건을 정상 완료로 볼 근거는 F 확인 대상. 조회 오류는 이 분기로 보내지 않음 |
| 근거 부족·부분 결과 | 제한을 드러내는 표시가 필요하며 구체 결과 의미·열람 여부는 미결로 표시 | F 사실 원문과 B/D 판단 필요. 성공/전량 실패·공개 허용을 공통 세션이 확정하지 않음 |
| 분석 실패 확인 | 실패 안내 → 기존 자료·링크 보존 → 허용된 명시 재요청 진입 | 자동 분석 재시도 없음. 부분 결과 비노출 원안은 삭제 정책이 아님 |
| 결과 재전달 | 이미 보존된 결과를 재전달·반영 | 새 분석과 구분, 추가 LLM 호출 근거가 아님. 중복 반영 방지 계약은 후속 |

서버 내부 자료·비밀값·객체 위치를 화면에 노출하는 설계가 아니다. UI에는 사용자용 대상·확인된 상태·조회 결과·다음 행동만 표현한다. 재요청 가능 시점·폴링 수치·상태 이름을 임의 확정하지 않는다.

## 실패·재요청과 재접속

```text
실패 이력 -> A-03 실패 내용
  -> 새 요청 허용 조건 확인 [E/F/D 미결 부분 유지]
  -> 사용자 명시 재요청
       + 요청 중 -> 접수 확인 창 -> [진행 상태 보기] -> 해당 작업 조회
       + 거절 -> 확인된 사유·다음 행동
       + 접수 불명 -> [요청 상태 확인] -> 확인된 사실에 따라 분기

상태/결과 화면 이탈 -> 재방문 -> 내 자산 GitHub 탭 -> 같은 분석 조회
  (이탈·재조회가 새 분석을 만들거나 기존 자료를 삭제하지 않음)
```

AE §5.1의 재인증 원안: 접수 전에는 같은 계정·이름·연결 확인 뒤 선택/동의로 돌아가 미저장 입력을 다시 작성한다. 접수 후에는 작업 식별·현재 권한이 확인되면 해당 상태를 조회하고, 조건이 부족하면 자산 GitHub 탭에서 안내한다. **접수 불명은 재인증 후에도 접수 여부 확인부터**이며 미접수로 가정하지 않는다. 다른 계정으로 로그인하면 이전 본인 자료 표시를 재개하지 않는 원안이다. D는 원안과의 이견·참조 없음 안내만 보완한다. 팀원 2에게 이 흐름을 다시 설계하라고 요청하지 않는다.

## 본인 결과 확인·공개·복귀

기존 A/B/D 원안: `A-02 또는 GitHub 이력 → W03-R → W04 → 같은 W03-R → 진입 출처`. 한 장이어도 목록을 거친다. AE §5.1/§5.4와 #23 Q2 최신 D 제안은 방향이 같지만 B 팀원 4의 인계 수용·출처 없음/대상 없음/권한 없음 표현은 남아 있다. 배치·라우트 최종 합의 완료로 보고하지 않는다.

| 상황 | 본인 행동·기대 경계 |
|---|---|
| 미공개 Catch 열람 | 근거/초안·질문 확인. 열람만으로 확인 완료·공개되지 않음 |
| 명시 확인 행동 | 확인 표시 저장과 공개 선택은 별개. 정확성 검증 통과로 표시하지 않음 |
| 불일치 발견 | 불일치 표시·미공개 유지. 내부 선택 공유(G) 경로와 본문 편집/재생성은 첫 MVP에 넣지 않음 |
| 공개 선택 | 별도 명시 행동과 성공 확인 후 공개 상태 표시. 실패를 성공으로 표시하지 않음 |
| 공개 Catch 숨김 | 현재 권한 변경이 기존 링크 열람에도 적용. 링크 자체 중단/삭제와 구분 |
| 결과 목록/상세 읽기 실패 | 조회 실패·권한/대상 없음 안내, 0건·분석 실패로 바꾸지 않음 |

Catch별 확인·불일치·공개 상태는 유지하되 결과 전체 검토 수·불일치 수 집계는 만들지 않는다. B 원안의 후속 대표·구 헤더·G 버튼은 팀원 4가 현재 범위에 맞춰 보완한다.

보류는 자동 추가/제외 또는 발행 시점 스냅샷 중 어느 쪽을 선택했다는 뜻도 아니다. 대표 보존을 미룬 결정에서 본문/자산 집합 정책을 추론하지 않는다.

## 평가용 문서 점검과 후속 인계

문서상 점검 범위: 로그인→자산 탭→선택/동의→접수→실제 결과 준비→본인 확인→별도 공개→대표 없는 발행→수신자 열람을 연결했다. 조회 실패·접수 불명·실패 재요청·숨김·중단/만료·비밀번호·0개를 별도 경계로 대조했다. 원안·미결 표시는 제거하지 않았다. 이는 실제 실행 시험이나 각 담당자의 수용 확인이 아니다.

| 다음 담당 판단 | 기존 입력에서 이미 있는 것 | 필요한 보완만 |
|---|---|---|
| D/B 화면 이동 | AE §5.1/5.4·A2/A3·W의 경유/복귀 원안 | A-01/02/03 배치, 탭 표현·출처 없음 안내 및 B 인계 수용 |
| E/F/D 복구·재요청 | AE §5.5의 접수/조회/반영 대기·복구·재전달 의미표 | 반영 대기·복구까지 기존 작업 반환 확대의 수용 여부, 실패 확정/새 요청 허용 시점 |
| F/B/D 결과 의미 | E의 결과 수/조회·열람 준비 구분 | F 결과 범위·근거 부족/0건/부분 실패의 실제 제공 가능 사실과 B/D 표현 |
| A/C/D 프로필·복귀 | AE §5.1·LC 현재 프로필 기준 | 담당자 간 남은 표시·복귀 차이. A/E 전체 재작성 없음 |

API·스키마·큐 호환성·인증/보존 수치·동시성·NCP 복구는 AR을 재사용할 후속 공식 설계로 넘긴다. M07 실제 배포/보존/복구 검증과 C01/C02·자료 보호·기존 착수 제한은 유지한다. 추가 호출·실험·구현·CI 착수 없이 문서만 통합했다. 단계 승인은 별도이며 현재 미결이 해결되거나 서비스가 검증됐다고 표시하지 않는다.
