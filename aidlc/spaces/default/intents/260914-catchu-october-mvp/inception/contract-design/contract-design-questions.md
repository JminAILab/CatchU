# Contract Design — API 명세 v1 작성 전 결정

## 기존 결정과 작성 범위

| 경계 | 작성할 계약 | 책임 |
|---|---|---|
| web → api 회원 | 계정/연동·분석 요청/상태·본인 Catch 확인/공개·링크 관리 OpenAPI | 팀원 2 A/E, 4 B, 3 C/D |
| 비로그인 수신자 → api | 현재 공개 Catch 전체와 공개 프로필, 없는 URL/중단/만료 공통 응답, 별도 비밀번호 분기 OpenAPI | 팀원 3 C, A/B 제공 자료 검토 |
| api ↔ worker | 제공자 비종속 요청·결과 메시지 스키마, 합성 가짜 생성기로 연결 가능한 형식 | 팀원 1 F, 2 E, 4 B 검토 |

- 링크–자산 연결은 만들지 않으며 최소 생각해볼 질문은 수신자 응답에서 제외한다. B가 초안·질문의 서비스 정본을 관리한다.
- 접수·처리·반영·본인 열람 준비와 조회 실패를 구분한다. 정상 0건·부분 실패·반영 실패를 오류 없이 구분하고 등록/본인 열람 준비 확인 뒤에만 결과 진입을 제공한다.
- 같은 사용자·저장소의 진행 중 요청은 기존 작업을 반환한다. DB 반영 대기·복구 중을 진행 중에 포함하며 자동 분석 재시도는 추가하지 않는다.
- E/F 전송은 #77 이후다. BullMQ·실제 제공자 연결은 정하지 않는다. A/F 자격정보 제공과 F 임시 결과의 보존 위치/수명은 담당자 제안·검토의 Open questions로 구분한다.
- 재분석·과거 동의 재사용·기존 Catch/링크 변경·원본 재공개·실패 후 초안 보완은 미결로 유지한다. 아래 Q1은 실패 요청의 사용자 재요청 경계만 묻는다.
- 명세 v1은 승인 후 개발 기준 계약이다. 이후 이슈 → PR → 해당 담당 리뷰와 AI-DLC 계약 기록으로 변경한다. 상류 문구 불일치는 목록으로만 남긴다.
- 자료 사용·잔여 조건: [#37](https://github.com/JminAILab/CatchU/issues/37).

## Q1 — 실패 후 새 분석 요청의 허용 범위

[#23 Q5·Q6](https://github.com/JminAILab/CatchU/issues/23#issuecomment-5786950699)와 [E 답변](https://github.com/JminAILab/CatchU/issues/23#issuecomment-5787076387)에서 실패 확정·새 요청 허용의 세부 조건이 미결이다. 결과를 열 수 있다는 사실과 재요청 허용은 별개다.

A. 권고: 실패가 확정되고 그 요청에 등록 가능한 결과·등록된 Catch가 없으며 처리/반영/복구가 진행 중이지 않을 때만, 사용자가 대상·범위를 다시 확인하고 새 동의로 새 요청을 만든다. 기존 요청 이력·자료·링크는 보존한다. 조회 실패·실행 불확실·DB 반영 실패만으로 새 분석을 허용하지 않는다. 정상 완료(0건 포함)의 재분석, 유효 결과가 있는 부분 실패의 추가 생성/보완은 보류한다.
B. 부분 실패로 유효 Catch가 제공된 경우까지 새 요청 대상으로 넓히고 싶다. 이 경우 보류 중인 보완·재분석 및 중복/기존 자료 영향 정책을 먼저 추가로 결정해야 하므로 이번 API에 바로 확정하지 않는다.

## Q2 — 서로 다른 저장소의 동시 분석 접수

같은 저장소 중복 차단은 확정이다. 다른 저장소 동시 요청은 #23 Q5의 미결이며 사용자에게 보일 접수/거절 응답을 정해야 한다. 서버 작업 큐와 worker 처리 병렬도는 이 결정과 별개다.

A. 권고: 첫 MVP는 사용자당 진행 중 분석 요청 1개. 다른 저장소 요청은 현재 작업 참조와 함께 접수하지 않고, 현재 요청의 처리·반영/복구가 끝난 뒤 사용자가 다시 요청한다. 다른 사용자의 요청까지 직렬화하거나 자동 대기 접수를 추가하지 않는다.
B. 사용자당 여러 저장소 접수 허용. 저장소별 진행 중 요청 1개를 적용하고 각 작업을 별도 조회한다. 처리 병렬도·자원 상한은 담당자의 기술 설계로 남긴다.
