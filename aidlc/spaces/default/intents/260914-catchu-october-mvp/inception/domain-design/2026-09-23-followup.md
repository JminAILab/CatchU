| 순서 | 결과·범위 |

| Contract Design | 개발 기준 API 명세 v1: 계약 표·회원/수신자 OpenAPI YAML·제공자 비종속 worker 메시지 스키마. 전송 방식은 #77 이후 |
| Delivery Planning | Minimal 담당 표·첫 연결 순서만 기록 |
| Functional Design | 기본 Unit 반복. api ERD v1 전체; web functional-spec/traceability와 worker entities/rules/functional-spec/traceability는 계약 참조·개발 이슈 보완 중심으로 최소 작성 |

- depth Minimal. 미실행 NFR 2단계·인프라 설계·코드 생성·빌드/테스트·CI 및 Operation 6단계의 12개 SKIP을 공식 반영했다. feedback-optimization의 기존 SKIP도 유지한다. 순서 점프·Unit 종류 위장·Functional 단독 실행으로 우회하지 않는다.
- 기술은 PostgreSQL·TypeORM(마이그레이션 포함)·Redis 확정. BullMQ는 #77 검증까지 연결하지 않는다. 서비스 LLM은 팀장이 개발 중후반 실제 제공자 연결 전에 선정하며 그 전에는 제공자 비종속 계약·가짜 생성기를 사용한다.
- API v1에서 요청/처리/반영 상태와 정상 0건·부분 실패·조회 실패·반영 실패, 사용자 재요청 조건/응답을 정한다. #23 Q5/Q6의 9/23 답변을 재사용한다. 수신자 거부는 공통 응답, 공유 링크는 현재 공개 Catch 전체(링크–자산 연결 없음), 최소 질문은 수신자 응답 제외다. 재분석·동의 재사용·기존 Catch/링크 변경·원본 재공개는 Open questions로 남긴다.
- api ERD는 논리 모델과 물리 전환 제약을 포함한다. F의 AnalysisResult·WorkCandidate·AnalysisEvidence·DraftOutcome은 서비스 DB 밖 외부 식별자 참조다. worker의 보존 위치는 Open question이다. **CatchAsset:CatchEvidence = 1:N**이며 evidenceReferences 중복을 없앤다. 초안 본문·최소 질문은 B의 서비스 정본이다. 최대 5개·유효 제목 유일성은 중단·만료되지 않은 링크에 적용한다.
- Functional 승인 뒤 intent는 **계약 마일스톤 완료**로 종료하며 MVP 완료로 표시하지 않는다. 개발 중 계약 변경은 이슈→PR→담당 리뷰를 승인으로 삼고 contract-design --single로 기록한다. 완료 intent의 단독 실행 거부나 Functional 단독 실행의 Unit 경로 불일치가 실제 발생하면 변경 intent를 제안한다.
- 코딩·검사·뼈대는 PR #72의 작업관리 §7 및 #81~#84에서 진행한다. 이번 세션은 구현하지 않는다. 상류의 기존 Construction 브랜치/80% 커버리지/CI 문구와 서비스 모델 결정 시점의 차이는 후속 코딩 운영 적용 차이로만 남기며 상류를 재개하지 않는다.
- NCP 수동 배포·복구와 통합 검증의 완료 기준은 #24, C04 수집 통제는 #37에서 추적한다. 미수행은 완료가 아니며 담당 미배정은 유지한다.
- Units·Contract·Functional 산출물은 #80 위의 별도 「API 명세 v1·ERD v1」 PR에 둔다(#80이 먼저 병합되면 dev 기준). 이 세션은 PR 병합·base 변경을 하지 않는다.
