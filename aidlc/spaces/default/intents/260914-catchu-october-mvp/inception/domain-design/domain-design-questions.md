## 이번 설계 범위와 유지할 결정

- 작성할 코드를 논리적인 업무 구성요소로 구분하고, 각 데이터의 단일 소유자·식별자·속성명·다른 구성요소 참조를 정리한다. 필드 타입·허용값·검증 제약·관계 수량·API 명세는 후속 설계/계약에서 다룬다.
- A 회원/프로필/연동, E 요청/작업, F 수집/근거/초안, B 본인 자산/공개, C 링크/수신자, D 홈/분석 화면의 기존 책임을 출발점으로 삼는다. A~I를 공식 Unit·서버·DB와 일대일로 고정하지 않는다. H 환경/배포·복구와 I 통합은 별도 운영/협업 책임이며 업무 데이터 소유자를 대체하지 않는다.
- 팀원 1 F/H/I·2 A/E·3 C/D·4 B가 자기 설계·구현·테스트를 맡는다. 공통 세션의 제안과 각 연결 당사자의 수용을 구분한다. DB/큐/LLM/GitHub는 의존 대상이며 별도 업무 구성요소로 세지 않는다. NCP 수동 배포 유지, AWS 서비스로 전환하지 않는다.
- UI는 각 담당의 기존 화면과 상태를 재사용한다. 화면 표시용 상태가 서버의 작업 완료·Catch 공개 권한을 임의 결정하지 않는다. 상세 화면 배치·재인증 복귀의 미합의는 담당자 보완으로 남긴다.
- 서비스 LLM은 미선정이다. 외부 생성과 CatchU 업무 모델의 경계를 구분하되 제공자별 API/오류/한도·비용/보관 위치를 확정하지 않는다. Astra 개발용·Luna medium 실험용 구분과 추가 호출 금지는 유지한다.
- C01 미달/R1 한 건 예외 공식 적용 대기, C02 제한 수용 방향·시간 상한/독립 대조 미확인, C03 PoC 수용과 사본 삭제 조건은 그대로다. domain-design 승인/관련 구현 착수 전 확인해야 하므로 설계 초안 작성과 최종 승인 가능 여부를 구분한다. 사본 삭제는 2026-09-23 23:59 KST 또는 더 이른 기존 경계 전이며 완료를 추정하지 않는다.
- 발행 후 Catch 구성/본문 변화와 기존 링크 영향, 재분석 결과의 기존 자산 관계는 보류다. Q1 책임 확인만으로 교체/동결/자동 편입·부분 성공/0건·복구 중 새 요청 정책을 결정하지 않았다. 이후 Q2/Q3의 사용자 답변으로 정상 0건·부분 성공 정책만 구체화하며, 나머지 보류는 유지한다.
- 기존 복구에 따른 approval-handoff 입력 존재 차이 안내와 초기화 Untracked는 보존한다. 인계 재승인/초기화 재수행·버전 변경·구현·CI·외부 호출은 수행하지 않는다.

## Q1 — 분석 결과를 Catch로 등록하는 업무 책임

[AR] §4는 E의 작업 상태, F의 결과 생성, B의 자산 저장/공개 책임을 구분하지만, §10은 결과 반영 책임을 Domain Design의 남은 결정으로 넘겼다. [W] 역시 E/F/B의 반영·열람 경계 대조를 남긴다. 기존 담당 변경이 아니라 **생성 결과를 서비스 자산으로 받아들이는 규칙을 누가 소유하는가**를 확인한다.

**A안 — B가 자산 등록 규칙 소유 (권고):** F는 분석 결과·근거를 만들고, E는 요청/작업 및 결과 전달·반영 진행을 관리한다. B는 결과를 Catch로 등록할 때의 자산 식별·근거 연결·중복 반영 방지와 최초 미공개 상태를 책임진다. E는 B의 반영 결과를 확인해 사용자 완료/결과 준비 상태를 결정한다. 다른 구성요소가 B 소유 데이터를 직접 바꾸지 않는 방향이다. 장점은 자산 생성과 공개/숨김 규칙의 소유가 일치한다는 점, 비용은 E/F/B의 등록 요청·응답·실패/복구 연결을 명시해야 한다는 점이다. 물리 DB·프로토콜·단계별 상세 처리는 후속 계약이며 별도 합의가 필요하다.

**B안 — 분석 결과 반영을 별도 구성요소로 분리:** F/E/B 사이에 등록·연결·중복 반영 조정을 맡는 별도 결과 반영 구성요소를 둔다. 여러 결과 경로의 복잡한 복구 규칙을 모을 수 있지만, 현재 MVP에서는 책임/호출 경계가 하나 늘고 소유 데이터와 담당이 추가로 필요하다. 선택 시 그 담당을 팀원 1이나 2에게 자동 배정하지 않는다. B의 공개/숨김 책임과 기존 담당별 설계/테스트 책임은 유지한다.

A. B가 자산 등록 규칙을 소유하는 안을 도메인 설계안에 반영한다. E/F/B 당사자 검토와 상세 계약은 별도로 남긴다.
B. 별도 결과 반영 구성요소를 검토한다. 구체 역할·소유 데이터·담당은 후속 질문으로 정한다.
X. Other (please specify)

[Answer]: B의 Catch 등록·공개 관리 책임은 유지하되, 등록에 필요한 제품 정책은 지금 공통 세션에서 제가 먼저 판단하겠습니다.

이미 확정된 정책은 재사용하고, Catch 등록 경계를 정하는 데 필요한 미결 정책만 한 번에 1~2개씩 질문해 주세요. 기존 보류 항목은 지금 결정이 필요한 이유와 영향을 먼저 설명해 주세요.

결정된 정책을 바탕으로 B 담당자가 자기 영역의 설계·구현·테스트를 맡고, E/F와 상세 계약을 검토하는 구조는 유지합니다.

**답변 반영:** B의 등록·공개 관리 책임을 유지한다. 등록에 필요한 미결 제품 정책은 사용자에게 먼저 확인하고, 담당자별 설계·구현·테스트와 E/F/B 상세 계약 검토는 유지한다. 이를 A안에 적힌 모든 처리 순서·상세 계약의 일괄 승인으로 확대하지 않는다. 기존 확정 정책은 재질문하지 않는다.

이 답변은 업무 책임 경계의 설계 방향이다. 구현·외부 호출 허가, 상세 계약 합의, C01/C02 조건 해소 또는 전체 단계 승인이 아니다. 후속 질문/미결 검토와 별도의 통합 요약 `Looks correct`를 거친 뒤 세 공식 산출물을 작성한다.

## Q2 — 오류 없이 분석했지만 등록할 Catch가 0개인 경우

**기존 보류 근거:** [R] FR2.1·OQ3, A/E v0.10 §5.4·§6 Q6. A/E 입력의 W03에는 정상 조회된 0건 안내가 있지만, 정상 0건의 업무 의미 자체는 미결이다. 입력은 로컬 Git 고정본 `2305ed19b20fb91e098c37808a3ae96ae9553608:docs/ai-dlc-input-mvp/CatchU_회원자산_흐름_와이어프레임_초안.md`로 대조했다.

**지금 필요한 이유와 영향:** 분석 작업이 끝나는 것과 B에 Catch가 생기는 것을 구분해야 한다. 오류 없이 분석을 마쳤으나 등록 기준에 맞는 후보가 없는 경우의 사용자 안내와 완료 의미를 정한다. 조회 실패·수집/생성 오류를 0건으로 바꾸지 않는다. 구체적인 후보 등록 기준은 후속 질문으로 따로 확인한다.

A. 정상 완료로 인정하고 Catch는 만들지 않는다. 사용자에게 검토할 Catch가 없다고 안내한다. (권고)
B. 정상 완료와 구분되는 ‘등록할 결과 없음’으로 안내한다. Catch는 만들지 않는다. 구체적인 상태명은 후속 설계에서 정한다.
X. Other (please specify)

[Answer]: Q2: 1 (대화 선택지 1 = 문서 A). 오류 없이 분석했지만 등록 기준에 맞는 후보가 0개인 경우 정상 완료로 인정하고, Catch를 만들지 않으며 검토할 Catch가 없다고 안내한다. 아래 Q2/Q3 답변 원문의 추가 조건을 함께 적용한다.

어느 선택도 자동 재분석·추가 입력 화면·외부 호출을 허용하지 않는다. 정상 0건을 서비스 품질 기준 충족으로 계산하지 않는다.

## Q3 — 일부 결과는 등록 가능하고 나머지는 실패한 경우

**기존 보류 근거:** [R] FR2.1·OQ3, A/E v0.10 §5.4·§6 Q6·S18의 부분 성공/노출 미결. 기존 화면 초안은 부분 실패 결과의 노출을 확정하지 않았으며, 비노출을 삭제 약속으로 취급하지 않는다.

**지금 필요한 이유와 영향:** 분석 처리가 종료된 뒤 일부 후보는 등록 기준을 충족하고 다른 부분은 실패한 경우, B가 유효한 후보를 Catch로 등록해 사용자에게 보여 줄지 정해야 한다. 아직 진행 중인 결과의 점진적 노출이나 재분석 시 기존 Catch 교체 정책은 이번 질문에 포함하지 않는다.

A. 기준을 충족한 후보만 미공개 Catch로 등록해 검토할 수 있게 하고, 일부 분석 실패 사실도 알린다. 전체 성공으로 표시하지 않는다. (권고)
B. 일부 실패가 있으면 이번 분석에서 새 Catch를 등록·노출하지 않고 실패를 안내한다. 기존 자산은 유지한다. 생성 결과의 보관·삭제는 별도 정책이며 이번 선택으로 정하지 않는다.
X. Other (please specify)

[Answer]: Q3: 1 (대화 선택지 1 = 문서 A). 실패의 영향과 분리해 등록 기준 충족을 확인할 수 있는 후보만 미공개 Catch로 제공하고, 일부 분석 실패도 알린다. 전체 성공으로 표시하지 않는다. 아래 답변 원문의 추가 조건을 함께 적용한다.

### Q2/Q3 답변 원문과 적용 구분

> Q2: 1, Q3: 1로 진행해 주세요.
>
> Catch는 확인 가능한 근거와 기여를 중심으로 판단합니다. 부분 실패 시에도 실패의 영향과 분리해 등록 기준 충족을 확인할 수 있는 후보만 제공합니다.
>
> 근거 부족·등록 기준 미달과 수집·생성 오류를 구분해 주세요. 특히 설명 초안 생성 실패를 곧바로 후보 부재나 Catch 등록 불가로 확정하지 말고, 초안의 필수 여부는 이어지는 등록 기준 질문에서 다뤄 주세요.

- 근거 부족·등록 기준 미달이라는 후보 평가와 수집·생성 오류라는 처리 결과를 구분한다. 오류가 후보 판단에 영향을 주어 등록 기준 충족 여부를 확인할 수 없다면, 그 후보를 부분 성공 대상으로 제공하지 않는다. 이를 후보가 없다는 판정으로 바꾸지 않는다.
- 설명 초안 생성 실패만으로 후보 부재·등록 불가를 확정하지 않는다. 초안의 등록 필수 여부는 Q4 답변 전까지 미결이다. 오류가 있는 분석을 Q2의 오류 없는 정상 0건으로 바꾸지 않는다.
- 근거·기여 중심의 제품 판단을 F의 기능 구현/정확성 검증 완료로 해석하지 않는다. 근거 부족과 기술적 실패를 구분할 수 있는 정보 및 실패 영향의 독립성은 E/F/B 상세 계약에서 검토한다.

## Q4 — 설명 초안은 Catch 등록의 필수 조건인가
