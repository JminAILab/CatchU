## 유지할 결정과 논의의 경계

- GitHub 기록을 정리한 자산으로 구직자의 자기 PR과 HR/HM의 JD에 따른 지원 자료 확인을 돕는다. 구직자 가이드의 첫 범위는 경험 후보·근거·생각해볼 질문이다. 자동 문장 작성·첨삭은 추가 확정하지 않는다. [IC]
- 링크 전달을 주 경로로 먼저 완성하고 HR 검색·소싱도 제품 구현 범위에 유지한다. 기존 ATS와 역할을 나누며, 직접 연동이나 전체 소셜 기능을 자동으로 추가하지 않는다. [IC]
- 사전 입력에 기록된 Catch 4구획, 선택 상한·맥락 가이드, JD 기반 한 장 요약 및 근거·질의응답 열람 방향을 유지한다. 이 질문에서 10월의 수준을 조정하는 선택은 12월 제품 범위의 자동 폐기가 아니다. 상세 동작·수치·최초 화면은 별도 확인 대상이다. [D1 §3] [D2 §3] [D3 §2]
- 10월 1~2일 중간 발표에서는 자료 준비 → 링크 발행 → 수신자 열람을 직접 완주하는 수준을 기대한다. 공식 발표 기준이나 일정 내 완성 가능성이 확인된 약속은 아니다. 여기서는 이 흐름에 포함할 구체적인 기능 수준을 묻는다. [FE-Q Q2·Q7·Q8]
- 4인, 평일 09:00~18:00 참여, 월 서버·LLM/API 합산 약 160만 원, 2026년 12월 중순 서비스 목표를 다시 묻지 않는다. 역할·실제 가용량과 PoC 재사용성은 미확인이며, 참여 시간 전체를 개발량으로 계산하지 않는다. [IC] [FE]
- 대한민국 우선 제공은 현재 구상이며 확정 제약은 아니다. 초기 이용량과 외부 AI 처리·보관 조건은 미확인으로 유지한다. 공개 범위 답변을 서버 위치·보관·전송 정책이나 외부 AI 처리 동의로 확대하지 않는다. [FE-Q Q5·Q6]
- 사용자 조사는 만족도·체감 유용성·개선 의견을 확인한다. 직접 사용·시연 응답을 구분하며 HM 미참여 시 업무 효과는 미검증이다. 5분 가설은 후속 검증 항목이고, 내부 기능·자료 품질 확인은 별도다. 구체적인 조사·품질 판정 기준은 요구사항 검토에서 다룬다. [IC] [D2 §4]

## 질문 순서와 미결 처리

먼저 공개 범위를 정리한다(Q1~Q3). Q3에서 받은 검토안과 질문 조정 요청에 따라 직접 전달 링크의 구독 적용(Q8), 검색·소싱의 구독별 열람 검토 방향(Q9)을 나누어 논의한다. 이어서 10월 핵심 흐름의 구성(Q4~Q6), 12월 검색·소싱의 최소 수준(Q7)을 다룬다. Q8~Q9는 Q3의 후속 질문이며 기존 질문 번호를 유지하기 위해 뒤에 추가했다. 선택지는 비교안이며 선택 전에는 채택하지 않는다.

Q5에서 사전에 정한 공개 저장소만 서비스에서 분석하는 안을 선택했으나 선정 기준은 답변하지 않았으므로, 후속 Q10에서 이를 확인한 뒤 Q6~Q7을 이어간다. Q10도 기존 질문 번호를 보존하기 위해 뒤에 추가했다.

Q7의 채용 제안·연락 흐름 검토 요청은 후속 Q11에서 비교한다. 직접 조건 입력 검색과 자산 공개 자동 확대 금지라는 결정은 유지하며, 채용 제안·텍스트 DM의 12월 채택 여부를 제안 상태에서 임의로 확정하지 않는다.

Q11에서 팀은 B를 선택해 채용 제안·동의한 외부 연락 연결·수신 설정·반복 발송 제한과 수락 이후 텍스트 DM을 12월 최소 범위에 포함했다. 추가된 기능량과 일정을 비교하기 위해 Q12에서 역할·실제 가용량의 현재 합의 여부를 확인한다.

기존 공개 범위 Q2의 “카드 수가 줄어든다면 링크별 선택도 괜찮다”는 조건부 의견은 이력으로 보존한다. 이번 Q1에서 첫 범위는 전역 공개만 사용하고 링크별 자산 선택은 두지 않는다고 답했으며, Q2에서 숨긴 GitHub 자산은 한 장 요약·질의응답에도 사용하지 않는다고 답했다. Q3의 구독 BM 검토 요청을 이 두 답변의 철회나 숨긴 자료의 유료 공개 허용으로 해석하지 않는다. Q8에서 직접 전달 링크의 GitHub 근거 열람은 구독으로 제한하지 않기로 했고, Q9에서는 비구독 기업도 대표 주장·연결 Catch 근거를 확인하는 안부터 비교하기로 했다. 검색·소싱의 정확한 구독별 노출 범위는 미결이다. Q7에서도 구독·제안 수락으로 자산 공개 범위를 자동 확대하지 않는다고 확인했다. [Q1] [Q2] [Q3] [Q7] [Q8] [Q9] [IC IC-OQ1] [D2 §5 Q2]

팀원별 역할·가용량, PoC 재사용 검증, API·계정·이용량 등 실행 여건은 실제 준비량·비용 판단 전에 필요한 별도 확인 항목으로 남긴다. 질문의 답변이 준비량을 크게 늘리면 해당 항목을 구체적으로 후속 질문한다. 지금 기술 구성을 선택하거나 구현·배포를 시작하지 않는다. [FE FE-OQ2~FE-OQ6]

## Q1. 링크에서 보여줄 GitHub 자산은 전역 숨김과 링크별 선택 중 어떤 관계로 정할까요?

이유·영향: 예를 들어 회사 A 링크에 넣었던 Catch를 나중에 모든 외부 열람에서 감추려는 경우와, 회사마다 다른 자산을 보여주려는 경우를 함께 판단해야 한다. 여기서는 Catch 등 GitHub 자산의 공개 원칙을 먼저 정한다. 전역 숨김은 이미 발행한 링크에도 공통으로 적용하는 숨김, 링크별 선택은 해당 링크에 넣을 자산을 고르는 기능을 뜻한다. 아래는 아직 채택되지 않은 비교안이다. [D2 §5 Q2]

A. 두 기능을 함께 둔다. 전역에서 숨긴 자산은 모든 링크에서 제외하고, 나머지 중 링크별로 보여줄 자산을 선택한다.
B. 링크별 선택만 둔다. 전역 숨김은 두지 않고 각 링크에서 선택한 자산만 보여준다. 이미 발행한 여러 링크의 변경을 어떻게 지원할지는 별도 확인한다.
C. 전역 공개 범위만 둔다. 숨기지 않은 공통 자산을 모든 링크에서 보여주며, 링크별 자산 선택은 첫 범위에 두지 않는다.
X. Other (please specify)

[Answer]: - C. 전역 공개 범위만 둔다. 숨기지 않은 공통 자산을 모든 링크에서 보여주고, 링크별 자산 선택은 첫 범위에 두지 않는다.

답변 해석: 첫 범위에서는 전역 공개 범위를 사용한다. 전역에서 숨기지 않은 공통 GitHub 자산을 모든 발행 링크에서 보여주고, 링크별 자산 선택은 포함하지 않는다. Q1의 설명에 따라 전역 숨김은 이미 발행한 링크에도 공통으로 적용한다. 과거의 조건부 링크별 선택 의견은 이 답변의 근거·이력으로 보존한다. 이 답변만으로 기업 검색 노출, 프로필·서류의 세부 공개 방식, 요약·질의응답의 사용 범위나 외부 AI 처리 조건을 함께 확정하지 않는다.

## Q2. 링크의 한 장 요약과 질의응답도 그 링크에서 열람을 허용한 GitHub 자산만 사용하도록 할까요?

이유·영향: Q1에서 숨기지 않은 공통 GitHub 자산을 모든 링크에 보여주기로 했다. 이제 한 장 요약과 질의응답도 그 공개 범위 안의 자산만 사용하는지 확인한다. 이는 공개 자산을 빠짐없이 요약에 넣는다는 뜻이 아니라, 사용할 수 있는 자료의 경계를 정하는 질문이다. 기존 원문에는 질의응답에 숨김 제외 전체 Catch를 쓰는 안이 있고 한 장 요약의 재료 범위는 미결이다. 프로필·서류 등 다른 자료의 세부 처리와 외부 AI 전송 조건은 이 답변으로 확정하지 않는다. [Q1] [D2 §5 Q2] [D3 F4~F6]

A. 같은 범위를 적용한다. 링크에서 열람할 수 없는 GitHub 자산은 그 링크의 요약·질의응답에도 사용하지 않는다.
B. 직접 열람과 요약·질의응답의 범위를 다르게 두려 한다. 어느 기능에 어떤 추가 자산을 허용하려는지와 구직자에게 이를 알리고 선택하게 할 범위를 설명한다.
C. 요약·질의응답에 사용할 자료 범위는 아직 결정하지 않는다. 결정에 필요한 사례나 조건을 적는다.
X. Other (please specify)

[Answer]: - A. 같은 범위를 적용한다. 전역에서 숨긴 GitHub 자산은 한 장 요약·질의응답에도 사용하지 않는다.

답변 해석: Q1의 전역 공개 경계를 한 장 요약과 질의응답에도 적용한다. 전역에서 숨긴 GitHub 자산은 두 기능의 자료로 사용하지 않는다. 공개된 자산을 빠짐없이 결과에 넣어야 한다는 뜻은 아니다. 프로필·서류의 세부 처리와 외부 AI 처리·보관 조건은 별도 확인 대상으로 유지한다.

## Q3. 기업 검색에 포함되는 구직자의 공개 자료는 발행 링크와 어떻게 구분할까요?

이유·영향: Q1~Q2에서 발행 링크와 요약·질의응답의 GitHub 자산 범위를 정했다. HR 검색으로 찾은 프로필에도 같은 범위를 적용할지는 별도 결정이다. 여기서 검색은 기업이 후보자를 찾는 기능이며, 링크 안에서 자료에 질문하는 기능과 다르다. 구직자가 검색 노출을 허용한 경우를 기준으로 아래 안을 비교한다. A는 공통 공개 범위를 재사용하고, B는 검색으로 확인할 자료를 줄이며, C는 검색용 자산 선택 기능을 추가한다. 어느 안도 아직 채택되지 않았다. 기본 프로필 항목과 자기소개서·포트폴리오의 검색 경로 공개 방식은 이 질문으로 일괄 확정하지 않는다. [Q1] [Q2] [D2 §2 기업 검색·소싱] [D3 F8]

A. 구직자가 검색 노출을 허용하면 기본 프로필과 전역에서 공개한 GitHub 자산을 검색 경로에서도 확인할 수 있게 한다. 별도의 검색용 자산 선택은 두지 않으며, 전역 숨김은 검색 경로에도 적용한다.
B. 검색 노출을 허용한 구직자의 기본 프로필만 검색에서 보여준다. GitHub 자산·서류는 구직자가 전달한 링크의 허용 범위로 확인한다. 기본 프로필 항목은 후속으로 정한다.
C. 구직자가 검색 노출을 허용하고, 전역 공개 GitHub 자산 중 검색 경로에서 보여줄 자산을 별도로 고른다. 전역에서 숨긴 자산은 검색에도 노출하지 않는다. 검색용 선택 기능을 첫 범위에 추가하는 안이다.
X. Other (please specify)

[Answer]: 기업 측에서 보는 기본 구성은 ‘기본 프로필 + 대표 주장 + 해당 주장을 뒷받침하는 Catch 근거’로 생각하고 있다. 예를 들어 ‘UI/UX를 신경 쓰는 프론트엔드 개발자’라는 주장과 관련 Catch 1~2개를 함께 보여주는 방식이다.

기업의 구독 여부에 따라 열람 가능한 정보의 정도를 다르게 하는 BM도 검토하고 있다. 구독별 정확한 노출 범위는 아직 정하지 않았다.

따라서 검색용 Catch를 별도로 선택하는 기능을 바로 확정하기보다는, 구직자가 구성한 기업 공개용 대표 주장과 근거 Catch를 검색 프로필에도 활용하는 안을 먼저 검토해 달라.

구직자의 공개 설정과 기업의 구독 권한은 구분해 달라. 또한 직접 전달한 링크에 적용할 열람 범위와 검색·소싱에서의 구독별 열람 범위를 별도로 논의할 수 있도록 질문을 조정해 달라.

답변의 상태: 기존 A/B/C 중 하나를 확정한 답변이 아니라, 새 검토안과 질문 조정 요청이다. 기업 공개용 기본 구성과 구독 BM의 채택·상세 요구사항은 아직 확정하지 않았다. 아래 해석에 따라 검토하고 Q8~Q9로 논의를 분리한다.

- 현재 구상: 기본 프로필 + 대표 주장 + 해당 주장의 근거 Catch. ‘UI/UX를 신경 쓰는 프론트엔드 개발자’와 Catch 1~2개는 예시이며, 문구·주장 수·Catch 수 상한을 확정한 것이 아니다.
