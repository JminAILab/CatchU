# CatchU 의도문

## 해결하려는 문제

HM 인터뷰에서는 면접 과정에서 GitHub를 확인해야 한다고 생각하지만 실제로는 거의 보지 못한다는 불편이 나왔다. HR 인터뷰에서는 JD에 적합한 인재를 찾기 어렵고 오래 걸리며, JD에 작성된 기술 스택에 대한 이해가 부족해 확인에도 시간이 걸린다는 불편이 나왔다. 이는 이번 팀이 전달한 인터뷰 근거로 다루며, 모든 HM·HR의 일반적 특성으로 확대하지 않는다. [Q1] [Q6]

CatchU는 GitHub 기록을 분석·정리한 자산으로 구직자의 자기 PR을 돕고, HR/HM이 자신의 JD에 따라 지원자의 프로필·자기소개서·포트폴리오·GitHub 자산을 확인하도록 하는 서비스다. 이 목적을 유지하되, 인터뷰에서 확인한 불편과 서비스가 실제로 개선한 효과를 구분한다. [desc] [Q6]

이번 문제 정의의 외부 근거는 HM·HR 인터뷰에서 전달된 불편이다. GitHub 자산을 구직자의 자기 PR과 HR/HM의 JD에 따른 자료 확인에 연결한다는 제품 방향을 이 근거와 함께 유지한다. [Q1] [Q6] [desc]

계획 기준은 팀 4인, 평일 09:00~18:00 참여, 서버·LLM/API 월 합산 약 160만 원이다. 참여 시간 전체를 순수 개발 시간으로 환산하거나 추가 근무를 일정에 포함하지 않는다. [desc]

## 초기 범위 방향

workflow-selected scope는 `catchu-definition`이다. 이 명칭은 선택된 AI-DLC 진행 경로를 뜻한다. 사용자와 확인한 제품 경계는 다음 목록이며, 진행 경로 선택을 세부 요구사항 전체의 승인으로 확대하지 않는다. [scope] [desc] [Q3]

- GitHub 기록을 분석·정리한 자산의 활용 기반을 유지한다. 이를 실제 구현 코드가 이미 존재한다는 주장으로 바꾸지 않는다. [desc]
- 링크 발행을 통한 전달을 주 경로로 먼저 완성한다. HR 검색·소싱도 제품 범위에 유지하되 완성도는 조절할 수 있다. [desc] [Q3]
- 구직자 가이드의 첫 범위는 경험 후보·근거·생각해볼 질문 제공이다. 문장 자동 작성·첨삭을 추가로 확정하지 않는다. [desc] [Q3]
- 기존 ATS와 역할을 나누며, 링크드인이라는 비유만으로 소셜 기능 전체를 추가하지 않는다. [desc]
- 현재 밝힌 제품 경계 외에 이 시점에 추가로 확정할 경계는 없다. 세부 범위는 범위 정의 단계에서 검토한다. [Q3]
- 이번에는 방향·초기 범위·요구사항을 팀과 검토한다. 요구사항 검토를 마친 뒤 다음 설계 작업을 정하며, 구현·배포는 이번 요청에 포함하지 않는다. [desc]
