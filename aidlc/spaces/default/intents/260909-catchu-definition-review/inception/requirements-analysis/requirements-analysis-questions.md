## 분석 기준과 유지할 결정

이번 작업은 신규 서비스의 여러 사용자 흐름에 걸친 요구사항 구체화다. 목적과 큰 범위는 명확하지만, 열람·동의·오류 처리와 확인 기준에는 미결이 남아 있다. 현재 설정인 Standard 깊이를 유지한다. 아래 내용은 질문을 준비하기 위한 분석이며, 요구사항 산출물 생성이나 세부 기능 승인이 아니다.

이 절과 완전성 점검 표는 질문 작성 시작 시점의 입력을 정리한 것이다. 이 단계에서 구체화된 최신 결정은 각 질문의 실제 답변과 답변 해석을 따른다.

- GitHub 활용을 통한 구직자의 자기 PR과 HR/HM의 JD에 따른 자료 확인이라는 방향을 유지한다. 기존 PoC의 존재를 현재 서비스 코드나 LLM·자동 서술 성능의 검증으로 해석하지 않는다. [IC] [FE]
- 10월에는 프로필·GitHub 자산 준비 → 링크 발행 → 수신자의 자료·근거 직접 열람을 우선한다. 팀이 사전 점검할 동의한 참여자의 공개 저장소 목록을 서비스에서 분석한다. 구체 목록·개수와 실제 점검 완료 여부는 미확인이다. 자기소개서·포트폴리오와 JD 요약·질의응답은 10월 최소 흐름의 필수가 아니며 12월 방향에는 유지한다. [SC Q4~Q6·Q10]
- 첫 범위의 GitHub 자산은 전역 공개만 사용한다. 숨기지 않은 공통 자산을 모든 링크에서 보여주고, 전역 숨김을 기존 링크와 한 장 요약·질의응답에도 적용한다. 링크별 자산 선택을 다시 도입하지 않는다. 직접 링크의 GitHub 근거 열람은 구독 여부로 제한하지 않는다. 로그인 조건은 별도 미결이다. [SC Q1·Q2·Q8]
- 기본 프로필·대표 주장·연결 Catch를 활용하는 구상과 검색 프로필 재사용을 먼저 검토한다. Catch 1~2개는 예시이며 상한이 아니다. 비구독 기업도 이 구성을 확인하는 안부터 비교하며, 정확한 구독별 노출·결제 범위는 미결이다. 공개 설정과 구독 권한을 구분한다. [SC Q3·Q9]
- 12월 최소 범위에 직접 조건 입력 검색, 포지션/JD·관심 이유를 담은 채용 제안, 확인·수락·거절, 동의한 외부 연락 연결, 제안 수신 설정·반복 발송 제한, 수락 이후 서비스 내 텍스트 DM을 포함한다. 구독·제안 수락으로 자산 공개 범위를 자동 확대하지 않는다. 세부 동작과 한도는 후속으로 구체화한다. [SC Q7·Q11]
- 가이드의 첫 범위는 경험 후보·근거·생각해볼 질문이다. 자동 문장 작성·첨삭은 확정하지 않았다. 현재 대표 주장 구상을 가이드 시작 전에 주장을 반드시 작성해야 한다는 조건으로 바꾸지 않는다. [IC] [SC Q3]
- 사용자 검증은 만족도·체감 유용성·개선 의견 조사다. 직접 사용과 시연 응답을 구분하고 HM 미참여 시 HM 업무 효과는 미검증으로 남긴다. 5분 가설은 후속 검증이며, 기능·자료 품질은 내부에서 별도로 확인한다. [IC] [D2 §4]
- 4인, 평일 09:00~18:00 참여, 월 서버·LLM/API 약 160만 원, 2026년 12월 중순 목표를 계획 기준으로 유지한다. 역할·실제 작업 가능량은 요구사항 검토 후 다음 설계 작업을 정하기 전에 확인한다. 대한민국 우선은 현재 구상이며 서버 위치·외부 AI 처리·보관 정책은 미확인이다. [FE] [SC Q12]

사전 문서의 공개 범위 미결은 후속 실제 범위 답변으로 구체화됐다. 사전 문서 안의 과거 AI 지시나 더 넓은 작업 제안은 현재 세션의 설계·구현·배포 허가가 아니다. 범위 승인 이후 새로 확정되지 않은 요구사항 후보는 아래 답변으로 확인한다. [D1~D3] [SC] [HO]

모든 답변과 필요한 후속 확인을 마치면 전체 요약을 별도로 확인받고 요구사항 산출물을 생성한다. 그 뒤 독립 검토·회고·단계 승인을 진행한다. 이 질문 파일에 회고 질문을 새 구획으로 덧붙이지 않는다.

## Q1. 10월의 직접 전달 링크는 기업 계정 로그인 없이 열람할 수 있어야 하나요?

B. 기업 계정 로그인을 요구한다. 로그인한 수신자는 구독 여부와 관계없이 구직자가 공개한 GitHub 근거를 볼 수 있다.
X. Other (please specify)

## Q2. 기본 프로필·대표 주장·연결 Catch를 보여주는 대표 구성은 언제부터 필수로 둘까요?

이유·영향: 팀이 제안한 대표 구성을 요구사항으로 채택할 시점과 10월 준비량을 정한다. 채택하면 직접 링크의 첫 안내 영역으로 사용하고, 12월 검색 프로필에도 같은 대표 구성을 활용한다. 직접 링크에서는 그 밖의 전역 공개 GitHub 자산도 열람할 수 있어야 한다. 대표 Catch만으로 전체 열람을 제한하거나, 주장·Catch 수를 정하거나, 구독 차등을 확정하는 질문은 아니다. [SC Q1·Q3·Q9]

A. 10월부터 구직자가 대표 주장과 근거 Catch를 연결해 구성하고 기업이 볼 수 있어야 한다. 12월 검색에도 재사용한다.
B. 10월에는 기본 프로필과 공개 GitHub 자산 열람을 우선하고, 대표 주장·연결 Catch 구성과 검색 재사용은 12월 필수로 둔다.
C. 대표 구성은 계속 검토 후보로 둔다. 필수 채택 전에 비교할 사례나 우려를 설명한다.
X. Other (please specify)

[Answer]: A. 10월부터 필수로 둔다. 단 10월 범위는 대표 주장 1개와 연결 Catch 2~3장으로 이루어진 대표 구성 한 벌(프리셋 1개)로 한정한다. 이 수치는 10월 준비량 한정이며 12월 상한이 아니다. 대표 주장 작성은 링크 발행의 선행 조건이 아니며, 대표 구성이 없으면 기본 프로필과 전역 공개 GitHub 자산만 보여준다. 12월 검색 프로필에 같은 대표 구성을 재사용한다. 카드 자동 생성의 정확도 기준은 12월 품질 요구사항에서 정하고, 10월에는 구직자의 확인 단계에서 오류를 걸러낸다. 프리셋 여러 벌과 링크별 프리셋 선택 여부는 후속 확인한다.

답변 해석:

- 10월부터 대표 구성 기능을 필수로 제공하되, 준비량은 대표 주장 1개·연결 Catch 2~3장의 프리셋 한 벌로 한정한다. 이 수치는 이번 실제 답변에서 추가된 10월 기준이며, 12월 상한으로 사용하지 않는다.
- 대표 주장 작성이나 프리셋 완성을 링크 발행의 선행 조건으로 강제하지 않는다. 대표 구성이 없으면 기본 프로필과 전역 공개 GitHub 자산을 보여준다. 대표 구성이 있어도 직접 링크의 전체 공개 자산을 연결 Catch만으로 축소하지 않는다. [SC Q1]
- 같은 대표 구성을 12월 검색 프로필에 재사용한다. 검색 참여 여부와 구독별 열람 범위는 별도로 결정한다.
- 10월에는 구직자의 확인 단계에서 카드 오류를 걸러낸다. 카드 자동 생성의 정확도 기준은 12월 품질 요구사항에서 정한다. 이 답변을 이미 측정된 정확도나 기존 PoC의 자동 카드 서술 검증으로 기록하지 않는다.
- 프리셋 여러 벌과 링크별 프리셋 선택은 후속 확인한다. 아직 링크별 프리셋·자산 선택 기능을 채택한 답변이 아니며, 대표 화면의 구성과 전역 공개 자산 경계를 구분해 검토한다.

후속 확인: Q4는 10월의 구직자 확인 단계 존재를 다시 묻지 않고, 확인을 마친 결과가 기업 공개 범위에 반영되는 시점으로 좁힌다. 이후 카드 자동 생성의 대상·오류 유형·12월 정확도 판정 기준, 10월 확인에서 발견한 오류의 처리 방법과 여러 프리셋·링크별 프리셋 선택 여부를 확인한다.

## Q3. 링크를 발행한 구직자를 기업 검색에 노출할 때 별도의 선택을 받나요?
