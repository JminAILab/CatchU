# CatchU 요구사항

## 문서 상태와 읽는 방법

이 문서는 요구사항 분석 Q1~Q36과 `Consolidated Summary Confirmation`의 실제 `Looks correct` 답변을 확인 기록으로 남긴 뒤 작성한 검토본이다. 요구사항 분석 단계 승인이나 설계·구현·배포의 완료를 의미하지 않는다. 초기 초안의 제안보다 후속 실제 답변을 우선하며, 원문과 과거 산출물은 수정하지 않는다. [CONF]

`FR1`~`FR10`은 승인 범위 SC01~SC10에 대응하는 기능 묶음이다. 하위 요구사항은 `FR1.1` 형식, 비기능 요구사항은 `NFR1` 형식의 고정 ID를 사용한다. 이후 문서·설계·검증에서 이 ID를 유지한다. 표의 통과 기준은 향후 구현을 확인할 기준이며, 현재 실행해 통과한 결과가 아니다.

- **10월:** 2026년 10월 1~2일 중간 발표를 위한 필수 범위. 별도 변경이 없는 한 12월에도 유지한다.
- **12월:** 2026년 12월 중순 실제 사용 가능한 서비스의 현재 최소 범위. 가용량 검토 후 범위 조정은 별도 결정한다.
- **공통:** 해당 기능·자료를 제공할 때 적용하는 규칙. 감지 주기·처리 시간 등 미결 수치를 의미하지 않는다.
- **후속:** 채택한 행동의 설계·운영 상세 또는 아직 채택하지 않은 후보. 둘을 구분하며 OQ 목록의 결정 시점 전에 임의로 확정하지 않는다.

## 의도 분석

구직자가 GitHub 기록에서 자신의 경험과 근거를 정리해 전달하고, HR/HM이 자신의 JD에 따라 지원 자료를 확인하도록 돕는 것이 목적이다. HR의 인재 탐색·기술 확인과 HM의 GitHub 확인 어려움은 팀이 전달한 인터뷰상의 불편이며, 모든 채용 담당자의 특성이나 검증된 개선 효과로 일반화하지 않는다. 초기 구직자 대상은 신입·취업준비생이고 인공지능사관학교 수료생 활용은 현재 구상이다. [IC] [SC]

주 경로는 구직자의 공개 저장소 분석 → 자산 확인·공개 → 프로필·대표 구성 준비 → 링크 발행 → 수신자 열람이다. 12월에는 선택한 서류와 JD 기준 요약·근거 확인·질의응답을 더한다. 별도 검색 참여 경로는 로그인 기업의 조건 검색 → 포지션/JD·관심 이유가 담긴 제안 → 구직자 응답 → 수락 후 텍스트 DM·별도 연락 공유다. 지원 접수·전형은 기존 ATS와 역할을 나눈다. [SC SC01~SC09] [Q1~Q33]

구직자 가이드의 첫 범위는 경험 후보·근거·생각해볼 질문이다. Catch 4구획 방향을 유지하되 세부 표시·맥락 가이드는 후속 설계에서 구체화한다. Q12는 Catch 설명 초안 자동 생성을 새로 확정했으며, 대표 주장·자기소개서 자동 작성·첨삭을 확정한 것은 아니다. [SC SC02·SC03] [Q12·Q13]

### 해결 근거와 확인 결과

위 표의 Finding과 Required action은 이전 검토 기록을 보존한 것이며, 현재 상태는 수정본의 다음 근거로 판단했다.

- R-01: FR1.1·FR1.2가 해당 저장소의 분석 동의를 선행 조건으로 정하고 미동의 시 실행하지 않는 통과 기준을 명시했다. C4가 같은 제약을 유지하고 OQ11은 동의를 받는 방식만 미결로 구분한다. 기존 공개·소유/커밋·지원 한도와 확인 후 별도 공개 선택은 유지됐다.
- R-02: FR6 공통 원칙과 FR6.1·FR6.2가 한 장 요약·패널·질의응답 모두에 JD 매칭 % 미제공을 적용한다. 매칭 %를 요청하는 질문도 확인 대상이며 범위 경계에 같은 원칙이 연결됐다. 패널의 현재 자료 한정, JD 순서, 요약 재사용·한도·공개 상태 규칙은 유지됐다.
- R-03: FR7.2가 프로필의 직무·기술 스택 입력값과 Catch 추출 속성을 구분하고, 자가 입력값을 GitHub 검증 사실로 표시하지 않는 통과 기준을 명시했다. OQ3·OQ8은 이 채택·출처를 확정 상태로 유지하면서 항목 구조·목록·조합 등 상세만 후속 결정으로 남긴다. 검색 대상 제외와 순위 제한은 유지됐다.
