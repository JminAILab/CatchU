## 종합 판단

**가능하다. 다만 일정이 가장 큰 위험이다.** 바뀌는 곳은 이미 있는 세 서비스(web·api·worker) 안에 머물고, 새 외부 연동도, 새로 모으는 자료도, 새 AWS 자원도 없다(Q2·Q3·Q6). 기술적으로 막히는 곳은 찾지 못했다. 위험은 두 가지다. 코드 착수 시점이 날짜가 정해지지 않은 1차 통합 확인과 Catch 개편 PR 3개에 묶여 있고(Q1·Q5), 공수는 모두 팀장 한 명 몫이며 11월 공수가 이미 가용을 넘는다(의도 설명 「Initiative Trigger」).

| 관점 | 판단 | 이유 |
|---|---|---|
| 기술 | 가능 | 기존 칸·계약에 칸을 더하는 변경이다. 작성자 설명은 지금의 한 칸(4,000자)을 그대로 쓴다(Q2). |
| 자료·고지 | 가능 | 새로 모으지 않는다. 3단계 결과 문장을 Catch에 남길 때만 고지 v3 4절에 한 줄을 더하고 팀장이 승인한다(Q3). |
| 이전 승인 기록 | 가능 | 승인 원본은 고치지 않고, 이 intent의 요구사항·계약·기능 설계에 대체 대상과 범위를 적는다(Q4). |
| 인프라 | 가능 | 새 자원이 없고, 3단계는 api와 worker를 함께 배포한다(Q6). |
| 일정 | 위험 높음 | 코드 PR은 1차 통합 확인과 Catch 개편 PR 3개 뒤다. 확인 날짜가 정해지지 않았다(Q5). |

## 작업 판본과 진행 순서

- 작업 브랜치 `worker/새-catch`는 Catch 개편 브랜치(`eb2bd46d`) 위에 `origin/dev`를 merge commit으로 합친 것이다. Catch 개편 코드는 이미 들어 있고, 통합 브랜치의 최근 커밋 40개(`7ef0dd69`까지)만 빠져 있다(Q1).
- 범위 정하기까지는 이 브랜치에서 그대로 한다. 12월 intent의 1차 통합 확인이 끝나 Catch 개편 PR 3개(CR1→CR3→CR2)가 통합 브랜치에 합쳐지면, 통합 브랜치를 이 브랜치에 merge commit으로 합친 뒤 대략 화면·기존 코드 읽기부터 이어 간다(Q1).
- 코드 PR 전에 문서 단계를 먼저 끝낸다(Q5).

## 기술 위험 요약

자세한 내용과 대응은 `raid-log.md`에 있다. 다섯 가지 모두 요구사항·기능 설계에서 다룬다(Q7).

- 짚어 볼 곳 링크가 한글 파일 이름에서 끊긴다.
- 작성자 설명 4,000자에 칸 제목 글자가 포함되고, 옛 글과 칸 제목 문구 변경을 처리해야 한다.
- 링크 표지는 사본 근거(본인 커밋 최근 20건)까지만 붙고, 작성자 주장 옮기기는 사람이 확인한다.
- 3단계 사실은 지금 버리는 파일 식별값을 남겨야 하고, 지금 시험 분류가 빌드 결과물도 센다.
- 2단계가 #488·Catch 개편 CR3와 같은 화면 파일을 고친다.

## 결론

진행한다. 다음 범위 정하기에서는 일정 위험(코드 착수 시점 미정, 팀장 한 명 공수)을 전제로, 1~3단계를 어떤 순서와 크기로 나눌지 정한다. 공수가 가용을 넘을 때 줄일 순서는 의도 정리에서 이번 판에 정하지 않기로 했다.
