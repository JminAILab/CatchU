입력: 승인된 의도 설명 `aidlc/spaces/default/intents/261109-new-catch/ideation/intent-capture/intent-statement.md`(Catch 정의, 성공 기준), 범위 문서 `ideation/scope-definition/scope-document.md`(할 일 11개와 만드는 순서), 할 일 목록 `ideation/scope-definition/intent-backlog.md`(항목별 내용), 입력 문서 `docs/ai-dlc-input-catch/CatchU_새_Catch_입력.md` §4-2~§4-4, 이 단계의 답 `rough-mockups-questions.md`(Q1~Q6, 2026-11-09 확인)와 화면 초안 검토 뒤 변경 요청 세 번(2026-11-09).

새 화면은 없다. 기존 화면 네 곳에서 바뀌는 곳만 그린다. 작성자 발행본 상세는 받은 사람 화면과 같은 발행본 표시를 쓰므로 4절의 변경이 함께 보인다. 반응형·접근성은 기존 화면 기준을 그대로 따른다(Q6). 그림 속 글과 예시는 모양을 보이려는 것이고, 실제 문구는 요구사항 분석·기능 설계에서 정한다. 〔 〕는 화면에 나오지 않는 설명이다.

## GitHub 링크 이름 (2절·4절이 함께 쓴다)

작성자 설명 안의 GitHub 링크는 지금 주소 전체를 글자로 보인다(`web/src/features/publications/snapshot-view.tsx`의 `LinkedText`). 이것을 주소 전체 대신 읽을 수 있는 이름으로 보인다. (변경 요청 1)

| 링크 모양 | 보이는 이름 | 예 |
|---|---|---|
| 파일 줄 링크(`/blob/<판본>/<경로>#L<시작>-L<끝>`, 한 줄이면 `#L<줄>`) | 파일 이름 · 줄 · 판본 | `CreateArticlePage.vue · L40–58 · 판본 ba6bba8`, `CreateArticlePage.vue · L40 · 판본 ba6bba8` |
| 파일 줄 링크인데 판본 자리가 커밋 식별값이 아님 | 파일 이름 · 줄 · 그 이름 | `CreateArticlePage.vue · L40–58 · 브랜치 main`, `CreateArticlePage.vue · L40 · 브랜치 main` |
| 줄 범위가 없는 파일·폴더 링크(`/blob/<판본>/<경로>`, `/tree/<판본>/<경로>`) | 경로 끝 이름 · 판본(커밋 식별값이 아니면 그 이름) | `utils.ts · 판본 ba6bba8`, `src · 브랜치 main` |
| 커밋 링크(`/commit/<식별값>`) | 커밋 식별값 | `커밋 ba6bba8` |
| PR 링크(`/pull/<번호>`) | PR 번호 | `PR #12` |
| 그 밖의 GitHub 주소 | 지금처럼 주소 전체 | — |

- **질의.** 주소에 붙은 질의(`?plain=1` 등)는 이름을 정할 때 무시한다. 링크 대상에서는 지우지 않는다. (3차 변경 요청 1)
- **다른 저장소 링크.** 링크의 저장소가 이 Catch 근거의 저장소와 다르면 이름 앞에 「소유자/저장소 ·」를 붙인다(예: `other/lib · utils.ts · L3–9 · 판본 1a2b3c4`). (2차 변경 요청 2)
- **표지가 붙는 조건.** 「이 작업의 본인 커밋」 표지는 링크의 저장소와 판본(또는 커밋)이 모두 발행 사본 근거와 맞을 때만, 줄 범위와 관계없이 붙는다. 표지는 2단계에 들어간다. (2차 변경 요청 2)
- **표지 흉내.** 작성자가 글로 「[이 작업의 본인 커밋]」을 적어도 진짜 표지와 구별되는 모양이어야 하고, 이름에서 푼 글자의 제어 문자는 지운다. 모양과 처리 방식은 기능 설계(보안 점검 「화면 출력」)에서 정한다(열린 질문). (2차 변경 요청 3)
- 링크 대상(새 탭에서 열리는 주소)은 바꾸지 않는다. 주소 전체는 마우스를 올리면 보인다.
- 퍼센트 인코딩된 한글 경로는 보이는 이름에서만 한글로 푼다. 링크 대상은 인코딩된 그대로다.
- 링크를 찾는 규칙은 지금 판별 규칙(`web/src/lib/github-source-url.ts`) 그대로다. 그래서 한글 앞에서 끊긴 주소는 끊긴 이름(예: 파일 이름 없이 폴더까지)으로 보인다.
- 화면에서만 계산하고 API는 바꾸지 않는다. 이름 모양은 1단계, 표지는 2단계에 들어간다.

- 추천·순위는 내지 않는다. 순서는 시각만 따른다. (의도 설명 「Catch의 정의」 원칙 넷)
- 접근성: `main` 안 h1 「내 자산」 → h2 「내 Catch」 → 카드 h3은 그대로다. 새 선택 칸은 이웃 선택 칸과 같은 `label`로 묶이고 키보드 순서는 공개 상태 다음이다. 걸러 본 개수는 지금처럼 `aria-live="polite"`로 알린다. (Q6)

- **순서.** 보며 쓸 재료(근거, 다시 볼 곳, Catch 설명 초안, 생각해 볼 질문)를 모두 작성자 설명 위에 둔다. 지금과 달라지는 것은 Catch 설명 초안과 생각해 볼 질문이 작성자 설명 위로 올라가고 「다시 볼 곳」이 근거 아래에 끼는 것뿐이다. (Q3)
- **다시 볼 곳.** 3단계(할 일 (9)·(10))의 규칙 사실이 들어가는 칸으로 지원자에게만 보인다. 3단계가 들어가기 전이나 사실이 하나도 없는 Catch에서는 칸을 그리지 않는다(가정, 아래 「Assumptions & Open Questions」). 항목의 커밋 식별값은 GitHub 커밋 링크(새 탭)로 보인다. 다시 고친 곳은 면접관이 묻기 좋은 자리라, 지원자가 열어 보고 짚어 볼 곳으로 옮기기 쉽게 하려는 것이다. 칸 이름은 요구사항 분석에서 정한다. (Q3, 할 일 목록 (9)·(10), 2차 변경 요청 8)
- **생각해 볼 질문.** 질문 내용·생성 방식은 #487 그대로다. 아래 문구 「질문에 대한 답변을 저장하는 기능은 제공하지 않습니다.」만 「질문을 보고 아래 칸에 자기 말로 적어 보세요」 같은 말로 바꾼다. (할 일 (3))

- **링크 표지.** 작성자 글 속 링크의 저장소와 커밋 식별값(또는 파일 링크의 판본)이 모두 발행 사본 근거의 본인 커밋과 맞을 때만, 줄 범위와 관계없이 그 판본·커밋 이름 바로 뒤에 「이 작업의 본인 커밋」 표지를 붙인다. 파일 링크에서 표지는 그 판본이 본인 커밋이라는 뜻이지, 고른 줄을 본인이 썼다는 뜻이 아니다. 맞지 않으면 아무 표지도 붙이지 않는다. 작성자가 글로 쓴 표지 흉내는 진짜 표지와 구별된다(위 「GitHub 링크 이름」). (할 일 (7), 변경 요청 1, 2차 변경 요청 2·3)
- **작업 전체 한계.** 「기록에서 확인한 내용」의 작업 사실 바로 아래에 펼친 채 둔다. 작업 전체에 걸린 한계만 겹치지 않게 보인다. 같은 작업을 다시 냈거나 cherry-pick으로 옮긴 변경일 수 있다는 경고와 커밋 목록을 다 받지 못한 PR이 있다는 한계가 여기에 든다. 근거마다의 조회 상태 문장(「병합 커밋이라 변경 내용을 조회하지 않았다」 등)은 넣지 않는다. 해당하는 한계가 없으면 목록을 그리지 않는다. 화면에만 보이고 받은 사람 AI 재료에는 넣지 않는다. (Q5, 할 일 (6))
- 받은 사람 AI 재료와 근거 딱지 둘('GitHub 기록 원문', '작성자 자료 원문')은 그대로다. 저장소 이름·작성 시점·작업 전체 한계·링크 이름·링크 표지는 AI 재료에 들어가지 않는다. (입력 문서 §8-1의 6·8)
- 접근성: 받은 사람 화면은 지금처럼 `main` 영역 안이고 첫 초점은 발행본 제목 h1이다(비밀번호가 걸린 링크는 비밀번호 화면 h1). 발행본 항목 제목 h3, Catch 안 구역 h4 구조는 그대로이고, 칸 제목은 h4 아래의 h5로 둔다(가정, 기능 설계에서 확정). 링크 이름은 링크의 접근 이름이 되고 「(새 탭)」 안내는 지금처럼 붙는다. 표지는 색만이 아니라 글자로 읽힌다. 「근거 자세히 보기」 접힘과 근거 위치로 옮기는 초점 이동은 #488 그대로다. (Q6, 변경 요청 7)
