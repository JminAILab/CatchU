# 새 Catch — 사용자 이야기

## 읽는 법

- 근거는 승인된 요구사항 `inception/requirements-analysis/requirements.md`(FR1~FR15, NFR1~NFR8, 수락 기준 AC1.1~AC14.3)다. 사람은 `personas.md`의 지원자(P1)와 면접관(P2) 둘이다.
- 묶음은 할 일 (1)~(11)마다 하나다(US1~US11, 질문 Q1 A). 묶음 안에서는 화면 동작 하나가 이야기 하나다.
- 이야기 ID는 `US{묶음}.{순번}`, 수락 기준 ID는 `AC{묶음}.{순번}.{순번}`이다. 요구사항의 수락 기준을 옮긴 것은 끝에 「(요구 AC1.1)」처럼 원래 ID를 적었다. 요구사항 문장에서 새로 쓴 수락 기준은 끝에 그 요구사항 ID를 적었다.
- 우선순위는 모두 **Must**다. 요구사항과 할 일 11개가 모두 Must다(할 일 목록 「우선순위 방식」).
- 화면에서 하는 일이 아닌 요구(FR11.2, FR15, NFR1, NFR3, NFR4, NFR8)는 이야기로 만들지 않았다(질문 Q2 A, `user-stories-assessment.md` 「이야기로 만들지 않는 요구」).
- 「가정」이라고 적은 수락 기준은 요구사항에 [assumption]으로 남은 항목이다. 기능 설계에서 확인될 때까지 가정이다.

## US1. 칸 제목이 붙은 작성자 설명 (할 일 (1), 1단계)

### US1.1 칸 제목별로 나눠 쓰고 한 번에 저장한다

- **사람:** 지원자
- **이야기:** 지원자로서 작성자 설명을 칸 제목 8개로 나눠 쓰고 [설명 저장] 하나로 저장하고 싶다. 그래야 판단을 빠짐없이 자기 말로 남기고, 면접관이 칸마다 골라 읽을 수 있다.
- **요구사항:** FR1.1, FR1.2, FR1.4, FR1.6, FR1.8, NFR6
- **우선순위:** Must
- **수락 기준:**
  - **AC1.1.1** Given 작성자 설명이 없는 Catch의 상세, When 「이 작업에서 정한 것」과 「짚어 볼 곳」 두 칸만 쓰고 [설명 저장]을 누른다, Then 저장된 글에는 두 칸만 칸 제목과 함께 들어가고 나머지 여섯 칸 제목은 없다. (요구 AC1.1)
  - **AC1.1.2** Given 「맡은 부분」에 두 줄, 「짚어 볼 곳」에 링크 두 줄을 쓰고 저장한 Catch, When 상세를 닫았다 다시 연다, Then 두 칸에 쓴 글이 칸 안의 줄바꿈까지 그대로 돌아오고 나머지 여섯 칸은 비어 있다. (요구 AC1.5)
  - **AC1.1.3** Given 이전 설명이 있는 Catch에서 8칸을 모두 비운 편집 화면, When 저장한다, Then 작성자 설명이 지워진다. (요구 AC1.3)
  - **AC1.1.4** Given 편집 화면, When 칸 제목 8개를 차례로 본다, Then 칸 제목은 위에서부터 「이 작업에서 정한 것」·「맡은 부분」·「무엇이 문제였나」·「고른 것과 버린 것」·「어떻게 확인했나·결과」·「AI가 낸 것 가운데 받아들이지 않았거나 고친 것」·「짚어 볼 곳」·「더 쓰기」이고, 모두 펼쳐져 있으며, 각 글칸의 보이는 `label`로 화면 낭독기에 읽힌다. (FR1.1, NFR6)
  - **AC1.1.5** Given 「고른 것과 버린 것」 칸 안에 칸 제목 줄과 같은 모양의 줄을 쓴 글, When 저장한다, Then 저장은 막히지 않는다. (FR1.6. 다시 열면 그 줄부터 다른 칸으로 읽히는 것은 한계다)
- **메모:** 저장되는 칸 제목 줄의 모양은 기능 설계에서 정한다(FR1.6). 칸 제목 문구를 나중에 바꾸면 이미 쓴 글에는 옛 문구가 남는다(FR1.8, 한계).

### US1.2 글자 상한 안에서 쓴다

- **사람:** 지원자
- **이야기:** 지원자로서 칸 제목까지 포함한 합계 글자 수를 쓰는 동안 보고 싶다. 그래야 4,000자를 넘겨 저장하지 못하는 일을 미리 피하고, 넘었을 때도 쓴 글을 잃지 않는다.
- **요구사항:** FR1.3
- **우선순위:** Must
- **수락 기준:**
  - **AC1.2.1** Given 칸 제목 글자를 포함한 합계가 4,001자인 글, When 저장한다, Then 저장되지 않고 상한 안내가 보이며 쓴 글은 화면에 남는다. (요구 AC1.2)
  - **AC1.2.2** Given 두 칸을 쓴 편집 화면, When 한 칸에 글자를 더 친다, Then 맨 아래 합계 글자 수 하나가 「(칸 제목 포함)」과 함께 늘어난다. (FR1.3)

### US1.3 옛 자유 글을 이어 고친다

- **사람:** 지원자
- **이야기:** 지원자로서 이 변경 전에 쓴 자유 글을 편집 화면에서 잃지 않고 이어 고치고 싶다. 그래야 처음부터 다시 쓰지 않고 칸 제목 방식으로 옮겨 갈 수 있다.
- **요구사항:** FR1.5, NFR7
- **우선순위:** Must
- **수락 기준:**
  - **AC1.3.1** Given 칸 제목 줄이 없는 3,990자의 옛 자유 글, When 편집 화면을 열고 그대로 저장한다, Then 글 전체가 「더 쓰기」 칸에 보였고 저장이 4,000자 상한에 걸리지 않는다. (요구 AC1.4)
  - **AC1.3.2** Given 「더 쓰기」 칸에만 글을 쓴 편집 화면, When 저장한다, Then 저장된 글에 칸 제목 글자가 붙지 않는다. (FR1.5)

### US1.4 면접관이 칸 제목별로 읽는다

- **사람:** 면접관
- **이야기:** 면접관으로서 작성자 설명을 칸 제목별로 나눠 읽고 싶다. 그래야 지원자가 정한 것·맡은 부분·확인한 방법을 바로 찾아 질문을 만들 수 있다.
- **요구사항:** FR2.1, FR2.2, FR2.3, FR2.4, NFR6
- **우선순위:** Must
- **수락 기준:**
  - **AC1.4.1** Given 「맡은 부분」과 「더 쓰기」 두 칸이 저장된 발행본, When 면접관이 연다, Then 「맡은 부분」과 「덧붙인 말」 두 칸만 보이고 다른 칸 제목은 없다. (요구 AC2.1)
  - **AC1.4.2** Given 작성자 설명이 통째로 없는 발행본, When 면접관이 연다, Then 「작성자 설명이 없습니다.」가 보인다. (FR2.3)
  - **AC1.4.3** Given 칸 제목별로 나뉜 발행본, When 면접관이 칸 순서를 본다, Then 불일치 표지 → AI 설명 초안 → 작성자 설명 → 기록에서 확인한 내용 순서이고, 「이 작업에서 정한 것」이 제목 바로 아래로 올라오지 않는다. (FR2.4)
  - **AC1.4.4** Given 빈 칸이 있는 발행본, When 화면 낭독기로 읽는다, Then 숨긴 빈 칸의 칸 제목은 읽히지 않는다. (NFR6)
  - **AC1.4.5** (이 기준의 사람은 지원자) Given 같은 발행본의 작성자 발행본 상세, When 지원자가 연다, Then 받은 사람 화면과 같은 칸 제목별 보기가 보인다. (FR2.1)
- **의존:** 칸 제목 저장 모양(US1.1, FR1.6)이 정해진 뒤에 만든다(할 일 목록 「만드는 순서」).

### US1.5 면접관이 옛 글도 지금처럼 읽는다

- **사람:** 면접관
- **이야기:** 면접관으로서 칸 제목 없이 쓴 옛 작성자 설명도 지금처럼 끊김 없이 읽고 싶다. 그래야 이 변경 전 발행본도 같은 링크로 계속 볼 수 있다.
- **요구사항:** FR2.2, NFR7
- **우선순위:** Must
- **수락 기준:**
  - **AC1.5.1** Given 칸 제목 줄이 없는 옛 자유 글이 든 발행본, When 면접관이 연다, Then 글 전체가 칸 제목 없이 지금처럼 보인다. (요구 AC2.2)
  - **AC1.5.2** Given 「더 쓰기」 칸만 저장된 발행본, When 면접관이 연다, Then 칸 제목 없이 글만 보인다. (FR2.2)

## US2. 짚어 볼 곳 링크와 관련 커밋 (할 일 (2), 1단계)

### US2.1 짚어 볼 곳에 줄 링크를 붙인다

- **사람:** 지원자
- **이야기:** 지원자로서 「짚어 볼 곳」 칸 아래 안내를 보고 GitHub 줄 링크와 메모 한 줄을 붙이고 싶다. 그래야 면접관이 설명을 청할 만한 코드 자리로 바로 갈 수 있다.
- **요구사항:** FR4.1, FR4.2
- **우선순위:** Must
- **수락 기준:**
  - **AC2.1.1** Given 짚어 볼 곳 칸, When 지원자가 칸을 본다, Then 다섯 가지 안내(설명을 청할 만한 줄 고르기, Copy permalink로 판본 고정, 한 줄에 링크 하나와 메모 한 줄, 한글 파일 이름 주소, 관련 커밋은 위 근거의 본인 커밋 주소)가 칸 아래에 보인다. (요구 AC4.1)
  - **AC2.1.2** Given 이 Catch 근거에 없는 커밋 주소, When 짚어 볼 곳에 붙여 저장한다, Then 저장되고, 관련 커밋을 넣는 단추나 목록은 화면에 없다. (FR4.2)
- **메모:** 「퍼센트 인코딩」 대신 쓸 쉬운 안내 문구는 기능 설계에서 정한다(FR4.1).

### US2.2 면접관이 링크를 이름으로 보고 원본으로 간다

- **사람:** 면접관
- **이야기:** 면접관으로서 작성자 설명 속 GitHub 링크를 주소 전체 대신 파일·줄·판본 이름으로 보고, 누르면 원본으로 가고 싶다. 그래야 무엇을 가리키는 링크인지 열기 전에 알고 한 번에 원본으로 간다.
- **요구사항:** FR3.1, FR3.2, FR3.3, FR3.4, FR3.5, FR3.6, NFR5, NFR6
- **우선순위:** Must
- **수락 기준:**
  - **AC2.2.1** Given 작성자 설명에 `https://github.com/o/r/blob/ba6bba8c…40자/src/CreateArticlePage.vue#L40-L58`, When 발행본을 연다, Then 링크 글자는 「CreateArticlePage.vue · L40–58 · 판본 ba6bba8」이고 누르면 원래 주소가 새 탭에서 열린다. (요구 AC3.1)
  - **AC2.2.2** Given `…/blob/main/src`, When 발행본을 연다, Then 링크 글자는 「src · 브랜치 main」이다. (요구 AC3.2)
  - **AC2.2.3** Given 근거 저장소가 `o/r`인 Catch에 `https://github.com/other/lib/commit/1a2b3c4d…`, When 발행본을 연다, Then 링크 글자는 「other/lib · 커밋 1a2b3c4」이다. (요구 AC3.3)
  - **AC2.2.4** Given `…/blob/ba6bba8/a.ts?plain=1#L3`, When 발행본을 연다, Then 링크 글자는 「a.ts · L3 · 판본 ba6bba8」이고 링크 대상에는 `?plain=1`이 남아 있다. (요구 AC3.4)
  - **AC2.2.5** Given 경로에 잘못된 퍼센트 인코딩 `%E0%A4`가 든 파일 링크, When 발행본을 연다, Then 그 부분은 `%E0%A4` 그대로 이름에 보이고 화면이 깨지지 않는다. (요구 AC3.5)
  - **AC2.2.6** Given 퍼센트 인코딩된 한글 경로의 파일 링크, When 발행본을 연다, Then 이름에는 한글로 풀려 보이고 링크 대상은 인코딩된 그대로다. (FR3.4)
  - **AC2.2.7** Given 이름으로 보이는 링크, When 마우스를 올리거나 화면 낭독기로 읽는다, Then 마우스를 올리면 주소 전체가 보이고, 화면 낭독기에 「(새 탭)」이 읽힌다(화면에는 보이지 않음, 지금 `snapshot-view.tsx`와 같다). (FR3.4, NFR6)
  - **AC2.2.8** Given 경로를 풀면 제어 문자가 나오는 링크, When 발행본을 연다, Then 이름에 제어 문자가 보이지 않는다. (NFR5)
  - **AC2.2.9** Given 텍스트 자료 본문에 든 같은 GitHub 링크, When 발행본을 연다, Then 지금처럼 주소 전체로 보인다. (가정 A6)
  - **AC2.2.10** Given AI 답의 근거가 GitHub 링크가 든 작성자 설명 문장을 가리키는 발행본, When 면접관이 근거 단추를 누른다, Then 링크가 이름으로 바뀐 뒤에도 같은 문장 범위가 강조된다(강조 위치는 원문 주소 길이로 센다). 저장된 글과 API 응답은 이름 계산 전과 같다. (FR3.5)
  - **AC2.2.11** Given 경로가 아주 긴 파일 링크, When 발행본을 연다, Then 이름이 잘리지 않고 줄이 바뀐다. (FR3.6)
- **메모:** 링크를 찾는 판별 규칙(`web/src/lib/github-source-url.ts`)은 그대로다(FR3.1).

### US2.3 발행하면 면접관에게 열릴 링크를 미리 본다

- **사람:** 지원자
- **이야기:** 지원자로서 쓰는 동안 발행하면 면접관에게 열릴 링크를 면접관이 볼 이름 그대로 미리 보고 싶다. 그래야 한글 앞에서 끊긴 주소나 브랜치 주소를 보내기 전에 고친다.
- **요구사항:** FR5.1, FR5.2, FR5.3, FR5.4, NFR6
- **우선순위:** Must
- **수락 기준:**
  - **AC2.3.1** Given 「맡은 부분」 칸에 커밋 링크 하나, 「짚어 볼 곳」 칸에 파일 줄 링크 하나, When 지원자가 쓴다, Then 목록에 두 링크가 US2.2와 같은 이름으로 보인다. (요구 AC5.1)
  - **AC2.3.2** Given 한글 파일 이름이 인코딩되지 않은 주소, When 지원자가 붙인다, Then 목록에 한글 앞에서 끊긴 이름(파일 이름 없이 폴더까지 등)이 보인다. (요구 AC5.2)
  - **AC2.3.3** Given 같은 커밋 링크를 「맡은 부분」과 「짚어 볼 곳」에 함께 쓴 글, When 지원자가 목록을 본다, Then 그 링크는 한 번만 보인다. (요구 AC5.3)
  - **AC2.3.4** Given 링크가 하나 이상 있는 글, When 목록을 본다, Then 목록 아래에 「이미 보낸 발행본에는 반영되지 않습니다. 고쳤다면 새로 발행하세요」가 보인다. (FR5.2)
  - **AC2.3.5** Given 링크가 하나도 없는 글, When 목록을 본다, Then 「발행하면 면접관에게 열릴 링크가 없습니다」 안내가 보인다. (FR5.2. 문구는 기능 설계)
  - **AC2.3.6** Given 편집 화면, When 화면 낭독기의 제목 목록으로 찾는다, Then h4 제목 「발행하면 면접관에게 열릴 링크」를 찾을 수 있고, 글자를 칠 때마다 목록이 소리 내어 읽히지 않는다. (NFR6, FR5.3)
  - **AC2.3.7** Given 편집 화면에서 링크를 쓰는 동안, When 목록이 바뀐다, Then API 요청은 일어나지 않는다. (FR5.3)
- **의존:** 링크 이름 규칙은 US2.2와 같은 것을 쓴다(FR5.1).

## US3. 쓰기 도움 문구 (할 일 (3), 1단계)

### US3.1 설명 초안과 질문을 보고 쓴다

- **사람:** 지원자
- **이야기:** 지원자로서 Catch 설명 초안과 생각해 볼 질문을 작성자 설명 칸보다 먼저 읽고 싶다. 그래야 질문을 보며 아래 칸에 자기 말로 적는다.
- **요구사항:** FR6.1, FR6.2
- **우선순위:** Must
- **수락 기준:**
  - **AC3.1.1** Given 설명 초안과 질문이 있는 Catch, When 지원자가 상세를 연다, Then Catch 설명 초안과 생각해 볼 질문이 작성자 설명 편집 영역보다 위에 있다. (요구 AC6.1)
  - **AC3.1.2** Given 같은 상세, When 칸 순서 전체를 본다, Then 위에서부터 작업에서 확인된 사실·나의 기여 → 근거 → 다시 볼 곳(있을 때) → Catch 설명 초안 → 생각해 볼 질문 → 작성자 설명(편집) → 현재 확인 상태다. (FR6.1)
  - **AC3.1.3** Given 질문이 있는 Catch, When 질문 아래를 본다, Then 「질문에 대한 답변을 저장하는 기능은 제공하지 않습니다.」 대신 질문을 보고 아래 칸에 자기 말로 적어 보라는 문구가 있고, 질문별 답을 넣는 칸은 없다. (FR6.2)
- **메모:** 질문의 내용과 만드는 방식은 #487 그대로다(FR6.2). 「다시 볼 곳」은 US9가 넣는다. 그 전에는 그 자리가 없을 뿐 나머지 순서는 같다.

### US3.2 편집 영역 안내로 무엇을 쓸지 안다

- **사람:** 지원자
- **이야기:** 지원자로서 편집 영역 위에서 빈 칸은 보이지 않는다는 것과 누가 이 글을 읽는지 알고 싶다. 그래야 쓰고 싶은 칸만 부담 없이 쓰고, 다른 사람의 이름·평가나 비밀값은 쓰지 않는다.
- **요구사항:** FR1.7
- **우선순위:** Must
- **수락 기준:**
  - **AC3.2.1** Given 지원자 상세의 편집 영역, When 안내를 본다, Then 첫 문장은 「쓰고 싶은 칸만 한두 문장씩 쓰면 됩니다. 빈 칸은 면접관에게 보이지 않습니다.」이고, 「AI가 만든 「Catch 설명 초안」은 이 설명을 바꾸지 않습니다」와 「비워 두고 저장하면 설명이 지워집니다」가 그대로 있으며, 그 아래에 「이 글은 링크를 가진 누구나 보고 외부 AI로도 보냅니다. 다른 사람의 이름·평가와 비밀값은 쓰지 마세요.」가 있다. (FR1.7)
  - **AC3.2.2** Given 같은 편집 영역, When 안내를 본다, Then 「경험의 맥락·판단·배운 점을 자유롭게 적어 주세요.」는 없다. (FR1.7)

## US4. 본인 목록 '설명 씀/안 씀' 걸러 보기 (할 일 (4), 1단계)

### US4.1 작성자 설명을 쓴 Catch와 안 쓴 Catch로 걸러 본다

- **사람:** 지원자
- **이야기:** 지원자로서 내 Catch 목록을 작성자 설명을 쓴 것과 안 쓴 것으로 걸러 보고 싶다. 그래야 아직 안 쓴 Catch를 찾아 쓰거나, 쓴 Catch만 모아 보낼 것을 고른다.
- **요구사항:** FR7.1, FR7.2, FR7.3, FR7.4, NFR6
- **우선순위:** Must
- **수락 기준:**
  - **AC4.1.1** Given 설명을 쓴 Catch가 25번째에만 있는 지원자, When 「씀」을 고른다, Then 그 Catch가 첫 쪽에 보인다. (요구 AC7.1)
  - **AC4.1.2** Given 「씀」 조건으로 받은 다음 쪽 커서, When 「안 씀」 조건으로 그 커서를 보낸다, Then 요청이 거부된다. (요구 AC7.2)
  - **AC4.1.3** Given 작성자 설명을 쓴 Catch가 하나도 없는 지원자, When 「씀」을 고른다, Then 빈 목록 대신 「작성자 설명을 쓴 Catch가 없습니다」 안내가 보인다. (요구 AC7.3)
  - **AC4.1.4** Given 내 Catch 목록, When 위의 선택 칸을 본다, Then 저장소·공개 상태 다음에 「작성자 설명: 전체/씀/안 씀」 칸이 보이는 `label`과 함께 있고, 걸러 본 개수는 `aria-live="polite"`로 알린다. (FR7.1, NFR6)
  - **AC4.1.5** Given 걸러 본 목록, When 카드를 본다, Then 카드에 설명 여부 표시가 없고 추천·순위도 없다. (FR7.3, FR7.4)

### US4.2 걸러 본 목록에서 설명을 써도 보던 자리를 잃지 않는다

- **사람:** 지원자
- **이야기:** 지원자로서 걸러 본 목록에서 Catch의 작성자 설명을 저장하거나 지워도 보던 쪽이 갑자기 바뀌지 않길 바란다. 그래야 같은 목록에서 여러 Catch를 이어서 쓴다.
- **요구사항:** FR7.4
- **우선순위:** Must
- **수락 기준:**
  - **AC4.2.1** Given 「안 씀」으로 걸러 본 목록에서 Catch A의 작성자 설명을 저장, When 상세를 닫는다, Then A는 지금 쪽에 그대로 있고, 걸러 보기를 다시 고르거나 화면을 다시 열면 A가 빠진다. (요구 AC7.4)

## US5. 발행 화면 (할 일 (5)와 대략 화면에서 더한 것, 1단계)

### US5.1 저장소마다 몇 개를 보낼지 안내를 본다

- **사람:** 지원자
- **이야기:** 지원자로서 발행할 자료를 고를 때 저장소마다 몇 개쯤 보내면 좋은지 안내를 보고 싶다. 그래야 너무 많이 보내 면접관이 읽지 못하는 일을 피한다.
- **요구사항:** FR8.1
- **우선순위:** Must
- **수락 기준:**
  - **AC5.1.1** Given 「발행할 자료 고르기」, When 안내를 본다, Then 기존 안내 아래에 「저장소마다 3~5개를 권합니다.」 한 줄이 있다. (FR8.1)
  - **AC5.1.2** Given 한 저장소의 Catch 7개를 고른 상태, When 확인 단계까지 간다, Then 저장소별 개수 경고·추천·순위가 보이지 않는다. (FR8.1)

### US5.2 고르기 목록에서 저장소 이름과 설명 여부를 본다

- **사람:** 지원자
- **이야기:** 지원자로서 고르기 목록의 Catch마다 저장소 이름과 작성자 설명을 썼는지를 보고 싶다. 그래야 여러 저장소의 Catch 가운데 보낼 것을 헷갈리지 않고 고른다.
- **요구사항:** FR8.2, FR8.6, FR8.7
- **우선순위:** Must
- **수락 기준:**
  - **AC5.2.1** Given 작성자 설명이 없는 Catch와 있는 Catch, When 발행 화면을 연다, Then 「내 Catch」 항목마다 저장소 이름이 보이고, 설명이 없는 Catch에만 「설명 안 씀」이 보인다. (FR8.2)
  - **AC5.2.2** Given 상세에서 작성자 설명을 막 저장한 Catch, When 발행 화면을 새로 연다, Then 그 Catch에 「설명 안 씀」이 없다. (FR8.7)
  - **AC5.2.3** Given 같은 Catch, When 본인 목록의 「씀」 걸러 보기와 발행 화면의 「설명 안 씀」 표시를 비교한다, Then 두 곳이 같은 판정을 낸다. (FR8.6)
- **메모:** 저장소 이름을 얻는 길(저장소 목록을 함께 부르기 또는 목록 응답에 칸 더하기)은 기능 설계에서 정한다(FR8.2).

### US5.3 작성자 설명을 쓴 Catch만 보며 고른다

- **사람:** 지원자
- **이야기:** 지원자로서 발행 화면에서 작성자 설명을 쓴 Catch만 보고 싶다. 그래야 20개씩 여러 쪽을 넘기지 않고 쓴 Catch를 찾아 고른다.
- **요구사항:** FR8.3, FR8.4, NFR6
- **우선순위:** Must
- **수락 기준:**
  - **AC5.3.1** Given 설명 없는 Catch A를 골라 둔 상태, When 「작성자 설명을 쓴 Catch만 보기」를 켠다, Then 목록에서 A는 사라지지만 고른 항목과 순서에는 A가 남는다. (요구 AC8.1)
  - **AC5.3.2** Given 처음 연 발행 화면, When 칸을 본다, Then 「작성자 설명을 쓴 Catch만 보기」는 꺼져 있고, 켜면 첫 쪽부터 다시 불러와 설명을 쓴 Catch만 보인다. (FR8.3)
  - **AC5.3.3** Given 최대 개수만큼 고른 상태(설명 없는 Catch 포함), When 칸을 켠다, Then 고른 개수는 그대로 최대로 세어져 더 고를 수 없다. (FR8.4)
  - **AC5.3.4** Given 발행 화면, When 칸을 켜거나 끈다, Then 체크 칸에 보이는 `label`이 있고 걸러 본 개수가 `aria-live="polite"`로 알려진다. (NFR6)

### US5.4 확인 단계에서 설명 없는 Catch 수를 본다

- **사람:** 지원자
- **이야기:** 지원자로서 발행 직전에 작성자 설명이 없는 Catch가 몇 개인지 보고 싶다. 그래야 면접관에게 「작성자 설명이 없습니다.」로 보일 Catch를 알고 보낸다.
- **요구사항:** FR8.5
- **우선순위:** Must
- **수락 기준:**
  - **AC5.4.1** Given 설명 없는 Catch 2개를 고른 상태, When 확인 단계로 간다, Then 「작성자 설명이 없는 Catch가 2개 있습니다…」가 보이고 [발행]은 누를 수 있다. (요구 AC8.2)
  - **AC5.4.2** Given 고른 Catch가 모두 작성자 설명이 있는 상태, When 확인 단계로 간다, Then 그 안내는 그려지지 않는다. (FR8.5)

## US6. 발행 사본의 세 칸 (할 일 (6), 2단계)

### US6.1 어느 저장소의 작업인지 본다

- **사람:** 면접관
- **이야기:** 면접관으로서 Catch 제목 아래에서 어느 저장소의 작업인지 보고 싶다. 그래야 여러 Catch를 받았을 때 저장소별로 구분해 묻는다.
- **요구사항:** FR9.1, FR9.7
- **우선순위:** Must
- **수락 기준:**
  - **AC6.1.1** Given 이 변경 뒤에 발행한 Catch, When 면접관이 연다, Then 제목 아래 줄에 저장소 이름이 보인다. (FR9.1, 요구 AC9.1)
  - **AC6.1.2** (이 기준의 사람은 지원자) Given 같은 발행본의 작성자 발행본 상세, When 지원자가 연다, Then 같은 저장소 줄이 보인다. (FR9.7)

### US6.2 작성자 설명을 언제 마지막으로 고쳤는지 본다

- **사람:** 면접관
- **이야기:** 면접관으로서 작성자 설명을 마지막으로 고친 달을 보고 싶다. 그래야 작업 뒤 얼마나 지나 쓴 글인지 알고 읽는다.
- **요구사항:** FR9.2
- **우선순위:** Must
- **수락 기준:**
  - **AC6.2.1** Given 작성자 설명을 2026년 11월에 고친 Catch, When 발행 뒤 면접관이 연다, Then 「작성자 설명」 머리 옆에 「2026년 11월에 마지막으로 고침」이 보인다. (요구 AC9.1)
  - **AC6.2.2** Given 작성자 설명을 2026-11-30T16:00Z(한국 시간 12월 1일 01:00)에 마지막으로 고친 Catch, When 발행 뒤 면접관이 연다, Then 「2026년 12월에 마지막으로 고침」이 보인다. (요구 AC9.5)
  - **AC6.2.3** Given 작성자 설명이 없는 Catch, When 발행 뒤 면접관이 연다, Then 작성 시점이 보이지 않고 사본에도 담기지 않는다. (FR9.2)
  - **AC6.2.4** Given 발행 뒤 지원자가 작성자 설명을 고친 Catch, When 면접관이 같은 발행본을 연다, Then 발행 때의 달이 그대로 보인다. (가정 A7)

### US6.3 이 기록으로 알 수 없는 것을 본다

- **사람:** 면접관
- **이야기:** 면접관으로서 이 작업의 기록만으로는 알 수 없는 것을 작업 사실 바로 아래에서 보고 싶다. 그래야 기록을 지나치게 믿지 않고 그 부분을 면접에서 직접 묻는다.
- **요구사항:** FR9.3, FR9.4
- **우선순위:** Must
- **수락 기준:**
  - **AC6.3.1** Given 커밋 목록을 다 받지 못한 PR 한계가 근거 두 개에 같은 문장으로 있는 Catch, When 발행본을 연다, Then 「이 기록으로 알 수 없는 것」에 그 문장이 한 번만 보인다. (요구 AC9.2)
  - **AC6.3.2** Given 같은 변경을 다시 냈거나 cherry-pick으로 옮긴 것일 수 있다는 경고와 「병합 커밋이라 변경 내용을 조회하지 않았다」 같은 근거별 조회 상태가 함께 있는 Catch, When 발행본을 연다, Then 목록에는 그 경고만 있고 근거별 조회 상태 문장은 없다. (FR9.3)
  - **AC6.3.3** Given 두 한계가 모두 없는 Catch, When 발행본을 연다, Then 「이 기록으로 알 수 없는 것」 목록이 그려지지 않는다. (FR9.4)
  - **AC6.3.4** Given 한계가 있는 발행본, When 면접관이 연다, Then 목록은 「기록에서 확인한 내용」 안 작업 사실 바로 아래에 펼쳐진 채 보인다. (FR9.4)
- **메모:** 두 문장을 골라내는 방법(고정 문장 대조 또는 종류 칸 더하기)은 계약 설계·기능 설계에서 정한다(FR9.3). 작업 전체 한계가 이 두 가지뿐이라는 것은 가정 A1이다.

### US6.4 이 변경 전에 받은 발행본도 지금처럼 본다

- **사람:** 면접관
- **이야기:** 면접관으로서 이 변경 전에 받은 발행본도 오류 없이 지금처럼 보고 싶다. 그래야 이미 받은 링크를 다시 받지 않아도 된다.
- **요구사항:** FR9.6, FR9.7, NFR7
- **우선순위:** Must
- **수락 기준:**
  - **AC6.4.1** Given 이 변경 전에 만든 사본, When 면접관이 연다, Then 저장소 줄·작성 시점·한계 목록 없이 지금처럼 보이고 오류가 나지 않는다. (요구 AC9.3)
  - **AC6.4.2** Given 세 칸이 있는 사본, When 면접관이 받은 사람 링크로 연다, Then 세 칸이 모두 보인다. (FR9.7)

### US6.5 AI 답은 화면에만 붙인 칸을 근거로 쓰지 않는다

- **사람:** 면접관
- **이야기:** 면접관으로서 AI 요약과 답이 GitHub 기록과 작성자 자료에서만 나오길 바란다. 그래야 CatchU가 화면에 붙인 저장소 이름·작성 시점·한계·링크 이름·표지를 AI가 근거처럼 옮기지 않는다.
- **요구사항:** FR9.5, NFR2
- **우선순위:** Must
- **수락 기준:**
  - **AC6.5.1** Given 세 칸이 있는 사본, When 받은 사람 AI가 요약 근거와 검색 조각을 만든다, Then 세 칸의 글자는 들어가지 않는다. (요구 AC9.4)
  - **AC6.5.2** Given 표지가 붙는 링크가 든 사본, When 검색 조각과 요약 근거를 만든다, Then 링크 이름과 표지 글자가 0건이다. (NFR2)
  - **AC6.5.3** Given 같은 발행본에서 AI 답을 받는다, When 근거 딱지를 본다, Then 딱지는 'GitHub 기록 원문'과 '작성자 자료 원문' 둘뿐이다. (NFR2)

## US7. 「이 작업의 본인 커밋」 링크 표지 (할 일 (7), 2단계)

### US7.1 본인 커밋을 가리키는 링크에 표지를 본다

- **사람:** 면접관
- **이야기:** 면접관으로서 작성자 글 속 링크가 이 작업의 본인 커밋을 가리키면 그 표지를 보고 싶다. 그래야 지원자가 붙인 링크가 이 작업에서 본인이 쓴 커밋인지 열기 전에 안다.
- **요구사항:** FR10.1, FR10.2, FR10.3, FR10.5, FR10.6, NFR6
- **우선순위:** Must
- **수락 기준:**
  - **AC7.1.1** Given 사본에 본인 커밋 근거 `ba6bba8c…`(40자)가 있는 Catch와 작성자 글 속 짧은 식별값 링크 `…/blob/ba6bba8/a.ts#L3`, When 면접관이 연다, Then 「a.ts · L3 · 판본 ba6bba8」 바로 뒤에 표지가 붙는다. (요구 AC10.1)
  - **AC7.1.2** Given 같은 Catch와 40자 전체 식별값 커밋 링크 `…/commit/BA6BBA8C…`(대문자), When 면접관이 연다, Then 「커밋 ba6bba8」 바로 뒤에 표지가 붙는다. (요구 AC10.2)
  - **AC7.1.3** Given 표지가 붙은 링크, When 화면 낭독기로 읽거나 색을 구별하지 못하는 화면으로 본다, Then 표지는 「이 작업의 본인 커밋」 글자로 읽힌다. (NFR6)
  - **AC7.1.4** Given 표지가 붙은 줄 범위 파일 링크, When 면접관이 본다, Then 표지는 판본 이름 바로 뒤에 있고, 표지의 뜻을 푸는 안내 문장은 화면에 없다. (FR10.5)
  - **AC7.1.5** Given 사본 근거 저장소가 `ljm0850/TheMe`인 Catch와 작성자 글 속 `LJM0850/theme` 저장소의 본인 커밋 링크, When 면접관이 연다, Then 표지가 붙는다. (FR10.3)
  - **AC7.1.6** Given 줄 범위가 없는 본인 커밋 판본의 파일 링크 `…/blob/ba6bba8/a.ts`, When 면접관이 연다, Then 판본 이름 뒤에 표지가 붙는다. (FR10.3)
- **의존:** US2.2의 링크 이름 뒤에 만든다. 짚어 볼 곳 링크(US2.1)가 먼저 있어야 한다(FR10.6, 할 일 목록 「항목 의존」).
- **메모:** 발행할 때 사본 근거에 본인 커밋 근거인지를 담는 것(FR10.2)은 그 결과를 AC7.2.2가 시험한다. 칸 모양은 계약 설계에서 정한다. 표지의 뜻(판본이 본인 커밋이라는 뜻이지 그 줄을 본인이 썼다는 뜻이 아님)은 기능 설계 문서와 README에 적는다(FR10.5).

### US7.2 본인 커밋이 확실하지 않은 링크에는 표지를 보지 않는다

- **사람:** 면접관
- **이야기:** 면접관으로서 본인 커밋인지 확실하지 않은 링크에는 아무 표지도 보지 않길 바란다. 그래야 남의 커밋이나 병합 커밋을 본인 것으로 잘못 읽지 않는다.
- **요구사항:** FR10.1, FR10.3, FR10.4, NFR5
- **우선순위:** Must
- **수락 기준:**
  - **AC7.2.1** Given 같은 식별값이지만 다른 저장소의 링크, When 면접관이 연다, Then 표지가 붙지 않는다. (요구 AC10.3)
  - **AC7.2.2** Given 같은 작업의 병합 커밋 링크, 그리고 본인 커밋이 아닌 PR 마지막 커밋을 판본으로 쓴 파일 링크, When 면접관이 연다, Then 둘 다 표지가 붙지 않는다. (요구 AC10.4)
  - **AC7.2.3** Given 링크의 7자 식별값이 사본의 본인 커밋 둘과 앞부분이 같은 경우, When 면접관이 연다, Then 표지가 붙지 않는다. (요구 AC10.5)
  - **AC7.2.4** Given 사본 근거와 맞지 않는 링크, When 면접관이 연다, Then 「CatchU가 확인하지 않은 주소」 같은 부정 표지도 붙지 않는다. (FR10.4)
  - **AC7.2.5** Given 본인 커밋이 20건을 넘는 작업에서 사본 근거에 들지 않은 오래된 본인 커밋 링크, When 면접관이 연다, Then 표지가 붙지 않는다. (FR10.3)
  - **AC7.2.6** Given 작성자가 글에 「[이 작업의 본인 커밋]」이라고 직접 적은 발행본, When 면접관이 연다, Then 그 글자는 진짜 표지와 화면 모양이 다르다. (NFR5)

## US8. 기본 요약·질의응답 지시 (할 일 (8), 2단계)

### US8.1 AI가 작성자 주장을 작성자의 말로 옮긴다

- **사람:** 면접관
- **이야기:** 면접관으로서 AI 요약과 답이 작성자 주장을 「작성자는 …라고 적었다」로 옮기길 바란다. 그래야 지원자의 말을 확인된 사실로 오해하지 않고 면접에서 확인할 거리로 본다.
- **요구사항:** FR11.1, NFR2
- **우선순위:** Must
- **수락 기준:**
  - **AC8.1.1** Given 작성자 설명에 「서버 쪽 일정이 빠듯해 화면에서 했다」가 있는 발행본, When 면접관이 「왜 화면에서 줄였나요?」를 묻는다, Then 답은 「작성자는 …라고 적었다」 꼴로 옮기고 '작성자 자료 원문' 딱지를 붙인다. (요구 AC11.1)
  - **AC8.1.2** Given 같은 발행본, When AI 기본 요약을 만든다, Then 작성자 설명에서 온 문장은 「작성자는 …라고 적었다」 꼴이고 '작성자 자료 원문' 딱지가 붙는다. (FR11.1)
  - **AC8.1.3** Given 바뀐 지시로 만든 AI 답, When 면접관이 질문한다, Then 남의 기여를 지원자 기여로 쓴 답이 없다. 판정은 빌드와 시험의 질의응답 10개 재측정(NFR3)에서 0건이다. (FR11.1, NFR3)
- **메모:** 지시를 바꾼 뒤 질의응답 10개를 다시 재는 일(FR11.2, NFR3)은 빌드와 시험(`build-and-test`)에서 한다.

## US9. 다시 볼 곳 — 기억 되살리기 사실 (할 일 (9), 3단계)

### US9.1 같은 작업 안에서 다시 고친 곳을 본다

- **사람:** 지원자
- **이야기:** 지원자로서 같은 작업 안에서 내가 나중에 다시 고친 줄을 Catch 상세에서 보고 싶다. 그래야 그때 무엇을 바꿨는지 기억을 되살려 작성자 설명에 쓴다.

  - **AC9.1.2** Given 다른 작업의 커밋이 앞 작업의 줄을 고친 경우, When 분석한다, Then 다시 고친 곳으로 남지 않는다. (요구 AC12.2)
  - **AC9.1.3** Given 사실이 없는 Catch, 또는 3단계 전에 만든 Catch, When 지원자가 상세를 연다, Then 「다시 볼 곳」 칸이 없다. (요구 AC12.3, FR12.2)

- **메모:** 지금 근거 링크(`safeEvidenceUrl`)는 바꾸지 않는다(가정 A4).

### US9.2 새 파일로 옮긴 곳과 확장자 바꿈을 본다

- **사람:** 지원자
- **이야기:** 지원자로서 같은 작업 안에서 파일을 옮기거나 확장자를 바꾼 곳을 보고 싶다. 그래야 구조를 왜 바꿨는지 떠올려 작성자 설명에 쓴다.
- **요구사항:** FR12.1, FR12.4
- **우선순위:** Must
- **수락 기준:**
  - **AC9.2.1** Given 같은 작업 안의 본인 커밋이 `src/a.js`를 지우고 내용이 같은 `lib/a.js`를 새로 만든 경우, When 분석한다, Then 「다시 볼 곳」에 새 파일로 옮긴 곳(`src/a.js` → `lib/a.js`)이 남는다. (요구 AC12.4)
  - **AC9.2.2** Given 같은 작업 안의 본인 커밋이 `util.js`를 `util.ts`로 이름을 바꾼 경우, When 분석한다, Then 확장자 바꿈이 남는다. (요구 AC12.5)
- **메모:** 옮긴 곳 판정에 수집 중의 파일 내용 식별값을 쓰는 것(FR12.4)은 AC9.2.1로 추적한다. 분석 뒤 GitHub를 다시 읽지 않는 것은 이야기로 만들지 않은 NFR1에서 시험한다.

### US9.3 되돌린 커밋을 본다

- **사람:** 지원자
- **이야기:** 지원자로서 같은 작업 안에서 내가 되돌린 커밋을 보고 싶다. 그래야 무엇을 시도했다가 버렸는지 떠올려 「고른 것과 버린 것」 칸에 쓴다.

- **수락 기준:**

- **메모:** 메시지 없이 손으로 되돌린 것은 다시 고친 곳(US9.1)으로만 잡힌다(가정 A2).

### US9.4 다시 볼 곳은 나만 본다

- **사람:** 지원자
- **이야기:** 지원자로서 「다시 볼 곳」은 나만 보길 바란다. 그래야 기억 정리용 사실이 면접관에게 평가 재료로 가지 않는다.

- **우선순위:** Must
- **수락 기준:**
  - **AC9.4.1** Given 「다시 볼 곳」 사실이 있는 Catch를 발행, When 면접관이 발행본을 열고 받은 사람 AI가 조각을 만든다, Then 사본·면접관 화면·조각 어디에도 그 사실이 없다. (요구 AC12.7)

## US11. 작업 시각과 본인 목록 정렬 (할 일 (11), 3단계)

### US11.1 최근에 한 작업부터 목록을 본다

- **사람:** 지원자
- **이야기:** 지원자로서 내 Catch 목록을 최근에 한 작업부터 보고 싶다. 그래야 기억이 생생한 작업부터 쓰고 고른다.
- **요구사항:** FR14.1, FR14.2, FR14.3, NFR7
- **우선순위:** Must
- **수락 기준:**
  - **AC11.1.1** Given 마지막 본인 커밋이 2025-04인 Catch A, 2025-06인 Catch B, 시각 없는 Catch C, When 목록을 연다, Then 순서는 B, A, C다. (요구 AC14.1)
  - **AC11.1.2** Given 마지막 본인 커밋의 작성 시각이 2025-04-10이고 커밋 시각은 리베이스로 2025-05-01인 Catch와, 마지막 작성 시각이 2025-04-20인 Catch, When 지원자가 목록을 연다, Then 2025-04-20인 Catch가 위에 있다. (요구 AC14.3을 지원자가 보는 순서로 바꿈, FR14.1)
  - **AC11.1.3** Given 마지막 작업 시각이 같은 Catch 둘, When 목록을 여러 번 연다, Then 두 Catch의 순서가 늘 같다. (FR14.2)
  - **AC11.1.4** Given 작업 시각이 있는 Catch, When 지원자가 목록 카드를 보고 면접관이 발행본을 연다, Then 어디에도 작업 시각이 보이지 않고 정렬 선택 칸도 없다. (FR14.3)
- **의존:** 정렬은 같은 이야기 안에서 작업 시각을 남긴 뒤에 만든다(할 일 목록 「항목 의존」).

### US11.2 다음 쪽을 불러와도 빠지거나 겹치는 Catch가 없다

- **사람:** 지원자
- **이야기:** 지원자로서 목록의 다음 쪽을 불러와도 Catch가 빠지거나 두 번 나오지 않길 바란다. 그래야 모든 Catch를 한 번씩 보고 고른다.
- **요구사항:** FR14.4
- **우선순위:** Must
- **수락 기준:**
  - **AC11.2.1** Given 45개의 Catch, When 20개씩 세 쪽을 불러온다, Then 45개가 한 번씩만 나온다. (요구 AC14.2)

## INVEST 점검

| 기준 | 점검 |
|---|---|
| Independent | 한 이야기는 한 화면 동작이다. 위 의존 표의 순서 말고는 서로 기대지 않는다. US7은 US2의 링크 이름에 기대므로 항목 의존을 그대로 적었다. |
| Negotiable | 칸 제목 줄 모양, 쉬운 안내 문구, 한계 문장 골라내는 법, 저장소 이름 얻는 길, 표지 흉내 처리는 기능 설계·계약 설계에서 정한다(요구사항 「열린 질문」). |
| Valuable | 이야기마다 「그래야」 절이 지원자나 면접관이 얻는 것을 말한다. 사용자 가치가 아닌 확인 일은 이야기로 만들지 않았다(Q2 A). |
| Estimable | 공수는 단계별 대략값(1단계 3~5, 2단계 7~13, 3단계 3~6인일, 실측 아님)만 있고 이야기별로 나누지 않는다(할 일 목록 「우선순위 방식」). 일정 계획에서 나눈다. |
| Small | 묶음 안에서 화면 동작 하나씩 나눴다. 가장 큰 것은 수락 기준이 11개인 US2.2(링크 이름)다. |
| Testable | 모든 이야기에 Given/When/Then 수락 기준이 있고, 요구사항의 수락 기준 AC1.1~AC14.3이 모두 어느 이야기에 옮겨졌다. |
