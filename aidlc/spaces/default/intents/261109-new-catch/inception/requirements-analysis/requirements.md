## Catch 정의

> Catch는 지원자가 분석된 작업 가운데 골라 면접관에게 보내는 한 장이다. 그 작업에서 내린 판단을 지원자가 자기 말로 적고, 면접관이 그 말을 시험해 볼 코드 자리와 GitHub 원본이 함께 붙는다. Catch는 판단을 증명하지 않는다. 판단은 면접에서 확인한다.

고르지 않은 작업도 지원자 화면에는 Catch로 남는다. 이미 있는 원칙 넷을 함께 지킨다.

- CatchU는 판단을 증명하거나 평가하지 않는다.
- 면접관에게 가는 글은 누가 썼는지 구분한다.
- 면접관은 원본으로 한 번에 갈 수 있어야 한다.
- 고르는 일은 지원자가 하고, CatchU는 순위나 추천을 내지 않는다.

'사람은 결과물이 아니라 판단의 흔적으로 설명된다'는 명제는 기능을 고르는 판정 기준으로 쓰지 않는다(입력 문서 §8-1의 13).

## 의도 분석

- **무엇을 이루려는가:** 면접관이 지원자가 무엇을 맡았고 무엇을 고르고 버렸는지, AI가 낸 것을 어떻게 확인했는지를 실제 코드 앞에서 물을 수 있게 한다. 이를 위해 지원자가 고른 Catch에 자기 말로 쓴 판단과 짚어 볼 코드 자리를 붙이고, 면접관 화면에 그 말을 시험할 재료(원본 링크, 저장소 이름, 작성 시점, 이 작업만의 조회 한계)를 더한다. (의도 설명 「Problem Statement」)
- **종류:** 기존 기능 고치기. web·api·worker 세 서비스에 걸치지만 새 외부 서비스는 없다(제약 1).
- **크기:** 할 일 11개, 모두 Must. 1~3단계 합계 약 13~24인일(실측 아님), 모두 팀장 몫이다(범위 문서, 제약 11).
- **깊이:** Standard.

## 기능 요구사항

### 1단계 — 지원자 화면 (할 일 (1)~(5))

#### FR1. 칸 제목이 붙은 작성자 설명 쓰기 (할 일 (1))

- **FR1.1** 지원자 Catch 상세의 작성자 설명은 칸 제목 8개를 모두 펼친 채 칸마다 글칸을 보인다. 칸 제목은 위에서부터 「이 작업에서 정한 것」·「맡은 부분」·「무엇이 문제였나」·「고른 것과 버린 것」·「어떻게 확인했나·결과」·「AI가 낸 것 가운데 받아들이지 않았거나 고친 것」·「짚어 볼 곳」·「더 쓰기」다. 모든 칸은 건너뛸 수 있다. (할 일 목록 (1), 대략 화면 Q4)
- **FR1.2** [설명 저장] 단추 하나로 쓴 칸들을 지금의 작성자 설명 한 칸에 칸 제목과 함께 넣어 저장한다. 빈 칸은 칸 제목째 저장하지 않는다. 칸마다 따로 저장하지 않는다. (입력 문서 §8-1의 7, 제약 2)
- **FR1.3** 글자 상한은 지금 그대로 4,000자이며 칸 제목 글자를 포함해 센다. 화면은 맨 아래에 합계 글자 수 하나를 「(칸 제목 포함)」과 함께 보인다. 4,000자를 넘으면 지금처럼 저장하지 못한다고 알리고, 쓴 글은 그대로 둔다. (제약 2, 대략 화면 Q4)
- **FR1.4** 8칸을 모두 비우고 저장하면 지금처럼 작성자 설명이 지워진다. (대략 화면 2절)
- **FR1.5** 「더 쓰기」 칸만 쓴 글은 칸 제목 글자를 붙이지 않고 저장한다. 칸 제목을 읽지 못하는 옛 글(지금의 자유 글 등)은 편집 화면을 열면 전체가 「더 쓰기」 칸에 들어가 있고, 그대로 다시 저장해도 칸 제목 글자 때문에 4,000자를 넘지 않는다. (대략 화면 2절)
- **FR1.6** 저장되는 칸 제목 줄의 모양은 기능 설계에서 정한다. 그 모양은 (a) 받은 사람 AI 재료에도 저장된 글 그대로 들어가므로 사람이 읽기 쉽고, (b) 일반 글과 겹치지 않으며, (c) 옛 자유 글이 칸으로 잘못 나뉘지 않아야 한다. 지원자가 글 안에 칸 제목 줄과 같은 줄을 써도 막지 않고, 그 줄부터 그 칸으로 읽히는 것을 한계로 둔다. (Q1)
- **FR1.7** 편집 영역 안내 첫 문장 「경험의 맥락·판단·배운 점을 자유롭게 적어 주세요.」를 「쓰고 싶은 칸만 한두 문장씩 쓰면 됩니다. 빈 칸은 면접관에게 보이지 않습니다.」로 바꾼다. 뒤의 두 안내(「AI가 만든 「Catch 설명 초안」은 이 설명을 바꾸지 않습니다」, 「비워 두고 저장하면 설명이 지워집니다」)는 그대로 두고, 그 아래에 「이 글은 링크를 가진 누구나 보고 외부 AI로도 보냅니다. 다른 사람의 이름·평가와 비밀값은 쓰지 마세요.」 한 줄을 더한다. (할 일 (3), 제약 8, 대략 화면 2절)
- **FR1.8** 칸 제목 문구를 나중에 바꾸면 이미 쓴 글에는 옛 문구가 남는다. 이것을 한계로 둔다. (입력 문서 §8-1의 7)

수락 기준:
- **AC1.1** Given 작성자 설명이 없는 Catch의 상세, When 「이 작업에서 정한 것」과 「짚어 볼 곳」 두 칸만 쓰고 저장, Then 저장된 글에는 두 칸만 칸 제목과 함께 들어가고 나머지 여섯 칸 제목은 없다.
- **AC1.2** Given 칸 제목 글자를 포함한 합계가 4,001자인 글, When 저장, Then 저장되지 않고 상한 안내가 보이며 쓴 글은 화면에 남는다.
- **AC1.3** Given 8칸이 모두 빈 편집 화면(이전 설명 있음), When 저장, Then 작성자 설명이 지워진다.
- **AC1.4** Given 칸 제목 줄이 없는 3,990자의 옛 자유 글, When 편집 화면을 열고 그대로 저장, Then 글 전체가 「더 쓰기」 칸에 보였고 저장이 4,000자 상한에 걸리지 않는다.
- **AC1.5** Given 「맡은 부분」에 두 줄, 「짚어 볼 곳」에 링크 두 줄을 쓰고 저장한 Catch, When 상세를 닫았다 다시 연다, Then 두 칸에 쓴 글이 칸 안의 줄바꿈까지 그대로 돌아오고 나머지 여섯 칸은 비어 있다.

#### FR2. 면접관 화면의 칸 제목별 보기 (할 일 (1))

- **FR2.1** 발행본 Catch(받은 사람 화면과 작성자 발행본 상세)는 저장된 작성자 설명을 칸 제목별로 나눠 보이고, 빈 칸은 칸 제목째 보이지 않는다. (할 일 (1), 대략 화면 4절)
- **FR2.2** 「더 쓰기」 칸만 있는 글(칸 제목을 읽지 못하는 옛 글 포함)은 칸 제목 없이 지금처럼 보인다. 「더 쓰기」가 다른 칸과 함께 있으면 면접관 화면에서만 머리 글자를 「덧붙인 말」로 보인다. 저장된 칸 제목은 「더 쓰기」 그대로다. (대략 화면 4절, Q2)
- **FR2.3** 작성자 설명이 통째로 없으면 지금처럼 「작성자 설명이 없습니다.」를 보인다. (대략 화면 4절)
- **FR2.4** 「이 작업에서 정한 것」을 제목 바로 아래로 올리지 않는다. 칸 순서는 #488 순서(불일치 표지 → AI 설명 초안 → 작성자 설명 → 기록에서 확인한 내용) 그대로다. (입력 문서 §3-4·§4-3)

수락 기준:
- **AC2.1** Given 「맡은 부분」과 「더 쓰기」 두 칸이 저장된 발행본, When 면접관이 연다, Then 「맡은 부분」과 「덧붙인 말」 두 칸만 보이고 다른 칸 제목은 없다.
- **AC2.2** Given 칸 제목 줄이 없는 옛 자유 글이 든 발행본, When 면접관이 연다, Then 글 전체가 칸 제목 없이 지금처럼 보인다.

#### FR3. 작성자 설명 안 GitHub 링크의 이름 (대략 화면 「GitHub 링크 이름」)

- **FR3.1** 작성자 설명 안의 GitHub 링크는 주소 전체 대신 아래 이름으로 보인다. 링크를 찾는 판별 규칙(`web/src/lib/github-source-url.ts`)은 그대로 둔다. 텍스트 자료 본문의 링크 표시는 바꾸지 않는다(가정 A6).

| 링크 모양 | 보이는 이름 |
|---|---|
| 파일 줄 링크(`/blob/<판본>/<경로>#L<시작>-L<끝>` 또는 `#L<줄>`) | 파일 이름 · L40–58(한 줄이면 L40) · 판본 ba6bba8 |
| 줄 범위 없는 파일·폴더 링크(`/blob/<판본>/<경로>`, `/tree/<판본>/<경로>`) | 경로 끝 이름 · 판본 ba6bba8 |
| 커밋 링크(`/commit/<식별값>`) | 커밋 ba6bba8 |
| 커밋 화면의 바뀐 줄 링크(`/commit/<식별값>#diff-<64자>R16-R23`, 한쪽 범위·한 줄만. 2026-11-10 더함: NC1 로컬 확인 중 팀장 발견) | 커밋 ba6bba8 · 바뀐 줄 16–23(한 줄이면 「바뀐 줄 16」, L 쪽은 「이전 줄」). 파일 이름은 주소에 없다 |
| PR 링크(`/pull/<번호>`) | PR #12 |
| 그 밖의 GitHub 주소 | 지금처럼 주소 전체 |

- **FR3.2** 판본 자리가 16진수 7~40자면 커밋 식별값으로 보고 앞 7자만 「판본 …」으로 보인다. 그 밖은 「브랜치 main」처럼 그 이름 그대로 보인다. (Q3)
- **FR3.3** 링크의 저장소가 이 Catch 근거의 저장소와 다르면 이름 앞에 「소유자/저장소 ·」를 붙인다. (대략 화면 「GitHub 링크 이름」)
- **FR3.4** 주소에 붙은 질의(`?plain=1` 등)는 이름을 정할 때 무시하고 링크 대상에서는 지우지 않는다. 퍼센트 인코딩된 한글 경로는 보이는 이름에서만 한글로 풀고, 링크 대상은 인코딩된 그대로다. 주소 전체는 마우스를 올리면 보인다. 링크는 새 탭에서 열린다. (대략 화면 「GitHub 링크 이름」)
- **FR3.5** 이름은 화면에서만 계산한다. API와 저장된 글은 바꾸지 않는다. 답의 근거 위치 강조(C-11)는 원문 주소 길이로 센다. (대략 화면, 코드 지식 「이 intent가 닿는 자리」)
- **FR3.6** 퍼센트 디코딩에 실패한 부분은 이름에서 원문 그대로 보인다. 긴 이름은 자르지 않고 줄을 바꿔 보인다. (변경 요청)

수락 기준:
- **AC3.1** Given 작성자 설명에 `https://github.com/o/r/blob/ba6bba8c…40자/src/CreateArticlePage.vue#L40-L58`, When 발행본을 연다, Then 링크 글자는 「CreateArticlePage.vue · L40–58 · 판본 ba6bba8」이고 누르면 원래 주소가 새 탭에서 열린다.
- **AC3.2** Given `…/blob/main/src`, When 발행본을 연다, Then 링크 글자는 「src · 브랜치 main」이다.
- **AC3.3** Given 근거 저장소가 `o/r`인 Catch에 `https://github.com/other/lib/commit/1a2b3c4d…`, When 발행본을 연다, Then 링크 글자는 「other/lib · 커밋 1a2b3c4」이다.
- **AC3.4** Given `…/blob/ba6bba8/a.ts?plain=1#L3`, When 발행본을 연다, Then 링크 글자는 「a.ts · L3 · 판본 ba6bba8」이고 링크 대상에는 `?plain=1`이 남아 있다.
- **AC3.5** Given 경로에 잘못된 퍼센트 인코딩 `%E0%A4`가 든 파일 링크, When 발행본을 연다, Then 그 부분은 `%E0%A4` 그대로 이름에 보이고 화면이 깨지지 않는다.

#### FR4. 짚어 볼 곳과 관련 커밋 넣기 (할 일 (2))

- **FR4.1** 「짚어 볼 곳」은 다른 칸과 같은 여러 줄 글칸이다. 칸 아래 안내는 네 가지를 알린다. 면접관이 설명을 청할 만한 줄(정한 것·고친 것이 드러나는 곳)을 고르라는 것, 위 근거의 본인 커밋을 열고 바뀐 줄의 줄 번호를 눌러 주소창의 주소를 붙이라는 것, 메모에 파일 이름과 짚을 까닭을 적으라는 것, 관련 커밋은 위 근거의 본인 커밋 주소를 붙이라는 것이다. 파일 줄 링크(`/blob/…#L…`)도 지금처럼 받는다. (할 일 (2), 대략 화면 2절. 2026-11-10 고침: 처음에는 Copy permalink·한 줄에 링크 하나와 메모 한 줄·한글 파일 이름 안내를 둔 다섯 가지였다. NC1 로컬 확인 중 팀장이 줄 고정 주소를 얻기 어렵다는 것을 발견해 커밋 화면 한 가지로 줄였다. 커밋 화면 주소는 파일 경로가 기호로 들어가 한글 앞에서 끊기지 않는다.)
- **FR4.2** 관련 커밋을 넣는 단추나 목록은 두지 않는다. 근거 밖 커밋을 붙여도 저장은 되고, 면접관 화면에서 표지가 붙지 않는다(FR10). (대략 화면 Q2 A)

수락 기준:
- **AC4.1** Given 짚어 볼 곳 칸, When 지원자가 칸을 본다, Then 네 가지 안내가 칸 아래에 보인다(2026-11-10 다섯에서 넷으로 고침, FR4.1).

#### FR5. 발행하면 면접관에게 열릴 링크 목록 (대략 화면 Q2의 더한 것)

- **FR5.1** 지원자 편집 화면의 8칸 아래, 합계 글자 수 바로 위에 h4 제목 「발행하면 면접관에게 열릴 링크」와 목록을 둔다. 목록은 8칸 전체의 글을 면접관 화면과 같은 판별 규칙으로 읽어, 링크가 될 주소를 FR3의 이름 그대로 보인다. 한글 앞에서 끊긴 주소나 브랜치 주소는 이름에서 드러나므로 따로 경고 표지를 달지 않는다. (대략 화면 2절)
- **FR5.2** 목록 아래에 「이미 보낸 발행본에는 반영되지 않습니다. 고쳤다면 새로 발행하세요」 한 줄을 붙인다. 링크가 하나도 없으면 「발행하면 면접관에게 열릴 링크가 없습니다」로 보인다(문구는 기능 설계). (대략 화면 2절)
- **FR5.3** 화면 안에서만 계산하고 API는 바꾸지 않는다. 목록은 알림 영역이 아니다(타자마다 읽히지 않게). (대략 화면 2절)
- **FR5.4** 같은 링크가 여러 칸에 있으면 목록에는 한 번만 보인다. (변경 요청)

수락 기준:
- **AC5.1** Given 「맡은 부분」 칸에 커밋 링크 하나, 「짚어 볼 곳」 칸에 파일 줄 링크 하나, When 지원자가 쓴다, Then 목록에 두 링크가 FR3 이름으로 보인다.
- **AC5.2** Given 한글 파일 이름이 인코딩되지 않은 주소, When 지원자가 붙인다, Then 목록에 한글 앞에서 끊긴 이름(파일 이름 없이 폴더까지 등)이 보인다.
- **AC5.3** Given 같은 커밋 링크를 「맡은 부분」과 「짚어 볼 곳」에 함께 쓴 글, When 지원자가 목록을 본다, Then 그 링크는 한 번만 보인다.

#### FR6. 지원자 상세의 칸 순서와 생각해 볼 질문 문구 (할 일 (3))

- **FR6.1** 지원자 Catch 상세는 위에서부터 작업에서 확인된 사실·나의 기여 → 근거 → 다시 볼 곳(3단계, FR12) → Catch 설명 초안 → 생각해 볼 질문 → 작성자 설명(편집) → 현재 확인 상태다. 지금과 달라지는 것은 Catch 설명 초안과 생각해 볼 질문이 작성자 설명 위로 올라가고 「다시 볼 곳」이 근거 아래에 끼는 것뿐이다. (대략 화면 Q3 B)
- **FR6.2** 생각해 볼 질문의 내용·생성 방식은 #487 그대로다. 질문 아래 문구 「질문에 대한 답변을 저장하는 기능은 제공하지 않습니다.」만 「질문을 보고 아래 칸에 자기 말로 적어 보세요」 같은 말로 바꾼다. 질문별 답은 저장하지 않는다. (할 일 (3), 입력 문서 §9)

수락 기준:
- **AC6.1** Given 설명 초안과 질문이 있는 Catch, When 지원자가 상세를 연다, Then Catch 설명 초안과 생각해 볼 질문이 작성자 설명 편집 영역보다 위에 있다.

#### FR7. 본인 목록 '설명 씀/안 씀' 걸러 보기 (할 일 (4))

- **FR7.1** 내 Catch 목록 위의 선택 칸에 「작성자 설명: 전체/씀/안 씀」 하나를 더한다(저장소·공개 상태 다음). (할 일 (4), 대략 화면 1절)
- **FR7.2** 이 걸러 보기는 저장소 걸러 보기처럼 목록 요청 조건으로 서버에서 거른다. 다음 쪽 커서는 이 조건도 함께 묶어, 다른 조건으로 받은 커서를 거부한다. 「작성자 설명이 있는지」는 저장된 작성자 설명이 비어 있지 않은지로 정한다. (대략 화면 1절, 코드 지식 「이 intent가 닿는 자리」)
- **FR7.3** 맞는 Catch가 없으면 지금 저장소 걸러 보기와 같은 꼴로 안내한다(예: 「작성자 설명을 쓴 Catch가 없습니다」). 추천·순위는 내지 않는다. (대략 화면 1절, 원칙 넷)
- **FR7.4** 목록 카드에는 설명 여부를 보이지 않는다(대략 화면 1절). 작성자 설명을 저장하거나 지운 뒤 걸러 본 목록은 다음에 불러올 때(걸러 보기를 바꾸거나 화면을 다시 열 때) 조건대로 바뀐다. 지금 쪽에서 바로 빼거나 넣지 않는다. (변경 요청)

수락 기준:
- **AC7.1** Given 설명을 쓴 Catch가 25번째에만 있는 지원자, When 「씀」을 고른다, Then 그 Catch가 첫 쪽에 보인다.
- **AC7.2** Given 「씀」 조건으로 받은 다음 쪽 커서, When 「안 씀」 조건으로 그 커서를 보낸다, Then 요청이 거부된다.
- **AC7.3** Given 작성자 설명을 쓴 Catch가 하나도 없는 지원자, When 「씀」을 고른다, Then 빈 목록 대신 「작성자 설명을 쓴 Catch가 없습니다」 안내가 보인다.
- **AC7.4** Given 「안 씀」으로 걸러 본 목록에서 Catch A의 작성자 설명을 저장, When 상세를 닫는다, Then A는 지금 쪽에 그대로 있고, 걸러 보기를 다시 고르거나 화면을 다시 열면 A가 빠진다.

#### FR8. 발행 화면 (할 일 (5)와 대략 화면에서 더한 것)

- **FR8.1** 「발행할 자료 고르기」의 기존 안내 아래에 「저장소마다 3~5개를 권합니다.」 한 줄을 더한다. 저장소별로 세거나 경고하지 않고, 추천·순위도 내지 않는다. (할 일 (5))
- **FR8.2** 「내 Catch」 항목마다 저장소 이름과, 작성자 설명이 없으면 「설명 안 씀」을 보인다. 저장소 이름을 얻는 길(저장소 목록을 함께 부르기 또는 목록 응답에 칸 더하기)은 기능 설계에서 정한다. (대략 화면 3절)
- **FR8.3** 「내 Catch」 위에 「작성자 설명을 쓴 Catch만 보기」 칸을 둔다. 처음에는 꺼져 있고, 켜거나 끄면 FR7.2와 같은 목록 요청 조건으로 첫 쪽부터 다시 불러온다. (대략 화면 3절)
- **FR8.4** 걸러 보기를 켜도 이미 고른 Catch와 순서는 그대로이고, 최대 개수에도 센다. (가정 확인, 코드 지식 「고른 자료는 고르기 목록과 따로 있다」)
- **FR8.5** 확인 단계에는 지금 비공개 Catch 안내와 같은 꼴로 「작성자 설명이 없는 Catch가 N개 있습니다. 면접관에게는 「작성자 설명이 없습니다.」로 보입니다」를 보인다. 수는 고른 자료로 센다. 발행을 막지 않고, 해당 Catch가 없으면 그리지 않는다. (대략 화면 3절)
- **FR8.6** 항목 표시(FR8.2·FR8.5)는 Catch 목록 자료의 「작성자 설명이 있는지」 칸을 쓰고, 걸러 보기(FR7·FR8.3)는 목록 요청 조건을 쓴다. 둘 다 FR7.2와 같은 기준이다. (대략 화면 3절)
- **FR8.7** 발행 화면은 열 때마다 목록을 새로 불러오므로 「설명 안 씀」이 그때까지 저장된 결과대로 보인다. (변경 요청)

수락 기준:
- **AC8.1** Given 설명 없는 Catch A를 골라 둔 상태, When 「작성자 설명을 쓴 Catch만 보기」를 켠다, Then 목록에서 A는 사라지지만 고른 항목과 순서에는 A가 남는다.
- **AC8.2** Given 설명 없는 Catch 2개를 고른 상태, When 확인 단계로 간다, Then 「작성자 설명이 없는 Catch가 2개 있습니다…」가 보이고 [발행]은 누를 수 있다.

### 2단계 — 면접관 화면 (할 일 (6)~(8))

#### FR9. 발행 사본의 세 칸 (할 일 (6))

- **FR9.1** 발행할 때 Catch 사본에 저장소 이름을 담고, 면접관 화면은 제목 아래 줄에 보인다. (할 일 (6), 입력 문서 §4-2)
- **FR9.2** 발행할 때 작성 시점(작성자 설명을 마지막으로 고친 달)을 담고, 「작성자 설명」 머리 옆에 「2026년 11월에 마지막으로 고침」처럼 보인다. 달은 한국 시간(KST)으로 정한다(지금 발행 화면의 `formatKst`와 같다). 작성자 설명이 없으면 작성 시점을 담지도 보이지도 않는다. (할 일 (6), 대략 화면 4절, 변경 요청)
- **FR9.3** 발행할 때 이 작업만의 조회 한계를 담는다. 담는 것은 두 가지뿐이다. (a) 같은 변경을 다시 냈거나 cherry-pick으로 옮긴 것일 수 있다는 경고, (b) 커밋 목록을 다 받지 못한 PR이 있다는 한계. 같은 문장은 한 번만 담는다. 근거마다의 조회 상태 문장(「병합 커밋이라 변경 내용을 조회하지 않았다」 등)은 담지 않는다. 지금 이 두 문장은 첫 근거의 `coverageLimits`에 다른 한계와 종류 표시 없이 섞여 있다(같은 작업 경고는 `registration_assessment`의 `groupingLimitations`에도 문장으로만 있다). 골라내는 방법(고정 문장 대조 또는 종류 칸 더하기)은 계약 설계·기능 설계에서 정한다. (대략 화면 Q5, 가정 확인)
- **FR9.4** 면접관 화면은 작업 전체 한계를 「기록에서 확인한 내용」 안 작업 사실 바로 아래에 펼친 채 「이 기록으로 알 수 없는 것」 목록으로 보인다. 해당하는 한계가 없으면 목록을 그리지 않는다. (대략 화면 Q5)
- **FR9.5** 세 칸(저장소 이름·작성 시점·작업 전체 한계)은 화면에만 보이고 받은 사람 AI 재료(검색 조각·요약 근거)에 넣지 않는다. (제약 3, 입력 문서 §8-1의 6)
- **FR9.6** 이 변경 전에 발행해 세 칸이 없는 사본은 세 칸을 그리지 않고 나머지는 지금 그대로 보인다. (대략 화면 4절)
- **FR9.7** 사본을 읽어 옮기는 모든 곳(받은 사람 web의 칸 고르기 포함)은 세 칸을 빠뜨리지 않고 옮긴다. 작성자 발행본 상세도 같은 표시를 쓴다. (코드 지식 「기술 부채」 사본 모양이 흩어짐)

수락 기준:
- **AC9.1** Given 작성자 설명을 2026년 11월에 고친 Catch, When 발행 뒤 면접관이 연다, Then 제목 아래 저장소 이름과 「작성자 설명」 옆 「2026년 11월에 마지막으로 고침」이 보인다.
- **AC9.2** Given 커밋 목록을 다 받지 못한 PR 한계가 근거 두 개에 같은 문장으로 있는 Catch, When 발행본을 연다, Then 「이 기록으로 알 수 없는 것」에 그 문장이 한 번만 보인다.
- **AC9.3** Given 이 변경 전에 만든 사본, When 면접관이 연다, Then 저장소 줄·작성 시점·한계 목록 없이 지금처럼 보이고 오류가 나지 않는다.
- **AC9.4** Given 세 칸이 있는 사본, When 받은 사람 AI가 요약 근거와 검색 조각을 만든다, Then 세 칸의 글자는 들어가지 않는다.
- **AC9.5** Given 작성자 설명을 2026-11-30T16:00Z(한국 시간 12월 1일 01:00)에 마지막으로 고친 Catch, When 발행 뒤 면접관이 연다, Then 「2026년 12월에 마지막으로 고침」이 보인다.

#### FR10. 「이 작업의 본인 커밋」 링크 표지 (할 일 (7))

- **FR10.1** 표지는 사본 근거 가운데 본인 커밋 근거와 맞을 때만 붙는다. 본인 커밋 근거는 기여 범위가 「연동 계정이 작성자로 기록된 커밋」(같은 변경으로 배정된 것 포함, `worker/app/candidates/build.py`의 `_OWN_COMMIT_SCOPES`)인 근거다. 병합 커밋 근거(「PR 없이 병합한 병합 커밋…」)·PR 근거·이슈 근거와 맞아도 붙이지 않는다. 지금 사본 근거는 `sourceUrl`·`sourceRevision`·`representedFacts`뿐이라 본인 여부가 없고, PR 근거의 판본은 PR 마지막 커밋 식별값(head_sha)이라 판본만 맞춰 보면 남의 커밋에도 표지가 붙을 수 있기 때문이다. (할 일 (7), 변경 요청)
- **FR10.2** 발행할 때 사본 근거에 본인 커밋 근거인지를 담는다(저장된 `catch_evidence.contribution_scope`에서 정할 수 있다). C-07의 칸 모양은 계약 설계에서 정한다. (변경 요청)
- **FR10.3** 비교 규칙: 링크의 저장소 이름이 사본 근거 저장소와 대소문자 무시로 같고, 링크의 식별값(7~40자 16진수, 대소문자 무시)이 본인 커밋 근거 식별값의 앞부분과 같을 때 맞는다. 둘 이상의 본인 커밋과 맞으면 붙이지 않는다. 줄 범위와 관계없이, 맞으면 그 판본·커밋 이름 바로 뒤에 「이 작업의 본인 커밋」 표지를 붙인다. 사본 근거는 본인 커밋 최근 20건까지라 그보다 오래된 커밋에는 붙지 않는다. (변경 요청, 대략 화면 「GitHub 링크 이름」)
- **FR10.4** 맞지 않으면 아무 표지도 붙이지 않는다. 'CatchU가 확인하지 않은 주소' 같은 부정 표지는 두지 않는다. (입력 문서 §4-3)
- **FR10.5** 파일 링크의 표지는 그 판본이 본인 커밋이라는 뜻이지 고른 줄을 본인이 썼다는 뜻이 아니다. 이 뜻은 표지를 판본·커밋 이름 바로 뒤에 두는 것으로 나타내고, 면접관 화면에 안내 문장을 더하지 않는다. 뜻은 기능 설계 문서와 README에 적는다. (변경 요청)
- **FR10.6** 표지는 FR3·FR5보다 늦게(2단계에) 넣는다. FR4의 짚어 볼 곳 링크가 먼저 있어야 한다. (할 일 목록 「항목 의존」)

수락 기준:
- **AC10.1** Given 사본에 본인 커밋 근거 `ba6bba8c…`(40자)가 있는 Catch와 작성자 글 속 짧은 식별값 링크 `…/blob/ba6bba8/a.ts#L3`, When 면접관이 연다, Then 「a.ts · L3 · 판본 ba6bba8」 바로 뒤에 표지가 붙는다.

- **AC10.3** Given 같은 식별값이지만 다른 저장소의 링크, When 면접관이 연다, Then 표지가 붙지 않는다.
- **AC10.4** Given 같은 작업의 병합 커밋 링크, 그리고 본인 커밋이 아닌 PR 마지막 커밋을 판본으로 쓴 파일 링크, When 면접관이 연다, Then 둘 다 표지가 붙지 않는다.

#### FR12. 기억 되살리기 사실과 「다시 볼 곳」 (할 일 (9))

- **FR12.1** 분석하는 동안 같은 작업 안의 본인 커밋끼리만 보고 네 가지 사실을 계산해 Catch에 남긴다. (a) 뒤 본인 커밋이 앞 본인 커밋이 넣은 줄을 다시 고친 곳, (b) 새 파일로 옮긴 곳, (c) 확장자 바꿈, (d) 되돌림 표시. 되돌림은 같은 작업 안의 본인 커밋을 가리키는 git revert 표시(「This reverts commit …」)가 커밋 메시지에 있을 때다. (할 일 (9), 가정 확인)
- **FR12.2** 지원자 Catch 상세의 근거 아래 「다시 볼 곳(본인만 확인)」 칸에 보인다. 면접관 화면과 발행 사본에는 보이지 않는다. 사실이 하나도 없거나 3단계 전에 만든 Catch면 칸을 그리지 않는다. (대략 화면 2절, 입력 문서 §3-1)
- **FR12.3** 항목의 커밋 식별값은 저장소 주소와 커밋 식별값으로 만든 github.com https 주소만 커밋 링크로 만들고, 새 탭에서 열며 「(새 탭)」을 붙인다. 지금 근거 링크는 바꾸지 않는다. (가정 확인)
- **FR12.4** (b) 옮긴 곳 판정에 필요한 파일 내용 식별값을 수집 중에 버리지 않고 판정에 쓴다. 분석 뒤 GitHub를 다시 읽지 않는다. (입력 문서 §5, 제약 5)

#### FR15. 3단계 공통

- **FR15.1** 3단계 결과는 결과 메시지 계약 판본을 올리고 api와 worker를 함께 배포한다. (제약 4, 입력 문서 §6-3)
- **FR15.2** FR12·FR13의 결과 문장을 Catch에 남기므로 분석 고지 v3 4절에 한 줄을 더하고, 그 문구를 바꾸는 PR에서 팀장이 승인한다. (제약 7, 성공 기준 「고지 승인」)
- **FR15.3** 3단계 변경은 출시 직전 DB 초기화 전에 통합 브랜치(이미 dev로 합쳐졌으면 dev)에 들어가야 한다. 초기화는 3단계와 Catch 개편 CR2가 통합 브랜치에 들어간 뒤에 하므로, 이 기준은 날짜와 무관하게 판정한다. 「Catch 재생성」은 열지 않는다. (의도 설명, 성공 기준 「3단계 반영 시점」)

## 비기능 요구사항

- **NFR1 호출과 수집.** 1~3단계는 GitHub 호출도 AI 호출도 늘리지 않는다. 새로 모으는 자료가 없고, 새 사실은 분석하는 동안 계산해 결과만 남기며 분석 뒤 GitHub를 다시 읽지 않는다. 판정: 같은 저장소를 바꾸기 전·후로 분석해 GitHub 호출 수와 AI 호출 수가 늘지 않는다. (제약 1·5·6, 입력 문서 §5)
- **NFR2 출처 구분.** 면접관에게 가는 글은 누가 썼는지 구분한다. 받은 사람 AI 근거 딱지는 'GitHub 기록 원문'과 '작성자 자료 원문' 둘 그대로다. 규칙이 만든 종류 줄과 본인 기여 문장도 'GitHub 기록 원문'으로 남는 것은 한계로 둔다. 세 칸(FR9)과 링크 이름·표지(FR3·FR10)는 AI 재료에 들어가지 않는다. 판정: 사본 하나로 만든 검색 조각과 요약 근거에 세 칸·표지 글자가 0건이다. (입력 문서 §8-1의 8, 제약 3)
- **NFR3 질의응답 재측정.** 시연 발행본 1개에 질문 10개와 정답 근거를 만들어 스크립트로 한 번 재고, 사람이 근거가 문장을 뒷받침하는지 함께 본다. 남의 기여를 본인 것으로 쓴 항목 0건을 유지하는 것이 합격 기준이다. 작성자 주장을 사실처럼 옮긴 항목 수는 기록만 하고 합격 기준으로 쓰지 않는다. (성공 기준 「질의응답 재측정」, 의도 설명 「판정 방법」)
- **NFR4 규칙 사실 대조.** FR15.4와 같은 시연 저장소에서 규칙이 만든 줄 30~50개를 사람이 원문과 맞춘 결과를 기록한다. 남의 일을 본인 것으로 붙인 줄 0개, 그 밖에 틀린 줄 2개 이하가 합격 기준이다. (성공 기준 「규칙 사실 대조」)
- **NFR5 화면 출력 안전.** 작성자 글과 링크 이름은 React 텍스트로만 그린다. 작성자가 글로 「[이 작업의 본인 커밋]」을 적어도 진짜 표지와 구별되는 모양이어야 하고, 이름에서 푼 글자의 제어 문자는 지운다. 모양과 처리 방식은 기능 설계에서 정한다(보안 점검 「화면 출력」). 판정: 표지 흉내 글과 제어 문자가 든 경로로 만든 시험에서 진짜 표지와 화면이 다르고 제어 문자가 보이지 않는다. (대략 화면 「GitHub 링크 이름」)
- **NFR6 접근성.** 기존 화면 기준을 따른다. 칸 제목 8개는 각 글칸의 보이는 `label`이다. 「발행하면 면접관에게 열릴 링크」는 h4 제목으로 찾을 수 있다. 숨긴 빈 칸은 화면 낭독기에도 나오지 않는다. 표지는 색만이 아니라 글자로 읽힌다. 새 탭 링크에는 「(새 탭)」이 붙는다. 새 선택 칸·체크 칸은 보이는 `label`이 있고 걸러 본 개수는 `aria-live="polite"`로 알린다. (대략 화면 Q6, 2절·3절·4절)
- **NFR7 호환.** 옛 사본(세 칸 없음), 옛 작성자 글(칸 제목 없음), 작업 시각 없는 Catch가 오류 없이 지금처럼 보인다. 판정: 각 경우의 시험이 통과한다(AC1.4, AC2.2, AC9.3, AC14.1). (대략 화면 1·2·4절)
- **NFR8 시험.** 팀 시험 방식을 따른다. 주요 업무 시나리오·기대 결과·실패 조건(이 문서의 수락 기준)을 먼저 정하고 세부 시험 코드는 구현 뒤 작성·실행한다. 기존 시험은 계속 통과한다. 커버리지 측정은 팀장이 공용 기반으로 넣은 서비스별 명령을 쓴다. (팀 규칙 「Testing Posture」)

## 가정

- **A1** 작업 전체 한계는 FR9.3의 두 가지뿐이다. 그 밖의 한계는 근거마다의 조회 상태라 면접관 화면에 넣지 않는다. (가정 확인)
- **A2** 「되돌림」은 같은 작업 안의 본인 커밋을 가리키는 git revert 표시가 커밋 메시지에 있을 때다. 메시지 없이 손으로 되돌린 것은 FR12 (a)의 다시 고친 곳으로만 잡힌다. (가정 확인)
- **A3** 작업 시각은 본인 커밋의 작성 시각(authored)이다. 커밋 시각(committed)은 리베이스로 바뀌기 쉽기 때문이다. (가정 확인)
- **A4** 「다시 볼 곳」의 커밋 링크는 github.com https 주소만 만든다. 지금 지원자 상세의 근거 링크(`safeEvidenceUrl`, http·https의 아무 호스트)는 이 intent에서 바꾸지 않는다. (가정 확인, 코드 지식)
- **A5** 발행 화면의 고른 항목은 고르기 목록과 따로 있어 걸러 보기가 바꾸지 않는다(지금 코드 동작). (가정 확인)
- **A6** 링크 이름(FR3)은 작성자 설명에만 쓴다. 같은 표시 함수를 쓰는 텍스트 자료 본문의 링크는 지금처럼 주소 전체다. 할 일 목록과 대략 화면이 작성자 설명만 말했기 때문이다. 기능 설계에서 함께 바꾸자는 판단이 나오면 질문으로 올린다. [assumption]
- **A7** 「작성 시점」은 발행 시점의 작성자 설명 마지막 고친 시각에서 달만 담는다. 발행 뒤 작성자 설명을 고쳐도 사본은 바뀌지 않는다(발행본은 고정 사본). (코드 지식 `business-overview.md` 「발행본은 고정 사본이다」) [assumption]

## 한계

- 면접관이 새로 얻는 글은 '나중에 쓴 자기 진술'이다. 증거처럼 보이게 하지 않고 시험할 자리와 원본을 붙인다. 지원자 답도 AI로 쓸 수 있고, 막지 않는다. (입력 문서 §8-3)
- 'AI가 낸 것 가운데 받아들이지 않았거나 고친 것'을 정직하게 쓴 사람이 더 많이 물릴 수 있다. 이 칸은 다른 칸과 같은 고정 칸(건너뛸 수 있음)이다. (입력 문서 §8-3)
- 짚어 볼 곳 링크를 붙이지 않은 Catch에는 짚어 볼 곳이 없다. 발행 뒤 저장소가 비공개로 바뀌거나 지워지거나 강제 푸시로 커밋이 사라지면 링크가 열리지 않는다. (입력 문서 §8-3)
- 지원자가 글 안에 칸 제목 줄과 같은 줄을 쓰면 그 줄부터 다른 칸으로 읽힌다(FR1.6). 칸 제목 문구를 바꾸면 옛 글에는 옛 문구가 남는다(FR1.8).
- 다른 곳(GitLab 등)에서 옮긴 저장소의 'PR 없이 합친 병합'은 제목이 작업 일부만 말할 수 있다. 에이전트가 자기 계정으로 커밋한 일, 남의 PR을 리뷰한 일은 Catch가 되지 않는다. (입력 문서 §8-3)
- DB 초기화 때 작성자 글도 사라진다. (입력 문서 §8-3)
- 규칙 버림 기준(FR15.4)을 시연 저장소 하나로 재므로, 표본이 작으면 되돌림처럼 드문 사실은 5% 미만으로 버려질 수 있다. (변경 요청)
- 면접관 쪽 근거는 인터뷰 한 번이고, 새 모양을 면접관에게 먼저 보이지 않고 만든다. (입력 문서 §8-3)
