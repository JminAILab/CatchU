## Q1. [설계] 작성자 설명 칸 나누기·합치기와 GitHub 링크 이름·표지는 어디에 둘까요?

**배경:** 칸 나누기는 세 곳이 함께 쓴다. 지원자 편집 화면(저장된 글 → 8칸, 8칸 → 저장할 글, 합계 글자 수), 발행하면 열릴 링크 목록, 면접관 발행본 보기다. 링크 이름은 지원자 링크 목록과 면접관 발행본(받은 사람 화면, 작성자 발행본 상세)이 함께 쓴다. 이름이 두 화면에서 달라지면 안 된다(FR5.1). 지금 링크 찾기는 `web/src/lib/github-source-url.ts`에 있고, 받은 사람 화면은 `recipient-format.ts`로 다시 내보낸다. api는 글을 칸으로 나누지 않는다(상한은 글 전체로 센다, FR1.3).

A. web 공통 자리(`web/src/lib`)에 새 구성 요소 둘을 둔다. 하나는 칸 나누기·합치기·글자 수, 하나는 링크 이름과 표지 판정이다(`github-source-url.ts` 곁). 세 화면이 이 둘을 함께 쓴다. (가장 단순)
B. 하나로 합친다(작성자 설명 글 다루기). 파일이 하나 줄지만, 링크 이름은 칸과 상관없이 바뀌는 규칙이라 두 바뀜이 한곳에 섞인다.
C. 화면마다 따로 둔다. 화면 사이에 이름과 칸 해석이 어긋날 수 있다.

## Q2. [설계] 3단계 규칙 사실은 worker 어디에 둘까요?

**배경:** 규칙 사실은 다섯이다. 다시 고친 곳, 새 파일로 옮긴 곳, 확장자 바꿈, 되돌림, 시험 파일 「있음」이다(FR12·FR13). 모두 같은 작업 안의 본인 커밋끼리 보고, 좁은 산출물 목록으로 거른다. GitHub를 다시 부르지 않는 계산이다(FR12.4, NFR1). 규칙은 하나씩 버릴 수 있어야 한다(FR15.4). 지금 후보 판정(`worker.candidates`, `grouping.py` 1,880줄)은 작업 단위·작업 사실·근거를 만들고, 재료 분류(`worker.generation` `title.classify`)는 그대로 둔다(FR13.1).

A. worker에 새 구성 요소 하나를 둔다(다시 볼 곳 사실). 규칙마다 따로 나누고, 처리(`worker.processing`)가 후보마다 부른다. 후보 판정과 재료 분류는 고치지 않는다. 파일 내용 식별값을 남기는 것만 수집(`worker.collection`)에서 고친다. (가장 단순)
B. 후보 판정 안에 넣는다. 구성 요소는 늘지 않는다. 대신 후보 판정의 경계(작업 단위·작업 사실·근거)가 바뀌고, 큰 파일 옆에 규칙이 붙어 규칙 하나를 버리기가 더 어렵다.

## Q3. [설계] 작업 시각(첫·마지막 본인 커밋의 작성 시각)은 어디서 계산할까요?

A. 후보 판정이 후보를 만들 때 본인 커밋 목록과 함께 두 시각을 싣는다. 시각은 작업 단위의 성질이라 단위를 정하는 곳에 둔다. 새 판정 규칙이 아니라 FR15.4의 버림 대상도 아니다. (가장 단순)

## Q4. [설계] Catch에 새로 남는 사실은 어떻게 저장할까요?

**배경:** 새로 남는 것은 둘이다. 다시 볼 곳 사실 목록(지원자만 보고 사본에는 넣지 않음, FR12.2)과 첫·마지막 작업 시각이다. 지금 `catch_asset`은 작업 사실을 글 배열(`work_facts`)로, 등록 판정을 jsonb(`registration_assessment`)로 칸에 담는다. 근거는 따로 표(`catch_evidence`)가 있다. 3단계 뒤 DB를 초기화하므로 옛 Catch에 값을 채우는 길은 없다(FR15.3). 탈퇴는 회원 연쇄 삭제로 Catch를 지운다.

A. `catch_asset`에 칸 셋을 더한다. 다시 볼 곳 사실 jsonb 하나(목록)와 첫·마지막 작업 시각 둘이다. 소유는 지금처럼 Catch 등록(`api.catches`)이다. 지원자 Catch 응답만 이 칸을 읽고, 사본 만들기는 읽지 않는다. 옛 Catch는 빈 값이다. (가장 단순)
B. 다시 볼 곳 사실은 새 표(사실 하나가 한 행)로 두고, 시각 둘은 `catch_asset` 칸으로 둔다. 사실을 행 단위로 고르고 셀 수 있다. 대신 표 하나, 외래 키, 연쇄 삭제가 더 생기고 탈퇴 시험 범위가 늘어난다. 요구사항에는 사실을 따로 고르거나 세는 일이 없다.
