## 용어

이 문서에서 「면접관」은 두 사람을 나눠 부른다(Q3).

| 말 | 뜻 |
|---|---|
| 저장소를 여는 면접관 | 팀원의 포트폴리오로 이 저장소를 여는 사람. 첫 화면의 첫 독자 |
| Catch를 받는 면접관 | 지원자가 보낸 Catch를 받아 보는 사람. 제품 용어 |
| 분석해 보는 사람 | CatchU로 이 저장소를 분석해 보는 사람. 첫 화면의 그다음 독자 |
| 첫 화면 문서 | 루트 `README.md`와 `docs/README.md` |
| 팀장 | 이 intent를 정하는 우리 팀장 |

첫 화면 문서 본문에서 「면접관」은 제품 용어(Catch를 받는 면접관)로만 쓴다(Q3).

## 대조 기준: Catch 정의

FR1.1과 NFR3은 아래 문장과 대조한다(수정 요청 5). 출처는 새 Catch 요구사항 `aidlc/spaces/default/intents/261109-new-catch/inception/requirements-analysis/requirements.md` 「Catch 정의」다.

> Catch는 지원자가 분석된 작업 가운데 골라 면접관에게 보내는 한 장이다. 그 작업에서 내린 판단을 지원자가 자기 말로 적고, 면접관이 그 말을 시험해 볼 코드 자리와 GitHub 원본이 함께 붙는다. Catch는 판단을 증명하지 않는다. 판단은 면접에서 확인한다.

## 의도 분석

- 저장소를 처음 여는 글이 9~10월 설명(증거카드·양면 플랫폼)과 8~9월 설계 문서로 이어져, 저장소를 여는 면접관이 지금 CatchU를 알 수 없다. 지금 제품을 한 번에 설명하는 글도 없다(의도 설명 「풀려는 문제」).
- 목표는 저장소를 여는 면접관이 루트 `README.md`에서 지금 CatchU가 무엇을 하는지, 내 컴퓨터에서 띄우는 법, 그리고 팀원이 무엇을 만들었는지를 바로 찾는 것이다(의도 설명 「성공 기준」, Q2).
- 문서를 고치는 일이고, 제품 코드·CI·AI-DLC 하네스·승인 기록은 바꾸지 않는다(의도 설명 「Initial Scope Signal」).

## 기능 요구사항

### FR1. 루트 `README.md`

- **FR1.1 첫 문장**: 제품 소개 첫 문장이 새 Catch 요구사항 「Catch 정의」와 맞는다. 증거카드·양면 플랫폼이라는 소개가 없다.
  - Given 루트 `README.md`를 열면, When 제목 아래 첫 문단을 읽으면, Then 위 「대조 기준: Catch 정의」와 어긋나지 않는다. 지원자가 고른 작업, 지원자가 자기 말로 적는 판단, 코드 자리와 GitHub 원본, 판단은 면접에서 확인한다는 점이 빠지거나 반대로 적히지 않는다.
  - Given 루트 `README.md` 전체에서, When 「증거카드」·「양면 플랫폼」을 찾으면, Then 제품 소개로 쓴 곳이 없다.
- **FR1.2 '지금 CatchU' 절**: 루트 `README.md` 안에 지금 CatchU를 한 번에 설명하는 절이 하나 있다(Q1).
  - 사용자가 하는 일 여섯 묶음을 기본으로 적는다(Q4). `dev`에 병합된 사용자 기능은 아래처럼 한 묶음에 넣어 빠지지 않게 한다(수정 요청 7). 이 표는 2026-11-15 `dev`의 `web/src/features/`·`api/src/` 폴더로 만들었다.

    | 묶음 | 넣는 사용자 기능 |
    |---|---|
    | 가입과 GitHub 연결 | 첫 소개 화면, Google 로그인과 가입 진입, 홈과 시작 안내, 프로필, GitHub 계정 연결, 탈퇴 |
    | 저장소 등록과 분석 | 저장소 등록, 분석 고지와 동의, 분석 요청, 하루 실행 횟수 |
    | Catch 확인과 작성자 설명 | 내 Catch 목록·상세, 작업 사실·나의 기여 확인, 작성자 설명 |
    | 발행 | 텍스트·PDF 자료 올리기, Catch와 자료를 골라 발행본 만들기, 링크 중지·삭제 |
    | Catch를 받는 면접관 화면 | 발행본 링크 화면, AI 기본 요약·질의응답, JD 관리·요약(면접관이 JD를 등록하고 받은 링크에서 JD 기준 요약을 받음), 받은 링크를 Claude로 분석하기(Claude 연결 묶음의 연결을 씀) |
    | Claude 연결 | 회원 본인의 Claude에 CatchU 도구 연결. 지원자는 자기 Catch·자료를 읽고, 면접관은 받은 링크를 분석하는 데 쓴다 |

  - Given 2026-11-15 `dev`의 `web/src/features/` 폴더 목록을, When 화면이 아닌 폴더(공용 로그인 세션, 개인정보처리방침 같은 안내 페이지)를 빼고 위 표와 대조하면, Then 표에 없는 사용자 기능이 없다.
  - 묶음마다 「`dev`에 병합됨」과 「개발 서버에서 확인됨」을 나눠 표시한다. 근거는 `docs/CatchU_통합확인.md`와 `docs/verification/`의 기록만 쓴다(Q4, 수정 요청 4). 개발 서버 확인 칸은 세 값 가운데 하나로 적는다(수정 요청 8).
    - 「개발 서버에서 확인됨」: `docs/CatchU_통합확인.md`에서 결과가 통과인 범위만, 확인한 날짜와 그 기록 링크를 함께 적는다.
    - 「미실행(사유)」: 결과가 미실행인 것. 괄호 안에 기록에 적힌 사유를 쓴다.
    - 「기록 없음」: 확인 기록이 없는 것.
  - 승인 원본은 고치지 않는다. 무엇이 무엇을 대체했는지(10월 → 12월 재승인 → Catch 개편 → 새 Catch)와 원본 위치만 적는다(입력 문서 §4-1).
  - 절 머리에 이 요약의 기준 날짜만 적는다. `dev` 커밋은 적지 않는다(수정 요청 4).
  - 절 머리에 "개발 서버 확인은 2026-11-09 판 기준이고, 그 뒤 병합된 것은 확인 기록이 없다"는 한 줄을 둔다(수정 요청 8).
  - Given 저장소를 여는 면접관이, When '지금 CatchU' 절을 읽으면, Then 각 묶음이 병합만 됐는지 개발 서버에서도 확인됐는지 구분할 수 있다.
- **FR1.3 내 컴퓨터에서 띄우는 법**: 루트 `README.md`에서 한 번의 링크로 `docs/CatchU_로컬통합실행.md`에 닿는다.
  - Given 루트 `README.md`에서, When 띄우는 법을 찾으면, Then 이 문서로 가는 링크가 이름으로 알아볼 수 있게 있다.
- **FR1.4 구조 표**: 구조 표에서 아래 세 항만 본다(수정 요청 3). 다른 최상위 폴더가 표에 있는지는 이번 기준이 아니다.
  - AI-DLC 입력 폴더 5개(`docs/ai-dlc-input/`, `docs/ai-dlc-input-mvp/`, `docs/ai-dlc-input-december/`, `docs/ai-dlc-input-catch/`, `docs/ai-dlc-input-reorg/`)와 `.claude/`가 표에 있다(입력 문서 §2-1·§4-1).
  - worker 설명이 지금 하는 일(수집과 Catch 초안 만들기)과 맞고, 「카드 추출」이라고 적지 않는다(입력 문서 §2-1).
  - AI-DLC 산출물을 「현재는 요구사항 문서」라고 적지 않는다(입력 문서 §2-1).
- **FR1.5 팀원별 맡은 부분**: 팀원마다 GitHub 계정과 맡은 영역을 한 표로 적는다. 실명은 적지 않는다(Q2, Q10).
  - 표 내용은 팀장이 PR 전에 확인한다(Q10).
  - Given 저장소를 여는 면접관이, When 팀원 표를 보면, Then 팀원의 GitHub 계정마다 맡은 영역을 알 수 있다.
- **FR1.6 기술 구성과 배포 환경**: Next.js·NestJS·FastAPI 구성과 배포 환경(AWS, 지금은 개발 서버)을 한두 줄로 적는다(Q2). 12월 최종 환경(EKS)은 「예정」으로 적고 배포된 것처럼 적지 않는다.
- **FR1.7 AI-DLC로 만든 방식**: 이 저장소를 AI-DLC로 만든 방식을 한두 줄로 적고, 기록 위치 `aidlc/`로 링크한다(Q2).
- **FR1.8 팀 줄**: 맨 아래 팀 줄을 "재민아이(JAEMIN_AI) · 인공지능사관학교 파이널 프로젝트 (2026-08 ~ 12)"로 쓴다. 「기업연계」를 뺀다(Q5).
- **FR1.9 문서 안내로 가는 길**: 루트 `README.md`에서 `docs/README.md`로 가는 링크를 둔다(입력 문서 §4-1).

### FR2. `docs/README.md`

- **FR2.1 문서 목록**: `docs/` 바로 아래의 문서와 폴더가 모두 문서 목록 표에 있다(의도 설명 「성공 기준」). 지금 빠진 것은 `ai-dlc-input/`, `ai-dlc-input-mvp/`, `ai-dlc-input-december/`, `ai-dlc-input-catch/`, `ai-dlc-input-reorg/`, `verification/`이다(2026-11-15 대조). `docs/README.md` 자신은 목록에 넣지 않는다.
  - Given `docs/` 바로 아래 항목 목록과 문서 목록 표를, When 하나씩 대조하면, Then 빠진 항목이 없다.
  - 입력 폴더의 지위 칸에는 입력 스냅샷이며 지금 기준이 아니라는 것을 적는다(AGENTS.md 「저장소 지도」와 같은 뜻).
- **FR2.2 처음 읽는다면**: 순서를 루트 `README.md`의 '지금 CatchU' → 새 Catch 요구사항 「Catch 정의」 → `docs/CatchU_로컬통합실행.md`로 바꾼다. 카드생성논리·페르소나는 이 순서에서 뺀다(Q6).
- **FR2.3 9/11 정리 대상 문서의 지위**: `카드생성논리_상세설명.md`, `증거카드_이상형과_추출방법.md`, `CatchU_KPI_성공기준_v4_1.md`, 페르소나 P1~P4, 설계 노트 P1~P4의 지위 칸을 「기록 · 8~9월 설계 당시, 지금 기준 아님」으로 바꾼다. 문서 본문은 고치지 않고, 지우지 않는다(Q7, 의도 설명 「Initial Scope Signal」).
- **FR2.4 AI-DLC 산출물과의 관계**: 이 절에 Catch 개편 intent(`261103-catch-redesign`)와 새 Catch intent(`261109-new-catch`)의 승인 요구사항 줄이 있다(의도 설명 「성공 기준」).
- **FR2.5 제품 소개**: `docs/README.md`가 제품을 증거카드·양면 플랫폼으로 소개하지 않는다(의도 설명 「성공 기준」). 문서 이름에 들어간 낱말(예: `증거카드_이상형과_추출방법.md`)과 9/11 정리 대상 문서의 설명 칸에 있는 「증거카드」는 그 문서가 다루는 내용이라 제품 소개가 아니다. 그 설명 칸은 그대로 둔다(수정 요청 2).
- **FR2.6 정리 기록**: 「정리 기록」 절 끝에 이번 변경 한 줄을 더한다. 옛 항목은 고치지 않는다(`docs/README.md` 「규칙」, 입력 문서 §4-3).

## 비기능 요구사항

- **NFR1 링크**: 고친 문서의 저장소 안 링크가 모두 열린다(의도 설명 「성공 기준」). 상대 경로와 절 이름 링크(한글 앵커 포함)를 모두 연다.
- **NFR2 문서 크기 검사**: `bash .github/scripts/check-doc-sizes.sh`가 통과한다. 대상 목록은 바꾸지 않는다(Q9).
- **NFR3 면접관 역할 AI 세션 확인**: 저장소를 처음 보는 새 AI 세션 1개에 저장소를 여는 면접관 역할을 주고, 루트 `README.md`에서 시작해 검색하지 않고 링크만 따라가서 (1) 지금 CatchU가 무엇을 하는지 (2) 내 컴퓨터에서 띄우는 법을 찾게 한다(의도 설명 「성공 기준」).
  - 통과 조건: 세션이 말한 한 줄 설명이 위 「대조 기준: Catch 정의」와 어긋나지 않고, 띄우는 법 답이 `docs/CatchU_로컬통합실행.md`의 「켜는 순서」 절을 가리킨다. 「준비물」을 먼저 말해도 된다(수정 요청 1, 수정 요청 9).
  - 증거: 세션이 지나간 링크 목록(검색 없음)을 PR에 붙인다(수정 요청 1).
  - 실패하면 문서를 고쳐 새 세션 1개로 다시 확인한다. 통과한 세션의 경로를 PR에 남긴다(Q8).
- **NFR4 같은 사실은 같은 값**: 루트 `README.md`와 `docs/README.md`가 같은 문서·폴더를 가리킬 때 지위와 설명이 서로 어긋나지 않는다.

## 제약

- 승인 기록·감사 기록, `docs/ai-dlc-input/` 스냅샷, AI-DLC 하네스(`.claude/`, `.codex/`, `.agents/`), `AGENTS.md`의 AI-DLC 관리 블록, 코드 지식 파일, 코드와 CI 설정은 고치지 않는다(의도 설명 「Initial Scope Signal」).
- 문서 수정은 이슈 → `docs/` 브랜치 → `dev` PR로 한다. 이 intent 기록과 첫 화면 문서를 PR 하나에 담는다(#552, 입력 문서 §6).
- 커밋·PR·문서에 AI 도구 표기를 넣지 않는다(팀 지침).
- 비밀값·인증정보·사용자 자료를 문서에 남기지 않는다(`team.md` 「Code Style」). 팀원 표에 실명을 적지 않는다(Q10).
- #552 본문의 완료 기준을 이 요구사항에 맞춰 고친다. 게시는 이 요구사항이 승인된 뒤에 한다(수정 요청 6).

## 가정

- '지금 CatchU'를 쓰려고 개발 서버를 새로 확인하지 않는다. 근거는 FR1.2의 두 기록뿐이다.
