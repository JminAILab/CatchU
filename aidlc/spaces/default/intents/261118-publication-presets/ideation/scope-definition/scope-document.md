근거: 승인된 의도 진술 `ideation/intent-capture/intent-statement.md`(intent-statement), 타당성 평가 `ideation/feasibility/feasibility-assessment.md`(feasibility-assessment), 제약 목록 `ideation/feasibility/constraint-register.md`(constraint-register), 이 단계 질문 `scope-definition-questions.md`의 답(Q1~Q4), 입력 문서 `docs/ai-dlc-input-preset/CatchU_발행_프리셋_입력.md` §3(팀장 결정).

## 최소 범위

범위 안 기능 9묶음은 모두 Must다(Q1). 하나라도 빠지면 의도 진술의 성공 기준(프리셋으로 발행, 두 화면의 탭, 출처의 탭 이동, 요약·자료 배치)을 채우지 못하거나, 개인정보처리방침·탈퇴 제약(constraint-register C-R2·C-R3)을 어긴다.

## 순서와 반영 방식

- 만드는 순서는 의존 순서다(Q2): 발행 요청·사본 계약과 프리셋 저장 → 프리셋 화면 → 프리셋으로 발행 → 두 화면의 탭과 출처 이동 → 받은 링크 읽기·JD 요약 맞춤.
- 기존 발행본 버리기(S8)는 발행 요청·사본 계약과 프리셋 저장과 함께 한다. 기존 발행본 행이 남아 있으면 사본에 프리셋 구분을 더하는 DB 변경이 프리셋 없는 행까지 받아 줘야 해서, 버리기로 한 이점이 사라진다.
- 계약 변경(발행 요청·사본)을 먼저 PR로 올려 담당 리뷰를 받고, 나머지는 이어서 올린다. 모두 2026-11-30까지 dev에 들어간다(Q3, constraint-register C-O1·C-O3).
- 팀원 3의 지금 화면 정리를 기다리지 않는다. 받은 사람 화면을 시작할 때 팀원 3의 정리가 dev에 들어와 있으면 그 위에서 시작하고, 없으면 그대로 진행한다. dev에 먼저 들어간 쪽이 기준이 되고 뒤에 들어오는 쪽이 거기에 맞춘다(Q4, feasibility-assessment 위험 표).

## 일정 검증

11월 안 dev 반영은 빠듯하다(feasibility-assessment). 범위를 줄이지 않기로 했으므로(Q1) 일정 위험은 계약 변경 PR을 먼저 올려 리뷰 대기를 앞당기는 것(Q3)과 팀원 3을 기다리지 않는 것(Q4)으로 줄인다.

## Assumptions & Open Questions

- 기존 발행본을 지울지 열리지 않게 둘지: 요구사항 단계(S8).
- 프리셋 6개째·0개일 때의 세부: 요구사항 단계(S2).
- 받은 링크 읽기에 프리셋 구분을 실을지: 요구사항 단계(S9).
- AI 요약 근거·질의응답 머리글·검색 조각에 프리셋 구분을 알릴지: 설계 단계, 가장 단순한 안은 알리지 않는 것(feasibility-assessment).
- 프리셋 이름을 외부 AI에 보낼지: 설계 단계(constraint-register C-R4).
