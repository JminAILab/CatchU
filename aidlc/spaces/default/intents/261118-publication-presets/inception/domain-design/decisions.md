# Decisions — 발행 프리셋

모든 결정의 상태는 「Accepted」(2026-11-19, 이 단계 답)다. 보안·개인정보 영향은 결정마다 「Consequences」에 적었다.

ADR-009는 2026-11-19 승인 검토에서 팀장이 더한 결정이다.

## ADR-001: 프리셋은 새 모듈이 맡고, 발행 자격·글자 수 규칙은 떼어 함께 쓴다

- **Context** — 프리셋 목록은 항목 수·글자 수·발행할 수 없는 자료를 보이고(FR1.2, FR1.11, FR1.14), 저장할 때 같은 상한을 지킨다(FR1.7). 이 판정과 글자 세기는 지금 발행 모듈(`publish.service.ts`, `snapshot-builder.ts`) 안에 있다. 발행은 고른 프리셋을 읽어야 하므로(ADR-002), 프리셋이 발행 판정을 부르면 서로 부르는 고리가 생긴다.
- **Decision** — 새 api 모듈 `presets`(PresetLibrary)가 프리셋 표 둘을 가진다. 「발행할 수 있는가」(공개·확인·보호·추출·소유)와 「사본 내용과 글자 수」 규칙을 발행 모듈에서 떼어 PublishableSource로 두고, 프리셋과 발행이 함께 쓴다. 의존은 발행 → 프리셋, 발행·프리셋 → 규칙이다. 잠금 순서(Catch → 텍스트 자료 → PDF)는 발행 쪽에 남는다(Q1).
- **Consequences** — 프리셋 화면과 발행이 같은 규칙으로 같은 결과를 낸다. 발행 모듈이 커지지 않는다. 대신 규칙 함수와 사본 내용 만들기를 옮기고 모듈 연결을 더하는 공수가 들며, 옮길 때 지금 발행 시험이 그대로 통과해야 한다. 보안: 소유 확인(NFR2)이 규칙 한 곳에 모여 프리셋 저장과 발행이 같은 검사를 쓴다.
- **Alternatives Rejected** — 프리셋을 발행 모듈 안에 두기(가장 적게 고치지만 발행 모듈이 커지고 프리셋이 발행 내부 변경에 휘말림). 새 프리셋 모듈이 발행 함수를 가져다 쓰고 발행은 프리셋 표를 SQL로 읽기(옮기는 코드는 적지만 두 모듈이 서로의 내부에 기댐).

## ADR-002: 발행 요청은 프리셋 ID 목록이고 서버가 펼친다

- **Context** — 서버는 발행할 때 고른 프리셋과 자료를 다시 확인하고, 막히면 어느 프리셋의 어느 자료 때문인지 알려야 한다(FR2.8). 프리셋은 요청한 지원자의 것만 받는다(NFR2). 사본에는 발행 당시 프리셋 이름을 복사한다(FR2.11). 지금 요청은 `items`만 받고 그 밖의 칸은 400이며, 거부 응답은 Catch ID와 요청 배열 위치만 준다.
- **Decision** — 요청은 `{ title, password?, presetIds }`(1~5개, 고른 순서)다. 서버가 발행 트랜잭션 안에서 PresetLibrary로 프리셋을 읽어 자료 목록으로 펴고(프리셋 순서, 그 안에서 프리셋 안 자료 순서), 이름을 사본에 복사한다. 막히면 응답에 프리셋 ID와 자료를 싣고, 오류 응답 필터가 details에서 옮기는 칸을 하나 더한다(Q2).
- **Consequences** — 화면이 본 프리셋과 서버가 발행한 내용이 어긋나지 않고, 다른 회원의 프리셋 ID는 서버가 거부한다. 발행 요청·사본 계약이 바뀌므로 먼저 PR로 올려 팀원 3, 받은 링크 읽기 담당, JD 요약 담당의 리뷰를 받는다(requirements Constraints). 이 PR의 리뷰 대상에는 요청 모양과 함께 사본 읽기 계약(C-07·C-10)의 변경, 곧 프리셋 구분 칸 둘(ADR-003)과 항목마다의 「앞선 사본인가」 값(ADR-006)이 든다. 한 발행본에 같은 원본을 한 번만 받던 검사는 「한 프리셋 안에서 한 번」으로 바뀐다(FR2.7). 잠그는 원본 ID는 중복을 없앤 집합이고, 사본과 PDF 사본 파일은 프리셋마다(항목마다) 따로 만들며, 전체 글자 수는 사본마다 더한다. 보안: 소유 확인이 서버에서 일어난다. 오류 응답에 싣는 것은 프리셋 ID와 자료 식별자뿐이고 이름·내용은 싣지 않는다(NFR4).
- **Alternatives Rejected** — web이 프리셋을 펴서 항목 목록과 묶음을 보내기(서버가 프리셋의 주인과 지금 내용을 확인하지 못해 FR2.8·NFR2와 맞지 않음).

## ADR-003: 사본의 프리셋 구분은 발행본 항목 표의 칸 둘로 저장한다

- **Context** — 받은 사람 화면과 작성자 상세가 탭을 그리려면 사본에 프리셋 순번과 발행 당시 이름이 있어야 한다(FR2.11, FR3.2). 항목 순서 번호 하나가 순서·조각·질의응답 표 글자·받은 링크 cursor를 모두 맡고, 발행본 전체에 이어 매기면 그대로 통한다(FR6.1).
- **Decision** — `published_item`에 프리셋 순번(1~5)과 발행 당시 프리셋 이름 칸을 더한다. 순서 번호는 발행본 전체에 이어 매긴다. 항목이 0개인 프리셋은 고를 수 없으므로(FR2.4) 항목만으로 탭을 만들 수 있다(Q3).
- **Consequences** — 새 표 없이 마이그레이션 하나로 끝나고, 사본 읽기는 지금처럼 항목 표 하나를 읽는다. 이름이 항목마다 되풀이되고, 같은 순번의 항목이 같은 이름을 갖는지는 발행 코드가 지키며 발행 시험으로 확인한다. 사본 모양(C-07)과 web 응답 검사 두 곳이 함께 바뀐다. 보안: 프리셋 이름은 모든 화면에서 글자로만 그린다(NFR3).
- **Alternatives Rejected** — 새 표(발행본, 순번, 이름) + 항목 순번 칸(짝을 외래 키가 지키지만 표·마이그레이션이 늘고 두 표를 읽음). 발행본 표의 jsonb 칸(칸 하나지만 항목과의 짝을 DB가 지키지 않음).

## ADR-004: 프리셋 항목은 종류별 외래 키로 원본을 가리킨다

- **Context** — 텍스트 자료나 PDF를 지우면 담긴 프리셋에서도 빠지고(FR4.1), 탈퇴하면 프리셋도 지워진다(FR4.2). 담은 뒤 숨긴 Catch는 남기고 이유를 보인다(FR1.11). 지금 자료 모듈은 발행 모듈을 모르고 자기 행만 지운다.
- **Decision** — 프리셋 항목 행에 Catch·텍스트 자료·PDF 외래 키 칸 셋을 두고 하나만 채운다. 세 칸 모두 원본을 지우면 연쇄 삭제한다(Catch 칸 포함). 프리셋 표는 회원 행에 연쇄 삭제로 묶는다(Q4).
- **Consequences** — 자료 모듈과 탈퇴 코드를 고치지 않고 DB가 지운다. 화면 확인 문장만 바뀐다. Catch를 지우는 경로는 탈퇴 말고는 없고, 탈퇴 때 Catch가 지워지므로 Catch 칸도 연쇄 삭제여야 탈퇴가 막히지 않는다(`api/src/database/foreign-keys.ts`의 연쇄 삭제 규칙을 따름, 기능 설계가 시험으로 묶음). 숨긴 Catch는 행을 남기고 PublishableSource가 이유를 정한다. 한 프리셋 안 중복은 종류별 유일 조건으로 지킨다(자세한 조건은 기능 설계). 보안: 다른 회원의 자료를 담지 못하게 하는 것은 외래 키가 아니라 저장할 때의 소유 확인(ADR-001)이다.
- **Alternatives Rejected** — 종류 + 원본 ID 한 쌍(발행 사본과 같은 모양이지만, 자료를 지울 때 자료 모듈이 프리셋 항목도 지워야 하고 빠뜨리면 없는 자료가 남음).

## ADR-005: 프리셋 상태는 저장하지 않고 읽을 때 센다

- **Context** — 프리셋 목록·편집 화면은 항목 수·글자 수·상한 넘음·발행할 수 없는 자료를 보인다(FR1.2). 담은 뒤 숨긴 Catch(FR1.11)와 길어진 원본 글(FR1.14)도 바로 보여야 한다. 목록은 50개까지 한 번에 준다(NFR6).
- **Decision** — 상태 값을 프리셋에 저장하지 않는다. 목록·편집 화면을 열 때마다 PresetLibrary가 PublishableSource로 원본을 읽어 센다(Q5).
- **Consequences** — 원본이 바뀌어도 늘 맞고, 다시 세는 장치가 필요 없다. 목록 한 번에 최대 50개 × 20항목의 원본을 읽으므로 읽는 쿼리 수를 묶는 방법은 기능 설계·NFR 단계가 본다. 편집 화면이 자료마다의 글자 수를 어디서 얻는지는 기능 설계의 첫 질문이다(다듬은 화면 단계).
- **Alternatives Rejected** — 저장할 때 세어 함께 저장하기(원본이 바뀌면 틀려져 다시 세는 장치가 더 필요).

## ADR-006: 겹친 사본은 앞선 것만 AI 근거와 받은 링크 읽기에 쓴다

- **Context** — 같은 자료를 담은 프리셋 둘을 한 발행본에 고르면 프리셋마다 사본이 따로 생긴다(FR2.7). 그대로 두면 같은 글이 검색 조각·요약 근거·받은 링크 읽기에 두 번 나온다.
- **Decision** — 같은 원본(종류 + 원본 ID)의 사본이 둘 이상이면, 순서 번호가 앞선 사본만 검색 조각과 기본 요약 근거로 쓴다(Q6). 질의응답과 JD 요약은 조각 검색을 쓰므로 함께 따른다. Claude 연결의 받은 링크 읽기도 둘째 사본부터 뺀다(Q9). SnapshotContract가 사본을 읽을 때 항목마다 「앞선 사본인가」 참·거짓 값을 계산해 싣는다. 판정에는 published_item의 item_kind와 source_id를 쓰되 원본 ID 자체는 사본에 싣지 않는다. 기본 요약 근거, 질의응답 머리글(표 글자 매기기와 둘째 줄이 같은 작업 세기), 받은 링크 읽기는 이 값만 보고, 조각 나누기는 published_item에서 source_id를 더 읽어 같은 판정 함수로 정한다. 받은 링크 열람 응답에서는 Publications가 이 값을 뺀다.
- **Consequences** — 같은 글이 AI 근거와 받은 링크 읽기에 한 번만 나온다. 둘째 탭의 사본은 화면에 보이지만 출처 단추가 가리키지 않는다. 판정은 한 함수이고, 조각 나누기·요약 근거 만들기·질의응답 머리글 만들기·받은 링크 읽기(쪽 나누기와 cursor에서 빠진 순서 번호를 건너뜀) 네 곳이 그 결과를 쓴다. 머리글도 앞선 사본만 세므로 겹친 사본 때문에 표 글자가 건너뛰거나 둘째 줄이 붙지 않는다(2026-11-19 승인 검토 팀장 결정, 기능 설계에서 시험으로 묶음). 사본 읽기 계약(C-07·C-10)이 넓어지므로 ADR-002의 PR 리뷰 대상(팀원 3, 받은 링크 읽기 담당, JD 요약 담당)에 든다. 요구사항 FR6.2와 이야기 AC3.6.2(같은 자료가 두 번 나온다)를 이 결정이 대신한다. 보안: 원본 ID는 사본에도 받은 사람 응답에도 싣지 않는다.
- **Alternatives Rejected** — 그대로 두기(코드 변경이 없지만 같은 근거가 두 번 나옴). 받은 링크 읽기만 그대로 두기(AI 근거와 받은 링크 읽기가 서로 다른 항목 집합을 봄).

## ADR-007: 프리셋 구분과 이름은 외부 AI에 보내지 않는다

- **Context** — 요구사항 단계가 요약 근거·질의응답 머리글·검색 조각에 프리셋 구분을 알릴지, 이름을 외부 AI(Claude)에 보낼지를 설계로 넘겼다. 보내면 개인정보처리방침의 외부 AI 절과 고지 문구가 바뀐다(constraint-register C-R4).
- **Decision** — 보내지 않는다. 요약 근거·질의응답 머리글·검색 조각은 지금 모양 그대로다(Q7).
- **Consequences** — 머리글에 프리셋 구분을 넣는 변경은 없고, 개인정보처리방침의 외부 AI 절은 바뀌지 않는다. 머리글 만들기는 ADR-006에 따라 앞선 사본만 세는 것만 바뀌어, 외부 AI로 가는 머리글이 지금과 같다. AI는 「어느 탭의」라고 말하지 못하고, 면접관은 출처 단추로 탭을 찾아간다(FR3.5). 개인정보: 외부로 나가는 내용이 늘지 않는다.
- **Alternatives Rejected** — 질의응답 머리글과 요약 근거에 프리셋 이름 넣기(AI가 탭 이름으로 말할 수 있지만 머리글 코드와 방침·고지 문구를 함께 바꿈).

## ADR-008: 출처 이동은 공용 함수 하나로 모으고 탭 부품을 함께 쓴다

- **Context** — 출처 단추가 다른 탭의 글을 가리키면 탭을 바꾸고 옮겨 가야 하며(FR3.5), 작성자 상세도 같이 움직여야 한다(FR3.7). 출처 이동 코드는 지금 두 화면에 같은 모양으로 두 벌 있다. 탭은 그려지지 않은 항목을 화면 id로 찾지 못하므로 탭 바꾸기와 강조 대상 정하기가 같은 상태 바뀜에서 일어나야 한다. 자료 화면의 탭도 같은 부품으로 화살표 키를 쓴다(FR7.1).
- **Decision** — 두 화면의 출처 이동을 SnapshotViewer의 공용 함수 하나로 모으고 탭 바꾸기를 거기에 한 번만 넣는다(Q8). 자료 화면의 탭 부품을 일반화해 TabStrip으로 두고 사본 탭과 자료 화면 탭이 함께 쓴다. [답으로 돌아가기]는 만들지 않는다(다듬은 화면 단계 2026-11-19 팀장 결정).
- **Consequences** — 고칠 곳과 시험할 곳이 한 곳이 된다. 지금 두 벌을 하나로 바꾸는 정리가 함께 들어가므로 작성자 상세의 동작이 그대로인지 시험한다. 자료 화면은 탭 이름·자리가 그대로이고 키보드 동작과 텍스트 쪽 tabpanel이 더해진다.
- **Alternatives Rejected** — 두 화면에 각각 탭 바꾸기 넣기(지금 구조는 그대로지만 같은 변경을 두 곳에 하고 둘 다 시험함).

## ADR-009: 프리셋 편집의 Catch 고르기 목록은 서버가 거른다

- **Context** — 프리셋에는 공개이고 작업 사실과 기여가 확인됐고 원본 저장소가 보호되지 않은 Catch만 담는다(FR1.5). 본인 Catch 목록 조회(GET /v1/catches)는 20개씩 주고, 지금 발행 화면은 받은 뒤 화면에서 고를 수 없는 것을 막는다. 화면에서 거르면 한 번 불러올 때 고를 수 있는 것이 몇 개 남지 않는다.
- **Decision** — 본인 Catch 목록 조회에 「담을 수 있는 Catch만」 조건을 더해 서버가 거른다. 지금 작성자 설명 걸러 보기와 함께 쓸 수 있다. 판정은 PublishableSource와 같은 결과여야 한다(2026-11-19 승인 검토 팀장 결정).
- **Consequences** — CatchLibrary가 바뀌는 구성 요소가 된다(조회 조건 하나). 목록 쪽 SQL 조건과 PublishableSource 판정이 어긋나지 않는지 시험으로 묶는다. cursor가 조건까지 묶으므로 조건을 더할 때 cursor 판본도 함께 본다(기능 설계). 보안: 본인 목록만 걸러 주므로 노출 범위는 그대로다.
- **Alternatives Rejected** — 화면에서 걸러 보이기(지금 발행 화면 방식, 20개씩 불러올 때 고를 수 있는 것이 적게 남음).
