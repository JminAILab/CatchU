# Requirements — 발행 프리셋

이 문서에서 발행본을 받아 읽는 사람은 「면접관」, 프리셋을 만들고 발행하는 사람은 「지원자」, intent를 정하는 우리 팀장은 「팀장」이다.

## Intent analysis

- 지원자는 발행할 때마다 Catch와 자료를 하나씩 고르지 않고, 미리 만든 묶음(프리셋)을 고른다. 면접관은 발행본이 한 줄로 길게 이어지지 않고 프리셋별 탭으로 나뉘어 무엇이 어떤 자리인지 구분한다(intent-statement).
- 성공은 기능이 되는지로 판단한다: 2026-11-30까지 dev 반영, 프리셋을 골라(최대 5개) 발행, 두 화면의 탭, 출처 단추의 탭 이동, 요약이 자료 맨 아래에 놓이지 않는 배치(intent-statement 성공 기준).
- 지금 발행본은 항목마다 순서 번호 하나로만 저장되고 묶음 개념이 없다. 순서 번호를 발행본 전체에 이어 매기면 검색 조각·요약 근거·질의응답 머리글·받은 링크 읽기는 지금대로 동작한다(`architecture.md`, `code-structure.md`, developer-scan.md).
- 지원자에게 보이는 서비스 쪽 바탕은 지금 그대로다(`business-overview.md`). 이 작업은 발행과 받은 사람 화면의 틀을 바꾼다.

## Functional requirements

### FR1. 프리셋 관리 (scope-document S1, S6, S7)

- **FR1.1** 상단 메뉴의 「텍스트 자료」와 「발행본」 사이에 「프리셋」이 있고, 누르면 프리셋 목록 화면으로 간다(W1).
  - Given 로그인한 지원자 When 상단 메뉴를 보면 Then 「내 자산 · 텍스트 자료 · 프리셋 · 발행본 · JD 관리」 순서로 보인다.
  - Given 프리셋 목록 화면 When 상단 메뉴를 보면 Then 「프리셋」만 현재 자리로 표시되고 「발행본」은 현재 자리로 표시되지 않는다.
- **FR1.2** 프리셋 목록은 지원자의 프리셋을 쪽을 나누지 않고 한 번에 보인다. 프리셋마다 이름, 항목 수, 글자 수를 보이고, 발행할 수 없는 자료가 있으면 그 수를 함께 보인다(Q5, W2).
  - Given 프리셋 3개 When 목록을 열면 Then 3개가 모두 이름·항목 수·글자 수와 함께 보인다.
  - Given 목록 불러오기 실패 When 화면을 보면 Then 실패 안내와 [다시 불러오기]가 보이고 「아직 만든 프리셋이 없습니다」로 보이지 않는다.
  - Given 프리셋 0개 When 목록을 열면 Then 「아직 만든 프리셋이 없습니다」와 [새 프리셋]이 보인다.
- **FR1.3** 지원자는 프리셋을 50개까지 만들 수 있다(Q5).
  - Given 프리셋 50개 When [새 프리셋]으로 저장하면 Then 저장되지 않고 50개까지 만들 수 있다는 안내가 보인다. 서버도 51번째를 거부한다.
- **FR1.4** 프리셋 이름은 앞뒤 공백을 뺀 1~50자이고, 같은 이름의 프리셋을 여러 개 만들 수 있다. 이름 칸에 이 이름이 받은 사람 화면의 탭 이름으로 보인다는 안내가 있다(Q4).
  - Given 이름 칸이 비었거나 51자 When 저장하면 Then 저장되지 않고 이름 칸에 무엇이 잘못됐는지 보이며, 담은 자료는 그대로 남는다.
  - Given 같은 이름의 프리셋이 이미 있을 때 When 같은 이름으로 저장하면 Then 저장된다.
- **FR1.5** 프리셋에는 Catch·텍스트 자료·PDF를 담는다. 담을 수 있는 것은 다음과 같다(Q6, Q10, W3).
  - Catch: 공개한 Catch 가운데 작업 사실과 기여가 확인됐고 원본 저장소가 보호되지 않은 것만 고르기 목록에 보인다. 공개는 내 자산 화면에서 한다. 목록 위에 「작성자 설명을 쓴 Catch만 보기」를 지금 발행 화면의 동작 그대로 둔다.
  - 텍스트 자료: 지원자의 텍스트 자료.
  - PDF: 글 추출이 끝난 PDF.
  - Given 비공개 Catch When 고르기 목록을 보면 Then 그 Catch는 목록에 없다.
  - Given 확인이 필요한 Catch When 고르기 목록을 보면 Then 그 Catch는 목록에 없다.
- **FR1.6** 한 프리셋 안에서는 같은 자료를 한 번만 담는다(Q1).
  - Given 이미 담긴 Catch When 다시 담으려 하면 Then 담기지 않는다. 서버도 같은 자료가 두 번 있는 저장 요청을 거부한다.
- **FR1.7** 프리셋 하나에 담는 양은 발행 상한과 같다: 항목 20개, 전체 글 60,000자(Q3).
  - Given 항목 20개 When 더 담으려 하면 Then 담기지 않고 상한 안내가 보인다.
  - Given 담으면 60,000자를 넘는 자료 When 담으려 하면 Then 담기지 않고 상한 안내가 보인다. 서버도 거부한다.
- **FR1.8** 프리셋 안 자료의 순서는 「위로」「아래로」 단추로 정하고, 「빼기」로 뺀다(W3, intent-statement).
- **FR1.9** 프리셋을 지울 때는 지울 프리셋 이름을 밝힌 확인을 거친다(W3, F2).
  - Given 확인에서 취소 When 돌아오면 Then 프리셋은 그대로다.
- **FR1.10** 프리셋을 고치는 화면에 「프리셋을 고쳐도 이미 보낸 링크는 바뀌지 않습니다」 안내가 있다(입력 문서 §3-3, W3).
- **FR1.11** 담은 뒤에 발행할 수 없는 상태가 된 Catch(숨긴 Catch, 원본 저장소가 보호된 Catch)는 담긴 목록에 그대로 두고 이유를 표시한다(Q11, Q10). 확인한 Catch를 다시 확인 전으로 되돌리는 길은 지금 코드에 없어 넣지 않는다.
  - Given 담긴 Catch를 내 자산 화면에서 숨김 When 프리셋을 열면 Then 그 Catch가 담긴 목록에 남고 「비공개」 이유가 보인다.
- **FR1.12** 저장에 실패하면 실패 안내를 보이고, 입력한 이름과 담은 자료를 그대로 둔다(W3).
- **FR1.13** 지원자는 만든 프리셋을 고쳐 저장할 수 있다: 이름 바꾸기, 자료 더하기·빼기, 순서 바꾸기. 저장할 때는 만들 때와 같은 검증(FR1.4~FR1.7)을 한다(W3, F2).
  - Given 프리셋 P When 이름을 바꾸고 자료 하나를 더하고 순서를 바꿔 저장하면 Then 프리셋 목록과 편집 화면에 바뀐 이름·항목 수·순서가 보인다.
  - Given 프리셋 P When 이름을 비우거나 51자로 바꿔 저장하면 Then 저장되지 않고 이름 칸에 무엇이 잘못됐는지 보이며, 바꾼 내용은 그대로 남는다.
  - Given 프리셋 P When 이미 담긴 자료를 다시 담거나 상한을 넘게 담아 저장하면 Then 저장되지 않는다. 서버도 거부한다.
- **FR1.14** 저장한 뒤에 담긴 원본 글이 길어져 프리셋이 발행 상한(전체 글 60,000자)을 넘으면, 프리셋 목록과 편집 화면에 상한을 넘었다고 보이고, FR2.4에 따라 발행 화면에서 그 프리셋을 고를 수 없다(이 단계 승인 검토).
  - Given 프리셋 P에 담긴 텍스트 자료를 고쳐 P가 60,000자를 넘음 When 프리셋 목록을 열면 Then P에 상한을 넘었다는 표시가 보인다.

### FR2. 프리셋으로 발행 (scope-document S2, S6)

- **FR2.1** 발행 화면의 흐름은 지금 그대로이고, 「발행할 자료 고르기」와 「고른 항목과 순서」 자리만 「프리셋 고르기」와 「고른 프리셋과 순서 (n/5)」로 바뀐다. 「제목과 비밀번호」 → 「발행 내용 확인」 → 「발행됨」은 그대로다(W4).
- **FR2.2** 한 발행본에 프리셋을 1~5개 고르고, 그 순서를 「위로」「아래로」 단추로 정한다(입력 문서 §3-1).
- **FR2.3** 다섯 개를 고르면 나머지 고르기 칸이 막히고 「최대 5개」라고 보인다(Q7).
- **FR2.4** 다음 프리셋은 고를 수 없고, 그 이유가 칸 옆에 보인다(Q7, Q11).
  - 항목이 0개인 프리셋.
  - 고르면 발행본 전체가 상한(항목 20개·전체 글 60,000자)을 넘게 되는 프리셋. 상한은 고른 프리셋들의 항목을 모두 더해 세고, 같은 자료가 두 프리셋에 있으면 두 번 센다(Q1, Q2).
  - 발행할 수 없는 자료(FR1.11)가 담긴 프리셋. 이유에 어느 자료 때문인지 보인다.
- **FR2.5** 프리셋이 하나도 없으면 「프리셋 고르기」 자리에 프리셋 목록 화면을 가리키는 링크만 보인다. 발행 화면 안에서는 프리셋을 만들지 않는다(입력 문서 §3-1, W4).
- **FR2.6** 프리셋 목록 불러오기에 실패하면 실패 안내와 [다시 불러오기]가 보이고, 「프리셋 없음」으로 보이지 않는다(W4).
- **FR2.7** 같은 자료가 담긴 프리셋 여럿을 한 발행본에 함께 고를 수 있다. 겹친 자료는 프리셋마다 사본을 따로 만들어 각 탭에 보인다(Q1).
  - Given Catch A가 프리셋 P1·P2에 담김 When P1·P2를 골라 발행하면 Then 발행되고, 받은 사람 화면의 P1 탭과 P2 탭에 Catch A가 각각 보인다.
- **FR2.8** 서버는 발행할 때 권한, 고른 프리셋과 자료, 크기를 다시 확인한다. 막히면 어느 프리셋의 어느 자료 때문인지 응답하고, 발행 화면이 그것을 보인다(12월 FR4.7, Q7, 입력 문서 §3-3).
  - Given 고른 뒤 다른 창에서 담긴 Catch를 숨김 When 발행하면 Then 발행되지 않고 그 프리셋과 Catch가 보인다.
- **FR2.9** 발행할 때 비공개 Catch를 공개로 바꾸는 동작을 없앤다(Q10).
- **FR2.10** 「발행 내용 확인」은 지금처럼 제목·비밀번호·만료를 보이고, 고른 자료 대신 고른 프리셋과 그 순서를 보인다(12월 FR4.6, W4).
- **FR2.11** 발행본은 발행 당시 자료를 고정한 사본이다. 프리셋을 고치거나 지워도 이미 만든 발행본은 바뀌지 않는다(12월 FR4.3, 입력 문서 §6).
  - Given 발행본을 만든 뒤 프리셋 이름과 담긴 자료를 바꿈 When 받은 사람 화면을 열면 Then 발행 당시의 탭 이름과 자료가 보인다.

### FR3. 받은 사람 화면과 작성자 발행본 화면의 탭 (scope-document S3, S4, S5)

- **FR3.1** 받은 사람 화면의 순서는 제목 → 이 링크에서 할 수 있는 것 안내 → Claude 연결 → 발행 시각 → 「AI 요약」 → 「발행본 자료」(탭 줄과 탭의 자료) → 「발행본에 질문하기」 → JD 요약이다. AI 요약과 질의응답은 탭 밖에 있다(Q4 화면 초안, W5).
  - Given 받은 사람 화면 When 위에서부터 읽으면 Then 「AI 요약」이 「발행본 자료」보다 위에 있다.
- **FR3.2** 탭 줄은 프리셋이 하나여도 보인다. 탭 이름은 발행 당시의 프리셋 이름이고, 길면 뒤를 줄이며, 탭을 누르면 그 아래에 프리셋 이름 전체가 보인다. 탭 이름 옆에 자료 개수를 붙이지 않는다(입력 문서 §3-2, W5).
- **FR3.3** 탭은 화살표 키로 옮기면 그 탭이 바로 열린다. 탭 줄에 Tab으로 들어오면 열려 있는 탭에 초점이 놓이고, 다시 Tab을 누르면 그 탭의 자료로 들어간다(W5).
- **FR3.4** 탭을 바꿔도 「발행본에 질문하기」의 대화가 남는다(입력 문서 §3-2).
  - Given 질문과 답이 하나 있음 When 다른 탭을 열면 Then 그 질문과 답이 그대로 보인다.
- **FR3.5** 답이나 요약의 출처 단추가 다른 탭의 글을 가리키면, 그 탭으로 바꾸고 그 글로 옮겨 가 강조한다(입력 문서 §3-2, W5).
  - Given 첫 탭이 열려 있고 답의 출처가 둘째 탭의 PDF를 가리킴 When 출처 단추를 누르면 Then 둘째 탭이 열리고 그 PDF 글이 강조된다.
- **FR3.6** 출처로 옮겨 간 글 바로 위에 [답으로 돌아가기]가 보인다. 가리킨 글이 열린 탭에 있어도 보인다. 누르면 답에서 눌렀으면 그 답으로, 요약에서 눌렀으면 요약으로 돌아가고, 초점은 눌렀던 출처 단추에 놓인다. 탭은 옮겨 간 탭 그대로 둔다(W5).
- **FR3.7** 작성자 발행본 상세 화면의 「발행본 자료」도 FR3.2~FR3.6과 같이 보이고 움직인다(W6).

### FR4. 자료 지우기·탈퇴·개인정보처리방침 (scope-document S7)

- **FR4.1** 텍스트 자료나 PDF를 지우면, 그 자료는 담긴 프리셋의 목록에서도 사라지고 자리표시를 남기지 않는다. 지우기 확인 문장에 「프리셋에 담겨 있으면 거기서도 빠진다」는 말을 더한다(W3, F6).
  - Given 텍스트 자료 T가 프리셋 P에 담김 When T를 지우면 Then P의 항목 수가 하나 줄고 T가 보이지 않는다. 이미 보낸 발행본의 T 사본은 그대로다.
- **FR4.2** 탈퇴하면 지원자의 프리셋도 지워진다. 탈퇴 화면은 바뀌지 않는다(W1 S7 절).
- **FR4.3** 개인정보처리방침의 저장 항목 표와 「하나씩 지우기」 문장에 프리셋을 더한다. 문구는 팀장 확정 문구로 바꾼다(feasibility, developer-scan.md §7).

### FR5. 이 변경 전 발행본 버리기 (scope-document S8)

- **FR5.1** 발행 요청·사본 계약과 프리셋 저장을 바꿀 때 함께, 이 변경 전에 만든 발행본의 DB 행과 파일 저장소의 발행본 PDF 사본을 모두 지운다. 발행본에 딸린 기록(검색 조각, 요약, 받은 사람의 JD 요약 기록)도 함께 지워진다(Q8, intent-backlog IB-8).
  - Given 변경 전 발행본 링크 When 변경 뒤에 열면 Then 지금의 「쓸 수 없는 링크」 화면이 보인다.

### FR6. 발행본을 읽는 다른 기능 (scope-document S9)

- **FR6.1** 발행본의 순서 번호는 발행본 전체에 하나로 이어 매긴다. 순서는 고른 프리셋 순서, 그 안에서 프리셋 안 자료 순서다(feasibility 영향 범위 2, `architecture.md`).
- **FR6.2** Claude 연결의 받은 링크 읽기는 프리셋 구분을 싣지 않고, 지금처럼 항목을 순서대로 읽는다(Q9).
- **FR6.3** AI 요약, 질의응답, 검색 조각, JD 요약은 바뀐 사본에서도 지금처럼 동작한다(12월 FR2.7·FR6.2). 등록한 프리셋 전체가 근거다. 같은 자료가 두 프리셋에 있는 경우는 설계 단계 결정(Q1)에 따른다.

### FR7. 자료 화면의 탭 (rough-mockups Q5)

- **FR7.1** 텍스트 자료 화면의 탭(「텍스트 자료」「PDF 자료」)도 받은 사람 화면과 같은 탭 부품을 써서 화살표 키로 옮겨진다. 탭 이름과 자리는 지금 그대로다(W5 자료 화면 절).

## Non-functional requirements

- **NFR1** 접근성: 탭, 프리셋 고르기, 순서 단추, 출처 이동, 돌아가기는 키보드만으로 모두 쓸 수 있다. 화면 낭독기에 탭의 역할과 선택 상태, 고를 수 없는 프리셋의 이유가 읽힌다. 고를 수 없음·비공개·상한 넘음 같은 상태를 색만으로 나타내지 않는다.
- **NFR2** 권한: 프리셋은 그 지원자만 읽고 쓴다. 다른 회원의 프리셋 ID로 읽기·고치기·지우기·발행하면 거부한다. 프리셋에 담는 자료와 발행에 고른 프리셋은 요청한 지원자의 것만 받는다.
- **NFR3** 화면 출력: 프리셋 이름은 모든 화면(목록, 편집, 발행 화면, 탭)에서 글자로만 그리고 HTML로 해석하지 않는다.
- **NFR4** 자료 보호: 프리셋 이름과 담긴 자료 내용을 로그와 AI·이슈·PR 공유 로그에 남기지 않는다(team-practices Code Style).
- **NFR5** 상태 표시: 불러오는 중, 비었음, 불러오기 실패를 서로 다른 화면으로 보이고, 조회 실패를 0건으로 보이지 않는다(W2, W4).
- **NFR6** 프리셋 목록은 50개까지를 한 번의 요청으로 받는다(Q5).

## Constraints

- 지금 스택(web Next.js, api NestJS, PostgreSQL·TypeORM)으로 만들고 새 라이브러리를 들이지 않는다. 탭은 자료 화면의 탭 부품을 고쳐 다시 쓴다(constraint-register C-T1·C-T2).
- DB 변경은 배포 때 도는 migration으로 넣는다(C-T3).
- 모든 작업은 2026-11-30까지 dev에 들어간다. 발행 요청·사본 계약 변경은 먼저 PR로 올려 팀원 3, 받은 링크 읽기 담당, JD 요약 담당의 리뷰를 받는다(scope-document, C-O1·C-O3).
- 한 작업 브랜치 `api/publication-presets`에서 dev PR을 차례로 연다(team-practices 면담 Q3).
- 첫 묶음(계약 + 프리셋 저장 + 기존 발행본 버리기)을 첫 작업 단위로 따로 돌려 승인받는다(team-practices 면담 Q5, intent-backlog IB-1·IB-8).
- 화면은 기능만 맞춘다. 모양 다듬기와 드래그는 이 작업 뒤 팀원 3이 한다(C-O4, C-T5).
- 시험은 팀 관행대로 시나리오·기대 결과·실패 조건을 먼저 정하고 세부 시험 코드는 구현 뒤에 쓴다. 커버리지 하한은 두지 않고 잰 값을 보고한다(team-practices Testing Posture).

## Assumptions

- 받은 사람 화면을 처음 열면 첫 번째 프리셋 탭이 열려 있다. 화면 초안이 첫 탭을 연 상태로 그렸고, 다른 기본값의 근거가 없다.
- 프리셋 목록의 순서는 만든 순서다. 순서를 정하는 요구가 없어 가장 단순한 순서를 쓴다.
- 기존 발행본을 지우는 일은 이용자가 팀 관련자뿐이라 따로 알리지 않는다(feasibility Q2·Q7).
- Catch가 지워지는 길은 지금 탈퇴뿐이라 FR1.11에 넣지 않는다. 앞으로 다른 길로 Catch가 지워지면 텍스트 자료·PDF처럼(FR4.1) 담긴 프리셋에서 함께 빠진다.

## Out of scope

- 대표 Catch 표시, Catch 검색과 JD 연계, 드래그, 화면 모양 다듬기, 「더 보기」 반복과 순서 단추가 잘 안 보이는 문제, 박스 크기와 펼쳐진 안내(intent-statement, scope-document).
- 입력 문서 §8의 채택하지 않은 안. 단, 「비공개 Catch를 고르는 목록에서 빼기」는 Q10 팀장 결정으로 채택한다.
- 받은 링크 읽기에 프리셋 구분 싣기(Q9).
- 새 AWS 자원, 새 라이브러리.

## Open questions

설계 단계에서 정한다.

- 같은 글이 두 프리셋에 사본으로 있을 때 질의응답·요약 근거에 두 번 쓰이는지와 그 처리(Q1).
- AI 요약 근거·질의응답 머리글·검색 조각에 프리셋 구분을 알릴지. 가장 단순한 안은 알리지 않는 것이다(feasibility).
- 프리셋 이름을 외부 AI에 보낼지. 보내면 개인정보처리방침의 외부 AI 절과 고지 문구도 고친다(constraint-register C-R4).
- 개인정보처리방침 확정 문구(팀장)(FR4.3).
- 발행이 막혔을 때 서버 응답에 프리셋과 자료를 싣는 모양(FR2.8).
- 프리셋 화면의 주소. 발행본 주소 아래에 두면 상단 메뉴에서 「발행본」도 현재 자리로 켜진다(developer-scan.md §8). 주소는 FR1.1의 기준(「프리셋」만 현재 자리로 표시)을 만족하게 정한다.

다듬은 화면 단계에서 정한다.

- 출처로 옮겨 간 직후 초점이 놓이는 자리와 [답으로 돌아가기]에 키보드로 닿는 방법(wireframes).
- 저장하지 않은 변경을 두고 프리셋 편집 화면을 떠날 때의 처리(wireframes).
- 상단 메뉴 5개와 프로필이 지금 헤더 폭에 들어가는지(rough-mockups 검토 R-07).
