# Performance Requirements — u2-applicant-screens

근거: 요구사항 `inception/requirements-analysis/requirements.md` NFR1·NFR5·NFR6, 기능 설계 `construction/u2-applicant-screens/functional-design/functional-spec.md` 흐름 1~3(기능 설계 Q3 A: 쪽마다 세기), U1 API `api/docs/presets.md`(목록 한 번, 세기 1~50개), 이 단계 질문 Q2(2026-11-20 팀장).

응답 시간 숫자 목표는 두지 않는다. 이용자는 12월까지 팀 관련자뿐이고, 지금 어느 화면에도 응답 시간 목표나 재는 장치가 없다(이 단계 Q2 A). 대신 화면이 부르는 요청 수를 고정하고 시험으로 센다. 요청 수가 고정되면 프리셋·자료 수가 늘어도 화면이 부르는 횟수는 늘지 않는다.

## 요구사항

| ID | 요구사항 | 확인 |
|---|---|---|
| NFR6.1 | 프리셋 목록 화면과 발행 화면은 프리셋 목록을 `GET /v1/presets` 한 번으로 받는다(50개까지 쪽 나눔 없음). 프리셋마다 따로 부르지 않는다 | 화면 시험: 목록 50개에 요청 1번 |
| NFR6.2 | 프리셋 편집 화면을 열 때 요청은 상세 1번(고치기만) + 고르기 목록 3번(Catch·텍스트 자료·PDF 첫 쪽) + 세기 최대 3번(쪽마다 1번, 고를 수 있는 자료가 없는 쪽은 부르지 않음)이다 | 화면 시험: 대역 호출 수를 셈 |
| NFR6.3 | [더 보기] 한 번은 그 목록 1번 + 세기 최대 1번이다. 걸러 보기를 바꾸면 Catch 첫 쪽 1번 + 세기 최대 1번이다 | 화면 시험 |
| NFR6.4 | 세기 한 번에 보내는 자료는 한 쪽(20개 이하)뿐이라 U1 세기 한도(50개) 안이다. 쪽을 합쳐 다시 세지 않는다 | 화면 시험: 세기 요청의 항목 수 ≤ 20 |
| NFR6.5 | 담기·빼기·순서 바꾸기·발행 화면의 고르기는 요청 없이 화면 안에서 셈한다(담긴 글자 합, 고른 프리셋들의 항목·글자 합) | 화면 시험: 고르기 동안 요청 0번 |
| NFR6.6 | 발행이 막혔을 때 다시 불러오기는 프리셋 목록 1번뿐이다(기능 설계 BR4.6). 자동으로 다시 발행하지 않는다 | 화면 시험 |
| NFR5.1 | 세기 요청이 늦거나 실패해도 고르기 단추는 목록 응답이 오는 대로 먼저 그린다. 글자 이유 막힘(「전체 글이 60,000자를 넘습니다」)은 세기 응답이 온 뒤에 붙고, 실패하면 붙지 않는다 | 화면 시험: 세기 대역을 늦추거나 실패시킴 |
| NFR5.2 | 불러오는 중·비었음·불러오기 실패는 서로 다른 글로 보이고, 실패를 0개로 보이지 않는다(목록·편집·발행 화면 모두) | 화면 시험 |
| NFR1.1 | 저장·불러오기 결과 안내는 화면을 다시 그리지 않고 읽힌다: 「저장했습니다.」는 `role="status"`, 실패는 `role="alert"`, 5개 안내는 `aria-live="polite"`(interaction-spec) | 화면 시험: 역할 속성 |

## 하지 않는 것

- 응답 시간 측정, 브라우저 성능 시험, 캐시. 지금 화면들과 같다.
- 고르기 목록 셋을 한 요청으로 합치는 새 api(기능 설계 Q2 B를 고르지 않았다).

## Assumptions & Open Questions

- 세기 요청은 고르기 목록 응답이 온 뒤에 보낸다. 목록과 세기를 한 번에 받을 수 없어 쪽마다 요청이 하나 늘지만, 그 수는 NFR6.2·NFR6.3으로 고정된다.
