# Functional Design — u1-preset-contract 질문

근거: 단위 `inception/units-generation/unit-of-work.md`(U1)와 `unit-of-work-story-map.md`(U1 16줄), 이야기 `inception/user-stories/stories.md`, 요구사항 `inception/requirements-analysis/requirements.md`, 구성 요소 `inception/domain-design/components.md`와 결정 `decisions.md`(ADR-001~009), 계약 `inception/contract-design/contract-summary.md`(P-1~P-6과 Open questions), 다듬은 화면 `inception/refined-mockups/mockups.md`·`interaction-spec.md`, 지금 코드(`api/src/publications/publish.service.ts`·`publication-manage.service.ts`, `api/src/file-storage/file-storage.ts`).

이 단계에서 정하는 것으로 넘어온 열린 질문 가운데, 사람이 정해야 하는 넷만 묻는다. 나머지(오류 문구, 막힘 이유를 고르는 순서, 「앞선 사본인가」 칸 이름과 빼는 자리, 목록 순서, 이름 앞뒤 공백)는 승인된 문서와 지금 코드를 따라 정하고 설계 문서에 적는다.

지금 코드에서 확인한 것:

- 발행은 트랜잭션 밖에서 PDF 추출 완료를 확인하고 PDF 사본 파일을 먼저 복사한 뒤, 트랜잭션 안에서 Catch·자료 행을 잠그고 다시 읽는다(`publish.service.ts` 157~170행, C-17). 그래서 어떤 PDF를 복사할지는 트랜잭션 전에 정해져야 한다.
- 발행본 PDF 사본 파일은 `members/<회원>/publications/<발행본>/` 아래에 있고, 작성자 삭제는 이 접두어를 먼저 지운 뒤 행을 지운다(`publication-manage.service.ts` 126~152행). DB 마이그레이션은 파일 저장소를 지우지 못한다.
- 자료 고르기 목록(Catch 목록, 텍스트 자료 목록, PDF 목록)에는 글자 수가 없다.

## Q1. [설계] 편집 화면이 자료마다의 글자 수를 어디서 얻을까

다듬은 화면 M3는 편집 중에 「항목 4개 · 12,300자」를 보이고, 담으면 60,000자를 넘는 자료를 막습니다(FR1.7). 이미 담긴 자료의 글자 수는 프리셋 상세 응답에 실을 수 있지만, 편집 중 새로 고른 자료의 글자 수는 지금 어디에도 없습니다. 글자 수는 발행과 같은 셈(Catch는 작업 사실·나의 기여·근거 문장·작성자 설명, PDF는 쪽 글)이라 화면이 직접 셀 수 없습니다.

A. 세기 경로 하나를 더한다. 편집 화면이 고른 자료 목록(종류 + ID)을 보내면 서버가 자료마다 글자 수와 발행할 수 없는 이유를 돌려준다. 프리셋 상세 응답도 담긴 자료마다 같은 값을 싣는다. 고치는 곳은 프리셋 모듈 하나다
B. 자료 고르기 목록 셋(Catch 목록, 텍스트 자료 목록, PDF 목록)의 응답에 글자 수 칸을 더한다. 경로는 늘지 않지만 세 목록(그중 Catch 목록은 CatchLibrary)을 고치고, Catch 목록은 쪽마다 사본 내용을 만들어 세야 한다
X. Other (please specify)

[Answer]: X. A로 하되, 편집 화면은 담긴 자료뿐 아니라 고르기 목록에 불러온 자료(Catch 쪽, 텍스트 자료, PDF)도 이 경로로 물어, M3처럼 담으면 60,000자를 넘는 자료의 단추를 담기 전에 막는다. 한 번에 받는 자료 수 상한은 기능 설계에서 정한다.

## Q2. [설계] 저장할 때 자료의 발행 자격을 볼까

담은 뒤 숨긴 Catch는 담긴 목록에 그대로 두고 이유를 보입니다(FR1.11). 고르기 목록은 담을 수 있는 자료만 보입니다(FR1.5, ADR-009). 서버가 저장 때 자격까지 거부할지 정해야 합니다.

A. 저장 때는 소유와 존재만 본다(NFR2). 자격(공개·확인·보호 아님·추출 완료)은 저장을 막지 않고 이유로 보이며, 발행 때 막는다(FR2.4·FR2.8). 담긴 채 숨겨진 Catch가 있어도 다른 것을 고쳐 저장할 수 있다
B. 새로 담는 자료만 자격을 보고 자격이 없으면 거부한다. 이미 담긴 자료는 자격이 없어도 남긴다. 서버가 새 자료와 원래 자료를 갈라야 하고, 거부 이유 칸이 하나 더 는다
X. Other (please specify)

[Answer]: A

## Q3. [설계] 발행 중에 프리셋이 바뀌면

PDF 사본을 트랜잭션 전에 복사해야 하므로 프리셋은 트랜잭션 밖에서 한 번 읽어 펴야 합니다. 그 뒤 트랜잭션까지의 짧은 틈에 같은 회원이 프리셋을 고치거나 지울 수 있습니다. 코딩 절차 「기술」 행은 동시 요청을 남의 자료 노출이나 삭제 실패로 이어질 때만 막는다고 합니다.

A. 트랜잭션 밖에서 한 번 읽어 편 목록으로 끝까지 간다(자료 행은 지금처럼 트랜잭션 안에서 잠그고 다시 읽는다). 그 틈에 프리셋을 고치거나 지우면 읽은 때의 내용으로 발행된다. 새 오류 코드가 없다. 승인된 ADR-002·components.md의 「트랜잭션 안에서 프리셋을 읽어 바뀌지 않게」 문장을 이 결정이 대신한다
B. 트랜잭션 안에서 프리셋을 다시 읽어 앞서 편 목록과 다르면 거부하고 다시 발행하게 한다. 승인 설계 문장 그대로지만 거부용 오류 코드가 하나 더 필요해 계약 P-2가 바뀐다
X. Other (please specify)

[Answer]: A

## Q4. [설계] 변경 전 발행본의 PDF 사본 파일을 어떻게 지울까

FR5.1은 변경 전 발행본의 DB 행과 파일 저장소의 PDF 사본을 모두 지운다고 정했습니다. 마이그레이션은 DB 행만 지울 수 있습니다. 이용자는 팀 관련자뿐이고 저장소는 로컬 폴더와 EKS의 S3입니다.

A. 마이그레이션은 행만 지우고, 파일은 배포 전에 팀장이 저장소에서 발행본 폴더(`members/*/publications/`)를 직접 지운다. 배포 안내와 PR 본문에 한 줄로 적는다. 코드는 늘지 않는다
B. 한 번 쓰는 api 명령을 만든다. 마이그레이션 전에 남은 발행본마다 지금 삭제 경로(접두어 삭제 → 행 삭제)를 돌고, 마이그레이션은 행이 남아 있으면 멈춘다. 명령·시험·실행 순서 안내가 는다
X. Other (please specify)

[Answer]: X. A로 하되, 배포 안내와 PR 본문에 지울 곳을 발행본 사본 폴더(members/*/publications/)로만 적고 원본(members/*/materials/)과 members/ 전체는 지우지 않는다고 적는다. S3는 먼저 --dryrun으로 지울 목록을 확인한 뒤 지우고, 팀원 로컬 폴더에 남은 사본은 가리키는 행이 없어 열리지 않으므로 지우기는 선택으로 적는다.
