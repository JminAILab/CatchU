## Q1. [설계] 첫 AI-DLC 제출 범위

계약 「Contract ownership rules」는 U4가 착수 직후 첫 AI-DLC 제출 범위(인터페이스·표 정의·마이그레이션·가짜 구현)로 `publication`·`published_item`·`text_material` 표와 `catch_asset` 작성자 설명 칸, 그리고 C-10 `PublicationAccess`의 인터페이스·가짜 구현을 먼저 내라고 정했다. 제출은 팀 규칙에 따른 AI-DLC 제출이고, 통합 브랜치 `intent/260925-intent-12`에 합치는 것은 팀장이 한다(2026-10-27 사용자 정정). U3(시험 자료)·U5·U10(합성 제공자)·U6(시험 자료)이 이것을 가져다 쓴다. C-11(받은 사람 화면 붙는 자리)도 U4가 주지만 첫 AI-DLC 제출 범위에 넣으라는 문장은 없다.

A. 계약이 적은 것만: C-07·C-13·C-14 표 정의·마이그레이션(탈퇴 삭제 문서 `member-withdrawal-deletion.md`에 표 행 추가 포함), C-10 인터페이스와 메모리 가짜 구현(시험 자료를 넣어 판정 결과를 정할 수 있는 것). 화면·API 경로는 넣지 않는다.
B. A에 C-11의 `RecipientSlotProps` 형(type)과 받은 사람 화면의 빈 자리 네 개만 더한다 — U5·U10이 web 컴포넌트를 붙일 자리를 먼저 쓸 수 있다. 작은 web 변경이 늘어난다.
C. A에 C-10의 실제 DB 구현까지 넣는다 — 소비 Unit이 가짜 대신 실제 판정을 바로 쓰지만, 링크 판정 본체가 첫 AI-DLC 제출 범위에 들어가 범위가 커지고 검토가 늦어진다.
X. Other (please specify)

## Q2. [설계] 아직 없는 공용 기반(U2)·색인(U3) 인터페이스를 U4가 기다리는 방식

U4의 발행은 U2의 `AiRun`(C-02)·`DailyRunLimit`(C-03)·`AiConsentGate`(C-04)·`FileStorage`(C-05)와 U3의 `PublishedIndexWriter`(C-08)를 부른다. 지금 통합 브랜치에는 이 인터페이스들이 아직 없다(U1의 `ai-generation`만 있음). U2·U3의 첫 제출 범위(인터페이스·가짜 구현)는 팀장이 맡는다.

A. U4는 이 인터페이스들을 계약 모양 그대로 시험 쪽에만 가짜로 두고 발행 로직을 시험한다. 앱에 실제로 연결(모듈 주입)하는 일은 U2·U3 첫 제출 범위가 통합 브랜치에 합쳐진 뒤 그 인터페이스·가짜 구현을 가져다 한다. 운영 코드에 U4 쪽 임시 구현이 남지 않는다.
B. U4가 api 안에 임시 구현(조각 나누기 안 함, 작업 등록은 로그만, 하루 횟수 항상 허용, 동의 항상 있음)을 두고 앱을 먼저 돌린 뒤 U2·U3이 합쳐지면 바꾼다 — 화면까지 먼저 돌려 볼 수 있지만, 동의·한도를 건너뛰는 코드가 운영 코드에 잠시 있게 되어(보안 점검 대상) 바꾸는 변경이 하나 더 든다.
X. Other (please specify)

[Answer]: A

## Q3. [설계] 10월 링크 발급 규칙 가운데 발행에 이어받을 것

10월 링크 발급에는 ① 같은 요청 재전송을 막는 `Idempotency-Key`(멱등 기록 표가 `share_link`를 외래 키로 가리킴), ② 유효 링크 5개 한도(`LINK_LIMIT_REACHED`), ③ 같은 제목 유효 링크 금지(`LINK_TITLE_CONFLICT`), ④ 회원별 발급 빈도 1분 10회(`429 RATE_LIMITED`)가 있다. 12월 요구사항·계약은 이 넷을 언급하지 않고, C-07 `publication` 표에는 멱등 기록과 묶을 짝이 없다. 발행 한 번은 하루 실행 횟수 1회를 쓴다(C-03).

A. ④ 발급 빈도만 이어받는다(10월 코드 재사용). ①②③은 두지 않는다. 두 번 누르면 발행본이 둘 생기고 하루 횟수를 2회 쓰는 것은 에러 대응 최소선 6의 한계로 적는다. web은 발행 중 버튼을 막는다.
B. ①까지 이어받는다 — 재전송 중복 발행을 막지만 공용 `idempotency_record` 표에 발행본을 가리키는 칸·외래 키를 더해야 해 공용 표 변경(팀장 협의)이 든다.
C. ①~④ 모두 이어받는다 — 10월 동작과 같지만 위 공용 표 변경에 더해 요구사항 근거 없는 한도·제목 규칙을 새 발행본에 들인다.
X. Other (please specify)

[Answer]: X. 재전송으로 같은 발행본이 중복 생성되지 않도록 하는 방향을 권고안으로 설계해 주세요. 구현 방식과 공용 idempotency_record 표 변경은 관련 담당·팀장과 합의 후 확정합니다. 유효 링크 5개 한도·같은 제목 금지·발급 빈도 제한은 12월 정책 확인 전까지 확정하지 말고 미결 사항으로 남겨 주세요.

> 정정 전 기록(2026-10-27). 문서 대조 전에 받은 답이라 사용자 요청으로 확정하지 않았다. **Q7의 답이 이 답을 대체한다.**

## Q4. [설계] 10월 공유 링크 표·화면·경로를 지우는 시점

계약 C-12 공통 전제는 10월 공유 링크 열람(공개 프로필·공개 Catch 목록·Catch 상세)을 U4가 발행본 경로로 바꾸면서 없앤다고 했다. 10월 데이터는 12월 전에 모두 초기화한다(요구사항 C04). 10월 `share_link` 표는 공용 `idempotency_record`가 외래 키로 가리킨다.

A. U4 본체(발행·열람이 동작하는 변경)에서 10월 `share-links` 발급·목록·중지 API와 화면, 받은 사람 Catch 목록·상세 경로를 지우고 새 경로로 바꾼다. `share_link` 표와 그 외래 키 삭제는 공용 표를 건드리므로 팀장에게 맡기고 U4는 표를 그대로 둔다.
B. A와 같되 `share_link` 표·`idempotency_record`의 외래 키 삭제 마이그레이션도 U4 본체에서 한다 — 한 번에 정리되지만 공용 표 변경이 U4에 들어간다.
C. 10월 경로·화면을 남겨 두고 새 발행본 경로를 나란히 둔다 — 이번 Unit은 작아지지만 두 링크 정책이 함께 돌아 C-12·FR4.1과 어긋난다.
X. Other (please specify)

[Answer]: X. U4는 기존 공유 링크 API·화면·경로를 새 발행 흐름으로 전환하는 범위로 설계합니다. 기존 경로 제거 시점은 새 흐름의 연결 검증과 관련 Unit 영향 확인 후 합의합니다. share_link 표와 idempotency_record 외래 키 정리는 관련 담당·팀장과 작업 주체 및 데이터 처리 방안을 합의한 뒤 진행하며, 이번 기능 설계에서는 미결 사항으로 명시해 주세요.

> 정정 전 기록(2026-10-27). 문서 대조 전에 받은 답이라 사용자 요청으로 확정하지 않았다. **Q8의 답이 이 답을 대체한다.**

## Q5. [설계] 입력·발행 상한 값

상한 값은 개발 담당 결정이다(요구사항 「개발 담당 결정」, C-13 "길이 상한 값은 U4 기능 설계"). 발행본은 기본 요약·질의응답의 AI 입력 상한 안에 들어야 한다(U2·U5가 정할 값). 10월 링크 제목은 1~50자다. 아래 값은 U4 안의 API 검증 값이라 계약을 바꾸지 않는다.

A. Catch 설명 0~4,000자, 텍스트 자료 제목 1~100자·본문 1~20,000자, 발행본 제목 1~50자(10월 그대로), 발행 항목 1~20개, 발행본 전체 글(사본 글자 합) 60,000자 이하. 넘으면 저장·발행하지 않고 이유를 안내한다(`400 VALIDATION_FAILED`). 전체 글 60,000자는 임시값이며, U2·U5가 정할 AI 입력 상한에 맞추는 일은 '담당 확인 필요'로 남긴다.
B. 항목 수·전체 글 상한 없이 필드 길이만 둔다 — 단순하지만 큰 발행본이 AI 입력 상한을 넘으면 요약·질의응답이 실패한다.
C. 값을 적어 주세요(설명·자료 제목·자료 본문·발행본 제목·항목 수·전체 글).
X. Other (please specify)

[Answer]: A. 확정: 입력과 발행 크기에 상한을 두고, 초과하면 저장·발행을 거부하며 이유를 안내합니다. 글자 수 계산 방식과 전체 합산 대상을 기능 설계에 명시합니다.
초기 설계값: Catch 설명 0~4,000자, 텍스트 자료 제목 1~100자·본문 1~20,000자, 발행본 제목 1~50자, 발행 항목 1~20개, 전체 사본 글자 합 60,000자 이하로 둡니다. 이는 승인 문서에 적힌 고정값이 아니라 U4 담당이 제안하는 설계값입니다.
회의·연결 확인 후 조정: 관련 담당과 AI 입력 처리 한도를 확인하고, 특히 전체 60,000자 상한을 맞춰 조정합니다. 현재 값으로 AI 처리가 가능하다고 검증된 것으로 기록하지 않습니다.

## Q6. [시험] U4의 '최소 연결 첫 결과'로 보일 것

팀 관행은 각 Unit이 처음 실제로 연결될 때 '최소 연결 첫 결과'를 한 번 승인받고, 합성 연결 성공을 실제 처리 성공으로 보고하지 않는다(team.md). B4의 보일 결과는 "작성자가 Catch와 텍스트 자료를 골라 발행하고 받은 사람이 링크로 여는 흐름"이고, 완료 기준은 U3과 실제 연결 확인이다.

A. 개발 서버(또는 로컬 전체 실행)에서 실제 로그인 회원이 Catch 1개와 텍스트 자료 1개를 골라 발행하고, 비로그인 브라우저가 그 링크를 열어 사본을 보는 한 번. 이때 U2(하루 횟수·동의·작업 등록)는 실제 구현, U3 조각 나누기는 그 시점에 합쳐진 것(가짜면 가짜라고 적음)을 쓴다. U3 실제 연결은 U3 구현 뒤 완료 확인 때 따로 본다. 확인 시점·환경(11/13 개발 서버 여부)과 그때 U2·U3가 실제인지는 '담당 확인 필요'로 남긴다.
B. U3 실제 조각 나누기가 합쳐진 뒤에만 한 번 본다 — 한 번에 끝나지만 U3을 기다려 첫 결과가 늦어진다.
X. Other (please specify)

[Answer]: A. 확정: 로그인한 작성자가 Catch 1개와 텍스트 자료 1개를 골라 발행하고, 발행 직후 고정 사본을 확인한 뒤 비로그인 브라우저에서 링크로 같은 내용을 보는 것을 첫 확인 시나리오로 합니다.
사전 확인: U3 실제 구현이 준비되기 전에는 시험 환경에서 계약에 따른 가짜 구현으로 흐름을 확인할 수 있습니다. 이를 ‘합성 연결을 포함한 사전 확인’으로 기록하고 실제 연결 성공으로 보고하지 않습니다.
실제 연결 기준: U2·U3 실제 구현으로 연결한 결과를 근거로 실제 연결 첫 결과의 승인을 받습니다. U4 완료에는 B4에 명시된 U3 실제 연결과 나머지 완료 기준 확인이 필요합니다.
회의 후 확인: U2·U3 실제 구현 제공 시점과 통합 확인 일정을 맞춥니다.

## Q7. [설계] (Q3 정정) 10월 링크 발급 규칙 가운데 발행에 이어받을 것

Q3의 답을 대체한다(2026-10-27 사용자 요청, Q3 답은 정정 전 기록으로 보존). 근거: 12월 요구사항·계약에는 ① 재전송 중복 방지(`Idempotency-Key`) ② 유효 링크 5개 한도 ③ 같은 제목 금지 ④ 발급 빈도 1분 10회가 없다. 계약 「에러 대응 최소선 6」은 동시 요청·재전송 같은 드문 겹침을 따로 막지 않고, 피해가 하루 횟수 1회나 생성 1회 중복이면 한계로 적는다고 정했다. ①을 넣으려면 공용 `idempotency_record` 표 변경이 필요하다. ADR-001은 "링크 규칙은 재사용"이라고만 적었다.

## Q9. [계약] 작성자 화면이 색인 상태를 읽는 방법

요약 확인 뒤 산출물 작성 전에 계약을 대조하다 찾은 빈틈이다. 색인 실패일 때만 작성자에게 [검색 다시 준비]를 보이려면(ADR-007, 컴포넌트 목록 Publication) U4가 발행본의 색인 상태를 알아야 한다. 색인 상태를 읽는 인터페이스는 C-09 `PublishedSearch.getIndexState`(U3 제공)인데, 계약의 소비자 목록은 U5·U10뿐이다. A. C-09 `getIndexState`를 모양 그대로 U4도 쓴다. 이름·자료형·의미는 바뀌지 않고 소비자만 늘어나는 변경이며, 계약 문서 수정은 제공 Unit(U3)이 하므로 '담당 확인 필요(U3 담당)'로 남기고 설계는 이 전제로 쓴다.

C. U4가 `publication_index` 표를 직접 읽는다 — 계약 변경 없이 되지만 U3 소유 표를 U4가 직접 쿼리해 소유 경계(Contract ownership rules)와 어긋난다.
