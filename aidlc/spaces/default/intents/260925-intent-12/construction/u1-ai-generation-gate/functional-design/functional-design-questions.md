## Q1. [설계] U1이 끝까지 돌리는 범위

계약 C-01의 `AiGenerationGate`에는 `generate`·`generateStream`, 기계 대조·버림(U2), 숨긴 지시 방어·역량 평가 표현 금지 공통 문구, 입력 상한 오류(`AiInputTooLarge`)가 있다. U1은 "공용 계약의 최소 부분"만 맡으므로, 어디까지를 U1에서 실제 호출로 돌릴지 정한다.

A. `generate()` 하나만: 줄 넘기기 → Claude 인용 호출 → 항목 묶기 → 인용 보존·원문 위치 계산 → 거부 사례 처리. 기계 대조·버림, `generateStream`, 공통 방어 문구, 입력 상한은 U2가 한다. 반환은 C-01 `GatedOutput` 모양 그대로(버림이 없으니 `droppedCount`는 0).
B. A에 공통 방어 문구(숨긴 지시 방어·역량 평가 표현 금지)까지 더한다 — 실제 호출을 사전 시험과 비슷한 지시 조건에서 볼 수 있다. 지시문 정리만큼 공수가 조금 는다.
C. A에 `generateStream`까지 더한다 — U5가 SSE를 붙일 자리를 먼저 확인한다. 스트리밍 응답의 인용 처리가 더해져 공수가 크다.
X. Other (please specify)

[Answer]: A

## Q2. [설계] 인용 단위(줄)를 나누는 규칙을 어디서 정하나

계약 C-01은 "줄 구분 문자와 줄 번호를 매기는 방식은 U2 기능 설계에서 정한다"고 적었지만, 실제로 줄을 먼저 넘기는 것은 U1이다. 이 규칙이 원문 위치(`charStart`·`charEnd`) 계산의 기준이 된다.

A. U1에서 정하고 U2는 그대로 쓴다: 줄바꿈(`\n`)으로만 나누고, 줄 끝의 `\r`·`\n`은 줄 글자에 넣지 않는다. 빈 줄(공백만 있는 줄 포함)은 넘기지 않되 다른 줄의 위치는 원문 기준 그대로 둔다.
B. U1은 A 규칙을 임시로 쓰고 U2 기능 설계에서 다시 정한다 — 계약 문장을 그대로 지키지만, U2에서 바뀌면 U1의 위치 계산과 시험을 다시 고친다.
X. Other (please specify)

[Answer]: A

## Q3. [설계] Claude 응답을 항목으로 묶는 기준

인용 기능 호출에서는 구조화된 출력을 함께 쓸 수 없어, Claude 응답은 인용이 붙은 글 조각과 안 붙은 글 조각이 이어진 형태로 온다. 이것을 `GatedItem` 하나하나로 나누는 기준이 관문의 "응답을 항목으로 묶기"다.

A. 지시문으로 "항목마다 한 문단, 문단 사이에 빈 줄"을 시키고 서비스는 빈 줄 기준으로 나눈다. 한 문단 안 조각들의 인용을 모두 그 항목의 인용으로 모으고, 인용이 하나도 없는 문단은 `AI_INTERPRETATION`으로 둔다.
B. 인용이 붙은 글 조각 하나를 항목 하나로 본다 — 지시문이 필요 없지만 한 문장이 여러 항목으로 쪼개질 수 있고, 인용 없는 이음 조각이 따로 남는다.
C. 사전 시험(2026-10-24)에서 쓴 방식을 그대로 쓴다 — 어떤 방식이었는지 적어 주세요.
X. Other (please specify)

[Answer]: C. 10/24 사전 시험 방식. 지시문으로 "한 줄에 한 항목, 줄 맨 앞은 '- '로 시작하고, 항목마다 사실 하나만 쓴다. 머리말·맺음말은 쓰지 않는다"를 준다. 서버는 응답에서 '- '로 시작하는 줄 하나를 항목 하나로 보고, 줄이 끝났을 때 그 줄 안 조각들의 인용을 모아 항목 인용으로 한다. 인용이 없는 줄은 AI_INTERPRETATION이다. '- '로 시작하지 않는 글(머리말, 섞여 나온 속 생각 등)은 항목으로 내보내지 않는다. 사전 시험 결과: 인용이 두 항목에 걸친 경우 0/215, 도구는 .local-handoffs/citation-pretest-tools/run_test.py.

## Q4. [제품] "거부 사례 처리"로 확인할 사례

관문 네 번째인 "거부 사례 처리"가 어떤 사례를 뜻하는지 상류 문서에 적혀 있지 않다. 납품 계획의 보일 결과는 "시험 자료 하나로 인용이 붙은 항목과 거부 사례가 나오는 실제 호출 한 번"이다.

A. 자료에 없는 것을 물으면(사전 시험 함정의 "자료에 없는 기술") 모델이 지어내지 않고 "이번 자료에서 찾지 못함"을 인용 없는 항목으로 답하며, 서비스는 그것을 `AI_INTERPRETATION`으로 둔다(버릴지는 U2 판정). U1은 이 한 사례를 실제 호출로 본다.
B. A에 더해 Claude API 쪽 거부(중단 이유가 거부인 응답, 빈 응답)를 `AiProviderError`로 구분해 처리한다 — 실제 호출로는 만들기 어려워 기록한 응답으로 시험한다. 공수가 조금 는다.
C. 사전 시험 함정 4종(자료에 없는 기술, 비교·계획만 한 것, 남이 한 일, 표기 차이)을 모두 U1 실제 호출로 다시 본다 — 버림 규칙(U2) 없이 보면 합격 판정 기준이 모호하고 공수가 크다.
X. Other (please specify)

[Answer]: X. 사전 시험(10/24)에서 '거부 사례 처리'를 ① 출력 상한에서 잘린 응답 ② 거절·빈 응답 ③ 자료 속 숨긴 지시 ④ 인용과 구조화된 출력의 400 거절로 풀어 확인했다. U1은 이 가운데 ①②만 맡는다.① 출력 상한에서 잘려 끝난 응답(중단 이유 max_tokens)은 마지막의 끝나지 않은 항목만 버리고 나머지 항목은 낸다. 출력 상한을 낮춘 실제 호출로 확인하며, 이 호출을 '인용 붙은 항목과 거부 사례가 나오는 실제 호출 한 번'으로 삼는다.② 중단 이유가 refusal이거나 항목이 하나도 없는 응답은 AiProviderError로 구분한다. 실제로 만들기 어려우므로 기록한 응답으로 시험한다.③ 자료 속 숨긴 지시와 검사에 걸린 항목 버리기는 버림 규칙과 함께 U2가 맡는다. ④는 구조화된 출력을 쓰지 않으므로 확인하지 않는다.

## Q5. [시험] 실제 Claude 호출을 확인하는 방법

U1 완료 기준은 "실제 Claude 인용 호출로 관문 네 가지가 끝까지 돈다"와 '최소 연결 첫 결과' 승인이다. Claude API 키는 팀장이 준비한다(납품 계획 외부 의존).

A. 기록한 Claude 응답으로 도는 일반 시험(줄 나누기·항목 묶기·위치 계산·거부 사례)을 api 시험 묶음에 두고, 실제 호출 시험은 같은 묶음에 두되 API 키 환경변수가 있을 때만 돈다(CI에서는 건너뜀). 실제 호출 결과는 팀장이 한 번 돌려 '최소 연결 첫 결과' 승인 자료로 쓴다(키·사용자 자료는 기록에 남기지 않음).
B. 실제 호출은 시험 묶음 밖의 일회 실행 스크립트로 돌리고 결과를 PR에 붙인다 — 시험 묶음은 기록한 응답만 쓴다. 나중에 다시 돌리기가 A보다 번거롭다.
C. CI에서도 실제 호출 시험을 돈다 — CI 비밀값 설정(팀장 공유 CI 변경)과 호출 비용이 매번 든다.

- 줄 규칙(U1에서 정하고 U2가 그대로 씀): `\n`으로만 나누고 줄 끝 `\r`·`\n`은 줄 글자에서 뺀다. 빈 줄(공백만 있는 줄 포함)은 넘기지 않고, 다른 줄의 위치는 원문 기준(UTF-16) 그대로 둔다. 근거 하나(`AiSource`)는 인용 문서 하나이며 출처 종류 설명은 문서의 context에 둔다(사전 시험과 같은 방식).
- 항목 묶기(사전 시험 방식): 지시문으로 "한 줄에 한 항목, 줄 맨 앞은 '- ', 항목마다 사실 하나, 머리말·맺음말 없음"을 준다. 응답에서 '- '로 시작하는 줄 하나가 항목 하나이고, 줄 안 조각들의 인용을 모아 항목 인용으로 한다. 인용 없는 줄은 `AI_INTERPRETATION`, '- '로 시작하지 않는 글은 내보내지 않는다.
