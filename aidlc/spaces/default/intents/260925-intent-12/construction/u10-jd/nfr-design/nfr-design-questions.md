# U10 비기능 설계 작성 전 확인

대상은 u10-jd의 NFR Design이다. 비기능 요구사항은 2026-11-02 사용자 승인을 받았고 출처 링크 수정·R-01 해소·승인 기록과 함께 커밋 `3f64a39`에 보존했다. 승인된 28개 상세 요구사항을 구체적인 설계 책임과 처리 경계에 연결한다. 새로운 제품 정책이나 성능·가동률·복구 목표는 정하지 않는다.

## 기존 결정에서 도출한 설계 방향

기존 답을 다시 묻지 않는다. 기능 설계·비기능 요구사항·공용 계약으로 정해진 사항을 다음 설계 문서의 기준으로 사용한다. 새로운 정책 선택이 필요한 미결은 확인되지 않았다.

| 영역 | 구체화할 설계 | 요구사항·근거 |
|---|---|---|
| 논리 책임 | JdManagement가 JD 원본과 CRUD를, JdSummary가 접수·실행 사본·요구사항 결과·조회 상태를 소유한다. 내부의 입력 검사·접수·처리기·조회·저장 책임을 구분하되 별도 서비스나 배포 단위로 나누지 않는다. web의 JD 관리 페이지와 JdSummaryPanel은 기존 화면 구성을 따른다. | 도메인 컴포넌트, 기능 명세 §1·§3·§6, 기술 결정 |
| 입력과 조회 | 서버에서 UTF-16 저장/실행 상한을 검사하고 실제 검색 반환을 생성 직전에 공용 계산으로 다시 검사한다. 목록은 소유자 조건과 cursor를 적용해 20개씩 요약 필드만 조회한다. 목록·상세·접수 조회에 필요한 검색 조건과 정렬을 저장 책임에 명시하며 새 결과 캐시·폴링·SSE를 만들지 않는다. | NFR4.1·NFR4.2·NFR4.4·NFR4.7, 기능 명세 §5·§9 |
| 접수·큐 경계 | 인증·C-10 접근·본인 JD·입력·동의·색인 준비를 확인한 후, JD 소유/판본 재확인과 C-03 차감·실행·사본·PENDING 결과 저장을 한 트랜잭션으로 묶는다. 커밋 뒤 C-02에 runId만 등록한다. 외부 검색·생성 호출을 DB 저장 트랜잭션 안에 넣지 않는다. | NFR2.1·NFR4.6·NFR6.4, C-02·C-03·C-04, 기능 명세 §4·§6 |
| 처리·실패 경계 | 요구사항별 검색→생성을 원문 순서대로 최대 한 번씩 수행한다. 한 행의 실패는 다음 행 처리를 막지 않으며 전체 시한과 처리기 오류는 승인된 상태 전이를 따른다. 자동 재시도·중간 재개·새 circuit breaker·실패 환급·합성 성공 대체를 추가하지 않는다. | NFR4.3·NFR4.5·NFR6.5·NFR7.2·NFR7.3, C-01·C-02·C-09 |
| 시한·삭제 무결성 | 접수부터 20분 시한을 처리·저장 전에 확인하고 상태 조회에서는 PENDING에만 조건부 실패 반영한다. 결과 저장 시 부모 존재·PENDING·시한 전 조건을 트랜잭션과 외래 키로 지킨다. JD/회원/발행본 삭제의 연쇄 범위와 타인 JD 원본 보존을 구분한다. 새 백업·복구·자동 삭제 정책은 없다. | NFR5.1~NFR5.3·NFR4.3, 기능 명세 §6~§8, C-06 |
| 접근·화면 보호 | 기존 회원 Guard와 요청별 C-10 판정 및 실행자·발행본 일치 검사를 재사용한다. U4의 getGrant/onAccessLost/showEvidence와 U2 동의 창을 소비한다. 인증·접근·선택 변경 시 화면 상태를 정리하고 이전 요청 응답을 버린다. 출력은 텍스트로 표시하며 공용 인용 위치·라벨을 유지한다. | NFR1.1~NFR1.4·NFR7.1, C-10~C-12, 화면 설계 |
| 외부 AI·비밀값 | C-01 HAIKU·C-09 검색만 소비한다. 원문을 신뢰하지 않는 자료로 전달하고 공용 검사·기존 외부 호출 제한을 우회하지 않는다. 기존 전송·비밀값·배포 보호 경계를 명시하되 암호화 표준·인프라 설정·공용 SDK 정책을 새로 선정하지 않는다. | NFR2.1~NFR2.4, 기술 결정, 보안 점검 |
| 로그·검증 연결 | 기존 로거에 접수·큐 등록·처리·실제 완료·실패를 구별하는 안전한 필드를 배정한다. runId와 고정 분류만 연결에 사용하고 원문·토큰·grant·전체 오류 객체는 제외한다. 새 trace 전파 계약·관제·경보·SLI/SLO를 만들지 않는다. 합성·실제 연결·실패·미실행은 기존 확인 결과 표에서 구분한다. | NFR6.1~NFR6.3, 코딩 절차 |
| 근거 품질·외부 의존 | JD 두 방식 비교 기록과 기계 검사/의미적 품질의 구분을 유지한다. 실제 분석·실측 #450과 실제 C-10/C-11 연결 #416의 책임을 바꾸지 않는다. 공용 계약 변경이 필요한 경우 별도 요청하고 U10에서 먼저 변경하지 않는다. | NFR3.1·NFR3.2·NFR6.3, 기능 명세 §10·§11 |

## 일관성과 범위 점검

- 기존 기능 설계 R-01의 개별 생성 시간 초과는 GENERATION_FAILED와 “이 요구사항을 처리하지 못했습니다.”로 유지한다. 전체 시한 초과는 DEADLINE_EXCEEDED이며 정상 빈 결과·일부 실패와 구별한다.
- 소유자 조건과 발행본 참조는 서로 다른 제약이다. 실행자는 JD 소유자와 같아야 하지만 발행본 작성자와 같을 필요는 없다.
- 20분은 종료 판정 시한이며 성능 보장이 아니다. 조회 기반 만료 판정을 정각 실행 스케줄러로 확장하지 않는다.
- 단계 템플릿에 나열된 캐시·분산 처리·재시도·암호화 선정·자동 확장·백업·대시보드는 예시다. 승인된 요구에 없는 장치를 설계에 추가하지 않는다.
- 성능·보안·확장성·신뢰성·관측성 설계와 논리 컴포넌트 문서 6개 및 추적표 1개를 작성한다. 28개 NFRx.y 각각을 구체적인 설계 위치에 연결한다. 실행 가능한 구현 코드는 작성하지 않는다.
- 작성 후 공식 검토 결과를 설명하고 비기능 설계 단계 승인을 별도로 기다린다. 다음 경로가 Code Generation이더라도 구현 계획·필요한 승인 절차를 생략하거나 이번 확인을 구현 승인·U10 완료로 취급하지 않는다.
