# U10 성능 요구사항

대상은 본인 JD 관리와 발행본 기반 JD 요약이다. 승인된 기능 설계와 작성 전 확인을 상세 요구사항으로 옮긴다. 아래 기준은 구현 후 확인할 조건이며 측정 결과가 아니다.

## 범위와 성능 기준

상류 NFR4는 소수 외부 사용자의 시연 규모를 정하고 새로운 처리 시간·가동률·복구 수치를 금지한다. 따라서 응답 지연 백분위, 초당 처리량, 동시 사용자 수, CPU·메모리 사용률 합격선을 만들지 않는다. 아래 숫자는 기능 설계의 입력·호출 한도와 종료 판정 조건이다.

| ID | 요구사항 | 확인할 결과 | 근거 |
|---|---|---|---|
| NFR4.1 | JD 제목 1~200자·본문 1~20,000자, 공백만인 값 거부를 유지한다. 실행은 비어 있지 않은 원문 줄 1~20개·각 2,000자 이내다. 길이는 UTF-16 코드 단위다. | 저장 상한과 실행 상한을 구분하고 초과 실행은 실행 생성·횟수 차감 전에 거부한다. 입력을 잘라 저장하거나 일부 줄만 실행하지 않는다. | 기능 명세 §3~§5, BR1.2·BR2.1 |
| NFR4.2 | 요구사항 순서대로 C-09 검색 최대 6개 조각을 받고 C-01 HAIKU 생성을 최대 한 번 호출한다. 조각 최대 1,000자 기준 정상 모델 입력 상한은 8,000자다. | 실제 sources.text 길이 합과 userText 길이를 공용 80,000자 한도에 대조한다. instruction·publicationText는 계산에서 제외한다. 검색 반환이 6개·1,000자 약속을 어기면 CONTRACT_INVALID로 실패시키며 생성하지 않는다. 실제 공용 한도 초과는 INPUT_TOO_LARGE다. | 기능 명세 §5·§6, BR3.1·BR3.2, C-01·C-09 |
| NFR4.3 | 전체 시한은 접수 시각부터 큐 대기를 포함한 20분이다. 처리·저장 전과 상태 조회에서 기존 시한 규칙을 적용한다. | 시한 이후 PENDING을 실패로 확정하며 늦은 결과를 저장하지 않는다. 20분 안의 완료를 약속하거나 API 응답 시간 목표로 쓰지 않는다. | 기능 명세 §6·§7, BR4.1, C-02 |
| NFR4.4 | JD 목록·본인 실행 목록은 최신순 20개씩 cursor로 조회하고, 실행 결과 확인은 목록 재열람·사용자 새로고침으로 한다. | 목록은 요약 필드만 반환하고 원문은 권한을 통과한 상세에서 읽는다. U10에 자동 폴링·SSE·병렬 생성 경로를 추가하지 않는다. | 기능 명세 §8·§9, 화면 설계 |

## 확인 범위와 측정의 한계

상한 경계, 실제 생성 입력 계산, 순차 처리, 시한 실패와 재열람은 기능 명세 §11의 기존 확인 시나리오에 연결한다. 코드·부하 시험은 이번 문서 단계에서 실행하지 않았다. 향후 실행 기록에 소요 시간을 남겨도 새 합격선을 만들지 않는다.

상류의 질의응답 SSE는 U5, 저장소 약 500커밋 실측은 U7·실측 작업 #450의 범위다. U10에 부하 시험·성능 벤치마크 작업을 새로 추가하지 않으며 합성 제공자의 빠른 응답을 실제 생성 성능으로 보고하지 않는다.

publicationText는 모델 입력 계산에서 빠지지만 공용 게이트의 대조에는 쓰인다. 그 처리 비용이 무제한이라는 뜻이 아니며 발행본 크기는 제공 Unit의 기존 제한을 따른다.
