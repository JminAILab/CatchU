# U10 신뢰성·자료 수명 요구사항

접수와 완료를 구분하고 실패를 숨기지 않으며, 삭제한 자료가 다시 생기지 않게 하는 기존 조건을 정리한다. 새 가동률·RTO·RPO·복구 시한·백업 정책을 정하지 않는다.

|---|---|---|---|
| NFR6.4 | 공용 횟수 차감·실행·입력 사본·PENDING 결과 행은 같은 트랜잭션으로 저장하고 커밋 후 큐에 등록한다. | 저장 실패면 함께 롤백한다. 202는 접수 성공이며 생성 완료가 아니다. ENQUEUE_FAILED는 접수된 PENDING을 유지하다 상태 조회에서 NFR4.3 시한으로 실패 확정한다. | 기능 명세 §4, C-02·C-03, 공통 에러 대응 최소선 |
| NFR6.5 | 자동 재시도·실패 복구·중간 이어하기 없이 사람의 새 실행으로 다시 처리한다. | 새 실행은 접근·동의·입력·색인·한도 검사를 다시 하고 새 runId와 사본을 만든다. 이미 차감한 실행은 실패해도 환급하지 않는다. 저장 불능을 완료로 보고하지 않는다. | 기능 명세 §4·§6·§8, BR2.4·BR4.1 |
| NFR7.2 | 정상 빈 결과와 처리 실패를 구분하고 R-01의 코드·안내 대응을 유지한다. | 정상 빈 출력은 DONE/EMPTY다. 개별 생성 호출 시간 초과·생성 제공자 오류는 FAILED/GENERATION_FAILED와 “이 요구사항을 처리하지 못했습니다.”를 최초 조회·재열람에 동일하게 사용한다. 검색 오류는 SEARCH_FAILED다. 전체 시한 초과는 DEADLINE_EXCEEDED와 “전체 처리 시한이 지나 완료하지 못했습니다.”로 구분한다. | 기능 명세 §7·§11, BR3.3·BR4.1, 기능 설계 R-01 재검토 |
| NFR7.3 | 일부 성공·빈 결과·일부 실패의 조합에서도 원문 순서와 이미 저장한 정상 결과를 보존한다. | 전 행 종료 후 하나라도 DONE이면 실행 DONE이고 전부 실패면 FAILED/ALL_REQUIREMENTS_FAILED다. 전체 시한은 실행 FAILED와 미처리 행의 DEADLINE_EXCEEDED로 확정하되 기존 DONE 결과는 남긴다. 처리기 전체 오류는 PROCESSING_FAILED다. | 기능 명세 §6·§7, BR3.4 |

시한은 조회 시 판정·조건부 저장하므로 별도 스케줄러가 정각에 모든 행을 바꾸는 보장을 하지 않는다. DONE/FAILED를 늦은 응답으로 되돌리지 않는다. 저장·접근 오류 안내와 JD 저장 실패 때 입력 보존은 기능·화면 설계를 유지한다.

## 확인 범위와 운영 한계

기능 명세 §11의 저장·일부 실패·시한·부모 삭제 확인과 상류의 핵심 보호 흐름에 연결한다. 삭제 무결성은 설계와 제약 조건에서 확인하며 동시 요청·재전송·늦은 결과의 기능별 세부 경쟁 시험 묶음을 새로 만들지 않는다(NFR6).

DB·큐·외부 제공자 장애 시 무중단 처리나 자동 복구를 약속하지 않는다. 새 복제·백업·재해 복구·dead-letter·재처리 체계를 요구하지 않는다. 기존 배포·공용 기반의 운영 정책을 U10 문서로 변경하지 않는다.
