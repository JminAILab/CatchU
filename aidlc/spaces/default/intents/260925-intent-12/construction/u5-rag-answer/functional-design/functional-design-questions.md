# U5 RAG 응답 — 기능 설계 질문

입력: [Unit 정의](../../../inception/units-generation/unit-of-work.md)의 U5, [스토리 대응](../../../inception/units-generation/unit-of-work-story-map.md)(US4.2, US6.2의 답 생성·SSE, US19.3), [사용자 스토리](../../../inception/user-stories/stories.md)의 US4.2·US6.2·US19.3, [요구사항](../../../inception/requirements-analysis/requirements.md)의 FR2.7·FR6.2·FR6.3·FR6.4·FR6.6·FR6.8·FR6.9·NFR3·NFR4와 「개발 담당 결정」, [컴포넌트 목록](../../../inception/domain-design/components.md)의 QnA·BaseSummary, [계약 요약](../../../inception/contract-design/contract-summary.md)의 C-01·C-02·C-03·C-06·C-09·C-10·C-11·C-12, [납품 계획](../../../inception/delivery-planning/bolt-plan.md)의 B8, U2 기능 설계의 게이트 규칙(BR3.1 입력 상한 80,000자, BR3.7 남은 항목 0개는 호출 Unit이 처리).

이미 정해진 것(다시 묻지 않음): 질의응답은 로그인 없이 `POST /v1/public/links/{token}/questions`로 받고 큐 없이 SSE(`item`·`done`·`error`)로 검사 통과 항목만 내보낸다(C-12, FR6.2). 질문마다 C-10 `resolveForRecipient`로 링크 조건을, C-09 `getIndexState`로 색인 상태를 다시 보고, 색인이 준비 전·실패면 `409 INDEX_NOT_READY`다. 찾는 범위는 C-09 의미 검색 결과뿐이고 AI 설명 초안은 들어가지 않는다(FR6.4). 대화는 서버에 저장하지 않고, 브라우저가 보낸 앞 대화는 신뢰할 수 없는 입력이다(FR6.2). 링크당 하루 질문 횟수는 Redis의 발행본ID+한국 시간 날짜 키로 세고, Redis 장애면 통과시키고 기록만 남긴다(429 `QUESTION_LIMIT_REACHED`). 기본 요약은 발행 뒤 `BASE_SUMMARY` 처리기로 JD 없이 만들고, 행 생성·시한 판정·늦은 결과 버림은 C-02 `row-creation`·`late-result` 그대로다. [다시 만들기]는 작성자만, 접수 때 하루 실행 제한(C-03)을 센다. 작성자 경로는 C-10 `resolveForOwner`를 먼저 부른다(C-11). 모델은 Haiku 5.5이고 NFR3 조정 때 질의응답만 Sonnet으로 바꿀 수 있다(FR6.9).

## Q1. [설계] 질문을 앞 대화에 맞게 다시 쓰는 방법

AC6.2.1은 "앞 대화에 맞게 질문을 다시 쓰고 관련 조각을 찾아 답한다"를 요구한다. 그런데 AI 생성 공통 계약(C-01)의 요청에는 질문 한 줄(`userText`)만 있고 앞 대화를 넣는 칸이 없다. "그건 왜 그렇게 했어?" 같은 질문은 앞 대화 없이는 검색어가 되지 않는다.

A. 앞 대화가 있을 때만 Haiku 5.5를 한 번 더 불러 "앞 대화를 보지 않아도 뜻이 통하는 한 문장 질문"으로 다시 쓰게 한다. 인용 기능은 쓰지 않고 결과는 화면에 보이지 않으며, 다시 쓴 질문을 검색어와 답 생성의 `userText`로 쓴다. 첫 질문은 다시 쓰지 않는다. 이 호출이 실패하면 그 질문은 SSE `error`로 끝낸다(자동 재시도 없음). AiGeneration의 Claude 연결 설정(API 키·모델)을 그대로 쓰는 U5 안의 작은 호출로 두고 게이트(C-01)는 고치지 않는다. 질문마다 짧은 호출 하나(약 1초)가 는다.
B. 모델을 부르지 않고 직전 사용자 질문 1~2개와 이번 질문을 이어 붙여 검색어로 쓴다 — 가장 가볍지만 지시어("그거", "왜")를 풀지 못해 AC6.2.1의 "다시 쓴다"를 약하게만 채운다.
C. 다시 쓰기 대신 C-01 요청에 앞 대화 칸을 더하는 계약 수정 PR을 내고 답 생성에 대화를 함께 넣는다 — U2 게이트 변경·시험이 늘고, 검색어 문제는 따로 남는다.
X. Other (please specify)

[Answer]: A

## Q2. [설계] 질의응답 상한 값

## Q3. [설계] 기본 요약 처리 시한과 결과 확인 방식

기본 요약은 발행 뒤 백그라운드로 만들어진다. 처리 시한이 지나도록 `DONE`이 안 되면 상태를 읽을 때 `FAILED`로 확정되고 작성자에게 [다시 만들기]가 보인다(C-02). 결과를 화면이 스스로 다시 확인할지(폴링) 새로고침에 맡길지는 개발 담당 결정이다(FR6.8).

A. 처리 시한 10분(임베딩과 같음). 화면은 자동으로 다시 확인하지 않고, `PENDING`이면 "AI 요약을 만드는 중입니다. 새로고침하면 다시 확인합니다"를 보인다. 가장 단순하다.
B. 처리 시한 10분, `PENDING`인 동안 화면이 5초마다 상태를 다시 읽고 `DONE`·`FAILED`가 되거나 화면을 떠나면 멈춘다 — 발행 직후 연 사람도 새로고침 없이 요약을 보지만 패널의 타이머 코드와 시험이 는다.
C. 처리 시한 3분과 B의 자동 확인 — 실패를 빨리 알지만 큐가 잠깐 밀려도 실패가 된다.

## Q4. [설계] 기본 요약 [다시 만들기]의 반복 제한

[다시 만들기]는 하루 실행 제한(C-03)을 센다. 그 밖의 반복 제한은 개발 담당 결정이다. 만드는 중(`PENDING`)에 또 누르면 C-02의 한계대로 두 번 생성되고 마지막 저장이 남으며 하루 횟수도 두 번 쓴다.

A. 하루 실행 제한 말고는 두지 않는다. 화면은 `PENDING`인 동안 [다시 만들기] 버튼을 감추고, 서버는 거부하지 않는다(겹친 요청은 C-02 한계로 둔다). 가장 단순하다.
B. A에 더해 서버도 `PENDING`이고 마감 전이면 `409`로 거부한다 — 겹친 요청의 중복 생성·횟수 낭비를 막지만 거부 규칙과 시험이 하나 는다.
C. 발행본마다 하루 n회 같은 별도 제한을 둔다 — 새 집계와 시험이 든다.
X. Other (please specify)

[Answer]: A

## Q5. [설계] 근거 검사 뒤 남은 항목이 0개일 때

게이트는 근거가 맞지 않는 항목을 버리고, 남은 항목이 0개여도 그대로 돌려준다. 0개를 "결과 없음"으로 보일지와 "너무 적음"의 기준은 호출 Unit이 정한다(U2 BR3.7, 요구사항 「개발 담당 결정」).

A. 0개만 본다(따로 "너무 적음" 기준 없음). 기본 요약은 0개면 `FAILED`로 저장해 받은 사람에게는 요약 없음, 작성자에게는 [다시 만들기]를 보인다. 질의응답은 서버가 그대로 `done`을 보내고, 화면이 받은 항목이 0개면 "발행본에서 이 질문의 근거를 찾지 못했습니다"를 보인다.
B. 기본 요약도 `DONE`(빈 목록)으로 두고 "요약할 내용을 찾지 못했습니다"를 보인다. 질의응답은 A와 같다 — 성공으로 남지만 작성자가 실패와 구분하기 어렵다(다시 만들기는 성공 뒤에도 할 수 있다).
C. 1~2개처럼 적을 때도 빈 결과로 보는 기준을 둔다 — 기준값을 정하고 시험해야 한다.

## Q7. [검증] RAG 품질 평가의 지표와 방식

US19.3은 시연 발행본 1개, 질문 10개와 정답 근거로 검색 적중률과 근거 통과율을 스크립트로 한 번 재고, 사람이 근거가 문장을 뒷받침하는지 보며, "맞는데 버려진 항목"은 건수만 기록하라고 한다(AC19.3.1·AC19.3.2). 게이트는 버린 항목의 글을 돌려주지 않고 버린 수(`droppedCount`)만 준다.

A. api에 실제 Voyage·Claude로 손으로 한 번 돌리는 스크립트(CI 밖)를 둔다. 입력은 평가 파일(질문 10개, 질문마다 정답 근거 = 발행본 항목·필드 위치). 검색 적중률 = 정답 근거 위치와 겹치는 조각이 검색 결과 안에 하나라도 든 질문 수 / 10. 근거 통과율 = 통과 항목 수 / (통과 + 버린 항목 수). "맞는데 버려진 항목"은 버린 글을 볼 수 없으므로 버린 건수를 그대로 상한값으로 적고 하나하나 판정하지 않는다. 결과(질문·답 항목·인용 원문·버린 수)와 비어 있는 사람 판정 칸(남의 기여 오귀속 / 근거 비뒷받침)을 `docs/` 아래 한 파일에 남긴다.
B. A와 같되 U2 게이트에 평가용 선택 출력(버린 항목 글·이유)을 더하는 변경을 요청해, 사람이 버린 항목마다 맞는데 버려졌는지 판정한다 — "맞는데 버려진 건수"를 정확히 세지만 U2 게이트 변경·시험과 계약 문서 고침이 는다.
X. Other (please specify)

[Answer]: A로 한다. 측정은 U4 본체가 통합 브랜치에 합쳐진 뒤, 실제 발행 경로로 만든 시연 발행본 1개로 한 번 한다. 그 전에는 스크립트만 만들고 합성 자료로 끝까지 도는지만 확인한다(이것을 NFR3 측정으로 보지 않는다). 질문은 시연 발행본에서 근거가 될 글귀를 먼저 고르고, 그 글귀로 답할 수 있게 면접관 말투로 만든다. 정답 근거는 원문 글귀로만 적고(질문마다 여러 개 가능), 스크립트가 그 글귀가 나오는 곳을 발행본에서 모두 찾아 정답 위치로 삼는다(한 곳도 없으면 오류로 멈춘다). 그중 하나라도 검색 결과에 들면 적중으로 센다. 조각 8개 기준으로 적중하지 않은 질문은 검색된 조각의 위치를 결과에 남기고, 사람이 그 안에 다른 맞는 근거가 있었는지 판정 칸에 적는다(적중률 숫자는 고치지 않고 "다른 곳의 맞는 근거 n건"을 함께 적는다). 검색 적중률은 검색을 조각 12개로 한 번 부르고 앞 5·8·12개 기준으로 각각 적어, Q2의 검색 조각 수를 다시 볼지 정하는 참고로 쓴다(답 생성과 NFR3 판정은 조각 8개 그대로). 평가 입력(질문·정답 근거)과 답·인용 원문은 로컬 파일에만 두고, docs/에는 건수·위치·판정만 남긴다.

## Q8. [검증] JD 두 방식 비교(AC19.3.6)를 어떻게 할지

AC19.3.6은 같은 JD 하나로 "전체 넣기"와 "검색 기반" 두 방식의 결과를 나란히 기록만 하라고 한다. 스토리 대응은 US19.3 전체를 U5에 두었지만, JD 요약 기능 자체(검색 기반)는 U10이다.

A. U5 평가 스크립트가 JD 하나를 요구사항 줄로 나누고(U10의 나누기 함수가 있으면 그것을, 없으면 빈 줄을 뺀 줄 단위) 요구사항마다 게이트(`JD_SUMMARY`)를 두 번 부른다: 검색 기반(C-09 검색 조각)과 전체 넣기(그 발행본 조각 전부, 80,000자를 넘으면 그 방식은 "상한 초과"로 기록). 두 결과를 Q7의 평가 파일에 나란히 적기만 한다. U10 코드는 고치지 않는다.
B. U10 담당에게 JD 요약 실행에 "전체 넣기" 모드를 더해 달라고 요청한다 — 실제 기능 경로로 비교되지만 기능에 없는 모드가 생기고 U10 코드·시험이 는다.
C. AC19.3.6을 U10 기능 설계로 넘긴다(U5 추적에서는 N/A) — 스토리 대응과 어긋나 U10 담당과의 합의가 필요하다.
X. Other (please specify)

[Answer]: A로 한다. Q7 측정과 같은 때(U4 뒤) 한 번에 돌린다. U10이 그때 통합 브랜치에 합쳐져 있으면 U10의 요구사항 나누기와 지시문을 쓰고, 아니면 스크립트의 것을 쓰고 어느 쪽인지 결과에 적는다. 전체 넣기의 근거는 검색(최대 50개)을 거치지 않고 그 발행본 조각을 모두 읽어 넣는다. 결과 원문은 Q7처럼 로컬 파일에만 두고, docs/에는 요구사항마다 두 방식의 항목 수·버린 수만 적는다.

## Consolidated Summary Confirmation
