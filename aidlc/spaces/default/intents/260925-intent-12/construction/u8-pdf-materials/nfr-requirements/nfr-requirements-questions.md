Unit: `u8-pdf-materials`(#420). 입력: [기능 명세](../functional-design/functional-spec.md), [규칙](../functional-design/rules.md), [재승인 요구사항](../../../inception/requirements-analysis/requirements.md) NFR1~NFR7, [계약 요약](../../../inception/contract-design/contract-summary.md) C-05·C-16·C-17과 「에러 대응 최소선」.

재승인 요구사항은 비기능 기준을 "12월 시연 규모로 보고 9월보다 높이지 않는다"고 했고, NFR4는 "처리 시간·가동률·복구 수치를 새로 만들지 않는다"고 했다. 그래서 이 단계는 새 수치 목표를 만들지 않고, 기능 설계가 이미 정한 값(상한·시한)과 계약의 규칙을 NFR ID로 묶어 적는다. 묻는 것은 기능 설계가 정하지 않았고 신뢰성·보안에 영향이 있는 두 가지뿐이다.

## Q1. [개발 담당(U8)] worker의 PDF 추출을 어떻게 격리할지

10월 저장소 분석 소비자는 작업마다 자식 프로세스를 띄워 시간 제한과 중단 코드를 둔다. PDF 추출은 pypdf가 악의적이거나 손상된 파일에서 멈추거나 메모리를 많이 쓸 수 있다. 격리 방식은 한 작업이 worker 프로세스 전체(분석 소비자 포함)에 미치는 영향과, 시한 10분(기능 설계 Q2) 전에 실패를 확정할 수 있는지를 정한다.

A. 분석 소비자와 같은 방식으로 작업마다 자식 프로세스를 띄우고 자체 시간 제한(예: 2분)과 메모리 제한을 둔다. 제한을 넘으면 FAILED(UNREADABLE_FILE)로 보고한다 (worker 프로세스 보호, 실패를 10분보다 일찍 확정; 10월 자식 프로세스 틀 재사용으로 공수는 중간)
B. 같은 프로세스 안에서 pypdf를 직접 실행하고 자체 제한은 두지 않는다. 멈춘 작업은 큐의 잠금 만료로 실패하고 자료는 10분 시한으로 FAILED가 된다 (가장 단순; 한 파일이 오래 걸리면 추출 Worker 하나가 그 동안 묶이고 메모리 보호가 없음)
X. Other (please specify)

[Answer]: X. A의 자식 프로세스 격리 방식을 선택합니다. 10월 분석 소비자의 격리 방식을 재사용하고, 시간·메모리 제한에 걸리면 해당 추출 작업을 종료해 기존 C-16 실패 규칙으로 처리합니다. 큐 대기를 포함한 전체 시한은 기존 10분을 유지합니다. 예시인 2분과 메모리 제한값은 이번 NFR의 새 수치 목표로 확정하지 않고, 기존 구현과 대표 PDF 측정 결과를 근거로 구현 단계에서 정합니다.

## Q2. [개발 담당(U8)] S3 호출의 전송 수준 재시도

계약 C-05는 `StorageUnavailable`을 "재시도 없이 호출자가 실패 처리"로 두고, 에러 대응 최소선 2는 "다시 시도는 사람이 한다"고 한다. 이것은 작업·요청 단위의 규칙이다. AWS SDK는 한 호출 안에서 일시 오류(쓰로틀·네트워크)를 기본 3회까지 스스로 다시 시도하는데, 이를 둘지 끌지는 정해지지 않았다.

A. SDK 기본 재시도(한 호출 안 최대 3회, 짧은 대기)를 그대로 둔다. 호출이 최종 실패하면 StorageUnavailable 한 번으로 끝낸다 (가장 단순, 일시 오류에 강함; 호출 1회가 몇 초 더 걸릴 수 있음)
B. SDK 재시도를 0으로 끈다. 첫 실패가 곧 StorageUnavailable이다 (원칙을 엄격히 적용; 네트워크 잠깐 끊김에도 발행·업로드가 실패해 사람이 다시 함)
X. Other (please specify)

[Answer]: A
