### 직접 등록의 근거와 입력 방식의 지위

- 승인된 제품 요구: 요구사항 FR1.2는 "회원은 공개 저장소를 직접 등록하고 분석을 요청한다" 및 "사전 선정 목록이 이 경로를 대신하지 않는다"고 정한다. US1.2·AC1.2.1과 Unit 정의 U7도 이 책임을 따른다.
- 주소 입력 방식: 위 근거는 URL 입력 UI까지 지정하지 않는다. **공개 GitHub 저장소 주소를 입력하는 방식은 이번 U7 기능 설계에서 제안한 선택이며, 이미 승인된 요구사항으로 인용하지 않는다.** 새 탐색 화면 없이 기존 모달의 입력 영역을 바꿔 직접 등록을 제공하는 최소안으로 제안한다. 이번 요약 확인과 이후 기능 설계 검토에서 판단한다.
- 현재 화면 근거: `web/src/features/analysis-request/README.md`는 `RepositoryManagement` 모달 아래의 "연결할 수 있는 저장소" 영역에서 서버가 허용한 저장소를 고른다고 설명한다. `web/src/features/repository-management/repository-management.tsx`도 위쪽의 분석 이력·상태 영역과 아래쪽의 `AnalysisRequestSection`을 같은 모달 안에 배치한다.

## 작성할 설계안

### 등록과 분석 요청

- **기존 "GitHub 저장소 연결 관리" 모달의 진입·열기·닫기와 위쪽 "연결된 저장소"의 분석 이력·상태 새로고침·Catch 보기·실패 재요청은 유지한다.** 모달 전체를 새 화면으로 대체하지 않는다.
- **아래쪽 "연결할 수 있는 저장소"의 사전 선정 목록 선택을 "공개 저장소 등록"의 주소 입력·등록 영역으로 대체한다.** 주소 등록 결과로 확인한 저장소 이름과 분석 대상을 표시한 뒤, 현재 고지를 보여 주고 [동의하고 분석 요청]으로 이어 간다. 주소 등록 자체는 분석 실행이나 동의로 보지 않는다. 10월의 선정 목록은 새 직접 등록 흐름의 전제나 대체 경로로 남기지 않는다.
- 모달 안의 기존 요청 중·응답 불명 안내, 닫았다 다시 열 때 붙잡은 요청의 키·본문 유지, 서버가 허용한 실패의 새 동의·재요청은 재사용한다. 새 GitHub 저장소 탐색 화면이나 관리자 선정 화면은 추가하지 않는다.
- 서버는 주소에서 저장소 좌표를 해석하고 고정 GitHub API 경로로 확인한다. 임의 호스트·경로로 외부 요청을 보내지 않는다. 등록 식별은 확인한 GitHub 저장소 ID와 회원 ID를 기준으로 하며, 같은 회원의 같은 저장소 입력은 기존 등록을 반환한다.
- 공개 여부·GitHub 연결·동의·지원 조건을 확인하되 소유자·기여자인지는 등록 허가 조건으로 쓰지 않는다. 본인 기록 판정은 분석에서 연결 계정 신원에 근거한다.
- 회원별 등록 정보를 접수, worker 내부 컨텍스트, 결과 반영의 좌표 확인까지 일관되게 연결한다. 동의 범위의 판본과 실제 수집 범위가 어긋나면 실행하지 않는다.
- 신규 분석 및 허용된 실패 재요청의 접수 트랜잭션에서 C-03의 ANALYSIS 1회를 소비한다. 기존 요청 조회·동일 접수 응답은 새 실행으로 세지 않는다. 한도 초과는 계약의 `429 DAILY_LIMIT_REACHED`로 알리고 남은 횟수는 보이지 않는다.

### 결과·실패·재요청

- 기존 접수 → 큐 → worker 수집·후보 판정·생성 → 결과 수신·Catch 반영 경로를 유지한다.
- 수집이 정상적으로 끝나 본인 커밋이 없다고 확인된 경우에만 본인 기록 없음으로 안내하고 Catch를 만들지 않는다. 조회 실패·수집 중단·범위 한계로 확인하지 못한 경우를 기록 없음으로 단정하지 않는다. 본인 커밋은 있지만 Catch 후보가 없는 경우도 구분한다.
- 처리 진행, 완료, 부분 결과, 확인된 실패, 상태 조회 실패를 구분한다. 재요청 허용은 기존 서버 판정으로 정하며 새 동의를 받는다.
- 자동 분석 재시도, 정상 완료 재분석, 부분 결과 추가 생성, 헤더 알림은 추가하지 않는다. 기존 비밀값·개인정보 가리기와 다른 회원 자료 차단은 유지한다.

### 수집 상한과 검증

- 커밋 목록·상세 조회·관계 조회 호출·수집 시간·생성 횟수·요청 처리 시한을 함께 검토한다. 기능 설계에는 상한 도달 때의 동작과 측정 항목을 적고, 구체 값은 후속 비기능 설계·구현의 실측으로 정한다. 임의 수치를 확정값으로 쓰지 않는다.
- 팀장 계정의 CatchU 저장소 약 500개 커밋이 수집·판정에 반영되는지 확인한다. 커밋 하나마다 Catch 하나를 생성한다는 뜻은 아니다. 기존 후보 묶음·작업 동일성·기여 판정을 유지한다.
- 실제 확인 전에는 요구사항 OQ2(시연 저장소 공개 여부와 대체 대상 결정)를 해결해야 한다. 공개 전환이나 외부 AI 실측을 이 설계 확인만으로 실행하지 않는다.
- U2 C-03 실제 연결은 별도 통합 확인 대상이며 합성 제공자의 성공을 실제 연결 완료로 기록하지 않는다.

### U7 완료에 필요한 실제 분석 확인

2026-10-29 사용자 수정 요청으로 이슈 #424의 완료 조건에 실제 분석 확인을 명시한다. 근거는 Unit 정의 U7의 "실제 분석 확인", 요구사항 FR19.1, 스토리 AC19.1.1·AC19.1.5·AC19.1.7이다. US19.1의 전체 통합 진행은 U2 책임으로 유지하고, U7은 자기 분석 경로의 실제 증거를 제공한다.

- 실제 계정으로 새 직접 등록 경로를 사용해 공개 GitHub 저장소를 등록하고 동의·분석을 요청한다. 실제 GitHub 수집 → 기존 worker 후보 판정·실제 생성 제공자 호출 → 결과 수신·DB 반영 → 본인 화면의 완료 상태와 생성된 Catch·근거 확인까지 한 요청으로 이어져야 한다. 접수 202나 큐 등록만으로 성공으로 보지 않는다.
- 정상 사례는 본인 기여와 Catch 생성이 가능한 실제 저장소로 확인한다. 기준 대상은 팀장 계정의 CatchU 저장소이며 OQ2에 따라 공개 여부 또는 승인된 대체 대상을 먼저 확정한다. 약 500개 커밋의 수집·판정 반영과 한계도 함께 기록한다.
- 거부 사례 1~2종을 실제 확인에 더하고, 수용 기준별 나머지 정상·거부·실패 검사는 U7의 기존 검사 범위에서 수행한다. 실제 사례와 합성 사례를 구분한다.
- 실행 날짜·대상 환경·대상 코드 버전·저장소/분석 대상 리비전·요청 식별자·최종 상태·Catch 확인 결과·실패/미실행·수집 한계를 검증 기록에 남기고 이슈/PR에서 연결한다. 비밀값·자격정보·원문 전체는 첨부하지 않는다. FR19.1의 AWS 통합 확인은 해당 환경에서 별도로 증명하고 로컬 성공으로 대신하지 않는다.
- 합성 공급자, 개발용 결과 주입, 10월 사전 선정 경로의 성공으로 새 경로의 실제 분석 완료를 대신하지 않는다. 환경·자격정보·대상 공개 결정 때문에 실행하지 못했다면 미실행으로 남기고 이 완료 조건을 충족했다고 표시하지 않는다.
- 이슈 종료에는 위 실제 분석 확인과 통합 브랜치 병합이 모두 필요하다. 새 이슈를 나누지 않고 기존 Unit 이슈 #424에서 관리하며, AI-DLC 단계 승인과 실제 기능 완료를 구분한다.

## 경계 조건과 불명확성 점검

| 조건 | 설계 처리 |
|---|---|
| 잘못된 주소·GitHub 외 주소 | 입력 오류와 고칠 위치 안내, 입력 보존 |
| 같은 저장소의 표기 차이·중복 등록 | 확인된 저장소 ID 기준으로 같은 회원의 기존 등록 사용 |
| 비공개·연결 없음·동의 없음·지원 불가·하루 한도 | 실행 전 판정 가능한 원인을 각각 안내. 관측 불가를 비공개나 본인 기록 없음으로 대체하지 않음 |
| 등록 뒤 저장소 이름·공개 상태 변경 | 실행 전 요청의 저장소 ID·범위·현재 관측을 대조, 불일치나 확인 불가 시 안전하게 거부 |
| 목록·상태 조회 장애 | 조회 실패로 표시하고 사용자가 다시 확인. 새 분석을 자동 실행하지 않음 |
| 수집 실패·상한 도달 | 실패와 수집 범위 한계를 기존 처리 의미에 맞게 구분하고 전체를 확인한 것처럼 표시하지 않음 |
| 결과 없음·부분 결과 | 본인 기록 없음과 후보 없음, 부분 결과를 구분. 부분 결과의 추가 생성은 없음 |
| 탈퇴 뒤 결과 도착 | 기존 회원·부모 참조와 수신·반영 보호 유지. 다른 회원 자료로 반영하지 않음 |

이미 확정된 제품 결정을 다시 질문하지 않는다. 주소 입력은 이번 설계 제안이고 수동 상태 새로고침은 기존 동작을 유지한다. 상한 실측과 시연 저장소 공개 결정은 지금 답을 추정하지 않고 해당 후속 시점의 미결로 남긴다. 이 미결은 설계안 작성을 막지 않지만 실제 분석 확인의 완료를 대신하지 않는다.
