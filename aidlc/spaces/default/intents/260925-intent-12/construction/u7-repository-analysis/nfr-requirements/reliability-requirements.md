# U7 저장소·분석 — 신뢰성 요구사항
## 근거와 적용 범위

작성일: 2026-10-29. [사용자가 확인한 작성안](nfr-requirements-questions.md)을 상세화한다. 코드 구현·실측·실제 분석 완료 기록이 아니다.

직접 근거: [기능 명세](../functional-design/functional-spec.md)(functional-spec), [업무 규칙](../functional-design/rules.md)(rules), [재승인 요구사항](../../../inception/requirements-analysis/requirements.md)(requirements), [계약 요약](../../../inception/contract-design/contract-summary.md)(contract-summary). 세부 NFR ID는 이 Unit 안에서 해당 상위 NFR을 구체화하며, 전체 대응은 [traceability.json](traceability.json)에 둔다.

NFR4·NFR5·NFR7과 기능 명세 F2~F4, 계약의 에러 대응 최소선·C-03·C-06을 적용한다. 기존 분석 접수·수신·반영·시한 보호를 재사용하고 새 가동률·복구 목표나 복구 장치를 만들지 않는다.

## 상태·시한·사용자 안내 요구사항

| ID | 요구사항 | 판정·검증 방법 |
|---|---|---|
| NFR4.6 | 접수 이후 끝나지 않은 요청은 기존 api 처리 시한 닫기로 처리한다. worker의 실행 상한과 별도로 상태·시도·수명 전이 조건을 지킨다. | 접수 202, 결과 수신, 반영 완료를 구분한다. 시한 조정이 필요한 경우 [성능 요구사항](performance-requirements.md)의 측정 결과를 사용하고 기존 전이와 요청·시도 잠금 순서를 보존한다. |
| NFR7.1 | 접수·진행·실행 확인 중·반영 중·정상 완료·정상 0건·부분 결과·확인된 실패·조회 실패를 실제 상태대로 표시한다. | 처리·반영·수명의 세 축과 ownerResultsReady를 함께 사용한다. 조회 실패나 접수 성공으로 완료/실패를 추정하지 않는다. |
| NFR7.2 | 본인 기록 없음, 생성 가능한 후보 없음, 수집 한계, 외부 장애, 비공개 확인, 동의/연결 문제와 하루 한도 도달을 구분해 안내한다. | NONE은 필요한 관측이 완료되고 부재를 막는 한계가 없을 때만 사용한다. 확인된 본인 커밋은 FOUND, 확인할 수 없으면 UNKNOWN이다. 일반 429 대기 안내로 하루 한도를 대신하지 않는다. |

현재 처리 시한은 접수 시각부터 60분이며 닫기 판정 완료 후 1분 뒤 다음 판정을 시작한다. worker 전체는 작업을 꺼낸 시각부터 20분이다. 이는 현재 계약·구현값이며 완료 시간이나 복구 시간 보장이 아니다. 앱·DB·큐 장애가 해소되지 않은 동안의 상태 정리를 새 가용성 약속으로 표현하지 않는다.

## 실패별 처리

정확한 상태·재요청 분기는 [기능 명세 F4](../functional-design/functional-spec.md#흐름-f4--상태와-재요청-us13)를 따른다. 다음 표는 실패 때 사용자 행동과 데이터 보호의 요구사항이다.

| 상황 | 결과·사용자 행동 | 보존할 조건 |
|---|---|---|
| 등록/공개 여부 조회 실패 | 확인 불가를 알리고 사용자가 다시 확인 | 비공개나 본인 기록 없음으로 바꾸지 않음. 분석 접수·하루 소비 없음 |
| 접수 응답 불명 | 기존 요청 키를 유지해 기존 접수 여부 확인 | 새 실패 재요청과 구분. 같은 키·같은 본문은 기존 응답 |
| 접수 후 큐 전달 실패·실행 유실 | 기존 상태·시한 판정으로 실패 확인 | 새 요청 자동 생성·횟수 환급 없음 |
| GitHub 수집 실패·필수 관계 확인 중단 | 실패 이유와 한계 표시 | 불완전 관측을 NONE으로 확정하지 않음 |
| 일부 생성 실패·생성 상한 도달 | 기존 부분 실패와 준비된 결과 표시 | 유효 결과의 추가 생성·재분석 없음 |
| 결과 반영 실패 | 기존 APPLY_FAILED 및 종료 여부 표시 | 조회만으로 성공으로 바꾸지 않음 |
| 상태 조회 실패 | 조회 실패와 상태 새로고침 제공 | 요청의 처리 상태를 바꾸거나 새 분석하지 않음 |
| 처리 시한 닫기 | 기존 조건에 따라 CLOSED 및 처리/반영 실패 | 기존 수신·반영이 늦은 결과를 거부하는 의미 유지 |
| 삭제된 부모의 결과 | 저장하지 않고 버림 | 계정·요청·Catch를 재생성하거나 재시도하지 않음 |

서버가 허용한 최신 종료 실패만 새 동의·새 요청 키·현재 공개/연결/범위 확인·C-03 소비를 거쳐 재요청한다. CLOSED + APPLY_FAILED는 기존 결과/Catch가 없을 때 처리 결과·후보 수와 무관한 기존 분기를 유지한다. CLOSED + FAILED + APPLIED는 후보 0과 서버의 실패 확정 근거 등 기존 조건을 모두 확인한다. 진행·복구·불명·정상 0건·정상 완료·유효 부분 결과는 새 분석을 허용하지 않는다.

## 자료 수명·삭제 요구사항

| ID | 요구사항 | 판정·검증 방법 |
|---|---|---|
| NFR5.1 | U7의 새 회원별 등록과 관련 행은 실제 부모를 참조하고 C-06의 ON DELETE CASCADE를 따른다. 두 부모의 소유자가 같아야 하면 복합 외래 키로 묶는다. | 마이그레이션·엔티티의 부모 관계를 대조하고 기존 회원 연쇄 삭제 검사를 적용한다. 같은 코드 PR에서 삭제 표에 새 표와 부모를 적는다. |
| NFR5.2 | 삭제 중이거나 삭제된 회원·요청의 늦은 결과가 자료를 되살리지 못해야 한다. 기존 결과 수신/반영 검사와 부모 외래 키를 유지한다. | 부모 없음으로 거부된 결과를 다시 처리하지 않는다. 탈퇴 API의 기존 차단·자격정보 삭제·연쇄 삭제 경계와 새 등록의 삭제 관계를 검토한다. |

회원별 신규 등록은 과거 전역 repository_selection의 외래 키 예외를 그대로 상속하지 않는다. 새 자료의 부모·소유자 관계를 설계와 마이그레이션에서 명시한다. 기존 분석 요청의 순환 참조 예외는 C-06이 허용한 범위만 보존한다.

Catch의 사용자 삭제, 새 자동 보관 만료, 삭제 작업 재처리 큐를 추가하지 않는다. 탈퇴 실행 순서 자체는 U2 소유이며 U7은 자기 새 표의 연쇄 삭제와 결과 반영 경계를 맞춘다. DB 밖의 새 파일 저장소는 만들지 않는다.

## 검증과 한계

기존 시한·상태·재요청·삭제 검사를 유지하고 새 등록 참조·관측값이 판정에 제대로 연결되는지 확인한다. 입력과 회원 자료 격리의 거부 사례는 필수이며, 별도의 기능별 동시 요청·재전송·늦은 결과 시험 체계를 신설하지 않는다. 프로젝트의 보호 흐름 3개 통합 확인은 U2가 취합한다.

새 백업·다중 리전·장애 자동 복구·자동 분석 재시도·모델 대체를 요구하지 않는다. 장애·미실행을 기록하고, 실제 새 경로 성공을 확인하지 못했으면 U7 완료로 표시하지 않는다.
