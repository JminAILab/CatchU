## 근거와 적용 범위

작성일: 2026-10-29. [사용자가 확인한 작성안](nfr-requirements-questions.md)을 상세화한다. 코드 구현·실측·실제 분석 완료 기록이 아니다.

직접 근거: [기능 명세](../functional-design/functional-spec.md)(functional-spec), [업무 규칙](../functional-design/rules.md)(rules), [재승인 요구사항](../../../inception/requirements-analysis/requirements.md)(requirements), [계약 요약](../../../inception/contract-design/contract-summary.md)(contract-summary). 세부 NFR ID는 이 Unit 안에서 해당 상위 NFR을 구체화하며, 전체 대응은 [traceability.json](traceability.json)에 둔다.

## 관측·검증 요구사항

| ID | 요구사항 | 판정·검증 방법 |
|---|---|---|
| NFR6.1 | 새 직접 등록 경로로 실제 GitHub 수집 → 실제 생성 → 결과 수신·DB 반영 → 본인 화면 Catch·근거 확인을 이어 증명한다. 실제 거부 1~2종도 남긴다. | 날짜·환경·코드 버전·대상 리비전·요청 ID·최종 상태·개수·한계·화면 확인을 한 실행에 연결한다. 합성·구 선정 경로·접수 성공은 대체 증거가 아니다. |
| NFR6.2 | 기존 로그를 요청 ID·시도 ID와 안전한 단계·결과 값으로 이어 실패 지점을 구분할 수 있어야 한다. | 원문·토큰·키·SQL·stack·오류 객체 전체를 빼고 필요한 코드·건수·시간만 기록한다. 단계 접수와 실제 완료를 서로 다른 사건으로 남긴다. |
| NFR6.3 | 검증 기록은 실제 성공·실패·미실행과 합성 검사를 구분한다. 기능 사이 보호 흐름은 공통 3개 확인에 연결한다. | U7의 기존 정상/거부 검사와 실제 분석 증거를 U2 전체 확인 표에 제공한다. 새 관제·알림·튜닝 반복·기능별 세부 재전송 시험 체계는 만들지 않는다. |

## 기존 로그 연결

| 구간 | 필요한 관측 | 기록 경계 |
|---|---|---|
| 주소 등록·신규 접수 | 성공/거부 원인, 등록·요청의 안전한 식별자, 접수 시각 | 입력 주소 원문이나 자격정보를 오류에 그대로 싣지 않음 |
| 큐·worker | requestId·attemptId·메시지 ID, 처리 시작/종료·실패, 현재 설정 상한 | 기존 연결 계약과 로그 형식을 사용. 큐 수신을 화면 완료로 기록하지 않음 |
| 수집·후보 | 목록·본인 관측·필요 상세·관계 조회 건수, 한계·실패 코드, 호출/시간/바이트 | 커밋 글·diff·개인정보·가린 값을 통째로 남기지 않음 |
| 생성 | 후보·생성·교정·미생성·실패 수, 안전한 제공자 모델·시간·토큰·요청 ID | 기존 생성 로그는 SHA·파일 경로·이름·제목·본문을 남기지 않음 |
| 결과 수신·반영 | receipt·사유, 처리/반영/수명, 반영 결과와 본인 열람 준비 여부 | ACCEPTED는 수신이며 반영·화면 완료와 다름 |
| 본인 화면 | 최종 상태, 준비된 Catch와 근거 확인 | 실제 확인에 필요한 최소 결과만 기록. 전체 화면/원문을 무조건 첨부하지 않음 |

현재 생성 제공자 로그는 호출별 CatchU 요청 ID 대신 자식 프로세스 로그의 attemptId 접두어로 연결된다. 새 전 구간 추적 플랫폼을 만들지 않고 기존 연결을 사용한다. 실제 측정에 필요한 값이 현재 기록에 없으면 U7 변경에서 최소한의 안전한 건수·소요·상한 값만 보완한다.

근거: [worker 큐 로그](../../../../../../../../worker/docs/queue-consumer.md), [생성 운영 로그](../../../../../../../../worker/docs/generation-limits.md#운영-로그), [생성 제공자 로그](../../../../../../../../worker/docs/generation-provider.md#운영-로그), [api 처리 시한 로그](../../../../../../../../api/docs/analysis-deadline.md#로그), [자료와 실행 로그](../../../../../../../../docs/CatchU_coding_procedures.md#자료와-실행-로그).

## 실제 확인에 남길 한 행

FR19.2의 공통 확인 표에 넣거나 연결할 U7 한 행은 다음 내용을 담는다. 실제 실행 전에는 결과 칸을 성공으로 채우지 않는다.

| 묶음 | 필수 내용 |
|---|---|
| 대상 | 날짜, 실행 환경, 코드 커밋, 저장소와 분석 대상 리비전, 계정 역할(비밀값 제외), 새 주소 등록 경로 여부 |
| 실행 식별 | 요청 ID·시도 ID, 실제 GitHub와 실제 생성 제공자 사용 여부, 실제 모델 |
| 처리 결과 | 처리·반영·수명 최종 상태, ownerResultsReady, Catch·근거를 본인 화면에서 확인한 결과 |
| 규모 | 목록·본인 관측·필요 상세/관계·후보·생성·반영 개수, 시간·호출·바이트·생성 상한, 제외·중단 이유 |
| 거부 사례 | 준비 가능한 실제 거부 1~2종, 실행 전 거부 여부와 사용자 안내. 비공개를 확인한 사례와 404 확인 불가를 구분 |
| 판정 | 실제 성공/실패/미실행, 미확인 범위와 사유, 증거 위치, 관련 통합 브랜치 병합 PR |

정상 사례는 본인 기여와 생성 가능한 후보가 있는 공개 저장소를 사용한다. 유효 결과가 일부 있더라도 실패한 칸을 정상 성공으로 감추지 않는다. 정상 완료·부분 결과·실패를 그대로 기록하고 약 500개 반영 조건의 충족 여부를 별도로 판단한다.

외부 AWS 환경의 FR19.1 확인은 해당 환경에서 실제로 수행한 증거가 필요하다. 로컬 실측은 로컬 결과로 남긴다. C-03도 합성 제공자의 성공과 실제 U2 제공자 연결을 구분한다.

## 준비 조건과 완료 판정

요구사항 OQ2에 따라 CatchU 공개 여부 또는 팀장이 정한 대체 대상을 실제 확인 전에 확정한다. 실행 환경·자격정보·허용 자료 범위·비용 조건을 확인하고 그 안에서만 실제 자료를 처리한다. 이 문서가 공개 전환·자료 외부 전송·실측 실행을 이미 완료했다는 뜻은 아니다.

U7 완료에는 실제 새 경로 분석과 거부 사례의 증거, 이슈 완료 조건에 맞는 통합 브랜치 병합이 모두 필요하다. 환경이나 대상 결정이 없어 수행하지 못했으면 미실행으로 남기고 완료로 닫지 않는다. 설계 승인과 실제 기능 완료는 서로 다르다.

## SLI·SLO·운영 경계

수집·생성·반영 건수와 시간은 이번 요구사항 판정에 필요한 관측값이다. 처리 시간·가동률·복구 SLO, 오류 예산, 자동 경보 임계값, 대시보드는 새로 정하지 않는다(NFR4·NFR6). 기존 로그로 실패를 확인하며 새 로그 플랫폼 도입을 개발 준비의 조건으로 삼지 않는다.

NFR3의 질의응답 10개 평가는 해당 기능 담당의 작업이다. U7은 저장소 분석의 실제 증거와 기존 기여·생성 검증을 제공하고 그 평가를 복제하지 않는다.
