# U7 저장소·분석 — 보안 설계

작성일: 2026-10-29. [확인한 작성안](nfr-design-questions.md)과 [보안 요구사항](../nfr-requirements/security-requirements.md)을 구현 지점에 연결한다. 구현·보안 검증·실제 자료 전송을 수행했다는 기록이 아니다.

## SD1 회원 권한과 내부 인증

대응: NFR1.1. 기존 회원 API의 Bearer 인증·Refresh 쿠키·CSRF 경계를 유지한다. 서버가 인증에서 얻은 memberId를 등록·목록·접수·동의·상태·Catch 조회의 조건으로 사용한다. 본문에서 받은 memberId로 소유자를 바꾸지 않는다. 다른 회원 등록/요청과 없는 등록/요청에는 같은 접근 불가 응답을 사용한다.

[논리 컴포넌트 LC2](logical-components.md#lc2-등록과-요청-사본)의 복합 외래 키로 요청의 회원·등록·GitHub ID를 묶는다. UNIQUE(member, repository)는 동일 회원의 중복 등록만 막으며 서로 다른 회원은 각각 등록·동의·분석 결과를 가진다. 기존 Catch 본인 조회에도 새로운 공개 읽기 권한을 추가하지 않는다.

[worker 컨텍스트](../../../../../../../../api/src/worker-context/worker-context.service.ts)는 기존 서비스 전용 인증을 사용한다. attemptId만 안다고 읽을 수 없으며 요청/현재 시도/동의/활성 회원/연결 상태를 대조한 뒤 자격정보를 제한된 내부 응답으로 전달한다. 조회 전후 연결 참조·GitHub 계정 ID·만료를 다시 확인하는 현재 보호를 유지한다. 관측값은 분석 맥락 검증을 통과한 Result에서만 저장한다.

검증: 두 회원의 등록·요청·동의 참조를 서로 바꾼 요청을 거부하고, 없는 자원과 오류 모양이 같은지 확인한다. 내부 인증 누락·틀린 시도/회원/동의/저장소 참조는 수집/반영되지 않아야 한다. 시험용 권한 우회는 만들지 않는다.

## SD2 주소와 외부 통신

대응: NFR1.2. 주소 파싱은 api 회원별 등록 공급의 책임이다. 프런트 검사만 신뢰하지 않는다.

| 경계 | 허용·거부 |
|---|---|
| 사용자 입력 | 앞뒤 공백 정리 후 https://github.com/{owner}/{repo}. 끝 슬래시·선택적 .git 정리 |
| 거부 | 사용자정보·명시 포트·쿼리·fragment·추가 경로·외부 호스트·인코딩으로 숨긴 경로 구분자/상위 경로 |
| 좌표 | 기존 owner/name 문자·길이 규칙을 재사용하고 . 및 .. 거부. URL 파서가 정리하기 전 금지 요소도 확인 |
| 실제 요청 | 서버 상수 https://api.github.com 에 검증한 owner/name으로 만든 저장소 메타데이터 경로만 호출 |
| 응답 | 양의 저장소 ID, canonical owner/name, 공개 여부와 필요한 지원 범위를 검증. 응답 속 URL을 요청 목적지로 사용하지 않음 |
| 네트워크 | redirect와 자동 재시도 없음. 시간·응답 크기 제한, 비정상 HTTP/JSON을 실패로 처리하고 원문을 오류에 싣지 않음 |

[현재 GitHub 클라이언트](../../../../../../../../api/src/github-connection/github.client.ts)의 보호 방식(10초·64 KiB·redirect 차단)을 등록 메타데이터 어댑터의 초기 기준으로 사용한다. 저장소 조회는 새로 필요한 U7 경계이며 이미 구현된 메서드가 아니다. 크기 초과는 확인 불가로 처리하고 제한을 없애지 않는다. 필요한 수치 조정은 정상 응답 실측과 함께 기록한다. 기존 OAuth 무권한 범위를 넓히거나 저장소 소유·기여·조직 관계를 등록 허가 조건으로 조회하지 않는다.

등록과 새 접수 때 확인한 공개 상태는 worker 실행 직전에도 재확인한다. GitHub ID가 다르거나 동의 사본과 좌표가 어긋나면 중단한다. 같은 경로에 새로 생긴 다른 저장소를 원래 등록으로 취급하지 않는다. 명시적으로 private임을 확인한 경우와 404/접근 확인 불가/외부 장애를 구분한다.

SQL은 기존 ORM/매개변수 바인딩을 사용한다. 입력·수집 글을 셸·eval·실행 코드로 넘기지 않는다. JSON/메시지 허용 필드 검증과 공통 입력 제한을 유지하며 스키마 이동은 [LC4](logical-components.md#lc4-현행-메시지와-패키징)를 따른다.

검증: 정상 정규화, 외부/유사 호스트, userinfo, 포트, encoded slash/dot segment, query, redirect, 과대·느린 응답, 잘못된 ID, 404를 합성 응답으로 확인한다. 실제 거부 1~2종은 OD1에서 별도로 기록한다.

## SD3 동의·실행 범위 고정

대응: NFR2.1. 등록은 분석을 시작하지 않는다. 분석 요청마다 현재 noticeRevision·scopeRevision·accepted=true를 확인하고 요청별 analysis_consent에 불변 사본을 저장한다. U2 첫 이용 AiConsentGate는 이 동의를 대체하지 않는다(C-04).

외부 확인은 접수 트랜잭션 전에 수행한다. 트랜잭션 안에서는 회원/연결/등록/판본을 다시 읽어 확인 대상과 대조한다. 변경되면 새 확인을 요구하고 이전 확인으로 접수하지 않는다. 같은 키의 이미 접수된 요청은 현재 공개/연결/고지 변경과 무관하게 기존 응답을 반환하며 새 동의·하루 소비를 만들지 않는다.

큐에는 기존 attemptId 기반 참조와 허용 자료 종류만 싣는다. worker는 보호된 내부 API로 그 참조를 해석하고 허용 범위를 모르면 넓혀 읽지 않는다. 결과 좌표는 현재 등록값이나 worker가 보낸 임의 URL 대신 그 요청의 서버 확인 사본에서 복원한다.

검증: 미동의·false·옛 판본·다른 등록 참조를 거부한다. 주소/연결 변경 뒤 이전 확인을 재사용하지 않는지, 이미 받은 동의 사본과 같은 키 재응답이 변경되지 않는지 확인한다.

## SD4 자료·프롬프트·생성 출력

대응: NFR2.2, NFR2.3. 저장소 글·커밋 메시지·diff·PR·이슈는 신뢰할 수 없는 입력이다. 기존 worker/generation의 material·redact·request·response·flow 경계를 재사용한다. 자료 영역과 생성 지시를 분리하고 기존 비밀값·개인정보 가리기를 거친 내용만 제공자에게 보낸다. 다른 회원 자료나 자격정보를 프롬프트에 넣지 않는다. 텍스트/PDF 업로드의 미가리기 예외는 저장소 수집에 적용하지 않는다.

본인 여부는 [GitHubAccount.same_account](../../../../../../../../worker/app/collection/identifiers.py)의 숫자 계정 ID와 기존 기여 판정을 사용한다. 저장소 소유자·표시 로그인·생성 문구로 본인 기여를 만들어내지 않는다. 후보 묶음·동일 작업·근거·제목 형식·출력 검사를 유지한다. 생성할 후보가 없으면 제공자를 호출하지 않는다.

web은 React 텍스트로 상태·Catch를 표시한다. HTML 삽입을 추가하지 않고 근거 링크는 서버가 허용한 GitHub 호스트·좌표로 구성한다. 새 창 링크의 noopener noreferrer를 유지한다. 수집 한계/실패는 생성 결과와 함께 표시하며 생성된 표현이 확인된 작업 사실을 덮어쓰지 않는다.

검증: 합성 비밀값과 숨긴 지시가 포함된 자료를 기존 가리기·자료 구분 검사에 통과시킨다. 본인 ID 불일치·근거 불일치·악성 링크/HTML·잘못된 생성 출력의 거부와 안전한 표시를 확인한다. 실제 원문을 검사 보고에 붙이지 않는다.

## SD5 제공자·비밀값·환경

대응: NFR1.3, NFR2.4. 기존 ClaudeProvider와 생성/제목 교정 Haiku 5.5 설정을 재사용한다. 제공자 고정 주소·TLS·명시 키·proxy 환경 차단·redirect 차단·응답/입출력 제한·SDK 재시도 0을 유지한다. 다른 모델로 실패 재호출하지 않는다. 근거는 [생성 제공자 문서](../../../../../../../../worker/docs/generation-provider.md)이며, U1 api 게이트의 시간 제한 특성을 worker 제공자에 그대로 옮겨 설명하지 않는다.

현재 자격정보 저장소·서비스 키·환경 검증을 재사용한다. 토큰을 등록 표·동의 사본·큐 메시지·Catch에 저장하지 않는다. 원문을 내부 보호 응답에서 꺼내는 기존 경계는 유지하고 일반 JSON·예외·로그로 직렬화하지 않는다. 운영 필수 비밀값 누락/오류와 개발·시험 LIVE 비활성/MOCK 제한은 기존 기동 규칙을 따른다.

새 암호화 방식·키 관리 서비스·보안 인증을 도입하거나 달성했다고 주장하지 않는다. 네트워크 전송과 기존 저장 보호를 유지하며 새 회원 자료는 기존 DB 접근 통제를 따른다. 상태/관측 로그는 [OD2](observability-design.md#od2-로그와-상관관계)의 허용 필드만 사용한다.

검증: 합성 키로 오류/로그/응답/객체 출력에서 비밀값이 빠지는지, 운영 MOCK 우회가 없는지, 제공자 실패가 추가 호출을 만들지 않는지 확인한다. 실제 모델·토큰·실행 조건은 허용된 실측 때 기록한다.

## SD6 삭제와 위협별 인계

| 위협 | 적용 보호·검증 |
|---|---|
| 다른 회원 자료 읽기/쓰기 | SD1 회원 조건·복합 FK·내부 인증 |
| 등록 URL로 임의 서버 접근 | SD2 고정 호스트·좌표 검증·redirect/크기/시간 제한 |
| 동의 뒤 범위 또는 계정 교체 | SD3 불변 사본·트랜잭션 내 재대조·worker 연결 참조 확인 |
| 저장소 글로 지시·비밀값 유출 | SD4 가리기·자료 구분·기여/출력 검사 |
| 삭제된 회원의 늦은 결과 | [RD3](reliability-design.md#rd3-부모-삭제와-자료-수명)의 부모 검사·CASCADE·반영 중단 |
| 로그/화면에서 원문 유출 | SD4 텍스트 출력·SD5 비밀값 경계·OD2 허용 목록 |

보안 설계의 직접 기준은 [보안 점검](../../../../../../../../docs/CatchU_security_checks.md)과 [자료와 실행 로그](../../../../../../../../docs/CatchU_coding_procedures.md#자료와-실행-로그)다. 합성 경계 검사와 실제 허용 자료 검증을 구분한다. 실제 외부 전송·저장소 공개·비용 사용은 OQ2와 실행 조건 확인 후 수행한다. 설계 승인만으로 해당 검증을 완료하지 않는다.
