# U7 저장소·분석 — 성능 설계

작성일: 2026-10-29. [확인한 작성안](nfr-design-questions.md)과 [성능 요구사항](../nfr-requirements/performance-requirements.md)을 따른다. 이 문서는 측정·변경 방법이며 새 상한의 확정값이나 실행 결과가 아니다.

## PD1 약 500개 반영의 판정

대응: NFR4.1. 목록 500개를 받았다는 사실과 해당 자료가 판정·생성·반영까지 다뤄졌다는 사실을 분리한다. 기존 수집 범위 안에서 다음 집계를 같은 요청/시도에 연결한다.

| 구간 | 필수 집계·대조 | 누락 판정 |
|---|---|---|
| 커밋 목록 | 읽은 고유 커밋 수, 범위 밖/읽지 못한 목록 여부 | 목록이 잘리면 남은 범위를 한계로 기록 |
| 본인 관측 | 숫자 GitHub 계정 ID로 확인한 본인 커밋 수와 UNKNOWN/NONE/FOUND | 알 수 없는 관측을 0으로 보정하지 않음 |
| 상세·관계 | 필요한 상세 수, 수행/제외 수, 관계 조회의 찾음/없음/한계/미도달 수 | 호출·시간·개수 상한으로 못 본 것과 정상 제외를 구분 |
| 후보 | 묶음 전후와 생성 대상 수, 미제공 이유별 수 | 하나의 작업에 묶이는 커밋을 누락으로 세지 않음 |
| 생성 | 실제 호출·성공·교정·실패·미생성 수, 입력/출력·토큰·시간 | 생성 상한으로 미처리한 후보를 성공으로 바꾸지 않음 |
| 반영 | 수신 후보·반영·기존 Catch 참조·거부 수, ownerResultsReady | 결과 수신만으로 DB 반영·화면 확인을 대체하지 않음 |

약 500개 커밋이 Catch 500개여야 한다는 조건은 없다. 기존 후보 묶음·기여 판정은 유지하고 정상 제외 이유를 설명할 수 있어야 한다. 필요한 자료가 자원 상한 때문에 처리되지 않았다면 약 500개 반영 충족으로 표시하지 않는다.

대상은 FR1.6의 팀장 계정 CatchU가 기본이다. [요구사항 OQ2](../../../inception/requirements-analysis/requirements.md)에 따라 공개하지 않으면 팀장이 대체 공개 저장소와 분석·평가 대상을 다시 정한다. 임의로 작은 대상의 성공을 원래 규모 조건 충족으로 보고하지 않는다. 공개 전환에는 이력·문서·AI-DLC 기록 점검이 선행한다.

## PD2 시계와 예산의 관계

대응: NFR4.2. 서로 다른 시작점을 하나의 처리 시간으로 섞지 않는다.

| 시점·예산 | 현재 시작/끝 | 설계 적용 |
|---|---|---|
| 접수 시한 | submittedAt부터 60분 | 신규 접수 시각 기준. 큐 대기·수신·반영 시간까지 포함해 관측 |
| worker 전체 | pickedAt부터 20분, 종결 프레임까지 | 자식 처리와 결과 조립/검사/프레임 전달을 포함 |
| 수집 | pickedAt부터 10분 | 내부 컨텍스트 조회 등에 이미 쓴 시간도 차감되는 기존 방식 |
| 생성 마감 | pickedAt + 전체 20분 − 마무리 여유 60초 | 남은 시간이 호출 제한보다 짧으면 새 생성/교정 호출 시작하지 않음 |
| api 닫기 검사 | 이전 판정 완료 뒤 1분 후 다음 판정 | 60분이 사용자 완료 보장 시간이 아님. 판정 지연을 별도로 기록 |
| receipt·반영 | 기존 결과 전송/receipt 대기와 api 반영 | worker 처리 종료와 화면 열람 준비 시점을 따로 기록 |

현재 값의 출처는 [worker 실행 설정](../../../../../../../../worker/app/consumer/settings.py), [실제 처리 조립](../../../../../../../../worker/app/processing/live.py), [api 시한](../../../../../../../../api/docs/analysis-deadline.md)이다. 기존 값은 기준선이며 새 목표가 아니다.

실측에서는 t접수, t꺼냄, t수집종료, t생성종료, t결과수신, t반영종료, t화면확인을 구분한다. 큐 대기=t꺼냄−t접수, worker 처리=t종결프레임−t꺼냄, 사용자 경과=t화면확인−t접수다. 서로 다른 호스트의 시각 오차를 점검하고 로컬 단계 소요는 같은 프로세스의 경과값으로 측정한다. 기존 시한 판정 시계의 구현을 새 체계로 교체하지 않는다.

상한 조정 때 수집만 늘려 생성 시간을 없애거나, worker 전체만 늘려 api 시한 이후의 결과를 정상 반영하려 하지 않는다. 큐 대기·결과 수신/반영을 함께 측정해 필요한 예산 관계를 정한다. 근거 없는 백분위 응답 시간·가동률·복구 SLO는 추가하지 않는다.

## PD3 개수·호출·크기 상한

대응: NFR4.3. 변경 지점과 현재 값의 지위를 한 실행의 설정으로 남긴다.

| 변경 지점 | 현재 기준 | 유지·조정 원칙 |
|---|---|---|
| [CollectionLimits](../../../../../../../../worker/app/collection/limits.py) | 목록 500·상세 200·호출 300·수집 10분·총 50 MiB·응답 10 MiB | 실측 전 제안값. 목록/상세/필수 관계 호출·시간·총량을 함께 검토 |
| [GenerationLimits](../../../../../../../../worker/app/generation/limits.py) | 생성 200·교정 요청당 20/제목당 최대 3, 호출 45초/20초 | 생성 200과 제목당 3은 기존 결정. 생성 상한은 FR1.6 실측으로 조정, 교정 규칙은 확대하지 않음 |
| 같은 생성 상한 | 자료 24,000 B·지시문 포함 32,000 B·출력 4,000 B | 입력/출력 보호 유지. 큰 후보를 무제한으로 제공자에게 보내지 않음 |
| 자식 프레임 | 16 MiB | 직렬화한 최종 프레임 바이트를 확인. 결과 확대 시 전달 가능 여부를 함께 검증 |
| 접수/worker 설정 | PD2 기준 | 시작점·종료 여유·큐/반영 시간을 함께 대조 |

개수 범위나 단일 응답 크기로 제외된 자료는 기존 수집 한계 의미를 보존한다. 필요한 조회의 전체 호출·시간·총량 초과는 기존 수집 실패로 남긴다. 관계 조회를 조용히 줄여 표면상 성공률을 올리지 않는다. 생성 상한으로 만들지 못한 후보는 기존 미제공/실패 의미에 맞춰 기록한다.

결과 프레임·스키마·api 수신·DB 반영까지 동일 실행을 대조한다. 큰 결과를 잘라 전송해 정상 완료로 만들지 않는다. 기존 실패 신호/시한 경로를 유지하며 크기 제한 조정이 필요하면 근거를 남긴다. 스트리밍 결과나 결과 분할 프로토콜은 새로 만들지 않는다.

## PD4 측정 순서와 확정 기록

1. 코드 구현 후 기존 합성 시험에 새 등록·관측 전달·개수/시간/크기 경계 사례를 연결한다. 생성·외부 HTTP는 합성 제공자로 확인하고 실제 분석 결과와 구분한다.
2. OQ2 대상, 연결 회원의 실제 기여, 대상 리비전, 환경, 자격정보, 허용 자료/비용을 확인한다. 현재 한도 설정·모델·소비자 수·코드 커밋을 고정해 기록한다.
3. 새 모달 주소 등록과 요청별 동의를 통해 실제 GitHub → 실제 생성 → 결과 수신 → DB 반영 → 본인 화면 Catch/근거를 확인한다.
4. PD1 집계와 PD2 시각, PD3 자원 한계를 대조한다. 처음 막힌 구간뿐 아니라 그 조정이 다음 구간에 미치는 영향을 검토한다.
5. 필요한 상한 변경은 값/지위/근거/영향을 기록하고, 변경한 경계의 합성 검사와 허용된 실제 실행으로 확인한다. 반복 튜닝 플랫폼을 만들거나 정상 완료 재분석을 허용하지 않는다.
6. 최종 설정·실측값·제외 이유·미확인 범위·성공/실패/미실행을 [OD1](observability-design.md#od1-실제-완료-증거)에 남긴다.

개발 반복이 필요하면 개발·시험 자료의 초기 상태와 허용된 실행 조건을 정한다. 운영 결과 삭제·정상 완료 요청의 재분석 우회·권한 우회는 측정 수단이 아니다. 비용 또는 대상 준비가 없으면 값을 임의 확정하지 않고 실측을 미실행으로 둔다.

## 최적화·기술 경계

현재 비동기 큐, DB 트랜잭션, 기존 페이지 조회·관계 조회·후보 묶음을 재사용한다. 회원별 UNIQUE와 복합 FK를 위한 키 외에 추측으로 인덱스·캐시·풀 크기를 늘리지 않는다. 실제 느린 구간의 근거 없이 병렬 생성·소비자 증설·별도 큐·CDN·새 부하 도구를 추가하지 않는다.

최종 U7 성능 판정에는 구현된 새 경로의 측정이 필요하다. 과거 10월 측정과 설계 문서의 값은 참고이며 이를 완료 증거로 전용하지 않는다.
