# U7 저장소·분석 — 규모와 자원 설계

작성일: 2026-10-29. [확인한 작성안](nfr-design-questions.md), [규모 요구사항](../nfr-requirements/scalability-requirements.md), [C-03 계약](../../../inception/contract-design/contract-summary.md)을 적용한다. 구현·용량 측정·U2 실제 연결 완료 기록이 아니다.

## SC1 현재 실행 규모

대응: NFR4.4. 기존 web·api·worker와 PostgreSQL·Redis/BullMQ 구성을 사용한다. worker 프로세스당 동시 분석 1을 유지한다. 전체 동시 수는 실행 중인 소비자들의 합이므로 측정 시 소비자 수·설정·환경을 함께 적는다.

한 요청은 기존 자식 프로세스에서 수집 → 후보 → 생성을 수행한다. 생성 병렬화나 자동 증설로 약 500개 반영 조건을 우회하지 않는다. 큐 대기는 정상적으로 생길 수 있으나 접수 응답을 완료로 바꾸지 않는다. 사용자 화면은 기존 이력과 상태 새로고침을 사용한다.

| 자원 | 제한 자리 | 넘거나 사용할 수 없을 때 |
|---|---|---|
| 요청당 GitHub 자료 | CollectionLimits | 기존 범위 한계/수집 실패 |
| 요청당 생성 비용·시간 | GenerationLimits와 worker 마감 | 기존 미생성/부분 실패·확인된 실패 |
| 회원별 하루 접수 | U2 DailyRunLimit | 429 DAILY_LIMIT_REACHED, 새 요청 저장 없음 |
| 동시 실행 | 기존 worker concurrency=1/프로세스 | 큐 대기, 기존 접수 시한 관측 |
| 결과 전달 | 기존 자식 프레임·메시지 검사 | 전달/검증 실패를 성공으로 숨기지 않음 |

현재 제약 근거: [worker 큐 소비자](../../../../../../../../worker/docs/queue-consumer.md). 자료 크기와 하루 접수 횟수는 별개다. 하루 한도에 여유가 있어도 한 요청의 시간·호출·입출력 제한은 지킨다.

## SC2 새 접수와 하루 소비

대응: NFR4.5. 기존 [AnalysisIntakeService](../../../../../../../../api/src/analysis-intake/analysis-intake.service.ts)의 새 요청 생성 분기에 소비를 삽입한다. 저장과 분리된 선차감이나 U7 전용 카운터는 만들지 않는다.

| 순서 | 처리 | 소비 |
|---|---|---|
| 입력·키 형식 확인 | 기존 허용 본문과 요청 지문 검사 | 없음 |
| 같은 키·같은 본문 | 기존 요청 응답, 현재 조건으로 재접수하지 않음 | 없음 |
| 새 키 예비 확인 | 실제 연결·본인 등록·현재 공개/지원/판본 확인. 외부 호출은 DB 트랜잭션 밖 | 없음 |
| 기존 접수 트랜잭션 | 멱등·회원 잠금 뒤 확인 대상 재대조 | 아직 없음 |
| 진행/과거 결과/재요청 판정 | 같은 저장소 ACTIVE는 기존 요청 반환, 다른 ACTIVE 또는 금지된 재분석은 기존 오류 | 없음 |
| 실제 신규 요청 생성 | consume(memberId, ANALYSIS, now, manager), ALLOWED면 요청/동의/시도/멱등 저장 | 한 번 |
| 커밋 뒤 큐 전달·실행 | 기존 dispatcher, worker, receiver | 추가 소비·실패 환급 없음 |

now는 접수 판정의 서버 시각이며 KST 날짜 계산은 U2 제공자가 맡는다. 같은 manager를 전달해 저장 실패 시 소비와 요청 모두 롤백한다. LIMIT_REACHED면 C-03의 429와 “오늘 한도에 도달했습니다”를 반환하고 요청·동의·시도를 남기지 않는다. 잔여 횟수를 응답하거나 U7이 날짜별 값을 별도로 계산하지 않는다.

동일 키 조회와 새 키의 기존 ACTIVE 반환은 새 실행이 아니다. 확인된 실패의 재요청은 새 동의·키·요청이므로 하루 한도를 새로 소비한다. 접수 뒤 외부 실패·큐 전달 실패·시한 종료는 환급하지 않는다.

접수 잠금과 C-03 원자적 소비는 기존 보호를 사용한다. 새로운 분산 잠금·중복 제거 서비스·재전송 플랫폼을 만들지 않는다. U2 구현이 제공되지 않았으면 계약에 맞는 합성 제공자로 독립 검사하되 실제 연결 성공으로 기록하지 않는다.

## SC3 저장·조회와 공유 자원

회원별 등록은 UNIQUE(member_id, repository_id)로 중복 자료를 제한한다. 목록·접수·결과 조회는 회원 조건을 포함하며 요청의 등록 FK는 [LC2](logical-components.md#lc2-등록과-요청-사본)를 따른다. 전역 선정 목록을 모든 회원에게 복제하거나 다른 회원의 등록을 공유해 사용하지 않는다.

기존 DB 연결 풀·큐 연결·목록 페이징을 재사용한다. 사용자 데이터 수명이 끝나는 조건은 C-06 탈퇴와 기존 부모 삭제다. U7 사용자용 등록 삭제, 자동 보관 만료·청소 스케줄러·추가 파일 저장소는 도입하지 않는다.

여러 서비스가 PostgreSQL·Redis를 공유한다. 오류가 공유 자원에서 비롯되면 회원별 잠금만으로 전체 영향이 격리된다고 주장하지 않는다. 기존 상태·로그와 시한을 통해 확인하고 새 용량 목표·샤딩·읽기 복제본·자동 확장 임계값을 만들지 않는다.

## SC4 검증과 판단 경계

- C-03 합성 제공자에서 신규 ALLOWED/LIMIT_REACHED와 동일 키·진행 요청 재사용을 검사한다. 요청 저장 실패가 소비까지 롤백되는지 같은 DB 트랜잭션 경계로 확인한다.
- U2 실제 제공자와 연결한 정상 소비·한도 거부 결과는 별도로 남긴다. KST 경계·원자적 소비 구현 자체의 정본은 U2이며 U7에서 별도 구현하지 않는다.
- 실제 환경의 소비자 수·큐 대기·요청당 호출/시간/바이트·생성 사용량을 [PD4](performance-design.md#pd4-측정-순서와-확정-기록)로 남긴다.
- 현재 실행 수로 필요한 반영량을 충족하지 못하면 실패 구간과 상한을 기록한다. 병렬 실행 확대가 필요하다는 판단은 이 설계가 미리 승인한 변경이 아니다.

별도 사용자 수·요청률·성장률 수치를 약속하지 않는다. 이 Unit은 시연 규모에서 제한된 자원을 써 실제 분석이 끝나는지 증명한다.
