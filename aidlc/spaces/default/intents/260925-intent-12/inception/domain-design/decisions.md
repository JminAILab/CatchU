## ADR-001: 발행본과 링크를 한 컴포넌트(Publication)로 둔다

### Status: Accepted

### Context

10월 `share-links` 모듈은 링크의 비밀번호·만료·중지·발급 제한을 가진다. 재승인 요구사항은 링크와 발행본을 함께 저장하고(FR4.7), 중지·만료 뒤에도 작성자가 발행본을 보며 삭제는 따로 한다(FR5). 링크 조건은 웹·질의응답·JD 요약·MCP에 같게 적용한다(NFR1). 입력 §2-5는 가장 단순한 안을 기본값으로 하라고 했다.

### Decision

기존 공유 링크 컴포넌트를 발행본까지 넓혀 Publication 하나가 발행본(고정 사본 항목 포함)과 링크를 소유한다. 링크 규칙은 재사용하고, 링크 조건 판정도 Publication이 제공한다(Q1 A).

발행본 소유 사본에는 PDF 쪽별 글과 "읽을 수 없는 쪽" 표시(PublishedPdfPage)도 들어간다. 글 추출이 끝나지 않은 PDF는 발행에 고를 수 없고 이유를 안내한다(PDF 부분은 후순위). 비공개 Catch의 공개 전환은 10월 공개 전환 로직(같은 트랜잭션에서 회원·보호 상태를 잠그고 판정)을 그대로 쓰되 발행 트랜잭션 안에서 부르며, 잠금을 새로 설계하지 않는다(팀장 수정 결정).

### Consequences

- 좋은 점: 발행본과 링크를 한 트랜잭션으로 저장하고, 발행 저장이 실패하면 공개 전환도 하지 않는 규칙(FR4.7)을 한 곳에서 지킨다. 권한 판정이 한 곳이라 경로별로 갈라지지 않는다.
- 나쁜 점: Publication이 커지고 의존하는 컴포넌트(PublishedIndex·BaseSummary·QnA·JdSummary·ClaudeMcp)가 많아진다. 10월 링크 코드에 발행본 사본 저장을 더해야 한다.
- 보안: 링크 조건 판정이 하나라 우회 경로가 줄어든다. 판정 실패는 모든 경로를 막는다.

### Alternatives Rejected

- 발행본과 링크 접근을 두 컴포넌트로 나누기(Q1 B): 링크 판정만 시험하기는 쉽지만, 발행 때 두 컴포넌트의 저장을 묶는 조정이 늘고 "함께 저장" 실패 처리가 복잡해진다.

## ADR-002: AI 생성 공통·질의응답·백그라운드 AI 실행을 api에 둔다

### Status: Accepted

### Context

입력은 AI 생성 공통(인용 기능 연결·근거 검사)과 백그라운드 AI 실행 공통을 팀장의 공용 기반으로 두었다. 질의응답은 큐가 아닌 바로 답하는 경로로 SSE를 내보내고(FR6.2), 기본 요약·JD 요약은 백그라운드로 처리한다(FR6.8). 10월에는 api가 큐로 worker에 분석을 넘기고 worker가 Claude를 부른다.

### Decision

AiGeneration·QnA(SSE)·AiRun(기본 요약·JD 요약 실행)을 api(TypeScript)에 둔다. AiRun은 api 안에서 기존 큐(Redis/BullMQ)를 재사용한다. worker는 저장소 분석과 PDF 글 추출만 맡는다(Q2 A).

### Consequences

- 좋은 점: 근거 검사 규칙이 한 언어·한 곳에 있어 세 기능이 같은 검사를 쓴다. 질의응답을 위해 api→worker 동기 경로나 SSE 중계를 새로 만들지 않는다.
- 나쁜 점: api 안에 백그라운드 실행을 새로 만들어야 한다. 10월 worker의 Claude 호출 코드는 재사용하지 않는다. api에 Claude API 비밀값이 새로 필요하다(공용 인프라 SSM).
- 보안: 외부 AI 호출이 api와 worker 두 곳에 있게 되므로, 비밀값 보호와 보안 점검 LLM 기준을 두 곳 모두에 적용한다.

### Alternatives Rejected

- worker(Python)에 AI 생성 공통과 기본 요약·JD 요약 실행을 두고 질의응답은 api가 worker 동기 경로를 불러 SSE를 중계(Q2 B): 10월 코드를 더 재사용하지만 새 동기 경로와 SSE 중계가 생기고, 질의응답 지연과 실패 지점이 늘어난다.

## ADR-003: PDF 원본과 발행 사본을 S3에 두고 파일 저장을 인터페이스로 감싼다

### Status: Accepted

### Context

PDF는 원본을 보관하고 발행 때 복사해 발행본마다 자기 파일을 가진다(FR3.2). 탈퇴·발행본 삭제는 DB 연쇄 삭제로 하지만 DB 밖 파일은 따로 지워야 한다(FR14.9). 요구사항 OQ1이 저장 위치를 이 단계로 넘겼다. PDF는 후순위다.

### Decision

(Q3, 팀장 답 그대로 요약)

- 저장: PDF 원본과 발행 사본을 S3에 두고, 키는 회원/{memberId}/자료/... 와 회원/{memberId}/발행본/{publicationId}/... 로 둔다(발행본 접두어가 회원 접두어 아래, 팀장 수정 결정).
- 삭제: 탈퇴는 회원 접두어 전체(자료와 발행 사본 모두), 발행본 삭제는 그 발행본 접두어를 목록으로 받아, 자료 삭제는 그 원본 파일만 지운다. S3를 먼저 지우고 DB를 지우며, S3 삭제가 실패하면 성공으로 응답하지 않고 오류를 보인다. 재시도 장치는 없다.
- 열람: presigned URL은 쓰지 않고, api가 요청마다 링크 조건을 확인한 뒤 S3에서 읽어 내려준다.
- 로컬: FileStorage 인터페이스로 감싸 로컬·시험은 로컬 파일, 배포는 S3를 쓴다. 팀원은 S3 없이 개발한다.
- 버킷: 환경별 1개, 공개 차단·자동 암호화 켜기, 버전 관리 끄기.
- 권한: 접근 키 대신 역할. 개발 서버는 EC2 역할(api·worker 공용), EKS는 서비스별 역할(api는 올리기·읽기·복사·목록·삭제, worker는 읽기만).
- 준비: 버킷·권한은 팀장 공용 인프라(#389)로 PDF Unit 시작 때 준비한다.

### Consequences

- 좋은 점: DB가 큰 파일로 불어나지 않고, presigned URL이 없어 링크 조건 우회가 없다. 팀원은 S3 없이 개발한다.
- 나쁜 점: 탈퇴·발행본 삭제에 S3 삭제 단계가 늘고, S3를 먼저 지운 뒤 DB 삭제가 실패하면 DB 행은 남고 파일은 없는 상태가 될 수 있다(오류를 보이고 팀이 확인한다). 공용 인프라 작업이 는다.
- 보안: 버킷 공개 차단·암호화·역할 권한·버전 관리 끔으로 지운 파일이 이전 버전으로 남지 않게 한다.

### Alternatives Rejected

- DB(PostgreSQL)에 저장(Q3 A): 연쇄 삭제가 파일까지 지워 가장 단순하지만, 팀장이 S3를 골랐다(파일 크기와 DB 부담을 피함).

## ADR-004: Catch 설명을 Catch의 속성으로 둔다

### Status: Accepted

### Context

Catch마다 작성자 설명 하나를 두고, 같은 작업이 다시 분석되면 기존 Catch를 참조해 설명이 유지된다(FR2.5). 10월 `catches` 모듈이 Catch를 소유한다.

### Decision

설명을 Catches 컴포넌트의 Catch 속성(authorDescription)으로 둔다(Q4 A).

### Consequences

- 좋은 점: 재분석 때 설명 유지가 자연히 성립하고 탈퇴 연쇄 삭제를 그대로 따른다. 소유 경계가 늘지 않는다.
- 나쁜 점: 발행·링크 덩어리가 10월 Catch 모듈(B 파트 코드)을 고쳐야 한다. Unit 나누기에서 담당 확인이 필요하다.

### Alternatives Rejected

- 별도 "Catch 설명" 컴포넌트(Q4 B): Catch 모듈을 덜 건드리지만 소유 경계와 재분석 때의 연결 유지 규칙이 하나 더 생긴다.

## ADR-005: 조각 나누기는 발행 트랜잭션 안에서, 임베딩과 기본 요약은 커밋 뒤 AiRun 작업으로 한다

### Status: Accepted

### Context

요구사항은 발행할 때 사본을 조각으로 나누고 위치를 기록하며(FR4.7), 기본 요약은 발행 뒤 백그라운드로 만든다(FR2.7). 임베딩(Voyage AI)과 생성(Claude)은 외부 호출이라 발행 트랜잭션에 묶으면 발행이 외부 지연·실패에 묶인다. 사후 처리가 멈추거나 실패하면 그 발행본은 질의응답·JD 요약을 쓸 수 없게 되므로 상태와 시한이 필요하다.

### Decision

(팀장 수정 결정)

- 조각 나누기·위치 기록은 발행 트랜잭션 안에서 Publication이 PublishedIndex를 불러 한다. PDF는 발행본 소유 사본(PublishedPdfPage)만 쓴다.
- 커밋 뒤 Publication이 api 안 기존 큐(AiRun)에 임베딩 작업과 기본 요약 작업을 넣는다. 각 작업은 PublishedIndex·BaseSummary가 AiRun에 등록한 처리기가 실행한다. 이것이 "발행 완료"의 전달 방식이다.
- PublishedIndex가 발행본마다 색인 상태(대기·완료·실패)와 처리 시한(PublicationIndex)을 소유한다. 처리 시한 판정은 처리기와 무관하게, 색인·기본 요약·JD 요약의 상태를 읽을 때 deadlineAt이 지났으면 그 자리에서 실패로 확정한다. 작업 등록이 실패하거나 큐에서 작업이 사라져도 "대기"에 영원히 남지 않고, 색인은 [검색 다시 준비], 기본 요약은 [다시 만들기]로 다시 할 수 있다(팀장 결정, 승인 때).
- PDF 복사는 발행 트랜잭션보다 먼저 하고 복사가 실패하면 발행 실패로 끝낸다. 트랜잭션이 실패하면 그 발행본 접두어를 지우고, 그래도 남은 파일은 탈퇴 때 회원 접두어째 지운다. 청소 장치는 두지 않는다(PDF 후순위, 세부는 계약 설계).
- 색인이 준비 전이거나 실패면 받은 사람에게 질의응답·JD 요약을 아직 쓸 수 없다고 보인다. 열람·기본 요약은 그대로 제공한다. 실패 때의 다시 시도는 ADR-007이다.

### Consequences

- 좋은 점: 조각과 위치가 발행과 함께 확정돼 발행본 고정 원칙과 맞고, 발행이 외부 임베딩·생성 지연에 묶이지 않는다. 호출 그래프에 순환이 없다(Publication → PublishedIndex·AiRun, BaseSummary → Publication).
- 나쁜 점: 발행 직후 잠시 질의응답·JD 요약을 쓸 수 없는 상태가 생기고, 그 상태를 화면에서 구분해야 한다(기능 설계). Publication과 PublishedIndex가 다른 Unit이면 발행 트랜잭션 안의 호출 경계를 계약 설계에서 먼저 정해야 한다.
- 보안: 처리기도 사본을 읽을 때 Publication의 링크 조건·삭제 상태를 따른다. 삭제된 발행본의 늦은 결과는 부모 외래 키로 거부되고 버려진다(FR14.10).

### Alternatives Rejected

- 조각 나누기까지 모두 발행 뒤 구독으로 처리: FR4.7("발행할 때 조각·위치 기록")과 어긋나고, 실패 시 발행본에 조각이 하나도 없는 상태가 생긴다.
- 임베딩까지 발행 트랜잭션 안에서 처리: 발행이 외부 임베딩 지연·실패에 묶인다.
- PDF 글을 Materials 원본에서 다시 읽어 조각 나누기: 발행 뒤 원본 수정·삭제가 발행본 색인에 섞이고 선언되지 않은 의존이 생긴다.

## ADR-006: 10월 분석 경로를 RepositoryAnalysis 한 컴포넌트로 재사용한다

### Status: Accepted

### Context

10월 api에는 member-repositories·analysis-intake/queue/receiver/deadline·member-analysis·result-application 모듈이, worker에는 collection·candidates·generation·consumer가 있다. 이번 변경은 등록 때 관계 검사를 없애고 수집 상한을 올리는 것뿐이다(FR1.2, FR1.6). 입력 §2-5는 설계가 공수를 늘리지 않게 하라고 했다.

### Decision

이 경로 전체를 논리 컴포넌트 RepositoryAnalysis 하나로 보고, 10월 모듈 경계를 그대로 둔다. 새 컴포넌트로 다시 나누지 않는다.

### Consequences

- 좋은 점: 10월 코드와 시험을 그대로 쓰고 변경 범위가 작다.
- 나쁜 점: 컴포넌트 하나가 api·worker에 걸쳐 크다. 내부 구조는 이 문서에서 다시 설계하지 않는다.

### Alternatives Rejected

- 접수·큐·수집·반영을 각각 컴포넌트로 다시 나누기: 이번 범위에 바뀌지 않는 부분을 다시 설계하는 일이 되어 공수만 늘린다.

## ADR-007: 색인 실패 때 작성자에게 [검색 다시 준비]를 둔다(요구사항 밖, 팀장 결정)

### Status: Accepted

### Context

임베딩은 발행 뒤 백그라운드로 돌고(ADR-005), FR6.8은 자동 복구·자동 재시도를 두지 않는다. 그래서 임베딩이 실패하면 그 발행본은 다시 발행하지 않는 한 질의응답·JD 요약을 계속 쓸 수 없다. 재승인 요구사항에는 이 경우의 다시 시도 경로가 없다.

### Decision

**이 버튼은 요구사항에 없던 것을 팀장 결정(2026-10-24)으로 더한 것이다.** 색인 상태가 실패일 때만 작성자에게 [검색 다시 준비] 버튼을 둔다. 작성자만, 실패 상태에서만 받고, 상태를 대기로 돌려 임베딩만 다시 맡기며, 하루 실행 제한에 세지 않는다. 요청은 Publication이 받아(작성자 확인) PublishedIndex에 넘긴다.

### Consequences

- 좋은 점: 외부 임베딩의 일시 실패 하나로 발행본을 새로 만들 필요가 없다. 사람이 누를 때만 다시 돌아 자동 재시도 금지(FR6.8)와 어긋나지 않는다.
- 나쁜 점: 요구사항에 없던 화면 요소와 시험 사례가 하나 는다(입력 §2-5의 설계 범위 상한에 대한 팀장 예외). 하루 실행 제한에 세지 않으므로 Voyage 호출이 늘 수 있다. 실패 상태에서만 받도록 해 반복 남용을 막는다.
- 보안: 작성자 본인 확인과 실패 상태 확인을 거친 요청만 받는다.

### Alternatives Rejected

- 다시 시도 경로를 두지 않고 새 발행만 안내: 요구사항 그대로라 가장 단순하지만, 링크를 이미 보낸 뒤라면 받은 사람이 새 링크를 다시 받아야 한다.
- 자동 재시도: FR6.8과 어긋난다.

## ADR-008: 분석의 요청별 동의와 다른 AI 기능의 첫 이용 동의를 병존시킨다

### Status: Accepted

### Context

10월 코드에는 분석 요청마다 받는 `analysis_consent`가 있다. 재승인 요구사항 FR20.1은 외부 AI 전송을 첫 이용 때 한 번 동의받는다고 했다.

### Decision

(팀장 수정 결정) 분석은 10월처럼 요청마다 동의(AnalysisConsent, AnalysisRequest.consentRef가 가리킴, 재요청 때 새 동의)하고, 그 밖의 AI 기능(요약·질의응답·JD 요약·PDF 처리)은 AiConsent의 첫 이용 동의를 쓴다. 두 엔티티를 병존시키며, FR20.1의 분석 동의는 10월 요청별 동의가 맡는다.

### Consequences

- 좋은 점: 10월 분석 경로와 시험을 바꾸지 않는다. 분석은 요청마다 저장소·범위가 달라 요청별 동의가 더 정확하다.
- 나쁜 점: 동의 엔티티가 둘이라 고지 화면 문구와 "첫 이용"의 범위를 기능 설계에서 맞춰야 한다.
- 보안: 두 동의 모두 회원 탈퇴 때 연쇄 삭제된다.

### Alternatives Rejected

- 분석 동의를 AiConsent로 흡수: 10월 분석 경로와 시험을 고쳐야 해 공수가 는다.

## ADR-009: Claude 연결의 OAuth 상태를 ClaudeMcp가 PostgreSQL에 소유한다

### Status: Accepted

### Context

FR13.1은 Claude 웹·Desktop의 같은 원격 연결을 최소 OAuth로 승인하고, 자동 갱신 없이 만료되면 재승인하며, 전체 연결 해제를 둔다. 승인 코드·토큰·클라이언트 등록을 어디에 두는지 정해야 해제·만료·탈퇴가 성립한다.

### Decision

(팀장 수정 결정) ClaudeMcp가 같은 PostgreSQL에 클라이언트 등록(McpClient)·승인 코드(McpAuthorizationCode, 짧게·한 번)·접근 토큰(McpAccessToken, 해시·회원·만료) 표를 소유한다. 갱신 토큰은 두지 않는다. 전체 해제는 회원 기준으로 그 회원의 접근 토큰과 연결 기록을 모두 지우고, 탈퇴는 연쇄 삭제를 따른다. OAuth 규칙은 MCP 공식 SDK의 인증 도구로 처리하며 세부는 기능 설계에서 정한다.

### Consequences

- 좋은 점: 해제·만료·탈퇴가 DB 삭제와 만료 시각으로 단순하게 성립한다. 별도 인증 서버를 두지 않는다.
- 나쁜 점: 갱신 토큰이 없어 만료 때마다 다시 승인해야 한다(FR13.1이 정한 대로).
- 보안: 승인 코드와 접근 토큰은 해시로만 저장하고 승인 코드는 한 번만 쓴다. 공식 SDK의 인증 도구를 써서 OAuth 규칙을 직접 구현하지 않는다.

### Alternatives Rejected

- 외부 인증 서비스에 위임: 계정·비밀값·연동이 하나 더 늘어 공용 인프라 작업이 커진다.
- 갱신 토큰 두기: FR13.1의 "자동 갱신 없음"과 어긋난다.
