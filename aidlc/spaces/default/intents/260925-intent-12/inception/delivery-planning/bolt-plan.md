# CatchU 12월 범위 — Bolt 계획

작성일: 2026-10-26. 입력: [재승인 요구사항](../requirements-analysis/requirements.md)(requirements), [사용자 스토리](../user-stories/stories.md)(stories), [컴포넌트 목록](../domain-design/components.md)(components), [Unit 정의](../units-generation/unit-of-work.md)(unit-of-work), [Unit 의존](../units-generation/unit-of-work-dependency.md)(unit-of-work-dependency), [스토리·Unit 대응](../units-generation/unit-of-work-story-map.md)(unit-of-work-story-map), [계약 요약](../contract-design/contract-summary.md)(contract-summary), [납품 계획 질문·답변](delivery-planning-questions.md)(Q1~Q7).

Bolt는 구현 단계에서 한 번에 지어 실제로 돌아가는 결과까지 가는 작업 묶음이다. 이 계획은 Unit 하나를 Bolt 하나로 둔다. 담당은 [담당 배정](team-allocation.md), 순서의 이유는 [순서 근거](risk-and-sequencing-rationale.md), 외부 의존은 [외부 의존](external-dependency-map.md)에 있다.

## 착수 규칙

- 일정은 요구사항 「지위와 일정」을 따른다(11/13 1차 통합 확인 → 11/30 개발 완료 → 12월 1~9일 리허설·제출 자료 → 12/10 제출).
- 착수 날짜는 정하지 않는다. B1(U1)이 통합 브랜치에 합쳐진 뒤, 10월 일을 마친 사람부터 자기 Unit을 맡는다(Q7). 승인된 Unit 문서의 "11/2부터 병행 착수"는 그대로 두며, 착수 시점은 이 계획이 정한다(Q6).
- 의존 YAML의 `depends_on`은 모두 빈 목록이라 B1 뒤에는 어느 Unit이든 맡을 수 있다. Unit 의존 문서의 그림·표(통합·완료 전제)는 실제 연결 확인과 완료 순서로만 쓴다.
- 경계를 주는 쪽은 착수 직후 첫 작은 PR(경계의 함수 모양·표·가짜 구현)을 낸다. 받는 쪽은 그 PR과 합성 제공자로 개발한다(Q1, 계약 요약).
- 각 Unit은 처음 실제로 연결될 때 '최소 연결 첫 결과'를 한 번 승인받는다(team.md). 합성 제공자로 통과한 것을 실제 연결 성공으로 보고하지 않는다.

## B1 — AI 생성 관문 최소 경로 (U1, walking skeleton)

- **진행 방식:** 맡기 없이 저장소 본체 폴더(새 clone)에서 통합 브랜치로 먼저 짓고 합친다(Q3).
- **완료 기준:** 공용 계약 최소 부분과 실제 Claude 인용 호출로 관문 네 가지(응답을 항목으로 묶기·인용 보존·원문 위치 연결·거부 사례 처리)가 끝까지 돈다. 시험이 통과하고 통합 브랜치에 merge commit으로 합쳐진다. '최소 연결 첫 결과'를 승인받는다.
- **확인하려는 것:** 실제 Claude 인용 호출로 AI 생성 공통의 핵심이 이 저장소에서 돈다. 통과하지 못하면 원문 열람부터 확보하고 다른 생성 방식은 다시 산정한다(요구사항 A04).
- **보일 결과:** 시험 자료 하나로 인용이 붙은 항목과 거부 사례가 나오는 실제 호출 한 번.

## B2 — 공용 기반 (U2)

- **진행 방식:** 팀장이 U2를 맡아 맡기·범위 고정·단계 진행을 먼저 확인한다. 이 확인은 팀원이 맡는 조건이 아니다(Q3·Q7). 착수 직후 경계 함수 모양·표·가짜 구현을 첫 작은 PR로 낸다.
- **완료 기준:** U2 책임(근거 검사 공통, 백그라운드 실행·처리 시한, 하루 실행 제한, 첫 이용 동의, 파일 저장 인터페이스·로컬 구현, 탈퇴, 시작 안내·기본 오류, 외부 사용자 Google 로그인 대상 설정, 통합 확인 진행)이 시험을 통과하고 통합 브랜치에 합쳐진다.
- **확인하려는 것:** 팀 방식의 맡기 흐름이 우리 저장소에서 돈다. 공용 계약이 다른 Unit의 합성 제공자와 실제 구현 사이에서 같은 모양을 유지한다.
- **보일 결과:** 다른 Unit이 합성 제공자 대신 U2 실제 구현으로 바꿔 시험을 돌린 결과.

## B3 — 발행본 색인·검색 (U3)

- **진행 방식:** 착수 직후 조각 나누기 호출 자리(C-08)·색인 상태·검색 인터페이스의 첫 작은 PR을 낸다. 발행본 시험 자료(C-07)로 먼저 개발한다.
- **완료 기준:** 조각 나누기·위치 기록, 임베딩 작업·색인 상태·처리 시한, 의미 검색, [검색 다시 준비]가 시험을 통과한다. U4와 실제 연결을 확인하고 합쳐진다.
- **확인하려는 것:** 발행 트랜잭션 안의 조각 나누기와 커밋 뒤 임베딩이 계약대로 맞물린다.
- **보일 결과:** 발행한 시험 발행본을 검색해 원문 위치가 붙은 조각이 나오는 것.

## B4 — 발행·링크 (U4)

- **진행 방식:** 착수 직후 텍스트 자료 표(C-13)·Catch 설명 칸(C-14)·발행본 최소 DB(C-07)·발행본 접근(C-10)의 첫 작은 PR을 낸다.
- **완료 기준:** Catch 설명·텍스트 자료, 발행(선택·공개 전환·조각 나누기 호출), 링크 조건·열람, 중지·만료·삭제, 발행 후 확인이 시험을 통과한다. U3과 실제 연결을 확인하고 합쳐진다.
- **확인하려는 것:** 고정 발행본과 링크 조건 판정이 받은 사람 화면·질의응답·JD·MCP에 같은 결과를 준다.
- **보일 결과:** 작성자가 Catch와 텍스트 자료를 골라 발행하고, 받은 사람이 링크로 여는 흐름.

## B5 — Claude MCP 본인 연결 (U6)

- **진행 방식:** 텍스트 자료 표·Catch 설명 칸의 계약 모양으로 시험용 자료를 써서 개발한다. U4와는 통합 때 만난다.
- **완료 기준:** 최소 OAuth 연결·전체 해제·첫 연결 동의, 본인 조회 도구, 회원 기준 빈도·응답 크기 제한이 시험을 통과한다. 외부에서 닿는 HTTPS 개발 서버(#304)에서 실제 Claude 웹·Desktop 연결을 확인한다.
- **확인하려는 것:** 구직자 본인의 Claude가 CatchU 자료를 계약대로 읽는다.
- **보일 결과:** Claude에서 본인 Catch·텍스트 자료를 조회하는 실제 대화.

## B6 — 저장소·분석 (U7)

- **진행 방식:** 기다리는 Unit이 없어 계약을 기다리지 않는 저장소 등록부터 시작한다(입력 §3).
- **완료 기준:** 관계 사전 검사 없는 등록과 분석 중 본인 커밋 확인, 수집 상한 상향(커밋 약 500개 실측), 이유별 거부·재요청이 시험을 통과하고, 실제 분석 확인(팀장 계정 CatchU 저장소와 거부 사례)을 마친다.
- **확인하려는 것:** 10월 분석 경로를 그대로 쓰면서 바뀐 등록·수집 규칙이 실제 저장소에서 돈다.
- **보일 결과:** 시연 저장소 등록부터 분석 결과가 Catch로 반영되는 실제 실행.

## B7 — JD (U10)

- **진행 방식:** JD 저장(US6.5)은 U3·U4 없이 시작한다. JD 요약은 C-09·C-10 첫 작은 PR과 합성 제공자로 개발한다.
- **완료 기준:** JD 관리 페이지와 JD 요구사항별 요약(색인 준비 전·실패 때 실행하지 않음)이 시험을 통과한다. U3·U4와 실제 연결을 확인하고 합쳐진다.
- **확인하려는 것:** 받은 링크의 발행본으로 JD 요구사항마다 근거가 붙은 요약이 나온다.
- **보일 결과:** 로그인한 받은 사람이 저장한 JD로 요약을 실행하고 다시 여는 흐름.

## B8 — RAG 응답 (U5)

- **진행 방식:** 팀장이 U3 뒤에 이어 맡는다(Unit 나누기 Q1). 팀장 몫이 밀리면 11/13에 먼저 넘길 후보다(Q1).
- **완료 기준:** 질의응답(SSE·질문 횟수), 기본 요약, RAG 품질 평가가 시험을 통과한다. U3·U4와 실제 연결을 확인하고 합쳐진다.
- **확인하려는 것:** 받은 사람이 근거가 붙은 답과 요약을 받는다.
- **보일 결과:** 받은 링크에서 기본 요약을 보고 질문해 근거 강조가 붙은 답을 받는 흐름.

## B9·B10 — 후순위 (U8 PDF 자료, U9 받은 사람의 Claude 연결)

- **진행 방식:** 순서 맨 뒤에 둔다. 11/13 1차 통합 확인에서 계속할지 뺄지와 담당을 정한다(Q2, 요구사항 「지위와 일정」). 핵심 Unit을 끝낸 사람이 이어 맡는다.
- **완료 기준:** U8은 PDF 업로드·글 추출·발행 사본·S3 접두어 삭제 확인, U9는 받은 링크 읽기 도구와 비밀번호 링크 웹 안내가 시험을 통과하고 합쳐진다. 빼면 해당 부분만 빠지며 승인 기준을 어기지 않는다.
- **확인하려는 것:** 후순위 기능이 핵심 흐름을 기다리게 하지 않고 붙는다.

## 합치기와 dev 반영

- 각 Unit은 팀장이 intent 통합 브랜치에 merge commit으로 합친다. 통합 브랜치에 합칠 때도 CI를 돌린다(팀장이 #389로 `ci.yml`에 `intent/**` 트리거를 더함, Q3).
- 팀원이 맡기 전에 팀장이 `dev`를 통합 브랜치에 merge commit으로 가져온다(Q7).
- 통합 브랜치는 PR·작성자 외 승인 1건·merge commit으로 `dev`에 올린다(입력 §3).
- 팀 방식이 막히면 구현만 이슈 → 브랜치 → PR로 바꾼다(Q3).
