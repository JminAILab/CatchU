# CatchU 12월 사용자군과 역할

## Sources

[승인 요구사항](../requirements-analysis/requirements.md)(requirements), [확인된 작성 계획](user-stories-questions.md), [의도·범위의 인계 결정](../../ideation/approval-handoff/decision-log.md)을 근거로 한다. 최초 의도에서 구분한 구직자·수신자·기업·운영 역할에 요구사항의 최종 권한 결정을 적용했다. 실제 이용자 조사 결과를 대신하는 가상 인물 설정은 하지 않는다.

## P1. 기록을 설명하고 공유를 통제하는 작성 회원

- 역할: 자기 Catch·강점 주장·서류를 관리하는 회원이며 기업의 발견·제안을 받을 때는 구직자다.
- 목표: 확인 가능한 기록에 자기 설명을 붙이고, 목적에 맞는 자료를 전달하며, 현재 공개·기업 열람·개별 공유와 연락을 각각 통제한다.
- 어려움: 기록만으로 선택 이유·역할을 설명하기 어렵다. 원본 수정·숨김과 발행본 중단의 차이를 이해해야 한다.
- 맥락: Google 로그인, GitHub 연결·분석 동의, 지원 공개 저장소 요청을 거쳐 자료를 준비한다. Catch마다 주장 작성이나 여러 주장 작성을 강제하지 않는다.
- 권한 경계: 본인 관리와 외부 제공은 다르다. 숨김 자료의 관리 확인은 가능하나 현재 외부 자료/RAG/MCP·새 발행에서 쓰지 않는다. 이미 발행한 고정 공유본은 독립된 조건으로 제공한다.
- 근거: FR1~5·FR8·FR10~14·FR16. 인구통계·기술 숙련도·사용 빈도는 미확인이다.

## P2. 전달받은 근거를 읽는 링크 수신자

- 역할: 개별 고정 공유본을 전달받아 지원자의 경험·근거를 검토한다. 비로그인 수신자도 포함한다.
- 목표: 짧은 요약에서 상세 자료로 들어가고, JD와 질문으로 확인된 내용·작성자 설명·AI 해석 및 남은 확인 사항을 구분한다.
- 어려움: 직접 GitHub 기록 전체를 읽을 시간이 부족하며, 자료 부재를 역량 부재로 오해할 수 있다. AI가 참고하지 못한 PDF와 접근 거부·조회 실패를 구분해야 한다.
- 맥락: 링크의 비밀번호·만료·중단·삭제 조건을 충족한 범위에서만 열람·JD/RAG를 이용한다. 작성자의 이후 원본 변경 내역은 안내 대상이 아니다.
- 권한 경계: 받은 링크만으로 기업 검색·제안·기업 소속 권한을 얻지 않는다. 비로그인 웹 열람과 기업 회원의 ‘받은 공유본 MCP’ 자격은 서로 다른 경로다.
- 근거: FR2.7·FR3~6·FR13.3·FR16.3. 직급·사용 빈도·실제 검토 효율 개선은 미확인이다.

## P3. 업무 역할에 따라 후보자를 검토하는 기업 회원

- 역할: 개인 회원 계정이 기업 소속 승인과 업무 역할을 받아 활동한다. 기업 등록·소속 승인 자체는 신원 인증이 아니다.
- 목표: 허용 자료로 후보자를 발견·검토하고 적절한 제안을 보내며 소속의 업무 권한을 관리한다.
- 어려움: 역할 자격과 후보자 자료 허용 조건을 함께 확인해야 한다. 검색 참여와 제안 수신 동의, 계정 차단과 일반 열람의 차이를 이해해야 한다.
- 맥락: 기업명으로 등록하거나 소속을 신청한다. 개인 소셜 활동은 회사 공동 계정 활동이 아니다.

| 하위 역할 | 허용 업무 | 구분할 제한 |
|---|---|---|
| P3-A 기업 관리자 | 소속 승인·해제·역할 관리, 허용 자료 검토·검색·제안 | CatchU 운영자 권한이나 타인의 연락처 동의를 대신 얻지 않음 |
| P3-H 채용 담당자 | 허용 자료 검토·검색·제안 | 소속·역할 관리 불가 |
| P3-R 검토자 | 허용 자료 열람·JD/RAG, 자격을 충족하는 받은 공유본 MCP | 기업 검색·제안·소속 관리 불가 |

소속·역할 상실, 기업 일시 중단·종료, 상대 동의·숨김·허용 철회와 자료 수명을 함께 적용한다. 역할 회복이 연락처 조회 권한을 자동 복원하지 않는다. 근거: FR7~15. 실재 기업·소속 확인 수준 및 사용 빈도는 추정하지 않는다.

## P4. 테스트 서비스를 운영하고 결과를 확인하는 개발팀

- 역할: 운영 권한을 가진 개발팀 구성원이 문제를 수동 접수하고 최소 조치·정리를 수행한다. 배포·검증·제출에서는 실행 책임이 다른 작업을 구분한다.
- 목표: 테스트 이용자가 연락을 통제하고 탈퇴·정리를 마칠 수 있게 하며, 실제 외부 서비스의 성공·실패·미검증 상태를 근거로 판단한다.
- 어려움: 두 가지 최소 운영 조치로 모든 공개 자료·AI 남용을 해결할 수는 없다. 모의 연결이나 승인 문서를 실제 배포·품질의 증거로 혼동하지 않아야 한다.
- 맥락: 기존 연락 경로로 접수·회신한다. 새 관리자 화면·포괄 비공개 자료 조회·자동 제재 판정을 필수로 추가하지 않는다.
- 책임: NCP 배포·환경 구성은 팀장으로 확정됐다. 기능 검증·오류 수정·접수 확인·개인정보 처리·제출 역할의 미지정 부분은 OQ11·13~15에 따라 별도로 확정한다. 운영자라는 이유로 이 책임을 모두 배정하지 않는다.
- 근거: FR14~19·NFR2~6. 구체 인력·가용 시간·법적 검토 완료·일정 가능성은 미확인이다.

## 관계와 우선순위

P1이 고정 공유본을 발행하면 P2가 읽는다. P1이 기업 검색에 동의하고 자료를 허용하면 검색 자격이 있는 P3가 발견·제안한다. 수락 후 P1의 별도 동의로 특정 P3 회원에게만 연락처를 전달한다. P4는 필요한 운영 조치와 검증을 담당하지만 자료 접근을 포괄적으로 얻지 않는다. 같은 사람이 P1·P2·P3 역할을 함께 가질 수 있다.

핵심 가치 흐름은 작성자와 검토자의 근거 전달이다. 대표 구성의 기존 1순위를 유지하며, 기업·MCP·자료 수명·운영의 필수 의존성을 함께 충족한다. 이는 사용자군 사이에 새로운 구현 순위나 담당 배분을 확정한 것이 아니다. 소셜·신고 등의 비필수 지위는 실제 제공 시점의 역할·검사 조건과 함께 유지한다.

## Assumptions & Open Questions

새 제품 전제: None. 역할은 승인 요구사항에서 도출했다. 실제 사용자 특성·사용 효과는 OQ7의 조사, 실제 팀 구성·가용량은 OQ15의 후속 확인 대상이다. 운영 책임의 미결은 위 P4의 근거와 시점을 유지한다.
