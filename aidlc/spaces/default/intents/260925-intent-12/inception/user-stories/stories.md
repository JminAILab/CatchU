# CatchU 12월 사용자 스토리 (2026-10-24 재승인판)

## Sources

[재승인 요구사항](../requirements-analysis/requirements.md)(requirements), [작성 계획·답변](user-stories-questions.md)의 2026-10-24 재승인 계획과 Q2, [사용자군 정의](personas.md)를 따른다. FR·NFR·OQ·C·A는 재승인 요구사항의 식별자다. 수용 기준은 요구사항의 확정 동작을 풀어 쓴 것이며 실제 구현·시험 결과를 뜻하지 않는다. 9월 스토리는 이 파일의 git 이력에 당시 판본으로 남는다.

## 읽는 방법과 공통 기준

`USx.y`는 사용자 결과, `ACx.y.z`는 Given/When/Then 수용 기준이다. ID는 요구사항과 같은 방식으로 9월 번호를 유지했다: 내용이 바뀐 스토리는 같은 ID에 새 내용을 쓰고, 프로젝트 목표에서 제외된 스토리 ID는 재사용하지 않고 맨 끝 범위 밖 표에 남기며, 새 결과는 묶음의 다음 번호와 새 묶음 US20을 쓴다. 선행은 시험에서 준비할 상태이며 실행 순서를 강제하는 일정이 아니다.

| 표기 | 지위 |
|---|---|
| Must Have | 필수. 11월에 개발해 2026-11-30까지 마친다. |
| 후순위 | 요구사항의 후순위와 같다(PDF 자료, 받은 사람의 Claude 연결). 별도 Unit으로 맨 뒤에 두고 11/13 1차 통합 확인에서 계속할지 뺄지 정한다. 빼도 승인 기준을 어기지 않는다. |

후순위 기능이 필수 스토리의 수용 기준에 걸친 부분은 "(PDF 부분은 후순위)"·"(받은 사람의 Claude 연결 부분은 후순위)"로 표시했다. 후순위를 빼면 그 부분만 빠지고 나머지 기준은 필수로 남는다. 요청의 접수만으로 발행·삭제·탈퇴 성공을 표시하지 않고, 실패나 미확정은 실제 상태대로 보인다.

## FR1 — 자기 기록 준비

### US1.1 Google로 로그인하고 GitHub를 연결해 시작한다

작성 회원(P1)인 나는 내 기록을 준비하기 위해 Google로 로그인한 뒤 GitHub 연결과 분석 동의를 하고 싶다.

- 지위: Must Have. 출처: FR1.1. 선행: 없음.

| ID | Given | When | Then |
|---|---|---|---|
| AC1.1.1 | Google 계정이 있는 외부 사용자 | Google로 로그인함 | 로그인 대상 설정에 따라 로그인되고 자기 회원 계정으로 시작한다 |
| AC1.1.2 | 로그인했으나 GitHub 연결 또는 분석 동의가 없음 | 분석을 시작하려 함 | 빠진 조건을 안내하고 그 조건 없이 분석하지 않는다 |
| AC1.1.3 | 로그인 화면 | 로그인 수단을 확인함 | Google 외 로그인과 기업 계정·기업 탭은 없다 |

### US1.2 공개 저장소를 직접 등록해 분석한다

작성 회원(P1)인 나는 팀에 저장소 선정을 부탁하지 않고 내 공개 저장소를 등록해 Catch를 얻고 싶다.

- 지위: Must Have. 출처: FR1.2, FR1.6, FR1.7, NFR4. 선행: US1.1.

| ID | Given | When | Then |
|---|---|---|---|
| AC1.2.1 | 연결·동의를 마친 회원과 공개 저장소 | 저장소를 등록하고 분석을 요청함 | 등록 때 소유·기여 관계를 미리 검사하지 않고 요청을 받는다 |
| AC1.2.2 | 분석 결과 그 계정의 본인 커밋이 없음 | 분석이 끝남 | "본인 기록이 없다"고 안내하고 Catch를 만들지 않는다 |
| AC1.2.3 | 비공개 저장소 | 요청을 시도함 | 실행 전에 비공개 저장소라는 이유를 알리고 분석하지 않는다 |
| AC1.2.6 | 분석 동의 없음 | 요청을 시도함 | 실행 전에 동의가 없다는 이유를 알리고 분석하지 않는다 |
| AC1.2.7 | 지원 조건 밖의 저장소 | 요청을 시도함 | 실행 전에 지원 조건 밖이라는 이유를 알리고 분석하지 않는다 |
| AC1.2.8 | 하루 실행 한도 초과 | 요청을 시도함 | 실행 전에 한도에 도달했다는 이유를 알리고 분석하지 않는다(US6.4) |
| AC1.2.4 | 팀장 계정의 CatchU 저장소(커밋 약 500개) | 분석을 요청함 | 올린 수집 상한 안에서 커밋이 반영된다(값은 실측으로 정함) |
| AC1.2.5 | 저장소에 비밀값·개인정보가 있음 | 분석함 | 10월 규칙대로 비밀값·개인정보를 가린다 |

AC1.2.3·AC1.2.6~AC1.2.8은 10월 구현의 이유 구분을 그대로 쓰며, 사례마다 따로 시험한다.

### US1.3 분석 상태와 허용된 재요청을 확인한다

작성 회원(P1)인 나는 다음 행동을 고르기 위해 내 분석의 진행·완료·실패를 저장소·분석 화면에서 구분해 보고 싶다.

- 지위: Must Have. 출처: FR1.3. 선행: US1.2. 후속 확인: 재요청 조건은 10월 구현에서 도메인 설계 때 확인(A06).

| ID | Given | When | Then |
|---|---|---|---|
| AC1.3.1 | 본인 분석 요청이 있음 | 저장소·분석 화면을 봄 | 진행·완료·확인된 실패를 구분하고 결과나 실패 안내로 이동한다. 헤더 알림은 없다 |
| AC1.3.2 | 상태 조회만 시간 초과됨 | 다시 확인함 | 조회 실패를 분석 실패로 단정하지 않고 새 분석을 자동 실행하지 않는다 |
| AC1.3.3 | 서버 실패가 확인됨 | 본인이 재요청을 선택함 | 유효 결과·등록 카드·진행/복구 상태와 새 동의 등 기존 조건을 충족할 때만 제한된 재요청을 받는다 |
| AC1.3.4 | 정상 완료 또는 부분 결과가 있음 | 재처리를 시도함 | 정상 완료 재분석·부분 결과 추가 생성·자동 재시도를 하지 않는다 |

### US1.4 Catch의 근거와 공개 상태를 관리한다

작성 회원(P1)인 나는 무엇을 발행할 수 있는지 알기 위해 Catch의 기록·설명·AI 초안을 구분해 보고 공개/비공개를 바꾸고 싶다.

- 지위: Must Have. 출처: FR1.4, FR1.5. 선행: US1.2의 Catch.

| ID | Given | When | Then |
|---|---|---|---|
| AC1.4.1 | Catch가 있음 | Catch를 봄 | 기록에서 확인한 내용, 작성자 설명, AI 설명 초안이 구분돼 보이고 타인의 기여를 본인 것으로 표시하지 않는다 |
| AC1.4.2 | Catch 근거를 보고 싶음 | 근거를 누름 | 일반 GitHub 근거 링크로 원문을 연다. 서비스 안 커밋 원문·diff 탐색은 없다 |
| AC1.4.3 | 공개 Catch | 비공개로 바꿈 | 상태가 바뀌고 "발행할 수 있는 상태"가 아님을 표시한다. 이미 발행한 사본은 바뀌지 않는다 |
| AC1.4.4 | Catch를 지우려 함 | 삭제를 찾음 | Catch 원본 삭제 기능은 없다 |

## FR2 — Catch 설명과 AI 기본 요약

### US2.1 Catch마다 내 설명을 쓴다

작성 회원(P1)인 나는 기록만으로 드러나지 않는 맡은 역할·판단 이유·결과를 Catch마다 적고 싶다.

- 지위: Must Have. 출처: FR2.1, FR2.2, FR2.3. 선행: US1.2의 Catch.

| ID | Given | When | Then |
|---|---|---|---|
| AC2.1.1 | Catch가 있음 | 설명을 쓰고 저장함 | Catch 하나에 설명 하나가 저장되고 다시 고칠 수 있다 |
| AC2.1.2 | 설명이 짧거나 일부 항목만 있음 | 저장함 | 항목별 필수 입력·최소 글자 수·품질 점수를 요구하지 않고 저장한다 |
| AC2.1.3 | AI 설명 초안이 있는 Catch | 작성자 설명을 저장함 | 작성자 설명과 AI 초안이 구분돼 보이고 AI 초안이 설명을 덮어쓰지 않는다 |
| AC2.1.4 | 여러 경험을 묶는 강점 문장을 쓰고 싶음 | 쓸 곳을 찾음 | 텍스트 자료에 쓰며, 독립 '주장'이나 Catch와의 구조적 연결은 없다 |

### US2.2 설명과 텍스트를 잃지 않고 저장한다

작성 회원(P1)인 나는 저장이 안 됐을 때 쓰던 내용을 잃지 않고 다시 저장하고 싶다.

- 지위: Must Have. 출처: FR2.4, FR3.1(텍스트 자료), NFR7. 선행: US2.1 또는 US3.1.

| ID | Given | When | Then |
|---|---|---|---|
| AC2.2.1 | 같은 설명을 두 탭에서 고침 | 두 탭에서 차례로 저장함 | 마지막 저장이 남는다. 충돌 감지는 없다 |
| AC2.2.2 | 저장하지 않은 변경이 있음 | 화면을 떠나려 함 | 경고한다 |
| AC2.2.3 | 서버 오류·연결 끊김·로그인 만료 중 하나 | 저장함 | 저장되지 않았다고 알리고 쓰던 내용을 화면에 남겨 다시 저장할 수 있다 |

### US2.3 다시 분석해도 내 설명이 유지된다

작성 회원(P1)인 나는 저장소를 다시 분석해도 같은 작업의 설명을 다시 쓰지 않고 싶다.

- 지위: Must Have. 출처: FR2.5. 선행: 설명이 있는 Catch.

| ID | Given | When | Then |
|---|---|---|---|
| AC2.3.1 | 설명이 있는 Catch의 같은 작업 | 다시 분석됨 | 기존 Catch를 참조해 설명이 그대로 유지된다 |
| AC2.3.2 | 다른 작업으로 판별돼 새 Catch가 생김 | 분석이 끝남 | 기존 설명을 새 Catch로 옮기지 않는다 |

### US4.2 발행본의 AI 기본 요약을 본다

링크를 받은 사람(P2)인 나는 자료를 다 읽기 전에 발행본 전체를 짧게 파악하고 싶다. 작성 회원(P1)인 나는 요약이 실패하거나 마음에 들지 않으면 다시 만들고 싶다.

- 지위: Must Have. 출처: FR2.7, FR6.4, FR6.8, NFR7. 선행: US4.1의 발행본. (9월 US4.2 "짧은 요약"을 대체하며 FR2 묶음의 요구사항이라 여기 둔다.)

| ID | Given | When | Then |
|---|---|---|---|
| AC4.2.1 | 발행이 끝남 | 시간이 지남 | 발행 당시 내용으로 JD 없이 백그라운드에서 요약이 하나 만들어진다 |
| AC4.2.2 | 요약이 만들어짐 | 누구든 유효한 링크를 엶 | 로그인 여부와 관계없이 'AI 요약' 표시와 함께 바로 보인다. 작성자 확인 단계는 없다 |
| AC4.2.3 | 요약 생성이 실패함 | 받은 사람과 작성자가 링크를 엶 | 받은 사람에게는 요약이 없다고만 보이고, 작성자에게는 다시 만들기 버튼이 보인다 |
| AC4.2.4 | 요약이 성공함 | 작성자가 다시 만들기를 누름 | 하루 실행 제한(US6.4) 안에서 새로 만든다 |
| AC4.2.5 | 링크가 중지·만료됨 | 받은 사람과 작성자가 봄 | 받은 사람에게는 막히고 작성자는 계속 본다 |
| AC4.2.6 | 발행본 삭제나 작성자 탈퇴 뒤 생성 결과가 늦게 도착함 | 결과를 저장하려 함 | 저장하지 않는다 |
| AC4.2.7 | 요약 문장이 근거 글과 맞지 않음 | 화면에 보임 | US6.3의 검사로 그 항목만 버리고 나머지를 보인다 |

## FR3 — 텍스트·PDF 자료

### US3.1 텍스트·PDF 자료를 등록하고 발행 때 고른다

작성 회원(P1)인 나는 자기소개서·이력서·포트폴리오를 형식 제한 없이 올려 두고 발행마다 고르고 싶다.

- 지위: Must Have(PDF 부분은 후순위). 출처: FR3.1, FR3.2, FR3.6, FR20.3. 선행: US1.1.

| ID | Given | When | Then |
|---|---|---|---|
| AC3.1.1 | 로그인한 회원 | 텍스트 자료를 여러 벌 쓰고 저장함 | 각각 저장되고 발행 때 고를 수 있다. 자료 종류별 형식 제한은 없다 |
| AC3.1.2 | 로그인한 회원 | PDF를 올림(PDF 부분은 후순위) | 상한 안이면 저장되고, 넘으면 이유를 알리고 받지 않는다 |
| AC3.1.3 | 외부 주소만 등록하려 함 | 자료를 만듦 | URL 자료 종류는 없고, 텍스트 자료 안에 주소를 적을 수 있다 |
| AC3.1.4 | 자료를 올리는 화면 | 화면을 봄 | "주민등록번호 같은 민감한 정보는 지우고 올려 주세요"를 안내하고, 서비스가 개인정보를 찾아 가리지 않는다 |
| AC3.1.5 | 발행에 고른 텍스트와 PDF | 발행 뒤 원본을 고치거나 지움 | 발행본은 발행 당시 내용을 유지한다. PDF는 발행 때 복사한 발행본 자기 파일을 쓴다(PDF 부분은 후순위) |

### US3.2 PDF를 원본으로 보고 읽을 수 없는 쪽을 구분한다

링크를 받은 사람(P2)인 나는 PDF를 원본 그대로 보고, AI가 읽지 못한 쪽을 읽은 것처럼 오해하지 않고 싶다.

- 지위: 후순위. 출처: FR3.3, FR3.4, NFR7. 선행: PDF가 든 발행본.

| ID | Given | When | Then |
|---|---|---|---|
| AC3.2.1 | PDF가 든 유효한 링크 | PDF를 엶 | 원본을 브라우저로 본다 |
| AC3.2.2 | PDF가 저장됨 | worker가 처리함 | 쪽마다 글을 뽑아 AI·검색 재료로 쓰고, 뽑은 글은 신뢰할 수 없는 입력으로 다룬다 |
| AC3.2.3 | 글이 나오지 않는 쪽이 있음 | 작성자와 받은 사람이 봄 | 그 쪽을 "읽을 수 없음"으로 안내한다. 이미지 글자 인식은 없다 |
| AC3.2.4 | 질문이 읽을 수 없는 쪽의 내용을 물음 | AI가 답함 | 그 쪽을 읽은 것처럼 답하거나 출처로 제시하지 않는다 |
| AC3.2.5 | PDF 글 안에 지시문이 숨어 있음 | AI가 그 글을 씀 | 숨긴 지시로 결과가 바뀌지 않는다 |

## FR4 — 고정 발행본 발행과 열람

### US4.1 Catch와 자료를 골라 고정 발행본을 발행한다

작성 회원(P1)인 나는 보낼 Catch와 자료를 직접 고르고 순서를 정해, 받은 사람과 내가 같은 내용으로 이야기할 수 있는 고정 발행본을 만들고 싶다.

- 지위: Must Have. 출처: FR4.1, FR4.6, FR4.7, NFR7. 선행: US1.4·US2.1·US3.1. 후속 확인: 기본 링크 기간은 OQ4.

| ID | Given | When | Then |
|---|---|---|---|

| AC4.1.8 | 발행 저장이 실패함 | 결과를 봄 | 발행 실패를 알리고 어떤 Catch도 공개로 바뀌지 않는다 |

### US4.4 받은 링크를 열어 발행본을 읽는다

| AC4.4.2 | 비밀번호 있는 링크 | 틀린 비밀번호를 넣음 | 자료를 보이지 않는다. 맞으면 본다 |

### US4.3 고정 발행본과 원본 변경을 구분한다

| AC4.3.2 | 발행 뒤 Catch 설명이나 텍스트를 고침 | 작성자가 발행본을 봄 | 원본 수정은 반영되지 않고, 수정 전달은 새 발행, 제공 중단은 링크 중지라고 안내한다 |
| AC4.3.3 | 발행 뒤 GitHub 저장소가 비공개로 전환됨 | 받은 사람이 엶 | 발행본과 그 검색 조각은 유지되고, 작성자에게 링크 중지·삭제로 제공을 끝내도록 안내한다 |

## FR5 — 링크 접근과 발행본 관리

### US5.1 링크 접근을 끝내고 내 발행 내용은 계속 본다

작성 회원(P1)인 나는 링크를 중지하거나 만료돼도 내가 무엇을 보냈는지 다시 확인하고 싶다.

| AC5.1.2 | 만료 시점이 지남 | 받은 사람이 엶 | 같은 경로가 모두 막힌다(받은 사람의 Claude 연결 부분은 후순위) |
| AC5.1.3 | 중지·만료된 링크 | 작성자가 봄 | 발행 내용과 AI 기본 요약을 계속 다시 볼 수 있다 |

| AC5.1.5 | 발행본 | 작성자가 만료 시점을 확인함 | 실제 만료 시점이 보인다. 만료일 선택·연장·발행 뒤 비밀번호 변경은 없다 |

### US5.2 발행본을 직접 삭제한다

작성 회원(P1)인 나는 보낸 발행본과 거기 딸린 결과를 모두 지우고 싶다.

| AC5.2.2 | 발행본에 딸린 자료가 있음 | 삭제함 | 발행 사본(PDF 사본 포함, PDF 부분은 후순위)·검색 조각·AI 기본 요약·그 발행본의 JD 요약 결과가 함께 지워진다 |

## FR6 — AI로 발행본 검토

### US6.2 발행본에 대화형으로 묻는다

링크를 받은 사람(P2-A)인 나는 로그인 없이 발행본에 이어서 물어 필요한 근거를 찾고 싶다.

| ID | Given | When | Then |

| AC6.2.2 | 답이 만들어지는 중 | 화면을 봄 | 검사를 통과한 항목만 차례로 보인다(SSE). 큐를 기다리지 않는다 |
| AC6.2.3 | 발행본에 없는 Catch·자료, 또는 Catch의 AI 설명 초안 | 관련 질문을 함 | 찾는 범위는 그 링크의 발행 사본(Catch의 GitHub 기록, 작성자 설명, 텍스트, PDF 글)뿐이고 AI 설명 초안은 쓰지 않는다(PDF 글 부분은 후순위) |
| AC6.2.4 | 대화 중 링크가 중지·만료·삭제됨 | 다음 질문을 함 | 거부한다 |

| AC6.2.6 | 턴·길이 상한을 넘는 대화 | 질문함 | 상한 안의 최근 대화만 보내고, 보낸 대화는 신뢰할 수 없는 입력으로 다룬다 |

### US6.1 내 JD로 요구사항별 요약을 받는다

로그인한 면접관 회원(P2-B)인 나는 내 JD의 요구사항마다 이 지원자의 근거와 확인되지 않은 점, 물을 질문을 보고 싶다. 작성 회원(P1)인 나는 내 링크로 면접을 준비하고 싶다.

- 지위: Must Have. 출처: FR6.1, FR6.8. 선행: US6.5의 저장한 JD, US4.4의 링크.

| ID | Given | When | Then |
|---|---|---|---|
| AC6.1.1 | 로그인 회원과 저장한 JD, 유효한 링크 | 그 링크에 JD 요약을 실행함 | 결과 하나가 만들어지고, JD 요구사항마다 JD 원문 줄·근거(GitHub 기록/작성자 자료 구분)·자료로 확인되지 않는 점·면접 질문이 보인다 |
| AC6.1.2 | 다른 회원이 내 링크에 JD 요약을 실행함 | 작성자가 결과를 찾음 | 작성자는 그 회원의 JD·결과를 볼 수 없고, 실행한 회원만 본다 |
| AC6.1.3 | 실행 중 브라우저를 닫음 | 나중에 다시 엶 | 접수된 처리는 취소되지 않고 상태·결과·실패 안내를 본다 |
| AC6.1.4 | 처리 시한이 지나도록 멈춤 | 상태를 봄 | 실패로 바뀐다. 자동 복구·중간 재개·자동 재시도는 없다 |
| AC6.1.5 | 일부 요구사항만 생성에 실패함 | 결과를 봄 | 요구사항과 결과의 대응을 유지하고 실패한 요구사항을 구분해 보인다 |
| AC6.1.6 | 입력이 상한을 넘음 | 실행하려 함 | 실행 전에 거부하고 안내하며 일부만 골라 자동으로 검토하지 않는다 |
| AC6.1.7 | 같은 JD로 다시 실행함 | 결과를 봄 | 새 실행이며 이전 결과를 재사용하지 않는다 |
| AC6.1.8 | 링크가 유효한 동안 | 본인 결과를 다시 엶 | 다시 볼 수 있다. 만료·중지 뒤에는 막힌다 |
| AC6.1.9 | 발행본 삭제, 작성자 또는 실행한 회원의 탈퇴, 그 JD 삭제 중 하나 | 일어남 | 결과·실행·실행 입력 사본이 함께 지워진다 |
| AC6.1.10 | 영어 표기가 이번에 찾은 자료 어디에도 없는 JD 요구사항 | 결과를 봄 | 「자료로 확인되지 않는 점」에 "이번에 찾은 자료에서 '…' 표기를 찾지 못함"처럼 적고 경험·역량이 없다고 쓰지 않는다 |

### US6.5 JD를 저장·수정·삭제한다

### US6.3 AI 문장의 근거 원문을 확인한다

링크를 받은 사람(P2)인 나는 AI가 쓴 문장을 사실로 오해하지 않고, 근거 원문을 눌러 직접 확인하고 싶다.

- 지위: Must Have. 출처: FR6.4, FR6.5, FR6.9, NFR2, NFR7. 선행: US4.2·US6.1·US6.2 중 하나의 결과.

| ID | Given | When | Then |
|---|---|---|---|
| AC6.3.1 | 기본 요약·질의응답·JD 요약의 항목 | 근거를 봄 | 근거는 인용 기능으로 붙은 원문 그대로이고 "GitHub 기록 원문"·"작성자 자료 원문"이 근거 원문에 표시된다. AI 문장은 확인된 사실로 표시되지 않는다 |
| AC6.3.2 | 문장의 숫자·PR 번호·파일 이름·영어 표기가 가리킨 근거 글에 없음 | 결과를 보임 | 그 항목만 경고 없이 버리고 나머지를 보인다. 그 근거 글이 속한 Catch의 PR 번호는 맞는 것으로 본다 |
| AC6.3.3 | 근거 없는 해석 문장 | 결과를 보임 | 'AI 해석'으로 표시하되, 숫자·PR 번호 또는 발행본 어디에도 없는 영어 표기가 있으면 버린다 |
| AC6.3.4 | Catch의 AI 설명 초안 | 근거를 만듦 | 초안은 인용 단위·검색 조각에 넣지 않는다. 발행본 화면에서는 'AI 초안'으로 표시해 보일 수 있다 |
| AC6.3.5 | 근거 원문 | 누름 | 원문의 해당 구절이 강조되고 그 위치로 이동한다. PDF는 쪽 번호·강조 구절·"원본 n쪽 열기"를 보인다(PDF 부분은 후순위) |
| AC6.3.6 | JD 요약의 면접 질문 | 검사함 | 영어 표기는 근거 원문과 그 JD 요구사항 줄에서, 숫자·PR 번호는 같은 요구사항의 근거 칸이 인용한 근거 원문에서 찾는다. 확인되지 않은 일을 이미 한 것처럼 전제하지 않는다 |
| AC6.3.7 | 작성자 설명·자료에 숨긴 지시문 | 생성함 | 숨긴 지시로 결과가 조작되지 않고, 점수·비율 같은 역량 평가 표현을 쓰지 않는다 |

### US6.4 하루 실행 한도에 도달하면 안다

작성 회원(P1)·로그인 회원(P2-B)인 나는 오늘 더 실행할 수 없을 때 그 사실을 알고 싶다.

- 지위: Must Have. 출처: FR6.6, NFR7. 선행: 로그인 회원. 제한 값은 개발 담당 결정.

| ID | Given | When | Then |
|---|---|---|---|
| AC6.4.1 | 계정의 하루 실행 횟수(분석·기본 요약 생성/다시 만들기·JD 요약 합산)에 도달함 | 다시 실행함 | "오늘 한도에 도달했습니다"를 안내하고 실행하지 않는다. 남은 횟수는 보이지 않는다 |
| AC6.4.2 | 한도에 도달함 | 허용된 열람을 함 | 열람은 막지 않는다 |
| AC6.4.3 | 같은 링크를 여러 면접관이 씀 | 한 사람이 많이 실행함 | 링크 단위로 합산하지 않으므로 다른 회원의 한도에 영향이 없다 |

## FR13 — Claude 연결

### US13.1 Claude를 연결하고 해제한다

## INVEST 점검과 추정의 한계

- 각 스토리는 한 사용자 결과와 확인 가능한 수용 기준을 갖는다. 웹·api·worker별로 같은 결과를 나누지 않았다.
- US6.1(JD 요약)과 US6.3(근거 검사)은 기준이 많아 큰 편이다. Unit 나누기에서 더 쪼갤 수 있다.
- US4.2(AI 기본 요약)도 행위자가 둘(받은 사람, 작성자)이고 기준이 7개라 큰 편이다. Unit 나누기에서 받은 사람 쪽(AC4.2.2, AC4.2.3의 수신자 부분)과 작성자 쪽(다시 만들기, AC4.2.3의 작성자 부분·AC4.2.4)으로 나눌 수 있다. ID는 입력의 대응표(FR2.7·US4.2)를 따르고 위치는 FR2 묶음 절에 두었다.
- FR13.5의 "시험을 위한 권한 우회 없음"은 NFR1에서, FR6.9의 "세 기능 모두 Haiku 5.5, 판정 AI 없음"은 NFR2에서 확인한다. 이 둘은 별도 수용 기준을 두지 않는다.
- 작업 일수·담당·일정은 적지 않는다. 11월 공수 초과(C03)와 후순위 판단은 납품 계획과 11/13 1차 통합 확인에서 다룬다.

## Assumptions & Open Questions

- 전제: 설명 없는 Catch도 발행에 고를 수 있다(요구사항 A03). 10월 공개 전환 규칙·분석 경로·재요청 조건은 10월 구현을 그대로 쓴다(A06). 재요청 조건의 세부는 도메인 설계에서 10월 구현을 확인해 옮긴다.
- 미결: 기본 링크 기간(OQ4), 시연용 저장소 공개(OQ2), PDF 저장 위치(OQ1), team.md 갱신 관문(OQ5)은 요구사항의 담당·시점을 따른다. 상한·제한 값과 결과 확인 방식 등은 개발 담당 결정이다.
