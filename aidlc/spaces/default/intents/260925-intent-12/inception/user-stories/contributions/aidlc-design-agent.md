## Contribution

User Stories mob round 1. 검토 대상은 lead 초안의 68개 스토리 전체와 personas.md, 확인된 user-stories-questions.md, 승인 requirements.md다. Q103의 신고 접수 결과·권한 경계는 원답변을 추가 대조했다. 다른 지원자의 기여는 읽지 않았다. 이 기여만 작성했으며 스토리·페르소나·승인 원본은 수정하지 않았다.

### 일치하는 사용자 흐름과 권한 경계

- P1~P4는 승인된 행위자·목표에서 도출했고 확인되지 않은 인구통계·사용 빈도를 만들지 않았다. 기업 관리자·채용 담당자·검토자와 서비스 운영자를 구분한다. P4를 미배정 검증·개인정보·제출 업무의 자동 담당자로 만들지 않았다.
- 현재 자료, 발행 당시 고정 공유본, 기업 소속 권한, 제안별 연락처가 분리되어 있다. 원본 숨김으로 기존 링크를 종료하거나 계정 연락 차단으로 일반 열람을 막는 오해가 없다. 기업 일시 중단 후 독립 공개 링크와 기업 MCP 자격도 구분한다.
- 짧은 요약에서 근거로 읽기, 미완성 주장 초안, 주장별 Catch 최소 한 장, AI가 읽지 못하는 PDF의 사람 열람, 검색 결과 없음/조회 실패, 기업 종료 성공/본인 탈퇴 실패가 사용자에게 관찰 가능한 결과로 드러난다.
- 프로필 소개·소셜·신고 제품·DM·마일리지·기업 JD 프리셋을 필수 흐름의 선행 구현으로 만들지 않았다. 기본 기간과 편의 기능, 수신 설정과 검색 동의, 수락과 연락처 동의도 분리한다.
- 기존 OQ1~15의 책임·시점을 유지한다. 이번 검토로 새 제품 정책·숫자·화면·구현 담당·마감 약속을 정할 필요는 없다.

### 후속 설계에 남길 권고

- US8.3의 ‘선행: 검색 참여·사용 가능한 추가 주장’은 기업 열람의 조건이다. 작성자가 허용/철회를 관리하는 조건과 섞이지 않도록 ‘본인 추가 주장; 기업 이용 시 검색 참여·자료 조건 적용’으로 표현하면 구현자가 검색 OFF 상태에서 관리 자체를 막는 오해를 줄일 수 있다. 승인된 설정 독립성의 설명 보완이며 새 설정 정책을 요구하지 않는다.
- US7.1의 등록 전 행위자는 로그인 회원이고 등록 성공 후 최초 P3-A가 된다. 본문의 ‘기업 회원(P3-A)’을 ‘기업을 등록하려는 로그인 회원(성공 후 P3-A)’으로 명료화할 수 있다. AC7.1.1은 이미 정확하다.
- 이 단계는 화면 배치·시각 설계가 아니다. 후속 UI 설계에서는 키보드 조작·보이는 포커스·입력 라벨·오류/상태의 텍스트 식별·보조기기 상태 안내를 WCAG 2.1 AA 설계 기준으로 구체화한다. 이는 디자인 역할의 점검 기준이며 현재 제품이 접근성 검사를 통과했다는 주장이 아니다. 승인되지 않은 시간·기기·수치 목표나 별도 필수 기능을 스토리에 추가하지 않는다.

### Round 2 재확인

수정된 공통 상태 변경 기준, AC5.2.4, US17.4 본문·AC17.4.1을 대조했다. 두 1차 발견은 위 표에 이력으로 남긴다. 이번 재확인은 해당 위치만 대상으로 하며 전체 재검토나 새 범위 제안은 하지 않았다.

- UX1 해결: 신고자의 목표를 제출 성공/실패 확인으로 좁혔고 AC17.4.1에서 신고자 안내와 운영자 전용 검토/이력을 분리했다. Q103의 승인 경계를 충족하며 새 신고자용 처리 결과 조회를 추가하지 않는다.
- UX2 해결: 공통 기준이 상태 변경 요청의 접수와 실제 성공을 구분한다. AC5.2.4는 삭제 실패·완료 미확정 시 삭제/파기 완료로 표시하지 않고 실제 확인한 상태를 구분한다. FR19.2와 팀의 비동기 완료/실패 구분을 충족하며 자동 재시도·새 알림·추가 복구 정책은 추가하지 않았다.
- 개발·품질 참여자의 Positions를 확인했다. 신고 역할 경계 의견은 UX1과 같은 기존 결정 보정이다. 나머지 NFR2·기업 종료·재생성 의견은 해당 참여자의 근거와 재확인에 맡기며 디자인 관점의 유지 이견은 없다.

AGREE: UX2 해결 — 공통 상태 변경 기준과 AC5.2.4가 접수·실제 완료·실패/미확정을 구분하며 새 복구 정책 없이 확인한 작성 계획·FR19.2·팀 기준을 반영한다.
