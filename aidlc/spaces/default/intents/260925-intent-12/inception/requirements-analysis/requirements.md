# CatchU 12월 범위 요구사항 (2026-10-24 재승인판)

작성일: 2026-10-24. Intent: `260925-intent-12` — 12월 범위 요구사항. Scope: `mvp`.

이 문서는 2026-09-28 승인 요구사항을 새 입력으로 고친 재승인판이다. 통합 요약의 `Looks correct` 확인(2026-10-24)을 근거로 작성했으며, **요약 확인은 최종 요구사항 승인·구현 완료·일정 내 구현 가능성 확인이 아니다.** 단계 승인 여부는 공식 상태·감사 기록으로 구분한다. 9월 승인판은 이 파일의 git 이력과 감사 기록에 당시 판본으로 남는다.

## 의도 분석 (Intent analysis)

CatchU는 팀원의 취업 포트폴리오이고, 12월 이용자는 소수의 외부 사용자가 자기 자료로 써 보는 수준이다. 그래서 실제 운영 서비스용 장치는 남의 자료를 다루는 데 꼭 필요한 것만 남기고, 그 시간을 설명할 수 있는 기능(특히 RAG)에 쓴다. 채용 검토자는 시간이 부족해 GitHub 기록을 직접 읽기 어렵다. 작성자는 Catch에 확인 가능한 기록을 담고 Catch마다 자기 설명을 붙여 발행하며, 검토자는 고정된 발행본을 읽고 AI 기본 요약·대화형 질의응답·자기 JD의 요구사항별 요약으로 근거와 확인되지 않은 점을 구분한다. 서비스는 작성자의 설명이나 AI 문장을 검증된 역량 평가로 바꾸지 않는다.

## 기능 요구사항 (Functional requirements)

각 행의 수용 기준은 구현 완료 주장이 아니라 확인할 사례다. 별도 표시가 없으면 필수다. 링크 조건(비밀번호·만료·중지·삭제)과 회원 자료 격리는 웹·질의응답·JD 요약·Claude MCP에 같게 적용한다(NFR1).

### FR1. 회원이 자기 저장소에서 Catch를 준비한다

근거: 입력 §3 「저장소 등록과 분석」·「대체하는 12월 기준」 FR1.2·FR1.5 행·「재승인 때 함께 정리할 것」, §2-1, Q122. 9월 FR1.3·FR1.4 이어받음.

| ID | 요구사항·수용 기준 |
|---|---|
| FR1.1 | 로그인은 Google만 제공한다. 외부 사용자가 Google로 로그인할 수 있게 로그인 대상을 설정한다. 로그인 뒤 GitHub 계정 연결과 분석 동의를 거쳐 자기 자료를 준비한다. 기업 계정·기업 소속 역할은 없고 채용담당자도 일반 개인 계정을 쓴다. |
| FR1.2 | 회원은 공개 저장소를 직접 등록하고 분석을 요청한다. 등록할 때 연결 계정과 저장소의 소유·기여 관계를 미리 검사하지 않고, 분석에서 본인 커밋을 확인한다. 분석할 본인 기록이 없으면 "본인 기록이 없다"고 안내한다. GitHub 연결 본인 신원, 공개 여부·동의·지원 조건·한도 확인과 회원별 자료 분리는 유지한다. 사전 선정 목록이 이 경로를 대신하지 않는다. |
| FR1.3 | 요청 뒤 진행·완료·실패를 구분하고 본인 결과와 실패 안내를 **저장소·분석 화면에서** 확인한다(헤더 알림 없음, Q122). 확인된 서버 실패에 대해서는 기존의 제한된 사용자 재요청을 제공하며, 재요청 전에 유효 결과·등록 카드·진행/복구 상태와 새 동의 등 기존 조건을 확인한다. 조회 시간 초과를 분석 실패로 단정하지 않는다. 자동 분석 재시도·정상 완료 재분석·부분 결과 추가 생성은 추가하지 않는다(9월 FR1.3 이어받음). |
| FR1.4 | Catch는 기록에서 확인한 내용, 작성자 설명, AI 설명 초안을 구분해 보여 준다. 타인의 기여를 본인 것으로 표시하지 않는다. 근거는 일반 GitHub 근거 링크로 원문을 확인하며, 서비스 안 커밋 원문·diff 탐색(카드 탐색 3층)은 이번 범위에 없다. |
| FR1.5 | Catch 원본의 사용자 삭제 기능은 없다. 본인은 Catch의 공개/비공개를 바꿀 수 있고, 이 상태는 "발행할 수 있는 상태인가"를 뜻한다. 비공개 Catch도 발행에 고를 수 있으며 발행할 때 공개로 바뀐다(FR4.1). 발행·질의응답·JD 요약은 작성자가 고른 발행 사본만 쓰고, 본인 Claude 연결은 동의 아래 비공개 Catch도 읽는다(FR13.2). |
| FR1.6 | 수집 상한(커밋 목록·상세 조회·호출 수·수집 시간·생성 횟수·요청 처리 시한)을 올린다. 수용 기준: 팀장 계정의 CatchU 저장소 커밋 약 500개가 반영된다. 구체 값은 실측으로 정한다. |
| FR1.7 | 저장소 분석의 비밀값·개인정보 가리기(10월 규칙)는 그대로 둔다. |

### FR2. 작성자가 Catch마다 설명을 쓰고, 발행본에는 AI 기본 요약이 붙는다

근거: 입력 §3 「자료와 발행 링크」·「AI 기본 요약」·「대체하는 12월 기준」 FR2·FR2.7 행, §2-1. 9월 FR2(강점 주장·대표·추가 자료)는 제외가 아니라 **대체**다. 같은 번호를 유지하고 아래 새 내용으로 바꾼다. 9월 FR2.6(관리 정보에서 주장·연결·숨김 확인, 연결 변경·숨김 해제, 발행 전 미리보기)은 주장 구조가 없어져 현행 FR1.5(공개/비공개 변경)와 FR4.6(발행 후 확인)으로 옮겼다.

| ID | 요구사항·수용 기준 |
|---|---|
| FR2.1 | 독립된 '주장'(제목·본문·여러 Catch 연결·순서·공개/대표)은 만들지 않는다. 작성자는 Catch마다 설명 하나(맡은 역할·판단 이유·결과 등)를 작성·수정한다. 설명 항목별 필수 입력·최소 글자 수·품질 점수는 요구하지 않는다(9월 FR2.5 이어받음). |
| FR2.2 | 작성자 설명은 AI가 만든 설명 초안·확인된 사실과 구분해 보여 주고, AI 초안이 작성자 설명을 덮어쓰지 않는다. |
| FR2.3 | 여러 경험을 묶는 강점 문장은 텍스트 자료(FR3)에 자유롭게 쓴다. Catch와 구조적으로 연결하지 않는다. |
| FR2.4 | Catch 설명을 여러 탭에서 고치면 마지막 저장이 남는다(충돌 감지 없음). 저장하지 않고 떠나면 경고한다. 저장이 실패하면(서버 오류·연결 끊김·로그인 만료) 저장되지 않았다고 알리고, 쓰던 내용을 화면에 남겨 다시 저장할 수 있게 한다. |
| FR2.5 | 같은 작업이 다시 분석되면 기존 Catch를 그대로 참조하므로 설명이 유지된다. 다른 작업으로 판별돼 새 Catch가 생기면 기존 설명을 옮기지 않는다. |
| FR2.7 | 발행본마다 AI 기본 요약을 하나 만든다. JD 없이 발행 당시 내용으로 발행 뒤 백그라운드에서 생성한다. 생성되면 로그인 여부와 관계없이 그 링크를 여는 모든 사람에게 'AI 요약' 표시와 함께 바로 보인다. 작성자 확인 단계와 요약 전용 미리보기는 없다. 실패하면 수신자에게는 요약이 없다고만 보이고 작성자에게는 다시 만들기 버튼이 보이며, 성공한 뒤에도 다시 만들 수 있다. 링크가 중지·만료되면 수신자에게는 막히고 작성자는 계속 본다. 발행본 삭제·작성자 탈퇴 때 함께 지우고 그 뒤 늦게 도착한 결과는 저장하지 않는다. 근거 검사는 FR6.4를 따른다. |

### FR3. 작성자가 텍스트·PDF 자료를 등록하고 발행 때 고른다

근거: 입력 §3 「자료와 발행 링크」·「대체하는 12월 기준」 FR3.1·FR3.2·FR3.3·FR3.4 행·「프로젝트 목표에서 제외」, Q119. **PDF 관련 요구사항(FR3.1의 PDF 부분, FR3.3, FR3.4)은 후순위다.**

| ID | 요구사항·수용 기준 |
|---|---|
| FR3.1 | 자료는 텍스트와 PDF 두 종류이며 각각 여러 벌 등록하고 발행 때 고른다. 자기소개서·이력서·포트폴리오 같은 종류별 형식 제한은 두지 않는다. 외부 URL 자료 종류는 없고, 텍스트 자료 안에 주소를 적는 것은 된다. 텍스트 자료도 FR2.4의 여러 탭·저장 실패 규칙을 따른다. 크기·쪽 수 등 상한 값은 개발 담당 결정이다. **PDF 부분은 후순위.** |
| FR3.2 | 발행에 고른 텍스트와 PDF는 발행 당시 내용으로 보존한다. PDF는 발행할 때 파일을 복사해 발행본마다 자기 파일을 갖는다(PDF 부분은 후순위). |
| FR3.3 | **후순위.** PDF는 원본을 보관하고, 받은 사람은 원본을 브라우저로 본다. worker가 쪽마다 글을 뽑아(`pypdf`) AI·검색 재료로 쓴다. 뽑은 글은 신뢰할 수 없는 입력으로 다룬다. |
| FR3.4 | **후순위.** 이미지 글자 인식은 없다. 글이 안 나오는 쪽은 "읽을 수 없음"으로 안내하고, AI가 그 쪽을 읽은 것처럼 답하거나 출처로 제시하지 않는다. |
| FR3.6 | 자료를 올리는 화면에 "주민등록번호 같은 민감한 정보는 지우고 올려 주세요"를 안내한다. 서비스가 자료 안의 개인정보를 찾아 가리지 않는다(FR20.3). |

### FR4. 작성자가 고정 발행본을 발행하고 받은 사람이 읽는다

근거: 입력 §2-1, §3 「자료와 발행 링크」·「대체하는 12월 기준」 FR4·FR4.2 행·「재승인 때 함께 정리할 것」 FR4.1·FR4.4. 9월 FR4.3·FR4.5 이어받음. 링크는 ATS 지원 접수 완료나 철회 불가능한 공식 제출이 아니다.

| ID | 요구사항·수용 기준 |
|---|---|
| FR4.1 | 작성자는 Catch(설명 포함)·텍스트·PDF(PDF 부분은 후순위)를 직접 고르고 순서를 정해 발행한다. 비공개 Catch도 고를 수 있다. 고르면 "발행하면 이 Catch는 공개로 바뀝니다"를 안내하고 실제 공개 전환은 발행할 때 한다. 골랐다가 빼면 바뀌지 않는다. 공개 전환에는 10월 공개 전환 규칙을 그대로 적용한다: 작업 사실·기여가 확인되지 않은 Catch와 원본 저장소가 비공개로 바뀐 것이 확인된 Catch는 발행에 넣을 수 없고 화면에 이유를 안내한다. 불일치 표시가 있는 Catch는 표시를 단 채 발행할 수 있다. 발행한 뒤 비공개로 바꿔도 이미 발행한 사본은 바뀌지 않는다. |
| FR4.2 | 받은 사람은 링크 조건(비밀번호·만료·중지)을 충족한 뒤 로그인 없이 발행본 자료(PDF 원본 포함, PDF 부분은 후순위)와 AI 기본 요약을 보고 질의응답을 쓴다. JD 요구사항별 요약은 로그인 회원만 실행한다(FR6.1). 같은 링크의 질의응답·JD 요약·MCP(받은 사람의 Claude 연결 부분은 후순위)에도 링크 조건을 적용한다. |
| FR4.3 | 받은 사람에게 발행 당시 자료를 고정한 발행본임을 알리고, 이후 원본 수정·공개 상태 변경·삭제 사실은 안내하지 않는다. 작성자에게 원본 수정은 반영되지 않으며 수정 전달은 새 발행, 기존 제공 중단은 링크 중지라는 차이를 안내한다. |
| FR4.4 | 발행본에 넣지 않은 Catch·자료는 열람·질의응답·JD 요약·MCP로 얻을 수 없다. 사본 보존을 링크 조건 우회 근거로 삼지 않는다. |
| FR4.5 | GitHub 저장소가 비공개로 전환돼도 이미 발행한 발행본과 그 검색 조각은 유지하고, 작성자에게 링크 중지·발행본 삭제로 제공을 끝내도록 안내한다. GitHub 조회 실패를 비공개 전환으로 단정하지 않는다. |
| FR4.6 | 발행 미리보기는 "발행 후 확인"으로 한다. 발행 전에는 고른 자료·순서와 접근 조건을 안내하고, 발행 직후 실제 고정 사본을 작성자에게 보여 준다. |
| FR4.7 | 발행할 때 권한·선택·크기를 다시 확인하고, 링크와 발행본을 함께 저장한다. 발행 저장이 실패하면 어떤 Catch도 공개로 바뀌지 않는다(FR4.1의 공개 전환은 발행 저장과 함께 성립한다). 발행할 때 사본을 조각으로 나누고 위치(항목·필드·글자, PDF 쪽)를 기록한다(FR6.2, PDF 부분은 후순위). 발행 사본에는 화면 표시용으로 Catch의 AI 설명 초안을 함께 고정할 수 있지만(FR6.5), 검색 조각과 인용 단위에는 넣지 않는다(FR6.4). |

### FR5. 작성자가 링크 접근과 발행본을 관리한다

근거: 입력 §3 「자료와 발행 링크」·「AI 기본 요약」·「프로젝트 목표에서 제외」, §2-2. 9월 FR5.1·FR5.2·FR5.4 이어받음.

| ID | 요구사항·수용 기준 |
|---|---|
| FR5.1 | 만료되거나 작성자가 중지한 링크는 받은 사람의 열람·기본 요약·질의응답·JD 요약·MCP(받은 사람의 Claude 연결 부분은 후순위) 접근을 막는다. 만료·중지된 링크는 되살리지 않는다. 작성자는 발행 내용과 AI 기본 요약을 계속 다시 볼 수 있다. |
| FR5.2 | 작성자가 발행본을 직접 삭제하면 링크를 쓸 수 없고 작성자도 발행 내용을 다시 볼 수 없다. 발행 사본(PDF 사본 포함, PDF 부분은 후순위)·검색 조각·AI 기본 요약·그 발행본의 JD 요약 결과를 함께 지우며, 늦게 도착한 결과는 되살리지 않는다(FR14.10). 원본 자료와 다른 발행본은 유지한다. |
| FR5.4 | 발행할 때 기본 접근 조건(비밀번호 여부·만료)을 정하고 작성자가 실제 만료 시점을 확인할 수 있다. 기본 링크 기간은 OQ4에서 정한다. 만료일 선택·연장·발행 뒤 비밀번호 변경 같은 편의는 제외다. |

보관: 자동 파기는 없다. 발행본은 작성자가 직접 삭제하거나 작성자가 탈퇴할 때까지 남는다(9월 FR5.3 제외).

### FR6. 받은 사람과 작성자가 AI로 발행본을 검토한다

근거: 입력 §3 「RAG 대화형 질의응답」·「JD 요구사항별 요약」·「근거와 AI 출력 검사」·「하루 실행 제한과 고지」·「대체하는 12월 기준」 FR6.1~FR6.6 행, §2-1 4번, §2-2.

| ID | 요구사항·수용 기준 |
|---|---|
| FR6.1 | **JD 요구사항별 요약.** 로그인한 회원이 저장한 JD로 그 링크에 실행한다. 링크를 받은 다른 회원(면접관)도 자기 JD로 실행할 수 있고, 결과는 실행한 회원만 본다. 링크 작성자는 다른 회원의 JD·결과를 볼 수 없다. 결과는 하나의 요약이며 JD 요구사항마다 JD 원문 줄, 관련 Catch·작성자 설명·자료 근거(GitHub 기록과 작성자 자료를 구분), 자료로 확인되지 않는 점, 그 요구사항에 연결된 면접 질문을 보여 준다. JD를 요구사항으로 나누고 요구사항마다 발행본에서 관련 조각을 찾아 근거로 넣으며, 생성은 요구사항마다 차례로 부른다. 요구사항과 결과의 대응, 일부 실패, 전체 실행 시한을 처리한다. 사이드 패널은 없다. 같은 JD로 다시 실행하면 새 실행이며 재사용은 없다. 본인 결과는 그 링크가 유효한 동안 다시 열 수 있고, 발행본 삭제·작성자 또는 실행한 회원의 탈퇴·그 JD 삭제 때 함께 지운다. 입력이 상한을 넘으면 실행 전에 거부하고 안내하며 일부만 골라 자동으로 검토하지 않는다. |
| FR6.2 | **RAG 대화형 질의응답.** 링크를 연 사람이 로그인 없이 그 발행본에 자유롭게 묻고 앞 대화를 이어서 묻는다. 질문을 앞 대화에 맞게 다시 쓰고 발행본에서 관련 조각을 찾아 답한다. 대화는 브라우저에만 두고 서버에 저장하지 않으며, 질문마다 보내는 최근 대화는 신뢰할 수 없는 입력으로 다루고 턴과 길이에 상한을 둔다. 찾는 범위는 그 링크의 발행 사본(Catch의 GitHub 기록, 작성자 설명, 텍스트, PDF 글)뿐이고, Catch의 AI 설명 초안은 찾는 범위에서 뺀다(FR6.4). PDF 글 부분은 후순위다. 질문마다 링크 조건을 다시 확인한다. 큐가 아닌 바로 답하는 경로로 처리하고, 답은 항목 단위로 받아 FR6.4 검사를 통과한 항목만 화면에 차례로 내보낸다(SSE). 발행 때 만든 조각은 Voyage AI API로 임베딩해 벡터 저장소에 두고 발행본 삭제 때 함께 지운다. 질문에 넘길 자료는 의미 검색으로만 고른다. |
| FR6.3 | 받은 사람이 특정 자료를 AI 참고에서 빼는 선택은 두지 않는다. AI가 찾는 범위는 FR6.2의 발행 사본이다. |
| FR6.4 | **근거와 AI 출력 검사(기본 요약·질의응답·JD 요약 공통).** 근거는 Claude API의 인용 기능으로 붙인다. 모델은 근거가 되는 줄만 가리키고 근거 글은 API가 넘긴 자료에서 그대로 복사하며, 인용 단위(줄)는 서비스가 정해 넘긴다. Catch의 AI 설명 초안(10월 분석이 만든 설명·제목·질문)은 근거에서 빼고, 인용 단위와 검색 조각에는 GitHub 기록과 작성자 자료만 넣는다. 문장의 숫자·PR 번호·파일 이름과 영어 표기(기술·저장소 이름 등)가 그 문장이 가리킨 근거 글 안에 있는지 기계적으로 확인하고, 맞지 않는 항목은 경고 없이 그 항목만 버리고 나머지를 보여 준다. 근거 없는 해석 문장은 'AI 해석'으로 표시하되, 숫자·PR 번호가 있거나 발행본 어디에도 없는 영어 표기가 있으면 버린다. 영어 표기는 대소문자를 가리지 않고 흔한 낱말은 짧은 예외 목록으로 뺀다. 그 근거 글이 속한 Catch의 PR 번호도 맞는 것으로 본다. 생성 지시는 원문 표기를 그대로 쓰고, PR·이슈 번호 대신 무엇을 했는지로 쓰게 한다. JD 요약의 면접 질문은 영어 표기를 근거 원문과 그 JD 요구사항 줄에서 함께 찾고, 숫자·PR 번호는 같은 요구사항의 근거 칸이 인용한 근거 원문에서 찾으며, 확인되지 않은 일을 이미 한 것처럼 전제하지 않게 지시한다. 질문이나 JD 요구사항의 영어 표기가 이번에 찾은 자료 어디에도 없으면 "이번에 찾은 자료에서 '…' 표기를 찾지 못함"처럼 알리고 경험·역량이 없다고 쓰지 않는다. 근거 없는 사실·역량 단정 금지, 점수·비율 같은 역량 평가 표현 금지, 작성자 설명·자료(PDF 포함)에 숨긴 지시로 결과를 조작하지 못하게 하는 방어를 유지한다. |
| FR6.5 | 출처 표시는 AI 문장이 아니라 근거 원문에 붙인다: "GitHub 기록 원문"(Catch의 GitHub 기록), "작성자 자료 원문"(설명·텍스트·PDF). 작성자가 미리 연결하는 구조가 없으므로 근거는 모두 AI가 찾은 것으로 보고, AI 문장은 근거가 붙어 있어도 확인된 사실로 표시하지 않는다. 근거를 누르면 원문의 해당 구절이 강조되고 그 위치로 이동한다. PDF는 쪽 번호와 뽑은 글의 강조 구절, "원본 n쪽 열기"를 보여 준다(PDF 부분은 FR3의 후순위를 따른다). 발행본 화면에서 Catch의 AI 설명 초안은 'AI 초안'으로 표시해 보여 줄 수 있으며, 'AI 해석' 표시와 구분한다. |
| FR6.6 | AI 호출이 드는 실행(저장소 분석, 기본 요약 생성·다시 만들기, JD 요약)은 계정당 하루 횟수 제한 하나만 둔다. 질의응답은 링크당 하루 질문 횟수 제한 하나만 둔다(접속 주소별 제한 없음). 남은 횟수는 보여 주지 않고 "오늘 한도에 도달했습니다"를 안내한다. 링크 단위 합산과 같은 JD 요약 재사용은 없다. 전체 지출 상한은 Claude API 콘솔에서 설정한다. 제한 값은 개발 담당 결정이며 넉넉하게 둔다. |
| FR6.7 | JD는 별도 JD 관리 페이지에서 로그인 회원이 저장·수정·삭제한다. JD 원본은 저장한 회원의 탈퇴나 본인 삭제 때 지우며, 링크 작성자가 탈퇴해도 다른 회원이 저장한 JD 원본은 남는다. |
| FR6.8 | 기본 요약 생성과 JD 요약 실행은 백그라운드로 처리한다. 브라우저를 닫아도 접수된 처리는 취소되지 않고 나중에 상태·결과·실패 안내를 본다. 멈춘 실행은 처리 시한이 지나면 실패로 바뀐다. 자동 복구·중간 재개·자동 재시도는 없다. 결과 확인 방식(자동 확인 또는 새로고침)은 개발 담당 결정이다. |
| FR6.9 | 세 기능(기본 요약·질의응답·JD 요약) 모두 Claude Haiku 5.5를 쓰고 판정 AI는 두지 않는다. NFR3의 평가 대상은 질의응답이므로, 질의응답이 NFR3 기준을 넘을 때 NFR3의 조정 절차에 따라 지시문 수정 또는 질의응답 기능만의 Sonnet 전환 중 하나를 쓸 수 있다. |

### FR13. 회원이 Claude에서 CatchU 자료를 읽는다

근거: 입력 §3 「Claude MCP」·「대체하는 12월 기준」 FR13.1·13.2·13.3·13.6 행·「재승인 때 함께 정리할 것」 FR13.5, Q119. **FR13.3은 후순위다.**

| ID | 요구사항·수용 기준 |
|---|---|
| FR13.1 | Claude 웹·Desktop은 같은 원격 연결을 쓴다. 최소 OAuth로 연결하며, 자동 갱신 없이 만료되면 다시 승인하고, 연결별 관리 대신 전체 연결 해제를 제공한다. 해제 뒤에는 그 연결의 접근을 막는다. |
| FR13.2 | 구직자 본인: 연결할 때 본인의 공개·비공개 Catch와 현재·이후 저장할 텍스트 자료를 읽게 된다는 것을 한 번 안내하고 동의를 받는다. 도구는 Catch 조회(설명 포함)와 텍스트 자료 조회다. PDF 글은 넣지 않는다. Claude의 개인 대화 맥락을 CatchU로 가져오지 않는다. |
| FR13.3 | **후순위.** 링크를 받은 사람: CatchU에 Google로 가입해 같은 방식으로 연결한다. Claude에 링크 주소를 주면 비밀번호 없는 링크는 웹과 같은 권한으로 읽는다. 비밀번호 있는 링크는 MCP로 읽지 않고 웹에서 보라고 안내하며 비밀번호는 Claude를 거치지 않는다. 도구는 발행본 읽기(PDF 글 포함, 길면 나눠 읽기) 하나이고 호출마다 링크 만료·중지·삭제를 다시 확인한다. 링크 화면에 "Claude에서 분석하기" 버튼(요청 문장 복사와 연결 안내)을 두고, 작성자에게는 발행 때 비밀번호 없는 링크는 받은 사람이 외부 AI 도구로 읽을 수 있다고 안내한다. 링크별 허용 설정은 없다. |
| FR13.5 | MCP로 쓰기·JD 요약·의미 검색은 하지 않는다. 시험은 시험 계정·자료로 허용과 거부를 확인하며, 시험을 위한 권한 우회를 두지 않는다. |
| FR13.6 | 기간별 사용 횟수는 기록하지 않고, 회원 기준으로 짧은 시간의 요청 빈도와 응답 크기만 제한한다. 원격 연결 요청은 Claude 쪽 서버에서 오므로 IP가 아니라 회원 기준으로 센다. 제한 값과 거부를 돌려주는 형태는 개발 담당 결정이다. |

### FR14. 회원이 탈퇴하면 즉시 접근을 막고 자료를 실제로 지운다

근거: 입력 §3 「운영 최소선」·「회원 탈퇴」, §2-4(PR #388, `08822dc2`). 9월 FR14.1·FR14.6 이어받음(탈퇴 방식은 새 입력으로 대체).

| ID | 요구사항·수용 기준 |
|---|---|
| FR14.1 | 로그인한 사용자가 확인창으로 탈퇴를 요청하면 즉시 로그인·링크·MCP 접근을 막고 계정과 자료를 실제로 지운다. DB 밖의 GitHub 자격정보 파일도 지운다. 실패하면 성공으로 응답하지 않고 오류를 보여 주며 팀이 확인한다. 반영과 탈퇴가 겹친 교착으로 탈퇴가 실패한 경우도 같다. 2단계 삭제·실패 기록·재처리는 두지 않는다. |
| FR14.6 | 정상 탈퇴 뒤 같은 Google 계정으로 다시 가입할 수 있으나 이전 자료·링크는 복원하지 않고 신규 기본값과 새 MCP 연결 승인을 적용한다. |
| FR14.8 | 탈퇴는 DB 연쇄 삭제로 처리한다. 회원이나 회원 자료(발행본 포함)를 참조하는 외래 키는 연쇄 삭제(ON DELETE CASCADE)로 만들고, 지우기 거부와 참조 비우기(SET NULL)는 쓰지 않는다. 외래 키를 빠뜨린 표는 시험이 잡지 못하므로 부모 관계는 설계에서 정한다. 한 행이 두 부모를 따라 지워질 때는 두 부모의 주인이 같음을 DB로 묶는다(복합 외래 키). |
| FR14.9 | 표별로 함께 지우는 때: JD 원본은 저장한 회원의 탈퇴·본인 삭제. JD 요약 실행·결과·실행 입력 사본은 발행본 삭제, 작성자 탈퇴, 실행한 회원 탈퇴, 그 JD 삭제 중 하나만 일어나도. 발행본·발행 사본(PDF 사본 포함)·검색 조각·AI 기본 요약은 발행본 삭제, 작성자 탈퇴. 텍스트 자료·PDF 원본(PDF 관련 규칙은 PDF를 둘 때만 적용), MCP 연결, 하루 실행 횟수 기록은 그 회원의 탈퇴(자료는 본인 삭제도). DB 밖 파일(PDF를 S3에 두는 경우 등)은 연쇄 삭제로 지워지지 않으므로 탈퇴·발행본 삭제에서 따로 지운다. |
| FR14.10 | 탈퇴 처리 중이거나 끝난 뒤, 또는 발행본 삭제 뒤 늦게 도착한 AI 결과는 저장하지 않는다. 결과 행이 부모(실행·발행본)를 외래 키로 참조하게 해서, 부모가 지워졌으면 저장이 거부되고 그 거부는 오류로 다시 시도하지 않고 버린다. |

## 비기능 요구사항 (Non-functional requirements)

입력 §2-5: 비기능 기준은 12월 시연 규모(소수 외부 사용자)로 보고 9월 승인 원본보다 높이지 않는다.

| ID | 요구사항·지위 | 수용 기준·후속 조건 |
|---|---|---|
| NFR1 | 권한 일관성·자료 격리 — 필수 | 웹·질의응답·JD 요약·MCP(받은 사람의 Claude 연결 부분은 후순위)에서 같은 링크 조건과 고정 발행본 예외를 적용하고, 회원 자료를 격리하며, 권한 확인과 비밀값 보호를 둔다. FR19.1의 보호 흐름 3개로 확인한다. 시험 전용 우회 권한을 두지 않는다. |
| NFR2 | 외부 AI 처리 — 필수 | 서비스가 호출하는 AI는 Claude API(Haiku 5.5)와 Voyage AI 임베딩이다. NFR3 조정 때는 그 기능(질의응답)만 Sonnet으로 전환할 수 있다. 고지·동의는 FR20을 따른다. [보안 점검](../../../../../../../docs/CatchU_security_checks.md)의 LLM 기준을 그대로 적용하며, 그중 "생성 문장의 사실을 근거와 대조하고 근거에 없는 사실은 확정하지 않는다"는 FR6.4의 기계 대조, 사전 시험으로 정한 모델(FR6.9), NFR3의 사람 확인으로 지킨다. 기계 대조만으로 충족했다고 보지 않는다. Voyage AI의 모델 선택과 자료 보존·학습 사용 조건 확인은 개발 담당 결정이다. |
| NFR3 | 근거 품질 — 필수 | **평가 대상은 질의응답 10개다.** RAG 품질 평가: 시연 발행본 1개에 질문 10개와 정답 근거를 만들어 검색 적중률과 근거 통과율을 스크립트로 한 번 재고 기록한다. 사람이 그 10개에서 근거가 문장을 뒷받침하는지 함께 본다. **통과 기준(Q120):** (a) 남의 기여를 본인 것으로 쓴 항목 0건, (b) 근거가 문장을 뒷받침하지 않는 항목(뜻 뒤집기·역할 부풀림 포함) 질문 10개 전체에서 1건 이하, (c) 맞는데 버려진 항목은 건수만 기록한다. (a)나 (b)를 넘으면 지시문 한 번 수정 또는 질의응답 기능만의 Sonnet 전환 중 하나로 조정하고 한 번만 다시 잰다. 다시 잰 뒤에도 (b)를 넘으면 한계로 기록하고 넘어간다. **(a)는 한계로 넘기지 않는다:** 다시 잰 뒤에도 0건이 아니면 통과가 아니며 팀장이 조정안을 정한다. JD 요약과 기본 요약은 이 통과 기준의 대상이 아니며, JD는 같은 JD 하나로 두 방식(전체 넣기·검색 기반) 결과를 나란히 기록만 한다. 튜닝 반복·CI·AI 채점은 없다. 기계 대조로 거르지 못하는 한계(진짜 근거를 가리키며 남의 일을 본인 것으로 쓰기, 뜻 뒤집기, 역할·성과 부풀리기)는 이 사람 확인으로 본다. 10/24 사전 시험은 한 번 돌린 결과이므로 안전하다는 근거로 쓰지 않는다. |
| NFR4 | 성능·규모 — 시연 규모 | 질의응답은 사람이 기다리는 기능이므로 바로 답하는 경로와 SSE로 처리한다(FR6.2). 수집 상한은 커밋 약 500개 반영을 기준으로 실측한다(FR1.6). 그 밖의 처리 시간·가동률·복구 수치는 새로 만들지 않는다. 다중 조건 검색 성능 기준은 기업 검색 제외로 없앤다. |
| NFR5 | 자료 수명·삭제 — 필수 | 탈퇴는 즉시 실제 삭제한다(FR14). 발행본은 작성자가 직접 삭제하거나 탈퇴할 때까지 남고 자동 파기는 없다. 삭제된 자료를 늦게 도착한 AI 결과가 되살리지 않는다(FR14.10). 9월 OQ11의 자료별 보관 항목·기간 확정 절차는 이 규칙으로 대체한다. |
| NFR6 | 검증 가능성 — 필수 | FR19의 확인 결과 한 표에 실제 결과·실패·미실행을 구분해 남긴다. 기능 사이 실패 시험은 핵심 3개(보호 흐름)만 두고, 동시 요청·재전송·늦은 결과의 기능별 세부 시험은 두지 않는다(입력 §3 「운영 최소선」). 자동 배포·별도 관제 화면은 이 intent에서 만들지 않는다. |
| NFR7 | 이해 가능성 — 필수 | 받은 사람은 고정 발행본·AI 요약·AI 해석·AI 초안·근거 원문의 차이를 화면 표시로 구분할 수 있다(FR2.7·FR6.4·FR6.5). 작성자는 발행 가능 여부와 거부 이유(FR4.1), 저장 실패(FR2.4), 한도 도달(FR6.6), 읽을 수 없는 PDF 쪽(FR3.4)을 구분해 안내받는다. 최소 글자 수·'5분 내 이해' 같은 합격점은 새로 만들지 않는다. |

## 제약 (Constraints)

- C01: 범위·우선순위·단계 승인은 팀장이 결정한다. 11월 범위 결정은 팀 합의나 AI-DLC 단계 승인이 아니라 팀장 결정이며, 받지 않은 팀원 검토·합의를 완료로 기록하지 않는다.
- C02: 기술 기준은 Next.js·NestJS·FastAPI이고 배포 대상은 AWS다. 서비스 AI는 Claude API(Haiku 5.5, NFR3 조정 때 그 기능만 Sonnet 전환 가능), 임베딩은 Voyage AI, PDF 글 추출은 worker의 `pypdf`다. 벡터 저장소 등 세부 구조는 도메인 설계·계약 설계에서 정한다.
- C03: 일정은 위 「지위와 일정」을 따른다. 11월 공수 추정(약 748~751인시)이 가용(672인시)보다 약 48~50인시 많다. 설계가 입력 §3 「11월 진행 방식」의 덩어리 시간을 늘리면 그 사실을 적고 팀장 결정을 받는다(입력 §2-5).
- C04: 12월 전에 10월 데이터를 모두 초기화하고 새 표 관계(FR14.8)로 시작한다. 10월 링크 전환·이관은 하지 않는다. 이 문서는 초기화를 실행하지 않는다.
- C05: 9월 승인 요구사항·사용자 스토리·질문 답·범위 문서의 원본과 감사 기록은 소급 수정하지 않는다. 새 범위의 추적 관계는 재승인 때 다시 검증한다.
- C06: 설계 범위 상한(입력 §2-5): 입력 §2·§3에 근거가 없는 기능·화면·운영 장치·검증 절차는 넣지 않고 질문으로 올린다. 「검토했지만 채택하지 않은 안」과 「프로젝트 목표에서 제외」는 되살리지 않는다. 선택지는 가장 단순한 안을 기본값으로 내고, 더 무거운 안은 무엇을 더 막는지와 늘어나는 공수를 함께 적는다.
- C07: 실행 계획(입력 §2-6): 이 intent는 운영 단계 7개와 인프라 설계·CI 문서를 만들지 않는다. 배포와 CI는 기존 개발 서버 CD·`dev-ci`와 EKS 작업으로 한다. 새 기능에 필요한 공유 인프라·CI 변경(RDS pgvector 확장, SSM 비밀값, `dev-ci` 필수 검사, EKS 반영)은 팀장이 공용 기반 작업으로 맡고, 11/2 전에 로컬·CI·합성 DB 이미지를 pgvector가 든 판으로 바꾸고 새 환경변수 이름을 예시 파일에 넣는다. 각 Unit은 자기 기능의 라이브러리·마이그레이션·로컬 설정을 자기 PR에서 바꾸고, 외부 AI·임베딩은 합성 제공자로 로컬과 시험을 돌린다.
- C08: 진행 방식(입력 §3 「11월 진행 방식」): 팀장이 재승인부터 도메인 설계 → Unit 나누기 → 계약 설계 → 납품 계획까지 이어서 진행한다. 다섯 덩어리(공용 기반 / 발행·링크 / RAG / Claude MCP / 저장소·JD)는 Unit 나누기의 출발안이며, 다른 덩어리의 세부는 "담당 확인 필요"로 남긴다. 구현은 AI-DLC 공식 팀 방식으로 하되, 개발 시작 전 Unit 하나로 맡기 → 진행 → 제출 → 합치기 → `dev` PR까지 시험하고 실패하면 구현만 이슈 → 브랜치 → PR로 바꾼다. 계약에 없는 모양이 필요하면 멈추고 계약 수정 PR로 처리한다.
- C09: 11월 기능 구현은 재승인 뒤에 시작한다. API 명세·ERD는 재승인 뒤 도메인 설계·계약 설계에서 정하고 PR로 반영하며, 이 문서만으로 10월 계약을 바꾸지 않는다. 10월 MVP 작업은 10월 승인 기준과 계약을 따른다.

### 의도 설명의 완료 기준 대조

[의도 설명](../../ideation/intent-capture/intent-statement.md)의 확인 항목에 따라: 입력의 포함·후순위·제외·미결 항목마다 요구사항 또는 처리 결정을 위 두 표에 연결했다. 포함한 요구사항마다 수용 기준을 적었다. 남는 미결(OQ1~OQ5)마다 담당·확정 시점을 적었다. 새 입력에 근거가 없는 요구사항은 추가하지 않았으며, 근거가 직접 없는 판단은 A03처럼 전제로 적어 승인 때 바로잡을 수 있게 했다.
