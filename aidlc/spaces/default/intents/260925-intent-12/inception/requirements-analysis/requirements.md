# CatchU 12월 범위 요구사항

작성일: 2026-09-28. Intent: `260925-intent-12` — 12월 범위 요구사항. Scope: `feature`.

이 문서는 통합 요약의 `Looks correct` 확인을 근거로 작성한 요구사항 산출물이다. **문서 작성 기준 확인은 최종 요구사항 승인·구현 완료·일정 내 구현 가능성 확인이 아니다.** 단계 승인 여부는 공식 상태·감사 기록으로 구분한다.

## 의도 분석 (Intent analysis)

채용 검토자는 시간이 부족해 GitHub 기록을 직접 읽기 어렵다. 작성자는 Catch에 확인 가능한 기록을 담고, 강점 주장의 제목·본문으로 배경·선택 이유·역할 등을 설명한다. 검토자는 우선 자료의 짧은 요약에서 상세 설명과 근거로 들어가며, JD와 질문을 이용해 허용 자료에서 필요한 근거와 확인되지 않은 부분을 구분한다. 서비스는 작성자의 주장이나 기술 사용 기록을 검증된 역량 평가로 바꾸지 않는다.

이번 목표는 MVP 이후 12월 기능의 동작·권한·실패 처리·수용 기준·후속 미결을 하나의 기준으로 정리하는 것이다. 개인 자료 작성 → 고정 공유본 → JD/RAG 검토, 기업 검색 → 제안 → 선택 동의한 연락처 전달, 제품 MCP의 본인 자료/받은 공유본/구직자 탐색 세 흐름을 유지한다. 소셜과 서비스 내 신고의 마감 비필수 변경은 아래에 반영한다.

## 기능 요구사항 (Functional requirements)

각 행의 수용 기준은 구현 완료 주장이 아니라 향후 확인할 사례다. 권한을 잃은 경로의 새 조회를 막는 조건은 웹·JD/RAG·MCP에 일관되게 적용하며, 고정 공유본의 독립 권한 예외를 함께 따른다. 아래 FR1~16·FR19는 별도 표시가 없으면 필수다. FR17은 포함·마감 비필수, FR18은 후순위 포함이다.

### FR1. 회원이 자기 저장소에서 Catch를 준비한다

근거: Q18·90·106~109·116·118, D-M08~10·15, O-S15·18.

| ID | 요구사항·수용 기준 |
|---|---|
| FR1.1 | 12월 로그인은 Google만 제공한다. 로그인 후 GitHub 계정 연결과 분석 동의를 거쳐 자기 자료를 준비한다. 기업 기능도 회원 계정·소속 역할로 이용하며 기업 인증 완료로 표시하지 않는다. |
| FR1.2 | 신규 회원이 개발팀과 사전 협의·저장소 선정을 받지 않고 연결 계정이 소유하거나 커밋한 지원 공개 저장소를 직접 선택·요청한다. 동의·공개 여부·계정과 저장소의 관계·지원 조건·한도를 확인하고 미지원이면 실행 전에 이유를 알린다. 사전 선정 목록만으로 이 경험을 대체하지 않는다. 모든 저장소·무제한 분석을 보장하지 않는다. |
| FR1.3 | 요청 후 진행·완료·실패를 구분하고 본인 결과를 확인할 수 있어야 한다. 확인된 서버 실패에 대한 기존 제한된 사용자 재요청은 유효 결과/등록 카드·진행/복구 상태와 새 동의 등 기존 조건을 확인한다. 조회 시간 초과를 분석 실패로 단정하지 않고 자동 분석 재시도·정상 완료 재분석·부분 결과 추가 생성을 이번 결정으로 추가하지 않는다. 세부 대조는 OQ8을 따른다. |
| FR1.4 | Catch 기록에서 확인한 내용, 작성자 설명, AI 해석을 구분하고 근거를 확인할 수 있게 한다. 타인의 기여를 본인의 것으로 표시하지 않는다. 일반 GitHub 근거 링크와 보류 중인 서비스 내 3층 탐색은 구분한다. |
| FR1.5 | 사용자의 Catch 원본 삭제 기능은 제공하지 않는다. 본인은 공개/숨김 상태를 변경한다. 숨긴 Catch는 현재 프로필·기업 검색·현재 자료 RAG/MCP·새 공유본에서 제공/사용하지 않는다. 숨김 해제 뒤 현재 사용 조건을 다시 적용한다. 관리 확인 및 이미 발행한 고정 공유본은 각각 FR2·FR4를 따른다. |

### FR2. 작성자가 강점 주장을 만들고 대표·추가 자료를 선택한다

근거: C-RA04, Q6-R1·7~13·17~20·35~39. ‘대표 주장 프리셋’은 같은 종류의 주장 작성 단위이며 별도의 검색 프리셋이나 경험 자료 관리 대상을 만들지 않는다.

| ID | 요구사항·수용 기준 |
|---|---|
| FR2.1 | 강점 주장은 제목(어필하려는 강점)·본문(경험/배경/판단/역할 설명)·관련 Catch 선택 구성으로 작성·저장·수정한다. 본문은 Catch만으로 알기 어려운 맥락을 보완한다. 여러 주장을 직접 작성할 수 있지만 모든 Catch에 주장 작성이나 여러 주장 작성을 의무화하지 않는다. |
| FR2.2 | 하나의 주장에 Catch 하나 또는 여러 개를 연결한다. 경험 전체가 한 Catch에 담기면 한 장으로 충분하다. 선택에서 제외하는 것은 연결 해제이며 원본 삭제가 아니다. 연결되었다는 이유만으로 다른 자료를 자동 포함·공개하지 않는다. |
| FR2.3 | 제목/본문/Catch가 미완성인 상태도 비공개 관리용 초안으로 저장·수정할 수 있다. 대표 노출·검색·RAG·새 공유본 이용에는 사용 가능한 Catch가 하나 이상 필요하다. 모두 숨김이거나 연결이 없으면 제목·본문을 포함한 주장 전체를 해당 용도로 사용하지 않고 문구·연결은 관리용으로 보존한다. 일부만 숨김이면 문구는 유지하고 나머지 허용 Catch만 제공한다. 하나 이상 다시 사용 가능해지면 사용 조건을 충족한다. |
| FR2.4 | 새 공유본의 대표 주장 하나와 선택적인 추가 참고 주장을 지정하고 실제 포함될 제목·본문·Catch를 발행 전 확인한다. 선택된 각 주장에는 비어 있지 않은 제목·본문과 실제 수신자 열람 가능한 Catch 최소 1장이 필요하다. 부족하면 보완하거나 해당 주장을 제외하도록 안내한다. 대표 구성을 갖추지 못한 상태는 초안으로 남긴다. |
| FR2.5 | 본문은 짧게 작성할 수 있다. 배경·판단·역할·결과를 각각 필수 입력으로 만들거나 최소 글자 수·품질 점수를 요구하지 않고 빈 본문을 서비스가 임의 생성하지 않는다. 입력 완성과 Catch 한 장 존재를 주장 입증·역량 검증으로 표시하지 않는다. |
| FR2.6 | 작성자는 자신의 관리 정보에서 주장·연결 구성·숨김 상태를 확인하고 연결 변경 또는 숨김 해제를 할 수 있다. Catch 원본 수정은 이를 연결한 현재 주장들이 참고하는 자료에 반영되지만 각 제목·본문·선택 구성은 자동 수정하지 않는다. 발행 전 미리보기에서 현재 문구와 근거를 함께 확인한다. |
| FR2.7 | 검토자는 우선 자료의 짧은 요약으로 경험을 파악한 뒤 설명·주장·Catch 근거를 상세 확인할 수 있다. 초기 노출의 출발 기준이었던 2~3장은 전체 보유/검색 자료 상한이나 발행 최소 2장을 뜻하지 않는다. 여러 주장마다 전부 펼쳐 보이는 방식도 확정하지 않는다. 정확한 수·길이·배치·생성 방식은 OQ1로 남긴다. 프로필 대표 소개 없이도 이 필수 흐름이 성립해야 한다. |

### FR3. 작성자가 서류를 등록하고 공유본별로 선택한다

근거: Q12·21~24, D-M03, 첫 intent FR5.1.

| ID | 요구사항·수용 기준 |
|---|---|
| FR3.1 | 자기소개서는 직접 텍스트 입력·붙여넣기, 포트폴리오는 PDF 업로드 또는 외부 URL 등록, 이력서는 PDF 업로드로 각각 여러 벌 등록하고 공유본별 서류를 선택한다. 서류는 주장 프리셋 밖에서 별도로 선택한다. 구체 파일 규격·용량·수량은 OQ2에서 확정하며 무제한으로 해석하지 않는다. |
| FR3.2 | 공유본에 선택된 텍스트와 PDF는 발행 당시 내용을 보존한다. 외부 URL은 주소만 보존하며 외부 원문으로 이동한다고 구분한다. 외부 페이지 본문까지 고정됐다고 표시하거나 자동 수집하지 않는다. |
| FR3.3 | 12월은 등록 텍스트/PDF의 서비스 안 열람과 허용 AI 참고를 제공한다. 별도 파일 다운로드 기능·링크별 다운로드 허용 설정은 제공하지 않는다. 이를 복사·캡처·파일 저장의 완전 차단으로 표시하지 않는다. |
| FR3.4 | 서비스에서 정상 열람 가능한 PDF는 AI가 읽지 못해도 등록·열람·공유 가능하다. 작성자와 수신자에게 AI 참고 불가를 구분한다. AI가 읽은 것처럼 답하거나 출처로 제시하지 않고 나머지 근거로 답할 때 미검토 범위를 밝힌다. 근거 부족을 경험/역량 부재로 단정하지 않는다. OCR은 추가하지 않는다. |
| FR3.5 | 작성자가 읽기 가능한 파일로 교체해도 기존 공유본은 바뀌지 않는다. 수정본 전달은 새 링크 발행으로 한다. 서류 선택과 AI 참고 선택은 서로 다르며 참고 선택만으로 미공유 자료 접근 권한을 얻지 않는다. |

### FR4. 작성자가 독립된 고정 공유본을 발행하고 수신자가 읽는다

근거: Q2-R1·3·5→18·10·14·19~24·27·88. 링크는 ATS 지원 접수 완료 또는 철회 불가능한 공식 제출이 아니다.

| ID | 요구사항·수용 기준 |
|---|---|
| FR4.1 | 발행 시 선택된 주장의 제목·본문·Catch 연결 구성, 실제 포함 Catch 내용, 선택된 텍스트/PDF와 외부 URL 주소를 고정 공유본으로 보존한다. 이후 원본/초안/프리셋 수정·숨김·원본 서류 삭제는 발행본 내용에 반영하지 않는다. 새 공유본에는 숨긴 Catch를 넣을 수 없고 먼저 숨김 해제가 필요하다. |
| FR4.2 | 유효한 링크의 수신자는 해당 비밀번호·만료·중단 접근 조건을 충족한 뒤 허용 자료를 읽는다. 비로그인 수신자의 기존 열람·JD/RAG 이용을 유지한다. 원본 현재 공개 정책과 독립된 공유본의 권한을 구분하며 같은 링크의 JD/RAG/MCP에도 링크 조건을 적용한다. |
| FR4.3 | 수신자에게 발행 당시 자료를 고정한 공유본임을 알리고 이후 원본 수정·교체·숨김·삭제 사실은 안내하지 않는다. 작성자에게 원본 수정은 비반영, 수정 전달은 새 발행, 기존 제공 중단은 링크 중단이라는 차이를 안내한다. |
| FR4.4 | 수신자는 대표뿐 아니라 공유본에 포함된 추가 자료도 필요할 때 직접 읽는다. 포함하지 않은 주장/Catch/서류는 열람·RAG·MCP로 얻을 수 없다. 사본 보존을 비밀번호·만료·중단·삭제 조건 우회 근거로 삼지 않는다. |
| FR4.5 | GitHub 저장소가 비공개로 전환되어도 이미 발행한 공유본과 해당 공유본의 RAG 자료는 유지한다. 작성자가 링크 중단/공유본 삭제로 제공을 끝내도록 안내한다. 원본 기반 현재 자료의 보호 규칙은 유지한다. GitHub 조회 실패를 비공개 전환으로 단정하거나 보존 Catch를 현재 GitHub 원문 확인으로 표시하지 않는다. |

### FR5. 작성자가 공유본 접근과 보관·삭제를 관리한다

근거: Q25~27·82~88·92·114.

| ID | 요구사항·수용 기준 |
|---|---|
| FR5.1 | 만료되거나 작성자가 중단한 링크는 수신자의 열람·JD/RAG/MCP 접근을 막는다. 만료·중단된 링크는 되살리지 않는다. 보관 중인 발행 당시 내용은 작성자가 다시 확인할 수 있으며 수신자 접근은 계속 차단한다. |
| FR5.2 | 작성자가 본인 공유본을 직접 삭제하면 링크를 사용할 수 없고 작성자도 발행 내용을 다시 볼 수 없다. 원본 자료와 다른 공유본은 유지한다. 삭제된 내용을 이전 요약·RAG·MCP의 새 조회로 다시 제공해서는 안 된다. |
| FR5.3 | 만료·중단 시점부터 정한 기간 보관한 뒤 자동 파기한다. 작성자에게 보관 종료 시점을 안내하고 보관 중 확인/직접 삭제를 허용한다. 기간은 과거 지원 확인 필요·저장 비용을 검토해 관련 개발 전에 확정한다(OQ3). 회원 탈퇴에는 이 일반 보관 기간을 자동 적용하지 않는다(FR14). |
| FR5.4 | 발행 시의 기본 접근 조건은 실제 만료 시점을 확인할 수 있어야 한다. 만료일 선택·유효 링크 연장·발행 후 비밀번호 변경 등의 추가 편의는 FR17.11을 따르며 필수로 올리지 않는다. 기본 기간의 미정값을 과거 기간이나 무기한으로 임의 확정하지 않는다. |

### FR6. 수신자가 JD와 질문으로 허용 자료를 검토한다

근거: Q10~16·21~24·62~63·112·117, D-M04, 기존 승인 JD 제한.

| ID | 요구사항·수용 기준 |
|---|---|
| FR6.1 | 수신자는 JD를 직접 입력해 한 장 요약·현재 자료의 사이드 패널·질의응답에 반영한다. 패널에는 현재 보고 있는 자료와 관련된 JD 대목을 제시하고 관련 근거가 없으면 같은 JD 요약의 해당 항목을 안내한다. 다른 서류 근거를 현재 자료의 근거처럼 섞지 않는다. JD 매칭 %와 패널의 개수·비율·색상 종합 평가를 추가하지 않는다. |
| FR6.2 | 수신자가 프리셋을 따로 고르지 않아도 질문을 시작할 수 있다. AI는 공유본의 허용 자료에서 질문 관련 근거를 찾고 필요한 경우 여러 주장에 연결된 자료를 함께 사용한다. 모든 자료를 매 답변에 사용하거나 실제 확인한 범위 이상을 검토했다고 표현하지 않는다. 수신자 프리셋별 수동 범위 조절은 후보로 남긴다. |
| FR6.3 | 포함·접근 허용·AI 읽기 가능 조건을 모두 충족한 서류는 기본 참고 대상이다. 수신자는 필요하면 특정 서류를 제외할 수 있다. 현재 참고 대상과 참고 불가 자료를 구분하며 외부 URL 본문·읽기 실패 PDF는 참고하지 않는다. 이 선택은 자료 내용이나 열람 권한을 변경하지 않는다. |
| FR6.4 | 답변은 기록에서 확인되는 내용, 작성자가 설명한 목표/판단/역할/결과, AI의 해석을 구분한다. 사용한 주장·Catch·서류의 실제 확인 가능한 출처를 제시하고 확인되지 않은 부분을 밝힌다. 자료가 없다는 이유로 경험이나 역량이 없다고 단정하지 않는다. |
| FR6.5 | 서류 주장과 작성자가 미리 연결하지 않은 경험/Catch 사이의 관련성도 허용 자료에서 ‘AI가 제안한 연결 후보’로 제시할 수 있다. 주장 중 어느 부분과 어떤 구체 내용/출처가 관련되는지, 확인되는 부분과 한계를 설명한다. 작성자 명시 연결과 구분하고 입증 완료로 표시하거나 저장된 연결을 자동 변경하지 않는다. 키워드 유사성만으로 후보를 억지로 만들지 않는다. 후보가 없으면 현재 자료에서 근거를 못 찾았다고 답하고 후속 질문을 제안한다. |
| FR6.6 | 같은 링크의 CatchU JD/AI 호출은 제공 경로와 무관하게 기존 링크 단위 한도로 합산하며, 경로나 MCP 연결을 바꿔 한도를 새로 얻거나 초기화하지 않는다(Q62·Q117). 이는 MCP에 새로운 CatchU AI 실행 기능을 추가하는 결정이 아니다. 기존 JD 요약은 현재 접근 권한·참고 선택·고정 공유본 조건을 만족하는 경우에만 재사용한다. 새 AI 호출 한도 소진 시 새 호출은 제한하되 유효한 기존 요약/원문 열람은 유지한다. 동일 JD 판정·재사용 유효 조건·기록 범위는 OQ9에서 사례로 확정한다. 다른 수신자의 JD/질의 내용을 공유하지 않는다. 재방문 이어보기·별도 이력·기업 내 질의 공유를 이 요구사항으로 추가하지 않는다. |

RAG의 과제별 수용 기준은 다음과 같다. 이는 검색 품질이 현재 검증됐다는 뜻이 아니다.

| 검토 질문 | 필요한 자료·답할 수 있는 내용 | 한계·출처·수용 기준 |
|---|---|---|
| 이 프로젝트에서 본인이 맡았다고 설명한 일과 기록은? | 주장 본문에 적힌 역할과 관련 Catch 기록 | 자기 설명과 기록 확인을 분리하고 관련 출처를 각각 제시한다. 기록만으로 확인 못 한 책임 범위를 추정 사실로 쓰지 않는다. |
| 기술적 선택 이유와 당시 제약은? | 작성자가 적은 이유/제약과 관련 변경 근거 | 기록에 없는 의도는 모른다고 구분한다. AI 해석이면 해석임을 밝히고 질문할 점을 제시한다. |
| 문제 해결 경험과 확인 가능한 결과가 있는가? | 문제·수행·결과 설명, Catch 및 허용 서류 | 측정하지 않은 성과 수치를 만들지 않는다. 결과가 자기 설명인지 기록인지 나눠 출처를 붙인다. |
| 서류 주장에 어떤 경험·Catch가 연결되는가? | 읽을 수 있는 선택 서류, 명시 연결 또는 관련 후보 | FR6.5대로 후보와 확정 연결을 구분하고 입증으로 표시하지 않는다. 읽기 실패 서류는 읽은 것처럼 다루지 않는다. |
| 면접에서 더 물어볼 것은? | 위 자료에서 남은 확인 공백 | 자료 범위의 공백과 질문 이유를 제시하며 역량 부족 판정으로 바꾸지 않는다. |
| 전체 자료를 요약하면? | 실제 참고 가능한 공유 자료와 검토 범위 | 특정 질문의 일부 근거만 확인한 결과를 전체 검토로 표시하지 않는다. 미참고/참고 불가 범위를 구분한다. |

### FR7. 기업 회원이 소속과 업무 권한을 관리한다

근거: Q28~31·64~67·94·105.

| ID | 요구사항·수용 기준 |
|---|---|
| FR7.1 | 로그인 회원이 기업명(필수)·웹사이트(선택)로 기업을 직접 등록하고 최초 기업 관리자가 된다. 기업 관리자와 CatchU 운영자를 구분한다. 등록/최초 관리자/소속 승인만으로 실제 기업·실제 소속 인증을 표시하지 않는다. 상세 회사 프로필을 등록 조건으로 요구하지 않는다. |
| FR7.2 | 다른 회원은 소속을 신청하고 기업 관리자가 승인한 뒤 권한을 얻는다. 승인 전에는 소속 자료/기능 권한이 없다. 초대·수락 경로는 추가하지 않는다. 승인 시 검토자를 기본 역할로 제시하되 관리자가 확인·변경한다. 신청자가 역할을 확정하지 못한다. |
| FR7.3 | 역할을 아래 표대로 부여·변경한다. 직급/직함이 아닌 업무 권한이며 개인별 조합 생성은 제공하지 않는다. 역할만으로 모든 후보자 자료를 읽을 수 없고 자료 접근·검색 참여·해당 기능의 차단 조건을 별도 적용한다. |
| FR7.4 | 본인 소속 해제와 관리자의 회원 소속 해제를 허용하고 해당 소속의 권한을 중단한다. 마지막 관리자의 일반 소속 해제·강등은 다른 관리자 확보 후 허용한다. 마지막 관리자 탈퇴의 기업 종료 경로는 FR14.3, 운영 제한 중 정리는 FR15를 따른다. |
| FR7.5 | 기업 소속이나 제안 가능한 역할을 잃은 발송자의 미응답 제안은 수신자가 읽고 거절할 수 있지만 수락할 수 없다. 같은 기업의 제안 가능한 자격을 회복하면 현재 조건으로 수락 가능하다. 연락처 공유 권한은 자동 복원하지 않는다. 관리자↔채용 담당자 변경은 제안 역할 상실로 보지 않는다. |

| 역할 | 허용 업무 | 허용하지 않는 업무 |
|---|---|---|
| 기업 관리자 | 소속·권한 관리, 허용 자료 검토·기업 검색·제안 | 운영자 권한, 자격만으로 비허용 후보자 자료 접근 |
| 채용 담당자 | 허용 자료 검토·기업 검색·제안 | 소속·권한 관리 |
| 검토자 | 허용 자료 열람·JD·RAG 검토 | 기업 검색·제안, 소속·권한 관리 |

### FR8. 작성자가 공개 대표와 기업에 보여 줄 다른 강점을 정한다

근거: Q32·48·69~72→77·80·81.

| ID | 요구사항·수용 기준 |
|---|---|
| FR8.1 | 개인 프로필에는 작성자가 대표 지정한 주장 1개의 제목·본문·연결된 허용 Catch를 전체 공개한다. 대표에 전체/맞팔 선택을 두지 않는다. 다른 주장이나 연결되지 않은 Catch를 자동 공개하지 않는다. 숨김/주장 사용 조건은 유지한다. |
| FR8.2 | 기업 검색 참여는 기본 OFF로 두고 명시 동의한 구직자만 새 발견 대상으로 삼는다. 검색 대표에 비어 있지 않은 제목·본문과 사용 가능한 Catch 최소 1장을 요구한다. 미충족이면 검색에서 제외하되 동의와 초안을 유지하며 다시 충족하면 기존 동의에 따라 노출한다. |
| FR8.3 | 추가 주장은 기본 기업 열람 미허용이며 작성자가 주장별로 허용·철회한다. 철회 후에는 이전 열람 여부와 무관하게 해당 경로의 새 조회를 막는다. 웹 검색과 MCP에 동일하게 적용한다. 개인 공개 대표와 이미 발행한 고정 공유본의 정책은 바뀌지 않는다. |
| FR8.4 | 기업 권한·검색 참여·자료 조건을 충족하면 공통 대표뿐 아니라 기업 열람 허용된 추가 주장과 연결 Catch도 검색 판정과 열람에 사용한다. 추가 자료 열람 전 제목과 ‘무료로 열람’ 안내, 열람 후 본문과 연결된 허용 Catch를 제공한다. 현재 테스트 서비스는 마일리지 차감 없이 제공하지만 작성자 허용/기업 권한을 생략하지 않는다. 가격·차감·열람 기간 BM은 후속이며 마일리지 구현은 비필수다. |

### FR9. 기업이 조건과 근거를 구분해 구직자를 검색한다

근거: Q54~56·69~72·77 후속·80~81·109.

| ID | 요구사항·수용 기준 |
|---|---|
| FR9.1 | 허용된 프로필 자가 입력 직무·기술과 Catch 기록으로 확인되는 사용 기술을 구분해 조건으로 사용한다. Catch 기술은 최소 필수 사실 필터다. 서로 다른 조건과 조건 안에서 선택한 여러 기술을 모두 충족해야 한다. 같은 구직자의 검색 허용 Catch 여러 장에 나뉜 근거도 가능하되 동일 프로젝트에서 함께 썼다고 표시하지 않는다. 나머지 검색 속성은 OQ5를 따른다. |
| FR9.2 | 자유 문자열은 공백으로 나눈 단어가 모두 허용 검색 항목에 있으면 일치한다. 서로 다른 항목에 있어도 되며 앞뒤 공백·영문 대소문자를 구분하지 않는다. 주장 제목·본문은 보조 문자열 대상이며 허용 Catch의 기존 제목·한 일 등 검색 항목과 출처를 구분한다. 비공개 자료나 서류 전체를 검색 대상으로 자동 확장하지 않는다. |
| FR9.3 | 일치 항목과 출처를 구분해 보여 주고 대표 본문과 연결된 허용 Catch를 상세 확인할 수 있게 한다. 추가 주장 본문·근거는 FR8.4의 열람 조건을 따른다. 문자열 일치를 Catch 사실 근거로, 기술 사용을 숙련도로 표시하지 않는다. 근거 없는 기술을 사용할 줄 모른다고 판정하지 않으며 결과 없음과 조회 실패를 구분한다. 유사도·일치 개수 순위·자동 조건 완화·추천을 추가하지 않는다. |
| FR9.4 | 필수 기술 필터에서 실제로 확인된 동일 기술의 표기 차이는 최소 대응 처리한다. 필요한 기술부터 근거 있는 대응표를 확정하고 미확인 표기를 임의로 합치지 않는다. 프로필 자가 입력과 Catch 사실 출처는 계속 구분한다. 별도 관리 화면·의미 검색·숙련도 평가는 추가하지 않는다. |

### FR10. 기업이 제안을 보내고 구직자가 응답한다

근거: Q32~33·40~42·45·47~53·67·101~102·105.

| ID | 요구사항·수용 기준 |
|---|---|
| FR10.1 | 새 제안 수신은 기본 OFF, 명시 허용 후 수신 가능하다. 검색 참여와 독립 설정이며 한 설정이 다른 설정을 자동 변경하지 않는다. 검색 참여를 켤 때 현재 수신 상태를 안내하고 별도 허용할 수 있게 한다. 수신 허용만으로 자료 접근이나 새 발견 경로를 주지 않는다. |
| FR10.2 | 12월 제안 시작 경로는 기업 검색으로 한정한다. 제안 가능한 기업 역할·기업 상태·대상의 수신 설정·차단·반복 제한 등 현재 조건을 확인해 포지션/JD/제안 사유를 전달한다. 공유 링크의 새 제안 기능은 추가하지 않는다. 링크 수신자는 기존 ATS/직접 전달의 채용 경로로 후속 연락할 수 있다. |
| FR10.3 | 반복 제한 단위는 발송 회원 계정–구직자 계정 쌍이다. 미응답이 있어도 정한 기간·횟수 안에서는 추가 제안 가능하다. 같은 기업 다른 발송자 건수는 합산하지 않는다. 직전 기간의 실제 전달 건수를 JD/포지션·응답·취소 여부와 관계없이 합산하며 차단 해제나 날짜 경계로 초기화하지 않는다. 실패/미전달 및 같은 요청의 중복 처리를 새 전달 건수로 세지 않는다. 한도 도달 시 이유를 안내하고 거부한 발송을 대기·자동 전달하지 않는다. 제한은 기존 제안 읽기·응답을 막는 용도로 확대하지 않는다. 값은 OQ4에서 확정한다. |
| FR10.4 | 이미 받은 미응답 제안은 읽고 수락·거절할 수 있다. 전체 새 수신 OFF만으로 기존 수락·거절을 막지 않는다. 상대 차단·발송자 자격·기업/계정 운영 제한은 별도로 적용한다. 수락만으로 연락처를 공개하거나 DM을 필수로 만들지 않는다. |
| FR10.5 | 구직자는 수락을 취소할 수 있다. 취소 전 같은 제안의 재수락 불가와 새 제안 필요를 안내하고 취소 후 해당 제안 기반 연락처 공유·조회를 중단한다. 재진행은 기업의 조건 충족 새 제안과 새 수락이 필요하다. 자동 재제안·재수락·연락처 복원은 없다. 취소는 계정 차단이나 외부 ATS 전형 취소가 아니다. |
| FR10.6 | 원래 발송자는 자기 미응답 제안을 철회할 수 있다. 구직자의 거절과 구분하고 응답된 제안은 변경하지 않는다. 현재 소속/역할 조건 및 FR15의 제한 중 정리 예외를 적용한다. 수락·철회가 경합하면 먼저 성립한 결과를 기준으로 중복 상태 변경을 막고 실제 결과를 안내한다. 철회 복원·별도 알림을 추가하지 않는다. |
| FR10.7 | 12월에는 미응답 제안 자동 만료를 제공하지 않는다. 응답 시 현재 조건을 판정한다. 기존 제안·응답 기록은 자료별 보존 정책에 따르며 자동 만료 미제공을 영구 보관이나 채용 의사 지속 보장으로 표시하지 않는다. |

### FR11. 이용자가 특정 계정의 연락을 차단한다

근거: Q34 후속·40~42·44. 차단은 연락 제한이며 상대를 서비스에서 보이지 않게 만드는 기능이 아니다.

| ID | 요구사항·수용 기준 |
|---|---|
| FR11.1 | 특정 회원 계정을 차단하면 해당 상대의 새 제안·DM을 막는다. 같은 기업의 다른 계정에 자동 적용하지 않고 소속/역할 변경만으로 해제하지 않는다. 구직자 간에도 같은 계정 단위 기준을 적용하되 DM의 비필수 지위를 유지한다. |
| FR11.2 | 차단한 사람도 상대에게 새 제안·DM을 보내려면 자기 차단을 명시 해제해야 한다. 발송 행동만으로 자동 해제하지 않는다. 해제해도 상대 차단이나 다른 발송 조건이 불충족이면 발송하지 않는다. |
| FR11.3 | 차단한 상대에게 이미 받은 미응답 제안은 읽고 거절할 수 있다. 수락 전에는 자기 차단 해제가 필요하며 수락 행동으로 해제하지 않는다. 거절 허용을 새 발송 허용으로 확대하지 않는다. |
| FR11.4 | 차단 중 보내지 못한 제안·DM을 대기·자동 전달하지 않는다. 해제 후 새 시도에 현재 권한·수신·차단·반복 제한을 적용한다. 기존 전달 기록은 차단만으로 삭제하지 않는다. |
| FR11.5 | 차단만으로 기업 검색·프로필·포스팅·Catch 노출·피드·팔로우/맞팔 관계·고정 공유 링크·기존 권한에 따른 JD/RAG/MCP 이용을 제한하지 않는다. 별도 연락처 공유는 FR12의 중단 조건을 따른다. |

### FR12. 구직자가 수락 후 선택한 연락처를 특정 회원에게 전달한다

근거: Q43~46·94·98~100·105. 일회 전달 의미와 서비스 안 조회 중단을 함께 적용한다.

| ID | 요구사항·수용 기준 |
|---|---|
| FR12.1 | 제안을 수락한 구직자는 이메일·전화번호 중 원하는 항목과 실제 제공할 값을 확인·선택해 별도 동의한다. 두 항목 모두의 등록/공유를 요구하지 않고 로그인 계정의 연락처를 자동 공개하지 않는다. 수신자는 동의한 특정 기업 회원이며 같은 기업의 다른 회원/관리자에게 확대하지 않는다. |
| FR12.2 | 선택·동의한 당시 값을 고정해 기존 제안 상세에서 수신자가 확인한다. ‘전달 당시 연락처’임을 안내하며 원본 수정으로 과거 값이나 조회 권한을 자동 변경하지 않는다. DM 없이 이용 가능해야 하며 별도 이메일/SMS/DM 전달 수단을 추가하지 않는다. |
| FR12.3 | 어느 쪽의 차단, 해당 제안 수락 취소, 수신자의 해당 기업 소속/제안 가능 역할 상실, 기업 종료·해당 탈퇴·운영 제한 시 관련 새 공유와 기존 연락처 조회를 중단한다. 관리자↔채용 담당자 변경만으로 중단하지 않는다. 이 조치는 연락처 기능의 권한에 한정하며 원본이나 다른 상대 공유를 바꾸지 않는다. |
| FR12.4 | 차단 해제·자격 회복·운영 해제·새 제안 수락만으로 이전 권한을 복원하지 않는다. 다시 공유하려면 현재 자격을 확인하고 구직자가 제공할 항목·값을 확인해 재동의한다. 동의한 새 전달 당시 값만 제공하며 과거 값/현재 원본을 자동 공개하지 않는다. |
| FR12.5 | 구직자는 기존 제안 상세에서 해당 제안으로 공유한 연락처 전체의 조회를 중단할 수 있다. 제안 수락·차단 상태, 원본 연락처·다른 상대 공유는 유지한다. 재공유는 FR12.4를 따른다. 이메일/전화번호별 개별 중단은 이번 필수 범위에 넣지 않는다. |
| FR12.6 | 기존 제안/대화 기록·고정 공유본을 이 중단만으로 수정·삭제하지 않는다. 이미 복사·저장한 값을 회수한다고 표시하지 않으며 허용 서류/고정 공유본에 적힌 연락처 자동 가림도 추가하지 않는다. 과거 전달 값의 내부 보관과 실제 조회 항목은 OQ11의 목적·근거·기간을 따른다. |

### FR13. 회원이 외부 도구에서 제품 MCP를 사용한다

근거: Q57~63·80·105·115, D-M08·09. 다음 세 흐름 모두 필수다.

| ID | 요구사항·수용 기준 |

## 제약 (Constraints)

- C01: 본 문서의 범위/우선순위·후속 제품 결정과 단계 승인은 팀장이 최종 결정한다. 팀원 검토는 이후 공유 때 하며 수행하지 않은 합의를 기록하지 않는다.
- C02: 현재 기술 기준은 Next.js·NestJS·FastAPI, 배포 NCP다. 세부 구조나 최적화 도입은 이 단계에서 확정하지 않는다.
- C03: 11월 30일 필수 완료, 12월 1~9일 검증·수정·제출 준비, 12월 10일 공식 제출을 유지한다. 실제 인력·가용 시간·개발량으로 일정 충돌이 확인되면 필수 항목 간 우선순위와 범위 대안을 제시해 결정받는다.
- C04: 오픈 전 서비스이며 유지해야 할 기존 운영 사용자/링크를 가정하지 않는다. 이후 배포 준비에서 개발·테스트 데이터 초기화 대상을 확인해 새 고정 공유본 정책 하나로 시작한다. 지금 데이터 삭제를 실행하지 않고 구형 링크 병행/이관 기능을 추가하지 않는다.
- C05: 과거 승인 원본은 보존하고 이번 명시적 정정은 질문·답변 이력 및 본 문서에 연결한다. 기존 목표·후보를 달성 결과/개발 약속으로 승격하지 않는다.
- C06: 미결의 세부 확정이 필수 기능 개발을 무기한 막는 대기 사유가 되지 않게 관련 착수 전에 책임과 근거를 확인한다. 필수 의존성이 발견돼도 해당 비필수 기능 전체를 자동 필수화하지 않는다.
- C07: 이번 작업은 한국어 로컬 문서 작업이다. 최종 요구사항 승인 직후 공식 park하고 전체 intent를 complete로 하지 않는다. 검증 후 관련 변경만 로컬 커밋한다. 푸시·PR·원격 이슈·Claude 설치·도메인/API/ERD/구현은 수행하지 않는다.
